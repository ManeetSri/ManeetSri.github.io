## Why it matters

The same app runs on a 6-inch phone, a 13-inch iPad, a resizable Stage Manager window, a Mac and Apple Vision Pro, and on iPad its width can change while the user is in the middle of something: they drag Safari alongside it and your three columns become one. Navigation that was designed as "a stack of screens" breaks there; navigation designed as "a selection the layout displays" adapts for free. Interviewers ask "how does this work on iPad?" precisely because it exposes whether your navigation state is tied to one layout.

## One app, many widths

SwiftUI and UIKit describe the space they have with **size classes**: each axis is `compact` or `regular`. What matters for navigation is the horizontal one.

| Where | Horizontal size class |
| --- | --- |
| iPhone in portrait; most iPhones in landscape | compact |
| The largest iPhones in landscape | regular |
| iPad full screen, or the larger side of Split View | regular |
| iPad in Slide Over, or the narrow side of Split View | compact |
| A Stage Manager window | either, and it changes as the user resizes it |

So the honest requirement is not "an iPhone layout and an iPad layout". It's **one navigation state that can be shown at any width, and moved between widths at any moment**. Apple's containers are built for exactly that, if your state lets them.

## NavigationSplitView: columns that collapse

`NavigationSplitView` shows two or three columns: a **sidebar**, an optional **content** column, and a **detail**. Navigation between columns isn't pushing; it's **selection**. Choosing a department in the sidebar sets a selection, the content column shows that department's products, and choosing a product sets a second selection the detail column shows.

In compact width the same split view **collapses into one stack**: the sidebar is the root, and each selection pushes the next column. Back clears the selection. You write one view; the layout follows the width.

Here's that browser. The model holds the selections and the detail column's own path; the views only display them.

```swift check ios title="BrowseView.swift"
import SwiftUI

struct Department: Identifiable, Hashable {
    let id: String
    let name: String
}

struct Product: Identifiable, Hashable {
    let id: Int
    let name: String
    let departmentID: String
}

enum ProductRoute: Hashable, Codable {
    case reviews(productID: Int)
    case sizeGuide(productID: Int)
}

@MainActor @Observable
final class BrowseModel {
    let departments = [Department(id: "shoes", name: "Shoes"), Department(id: "bags", name: "Bags")]
    let products = [
        Product(id: 7, name: "Trail runners", departmentID: "shoes"),
        Product(id: 8, name: "Canvas tote", departmentID: "bags"),
    ]

    // Selections are the navigation state. Changing one resets what depended on it.
    var departmentID: Department.ID? {
        didSet { if departmentID != oldValue { productID = nil } }
    }
    var productID: Product.ID? {
        didSet { if productID != oldValue { detailPath = [] } }
    }
    /// Screens pushed inside the detail column, such as reviews for the selected product
    var detailPath: [ProductRoute] = []

    var productsInDepartment: [Product] {
        products.filter { $0.departmentID == departmentID }
    }
}

struct BrowseView: View {
    @State private var model = BrowseModel()
    // Which column is on top when collapsed; the sidebar is a better start on iPhone than an empty detail
    @State private var compactColumn = NavigationSplitViewColumn.sidebar

    var body: some View {
        NavigationSplitView(preferredCompactColumn: $compactColumn) {
            List(model.departments, selection: $model.departmentID) { department in
                Text(department.name)
            }
            .navigationTitle("Shop")
        } content: {
            List(model.productsInDepartment, selection: $model.productID) { product in
                Text(product.name)
            }
        } detail: {
            // The detail column owns one stack for drilling further into the selected product
            NavigationStack(path: $model.detailPath) {
                Group {
                    if let id = model.productID {
                        Button("Reviews") { model.detailPath.append(.reviews(productID: id)) }
                    } else {
                        ContentUnavailableView("Choose a product", systemImage: "bag")
                    }
                }
                .navigationDestination(for: ProductRoute.self) { route in
                    switch route {
                    case .reviews(let id): Text("Reviews for product \(id)")
                    case .sizeGuide(let id): Text("Size guide for product \(id)")
                    }
                }
            }
        }
    }
}
```

Three design choices in there are the lesson:

- **Selections, not pushes, between columns.** `List(_:selection:)` in a split view column drives the next column at regular width and pushes it at compact width. A `NavigationLink(value:)` in those lists sets the selection too.
- **Dependent state resets with its parent.** Choosing another product clears `detailPath`; choosing another department clears the product. Without those two `didSet`s, a user who opened reviews for the trail runners and then tapped a tote would see the tote's detail with the trail runners' reviews pushed on top of it.
- **Deeper navigation lives in the detail column's stack.** The split view handles the two levels of hierarchy; a `NavigationStack` inside the detail handles anything below the product. That's the one place a stack inside another container is right: one stack per column.

## TabView in iOS 18: tabs that become a sidebar

Split views suit **one hierarchy** browsed with a persistent list: mail, notes, files, settings. Many apps instead have **a few parallel places**: Home, Search, Basket, Account. iOS 18 rebuilt `TabView` for those apps:

- **`Tab` values** with a selection value each, replacing `.tabItem`.
- **`.tabViewStyle(.sidebarAdaptable)`**: an ordinary tab bar on iPhone; on iPad a compact tab bar at the top that the user can expand into a sidebar. On the Mac it's a sidebar.
- **`TabSection`** groups tabs under a heading in the sidebar, for secondary places such as departments or collections that would crowd a tab bar.
- **Customisation**: with `customizationID` and `TabViewCustomization`, users can reorder and hide tabs, and the app can save their choices.

```swift check ios title="ShopTabs.swift"
import SwiftUI

enum ShopSection: Hashable {
    case home, search, basket, department(String)
}

struct ShopTabs: View {
    @State private var selection: ShopSection = .home
    @AppStorage("shop.tabs") private var customization: TabViewCustomization

    var body: some View {
        TabView(selection: $selection) {
            Tab("Home", systemImage: "house", value: ShopSection.home) {
                Text("Home")   // each tab's content is its own NavigationStack in the real app
            }
            .customizationID("home")

            Tab("Basket", systemImage: "bag", value: ShopSection.basket) {
                Text("Basket")
            }
            .customizationID("basket")

            Tab(value: ShopSection.search, role: .search) {
                Text("Search")
            }

            // Secondary places: in the sidebar, hidden from the iPhone tab bar
            TabSection("Departments") {
                ForEach(["shoes", "bags"], id: \.self) { slug in
                    Tab(slug.capitalized, systemImage: "tag", value: ShopSection.department(slug)) {
                        Text(slug.capitalized)
                    }
                    .customizationID("department.\(slug)")
                }
            }
            .defaultVisibility(.hidden, for: .tabBar)
        }
        .tabViewStyle(.sidebarAdaptable)
        .tabViewCustomization($customization)
    }
}
```

Notice the selection type. `ShopSection` has a case with a value, `.department("shoes")`, so a deep link to a department can select its sidebar entry directly. Selection is navigation state like any other: a deep link sets it, restoration saves it.

Each tab keeps its own `NavigationStack` and path, exactly as each tab owns a `UINavigationController` in UIKit. A tab's content can itself be a `NavigationSplitView`, which is how an app with a few top-level places can still show a list and detail side by side inside one of them on iPad.

## UIKit: the split view controller

`UISplitViewController(style: .doubleColumn)` or `.tripleColumn` (iOS 14) works the same way, with `setViewController(_:for:)` for `.primary`, `.supplementary` and `.secondary`. Two extra controls are worth knowing:

- **A separate compact tree.** `setViewController(_:for: .compact)` gives compact width an entirely different hierarchy, say a tab bar controller, instead of collapsing the columns. It's flexible, and it doubles the navigation state you must keep in step when the width changes.
- **Choosing what shows after collapsing.** By default the collapsed stack shows the secondary column. If nothing is selected that's an empty screen on an iPhone, so the delegate returns the primary column instead:

```swift check ios title="Collapsing to the sidebar when nothing is selected"
import UIKit

final class BrowseSplitDelegate: NSObject, UISplitViewControllerDelegate {
    var hasSelection: () -> Bool = { false }

    func splitViewController(_ svc: UISplitViewController, topColumnForCollapsingToProposedTopColumn proposedTopColumn: UISplitViewController.Column) -> UISplitViewController.Column {
        hasSelection() ? proposedTopColumn : .primary
    }
}
```

## Designing state that survives any width

Every example above follows one rule: **navigation state describes what the user chose, never how it's laid out.** In practice:

- Store **selections and paths**, not "is the detail visible" or "which column is on top". Visibility is derived from width and selection.
- Keep **one model per window**, shared by every layout. Separate compact and regular state goes out of step the first time the width changes mid-task.
- Make every selection **an id**, so a deep link or a restored snapshot can set it without the screens existing yet.
- **Test the collapse.** Run on an iPad, open a product's reviews, drag another app alongside, then back. Most adaptive bugs show up in that thirty-second test.

## Trade-offs

| | Tab bar | `sidebarAdaptable` TabView | NavigationSplitView | Tabs containing split views |
| --- | --- | --- | --- | --- |
| Best for | 3–5 parallel places | parallel places, plus secondary ones in a sidebar on iPad | one deep hierarchy browsed from a list | a few places, one of them a list and detail |
| iPad use of space | poor: a phone layout, stretched | good | very good | good |
| State to manage | selected tab + a path per tab | the same, plus customisation | selections + a detail path | all of the above |
| Compact width | as is | becomes a tab bar | collapses to one stack | each tab's split view collapses |
| Examples | most shopping and social apps on iPhone | Music, TV, Podcasts on iPad | Mail, Notes, Files, Settings | a shop whose Browse tab shows departments beside products |

A phone-first app with a few places starts with tabs, and `sidebarAdaptable` makes the iPad version respectable for one modifier. An app that *is* a hierarchy (a mailbox, a document library) is a split view at the root. Combine them when one of your places is itself a hierarchy worth seeing side by side.

<Callout kind="interview">

**What to say:** "Navigation state is selections and paths, per window, independent of layout. On iPad the Browse tab is a split view driven by the selected department and product; at compact width it collapses into a stack from the same state, so resizing loses nothing." Mention `sidebarAdaptable` for the tabs, and that changing a selection resets the state that depended on it.

**What to ask:** is iPad a priority, or a scaled-up phone? Should the app support several windows (each then has its own navigation)? Is the content one hierarchy or several parallel places?

**Red flags:** `if horizontalSizeClass == .regular` choosing between two navigation trees with separate state; a phone-only stack stretched across an iPad; storing "which column is visible"; forgetting to reset the detail path when the selection changes.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: don't wrap a split view in a stack">

`NavigationSplitView` manages its own stacks: it collapses into one on compact width. Putting it inside a `NavigationStack`, or pushing a split view onto a stack, gives you nested stacks, doubled bars and broken collapse. A split view belongs at the root of a window or a tab, with at most one `NavigationStack` per column inside it.

</Callout>
