## Why it matters

`NavigationStack` turned SwiftUI navigation from something views *do* into something your code *holds*: the stack is an array of values, and changing the array changes the screens. That one change is what makes deep links, restoration, pop-to-root after a purchase, and tests of navigation possible. It also brings new ways to fail: destinations registered in the wrong place, paths that can't be saved, and view models recreated on every update. "How does navigation work in your SwiftUI app?" is now a standard interview question, and "the path is a value I own" is the start of a good answer.

## From views that push to values that push

Before iOS 16, SwiftUI used `NavigationView`, and a link carried the view it would push: `NavigationLink(destination: ProductScreen(id: 7))`. The pushed screen existed only inside SwiftUI. Your code couldn't read which screens were open, push three at once, or pop to the root without tricks. `NavigationView` is deprecated; you'll still meet it in older code.

`NavigationStack` separates two things a link used to tie together:

- **What to show** is a value: `NavigationLink("Running shoes", value: ShopRoute.product(id: 7))`. A link appends that value to the stack's path.
- **How to show it** is registered once, by type: `.navigationDestination(for: ShopRoute.self) { route in … }` turns any `ShopRoute` on the path into a view.

Because the link only appends a value, anything else can append values too: a button's action, a model's method, a deep-link handler. And because the path is plain data, you can store it, compare it, test it and save it.

Every navigation operation is an array operation:

| You want | Typed array `[ShopRoute]` | `NavigationPath` |
| --- | --- | --- |
| Push | `path.append(.product(id: 7))` | `path.append(ShopRoute.product(id: 7))` |
| Pop one | `path.removeLast()` | `path.removeLast()` |
| Pop to root | `path.removeAll()` | `path.removeLast(path.count)` |
| Deep link | `path = [.category(slug: "shoes"), .product(id: 7)]` | append each value to a fresh path |
| Read what's open | `path.last`, `path.contains(…)`, any `Array` API | only `count` and `isEmpty` |

## A stack your model owns

Here's a catalogue tab whose navigation belongs to a model rather than to its views, so logic can navigate (pop to the root after adding to the basket) and a deep link can replace the whole path:

```swift check ios title="CatalogueTab.swift"
import SwiftUI

enum ShopRoute: Hashable, Codable {
    case category(slug: String)
    case product(id: Int)
    case reviews(productID: Int)
}

@MainActor @Observable
final class CatalogueModel {
    var path: [ShopRoute] = []

    func showReviews(for productID: Int) {
        path.append(.reviews(productID: productID))
    }

    /// After a purchase the browsing trail is done: back to the catalogue in one step
    func addedToBasket() {
        path.removeAll()
    }

    /// A deep link replaces the whole stack, so Back makes sense afterwards
    func open(_ route: [ShopRoute]) {
        path = route
    }
}

struct CatalogueTab: View {
    @State private var model = CatalogueModel()

    var body: some View {
        NavigationStack(path: $model.path) {
            List {
                NavigationLink("Shoes", value: ShopRoute.category(slug: "shoes"))
                NavigationLink("Bags", value: ShopRoute.category(slug: "bags"))
            }
            .navigationTitle("Catalogue")
            // Registered once, on the root content and outside the List's rows, for every depth
            .navigationDestination(for: ShopRoute.self) { route in
                switch route {
                case .category(let slug):
                    CategoryScreen(slug: slug)
                case .product(let id):
                    ProductScreen(
                        id: id,
                        onShowReviews: { model.showReviews(for: id) },
                        onAddedToBasket: { model.addedToBasket() }
                    )
                case .reviews(let productID):
                    Text("Reviews for product \(productID)")
                }
            }
        }
    }
}

struct CategoryScreen: View {
    let slug: String

    var body: some View {
        List([7, 8, 9], id: \.self) { id in
            // The row only says *what*; the registration above says *how*
            NavigationLink("Product \(id)", value: ShopRoute.product(id: id))
        }
        .navigationTitle(slug.capitalized)
    }
}

struct ProductScreen: View {
    let id: Int
    let onShowReviews: () -> Void
    let onAddedToBasket: () -> Void

    var body: some View {
        VStack(spacing: 16) {
            Text("Product \(id)")
            Button("Reviews", action: onShowReviews)
            Button("Add to basket", action: onAddedToBasket)
        }
    }
}
```

Look at what each part knows. The screens know their inputs and report what happened through closures; none of them names another screen's type or touches the path. The tab knows which view each route becomes. The model knows the navigation rules. That's the split the rest of this module builds on, and later in this module those closures become a SwiftUI coordinator's outputs.

### Where destinations are registered

`navigationDestination(for:)` is a registration, and SwiftUI is particular about where it goes:

- **Inside the stack**, on its root content or any view the stack shows. A registration on the root covers every depth.
- **Not inside a lazy container's rows.** `List`, `LazyVStack` and friends only build rows that are on screen, so a registration attached to a row may not exist when the stack needs it. Attach it to the `List` itself, as above, or higher.
- **Once per type.** Registering `ShopRoute` twice in one stack is ambiguous; SwiftUI warns that it uses the one closest to the root.

Two variations drive a push from state without a path entry of your own: `navigationDestination(isPresented:)` pushes while a `Bool` is true, and `navigationDestination(item:)` (iOS 17) pushes while an optional holds a value, which suits "a barcode was scanned, show that product" on a screen that otherwise doesn't navigate.

## Typed paths and `NavigationPath`

A stack's path can be a typed array, `[ShopRoute]`, or a `NavigationPath`, which erases the types so one path can hold values of several unrelated types.

`NavigationPath` exists for one situation: **features that don't share a route type.** If the reviews feature lives in its own module and defines `ReviewsRoute`, it can register its own destination without the app's `ShopRoute` knowing it exists:

```swift check ios title="A feature that registers its own destinations"
import SwiftUI

// In the Reviews module, which knows nothing about the app's other routes
struct ReviewsRoute: Hashable, Codable {
    let productID: Int
}

extension View {
    func reviewsDestinations() -> some View {
        navigationDestination(for: ReviewsRoute.self) { route in
            Text("Reviews for product \(route.productID)")
        }
    }
}

// In the app, which assembles the features
struct ProductRoute: Hashable, Codable {
    let id: Int
}

struct ShopStack: View {
    @State private var path = NavigationPath()

    var body: some View {
        NavigationStack(path: $path) {
            Button("Open product 7") { path.append(ProductRoute(id: 7)) }
                .navigationDestination(for: ProductRoute.self) { route in
                    Button("Reviews") { path.append(ReviewsRoute(productID: route.id)) }
                }
                .reviewsDestinations()
        }
    }
}
```

The price is that a `NavigationPath` is opaque. You can't ask what's on it, find the product screen, or drop the screens for a deleted product, which [Coupling between state and navigation](/design/learn/sd-state-navigation-coupling) showed you need. A typed array gives you all of that, plus equality for tests. Prefer `[Route]` for any stack whose routes one module can name, which is most of them, and reach for `NavigationPath` at module boundaries where a shared enum would couple features together. A middle way, nesting feature enums inside an app enum (`case reviews(ReviewsRoute)`), keeps the path typed at the cost of the app module depending on every feature's route type; the lesson on routers and route enums, later in this module, weighs that choice.

## Saving a path

To restore navigation after a relaunch, the path has to become data. A typed array of `Codable` routes encodes like any array. A `NavigationPath` offers `codable`, a `CodableRepresentation` you can encode, and it's worth seeing what that contains:

```swift run title="What a saved NavigationPath looks like"
import SwiftUI

enum ShopRoute: Hashable, Codable {
    case product(id: Int)
    case reviews(productID: Int)
}

struct Category: Hashable, Codable {
    var slug: String
}

var path = NavigationPath()
path.append(Category(slug: "shoes"))
path.append(ShopRoute.product(id: 7))
path.append(ShopRoute.reviews(productID: 7))

// Each element is saved as its type's name and its own JSON, last element first
if let representation = path.codable {
    let data = try JSONEncoder().encode(representation)
    print(String(decoding: data, as: UTF8.self))
}

// One element that isn't Codable, and the whole path can't be saved
struct Draft: Hashable {
    var text: String
}
var withDraft = path
withDraft.append(Draft(text: "Great shoes"))
print("\(withDraft.count) screens, codable: \(withDraft.codable == nil ? "nil" : "yes")")

// Restoring doesn't check the elements: a renamed type still "decodes"
let fromOldBuild = #"["main.ProductRoute","{\"product\":{\"id\":7}}"]"#
let old = try JSONDecoder().decode(NavigationPath.CodableRepresentation.self, from: Data(fromOldBuild.utf8))
print("restored \(NavigationPath(old).count) screen of a type that no longer exists")
```

```output
["main.ShopRoute","{\"reviews\":{\"productID\":7}}","main.ShopRoute","{\"product\":{\"id\":7}}","main.Category","{\"slug\":\"shoes\"}"]
4 screens, codable: nil
restored 1 screen of a type that no longer exists
```

Three things to take from that output:

1. **The type's full name is in the data.** In this script the module is `main`; in your app it's your module's name, as in `Shop.ShopRoute`. Rename the type, or move it into a feature module during modularisation, and every saved path names a type that no longer exists.
2. **One element that isn't `Codable` makes the whole path unsavable.** `codable` returns `nil`, and nothing tells you which element was the problem.
3. **Restoring checks nothing.** The representation keeps each element as its saved name and JSON and resolves it only when the stack needs it, so a stale path isn't caught where you could handle it.

A typed `[ShopRoute]` that you encode yourself avoids all three: no type names in the data, a compiler error if a route isn't `Codable`, and a decoding error you can catch, element by element if you like. The last lesson of this module, on restoring navigation, builds on that.

## Lifetimes: what lives on the stack

A pushed screen is a view with an identity: its position on the stack plus its route value. While it's on the stack its `@State` survives; when its value is removed from the path, the screen and its state are discarded. Push `.product(id: 7)` twice and you get two independent product screens. That much matches UIKit.

What differs is that the destination closure runs whenever SwiftUI needs to re-evaluate it, not once per push. Anything created *inside* the closure is created again:

```swift
// Each evaluation makes a new model; the screen loses whatever the old one loaded
case .product(let id):
    ProductScreen(model: ProductModel(id: id))
```

Pass the id and let the screen own its model as `@State`, created cheaply and loaded in `.task(id:)`, so its lifetime matches the screen's ([View lifetime vs state lifetime](/design/learn/sd-swiftui-lifetimes) explains why). Or have a model that outlives the screens hand out per-route models from a cache keyed by route. Either way, a destination closure should be a cheap mapping from a value to a view.

## Trade-offs

| | `[Route]` path | `NavigationPath` | `navigationDestination(item:)` | `NavigationLink(destination:)` |
| --- | --- | --- | --- | --- |
| Code can read the stack | yes, any array API | count only | the one optional | no |
| Deep links and pop-to-root | assign the array | rebuild a path | one screen only | no |
| Saving for restoration | encode it yourself, safely | `CodableRepresentation`, with type names | the optional's value | no |
| Features with their own route types | need a shared or nested enum | yes | yes | yes |
| Testable without UI | equality on the array | barely | yes | no |
| Wins for | most stacks | stacks assembled from independent modules | a single push from screen state | static content with no programmatic navigation |

<Callout kind="interview">

**What to say:** "Each tab's `NavigationStack` is bound to a typed array of `Codable`, `Hashable` routes that hold ids, owned by the feature's model. Destinations are registered once at the root of the stack. Pushing is appending, a deep link assigns the array, and restoration encodes it." If modules are in play: "At module boundaries I'd use `NavigationPath` or nested route enums, and I know `NavigationPath` saves type names."

**What to ask:** which screens must be reachable from a link or a notification? Will the app be split into modules? Does navigation need to survive a relaunch?

**Red flags:** model objects or view models in the path; `NavigationView` in new code; `navigationDestination` attached inside `List` rows; a `NavigationStack` inside a pushed screen; creating view models in the destination closure.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: view-destination links aren't in the path">

A `NavigationLink(destination:)` (or `NavigationLink { … } label: { … }`) inside a path-driven stack still pushes, but nothing is appended to your path. Your model believes the stack is shorter than it is, restoration loses that screen, and code that pops or prunes by editing the path can't see it. In a stack bound to a path, use value-based links only.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: one NavigationStack per column">

A screen pushed onto a stack must not contain a `NavigationStack` of its own. Nested stacks aren't supported: you get doubled navigation bars, pushes that land in the wrong stack, or nothing at all. Each tab, each `NavigationSplitView` column and each presented sheet gets exactly one stack, at its root.

</Callout>
