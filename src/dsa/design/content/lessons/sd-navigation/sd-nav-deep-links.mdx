## Why it matters

Links are how most people arrive in an app that isn't already open: a product shared in Messages, a "your order has shipped" email, a password-reset link, a QR code on a poster, a search result. When they work, the user lands exactly where the link promised. When they don't, the app opens on its home screen, or Safari opens instead, and the campaign that paid for the click is wasted. iOS offers two mechanisms, custom URL schemes and universal links, with very different guarantees, and the system decides which app opens a link before your code runs. "Design deep linking" is a staple mobile interview question, and it rewards knowing exactly where iOS's part ends and yours begins.

## Two kinds of link

| | Custom URL scheme | Universal link |
| --- | --- | --- |
| Looks like | `shop://product/42` | `https://shop.example.com/product/42` |
| Who can claim it | any app that lists the scheme | only an app the domain's owner names in a file on the domain |
| App not installed | the link fails | the web page opens, so it always goes somewhere |
| From Safari | a prompt: "Open in Shop?" | opens the app directly when tapped |
| Set up | one Info.plist entry | an entitlement plus a file on your web server |
| Good for | links between your own apps, testing, a fallback | everything users see: email, social, sharing, marketing |

A **custom URL scheme** is a prefix you declare in the Info.plist under `CFBundleURLTypes`. It's easy and it proves nothing: any app can declare `shop:`, and if two do, iOS doesn't define which one opens. That makes schemes wrong for anything sensitive, such as an OAuth callback carrying a code (use `ASWebAuthenticationSession`, which returns the callback to the session that started it). It also means a scheme link pasted into an email or a tweet does nothing for anyone without the app.

A **universal link** is an ordinary `https` URL on a domain you control. You prove you control it by publishing a file there that names your app; iOS checks that file, and only then opens your app for matching links. Without the app, the same URL opens your website. That's why every link a user might see should be a universal link, with the website as the fallback.

## How a universal link reaches your app

Two moments matter: when the app is installed, and when the link is tapped.

Three consequences of that picture surprise people:

- **Changes to the file take time.** Devices read the file through Apple's CDN, which caches it, and they don't fetch it on every tap, so a new path you add today reaches users over the following hours or days, not instantly. Plan link launches around that. For development, add `?mode=developer` to the entitlement's domain and enable associated domains development in the device's Developer settings, and the device fetches from your server directly.
- **The decision is made before your code runs.** If a link opens Safari instead of the app, no amount of app code can fix it; the cause is in the file, the entitlement, or how the link was tapped.
- **The website is half of the feature.** Every universal link must work as a web page too, because some users don't have the app and some taps go to Safari anyway.

## Setting it up

**The entitlement.** In the app's Signing & Capabilities, add Associated Domains with one entry per domain:

```text title="Shop.entitlements"
com.apple.developer.associated-domains
    applinks:shop.example.com
    applinks:www.shop.example.com
    webcredentials:shop.example.com
```

**The file.** Serve it at `https://shop.example.com/.well-known/apple-app-site-association`: HTTPS with a valid certificate, no redirects, no file extension, as JSON, and under 128 KB.

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["ABCDE12345.com.example.shop"],
        "components": [
          { "/": "/help/*", "exclude": true, "comment": "Help pages stay on the web" },
          { "/": "/product/*" },
          { "/": "/category/*" },
          { "/": "/search", "?": { "q": "?*" } },
          { "/": "/orders/*" },
          { "/": "/basket" }
        ]
      }
    ]
  },
  "webcredentials": {
    "apps": ["ABCDE12345.com.example.shop"]
  }
}
```

- **`appIDs`** are your Team ID plus bundle ID. List every app (and every environment's bundle ID) that should open these links.
- **`components`** are checked in order, and the first match decides, so `exclude` rules go before the patterns they carve out of. `*` matches any run of characters and `?` exactly one; `"q": "?*"` requires a non-empty query parameter. [Interpreter: mini DSLs and route grammars](/design/learn/sd-behavioural-interpreter) treats this file as the small language it is.
- **`webcredentials`** in the same file lets Password AutoFill offer the website's saved passwords in the app. It's the same proof of ownership, reused.

A universal link opens the app only for paths the file lists, and the app can only show paths it can parse. Keep the two in step: generate the file from the app's route table, or test one against the other in CI.

## When a universal link doesn't open the app

Even with a perfect file, iOS deliberately leaves some taps in Safari. Know them, because each one is a support ticket that says "links are broken":

- **Typed or pasted** into Safari's address bar. Typing a URL means "I want the website".
- **A link to the same domain, from a page on that domain.** If the user is browsing your site in Safari and taps a link to another page of it, iOS assumes they want to stay on the web. Links to your domain from *other* domains open the app.
- **The user chose Safari.** Long-press a universal link and pick "Open in Safari", or tap the breadcrumb that iOS shows in the corner after opening your app, and iOS remembers that choice for your domain until the user reverses it (through the same menu, or a Smart App Banner on your site).
- **Redirects.** The tap must be on a URL the file covers. A link that points at another domain and *redirects* to yours opens Safari, because iOS decided on the first URL.
- **Some in-app browsers and web views** load links themselves instead of handing them to the system.

The redirect case catches nearly every marketing team. Email services rewrite links for click tracking, so `https://shop.example.com/product/42` becomes `https://click.mailer.example/ls/abc123`, which redirects to the product. The tap lands on the mailer's domain, which isn't in your file, so Safari opens. The fix is to give tracking its own subdomain of yours, such as `click.shop.example.com` pointed at the email provider, serve your association file there too (providers that support this host it for you), add `applinks:click.shop.example.com`, and have the app resolve the tracked URL to its real destination before parsing it.

## Handling links in the app

Once iOS opens the app, links arrive through different doors depending on whether the app was already running, and missing the cold-start door is the most common deep-linking bug in UIKit apps.

| | SwiftUI | UIKit, app already running | UIKit, app launched by the link |
| --- | --- | --- | --- |
| Custom scheme | `onOpenURL` | `scene(_:openURLContexts:)` | `connectionOptions.urlContexts` |
| Universal link | `onOpenURL` (or `onContinueUserActivity` for the browsing-web type) | `scene(_:continue:)` | `connectionOptions.userActivities` |

In UIKit, `scene(_:openURLContexts:)` and `scene(_:continue:)` are **not** called when the link launches the app; the link is in the connection options of `scene(_:willConnectTo:options:)`, and only there. In SwiftUI, `onOpenURL` receives both kinds, cold or warm, as long as the view it's attached to exists, so attach it at the root of the window.

Either way, the app often isn't ready to navigate when the link arrives: the window is still being built, the session is being restored, or the user must sign in first. So links go into a small handler that parses them and **holds the route** until the UI says it's ready:

```swift check ios title="Links from every door, held until the UI is ready"
import SwiftUI
import UIKit

enum AppRoute: Equatable, Sendable {
    case product(id: Int)
    case basket

    /// Accepts shop://product/42 and https://shop.example.com/product/42; anything else is nil
    init?(url: URL) {
        var segments = url.pathComponents.filter { $0 != "/" }
        switch url.scheme?.lowercased() {
        case "shop": if let host = url.host() { segments.insert(host, at: 0) }
        case "https" where url.host()?.lowercased() == "shop.example.com": break
        default: return nil
        }
        switch (segments.first, segments.count) {
        case ("product", 2):
            guard let id = Int(segments[1]), id > 0 else { return nil }
            self = .product(id: id)
        case ("basket", 1):
            self = .basket
        default:
            return nil
        }
    }
}

/// Turns links into routes, and holds one until the UI can show it
@MainActor
final class LinkHandler {
    var perform: ((AppRoute) -> Void)?
    private var pending: AppRoute?
    private var isReady = false

    func receive(_ url: URL) {
        guard let route = AppRoute(url: url) else { return }   // not ours, or malformed: ignore it
        if isReady { perform?(route) } else { pending = route }  // the latest link wins
    }

    /// Called once the window, the tabs and the signed-in state are in place
    func uiIsReady() {
        isReady = true
        if let route = pending {
            pending = nil
            perform?(route)
        }
    }
}

final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?
    private let links = LinkHandler()

    func scene(_ scene: UIScene, willConnectTo session: UISceneSession, options connectionOptions: UIScene.ConnectionOptions) {
        guard let windowScene = scene as? UIWindowScene else { return }
        let window = UIWindow(windowScene: windowScene)
        window.rootViewController = UITabBarController()
        window.makeKeyAndVisible()
        self.window = window
        links.perform = { route in print("route to", route) }   // the router, in a real app

        // Cold start: the link that launched the app arrives here, and only here
        if let url = connectionOptions.urlContexts.first?.url {
            links.receive(url)
        }
        if let activity = connectionOptions.userActivities.first(where: { $0.activityType == NSUserActivityTypeBrowsingWeb }),
           let url = activity.webpageURL {
            links.receive(url)
        }
        links.uiIsReady()
    }

    // Warm start, custom scheme: the app was already running
    func scene(_ scene: UIScene, openURLContexts URLContexts: Set<UIOpenURLContext>) {
        if let url = URLContexts.first?.url { links.receive(url) }
    }

    // Warm start, universal link
    func scene(_ scene: UIScene, continue userActivity: NSUserActivity) {
        guard userActivity.activityType == NSUserActivityTypeBrowsingWeb, let url = userActivity.webpageURL else { return }
        links.receive(url)
    }
}

struct ShopWindow: View {
    @State private var links = LinkHandler()
    @State private var opened: AppRoute?

    var body: some View {
        Text(opened.map { String(describing: $0) } ?? "Home")
            // Both custom-scheme URLs and universal links arrive here, cold or warm
            .onOpenURL { url in links.receive(url) }
            .onAppear {
                links.perform = { route in opened = route }
                links.uiIsReady()
            }
    }
}
```

"The latest link wins" is a policy, not an accident: if two links arrive before the UI is ready (rare, but a cold launch plus a quick second tap does it), the user's most recent intent is the one to honour. The same buffer is where a route that needs sign-in waits while the user signs in. The next lesson brings every other entry point into the same handler.

## Links are untrusted input

Anyone can create a link to your app and get a user to tap it: in an email, on a web page, in a QR code. Treat every link the way a server treats a request from the internet.

- **Validate everything.** Ids must have the right format, numbers the right range, and anything unexpected must be rejected, not force-unwrapped. A malformed link that crashes the app is a crash anyone can trigger.
- **Navigate, don't act.** A link may *show* the checkout with an item; it must never *place* the order, follow someone, delete something or change a setting without the user confirming in the UI. `shop://basket/add?product=42&quantity=99` should open a screen that asks.
- **No open redirects.** A route like `shop://web?url=…` that loads any URL in an in-app web view, with the user's session cookies, is a phishing kit. Allow only your own hosts.
- **Secrets in links are short-lived and single-use.** Magic sign-in and password-reset links carry a token; the server must expire it within minutes, accept it once, and bind it to the request that asked for it.

## Deferred deep links

A link tapped by someone without the app opens the website, and they may then install the app. Can the app open on the product they tapped, on first launch? iOS has no built-in mechanism for this "deferred" deep link. The workable options are honest ones: the website carries the context into the App Store via a Smart App Banner's `app-argument` (which reaches the app only if it's already installed, so it helps returning users), the user signs in on first launch and the server remembers what they were looking at, or an attribution service provides a best guess, subject to Apple's privacy rules. Promising exact deferred deep links in an interview is a red flag; naming the trade-offs is not.

## Testing links

- **Simulator:** `xcrun simctl openurl booted "shop://product/42"` and `xcrun simctl openurl booted "https://shop.example.com/product/42"` exercise both paths, cold (after quitting the app) and warm.
- **Device:** tap links from Notes or Messages, not from Safari's address bar, which never opens the app. The Developer settings include a universal links diagnostics screen that tells you whether a URL matches your app.
- **Unit tests:** the parser, with good and bad URLs for every route, and a round trip from route to URL and back.
- **The file:** a CI check that it's valid JSON, served without redirects, and covers every route the app accepts.

## Trade-offs

| | Universal links | Custom scheme | Both |
| --- | --- | --- | --- |
| Works without the app | yes, the website | no | yes, for the links users see |
| Can be hijacked by another app | no | yes | only the scheme |
| Opens from every tap | no: same-domain taps, typed URLs, redirects and user choice go to Safari | yes, after a prompt from Safari | best coverage |
| Set-up and upkeep | the file, the entitlement, the CDN delay, the website | one plist entry | both |
| Wins for | everything shared, emailed or published | internal links, testing, apps without a website | most production apps: universal links outside, the scheme as a fallback and for tools |

<Callout kind="interview">

**What to say:** "Universal links on our domain for everything users see, with the website as the fallback; a custom scheme only for internal use. The association file lists our routes in order, generated from the app's route table. In the app, every link (cold start included) goes into one handler that parses it into a typed route, validates it, holds it until the UI and session are ready, then hands it to the router. Links navigate; they never perform actions without confirmation."

**What to ask:** do links come through email click tracking or other redirects? What must happen for users without the app? Which routes need sign-in? Do old links from past campaigns have to keep working?

**Red flags:** custom schemes in marketing links; OAuth callbacks on a custom scheme handled by `openURL`; handling only the warm-start callbacks; force-unwrapping link parameters; links that perform actions.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the link that launched the app isn't sent to openURLContexts">

In a scene-based UIKit app, a link that cold-launches the app is delivered once, in `scene(_:willConnectTo:options:)`, through `connectionOptions.urlContexts` (schemes) and `connectionOptions.userActivities` (universal links). `scene(_:openURLContexts:)` and `scene(_:continue:)` only handle links that arrive while the scene is already connected. Code that handles only those two works perfectly in development, where the app is usually running, and opens on the home screen for every user who taps a link with the app closed.

</Callout>
