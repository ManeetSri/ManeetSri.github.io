## Why it matters

Interview prompts are short on purpose. Everything that makes a design interesting hides in a few words, or is missing entirely, and finding it is part of the test. Real projects are no different: a product brief rarely says "and two people will edit the same list in a basement with no signal". Read a prompt well and you design the right thing; read it badly and you can design the wrong thing beautifully.

## A prompt to practise on

> Design a shared grocery list app. A household keeps one list. Anyone in it can add items, and whoever is at the shop ticks them off as they go. About 2 million households use it each week.

Four sentences. Before you draw anything, read it three times, each time looking for something different.

1. **For the product.** Who uses it, and what's the core journey? Someone adds milk at home; someone else ticks it off in the shop.
2. **For the words that carry requirements.** "Shared", "anyone", "at the shop", "as they go", "2 million households".
3. **For what's missing.** How soon must others see a change? What if two people tick the same item? Does it work without signal? Which platforms?

## Spotting the real requirements

Each loaded phrase turns into something the design must do:

| Words in the prompt | What they ask for |
| --- | --- |
| "A household keeps one list" | Several people and devices editing the same data: sync, and conflicts |
| "Anyone in it can add items" | Shared access: accounts, invitations or a sharing link |
| "At the shop" | Supermarkets are notorious for weak signal: offline-first |
| "Ticks them off as they go" | Instant local writes and optimistic UI |
| "About 2 million households a week" | Modest load. The hard part is sync, not scale |

So the heart of this design is **sync between devices, with edits made offline**. A candidate who spends twenty minutes sharding a database for 2 million households has read the prompt badly. Someone who asks "what happens when two people edit the list in a dead zone, then both come back online?" has found the real problem.

## Ambiguity is deliberate

Prompts leave two kinds of gap. **Scope** gaps: which features are in? Sharing, notifications, recipes, a widget? **Quality** gaps: how fresh, how fast, how many, how private? Interviewers leave them to see whether you notice and ask. Product managers leave them because nobody has thought about them yet. Either way, the gap is your cue.

## Numbers, and what they change

Some numbers are given, and you derive the rest. Turn a user count into requests a second, data served a day and data per phone, the way you would on a whiteboard. Move the sliders:

```visual estimator
title: A shared grocery list, back of the envelope
inputs:
  - { id: dau, label: Daily active users, min: 10000, max: 100000000, value: 1000000, scale: log, unit: users }
  - { id: opens, label: Opens per user per day, min: 1, max: 30, step: 1, value: 6 }
  - { id: requests, label: Requests per open, min: 1, max: 20, step: 1, value: 3 }
  - { id: kb, label: Average response size, min: 1, max: 500, step: 1, value: 4, unit: KB }
  - { id: peak, label: Busiest hour compared with average, min: 1, max: 10, step: 0.5, value: 3 }
outputs:
  - { id: perDay, label: Requests per day, formula: dau * opens * requests, format: si }
  - { id: average, label: Average requests per second, formula: perDay / 86400, format: si, unit: /s }
  - { id: busiest, label: Requests per second in the busiest hour, formula: average * peak, format: si, unit: /s }
  - { id: served, label: Data served per day, formula: perDay * kb * 1000, format: bytes, unit: /day }
  - { id: perPhone, label: Data per phone per month, formula: opens * requests * kb * 1000 * 30, format: bytes, unit: /month }
```

At the starting values the backend sees a few hundred requests a second: ordinary. Now drag the response size up to 300 KB, as if every open downloaded the whole list with a photo of each product. The backend now serves over 5 TB a day, which is a real bill, and each phone pulls about 160 MB a month for a grocery list, which is a real complaint. On mobile, the per-device numbers matter as much as the totals.

## Constraints

Constraints are the limits you design inside, and prompts mention them only sometimes:

- **Platforms and versions:** iOS only, or Android too? What's the oldest iOS version?
- **Existing systems:** an API you must use, a sign-in service, a design system.
- **Team and time:** two engineers and three months rules out a custom sync engine.
- **Rules:** health, payment or children's data brings legal obligations.
- **Surfaces:** iPad, Apple Watch, widgets, Siri.

## The clarifying questions that change a design

Good questions are the ones whose answer changes what you'd build:

| Question | One answer leads to | The other leads to |
| --- | --- | --- |
| Must it work with no signal at all? | A local database as the source of truth, with changes queued in an outbox | A cached copy for reading; edits need a connection |
| Can two people edit the same item at once? | A conflict rule: merge per field, or last writer wins per item | Overwriting is fine |
| How soon must others see a change? | Seconds: a live connection or push while the list is open | Minutes: refresh on open and on pull |
| How long can a list get? | Thousands of items: send only changes | Dozens: send the whole list |
| Do we own the backend? | Design the API around the app | Adapt to an existing API |
| What's the oldest iOS version? | iOS 17 or later: SwiftData and Observation are available | Older: Core Data or SQLite, and `ObservableObject` |

Questions whose answers change nothing, like the colour of the tick or the app's name, can wait.

## When the answer is "you decide"

Often the interviewer hands the question back. Then state an assumption, give the reason, say what would change if it's wrong, and move on: "I'll assume lists stay under 200 items, so the app can send the whole list. If they grew into the thousands, I'd switch to sending changes." Write your assumptions where the interviewer can see them, so both of you can point back at them later.

## Trade-offs

| How much you clarify | Time used | Risk of designing the wrong thing | How it comes across |
| --- | --- | --- | --- |
| Ask nothing and start drawing | None | High | Rushed: likely to miss the real problem |
| Ask the few questions that change the design, and state assumptions for the rest | 3 to 6 minutes | Low | Focused and senior |
| Ask everything you can think of | 10 minutes or more | Low, but little time left to design | Indecisive |

<Callout kind="interview">

**Say** what you think the heart of the problem is once you've read the prompt: "The interesting part seems to be offline edits syncing between devices. Is that where you'd like me to focus?" **Ask** the three or four questions that change the design, then put rough numbers on it. **Red flags:** designing for a scale the prompt doesn't have, asking a long list of questions without using the answers, and never writing an assumption down.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: up to date can't depend on background refresh">

If a requirement says others must see changes soon, don't rely on Background App Refresh to fetch them. People can switch it off per app, Low Power Mode pauses it, and iOS decides when it runs. Refresh when the app comes to the foreground, keep a live connection only while the list is on screen, and use push notifications for changes that really can't wait.

</Callout>
