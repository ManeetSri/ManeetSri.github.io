## Why it matters

Most system design material is written for backend engineers: load balancers, databases, millions of requests a second. A mobile app shares some of those problems and adds its own. It runs on a device you don't control, over a network you can't trust, under rules you didn't write, and long after you shipped it. Mobile system design interviews probe exactly those differences, and so does every real user on a train.

## What's different on a phone

### The network is slow, flaky and sometimes paid for

A server talks to its database over a data-centre network that almost never drops a packet. Your app talks to its server over café Wi-Fi, over 5G that falls to one bar in a lift, or through a captive portal on a train that answers every request with a login page. Round trips on a mobile network are often several times slower than on office Wi-Fi, and they change from one minute to the next.

People also pay for data. iOS has **Low Data Mode**, and `URLSession` can tell you when a connection is expensive (cellular, a personal hotspot) or constrained. A design that downloads 5 MB of images on every launch is spending someone's money.

So mobile designs favour fewer, larger requests, small payloads, timeouts and careful retries, and caching. Every screen needs an answer to one question: what does it show when the request never comes back?

### Battery, memory and CPU are small and shared

Every request wakes the cellular radio, and the radio stays in a high-power state for several seconds after the last byte. Ten small requests spread over a minute can cost far more battery than one batched request. Location, Bluetooth and background work all have similar costs, and users notice an app that drains their battery.

Memory is tight too. An iPhone doesn't write your app's memory out to disk when RAM runs short: iOS warns the app, then terminates apps to reclaim it. That's called **jetsam**. A decoded image takes width × height × 4 bytes, so one 12-megapixel photo is about 48 MB in memory. A feed that decodes full-size photos can be killed while the user scrolls it.

### Your app doesn't decide when it runs

A server process runs until someone stops it. An iOS app runs when iOS lets it. When the user leaves, the app gets a few seconds in the background, then it's **suspended**: frozen in memory, running no code. A suspended app can be terminated at any moment, without being told. So every mobile design has to answer two questions. What must be saved before the app leaves the screen? And what work must survive suspension? Long uploads and downloads go to a **background URLSession**, which the system runs outside your process. Deferrable work goes to **BGTaskScheduler**, which runs it when iOS judges the moment right, not when you ask. You'll design with both in D52.

Saving at the right moment is usually a few lines. In SwiftUI, watch the scene phase:

```swift check ios title="ComposeView.swift"
import SwiftUI

struct ComposeView: View {
    @Environment(\.scenePhase) private var scenePhase
    @State private var draft = ""
    let saveDraft: (String) -> Void

    var body: some View {
        TextEditor(text: $draft)
            .onChange(of: scenePhase) { _, phase in
                // After this the app may be suspended, then terminated without another word
                if phase == .background {
                    saveDraft(draft)
                }
            }
    }
}
```

### Shipped code is out of your hands

A backend team can deploy a fix in minutes and roll back a bad release just as fast. Once a build is on people's phones, it stays there.

- **No hot fixes.** The App Store's rules don't let an app download code that adds or changes features. A fix is a new build through App Review, which usually takes a day or so and isn't guaranteed.
- **Slow rollouts.** A phased release reaches users with automatic updates over seven days, and plenty of people update late or never.
- **Many versions at once.** Next year your server will still be answering the app you ship today. Rename a JSON field or remove an endpoint and every phone still running the old version breaks.

That's why mobile designs lean on what *can* change after release: remote configuration, feature flags and kill switches, server-driven content, and APIs that stay backward compatible. You'll meet them in D34 and D54.

### Privacy is enforced by the platform

On a server, privacy is mostly policy. On iOS, much of it is enforced for you. You get the user's location, photos, contacts or camera only after a system prompt that shows a purpose string you wrote, and the user can refuse, or change their mind later in Settings. Tracking people across other companies' apps needs App Tracking Transparency consent. Since May 2024, apps and the SDKs inside them must declare in a **privacy manifest** why they use certain APIs, such as `UserDefaults` or file timestamps. A design that assumes it always has the user's location is a broken design.

### Offline is a normal state, not an error

A server is expected to be up. A phone is expected to be offline sometimes: on a plane, underground, in a basement gym. People still expect the app to open, show what they saw last time, and keep what they type. Designing for offline changes where the truth lives: a cache that's shown first, or a local database that *is* the source of truth and syncs later. That's D39.

## What stays the same

Most of the thinking carries over. You still start from requirements and numbers, divide the system into parts with clear jobs, design the API and the data model, cache what's expensive, plan for failure and weigh trade-offs out loud. Caching, consistency, idempotency, rate limits and backoff mean the same thing on both sides. The app is one more participant in the system: an unusually unreliable one that you can't redeploy.

## What mobile system design interviews ask

A backend interview might ask you to design a URL shortener and spend most of the hour on databases and sharding. A mobile interview asks for a product or a component, seen from the client:

- a news feed, a chat app or a photo-sharing app;
- an image-loading library or an offline-first notes app;
- the rider app for a ride-hailing service.

Interviewers expect depth on the client: architecture, state, caching, persistence, offline behaviour, pagination, background work, battery and memory. They also expect you to sketch the backend contract the app needs: the API, real-time updates, push, and roughly how the server stores and serves the data. You'll practise all of these in Part X.

## How much backend you need

Enough to design the contract and reason about the server's side of it, but not enough to run it.

| Depth | Topics |
| --- | --- |
| Know it well | API design (resources, pagination, errors, versioning), HTTP caching, auth tokens, push notifications, real-time options, idempotency, estimating load |
| Know the shape | Load balancers, CDNs, SQL vs NoSQL, replication, queues, rate limiting, consistent hashing, observability |
| Leave to specialists | Consensus algorithms, storage-engine internals, running a database cluster |

Part VI covers the first two rows. The third is out of scope for this course.

## Trade-offs

Many mobile design decisions come down to one question: does this logic live in the app or on the server?

| Where it lives | Can change after release | Works offline | Same on iOS, Android and web | Private data |
| --- | --- | --- | --- | --- |
| In the app | Only with a new build | Yes | Each platform builds it again | Can stay on the device |
| On the server | Any time | No | One implementation | Must leave the device |
| In the app, configured by the server | Within what the build supports | With the last config it saw | Shared rules, separate code | Only the config travels |

Rules that change often, like prices or which features are switched on, belong on the server or in remote config. Behaviour that must work offline, or that touches private data, belongs in the app. Most real features split the difference.

<Callout kind="interview">

**Say** early that you're designing for a phone: "I'll assume a flaky network, so the feed shows cached posts first," or "Uploads must survive the app being suspended, so they go through a background session." **Ask** how old the oldest supported app version is, and whether you own the backend. **Red flags:** treating the network as reliable, ignoring suspension and termination, and an API that can't change without breaking last year's app.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the Simulator has your Mac's network">

The Simulator uses your Mac's fast, reliable connection, so a design that only works on good networks looks fine at your desk. On a device set up for development, **Settings → Developer → Network Link Conditioner** simulates 3G, high latency and lost packets. Test offline with Airplane Mode, and test suspension by leaving the app in the middle of a request.

</Callout>
