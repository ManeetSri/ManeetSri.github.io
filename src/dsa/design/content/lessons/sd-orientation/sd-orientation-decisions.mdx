## Why it matters

Every day on an app team you make dozens of decisions: what to call a type, whether a screen gets a view model, which database holds the user's data. A few of them will shape the app for years. Most can be changed before lunch. Telling the two apart is the core skill of architecture: it tells you where to spend your thinking, what to write down, and what is worth arguing about in a design review or an interview.

## Three levels of decision

- **Architecture decisions** shape the whole app and are expensive to change: how the app splits into modules, where data is stored and how it syncs, SwiftUI or UIKit as the base, the app-wide pattern, the style of the API.
- **Design decisions** shape one part: the types inside a feature, a protocol's methods, which object owns a piece of state, the cases of a view-state enum.
- **Implementation decisions** live inside a function or a type: a local variable's name, a loop or `map`, an `Array` or a `Set` for a small lookup.

The line between them isn't the amount of code or how clever it is. It's **how much it costs to change your mind**. One line that fixes the on-disk format of user data is an architecture decision. A thousand lines of layout code can be an implementation detail, if nothing else depends on how they're written.

<Callout kind="analogy">

In a house, where the load-bearing walls go is architecture, the layout of the kitchen is design, and the colour of the paint is implementation. Repainting takes a weekend. Moving a load-bearing wall takes an engineer, permission and months.

</Callout>

## One-way and two-way doors

Amazon popularised a simple test. Is this a **one-way door** or a **two-way door**? Walk through a two-way door and dislike what you find, and you walk back at little cost. A one-way door can't be undone, or only at great cost.

Most decisions are two-way doors and deserve fast decisions: treating them as permanent slows the team down for nothing. A few are one-way, and those deserve real time: alternatives, a prototype, a second opinion and a written record.

On iOS, three things turn an ordinary decision into a one-way door:

- **Data on the device.** Once a million phones store notes in your Core Data model, every change to it is a migration that must work on every one of them.
- **Old app versions.** Once an API shape ships in a build, the server must support it for as long as that build is in use.
- **Dependencies everywhere.** A third-party SDK called directly from 200 files is costly to remove. The same SDK behind one wrapper type is cheap.

## Blast radius

**Blast radius** is how much is affected if a decision turns out to be wrong: how many files, modules, teams, users and app versions. Renaming a private method has a blast radius of one file. Changing the `User` model that every feature imports touches the whole app. Changing what an endpoint returns reaches every installed copy of every version.

Reversibility and blast radius usually travel together, and you can shrink both on purpose.

## Making a one-way door two-way

You often can't avoid a big decision, but you can make it cheaper to reverse. The commonest tool is an interface around the risky choice. Here an app needs to store notes, and nobody knows yet whether a JSON file will be enough or a database will be needed later:

```swift check title="NoteStore.swift"
import Foundation

struct Note: Codable, Identifiable, Sendable {
    let id: UUID
    var text: String
}

/// All the app knows about storage. Screens and view models depend on this, never on a database.
protocol NoteStore: Sendable {
    func allNotes() async throws -> [Note]
    func save(_ note: Note) async throws
}

/// Version one: a JSON file. Moving to SQLite or SwiftData later means writing one new type.
actor FileNoteStore: NoteStore {
    private let url: URL

    init(url: URL) {
        self.url = url
    }

    func allNotes() throws -> [Note] {
        guard let data = try? Data(contentsOf: url) else { return [] }
        return try JSONDecoder().decode([Note].self, from: data)
    }

    func save(_ note: Note) throws {
        var notes = try allNotes()
        notes.removeAll { $0.id == note.id }
        notes.append(note)
        try JSONEncoder().encode(notes).write(to: url, options: .atomic)
    }
}
```

The rest of the app sees `NoteStore` and plain `Note` values. If the file grows too slow at 10,000 notes, you write a `SQLiteNoteStore`, migrate the data once, and change the one line where the store is created. The storage choice still matters, but it's no longer welded into every screen.

Other ways to widen a door:

- **Feature flags:** ship a change to 1% of users, and turn it off without a release.
- **Versioned formats:** a `version` field in stored files and payloads lets tomorrow's code read today's data.
- **Spikes:** a throwaway prototype answers "will this database cope with our sync?" before you commit.
- **Deferring:** when information is missing, decide the smallest thing that keeps options open, and set a date to decide properly.

Each has a price. An interface is one more type to understand, and a flag is a branch to test and, later, delete.

## Examples on iOS

| Decision | Level | Door | Why |
| --- | --- | --- | --- |
| A local variable's name | Implementation | Two-way | One rename |
| A loop or `map` | Implementation | Two-way | Contained in one function |
| A view model's methods | Design | Two-way, mostly | Its callers live in the same feature |
| Calling an analytics SDK directly, or through your own protocol | Design | Two-way only with the protocol | Direct calls spread the SDK through the app |
| Module boundaries in your Swift packages | Architecture | Costly | Imports, build graph and team ownership all follow them |
| The store for user data | Architecture | One-way without an interface | Data on every device must be migrated |
| JSON field names in a shipped API | Architecture | One-way | Old builds read them for years |

## Trade-offs

| Approach | Speed now | Cost if wrong | Added complexity | When it wins |
| --- | --- | --- | --- | --- |
| Decide quickly and move on | Fastest | Low for two-way doors, high for one-way | None | Two-way doors, which is most decisions |
| Decide carefully: options, prototype, review, write-up | Slowest | Lower, because the risks were explored | None in the code | Unavoidable one-way doors |
| Put the choice behind an interface or a flag | Medium | Low: swap the implementation | One more abstraction to maintain | Risky choices where better information arrives later |

<Callout kind="interview">

**Say** which decisions you're spending time on, and why: "The sync model is the hard-to-reverse choice here, so I'd like to go deep on it. The view layer we can change later." That sentence alone shows judgement. **Ask** what's already fixed: an existing backend, a minimum iOS version, a team standard. **Red flags:** ten minutes on view-model names while offline sync goes unmentioned, and treating every choice as equally permanent.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: renaming a Codable property is a data migration">

`Codable` uses property names as keys. Rename `title` to `headline` in a type you save to disk, and every file the old version wrote fails to decode with `keyNotFound`. A one-word change in Swift has become a one-way door for data. Keep the old key with `CodingKeys`, or decode it as a fallback, until no old data is left.

</Callout>
