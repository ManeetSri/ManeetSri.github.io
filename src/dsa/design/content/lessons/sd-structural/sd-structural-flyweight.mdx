## Why it matters

When an app shows thousands of similar things (pins on a map, stickers in a chat, glyphs in a text view, tiles in a game), most of what each one carries is the same as its neighbours. Duplicating it wastes memory, and on a phone memory is what gets your app terminated in the background. The **flyweight** pattern splits each object's state into the part many objects can share and the part that's theirs alone, and shares the first through a factory. "10,000 pins on a map" is a classic mobile interview question, and flyweight is one of the three tools a strong answer combines.

## Intrinsic and extrinsic state

Look at a map of cafés, pharmacies, parks and stations. Each pin has:

- **Intrinsic state**, which is the same for every pin of its kind and doesn't depend on where the pin is: the icon, its colour, the category name. A café pin's icon is identical to every other café pin's.
- **Extrinsic state**, which belongs to one pin: its coordinate, its title, whether it's selected.

A **flyweight** is an immutable object holding intrinsic state, shared by every object that needs it. The extrinsic state stays with each pin, or is passed in when the flyweight is used. A **factory** guarantees there's only one flyweight per key, by handing out the existing one when it's asked again.

<Callout kind="analogy">

Movable type. A printer doesn't cast a new letter *e* for every *e* on the page. There's a tray of *e*s, and each use only adds where it goes. The letter's shape is intrinsic; its position on the page is extrinsic.

</Callout>

## A flyweight factory

Here 10,000 pins in four categories ask a factory for their style. `PinStyle` stands in for an object that would hold a decoded icon image; a constant gives its size.

```swift run
// Intrinsic state: the same for every pin of a category, and never changed
final class PinStyle: Sendable {
    static let iconBytes = 120 * 120 * 4    // a decoded 120 × 120 px icon, 4 bytes per pixel

    let category: String
    let symbolName: String
    let tint: String

    init(category: String, symbolName: String, tint: String) {
        self.category = category
        self.symbolName = symbolName
        self.tint = tint
    }
}

// The flyweight factory: one shared style per category, created on first request
final class PinStyleFactory {
    private var styles: [String: PinStyle] = [:]
    private let looks = ["cafe": ("cup.and.saucer.fill", "brown"), "pharmacy": ("cross.fill", "green"),
                         "park": ("tree.fill", "teal"), "station": ("tram.fill", "blue")]

    var count: Int { styles.count }

    func style(for category: String) -> PinStyle {
        if let style = styles[category] { return style }
        let (symbol, tint) = looks[category] ?? ("mappin", "red")
        let style = PinStyle(category: category, symbolName: symbol, tint: tint)
        styles[category] = style
        return style
    }
}

// Extrinsic state: different for every pin, kept outside the flyweight
struct Pin {
    let latitude: Double
    let longitude: Double
    let title: String
    let style: PinStyle
}

let categories = ["cafe", "pharmacy", "park", "station"]
let factory = PinStyleFactory()
let pins = (0..<10_000).map { index in
    Pin(latitude: 51.5 + Double(index % 100) / 1_000,
        longitude: -0.12 + Double(index / 100) / 1_000,
        title: "Place \(index)",
        style: factory.style(for: categories[index % categories.count]))
}

let distinctStyles = Set(pins.map { ObjectIdentifier($0.style) }).count
print("\(pins.count) pins share \(distinctStyles) style objects (the factory made \(factory.count))")
print("Icons if every pin had its own: \(pins.count * PinStyle.iconBytes / 1_000_000) MB")
print("Icons shared through the factory: \(factory.count * PinStyle.iconBytes / 1_000) KB")
```

```output
10000 pins share 4 style objects (the factory made 4)
Icons if every pin had its own: 576 MB
Icons shared through the factory: 230 KB
```

The arithmetic is the whole argument. A decoded image costs width × height × 4 bytes, whatever size the file was on disk, so one 120-pixel icon is 57.6 KB. Ten thousand copies would be over half a gigabyte for icons alone, enough to get the app terminated on many devices. Four shared copies are a rounding error. Each pin pays only for its own coordinate and title, plus an 8-byte reference to its style.

## Sharing only works if nothing changes

A flyweight is used by many objects at once, so changing it changes all of them. If selecting one café pin set `style.tint = "orange"`, every café on the map would turn orange. So:

- **Make flyweights immutable.** `let` properties on a `final class`, as `PinStyle` has. Per-use variations (selected, dimmed) are extrinsic: pass them in when drawing, or pick a different flyweight (`"cafe-selected"`).
- **Make them `Sendable`.** An immutable final class can be, and then Swift 6 lets you share it across tasks and actors freely, which is what a flyweight is for.
- **Protect the factory.** The factory's dictionary *does* change. If only the UI asks for styles, mark the factory `@MainActor`; if background tasks ask too, make it an actor.

Swift's value types give you a quiet form of sharing for free. `Array`, `String` and `Data` keep their contents in a reference-counted buffer and copy it only when someone writes to a shared one, so ten thousand copies of an unmodified `Data` are ten thousand small values pointing at one buffer. The flyweight pattern is still worth knowing because it makes that sharing deliberate, keyed and visible.

## Apple's flyweights

- **`UIImage(named:)`** looks in a system cache before loading, so asking for `"pin-cafe"` ten thousand times gives you shared image data, not ten thousand decodes. `UIImage(contentsOfFile:)` doesn't use that cache: every call loads and decodes again. That one choice of initialiser is a flyweight decision.
- **Tagged pointers** take the idea to its limit. On 64-bit Apple platforms, small `NSNumber`, `NSDate` and short `NSString` values can be stored inside the pointer itself, so there's no object to allocate or share at all.

## Flyweight, pool or cache?

Three patterns reuse objects, and they're easy to confuse:

| | Flyweight | Object pool | Cache |
| --- | --- | --- | --- |
| Used by | many objects at the same time | one user at a time, then returned | whoever asks |
| Must be immutable | yes | no: it's reset when it's returned | ideally |
| May be thrown away | no, or identity breaks | not usually | yes: under memory pressure, or when stale |
| Saves | memory | creation time | recomputation or refetching |
| iOS example | `UIImage(named:)`, a shared `PinStyle` | table and collection view cell reuse | `NSCache` of thumbnails, `URLCache` |

Cell reuse, which you met in [object pools](/design/learn/sd-creational-object-pools), is a pool: a cell shows one row at a time and is reset before the next. A flyweight is never "checked out"; every user holds it at once.

## How much does sharing save?

Move the sliders to see when a flyweight is worth it. The saving is roughly the number of pins times the size of the shared part, so it grows with both. With small icons and few pins it hardly matters; with large icons and many pins it decides whether the map fits in memory at all.

## Trade-offs

| | Each object owns its state | Flyweights through a factory |
| --- | --- | --- |
| Memory | grows with every object | shared part paid once per key |
| Code | simplest | a factory, keys, and the intrinsic/extrinsic split |
| Changing one object's look | change its property | pass state in, or switch it to another flyweight |
| Concurrency | each object is independent | flyweights must be immutable; the factory needs isolation |
| Lookup cost | none | a dictionary lookup per request |

Flyweight pays off when there are many objects **and** a large shared part. Sharing a 16-byte colour between pins saves nothing: the reference to it is 8 bytes, and the reference counting costs time. Don't share state that genuinely varies, and don't build a factory for a screen that shows twenty items.

<Callout kind="interview">

**What to say for "show 10,000 pins on a map":** three different tools. **Flyweight** for the heavy shared parts: one image per category, not per pin. **Clustering** so the map draws a few dozen views instead of ten thousand (`MKAnnotationView.clusteringIdentifier` in MapKit). **Reuse**, a pool, for the annotation views that are on screen, plus loading only pins in the visible region. Say which problem each solves: memory per pin, number of views, and creation cost.

**What to ask:** how many pins are visible at once versus loaded, how many distinct looks there are, and whether pins change appearance when selected.

**Red flags:** decoding the same image per pin; a mutable shared style; a factory that's touched from several threads without isolation.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the file size isn't the memory size">

A 12 KB PNG icon becomes width × height × 4 bytes once it's decoded for display, at the screen's scale. A 40-point icon on a 3× screen is 120 × 120 pixels: 57.6 KB in memory, nearly five times the file. Estimate memory from pixels, not from what's on disk, and share decoded images rather than decoding the same file again.

</Callout>
