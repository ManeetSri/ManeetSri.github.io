## Why it matters

Some features vary along two independent lines at once: *what* they do and *how* it's done underneath. Reports and the formats they're exported in. Map features and the map SDK that draws them. Controls and the styles that draw them. Model each combination as its own subclass and the types multiply: three reports in three formats is nine classes, and each new format adds three more. The **bridge** splits the two dimensions into two families joined by one reference, so each grows on its own. It's the pattern behind "support MapKit and a third-party map SDK", a real requirement in apps that ship in markets where one provider is weaker, and a good interview test of whether you can find the right seam.

## Two things that vary

Picture an app that exports reports. There are invoices, monthly sales summaries and refund notes, and each can be exported as PDF, CSV or Markdown. The obvious design is a class per combination:

- `PDFInvoice`, `CSVInvoice`, `MarkdownInvoice`
- `PDFMonthlySales`, `CSVMonthlySales`, `MarkdownMonthlySales`
- `PDFRefundNote`, `CSVRefundNote`, `MarkdownRefundNote`

Nine classes, and the trouble is in what they share. Every PDF class repeats the same PDF code; every invoice class repeats the same invoice logic. Add an Excel export and you write three more classes, copying the invoice, sales and refund logic once more. The hierarchy is trying to express two independent choices with one tree, and a tree can only branch one way at a time.

## The bridge: two families, one reference

The bridge pulls the two dimensions apart:

- The **abstraction** is what the feature *is*: a report that has a heading, rows and a total. **Refined abstractions** are the kinds of report: invoice, monthly sales, refund note.
- The **implementor** is a protocol of *primitives* the abstraction needs: write a heading, write a row, write a total. **Concrete implementors** are the formats: PDF, CSV, Markdown.
- The abstraction **holds** an implementor and is written entirely in terms of its primitives. That reference is the bridge.

In Swift:

```swift run
// The implementation side: primitives that every output format can provide
protocol ReportRenderer {
    func heading(_ text: String) -> String
    func row(_ cells: [String]) -> String
    func total(_ label: String, pence: Int) -> String
}

struct MarkdownRenderer: ReportRenderer {
    func heading(_ text: String) -> String { "## \(text)" }
    func row(_ cells: [String]) -> String { "| " + cells.joined(separator: " | ") + " |" }
    func total(_ label: String, pence: Int) -> String { "**\(label): £\(pounds(pence))**" }
}

struct CSVRenderer: ReportRenderer {
    func heading(_ text: String) -> String { "# \(text)" }
    func row(_ cells: [String]) -> String { cells.map { $0.contains(",") ? "\"\($0)\"" : $0 }.joined(separator: ",") }
    func total(_ label: String, pence: Int) -> String { "\(label),\(pounds(pence))" }
}

func pounds(_ pence: Int) -> String {
    let remainder = pence % 100
    return "\(pence / 100).\(remainder < 10 ? "0" : "")\(remainder)"
}

// The abstraction side: what each report says, written only with the primitives
struct LineItem {
    let name: String
    let quantity: Int
    let unitPence: Int
}

struct Invoice {
    let renderer: any ReportRenderer
    let number: String
    let items: [LineItem]

    func render() -> [String] {
        let total = items.reduce(0) { $0 + $1.quantity * $1.unitPence }
        return [renderer.heading("Invoice \(number)")]
            + items.map { renderer.row([$0.name, String($0.quantity), pounds($0.quantity * $0.unitPence)]) }
            + [renderer.total("Total", pence: total)]
    }
}

struct MonthlySales {
    let renderer: any ReportRenderer
    let month: String
    let days: [(day: String, pence: Int)]

    func render() -> [String] {
        let total = days.reduce(0) { $0 + $1.pence }
        return [renderer.heading("Sales, \(month)")]
            + days.map { renderer.row([$0.day, pounds($0.pence)]) }
            + [renderer.total("Month", pence: total)]
    }
}

let items = [LineItem(name: "Notebook", quantity: 2, unitPence: 450), LineItem(name: "Pens, pack of 5", quantity: 1, unitPence: 399)]
for renderer: any ReportRenderer in [MarkdownRenderer(), CSVRenderer()] {
    Invoice(renderer: renderer, number: "1042", items: items).render().forEach { print($0) }
    print()
}
MonthlySales(renderer: CSVRenderer(), month: "May", days: [("1 May", 12_050), ("2 May", 9_875)]).render().forEach { print($0) }
```

| Pens, pack of 5 | 1 | 3.99 |
**Total: £12.99**

Each side keeps its own knowledge. Only `Invoice` knows that an invoice's total is the sum of quantity times price; only `CSVRenderer` knows that a cell containing a comma must be quoted. Neither knowledge is repeated.

The hard part of a bridge is choosing the **primitives**. Too few and abstract ("render this report") and every format must understand every report again, which is the explosion in disguise. Too many and specific ("draw a two-column table with a bold footer") and simple formats can't implement them. Good primitives are the smallest set of operations every report needs and every format can do.

## Bridges you already use

**Codable.** A type's `encode(to:)` is written against the `Encoder` protocol's containers (keyed, unkeyed, single value), and `JSONEncoder` and `PropertyListEncoder` supply implementations. Any `Codable` type works with any encoder: hundreds of types and a handful of formats, with no code per combination. That's a bridge, with the containers as primitives.

**SwiftUI controls and their styles.** A `Button` is what the control *is*: a label, a role, an action, accessibility. A `ButtonStyle` is how it's *drawn*. Every button works with every style, and you saw in [the modifiers lesson](/design/learn/sd-structural-swiftui-modifiers) how one `.buttonStyle(_:)` restyles a whole subtree. `Toggle` with `ToggleStyle` and `Label` with `LabelStyle` follow the same split.

**Core Data stores.** An `NSPersistentStoreCoordinator` talks to its stores through one abstraction, whether the store is SQLite, in memory or binary, and a custom `NSIncrementalStore` subclass can put a web service behind the same interface. Your fetch requests don't change.

## A bridge for map SDKs

Some apps must support more than one map provider: MapKit in most places, another SDK where its data is better, or for a client who insists. The features (track a delivery, find a store, show a running route) are one family; the SDKs are the other. The implementor is a small protocol of map primitives:

```swift check ios
import MapKit

struct Pin {
    let coordinate: CLLocationCoordinate2D
    let title: String
}

// The implementation side: primitives that every map SDK can provide
@MainActor
protocol MapCanvas: AnyObject {
    func show(_ pins: [Pin])
    func drawRoute(_ coordinates: [CLLocationCoordinate2D])
    func fit(_ coordinates: [CLLocationCoordinate2D])
}

@MainActor
final class MapKitCanvas: MapCanvas {
    let mapView = MKMapView()

    func show(_ pins: [Pin]) {
        mapView.removeAnnotations(mapView.annotations)
        mapView.addAnnotations(pins.map { pin in
            let annotation = MKPointAnnotation()
            annotation.coordinate = pin.coordinate
            annotation.title = pin.title
            return annotation
        })
    }

    func drawRoute(_ coordinates: [CLLocationCoordinate2D]) {
        // The map view's delegate supplies an MKPolylineRenderer to draw it (left out here)
        mapView.removeOverlays(mapView.overlays)
        mapView.addOverlay(MKPolyline(coordinates: coordinates, count: coordinates.count))
    }

    func fit(_ coordinates: [CLLocationCoordinate2D]) {
        let points = coordinates.map { MKMapRect(origin: MKMapPoint($0), size: MKMapSize(width: 0, height: 0)) }
        guard let first = points.first else { return }
        let area = points.dropFirst().reduce(first) { $0.union($1) }
        mapView.setVisibleMapRect(area, edgePadding: UIEdgeInsets(top: 48, left: 48, bottom: 48, right: 48), animated: true)
    }
}

// The abstraction side: a feature written only in terms of the primitives
@MainActor
final class DeliveryTrackingMap {
    private let canvas: any MapCanvas

    init(canvas: any MapCanvas) {
        self.canvas = canvas
    }

    func update(courier: CLLocationCoordinate2D, destination: CLLocationCoordinate2D, route: [CLLocationCoordinate2D]) {
        canvas.show([Pin(coordinate: courier, title: "Courier"), Pin(coordinate: destination, title: "You")])
        canvas.drawRoute(route)
        canvas.fit(route + [courier, destination])
    }
}
```

`DeliveryTrackingMap` decides *what* the user sees: two pins, the route, everything in view. `MapKitCanvas` decides *how* MapKit shows it: annotations, an overlay, a visible map rect. A `StoreLocatorMap` would be a second abstraction over the same canvas, and a canvas for another SDK would serve both features without either changing.

Notice that `MapKitCanvas` is also an [adapter](/design/learn/sd-structural-adapter): it makes MapKit's API fit the `MapCanvas` protocol. That's common. The bridge is the overall design, two families varying independently, and the concrete implementors are often adapters over the platforms they wrap.

## Bridge, adapter and strategy

The three look alike in code, so the difference is in timing and scope:

- An **adapter** is applied *after the fact*: an existing interface doesn't fit, so you translate it. A bridge is designed *up front*, because you know both sides will grow.
- A **strategy**, which you'll meet in D12, swaps one algorithm inside an object: a sort order, a pricing rule. A bridge's implementor is a whole platform with several primitives, and the abstraction side has a family of its own. If only one side varies, you have a strategy, or no pattern at all.

## Generics or existentials for the bridge

The reference between the two sides can be an existential, as above, or a generic parameter:

- `any MapCanvas` lets the app choose the SDK **at run time**: from remote configuration, per country, or in an A/B test. Calls go through dynamic dispatch, which is negligible next to drawing a map.
- `DeliveryTrackingMap<Canvas: MapCanvas>` fixes the SDK **at compile time** for each instance. The compiler can specialise the calls, and the type says which SDK is in use, but switching means building a different type.

For SDK choices, run time is usually what you want. For performance-sensitive primitives called thousands of times per frame, generics can be worth it. [`some` vs `any`](/design/learn/sd-swift-design-some-any) covers the costs in detail.

## Trade-offs

| | A subclass per combination | Bridge | One type that switches on the format |
| --- | --- | --- | --- |
| Types for N kinds and M formats | N × M | N + M, plus one protocol | N, plus a `switch` in every method |
| Adding a format | N new subclasses | one new type | edit every `switch` |
| Adding a kind | M new subclasses | one new type | one new type, with a `switch` in it |
| Up-front design | none | finding the right primitives | none |
| Main risk | duplicated code in every sibling | lowest-common-denominator primitives; building it too early | switches that grow and drift apart |

The bridge earns its keep only when **both** dimensions really vary. With one format and no second in sight, a plain type is better: a bridge with one implementor is indirection you pay for and never use. With two formats and two reports, the `switch` is often simpler and perfectly honest. Reach for the bridge when the combinations start to hurt, or when a second provider is a stated requirement.

<Callout kind="interview">

**What to say for "support MapKit and another map SDK":** "I'd separate the map features from the map SDK. Features like delivery tracking are written against a small `MapCanvas` protocol of primitives (pins, routes, the visible region), with one implementation per SDK, chosen at run time. Each implementation is an adapter over its SDK."

**What to ask:** which features need which capabilities, whether both SDKs support all of them, and how the SDK is chosen (per user, per country, per build).

**Red flags:** primitives that are really whole features ("show the delivery screen"), which forces every SDK to reimplement them; a bridge with one implementation "for flexibility"; a primitive that one SDK fills with a crash.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: when one side can't do what the protocol asks">

Map SDKs don't all support the same things: one draws heat maps, another doesn't. Don't give the missing one a method that crashes or silently does nothing, because callers can't tell. Either keep the shared protocol to what every SDK can do and put extras in a second protocol (`HeatmapDrawing`) that features check for with `as?`, or expose capabilities (`var supportsHeatmaps: Bool`) so features can adapt their UI.

</Callout>
