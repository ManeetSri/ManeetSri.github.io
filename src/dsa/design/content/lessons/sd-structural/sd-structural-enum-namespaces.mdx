## Why it matters

Swift has modules, but no `namespace` keyword for grouping names inside one. Caseless enums fill the gap: they gather related constants, functions and types under one name that can never be instantiated. You'll find them in design tokens, API endpoints, header names and notification keys, in Swift's standard library, and in every kata in this course. The pattern is small, but using it well (and knowing when a value belongs somewhere else) is a quick signal of Swift fluency, and Swift 6 turned one common misuse into a compile error.

## Why an enum with no cases

An enum's instances are its cases. An enum with **no cases has no possible instances**, so it can only be used as a name to put things under:

```swift
enum Theme {
    enum Spacing {
        static let small = 8.0
    }
}

let spacing = Theme.Spacing()
```

```text title="What you'll see"
error: 'Theme.Spacing' cannot be constructed because it has no accessible initializers
```

A struct would compile here: structs get an implicit `init()`, so `Theme.Spacing()` would create a value that means nothing. You can stop that with `private init()`, but the caseless enum says "this is only a namespace" without any extra code.

The standard library uses the same trick. `MemoryLayout` is a caseless generic enum (`MemoryLayout<Int>.size`), `CommandLine` is a caseless enum holding `arguments`, and `Unicode` is a namespace enum for `Unicode.Scalar`, `Unicode.UTF8` and friends. In this course's Swift package, every kata keeps its types inside a `public enum` such as `AtlasGeocoderAdapter`, so hundreds of katas share one module without a single name clash.

## What goes in a namespace

Static constants, static functions and nested types. And because extensions work on enums, a namespace can grow across files: the networking code can add `API.Header` without touching the file that declared `API`.

```swift run
enum Theme {
    enum Spacing {
        static let small = 8.0
        static let medium = 16.0
        static let large = 24.0
    }

    enum Radius {
        static let card = 12.0
        static let button = 22.0
    }
}

enum API {
    static let version = "v2"

    enum Endpoint {
        static func orders(page: Int) -> String { "/\(API.version)/orders?page=\(page)" }
        static func order(id: String) -> String { "/\(API.version)/orders/\(id)" }
    }
}

// A namespace can grow across files: this extension could live anywhere in the module
extension API {
    enum Header {
        static let requestID = "X-Request-ID"
    }
}

print(Theme.Spacing.medium + Theme.Radius.card)
print(API.Endpoint.orders(page: 2))
print(API.Endpoint.order(id: "A1042"))
print(API.Header.requestID)
```

```output
28.0
/v2/orders?page=2
/v2/orders/A1042
X-Request-ID
```

`Theme.Spacing.medium` reads as what it is, autocompletes from `Theme.`, and can't be confused with a spacing constant from somewhere else. That's the whole benefit, and it's a real one in a large codebase.

## Put values on the type they describe, when there is one

A namespace isn't always the best home. When a value *is* a `Color`, a `Font` or a `Duration`, putting it on that type lets callers use leading-dot syntax wherever the type is expected:

```swift check ios
import SwiftUI

enum Theme {
    enum Spacing {
        static let small: CGFloat = 8
    }
}

extension ShapeStyle where Self == Color {
    static var brand: Color { Color(red: 0.95, green: 0.45, blue: 0.2) }
}

extension Font {
    static let cardTitle = Font.system(.headline, design: .rounded)
}

struct PriceTag: View {
    let price: String

    var body: some View {
        Text(price)
            .font(.cardTitle)
            .foregroundStyle(.brand)
            .padding(Theme.Spacing.small)
    }
}
```

`.font(.cardTitle)` and `.foregroundStyle(.brand)` read like the built-in `.headline` and `.blue`, and they show up in autocomplete exactly where they're useful. Note the `where Self == Color`: `foregroundStyle(_:)` is generic over `ShapeStyle`, so `.brand` must be found on `ShapeStyle` for the leading dot to work. A plain `extension Color` would make `Color.brand` work, but not `.brand` there.

Spacing stays in a namespace because it's a bare `CGFloat`; putting `small` on `CGFloat` would offer it everywhere a number is expected.

One more alternative beats both: when the values are a **closed set used as a parameter**, make them an enum *with* cases. `enum Screen: String { case basket, checkout }` lets the compiler check every value; a namespace of `static let basket = "basket"` strings is still stringly typed, a smell you'll meet in D15.

## Namespaces and modules

The module is Swift's real namespace: two modules can each have an `Order`, and `Shop.Order` and `Billing.Order` tell them apart. Caseless enums organise names *inside* a module. Two cautions follow:

- **Don't name a type after its module.** If the `Networking` module declares a type called `Networking`, then `Networking.Request` looks for a member of the type, not the module, and qualifying the module's other names becomes awkward.
- **Namespaces aren't modules.** Thirty nested enums in one app target organise names, but every type can still see every other. Boundaries that the compiler enforces come from separate modules and access control, which you'll set up in D61.

## The Swift 6 trap: a namespace is global state

A namespace is a fine home for constants and a bad home for variables. A `static var` on a namespace is a global variable with a nicer name, and Swift 6 treats it as one:

```swift
enum FeatureFlags {
    static var overrides: [String: Bool] = [:]
}
```

```text title="What you'll see"
error: static property 'overrides' is not concurrency-safe because it is nonisolated global shared mutable state
```

Any task on any thread could read and write it at once, which is a data race. The compiler offers three ways out, and they rank like this:

1. **Make it a `let`** if it never really changes. Constants of `Sendable` types are safe to share.
2. **Inject it** if it's real state: a `FeatureFlags` instance, owned by the composition root and passed to whoever needs it, which tests can replace. (This is [the singleton problem](/design/learn/sd-creational-singleton-alternatives) again, in disguise.)
3. **Isolate it**, with `@MainActor static var`, if it's UI-only state you can't untangle yet. `nonisolated(unsafe)` also silences the error, by promising you've synchronised it yourself; treat it as a debt, not a fix.

## Trade-offs

| | Caseless enum | Struct with `private init()` | Static members on the value's type | An enum with cases | A separate module |
| --- | --- | --- | --- | --- | --- |
| Can be instantiated by mistake | no | no, once you add the `init` | not applicable | only as one of its cases | not applicable |
| Leading-dot syntax at call sites | no | no | yes | yes | no |
| Compiler-checked set of values | no | no | no | yes | no |
| Enforced boundary | no | no | no | no | yes |
| Best for | tokens, endpoints, keys, kata namespaces | rarely needed | colours, fonts, durations, shapes | screens, payment methods, any closed choice | real separation between parts of the app |
