## Why it matters

Every `.padding()`, `.background()` and `.shadow()` you write is a decorator: it wraps a view in a new view that adds layout, drawing or configuration, and leaves the original untouched. Seeing modifiers this way explains why their order changes what's on screen, why SwiftUI needs `some View`, and how to build reusable styling that a whole app shares. Interviewers ask "why do `.padding().background(.yellow)` and `.background(.yellow).padding()` look different?" precisely because the answer shows whether you understand the model or have memorised the API.

## Every modifier wraps the view

A modifier doesn't change the view you call it on. Views are values, and a modifier returns a **new** view that contains the old one. Ask Swift for the type and you can see the layers:

```swift check ios
import SwiftUI

@MainActor func inspect() {
    print(type(of: Text("Sale").padding(12).background(.yellow)))
    print(type(of: VStack { Text("Total") }.font(.headline)))
    print(type(of: Text("Total").font(.headline)))
}
```

```text title="What you'll see"
ModifiedContent<ModifiedContent<Text, _PaddingLayout>, _BackgroundStyleModifier<Color>>
ModifiedContent<VStack<Text>, _EnvironmentKeyWritingModifier<Optional<Font>>>
Text
```

Read the first line from the inside out: a `Text`, wrapped in padding, wrapped in a background. Each `ModifiedContent` is one decorator layer, holding its content and the modifier that decorates it. The underscored names are SwiftUI's private types and can change between releases; the nesting is the part that matters, and it's why `body` returns `some View`. Nobody wants to write that type, and with `some View` the compiler keeps it exact without you spelling it out.

The third line is the exception that proves the rule. `Text` has its own `font(_:)` that returns a `Text`, not a wrapper, which is why you can keep calling `Text`-only methods after it.

## Order matters, because each layer sees only what's inside it

Compare two badges:

- `Text("Sale").padding(12).background(.yellow)`: yellow fills the padded area, a comfortable pill.
- `Text("Sale").background(.yellow).padding(12)`: yellow hugs the letters, with 12 points of clear space around it.

The modifiers are identical; the nesting isn't. To see why, follow how SwiftUI lays the first badge out. A parent **proposes** a size to its child, the child **chooses** its own size, and the parent places it. Every decorator layer takes part:

```visual flow
title: "Laying out Text(\"Sale\").padding(12).background(.yellow)"
nodes:
  - { id: parent, label: Parent, kind: view, at: [0, 0] }
  - { id: background, label: .background, kind: view, at: [2, 0] }
  - { id: padding, label: .padding(12), kind: view, at: [4, 0] }
  - { id: text, label: Text, kind: view, at: [4, 2] }
edges:
  - [parent, background, proposal]
  - [background, padding, proposal]
  - [padding, text, proposal]
steps:
  - say: The parent proposes a size to its child, which is the **outermost** layer, `.background`.
    send: parent->background
    label: { parent->background: 300 × 80 }
  - say: "`.background` passes the same proposal straight on to the view it decorates."
    send: background->padding
    label: { background->padding: 300 × 80 }
  - say: "`.padding(12)` takes 12 points off every side and proposes what's left to `Text`."
    send: padding->text
    label: { padding->text: 276 × 56 }
  - say: "`Text` needs only 38 × 20 for the word, and reports that back."
    send: text->padding
    label: { padding->text: 38 × 20 }
    state: { text: ok }
  - say: The padding layer adds its 12 points back on every side, so it's 62 × 44.
    send: padding->background
    label: { background->padding: 62 × 44 }
    state: { padding: ok }
  - say: "`.background` draws yellow at exactly the size of what it wraps, 62 × 44, so the yellow includes the padding. Swap the two modifiers and the yellow is drawn at 38 × 20, before the padding exists."
    send: background->parent
    label: { parent->background: 62 × 44 }
    state: { background: active }
```

Each layer knows only its content. A background can't know about padding added outside it, and a frame can't size a background that was applied inside it. When a modifier "doesn't work", the first question is always which layer it's wrapping.

## Writing your own modifier

When the same stack of modifiers appears on several screens, give it a name. A `ViewModifier` is a decorator you can reuse, and an extension on `View` makes it read like a built-in:

```swift check ios
import SwiftUI

struct CardStyle: ViewModifier {
    func body(content: Content) -> some View {
        content
            .padding(16)
            .background(.background.secondary, in: .rect(cornerRadius: 12))
            .shadow(color: .black.opacity(0.08), radius: 8, y: 2)
    }
}

struct LoadingOverlay: ViewModifier {
    let isLoading: Bool
    @Environment(\.accessibilityReduceMotion) private var reduceMotion

    func body(content: Content) -> some View {
        content
            .redacted(reason: isLoading ? .placeholder : [])
            .overlay {
                if isLoading {
                    ProgressView()
                }
            }
            .allowsHitTesting(!isLoading)
            .animation(reduceMotion ? nil : .easeInOut, value: isLoading)
    }
}

extension View {
    func cardStyle() -> some View {
        modifier(CardStyle())
    }

    func loadingOverlay(_ isLoading: Bool) -> some View {
        modifier(LoadingOverlay(isLoading: isLoading))
    }
}

struct OrderSummary: View {
    let total: String
    let isLoading: Bool

    var body: some View {
        VStack(alignment: .leading, spacing: 8) {
            Text("Order total")
                .font(.headline)
            Text(total)
                .font(.title2.monospacedDigit())
        }
        .cardStyle()
        .loadingOverlay(isLoading)
    }
}
```

`content` is the view being decorated, opaque to the modifier: it can wrap it, but it can't look inside. That's what makes a modifier reusable on any view. A modifier can also have dependencies of its own: `LoadingOverlay` reads `accessibilityReduceMotion` from the environment, and a modifier can hold `@State` too, because SwiftUI gives it storage just as it does a view.

`CardStyle` could have been a plain `View` extension that chains the three built-ins. Use a `ViewModifier` struct when the decorator needs `@State` or `@Environment`, or when you want to pass it around as a value; the extension is enough otherwise. Either way, this is where a design system starts: named decorators instead of numbers repeated on every screen, which you'll build properly in D62.

## Some decorators configure a whole subtree

The second line of the type printout showed a different kind of modifier. `.font(.headline)` on a `VStack` doesn't draw anything. It wraps the stack in a layer that **writes an environment value**, and every `Text` inside reads it. `.tint(_:)`, `.buttonStyle(_:)`, `.disabled(_:)` and `.environment(_:_:)` work the same way.

So modifiers come in two flavours:

- **Wrapping one view:** `.padding`, `.background`, `.border`, `.clipShape`. They change layout or drawing for exactly the view they wrap.
- **Configuring a subtree:** `.font`, `.tint`, `.buttonStyle`. They decorate the environment, and everything inside inherits it unless it's overridden closer to the leaf.

That second flavour is how style protocols work. A `ButtonStyle` changes how buttons *look* while each button keeps its own role, action and accessibility, and one `.buttonStyle(_:)` high in the tree styles every button below it:

```swift check ios
import SwiftUI

struct PillButtonStyle: ButtonStyle {
    func makeBody(configuration: Configuration) -> some View {
        configuration.label
            .padding(.horizontal, 20)
            .padding(.vertical, 10)
            .background(.tint, in: .capsule)
            .foregroundStyle(.white)
            .opacity(configuration.isPressed ? 0.7 : 1)
    }
}

struct CheckoutButtons: View {
    var body: some View {
        HStack {
            Button("Pay now") {}
            Button("Save for later", role: .cancel) {}
        }
        .buttonStyle(PillButtonStyle())
    }
}
```

Reach for a style protocol when you're customising a *control* everywhere it appears, and for a modifier when you're decorating *any* view. You'll see the style idea again, as two hierarchies varying independently, in the bridge lesson.

## The conditional modifier trap

Sooner or later someone adds this to a codebase, because it reads so nicely:

```swift check ios
import SwiftUI

extension View {
    @ViewBuilder
    func `if`<Modified: View>(_ condition: Bool, transform: (Self) -> Modified) -> some View {
        if condition {
            transform(self)
        } else {
            self
        }
    }
}
```

The `if` inside a view builder produces two branches with different types, and SwiftUI treats them as **two different views**. When `condition` flips, it doesn't modify the view: it removes one and inserts the other. Any `@State` inside resets, a text field loses its focus and what's been typed, and an animation plays as a removal and an insertion instead of a smooth change.

The fix is to keep one view and change a modifier's *value*:

- `.padding(isCompact ? 4 : 16)` instead of `.if(isCompact) { $0.padding(4) }`
- `.opacity(isHidden ? 0 : 1)` instead of adding and removing the view
- `.redacted(reason: isLoading ? .placeholder : [])`, as `LoadingOverlay` does

Branching is right when you genuinely mean two different views. You'll meet the rules behind this, structural identity, in D18.

## Trade-offs

| | `View` extension chaining built-ins | Custom `ViewModifier` | Container view, such as `Card { … }` | Style protocol, such as `ButtonStyle` |
| --- | --- | --- | --- | --- |
| Works on | any view | any view | the content you pass it | one kind of control |
| Own `@State` or `@Environment` | no | yes | yes | yes, plus the control's state (`isPressed`) |
| Arranges other views around the content | awkward | awkward | yes: titles, footers, layout | the control's label only |
| Applies to a whole subtree | no | no | no | yes, through the environment |
| Reads at the call site | `.cardStyle()` | `.cardStyle()` | `Card { … }` | `.buttonStyle(.pill)` |

Start with an extension; promote it to a `ViewModifier` when it needs state or the environment. Use a container view when the decoration includes other views laid out around the content. Use a style when every instance of a control should change together.

<Callout kind="interview">

**What to say:** "Modifiers are decorators: each returns a new view wrapping the old one, and layout flows through the layers, proposals going in and sizes coming out. So a background applied after padding fills the padding." For shared styling: "a `ViewModifier` with an extension, or a style protocol for controls, backed by design tokens."

**What to ask:** whether the style must reach every instance of a control (a style or environment value) or only some views (a modifier).

**Red flags:** an `if` modifier that resets state; `AnyView` used to make two branches' types match, which hides the structure SwiftUI uses to tell views apart; magic numbers repeated across screens instead of named modifiers.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: padding doesn't make empty space tappable">

`Text("Edit").padding(12).onTapGesture { … }` only responds to taps on the letters. The padded area is transparent, and SwiftUI hit-tests the shapes a view actually draws. Add `.contentShape(.rect)` before the gesture: one more decorator, which gives the padded view a hit-testing shape that covers its whole frame.

</Callout>
