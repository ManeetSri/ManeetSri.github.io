## Why it matters

SOLID is the most quoted set of design principles in software, and the one interviewers reach for when they ask you to critique a view controller or "make this testable". It's also widely misunderstood: people recite the five names and then use them to justify a protocol for every class. This module teaches what each principle actually says, where it came from, how it maps onto Swift's protocols, enums, value types and closures, and where it stops helping.

## Five principles, one goal

SOLID is an acronym for five principles about how to arrange code into types and modules:

| Letter | Principle | In one sentence | The question it makes you ask |
| --- | --- | --- | --- |
| **S** | Single responsibility | A module should answer to one source of change. | Who will ask for this code to change? |
| **O** | Open–closed | Add behaviour by writing new code, not by editing code that works. | What do I have to edit to add the next one? |
| **L** | Liskov substitution | Anything that claims to be a `T` must keep `T`'s promises. | Could a caller tell which conforming type it got? |
| **I** | Interface segregation | Don't make clients depend on things they don't use. | How much of this protocol does this caller need? |
| **D** | Dependency inversion | Policy shouldn't depend on detail; both depend on an abstraction the policy owns. | Which way does the `import` point, and who owns the protocol? |

They share one goal: **make the changes you expect cheap, local and safe.** A new payment method, a new analytics vendor, a different cache, a guest mode: each should mean adding a type and a line of wiring, not editing ten files and hoping.

If you've done the coupling and cohesion module, you already have the vocabulary. SRP is cohesion stated as a rule ([Kinds of cohesion, from coincidental to functional](/design/learn/sd-coupling-cohesion)). OCP, ISP and DIP are about the direction and width of coupling ([Dependency direction and stable dependencies](/design/learn/sd-coupling-stable-dependencies)). LSP is about contracts, so that swapping one implementation for another is safe ([Contracts: preconditions, postconditions and invariants](/design/learn/sd-modelling-contracts)).

<Callout kind="analogy">

Think of a building's wiring. Single responsibility: each circuit serves one area, so fixing the kitchen doesn't black out the bedrooms. Open–closed: you add a lamp by plugging into a socket, not by rewiring the wall. Liskov: anything with a standard plug must actually run on 230 volts. Interface segregation: a phone charger doesn't need a three-phase industrial socket. Dependency inversion: the socket standard belongs to the building, and appliance makers build to it, not the other way round.

</Callout>

## Where they came from

The principles are older than the acronym, and each has its own author and context:

- **Open–closed** is Bertrand Meyer's, from *Object-Oriented Software Construction* (1988). His version used inheritance: a finished class stays closed, and you extend it by subclassing.
- **Liskov substitution** comes from Barbara Liskov's 1987 keynote "Data Abstraction and Hierarchy", made precise with Jeannette Wing in 1994 as *behavioural subtyping*. Liskov received the Turing Award in 2008 for contributions that include her work on data abstraction.
- **Robert C. Martin** wrote up OCP (in its polymorphic, interface-based form), LSP, dependency inversion and interface segregation in a series of *C++ Report* articles in 1996, gathered them in the paper "Design Principles and Design Patterns" (2000), and added **single responsibility** in *Agile Software Development: Principles, Patterns, and Practices* (2002), building on Tom DeMarco's and Meilir Page-Jones's work on cohesion.
- **Michael Feathers** noticed the initials spelled SOLID, around 2004, and the name stuck.

That history explains the flavour. These were written for C++ and Java in the 1990s, where class hierarchies were the main tool for reuse, interfaces were the main tool for decoupling, and touching a header file could recompile a large program. Some of the original motivation, such as long rebuilds after editing a widely included header, matters less today. The core ideas about change and dependency still matter a great deal.

## What changes in Swift

Swift gives you more tools than the languages SOLID was written for, so each principle has more than one way to be satisfied:

- **Value types** (structs and enums) can't be subclassed, so most Liskov problems in Swift are about **protocol conformances**, not inheritance.
- **Enums with associated values** give you closed sets checked by the compiler. Open–closed in Swift is often a deliberate choice between an enum (easy to add operations) and a protocol (easy to add types).
- **Protocol composition** (`A & B`) makes interface segregation nearly free: small role protocols combine where needed.
- **Closures** are one-method abstractions. A screen that needs to load a profile can take `() async throws -> Profile` instead of a protocol, which is dependency inversion without any new types.
- **Modules and access control** (Swift packages, `internal`, `package`, `public`) let you enforce which way dependencies point, which is what dependency inversion is really about.
- **Swift 6 concurrency** adds a new kind of contract. An abstraction now says where it runs (`@MainActor`) and whether it can cross threads (`Sendable`), and conforming types must keep those promises too.

## Using them well

Treat the principles as **questions to ask in a design review**, not rules to apply everywhere. Each one names a kind of change and asks whether your design makes it cheap:

1. When the analytics team, the backend team and the designers each want something, do they edit the same file? (SRP)
2. When the next variant arrives, which existing files must change? (OCP)
3. If I hand this code a different implementation, a test double, a guest mode, does it still behave? (LSP)
4. Does this screen know about operations it never calls? (ISP)
5. Can I build and test this feature without its database, network or SDK? (DIP)

Ask them where change is actually happening or clearly coming. Applied to code that never changes, every principle adds indirection and buys nothing. The last lesson in this module, on over-abstraction, is about exactly that line.

## Trade-offs

| Approach | Cost to write | Cost to change later | Testability | Wins when |
| --- | --- | --- | --- | --- |
| Ignore the principles | Lowest | High once the code grows | Poor: everything needs the real world | Prototypes, spikes, code you'll delete |
| Apply them where change happens | Moderate | Low for the expected changes | Good where it matters | Most product code with a future |
| Apply all five everywhere, up front | High | Often *higher*: more types to move | Good, but tests mirror the indirection | Rarely; perhaps a public SDK with many outside clients |

<Callout kind="interview">

**What to say:** name the principle *and the change it protects against*. "This view controller has three reasons to change, so I'd split out the formatting and the persistence" beats "this violates SRP". Mention trade-offs unprompted: "I wouldn't add a protocol here until there's a second implementation or a test that needs one."

**What to ask:** which parts of the product change most often, how many teams touch this code, and what's hard to test today. The answers tell you where the principles pay off.

**Red flags:** reciting definitions without examples; claiming SOLID is always good, or always over-engineering; and confusing dependency inversion with dependency injection (you'll separate them in the DIP lesson).

</Callout>

<Callout kind="gotcha" title="Swift gotcha: SOLID isn't only about classes">

Most SOLID material shows Java class hierarchies, so it's tempting to think Swift's structs, enums and protocols put you beyond its reach. They don't. A struct that conforms to `Hashable` but breaks its rules violates Liskov substitution. An enum switched over in twenty files is an open–closed decision. A protocol with fifteen requirements is an interface segregation problem whether its conformers are classes or not. The principles are about change and dependency, and those exist in every paradigm.

</Callout>
