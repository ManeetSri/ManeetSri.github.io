## Why it matters

Every time you pass a test double, a guest mode, a cached version or a subclass where the real thing is expected, you're relying on substitution: the caller shouldn't be able to tell, or at least shouldn't break. When substitution fails, the bug shows up far from its cause, in code that was correct for every type it was written against. The Liskov substitution principle is the rule that keeps those swaps safe, and in Swift it applies as much to protocol conformances (`Hashable`, your own repository protocols) as to subclasses.

## The substitution rule

Barbara Liskov's idea, from her 1987 keynote, is that a subtype must be usable anywhere its supertype is expected **without the program behaving incorrectly**. Code written against `T` keeps working when it's given any subtype of `T`.

In 1994, Liskov and Jeannette Wing made "without behaving incorrectly" precise as **behavioural subtyping**. In terms of the contracts from [Contracts: preconditions, postconditions and invariants](/design/learn/sd-modelling-contracts), a subtype:

- **can't strengthen preconditions**: it can't demand more of callers than the supertype did (an image loader whose subclass rejects names with spaces);
- **can't weaken postconditions**: it can't promise less than the supertype did (a `save` that sometimes saves nothing);
- **must preserve invariants**: whatever is always true of the supertype stays true (a cart's total is the sum of its lines);
- **can't allow changes the supertype forbids**, the "history rule": a subtype of an immutable type can't become mutable, because callers rely on the value never changing.

Notice what isn't on the list: "the subtype must behave identically". It can do more, do it faster, or do it differently, as long as it keeps every promise callers rely on.

## What Swift checks, and what it can't

The compiler enforces the **signature** half of these rules. A class override may return something more specific and accept something more general, which is exactly "postconditions no weaker, preconditions no stronger" for types:

```swift check title="Variance Swift allows in overrides"
import Foundation

class ImageLoader {
    func image(named name: String) -> Data? { nil }
    func preload(_ names: [String]) {}
}

final class BundledImageLoader: ImageLoader {
    // Promises more: never nil
    override func image(named name: String) -> Data { Data() }
    // Accepts more: nil is fine too
    override func preload(_ names: [String]?) {}
}
```

For protocols, a witness can't add failure modes the requirement doesn't have. A non-throwing requirement can't be satisfied by a throwing method (the opposite is fine), and the same goes for `async`:

```swift
protocol TokenStore {
    func token() -> String?
}

struct KeychainTokenStore: TokenStore {
    func token() throws -> String? { nil }
}
```

```text title="What you'll see"
error: type 'KeychainTokenStore' does not conform to protocol 'TokenStore'
note: candidate throws, but protocol does not allow it
```

Swift 6 adds isolation and `Sendable` to the signature: a requirement declared `@MainActor` or `Sendable` is a promise every conformer must keep, and the compiler checks it.

What the compiler **can't** check is behaviour. A method with exactly the right signature can still ignore its arguments, do nothing, return a placeholder, or crash. That's the half of Liskov that's on you.

## Class hierarchies: the classic breaks

The textbook example is a square that inherits from a rectangle. Geometrically a square *is* a rectangle; behaviourally it isn't, because a rectangle promises that setting its width leaves its height alone:

```swift run title="A subclass that keeps the signatures and breaks the contract"
class Rectangle {
    var width: Double
    var height: Double

    init(width: Double, height: Double) {
        self.width = width
        self.height = height
    }

    var area: Double { width * height }
}

final class Square: Rectangle {
    init(side: Double) {
        super.init(width: side, height: side)
    }

    override var width: Double { didSet { if height != width { height = width } } }
    override var height: Double { didSet { if width != height { width = height } } }
}

// Written against Rectangle's contract: each side can be set on its own
func resizeBanner(_ banner: Rectangle) -> Double {
    banner.width = 320
    banner.height = 50
    return banner.area
}

print(resizeBanner(Rectangle(width: 1, height: 1)))
print(resizeBanner(Square(side: 1)))
```

```output
16000.0
2500.0
```

`resizeBanner` is correct for every `Rectangle`, and still gets the wrong answer. "Is a" in the real world doesn't make a subtype; **"keeps every promise of"** does. The usual fixes are not to relate the types at all (two structs conforming to a `Shape` protocol that only promises `area`), or to make them immutable, so there's no "set the width" promise to break.

In app code the same break looks like this:

- **No-op overrides.** A `GuestProfileViewController` whose `save` does nothing, while the base class's caller shows "Saved". The signature is perfect; the postcondition is gone.
- **"Not supported" overrides.** A read-only subclass that overrides `add(_:)` to throw or `fatalError`. Every caller of the base type now has to know about the subclass, which is the opposite of substitution.
- **Skipping `super`.** UIKit documents that overrides of `viewWillAppear(_:)` and its siblings must call `super` at some point. A subclass that doesn't breaks a precondition the base class relies on, and leaves UIKit's own bookkeeping in a state nobody tested; the bugs that follow are rare and hard to trace.

UIKit's own exception is worth knowing. `required init?(coder: NSCoder) { fatalError("init(coder:) has not been implemented") }` is a deliberate, local break: you're declaring that this view controller can't be created from a storyboard. It's accepted because nobody substitutes it into the archive-loading path; if someone does, it fails at once and loudly rather than silently.

Swift's defaults help keep hierarchies honest. Mark classes `final` unless they're designed for subclassing. A `public` class can't be subclassed outside its module (only `open` can), so a library author chooses where substitution must hold, and you'll see how access control shapes architecture in D06.

## Protocol conformances are subtypes too

Because structs and enums can't inherit, most substitution in Swift happens through protocols, and protocols have **semantic requirements** the compiler never sees. Some from the standard library:

| Protocol | The promise every conformer must keep | What breaks if one doesn't |
| --- | --- | --- |
| `Equatable` | `==` is reflexive, symmetric and transitive | `firstIndex(of:)`, diffing, SwiftUI updates |
| `Hashable` | equal values have equal hashes | `Set`, `Dictionary`, diffable data sources |
| `Comparable` | `<` is a strict total order | `sort()`, `min()`, binary search |
| `Collection` | you can iterate it more than once | anything that walks it twice |
| `RandomAccessCollection` | moving an index any distance is O(1) | algorithms that assume fast `count` and indexing |

The most common Swift substitution bug lives in that second row:

```swift check title="Equal, but hashed differently"
struct AppVersion: Hashable {
    let raw: String

    var components: [Int] {
        var parts = raw.split(separator: ".").map { Int($0) ?? 0 }
        while parts.last == 0 { parts.removeLast() }
        return parts
    }

    // "1.2" and "1.2.0" are the same version…
    static func == (lhs: AppVersion, rhs: AppVersion) -> Bool {
        lhs.components == rhs.components
    }
    // …but `hash(into:)` is still synthesised from `raw`, so they hash differently
}
```

Writing your own `==` doesn't stop the compiler from synthesising `hash(into:)` from every stored property. Now `"1.2"` and `"1.2.0"` are equal but usually land in different hash buckets, so a `Set` can hold both, and a dictionary lookup for a "minimum supported version" can miss. Worse, Swift seeds hashing randomly on each launch, so the bug can appear on one run and vanish on the next. The fix is to hash exactly what `==` compares: `func hash(into hasher: inout Hasher) { hasher.combine(components) }`.

Your own protocols have semantic requirements too, usually unwritten. Here's a debug menu that toggles a setting through a store that "conforms" without keeping the promise:

```visual sequence
title: A store that conforms in signature only

```

## Designing so substitution holds

**Promise only what every conformer can keep.** If some stores can't write, split the protocol into `SettingsReader` and `SettingsWriter` (the subject of the next lesson), and the problem can't be written. If some players can't seek, `Seekable` is a separate capability, not a `seek` that throws "unsupported".

**Make "can't" part of the type.** If a guest's save stays on the device, the result says so: `enum SaveResult { case saved, savedOnDevice }`. Callers then handle it, instead of being told "saved" by a no-op.

**Prefer composition when behaviour varies.** Most no-op and "not supported" overrides exist because inheritance was the only extension point. An injected strategy, a closure or a protocol conformance lets each variant keep its own promises. You'll meet this as composition over inheritance in D05.

**Write the contract down, then test it against every implementation.** One test, many conformers, including the fakes in your test target:

```swift run title="One contract, run against every store"
protocol KeyValueStore {
    func value(for key: String) -> String?
    mutating func set(_ value: String, for key: String)
}

struct MemoryStore: KeyValueStore {
    private var values: [String: String] = [:]
    func value(for key: String) -> String? { values[key] }
    mutating func set(_ value: String, for key: String) { values[key] = value }
}

// Added for guest mode: guests can't save, so set does nothing
struct GuestStore: KeyValueStore {
    func value(for key: String) -> String? { nil }
    mutating func set(_ value: String, for key: String) {}
}

func contractProblems<Store: KeyValueStore>(_ store: Store) -> [String] {
    var store = store
    var problems: [String] = []
    store.set("dark", for: "theme")
    if store.value(for: "theme") != "dark" { problems.append("a value that was set doesn't read back") }
    store.set("light", for: "theme")
    if store.value(for: "theme") != "light" { problems.append("the latest value doesn't win") }
    return problems
}

for (name, problems) in [("MemoryStore", contractProblems(MemoryStore())), ("GuestStore", contractProblems(GuestStore()))] {
    print(name + ":", problems.isEmpty ? "keeps the contract" : problems.joined(separator: "; "))
}
```

```output
MemoryStore: keeps the contract
GuestStore: a value that was set doesn't read back; the latest value doesn't win
```

In a real test target, the same function becomes a generic helper that calls `#expect`, run once per conformer. It also keeps your **test doubles honest**: a fake repository that never throws, or answers instantly when the real one paginates, passes every test and proves nothing about the screen's error handling.

## Trade-offs

| Approach | Reuse | Risk of broken substitution | Testability | Wins when |
| --- | --- | --- | --- | --- |
| Subclass and override | High: inherit everything | High: every override can weaken a promise | Moderate | The base class is designed for it (UIKit controllers and views) |
| `final` classes and structs, composition inside | Moderate | Low | High | Most app types |
| Protocol with a written contract and contract tests | High: any conformer | Low, and caught by tests | High | Several implementations, including fakes |
| Capability split (`Reader` and `Writer`, `Playable` and `Seekable`) | High | Lowest: impossible calls don't compile | High | Some implementations genuinely can't do everything |

<Callout kind="interview">

**What to say:** "A subtype has to keep its supertype's promises: no stronger preconditions, no weaker postconditions." Then point at the concrete break: "This guest subclass makes `save` a no-op, so the caller's 'Saved' message lies." Propose a capability split or composition rather than another override.

**What to ask:** what callers assume about this method. Is the protocol's contract written down anywhere, and do the test doubles keep it?

**Red flags:** overrides that throw "not supported" or call `fatalError`; "a square is a rectangle, so it should inherit"; and custom `==` without a matching `hash(into:)`.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: custom `==` doesn't change the synthesised hash">

If a type conforms to `Hashable` and you write `==` yourself, the compiler still synthesises `hash(into:)` from **all** stored properties. Whenever your `==` ignores or normalises a property (case-insensitive emails, `"1.2"` equal to `"1.2.0"`, an `id`-only equality), write `hash(into:)` too and combine exactly what `==` compares. Equal values with different hashes break `Set`, `Dictionary` and diffable data sources, and because hashing is seeded per launch, the failures come and go.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: `init(coder:)` and `fatalError`">

The `fatalError` in `required init?(coder:)` is an accepted, deliberate break of substitution for view controllers built in code. Don't copy the pattern elsewhere: a `fatalError` or "not supported" error in any other override means the type hierarchy is promising something one member can't do. Reshape the hierarchy instead.

</Callout>

**Layered feature flags** is a capability split in practice: read-only flag sources that can't be written to, a layered store that keeps the writer contract exactly, and tests that run one contract check against every writer.
