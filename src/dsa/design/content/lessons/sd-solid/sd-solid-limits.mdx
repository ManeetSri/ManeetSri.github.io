## Why it matters

The opposite of a massive view controller is as common, and harder to fix: a codebase where every type has a protocol and an `Impl`, every tap goes through six layers, and adding one setting touches nine files. It usually comes from applying SOLID everywhere, in advance, as a rule. Knowing when a principle stops paying for itself is what separates a senior engineer from someone who has memorised the principles, and interviewers test it directly: "isn't this over-engineered?" deserves a better answer than yes or no.

## What indirection costs

Every abstraction the principles suggest (a protocol, a layer, a new type) has a price, even when it's worth paying:

- **A name to invent and learn.** `SettingsRepository`, `SettingsDataSource` and `UpdateSettingUseCase` all have to mean something different, and everyone on the team has to learn which is which.
- **A hop when reading.** In Xcode, Jump to Definition on a call through a protocol lands on the requirement, not on the code that runs. Each hop is another search for the implementation.
- **Changes that cross it get bigger.** Adding a parameter means changing the protocol, the implementation, every fake and every caller. Abstraction makes changes *behind* it cheap and changes *through* it expensive.
- **Wiring and fakes to maintain.** Every protocol needs a live instance at the composition root and usually a fake in tests, and both drift.
- **Runtime cost.** Calls through `any P` are dynamically dispatched and may box their value. In app code this almost never matters; in a tight loop over thousands of elements it can, and generics (`some P`) avoid it.

Here's what that looks like when it accumulates. A dark-mode switch, built "properly":

## Smells of over-abstraction

These signs mean a principle was applied where no change pressure existed:

- **A protocol with one conformer and no fake** that any test uses. The `FooProtocol` and `FooImpl` pair, where the `Impl` suffix exists only because the good name was taken by the protocol.
- **Pass-through layers.** A use case whose body is `try await repository.save(setting)`, a repository that only calls a data source. If you can't describe a layer's job without saying "it calls the next layer", it has none.
- **Speculative extension points.** A plugin system with one plugin, a generic parameter that's always the same type, a strategy protocol for a strategy nobody has asked to vary.
- **Shrapnel.** One small feature spread across fifteen files of one method each, because "single responsibility" was read as "one function per type".
- **Tests that mirror the wiring.** Mocks that check "the use case called the repository once with these arguments". They fail when you restructure and pass when the behaviour is wrong, so they protect the indirection rather than the product.

The most common shape of all, side by side with what it replaces:

```swift check title="Over-abstracted, and plain"
import Foundation

// Over-abstracted: three types, a protocol, one real implementation, and nothing that varies
protocol DateFormattingServiceProtocol: Sendable {
    func shortDate(_ date: Date) -> String
}

struct DateFormattingServiceImpl: DateFormattingServiceProtocol {
    func shortDate(_ date: Date) -> String {
        date.formatted(date: .abbreviated, time: .omitted)
    }
}

enum DateFormattingServiceFactory {
    static func make() -> any DateFormattingServiceProtocol { DateFormattingServiceImpl() }
}

// Plain: the platform already gives you the abstraction
func orderDateText(_ date: Date) -> String {
    date.formatted(date: .abbreviated, time: .omitted)
}
```

`Date.formatted` is already a well-designed, stable, deep abstraction. Wrapping it adds three names and protects against nothing. If tests need a fixed locale or time zone, pass them as values; that's a seam, too.

## The counter-arguments worth knowing

SOLID isn't the only view of good design, and the best-known critiques sharpen your judgement:

- **Deep modules.** John Ousterhout's *A Philosophy of Software Design* (2018) argues that the best modules are **deep**: a small interface hiding a lot of functionality, like `URLSession` or Core Data. Splitting everything into tiny single-purpose types creates shallow modules whose interfaces cost almost as much to learn as their implementations; he calls the habit "classitis". You met the idea in [Modules and interfaces: deep vs shallow](/design/learn/sd-modelling-interfaces). Single responsibility, read as "split by actor", and depth are compatible. Read as "split by verb", they collide.
- **The wrong abstraction.** Sandi Metz's widely quoted line is that "duplication is far cheaper than the wrong abstraction". An abstraction made too early bakes in a guess about what varies, and every later change has to fight it. You'll meet this as AHA, "avoid hasty abstractions", in D05.
- **Properties instead of principles.** Dan North's CUPID (2022) proposes properties to aim for rather than rules to obey: code that's composable, follows the Unix philosophy (does one thing well), is predictable, is idiomatic, and is domain-based. It's a useful second lens, because "is this idiomatic Swift?" catches over-abstraction that SOLID's questions don't.

None of these says the principles are wrong. They say the principles are **tools with costs**, to be used where the change they protect against is real.

## When SOLID earns its keep

| Signal | Points towards abstraction | Points towards plain code |
| --- | --- | --- |
| Change history | This area changes often, in the same direction | It hasn't changed in a year |
| Ownership | Several teams touch it | One person owns it |
| Testing | Rules can't be tested without a device or network | It's pure, or trivial |
| Third parties | A vendor SDK or API you may replace | Apple's stable frameworks used as designed |
| Reuse | Shared by the app, a widget and a watch app | Used in one place |
| Lifetime | Core product, years ahead | A spike, prototype or experiment behind a flag |
| Audience | A public SDK with outside clients | Internal code you can change in one pull request |

The right default for most app code is in the middle: **plain code, with seams added when a test or a second implementation needs one**. The rule of three is a good guide: write it once, copy it the second time if you must, and abstract on the third, when you can see what actually varies.

## Undoing an abstraction

Removing indirection is a refactor like any other, done in small steps with tests passing:

1. **Inline a protocol with one conformer.** Delete the protocol, rename `FooImpl` to `Foo`, and fix the call sites. If a test needed the seam, replace the protocol with a closure the test can supply.
2. **Collapse pass-through layers.** Have the caller call the layer below directly, then delete the empty layer.
3. **Merge shrapnel.** Fold one-method types that always change together back into the type that uses them.
4. **Replace mock-the-wiring tests** with tests of behaviour: given this input, the screen shows this state.

Doing this is not "giving up on SOLID". It's applying the same question the principles ask, "what change does this make cheap?", and accepting the answer "none".

## Before you add an abstraction

Four questions, in order:

1. **What change does it make cheaper?** Name it. "Flexibility" isn't a change.
2. **Has that change happened, or is it planned?** A second implementation, a test that truly needs a fake, a vendor you're about to switch.
3. **Is there a smaller seam?** A closure, a value parameter (`now: Date`), a generic parameter, or a concrete type that's already easy to test.
4. **Can you describe the new layer's job without "calls the next one"?**

## Trade-offs

| Approach | Reading cost | Cost of expected changes | Cost of unexpected changes | Wins when |
| --- | --- | --- | --- | --- |
| Plain code, no seams | Lowest | Moderate to high | Moderate: one place to change | Small, stable, single-owner code |
| Targeted abstraction where change is real | Moderate | Low | Moderate | Most product code |
| Abstraction everywhere, up front | High | Low, if the guesses were right | High: every layer must change | Rarely; perhaps a framework with many outside clients |

<Callout kind="interview">

**What to say:** tie every abstraction to the change it protects against, and be willing to leave one out: "I wouldn't add a repository protocol for settings until there's sync or a second store; `@AppStorage` is enough today, and extracting a protocol later is a small refactor." When asked to review layered code, point to pass-through layers and single-conformer protocols, and propose removing them in small steps.

**What to ask:** how often this area changes, who changes it, and what's painful today. Over-abstraction and under-abstraction have different symptoms; let the symptoms decide.

**Red flags in both directions:** "every class should have a protocol for testability", and "SOLID is enterprise over-engineering". Both replace judgement with a slogan.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: a protocol isn't the only seam">

Swift gives you lighter ways to make code testable than a protocol per dependency. Pass values instead of services (`now: Date` rather than a `ClockProtocol` when you only need the time once). Inject a closure for a single operation. Use a generic parameter when the type is fixed per call site. Test pure functions directly. Reach for a protocol when several operations travel together or several implementations exist, not as the default way to write a test.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: SwiftUI property wrappers are abstractions already">

`@AppStorage`, `@Environment`, `@Query` and `@Observable` already put an abstraction between your view and the store behind it, and SwiftUI previews can feed them sample data. Wrapping `@AppStorage` in a repository and a use case to make a settings screen "testable" usually adds layers without adding a seam you'll use. Add the layers when a rule appears that deserves its own tests.

</Callout>
