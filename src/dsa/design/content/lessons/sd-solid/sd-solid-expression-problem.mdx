## Why it matters

Every feed, form builder, document editor and server-driven screen is a set of **variants** (kinds of card, kinds of field) with a set of **operations** on them (render, measure, track, prefetch). The open–closed lesson ended with a fork: enums make one of those easy to extend, protocols the other. Picking the wrong side is one of the most common Swift design mistakes, and it's expensive to undo once a hundred files depend on it. At senior and staff level, interviewers designing a feed with you expect you to name this trade-off and choose on purpose.

## Two directions of change

Philip Wadler named it the **expression problem** in 1998, after its classic example, a small language of expressions: can you add both new kinds of expression and new operations over them, without editing or recompiling existing code, and without giving up static type checking? Most languages make one direction easy and the other hard.

Picture it as a grid. Rows are variants, columns are operations, and every cell is code someone has to write. The question is which edits a new row or a new column forces on code that already exists:

## The enum side

```swift check title="Feed items as an enum"
enum FeedItem {
    case text(String)
    case image(url: String, aspectRatio: Double)
    case video(url: String, seconds: Int)
}

func height(of item: FeedItem, width: Double) -> Double {
    switch item {
    case .text(let body): 24 * Double(body.count / 40 + 1)
    case .image(_, let aspectRatio): width / aspectRatio
    case .video: width * 9 / 16
    }
}

func analyticsName(of item: FeedItem) -> String {
    switch item {
    case .text: "text"
    case .image: "image"
    case .video: "video"
    }
}
```

What it's good at:

- **New operations are free.** `prefetchURL(of:)` or `accessibilityLabel(of:)` is one new function in any file, even in another module.
- **All the behaviour for one operation sits together**, so you can read "how tall is everything?" in one place.
- **Exhaustiveness is checked.** A new case produces a compile error at every `switch` that doesn't handle it (as long as nobody wrote `default`).
- **Values are plain data**: `Equatable`, `Hashable`, `Codable` and `Sendable` come cheaply, which suits SwiftUI diffing and persistence.

What it costs: every new case edits every function, and only the module that declares the enum can add cases. Other teams can't plug in a card type of their own.

## The protocol side

```swift run title="Adding an operation to a protocol, and the trap"
protocol FeedCard {
    var id: String { get }
    func height(width: Double) -> Double
}

// Added later as an operation on every card, without touching the types
extension FeedCard {
    var accessibilityLabel: String { "Feed item" }
}

struct PollCard: FeedCard {
    let id: String
    let question: String
    func height(width: Double) -> Double { 120 }
    var accessibilityLabel: String { "Poll: \(question)" }    // looks like an override
}

let poll = PollCard(id: "p1", question: "Tea or coffee?")
let feed: [any FeedCard] = [poll]
print(poll.accessibilityLabel)
print(feed[0].accessibilityLabel)
```

```output
Poll: Tea or coffee?
Feed item
```

New card types are free: `PollCard` is one new type, and other modules can add their own. Adding an *operation* is where it goes wrong. The tempting shortcut is a protocol extension, which compiles without touching any type. But a method that's only in an extension is **not a requirement**, so it isn't dynamically dispatched: called through `any FeedCard`, Swift uses the extension's version and ignores `PollCard`'s. VoiceOver users hear "Feed item" for every card.

The fix is to declare it as a requirement, keeping the extension as the default:

```swift check title="A requirement with a default is dispatched dynamically"
protocol FeedCard {
    var id: String { get }
    func height(width: Double) -> Double
    var accessibilityLabel: String { get }    // now a customisation point
}

extension FeedCard {
    var accessibilityLabel: String { "Feed item" }
}
```

Now `feed[0].accessibilityLabel` is "Poll: Tea or coffee?". But look at what that cost: you edited the protocol, every existing card silently gets the generic default (exactly the cards whose accessibility nobody reviewed), and if there's no sensible default, every conforming type must change. That's the protocol's half of the expression problem.

## Swift's partial escapes

No mainstream language makes both directions free, but Swift has several ways to soften the side you didn't pick:

**Retroactive conformance.** Declare a new protocol and conform existing types to it in extensions, in a new file or even another module:

```swift check title="A new operation through a new protocol"
protocol FeedCard {
    var id: String { get }
}

struct TextCard: FeedCard {
    let id: String
    let body: String
}

protocol Prefetchable {
    var prefetchURLs: [String] { get }
}

extension TextCard: Prefetchable {
    var prefetchURLs: [String] { [] }
}

func prefetch(_ feed: [any FeedCard]) -> [String] {
    feed.flatMap { ($0 as? any Prefetchable)?.prefetchURLs ?? [] }
}
```

The types are untouched, but the `as?` cast moved the check from compile time to runtime: a card that forgets to conform is silently skipped. You traded static safety for openness, which Wadler's definition rules out. (Conforming a type you don't own to a protocol you don't own draws a warning in Swift 6 unless you mark it `@retroactive`, because the owner could add the same conformance later and the two would clash.)

**The visitor pattern** turns a protocol hierarchy into something enum-like: each card has one `accept(_ visitor:)` method, and each operation becomes a visitor type. New operations are then cheap, and new cards are expensive again, because the visitor protocol lists every card. It *flips* the trade-off rather than escaping it. In Swift, an enum gives you the same shape with less ceremony, so you'll mostly meet visitors in code ported from other languages and in compiler-like tools (you'll meet them properly in D13).

**A closed enum with an open case.** Keep the cards you own in an enum, and leave one door for others:

```swift check title="Closed core, open edge"
protocol PluginCard {
    var id: String { get }
    func height(width: Double) -> Double
}

enum FeedItem {
    case text(String)
    case image(url: String)
    case plugin(any PluginCard)
}
```

Your operations switch over three cases, and the `.plugin` branch delegates to the protocol. Other teams' cards don't touch your enum, and your own operations stay exhaustive.

## Variants you can't control: the server

On iOS there's a version of this problem with no clean escape. In a server-driven feed, the **server** adds variants, and the app versions already on people's phones can't be modified at all. Your decoding has to plan for cases that don't exist yet:

```swift run title="Decoding a card type this build has never seen"
import Foundation

enum Card: Decodable {
    case text(String)
    case image(url: String)
    case unsupported(type: String)

    private enum Key: String, CodingKey { case type, body, url }

    init(from decoder: any Decoder) throws {
        let container = try decoder.container(keyedBy: Key.self)
        let type = try container.decode(String.self, forKey: .type)
        switch type {
        case "text": self = .text(try container.decode(String.self, forKey: .body))
        case "image": self = .image(url: try container.decode(String.self, forKey: .url))
        default: self = .unsupported(type: type)
        }
    }
}

let json = Data(#"[{"type": "text", "body": "Hello"}, {"type": "poll", "question": "Tea?"}, {"type": "image", "url": "a.jpg"}]"#.utf8)
let cards = try JSONDecoder().decode([Card].self, from: json)
for card in cards {
    switch card {
    case .text(let body): print("text:", body)
    case .image(let url): print("image:", url)
    case .unsupported(let type): print("skipped a \(type) card")
    }
}
```

```output
text: Hello
skipped a poll card
image: a.jpg
```

Here `default` is right, because it's in the *decoder*, mapping open server strings to a closed set, and the rest of the app still switches exhaustively over `Card`. Without the `unsupported` case, a single new card type would fail the decode of the whole array and empty the feed for everyone on an older build. Pair it with a server that knows each client's version and only sends what that version understands.

## Choosing a side

Ask which axis will change more, and **who** changes it:

- **You add operations more often than variants, and you own the variants**: enum. Most app models are like this: payment states, sign-in methods, a settings screen's rows.
- **Others add variants** (feature teams, plugins, a design system's consumers), **or variants grow faster than operations**: protocol, with a registry or the composition root listing the conformers.
- **The server adds variants**: an enum with an `unsupported` case at the decoding boundary, and version negotiation with the server.
- **Both grow fast**: split the problem. Keep the variants an enum and make the busiest operation open (a renderer protocol per case), or keep a protocol and accept that some operations are requirements with defaults that must be reviewed.

## Trade-offs

| Design | New variant | New operation | Static safety | Who can extend | Wins when |
| --- | --- | --- | --- | --- | --- |
| Enum + functions | Edit every switch (compiler finds them) | One new function | Full | Only the declaring module, for cases | You own the set; operations grow |
| Protocol + types | One new type | Edit every type, or a default | Conformance, not behaviour | Anyone | Variants grow, or others add them |
| Protocol + retroactive protocols | One new type | New protocol and extensions | Lost at the `as?` cast | Anyone | Optional capabilities, such as prefetching |
| Visitor | Edit the visitor protocol | One new visitor | Full | Anyone, for operations | Ports of tree-walking code; rarely in apps |
| Enum with `unsupported` or `plugin` case | Server or plugin, no app change | One new function | Full for known cases | Server, other modules | Server-driven UI, plugin points |

<Callout kind="interview">

**What to say:** in a feed or server-driven UI question, say the trade-off out loud: "Card types change on the server weekly, but our operations (layout, analytics, prefetch) are stable, so I'd decode into an enum with an `unsupported` case and keep rendering exhaustive." Mention that old app versions are the most closed code you have, and how the server avoids sending them cards they can't show.

**What to ask:** who adds new card types, how often, and whether older app versions must keep working (they always must; ask how many are in use).

**Red flags:** a protocol per card with operations added later as protocol extensions; a decoder that throws on unknown types; and "protocols are more flexible" without saying flexible in which direction.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: extension methods aren't overridable">

A method declared only in a protocol extension is statically dispatched. Conforming types can define a method with the same name, but calls through `any P`, or through a generic `T: P`, use the extension's version. If an operation should be customisable per type, it has to be a **requirement** in the protocol body, with the extension providing the default. This is the most common way "we added an operation without touching the types" quietly ships the wrong behaviour.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: one unknown case can empty a screen">

`Decodable` enums with raw values (`enum Kind: String, Decodable`) throw `DecodingError.dataCorrupted` on any value they don't know, and the error fails the decode of the whole response. When the server owns the list of variants, decode the discriminator as a `String` and map unknown values to an explicit fallback case, as above.

</Callout>

In **Open pricing rules**, promotions are a protocol, so a new promotion costs one type. Sketch what that does to every rule, and whether an enum of rule kinds would serve better if new explanations arrive more often than new promotions.
