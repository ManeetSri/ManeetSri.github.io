## Why it matters

Every app has a shape, whether anyone chose it or not. Naming that shape, "layered", "event-driven", "a plug-in core", lets you predict what it will be good and bad at before you've written much code, and lets a team argue about the shape instead of about folder names. In interviews, "what architecture would you use here, and why?" is usually a question about styles, and the "why" is what's being scored.

## Style, pattern, architecture

Three words get used interchangeably. They mean different things.

- **An architecture** is the actual structure of *your* system: these modules, these processes, these connections. Every system has exactly one, written down or not.
- **An architecture style** is a named family of architectures that share the same constraints: "components may only call the layer below", "components never call each other, they publish events". Styles are reusable vocabulary. Roy Fielding, who defined REST as a style, put it as a coordinated set of constraints.
- **A design pattern** solves a smaller, recurring problem inside one part of the system: an adapter around an SDK, an observer on a model. You'll meet the classic catalogue in D10–D13.

A rough test: a style shapes how *the whole thing*, or a big part of it, is divided and connected. A pattern shapes a handful of types. MVVM sits on the border, which is why it gets its own family later in this module.

## What a style is made of

Every style describes the same three things.

1. **Components**: the units that hold logic or state. Layers, services, filters, plug-ins.
2. **Connectors**: how components talk. A direct function call, an `async` call across an actor, an event on a bus, a stream of values, an HTTP request, a shared file.
3. **Constraints**: the rules about which components may connect, and how. "Data flows one way." "Plug-ins never import each other." "The server never calls the client first."

The constraints are the point. A style earns its qualities **by forbidding things**:

- A layered style forbids calls upwards, so you can replace the bottom layer (swap a REST client for GraphQL) without touching the top.
- An event-driven style forbids a publisher from knowing its subscribers, so you can add a new reaction without editing the code that triggered it. It also means nobody can answer "what happens when an order is placed?" by reading one function.
- Pipes and filters forbid shared state between filters, so you can reorder or reuse them, and run them in parallel.

<Callout kind="analogy">

A style is like a building's structural system: timber frame, steel frame, load-bearing brick. It doesn't tell you where the kitchen goes, but it decides how tall you can build, how easily you can knock down a wall, and what fails first in an earthquake.

</Callout>

## Constraints you can check

Because a style is a set of rules, you can test whether code obeys it. Here's the layered rule written as a check over a module graph, the kind of thing a CI job runs against your `Package.swift` targets. D01 called checks like this [fitness functions](/design/learn/sd-quality-measuring).

```swift run title="A layering check"
// The layered style as rules a script can check: every module sits in a layer, and imports only
// modules in layers below its own. Two features in the same layer may not import each other.
let layer = [
    "App": 0,
    "Checkout": 1, "Profile": 1,
    "Payments": 2,
    "Networking": 3, "DesignSystem": 3,
]

// What each module imports, as its Package.swift target would declare it
let imports = [
    "App": ["Checkout", "Profile"],
    "Checkout": ["Payments", "Profile", "DesignSystem"],
    "Profile": ["Networking", "DesignSystem"],
    "Payments": ["Networking"],
    "Networking": ["Checkout"],
    "DesignSystem": [],
]

var violations = 0
for module in imports.keys.sorted() {
    for dependency in imports[module, default: []] {
        let from = layer[module]!, to = layer[dependency]!
        if to < from {
            print("✘ \(module) → \(dependency): imports upwards")
            violations += 1
        } else if to == from {
            print("✘ \(module) → \(dependency): imports a neighbour in its own layer")
            violations += 1
        }
    }
}
print(violations == 0 ? "The layering holds" : "\(violations) imports break the style")
```

```output
✘ Checkout → Profile: imports a neighbour in its own layer
✘ Networking → Checkout: imports upwards
2 imports break the style
```

Both violations are real ones you'll see in codebases. `Networking → Checkout` usually starts as "the client needs to clear the basket on a 401", and quietly makes your lowest layer depend on a feature. A style you don't check decays one convenient import at a time.

## One app, several styles

Real systems mix styles, each at its own scale. Step through a typical feed app:

```visual flow
title: Styles at different scales in one app
layers:
  - { label: Device, rows: [0, 2] }
  - { label: Backend, rows: 3 }
nodes:
  - { id: view, label: Feed view, kind: view, at: [0, 0] }
  - { id: model, label: Feed model, kind: service, at: [2, 0] }
  - { id: repo, label: Repository, kind: service, at: [4, 0] }
  - { id: images, label: Image pipeline, kind: service, at: [0, 2] }
  - { id: bus, label: Event bus, kind: queue, at: [2, 2] }
  - { id: cdn, label: Image CDN, kind: cdn, at: [0, 3] }
  - { id: analytics, label: Analytics, kind: external, at: [2, 3] }
  - { id: api, label: Feed API, kind: service, at: [4, 3] }
groups:
  - { id: layered, label: Layers, nodes: [view, model, repo] }
edges:
  - [view, model, load]
  - [model, repo, fetch]
  - [repo, api, GET /feed]
  - [view, images, URL]
  - [images, cdn, download]
  - [model, bus, itemViewed, { style: async }]
  - [bus, analytics, batch, { style: async }]
steps:
  - say: Inside the app, **layers**. The view talks to the model, the model to the repository, and never the other way round.
    active: [layered]
    send: view->model
  - say: The repository is the **client** in a client–server style. It asks; the Feed API answers. The server never calls first.
    send: repo->api
  - say: Images flow through **pipes and filters**. Download, decode and downsample are separate steps that each know only their input and output.
    active: [images, cdn]
    send: images->cdn
  - say: Analytics is **event-driven**. The model announces `itemViewed` and never learns who listens.
    send: model->bus
  - say: Each style earned its place with a quality. Layers buy testability, the pipeline buys performance, events buy decoupling.
    send: bus->analytics
```

The widget for this app would add one more: WidgetKit is a **plug-in host**, and your widget extension is a plug-in that obeys its contract. That's the microkernel style, later in this module.

## How styles divide a system

Styles also differ in *what* they cut along. Mark Richards and Neal Ford call this partitioning:

- **Technical partitioning** splits by kind of code: all views here, all networking there. Layered architecture is the classic example. It's easy to explain, but one feature change touches every layer.
- **Domain partitioning** splits by business capability: Checkout, Profile, Search, each owning its own views, logic and data access. Modular monoliths and microservices partition this way. A feature change usually stays inside one module, at the cost of some duplication.

Most iOS codebases that scale end up domain-first at the top (feature modules) and technical inside each feature (view, view model, repository). Keep this distinction in mind: it comes back in every lesson.

## Trade-offs

A first map of the module. Each row is a lesson.

| Style | Its key constraint | What that buys | What it costs |
| --- | --- | --- | --- |
| Layered | Calls go down, never up | Swappable lower layers, clear roles | Pass-through code; features cut across layers |
| Client–server | Clients ask, servers answer | One source of truth, central control | Latency, offline, old clients in the wild |
| Event-driven | Publishers don't know subscribers | Easy to add reactions | Hard to trace, order and debug |
| Pipes and filters | Filters share no state | Reuse, reordering, streaming | Copying data; awkward for interactive flows |
| Microkernel | Plug-ins only touch the core's contract | Extensible by other teams | Contract design and versioning |
| Modular monolith | One deployable, strict module boundaries | Team independence without a network | Discipline to keep boundaries |
| Distributed | Parts deploy and fail separately | Independent scaling and releases | Network failure, consistency, operations |

None of these is better in general. Each wins when the quality it buys is the one you need most, which is what the last lesson of this module is about.

<Callout kind="interview">

**Say:** name the style *and* the quality it buys you: "Inside the app I'd use feature modules with layers inside each, because testability and parallel work across three squads matter most here."

**Ask:** what the system must be best at. Offline? Many teams? Fast iteration? The answer picks the style.

**Red flags:** naming a style with no reason ("we'll use Clean Architecture"), or treating one style as the answer at every scale. Interviewers also notice when a candidate can't say what a style *forbids*.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: Xcode groups enforce nothing">

Folders named `Presentation`, `Domain` and `Data` in one app target are a hope, not a style. Any file can still use any type. Only module boundaries (Swift packages, frameworks or separate targets) and access control (`internal`, `package`, `public`) make the compiler refuse a forbidden import. If a constraint matters, put it where the compiler can see it, or write a check like the one above.

</Callout>
