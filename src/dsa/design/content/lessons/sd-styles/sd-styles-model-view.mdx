## Why it matters

MVC, MVP, MVVM, MVI, VIPER, TCA: the alphabet soup of iOS architecture. They're all answers to one question, how to keep the screen apart from the logic behind it, and they differ in a few specific choices. See those choices once, side by side, and every later debate gets easier to follow. Interviewers rarely care which one you pick; they care whether you can say what it costs. Part IV of the course gives each its own module; this lesson is the map.

## The shared idea: separated presentation

Every member of the family applies one idea, which Martin Fowler calls **separated presentation**: keep the code that draws the screen apart from the code that decides what the screen should show.

- The **model** holds data and the domain's rules. It knows nothing about screens.
- The **view** draws pixels and reports what the user did. It should decide as little as possible.
- Something in between holds **presentation logic**: "the Sign in button is enabled when the email looks valid", "show 'Updated 5 min ago'".

The patterns differ in three choices:

1. **Who holds presentation logic and presentation state.**
2. **How the view finds out about changes:** it's told directly, it observes, or it renders a new state.
3. **Which way data flows:** both ways freely, or round one loop in one direction.

## One rule, three shapes

Here is the same sign-in rule wired three ways. The model is a plain function; what changes is who calls it and how the result reaches the view.

```swift run title="The same screen logic in MVP, MVVM and unidirectional form"
// The model: the rule all three versions share
func isPlausibleEmail(_ text: String) -> Bool {
    let parts = text.split(separator: "@")
    return parts.count == 2 && parts[1].contains(".")
}

// MVP: the presenter decides, then pushes the result into a passive view through a protocol
protocol SignInView: AnyObject {
    func setSignInEnabled(_ enabled: Bool)
}

final class SignInPresenter {
    weak var view: (any SignInView)?

    func emailChanged(to email: String) {
        view?.setSignInEnabled(isPlausibleEmail(email))
    }
}

final class RecordingView: SignInView {
    var enabled = false
    func setSignInEnabled(_ enabled: Bool) { self.enabled = enabled }
}

// MVVM: the view model exposes state; the view reads (binds to) it and the view model never sees the view
final class SignInViewModel {
    var email = ""
    var isSignInEnabled: Bool { isPlausibleEmail(email) }
}

// Unidirectional: every change is an action, and one pure function makes the next state
struct SignInState: Equatable {
    var email = ""
    var isSignInEnabled = false
}

enum SignInAction {
    case emailChanged(String)
}

func reduce(_ state: SignInState, _ action: SignInAction) -> SignInState {
    var next = state
    switch action {
    case .emailChanged(let email):
        next.email = email
        next.isSignInEnabled = isPlausibleEmail(email)
    }
    return next
}

let typed = "maneet@example.com"

let view = RecordingView()
let presenter = SignInPresenter()
presenter.view = view
presenter.emailChanged(to: typed)
print("MVP: the presenter set enabled =", view.enabled)

let viewModel = SignInViewModel()
viewModel.email = typed
print("MVVM: the view model exposes isSignInEnabled =", viewModel.isSignInEnabled)

let state = reduce(SignInState(), .emailChanged(typed))
print("Unidirectional: the reducer returned isSignInEnabled =", state.isSignInEnabled)
```

```output
MVP: the presenter set enabled = true
MVVM: the view model exposes isSignInEnabled = true
Unidirectional: the reducer returned isSignInEnabled = true
```

All three are testable without a screen, which is the point of the family. Look at what each test needs: MVP needs a fake view to record what it was told; MVVM needs only to read a property; the reducer needs nothing at all, because it's a pure function from one state to the next.

## The family at a glance

| Pattern | Holds presentation logic | The view learns of changes by | Testing | Where you'll see it on iOS |
| --- | --- | --- | --- | --- |
| **Apple MVC** | The view controller | The controller setting views directly | Hard: logic tangled with UIKit lifecycle | UIKit's default template |
| **MVP** | The presenter | The presenter calling a view protocol | Good, with a fake view | UIKit apps that wanted testable logic |
| **MVVM** | The view model | Observing or binding (`@Observable`, Combine) | Good: read the state | The usual SwiftUI shape |
| **Unidirectional** (Redux, Elm, MVI, TCA) | A reducer | Rendering each new state from one store | Excellent: pure functions | TCA, custom stores |
| **VIPER, VIP, RIBs** | Presenter, with an interactor for business logic and a router for navigation | Like MVP | Good, at a cost in boilerplate | Large UIKit codebases |

Two notes on that table. **Classic MVC** from Smalltalk had views observing the model directly; **Apple's** version makes the controller the mediator between a view and a model that never meet, which is why so much logic piles up in view controllers. And in **SwiftUI**, the view struct already does some of a view model's job: it's a cheap description, re-created on every change, with `@State` for local state. That's why some teams skip per-screen view models for simple screens and put an `@Observable` model straight into the view. It's a reasonable choice, the same one as a relaxed layer, and the trade-off is the same: less code, logic that's harder to test once it grows.

## Trade-offs

| | MVC (Apple) | MVP | MVVM | Unidirectional |
| --- | --- | --- | --- | --- |
| Code to write | Least | More: a view protocol per screen | Moderate | Most: actions, state, reducer, effects |
| Testability of screen logic | Low | High | High | Highest |
| Fits SwiftUI | Poorly | Awkwardly (SwiftUI views aren't objects to call) | Naturally | Naturally |
| Handling complex shared state | Poor | Poor | Fair | Strong |
| Learning curve | Low | Low | Low to medium | Medium to high |

MVC wins for small UIKit screens with little logic. MVVM is the default for most SwiftUI apps. Unidirectional pays off when state is shared across many screens, or when the team values exhaustive tests and replayable changes enough to accept the ceremony.

<Callout kind="interview">

**Say:** the choice and its reason. "MVVM with `@Observable` view models: presentation logic is testable by reading properties, and it's the shape SwiftUI expects. If several screens shared a lot of state, I'd consider a unidirectional store for that part."

**Ask:** UIKit or SwiftUI? How big is the team, and what's the codebase already using? Consistency with the rest of the app often beats the "best" pattern.

**Red flags:** treating a pattern as an identity ("we're an MVVM shop"); a view model per view even for a static label; a view model that imports UIKit and holds a view controller; not knowing where navigation lives in the chosen pattern.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: who owns the view model in SwiftUI?">

A view model created in a view's initialiser is re-created every time the parent re-renders, losing its state. Own it with `@State private var model = ProfileModel()` in the view that creates it (for `@Observable` classes), or inject it from a parent that owns it. The older `@StateObject` plays the same role for `ObservableObject`. D18 covers this properly.

</Callout>
