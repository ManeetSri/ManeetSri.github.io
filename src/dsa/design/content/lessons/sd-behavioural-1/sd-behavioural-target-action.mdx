## Why it matters

Every `UIControl` (buttons, switches, sliders, segmented controls, text fields) and every gesture recognizer tells your code about the user through **target–action**, and UIKit's menus and keyboard shortcuts run on the same machinery. It's the simplest of the callback styles, and it has rules of its own: which object is retained, what a missing target means, and when a `UIAction` closure is the better choice. "How does a button tell your code it was tapped?" is a fair warm-up question in an iOS interview.

## A target, an action and an event

Target–action stores three things: the **target** (the object to call), the **action** (a selector, the name of the method to call), and the **control event** that triggers it.

```swift check ios title="Target–action, UIAction and a gesture recognizer"
import UIKit

final class PlayerSettingsViewController: UIViewController {
    private let autoplaySwitch = UISwitch()
    private let speedControl = UISegmentedControl(items: ["1×", "1.5×", "2×"])
    private var saveButton: UIButton!

    override func viewDidLoad() {
        super.viewDidLoad()

        // Target–action: an object, a selector, and the event that triggers it
        autoplaySwitch.addTarget(self, action: #selector(autoplayChanged(_:)), for: .valueChanged)
        speedControl.addTarget(self, action: #selector(speedChanged(_:)), for: .valueChanged)

        // UIAction (iOS 14): the control keeps the closure, so capture self weakly
        saveButton = UIButton(configuration: .filled(), primaryAction: UIAction(title: "Save") { [weak self] _ in
            self?.save()
        })

        // Gesture recognizers use target–action too
        let doubleTap = UITapGestureRecognizer(target: self, action: #selector(resetSpeed))
        doubleTap.numberOfTapsRequired = 2
        speedControl.addGestureRecognizer(doubleTap)

        [autoplaySwitch, speedControl, saveButton].forEach(view.addSubview)
    }

    @objc private func autoplayChanged(_ sender: UISwitch) {
        print("Autoplay \(sender.isOn ? "on" : "off")")
    }

    @objc private func speedChanged(_ sender: UISegmentedControl) {
        print("Speed option \(sender.selectedSegmentIndex)")
    }

    @objc private func resetSpeed() {
        speedControl.selectedSegmentIndex = 0
    }

    private func save() {
        print("Saved")
    }
}
```

The details that matter:

- **Action methods are `@objc`,** because the Objective-C runtime calls them by name. `#selector` checks at compile time that the method exists, so renaming it can't silently break the button.
- **Three signatures are allowed:** no arguments, `(_ sender:)`, or `(_ sender:, forEvent:)` with the `UIEvent`. The sender lets one method serve several controls.
- **Pick the event that means what you mean.** `.touchUpInside` for a tap, `.valueChanged` for switches, sliders, steppers and segmented controls, `.editingChanged` for each change to a text field's text, and `.primaryActionTriggered` for a control's main action, whatever that is for the control.
- **A control can have many targets and actions,** even for the same event.
- **The control doesn't retain its target.** UIKit's header says so plainly. The usual owner of a control is the view controller that is also its target, so there's no cycle to worry about.

### How the action is delivered

A control doesn't call your method directly. It asks the application to deliver the action, and that's what makes the missing-target case useful:

```visual sequence

participants:
  - { id: button, label: UIButton }
  - { id: app, label: UIApplication }
  - { id: target, label: Settings screen }
  - { id: chain, label: Responder chain }
messages:
  - [button, button, touch up inside]
  - [button, app, "sendAction(_:to:from:for:)"]
  - [app, target, "save(_:)"]
  - [app, chain, "save(_:) to the first responder that has it"]
fragments:
  - { kind: alt, label: target set, from: 2, to: 3, else: 3, elseLabel: target is nil }
steps:
  - { upTo: 0, say: "The control tracks the touch itself and decides which control events happened: here, `touchUpInside`." }
  - { upTo: 1, say: "For each matching target and action it calls `sendAction(_:to:for:)`, which hands the action to `UIApplication`." }
  - { upTo: 2, say: "With a target, the application calls the action method on it, passing the control as the sender." }
  - { upTo: 3, say: "With a **nil** target, the application starts at the first responder and walks up the **responder chain** until an object implements the method. That's the next lesson." }
```

## UIAction: closures for controls

iOS 14 added `UIAction`, an object with a title, an image and a handler closure. Pass one as a control's `primaryAction`, or add it with `addAction(_:for:)`. The same `UIAction` can also be a `UIMenu` item, a bar button item's `primaryAction` or a context-menu entry, so a screen can describe "Save" once and use it everywhere.

Two things change compared with target–action:

- **The control retains the closure.** A view controller owns the button, the button owns the action, and an action that captures `self` strongly owns the view controller: a cycle. Capture `[weak self]`, as above.
- **Actions are unique by identifier.** Adding a `UIAction` whose `identifier` matches one already on the control replaces it, and `removeAction(identifiedBy:for:)` removes it, so you don't need to keep the action object around.

SwiftUI has no target–action at all. `Button("Save") { save() }` takes a closure, and `Toggle(isOn: $autoplay)` takes a **binding**: the control writes to your state instead of calling you. When you wrap a UIKit control in `UIViewRepresentable`, its coordinator becomes the target and writes the value back through the binding.

## Not every target is unretained

Target–action appears outside controls too, with different ownership rules:

| API | Holds its target | What to do |
| --- | --- | --- |
| `UIControl.addTarget(_:action:for:)` | No | Nothing special |
| `UIGestureRecognizer(target:action:)` | No | Nothing special |
| `UIBarButtonItem(title:style:target:action:)` | No (`weak`) | Nothing special |
| `Timer.scheduledTimer(timeInterval:target:selector:userInfo:repeats:)` | **Yes**, until invalidated | Use the block form with `[weak self]`, and invalidate |
| `CADisplayLink(target:selector:)` | **Yes**, until invalidated | Call `invalidate()` when the screen goes, or target a small object that forwards weakly |

The timer case bites often: a screen that schedules a repeating timer with `target: self` can't be freed until something invalidates the timer, and the run loop keeps the timer alive in the meantime.

## Trade-offs

| | Target–action | UIAction closure | Delegate |
| --- | --- | --- | --- |
| Ownership | Target not retained | Closure retained: needs `[weak self]` | `weak` property |
| Code location | A separate `@objc` method | Inline at the control | A protocol conformance |
| Sender and event | Passed in | `action.sender` | Passed in |
| Reuse | One method for many controls | One action for button, menu and shortcut | One delegate for many events |
| Nil target | Goes up the responder chain | Not applicable | Not applicable |
| Wins when | Several controls share a handler, or the action should travel the chain | One control, short handler, or shared with a menu | A component has many events and questions |

<Callout kind="interview">
**Say:** "A control stores target, selector and event, and hands the action to `UIApplication`, which calls the target, or walks the responder chain when the target is nil. Controls don't retain targets; `UIAction` closures are retained, so I capture weakly."

**Ask:** Is this control's action handled by the screen that owns it, or by something further up (a menu command, a container)? That decides between a target and a nil-targeted action.

**Red flags:** a repeating `Timer` with `target: self` and no `invalidate()`; `UIAction { _ in self.… }` stored on a control the same object owns; using `.touchDown` for a button (users expect to be able to drag off and cancel).
</Callout>

<Callout kind="gotcha" title="iOS gotcha: the sender is a cast, not a promise">
`@objc func speedChanged(_ sender: UISegmentedControl)` compiles even if you later attach it to a `UISlider`, because selectors don't carry parameter types. The method then receives the wrong kind of object. Keep one action per kind of control, or type the parameter as `UIControl` and check it.
</Callout>
