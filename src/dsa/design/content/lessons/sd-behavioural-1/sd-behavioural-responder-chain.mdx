## Why it matters

When a button with no target is tapped, when the user presses ⌘C, or when a menu item says "Delete", UIKit has to decide which object should act. It asks a chain of objects in turn, starting from the one the user is focused on: the **responder chain**. It's Apple's own chain of responsibility (the pattern after this lesson), and it explains how the keyboard is dismissed, how edit menus and keyboard shortcuts find their target, and how a cell can trigger an action in a view controller it has never heard of. Interviewers ask about it to see whether you know UIKit beyond the views you can see.

## A chain of objects that might handle it

A **responder** is any `UIResponder`: every `UIView`, `UIViewController`, `UIWindow`, `UIWindowScene` and `UIApplication`. Each has a `next` responder, and following `next` from any responder walks up towards the application:

- **A view:** its view controller, if it's that controller's root view; otherwise its superview.
- **A view controller:** the superview of its view for a child controller, the presenting controller for a presented one, the window for the window's root controller.
- **A window:** its window scene. **A scene:** the application. **The application:** the app delegate, if the app delegate is itself a responder.

One responder is special: the **first responder**. It's the object receiving keyboard input (a text field being edited), and the starting point for actions and commands that have no target. Views become it with `becomeFirstResponder()` and give it up with `resignFirstResponder()`.

Touches arrive by a different route first: UIKit hit-tests to find the deepest view under the finger and delivers the touch there; a view that doesn't handle it can pass it up the same chain. D17 covers event delivery and hit-testing in full. Here, the interest is the chain as a design tool.

## Nil-targeted actions

Give a control a **nil target**, and UIKit searches the chain for an object that implements the action, starting from the first responder (or from the control itself when nothing is first responder):

```swift check ios title="Actions that travel the responder chain"
import UIKit

/// Names the action so #selector can refer to it. Any responder may implement it.
@MainActor @objc protocol ProductActions {
    func addToBasket(_ sender: Any?)
}

final class ProductCell: UITableViewCell {
    let addButton = UIButton(configuration: .borderless())

    override init(style: UITableViewCell.CellStyle, reuseIdentifier: String?) {
        super.init(style: style, reuseIdentifier: reuseIdentifier)
        addButton.configuration?.title = "Add"
        // No target: UIKit searches the responder chain for something that implements the action
        addButton.addTarget(nil, action: #selector(ProductActions.addToBasket(_:)), for: .touchUpInside)
        contentView.addSubview(addButton)
    }

    required init?(coder: NSCoder) { nil }
}

final class ProductListViewController: UITableViewController, ProductActions {
    private var products = ["Mug", "Beans", "Grinder"]
    private(set) var basket: [String] = []

    @objc func addToBasket(_ sender: Any?) {
        // The sender is the button; find its row from where it sits in the table
        guard let button = sender as? UIView else { return }
        let point = button.convert(CGPoint.zero, to: tableView)
        guard let indexPath = tableView.indexPathForRow(at: point) else { return }
        basket.append(products[indexPath.row])
    }

    // ⌘B works on the selected row; the command has no target, so it travels the chain too
    override var keyCommands: [UIKeyCommand]? {
        [UIKeyCommand(title: "Add to Basket", action: #selector(addSelectedToBasket), input: "b", modifierFlags: .command)]
    }

    @objc private func addSelectedToBasket() {
        guard let row = tableView.indexPathForSelectedRow?.row else { return }
        basket.append(products[row])
    }

    // The standard Delete action, offered only while a row is selected
    override func delete(_ sender: Any?) {
        guard let row = tableView.indexPathForSelectedRow?.row else { return }
        products.remove(at: row)
        tableView.reloadData()
    }

    override func canPerformAction(_ action: Selector, withSender sender: Any?) -> Bool {
        if action == #selector(delete(_:)) || action == #selector(addSelectedToBasket) {
            return tableView.indexPathForSelectedRow != nil
        }
        return super.canPerformAction(action, withSender: sender)
    }
}

@MainActor
func dismissKeyboard() {
    // The classic nil-targeted action: whoever is first responder resigns
    UIApplication.shared.sendAction(#selector(UIResponder.resignFirstResponder), to: nil, from: nil, for: nil)
}
```

Three techniques are in there:

- **A nil-targeted control action** lets the cell stay ignorant of the controller. An `@objc protocol` names the selector, so `#selector` is checked at compile time without the cell importing the controller.
- **`keyCommands` and the standard edit actions** (`copy(_:)`, `paste(_:)`, `delete(_:)` from `UIResponderStandardEditActions`) are found the same way. That's why ⌘B and the Edit menu work on the selected row without being wired to it. Commands in the iPad menu bar and Mac Catalyst menus, built with `buildMenu(with:)`, are delivered like this too.
- **`canPerformAction(_:withSender:)`** lets a responder say "not right now". UIKit uses it to grey out menu items and to skip a responder while searching. (`target(forAction:withSender:)` is the method that does the searching, and you can override it to redirect an action.)

`dismissKeyboard()` is the classic one-liner: it sends `resignFirstResponder` to whoever is first responder, without knowing which text field that is.

<Callout kind="gotcha" title="iOS gotcha: the search starts at the first responder, not at the button">
If a search field in the navigation bar is being edited, it's the first responder, and a nil-targeted action from a cell starts in *its* chain: search bar, navigation bar, navigation controller, window. The list controller isn't on that path, so the tap does nothing. Nil targets are ideal for commands that should act on whatever is focused; for "this cell's button", a closure or delegate is more predictable.
</Callout>

## SwiftUI has no responder chain

SwiftUI views aren't responders, so you can't send them actions. SwiftUI solves the same problems in the opposite direction: instead of requests bubbling **up**, capabilities flow **down** through the environment. `@Environment(\.dismiss)` hands a view the power to dismiss whatever presented it; `@FocusState` tracks focus; `.focusedValue` and `@FocusedValue` let menu commands (declared with `.commands`) act on the focused window or field. In a mixed app, UIKit's chain still carries actions for the UIKit parts, including hosting controllers.

## Trade-offs

| | Nil-targeted action | Delegate or closure | Notification |
| --- | --- | --- | --- |
| Sender knows the receiver | No, only the action's name | Yes, through a protocol or closure | No |
| Who handles it | The first responder up the chain that can | Exactly the object you set | Every observer |
| Depends on focus | Yes: it starts at the first responder | No | No |
| Disable it | `canPerformAction` | Your own code | Your own code |
| Typing | Selector only; the sender is `Any?` | Fully typed | Untyped payload |
| Wins when | Menus, shortcuts and edit actions that act on whatever is focused | One component reporting to its owner | Many listeners |

<Callout kind="interview">
**Say:** "The responder chain is UIKit's chain of responsibility: a nil-targeted action starts at the first responder and walks `next` until something implements it and `canPerformAction` agrees. That's how the Edit menu and keyboard shortcuts find the focused object."

**Ask:** Should this act on whatever's focused (a command), or on one specific object (a callback)? The answer decides whether the chain is the right tool.

**Red flags:** walking `superview` by hand to find a view controller; relying on nil targets for core flows (they fail silently when nothing handles them); not knowing that SwiftUI views aren't in the chain.
</Callout>
