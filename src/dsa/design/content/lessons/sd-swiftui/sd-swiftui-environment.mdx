## Why it matters

Some data is needed by many views at many depths: the colour scheme, the locale, a theme, the signed-in session, a way to show a toast. Passing it through every initialiser buries the real parameters in noise; reaching for a singleton hides the dependency and breaks previews. SwiftUI gives you two channels instead: the **environment**, for values flowing **down** the tree, and **preferences**, for values flowing **up**. Interviewers ask "how would a deeply nested button get the analytics logger?", and the strong answer weighs explicit parameters against the environment rather than picking one by habit.

## The environment flows down

Every view has a set of `EnvironmentValues` that it inherits from its ancestors. A modifier like `.environment(\.locale, Locale(identifier: "de"))` changes a value **for that subtree only**: everything inside sees the new value, siblings and ancestors don't, and an inner override beats an outer one. A view reads a value with `@Environment(\.key)`.

You use the environment constantly without naming it:

- **System values** SwiftUI fills in: `colorScheme`, `dynamicTypeSize`, `locale`, `horizontalSizeClass`, `scenePhase`, `accessibilityReduceMotion`, `isEnabled`.
- **Modifiers that write it:** `.font(_:)`, `.tint(_:)`, `.disabled(_:)`, `.redacted(reason:)`. `.disabled(true)` on a `Form` sets `isEnabled` to false, and every control inside reads it.
- **Actions** SwiftUI provides as values: `dismiss`, `openURL`, `refresh`. They're structs you call like functions.

Here's both channels on one screen; step through it, then the code shows each piece.

## Your own environment values with `@Entry`

Declare a value once, with a default, and it's available everywhere:

```swift check ios group=env title="CardDensity.swift"
import SwiftUI

enum CardDensity: Sendable {
    case regular, compact
}

extension EnvironmentValues {
    @Entry var cardDensity: CardDensity = .regular
}

extension View {
    /// Reads better at the call site than `.environment(\.cardDensity, …)`
    func cardDensity(_ density: CardDensity) -> some View {
        environment(\.cardDensity, density)
    }
}

struct OrderCard: View {
    let title: String
    @Environment(\.cardDensity) private var density

    var body: some View {
        Text(title)
            .padding(density == .compact ? 8 : 16)
            .background(.quaternary, in: .rect(cornerRadius: 12))
    }
}
```

`@Entry` arrived with Xcode 16 and back-deploys to every iOS version SwiftUI supports. Older code writes the same thing by hand: a type conforming to `EnvironmentKey` with a `static let defaultValue`, plus a computed property on `EnvironmentValues`. Either way, **the default is a design decision**: a view that reads the value always gets something, so it never crashes and its previews work with no setup.

Values can be actions too. A deep view that wants to show a toast shouldn't know who draws toasts; it should call one:

```swift check ios group=env
struct ShowToastAction {
    private let handler: @MainActor (String) -> Void

    init(_ handler: @escaping @MainActor (String) -> Void) {
        self.handler = handler
    }

    @MainActor func callAsFunction(_ message: String) {
        handler(message)
    }
}

extension EnvironmentValues {
    @Entry var showToast = ShowToastAction { _ in }      // default: do nothing
}

struct SaveAddressButton: View {
    @Environment(\.showToast) private var showToast

    var body: some View {
        Button("Save address") { showToast("Address saved") }
    }
}

struct AppRoot: View {
    @State private var toast: String?

    var body: some View {
        SaveAddressButton()
            .environment(\.showToast, ShowToastAction { message in toast = message })
            .overlay(alignment: .bottom) {
                if let toast {
                    Text(toast).padding().background(.thinMaterial, in: .capsule)
                }
            }
    }
}
```

The button depends on a capability, not on the toast system. The root installs the real one; a preview or a test installs one that records the message. That's dependency injection through the environment, which D21 develops properly.

## Objects in the environment

`.environment(session)` puts an `@Observable` object into the environment, and `@Environment(Session.self) private var session` finds it, as the Observable lesson's `PayButton` did. Use it for **shared models** that many views at different depths need: the signed-in session, the cart, the audio player.

The difference from a value: **an object has no default**. Reading one that no ancestor provided crashes with "No Observable object of type Session found". Inject such objects at the root of the app (and of every preview), or declare the property optional, `Session?`, when the view can do without it.

### What a change in the environment costs

Values and objects also differ in **what counts as a change**, and that decides how often readers update.

- **A value** is compared with the one it replaces. Each time the ancestor that sets it runs its body, SwiftUI checks whether the new value differs, and invalidates every view that reads that key if it does. Small `Equatable` values such as `CardDensity` only trigger updates when they really change. A value holding a **closure** is the trap: `AppRoot` above builds a new `ShowToastAction` every time its body runs, and two closures can't be shown equal, so every reader of `showToast` is usually invalidated along with it. That's harmless while the root rarely re-runs, as here, but expensive if it sits high in a busy screen.
- **An object** is the same reference every time, so injecting it never changes anything by itself. Readers update through Observation, only for the properties they read.

So when an action needs state, such as a toast queue, it often reads better as an object: put a `@MainActor @Observable final class ToastCenter` in the environment with a `show(_:)` method, and let only the overlay that draws toasts read its `current` toast. Keep closure-based actions for stateless capabilities, created somewhere that rarely re-runs.

## Preferences flow up

Sometimes a child knows something its ancestor needs: the title it wants in the navigation bar, its size, whether it holds unsaved edits. A **preference** carries that upward. The child sets `.preference(key:value:)`, SwiftUI combines the values from every descendant with the key's `reduce`, and an ancestor reads the result with `.onPreferenceChange(_:perform:)`. `navigationTitle` and `toolbar` work this way: the pushed view declares them and the navigation stack reads them.

```swift check ios group=env
struct UnsavedChangesKey: PreferenceKey {
    static let defaultValue = false

    static func reduce(value: inout Bool, nextValue: () -> Bool) {
        value = value || nextValue()           // dirty if any section is dirty
    }
}

struct AddressSection: View {
    let saved: String
    @State private var draft: String

    init(saved: String) {
        self.saved = saved
        _draft = State(initialValue: saved)     // a draft, seeded once on purpose
    }

    var body: some View {
        Section("Address") {
            TextField("Street", text: $draft)
        }
        .preference(key: UnsavedChangesKey.self, value: draft != saved)
    }
}

struct EditProfileSheet: View {
    @State private var hasUnsavedChanges = false

    var body: some View {
        Form {
            AddressSection(saved: "1 Infinite Loop")
        }
        .cardDensity(.compact)
        .onPreferenceChange(UnsavedChangesKey.self) { hasUnsavedChanges = $0 }
        .interactiveDismissDisabled(hasUnsavedChanges)
    }
}
```

The sheet is a container that doesn't need to know which sections it holds. That's the strength of preferences, and their cost: the flow is implicit, values arrive after the children have been evaluated, and an ancestor that sets state which changes the preferences again can loop. When the parent already owns the data (here, it could own a draft model), plain data flow is clearer. Reach for preferences when the **child** is the only one that knows, as with titles, sizes and anchors.

## Trade-offs

| Mechanism | Direction | Visible at the call site? | If nothing provides it | Previews and tests | When it wins |
| --- | --- | --- | --- | --- | --- |
| Initialiser parameter | Down, one level | Yes | Compile error | Easiest | The default for most data |
| Environment value (`@Entry`) | Down, any depth | No | The default value | Override per preview | Cross-cutting settings and actions: theme, density, toast, analytics |
| Environment object | Down, any depth | No | Crash, unless optional | Inject a fake | Shared models: session, cart, player |
| Preference | Up, combined | No | The default value | Read in the container | A child declaring facts: titles, sizes, dirty flags |
| Singleton or global | Everywhere | No | n/a | Hard to replace | Rarely, and never reached from views |

<Callout kind="interview">

**Say:** "Parameters by default, because they're explicit and checked by the compiler. The environment when many views at different depths need the same thing, such as a theme, a logger or an action, with a safe default so previews work with no setup. Objects in the environment for shared models, injected at the root. Preferences when a child knows something its container needs." **Ask:** "How many views need this, and how deep are they?" **Red flags:** putting everything in the environment (dependencies nobody can see, crashes when one is missing), singletons called from views, and per-row data passed through the environment instead of parameters.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: a hosting controller starts a new environment">

A `UIHostingController` you create in UIKit begins its own SwiftUI tree. Values and objects set with `.environment` in another hierarchy don't reach it; only what the system derives from traits, such as the colour scheme and Dynamic Type, carries over. Inject at the root view you give the hosting controller, ideally from one helper that every hosting controller uses.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: fast-changing values don't belong in the environment">

Every view that reads an environment value is invalidated when it changes. A scroll offset or a progress value written into the environment re-runs every reader on every frame. Keep high-frequency values in an observable model read by a small leaf view.

</Callout>
