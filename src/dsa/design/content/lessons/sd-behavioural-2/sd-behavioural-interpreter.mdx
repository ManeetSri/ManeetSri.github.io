## Why it matters

Apps are full of tiny languages. Deep-link routes like `/users/:id/posts/:post`, the path patterns in an `apple-app-site-association` file, `NSPredicate` format strings and `#Predicate`, regular expressions, search syntax like `from:alex has:photo`, and the feature-flag targeting rules a server sends down. The **Interpreter** pattern is how you build one: turn the grammar into types, parse sentences into a tree, and evaluate the tree. Interviewers meet it in "design a deep-link router" and "how does the app decide who sees this feature?", where the strong answer treats routes and rules as **data the app interprets**, not `if` statements scattered through the code.

## The pattern

The Gang of Four's intent: given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language. In practice that's three steps:

1. **A grammar**: the rules for what a sentence looks like.
2. **An abstract syntax tree (AST)**: one type per grammar rule, so a parsed sentence is a tree of values. Leaves are *terminal* expressions (a literal word, a number); inner nodes are *nonterminal* ones (an `and` of two conditions).
3. **An interpreter**: a function that walks the tree against some context (a URL, a user) and produces a result.

In Swift the AST is almost always an enum, often `indirect`, and the interpreter is a recursive switch over it: the enum-and-switch form of a visitor from [the previous lesson](/design/learn/sd-behavioural-visitor). The pattern's real lesson is the pipeline around it: **parse once, early, into a checked tree; interpret many times.**

## A route grammar

Here's the grammar for deep-link paths. A pattern is a list of segments separated by `/`, and each segment is a literal word, a named parameter (`:id`), or a `*` that captures everything left:

```text
pattern = segment ("/" segment)*
segment = literal | ":" name | "*"
```

The parser checks the rules a string can't express: no empty segments, no parameter named twice, and `*` only at the end. It throws a typed error (Swift 6's `throws(PatternError)`), so a bad pattern is caught where it's written. The interpreter then matches paths against the segments, and a small router maps each match to a typed `Route`:

```swift run title="A route pattern parser, interpreter and router"
import Foundation

// The grammar:  pattern = segment ("/" segment)*   segment = literal | ":" name | "*"
enum Segment: Equatable {
    case literal(String)
    case parameter(String)
    case rest          // "*": everything that's left, and only allowed last
}

enum PatternError: Error {
    case empty, emptySegment, duplicate(String), restNotLast
}

struct RoutePattern {
    let segments: [Segment]

    // Parsing: text in, a checked tree (here, a list) out. Done once, at launch or in a test.
    init(_ text: String) throws(PatternError) {
        let parts = text.split(separator: "/", omittingEmptySubsequences: false).dropFirst()
        guard !parts.isEmpty else { throw .empty }
        var names: Set<String> = []
        segments = try parts.map { (part) throws(PatternError) -> Segment in
            if part.isEmpty { throw .emptySegment }
            if part == "*" { return .rest }
            guard part.hasPrefix(":") else { return .literal(String(part)) }
            let name = String(part.dropFirst())
            guard names.insert(name).inserted else { throw .duplicate(name) }
            return .parameter(name)
        }
        if let index = segments.firstIndex(of: .rest), index != segments.count - 1 { throw .restNotLast }
    }

    // Interpreting: walk the segments against a path, collecting parameters
    func match(_ path: [String]) -> [String: String]? {
        var captured: [String: String] = [:]
        for (index, segment) in segments.enumerated() {
            switch segment {
            case .rest:
                captured["*"] = path.dropFirst(index).joined(separator: "/")
                return captured
            case .literal(let word):
                guard index < path.count, path[index] == word else { return nil }
            case .parameter(let name):
                guard index < path.count else { return nil }
                captured[name] = path[index]
            }
        }
        return path.count == segments.count ? captured : nil
    }
}

enum Route {
    case profile(userID: Int)
    case post(userID: Int, postID: Int)
    case settings
    case help(topic: String)
}

struct Router {
    private var table: [(RoutePattern, ([String: String]) -> Route?)] = []

    mutating func add(_ pattern: String, _ build: @escaping ([String: String]) -> Route?) throws(PatternError) {
        table.append((try RoutePattern(pattern), build))
    }

    // First match wins, so order the table from specific to general
    func route(for url: URL) -> Route? {
        let path = Array(url.pathComponents.dropFirst())   // drop the leading "/"
        for (pattern, build) in table {
            if let parameters = pattern.match(path), let route = build(parameters) { return route }
        }
        return nil
    }
}

var router = Router()
try router.add("/settings") { _ in .settings }
try router.add("/users/:id") { p in
    p["id"].flatMap(Int.init).map { .profile(userID: $0) }
}
try router.add("/users/:id/posts/:post") { p in
    guard let user = p["id"].flatMap(Int.init), let post = p["post"].flatMap(Int.init) else { return nil }
    return .post(userID: user, postID: post)
}
try router.add("/help/*") { p in
    p["*"].map { .help(topic: $0) }
}

for path in ["/users/42", "/users/42/posts/7", "/users/alex", "/help/billing/refunds", "/settings/advanced"] {
    let route = URL(string: "https://example.com" + path).flatMap(router.route(for:))
    print(path, "→", route.map { "\($0)" } ?? "no match")
}

for bad in ["/users/:id/friends/:id", "/files/*/edit", "/users//posts"] {
    do throws(PatternError) {
        _ = try RoutePattern(bad)
    } catch {
        print(bad, "is rejected:", error)
    }
}
```

```output
/users/42 → profile(userID: 42)
/users/42/posts/7 → post(userID: 42, postID: 7)
/users/alex → no match
/help/billing/refunds → help(topic: "billing/refunds")
/settings/advanced → no match
/users/:id/friends/:id is rejected: duplicate("id")
/files/*/edit is rejected: restNotLast
/users//posts is rejected: emptySegment
```

The design choices are the lesson:

- **Two stages.** Patterns are parsed when the router is built, so `/files/*/edit` fails in a unit test, not when a user taps a link. Matching never parses anything.
- **Typed output.** `/users/alex` matches the pattern's *shape* but its builder rejects a non-numeric id, so the router moves on. Everything after the router sees `Route.profile(userID: 42)`, never `["id": "42"]`.
- **Order is part of the language.** First match wins, so the table runs from specific to general. Universal links on iOS work the same way, which is worth knowing when you write the file Apple's system interprets for you.

### A language you configure but don't write

Universal links are decided by iOS before your app runs, using the `components` patterns in your site's `apple-app-site-association` file. `*` matches any run of characters and `?` exactly one; components are checked in order and the first match decides, including `exclude` rules:

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["ABCDE12345.com.example.travel"],
        "components": [
          { "/": "/help/website/*", "exclude": true },
          { "/": "/help/*" },
          { "/": "/trips/*", "?": { "ref": "?*" } }
        ]
      }
    ]
  }
}
```

Swap the first two entries and `/help/website/cookies` opens the app instead of Safari. Knowing it's an ordered interpreter makes that bug obvious. D20 covers universal links end to end.

## Apple's interpreters: strings vs trees

`NSPredicate` and `#Predicate` express the same idea, and the difference between them is a lesson in interpreter design.

```swift check title="One rule, two ways"
import Foundation

struct Trip {
    var city: String
    var nights: Int
    var isBooked: Bool
}

// The macro checks this at compile time and builds an expression tree, not a closure
let longUnbookedBreaks = #Predicate<Trip> { trip in
    trip.nights >= 3 && !trip.isBooked
}

let lisbon = Trip(city: "Lisbon", nights: 4, isBooked: false)
let matches = try longUnbookedBreaks.evaluate(lisbon)   // interpreted in memory

// The string version is parsed at run time: a typo here is a crash, not a compile error
let sameRule = NSPredicate(format: "nights >= %d AND isBooked == NO", 3)
```

- `NSPredicate(format:)` parses a string **at run time** into a tree of comparison and compound predicates. Core Data translates that tree to SQL. A misspelt key path or a stray quote is found by a crash, in front of a user.
- `#Predicate` (iOS 17) is a macro: the compiler type-checks the closure and builds a tree of `PredicateExpressions` values. SwiftData **translates** the tree into a database query; `evaluate(_:)` **interprets** it in memory. One tree, two interpreters.

That second point generalises. Once a rule is a tree, you can do more with it than evaluate it: translate it to SQL or a server query, print it for a debug screen, check it for contradictions. A closure can only be called.

## Rules as data: interpreting what the server sends

Feature-flag targeting is a language the server writes and the app interprets. A rule like "app version 8.2 or later, and either in the UK or Ireland, or a beta tester" arrives as JSON and decodes into a tree:

```swift check title="A targeting rule, decoded and interpreted"
import Foundation

struct UserContext: Sendable {
    var appVersion: [Int]       // [8, 2, 0]
    var country: String
    var isBetaTester: Bool
}

// A targeting rule as the server sends it, decoded into a tree
indirect enum Condition: Decodable, Sendable {
    case all([Condition])
    case any([Condition])
    case not(Condition)
    case versionAtLeast([Int])
    case countryIn([String])
    case betaTester
    case unknown                 // an operator this build doesn't understand

    func evaluate(in user: UserContext) -> Bool {
        switch self {
        case .all(let conditions): conditions.allSatisfy { $0.evaluate(in: user) }
        case .any(let conditions): conditions.contains { $0.evaluate(in: user) }
        case .not(let condition): !condition.evaluate(in: user)
        case .versionAtLeast(let minimum): !user.appVersion.lexicographicallyPrecedes(minimum)
        case .countryIn(let countries): countries.contains(user.country)
        case .betaTester: user.isBetaTester
        case .unknown: false     // fail closed: never switch a feature on by accident
        }
    }

    private enum Key: String, CodingKey { case all, any, not, versionAtLeast, countryIn, betaTester }

    init(from decoder: any Decoder) throws {
        let json = try decoder.container(keyedBy: Key.self)
        if let list = try json.decodeIfPresent([Condition].self, forKey: .all) { self = .all(list) }
        else if let list = try json.decodeIfPresent([Condition].self, forKey: .any) { self = .any(list) }
        else if let inner = try json.decodeIfPresent(Condition.self, forKey: .not) { self = .not(inner) }
        else if let version = try json.decodeIfPresent([Int].self, forKey: .versionAtLeast) { self = .versionAtLeast(version) }
        else if let countries = try json.decodeIfPresent([String].self, forKey: .countryIn) { self = .countryIn(countries) }
        else if json.contains(.betaTester) { self = .betaTester }
        else { self = .unknown }
    }
}
```

```json
{ "all": [
    { "versionAtLeast": [8, 2] },
    { "any": [{ "countryIn": ["GB", "IE"] }, { "betaTester": true }] }
] }
```

Two decisions here matter more than the code. **Unknown operators fail closed**: an app from last year that receives a newer operator treats it as false, so it never shows a feature it can't support. And the language has **no loops, variables or functions**: it selects among behaviours the app already ships. That keeps evaluation fast and predictable, and it's the line App Review guideline 2.5.2 draws: apps may not download code that adds or changes features, but configuration that chooses between existing ones is everyday practice.

D54 builds a whole flag client on top of rules like these.

## Designing a mini-language that stays mini

- **Parse early, interpret often.** Parse built-in patterns at launch and in tests; parse server-sent rules once when they arrive, not on every evaluation.
- **Return typed results.** A router returns `Route`, a rule returns `Bool`, a query returns a typed filter. Raw dictionaries stop at the interpreter's edge.
- **Make failure safe and visible.** Unknown operators fail closed, unknown components render nothing, and both are logged so you know which app versions are behind.
- **Bound the input.** A server-sent tree 10,000 levels deep will overflow the stack of a recursive interpreter. Cap the depth and size when decoding.
- **Know when to stop.** Once the language wants precedence rules, variables or user-defined functions, it isn't mini any more. Use an existing one (regex, `#Predicate`, a parsing library) rather than growing your own.

## Trade-offs

| | `if` statements in code | Mini-language you interpret | Runtime string DSL (`NSPredicate(format:)`) | Compile-time DSL (`#Predicate`, `Regex` builder) |
| --- | --- | --- | --- | --- |
| Change without an app release | No | Yes, if the server sends it | Yes | No |
| Errors found | At compile time | At parse time: tests, or when rules arrive | At run time, often as a crash | At compile time |
| Can be inspected, translated, logged | No | Yes: it's a tree | Partly | Yes |
| Cost to build | None | Parser, AST, interpreter, tests | None: it's Apple's | None: it's Apple's |
| Risk | Rules scattered across the app | A language that keeps growing | Typos and injection | Limited to what the macro supports |

**Plain code** wins for rules that change only with releases. **Your own mini-language** wins for routes, targeting and anything ops or product teams change without a release, provided it stays declarative and small. **Apple's DSLs** win whenever they cover the job: prefer the compile-checked forms to their string ancestors.

<Callout kind="interview">

In a deep-link router design, say: patterns are parsed once into segments at launch and covered by table-driven tests; matching walks segments against path components; the result is a typed route enum handed to the coordinator; order runs from specific to general; unknown links fall back to a safe default screen. For server-driven rules, say you decode into a tree, evaluate locally, fail closed on unknown operators and cap depth. Questions to ask: *Who writes these rules, and how often do they change? What should an old app do with a rule it doesn't understand?* Red flags: parsing URL strings with `components(separatedBy:)` in five places, routes returning `[String: Any]`, and rules evaluated by building format strings at run time.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: never build a predicate format string from user input">

`NSPredicate(format: "name == '\(query)'")` breaks on the first apostrophe ("O'Brien") and lets input change the predicate's meaning: injection, Core Data style. Pass values as arguments, `NSPredicate(format: "name == %@", query)`, so the parser treats them as values, or use `#Predicate`, where the compiler does it for you.

</Callout>
