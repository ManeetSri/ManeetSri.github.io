## Why it matters

Some collaborators are optional by nature: analytics in a widget extension, logging in a preview, haptics on an iPad, a crash reporter in tests. Making them `Optional` spreads `?.` and `if let` through every call site, and each one is a chance to forget. A **null object** is a real implementation that does nothing, so callers never check. SwiftUI's `EmptyView` is one you use daily. The interview angle is judgement: when "do nothing" is a safe default, and when it hides a bug.

## The pattern

A null object implements the same protocol as the real thing, with behaviour that's deliberately empty: `track` sends nothing, `record` logs nothing, `play` makes no sound. Callers hold a non-optional dependency and call it unconditionally. The pattern isn't in the Gang of Four's book; Bobby Woolf described it a few years later, in *Pattern Languages of Program Design 3* (1997).

The classic case is analytics. Every screen tracks events; previews, widgets and unit tests shouldn't send any. Put a null object in the SwiftUI environment as the default, and inject the real client once at the app's root:

```swift check ios title="A null object as the environment's default"
import SwiftUI
import os

protocol Analytics: Sendable {
    func track(_ event: String)
}

// The null object: a real implementation that does nothing
struct NoAnalytics: Analytics {
    func track(_ event: String) {
        #if DEBUG
        Logger(subsystem: "com.example.shop", category: "analytics").debug("Not sent (no analytics configured): \(event)")
        #endif
    }
}

extension EnvironmentValues {
    // Previews, widgets and tests get the null object unless someone injects a real one
    @Entry var analytics: any Analytics = NoAnalytics()
}

struct CheckoutButton: View {
    @Environment(\.analytics) private var analytics

    var body: some View {
        Button("Pay now") {
            analytics.track("checkout_pay_tapped")   // no optional chaining, no if-let
        }
    }
}
```

The app's root view adds `.environment(\.analytics, LiveAnalytics())`, and every view below it sends real events. Nothing else changes between the app, a preview and a test. Notice the debug log: this null object *whispers*. If someone forgets the root injection, events don't vanish silently in a debug build; the console says so.

## You already use null objects

Apple's frameworks are full of them, usually named "empty":

- **`EmptyView`**: a view that draws nothing and takes no space. It's the default for generic slots, such as a container's optional accessory, so the container's code never handles "no accessory".
- **`EmptyModifier.identity`**: a view modifier that changes nothing, handy when a function must return *some* modifier.
- **`Empty`** in Combine: a publisher that finishes at once without a value.
- **`OSLog.disabled`**: pass it to `Logger` and every log call becomes a no-op.
- **An empty collection.** `for item in []` runs zero times; nobody writes `if let items`. Returning `[]` rather than `nil` for "no results" is the null object you reach for without thinking.

The last one points at a deeper idea: a null object is often an **identity element**. An analytics client that forwards to a list of destinations does nothing when the list is empty; a rule that is the `all` of no conditions is always satisfied (you'll meet that in the next lesson); an empty stack in a view hierarchy renders nothing. Designing composites so the empty case is the null object means the "nothing configured" path needs no special code.

## Null object or Optional?

Swift has optionals built into the language, so you need the pattern less than Java developers did. The deciding question is **whether the caller should care that the thing is missing**.

- **Use `Optional`** when absence means something: no signed-in user (show the sign-in button), no cached image (show a placeholder), no search result (show "nothing found"). The compiler then makes every caller handle it, which is what you want.
- **Use a null object** when absence is uninteresting to the caller: "record this event if anyone is listening". The caller's job is the same either way, so it shouldn't have to branch.

And there's a third option, for dependencies that are **required**: neither. If the payment screen has no payment client, doing nothing is a bug that loses money. Don't paper over it with a null object; make the dependency non-optional with no default, so forgetting it doesn't compile.

## Trade-offs

| | Optional and `?.` | Null object | Required, no default |
| --- | --- | --- | --- |
| Call sites | Branch or chain at each one | Call unconditionally | Call unconditionally |
| Missing collaborator | Compiler forces a decision | Silently does nothing (unless it whispers) | Doesn't compile |
| Previews, tests, extensions | `nil` | The null object | A fake or stub every time |
| Hides configuration bugs | No | Yes, if it's the production default | No |
| Best for | Absence that changes behaviour | Absence that shouldn't | Collaborators the feature can't work without |

**Optional** wins when the caller would do something different. **A null object** wins for cross-cutting, fire-and-forget collaborators: analytics, logging, haptics, performance tracing. **Required** wins for anything whose absence is a defect: storage, payments, authentication.

<Callout kind="interview">

When you design an SDK or a cross-cutting service, say what happens before it's configured: "calls before `configure()` are no-ops through a null object, and the SDK logs a warning once, so a misconfigured app never crashes but the developer finds out." For app code, say which dependencies are optional, which have null-object defaults for previews and tests, and which are required. Red flag: a null-object default on something that matters, such as `init(payments: PaymentClient = NoPayments())`, which turns a missing dependency into a silent failure in production.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: a null object can swallow a missing environment value">

Environment values flow down the SwiftUI view tree from where you inject them. A view hosted in a `UIHostingController` you create by hand isn't below that point, so it starts from the defaults, and with `@Entry var analytics: any Analytics = NoAnalytics()` its events quietly go to the null object. Inject again in the hosting controller's root view, and keep the debug log in the null object (as above): it's the cheapest way to notice.

</Callout>
