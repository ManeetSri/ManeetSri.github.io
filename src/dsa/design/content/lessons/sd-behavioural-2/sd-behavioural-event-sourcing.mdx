## Why it matters

Most apps store **current state**: the shopping list as it is now. **Event sourcing** stores what *happened* instead (an item was added, renamed, checked, removed) and works out the current state by replaying those events. You'll rarely event-source a whole iOS app, but pieces of the idea are everywhere: offline outboxes of pending changes, undo logs, audit trails, sync engines and collaborative editing. Interviewers bring it up in offline-first, messaging and sync designs, and when they ask how you'd reproduce a bug from a user's data. This lesson is a preview; D39 builds sync on top of it.

## State is a fold over events

An **event** is a fact in the past tense: `itemAdded`, `itemChecked`. Events go into an append-only **log**. Nothing is ever updated or deleted in place; a correction is another event (`itemRenamed`).

The current state is what you get by starting empty and applying every event in order. That's a reduce, with the reducer you wrote in [Reducers: state changes as pure functions](/design/learn/sd-functional-reducers): `state = events.reduce(initial, apply)`. The difference is that you **keep the log** and treat the state as a disposable, derived view of it.

<Callout kind="analogy">

A bank doesn't store your balance and edit it. It stores transactions, and the balance is the sum of them. If the balance looks wrong, the statement shows exactly how it got there, and fixing a mistake means adding a correcting transaction, not rubbing one out.

</Callout>

Keep events apart from **commands**. A command is a request that may be refused: "check item 3" fails if item 3 was removed on another device. An event is the record that something *did* happen. The [Command pattern](/design/learn/sd-behavioural-command) gave requests a type; event sourcing gives their outcomes a permanent home.

## A shopping list, event-sourced

```swift run title="Replaying a log, travelling in time, and starting from a snapshot"
// Facts, in the past tense. Once appended, never edited.
enum ListEvent {
    case itemAdded(id: Int, name: String)
    case itemRenamed(id: Int, name: String)
    case itemChecked(id: Int)
    case itemRemoved(id: Int)
}

struct Item {
    let id: Int
    var name: String
    var isChecked = false
}

// A projection: the current list, derived by applying events in order
struct ShoppingList {
    private(set) var items: [Item] = []

    mutating func apply(_ event: ListEvent) {
        switch event {
        case .itemAdded(let id, let name):
            items.append(Item(id: id, name: name))
        case .itemRenamed(let id, let name):
            if let index = items.firstIndex(where: { $0.id == id }) { items[index].name = name }
        case .itemChecked(let id):
            if let index = items.firstIndex(where: { $0.id == id }) { items[index].isChecked = true }
        case .itemRemoved(let id):
            items.removeAll { $0.id == id }
        }
    }

    var summary: String {
        items.map { "\($0.isChecked ? "[x]" : "[ ]") \($0.name)" }.joined(separator: ", ")
    }
}

func replay(_ events: some Sequence<ListEvent>, from start: ShoppingList = ShoppingList()) -> ShoppingList {
    events.reduce(into: start) { list, event in list.apply(event) }
}

let log: [ListEvent] = [
    .itemAdded(id: 1, name: "Milk"),
    .itemAdded(id: 2, name: "Bread"),
    .itemAdded(id: 3, name: "Eggs"),
    .itemRenamed(id: 2, name: "Sourdough"),
    .itemChecked(id: 1),
    .itemRemoved(id: 3),
]

print("now:", replay(log).summary)
print("after 3 events:", replay(log.prefix(3)).summary)   // time travel

// A second projection of the same facts
let activity = log.map { event -> String in
    switch event {
    case .itemAdded(_, let name): "added \(name)"
    case .itemRenamed(_, let name): "renamed to \(name)"
    case .itemChecked: "checked an item"
    case .itemRemoved: "removed an item"
    }
}
print("activity:", activity.suffix(3).joined(separator: "; "))

// A snapshot (a memento) after 4 events, so launch replays only the tail
let snapshot = replay(log.prefix(4))
let fromSnapshot = replay(log.dropFirst(4), from: snapshot)
print("from snapshot:", fromSnapshot.summary, "· replayed", log.count - 4, "events")
```

```output
now: [x] Milk, [ ] Sourdough
after 3 events: [ ] Milk, [ ] Bread, [ ] Eggs
activity: renamed to Sourdough; checked an item; removed an item
from snapshot: [x] Milk, [ ] Sourdough · replayed 2 events
```

Each line shows something a current-state store can't do without extra work:

- **Time travel.** The state after any event is a replay of a prefix. Debugging a user's report becomes "replay their log and watch where it goes wrong".
- **Many projections.** The list and the activity feed are two folds over the same facts. Adding a third (a count badge, a search index) needs no migration: replay the log into it.
- **Snapshots keep replay fast.** A snapshot is a [memento](/design/learn/sd-behavioural-memento) of a projection at a known position in the log. Launch loads the snapshot and replays only the events after it.

## What it costs

Event sourcing trades simple writes for permanent obligations. These are the ones that bite:

- **Events are forever, so their schema is too.** Every build must read every event any earlier build wrote. Renaming a field means keeping a decoder for the old shape, or **upcasting**: converting old events to the new shape as they're read.
- **The log only grows.** Snapshots fix replay time but not storage. Long-lived logs need compaction: replace a prefix with a snapshot once nobody can need the history.
- **Deleting is hard.** "Delete my data" collides with "never delete events". Systems handle it by compacting the user's events away, or by encrypting each user's events with their own key and destroying the key (**crypto-shredding**).
- **Ordering across devices.** Two phones appending offline produce two logs. Merging them needs an order everyone agrees on, and device clocks disagree. That's the heart of D39.
- **Two models to keep in step.** The log is the truth and projections lag behind it, so code that reads a projection right after a command can see stale data.

## Where it shows up on iOS

You'll more often use event-sourced *parts* than build a fully event-sourced app:

- **An offline outbox.** While offline, the app records operations (`itemChecked(3)`) in a durable queue and uploads them in order when the network returns, instead of uploading a whole snapshot that would overwrite other devices' edits.
- **Undo history.** An editor's log of operations, from which undo removes or inverts the latest.
- **Store change history.** Core Data's persistent history tracking and SwiftData's history API (iOS 18's `fetchHistory(_:)`) record the inserts, updates and deletes each transaction made, so a widget, an extension or your sync code can catch up from a saved token. That's a change log rather than event sourcing, since the rows remain the source of truth, but you consume it the same way: from a position, in order.
- **Analytics.** An append-only stream of what users did, projected later into funnels and dashboards.

## Trade-offs

| | Current state only | Current state plus a change log | Event sourcing |
| --- | --- | --- | --- |
| Source of truth | The rows | The rows | The events |
| History, audit, time travel | None | Recent changes | Complete |
| New views of old data | Migration | Partly | Replay into a new projection |
| Sync | Snapshots: last writer wins | Changes since a token | Operations: mergeable |
| Storage and complexity | Lowest | Moderate | Highest: versioning, snapshots, compaction |
| Deleting data | Easy | Easy, plus pruning the log | Hard: compaction or crypto-shredding |

**Current state** is right for most app data: preferences, caches, content the server owns. **A change log** next to it wins when extensions or sync code need to catch up on what changed. **Event sourcing** wins where history *is* the product or the merge strategy: collaborative documents, financial ledgers, chat, and offline-first apps whose devices must converge.

<Callout kind="interview">

In an offline-first or sync design, say you'd record local changes as **operations** in a durable outbox rather than overwriting snapshots, apply them to local state immediately, and upload them in order with ids so the server can de-duplicate. Mention the costs before the interviewer does: event versioning, log growth with snapshots, and how deletion works. Questions to ask: *Do users edit the same data on several devices? Do we need an audit trail?* Red flags: event-sourcing everything by default, events named like commands (`checkItem` instead of `itemChecked`), and mutating events after they're written.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: Codable enums don't forgive renamed cases">

Synthesised `Codable` encodes an enum case by its name. Rename `itemChecked` to `itemCompleted` and every event already on disk fails to decode. For persisted events, write the coding keys explicitly, keep old case names decodable for as long as old events exist, and add tests that decode events saved by previous versions.

</Callout>
