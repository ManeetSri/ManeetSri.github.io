## Why it matters

Across D12 and this module you've met nearly twenty behavioural patterns. Knowing them one by one is the easy part. The skill that matters in code review and in interviews is going the other way: from a problem ("these three screens need to react when the basket changes") to the right shape, and noticing when no pattern is needed at all. A pattern's name is also a compression: "the coordinator mediates between the screens" tells a reviewer in six words what would otherwise take a paragraph.

## Start from the question the code must answer

Each behavioural pattern answers one question about how objects share work. Find the question first; the pattern follows. The third column is the shape it usually takes in Swift, which is often lighter than the textbook version.

| The question | Pattern | Usual Swift shape |
| --- | --- | --- |
| Who needs to know when this changes? | Observer | `@Observable`, an `AsyncStream`, Combine; `NotificationCenter` for app-wide broadcasts |
| Who decides some details on my behalf? | Delegate, data source | A protocol with a `weak` delegate, or a few closures |
| Which control fired, and what should it do? | Target–action | `UIControl` actions, SwiftUI `Button` closures |
| Tell me once when you're done | Callback | An `async` function; a completion closure in older APIs |
| Who handles this if I don't? | Chain of responsibility, responder chain | An array of interceptors; `UIResponder.next` |
| Do this later, queue it, undo it | Command | A value describing the action; `UndoManager` |
| How should this be done, this time? | Strategy | A protocol, or a closure property |
| Same steps, different details | Template method | A protocol extension with hook requirements |
| Does behaviour depend on the mode I'm in? | State | An enum with associated values and a transition function |
| Do several objects react to each other? | Mediator | A coordinator, a form model |
| Can we go back to how it was? | Memento | A value-type snapshot; edit a copy; a restoration activity |
| Walk these without knowing how they're stored | Iterator | `Sequence`, `AsyncSequence` |
| Many operations over a fixed tree of types | Visitor | An indirect enum and a `switch` per operation |
| Is this rule or route really data? | Interpreter | An indirect enum, a parser and an `evaluate` |
| What if the collaborator isn't there? | Null object | A do-nothing conformance as the default |
| Is this business rule used in several places? | Specification | A named, composable rule value |
| Is the history the real truth? | Event sourcing | An append-only log of events and projections |

## Swift collapses the ceremony, not the idea

Many patterns were written for languages without closures, enums with data, or value types. In Swift the idea survives and the scaffolding shrinks:

- **One-method protocols become closures.** A strategy, a command or a callback with a single method is often a function value: `var sort: (Item, Item) -> Bool`.
- **Class hierarchies become enums.** State objects and visitors exist to fake a closed set of cases with exhaustive handling. Swift has that natively.
- **Copies are free.** A memento is `let snapshot = state` when the state is a struct.
- **Protocol extensions are template methods.** The extension is the fixed algorithm; the requirements are the hooks.
- **`async`/`await` replaces callback plumbing**, and `AsyncSequence` turns observers and paging into loops.

In an interview, naming both is the strongest answer: "it's the State pattern; in Swift I'd write it as an enum with a transition function, because the states are known and I want the compiler to check every transition."

## Patterns that look alike

Most confusion comes from pairs that sit in the same place but do different jobs. One question separates each pair:

- **Strategy or State?** *Who changes it?* A strategy is picked from outside and stays put; a state replaces itself as events arrive.
- **Command or event?** *Could it still be refused?* A command is a request; an event is a fact that's already happened.
- **Mediator or observer?** *Does someone decide?* A mediator holds the rules and acts; an observer broadcasts and lets each listener decide.
- **Memento or command, for undo?** *What's cheaper to keep correct?* A snapshot of small state, or an inverse operation for large or shared state.
- **Delegate, closure or `async`?** *How many questions, and how many answers?* Several related questions over time suit a delegate; one answer, once, suits `async`; a single hook suits a closure.
- **Chain of responsibility or decorator?** *Can it stop?* Each link in a chain may handle the request and stop; a decorator always passes it on, adding behaviour around it.
- **Visitor or interpreter?** *Is the operation "evaluate"?* An interpreter is one particular operation over a grammar's tree; a visitor is the general way to add any operation.
- **Specification or strategy?** *Is the answer yes or no?* A specification is a composable yes-or-no rule; a strategy is an interchangeable algorithm that does work.

## Patterns working together

Real features combine several patterns, each with a narrow job. Step through a photo editor's editing screen:

```visual flow
title: One editing screen, several patterns
nodes:
  - { id: toolbar, label: Toolbar, kind: view, at: [0, 0] }
  - { id: canvas, label: Canvas, kind: view, at: [0, 2] }
  - { id: model, label: Editor model, kind: service, at: [2, 1] }
  - { id: history, label: Edit history, kind: store, at: [4, 0] }
  - { id: exporter, label: Exporter, kind: service, at: [4, 2] }
edges:
  - [toolbar, model, tool chosen]
  - [model, canvas, observed]
  - [model, history, edits]
  - [model, exporter, export]
steps:
  - say: "The **editor model** is a **mediator**: the toolbar, canvas and sliders never talk to each other, only to it."
    show: [toolbar, canvas, model]
    send: toolbar->model
  - say: "Its mode (`.idle`, `.cropping`, `.exporting(progress)`) is an enum **state machine**, so the toolbar can't start a crop mid-export."
    label: { model: state machine }
  - say: "The canvas **observes** the model through `@Observable` and redraws when the edits change."
    send: model->canvas
  - say: "Each edit is a **command** pushed to the history. Cancel restores a **memento**: the settings struct copied when editing began."
    send: model->history
    label: { history: commands + snapshot }
  - say: "The export format is a **strategy** (HEIC, JPEG, PNG), and progress comes back as an **async sequence** the model iterates."
    send: model->exporter
    label: { exporter: strategy }
  - say: "In the share extension, analytics is a **null object**, so none of this code checks whether it exists."
    active: [model]
```

None of these patterns is doing anything clever. Each one gives a single responsibility a recognisable shape, which is why a new teammate can find their way around the screen.

## When not to use a pattern

A pattern is a cost you pay in types and indirection, in exchange for flexibility along one axis. If the code doesn't change along that axis, you've paid for nothing.

- **Wait for the variation.** One export format doesn't need a strategy protocol; the second format might, and the third certainly does. That's YAGNI from D05, applied to patterns.
- **Count types against behaviours.** A `PaymentStrategyFactoryProvider` that wraps one closure is ceremony. If explaining the indirection takes longer than reading the code it replaced, unwind it.
- **Prefer the language feature.** Reach for an enum, a closure or a value copy before a hierarchy of classes.

Good signs a pattern is earning its keep: it removed conditionals or duplication you really had, the tests got simpler, and its name helps reviewers rather than needing a comment.

## Trade-offs

The deciding question is usually **what will change most often**, because each pattern makes one kind of change cheap and another expensive.

| What changes often | Favour | Because | Watch out for |
| --- | --- | --- | --- |
| New operations over a fixed set of cases | Enums with switches (State, Visitor, Interpreter) | Each operation is one function; the compiler finds gaps | Adding a case touches every switch |
| New cases, added by other teams or plug-ins | Protocols and objects (State objects, Strategy) | Each case is a new type; nothing else changes | Transitions and rules spread across types |
| Who reacts to a change | Observer | Listeners come and go without touching the source | Nobody owns the decision; hard to trace |
| The steps and order of a flow | Mediator (coordinator) | Flow rules live in one place | The mediator growing into a god object |
| Rules that product changes without a release | Interpreter, Specification | Rules become data the app evaluates | A mini-language that keeps growing |
| Nothing much | Plain code | Simplest to read and change | Re-evaluate when the second variant appears |

<Callout kind="interview">

When you reach for a pattern, say three things: the name, the Swift shape, and the axis of change that justifies it. "Screens report outputs to a coordinator, a mediator, because the onboarding order is what product changes most." Then say what you're *not* doing: "I won't add a strategy for export formats until there's a second one." Interviewers listen for pattern names used precisely (State versus Strategy is a classic probe) and for over-engineering: a pattern per class, factories for things created once, protocols with a single conformance and no test that needs another.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: a protocol with one conformance is a smell, unless tests need it">

Strategy, State and Mediator all invite protocols. A protocol with exactly one conforming type, and no test double, is indirection without a payoff. Start with the concrete type; extract the protocol when a second implementation or a test fake appears. Swift makes that extraction a small, safe refactor.

</Callout>
