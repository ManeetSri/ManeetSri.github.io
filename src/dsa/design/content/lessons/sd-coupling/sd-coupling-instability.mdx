## Why it matters

Once an app is split into modules (Swift packages, frameworks or just well-kept folders), some of them become load-bearing. Everything imports `Models`; nothing imports the app target. Changing the first is expensive and changing the second is cheap, and that's fine as long as the expensive ones rarely need to change. Afferent and efferent coupling put numbers on that, so you can spot a module that's both hard to change *and* changing every week. Staff-level interviews and architecture reviews use exactly this reasoning, usually without the formulas.

## Counting the arrows

Draw the modules and an arrow from each module to every module it imports. Then, for any one module, count two things:

- **Afferent coupling (Ca):** arrows coming *in*. How many other modules depend on this one. "Afferent" means carrying towards, as in afferent nerves.
- **Efferent coupling (Ce):** arrows going *out*. How many modules this one depends on.

Robert C. Martin defined these metrics in 1994, for C++ class categories, and later brought them to a wider audience in *Agile Software Development* and *Clean Architecture*. They work at any level: modules, targets or types.

Ca measures **responsibility**: a module with many dependents can't change without affecting them. Ce measures **dependence**: a module with many dependencies is affected whenever any of them changes.

## Instability

Martin combined the two into one number, **instability**:

`I = Ce / (Ca + Ce)`

It runs from 0 to 1:

- **I = 0, maximally stable:** others depend on it, and it depends on nothing. Every change ripples outwards, so it's *hard* to change. A `Models` module of plain value types is usually here.
- **I = 1, maximally unstable:** it depends on others, and nothing depends on it. Changes affect nobody, so it's *easy* to change. The app target is always here.

"Stable" in this sense has nothing to do with crashes or quality. It means **hard to move**, the way a heavy table is stable. A stable module isn't good and an unstable one isn't bad; the question is whether each module's stability matches how often it needs to change.

You don't need to count by hand. This program reads the same graph (in a real project you'd read it from `swift package describe --type json`, whose targets list their `target_dependencies`) and prints each module's numbers:

```swift run title="Instability from a dependency graph"
import Foundation

// Each module and the modules it imports
let imports: [String: [String]] = [
    "App": ["Feed", "Checkout"],
    "Feed": ["Networking", "DesignSystem", "Analytics", "Models"],
    "Checkout": ["Networking", "DesignSystem", "Analytics", "Models"],
    "Networking": ["Models"],
    "Analytics": ["AcmeSDK"],
    "DesignSystem": [],
    "Models": [],
    "AcmeSDK": [],
]

struct Metrics {
    let module: String
    let afferent: Int    // Ca: modules that import this one
    let efferent: Int    // Ce: modules this one imports

    var instability: Double {
        afferent + efferent == 0 ? 0 : Double(efferent) / Double(afferent + efferent)
    }
}

let metrics = imports.keys.map { module in
    Metrics(
        module: module,
        afferent: imports.values.filter { $0.contains(module) }.count,
        efferent: imports[module, default: []].count
    )
}

let mostUnstableFirst = metrics.sorted { a, b in
    a.instability != b.instability ? a.instability > b.instability : a.module < b.module
}
for m in mostUnstableFirst {
    let name = m.module.padding(toLength: 13, withPad: " ", startingAt: 0)
    print("\(name) Ca \(m.afferent)  Ce \(m.efferent)  I \(String(format: "%.2f", m.instability))")
}
```

```output
App           Ca 0  Ce 2  I 1.00
Checkout      Ca 1  Ce 4  I 0.80
Feed          Ca 1  Ce 4  I 0.80
Analytics     Ca 2  Ce 1  I 0.33
Networking    Ca 2  Ce 1  I 0.33
AcmeSDK       Ca 1  Ce 0  I 0.00
DesignSystem  Ca 2  Ce 0  I 0.00
Models        Ca 3  Ce 0  I 0.00
```

The ordering is the healthy one: features near 1, shared infrastructure in the middle, foundations at 0. The next lesson turns that into a rule about which way arrows may point.

## Stable and concrete: the zone of pain

Instability alone misses something. A stable module is hard to change, so it should be the kind of code that rarely *needs* to change, or code that others depend on only through abstractions. Martin's second metric captures that:

- **Abstractness (A):** the share of a module's types that are abstract. In Swift, count protocols as abstract and everything else as concrete. `A = abstract types / all types`, from 0 to 1.
- **Distance from the main sequence (D):** `D = |A + I − 1|`. A module on the "main sequence" (D near 0) is either stable and abstract, or unstable and concrete.

The two corners far from that line have names:

- **The zone of pain** (I and A both near 0): stable and concrete. Many modules depend on concrete code, so every change to it hurts. A `Core` module full of concrete service classes that every feature imports lives here.
- **The zone of uselessness** (I and A both near 1): abstract, but nothing depends on it. Protocols nobody implements or uses.

Not everything in the zone of pain is a problem. `Foundation` is stable and concrete, and it's fine, because it almost never changes in ways that break you. A `Money` type with no dependencies is fine for the same reason. The zone of pain hurts when the module is stable, concrete **and volatile**: depended on by everything, and edited every sprint.

Try it: start with a module that six others import, then add protocols and see the distance fall.

```visual estimator
title: Where does this module sit?
inputs:
  - { id: ca, label: Modules that import it (Ca), min: 0, max: 30, value: 6 }
  - { id: ce, label: Modules it imports (Ce), min: 0, max: 30, value: 2 }
  - { id: abstract, label: Protocols in it, min: 0, max: 40, value: 2 }
  - { id: total, label: Types in it (including protocols), min: 1, max: 40, value: 20 }
outputs:
  - { id: instability, label: "Instability I = Ce / (Ca + Ce)", formula: "ce / max(1, ca + ce)" }
  - { id: abstractness, label: "Abstractness A = protocols / types", formula: "min(abstract, total) / total" }
  - { id: distance, label: "Distance from the main sequence |A + I − 1|", formula: abs(abstractness + instability - 1) }
```

At the start, I is 0.25 and A is 0.1, so D is 0.65: stable, concrete, and well off the line. Raising the number of protocols, or lowering the number of importers, brings D towards 0.

## Using the numbers well

The metrics are signals, not targets. Once a number becomes a goal, people game it: adding empty protocols makes A go up without making anything easier to change. Use them to ask better questions:

- **Is a stable module changing often?** Compare I with how often each module appears in your commit history. A module with I near 0 that's touched in most pull requests is your most expensive code.
- **Is a stable module concrete and busy?** Then put the parts others depend on behind protocols or value types, and move the volatile implementation into a less stable module.
- **Do features depend on features?** `Feed` importing `Checkout` gives two unstable modules a dependency between them, so they can no longer change or build independently. Route that through a shared abstraction or the app target.

You can make the rules executable: a small script or test in CI that reads the package graph and fails when a feature imports another feature, or when a foundation module gains a dependency. That's a **fitness function**, as in [Measuring quality: ISO 25010 and fitness functions](/design/learn/sd-quality-measuring).

## Trade-offs

| Approach | Effort | What it catches | Risk |
| --- | --- | --- | --- |
| Eyeball the import graph | Minutes | Obvious tangles | Misses slow drift |
| Compute Ca, Ce and I per module | A short script | Modules whose stability doesn't match their churn | Gaming the numbers if they become targets |
| Add A and D | A script that parses types | Stable, concrete, busy modules | Counting protocols isn't the same as being easy to change |
| Enforce rules in CI | A test per rule | New violations, the day they're written | Rules that outlive their reasons; review them yearly |

On a single-target app with a few thousand lines, none of this is worth it. Reach for the numbers when there are several modules and several teams, or when builds and merges have started to hurt.

<Callout kind="interview">

**Say** which modules are meant to be stable and why: "`Models` and `DesignSystem` are foundations, so they stay small and dependency-free; features depend on them, never on each other, and the app target wires it all together." **Ask** how many teams share the codebase and how long a clean build takes, since both grow with high-Ca modules. **Red flags:** a `Core` or `Common` module that everything imports and that imports everything, and feature modules importing each other.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: high Ca costs build time">

When a module's public interface changes, every module that imports it has to be recompiled, and then everything that imports *those*. A busy, concrete module with a high Ca, such as a `Core` that holds models, networking and helpers together, can turn a one-line change into a rebuild of most of the app. Splitting it so that the stable, rarely changing parts sit apart from the busy ones is often the cheapest build-time win in a large Xcode project.

</Callout>
