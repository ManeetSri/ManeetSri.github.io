## Why it matters

Once an app has more than a handful of modules, the question changes from "which type should do this?" to "which **module** should this live in?" Get the boundaries wrong and every feature touches five modules, or a widget extension links half the app. Robert C. Martin's three component cohesion principles are the vocabulary for deciding what goes together. Staff-level interviews ask how you'd modularise a large app, and these are the reasons behind a good answer.

## From types to components

Martin introduced the component principles in the 1990s and collected them in *Agile Software Development: Principles, Patterns, and Practices* (2002); *Clean Architecture* (2017) revisits them. A **component** is a unit you build, version and depend on as a whole. On iOS that's a Swift package target or product, a framework, or an XCFramework.

There are six principles. Three are about **cohesion**, what belongs inside a component, and they're this lesson. Three are about **coupling** between components, and they're the next.

It helps to remember what a module actually changes in Swift:

- **An access boundary.** `internal` code is invisible outside the module, so a module is the strongest information hiding the language offers.
- **A build unit.** When a module's interface changes, modules that import it are recompiled; when it doesn't, build systems can reuse cached results.
- **An explicit dependency graph.** A SwiftPM target lists exactly what it depends on, and nothing else can be imported.
- **A unit of reuse** across the app, its widgets, a watch app, an App Clip, or several apps.

## REP: the granule of reuse is the granule of release

> The **reuse/release equivalence principle**: what you reuse together, you release together, with version numbers and release notes.

If other code reuses a component, its users need to know when it changes and whether a change can break them. That means a release process: semantic versions (a breaking change bumps the major version), notes, and a public API kept stable on purpose. And a release only means something if the component's contents share a **theme**.

- A SwiftPM package in its own repository, tagged `2.4.0` and depended on with `from: "2.0.0"`, is REP made literal.
- In a monorepo of local packages, everything releases together with the app. REP still applies wherever a module serves several clients, such as the app, its widget and its watch app: treat its public API as a contract.

**A quick test:** could you write one sentence of release notes for a typical change? "Changed the date formatter, the Keychain wrapper and the image resizer" describes three components that happen to share a name.

## CCP: what changes together, lives together

> The **common closure principle**: gather into a component the types that change for the same reasons and at the same times. Separate those that change at different times for different reasons.

This is [Single responsibility: reasons to change](/design/learn/sd-solid-srp), one level up. Its most important consequence on iOS is the choice between **layer** modules and **feature** modules.

Layer modules group code by kind: `Models`, `Networking`, `ViewModels`, `Views`. Feature modules group it by what it's for: `Checkout`, `Search`, `Profile`. Count the modules a typical change touches:

| Change request | Layer modules touched | Feature modules touched |
| --- | --- | --- |
| Add a promo-code field to checkout | 4: model, endpoint, view model, view | 1: `Checkout` |
| Show delivery slots in checkout | 4 | 1: `Checkout` |
| Change how all requests decode dates | 1: `Networking` | 1: `NetworkingCore` |
| Restyle the primary button everywhere | 1: `Views` | 1: `DesignSystem` |

Most changes are feature changes, so CCP favours **feature modules** for feature code, plus a few shared foundation modules for what's genuinely cross-cutting and stable: a networking core, a design system, an analytics interface. You'll see how teams organise this at scale in D61.

## CRP: don't make clients depend on what they don't use

> The **common reuse principle**: types that are used together belong together. Don't force a component's users to depend on things they don't need.

This is [Interface segregation with role protocols](/design/learn/sd-solid-isp), one level up. It matters more than it sounds, because you can't import a third of a module. Depend on a module and you get:

- **All of its dependencies**, linked into your target, including any third-party SDKs it imports.
- **All of its changes.** When its interface changes, you're recompiled; your tests rerun even if the change was in a part you never call.
- **Its size and start-up work**, for anything that registers or initialises itself when loaded.

Here's the classic failure, and the fix:

In SwiftPM the split costs little. One package can offer several products, and the `package` access level (Swift 5.9) lets its targets share code with each other without making it public API:

```swift title="Package.swift: one package, three products"
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "AppFoundations",
    platforms: [.iOS(.v18), .watchOS(.v11)],
    products: [
        .library(name: "Formatting", targets: ["Formatting"]),
        .library(name: "ChartsUI", targets: ["ChartsUI"]),
        .library(name: "AnalyticsKit", targets: ["AnalyticsKit"]),
    ],
    dependencies: [
        .package(url: "https://github.com/example/plotting", from: "4.0.0"),
        .package(url: "https://github.com/example/analytics-sdk", from: "11.0.0"),
    ],
    targets: [
        .target(name: "Formatting"),
        .target(name: "ChartsUI", dependencies: ["Formatting", .product(name: "Plotting", package: "plotting")]),
        .target(name: "AnalyticsKit", dependencies: [.product(name: "AnalyticsSDK", package: "analytics-sdk")]),
    ]
)
```

The widget target lists only `Formatting`, and neither SDK can reach it.

## The tension: you can't max out all three

The principles pull in different directions. REP and CCP are **inclusive**: they make components bigger, gathering what's released or changed together. CRP is **exclusive**: it makes them smaller, splitting what isn't used together. *Clean Architecture* draws this as a triangle, and each edge describes what you give up:

| You favour | You neglect | Symptom |
| --- | --- | --- |
| REP and CCP | CRP | Too many needless rebuilds and releases: clients get changes they don't use |
| REP and CRP | CCP | Too many components change for each feature |
| CCP and CRP | REP | Hard to reuse: no coherent, versioned units others can depend on |

Martin's useful observation is that a project **moves around the triangle over time**. Early on, when the team's main problem is shipping features, favour CCP: fewer, feature-shaped modules that are easy to change. As other targets, teams or apps start reusing code, shift towards REP and CRP: smaller, stable, well-named components with deliberate public APIs.

## Trade-offs

| Module structure | Build times | Change locality (CCP) | Reuse (REP, CRP) | Overhead | Wins when |
| --- | --- | --- | --- | --- | --- |
| One app target | Every change can rebuild everything | Fine while small | None | None | A small app or a small team |
| Layer modules (`Models`, `Networking`, `Views`) | Moderate | Poor: features cut across every layer | Poor: each layer is a grab-bag | Low | Rarely; it's the most common first attempt |
| Feature modules plus a few small foundations | Good: changes stay local | Good | Good for the foundations | Moderate | Most growing apps and teams |
| A module per type or two | Many small builds, lots of graph overhead | Poor: one change spans many modules | High, but mostly unused | High | Almost never; there's nothing to gain from splitting cohesive code |

<Callout kind="interview">

**What to say** when asked how you'd modularise a large app: feature modules owned by teams, so a feature change stays in one module (CCP); a small set of foundation modules such as networking, design system and analytics interfaces, each with a clear theme and a stable API (REP); and no `Common` or `Utilities` grab-bags, so targets like widgets depend only on what they use (CRP).

**What to ask:** "Which targets ship this code: widgets, a watch app, an App Clip, other apps?" Every extra client raises the value of small, focused components.

**Red flags interviewers listen for:** modularising by layer only; a `Core` module everyone depends on; and splitting a codebase into modules before anyone knows where the boundaries are.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: extensions pay for everything they link">

App extensions such as widgets run under much tighter memory limits than the app, and an App Clip has a strict size limit. A dependency added "for one helper" brings its whole module, its SDKs and their start-up work into the extension. Check what each extension target actually links, and keep the modules extensions use small and boring.

</Callout>

## Practice

The design exercise [Split the Shared module](/design/practice/sd-design-principles-split-shared-module) gives you a real-sized grab-bag module, the targets that use it and its build numbers. Plan the split in shippable steps, using all six package principles.

```cards
- id: rep
  front: "What does the reuse/release equivalence principle say?"
  back: "The granule of reuse is the granule of release: what you share, you version and release as a unit, so its contents need a single theme."
- id: ccp
  front: "What does the common closure principle say, and what does it favour on iOS?"
  back: "Types that change together for the same reasons belong in one component. It favours feature modules over layer modules for feature code."
- id: crp
  front: "What does the common reuse principle say?"
  back: "Don't make a component's users depend on things they don't use. Depending on a module means linking, rebuilding and retesting all of it."
- id: tension
  front: "How do REP, CCP and CRP pull against each other?"
  back: "REP and CCP make components bigger; CRP makes them smaller. Early projects favour CCP, then shift towards REP and CRP as code is reused."
```
