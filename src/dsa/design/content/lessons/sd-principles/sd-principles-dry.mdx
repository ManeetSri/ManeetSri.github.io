## Why it matters

"Don't repeat yourself" is the first design rule most developers learn, and the one most often misapplied. Merging code that only *looks* the same produces shared views with nine boolean parameters, base classes every screen inherits from, and "Core" modules nobody can change. Interviewers probe this because it separates people who follow rules from people who understand what the rule protects.

## What DRY actually says

Andy Hunt and Dave Thomas coined DRY in *The Pragmatic Programmer* (1999), and their wording is precise:

> Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.

The unit is **knowledge**: a business rule, a format, a fact about the world. It isn't lines of code. Two identical lines can hold different knowledge, and one rule can be duplicated in code that looks nothing alike: a Swift constant, a server config value and a sentence in a localised string.

### Knowledge duplication: the kind worth removing

A shopping app shows a banner, "Spend £4.01 more for free delivery", and charges delivery at checkout. Both depend on one rule: orders of £40 or more ship free. If the banner and the checkout each hard-code `4000`, the day marketing changes the threshold to £50, someone updates one and the banner starts lying.

```swift run title="One home for the delivery rule"
import Foundation

struct DeliveryPolicy {
    var freeThresholdPence = 4_000
    var feePence = 399

    func fee(forSubtotal subtotal: Int) -> Int {
        subtotal >= freeThresholdPence ? 0 : feePence
    }

    func bannerText(forSubtotal subtotal: Int) -> String? {
        let remaining = freeThresholdPence - subtotal
        guard remaining > 0 else { return nil }
        return "Spend \(pounds(remaining)) more for free delivery"
    }
}

func pounds(_ pence: Int) -> String {
    String(format: "£%d.%02d", pence / 100, pence % 100)
}

let policy = DeliveryPolicy()
for subtotal in [3_599, 4_000] {
    let banner = policy.bannerText(forSubtotal: subtotal) ?? "Free delivery"
    print("\(pounds(subtotal)): \(banner), delivery \(pounds(policy.fee(forSubtotal: subtotal)))")
}
```

```output
£35.99: Spend £4.01 more for free delivery, delivery £3.99
£40.00: Free delivery, delivery £0.00
```

The banner and the fee can't disagree, because they ask the same type.

On mobile there's a level above this. The authoritative home for a business rule is usually the **server**, because a rule compiled into a shipped app can't be fixed for people who never update. If the cart response carries `deliveryFee` and `freeDeliveryRemaining`, the app holds no copy of the rule at all. That's DRY across the client–server boundary, and it's the duplication that costs most on mobile.

### Coincidental duplication: the kind to leave alone

Now a sign-up form. Usernames can be at most 20 characters, and so can display names:

```swift check title="Same number, different knowledge"
enum UsernameRules {
    static let maxLength = 20     // URLs and @mentions must stay short
}

enum DisplayNameRules {
    static let maxLength = 20     // fits the profile header on the smallest iPhone
}
```

They look like duplication. They aren't: one exists because of URLs, the other because of a layout. When design asks for 30-character display names, usernames must stay at 20. Merge them into `NameRules.maxLength` and that change breaks usernames, or it forces someone to un-merge them under deadline. This is **coincidental duplication**: the same text by accident.

### The test: would they change together?

For any two pieces of similar code, ask one question: **if this rule changes, must the other copy change too, every time?**

- Yes: it's one piece of knowledge in two places. Give it one home.
- Not necessarily: they only look alike. Leave them separate, and perhaps name them so nobody "fixes" them later.

This is the single responsibility test from [Single responsibility: reasons to change](/design/learn/sd-solid-srp), applied to similarity. Code that changes for different reasons, at the request of different people, should stay apart even when it reads the same.

## How the wrong abstraction grows

Sandi Metz described the pattern in her 2016 essay "The Wrong Abstraction", and her conclusion is widely quoted: **duplication is far cheaper than the wrong abstraction.** The steps are always the same, and you can watch them below.

```visual states

states:
  - { id: duplicated, label: Two copies, at: [0, 0] }
  - { id: extracted, label: Shared view, at: [1, 0] }
  - { id: flagged, label: Flags added, at: [2, 0] }
  - { id: tangled, label: Knows callers, at: [3, 0] }
  - { id: recomposed, label: Shared parts, at: [0, 1] }
initial: duplicated
final: [recomposed]
transitions:
  - [duplicated, extracted, extract]
  - [extracted, flagged, addFlag]
  - [flagged, flagged, addFlag]
  - [flagged, tangled, checkCaller]
  - [tangled, duplicated, inline]
  - [duplicated, recomposed, shareRealParts]
events:
  - { event: extract, say: "Someone extracts `ProductRow`. Today it's a real improvement: one place to change." }
  - { event: addFlag, say: "Order history needs the row too, but with a line total. A `context` parameter seems cheaper than a third view." }
  - { event: addFlag, say: "Then `showsStepper`, `showsMoveToCart`, `isEditable`. Each Boolean doubles the combinations nobody tests." }
  - { event: checkCaller, say: "Finally the shared code asks **who is calling**: `if context == .wishlist`. It now depends on every screen that uses it." }
  - { event: inline, say: "The way out is backwards: copy the code into each caller and delete the branches that caller never takes." }
  - { event: shareRealParts, say: "With three honest copies side by side, the real shared knowledge shows: a price label and a thumbnail. Share **those**." }
```

Here's the row after a year of "reuse". Every line made sense when it was added:

```swift check ios group=rows title="ProductRow.swift, a year later"
import SwiftUI

struct Product: Identifiable {
    let id: String
    let name: String
    let pricePence: Int
    let wasPricePence: Int?
    let imageName: String
}

func formattedPrice(_ pence: Int) -> String {
    (Decimal(pence) / 100).formatted(.currency(code: "GBP"))
}

enum RowContext { case cart, wishlist, orderHistory }

struct ProductRow: View {
    let product: Product
    let context: RowContext
    var quantity = 1
    var showsStepper = false
    var showsMoveToCart = false
    var isEditable = true
    var onQuantityChange: ((Int) -> Void)? = nil
    var onMoveToCart: (() -> Void)? = nil

    var body: some View {
        HStack {
            Image(product.imageName)
            VStack(alignment: .leading) {
                Text(product.name)
                if context == .wishlist, let was = product.wasPricePence {
                    Text(formattedPrice(was)).strikethrough()
                }
                Text(formattedPrice(context == .orderHistory ? product.pricePence * quantity : product.pricePence))
            }
            Spacer()
            if showsStepper && isEditable {
                Stepper("Quantity", value: Binding(get: { quantity }, set: { onQuantityChange?($0) }), in: 1...10)
                    .labelsHidden()
            }
            if showsMoveToCart && context != .orderHistory {
                Button("Move to cart") { onMoveToCart?() }
            }
        }
    }
}
```

### The smells of a wrong abstraction

- **Boolean and mode parameters** that switch behaviour on and off. That's control coupling from [Kinds of coupling, from content to data](/design/learn/sd-coupling-kinds): the caller steers the callee's internals.
- **Branches on the caller's identity**: `context == .wishlist`. The shared code now knows about its users, which is the opposite of what sharing should do.
- **Most call sites pass defaults** or `nil` for most parameters. Each caller uses a different third of the type.
- **A vaguer name** each year: `ProductRow` becomes `ItemCell`, then `GenericRow`.
- **Every change needs every caller retested**, so people stop changing it, and copy it instead. The abstraction failed at the one thing it was for.

## Backing out: inline, then find the real seams

Metz's advice is the counter-intuitive part. Don't add another parameter. **Go back to duplication**:

1. Inline the shared code into every caller.
2. In each copy, delete the branches that caller never takes. Each copy becomes short and obvious.
3. Put the copies side by side and look for what's *really* the same knowledge. Extract only that.

```swift check ios group=rows title="Three honest rows, sharing two real parts"
struct PriceText: View {
    let pence: Int
    var wasPence: Int? = nil

    var body: some View {
        HStack(spacing: 6) {
            if let wasPence {
                Text(formattedPrice(wasPence)).strikethrough().foregroundStyle(.secondary)
            }
            Text(formattedPrice(pence))
        }
    }
}

struct CartRow: View {
    let product: Product
    @Binding var quantity: Int

    var body: some View {
        HStack {
            Image(product.imageName)
            VStack(alignment: .leading) {
                Text(product.name)
                PriceText(pence: product.pricePence)
            }
            Spacer()
            Stepper("Quantity", value: $quantity, in: 1...10).labelsHidden()
        }
    }
}

struct WishlistRow: View {
    let product: Product
    let moveToCart: () -> Void

    var body: some View {
        HStack {
            Image(product.imageName)
            VStack(alignment: .leading) {
                Text(product.name)
                PriceText(pence: product.pricePence, wasPence: product.wasPricePence)
            }
            Spacer()
            Button("Move to cart", action: moveToCart)
        }
    }
}

struct OrderHistoryRow: View {
    let product: Product
    let quantity: Int

    var body: some View {
        HStack {
            Image(product.imageName)
            Text("\(quantity) × \(product.name)")
            Spacer()
            PriceText(pence: product.pricePence * quantity)
        }
    }
}
```

There's more code in total, and that's fine. Each row now changes only when its screen changes. `PriceText` is real shared knowledge: how this app shows money, including the struck-through old price. When finance decides prices show without pence over £100, that's one edit, and every screen agrees.

<Callout kind="tip">

Before inlining a wrong abstraction that matters, pin down today's behaviour with a few tests or snapshot tests, so untangling it can't change what users see. You'll do this properly with characterisation tests in D15.

</Callout>

## AHA and the rule of three

If merging too early is the risk, when *should* you merge?

- **The rule of three.** Don Roberts' heuristic, popularised by Martin Fowler's *Refactoring*: the first time, write it; the second time, wince and duplicate; the third time, refactor. Three examples show you which parts vary. Two can't.
- **AHA, "avoid hasty abstractions"**, Kent C. Dodds' name for the same instinct: prefer duplication until the right abstraction is obvious, and optimise for change first.

Neither is a counting rule. Real knowledge duplication, such as the delivery threshold, deserves one home **the first time you see it**, because two copies of a rule are a bug waiting for its date. The waiting applies to *structural* similarity: two screens, two cells, two request builders that look alike.

## DRY beyond code

The same principle shows up in iOS work outside functions and types:

- **State.** In SwiftUI each piece of state should have one owner, with `@Binding` or the environment passing access down. Two `@State` copies of "is the user signed in" will disagree. That's DRY for data, usually called a *single source of truth*.
- **Schemas.** Generating client code from an API description, for example with Apple's `swift-openapi-generator`, keeps one authoritative description of every endpoint instead of hand-written models that drift from the server.
- **Strings and assets.** A String Catalog (`.xcstrings`) and asset catalog colours give each piece of copy and each brand colour one home.
- **Analytics.** An event name typed as a string in 30 places is 30 copies of the knowledge "this event is called `checkout_started`". An enum of events is one.

## Trade-offs

| Option | Cost now | When the rule changes | Coupling between callers | Wins when |
| --- | --- | --- | --- | --- |
| Leave duplicates | None | Edit each copy, and remember to | None | The copies represent different knowledge, or you've seen only two cases |
| Shared function or constant | Low | One edit | Low: callers share one fact | The duplication is one piece of knowledge, such as a rule, format or limit |
| Parameterised shared component | Medium | One edit, if it fits every caller | High: every caller depends on every flag | Callers truly vary along one or two stable dimensions |
| Small shared parts, composed per caller | Medium | One edit for shared parts, local edits elsewhere | Low | Screens look alike but evolve separately |
| Generated code from a schema | High setup | Regenerate | Low | Many types mirror one external description, such as an API or a database |

<Callout kind="interview">

**What to say:** "I'd share the knowledge, not the shape." When you propose a shared module or component in a design interview, say what knowledge it owns and who changes it. For example: "The design system owns how prices look; each feature owns its own rows."

**What to ask:** "Do these two screens change at the request of the same people?" If checkout and wishlist have different product owners, a shared component between them is a coordination cost.

**Red flags interviewers listen for:** proposing a generic `BaseViewController` or `GenericListViewController` for screens you've only just heard about; extracting after a single use; or the opposite, a pricing rule copied into three features and the server.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the Core module as a dumping ground">

A `Core` or `Common` module starts as "things two features share" and becomes the place for everything nobody wants to own. Every feature depends on it, so every change to it rebuilds and retests the whole app. Share small, named modules with one job each (`Money`, `DesignSystem`), not a drawer. You'll see the principle behind this in [Package cohesion: REP, CCP and CRP](/design/learn/sd-principles-package-cohesion).

</Callout>
