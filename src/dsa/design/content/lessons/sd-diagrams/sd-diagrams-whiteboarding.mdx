## Why it matters

In a system design interview, the board is the only artefact. The interviewer judges your design by what they can follow on it, and judges your communication by how it got there. The same skill runs every design discussion at work: the engineer who can sketch a system clearly while talking through it steers the decision. Whiteboarding well is a technique, and like any technique it can be practised until you stop thinking about it.

## The board is shared memory

Treat the board as the memory you and the interviewer share for the next 45 minutes. Anything that matters goes on it, in a predictable place, so either of you can point at it later:

- **Top left: requirements and numbers.** The functional requirements as a short list, the non-functional ones beside them ("works offline", "feed opens in under a second"), and two or three numbers: daily users, peak requests a second, payload size.
- **Centre: the main diagram.** Containers first, with room around them.
- **Right side: the API.** Endpoint names and the key fields, as you decide them.
- **Bottom: the data model.** Entities and where each one lives: on the device, on the server, or both.
- **A corner for the parking lot.** Questions you've deferred ("edit offline? later"), so you can say "I've parked that" and come back to it.

Requirements written on the board earn their place in the last ten minutes. When you justify a trade-off, you point at "works offline" rather than reciting it, and the interviewer sees the design is driven by what was asked.

<Callout kind="analogy">

A whiteboard in an interview is like a pilot's checklist and map on one table: both people can see it, it records what's been decided, and either can put a finger on it. A design you only describe out loud is like giving directions over the phone. It can work, but one wrong turn and nobody knows where they are.

</Callout>

## The order to draw things

Draw the design in the order you'd explain it, so each stroke answers a question the interviewer already has. Step through a board for "design the feed of a photo-sharing app":

```visual flow
title: "A board, in the order it's drawn"
nodes:
  - { id: app, label: iOS app, kind: client, at: [0, 0] }
  - { id: api, label: Feed API, kind: service, at: [2, 0] }
  - { id: db, label: Posts DB, kind: db, at: [4, 0] }
  - { id: cdn, label: Image CDN, kind: cdn, at: [2, 1.5] }
  - { id: apns, label: APNs, kind: external, at: [4, 1.5] }
  - { id: view, label: FeedView, kind: view, at: [0, 3] }
  - { id: model, label: FeedModel, kind: service, at: [2, 3] }
  - { id: repo, label: FeedRepository, kind: service, at: [4, 3] }
  - { id: client, label: API client, kind: service, at: [2, 4] }
  - { id: cache, label: Feed cache, kind: store, at: [4, 4] }
groups:
  - { id: zoom, label: "iOS app, zoomed in", nodes: [view, model, repo, client, cache] }
edges:
  - [app, api, "1 GET /feed"]
  - [api, db, 2 query, { style: data }]
  - [app, cdn, 3 GET image]
  - [api, apns, 4 push, { style: async }]
  - [view, model, observes]
  - [model, repo, "feed()"]
  - [repo, client, fetch]
  - [repo, cache, "read, write", { style: data }]
steps:
  - say: "Two boxes and **one numbered arrow**: the app asks the Feed API for the feed. Say it as you draw it: *the app asks for the first page of the feed over HTTPS*."
    show: [app, api]
    send: app->api
  - say: "The store behind the API, arrow **2**. One box for now; the backend's insides are a deep dive you may not need."
    show: [db]
    send: api->db
  - say: "Images don't come from the API. The response carries image URLs, and the app fetches them from a CDN at the edge: arrow **3**, and the reason the feed scrolls smoothly on cellular."
    show: [cdn]
    send: app->cdn
  - say: "New likes and comments arrive by push, so arrow **4** is dashed: asynchronous, and not guaranteed to arrive."
    show: [apns]
    send: api->apns
  - say: "That's the happy path end to end in four arrows. **Check in**: *shall I go deeper on the client?* Then zoom in a **new area** of the board, instead of cramming boxes inside the app's box."
    show: [zoom]
    active: [app]
    label: { app: zoomed below }
  - say: "Inside the app: the view observes a model, the model asks a repository, and the repository is the only part that knows about both the network and the cache."
    send: [view->model, model->repo]
  - say: "The repository serves the cache first, then fetches. Now *works offline* from the requirements corner has a box you can point at."
    send: [repo->cache, repo->client]
    state: { cache: ok }
```

The general order:

1. **Requirements and numbers** in their corner.
2. **The happy path** of the most important use case: three to five boxes, numbered arrows.
3. **Stores and caches** behind the boxes that need them.
4. **Asynchronous parts**: push, background work, queues, drawn dashed.
5. **Check in** with the interviewer about where to go deeper.
6. **Zoom** into the part they choose, in its own area, labelled with what it zooms into.
7. **Failures**, added on top, ideally in a different colour: the offline path, the retry, the push that never arrives.
8. **Wrap-up**: circle the decisions, list the trade-offs, and point at the parking lot.

## Narrate while you draw

Silent drawing loses the room. The interviewer is trying to follow your reasoning, and a box appearing without a sentence gives them nothing to evaluate.

- **Say why before what:** "Because the feed has to work offline, I'm putting a cache on the device" is a design decision; "and here's a cache" is a drawing.
- **Keep silences short.** If you need to think, say so: "Give me twenty seconds to think about pagination."
- **Use the interviewer's words.** If they said "stories", don't draw "ephemeral posts".
- **Name trade-offs as you pass them:** "cursor pagination rather than pages, because posts arrive while you scroll; I'll come back to that."
- **Invite interruptions.** "Stop me if you'd rather I spent this time on the backend."

## Conventions that make a board readable

- **Client on the left, server on the right**, or device on top and backend below. Pick one and keep it, so the network is always the same line on the board.
- **Number the arrows** of the flow you're describing; numbers do the work of a sequence diagram without drawing one.
- **Dashed for asynchronous**, solid for request and response, and say so once in a tiny legend in the corner.
- **Boxes big enough to write in**, with a label and, where it matters, a technology: "Feed cache (SQLite)".
- **Leave space.** Leave an empty column where you expect to add things (a CDN, a queue), so adding them doesn't mean squeezing.
- **Strike through, don't erase,** an option you've rejected. The crossed-out "WebSocket" next to "push + pull on open" shows the trade-off you made.

## Managing the time

A typical mobile system design interview gives you about 45 minutes after introductions. The exact split moves with the question; what shouldn't move is that the deep dive gets the most time and the wrap-up isn't skipped. Step through a well-run one:

```visual timeline
title: "45 minutes, and what the board shows"
unit: min
lanes:
  - { id: you, label: You }
  - { id: board, label: Board }
  - { id: them, label: Interviewer }
spans:
  - { lane: you, from: 0, to: 5, label: clarify scope, tone: active }
  - { lane: board, from: 0, to: 5, label: requirements }
  - { lane: them, from: 0, to: 5, label: answers, tone: wait }
  - { lane: you, from: 5, to: 8, label: numbers, tone: active }
  - { lane: board, from: 5, to: 8, label: estimates }
  - { lane: you, from: 8, to: 18, label: happy path, tone: active }
  - { lane: board, from: 8, to: 18, label: boxes + numbered arrows }
  - { lane: you, from: 18, to: 25, label: API and data, tone: active }
  - { lane: board, from: 18, to: 25, label: endpoints, entities }
  - { lane: you, from: 25, to: 40, label: deep dive on the client, tone: active }
  - { lane: board, from: 25, to: 40, label: client zoom-in, failures }
  - { lane: them, from: 25, to: 40, label: probes, tone: wait }
  - { lane: you, from: 40, to: 45, label: trade-offs, tone: ok }
  - { lane: board, from: 40, to: 45, label: decisions circled, tone: ok }
  - { lane: them, from: 40, to: 45, label: questions, tone: wait }
markers:
  - { at: 18, label: check in }
  - { at: 31, label: "what if it's offline?" }
steps:
  - { at: 0, say: "Five minutes of questions, with the answers written in the requirements corner as you get them." }
  - { at: 5, say: "A few numbers, only the ones that change the design: users, peak requests, payload size." }
  - { at: 8, say: "The happy path, drawn and narrated, with numbered arrows. Aim to have it end to end by about minute 18." }
  - { at: 18, say: "**Check in.** It's the moment to agree where the deep dive goes, before you spend 15 minutes somewhere the interviewer doesn't care about." }
  - { at: 25, say: "The deep dive gets the most time. For a mobile role that's usually the client: layers, state, caching, offline." }
  - { at: 31, say: "The interviewer probes. A good probe is a gift: add the failure path to the board in another colour, and keep going." }
  - { at: 40, say: "Stop adding boxes. Circle the decisions, say what you'd do differently at ten times the scale, and point at the parking lot." }
  - { at: 45, say: "The board now tells the whole story without you, which is exactly what the interviewer writes their feedback from." }
```

## When the board gets messy

It will. Three habits recover it:

- **Redraw instead of patching.** "Let me redraw this cleanly with what we've decided" costs a minute and buys back the interviewer's attention. Redraw in a clear area, then rub out the old one.
- **Go back to the requirements corner** when you're lost. Read the next unaddressed requirement aloud and design for it.
- **Admit a wrong turn out loud.** "I put the cache in the wrong place; it should sit behind the repository" shows judgement. Quietly moving it hides it.

## Remote boards

Most interviews are now on a shared canvas: Excalidraw, Miro, FigJam or the interview platform's own tool. The habits are the same, plus a few:

- **Practise the tool** until shapes are muscle memory. In Excalidraw, single keys pick tools: R for a rectangle, A for an arrow, T for text.
- **Type, don't handwrite** with a trackpad. Typed labels are faster to read and to fix.
- **Mind the zoom.** Your screen isn't theirs. Zoom out to show the whole picture at each check-in, then zoom in to work.
- **When there's no drawing tool**, a shared document works: an indented list of boxes and numbered arrows, or simple text boxes such as `[App] --1 GET /feed--> [Feed API]`.

## Trade-offs

| Medium | Speed | Readability | Editing | When it wins |
| --- | --- | --- | --- | --- |
| Physical whiteboard | Fast, once practised | Good if you write large | Erasing is messy; redraws are easy | On-site interviews, team design sessions |
| Shared canvas (Excalidraw, Miro, FigJam) | Fast with shortcuts | Best: typed labels, clean lines | Easy to move and restyle | Remote interviews, recorded design reviews |
| Text-only document | Slowest for structure | Fine for lists, poor for layout | Easy | No drawing tool available, or very structured answers |
| Your own prepared template | Fastest start | Good | Easy | Practice and real design sessions; check whether interviews allow it |

<Callout kind="interview">

**Say** the plan in one sentence before drawing: "I'll list the requirements, sketch the happy path end to end, then go deep on the client." At about the 18-minute mark, **ask** where the interviewer wants the deep dive. Before the end, **summarise from the board**: point at each requirement and the box that meets it. **Red flags:** long silent drawing, a board with no requirements on it, spending twenty minutes on backend scaling in a mobile interview without being asked, and running out of time with no trade-offs said.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: leave room inside the phone">

Backend-heavy habits put one small "Mobile app" box in the corner and spend the board on servers. In a mobile interview the app is where most of the questions go: the cache, the offline queue, background refresh, push handling, extensions. Draw the app box large, or leave the space below it for the zoom, from the start.

</Callout>

## Practice

Do this module's design exercises as live whiteboard sessions: **C4 views of a grocery delivery app** in 30 minutes, then **Component view of a podcast app** in 35, with a timer and either a real board or Excalidraw. Talk out loud as if someone were listening, and photograph or export the board before you reveal the model answer. Then compare the board, not only the text: could someone follow it without you?
