## Why it matters

When someone new asks "so how does it all fit together?", the answer they need is a system context diagram and a container diagram. Those two pictures carry most of the value of any architecture documentation, and the high-level design you draw in a mobile system design interview is a container diagram in all but name. The C4 model gives you a small, shared vocabulary for drawing them, so your diagrams mean the same thing to every reader.

## The C4 model: four zoom levels

Simon Brown created the C4 model to fix the problem from [What makes a design diagram useful](/design/learn/sd-diagrams-why): diagrams that mix levels and mean different things to different readers. It names four kinds of thing and gives each a diagram:

| Level | Diagram | Shows | Main reader |
| --- | --- | --- | --- |
| 1 | System context | Your system as one box, the people who use it, the systems it depends on | Everyone, including non-engineers |
| 2 | Container | The separately running apps, services and data stores inside your system | Engineers, architects, operations |
| 3 | Component | The major parts inside one container | Engineers working in that container |
| 4 | Code | Classes and types inside one component | Rarely drawn; usually generated |

The four names are deliberately plain:

- A **person** is a role that uses the system: a rider, a support agent, an administrator.
- A **software system** is something that delivers value, owned by one team or organisation: yours, or someone else's.
- A **container** is something that must be **running** for the system to work: an app, an app extension, a service, a database, a file store. It has nothing to do with Docker; the name predates it.
- A **component** is a group of related code behind a clear interface, *inside* a container. You'll meet these in the next lesson.

<Callout kind="analogy">

C4 works like a map app. Zoomed out, you see countries and the roads between them (context). Zoom in and cities appear (containers), then streets (components), then buildings (code). Each zoom level shows only what makes sense at that scale, and you always know which level you're looking at.

</Callout>

## Level 1: the system context diagram

The running example for this lesson and the next is **Pedal**, a bike-share app. Riders find a bike on a map, unlock it from their iPhone, ride, and pay by the minute. Support agents handle refunds. The locks are made by another company, which runs its own cloud for opening them over cellular.

A context diagram puts your system in the middle as **one box**, and surrounds it with the people who use it and the external systems it depends on:

```visual flow
title: "Pedal: system context"
nodes:
  - { id: rider, label: Rider, kind: actor, at: [0, 1] }
  - { id: agent, label: Support agent, kind: actor, at: [0, 3] }
  - { id: pedal, label: Pedal bike share, kind: service, at: [2, 2] }
  - { id: apns, label: APNs, kind: external, at: [2, 0] }
  - { id: locks, label: Lock platform, kind: external, at: [4, 1] }
  - { id: payments, label: Payment provider, kind: external, at: [4, 3] }
edges:
  - [rider, pedal, rents bikes]
  - [agent, pedal, refunds rides]
  - [pedal, locks, unlocks bikes]
  - [pedal, payments, charges rides]
  - [pedal, apns, sends alerts, { style: async }]
  - [apns, rider, notifies, { style: async }]
caption: "Pedal is one box. Everything around it is either a person who uses it or a system somebody else runs. There's no technology on this diagram, so a product manager can read it too."
```

What goes on it, and what stays off:

- **People by role**, not by name: "Rider", not "Sam from marketing".
- **External systems** are the ones your team doesn't own and can't change: the lock vendor, the payment provider, Apple's push service. Systems another team in your company owns count as external too, because you depend on their interface, not their insides.
- **Relationships** say what each one is for: "unlocks bikes", "charges rides".
- **No technology, no protocols, no internals.** Not "REST", not "iOS app", not "Postgres". Those belong one level down.

Its value is in the questions it raises early. Who else uses this? What happens when the lock platform is down? Does the payment provider see the rider's location? A missing box on this diagram is a missing requirement.

## Level 2: the container diagram

Zoom into the Pedal box and you see the things that run: the app, its extension, the API, the database. Step through starting a ride, and watch which containers each step touches:

```visual flow
title: "Pedal: containers, starting a ride"
layers:
  - { label: Device, rows: [0, 1] }
  - { label: Backend, rows: 2 }
  - { label: External, rows: 3 }
nodes:
  - { id: rider, label: Rider, kind: actor, at: [0, 0] }
  - { id: app, label: iOS app, kind: client, at: [2, 0] }
  - { id: widget, label: Widget extension, kind: view, at: [4, 0] }
  - { id: shared, label: App Group files, kind: store, at: [3, 1] }
  - { id: db, label: Rides DB, kind: db, at: [0, 2] }
  - { id: api, label: Ride API, kind: service, at: [2, 2] }
  - { id: payments, label: Payments, kind: external, at: [0, 3] }
  - { id: locks, label: Lock platform, kind: external, at: [2, 3] }
  - { id: apns, label: APNs, kind: external, at: [4, 3] }
edges:
  - [rider, app, taps Unlock]
  - [app, api, "POST /rides"]
  - [api, locks, unlock]
  - [api, db, "read, write", { style: data }]
  - [app, shared, writes, { style: data }]
  - [widget, shared, reads, { style: data }]
  - [api, apns, push, { style: async }]
  - [apns, widget, updates, { style: async }]
  - [api, payments, charge]
steps:
  - say: "The rider holds the **iOS app**: a container, because it's a separately running thing Pedal can't work without."
    show: [rider, app]
    send: rider->app
  - say: "The app asks the **Ride API** to start a ride over HTTPS. The API is a second container, and every arrow between containers is a call that can fail, time out or arrive twice."
    send: app->api
    label: { app: Swift · SwiftUI, api: Go · REST }
  - say: "The API asks the **lock platform** to open the lock. It's drawn dashed because it's someone else's system: you can't fix it, only cope when it's down."
    send: api->locks
  - say: "It records the ride in the **Rides DB**, a third container. A database counts, because the system stops without it."
    send: api->db
    label: { db: PostgreSQL }
  - say: "Back on the phone, the app writes the current ride into its **App Group container**, a folder that more than one process on the device can read."
    send: app->shared
  - say: "The **widget extension** is a separate container: its own process, its own memory limit and its own lifecycle. It can't call into the app; it reads what the app left in the shared folder."
    send: widget->shared
    label: { widget: WidgetKit }
  - say: "The ride's Live Activity on the Lock Screen ticks along on **push updates**: the API sends them through APNs, and the system redraws the Live Activity from the extension's views."
    send: [api->apns, apns->widget]
  - say: "When the ride ends, the API charges it through the payment provider. That's every container, and every arrow between them, for this flow."
    send: api->payments
  - say: "The arrows that cross the **Device** band are network calls; the two into the App Group are files. A diagram that drew the app as one box would have hidden both, and they're where stale widgets come from."
    active: [app->shared, widget->shared, app->api]
```

### What counts as a container on iOS

The test is "does it run, or store data, on its own?". On Apple platforms that draws the lines in places a single "iOS app" box hides:

| Thing | On the container diagram? | Why |
| --- | --- | --- |
| The app | Yes | Its own process and bundle |
| Widget, notification service, share and other app extensions | Yes, each one | Each runs in its own process with its own memory limit, lifecycle and entitlements |
| A watchOS app or an App Clip | Yes | A separate binary, often on another device |
| An App Group container or a shared Keychain access group | Yes, when two containers share it | It's the only way they exchange data on the device |
| A local database only the app uses | Your choice | Draw it when persistence is the point (an offline-first app); otherwise it belongs inside the app, at component level |
| A Swift package or feature module | No | It lives inside the app's process: a component |
| A third-party SDK | No, but its vendor's backend is an external system | The SDK is code in your process; where it sends data is a relationship worth showing |

### Notation that makes C4 diagrams readable

C4 doesn't prescribe shapes. It asks for a few things on every diagram:

- **A title** with the diagram type and scope: "Pedal: containers".
- **Each element** shows its name, its type, its technology (for containers and components) and a short description: *Ride API · Container: Go, REST/JSON · Starts, ends and prices rides.*
- **Each relationship** is one-way and labelled with its intent, plus the technology when it crosses a process: *Starts and ends rides · HTTPS/JSON.*
- **A key** explaining shapes, colours, line styles and acronyms.
- **A boundary** around the containers that belong to your system, so it's obvious what you own.

## Writing the model once

A diagram drawn by hand is one view. Structurizr's DSL describes the **model**, the elements and relationships, and generates each view from it. The context and container diagrams above come from one file:

```text title="pedal.dsl (Structurizr DSL)"
workspace "Pedal" {
    model {
        rider = person "Rider" "Rents bikes by the minute."
        agent = person "Support agent" "Handles refunds and damage reports."

        pedal = softwareSystem "Pedal" "Find, unlock, ride and pay for bikes." {
            app = container "iOS app" "Map, unlock, ride and pay." "Swift, SwiftUI"
            widget = container "Widget extension" "Home Screen widget and the ride's Live Activity." "WidgetKit, ActivityKit"
            shared = container "App Group container" "The current ride, shared by app and widget." "JSON files"
            api = container "Ride API" "Starts, ends and prices rides." "Go, REST/JSON"
            db = container "Rides DB" "Riders, rides and payments." "PostgreSQL"
            console = container "Support console" "Refunds and damage reports." "Web app"
        }

        locks = softwareSystem "Lock platform" "The lock vendor's cloud."
        payments = softwareSystem "Payment provider" "Cards and Apple Pay."
        apns = softwareSystem "APNs" "Apple Push Notification service."

        rider -> app "Finds and unlocks bikes with"
        agent -> console "Refunds rides with"
        app -> api "Starts and ends rides" "HTTPS/JSON"
        app -> shared "Writes the current ride to"
        widget -> shared "Reads the current ride from"
        console -> api "Refunds rides" "HTTPS/JSON"
        api -> db "Reads from and writes to" "SQL"
        api -> locks "Unlocks and locks bikes" "HTTPS"
        api -> payments "Charges rides" "HTTPS"
        api -> apns "Sends Live Activity updates" "HTTP/2"
        apns -> widget "Delivers ride updates to"
    }
    views {
        systemContext pedal {
            include *
            autoLayout
        }
        container pedal {
            include *
            autoLayout
        }
    }
}
```

The context view shows `pedal` as one box, because its containers are inside it. Relationships to and from containers roll up to the system: `rider -> app` appears on the context view as Rider → Pedal, and `api -> locks` as Pedal → Lock platform. Structurizr calls these implied relationships. Rename `api` once, and both views change.

## The arrow between two containers, in Swift

Every arrow on a container diagram is something concrete in code. The App Group arrows in Pedal are a file in a folder both targets have the entitlement for. This is the whole of that relationship:

```swift check ios title="SharedRideStore.swift"
import Foundation
import WidgetKit

struct RideSnapshot: Codable, Sendable {
    let bikeID: String
    let startedAt: Date
    let pricePerMinute: Decimal
}

/// The "writes ride" and "reads ride" arrows: a file in the App Group container.
/// The app and the widget extension each compile this type; neither can call the other.
struct SharedRideStore: Sendable {
    static let appGroup = "group.com.example.pedal"
    private let url: URL

    init?() {
        guard let folder = FileManager.default.containerURL(forSecurityApplicationGroupIdentifier: Self.appGroup) else {
            return nil // The App Groups entitlement is missing from this target
        }
        url = folder.appending(path: "current-ride.json")
    }

    /// Called by the app when a ride starts or ends
    func save(_ ride: RideSnapshot?) throws {
        if let ride {
            try JSONEncoder().encode(ride).write(to: url, options: .atomic)
        } else {
            try? FileManager.default.removeItem(at: url)
        }
        // The widget won't notice the file changed; ask the system to rebuild its timeline
        WidgetCenter.shared.reloadTimelines(ofKind: "CurrentRide")
    }

    /// Called by the widget's timeline provider, in the extension's own process
    func load() -> RideSnapshot? {
        guard let data = try? Data(contentsOf: url) else { return nil }
        return try? JSONDecoder().decode(RideSnapshot.self, from: data)
    }
}
```

Reading the code with the diagram in mind tells you where it will break. The format is a contract between two containers that may be **different builds** for a few minutes after an update, so it needs to stay decodable both ways. The `.atomic` write keeps the widget from reading half a file. And the reload call is the "notify" half of the arrow: without it the widget shows the old ride until its timeline next refreshes.

## Trade-offs

| Diagram | Effort | Who it serves | Goes stale | When it wins |
| --- | --- | --- | --- | --- |
| Context only | Minutes | Everyone, including product and security | Rarely: external dependencies change slowly | Kick-offs, scoping, a new integration |
| Context and container | An hour, kept up with the code | Engineers, new joiners, reviewers, on-call | When an extension, service or store is added | Almost every team: the best value per hour of any diagram |
| One combined "everything" diagram | Feels quick | Nobody well | Constantly | Rarely: it mixes levels and readers |
| A model (Structurizr) with generated views | Most up front | Large orgs with many views to keep consistent | Least: one rename updates every view | Many systems, many teams, many diagrams |

<Callout kind="interview">

The high-level design step of a mobile system design interview **is** a container diagram. **Say** it in container terms: "On the device there's the app and a notification service extension; on our side an API, a database and a CDN for images; and APNs, which we don't own." **Ask** whether to treat the backend as one box so you can spend the time on the client. **Red flags:** drawing classes before the containers exist, forgetting push and the CDN, and leaving out the extensions that need data (a widget, a notification extension) until the interviewer asks how they get it.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: extensions can't share memory with the app">

A widget or notification service extension is not a thread of your app. It's a separate process, often launched when your app isn't running at all, with a much tighter memory limit. Singletons, in-memory caches and `@Observable` models in the app are invisible to it. If the container diagram has no arrow between the app and an extension, ask how the extension gets its data, because the honest answer is often "it doesn't, yet".

</Callout>
