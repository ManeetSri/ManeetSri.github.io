## Why it matters

A design that lives only in your head can't be reviewed, built by a team or defended in an interview. A diagram is the fastest way to move it into someone else's head, but only when it answers a question that person has. Most architecture diagrams fail quietly: everyone nods at the boxes and arrows, and nobody can use them to decide anything. This lesson covers the few habits that separate a useful diagram from decoration. Every other lesson in this module builds on them.

## A diagram answers one question for one audience

Before you draw anything, finish this sentence: *"This diagram shows ___ so that ___ can ___."* If you can't, you're not ready to draw.

| Audience | Their question | The diagram that answers it |
| --- | --- | --- |
| A new iOS engineer | What are the big pieces, and which ones does the app talk to? | A container diagram |
| A pull-request reviewer | Which parts does this change touch, and what depends on them? | A component or class diagram |
| A security reviewer | Where does personal data go, and where does it leave the phone? | A data-flow diagram with trust boundaries |
| The on-call engineer | What happens, in order, when sign-in fails halfway? | A sequence diagram |
| A product manager | What states can an order be in, and what moves it on? | A state diagram |
| An interviewer | Do you understand this system end to end? | A container diagram first, then a zoom into the app |

Two things follow. A useful diagram **leaves things out on purpose**: the sequence diagram for sign-in has no database tables in it, and that's correct. And **several small diagrams beat one big one**, because each can be right for its reader without being cluttered by everyone else's questions.

<Callout kind="analogy">

A city has a road map, a metro map and a land-registry map, and all three are true. The metro map bends distances and leaves out every street, and that's exactly why a tourist can use it in five seconds. Nobody complains that it doesn't show the roads. A design diagram is a map with one job.

</Callout>

## Structure, behaviour and data

Diagrams come in three families, and choosing the family is the first decision:

- **Structure:** what exists and what depends on what. C4 context, container and component diagrams, UML class and deployment diagrams.
- **Behaviour:** what happens over time. UML sequence, state and activity diagrams.
- **Data:** where information goes and where it rests. Data-flow diagrams.

The commonest mistake is forcing one family to do another's job. When you find yourself numbering fourteen arrows on a box diagram to explain the order things happen in, you want a sequence diagram. When a sequence diagram grows an `alt` box for every state an order can be in, you want a state diagram.

## Boxes and lines that say what they mean

Here is the diagram most teams draw first, and what it takes to make it readable. Step through it:

```visual flow
title: Same boxes, readable lines
nodes:
  - { id: app, label: iOS app, kind: client, at: [0, 0] }
  - { id: api, label: Orders API, kind: service, at: [2, 0] }
  - { id: db, label: Orders DB, kind: db, at: [4, 0] }
  - { id: apns, label: APNs, kind: external, at: [2, 2] }
edges:
  - [app, api]
  - [api, db, { style: data }]
  - [api, apns, { style: async }]
  - [apns, app, { style: async }]
steps:
  - say: "Four boxes, four lines, three line styles and no words on any line. Does the app call the API, or does the API push to the app? What does the dotted line mean? Every reader **guesses**, and they guess differently."
  - say: "Give every line a verb, and give direction a meaning: the arrow points **from whoever starts the conversation**. The app fetches; the answer comes back on the same request, so it needs no arrow of its own."
    send: app->api
    label: { app->api: fetch orders }
  - say: "Dotted means **reads and writes data** rather than calling a service. The label says what's stored."
    send: api->db
    label: { api->db: "read, write" }
  - say: "Dashed means **asynchronous**. The API hands a notification to Apple's push service and moves on; it gets no answer from the phone."
    send: api->apns
    label: { api->apns: send push }
  - say: "APNs delivers it whenever the phone is reachable, which may be minutes later or never. That delay is why the line is dashed."
    send: apns->app
    label: { apns->app: deliver }
  - say: "Badges add the **technology** where it helps a reader decide something, such as whether the database can do a join."
    label: { app: SwiftUI, api: "Go · REST", db: Postgres, apns: Apple }
  - say: "The legend now fits on one line: *solid* is a request and response, *dashed* an async message, *dotted* a read or write. Put it on the diagram, because the next reader won't have this walkthrough."
    active: [app->api, api->apns, api->db]
  - say: "This diagram answers *what talks to what*. It can't answer *what happens when the push never arrives*. That's a different question, so it needs a different diagram: a sequence."
    state: { apns: wait }
```

The rules that walkthrough used are worth learning by heart:

- **Every box** has a name, the kind of thing it is (an app, a service, a database, someone else's system), the technology where it matters, and, on a diagram meant for reading rather than talking over, a one-line responsibility.
- **Every line** has one direction and a label with a verb: "fetches orders", "sends push", not "uses" or nothing at all. Between processes, add the protocol: HTTPS, WebSocket, APNs.
- **Direction means one thing.** For calls, the arrow points from the caller. Say so in the legend, because some teams draw arrows the way data flows, and the two conventions point in opposite directions for every read.
- **Each line style means one thing.** Solid for request and response, dashed for asynchronous messages, dotted for data reads and writes is a common set; any set works if the legend says what it is.
- **Avoid two-headed arrows.** "App ↔ API" hides who starts the conversation, which is the difference between polling and push.
- **Give it a title with its scope and its date or version:** "Orders: container view, app 5.2, March". A diagram without a date can't tell you whether it's still true.

## One level of detail at a time

The second way diagrams fail is by mixing levels. A box called `OrderCell` (one UIKit class) beside a box called "Payments" (somebody's whole system) beside a box called "AWS" (a vendor) makes the reader re-zoom on every box. Nothing on the diagram is comparable to anything else.

The rule: **every box on one diagram should be the same kind of thing.** All deployable apps and services; or all modules inside one app; or all types inside one module. When you need to show what's inside a box, draw another diagram for it and say which box it zooms into. The C4 model, in the next lesson, turns this into a system of four zoom levels.

Size is a symptom. When a diagram needs more than about a dozen boxes, it's usually two diagrams at two levels pretending to be one.

## Notation: precise or familiar

You can draw on a spectrum of formality:

- **Informal boxes and lines** are fast and need no training, and are ambiguous unless you label everything.
- **C4** adds a small set of conventions (four levels, a few element types, labelled lines) but no required shapes.
- **UML** is a standard with precise meanings for every arrowhead and line style. The current version, UML 2.5.1, defines fourteen diagram types; you'll learn the five worth knowing in this module. It's unambiguous to readers who know it, and a puzzle to those who don't.

Pick **the least formal notation your readers already understand that is still unambiguous**, and add a legend for anything that isn't obvious. In an interview that's labelled boxes and lines. In a design doc it's C4 for structure plus a sequence diagram for the critical flow. In a low-level design interview about objects ("design the classes for a parking garage") it's a UML class diagram, because that's the shared language for object models.

## Diagrams as code

A diagram drawn in a picture editor is out of date the moment someone renames a module. Text-based tools keep the diagram next to the code, so it's reviewed in the same pull request:

- **Mermaid** renders inside Markdown on GitHub, GitLab and many wikis.
- **PlantUML** covers every UML diagram, and has a widely used C4 extension.
- **Structurizr DSL** describes a C4 *model* once and generates each view from it, so renaming a container updates every diagram that shows it.
- **D2** is a newer diagram language with good automatic layout.

The diagram from the walkthrough, in Mermaid:

```text title="orders-overview.mmd"
flowchart LR
    app["iOS app (SwiftUI)"] -- "fetch orders · HTTPS" --> api["Orders API (Go)"]
    api -. "read, write · SQL" .-> db[("Orders DB (Postgres)")]
    api -. "send push · HTTP/2" .-> apns["APNs (Apple)"]
    apns -. "deliver" .-> app
```

Text diagrams lose fine control over layout, and a dense one comes out tangled. Drawing tools such as Excalidraw, diagrams.net or Figma win when you're sketching live, or when the picture is for a talk. Many teams sketch in a drawing tool to think, then commit the settled version as code.

## Trade-offs

| Approach | Speed to make | Precision | Stays true | When it wins |
| --- | --- | --- | --- | --- |
| Sketch (whiteboard, Excalidraw) | Fastest | Low unless you label everything | No: it's a snapshot | Interviews, early discussions, thinking aloud |
| Drawing tool (diagrams.net, Figma) | Medium | As good as your discipline | Poorly: every change is by hand | Polished docs and presentations |
| Diagrams as code (Mermaid, PlantUML) | Medium | Good | Better: reviewed with the code | READMEs, design docs, ADRs |
| Model-based (Structurizr) | Slowest to set up | High, and consistent across views | Best: one model, many views | Large systems that need many diagrams |

<Callout kind="interview">

**Say** what you're about to draw and why: "Let me put down the main pieces first, then zoom into the app." Label each arrow as you draw it, out loud. **Ask** whether the level is right: "Is this enough detail on the backend, so I can spend the time on the client?" **Red flags:** unlabelled arrows, one box called "Backend" doing everything, two-headed arrows, drawing in silence, and a diagram you can't sum up in one sentence.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the app is not one box">

Your app, its widget, its notification service extension and its share extension are **separate processes** with separate memory. They share data only through an App Group container, a shared Keychain access group or the network. A diagram that shows "iOS app" as one box hides the arrows that break most often: the widget showing yesterday's data, or a notification extension that can't read the token it needs.

</Callout>
