## Why it matters

The container diagram tells you the iOS app exists. It says nothing about how the app is built, and that's what you, your reviewers and your interviewer spend most of their time on. A component diagram zooms into one container and shows its major parts and how they depend on each other. In an iOS codebase it's the picture of your module graph, and in an interview it's what "now tell me about the client" is asking for.

## What a component is

In C4, a **component** is a group of related functionality behind a well-defined interface, running inside one container. Three parts of that definition do the work:

- **Inside one container.** Components share a process and memory. The arrows between them are function calls, not network requests, so they don't time out or arrive twice the way the arrows between containers do.
- **Behind an interface.** A component is the thing other code talks to through a small surface: a protocol, a few public types. What's behind it can change without the arrows changing.
- **Group, not class.** A component is a feature, a service or a client, usually many types. `RideService` with its helpers and models is a component. `RideCardView` is not.

In Swift, the natural boundary is a **module**: a Swift package target or a framework, with `public` marking its interface. In an app that's still one big target, a component is a folder of types behind one protocol, and the boundary is only as real as the team's discipline.

## Zooming into the Pedal app

The [previous lesson](/design/learn/sd-diagrams-c4-context) drew Pedal's containers. Zoom into the iOS app and you find its components. A **static** component diagram shows who depends on whom. A **dynamic** one, which C4 lists as a supplementary diagram, numbers the interactions for one flow. Here's the dynamic view of starting a ride, step by step:

Notice the conventions carried over from the container level, and the ones that changed:

- The **boundary** is the container you zoomed into. Other containers (the Ride API, the App Group files) appear outside it, so the reader sees where the process ends.
- **Labels on in-process arrows** name the interface style, because there's no protocol to name: `async`/`await`, an `AsyncStream`, a delegate, a Combine publisher, a notification.
- **Technology** on a component is the framework it wraps: SwiftData, ActivityKit, the Keychain. That's what tells a reviewer which component they'd touch to change it.

## The diagram is the module graph

When the components are Swift modules, the static component diagram already exists: it's the dependency list in your package manifest. Pedal's local package looks like this:

```swift title="Package.swift (PedalKit)"
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "PedalKit",
    platforms: [.iOS(.v18)],
    products: [
        .library(name: "PedalApp", targets: ["RideFeature", "MapFeature"]),
        .library(name: "PedalWidget", targets: ["SharedRide"]),
    ],
    targets: [
        .target(name: "RideFeature", dependencies: ["RideDomain"]),
        .target(name: "MapFeature", dependencies: ["RideDomain"]),
        .target(name: "RideDomain", dependencies: ["APIClient", "RideHistory", "LiveRide", "SharedRide"]),
        .target(name: "APIClient", dependencies: ["Session"]),
        .target(name: "Session"),
        .target(name: "RideHistory"),
        .target(name: "LiveRide"),
        .target(name: "SharedRide"),
    ]
)
```

Two facts on that page are architecture. Features depend only on `RideDomain`, so the arrows on the diagram can't be bypassed: a feature that imports `APIClient` fails to build until someone adds the dependency in review. And the widget extension links only `SharedRide`, so the widget container's whole component diagram is one box, which is why it stays small enough for an extension's memory limit.

SwiftPM also refuses cyclic dependencies between targets, so a package graph is always a directed acyclic graph. Inside a single app target, nothing stops `MapView` from calling the Keychain directly, and a hand-drawn diagram can claim layers that the code ignores.

### The interface behind the box

A box on a component diagram stands for an interface. RideDomain's is small enough to read in one breath, and its doc comments are the descriptions that belong in the boxes:

```swift check title="RideService.swift (RideDomain)"
import Foundation

public struct BikeID: Hashable, Sendable {
    public let rawValue: String
    public init(_ rawValue: String) { self.rawValue = rawValue }
}

public struct Ride: Identifiable, Sendable {
    public let id: UUID
    public let bike: BikeID
    public let startedAt: Date
}

public struct Receipt: Sendable {
    public let ride: Ride.ID
    public let minutes: Int
    public let total: Decimal
}

public enum RideError: Error, Sendable {
    case bikeUnavailable
    case lockDidNotOpen
    case notSignedIn
    case offline
}

/// Starts, ends and tracks rides. The only component the features talk to about rides:
/// it hides the API client, the ride history store, Live Activities and the widget snapshot.
public protocol RideService: Sendable {
    /// Unlocks the bike and starts a ride, or explains why it couldn't
    func start(bike: BikeID) async throws(RideError) -> Ride
    /// Ends the ride and returns what it cost
    func end(_ ride: Ride.ID) async throws(RideError) -> Receipt
    /// The ride in progress, if any: every screen and the Live Activity follow this one value
    var currentRide: AsyncStream<Ride?> { get }
}
```

If you can't write the interface of a box in ten lines, it's either more than one component or a component with no real boundary. Both are worth knowing before you draw it.

## Level 4: code diagrams

The fourth C4 level shows the types inside one component: UML class diagrams, or entity-relationship diagrams for a schema. C4's own advice is to draw them **only for the most important or intricate components**, and to generate them from code where you can, because they change with every refactor. Xcode doesn't draw class diagrams; open-source tools such as SwiftPlantUML generate PlantUML from Swift sources.

In practice, a code-level diagram earns its place in two situations: a tricky object model a team keeps getting wrong (the types behind a payment flow), and the low-level design interview, where drawing the classes *is* the task. You'll learn the notation for both in the next lesson.

## How big, and how many

- **Five to fifteen components** per diagram. Past that, draw one diagram per feature, or group the features into one box and zoom separately.
- **One diagram per container that's worth explaining.** The app gets one; the widget extension, with one component, doesn't need one.
- **Shared infrastructure** (logging, analytics, image loading) used by everything turns the diagram into a hairball. Leave it off and say so in a note, or show it once as a box that everything may use.

## Keeping it true

A component diagram drifts the first time someone adds an `import`. Three habits keep it honest:

- **Generate the static view** from the build graph: `tuist graph` for Tuist projects, or a small script over `swift package describe --type json`, committed as Mermaid next to the code.
- **Turn the arrows into rules.** A test or CI step that fails when a feature module imports another feature, or anything but its domain module, is a fitness function, the idea from [Measuring quality: ISO 25010 and fitness functions](/design/learn/sd-quality-measuring). The diagram then describes a rule the build enforces.
- **Keep dynamic views few.** Draw one for each flow people actually ask about (starting a ride, signing in, restoring a purchase) and let the rest live in tests.

## Trade-offs

| View | Shows | Effort to keep current | Best reader | When it wins |
| --- | --- | --- | --- | --- |
| Static component diagram | Every component and its dependencies | Low if generated from the package graph | Reviewers, new joiners | Explaining layering and module boundaries |
| Dynamic view (numbered) | One flow through the components | Medium: redraw when the flow changes | Anyone debugging or extending that flow | The two or three flows everyone asks about |
| Code diagram (classes) | Types inside one component | High unless generated | The people working on that component | Intricate models, low-level design interviews |
| A README list of modules and their jobs | Names and responsibilities, no arrows | Lowest | Quick orientation | Small apps with few modules |

<Callout kind="interview">

When the interviewer says "let's go into the client", draw a component diagram: views, view models, a repository or service per domain, the API client, persistence, and the cross-cutting pieces (auth, image loading, analytics) as separate boxes. **Say** the interface style on each arrow: "the view model calls the repository with async/await and observes an `AsyncStream` of updates". **Ask** which flow they'd like to trace, then number it. **Red flags:** class names everywhere instead of components, a view that calls the network directly, no persistence box in an app that must work offline, and arrows with no direction.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: one target lets the diagram lie">

In a single app target, every type can see every other non-private type, so the layering on your diagram is a convention nobody checks. `@testable import` widens it further in tests. Moving components into Swift package targets turns each arrow into a declared dependency, and each missing arrow into a build error, which is the cheapest way to make a component diagram true.

</Callout>
