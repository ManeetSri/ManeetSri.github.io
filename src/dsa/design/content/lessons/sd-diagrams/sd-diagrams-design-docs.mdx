## Why it matters

Diagrams explain a design; documents get it **decided**. A design doc lets a team agree on a change before anyone builds it, across time zones and without a meeting, and an architecture decision record (ADR) keeps the reason for a decision long after the people who made it have moved on. At senior and staff level, much of your influence travels through these two documents, and interviewers ask about them directly: "tell me about a design doc you wrote, and how it changed".

## What a design doc is for

A design doc is written **before** the work, to reach a decision. It isn't a manual for the finished system. It does three jobs:

- **Thinking.** Writing the alternatives down is how you find out you only have one.
- **Agreement.** Reviewers comment in their own time, and disagreements surface while they're cheap.
- **Memory.** In a year, "why did we build sync this way?" has an answer with a date on it.

Not every change needs one. Write one when a change crosses team boundaries, is hard to reverse (the one-way doors from [Architecture, design and implementation decisions](/design/learn/sd-orientation-decisions)), touches security, privacy or data stored on devices, or will take more than a couple of weeks. A small, reversible change needs a good pull-request description and nothing more.

## The shape of a design doc

Teams vary the headings, but strong design docs share a skeleton:

1. **Header:** title, author, reviewers, status (draft, in review, approved), date.
2. **Context:** what exists today and what's wrong with it, with numbers where you have them.
3. **Goals and non-goals.** Goals are measurable ("an edit made offline reaches other devices within a minute of reconnecting"). Non-goals are what you're deliberately not doing ("real-time collaborative editing"). Non-goals prevent more arguments than any other section.
4. **The proposal:** the design, with its diagrams, API and data model.
5. **Alternatives considered:** each serious option, what it would cost and why it lost. A doc with no alternatives reads as a decision already made.
6. **Risks, security and privacy:** what could go wrong, and what new data flows the change creates.
7. **Rollout:** flags, migration, how you'll know it worked, and how to back out.
8. **Open questions:** what's still undecided, and who will decide it.

For an iOS change, a few questions belong in every doc, because reviewers from other platforms won't think to ask them:

| Question | Why it matters on iOS |
| --- | --- |
| What's the minimum iOS version? | It decides which APIs you can use: SwiftData and Observation need iOS 17 |
| How do older app versions behave? | They stay in the field for months and call the same API |
| What happens offline and in the background? | The system suspends apps, and background time is limited and not guaranteed |
| Does the privacy label or privacy manifest change? | New data flows must be declared before release |
| How does it roll out, and how does it roll back? | A shipped binary can't be rolled back, only replaced or switched off by a flag |
| What does it cost in app size, battery and data? | Users and App Store reviews notice all three |

## Diagrams inside a design doc

The diagrams from this module each have a natural place in a doc:

- **Near the top, a container diagram** (or the relevant part of one), so every reviewer starts from the same picture.
- **In the proposal, a sequence diagram** for the flow that changes, and a **state diagram** if the change introduces a lifecycle.
- **For a change, before and after.** Two small diagrams side by side say more than a paragraph of "currently… whereas in the new design…".
- **A caption on every figure** saying what question it answers: *Figure 2: what happens when two devices edit the same note offline.*
- **Diagrams as code** where your docs tool renders them (Mermaid in Markdown, PlantUML in many wikis), so reviewers can comment on a line and the diagram can change with the design.

The commonest failure is a diagram and prose that **disagree**: the text says the app uploads through the API, the figure shows it writing straight to storage. Reviewers can't tell which is the design, so they review neither. Read your own doc once looking only at the figures, and once only at the text.

## Architecture decision records

A design doc is long and covers many decisions; an ADR records **one decision** in a page or two. The format comes from Michael Nygard's 2011 post *Documenting Architecture Decisions*, and it has five parts:

- **Title:** a number and a short noun phrase. *ADR 0012: Observation for view models.*
- **Status:** proposed, accepted, deprecated, or superseded by a later ADR.
- **Context:** the forces at play: constraints, requirements, what's true today.
- **Decision:** what you will do, in full sentences, in the active voice.
- **Consequences:** what becomes easier and what becomes harder, honestly, including the costs.

ADRs live **in the repository**, usually in a folder like `docs/adr/`, numbered in order, so they're reviewed in pull requests and versioned with the code they describe. Once accepted, an ADR isn't edited: when the decision changes, a new ADR supersedes it, and the old one's status points at the new one. The log becomes a history of how the architecture got to where it is:

```visual states
title: An ADR's status, over its life
states:
  - { id: proposed, label: Proposed, at: [0, 0] }
  - { id: accepted, label: Accepted, at: [1, 0] }
  - { id: superseded, label: Superseded, at: [2, 0] }
  - { id: rejected, label: Rejected, at: [1, 1] }
  - { id: deprecated, label: Deprecated, at: [2, 1] }
initial: proposed
final: [superseded, rejected, deprecated]
transitions:
  - [proposed, proposed, revise]
  - [proposed, accepted, approve]
  - [proposed, rejected, reject]
  - [accepted, superseded, supersede]
  - [accepted, deprecated, deprecate]
intro: "An ADR starts as a **proposal** in a pull request, where its text can still change."
events:
  - { event: revise, say: "Review comments change the wording, the options or the consequences. This is the only state in which the text is edited." }
  - { event: approve, say: "Merged: **accepted**. From here on the context, decision and consequences are frozen, because they record what was true when the decision was made." }
  - { event: supersede, say: "Two years later the team changes its mind. A **new** ADR records the new decision and links back; this one's only edit is its status, *Superseded by ADR 0031*. Reading the two in order tells the whole story." }
```

Variants such as MADR (Markdown Architectural Decision Records) add a list of the options considered with the pros and cons of each.

Here's one for a decision many iOS teams have recently made:

```markdown title="docs/adr/0012-observation-for-view-models.md"
# 12. Observation for view models

Date: 2026-03-02
Status: Accepted

## Context

Release 6.0 raises the minimum deployment target to iOS 17. Our 140 view models
are ObservableObject classes with @Published properties. SwiftUI re-evaluates a
view whenever any @Published property of an observed object changes, so the feed's
large view model makes every row's view recompute on each like. The Observation
framework (iOS 17) tracks which properties each view's body actually reads.

## Decision

New view models use the @Observable macro. Existing view models move to
@Observable when a change touches them. View models no longer use Combine;
streams from the data layer are consumed with async sequences.

## Consequences

- Views update only when a property they read changes; the feed no longer
  recomputes every row on each like.
- Less boilerplate: no @Published, and @State replaces @StateObject at creation.
- For a year or more the codebase mixes both styles; reviews must check that
  a view uses the wrapper that matches its model.
- Code that subscribed to $property publishers must be rewritten, and so must
  the tests that observed them.
- Supersedes nothing. Revisit if we adopt a store-based architecture (see ADR 0009).
```

Notice what makes it useful: a number and a date, the constraint that made the decision possible (iOS 17), the measured problem it fixes, a decision a new joiner can follow without asking, and consequences that include the costs.

## Trade-offs

| Document | Length | Decides | Lives in | When it wins |
| --- | --- | --- | --- | --- |
| Pull-request description | A paragraph | One reversible change | The pull request | Most changes |
| ADR | One or two pages | One significant decision | The repository, numbered | Decisions people will later ask "why?" about |
| Design doc | A few pages | A whole design and its alternatives | The team's docs tool | Large, cross-team or hard-to-reverse changes |
| RFC | A design doc with a formal review | Changes that need agreement from many teams | A shared RFC process | Platform-wide changes, shared libraries, standards |

<Callout kind="interview">

Senior and staff interviews ask for stories: "tell me about a design you proposed that others disagreed with." **Say** what the doc contained (the goals, the non-goals, the alternatives) and what changed because of the review. **Ask**, when you're the candidate, how the team records decisions; it tells you a lot about how it works. In a design interview, the wrap-up *is* the "alternatives considered" section spoken aloud. **Red flags:** docs written after the code to justify it, no alternatives ever considered, and decisions that live only in a chat thread.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: you can't roll back an app">

A backend rollout plan can say "revert the deploy". An iOS one can't: once a version is installed, the App Store has no way to put the previous build back. You can pause a phased release, and you can submit a fixed build and wait for review, but the safe exits must be built in **before** release: a server-side flag that turns the feature off, a kill switch for the new code path, and data formats the previous version can still read. A rollout section that doesn't name them isn't finished.

</Callout>

## Practice

**The offline sync design doc** is a design doc with exactly the problems this lesson describes: a figure that disagrees with the text, no non-goals, no alternatives and a rollout plan that assumes you can roll back an app. Review it, then compare your findings with the reference review.

```cards
- id: design-doc-purpose
  front: "What is a design doc for, and when is it written?"
  back: "It's written before the work, to reach a decision: it helps the author think, lets reviewers agree asynchronously, and records why. It isn't documentation of the finished system."
- id: design-doc-non-goals
  front: "Why do design docs list non-goals?"
  back: "They say what the design deliberately won't do, which stops reviewers arguing about features that were never in scope and keeps the design small."
- id: adr-format
  front: "What are the parts of an ADR in Michael Nygard's format?"
  back: "Title (numbered), status, context, decision and consequences. One decision per record, kept in the repository, never edited after acceptance: a new ADR supersedes it."
- id: ios-rollback
  front: "Why must an iOS design doc's rollout plan be different from a backend's?"
  back: "A shipped binary can't be rolled back. The exits (server-side flags, kill switches, formats the old version can read) have to exist before release."
```
