## Why it matters

You'll read many more diagrams than you draw: in onboarding docs, design reviews, incident write-ups, the backend team's wiki, and in interviews where the interviewer sketches a system and asks what you'd change. Most of them break at least one of the rules from this module. Reading one well means knowing what to check, spotting what's missing, and turning each gap into a question rather than a verdict.

## Read it like a code review

A diagram is a claim about a system. Review it the way you'd review a pull request, in a fixed order, so you don't stop at the first thing that catches your eye:

1. **Purpose and scope.** Is there a title, a date or version, an author? What question does it answer, and for whom? A diagram with no date can't tell you whether it's still true.
2. **The key.** What do the shapes, colours and line styles mean? If there's no key, write down your guess and check it with the author.
3. **Level.** Is every box the same kind of thing: all deployable apps and services, or all modules in one app? Mixed levels mean someone zoomed in on part of the picture and not the rest.
4. **Trace one real request.** Pick a user action ("open the feed") and follow it box to box. If you can't, an arrow is missing or ambiguous, and that's your first question.
5. **Interrogate each arrow.** Who starts it? Does the sender wait? What does it carry, over what? What happens when it fails or arrives twice?
6. **Look for what isn't there.** Failure paths, push, background work, caches and on-device storage, authentication, third parties, monitoring, older app versions.
7. **Check it against reality.** The package graph, the Xcode targets, the API spec, the date of the last change. Ask the owner if it's current.

The output is a short list of questions, not a grade.

## A kick-off diagram, read critically

Here's the kind of slide you'll see in a first meeting about a photo-sharing app. Step through a careful reading of it:

```visual flow
title: "Architecture (from the kick-off deck)"
nodes:
  - { id: cell, label: FeedCell, kind: view, at: [0, 0] }
  - { id: app, label: iOS App, kind: client, at: [0, 2] }
  - { id: backend, label: Backend, kind: service, at: [2, 1] }
  - { id: redis, label: Redis, kind: cache, at: [4, 0] }
  - { id: db, label: DB, kind: db, at: [4, 2] }
  - { id: aws, label: AWS, kind: external, at: [2, 3] }
edges:
  - [cell, app]
  - [app, backend]
  - [backend, app]
  - [backend, redis]
  - [backend, db]
  - [redis, db]
  - [app, aws, uploads]
steps:
  - say: "First, purpose and scope. There's no date, no version and no sentence saying what this shows. Is it today's system, or the plan? Write that down as question one."
  - say: "**Mixed levels.** `FeedCell` is one UIKit class; *Backend* is a whole system; *AWS* is a vendor. Somebody zoomed in on the part they work on. Ask which level the diagram is meant to be at."
    active: [cell, backend, aws]
    state: { cell: error }
  - say: "**Two unlabelled arrows** between the app and the backend. Request and response? Polling? A WebSocket the server pushes on? Each answer is a different design."
    active: [app->backend, backend->app]
    state: { cell: null, app: error }
  - say: "**One box called Backend.** Auth, feed, uploads and notifications are probably all in there, and they fail independently. Ask what's inside, and which parts the app calls directly."
    state: { app: null, backend: error }
  - say: "**Redis talks to the DB on its own?** Caches don't usually do that. It may be a write-through cache, a replica or a slip of the mouse; each changes how fresh the feed can be."
    active: [redis->db]
    state: { backend: null, redis: wait }
  - say: "**One label, and it's vague.** Does the app upload straight to storage with a pre-signed URL, or through the backend? It matters for large videos on cellular."
    active: [app->aws]
    state: { redis: null, aws: wait }
  - say: "**What's missing** matters most. A photo app with no CDN for images, no push for likes and comments, and no store on the device, although the brief says the feed works offline."
    state: { aws: null, app: wait }
  - say: "None of this means the design is bad. It means the diagram can't yet answer the questions a reviewer needs it to. Six questions to the author, and an offer to redraw it with them, is a good outcome."
    state: { app: null }
```

The order mattered. Starting from "what's missing" would have produced a wish list; starting from purpose and level showed that the diagram was drawn by someone who knew the app well and the backend barely, which tells you whom to ask about which box.

## Diagram smells

Some patterns come up again and again. Each one hides a specific piece of information, and each has a question that recovers it:

| Smell | What it hides | Ask |
| --- | --- | --- |
| An unlabelled arrow | What's carried, who starts it, over what | "What goes along this line, and who starts it?" |
| A two-headed arrow | Polling or push; which side can call the other | "Can the server reach the app, or does the app always ask?" |
| A box called Backend, Server or Cloud | The parts that fail and scale independently | "What's inside, and which of those does the app call?" |
| Mixed levels | What the rest of the system looks like at that level | "Is this the container view or the component view?" |
| A vendor logo instead of a role (AWS, Firebase) | What it's actually used for | "Which service, for what: storage, auth, analytics?" |
| No failure or offline path | Behaviour when the network or a dependency is down | "What does the user see if this call fails?" |
| Everything connected to everything | Layering and dependency rules | "Which dependencies are allowed, and which are accidents?" |
| Colours or line styles with no key | Whatever the author meant by them | "What does dashed mean here?" |
| No date or version | Whether it's still true | "When was this last right?" |

## Reading behaviour diagrams

Sequence, state and data-flow diagrams have their own checks:

- **Sequence diagrams:** find every call without a reply and ask who waits. Find the first network arrow and ask what happens if it never returns; look for an `alt` or `break` covering it. Check that participants are at one level, and that work after an `await` happens where the diagram says (on the main actor or not).
- **State diagrams:** for each state, ask what happens on cancel, on an error and when the app goes to the background. Look for states you can't reach from the start, and states you can't leave that aren't final. Check that two arrows don't leave one state on the same event without guards to tell them apart.
- **Data-flow diagrams:** follow every flow that crosses a trust boundary and ask what data it carries and why. Look for stores that receive data from outside without a process in between, and for SDKs drawn as boxes with no arrows leaving the device.

### A backend diagram, read by a client engineer

When the backend team shows you their architecture, you don't need to judge their database choice. You need answers to the questions that shape the app:

- Which endpoints does the app call, and through what: a gateway, a CDN, directly?
- Which region serves which users, and what latency does that mean on cellular?
- Which calls are **idempotent**, so the app can retry them safely after a timeout?
- What can the server push, and through what: APNs, a WebSocket, nothing?
- What's cached at the edge, and for how long?
- How are breaking changes rolled out, given that old app versions stay in the field?

You'll go deeper in D41, which has a whole lesson on reading backend diagrams from the client's side.

## Asking without making enemies

The author of the diagram usually knows things it doesn't show. Phrase questions as what you couldn't tell, not what they got wrong:

- "I couldn't tell whether the feed is pulled or pushed. Which is it?" rather than "This arrow is wrong."
- "Is the Redis-to-DB line a replica or a write-through?" rather than "Caches don't talk to databases."
- Offer to fix it: "Want me to put the answers on the diagram?" If the diagram lives in the repo as Mermaid or Structurizr, that's a pull request, and the next reader benefits.

## Trade-offs

| How you read | Time | Catches | Misses | When it wins |
| --- | --- | --- | --- | --- |
| Skim for the gist | A minute | The big pieces | Ambiguity, gaps, staleness | Orientation before a meeting |
| The seven-step review | Ten to twenty minutes | Ambiguous arrows, mixed levels, missing parts | Whether it matches the code | Design reviews, onboarding into a codebase |
| Tracing scenarios | Five minutes per scenario | Missing arrows and failure paths | Parts no scenario touches | Before building on top of the system |
| Checking against code and config | Longest | Drift between the picture and reality | Intent the code doesn't show | Before trusting it for a decision |

<Callout kind="interview">

Some interviews hand you a diagram: "here's our current design; what would you change?" **Say** what you see first, out loud and in order: purpose, level, one traced request. Then **ask** about the arrows that matter for the client: "is this a poll or a push?", "does the app talk to storage directly?". Only then suggest changes, each tied to a requirement. **Red flags:** criticising the notation instead of the design, redesigning everything without asking a question, and accepting the diagram as complete when push, offline or failure paths are obviously missing.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: 'the app uploads' may not be the app">

A diagram arrow from the app to storage, labelled "upload video", hides a real choice. With a background `URLSession`, the transfer is run by the system, not your process: it carries on while your app is suspended, or even after the system has terminated it, and the system relaunches the app in the background to deliver the result. A sequence diagram that shows the app waiting for the response is wrong for that design. When you read an upload or download arrow, ask which session type it uses, because it decides which process the arrow really starts from and where the reply goes.

</Callout>

  front: "As a client engineer, what do you need from a backend diagram?"
