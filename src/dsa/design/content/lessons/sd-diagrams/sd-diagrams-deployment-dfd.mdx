## Why it matters

A container diagram says what runs; it doesn't say **where**, or how many copies, or which versions. A deployment diagram does, and for a mobile app the answer is unusual: the client is installed on millions of devices you don't control, in several versions at once. A data-flow diagram answers a different question that every app now has to answer in writing: where does the user's data go, and where does it leave the phone? App Store privacy labels, privacy manifests, security reviews and threat models all start from it.

## Deployment diagrams

A UML deployment diagram shows the hardware and runtime environments, and what's deployed onto each:

- A **node** is drawn as a 3D box: a «device» (an iPhone, a server, a smart lock) or an «execution environment» (an iOS process, a container runtime, a cloud region).
- An **artifact** is a deployable file placed on a node: `Pedal.app`, `PedalWidget.appex`, a server's container image.
- A **communication path** is a line between nodes, labelled with its protocol: HTTPS, Bluetooth LE, cellular.
- Multiplicity on a node says how many: `ride-api × 3`.

Here is where the Pedal containers from [C4: system context and container diagrams](/design/learn/sd-diagrams-c4-context) actually run. The dashed boundaries are deployment nodes:

Deployment diagrams earn their keep when **where** something runs changes the design: an offline fallback path (the Bluetooth line), instances that can't share memory (the three API copies), a database in one region with users on three continents, a watch that only reaches the network through the phone.

### The client is deployed by millions of people

On the server you choose when a new version replaces the old one. On iOS, the App Store and your users do. A deployment diagram for a mobile product is honest only if it shows **every version still in use**:

- A release with **phased release** turned on reaches users with automatic updates over seven days: 1%, 2%, 5%, 10%, 20%, 50%, then 100%. People can still update by hand on day one.
- Many people keep an old version for months. Some can't update at all, because their device can't run your new minimum iOS version.
- So the API in the diagram above is talking to version 5.4, 5.3 and several older ones at the same moment.

| What the version spread forces | Why |
| --- | --- |
| Backwards-compatible API changes, or versioned endpoints | You can't change every client when you change the server |
| Server-side feature flags | A shipped binary can't be changed, but its behaviour can |
| A minimum supported version, enforced politely | Eventually old versions cost more than they're worth |
| Stored formats with a version number | 5.4 may read a file that 5.2 wrote, or the App Group file another build wrote |

Draw it as a note on the client node ("5.2 to 5.4 in the field") or as several client artifacts. Either way, the reader can't miss that the client isn't one thing.

## Data-flow diagrams

A **data-flow diagram** (DFD) follows data instead of calls. It's older than UML, and it's still the standard input to threat modelling and privacy reviews. It has four symbols:

- **External entities**: people and systems outside your control that data comes from or goes to. The rider, Core Location, an analytics vendor.
- **Processes**: something that transforms data, numbered and named with a verb: *1 Track ride*. One notation draws them as circles, another (Gane–Sarson) as rounded rectangles.
- **Data stores**: data at rest. Ride history on the device, the rides database on the server.
- **Data flows**: arrows labelled with the **data** they carry, a noun phrase: *route*, *payment token*, not *sends* or *calls*.

And a few rules, which are what make a DFD trustworthy:

- **Every flow touches a process.** Data never moves from a store to a store, from an external entity to a store, or between two external entities without a process doing it. If you can't name the process, you don't know what code moves the data.
- **Every process has inputs and outputs.** A process with only inputs is a black hole; one with only outputs is a miracle. Both mean something's missing.
- **Levels nest.** A context-level DFD shows the whole system as one process. Level 1 splits it into processes 1, 2 and 3; level 2 splits process 1 into 1.1, 1.2 and so on.
- **Trust boundaries** are dashed lines where data crosses from one level of trust to another: from the device to your servers, from your servers to a vendor, from your app's process into an SDK's.

### The boundary, in code

A trust boundary on the diagram should be a place in the code where you can enforce it. For third-party analytics, that's a wrapper every event passes through, with an **allow-list** of what may leave:

```swift check title="BoundaryAnalytics.swift"
struct AnalyticsEvent: Sendable {
    let name: String
    var properties: [String: String]
}

protocol AnalyticsSink: Sendable {
    func send(_ event: AnalyticsEvent) async
}

/// The device-to-vendor trust boundary from the data-flow diagram. Every event bound for a
/// third party passes through here, and only allow-listed properties cross it.
struct BoundaryAnalytics: AnalyticsSink {
    let vendor: any AnalyticsSink
    static let allowedKeys: Set<String> = ["ride_minutes", "bike_model", "app_version"]

    func send(_ event: AnalyticsEvent) async {
        var outgoing = event
        outgoing.properties = event.properties.filter { Self.allowedKeys.contains($0.key) }
        await vendor.send(outgoing)
    }
}
```

An allow-list rather than a block-list means a new property someone adds next year (`last_location`) stays on the device until a person decides it may leave. The diagram says *what* crosses; the wrapper makes sure nothing else does.

## Trade-offs

| Diagram | Answers | Shows time or order | Best reader | When it wins |
| --- | --- | --- | --- | --- |
| Container | What runs, and what talks to what | No | Engineers, new joiners | Explaining the system's parts |
| Deployment | Where each part runs, how many copies, which versions | No | Operations, on-call, backend engineers | Regions, failover, offline paths, version skew |
| Data-flow | Where data goes and rests, and where it crosses trust boundaries | No | Security, privacy, legal, App Review answers | Privacy labels, threat models, GDPR requests |
| Sequence | What happens in order for one flow | Yes | Anyone debugging that flow | Purchases, sign-in, sync |

<Callout kind="interview">

Two questions in mobile design interviews are deployment and data-flow questions in disguise. "How do you ship a breaking API change?" is about the versions on the deployment diagram: **say** that old clients stay in the field for months, so you add fields rather than change them, version endpoints, and gate behaviour behind server-side flags. "What data does this feature collect?" is a DFD: **trace** each flow off the device and say who receives it and why. **Red flags:** assuming every user updates on release day, and an analytics SDK drawn as a box with no arrows leaving the phone.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: an SDK's data flows are yours">

Data that a third-party SDK sends from inside your app is data **your app** collects, as far as your App Store privacy details are concerned. SDKs on Apple's list of commonly used SDKs must ship their own privacy manifest, and Xcode can combine every manifest in an archive into one privacy report. That report tells you what the SDKs *declare*; only a data-flow diagram, checked against real network traffic, tells you what they *do*.

</Callout>
