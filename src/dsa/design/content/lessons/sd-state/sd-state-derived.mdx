## Why it matters

A basket total that's a few pence off, a Checkout button that stays disabled after the last item is added, a badge that says 3 when the list shows 2. Each is a value that could have been computed, stored instead, and then not updated on one path. The fix is a habit: **store the facts, compute everything else.** In interviews it's the quickest way to show you design state deliberately: you list what's stored, and say what's derived from it.

## Facts and derived values

**Derived state** is any value you can compute from other state: a count, a total, whether a form is valid, the filtered and sorted list, the list grouped into sections, an "Updated 5 min ago" label, whether a button is enabled.

The test is one question: **is this ever set on its own?** If it only ever changes because something else changed, it's derived. If the user or the server can set it independently, it's a fact, even if it usually matches a calculation. A delivery fee the server quotes is a fact; a subtotal of the lines is derived. A list sorted by the user's chosen order is derived from two facts: the items *and* the chosen order.

Keep the stored facts to the smallest set that's independent, and compute the rest.

## Stored derived state drifts

Here are two baskets. The first stores its total and updates it as lines change; the second stores only the lines:

```swift run title="Storing a total vs computing it"
struct Line {
    let name: String
    let pence: Int
    var quantity: Int
}

/// Stores a total as well as the lines it comes from
struct DriftingBasket {
    private(set) var lines: [Line] = []
    private(set) var totalPence = 0

    mutating func add(_ line: Line) {
        lines.append(line)
        totalPence += line.pence * line.quantity
    }

    mutating func setQuantity(_ quantity: Int, at index: Int) {
        lines[index].quantity = quantity   // the total was forgotten here
    }
}

/// Stores only the facts, and computes the rest when asked
struct Basket {
    private(set) var lines: [Line] = []

    var totalPence: Int { lines.reduce(0) { $0 + $1.pence * $1.quantity } }
    var itemCount: Int { lines.reduce(0) { $0 + $1.quantity } }
    var canCheckOut: Bool { itemCount > 0 }

    mutating func add(_ line: Line) { lines.append(line) }
    mutating func setQuantity(_ quantity: Int, at index: Int) { lines[index].quantity = quantity }
}

var drifting = DriftingBasket()
var basket = Basket()
for line in [Line(name: "Coffee", pence: 450, quantity: 1), Line(name: "Bagel", pence: 300, quantity: 2)] {
    drifting.add(line)
    basket.add(line)
}
drifting.setQuantity(3, at: 0)
basket.setQuantity(3, at: 0)

print("Stored total:", drifting.totalPence)
print("Computed total:", basket.totalPence, "for", basket.itemCount, "items")
```

```output
Stored total: 1050
Computed total: 1950 for 5 items
```

Every mutation of `DriftingBasket` has to remember the total, and the next developer to add `remove(at:)` or `applyPromo(_:)` must remember too. `Basket` has nothing to remember: its total can't be wrong unless its lines are.

## Computed properties, and how SwiftUI sees them

In Swift, derived state is a computed property. With `@Observable` there's nothing more to wire up: when a view's `body` reads `basket.totalPence`, Observation records which **stored** properties the getter touched (`lines`), and re-renders the view when any of them changes. A computed property is tracked through its inputs.

```swift check ios title="Derived values in a SwiftUI basket"
import SwiftUI

struct Line: Identifiable {
    let id: String
    let name: String
    let pence: Int
    var quantity: Int
}

@Observable
final class BasketModel {
    var lines: [Line] = []
    var updatedAt: Date?

    var totalPence: Int { lines.reduce(0) { $0 + $1.pence * $1.quantity } }
    var itemCount: Int { lines.reduce(0) { $0 + $1.quantity } }
    var canCheckOut: Bool { itemCount > 0 }
}

struct BasketFooter: View {
    let basket: BasketModel

    var body: some View {
        VStack {
            Text(Decimal(basket.totalPence) / 100, format: .currency(code: "GBP"))
            if let updatedAt = basket.updatedAt {
                // Derived from a stored date and the clock; SwiftUI keeps it current
                Text("Prices checked \(updatedAt, style: .relative) ago")
            }
            Button("Check out (\(basket.itemCount))") {}
                .disabled(!basket.canCheckOut)
        }
    }
}
```

The "checked 5 minutes ago" label is derived from a stored date *and the clock*. Store the date, never the string: `Text(date, style: .relative)` keeps the label current without a timer, and `TimelineView` does the same for anything more custom.

## When computing it is too expensive

Most derived values are cheap. Summing 100 basket lines takes microseconds; computing it on every render is fine, and caching it would only add a way to be wrong. Some are not cheap: filtering and sorting thousands of rows with locale-aware comparison, grouping a feed into sections, or building an attributed string per row. Do those in `body` and they run on every invalidation, including every keystroke in a search field.

Estimate before you cache. Move the sliders to see when a filter-and-sort stops fitting in a frame:

```visual estimator

  - { id: comparisons, label: Comparisons in one sort, formula: items * log2(items), format: si }
```

When it doesn't fit, cache the result, but follow one rule: **the owner of the inputs maintains the cache, privately, in the same change.** Then the cached value can't drift, because nothing else can change the inputs without the owner noticing.

```swift check ios title="A cached derived list, maintained by the owner of its inputs"
import SwiftUI

struct Product: Identifiable {
    let id: Int
    let name: String
}

@Observable
final class CatalogueSearch {
    var products: [Product] = [] { didSet { rebuild() } }
    var query = "" { didSet { rebuild() } }

    /// Derived from `products` and `query`; only `rebuild()` writes it
    private(set) var results: [Product] = []

    private func rebuild() {
        results = products
            .filter { query.isEmpty || $0.name.localizedStandardContains(query) }
            .sorted { $0.name.localizedStandardCompare($1.name) == .orderedAscending }
    }
}

struct CatalogueList: View {
    @State private var search = CatalogueSearch()

    var body: some View {
        List(search.results) { product in
            Text(product.name)
        }
        .searchable(text: $search.query)
    }
}
```

`results` is still derived state, just computed eagerly. What makes it safe is that it's `private(set)` and written in one function, triggered by the only two inputs. For work too slow even for that (a search over 100,000 messages), move it off the main actor and drop results that arrive for an old query, as the next lesson's view states do with numbered requests.

## Trade-offs

| | Compute on every read | Cache in the owner of the inputs | Store it separately |
| --- | --- | --- | --- |
| Can it drift? | no | no, if only the owner writes it | yes, on any missed path |
| Cost | the work on every render | the work once per input change, plus memory | the work once, plus the sync code |
| Code | a computed property | `didSet` (or a method) and a `private(set)` value | updates in every mutation |
| Wins when | it's cheap: almost always | it's measurably expensive and read often | almost never; only for values the server sends as facts |

<Callout kind="interview">

**What to say:** list the stored state, then the derived state, out loud: "The basket stores lines and a promo code. The subtotal, discount, total, item count and whether you can check out are all computed from those." Interviewers hear that you've kept the stored state minimal.

**What to ask:** is this number computed on the client or quoted by the server? A delivery fee or tax the server calculates is a fact to store and display, not a value to recompute.

**Red flags:** an `isValid` flag updated by hand from three text fields; a stored `count` next to the array; "we'll recompute it in `viewWillAppear`".

</Callout>

<Callout kind="gotcha" title="iOS gotcha: onChange that copies one state into another">

`.onChange(of: items) { count = items.count }` stores derived state in a second `@State` and keeps it in step by hand. It's a frame late (the view renders once with the old count, then again), and it's one more path that can be missed. Read `items.count` directly in `body`, or make it a computed property on the model.

</Callout>
