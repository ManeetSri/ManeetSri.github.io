## Why it matters

MVP is the first pattern most UIKit teams reached for when their view controllers became unmanageable, and plenty of large apps still run on it. It moves every decision a screen makes out of the view controller into a plain object you can test without UIKit, while keeping UIKit's own lifecycle untouched. Interviewers ask "MVP or MVVM?" often, and the answer they want isn't a preference: it's the difference in **which way the arrows point** and what that costs.

## From MVC to MVP

In Apple MVC, which you met in [Apple MVC: the view controller as mediator](/design/learn/sd-mvc-apple), a view controller does two jobs. It's part of the view (it owns the labels, the layout, the table view) and it's the controller (it fetches, decides what to show, reacts to taps). Those jobs change for different reasons, and the second can't be tested without the first.

**Model–View–Presenter** splits them:

- **The model** is everything below the screen: domain types, repositories, services.
- **The view** is the view controller and its views, demoted. It forwards user events and does what it's told. It implements a small **view protocol**.
- **The presenter** is a plain Swift class. It receives the view's events, talks to the model, makes every decision, and tells the view what to show through that protocol.

The view controller still exists, and UIKit still calls `viewDidLoad` on it. What changes is that it holds no logic: it's the screen's hands, and the presenter is its head.

<Callout kind="analogy">

A newsreader and an editor. The newsreader reads exactly what's on the autocue, in the order it appears, and decides nothing. The editor decides what goes on the autocue. To check the editor's choices, you don't need a studio: read the autocue script.

</Callout>

## A round trip

Here's a recipe screen loading and then reacting to a tap on the servings stepper. Watch which way each message goes.

```visual sequence

  - [user, view, taps +]
  - [view, presenter, increaseServingsTapped()]
  - [presenter, view, showServings("5 servings")]
  - [presenter, view, "showIngredients([…])"]
steps:
  - { upTo: 0, say: "UIKit calls `viewDidLoad()` on the view controller, which tells its presenter and nothing more." }
  - { upTo: 3, say: "The presenter turns on loading through the view protocol and asks the service for the recipe." }
  - { upTo: 5, say: "With the recipe in hand, the presenter **formats** it: the view receives a title and `\"1 h 15 min\"`, never a `Recipe`." }
  - { upTo: 7, say: "A tap is an event, not a decision. The view forwards it to the presenter, which knows the current servings and the limits." }
  - { upTo: 9, say: "The presenter recalculates every quantity and pushes the results. The view could be replaced by a spy that records these calls." }
```

Two properties fall out of that picture. The presenter holds **all** the screen's state (the recipe, the current servings), so the view has nothing to remember. And every arrow from the presenter to the view is a **command** through a protocol, so a test can stand in for the view.

## The view protocol and the presenter

An order-tracking screen, in MVP. Start with the contract: everything the presenter may tell the screen.

```swift check ios group=mvp title="OrderStatus.swift"
import UIKit

struct Order: Sendable {
    enum Status: Sendable { case placed, packing, outForDelivery, delivered }
    let id: String
    let status: Status
}

protocol OrderService: Sendable {
    func order(id: String) async throws -> Order
    func cancel(orderID: String) async throws
}

/// What the presenter can tell the screen. Every method is a command; none returns anything.
@MainActor
protocol OrderStatusView: AnyObject {
    func showStatus(title: String, detail: String)
    func showProgress(step: Int, of steps: Int)
    func setCancelHidden(_ hidden: Bool)
    func showError(_ message: String)
}

@MainActor
final class OrderStatusPresenter {
    weak var view: (any OrderStatusView)?     // weak: the view controller owns the presenter
    private let orderID: String
    private let service: any OrderService
    private var order: Order?

    init(orderID: String, service: any OrderService) {
        self.orderID = orderID
        self.service = service
    }

    func viewDidLoad() async {
        do {
            let order = try await service.order(id: orderID)
            self.order = order
            show(order)
        } catch {
            view?.showError("We couldn't load your order. Pull to try again.")
        }
    }

    func cancelTapped() async {
        guard let order, order.status == .placed else { return }
        do {
            try await service.cancel(orderID: order.id)
            view?.showStatus(title: "Order cancelled", detail: "You haven't been charged.")
            view?.setCancelHidden(true)
        } catch {
            view?.showError("We couldn't cancel this order.")
        }
    }

    private func show(_ order: Order) {
        let (title, detail, step): (String, String, Int) = switch order.status {
        case .placed: ("Order placed", "We'll start packing soon.", 1)
        case .packing: ("Packing your order", "Your shopper is picking your items.", 2)
        case .outForDelivery: ("On its way", "Your driver is nearby.", 3)
        case .delivered: ("Delivered", "Enjoy your shopping.", 4)
        }
        view?.showStatus(title: title, detail: detail)
        view?.showProgress(step: step, of: 4)
        view?.setCancelHidden(order.status != .placed)     // a rule: only placed orders can be cancelled
    }
}
```

The presenter imports nothing from UIKit that it uses: it would compile against Foundation alone, which is what lets its tests run on a Mac. The view controller is the other half, and it's deliberately dull:

```swift check ios group=mvp title="OrderStatusViewController.swift"
final class OrderStatusViewController: UIViewController, OrderStatusView {
    private let presenter: OrderStatusPresenter
    private let titleLabel = UILabel()
    private let detailLabel = UILabel()
    private let progressView = UIProgressView(progressViewStyle: .default)
    private let cancelButton = UIButton(configuration: .gray())

    init(presenter: OrderStatusPresenter) {
        self.presenter = presenter
        super.init(nibName: nil, bundle: nil)
    }

    required init?(coder: NSCoder) { nil }

    override func viewDidLoad() {
        super.viewDidLoad()
        // Layout omitted: a stack view with the labels, progress and button
        presenter.view = self
        cancelButton.addAction(UIAction { [presenter] _ in
            Task { await presenter.cancelTapped() }
        }, for: .primaryActionTriggered)
        Task { await presenter.viewDidLoad() }
    }

    func showStatus(title: String, detail: String) {
        titleLabel.text = title
        detailLabel.text = detail
    }

    func showProgress(step: Int, of steps: Int) {
        progressView.setProgress(Float(step) / Float(steps), animated: true)
    }

    func setCancelHidden(_ hidden: Bool) {
        cancelButton.isHidden = hidden
    }

    func showError(_ message: String) {
        let alert = UIAlertController(title: nil, message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default))
        present(alert, animated: true)
    }
}
```

Each method is a line or two that maps a value onto a view. There's nothing in it worth a unit test, and that's the goal: whatever is left in the view controller should be so simple that a glance verifies it.

### Who creates whom

Something has to build both halves and connect them. Usually it's a coordinator or a small factory:

```swift check ios group=mvp title="Assembling the screen"
@MainActor
enum OrderStatusScreen {
    static func make(orderID: String, service: any OrderService) -> UIViewController {
        let presenter = OrderStatusPresenter(orderID: orderID, service: service)
        return OrderStatusViewController(presenter: presenter)
    }
}
```

The ownership is one-way: the view controller holds the presenter **strongly**, the presenter holds the view **weakly**. Make both strong and neither is ever freed. The button's action captures the presenter (not the view controller), which is safe for the same reason.

## Passive view or supervising controller

Martin Fowler named two flavours of MVP, and real codebases sit somewhere between them:

- **Passive view:** the view has no logic at all. The presenter sets every label and every flag. Everything is testable; the cost is a wide view protocol and a lot of forwarding.
- **Supervising controller:** the view handles simple mapping itself, for example given an `OrderSummary` it fills its own labels, while the presenter handles anything with rules. The protocol is smaller, but the view now holds a little logic that tests can't reach.

A useful line: if getting it wrong would be a bug a product manager could file ("cancel shows for delivered orders"), it belongs in the presenter. If getting it wrong is a layout nit, the view can own it.

## Many commands, or one render

The protocol above sends many small commands. The alternative is one method that sends everything at once:

```swift
struct OrderStatusViewData: Equatable {
    let title: String
    let detail: String
    let progress: Double
    let isCancelHidden: Bool
}

protocol OrderStatusView: AnyObject {
    func render(_ data: OrderStatusViewData)
    func showError(_ message: String)
}
```

Small commands make each change explicit and cheap, but they're order-sensitive: forget one call on one path and the screen shows a stale label next to a fresh one. A single `render` is **idempotent**: call it twice with the same value and nothing changes, and every path produces a complete screen. Tests compare one value instead of a call log. Many MVP teams drift towards `render(_:)`, and once the presenter only ever hands over a value describing the whole screen, it's one step from MVVM: let the view *observe* that value instead of being handed it. That's the next lesson.

## Testing with a spy

Because the view is a protocol, a test can implement it with a **spy**: an object that records each call.

```swift check ios group=mvp title="OrderStatusPresenterTests.swift"
import Testing

@MainActor
final class OrderStatusViewSpy: OrderStatusView {
    enum Call: Equatable {
        case status(String, String), progress(Int, Int), cancelHidden(Bool), error(String)
    }
    private(set) var calls: [Call] = []

    func showStatus(title: String, detail: String) { calls.append(.status(title, detail)) }
    func showProgress(step: Int, of steps: Int) { calls.append(.progress(step, steps)) }
    func setCancelHidden(_ hidden: Bool) { calls.append(.cancelHidden(hidden)) }
    func showError(_ message: String) { calls.append(.error(message)) }
}

struct StubOrderService: OrderService {
    let status: Order.Status
    func order(id: String) async throws -> Order { Order(id: id, status: status) }
    func cancel(orderID: String) async throws {}
}

@Test @MainActor func aPackingOrderCanNoLongerBeCancelled() async {
    let presenter = OrderStatusPresenter(orderID: "42", service: StubOrderService(status: .packing))
    let spy = OrderStatusViewSpy()
    presenter.view = spy

    await presenter.viewDidLoad()

    #expect(spy.calls == [
        .status("Packing your order", "Your shopper is picking your items."),
        .progress(2, 4),
        .cancelHidden(true),
    ])
}
```

The test runs in milliseconds with no window, no simulator UI and no network. Notice what it pins down, though: the **order** of the calls. Swap `showProgress` and `showStatus` in the presenter, a change no user would notice, and this test fails. That brittleness is the main cost of testing MVP. Keep it in check by asserting on the calls an interaction *adds* (clear the log after loading), and by asserting on the last call of each kind when order genuinely doesn't matter.

## MVP on other platforms

Android leaned on MVP heavily before Jetpack, with a "contract" interface pairing each view with its presenter. Its biggest pain there was lifecycle: Android destroys and recreates activities on rotation, so presenters had to detach from a dying view and reattach to a new one without losing work. Google's answer was a lifecycle-aware `ViewModel` that outlives the view, plus observable state, which is a large part of why Android moved to MVVM. iOS doesn't recreate view controllers on rotation, so MVP's worst problem there is milder here, and the pattern remains a reasonable choice for UIKit screens.

## Trade-offs

| | Apple MVC | MVP, passive view | MVP, supervising controller | MVVM |
| --- | --- | --- | --- | --- |
| Where screen logic lives | the view controller | the presenter | mostly the presenter | the view model |
| Testable without UIKit | barely | all of it | the presenter's part | all of it |
| Who knows whom | VC knows everything | presenter → view protocol | presenter → view protocol | view → view model only |
| Boilerplate | least | a protocol method per change | a smaller protocol | a state type and a binding |
| Fits SwiftUI | n/a | poorly: views are values | poorly | naturally |
| Wins for | simple screens | UIKit screens with real rules | UIKit screens where the view's mapping is trivial | most screens, especially SwiftUI |

<Callout kind="interview">

**What to say:** "In MVP the presenter holds the screen's state and logic and drives the view through a protocol, weakly referenced; the view controller just forwards events. In MVVM the arrow flips: the view model exposes state and doesn't know the view exists, and the view observes it. MVP is easy to retrofit into UIKit because it needs no binding; MVVM fits SwiftUI because binding is built in."

**What to ask:** "Is this screen UIKit or SwiftUI? Do we have a binding mechanism already?" The answers usually settle it.

**Red flags:** a presenter that imports UIKit to build alerts or push view controllers; a strong reference to the view; tests that assert on twenty ordered calls; calling MVP and MVVM "the same thing with different names".

</Callout>

<Callout kind="gotcha" title="Swift gotcha: a weak reference needs a class-only protocol">

`weak var view: (any OrderStatusView)?` only compiles if the protocol is constrained to `AnyObject`, because `weak` needs a reference type. Leave the constraint off and the tempting "fix" is a strong reference, which makes the retain cycle. Mark the protocol `@MainActor` too, so the presenter (also main-actor) calls it without `await`.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: don't call the view before it has loaded">

A presenter that starts work in its `init`, or is told to load before `viewDidLoad`, can call `showStatus` while the view controller's views don't exist yet. With storyboard outlets declared as `UILabel!`, that's a crash. Start the presenter from `viewDidLoad`, and set `presenter.view = self` first.

</Callout>
