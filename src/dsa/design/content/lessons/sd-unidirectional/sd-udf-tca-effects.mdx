## Why it matters

A feature is only as testable as its least controlled dependency. A reducer that returns effects is pure, but the effect itself calls the network, sleeps on a clock, makes a UUID or reads the date, and if those are the real ones, your tests are slow and flaky and your previews hit production. TCA answers with two things that work together: an `Effect` type with cancellation built in, and a dependency system that makes every outside call a swappable value with a test version that fails loudly when you forget to override it. This is the part of TCA that pays for the rest, and the part interviewers probe when they ask how you test a debounced search or a timer.

## Effects in TCA

Every reducer case returns an `Effect<Action>`. The ones you'll use:

| Effect | Use it for |
| --- | --- |
| `.none` | Nothing to do: most cases |
| `.run { send in … }` | Async work. `send` delivers actions back to the store; optional `catch: { error, send in … }` handles errors |
| `.send(action)` | An action straight away, typically a delegate action to a parent |
| `.merge(a, b)` | Several effects at once |
| `.cancellable(id:cancelInFlight:)` | Mark an effect so it can be cancelled by id; `cancelInFlight: true` cancels the previous one first |
| `.cancel(id:)` | Cancel whatever is running under an id |

Version 1.25 deprecated a few older pieces in preparation for 2.0: the scheduler-based `Effect.debounce`, `Effect.throttle` and `Effect.animation` (sleep on a clock, or pass an animation to `send`, inside `.run` instead) and, behind an opt-in package trait, `.concatenate` and `.map` (sequence work with `await` inside one `.run` instead). Code written in the style below is current.

Here's a book search: debounced, cancellable and failure-aware.

```swift
@Reducer
struct BookSearch {
    @ObservableState
    struct State: Equatable {
        var query = ""
        var results: [Book] = []
        var isSearching = false
        var errorMessage: String?
    }

    enum Action {
        case queryChanged(String)
        case searchResponse(Result<[Book], any Error>)
        case clearButtonTapped
    }

    enum CancelID { case search }

    @Dependency(\.bookClient) var bookClient
    @Dependency(\.continuousClock) var clock

    var body: some ReducerOf<Self> {
        Reduce { state, action in
            switch action {
            case let .queryChanged(query):
                state.query = query
                state.errorMessage = nil
                guard query.count >= 2 else {
                    state.results = []
                    state.isSearching = false
                    return .cancel(id: CancelID.search)
                }
                state.isSearching = true
                return .run { send in
                    try await clock.sleep(for: .milliseconds(300))
                    let books = try await bookClient.search(query)
                    await send(.searchResponse(.success(books)))
                } catch: { error, send in
                    await send(.searchResponse(.failure(error)))
                }
                .cancellable(id: CancelID.search, cancelInFlight: true)

            case let .searchResponse(.success(books)):
                state.isSearching = false
                state.results = books
                return .none

            case .searchResponse(.failure):
                state.isSearching = false
                state.errorMessage = "Couldn't search. Check your connection."
                return .none

            case .clearButtonTapped:
                state = State()
                return .cancel(id: CancelID.search)
            }
        }
    }
}
```

What each detail buys:

- **The debounce is a sleep.** Each keystroke returns a new effect with the same id and `cancelInFlight: true`, which cancels the previous one while it's still sleeping. Only a query that stays unchanged for 300 ms reaches the network.
- **Short queries cancel.** Deleting back to one character cancels a pending search, so results for "du" can't appear under a query of "d".
- **The query is captured by value.** The effect searches for exactly what the reducer saw, whatever the state becomes meanwhile.
- **Cancellation is quiet.** When a cancelled `clock.sleep` throws `CancellationError`, TCA doesn't call the `catch` handler, and `send` from a cancelled effect does nothing. A stale search can't report an error, either.
- **Both outside calls are dependencies.** `clock` and `bookClient` are declared with `@Dependency`, so a test can replace them. That's the second half of this lesson.

## Effect lifetimes

An effect lives until it finishes or is cancelled. Three tools decide when that is:

- **Ids**, as above, for work that a later action supersedes or stops.
- **Presentation.** When a child feature presented with `ifLet` (a sheet, a pushed screen) is dismissed, TCA cancels every effect the child started. You'll see this in navigation; it's why a child's timer can't outlive its sheet.
- **The view's lifetime**, for work that should run exactly while a screen is visible, such as observing a stream:

```swift
// In the reducer
case .task:
    return .run { send in
        for await count in bookClient.finishedCountUpdates() {
            await send(.finishedCountChanged(count))
        }
    }

// In the view
.task { await store.send(.task).finish() }
```

`store.send` returns a `StoreTask` for the effects the action started, and `finish()` waits for them. Awaiting it inside SwiftUI's `.task` ties the effect to the view: when the view disappears, SwiftUI cancels its task, and TCA cancels the effect. This is the `.task(id:)` subscription idea from [The Elm architecture](/design/learn/sd-udf-elm), routed through the reducer so the stream's values are actions you can test.

## Dependencies

Look at what effects typically touch: `URLSession`, `Date()`, `UUID()`, `ContinuousClock`, `UserDefaults`, notification permissions, analytics. Call any of them directly and three things go wrong. Tests depend on the network and on real time. Assertions about ids and timestamps can't be written. Previews make real requests. [Dependencies as closures and structs](/design/learn/sd-functional-environment) showed the fix as a struct of closures passed in by hand; TCA uses Point-Free's **swift-dependencies** library to do the passing for you ([Dependencies as values, swift-dependencies style](/design/learn/sd-di-dependency-values) covers the library on its own).

### Using a dependency

A reducer declares what it needs with `@Dependency` and a key path. Common ones are built in: `\.continuousClock`, `\.uuid`, `\.date`, `\.openURL`, `\.dismiss`, `\.calendar`, `\.locale`. In the app they're the real thing; in tests and previews you replace them.

### Writing your own

A dependency is usually a struct of `@Sendable` closures, with a live, a test and a preview value:

```swift
@DependencyClient
struct BookClient {
    var search: @Sendable (_ query: String) async throws -> [Book]
    var finishedCountUpdates: @Sendable () -> AsyncStream<Int> = { .finished }
}

extension BookClient: DependencyKey {
    static let liveValue = BookClient(
        search: { query in
            var components = URLComponents(string: "https://api.example.com/search")!
            components.queryItems = [URLQueryItem(name: "q", value: query)]
            let (data, _) = try await URLSession.shared.data(from: components.url!)
            return try JSONDecoder().decode([Book].self, from: data)
        },
        finishedCountUpdates: { /* observe the local database */ .finished }
    )

    static let testValue = BookClient()

    static let previewValue = BookClient(
        search: { _ in [.dune, .emma] },
        finishedCountUpdates: { AsyncStream { $0.yield(3) } }
    )
}

extension DependencyValues {
    var bookClient: BookClient {
        get { self[BookClient.self] }
        set { self[BookClient.self] = newValue }
    }
}
```

`@DependencyClient` generates an initialiser in which every endpoint you don't pass is **unimplemented**: calling it fails the current test with a message naming the endpoint (and an endpoint that returns a value gets a default, like `{ .finished }` here, so it has something to return). That's why `testValue` is simply `BookClient()`. A test must override exactly what the feature is supposed to use, and if a refactor makes the feature call something new, the test fails and tells you.

### Overriding

Tests override dependencies when they create the store, and previews do the same:

```swift
let store = TestStore(initialState: BookSearch.State()) {
    BookSearch()
} withDependencies: {
    $0.continuousClock = ImmediateClock()
    $0.bookClient.search = { _ in [.dune] }
}
```

`ImmediateClock` makes every sleep return at once; `TestClock` from swift-clocks lets the test advance time step by step. You'll use both in [TCA: exhaustive tests with TestStore](/design/learn/sd-udf-tca-testing). A parent can also override a dependency for one child with the `.dependency(\.bookClient, .mock)` reducer operator, for a demo mode, say.

### How it works, briefly

Dependencies are resolved from a task-local context. The store sets up that context when it runs a reducer, and effects inherit it, so everything a reducer and its effects touch sees the same overrides. Anything outside that context, such as a helper object created in a view or a singleton made at launch, reads the default instead. That's the price of not passing dependencies by hand.

## Trade-offs

| | Singletons called directly | Protocols injected through initialisers | Structs of closures, passed by hand | `@Dependency` (swift-dependencies) |
| --- | --- | --- | --- | --- |
| Visible in the type's API | No | Yes | Yes | No: declared inside the reducer |
| Wiring | None | Every layer passes them down | Every layer passes them down | None: resolved from context |
| Overriding in a test | Hard, global | A mock class per protocol | A closure per endpoint | A closure per endpoint, in `withDependencies` |
| A forgotten override | Hits the real thing | Doesn't compile | Doesn't compile | Fails the test as unimplemented |
| Previews | Hit the real thing | A preview implementation | A preview value | `previewValue`, or the live one if you didn't write it |
| Wins when | Never, for effects | Small apps; teams that prefer explicit wiring | Small apps without a library | TCA apps, and apps with many dependencies and deep trees |

<Callout kind="interview">

**Say** "Effects are returned, never run in the reducer. A search effect sleeps 300 ms on an injected clock and is cancellable with cancel-in-flight, so typing cancels it and only the last query hits the API. Every outside call (API, clock, UUID, date) is a dependency with a live value, a preview value and an unimplemented test value, so a test must override what the feature uses." **Ask** which effects must outlive the screen, since presentation cancels a child's effects. **Red flags:** `Task.sleep` or `Date()` called directly in an effect, `Effect.debounce` in new code, and long-running effects started with no id and no view lifetime.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: a .task effect that never finishes">

Write `.task { store.send(.task) }` without `await … .finish()` and the closure returns immediately: SwiftUI has nothing to cancel when the view disappears, so the observation keeps running and sending actions to a feature nobody is looking at. Always await `finish()` for effects meant to live as long as the view.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: previews quietly use the live value">

A dependency with no `previewValue` falls back to its `liveValue` in Xcode previews, so a preview of the search screen makes real network calls (and fails offline). Give every client that touches the network, the disk or system permissions a `previewValue`, or override it in the preview's store with `withDependencies`.

</Callout>
