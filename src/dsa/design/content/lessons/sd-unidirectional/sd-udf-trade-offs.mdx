## Why it matters

Every lesson in this module has argued for unidirectional flow: one owner, one door in, effects as values, exhaustive tests. This one is about the bill. Routing every change through a reducer costs main-thread time, and at 120 changes a second that can cost frames. Actions, delegates and dependency clients cost typing, reading and onboarding. A large third-party architecture costs migrations when it changes. None of that means "don't", but a senior answer to "should we adopt TCA?" or "why is this screen janky?" names the costs, measures them, and says where the pattern stops paying. That's what interviewers listen for.

## What one action costs

In a TCA-style tree, every action enters at the root store and runs the root's `body`. Each `Scope` checks whether the action is its child's, which is a cheap enum match, and the matching path runs down to the leaf feature, plus any parent logic along the way. Then observation notifies the views that read fields that changed, and SwiftUI re-evaluates their bodies. Effects add a `Task` and an actor hop or two.

For a tap, all of that takes microseconds and never matters. It matters when actions arrive **many times a second**: a scroll offset, a drag gesture, download progress, a playback position, a 60 Hz timer, motion sensor readings. On a ProMotion display a frame lasts 8.3 ms, and everything the main actor does in that frame competes with rendering. Try the numbers: the defaults are a drag gesture sent to the store on every frame.


With the defaults, each action costs about 2.5 ms and nearly a third of every frame goes on one gesture, most of it re-evaluating 40 views. Drop the views to 2, as narrow observation does, and it falls to about 2.5%. Push the rate to 240 or the body time up and the screen can't keep up at all. The reducers themselves are rarely the problem; what each action makes SwiftUI redo usually is.

## Keeping the hot path fast

### Keep high-frequency state out of the store

Not every change needs to be an action. A drag's live offset belongs in the view's `@GestureState` or `@State`; the store hears about it once, when the drag ends and something meaningful happened (`cardDropped(on: column)`). A scroll position that no logic reads stays in the view. The test from [TCA: state, actions and reducers](/design/learn/sd-udf-tca-reducers) applies: if no test of the feature would assert on every intermediate value, the store doesn't need every intermediate value.

### Throttle at the source

When the store does need a stream of values, such as download progress for a progress bar, send fewer of them. The effect that observes the download can send an update only when the percentage changes by a whole point, or at most ten times a second using the injected clock. A progress bar that moves ten times a second looks smooth; the other fifty updates were pure cost.

### Narrow what each view observes

`@ObservableState` tracks fields, so a view re-renders only when a field it read changes. That only helps if views read narrowly:

- **Give rows their own scoped stores** (`ForEach(store.scope(state: \.rows, action: \.rows))`) rather than passing arrays down, so changing one row re-renders one row.
- **Watch computed properties on big state.** `finishedCount` reads every row; a view that shows it re-evaluates whenever any row changes, and recomputes an O(n) count each time. For large collections, keep the derived value somewhere it's computed once per change, or show it in fewer places.
- **Legacy TCA code** (before 1.7) used `WithViewStore` and `ViewStore`, which compared whole observed states with `==` after every action. Moving those screens to `@ObservableState` is a performance fix as much as an API update.

### Keep heavy work out of reducers

Reducers run on the main actor, inside `send`. Sorting ten thousand books, parsing a large file, diffing two big collections or resizing an image in a reducer blocks the UI for as long as it takes. Do it in an effect, off the main actor, and send the result back as an action.

### Measure before you change anything

Guessing about performance is usually wrong. Instruments' SwiftUI template shows how often each view's body runs and how long it takes; the Time Profiler shows which reducer or computed property is hot. In debug builds, TCA's `._printChanges()` shows every action with its state diff, which quickly reveals an action firing far more often than you thought. For production numbers, wrap `send` in signposts ([Signposts: measuring intervals with OSSignposter](/design/learn/sd-diag-signposts)) and look at the intervals in a field trace.

## Compile times and the build

Performance isn't only runtime. A feature with a 60-case action enum, a `body` with a dozen composed reducers and a long `switch` gives the type checker a lot to solve, and TCA's macros bring in swift-syntax, which adds to clean builds. TCA's documentation has advice for when the compiler struggles: break a long `Reduce` closure out into a method, split a large `body` into smaller reducers, and add explicit types where inference has to search. Modularising features into separate targets, as in [TCA: composing and scoping features](/design/learn/sd-udf-tca-scoping), helps the most: a change to one feature rebuilds one module, and previews build only what they need.

## Ergonomic costs

The costs people feel day to day aren't milliseconds:

- **Indirection.** "Jump to definition" on `store.send(.saveButtonTapped)` lands on the enum case, not the code that runs. Finding what a tap does means finding the case in the reducer, then following delegate actions up through parents. Clear naming and small features keep that short; deep trees with delegates three levels up make it long.
- **Ceremony.** An action for every change, a delegate enum per child, a client struct per dependency, a test for every effect. Some of that is the point (it's where the testability comes from), and some is tax. `BindableAction`, helper methods and good templates reduce it; they don't remove it.
- **Learning curve.** Case paths, scoping, `@Presents`, effect lifetimes and exhaustive testing take a newcomer weeks to be fluent in, not days. Point-Free's documentation and tutorials are free; much of the deeper explanation lives in their paid video series. Factor that into hiring and onboarding.
- **A big dependency, and its versions.** TCA's 0.x releases, the reducer protocol, the move to Observation in 1.7 and now the 2.0 beta have each asked large codebases for real migration work. Point-Free makes these gradual (1.25's opt-in deprecation traits exist so teams can prepare for 2.0 at their own pace), but an app built entirely on one library inherits its roadmap.
- **Interop.** TCA works with UIKit and with features written in other styles, and you can adopt it one feature at a time inside an MVVM app. The seams between the two styles still need care: who owns shared state, how a TCA feature reports to a coordinator, how dependencies reach both.

The other side of the ledger is real, too: one way to build every feature, state changes you can read in a log, dependencies that are explicit and swappable, navigation that's testable state, and tests that catch the change you didn't mean to make.

## Trade-offs

| Situation | Lean towards | Why |
| --- | --- | --- |
| A small app, one to three developers | `@Observable` view models, with a reducer inside the one or two complex ones | The ceremony would cost more than the bugs it prevents |
| A mostly MVVM app with one intricate feature (an editor, a checkout, a live session) | A homemade reducer store, or TCA, for that feature only | Contain the complexity where it lives |
| A large SwiftUI app with several teams that want one consistent style | TCA, with features in modules | Consistency, composition and exhaustive tests across teams |
| An app built alongside an Android team that uses MVI | MVI-style view models with one view state | Shared shapes and vocabulary in design reviews |
| An existing ReSwift or ReactorKit app | Keep it consistent, migrate feature by feature if at all | A rewrite costs more than the pattern's flaws |
| Real-time UI: drawing, games, audio scrubbing, live video effects | Plain mutable state on the hot path, unidirectional flow around it | 120 Hz updates shouldn't go through a reducer tree |

<Callout kind="interview">

**Say** "Unidirectional flow costs a little per action and a lot per high-frequency action: every action runs from the root and can invalidate many views. I keep gesture and scroll state local, throttle streams at the source, scope stores so views observe narrowly, and move heavy work into effects, then measure with Instruments. The bigger costs are ergonomic: indirection, boilerplate, onboarding and depending on one library's roadmap." Then give a recommendation tied to the team and app, as in the table above. **Ask** how many developers will work in it and how often features interact, since those decide whether the ceremony pays. **Red flags:** "TCA is slow" with no measurement, scroll offsets in a global store, and adopting an architecture because it's fashionable rather than because of a problem it solves.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: a scroll offset in the store">

`onScrollGeometryChange` or a `GeometryReader` that sends the offset to the store on every frame turns scrolling into 120 actions a second, each re-evaluating whatever reads that field. Keep the offset in the view, and send an action only when a threshold is crossed: "header collapsed", "near the end of the list".

</Callout>

<Callout kind="gotcha" title="Swift gotcha: derived values that walk the whole state">

A computed property such as `rows.filter(\.isFinished).count`, read by a header and by every row's badge, recomputes over all rows for each view that reads it, every time any row changes. With 20 rows, nobody notices; with 2,000 rows and a progress action every second, it shows up in the Time Profiler. Read it in one place, or maintain the count in the reducer when profiling says you must.

</Callout>
