## Why it matters

Two screens show the same thing, a recipe's favourite heart in a list and on its detail page, and after a while they disagree. Somebody updated one copy and forgot the other, or a delegate and a notification fought over who changes what. **Unidirectional data flow** prevents that whole class of bug with a few rules about which way data may travel. It's the idea underneath SwiftUI itself, and behind Redux, the Elm architecture, MVI and TCA, which D28 compares in depth. Knowing the core ideas lets you apply them in a plain SwiftUI app, and explain in an interview why they work.

## Four rules

1. **One source of truth.** Each piece of state has exactly one owner: a store, a view model, an `@State`. Everything else reads it.
2. **State flows down.** Views receive state and render it. They don't keep their own copies.
3. **Actions flow up.** Views report *what happened* ("the heart was tapped"), not *what to change* ("set `isFavourite` to true").
4. **State changes in one place.** The owner applies each action, usually with a [reducer](/design/learn/sd-functional-reducers), and runs side effects at the edge. Their results come back as more actions.

Put together they form a loop: state renders a view, the user does something, an action changes the state, and the new state renders again. Apple's own framing of SwiftUI, from its 2019 talk *Data Flow Through SwiftUI*, is that a view is a function of state. UDF takes that seriously all the way down.

<Callout kind="analogy">

A shared spreadsheet works the same way. Nobody edits their own printout and posts it round the office: everyone looks at the one sheet, edits go to the sheet, and every screen showing it updates. Two printouts disagreeing is the bug UDF removes.

</Callout>

## What two-way flow gets wrong

Before SwiftUI, a common UIKit setup for the favourites heart looked like this: the list cell kept an `isFavourite` flag and posted a notification when tapped; the detail view controller kept its own flag and told the list through a delegate; the network callback updated whichever controller started the request. Every arrow pointed both ways. The result was familiar:

- **Copies drift.** One path forgets to update one copy, and the screens disagree.
- **Updates loop.** A change notifies a listener, whose change notifies the first one back.
- **Nobody can say why.** A bug report says the heart flickered; there are five places that could have done it.

With one-way flow, both screens read `favourites` from one owner and both send `favouriteTapped(id)`. There's one place a heart can change, and it's a pure function you can test.

## The loop, with an optimistic update

Favouriting should feel instant, so the app fills the heart straight away and tells the server in the background. If the server refuses, the heart must empty again and the user should hear why. Here's that whole behaviour as state, actions, effects and a reducer:

```swift run title="Favourites: one state, two screens, an optimistic update and a rollback"
struct RecipesState: Equatable {
    var favourites: Set<Int> = []
    var pending: Set<Int> = []
    var toast: String?
}

enum RecipesAction {
    case favouriteTapped(Int)
    case saveFinished(Int, succeeded: Bool)
}

enum RecipesEffect: Equatable {
    case save(recipe: Int, isFavourite: Bool)
}

func reduce(_ state: inout RecipesState, _ action: RecipesAction) -> [RecipesEffect] {
    switch action {
    case .favouriteTapped(let id):
        guard !state.pending.contains(id) else { return [] }   // one request per recipe at a time
        let isFavourite = !state.favourites.contains(id)
        if isFavourite { state.favourites.insert(id) } else { state.favourites.remove(id) }
        state.pending.insert(id)
        state.toast = nil
        return [.save(recipe: id, isFavourite: isFavourite)]
    case .saveFinished(let id, succeeded: true):
        state.pending.remove(id)
        return []
    case .saveFinished(let id, succeeded: false):
        state.pending.remove(id)
        // Roll back the optimistic change
        if state.favourites.contains(id) { state.favourites.remove(id) } else { state.favourites.insert(id) }
        state.toast = "Couldn't update favourites. Check your connection."
        return []
    }
}

// Two screens, one state: the list row and the detail page both draw from `favourites`
func heart(_ state: RecipesState, _ id: Int) -> String { state.favourites.contains(id) ? "♥" : "♡" }

let actions: [RecipesAction] = [
    .favouriteTapped(42),
    .favouriteTapped(42),
    .saveFinished(42, succeeded: false),
    .favouriteTapped(42),
    .saveFinished(42, succeeded: true),
]

var state = RecipesState()
for action in actions {
    let effects = reduce(&state, action)
    var line = "\(action) → list \(heart(state, 42)), detail \(heart(state, 42))"
    if state.toast != nil { line += ", toast shown" }
    if let effect = effects.first { line += ", effect: \(effect)" }
    print(line)
}
```

```output
favouriteTapped(42) → list ♥, detail ♥, effect: save(recipe: 42, isFavourite: true)
favouriteTapped(42) → list ♥, detail ♥
saveFinished(42, succeeded: false) → list ♡, detail ♡, toast shown
favouriteTapped(42) → list ♥, detail ♥, effect: save(recipe: 42, isFavourite: true)
saveFinished(42, succeeded: true) → list ♥, detail ♥
```

The list and detail can't disagree, because neither has anything of its own to disagree with. The second tap, made while the first request was still out, is refused rather than racing it. And the rollback is three lines in the one place that knows what the optimistic change was. Here's the same journey across the app's parts:

## SwiftUI is already halfway there

You don't need a framework to work this way. A SwiftUI view reading an `@Observable` view model already has state flowing down; calling the model's methods is actions flowing up, though not written as values. The one place SwiftUI is deliberately two-way is `@Binding`: a child view can write straight into its parent's state. That's the right tool for local, simple state such as a toggle in a form. When the owner needs to apply rules to every change, derive a binding that sends an action instead:

```swift check ios title="A text field that sends actions instead of writing state"
import SwiftUI

@MainActor
@Observable
final class SearchModel {
    enum Action {
        case queryChanged(String)
        case clearTapped
    }

    private(set) var query = ""

    func send(_ action: Action) {
        switch action {
        case .queryChanged(let text): query = String(text.prefix(100))
        case .clearTapped: query = ""
        }
    }
}

struct SearchField: View {
    let model: SearchModel

    var body: some View {
        HStack {
            TextField("Search recipes", text: Binding(
                get: { model.query },
                set: { model.send(.queryChanged($0)) }
            ))
            Button("Clear") { model.send(.clearTapped) }
        }
    }
}
```

`query` is `private(set)`, so the only way to change it is `send`. The text field still feels like an ordinary binding, but the 100-character limit lives in the model, and so would analytics, validation or a search effect.

### A spectrum, not a switch

How far to go is a choice per feature, and each step buys something:

| Step | What it adds | What it costs |
| --- | --- | --- |
| `@Observable` model, views call its methods | State down, calls up; one owner | Little; methods can still write anything |
| Model with one `send(_ action:)` | Every change is a value you can log; one switch to read | An action enum |
| A pure reducer returning effects | Every rule testable with plain values; replayable bug reports | Effects as values, and a small store to run them |
| A framework such as TCA | Composition, dependency control and exhaustive test tools | Its conventions, and the time to learn them |

## One store, or many?

Redux on the web keeps **one store for the whole app**. That gives a single place to log and replay everything, but every feature depends on one giant state type, and a change anywhere can make every screen re-check whether it changed. Most iOS apps do better with **a store per feature**, plus a few app-wide owners for things that really are shared, such as the signed-in session and settings. Features talk through those shared owners or through their parent, not by reaching into each other's state. D19 weighs global stores in detail.

## Trade-offs

| Approach | Consistency between screens | Debugging | Ceremony | When it wins |
| --- | --- | --- | --- | --- |
| Two-way: each screen keeps a copy, synced by delegates and notifications | Fragile | Hard: many writers | Low at first, high later | Small, isolated screens that share nothing |
| One-way with an `@Observable` owner and methods | Good: one owner | Medium: any method can write | Low | Most SwiftUI features |
| One-way with actions and a reducer | Strong | Easy: log and replay actions | Medium | Features with async results, optimistic updates or rules worth exhaustive tests |
| One app-wide store | Strong | Easy, all in one log | High, and grows with the app | Small apps, or apps built around one framework that expects it |

<Callout kind="interview">

**Say** "State has one owner and flows down; views send actions up describing what happened; the owner changes state in one place and runs effects, whose results come back as actions. So two screens can't disagree, and every change is traceable." **Ask** which state is genuinely shared between features, because that decides what needs an app-level owner. **Red flags:** child views holding copies of parent state "for convenience", effects that write state directly instead of sending an action, and one global store for a large app with no plan for its performance.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: a text field's binding must update synchronously">

If `send(.queryChanged)` hops to a `Task` before changing `query`, the text field renders the old value for a frame, the cursor jumps and fast typing loses characters. Apply the change to state synchronously on the main actor inside `send`, and start any slow work (a search) as an effect afterwards.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: effects shouldn't read state later">

An effect that reads `store.state.favourites` when it runs may see a newer state than the one the reducer decided on, because other actions got in first. Put what the effect needs into its payload when the reducer creates it, as `save(recipe:isFavourite:)` does. The effect then carries out exactly the decision that was made.

</Callout>
