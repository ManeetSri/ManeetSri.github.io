## Why it matters

`URLSession.shared`, `UserDefaults.standard`, `UIApplication.shared`, `FileManager.default`: you use singletons, or things that look like them, in every app. They're also the pattern interviewers ask about most, usually as "what's wrong with singletons?" To answer well you need to know how Swift creates them, what Swift 6 demands of them, and the difference between a real singleton and a **shared default**, which is what most of Apple's are.

## Two promises in one pattern

The Gang of Four: *ensure a class only has one instance, and provide a global point of access to it.* That's two separate promises:

1. **Uniqueness:** there is exactly one instance, and nobody can make another.
2. **Global access:** any code, anywhere, can reach it by name.

Keep them apart in your head. Uniqueness is sometimes exactly right: there is one audio session, one application object, one database file that must be opened once. Global access is what causes the trouble, as you'll see in [Why to avoid singletons, and testable alternatives](/design/learn/sd-creational-singleton-alternatives). Most good designs keep the first promise and drop the second.

## Writing one in Swift

```swift run
final class Analytics: Sendable {
    static let shared = Analytics()
    private init() { print("Analytics created") }

    func track(_ event: String) { print("track \(event)") }
}

print("App launched")
print("First screen shown")
Analytics.shared.track("tap")
Analytics.shared.track("scroll")
```

```output
App launched
First screen shown
Analytics created
track tap
track scroll
```

Three parts, each doing a job:

- **`static let shared`.** Swift initialises static and global stored properties **lazily, on first access**, and guarantees the initialiser runs **exactly once**, even if several threads arrive at the same moment. On Apple platforms it's built on the same mechanism as `dispatch_once`, which is why Swift never needed the Objective-C `+sharedInstance` boilerplate. The output shows the laziness: `Analytics created` appears at the first use, not at launch.
- **`private init()`** enforces uniqueness: nobody outside the type can call `Analytics()`.
- **`final`** stops a subclass from adding a second, different kind of instance.

Lazy and once-only are good properties, but "once" means the first caller **waits** for the initialiser, and "lazy" means you don't control *when* that is. If the initialiser is slow, the cost lands on whichever thread gets there first:

## Swift 6: a singleton is a global

A `static let` is global state that any thread can reach, so Swift 6's data-race checking applies to it. A singleton whose type isn't `Sendable` doesn't compile, and a mutable `static var` never does unless it's isolated to an actor:

```swift
final class ImageCache {
    static let shared = ImageCache()
    private var images: [String: [UInt8]] = [:]
}

final class Session {
    static var current = Session()
}
```

```text title="What you'll see"
error: static property 'shared' is not concurrency-safe because non-'Sendable' type 'ImageCache' may have shared mutable state
error: static property 'current' is not concurrency-safe because it is nonisolated global shared mutable state
```

The compiler is pointing at a real problem: two threads could mutate `images` at once. You have three honest ways to make a singleton safe, and they differ in who can call it and how:

```swift check
import Foundation
import Synchronization

// 1. Main-actor isolated: for state the UI owns
@MainActor
final class ThemeStore {
    static let shared = ThemeStore()
    private init() {}

    var accentName = "teal"
}

// 2. An actor: every call from outside is async, and the actor serialises access
actor ThumbnailCache {
    static let shared = ThumbnailCache()
    private var thumbnails: [URL: Data] = [:]

    func thumbnail(for url: URL) -> Data? { thumbnails[url] }
    func store(_ data: Data, for url: URL) { thumbnails[url] = data }
}

// 3. A Sendable class guarding its state with a Mutex: synchronous calls from any thread
final class FeatureFlags: Sendable {
    static let shared = FeatureFlags()
    private let flags = Mutex<[String: Bool]>([:])

    func isEnabled(_ name: String) -> Bool {
        flags.withLock { $0[name] ?? false }
    }

    func set(_ name: String, enabled: Bool) {
        flags.withLock { $0[name] = enabled }
    }
}

func useThem() async {
    let flagOn = FeatureFlags.shared.isEnabled("newCheckout")
    let cached = await ThumbnailCache.shared.thumbnail(for: URL(string: "https://img.example.com/1.jpg")!)
    let accent = await ThemeStore.shared.accentName
    print(flagOn, cached == nil, accent)
}
```

`Mutex` comes from the Synchronization module (iOS 18, macOS 15). There's also a dishonest way: `nonisolated(unsafe) static var shared` or `@unchecked Sendable` tell the compiler to stop checking, and promise that you synchronise access yourself. They exist for code the compiler can't reason about, such as state already protected by a lock it can't see. As a way to make an error go away, they're the singleton bug of the 2010s with the warning switched off, and reviewers rightly flag them. [Sendable and isolation as design constraints](/design/learn/sd-swift-design-sendable) covers the options in depth.

## Apple's shared instances

Look closely at Apple's "singletons" and most aren't singletons at all. They're **shared defaults**: a convenient instance of a type you're free to create yourself.

| Shared instance | Really only one? | Can you make your own? | Worth knowing |
| --- | --- | --- | --- |
| `UIApplication.shared` | Yes: one per process | No: UIKit creates it at launch | Unavailable in app extensions |
| `UIDevice.current` | Yes | No | Models the physical device |
| `AVAudioSession.sharedInstance()` | Yes: the app's audio session | No | Configure it once, deliberately |
| `UNUserNotificationCenter.current()` | Yes, for the app | No | |
| `URLSession.shared` | No | `URLSession(configuration:delegate:delegateQueue:)` | No delegate, no background transfers, no custom configuration |
| `FileManager.default` | No | `FileManager()` | Make your own if you need a delegate |
| `NotificationCenter.default` | No | `NotificationCenter()` | Your own keeps tests and module events private |
| `UserDefaults.standard` | No | `UserDefaults(suiteName:)` | App Groups need a suite |

The second half of the table is the healthier design, and Apple uses it for a reason: the **type** isn't restricted to one instance; the **app** happens to share one. Tests can make a fresh `NotificationCenter()`, a widget can use `UserDefaults(suiteName: "group.com.example.app")`, and an upload feature can have its own `URLSession` with a delegate. Apple's own documentation for `URLSession.shared` lists its limits: you can't get data incrementally, customise connection behaviour much, do much authentication, or transfer in the background. A singleton that serves one common case, with a real initialiser for everything else, is a good API. A type you can **only** get as `.shared` locks every caller into the common case.

Apple has also retired a singleton the platform outgrew. `UIScreen.main` made sense when an iPhone had one screen. With iPad multitasking, external displays and multiple scenes there is no single "the screen", so Apple long recommended finding the screen through context (`view.window?.windowScene?.screen`) or the trait collection, and formally deprecated `UIScreen.main` in iOS 26. A global "the X" is a bet that there will only ever be one X.

Notice too what Apple did **not** make a singleton: `Logger` from the `os` framework is a struct you create per subsystem and category, `Logger(subsystem: "com.example.app", category: "sync")`. It's cheap to create, carries its own context, and there's no global logger to configure.

## When a singleton is the right answer

A true singleton, one instance enforced by the type, fits when:

- it **models something there really is one of** in the process: the application, the device, the audio session, the hardware haptics engine, a database file that must be opened once;
- **two instances would be a bug**, not just a waste, for example two Core Data stacks opening the same store file;
- its state is either **global by nature** or **immutable after launch**.

Even then, you can keep uniqueness without global access: create the one instance at start-up and **pass it in**. That's the next lesson.

## Trade-offs

| | `@MainActor` class | `actor` | `Sendable` class + `Mutex` | `nonisolated(unsafe)` | One instance created at start-up and passed in |
| --- | --- | --- | --- | --- | --- |
| Data-race safety | Checked | Checked | Checked | Your promise only | Whatever the type provides |
| Calls from background code | `await` | `await` | Synchronous | Synchronous | Synchronous or `await` |
| Good for | UI state: theme, navigation, haptics | Caches and stores with async work | Small, fast, synchronous state like flags | Bridging code the compiler can't see into | Almost everything else |
| Testable | Poorly: one global instance | Poorly | Poorly | Poorly | Well: tests pass their own |

<Callout kind="interview">

**What to say:** "There are two promises: one instance, and global access. I keep the first when the thing really is unique, but I create it at the composition root and inject it, so code says what it depends on and tests can substitute it." Then mention Swift 6: a shared instance must be `Sendable` or actor-isolated.

**What to ask:** "Would two instances be a bug, or just wasteful? Does anything need a different configuration, such as a background URL session?"

**Red flags:** "singletons are always bad" with no nuance; `nonisolated(unsafe) static var shared` with no locking; a singleton with a public `init` (it's just a global variable); heavy work in a singleton's initialiser.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: every extension gets its own singletons">

A widget, a share extension or a notification service extension runs in **its own process**. `MyCache.shared` in the widget is a different object from `MyCache.shared` in the app, created separately and starting empty. Share data through an App Group container or `UserDefaults(suiteName:)`, never through a singleton. And `UIApplication.shared` is marked unavailable in extensions, so a shared framework that calls it won't build for one.

</Callout>

The **singletons and hidden construction** review asks you to find what's wrong with a profile screen built on `nonisolated(unsafe)` singletons, and the **testable review prompter** kata replaces a `.shared` prompter with one you can test.

```cards

  front: "What two promises does the singleton pattern make, and which one causes most of the trouble?"
  back: "Exactly one instance, and global access to it. Global access causes most of the trouble: hidden dependencies and shared mutable state."
- id: static-let-semantics
  front: "When is a `static let` initialised, and how many times?"
  back: "Lazily, on first access, and exactly once, even when several threads arrive together. Callers that arrive during initialisation wait for it."
- id: swift6-singleton
  front: "What are the honest ways to make a singleton compile in Swift 6?"
  back: "Isolate it to the main actor, make it an actor, or make it a `Sendable` class whose mutable state sits behind a `Mutex`. `nonisolated(unsafe)` only switches the checking off."
- id: shared-default
  front: "How do most of Apple's 'singletons' differ from the textbook pattern?"
  back: "They're shared defaults: `URLSession`, `FileManager`, `NotificationCenter` and `UserDefaults` can all be created yourself. The app shares one instance; the type isn't restricted to one."
```
