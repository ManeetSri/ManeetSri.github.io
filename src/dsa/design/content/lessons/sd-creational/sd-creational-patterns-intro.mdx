## Why it matters

Every app creates objects all day: view controllers, API clients, formatters, cells, view models. Where and how that creation happens decides what you can test, swap and reuse later. Design patterns give those decisions names, so in a code review or an interview you can say "a factory picks the cell type" and be understood in five words.

This module covers the **creational** patterns: the ones about making objects. They're the first family because every other design decision starts with "who builds this, and with what?"

## What a design pattern is

A design pattern is a **named solution to a problem that keeps coming up in a particular context**, together with what it costs. The classic description has four parts:

1. **Name:** a word or two the team can use ("builder", "singleton").
2. **Problem:** the situation and the forces in it ("this object has twelve optional settings").
3. **Solution:** the shape of the answer: which roles exist and how they relate. Not finished code.
4. **Consequences:** what you gain and what you pay.

The idea comes from architecture. Christopher Alexander's *A Pattern Language* (1977) catalogued recurring solutions in buildings and towns. In 1994 Gamma, Helm, Johnson and Vlissides published *Design Patterns: Elements of Reusable Object-Oriented Software*, usually called the **Gang of Four** (GoF) book. It describes 23 patterns in three families:

| Family | Concern | GoF patterns | This course |
| --- | --- | --- | --- |
| Creational | Making objects | 5 | D10 (this module) |
| Structural | Composing types into larger structures | 7 | D11 |
| Behavioural | How objects talk and share work | 11 | D12 and D13 |

<Callout kind="analogy">

A pattern is like a cooking technique rather than a recipe. "Braise it" doesn't tell you what's for dinner, but it tells another cook a great deal: low heat, a lid, liquid, time. Two braised dishes can share no ingredients and still be the same technique. Two builders in Swift can share no code and still be the same pattern.

</Callout>

### A pattern is a shape, not a library

You never "add the factory pattern" to a project the way you add a package. You recognise a problem, then shape your own types so they play the pattern's roles. That's why the same pattern looks different in Java, Kotlin and Swift: each language gives you different tools to build the shape with.

### Swift absorbs some patterns

In 1996 Peter Norvig showed that 16 of the 23 GoF patterns become simpler or disappear in a language with first-class functions and dynamic types. A pattern often marks a feature the language lacks. Swift has many of those features, so several creational patterns shrink:

| Pattern | The problem it solved in 1994 | What Swift gives you |
| --- | --- | --- |
| Prototype | Copying a configured object without knowing its class | Value types copy on assignment |
| Factory method with one product | Letting someone else decide what to create | A closure, `() -> Product` |
| Singleton's safe one-time creation | Thread-safe lazy initialisation | `static let`, initialised once on first use |
| Builder for optional parameters | Constructors with ten arguments | Default arguments and memberwise initialisers |

The **forces** are still there: you still need to swap types, assemble complex objects and control lifetimes. The code to do it gets shorter. Throughout this module, you'll see the textbook shape first, then the Swift that usually replaces it.

## The creational problem

Here's a view model that creates its own API client:

```swift check
import Foundation

struct Profile: Codable, Sendable {
    let name: String
}

struct URLSessionProfileAPI: Sendable {
    let session: URLSession
    let baseURL: URL

    func profile() async throws -> Profile {
        let (data, _) = try await session.data(from: baseURL.appending(path: "me"))
        return try JSONDecoder().decode(Profile.self, from: data)
    }
}

@MainActor
final class ProfileViewModel {
    private let api = URLSessionProfileAPI(session: .shared, baseURL: URL(string: "https://api.example.com")!)
    var name = ""

    func load() async {
        name = (try? await api.profile().name) ?? "Unknown"
    }
}
```

That one line, `private let api = URLSessionProfileAPI(...)`, fixes three decisions at once:

1. **Which type.** It's always `URLSessionProfileAPI`. A test or a SwiftUI preview can't substitute a stub, so they hit the real network.
2. **How it's assembled.** The base URL and session are baked in. A staging build or a demo mode has to edit this file.
3. **How many, and for how long.** Each view model makes its own client, which lives exactly as long as the view model.

Every creational pattern moves at least one of those decisions out of the call site, to somewhere better placed to make it. Step through the picture:


That last picture is dependency injection, which you'll study properly in D21. The creational patterns are the tools for the "makes" arrows: how the decision-maker builds the right object.

## The creational family

Eight patterns cover nearly everything an iOS app does when it makes objects. Five are from the GoF book; static factories come from Joshua Bloch's *Effective Java*, and object pools and lazy initialisation are older still.

| Pattern | The question it answers | Where you've already seen it |
| --- | --- | --- |
| Static factory | Which type and how assembled, behind a clear name | `UIButton.Configuration.filled()`, `URL(string:)` |
| Factory method | Which type, decided by a subclass or conforming type | `UIView.layerClass`, `makeUIView(context:)` |
| Abstract factory | Which **family** of related types | Live, demo and UI-test dependencies |
| Builder | How a complex object is assembled, step by step | `URLComponents`, `UNMutableNotificationContent` |
| Prototype | How, by copying a configured example | `URLSessionConfiguration.default`, struct copies |
| Singleton | How many: exactly one, reachable from anywhere | `UIApplication.shared` |
| Object pool | How long: keep instances and reuse them | `dequeueReusableCell(withIdentifier:for:)` |
| Lazy initialisation | When: on first use, not up front | `lazy var`, `static let`, a view controller's `view` |

Notice how much of UIKit and SwiftUI is built from these. When SwiftUI calls your `makeUIView(context:)`, it's using a factory method: SwiftUI decides *when* to create the view, you decide *what* to create.

## When a pattern is worth it

Every pattern adds indirection: another type, another file, one more jump when someone reads the code. A pattern earns that cost only when one of its forces is actually present:

- **You need to swap the type:** tests, previews, a demo mode, a staging server, a second payment provider.
- **Construction is complicated or repeated:** many optional parts, validation across fields, the same setup copied into five places.
- **Lifetime needs control:** exactly one shared resource, expensive objects worth keeping, work you'd rather not do at launch.

If none of those apply, `let formatter = ListFormatter()` is the right design. You met the cost of premature abstraction in [When SOLID hurts: over-abstraction and indirection](/design/learn/sd-solid-limits) and [KISS, YAGNI and least astonishment](/design/learn/sd-principles-simplicity); patterns are the most common way to over-abstract.

The GRASP **Creator** principle from [GRASP: information expert, creator and controller](/design/learn/sd-principles-grasp-ownership) gives the default answer: the type that contains, records or closely uses an object, or holds the data to initialise it, should create it. Reach for a creational pattern when following Creator would couple that type to something it shouldn't know, such as the network, the environment or a concrete class from another module.

## Trade-offs

| | Direct `init` at the call site | A creational pattern |
| --- | --- | --- |
| Reading the code | Obvious: you see exactly what's made | One jump away; you must find the factory |
| Testability | Fixed type, so no seam for a stub | A seam where tests substitute their own |
| Changing the type later | Edit every call site | Edit the one place that decides |
| Number of types | None extra | A protocol, a factory or a builder |
| Compile-time checks | Full | Full with protocols and enums; weaker with string-keyed registries |

Direct construction wins for values and leaf objects with no environment-dependent behaviour: models, formatters, small helpers. A pattern wins where a decision depends on context the call site shouldn't know.

<Callout kind="interview">

**What to say:** name the force before the pattern. "The checkout screen shouldn't know whether we're talking to Stripe or Adyen, so a factory at the composition root picks the payment provider" beats "I'd use the abstract factory pattern".

**What to ask:** "Do we need to swap this in tests or per environment?" and "Who else creates this object?" The answers tell you whether a pattern is justified.

**Red flags:** reciting GoF definitions without an iOS example; adding a factory, a builder and a protocol for a type with one implementation and no tests; treating a pattern name as the end of the design rather than the start.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: patterns translated from Java">

Many pattern tutorials are line-by-line ports from Java: an abstract base class whose methods call `fatalError("override me")`, a `getInstance()` method, a builder for a struct with three fields. Swift has protocols with default implementations, `static let`, default arguments and value types. Reach for those first, and use the textbook shape only when they don't fit.

</Callout>
