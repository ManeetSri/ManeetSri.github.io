## Why it matters

A name is the smallest interface you'll ever design, and the one people read most. If you can't find a precise name for a type or method, you usually haven't decided what it's responsible for, and the name is where that shows first. Reviewers and interviewers read your names before your code: a whiteboard box labelled `DataManager` tells them nothing, while `UploadQueue` tells them what it owns, what it hides, and roughly how it works.

## A name is a promise about responsibility

Some words turn up in names precisely because the author couldn't say what the thing does: **Manager**, **Helper**, **Util**, **Handler**, **Processor**, **Service** on its own, **Data**, **Info**, **Common**, **Base**. `UserManager` might fetch users, cache them, validate usernames, format display names and log people out. It ends up doing all of those, because the name doesn't rule any of them out.

Treat a vague name as a design smell, and try naming the jobs instead:

| Vague | What it actually did | Split into |
| --- | --- | --- |
| `UserManager` | Fetched and cached profiles, checked usernames, formatted names | `ProfileRepository`, `UsernameRules`, `PersonNameComponents.formatted()` |
| `NetworkHelper` | Built requests, added auth, decoded JSON, retried | `APIClient`, with an `AuthenticatingClient` decorator and a `RetryPolicy` |
| `AppUtils` | Date formatting, haptics, a keychain wrapper | Three types in three places, or deleted in favour of Apple's APIs |

Two quick tests catch most problems. If the honest name needs **"and"** (`fetchAndCacheAndNotify`), the function does too much. If the name describes **when** it's called rather than **what** it does (`viewDidLoadSetup`, `handleButtonTap`), the work inside has no name yet; `viewDidLoad` should call `loadOrders()` and `configureLayout()`, which say what happens.

## Name things in the domain's words

The best names come from the product, not from programming. A fitness app has `ClassSession`, `Booking` and `Waitlist`, not `Item`, `Entry` and `Queue`. When code uses the words the product team, support staff and designers use, everyone can read the model, and requirements translate into code without a dictionary.

Watch for one concept with several names. If product calls it a *pass*, the backend calls it an *admission* and the iOS code calls it a *ticket*, every conversation includes a translation step, and translations are where bugs hide ("does an admission include the guest pass?"). Agree one word, write it in a short glossary in the repository, and use it everywhere you control. Where the API's name differs, map it once at the boundary with `CodingKeys` or a DTO, so the odd name stays in one file. Domain-driven design calls this shared vocabulary the *ubiquitous language*, and you'll go further with it in D30.

## Swift's API Design Guidelines

Swift has an official naming guide, the *API Design Guidelines* on swift.org, and Apple's frameworks follow it closely. Its first rule is the one to remember: **clarity at the point of use**. A declaration is written once and read at every call site, so optimise for the call site.

The rules you'll use most:

- **Omit needless words.** `list.remove(member)`, not `list.removeElement(member)`: the type already says it's an element.
- **Name by role, not by type.** `var greeting: String`, not `var string: String`. `func add(_ observer: Observer)`, not `func add(_ object: Observer)`.
- **Make uses read as English phrases.** `x.insert(y, at: z)` reads "x, insert y at z". `x.insert(y, position: z)` doesn't.
- **Booleans read as assertions about the receiver:** `isEmpty`, `canCancel`, `hasUnreadMessages`, `line.intersects(other)`.
- **Name methods by their side effects.** A mutating method is an imperative verb (`sort()`, `append(_:)`); its non-mutating twin is a noun, or a past participle or *-ing* form (`sorted()`, `appending(_:)`). When the operation is naturally a noun, the mutating form gets `form`: `union(_:)` and `formUnion(_:)`.
- **Factory methods begin with `make`:** `makeIterator()`, `makeCoordinator()`.
- **Protocols that describe what something is are nouns** (`Collection`, `Sequence`). **Protocols that describe a capability end in -able, -ible or -ing** (`Equatable`, `Sendable`, `ProgressReporting`).
- **Drop `get`.** Swift doesn't prefix accessors: `user(id:)`, not `getUser(id:)`.

Here's a declaration written without them, and the same one with them:

```swift check title="Names that read at the call site"
import Foundation

struct Order: Identifiable {
    let id: UUID
    var title: String
}

// Before: names that describe types and plumbing
final class OrderDataManager {
    func getData(_ flag: Bool, _ s: String) async throws -> [Order] { [] }
}

// After: names that describe roles and intent
enum CachePolicy {
    case returnCachedIfAvailable
    case reloadFromServer
}

protocol OrderHistory {
    func orders(matching search: String, cachePolicy: CachePolicy) async throws -> [Order]
}

func showResults(manager: OrderDataManager, history: some OrderHistory) async throws {
    let before = try await manager.getData(true, "trainers")
    let after = try await history.orders(matching: "trainers", cachePolicy: .reloadFromServer)
    print(before.count, after.count)
}
```

At the call site, `getData(true, "trainers")` leaves you guessing what `true` means and what the string is. `orders(matching: "trainers", cachePolicy: .reloadFromServer)` reads as a sentence. Replacing the `Bool` with a two-case enum is a naming decision too: an enum gives both values a name, and leaves room for a third policy later.

## Names at the right level of abstraction

A name should describe the level it lives at, not the one below.

- `fetchUserFromCoreData()` puts the implementation in the interface: move to SwiftData and the name lies, or every caller changes. Call it `user(id:)`, and let the conforming type say how: `protocol UserStore` with `struct CoreDataUserStore: UserStore`.
- Name a protocol for its role, and the concrete type for what's special about it: `ImageLoading` (or `ImageLoader`) as the protocol; `URLSessionImageLoader` and `PreviewImageLoader` as conformers.
- Avoid a `Protocol` suffix unless the natural name is taken. Apple uses it only when it must: `IteratorProtocol` and `StringProtocol` exist because `Iterator` is an associated type name and `String` is a struct. `UserServiceProtocol` with `UserService` usually means the protocol mirrors its one conformer, which the lesson on deep modules warned about.

## Names that carry units and meaning

Some names fail because the type is too weak to say what the value means.

- `let timeout = 30` (seconds? milliseconds?) becomes `let timeout: Duration = .seconds(30)`. `Duration`, from Swift 5.7, carries its unit, and `Task.sleep(for:)` and `Clock` take it directly.
- `let distance = 5.0` becomes `Measurement(value: 5, unit: UnitLength.kilometers)`, which converts and formats for the user's locale.
- `let refundWindow = 86_400` becomes a named constant whose name says what it is *for*, with a type that says what it is *in*: `static let refundWindow: Duration = .seconds(24 * 60 * 60)`.

The lesson on domain types takes this all the way: when a name has to carry meaning the type can't, it's often time for a new type.

## Renaming is design work

A good name is often found, not chosen. You name something early, you learn what it really does, and the name should follow. Xcode's **Refactor ▸ Rename** updates every reference safely, so renaming code is cheap.

Renaming **data** isn't. Some names leave your code and live on:

- `Codable` property names become JSON keys and stored file formats;
- `UserDefaults` keys, Keychain account names and App Group file names persist across launches and versions;
- analytics event names feed dashboards other teams rely on;
- `@AppStorage` and `@SceneStorage` keys, notification names, URL schemes and App Intents identifiers.

Decouple the code name from the stored name wherever you can (`CodingKeys`, a key constant in one place), so code can be renamed freely and data never is.

## Trade-offs

| Name style | Reads well at the call site | Survives a change of implementation | Easy to search for | Example |
| --- | --- | --- | --- | --- |
| Domain word | Yes, to everyone on the team | Yes | Yes | `Waitlist.promoteNext()` |
| Technical role | Yes, to engineers | Yes | Yes | `UploadQueue`, `ProfileRepository` |
| Implementation detail | Only if you know the internals | No: it lies after a refactor | Yes | `CoreDataUserFetcher` as a protocol |
| Vague catch-all | No | It never said anything to break | No: every module has one | `DataManager`, `Utils` |
| Very short | Only within a few lines | Yes | No | `x`, `vm`, `res` |

Short names are fine in tiny scopes (`for item in items`, `$0` in a one-line closure). The wider a name is visible, the more it should say.

<Callout kind="interview">

**Say** the responsibility in the name when you draw boxes: "Feed repository", "Upload queue", "Image pipeline", never "Manager". When you introduce a type, define it in one sentence; if the sentence needs "and", split the box. **Ask** what the interviewer calls things ("is a *story* the same as a *post* here?") and use their words. **Red flags:** "and then the Manager handles it", three names for one concept in one design, and Boolean parameters nobody can read at the call site.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: renaming a Codable property renames its JSON key">

With synthesized `Codable`, the property name *is* the key. Rename `var title` to `var headline` for readability and the app stops decoding the server's `title`, and every file you saved last release. The project still compiles; it fails at runtime. Add `CodingKeys` (`case headline = "title"`) before renaming, and keep a decoding test that loads a saved sample from the previous release.

</Callout>
