## Why it matters

The first question to ask about anything in your data model: is it defined by *who* it is, or by *what* it is? A customer stays the same customer after changing her name; £5 is £5, whichever coin you hold. The answer decides how you compare things, what you give an id, what you store and sync, and how SwiftUI tracks rows in a list. In an interview's data-model section, getting it right is what makes the rest of the model hang together.

## Two kinds of thing

Eric Evans's *Domain-Driven Design* (2003) gave these two kinds the names most teams use.

- An **entity** has an identity that lasts through change. A customer, an order, a booking, a conversation. Every attribute can change and it's still the same one, so you need something other than its attributes (an id) to tell it apart.
- A **value object** is defined entirely by its attributes. An amount of money, an address on a parcel label, a date range, a colour, a coordinate. Two with the same attributes are interchangeable, and "changing" one means replacing it with another.

Two quick tests settle most cases. *If every attribute changed, would it still be the same thing?* If yes, it's an entity. *Would anyone care which one they got, as long as the attributes match?* If not, it's a value.

<Callout kind="analogy">

Banknotes and people. If you lend a friend a £10 note, you don't want *that* note back, just any £10 note: money is a value. If you lend your car to a friend, you want *that* car back, even if they've had it resprayed: it's an entity, and the number plate is its id.

</Callout>

## Entities and values in Swift

In Swift both are usually `struct`s, and that confuses people at first. *Value semantics* (a `struct` is copied on assignment) is a language feature. A *value object* is a modelling idea. A `Customer` struct has value semantics, but it models an entity: copying it gives you a second snapshot of the same customer, not a second customer.

So in Swift you mark identity explicitly, with an `id` and `Identifiable`:

```swift run title="Same entity, different snapshots"
import Foundation

/// A value: two addresses with the same lines are the same address
struct PostalAddress: Hashable, Sendable {
    let line1: String
    let city: String
    let postcode: String
}

/// An entity: identified by `id`, whatever else changes
struct Customer: Identifiable, Hashable, Sendable {
    let id: UUID
    var name: String
    var address: PostalAddress
}

let id = UUID(uuidString: "6F1C2D8E-4A5B-4C3D-9E8F-1A2B3C4D5E6F")!
let leeds = PostalAddress(line1: "1 High St", city: "Leeds", postcode: "LS1 1AA")
let before = Customer(id: id, name: "Sam Lee", address: leeds)

var after = before
after.address = PostalAddress(line1: "9 Park Rd", city: "York", postcode: "YO1 7HH")
after.name = "Samira Lee"

print("Same customer? \(before.id == after.id)")
print("Same snapshot? \(before == after)")
print("Same address as a fresh copy? \(leeds == PostalAddress(line1: "1 High St", city: "Leeds", postcode: "LS1 1AA"))")

// Find an entity by its identity, then replace the old snapshot
var customers = [before]
if let index = customers.firstIndex(where: { $0.id == after.id }) {
    customers[index] = after
}
print(customers.map(\.name))
```

```output
Same customer? true
Same snapshot? false
Same address as a fresh copy? true
["Samira Lee"]
```

Two different questions, two different tools. `id` answers *is this the same customer?* The synthesized `==` answers *has anything about her changed?* You need both, and in Swift they live side by side. That's different from what some DDD books recommend (comparing entities only by id), and for a good reason, which the gotcha below explains.

Classes add a third kind of sameness: **object identity** (`===`, the same instance in memory). It isn't domain identity. Fetch customer 42 twice into two class instances and `===` is false while their ids match. Core Data handles this with *uniquing*: within one managed object context, there's at most one object for each record, so `===` and identity agree inside a context. Across contexts, or with your own classes, they don't.

## Values are replaced, not edited

A value object should be **immutable**: build a new one instead of changing the old. In languages where everything is a reference, that rule prevents aliasing bugs (two orders sharing one address object, so editing one moves both). Swift structs already protect you from aliasing, so a `var` inside a value struct is safe in that sense.

Immutability still matters for **validated** values. If `PostalAddress` checks its postcode in `init`, a `var postcode` would let any code set an invalid one afterwards. `let` properties plus a validating `init` mean every `PostalAddress` that exists is valid. You'll build exactly that in the lesson on domain types.

Values bring a lot of benefits for free:

- **They're safe to share.** A value made of `Sendable` parts is `Sendable`; pass it to any actor.
- **They're easy to test.** Build one, compare with `==`. No ids, no mocks.
- **They're easy to cache and store.** No lifecycle, so they live inside their entity: a nested `Codable` struct in JSON, a property on a SwiftData model.
- **They can hold behaviour.** `Money.adding(_:)`, `DateRange.contains(_:)`, `Coordinate.distance(to:)`. A value object is a great home for small rules.

## Where identity comes from

An entity's id has three jobs: it must be **unique** in its scope, **stable** for the entity's whole life, and **available** when you need it. Where you get it from is a real design decision on mobile:

| Source | Example | Create offline | Stable | Watch out for |
| --- | --- | --- | --- | --- |
| Server-assigned | `"order_8231"` from `POST /orders` | No: no id until the server answers | Yes | Temporary local ids that must be swapped later |
| Client-generated UUID | `UUID()` when the user taps New | Yes | Yes | The server must accept your ids |
| Natural key | Email, phone number, ISBN | Yes | Often not: emails change, numbers get recycled | Personal data in logs and URLs |
| Array index or position | `messages[3]` | Yes | No: changes on every insert | Wrong rows animating, state on the wrong row |

Client-generated UUIDs are the usual choice for anything a user can create offline: a note, a draft, a photo upload. They also make sync safer. If the app sends "create note `7D3F…`" and the response is lost, sending it again creates nothing new, because the server already has a note with that id. That property, *retrying gives the same result*, is called **idempotency**, and you'll lean on it in D45.

## The same thing can be either

Whether something is an entity or a value depends on what your app does with it.

- An **address** is a value on a parcel label. For a delivery company's routing system, a location might be an entity, with an id, a geocode and the driver's notes about the gate code.
- A **seat** is a value on a cinema ticket ("row F, seat 12"). For the cinema's seating system, each seat is an entity with a maintenance history.
- A **product** in the catalogue is an entity whose price changes. The product *in an order line* should be a value: a snapshot of the name and the price the customer actually paid. If the order line pointed at the live product, last year's receipts would change every time the price did.

That last pattern, an entity's reference plus a value snapshot, appears in almost every commerce app, and you'll use it in the shopping-cart worked example at the end of this module.

## Identity in SwiftUI lists

SwiftUI's `List` and `ForEach` use identity to decide which row is which between updates: which to update in place, which to insert, which to animate when sorting. Give them the entity's id:

```swift check ios title="CustomersView.swift"
import SwiftUI

struct Customer: Identifiable {
    let id: UUID
    var name: String
}

struct CustomersView: View {
    let customers: [Customer]

    var body: some View {
        // Rows are keyed by customer.id, so a rename updates a row instead of replacing it
        List(customers) { customer in
            Text(customer.name)
        }
    }
}

struct TagsView: View {
    let tags: [String]

    var body: some View {
        // Values can be their own id, but only if no two are ever equal
        ForEach(tags, id: \.self) { tag in
            Text(tag)
        }
    }
}
```

Two mistakes are common. Keying rows by **index** (`id: \.offset` or `0..<items.count`) means inserting at the top shifts every id, so SwiftUI animates the wrong rows and leaves `@State` (a text field's contents, an expanded section) attached to the wrong one. Keying by **value** with `id: \.self` breaks when two values are equal, such as two chat messages that both say "OK": SwiftUI warns at runtime that an id occurs more than once, and the results are undefined.

## Trade-offs

| Decision | Option | Wins when | Costs |
| --- | --- | --- | --- |
| Entity or value? | Entity with an id | It has a lifecycle, changes, and is referred to from elsewhere | Needs an id, storage, sync and conflict handling |
| | Value | It's defined by its attributes and replaced whole | Can't be referred to on its own; copied wherever it's used |
| Entity equality | Synthesized `==` plus `Identifiable` | Almost always in Swift | Two questions, two APIs to remember |
| | `==` by id only | Rarely; maybe a reference type with no change tracking | Breaks change detection everywhere |
| Id source | Client UUID | Offline creation, idempotent sync | The server must trust client ids |
| | Server id | Server-created things (orders after payment) | No id until the network answers |

<Callout kind="interview">

**Say**, for each noun in your data model, whether it's an entity or a value, and where an entity's id comes from: "A `Post` is an entity with a server id; a `Draft` gets a client UUID so it can be created offline and synced idempotently; the money on an order line is a value snapshot of what was paid." **Ask** whether things can be created offline, and whether two devices can edit the same entity. **Red flags:** email or username as a primary key, index-based ids in lists, and order lines that point at live product prices.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: an id-only == hides every change">

It's tempting to write `static func == (lhs: Customer, rhs: Customer) -> Bool { lhs.id == rhs.id }` because "entities are equal when their ids are". Then `onChange(of: customer)` stops firing when her name changes, Combine's `removeDuplicates()` drops real updates, SwiftUI can skip re-rendering a row whose input it now thinks is unchanged, and `Hashable` is broken unless you also hash only the id. Keep the synthesized `==` for *has it changed?*, and use `id` for *is it the same one?*

</Callout>
