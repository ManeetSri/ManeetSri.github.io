## Why it matters

Every persistent connection on a phone dies, many times a day: in lifts and tunnels, when Wi-Fi hands over to cellular, when the app is suspended, when the server deploys. The quality of a real-time feature is mostly decided by what happens next: how fast the app notices, how politely it reconnects, and whether it picks up where it left off. Get it wrong and you get chat apps that silently stop receiving, and fleets of phones that knock a recovering server over. "What happens when the connection drops?" is the follow-up to every WebSocket answer in an interview.

## How connections die

A connection can end in four ways, and only two of them tell you:

- **A clean close.** One side sends a close frame with a code, such as `1001` from a draining server. You know at once, and you know why.
- **A reset.** The server process crashed, or a middlebox gave up, and the next packet is answered with a TCP reset. The pending receive fails with an error within moments.
- **Silence.** The phone walked into a lift; a NAT on the carrier's network forgot the connection's mapping; Wi-Fi handed over to cellular and the old route is gone; a server lost power. Neither side is told. The socket still looks open, receives nothing, and a send may sit in a buffer for minutes before TCP gives up. TCP's own keepalive is no help: by default it waits two hours before probing.
- **Suspension.** The app stops running a few seconds after the user leaves. Nothing reads the socket or answers the server, which closes it after its own timeout; iOS may reclaim the socket too. Either way, the connection you return to is gone.

Silence is the dangerous one, because the app keeps showing "Live" over data that stopped flowing. Detecting it is the heartbeat's job.

## Heartbeats

A **heartbeat** is a small message one side sends on a timer and the other answers. If no answer comes within a timeout, the connection is treated as dead, whatever the socket says. Use WebSocket ping frames or an application message such as `{"type": "ping"}`; MQTT builds it in as keep-alive.

Three numbers to choose:

- **Interval.** Shorter than the shortest idle timeout on the path, or the path closes healthy connections for you. Proxies and load balancers often cut idle connections at 60 seconds, and some cellular NATs drop idle mappings after a few minutes or less, so 20–30 seconds is a common choice. Socket.IO's default is a ping every 25 seconds.
- **Timeout.** Long enough for a slow cellular round trip, typically 10–20 seconds. Too short and a congested network causes needless reconnects.
- **Detection time** follows from both: up to interval plus timeout. With 25 and 10, a dead connection is noticed within 35 seconds, and usually sooner, because…

…**any traffic counts**. A connection that just delivered a message is alive. Reset the ping timer on every frame received and ping only when the connection has been quiet. A busy chat never needs a heartbeat; an idle one sends one every 25 seconds.

**Both sides check.** The server needs its own heartbeat (or to expect the client's) to free memory held by dead connections and to know who's really online. And prefer heartbeats that reach your application, not only the first proxy: a load balancer or proxy that terminates WebSockets may answer protocol pings itself, which proves the path to the proxy and says nothing about whether your server is still processing messages.

Every heartbeat wakes the radio. The last lesson of this module puts a battery cost on that choice.

## When to reconnect, and when not to

Reconnect when:

- the receive loop fails, or the server closes with a code that invites it (`1001`, `1006`, `1011`, `1012`, `1013`);
- a heartbeat goes unanswered;
- the **network path changes**: it comes back after being unavailable, or moves from Wi-Fi to cellular. The old socket is bound to the old route and may hang for a long time before failing, so don't wait for the heartbeat to find out;
- the app returns to the foreground;
- the server asks: a "reconnect" message during a deploy, ideally with a suggested delay.

Don't reconnect when:

- there's **no network**: wait for a path instead of burning attempts and battery;
- the user **signed out**, or the server closed with a normal `1000`;
- **authentication failed**: refresh the token first; if the refresh fails too, sign the user out instead of looping;
- the server says **this app version is too old**: show "please update";
- the app is in the **background**: close the connection deliberately and reconnect when it returns.

## Backoff, jitter and when to reset

Reconnection is a retry, and everything from [retry with backoff](/design/learn/sd-resilience-retry-backoff) applies: capped exponential delays, full jitter, and a loop that stops when told. Two details are specific to connections.

**Jitter the first attempt too.** When a server restarts, every connected client drops at the same instant. If they all reconnect immediately, the first wave is the whole fleet at once. A random delay of a second or two before the first attempt spreads it out.

**Reset the backoff only when a connection proves itself**, not when TCP connects. A server that's overloaded, or rejecting a token after the upgrade, may accept connections and close them a moment later. A client that resets its backoff on every successful connect will hammer that server at the base rate forever. Reset once the connection has delivered something (a pong, a message) or stayed up for a while.

The result is a small state machine, the same one the kata for this lesson asks you to build:

In the foreground, cap the delay at 30–60 seconds and show the state honestly: "Reconnecting…" after the first failure, "Offline" when there's no path, and the last data you had in the meantime.

## Resuming, not restarting

A new connection is a blank slate on the server: it doesn't know what this client was subscribed to or what it last saw. The client must restore its session, in order:

1. **Authenticate** the new connection, with a fresh token if the old one expired.
2. **Resubscribe** to every topic. The client, not the server, is the owner of "what this app currently cares about"; keep that set in the client and replay it on every connect.
3. **Catch up** on what was missed while disconnected, from the last sequence number per channel, an SSE `Last-Event-ID`, or a cursor for the HTTP API.
4. **Go live**, applying new events on top.

The order of 2 and 3 matters more than it looks: subscribing *after* fetching the catch-up opens a window where events slip between the two. The next lesson works through that race and the sequence numbers that close it.

## The server's side: reconnect storms

A gateway holding 50,000 connections that crashes sends 50,000 clients to the other gateways at once, and each reconnect costs a TCP handshake, a TLS handshake (the expensive part; [TLS session resumption](/design/learn/sd-net-tls-handshake) helps) and an authentication check. Servers protect themselves too:

- **Drain gradually on deploys.** Close connections a slice at a time over minutes with `1001` or `1012`, rather than all at once.
- **Send hints.** A "reconnect in 0–30 seconds" message with a random delay per client turns a spike into a ramp.
- **Refuse early when overloaded.** Answering `1013 Try Again Later` (or `503` on the upgrade) costs far less than accepting a connection the server can't serve.
- **Keep spare capacity for the storm**, not only for the steady state: the steady state is idle connections, but the storm is handshakes.

## Supervising the connection in an iOS app

Something in the app must turn the platform's signals into "connect now" and "disconnect now": the scene phase and the network path. Keep that separate from the client that does the connecting, so each is testable:

```swift check ios title="ConnectionSupervisor.swift"
import Network
import SwiftUI

/// Decides when the live connection should exist: the app is active and there's a network path
@MainActor @Observable
final class ConnectionSupervisor {
    enum Network: Equatable {
        case unknown
        case online(NWInterface.InterfaceType?)
        case offline
    }

    private(set) var network = Network.unknown
    private var isActive = false
    private let monitor = NWPathMonitor()
    /// Starts a connection now, replacing any existing one and skipping any backoff wait
    private let connect: @MainActor () -> Void
    private let disconnect: @MainActor () -> Void

    init(connect: @escaping @MainActor () -> Void, disconnect: @escaping @MainActor () -> Void) {
        self.connect = connect
        self.disconnect = disconnect
        monitor.pathUpdateHandler = { [weak self] path in
            let status = path.status
            let interface = [NWInterface.InterfaceType.wifi, .cellular, .wiredEthernet].first { path.usesInterfaceType($0) }
            Task { @MainActor in self?.pathChanged(satisfied: status == .satisfied, interface: interface) }
        }
        monitor.start(queue: DispatchQueue(label: "live.path-monitor"))
    }

    func scenePhaseChanged(to phase: ScenePhase) {
        isActive = phase == .active
        if isActive, case .online = network {
            connect()
        } else if !isActive {
            // A suspended app can't keep a socket alive; close it cleanly and reconnect on return
            disconnect()
        }
    }

    private func pathChanged(satisfied: Bool, interface: NWInterface.InterfaceType?) {
        let previous = network
        network = satisfied ? .online(interface) : .offline
        guard satisfied else {
            // No path: stop the backoff loop instead of burning attempts, and show "Offline"
            disconnect()
            return
        }
        // Back online, or moved from Wi-Fi to cellular: the old socket is tied to the old route
        if isActive, previous != network {
            connect()
        }
    }
}
```

The root view forwards `scenePhase` with `.onChange(of: scenePhase)`, and the reconnecting client underneath owns backoff, heartbeats and resubscription. Neither knows about the other's concerns, which is what lets the kata test the client with a fake transport and a test clock.

## Trade-offs

| Heartbeat interval | Detects a dead connection within | Radio and server cost | Risk |
| --- | --- | --- | --- |
| 10 s | About 20 s | High: the radio rarely rests | Battery drain; heartbeats outnumber real messages |
| 25–30 s | About 40 s | Moderate | The usual default |
| 60 s or more | Over a minute | Low | Idle timeouts on the path close healthy connections; stale "Live" screens |

| Reconnect policy | Recovery for one client | Fleet behaviour | Wins when |
| --- | --- | --- | --- |
| Immediately, in a loop | Fastest | A storm that can take the server down | Never |
| Fixed delay | Predictable | Synchronised waves | A handful of clients |
| Backoff with jitter, reset on connect | Good | Hammering servers that accept then close | Almost never; reset too early |
| Backoff with jitter, reset when healthy, server hints honoured | Good | Smooth | The default |

<Callout kind="interview">

**Say** detection, policy and resumption in that order: "Heartbeats every 25 seconds when the connection is quiet, with a 10-second timeout, on both sides. On a drop, path change or return to the foreground, reconnect with capped exponential backoff and full jitter, including on the first attempt, and reset only after the new connection delivers something. Don't retry while offline or after an auth failure. Every new connection re-authenticates, resubscribes and catches up from the last sequence number." **Ask** how the server drains connections on deploys. **Red flags:** relying on TCP to notice dead connections, reconnecting in a loop without backoff, resetting backoff on connect, and forgetting to resubscribe.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the socket you come back to">

When the app returns from the background, the `URLSessionWebSocketTask` object is still there and may look open, but the connection behind it is almost certainly dead. Waiting for a heartbeat to discover that shows stale data for half a minute. Close the socket when the scene goes to the background, and open a new one as soon as it's active again.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: satisfied isn't the same as online">

`NWPathMonitor` reports `.satisfied` when there's a route, not when your server is reachable: a captive portal on hotel Wi-Fi is satisfied, and so is a network that drops everything. Treat a path change as a reason to try now, never as proof the connection will work, and keep the heartbeat as the real test. Path updates can also arrive in quick bursts during a handover, so a short debounce (half a second or so) before reconnecting avoids opening two sockets.

</Callout>

## Practice

The kata **"A reconnecting socket client"** has you build the state machine above as an actor: connect over an injected transport, resubscribe after every reconnect, ping on a test clock, close silent connections and back off with a reset rule that resists flapping. It builds on the [backoff schedule](/design/learn/sd-resilience-retry-backoff) from D14. The review **"a live-scores socket client"** then shows what happens without any of it: no heartbeat, instant reconnects, lost subscriptions and receive loops that multiply.
