## Why it matters

A quality nobody measures erodes one pull request at a time. Launch gets 30 ms slower, a feature module quietly imports another, a new screen ships without VoiceOver labels, and each change looked harmless on its own. Two tools stop the slide. **ISO/IEC 25010** gives you a checklist and a shared vocabulary, so no quality is forgotten when you gather requirements. **Fitness functions** turn the qualities that matter into automated checks, so they can't regress silently. "How would you keep the architecture the way you designed it?" is a classic staff-level interview question, and this is the answer.

## ISO 25010: a checklist of qualities

ISO/IEC 25010 is the international standard model of software product quality. It was first published in 2011 and revised in 2023, and it sorts quality into **nine characteristics**, each with sub-characteristics. You don't need to memorise them; you need to recognise them, and to use the list as a prompt when you gather requirements.

| Characteristic | Sub-characteristics | The question for an iOS app |
| --- | --- | --- |
| Functional suitability | Completeness, correctness, appropriateness | Does the refund flow handle partial refunds correctly? |
| Performance efficiency | Time behaviour, resource utilisation, capacity | p90 launch time? Memory? How many items before it slows? |
| Compatibility | Co-existence, interoperability | Does it share data with its widget and watch app? Does it behave when another app plays audio? |
| Interaction capability | Recognisability, learnability, operability, user error protection, engagement, inclusivity, user assistance, self-descriptiveness | Can a first-time user, or a VoiceOver user, finish checkout? |
| Reliability | Faultlessness, availability, fault tolerance, recoverability | Crash-free rate? Does a draft survive the app being killed? |
| Security | Confidentiality, integrity, non-repudiation, accountability, authenticity, resistance | Can a stolen phone or a modified client get at someone's data? |
| Maintainability | Modularity, reusability, analysability, modifiability, testability | Can one team change checkout without breaking the feed? |
| Flexibility | Adaptability, scalability, installability, replaceability | iPad, new screen sizes, a bigger catalogue, download size? |
| Safety | Operational constraint, risk identification, fail safe, hazard warning, safe integration | Could a navigation or health feature hurt someone if it's wrong? |

You'll still see the 2011 names in books and job descriptions: **usability** (now interaction capability, where accessibility became *inclusivity* and *user assistance*) and **portability** (now flexibility). Safety is new in 2023. A separate *quality in use* model describes the experience of using the product: effectiveness, efficiency, satisfaction and freedom from risk.

<Callout kind="note">

ISO's *operability* is a sub-characteristic of interaction capability: how easily a **user** can operate the app. Engineers usually mean something else by the word, as in the reliability lesson: how easily the **team** can run the system in production. When you use the word in a design review, say which you mean.

</Callout>

ISO 25010 tells you **what** to think about, not how good is good enough. It has no target numbers; those come from your product, as scenarios and budgets.

## From a quality to a measurement

To check a quality, you need a measurement, and for most qualities you'll want two: one from the **lab** (CI, a test device, before release) to catch regressions early, and one from the **field** (real people on real devices) to see what they actually experience.

| Quality | Lab measurement | Field measurement |
| --- | --- | --- |
| Launch time | XCTest's `XCTApplicationLaunchMetric` on a fixed older device | MetricKit's launch metrics; Xcode Organizer |
| Scrolling | XCTest's scroll hitch metric (`XCTOSSignpostMetric.scrollingAndDecelerationMetric`) | MetricKit's `MXAnimationMetric` hitch time ratio |
| Memory | `XCTMemoryMetric` in a test that opens the heavy screens | MetricKit's peak memory; terminations for memory |
| Reliability | Crash-free UI test runs; fault-injection tests | Crash-free users and sessions; hang rate |
| App size | Size of the built `.ipa` in CI | App Store Connect's download and install sizes |
| Accessibility | `performAccessibilityAudit()` in UI tests | Support tickets and feedback from assistive-technology users |
| Maintainability | Dependency rules between modules; build time | Lead time from commit to release; hotspots of churn and complexity |
| Security and privacy | No secrets in the repository or binary; no ATS exceptions; a complete privacy manifest | Abuse reports; App Attest rejections |

Pick measurements with care, because people optimise whatever you measure. This is **Goodhart's law**: once a measure becomes a target, it stops measuring well. A team told to reach 80% code coverage writes tests that run lines without checking anything; a team judged on crash-free sessions catches every error and shows a blank screen instead. Measure the outcome you care about, and pair numbers with judgement.

## Fitness functions

The term comes from *Building Evolutionary Architectures* by Neal Ford, Rebecca Parsons and Patrick Kua. An **architectural fitness function** is any mechanism that gives an objective, repeatable verdict on how well the system meets a quality it's supposed to have. A unit test checks behaviour ("this function returns 4"); a fitness function checks a quality ("cold launch stays under a second", "no feature module imports another").

Fitness functions vary along a few dimensions, and naming them helps you choose:

- **Atomic or holistic:** one quality in isolation (a dependency rule), or several together (launch time measured with encryption and analytics switched on, because that's how users get it).
- **Triggered or continual:** run on an event such as a pull request, or running all the time, such as a production alert on crash rates.
- **Static or dynamic:** a fixed threshold ("under 60 MB"), or one relative to something else ("no more than 10% slower than the last release").
- **Automated or manual:** most should be automated, but a VoiceOver walkthrough of the main flows before each release is still a fitness function.

Step through where an iOS team typically runs them:


### Writing one

A fitness function is often a few lines. Here's a static, atomic one for a modular app: dependencies must point down the layers, and feature modules may not import each other (so two teams can change their features independently). In a real project it would read the module graph from `Package.swift`; the rules are the interesting part.

```swift run
enum Layer: Int {
    case app, feature, domain, platform   // top to bottom
}

struct Module {
    let name: String
    let layer: Layer
    let imports: [String]
}

let modules = [
    Module(name: "App", layer: .app, imports: ["Feed", "Profile", "Networking"]),
    Module(name: "Feed", layer: .feature, imports: ["Posts", "Profile", "DesignSystem"]),
    Module(name: "Profile", layer: .feature, imports: ["Accounts", "DesignSystem"]),
    Module(name: "Posts", layer: .domain, imports: ["Networking"]),
    Module(name: "Accounts", layer: .domain, imports: ["Networking"]),
    Module(name: "Networking", layer: .platform, imports: ["Accounts"]),
    Module(name: "DesignSystem", layer: .platform, imports: []),
]

let layerOf = Dictionary(uniqueKeysWithValues: modules.map { ($0.name, $0.layer) })
var violations: [String] = []

for module in modules {
    for name in module.imports {
        guard let target = layerOf[name] else { continue }
        if target.rawValue < module.layer.rawValue {
            violations.append("\(module.name) imports \(name): dependencies must point down the layers")
        } else if module.layer == .feature && target == .feature {
            violations.append("\(module.name) imports \(name): features must not import each other")
        }
    }
}

violations.forEach { print("✘ \($0)") }
print(violations.isEmpty ? "✔ module rules hold" : "\(violations.count) violations: fail the build")
```

```output
✘ Feed imports Profile: features must not import each other
✘ Networking imports Accounts: dependencies must point down the layers
2 violations: fail the build
```

Performance fitness functions on iOS usually start as XCTest performance tests. They run inside a UI test target:

```swift check ios title="LaunchFitnessTests.swift (a UI test target)"
import XCTest

final class LaunchFitnessTests: XCTestCase {
    // Compared with the baseline Xcode stores for this device; fails if it's slower by more than the allowed deviation
    func testColdLaunchStaysFast() {
        let options = XCTMeasureOptions()
        options.iterationCount = 10
        measure(metrics: [XCTApplicationLaunchMetric()], options: options) {
            XCUIApplication().launch()
        }
    }

    // Fails on missing labels, clipped text at large sizes, low contrast and small hit targets
    func testHomeScreenPassesAccessibilityAudit() throws {
        let app = XCUIApplication()
        app.launch()
        try app.performAccessibilityAudit()
    }
}
```

Xcode keeps baselines per device, so a launch test is meaningful only on the same, dedicated device every time; on a shared simulator the noise swamps the signal. Many teams therefore record the raw numbers and apply their own budgets, which is exactly the job of this lesson's kata.

## Trade-offs

| Kind of check | Catches | Misses | Cost | Use it for |
| --- | --- | --- | --- | --- |
| Static threshold in CI | Rule breaks and big regressions, before merge | Slow drift that stays under the threshold | Low | Dependency rules, app size, ATS exceptions, audits |
| Baseline comparison in CI | Drift of a few percent per change | Noise causes false failures unless you take many samples | Medium: dedicated devices, care with baselines | Launch, scrolling, memory |
| Field metrics, continually | What real people on real devices feel | Arrives late (a day or more), and can't block a merge | Low to medium | Launch, hangs, crashes, battery |
| Manual review | What's hard to automate: whether a VoiceOver flow makes sense | Anything between reviews | High per run | Accessibility walkthroughs, threat modelling |

<Callout kind="interview">

**Say:** "Each quality we promised gets a budget and a fitness function: dependency rules and size checks on every pull request, performance tests against a baseline nightly on an older device, and the same budgets watched in production with MetricKit and crash reporting, wired to pause the phased release." That one sentence covers lab, field, static, dynamic and the operational response.

**Ask:** "Which qualities are we actually promising, and who looks at the dashboard?" A metric nobody owns is decoration.

**Red flags:** measuring on the simulator; a code-coverage target standing in for quality; metrics with no threshold and no owner; "we'll notice if it gets slow".

</Callout>

<Callout kind="gotcha" title="iOS gotcha: MetricKit is daily, not real time">

`MXMetricPayload` arrives about once a day, summarising the previous day as histograms, so it's ideal for trends and budgets but can't drive a ten-minute alert. Diagnostic payloads (crashes, hangs, disk writes) arrive straight away since iOS 15. For a fast signal during a rollout, combine crash reporting with your own lightweight events, such as "home screen shown" with its duration.

</Callout>

## Practice

The kata *Performance budget gate* builds the core of a dynamic fitness function: it turns launch samples into a p90, compares it with an absolute budget and with the last good baseline, treats missing data as a failure, and ratchets the baseline as the app gets faster.

```cards
  front: "What is an architectural fitness function?"

- id: fitness-dimensions
  front: "What dimensions describe a fitness function?"
```
