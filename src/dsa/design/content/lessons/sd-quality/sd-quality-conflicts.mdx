## Why it matters

You can't maximise every quality at once. A tighter lock makes a banking app more secure and more annoying; an offline cache makes a feed more available and more stale; more analytics makes problems easier to find and the app less private. Knowing the qualities is the easy part. Seeing where they collide, and choosing on purpose, is what interviewers mean when they ask about trade-offs, and it's the habit that separates a senior answer from a list of buzzwords.

## Some qualities pull together, some apart

Not every pair conflicts. Some reinforce each other, and it's worth knowing which, because improving one gives you the other for free:

- **Testability and maintainability:** code with explicit inputs is easier to test *and* to change.
- **Performance and battery:** doing less work makes the app faster and cheaper to run.
- **Accessibility and usability:** larger targets, clear labels and good contrast help everyone, in bright sun or with one hand.
- **Reliability and availability:** fewer failures, and faster recovery from them, mean more time usable.

The conflicts are where design happens. These are the ones you'll meet again and again on iOS:

| Tension | What it looks like |
| --- | --- |
| Security vs usability | How often to ask for Face ID; how long a session lasts; how strict a password rule is |
| Privacy vs personalisation and diagnosis | Fewer analytics events and shorter retention mean less to personalise with and less to debug with |
| Availability vs freshness | Showing cached data offline means sometimes showing stale data; letting people edit offline means conflicts to merge later |
| Performance vs maintainability | Layers and generic abstractions cost a little speed; a hand-tuned fast path costs readability |
| Performance vs battery and data | Prefetching the next page makes scrolling instant and wastes downloads that are never viewed |
| Security vs availability | Certificate pinning, strict time windows or account lockouts can turn away legitimate users |
| Flexibility vs simplicity | Server-driven, configurable screens change without a release, but are harder to test and reason about |
| Time to market vs everything | Shipping in March may mean less of all of the above, on purpose |

## Four ways to resolve a conflict

When two qualities collide, you have more choices than picking a winner.

1. **Prioritise.** Decide which quality wins, based on what the product is for, and write it down. "For this banking app, security beats convenience; for this recipe app, convenience wins." A priority agreed in advance turns an argument into a lookup.
2. **Separate by context.** Apply the strict version only where it matters. Ask for Face ID before a transfer over £250, not to view a balance. Pin certificates for the payments host, not the image CDN. Most conflicts are much smaller than they first appear once you ask *where* each quality really matters.
3. **Find a design that weakens the conflict.** Sometimes a better design gives you most of both. Face ID made strong authentication cheap in usability. Stale-while-revalidate, with the data's age on screen, gives availability with honesty about freshness. On-device processing gives personalisation without uploading personal data.
4. **Make it a dial.** Turn the trade-off into a parameter (a lock grace period, a cache lifetime, how far ahead to prefetch), start with a sensible value, measure, and tune it. Put dials you expect to change in remote configuration, so tuning doesn't need a release.

<Callout kind="analogy">

A car's suspension trades comfort against handling. Manufacturers don't pick one for every driver: they prioritise by model (a family car against a sports car), separate by context (a sport mode for the motorway), invent better designs (adaptive dampers) and leave a dial for the driver. Your app's qualities work the same way.

</Callout>

## Worked example: when should a banking app lock?

A banking app locks itself and asks for Face ID when it comes back from the background. How long may it stay in the background before it locks? That **grace period** is a dial between security and usability:

```visual states
title: A banking app's lock, with a grace period
states:
  - { id: active, label: Unlocked, at: [0, 0] }
  - { id: background, label: In background, at: [1, 0] }
  - { id: locked, label: Locked, at: [2, 0] }
  - { id: authenticating, label: Face ID, at: [2, 1] }
initial: active
transitions:
  - [active, background, didEnterBackground]
  - [background, active, willEnterForeground, within grace]
  - [background, locked, graceExpired]
  - [locked, authenticating, willEnterForeground]
  - [authenticating, active, succeeded]
  - [authenticating, locked, failed]
intro: "The customer is in the app, unlocked."
events:
  - { event: didEnterBackground, say: "They switch to Messages to read a one-time code. The grace timer starts." }
  - { event: willEnterForeground, say: "They're back within the grace period, so no Face ID: the transfer they were making carries on." }
  - { event: didEnterBackground, say: "Later they put the phone down with the app open." }
  - { event: graceExpired, say: "The grace period passes, so the app locks while it's in the background, and covers its content in the app switcher." }
  - { event: willEnterForeground, say: "Whoever picks up the phone next sees the lock, not the balance." }
  - { event: failed, say: "A failed attempt keeps it locked." }
  - willEnterForeground
  - { event: succeeded, say: "The owner authenticates and is back where they were." }
```

Look at the two ends of the dial:

- **Zero grace** (lock on every switch) is the most secure, and it breaks the one-time-code flow: the customer leaves to read an SMS, comes back to a Face ID prompt mid-transfer, and does it again for the next code.
- **Never lock** is the most convenient, and anyone who borrows the unlocked phone can move money.

The usual resolution combines strategies. **Separate by context**: lock quickly (say, after a minute) because money is at stake, but ask again before any payment over a threshold whatever the timer says. **Weaken the conflict**: Face ID makes the prompt quick. **Keep it a dial**: put the grace period in remote configuration, watch abandonment of transfers and fraud reports, and tune it.

## Trade-offs

The resolution strategies have their own costs:

| Strategy | Strength | Cost | When it wins |
| --- | --- | --- | --- |
| Prioritise | Fast, consistent decisions | The losing quality can be neglected everywhere, even where it was cheap to keep | Clear product priorities, such as banking or a children's app |
| Separate by context | Each part gets the right balance | More rules, more combinations to test | The conflict only really matters in a few places |
| Redesign to weaken it | Most of both qualities | Design and build effort, sometimes new technology | A core conflict you'll live with for years |
| Make it a dial | Decide later, with data | Needs measurement, and a dial nobody owns never gets tuned | You're unsure where the balance is, and it can change safely |

<Callout kind="interview">

**Say the tension out loud, then the decision:** "Showing cached data offline means it can be stale. Availability matters more here than freshness, so I'll show the cache with its age and refresh in the background. If this were a trading app, I'd make the opposite call." Naming what you gave up, and when you'd decide differently, *is* the answer.

**Ask:** "If these two conflict, which matters more to the business?" Interviewers often want you to ask rather than assume.

**Red flags:** claiming a design has no downsides; resolving every conflict the same way; "we'll make it configurable" for everything, with no default and no owner.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: biometrics-only locks people out">

`LAPolicy.deviceOwnerAuthenticationWithBiometrics` accepts only Face ID or Touch ID. People who can't use biometrics (some disabilities, a mask, a broken sensor) are stuck, which trades accessibility away for no real security gain. `.deviceOwnerAuthentication` falls back to the device passcode. Face ID also needs an `NSFaceIDUsageDescription` entry in the Info.plist.

</Callout>

```swift check
import LocalAuthentication

/// Face ID or Touch ID, falling back to the device passcode, so nobody is locked out
func unlockAccounts() async -> Bool {
    let context = LAContext()
    do {
        return try await context.evaluatePolicy(.deviceOwnerAuthentication, localizedReason: "Unlock your accounts")
    } catch {
        return false
    }
}
```

The design exercise *Quality scenarios for a transit ticket* turns on one conflict above all: codes that resist screenshots (security) and still work with no network at either end (availability). Before you read the model answer, write down which of the four strategies you'd use for it.

```cards

  back: "Prioritise one; separate by context (strict only where it matters); redesign to weaken the conflict; make it a dial and tune it with data."
```

```quiz
- id: q1

  type: mcq

  answer: 2
  explain: "The conflict depends on context (network type, Low Data Mode), so separate by context and keep the depth tunable. Removing it loses the performance win; ignoring it or prefetching more makes the conflict worse."
```
