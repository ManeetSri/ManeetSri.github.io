## Why it matters

People hand an app two things: their data and their attention. **Security** and **privacy** decide whether the data is safe, from attackers and from misuse by the app itself. **Usability** and **accessibility** decide whether everyone, including the one in six people with a disability, can get done what they came to do. All four are enforced from outside as well as inside: by App Review, by privacy and accessibility law, and by users who leave. And all four are far cheaper designed in than added later, which is why interviewers notice when you raise them unprompted.

## Security: protecting against people who mean harm

Security is the system's ability to protect information and behaviour against deliberate attack. The classic summary is **CIA**:

- **Confidentiality:** only the right people can read the data.
- **Integrity:** nobody can change it without being noticed.
- **Availability:** attackers can't stop legitimate users from using it.

ISO 25010 adds **authenticity** (you know who you're talking to), **accountability** (actions can be traced to who did them), **non-repudiation** (they can't deny it later) and, since its 2023 revision, **resistance** to attack.

Security design starts with **threats**: who would attack, what do they want, and where can they reach it? A mobile app has three places to defend, and each has its own tools:

The rules that come out of this picture:

- **On the device:** tokens and keys in the Keychain, never in `UserDefaults` (a plist in the app's container, included in backups). Choose the Keychain accessibility class on purpose: `WhenUnlockedThisDeviceOnly` for the most sensitive items, `AfterFirstUnlock` for tokens a background refresh must read. Use stronger file protection for sensitive files.
- **On the network:** HTTPS everywhere, which App Transport Security enforces by default. Certificate pinning (declared with `NSPinnedDomains` since iOS 14) also defeats compromised certificate authorities and inspection proxies, at the cost of an app that stops working if the certificates rotate unexpectedly.
- **On the server:** **never trust the client.** Prices, discounts, entitlements and limits are checked server-side. App Attest (in the DeviceCheck framework) lets the server check that a request comes from a genuine copy of your app, which raises the cost of abuse but doesn't replace server-side checks.

D49 goes much deeper; for now, the habit is to name the threat before choosing the defence.

## Privacy: taking only what you need

Privacy is not the same as security. Security keeps attackers out; privacy limits what **you** collect, keep and share, even if your security is perfect. A perfectly secure app that uploads everyone's contact list is not private.

The principles are simple to state and demanding to design for:

- **Minimise:** collect only what the feature needs, at the lowest precision that works (approximate location for weather, not precise).
- **Process on the device** where you can: Vision, Natural Language and Core ML run locally, so the data never leaves the phone.
- **Limit retention:** delete what you no longer need, on a schedule.
- **Be transparent and give control:** explain why you ask, and let people export and delete their data. App Review requires apps that let people create an account to let them delete it from within the app.

iOS turns these into concrete requirements. Permissions need a purpose string. **App Tracking Transparency** (iOS 14.5) requires permission before tracking people across other companies' apps and websites. Every app has privacy "nutrition labels" on the App Store. And since May 2024, apps and listed third-party SDKs must ship a **privacy manifest** (`PrivacyInfo.xcprivacy`) declaring the data they collect and their reasons for using "required reason" APIs such as `UserDefaults`, file timestamps and disk space.

The best privacy design often avoids the question entirely. To let someone pick a profile photo, you don't need access to their photo library at all: the system picker runs outside your app and hands you only the photo they chose, so there's no permission prompt.

```swift check ios
import PhotosUI
import SwiftUI

struct AvatarPicker: View {
    @State private var selection: PhotosPickerItem?
    @State private var avatar: Image?

    var body: some View {
        PhotosPicker(selection: $selection, matching: .images) {
            (avatar ?? Image(systemName: "person.crop.circle"))
                .resizable()
                .scaledToFill()
                .frame(width: 96, height: 96)
                .clipShape(Circle())
        }
        .accessibilityLabel("Profile photo")
        .accessibilityHint("Choose a photo from your library")
        .onChange(of: selection) { _, item in
            Task {
                // Only the chosen photo crosses into the app: no library permission, no prompt
                guard let data = try? await item?.loadTransferable(type: Data.self),
                      let picked = UIImage(data: data) else { return }
                avatar = Image(uiImage: picked)
            }
        }
    }
}
```

## Usability: getting things done without friction

Usability is how well people can achieve their goals with the app: effectively, quickly and with satisfaction. The 2023 ISO model renames it *interaction capability* and covers learnability, ease of operation, protection from user error, engagement and help. It's measured with tasks: the share of people who complete sign-up, the time it takes, the errors they make.

Usability looks like a design-team concern, but several parts of it are architectural:

- **Response time.** About 0.1 s feels instant, about 1 s keeps someone's flow, and beyond about 10 s they lose attention (Jakob Nielsen's long-standing limits). Meeting the first needs **optimistic updates**: show the like immediately and reconcile with the server later, which needs a model that can roll back.
- **Error protection.** "Undo" is friendlier than "Are you sure?", but it needs commands that can be reversed (`UndoManager`, or a soft delete on the server that can be restored).
- **Not losing work.** Drafts saved as people type, state restored after the app is killed, actions queued offline instead of failing.
- **Following the platform.** Standard navigation, swipe back, share sheets and system controls behave as people expect, and they come with accessibility built in.

## Accessibility: usable by everyone

The WHO estimates 1.3 billion people, about one in six, live with a significant disability, and everyone has situational limits: bright sun, one hand on a bus handle, a noisy street. iOS has deep support: **VoiceOver**, **Dynamic Type** (including much larger accessibility sizes), Voice Control, Switch Control, Reduce Motion, Increase Contrast and Bold Text. Accessibility is also law: the **European Accessibility Act** has applied to many consumer services in the EU, including e-commerce, banking and passenger transport, since 28 June 2025, and WCAG 2.2 at level AA is the usual yardstick.

Architecturally, accessibility is cheapest **in shared components**. Build it once into the design system's button, row and form field (labels, traits, hit targets of at least 44 × 44 points, layouts that reflow at large text sizes), and every screen inherits it. Retrofitting it screen by screen, after launch, costs many times more. A row that reflows when the text is large:

```swift check ios
import SwiftUI

struct PriceRow: View {
    let title: String
    let price: Decimal
    @Environment(\.dynamicTypeSize) private var typeSize

    var body: some View {
        // Side by side normally; stacked at accessibility sizes, so nothing is truncated
        let layout = typeSize.isAccessibilitySize
            ? AnyLayout(VStackLayout(alignment: .leading, spacing: 4))
            : AnyLayout(HStackLayout())
        layout {
            Text(title)
            Spacer(minLength: 8)
            Text(price, format: .currency(code: "GBP"))
                .monospacedDigit()
        }
        .font(.body)
        .accessibilityElement(children: .combine)
    }
}
```

Test it like any other quality: the Accessibility Inspector during development, and Xcode's automated accessibility audits (`performAccessibilityAudit()` in UI tests, from Xcode 15) on every build. D53 covers the architecture in depth.

## Trade-offs

These four qualities pull against each other and against everything else; the next lesson is about exactly that. Here are the decisions you'll meet most often:

| Decision | Improves | Costs | When it wins |
| --- | --- | --- | --- |
| Keychain item `WhenUnlockedThisDeviceOnly` | Security: no backups, no access while locked | Background tasks can't read it; a new phone means signing in again | Credentials for money, health or identity |
| Biometric re-authentication on open | Security against a borrowed or stolen phone | Usability: a step on every visit | Banking, health, password managers |
| Certificate pinning | Security against interception | Operability: a botched certificate rotation breaks every installed copy | High-value targets with tight control of their certificates |
| On-device processing | Privacy; works offline | Battery and app size; only the models a phone can run | Classification, OCR, suggestions on personal data |
| Optimistic updates | Usability: feels instant | Reliability work: rollback and reconciliation | Likes, toggles, reordering; not payments |
| Custom controls instead of system ones | Brand and differentiation | Accessibility, which must be rebuilt by hand | Rarely; when the control is the product |

<Callout kind="interview">

**Say:** "Secrets live in the Keychain; the server authorises every request, because the client can't be trusted; we collect only what the feature needs, and process on the device where we can." On accessibility: "It goes into the design system's components, so every screen gets VoiceOver labels and Dynamic Type for free."

**Ask:** "What's the most sensitive data here, and are there legal requirements: health, payments, children, the EU?" The answer changes storage, logging and analytics.

**Red flags:** tokens in `UserDefaults`; checking prices or entitlements only in the app; asking for every permission at first launch; personal data in analytics events or logs; "we'll do accessibility after launch".

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the app switcher and the Keychain remember more than you think">

When the app moves to the background, iOS takes a **snapshot** of the screen for the app switcher, so a banking balance or a medical record can sit there in plain view. Cover sensitive screens when `scenePhase` leaves `.active`. And **Keychain items survive deleting the app**: someone who reinstalls may find themselves still signed in with an old token. Many apps keep a "has launched before" flag in `UserDefaults` (which *is* deleted with the app) and clear their Keychain items on the first launch after a reinstall.

</Callout>

## Practice

The design exercise *Quality scenarios for a transit ticket* is built on this lesson's tensions: a code that must resist screenshots, verify with no network, reveal nothing personal and work with VoiceOver at a crowded gate. Write a scenario for each of the four qualities before you design anything.

```cards
- id: client-not-boundary
  front: "Why is the app never the security boundary?"
  back: "Anyone can call your API with a modified app or a script. Prices, entitlements and permissions must be checked on the server for every request."
- id: privacy-vs-security
  front: "How is privacy different from security?"
  back: "Security keeps attackers out. Privacy limits what you collect, keep and share, even with perfect security: minimise, process on device, limit retention, give control."
- id: secrets-storage
  front: "Where do tokens and keys belong on iOS, and why not UserDefaults?"
  back: "In the Keychain, with a deliberately chosen accessibility class. UserDefaults is a plain plist in the app container and is included in backups."
- id: accessibility-in-components
  front: "Where is accessibility cheapest to build?"
  back: "In the design system's shared components: labels, traits, 44-point targets and Dynamic Type reflow built once, inherited by every screen."
```

```quiz
- id: q1
  type: sort
  prompt: "Which quality does each requirement mainly serve?"
  buckets: [Security, Privacy, Usability, Accessibility]
  items:
    - ["Refresh tokens are unreadable from a backup of the phone", 0]
    - ["Location is requested only while the map is open, at approximate precision", 1]
    - ["A deleted message can be restored with Undo for 10 seconds", 2]
    - ["Every control has a VoiceOver label and works at the largest text size", 3]
    - ["The server rejects an order whose price was changed by the client", 0]
    - ["Photos are classified on the device and never uploaded for analysis", 1]
  explain: "Security resists attackers; privacy limits what the app itself collects and shares; usability lets people succeed without friction; accessibility makes that true for people using assistive technology or larger text."
- id: q2
  type: mcq
  prompt: "Your app refreshes its access token in a background task, sometimes while the phone is locked. Where should the refresh token live?"
  options:
    - "UserDefaults, so the background task can always read it"
    - "The Keychain, with WhenUnlockedThisDeviceOnly"
    - "The Keychain, with AfterFirstUnlockThisDeviceOnly"
    - "A file in the Documents directory"
  answer: 2
  explain: "It's a secret, so the Keychain. WhenUnlocked would block the background refresh while the phone is locked; AfterFirstUnlock allows it once the phone has been unlocked since starting, and ThisDeviceOnly keeps it out of backups. UserDefaults and Documents aren't meant for secrets."
- id: q3
  type: mcq
  prompt: "A shopping app applies discount codes in the app, then sends the final price to `POST /orders`. What's the real problem?"
  options:
    - "Discount logic should be in a separate Swift package"
    - "Anyone can send `POST /orders` with any price; the server must work out the price itself"
    - "The discount should be cached for offline use"
    - "The request should use a PUT instead of a POST"
  answer: 1
  explain: "The client is never the security boundary. A modified app, a proxy or a script can send any price. The app can show an estimate, but the server must compute and validate the price it charges."
- id: q4
  type: multi
  prompt: "You're adding \"choose a profile photo\". Which choices respect privacy?"
  options:
    - "Use the system PhotosPicker, which needs no library permission"
    - "Ask for full library access at first launch, in case it's needed later"
    - "Strip location metadata before uploading the photo"
    - "Upload the whole camera roll so people can choose on the web too"
  answer: [0, 2]
  explain: "The picker hands over only the chosen photo, with no prompt. Photos often carry precise location in their metadata, which a profile photo doesn't need. Asking for everything up front, or uploading more than the feature needs, breaks data minimisation."
- id: q5
  type: truefalse
  prompt: "If an app's security is excellent, it's automatically good for privacy."
  answer: false
  explain: "Security stops attackers; it says nothing about what the app itself collects, keeps or shares. An app can encrypt everything perfectly and still upload far more than it needs."
- id: q6
  type: mcq
  prompt: "A team of eight is adding accessibility to an app with 60 screens. Where should they start?"
  options:
    - "Audit and fix each screen in order of traffic"
    - "Build labels, traits, target sizes and Dynamic Type into the shared components, then fix screens that bypass them"
    - "Wait for user complaints and fix those screens"
    - "Add a separate simplified \"accessible mode\" of the app"
  answer: 1
  explain: "Shared components carry accessibility to every screen that uses them, so the fix scales. Screen-by-screen work is still needed for custom layouts, but last. A separate mode doubles the maintenance and usually falls behind."
```
