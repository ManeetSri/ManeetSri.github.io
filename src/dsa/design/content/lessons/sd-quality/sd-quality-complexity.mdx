## Why it matters

Complexity is the root cause behind most of the maintainability problems you met earlier: changes that take a week, bugs in code nobody touched, new engineers who need months. But not all complexity can be removed. Some of it *is* the problem: time zones are complicated because time is complicated. Telling the complexity you must manage from the complexity you created is how you spend effort in the right place, and in an interview it's how you defend a simple design, or justify a complicated one.

## Essential and accidental complexity

In his 1986 essay *No Silver Bullet*, Fred Brooks split software complexity into two kinds:

- **Essential complexity** belongs to the problem. Any correct solution has to deal with it, whatever tools you use.
- **Accidental complexity** comes from how we chose to solve it: our tools, frameworks, structure and habits. It could, in principle, be removed.

Brooks's point was that tools had already removed much of the accidental kind, so no new tool would make software ten times easier to build: what's left is mostly essential. The practical lesson for you is the reverse: in a real codebase there's usually a *lot* of accidental complexity, and it's the part you can do something about.

| Essential (it's the problem) | Accidental (it's the solution) |
| --- | --- |
| Time zones, daylight saving and calendars in a booking app | Converting time zones in views, view models *and* the API layer |
| Two devices editing the same note offline | Three different ways of saving a note, written by three teams |
| Payment states: authorised, captured, refunded, partly refunded, disputed | Payment state tracked in five booleans that can contradict each other |
| The app can be suspended and killed at any moment | Work that assumes it will finish because "it's usually quick" |
| Text that must fit at every Dynamic Type size, in 30 languages | A custom layout engine where a stack would do |
| Networks that drop and reorder requests | A network wrapper around a wrapper around `URLSession` |

You can't delete essential complexity; you can only decide **where it lives**. The good answer is almost always: in one place, behind a simple interface, with thorough tests. All the calendar logic in one `BookingCalendar` type that the rest of the app calls with plain questions ("is this slot bookable?") is manageable. The same logic scattered through every layer is not. D02 develops this as *deep modules*: a lot of functionality behind a small interface.

## How complexity shows up

John Ousterhout's *A Philosophy of Software Design* defines complexity as anything about a system's structure that makes it hard to understand and change, and names three symptoms you can spot in a code review:

- **Change amplification:** a simple change needs edits in many places.
- **Cognitive load:** how much you need to know before you can make a change safely.
- **Unknown unknowns:** it isn't obvious what you need to change, or what you need to know. This is the worst of the three, because you find out in production.

Its two causes are **dependencies** (a piece of code can't be understood or changed on its own) and **obscurity** (important information isn't visible where it's needed). Watch change amplification happen when a product manager asks for one small thing:

## State is the biggest source of accidental complexity

In *Out of the Tar Pit* (2006), Ben Moseley and Peter Marks argued that most accidental complexity comes from **state**, and especially from state that's derived from other state and kept in step by hand. iOS code is full of it: `items` stored next to `isEmpty`, `selectedID` next to `selectedItem`, a cached `filteredResults` that someone forgets to recompute. Each copy is a promise that every code path will update both, and eventually one doesn't:

```swift run
import Foundation

struct LineItem {
    let name: String
    let pence: Int
    var quantity: Int
}

// Stores the total, so every mutation must remember to update it
struct StoredTotalCart {
    var items: [LineItem] = []
    var total = 0

    mutating func add(_ item: LineItem) {
        items.append(item)
        total += item.pence * item.quantity
    }

    mutating func setQuantity(_ quantity: Int, at index: Int) {
        items[index].quantity = quantity   // the total is now wrong, and nothing says so
    }
}

// Derives the total, so it can't disagree with the items
struct DerivedTotalCart {
    var items: [LineItem] = []
    var total: Int { items.reduce(0) { $0 + $1.pence * $1.quantity } }

    mutating func add(_ item: LineItem) { items.append(item) }
    mutating func setQuantity(_ quantity: Int, at index: Int) { items[index].quantity = quantity }
}

var stored = StoredTotalCart()
var derived = DerivedTotalCart()
for item in [LineItem(name: "Coffee", pence: 350, quantity: 1), LineItem(name: "Croissant", pence: 280, quantity: 1)] {
    stored.add(item)
    derived.add(item)
}
stored.setQuantity(3, at: 0)
derived.setQuantity(3, at: 0)

print("Stored total: £" + String(format: "%.2f", Double(stored.total) / 100))
print("Derived total: £" + String(format: "%.2f", Double(derived.total) / 100))
```

```output
Stored total: £6.30
Derived total: £13.30
```

The stored version is off by £7, and no test of `add` alone would notice. The fix removes state instead of adding a check: compute derived values, and keep one **source of truth** for each fact (D19 is about exactly this). Sometimes a cached value is worth it, because it's expensive and measured to be a bottleneck. Then make it private, update it in exactly one place, and treat it as the deliberate, contained piece of accidental complexity it is.

## Where accidental complexity comes from

It rarely arrives in one decision. It accumulates:

- **Speculative generality:** abstractions for futures that never come, such as a plugin system for one plugin or a protocol with one conformer "in case we swap it". (D05 covers YAGNI.)
- **Two ways to do one thing:** half the app on Combine, half on async/await, a few screens on delegates. Every engineer must know all of them.
- **Workarounds that outlive their cause:** a delay added for an iOS 15 bug, still there on iOS 18.
- **Frameworks adopted for one feature:** a reactive library, an architecture framework or a dependency injection container where a few initialisers would do.
- **Copies of state,** as above.

A useful test: explain the design to a new teammate. The parts you'd explain by describing the *problem* ("bookings can span a daylight-saving change, so…") are essential. The parts you'd explain by apologising ("we have two image caches because…") are accidental.

## Trade-offs

Some accidental complexity is worth paying for, because it buys something the team needs. The question is always whether you're getting that something:

| Choice | Complexity it adds | What it buys | Worth it when |
| --- | --- | --- | --- |
| A reactive framework (Combine) | A new mental model; long chains that are hard to debug | Composing streams of events over time | Many live streams: search as you type, sockets, sensors |
| A dependency injection container | Indirection; wiring errors at runtime instead of compile time | Wiring dozens of modules in one place | A very large app; otherwise pass dependencies to initialisers |
| A strict architecture (VIPER, TCA) | Several types and files per screen | The same shape everywhere; testable by construction | Large teams that need consistency; not five screens |
| Caching derived state | Keeping copies in step | Speed | A measured hot path, with one place that updates it |
| Code generation (OpenAPI, asset catalogues) | A build step and generated code to understand | No hand-written boilerplate drifting from the source | Large APIs or many assets |

<Callout kind="interview">

**Say where the essential complexity is, and keep the rest simple:** "The hard part of this booking app is time zones and availability rules, so that lives in one well-tested module. The screens around it are plain SwiftUI views and view models." When you do add structure, say what it buys: "I'd use a coordinator here because the flow branches five ways, not because every screen needs one."

**Ask:** "What's the hardest part of this domain?" The answer is where the essential complexity is.

**Red flags:** patterns for their own sake ("I'd use VIPER" for a settings screen); a layer per buzzword; calling complexity essential to avoid simplifying it; or the opposite, waving away genuinely hard parts like sync conflicts as "just merge them".

</Callout>

<Callout kind="gotcha" title="iOS gotcha: @State copies are a second source of truth">

`@State` takes its initial value once, when the view's identity is created. A child view that copies a value from its parent into `@State` in its initialiser keeps the first value and silently ignores every later change from the parent. That's derived state again, with SwiftUI as the cache. Pass a `Binding`, read the parent's `@Observable` model directly, or keep the state in one place and pass it down.

</Callout>

## Practice

The architecture review *A workout streak that nobody can test* has accidental state at its heart: the streak lives in memory *and* in `UserDefaults`, but only one copy is ever read. As you review it, sort each problem into essential (calendars really are hard) or accidental (nobody needed two copies).

```cards
- id: essential-vs-accidental
  front: "What's the difference between essential and accidental complexity?"
  back: "Essential complexity belongs to the problem and any solution must handle it (time zones, sync conflicts). Accidental complexity comes from how we solved it (wrappers, duplicated state, unneeded frameworks) and can be removed."
- id: ousterhout-symptoms
  front: "What are Ousterhout's three symptoms of complexity?"
  back: "Change amplification (one change, many edits), cognitive load (much to know before changing), and unknown unknowns (not obvious what to change). Caused by dependencies and obscurity."
- id: derived-state
  front: "Why is stored derived state accidental complexity, and what's the fix?"
  back: "Every copy must be kept in step by hand, and eventually one path forgets. Compute derived values from one source of truth; cache only measured hot paths, updated in one place."
- id: where-essential-lives
  front: "If you can't remove essential complexity, what can you do with it?"
  back: "Decide where it lives: concentrate it in one module behind a simple interface, with thorough tests, instead of spreading it through every layer."
```
