## Why it matters

"It depends" is the most honest answer in system design and, on its own, the least useful. Interviewers want to hear *what* it depends on, which way you'd go here, and what would change your mind. At work, decisions made by whoever argues loudest get argued again every quarter. A **decision matrix** makes the reasoning visible: it shows where people really disagree (usually about priorities, not facts), whether the winner is a clear winner, and it leaves a record for the next person to ask "why did we do this?"

## From "it depends" to a decision

A good answer to any design choice has three parts:

1. **What it depends on:** the two or three things that would change the answer.
2. **The call, for this case:** which option, and the reason taken from the requirements.
3. **The flip condition:** what would have to be different for you to choose otherwise.

Compare two answers to "Should this notes app store its data in SwiftData or in SQLite through GRDB?":

- *Weak:* "It depends. Both have pros and cons. SwiftData is newer, GRDB is more mature."
- *Strong:* "It depends on how much data a heavy user has, whether we need full-text search, and how the team feels about a third-party dependency. We said 50,000 notes with search, so I'd pick GRDB for SQLite's full-text search and explicit migrations. If notes stayed in the hundreds, or a dependency was ruled out, SwiftData would be simpler and good enough."

The strong answer is short, and it's built from exactly the parts of a decision matrix: criteria, weights, scores and the sensitivity of the result. On a whiteboard you do it in your head. For a decision your team will live with for years, write it down.

## Building a weighted decision matrix

1. **Frame the decision.** One question, two to four real options. Include "keep what we have" when there's something to keep.
2. **Apply the must-haves first.** Constraints and hard requirements are **knockouts**: an option that fails one is out before any scoring. A weighted total must never let five good scores buy back a fatal one.
3. **Choose the criteria.** Use the quality attributes that matter for this decision *and differ between the options*. A criterion every option scores 4 on adds nothing. Four to seven criteria is plenty.
4. **Agree the weights before scoring.** Weights come from the product's priorities. Set them first, together, so nobody tunes them afterwards to make their favourite win.
5. **Score each option,** usually 1 to 5, with a one-line reason for each score. Where you're guessing, run a spike or a benchmark.
6. **Compute weighted totals:** Σ(weight × score) ÷ Σ weight, so totals stay on the 1–5 scale.
7. **Test the sensitivity.** Would the winner change if one weight moved by, say, 25%? The criteria that flip it are where the real discussion is.
8. **Record the decision:** the context, the options, the matrix, the choice and its consequences. D09 introduces the usual format, an architecture decision record.

### A worked example

An offline-first notes app. Heavy users have about 50,000 notes, search must be instant, the schema will change for years, and the team of three knows SwiftUI well and SQL a little. The options are SwiftData, Core Data, SQLite through the open-source GRDB library, and plain JSON files. The scores below are this team's judgement, each with a reason:

| Criterion (weight) | SwiftData | Core Data | GRDB (SQLite) | JSON files |
| --- | --- | --- | --- | --- |
| Query and search speed at 50k notes (3) | 3: fewer tools for tuning large fetches | 4: mature, well-understood performance | 5: SQLite's built-in full-text search | 1: load everything to search |
| Migration safety over years (3) | 3: schema versioning works, with fewer escape hatches | 4: mature migration tooling | 5: explicit, versioned, testable migrations | 2: versioning by hand |
| Testability (2) | 4: in-memory configuration | 3: in-memory stores, more setup | 5: in-memory databases, plain SQL | 4: a temporary directory |
| Team familiarity (1) | 4 | 3 | 2 | 5 |
| No third-party dependency (1) | 5 | 5 | 1 | 5 |
| **Weighted score** | **3.50** | **3.80** | **4.30** | **2.70** |

GRDB wins clearly, for the reasons the requirements put first. Now the sensitivity: how much would the priorities have to change to flip it? The code below scores the matrix, then raises the weight on "no third-party dependency" one step at a time, leaving everything else alone:

```swift run
import Foundation

struct Option {
    let name: String
    let scores: [Double]   // speed, migrations, testability, familiarity, no dependency
}

let options = [
    Option(name: "SwiftData", scores: [3, 3, 4, 4, 5]),
    Option(name: "Core Data", scores: [4, 4, 3, 3, 5]),
    Option(name: "GRDB", scores: [5, 5, 5, 2, 1]),
    Option(name: "JSON files", scores: [1, 2, 4, 5, 5]),
]
let weights: [Double] = [3, 3, 2, 1, 1]

func score(_ option: Option, _ weights: [Double]) -> Double {
    zip(option.scores, weights).reduce(0) { $0 + $1.0 * $1.1 } / weights.reduce(0, +)
}

func winner(_ weights: [Double]) -> String {
    options.max { score($0, weights) < score($1, weights) }!.name
}

for option in options {
    print(option.name, String(format: "%.2f", score(option, weights)))
}
print("Winner:", winner(weights))

for weight in [1.0, 2, 3, 4, 5] {
    var nudged = weights
    nudged[4] = weight
    print("No-dependency weight \(Int(weight)): \(winner(nudged))")
}
```

```output
SwiftData 3.50
Core Data 3.80
GRDB 4.30
JSON files 2.70
Winner: GRDB
No-dependency weight 1: GRDB
No-dependency weight 2: GRDB
No-dependency weight 3: Core Data
No-dependency weight 4: Core Data
No-dependency weight 5: Core Data
```

So "it depends" now has a precise meaning: **if avoiding a third-party dependency matters as much as query speed, choose Core Data; otherwise GRDB.** That's a question you can put to the team, or the interviewer, directly. A 25% change in any one weight doesn't flip it, so it isn't a fragile decision; you'd need a real change in priorities.

Two knockouts would short-cut the whole matrix:

- **"Must support iOS 16."** SwiftData needs iOS 17, so it's out before scoring.
- **"No new third-party code without a security review we can't get this year."** GRDB is out, and Core Data wins.

With familiarity and independence weighted highest, SwiftData edges ahead: a small team that values simplicity over raw capability. Neither answer is wrong. The matrix's job is to show which priorities lead to which answer, so the team argues about the priorities.

## Where matrices go wrong

- **Weights fitted to a favourite.** If the weights appear after the scores, the matrix is decoration. Agree them first; better still, have two people score independently and discuss where they differ.
- **False precision.** 4.31 against 4.27 is a tie. Treat totals within a few tenths as equal, and let sensitivity, risk or a spike decide.
- **Double counting.** "Performance" and "query speed" measure the same thing; together they give it twice the weight you meant.
- **Too many criteria.** Fifteen criteria average each other into mush. Keep the few that differ and matter.
- **Scores without evidence.** "GRDB: 5 for speed" needs a reason; for anything uncertain, an afternoon's benchmark beats an hour's debate.
- **Ceremony for small decisions.** Some decisions are cheap to reverse: a layout, a library behind your own protocol, a flag-guarded feature. Decide those quickly and move on. Spend the matrix on **one-way doors**, the decisions that are expensive to undo: the on-device data model, a public API contract, a sync protocol, the minimum OS.

## Other tools you'll meet

- **Pugh matrix:** score each option against a baseline option as better, same or worse (+1, 0, −1) on each criterion. Quicker, and good for early, rough comparisons.
- **Pros and cons per option:** fine for two options and a quick call; poor at showing *how much* each point matters.
- **A spike or prototype:** build the risky part in a day or two. The best way to replace a guessed score with a measured one.
- **ATAM** (the SEI's Architecture Tradeoff Analysis Method): a structured review that uses the quality-attribute scenarios and utility tree from [Functional and non-functional requirements](/design/learn/sd-quality-requirements) to find each design's sensitivity points and trade-off points. Heavyweight; used for large systems.

## Trade-offs

| Method | Speed | Rigour | Leaves a record? | When it wins |
| --- | --- | --- | --- | --- |
| Gut call by an experienced engineer | Minutes | Low, and invisible | No | Two-way doors; low stakes |
| Pros and cons | An hour | Medium | Somewhat | Two options, one clear priority |
| Weighted decision matrix | A few hours | Good: priorities and scores are explicit | Yes | Several options, several qualities, a one-way door |
| Spike or prototype | Days | High for the questions it answers | If written up | One uncertain score that decides everything |
| Formal review (ATAM) | Days to weeks | Highest | Yes | Large, long-lived systems with many stakeholders |

<Callout kind="interview">

**Say the three parts:** "It depends on data size, search and the team's appetite for a dependency. With 50,000 notes and instant search, I'd take GRDB. If a dependency were off the table, Core Data." In a whiteboard round, a quick spoken matrix of three criteria is plenty: "SwiftData is simpler, GRDB is faster and safer to migrate, and we said speed and migrations matter most."

**Ask:** "Which of these matters most to you: speed, simplicity or avoiding dependencies?" It's the swing criterion, so asking it shows you've found the crux.

**Red flags:** "it depends" with no follow-up; claiming one option is best in every respect; a fifteen-row matrix in a 45-minute interview; treating a 0.1 difference as decisive.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: check the platform knockouts before you score">

Many promising options fail a constraint you already have. SwiftData and the Observation framework need iOS 17; some newer SwiftUI APIs need iOS 18. A library that hasn't adopted Swift 6's strict concurrency can bury your build in `Sendable` warnings or force `@preconcurrency` imports. A third-party SDK may lack a privacy manifest. Check minimum OS, language mode and App Store requirements first: they're knockouts, not low scores.

</Callout>

## Practice

The kata *Weighted decision matrix* builds the scorer behind this lesson: weighted means, knockouts that eliminate an option whatever its total, deterministic tie-breaking, and the sensitivity check that lists the criteria a 25% change would flip the decision on. Write it, then feed it a real decision from your own work.

```cards
- id: three-part-it-depends
  front: "What are the three parts of a useful \"it depends\"?"
  back: "What it depends on; the call for this case and why; and the flip condition: what would make you choose differently."
- id: knockouts-first
  front: "Why apply must-have criteria before scoring?"
  back: "A weighted total lets good scores buy back a fatal one. Constraints like minimum OS or a ban on dependencies eliminate options outright."
- id: weights-before-scores
  front: "Why agree weights before scoring the options?"
  back: "Weights set afterwards tend to be tuned to make a favourite win. Weights come from the product's priorities, and agreeing them first moves the debate to where it belongs."
- id: sensitivity
  front: "What does a sensitivity check on a decision matrix tell you?"
  back: "Whether a small change in one weight (say 25%) flips the winner. If none does, the decision is robust; if one does, that criterion is the conversation to have."
```
