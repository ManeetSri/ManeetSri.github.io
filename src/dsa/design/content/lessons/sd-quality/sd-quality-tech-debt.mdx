## Why it matters

Every codebase has technical debt. What separates healthy teams from struggling ones is whether the debt was **chosen and managed** or **accumulated by accident**. A senior engineer is expected to see debt, say what it costs in terms the business understands, take it on deliberately when that's the right call, and pay it down without stopping the roadmap. Expect it in interviews as "how do you balance refactoring against features?" and "tell me about some technical debt you dealt with".

## The cost of change

In 1981 Barry Boehm published data showing that the later a defect is found, the more it costs to fix: a mistake caught while writing requirements is cheap, the same mistake found in production can cost many times more, because so much has been built on top of it. (The exact multipliers are debated; the direction isn't.) In 1999 Kent Beck argued, with Extreme Programming, that good practice can flatten that curve: with automated tests, small changes, continuous integration and constant refactoring, the cost of a change grows slowly, which is what makes building software iteratively affordable at all.

For apps, the end of the curve is steeper than for servers:

- A fix found in production needs a build, App Review, a phased rollout, and then waits for people to update. Some never do.
- The server must keep supporting every old app version still in use, so a mistake in an API contract is paid for years.
- Data migrations run **on people's phones**. Once a Core Data or SwiftData migration ships, you can't undo it for those devices.

So invest early where change will be expensive later (the on-device data model, public API contracts, security and privacy) and stay loose where change is cheap (layout, copy, anything behind a feature flag).

## Technical debt

Ward Cunningham coined the metaphor in 1992. Shipping code before you fully understand the problem is like borrowing money: it lets you move faster now, and it's fine *if you pay it back*, by reworking the code once you've learned what it should be. If you don't, you pay **interest**: every change in that area takes longer than it should.

The metaphor gives you two numbers to reason with:

- **Principal:** what it would cost to fix the code properly.
- **Interest:** the extra cost you pay *each time you work in that area* because it isn't fixed.

Interest is only charged where you make changes. A messy file nobody has touched in two years costs almost nothing; a slightly awkward file that every feature passes through costs you every week. That single idea is what lets you prioritise.

Most debt can be found in your history. Files that change often (**churn**) *and* are hard to work with (**complexity**) are **hotspots**: Adam Tornhill's *Your Code as a Crime Scene* builds a whole method on this. A rough ranking takes a few lines:

```swift run
struct SourceFile {
    let name: String
    let commitsLastSixMonths: Int
    let complexity: Int   // for example, cyclomatic complexity summed over the file
}

let files = [
    SourceFile(name: "CheckoutViewController.swift", commitsLastSixMonths: 48, complexity: 310),
    SourceFile(name: "FeedViewModel.swift", commitsLastSixMonths: 35, complexity: 90),
    SourceFile(name: "LegacyReports.swift", commitsLastSixMonths: 2, complexity: 520),
    SourceFile(name: "APIClient.swift", commitsLastSixMonths: 20, complexity: 140),
    SourceFile(name: "SettingsView.swift", commitsLastSixMonths: 12, complexity: 40),
]

let ranked = files.sorted { $0.commitsLastSixMonths * $0.complexity > $1.commitsLastSixMonths * $1.complexity }
for file in ranked {
    print("\(file.name): \(file.commitsLastSixMonths * file.complexity)")
}
```

```output
CheckoutViewController.swift: 14880
FeedViewModel.swift: 3150
APIClient.swift: 2800
LegacyReports.swift: 1040
SettingsView.swift: 480
```

`LegacyReports.swift` is the most complex file in the project, and it ranks fourth: nobody changes it, so its debt charges almost no interest. The checkout screen is where refactoring pays.

## The technical-debt quadrant

Not all debt is the same, and treating it all as "bad code" misses why it's there. Martin Fowler's **technical-debt quadrant** (2009) sorts it on two axes: was it taken on **deliberately** or **inadvertently**, and was that **prudent** or **reckless**?

| | Reckless | Prudent |
| --- | --- | --- |
| **Deliberate** | "We don't have time to design it properly." Networking code copied into every view controller, knowingly, with no plan to fix it. | "We'll ship now and fix it after launch, and here's how." One payment provider hard-coded to hit a launch date, behind a seam, with the follow-up planned. |
| **Inadvertent** | "What's a main thread?" The team didn't know the platform's rules, so JSON is decoded on the main thread throughout. | "Now we know how we should have built it." A year in, the team understands the domain well enough to see that one account per person was wrong: families share. |

Each quadrant calls for a different response:

- **Prudent and deliberate** is a real loan: a trade made with open eyes. Record it, with the trigger for paying it back ("when we add a second provider").
- **Prudent and inadvertent** is unavoidable. Learning creates it: the better you understand the problem, the more you see where the design falls short. Budget for it.
- **Reckless and inadvertent** is a skills gap. Fix it with reviews, guidelines and teaching, or it keeps being created.
- **Reckless and deliberate** is the one to stop: it's not a loan, it's not paying the rent.

### Debt that's special to apps

- **Platform debt** arrives with a deadline. Apple stopped accepting new apps that used `UIWebView` in April 2020, and updates in December 2020; every team that had put off moving to `WKWebView` paid the principal at once. Deprecation warnings are invoices.
- **Minimum OS version.** Supporting an old iOS version is interest on every feature: support iOS 16 and you can't use `@Observable` or SwiftData (iOS 17) without keeping a second path.
- **Language and toolchain:** strict concurrency checking in the Swift 6 language mode turns years of unexamined threading into compiler errors to work through.
- **Third-party SDKs** pinned to old versions, which block OS updates or privacy-manifest requirements.
- **Old app versions** that force the server to keep compatibility code around.

## Deciding whether to pay it down

Paying debt is an investment: you spend the principal once to stop paying interest. Whether it's worth it depends on how much interest you're paying and for how long you'll keep paying it. Try it:

```visual estimator
title: Is it worth paying this debt down?
inputs:
  - { id: principal, label: Days to fix it properly, min: 1, max: 60, value: 10, unit: days }
  - { id: interest, label: Extra hours each change costs, min: 0.5, max: 40, step: 0.5, value: 6, unit: h }
  - { id: changes, label: Changes in this area per month, min: 0.5, max: 20, step: 0.5, value: 4 }
  - { id: horizon, label: Months the code will live, min: 1, max: 36, value: 12, unit: months }
outputs:
  - { id: perMonth, label: Interest per month, formula: interest * changes / 8, unit: days }
  - { id: payback, label: Months to earn the fix back, formula: principal / perMonth, unit: months }
  - { id: leftAlone, label: "Interest over the code's life, if left", formula: perMonth * horizon, unit: days }
  - { id: saved, label: Days saved by fixing it now, formula: leftAlone - principal, unit: days }
```

With the defaults, ten days of work pays for itself in a little over three months, and saves 26 days over a year. Drop the changes per month to 0.5 and the same fix takes more than two years to earn back: leave it. Shorten the horizon (the feature is being replaced next quarter) and fixing it loses outright. That's the argument to bring to a planning meeting: not "the code is ugly", but "this costs us three days a month, and we can stop that for ten".

How to pay it, in order of preference:

1. **Preparatory refactoring:** when a feature needs to change a messy area, first reshape the code so the change is easy, then make the easy change. The debt is paid exactly where interest is due, and the feature carries the cost.
2. **The boy scout rule:** leave each file a little better than you found it. Cheap and continuous, but it never tackles anything big.
3. **A planned slice:** a fixed share of each cycle (many teams use 10–20%) for items from the debt register, chosen by interest.
4. **A rewrite,** rarely. Big-bang rewrites stall feature work for months, rediscover old bugs the hard way, and often ship late. Replacing a system piece by piece while it keeps running (you'll meet the strangler fig in D31) is almost always safer.

## Trade-offs

| Approach | Pays down | Costs | When it wins |
| --- | --- | --- | --- |
| Take on prudent, deliberate debt | Time to market now | Interest until repaid, and the discipline to repay | A real deadline, with a seam and a written trigger to repay |
| Preparatory refactoring | Debt exactly where features touch it | Features take a little longer | The default for most debt |
| Dedicated refactoring time | Debt features never reach | Feature time; needs a ranked register to spend it well | Hotspots, platform deadlines, upgrades |
| Rewrite | Everything, in theory | Months of no new value, high risk | The platform or technology is truly at its end, and pieces can't be replaced one by one |
| Leave it alone | Nothing | Interest, which may be near zero | Code that rarely changes, or is about to be deleted |

<Callout kind="interview">

**Say:** "I'd make the debt visible and put numbers on it: where it is, the interest (how much it slows the next features) and the principal. Then I'd tie it to the roadmap: we're changing checkout eight times this year, it costs about two days each time, and the fix is six days. Mostly I'd pay it down through preparatory refactoring inside those features."

**Ask:** "Which parts of the code are on the roadmap?" Debt on the roadmap charges interest; debt off it mostly doesn't.

**Red flags:** proposing a rewrite first; "we never take on debt"; blaming the previous team (most debt is prudent and inadvertent: they knew less than you know now); refactoring with no tests to protect behaviour.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: on-device data migrations only go forward">

Once an update migrates its Core Data or SwiftData store, the data on each phone is in the new shape. People can't downgrade an App Store app, and an older build can't open the newer store. So the persisted data model is where shortcuts are most expensive to undo: version it (`VersionedSchema` and a `SchemaMigrationPlan` in SwiftData), test migrations from every shipped version, and think hard before adding a field you can't take back.

</Callout>

## Practice

The architecture review *A workout streak that nobody can test* asks for a fix "in small steps". That's preparatory refactoring under real constraints: the bug has to be fixed now, the file can't be rewritten in one go, and each step must ship safely. Classify its problems with the quadrant as you go: which were deliberate, and which did the team not know?

```cards
- id: principal-interest
  front: "In the technical-debt metaphor, what are principal and interest?"
  back: "Principal is the cost of fixing the code properly. Interest is the extra cost paid every time you work in that area. Interest is only charged where code changes."
- id: debt-quadrant
  front: "What are the two axes of Fowler's technical-debt quadrant?"
  back: "Deliberate or inadvertent, and prudent or reckless. Prudent-deliberate is a real loan; prudent-inadvertent comes from learning; reckless debt is what to stop creating."
- id: hotspots
  front: "How do you find the debt most worth paying first?"
  back: "Hotspots: files with high churn and high complexity. A complex file nobody changes charges little interest."
- id: steep-app-curve
  front: "Why is the cost of change steeper for apps than for servers?"
  back: "Production fixes need review and slow adoption, old versions stay in use (so APIs carry compatibility for years), and on-device data migrations can't be rolled back."
```
