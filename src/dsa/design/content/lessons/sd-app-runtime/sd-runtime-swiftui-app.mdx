## Why it matters

A SwiftUI app replaces the app delegate and scene delegates with a few declarations: an `App`, its `Scene`s, and an environment value called `scenePhase`. The lifecycle underneath is exactly the one from [the previous lesson](/design/learn/sd-runtime-app-states); SwiftUI only changes how you hear about it. The architectural questions are the same as ever: where app-wide state lives, which code hears which window's transitions, and how to reach the UIKit callbacks SwiftUI doesn't expose. Getting the aggregate `scenePhase` wrong is one of the most common SwiftUI lifecycle bugs, and interviewers who know SwiftUI ask about it.

## The App: your app as a value

```swift
@main
struct ShelfApp: App {
    var body: some Scene {
        WindowGroup {
            LibraryView()
        }
    }
}
```

`@main` on a type conforming to `App` makes SwiftUI generate the program's entry point. It starts UIKit for you, creates its own app delegate and scene delegates, and asks your `body` which scenes the app has.

Two facts about the `App` value shape your design:

- **Its `init` runs once per process, during launch**, before the first frame. Whatever you do there delays the first frame, so keep it to building cheap objects.
- **Its `body` can be evaluated more than once**, like a view's: whenever state it reads changes. Don't start work from `body`.

State declared in the `App` with `@State` lives as long as the process. That makes it the natural owner of app-wide models: the library store, the session, the API client. Every window then gets them through the environment.

## Scenes: templates for windows

A `Scene` describes a kind of window, not a window. SwiftUI creates actual windows from it as the system and the user ask.

| Scene | On iOS and iPadOS | What it creates |
| --- | --- | --- |
| `WindowGroup { … }` | Yes | One window on iPhone; on iPad, as many as the user opens, each with its own view state |
| `WindowGroup(for: Note.ID.self) { $id in … }` (iOS 16+) | Yes | A window per value: `openWindow(value: note.id)` opens one for that note, or brings it forward |
| `DocumentGroup` | Yes | Document-based apps: the system browser, then one window per open document |
| `Window`, `Settings`, `MenuBarExtra` | No | macOS (and `Window` on visionOS) |

Scene-level modifiers attach behaviour to every window a scene creates: `.backgroundTask(.appRefresh("id"))` runs a BGTask (iOS 16+), `.commands` adds keyboard menu commands on iPad, and `.handlesExternalEvents(matching:)` chooses which window a URL or activity opens in.

## scenePhase: three values, and where you read them

`@Environment(\.scenePhase)` reports one of three values:

| `ScenePhase` | UIKit state | Meaning |
| --- | --- | --- |
| `.active` | foreground active | On screen and interactive |
| `.inactive` | foreground inactive | On screen, not interactive: launching, interrupted, in the app switcher |
| `.background` | background | Not visible. Expect suspension, and possibly termination, soon after |

There's no `.suspended` and no "not running": your code isn't running then, so there'd be nobody to tell. There's also no separate "will enter foreground"; it shows up as a change from `.background` to `.inactive`.

**Where you read `scenePhase` decides what it means:**

- **In a view**, it's the phase of the window that view is in.
- **In the `App`**, it's an **aggregate** over every window: `.active` if any window is active, `.inactive` if none is active but not all have left, and `.background` only when every window is in the background.
- **In a custom `Scene`**, it's the aggregate over that scene's windows.

On an iPhone with one window, the three agree, which is why the difference catches people out the first time their app runs on an iPad. Step through two windows side by side:

Flushing the app-wide store belongs in the `App`, at the moment no window is left.

## Putting it together

Here's an app with an app-wide model owned by the `App`, a save when the whole app leaves, a per-window refresh, and a BGTask:

```swift check ios title="ShelfApp.swift"
import SwiftUI
import UIKit

@MainActor @Observable
final class Library {
    private(set) var titles: [String] = []
    private var lastRefresh: Date?

    func refreshIfStale() async {
        if let lastRefresh, Date.now.timeIntervalSince(lastRefresh) < 15 * 60 { return }
        lastRefresh = .now
        // fetch, then update titles
    }

    func save() { /* write the store to disk */ }
    func syncInBackground() async { /* the BGTask's work */ }
}

final class AppDelegate: NSObject, UIApplicationDelegate {
    func application(_ application: UIApplication, didRegisterForRemoteNotificationsWithDeviceToken deviceToken: Data) {
        // SwiftUI has no equivalent: hand the token to the push service here
    }
}

// Marked @main in the app target
struct ShelfApp: App {
    @UIApplicationDelegateAdaptor(AppDelegate.self) private var appDelegate
    // One per process, shared by every window
    @State private var library = Library()
    // Read here, this is the aggregate over all windows
    @Environment(\.scenePhase) private var phase

    var body: some Scene {
        WindowGroup {
            LibraryView()
                .environment(library)
        }
        .onChange(of: phase) { _, newPhase in
            if newPhase == .background { library.save() } // no window is left
        }
        .backgroundTask(.appRefresh("library-sync")) {
            await library.syncInBackground()
        }
    }
}

struct LibraryView: View {
    @Environment(Library.self) private var library
    // Read here, this is this window's phase
    @Environment(\.scenePhase) private var phase

    var body: some View {
        List(library.titles, id: \.self) { Text($0) }
            .onChange(of: phase) { _, newPhase in
                if newPhase == .active {
                    Task { await library.refreshIfStale() }
                }
            }
    }
}
```

A few details worth noticing:

- `refreshIfStale()` checks the data's age, so a burst of `.inactive`/`.active` flips (Control Center, a Face ID prompt) costs nothing.
- `.backgroundTask(.appRefresh(...))` only *handles* the task. You still list the identifier under `BGTaskSchedulerPermittedIdentifiers` in Info.plist and submit a `BGAppRefreshTaskRequest`, and iOS still decides when, or whether, it runs. You'll design with it in D52.
- `@UIApplicationDelegateAdaptor` is the escape hatch for what SwiftUI doesn't cover: the push token, SDKs that want `launchOptions`, and handlers that must be registered before launch finishes. SwiftUI creates the delegate itself; never instantiate it yourself.

### App-wide or per window?

| Kind of state | Where it lives in SwiftUI | Lifetime |
| --- | --- | --- |
| Stores, session, API client, caches | `@State` in the `App`, passed down with `.environment` | The process |
| Navigation path, selection, a draft in progress | `@State` in the window's root view | That window |
| What to restore if the window is recreated | `@SceneStorage` (more on it later in this module) | That window, across launches |
| Small preferences | `@AppStorage` (backed by `UserDefaults`) | Across launches, all windows |

The classic mistake is putting per-window state, such as the navigation path, in an app-wide model. On an iPhone it works. On an iPad, opening a second window makes both windows navigate together.

## Trade-offs

| Lifecycle | Effort | Access to UIKit callbacks | Testability | When it wins |
| --- | --- | --- | --- | --- |
| Pure SwiftUI `App` | Lowest | None beyond what SwiftUI exposes | Good if logic lives in models | New apps whose needs SwiftUI covers |
| SwiftUI `App` plus `@UIApplicationDelegateAdaptor` | Low | App delegate events; scene delegate via a returned configuration | Good | Most real SwiftUI apps: push, SDKs, BGTask registration |
| UIKit delegates hosting SwiftUI in `UIHostingController` | Higher | Everything | Good | Existing UIKit apps adopting SwiftUI screen by screen, or apps with heavy scene-level needs |

None of these is a one-way door: a UIKit app can host SwiftUI screens today and move to a SwiftUI `App` later, once nothing depends on the delegates directly.

<Callout kind="interview">

**Say** where each piece of state lives and which phase you watch: "The store is `@State` in the App and goes down through the environment; each window owns its navigation; the App saves when the aggregate phase reaches background; each window refreshes stale data when its own phase becomes active." **Ask** whether the app supports multiple windows on iPad, because it changes where state goes. **Red flags:** treating `onAppear` of the root view as "app launched", heavy work in `App.init`, and per-window state in a global model.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: onAppear isn't launch">

`.onAppear` and `.task` on the root view run once **per window**, and again whenever that view is recreated. Analytics that log "app opened" there double-count on iPad, and setup done there runs twice. One-time process setup belongs in the `App`'s `init` (if cheap) or in a model that remembers it has started.

</Callout>

## Practice

[The lifecycle kata](/design/practice/sd-kata-app-runtime-lifecycle-machine) is framework-neutral on purpose: the same machine sits behind a scene delegate or behind `onChange(of: scenePhase)`. Notice that `scenePhase` has no separate "will enter foreground", so mapping `.background` to `.inactive` onto the machine's events is the adapter's job.

```cards
- id: scenephase-values
  front: "What values can scenePhase have, and which UIKit states are missing?"
  back: "`.active`, `.inactive` and `.background`. Suspended and not running are missing, because no code runs then."
- id: aggregate-phase
  front: "What does scenePhase mean when read in the App rather than in a view?"
  back: "An aggregate over all windows: active if any window is active, background only once every window is. A single window leaving doesn't change it."
- id: app-init
  front: "When does an App's init run, and what does that imply?"
  back: "Once per process, during launch and before the first frame. Keep it cheap: anything slow there delays the first frame."
```
