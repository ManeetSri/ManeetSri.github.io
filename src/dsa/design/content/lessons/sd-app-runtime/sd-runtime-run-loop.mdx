## Why it matters

Every touch, every animation frame and every line of UI code in your app runs on one thread. When that thread is busy, scrolling stutters, taps feel ignored, and after long enough the system kills the app. Understanding the **run loop**, the loop that thread spends its life in, explains a lot of iOS folklore at once: why a label doesn't change until your function returns, why a timer stops while the user scrolls, why a 50 ms decode drops frames, and why `await` on the main actor doesn't freeze the screen. "Why does my list stutter?" is a favourite interview question, and the answer starts here.

## One thread for all UI

UIKit and SwiftUI are not thread-safe. Every view, view controller and SwiftUI view must be touched only from the **main thread**, the thread the process started on. Swift 6 turns this into types: `UIView`, `UIViewController` and SwiftUI's `View` protocol are all `@MainActor`, so the compiler checks most calls for you.

Most, not all. Objective-C callbacks such as `URLSession`'s completion handler are imported leniently, so the mistake is only a warning:

```swift
URLSession.shared.dataTask(with: url) { data, _, _ in
    self.label.text = "Loaded \(data?.count ?? 0) bytes" // runs on a background queue
}.resume()
```

```text title="What you'll see"
warning: main actor-isolated property 'text' can not be mutated from a Sendable closure
```

Treat that warning as an error. At run time, Xcode's **Main Thread Checker** also catches UIKit calls made off the main thread in debug builds.

## The run loop

The main thread doesn't run your code top to bottom and exit. After launch it enters a loop that it never leaves:

1. **Sleep** until something needs doing. A sleeping main thread uses no CPU at all.
2. **Wake** for whatever arrived: a touch from the system, a timer coming due, a block on the main dispatch queue, a job for the main actor.
3. **Run the handlers**, one after another: your gesture handler, your timer's closure, your `DispatchQueue.main.async` block, the next slice of a `@MainActor` async function.
4. **Commit** before going back to sleep. Core Animation's run loop observer runs the pending layout (`layoutSubviews`, SwiftUI's body updates and layout), the pending drawing, and sends the resulting layer tree to the **render server**, a separate system process that composites the frame and puts it on the display.

<Callout kind="analogy">

Think of a receptionist at a quiet front desk. They doze until the phone rings or an alarm goes off, deal with each call in turn, and only file the day's paperwork (the commit) once nobody is waiting. A caller who keeps them talking for ten minutes delays everyone behind, and the paperwork too.

</Callout>

```visual states
  - { event: wake, say: "A touch arrives. The run loop wakes and your button's action runs: it sets `label.text` three times. Nothing appears yet." }
  - { event: next, say: "In the same turn, a `DispatchQueue.main.async` block that was queued earlier runs too. Each handler runs to completion before the next starts." }
  - { event: beforeWaiting, say: "Nothing else is due, so **Core Animation commits**: layout runs once, the label draws its *final* text once, and the layer tree goes to the render server." }
  - { event: sleep, say: "Back to sleep. The render server puts the new frame on screen at the next display refresh." }
  - { event: wake, say: "A timer fires. Its closure updates a progress bar." }
  - { event: beforeWaiting, say: "Commit again. One turn, one commit: that's why changes you make in a handler appear together, after it returns." }

```

That last sentence is the whole lesson. **Your code runs inside the loop.** While a handler is running, the loop can't take new touches or commit new frames.

## The frame budget

The display refreshes 60 times a second on most iPhones, and up to 120 times on ProMotion displays. For smooth motion, each frame's work must be done in time:

| Refresh rate | Time per frame | Main thread's share |
| --- | --- | --- |
| 60 Hz | 16.7 ms | Less: the render server needs its part of the frame too |
| 120 Hz | 8.3 ms | Less again |

A frame that arrives late is a **hitch**: the scroll jumps instead of gliding. When the main thread is busy long enough that the app visibly stops responding, it's a **hang**: Apple's tools count 250 ms or more as a hang, and users start to notice stalls from about 100 ms. Watch what one synchronous decode costs, and what moving it off the main thread buys:

## Main thread, main queue, main actor

Three names, one thread:

- The **main thread** is the thread itself.
- The **main dispatch queue** is GCD's serial queue whose blocks the main run loop runs on the main thread. `DispatchQueue.main.async` puts a block on it.
- The **main actor** is Swift concurrency's global actor for the main thread. Code marked `@MainActor` runs there, and its executor schedules jobs through the main queue.

What matters for design is the difference between **suspending** and **blocking**. When a `@MainActor` function reaches an `await`, it gives the main thread back to the run loop until the awaited work finishes, so touches and frames carry on. When it runs synchronous code, it holds the thread until that code returns. A `@MainActor` view model is fine; a `@MainActor` view model that decodes 2 MB of JSON synchronously is a hitch.

To move work off the main actor, call code that isn't isolated to it: an `actor`, or an async function that runs on the thread pool. The simplest is a function marked `@concurrent` (Swift 6.2 and later), which always leaves the caller's actor:

```swift run title="Hopping off the main actor and back"
import Foundation

// A synchronous check, so async code can show where it's running (for teaching, not for logic)
func whereAmI() -> String { Thread.isMainThread ? "the main thread" : "a pool thread" }

// Synchronous work runs on whatever thread calls it
func checksum(_ bytes: [UInt8]) -> Int {
    bytes.reduce(0) { $0 + Int($1) }
}

// @concurrent: runs on the thread pool, never on the caller's actor
@concurrent
func checksumOffMain(_ bytes: [UInt8]) async -> Int {
    print("2. checksum runs on \(whereAmI())")
    return checksum(bytes)
}

@MainActor
func refresh() async {
    print("1. refresh starts on \(whereAmI())")
    let bytes = [UInt8](repeating: 7, count: 1_000_000)
    let total = await checksumOffMain(bytes) // the main thread is free while this runs
    print("3. refresh resumes on \(whereAmI())")
    print("4. total \(total)")
}

await refresh()
```

```output
1. refresh starts on the main thread
2. checksum runs on a pool thread
3. refresh resumes on the main thread
4. total 7000000
```

Without `@concurrent`, where a plain `nonisolated async` function runs depends on your build settings, which is a recent change worth knowing. In Swift 6 language mode it runs on the thread pool. With the upcoming feature `NonisolatedNonsendingByDefault` (part of Xcode's "Approachable Concurrency" setting), it runs on the **caller's** actor, so called from the main actor it stays on the main thread. `@concurrent` says what you mean either way. You'll go deep on actors, isolation and these settings in D22.

## Run loop modes, and the timer that stops

The run loop runs in a **mode**, and each timer or source is registered for some modes and not others. While the user's finger is dragging a scroll view, UIKit switches the main run loop into a tracking mode. A timer scheduled the usual way, with `Timer.scheduledTimer`, is registered only for the default mode, so **it stops firing while the user scrolls**: the countdown freezes, the "live" clock lags.

Register it for the **common** modes, which include tracking:

```swift check title="CountdownTicker.swift"
import Foundation

@MainActor
final class CountdownTicker {
    private var timer: Timer?

    func start(onTick: @escaping @MainActor () -> Void) {
        let timer = Timer(timeInterval: 1, repeats: true) { _ in
            // A timer on the main run loop fires on the main thread; say so to the compiler
            MainActor.assumeIsolated { onTick() }
        }
        // .common includes the tracking mode UIKit runs while the user scrolls
        RunLoop.main.add(timer, forMode: .common)
        self.timer = timer
    }

    func stop() {
        timer?.invalidate()
        timer = nil
    }
}
```

Main-queue blocks and main-actor jobs run in the common modes already, which is why a `Task` loop with `Task.sleep` keeps ticking during a scroll. For anything tied to the display's refresh, such as a custom animation, use `CADisplayLink` instead of a timer: it fires once per frame, in step with the display.

## Trade-offs: where should this work run?

| Where | Responsiveness | Safety | Cost | When it wins |
| --- | --- | --- | --- | --- |
| Synchronously on the main actor | Blocks for as long as it takes | Simplest: no data crosses threads | None | Small work (well under a millisecond), and anything that touches UI |
| `await` from the main actor into an `actor` or `@concurrent` function | Main thread stays free | Data passed across must be `Sendable` | A hop each way | Decoding, parsing, image work, disk and database I/O |
| A GCD queue with a completion handler | Main thread stays free | Easy to touch UI from the wrong queue | Callback plumbing | Older code and APIs that have no async version |
| Precompute ahead of time (prefetch, cache) | Best: no work at the moment of need | Depends on the cache | Memory, and work that may be wasted | Scrolling lists: prefetch cells, decode images before they're visible |

<Callout kind="interview">

**Say** how you'd find the cause before guessing: "I'd record the scroll in Instruments with the Hangs and Animation Hitches instruments, look at what the main thread was doing during the long frames, and move that work off the main actor or out of the scroll path." **Ask** which devices and refresh rates matter: a 120 Hz target halves the budget. **Red flags:** "use a background thread" with no word about getting results back safely, `DispatchQueue.main.sync`, and believing `async` alone moves work off the main thread.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: callbacks that trap in Swift 6">

In Swift 6 mode, a closure written inside a `@MainActor` type is isolated to the main actor, and the compiler inserts a check where an Objective-C API might call it. If the API calls it on a background queue, as some notification, authorisation and SDK callbacks do, the app now **traps** with `_dispatch_assert_queue_fail` instead of racing silently. Prefer the API's `async` version, or mark the closure `@Sendable` and hop to the main actor explicitly.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: DispatchQueue.main.sync deadlocks">

Calling `DispatchQueue.main.sync` from the main thread waits for the main queue to run a block, but the main queue can't run anything until the current block (yours) returns. The app freezes forever. The same deadlock hides in a semaphore that waits on the main thread for a callback delivered on the main queue.

</Callout>

## Practice

[The launch review](/design/practice/sd-review-app-runtime-launch-main-thread) is a run-loop exercise in disguise: find everything that holds the main thread before the first commit, and say where each piece should run instead.

```cards
- id: run-loop-turn
  front: "What happens in one turn of the main run loop?"
  back: "It wakes for input, a timer, main-queue blocks or main-actor jobs, runs their handlers one after another, then commits layout and drawing to the render server before sleeping again."
- id: suspend-vs-block
  front: "Why doesn't `await` on the main actor freeze the UI, while synchronous work does?"
  back: "At an `await` the function suspends and the run loop keeps turning. Synchronous work holds the main thread until it returns, so no touches or frames are handled."
- id: timer-modes
  front: "Why does a scheduled Timer stop firing while the user scrolls, and what's the fix?"
  back: "Scrolling switches the run loop to its tracking mode, and `scheduledTimer` registers only for the default mode. Add the timer for `.common` modes, or use a Task loop or CADisplayLink."
- id: frame-budget
  front: "What's the frame budget at 60 Hz and at 120 Hz?"
  back: "16.7 ms and 8.3 ms per frame, of which the main thread gets only part."
```
