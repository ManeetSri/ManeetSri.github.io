## Why it matters

Swift frees an object the moment nothing holds a strong reference to it. That makes memory predictable, and it makes one class of bug structural: if two objects hold each other, neither is ever freed. In a real app the cycle rarely sits inside one class. It runs **across layers**: a screen, its view model, a shared repository's observer list, a timer, a task. Every leaked screen keeps working for nobody, fetching, logging and reacting to updates, until the footprint climbs into jetsam's range. Interviewers ask about `weak` and `unowned` to check the basics; staff-level candidates are expected to draw the ownership graph of a feature and say where the arrows must be weak.

## ARC in one page

Every class instance carries a **reference count**. Each strong reference to it adds one; when a reference goes away, the count drops; at zero, `deinit` runs and the memory is freed, right then, on whatever thread released the last reference. There's no garbage collector looking for unreachable objects later. You met the value-semantics side of this in [value vs reference semantics](/design/learn/sd-swift-design-value-semantics): structs and enums aren't counted, but a struct that stores a class reference retains it, and every copy of the struct retains it again.

Three kinds of reference decide the graph:

| Reference | Keeps the object alive? | If the object is freed | Use it for |
| --- | --- | --- | --- |
| `strong` (the default) | Yes | Can't happen while you hold it | Ownership: a parent holding its child |
| `weak` | No | Becomes `nil` | Back-references, delegates, observers: anything that may outlive its target |
| `unowned` | No | Reading it **traps** | A back-reference to an owner that's guaranteed to outlive you |

And one fact that causes most real leaks: **closures are reference types that capture strongly.** A closure that mentions `self` holds `self`, unless its capture list says `[weak self]` or `[unowned self]`. Store that closure on an object that `self` owns, and you have a cycle.

## Ownership graphs

Draw a feature as a graph: one box per object, one arrow per stored strong reference. A healthy graph is a **tree** hanging from roots the app holds: the app delegate, the scene, the window, the navigation stack, the composition root's shared services. Three rules keep it that way:

1. **Ownership points down.** Parents own children: a navigation stack owns its screens, a screen owns its view model, the composition root owns shared services.
2. **Anything pointing back up is weak.** Delegates, parent pointers, observers, and closures that call back to their owner. Use `unowned` only when the lifetime is guaranteed by construction.
3. **Long-lived objects never strongly hold short-lived ones.** A repository lives for the whole session; a screen lives until the user taps Back. If the repository's observer list holds the screen's view model strongly, the screen lives for the session too.

Rule 3 is the one that bites across layers. Watch a detail screen leak through a shared repository:


Notice what kind of leak that is. The screen isn't part of an unreachable island: the app can still reach it, through the repository. Xcode's **Memory Graph debugger** flags unreachable cycles with a purple warning, but objects held by a live owner look legitimate to it, and Instruments' Leaks template agrees. You find this kind by **counting**: "why are there ten `DetailViewModel` instances after I closed the screen ten times?" Instruments' Allocations with generations, or the instance counts in the memory graph, show it at once.

### Lifetimes, layer by layer

Rule 3 is easier to apply when every object has a stated lifetime. Most iOS apps have four:

| Lifetime | Typical objects | Owned by |
| --- | --- | --- |
| **Session** (the process) | API client, repositories, caches, the signed-in session | The composition root in the app delegate or `App` |
| **Window** (a scene) | The window's root coordinator, its navigation state | The scene delegate, or the `WindowGroup`'s root view |
| **Flow and screen** | Child coordinators, view controllers, views, view models | The parent coordinator, the navigation stack, the view |
| **Request** | A task loading one page, a decode, an upload | Its caller: a structured scope, or a stored task cancelled with its owner |

Any reference from a longer lifetime to a shorter one must be weak, or a token the shorter-lived object cancels. A repository (session) holding a view model (screen), a coordinator (flow) holding a finished child, a singleton analytics client holding a screen's closure: each is an arrow pointing the wrong way down that table.

SwiftUI shifts where the cycles live. A view is a struct, so `self` inside a view's closure is a copy of a value, not a reference, and can't form a cycle. The references are in your `@Observable` models and the tasks and closures *they* store. `@State` in a view owns its model for as long as the view's identity lasts, and the `.task` modifier ties a task to the view's appearance, cancelling it when the view goes. Those two cover most screen-lifetime needs without any `[weak self]` at all.

## The usual suspects

Almost every retain cycle in an iOS codebase is one of these.

### A strong delegate

A delegate points back at whoever owns you. Declared strong, it closes a loop. Constrain the protocol to classes so it can be `weak`:

```swift check title="ListScreen.swift"
import Foundation

protocol ListScreenDelegate: AnyObject {
    func listScreen(didSelect id: UUID)
}

final class ListScreen {
    // The coordinator owns this screen; this arrow points back up, so it's weak
    weak var delegate: (any ListScreenDelegate)?

    func select(_ id: UUID) {
        delegate?.listScreen(didSelect: id)
    }
}
```

### A stored closure that captures its owner

`viewModel.onChange = { self.render() }`, inside the view controller that owns the view model: self owns the view model, the view model owns the closure, the closure owns self. Write `{ [weak self] in self?.render() }`.

### Timers

A repeating `Timer` is retained by the run loop, and it retains its target or its closure. A screen that starts a timer capturing `self` and plans to `invalidate()` it in `deinit` never reaches `deinit`, because the timer is holding it. Capture `[weak self]`, and invalidate the timer when the screen stops needing it (`viewWillDisappear(_:)`, or when the work ends), not in `deinit`.

### NotificationCenter block observers

`addObserver(forName:object:queue:using:)` returns a token, and the center keeps the block alive until you remove that token. A block that captures `self` strongly keeps `self` alive for as long as the token is registered, which is forever if nobody removes it. Capture weakly and remove the token, or use `NotificationCenter.default.notifications(named:)` in a task that's cancelled with the screen.

### Combine subscriptions

`publisher.sink { self.update($0) }.store(in: &cancellables)` builds the loop by itself: self owns `cancellables`, which owns the subscription, which owns the closure, which owns self. Capture `[weak self]`, or bind straight to a property with `assign(to: &$property)`, which ties the subscription's lifetime to that `@Published` property without capturing `self`.

### Tasks that never finish

A `Task` holds everything its closure captures until the task **ends**. For a one-shot `Task { await self.load() }`, that's a short delay before `self` can be freed, not a leak. A task that loops over an endless stream is different: it never ends, so if it captures `self` strongly, `self` is never freed, and the `cancel()` you put in `deinit` never runs.

```swift check title="ProfileViewModel.swift"
import Combine
import Foundation

struct Profile: Sendable, Equatable {
    var name: String
}

@MainActor
final class ProfileViewModel {
    @Published private(set) var profile = Profile(name: "")
    var onChange: (() -> Void)?

    private var cancellables = Set<AnyCancellable>()
    private var updates: Task<Void, Never>?

    init(profiles: AnyPublisher<Profile, Never>, events: AsyncStream<String>) {
        profiles
            .sink { [weak self] profile in self?.profile = profile }
            .store(in: &cancellables)

        updates = Task { [weak self] in
            for await event in events {
                guard let self else { return } // strong only for this iteration
                self.handle(event)
            }
        }
    }

    deinit {
        updates?.cancel() // reachable now, because nothing above holds self strongly
    }

    private func handle(_ event: String) {
        onChange?()
    }
}
```

The `guard let self` sits **inside** the loop on purpose. Between events, while the loop waits at `for await`, the task holds only the weak reference, so the view model can be freed.

<Callout kind="gotcha" title="Swift gotcha: [weak self] that isn't">

`Task { [weak self] in guard let self else { return }; for await e in events { self.handle(e) } }` looks safe and isn't. The `guard` at the top makes a strong reference that lasts until the task ends, which for an endless stream is never. Rebind inside the loop, or tie the task's lifetime to the view: SwiftUI's `.task` modifier cancels its task when the view disappears.

</Callout>

### Coordinators that keep their children

A parent coordinator keeps its child coordinators in an array so they stay alive while their flow runs. When the flow finishes, the parent must remove the child. Forget, and every completed sign-up or checkout flow stays in memory with its screens and services. You'll design coordinators properly in D20.

## `weak` or `unowned`?

Both break a cycle; they differ in what happens if you're wrong about lifetimes.

- **`weak`** turns "the object is gone" into `nil`, which you handle. It costs an optional and a little bookkeeping.
- **`unowned`** turns "the object is gone" into a crash the moment you touch it. It's right only when the target **owns** you, directly or indirectly, so it can't be freed first: a child view model's reference to the coordinator that created and holds it, a node's reference to the tree that owns it.

If you can't say *why* the target must outlive the reference, use `weak`. An `unowned self` in a network completion handler is the classic crash: the user leaves the screen, the request finishes, and the handler touches a freed object.

## Proving it in tests

Leaks come back unless a test stops them. The pattern is a weak reference that must become `nil`:

```swift
@Test("Closing the detail screen frees its view model")
func detailIsReleased() async {
    weak var released: DetailViewModel?
    do {
        let viewModel = DetailViewModel(repository: repository)
        released = viewModel
        await viewModel.start()
    }
    #expect(released == nil)
}
```

Build the object the way the app does, with its real dependencies (the shared repository, the analytics client), because the cycle usually runs through them. A test with every dependency stubbed out can pass while the real wiring leaks.

## Trade-offs

| Technique | If the target is freed | Cost | When it wins |
| --- | --- | --- | --- |
| Strong reference | Can't be freed: that's the point | None | Ownership, down the tree |
| `weak` | Becomes `nil` | Optional handling, slight overhead | Delegates, observers, callbacks to an owner, anything you can't prove outlives you |
| `unowned` | Trap on access | None at the use site | Back-references to a guaranteed owner |
| Explicit teardown: `cancel()`, `invalidate()`, removing tokens | Depends on someone calling it at the right time | Discipline, and a moment that isn't `deinit` | Timers, tasks, observers, always alongside weak capture |
| Lifetime-scoped APIs: SwiftUI's `.task`, `AnyCancellable`, value-type models | Handled by the framework | Tied to that framework's lifetimes | Whenever one fits |

<Callout kind="interview">

**Say** the ownership rule and apply it to the feature: "The composition root owns the repository; screens own their view models; anything that calls back up the tree is weak. The repository's observers are tokens the view model cancels, so a closed screen can't stay subscribed." **Ask** how long each object should live: the session, the screen, the request. Mismatched lifetimes are where leaks come from. **Red flags:** `[weak self]` sprinkled everywhere with no reasoning, `unowned` in async callbacks, and "ARC handles memory" with no mention of cycles.

</Callout>
