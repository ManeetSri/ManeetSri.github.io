## Why it matters

SwiftUI ships with a dependency injection system built in: the environment. Every value you put there is available to a whole subtree, can be overridden for part of it, and falls back to a default when nobody set it. That makes it the natural home for capabilities that many views need (loading images, tracking events, opening links), and a dangerous home for everything else, because none of it shows up in a signature. [Environment values and preferences](/design/learn/sd-swiftui-environment) covered how the environment works. This lesson is about using it as a DI mechanism: what to put there, how to choose defaults, how to get environment dependencies into view models, and how a subtree becomes a scope.

## Ambient injection, with a scope built in

Compared with the forms in [Constructor, property and method injection](/design/learn/sd-di-injection-forms), the environment is **ambient**: the dependency isn't passed to the view, it's in the view's surroundings. That brings three properties a DI designer cares about:

- **Scoping comes free.** A value set on a subtree applies to that subtree only. Put a basket in the environment at the root of the signed-in UI and it's session-scoped without any extra code: when that subtree goes, so does access to the basket.
- **Overrides are local.** A preview, a test host, or one feature's subtree can replace a value for itself without touching anything else.
- **Something always answers.** An `@Entry` value has a default, so a view never fails to find it. That's convenient, and it's also the environment's biggest risk: a forgotten override doesn't fail, it silently uses the default.

Its limits are as important. The environment is readable only by views (and view modifiers), only once they're in the hierarchy, and it's invisible at the call site: `TripRow(trip:)` doesn't tell you the row also loads images and tracks taps.

## What belongs in the environment

A practical test: **would you be happy for every view in the subtree to call this?** If yes, and it has a sensible default, the environment fits. If only one screen's model needs it, use an initialiser.

| Put it in the environment | Pass it through initialisers |
| --- | --- |
| Capabilities many views call at many depths: image loading, `track`, open a URL, haptics, show a toast | What one screen's model needs: its repository, its use cases |
| Values with a natural default: theme, density, feature-flag snapshot | Per-item data: the trip a row shows |
| Shared observable models for a scope: the session, the basket, the audio player | Anything a non-view type needs: services, view models, background work |
| Things a container passes to children it doesn't know about | Anything with no safe default, where a missing value must be a compile error |

## Capabilities, not service objects

When you do put a dependency in the environment, prefer a small **capability**, a value with one job, over a whole service:

```swift check ios group=env title="A capability with a deliberate default"
import SwiftUI
import os

/// The one thing views need from analytics: a way to record an event
struct TrackAction: Sendable {
    private let handler: @Sendable (String, [String: String]) -> Void

    init(_ handler: @escaping @Sendable (String, [String: String]) -> Void) {
        self.handler = handler
    }

    func callAsFunction(_ event: String, _ properties: [String: String] = [:]) {
        handler(event, properties)
    }

    /// The default does nothing, but says so in the console, so a missing install is easy to spot
    static let notInstalled = TrackAction { event, _ in
        Logger(subsystem: "com.example.travel", category: "di")
            .fault("track(\(event, privacy: .public)) was called, but no analytics is installed")
    }
}

extension EnvironmentValues {
    @Entry var track: TrackAction = .notInstalled
}

struct SaveTripButton: View {
    @Environment(\.track) private var track
    let tripID: String

    var body: some View {
        Button("Save trip") {
            track("trip_saved", ["trip": tripID])
        }
    }
}
```

A capability is easy to fake (one closure), easy to decorate, and doesn't drag the analytics SDK's API into every view. It also makes the dependency honest about what views may do: track events, not reconfigure the analytics pipeline.

### Choosing the default is the design decision

Every `@Entry` needs a default, and which one you pick decides how the app fails when someone forgets to install the real thing:

| Default | Production with a forgotten install | Previews and tests with no setup | Use it for |
| --- | --- | --- | --- |
| The live implementation | Works | Silently hits real services: previews log analytics to production, tests touch the network | Pure, local behaviour only (a formatter, a theme) |
| A no-op | Silently does nothing: the feature "works" but nothing is recorded | Safe and quiet | Purely visual capabilities, like haptics |
| A no-op that reports (as `notInstalled` above) | Does nothing, but logs a fault you'll see in Console and in crash-reporting breadcrumbs | Safe, and visible when it matters | Side effects: analytics, saving, network calls |

A live default is the dangerous one, because it hides the mistake everywhere: production works, so nobody notices that previews and tests are calling real services. If production depends on it, install it explicitly at the root and make the default harmless.

## Installing, overriding and decorating

The composition root installs the real capabilities once, near the top of the tree. Any subtree can then override or **decorate** what it inherited, which is the decorator pattern applied through the environment:

```swift check ios group=env title="Installed at the root, decorated by one flow"
protocol AnalyticsClient: Sendable {
    func log(_ event: String, properties: [String: String]) async
}

struct CheckoutFlow: View {
    var body: some View {
        SaveTripButton(tripID: "LIS-42")
            // Every event tracked inside checkout is tagged, without any view knowing
            .transformEnvironment(\.track) { track in
                let parent = track
                track = TrackAction { event, properties in
                    parent(event, properties.merging(["flow": "checkout"]) { current, _ in current })
                }
            }
    }
}

struct AppRootView: View {
    let analytics: any AnalyticsClient

    var body: some View {
        CheckoutFlow()
            .environment(\.track, TrackAction { event, properties in
                Task { await analytics.log(event, properties: properties) }
            })
    }
}
```

## Getting environment dependencies into a view model

Here's the problem every SwiftUI-plus-MVVM codebase hits. A view model is a plain class and can't read the environment. The view can, but **only once it's installed in the hierarchy**: reading an `@Environment` property in the view's `init` gives you the default value, and SwiftUI logs `Accessing Environment<Value>'s value outside of being installed on a View. This will always read the default value and will not update.` So `_model = State(initialValue: TripModel(trips: trips))` in `init` silently wires the model to the default.

There are three good ways round it:

1. **Create the model once the environment exists**, in `.task`. The view holds an optional model and builds it with the environment's values:

```swift check ios group=env title="Building a view model from environment dependencies"
struct Trip: Sendable {
    let id: String
    let destination: String
}

struct TripsClient: Sendable {
    var trip: @Sendable (String) async throws -> Trip

    static let notInstalled = TripsClient { _ in throw URLError(.unsupportedURL) }
}

extension EnvironmentValues {
    @Entry var tripsClient: TripsClient = .notInstalled
}

@MainActor @Observable final class TripModel {
    private let tripID: String
    private let trips: TripsClient
    private let track: TrackAction
    private(set) var trip: Trip?

    init(tripID: String, trips: TripsClient, track: TrackAction) {
        self.tripID = tripID
        self.trips = trips
        self.track = track
    }

    func load() async {
        trip = try? await trips.trip(tripID)
        track("trip_viewed", ["trip": tripID])
    }
}

struct TripScreen: View {
    let tripID: String
    @Environment(\.tripsClient) private var trips
    @Environment(\.track) private var track
    @State private var model: TripModel?

    var body: some View {
        Group {
            if let trip = model?.trip {
                Text(trip.destination)
            } else {
                ProgressView()
            }
        }
        // Runs once the view is in the hierarchy, so the environment is real; a new tripID builds a new model
        .task(id: tripID) {
            let model = TripModel(tripID: tripID, trips: trips, track: track)
            self.model = model
            await model.load()
        }
    }
}
```

2. **Pass the capability per call**: the view reads `track` from the environment and calls `model.save(using: track)`. It's method injection, fed from the environment, and it suits capabilities only one or two actions need.
3. **Don't read the environment for models at all.** The parent (ultimately the composition root) builds the model with initialiser injection, and the environment is reserved for leaf views. This is the most explicit option and the easiest to test; it costs a little plumbing.

Mixing the three is normal. What doesn't work is a view model reaching for a global because the environment was awkward.

## Environment objects as scoped services

`.environment(basket)` with an `@Observable` object, read with `@Environment(BasketModel.self)`, is the environment's version of a scoped service. Installed at the root of the signed-in tree, as in [Scopes and lifetimes](/design/learn/sd-di-scopes), it's available to every view in the session and to nothing outside it.

Unlike an `@Entry` value, an object has **no default**: a view that reads one nobody installed crashes. For a required dependency that's arguably better than silently using a fake, but it's still a run-time failure, not a compile-time one, and every preview of such a view must install it. A `PreviewModifier` trait (from [Previews as a design tool](/design/learn/sd-swiftui-previews)) installs it in one line. If a view genuinely works without the object, declare it optional, `@Environment(BasketModel.self) private var basket: BasketModel?`, and handle `nil`.

## Where the environment stops

The environment flows down one SwiftUI hierarchy, and some boundaries start a new one:

- A **`UIHostingController`** you create in UIKit starts with a fresh environment: install your capabilities on its root view, ideally from one helper every hosting controller uses.
- A **widget** or **App Intent snippet** is rendered in another process with its own hierarchy, so the app's root never installs anything there.
- **UIKit code** inside SwiftUI reads the environment through the representable's `context.environment`, and can't see it at all once it's been handed to some other object.

Each of those boundaries needs its own small installation step, which is the composition root again, at a smaller scale.

## Trade-offs

| Mechanism | Visible in the signature | If nothing provides it | Readable from view models | Scope | Wins when |
| --- | --- | --- | --- | --- | --- |
| Initialiser parameter | Yes | Compile error | Yes | Whatever the creator decides | The default for models and per-screen services |
| `@Entry` capability | No | The default runs | No: pass it in or build the model in `.task` | The subtree that set it | Cross-cutting actions many views call |
| Environment object | No | Crash (or `nil` if optional) | No | The subtree that set it | Session- or flow-scoped observable models |
| Global or singleton | No | Always "works" | Yes | The process | Almost never in SwiftUI |

<Callout kind="interview">

**What to say:** "Initialisers for view models and services; the environment for capabilities that many views call, like image loading and analytics, each with a default that's safe but visible when it's missing; environment objects for session-scoped models, installed at the root of the signed-in tree. View models get environment dependencies through the view, in `.task` or per call, never by reading globals."

**What to ask:** "How many views need this, and how deep are they? What should happen if it isn't installed: crash, do nothing, or warn?"

**Red flags:** every service in the environment so nothing has initialisers; live defaults that make previews hit production; building view models in `init` from `@Environment` properties.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: previews run your defaults">

Xcode previews execute real code. A preview of a view whose `@Entry` default is the live analytics client sends events from your Mac to the production pipeline every time the canvas refreshes, and a live network default makes previews depend on the server being up. Make side-effecting defaults harmless, and give previews explicit fakes.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: environment reads in init are always the default">

Inside a view's `init`, `@Environment` properties aren't connected yet, so they return the default value, and SwiftUI warns in the console at run time rather than at build time. Anything built in `init` from them is wired to the default for good. Build environment-dependent models in `.task`, or receive the dependency as a parameter instead.

</Callout>
