## Why it matters

Some smells are invisible in any single file. You only see them when the code changes: one file that every kind of change has to touch, or one small change that has to touch a dozen files. Divergent change, shotgun surgery and feature envy are all about *where knowledge lives* compared with *how it changes*. They explain why "a small feature" takes a week, and why a change ships with one place forgotten. Interviewers ask "what did adding that require?" to hear whether you notice.

## Divergent change: one type, many reasons

**Divergent change** is when one type is edited for many unrelated reasons. A `CheckoutViewController` that changes when the tax rules change, when the payment SDK is upgraded, when design refreshes the screen, when analytics renames its events and when a delivery option is added has five reasons to change. Each edit happens next to code that serves another reason, so each one risks breaking something unrelated, and two teams editing it the same week conflict.

It's the [single-responsibility principle](/design/learn/sd-solid-srp) seen through the history. A useful way to find the reasons is to ask *who* asks for changes to this type: the tax team, the payments team and the design team are three different sources of change, so they're three responsibilities.

The fix is **extract class** along those reasons: a `TaxCalculator`, a `PaymentProcessor` that adapts the SDK, a `CheckoutAnalytics`. Each then changes for one kind of request.

## Shotgun surgery: one reason, many types

**Shotgun surgery** is the mirror image: one change needs small edits in many places. A news app adds podcasts as a new content type, and the pull request touches the feed cell factory, the router, the share text, the analytics names, the offline download rules, the search filters and the API decoder. Seven files, often owned by different people.

The cost isn't only the effort. Each place is found by searching, and a missed one usually compiles and ships. Knowledge about "what a content kind is" has been scattered, so no single type can be asked about it.

The fix is to **gather** that knowledge: **move method** and **move field** until one type (`ContentKind`, or one type per kind) owns its cell, its share text, its analytics name and its download rule. Sometimes it's **inline class**: two half-types that always change together become one. Later in this module you'll replace the repeated switches themselves with polymorphism.

Divergent change and shotgun surgery are both cohesion failures: things that change together should live together, and things that change for different reasons should live apart. That's the [common closure principle](/design/learn/sd-principles-package-cohesion) applied inside a module.

## Feature envy: a method that wants to live elsewhere

**Feature envy** is a method more interested in another type's data than in its own. This view model works out the cart's total from the cart's fields:

```swift title="Before: the view model envies the cart"
struct CartSummaryViewModel {
    let cart: Cart

    var totalText: String {
        var pence = cart.lines.reduce(0) { $0 + $1.unitPrice * $1.quantity }
        pence -= pence * (cart.discount?.percentOff ?? 0) / 100
        if pence < cart.freeDeliveryFrom { pence += cart.deliveryFee }
        return format(pence)
    }
}
```

Nothing here uses the view model's own state. The trouble shows up when checkout needs the total too: now the rule exists twice, and the day marketing changes how discounts combine with delivery, one copy is updated and the other isn't. The basket shows one price and the payment sheet another.

The fix is **move method**: put the rule on the type whose data it uses, and leave presentation where it is. It's the same advice as [tell, don't ask](/design/learn/sd-coupling-demeter): ask the cart for its total instead of asking for its parts and doing the sums yourself.

```swift run
struct DiscountCode {
    let percentOff: Int
}

struct Line {
    let unitPrice: Int
    let quantity: Int
}

struct Cart {
    var lines: [Line]
    var discount: DiscountCode?
    var deliveryFee = 399
    var freeDeliveryFrom = 5000

    // Moved here from the view model: the cart's data, so the cart's rule
    var subtotal: Int {
        lines.reduce(0) { $0 + $1.unitPrice * $1.quantity }
    }

    var total: Int {
        let discounted = subtotal - subtotal * (discount?.percentOff ?? 0) / 100
        return discounted >= freeDeliveryFrom ? discounted : discounted + deliveryFee
    }
}

// What's left is presentation: it uses the cart's answer instead of recomputing it
struct CartSummaryViewModel {
    let cart: Cart

    var totalText: String {
        let pence = cart.total % 100
        return "Total: £\(cart.total / 100).\(pence < 10 ? "0" : "")\(pence)"
    }
}

let small = Cart(lines: [Line(unitPrice: 1250, quantity: 2)])
let large = Cart(lines: [Line(unitPrice: 2000, quantity: 3)], discount: DiscountCode(percentOff: 10))
print(CartSummaryViewModel(cart: small).totalText)
print(CartSummaryViewModel(cart: large).totalText)
```

```output
Total: £28.99
Total: £54.00
```

Feature envy isn't absolute. The view model still reads `cart.total`, and that's fine: formatting a price for display is presentation, and it uses the cart's *answer*. Patterns like [strategy](/design/learn/sd-behavioural-strategy) and visitor separate behaviour from data on purpose. Move the **rules**; keep the **presentation**.

## Reading the smells from history

These smells live in how files change together, so git can find them. Tornhill calls it **change coupling**: files that keep appearing in the same commits are coupled whether or not the code says so. Export the history with `git log --since="6 months ago" --format="--%h" --name-only -- '*.swift'`, then count. Here's the counting on a small sample:

```swift run
// Each commit lists the files it touched, as `git log --name-only` prints them
let commits: [[String]] = [
    ["FeedCell.swift", "Router.swift", "ShareText.swift", "Analytics.swift"],
    ["CheckoutViewController.swift"],
    ["FeedCell.swift", "Router.swift", "Analytics.swift"],
    ["CheckoutViewController.swift", "TaxRules.swift"],
    ["FeedCell.swift", "ShareText.swift", "Router.swift"],
    ["CheckoutViewController.swift"],
    ["Router.swift", "FeedCell.swift"],
]

var changes: [String: Int] = [:]
var together: [String: Int] = [:]
for files in commits {
    let sorted = files.sorted()
    for file in sorted {
        changes[file, default: 0] += 1
    }
    for (index, first) in sorted.enumerated() {
        for second in sorted[(index + 1)...] {
            together["\(first) + \(second)", default: 0] += 1
        }
    }
}

// Most first, ties in name order, so the output never depends on dictionary order
func top(_ counts: [String: Int], _ count: Int) -> [(String, Int)] {
    counts.sorted { $0.value != $1.value ? $0.value > $1.value : $0.key < $1.key }
        .prefix(count)
        .map { ($0.key, $0.value) }
}

print("Changed most often:")
for (file, count) in top(changes, 3) {
    print("  \(count)  \(file)")
}
print("Changed together most often:")
for (pair, count) in top(together, 3) {
    print("  \(count)  \(pair)")
}
let wide = commits.filter { $0.count >= 3 }.count
print("Commits touching 3 or more files: \(wide) of \(commits.count)")
```

```output
Changed most often:
  4  FeedCell.swift
  4  Router.swift
  3  CheckoutViewController.swift
Changed together most often:
  4  FeedCell.swift + Router.swift
  2  Analytics.swift + FeedCell.swift
  2  Analytics.swift + Router.swift
Commits touching 3 or more files: 3 of 7
```

Read it like a detective. `FeedCell` and `Router` changed together every time either changed: the knowledge of content kinds is split between them, which is shotgun surgery. `CheckoutViewController` changes often and usually alone; its commit messages will tell you whether those are one reason or five. Real tools (Tornhill's CodeScene, or the open-source code-maat) do the same counting over thousands of commits.

## Trade-offs

| Refactoring | Fixes | Cost | Watch out for | Wins when |
| --- | --- | --- | --- | --- |
| Extract class | divergent change | moderate | new classes that still change together | the history shows distinct reasons |
| Move method or field | feature envy | small | moving display logic into the model | a rule is computed from another type's data |
| Gather into one type | shotgun surgery | small to moderate | building the next god object | the same set of files changes together repeatedly |
| Leave it | nothing | none | the smell spreading | the change is rare, or the code is going away |

<Callout kind="interview">

**What to say:** tie smells to evidence about change. "Adding a content type touched seven files and we missed one, so I gathered what a kind is into one type; adding one is now a new type and a line in a factory, and the compiler checks it." Interviewers remember a concrete before-and-after.

**What to ask:** What changed together in the last few months? Which teams ask for changes to this code? How often does a new case (a plan, a content type, a payment method) get added?

**Red flags:** splitting a type by technical layer instead of by reason to change; "making it DRY" by merging code that only looks alike, so two features that change for different reasons become coupled; ignoring the history and arguing from how the code looks.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: project files drown the signal">

In change-coupling analysis, `project.pbxproj` appears in almost every commit that adds a file, and String Catalogs (`Localizable.xcstrings`) and asset catalogs in most UI changes. Filter them out before counting. Folders that Xcode 16 and later keep in sync with the file system, in place of groups, also stop file additions from editing the project file at all, which helps merges too.

</Callout>

## Practice

**Adding a Family plan** is a pull request that commits shotgun surgery in front of you: a new subscription tier added to every switch the author could find, one missed, and feature envy on the side. Review it, then say what the change tells you about the design.

```cards
- id: divergent-vs-shotgun
  front: "What's the difference between divergent change and shotgun surgery?"
  back: "Divergent change: one type edited for many unrelated reasons (split it). Shotgun surgery: one reason needs edits in many types (gather them)."
- id: feature-envy
  front: "What is feature envy, and the usual fix?"
  back: "A method that works mostly with another type's data. Move the rule onto that type, and keep only presentation where it was."
- id: change-coupling
  front: "How can git history reveal shotgun surgery?"
  back: "Change coupling: files that keep changing in the same commits share knowledge, even if the code doesn't show it."
```
