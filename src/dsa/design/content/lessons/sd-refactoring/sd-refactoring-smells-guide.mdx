## Why it matters

Codebases rarely rot through one bad decision. They rot through hundreds of small, reasonable ones: one more property on the view controller, one more `case` in a switch, one more call to `.shared`. A **smell** is the name for the shape those decisions leave behind. Knowing the names lets you spot trouble in review, explain it in a sentence, and reach for a fix that's known to work. Interviewers show you code like this on purpose, because "what would you change here, and in what order?" is a senior question.

## Smells, anti-patterns and refactorings

This module uses three words precisely.

- A **code smell** is a surface sign that *often* points to a deeper design problem. Kent Beck coined the term, and Martin Fowler's *Refactoring* (1999, second edition 2018) made it famous. A smell isn't a bug, and it isn't always a problem. It's a reason to look closer.
- An **anti-pattern** is a recurring solution that looks reasonable and reliably causes trouble. Massive View Controller and the singleton used as a global variable are the iOS classics. A smell is a symptom; an anti-pattern is a habit that produces it.
- A **refactoring** is a change to a program's structure that doesn't change what it does. Extract method, move method and replace conditional with polymorphism are named refactorings, each with steps small enough that the code works after every one.

That last definition matters more than it looks. If behaviour changes, it isn't a refactoring, and it needs the review and testing that a behaviour change needs. Kent Beck describes this as wearing **two hats**: at any moment you're either adding behaviour or restructuring, and you switch hats between commits, never inside one.

<Callout kind="analogy">

A smell is like an odd noise from a car. It doesn't tell you what's broken, and some noises are harmless. But a mechanic who knows the common ones can say "that's usually the belt" and check there first.

</Callout>

## The field guide

These are the smells this module covers. The groups follow the families Mika Mäntylä drew from Fowler's catalogue: **bloaters** grow too big, **couplers** tie things together that should be apart, and **change preventers** make every change expensive. To those, add the abstraction, API and conditional smells that iOS code meets every day.

| Smell | Seen in iOS as | What it costs | Usual fix |
| --- | --- | --- | --- |
| Massive View Controller, god object | a 3,000-line screen, `AppManager`, `AppDelegate` | every change touches it; can't test parts | extract class, extract child VC |
| Long parameter list, data clump | `search(from:to:date:adults:children:…)` | callers mix up arguments | introduce parameter object |
| Global state, service locator | `Session.shared` deep inside logic | hidden dependencies; tests leak | inject the dependency |
| Feature envy | a view model doing sums on another type's fields | the rule gets copied and drifts | move method |
| Divergent change | one file edited for five unrelated reasons | conflicts; risky changes | extract class |
| Shotgun surgery | one change needs edits in ten files | missed edits ship as bugs | move method; gather into one type |
| Leaky abstraction | a repository that returns `NSManagedObject` | callers depend on what was hidden | map at the boundary |
| Speculative generality | a protocol and generic base class with one user | indirection; wrong guesses | inline; collapse hierarchy |
| Callback pyramid | four nested completion handlers | forgotten completions; unclear threads | async/await |
| Stringly typed | `Notification.Name("cartChanged")`, `[String: Any]` | typos compile | enums, constants, Codable |
| Repeated switch on a type code | `switch item.type` in six files | each new case is shotgun surgery | replace conditional with polymorphism |

The rest of this module takes them a few at a time. For each, you'll learn to recognise it, say what it costs, and remove it in small steps.

## Look at change, not only at code

Reading code finds some smells. Its history finds the ones that matter. A file that's ugly but hasn't changed in two years costs you nothing today; a file that's mildly messy and changes every week costs you every week. Adam Tornhill calls code that is both complex and frequently changed a **hotspot**, and hotspots are where refactoring pays.

You can list candidates in a minute:

```bash
# The Swift files changed most often in the last six months
git log --since="6 months ago" --format= --name-only -- '*.swift' \
  | sort | uniq -c | sort -rn | head -15
```

Then cross-check with signals you already have:

- **Size and shape:** file length, longest function, number of stored properties, how many protocols a type conforms to. SwiftLint's `file_length`, `type_body_length`, `function_body_length`, `cyclomatic_complexity` and `function_parameter_count` rules measure these.
- **Pain:** where crash reports cluster, which files cause merge conflicts, which code people avoid or always ask the same colleague about.
- **Test friction:** "to test this I'd need to log in, mock the network and set a singleton" is a smell report in one sentence.

## Triage: what to do about a smell

Finding a smell is the easy part. Deciding whether to act on it is the skill.

```visual flow
title: Triage for a smell you've noticed
nodes:
  - { id: smell, label: Smell noticed, kind: actor, at: [0, 0] }
  - { id: hot, label: Changes often?, kind: service, at: [2, 0] }
  - { id: note, label: Note it and move on, kind: store, at: [4, 0] }
  - { id: tests, label: Tests pin behaviour?, kind: service, at: [2, 2] }
  - { id: pin, label: Characterise it, kind: service, at: [0, 2] }
  - { id: refactor, label: Small steps, kind: service, at: [2, 4] }
edges:
  - [smell, hot]
  - [hot, note, "no"]
  - [hot, tests, "yes"]
  - [tests, pin, "no"]
  - [pin, refactor]
  - [tests, refactor, "yes"]
steps:
  - say: You notice a smell, say a 2,000-line view controller. The first question isn't how bad it is.
    show: [smell, hot]
    send: smell->hot
  - say: "**Does it change often?** If not, it costs little where it is. Write it down and spend the effort somewhere it pays."
    send: hot->note
  - say: If it's a **hotspot**, ask whether tests pin what it does today, because a refactoring must not change behaviour.
    send: hot->tests
  - say: "No tests? Write **characterisation tests** first: they record what the code does now, right or wrong."
    send: tests->pin
    state: { pin: active }
  - say: Then restructure in **small steps**, running the tests after each one and committing when they pass.
    send: pin->refactor
    state: { pin: null, refactor: ok }
```

Once you've decided to act, the size of the smell decides how:

- **Leave it** when the code is stable, about to be deleted, or a prototype. Note it in a ticket or your design journal and move on.
- **Refactor as you go** when you're about to change that code anyway. Kent Beck's advice is to make the change easy first, then make the easy change. This *preparatory refactoring* is most of the refactoring a healthy team does.
- **Plan it** when the smell is big (a 4,000-line screen, a singleton used in 300 places) and sits in a hotspot. It needs a sequence of shippable steps, sometimes across teams.
- **Rewrite** rarely, and only a part with clear edges. A rewrite throws away years of bug fixes and edge cases the old code learned, and the old code keeps changing while you write the new one.

## Trade-offs

| Response | Cost now | Risk | Wins when |
| --- | --- | --- | --- |
| Note it, leave it | none | the smell spreads by copying | the code is stable or going away |
| Refactor as you go | small, inside feature work | low, with tests | you're changing that code anyway |
| Planned refactor | days to weeks | medium; needs sequencing | a hotspot slows several people |
| Rewrite | large | high: lost edge cases, two versions at once | a bounded part that's beyond repair |

<Callout kind="interview">

**What to say:** describe a smell by its *consequence*, with evidence. "This file changed in 40 of our last 50 pull requests and produces a fifth of our crashes" lands far better than "it's a god object". Then give an order: what you'd fix first, why, and which tests you'd add before touching it.

**What to ask:** How often does this code change? What tests exist? Who else works in it? Can risky changes ship behind a flag?

**Red flags:** "I'd rewrite it" as the first answer; naming smells without saying what they cost; restructuring and changing behaviour in one step; treating a lint threshold as the goal.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: lint numbers are signals, not goals">

Once a `type_body_length` warning becomes a target, people meet it by moving methods into extensions in other files, or by adding `// swiftlint:disable`. The number improves and the design doesn't. Use thresholds to find candidates, then judge each one by how often it changes and whether its parts belong together.

</Callout>

## Practice

**Adding a Family plan** is a good first review for this module: a small pull request where several smells from the table above meet, and one of them has already shipped a bug. Name each smell by what it costs, then put them in the order you'd fix them.

```cards
- id: smell-vs-bug
  front: "Is a code smell a bug?"
  back: "No. It's a surface sign that often points to a design problem: a reason to look closer. Some smells are harmless where they are."
- id: refactoring-definition
  front: "What makes a change a refactoring?"
  back: "It changes structure without changing observable behaviour, in steps small enough that the code works after each one."
- id: hotspot
  front: "Where does refactoring pay off most?"
  back: "In hotspots: code that is both complex and changed often. Messy code that nobody touches costs little."
```

```quiz
- id: q1
  type: sort
  prompt: "Which family does each smell belong to?"
  buckets: [Bloater, Coupler, Change preventer]
  items:
    - [Massive View Controller, 0]
    - [Long parameter list, 0]
    - [Feature envy, 1]
    - [A singleton reached from everywhere, 1]
    - [Shotgun surgery, 2]
    - [Divergent change, 2]
  explain: "Bloaters have grown too big to work with. Couplers tie code to other code it shouldn't depend on so closely. Change preventers make each change expensive: one file changing for many reasons, or one reason needing many files."
- id: q2
  type: mcq
  prompt: "You have time to refactor one of these this sprint. Which do you pick?"
  options:
    - "A 3,000-line legacy importer that hasn't changed in two years and has no open bugs"
    - "A 600-line checkout view model that changes in most sprints and has no tests"
    - "A 200-line helper with poor names that nothing calls any more"
    - "Whichever file has the most SwiftLint warnings"
  answer: 1
  explain: "The checkout view model is a hotspot: it changes often, so every improvement pays back every sprint, and its lack of tests makes each change risky today. The importer is ugly but costs nothing while it's stable. The unused helper should be deleted, which isn't a refactoring. Warning counts find candidates but don't rank them."
- id: q3
  type: truefalse
  prompt: "Renaming a method and fixing an off-by-one bug inside it, in one commit, is a refactoring."
  answer: false
  explain: "The bug fix changes behaviour, so the commit is a behaviour change with a rename mixed in. Split them: rename in one commit (tests unchanged and green), fix the bug in another (with a test that shows the new behaviour). Each is then easy to review and to revert."
- id: q4
  type: multi
  prompt: "Which of these are good evidence that a file deserves refactoring now?"
  options:
    - "It's changed in most pull requests this quarter"
    - "Crash reports cluster in it"
    - "It's written in Objective-C"
    - "Testing any of it needs a real network and a logged-in user"
    - "It's long, but unchanged and bug-free for two years"
  answer: [0, 1, 3]
  explain: "Frequent change, crashes and test friction are costs you pay now. Objective-C isn't a smell in itself, and long but stable code isn't costing you anything; refactor it when you next need to change it."
- id: q5
  type: recall
  prompt: "A colleague proposes rewriting the 4,000-line settings screen from scratch in SwiftUI. What would you ask before agreeing?"
  model: "How often does the screen change, and what does the current code cost us (bugs, crashes, slow changes)? What tests pin its behaviour today, including the edge cases it has learned? Can we move it in parts, one section at a time behind a flag, instead of all at once? Who keeps shipping features in the old screen while the new one is built? What would tell us the rewrite worked?"
```
