## Why it matters

Most refactoring in a real job happens in code without tests: it's the code nobody dared touch, which is why it needs refactoring in the first place. Michael Feathers, in *Working Effectively with Legacy Code* (2004), defines legacy code as exactly that: code without tests. This lesson is how you change it safely anyway. You pin what it does with **characterisation tests**, then restructure it in steps small enough that any mistake shows up straight away. It's also the interview question behind every smell in this module: "there are no tests; how would you change this?"

## Characterisation tests: record what the code does

A **characterisation test** records what code *actually does* today, not what it should do. Before a refactor, that's the only thing that matters: the refactor must not change it. Feathers' recipe is almost mechanical:

1. Call the code from a test.
2. Write an assertion you know is wrong, such as `#expect(points == -1)`.
3. Run it, and let the failure tell you the real value.
4. Change the assertion to that value, and name the test after the behaviour it pins.
5. Repeat for each input that matters: either side of every condition in the code.

Take a loyalty-points rule from a shopping app, with no tests and a history of support tickets:

```swift title="The legacy rule"
func legacyPoints(total: Int, tier: String, firstOrder: Bool) -> Int {
    var points = total / 100
    if tier == "gold" {
        points = points * 2
    } else if tier == "silver" {
        points = points + points / 2
    }
    if firstOrder && total > 2000 {
        points += 50
    }
    if points > 500 {
        points = 500
    }
    return points
}
```

Reading it with the recipe in mind, you find the inputs worth pinning: amounts either side of £20, each tier, a tier name with a capital letter, and totals near the 500 cap. The tests come out like this:

```swift title="Characterisation tests in Swift Testing"
@Suite struct LoyaltyPointsCharacterisation {
    @Test("One point per whole pound; pence are dropped")
    func basePoints() {
        #expect(legacyPoints(total: 1999, tier: "bronze", firstOrder: false) == 19)
    }

    @Test("Silver earns half as much again, rounded down")
    func silver() {
        #expect(legacyPoints(total: 1500, tier: "silver", firstOrder: false) == 22)
    }

    @Test("The first-order bonus needs more than £20: exactly £20 gets none (current behaviour)")
    func firstOrderThreshold() {
        #expect(legacyPoints(total: 2000, tier: "bronze", firstOrder: true) == 20)
        #expect(legacyPoints(total: 2001, tier: "bronze", firstOrder: true) == 70)
    }

    @Test("Tier names are case-sensitive: \"Gold\" earns base points (current behaviour)")
    func tierCase() {
        #expect(legacyPoints(total: 1000, tier: "Gold", firstOrder: false) == 10)
    }

    @Test("The 500 cap applies after the first-order bonus")
    func capAfterBonus() {
        #expect(legacyPoints(total: 24900, tier: "gold", firstOrder: true) == 500)
    }
}
```

Two of those tests say "current behaviour" because the behaviour looks like a bug. Characterisation tests record bugs too, deliberately. A refactor that quietly fixes one is a behaviour change hiding inside a refactor: someone's points change and nobody decided they should. Record it, tell the product owner, and fix it later on purpose, in its own pull request, where the test diff shows exactly who is affected.

<Callout kind="analogy">

Characterisation tests are the photos you take of a room before you move the furniture. They don't say the room was arranged well, only how it was, so that afterwards you can tell what moved.

</Callout>

## Golden masters: many inputs at once

Hand-written tests capture the cases you thought of. For a function with many paths, add a **golden master** (also called approval testing): run the legacy code over a large set of inputs, keep its outputs, and compare the refactored code against them. Here, the legacy function itself is the oracle, and two candidate refactors are checked against it:

```swift run
// The legacy rule, untouched: it's the oracle
func legacyPoints(total: Int, tier: String, firstOrder: Bool) -> Int {
    var points = total / 100
    if tier == "gold" {
        points = points * 2
    } else if tier == "silver" {
        points = points + points / 2
    }
    if firstOrder && total > 2000 {
        points += 50
    }
    if points > 500 {
        points = 500
    }
    return points
}

// Two refactored candidates. One of them changed behaviour.
func refactoredPoints(total: Int, tier: String, firstOrder: Bool) -> Int {
    let base = total / 100
    let earned = base + tierBonus(base, tier)
    let bonus = firstOrder && total > 2000 ? 50 : 0
    return min(earned + bonus, 500)
}

func hastyPoints(total: Int, tier: String, firstOrder: Bool) -> Int {
    let base = total / 100
    let earned = min(base + tierBonus(base, tier), 500)
    return earned + (firstOrder && total > 2000 ? 50 : 0)
}

func tierBonus(_ base: Int, _ tier: String) -> Int {
    switch tier {
    case "gold": base
    case "silver": base / 2
    default: 0
    }
}

// The golden master: every combination of values either side of each condition
func differences(_ candidate: (Int, String, Bool) -> Int) -> [String] {
    var found: [String] = []
    for total in [0, 99, 100, 1999, 2000, 2001, 24900, 25000, 26000] {
        for tier in ["bronze", "silver", "gold", "Gold", ""] {
            for firstOrder in [false, true] {
                let expected = legacyPoints(total: total, tier: tier, firstOrder: firstOrder)
                let actual = candidate(total, tier, firstOrder)
                if actual != expected {
                    found.append("total \(total), tier \(tier), first order \(firstOrder): legacy \(expected), new \(actual)")
                }
            }
        }
    }
    return found
}

for (name, candidate) in [("refactoredPoints", refactoredPoints), ("hastyPoints", hastyPoints)] {
    let found = differences(candidate)
    print("\(name): \(found.count) differences in 90 orders")
    if let first = found.first {
        print("  first: \(first)")
    }
}
```

```output
refactoredPoints: 0 differences in 90 orders
hastyPoints: 3 differences in 90 orders
  first: total 24900, tier gold, first order true: legacy 500, new 548
```

`hastyPoints` looks equally tidy, but it caps before adding the bonus, so gold customers near the cap could earn more than 500. Nobody would spot that in review. The named test `capAfterBonus` catches it only because someone thought to write it; the golden master caught it without anyone having to, in milliseconds.

The trick is choosing inputs: take every literal the code compares against and use the values either side of it (1999, 2000, 2001), plus every distinct string it tests and one it doesn't. Swift Testing helps: `@Test(arguments: totals, tiers)` runs a test for every combination of two collections.

Golden masters pin *everything*, including behaviour you'll want to change later, so treat them as scaffolding for the refactor. Keep the named tests afterwards; retire the golden master once the new code has shipped and the old one is deleted. For views, snapshot tests play the same role; you'll meet them in D59.

## Seams: getting the code into a test

Often you can't call the code from a test at all: it creates its own `URLSession`, reads `Date()`, or reaches for a singleton. Feathers calls the way in a **seam**: a place where you can change what the code does without editing it there. Swift gives you several:

- **A parameter with a default value.** Existing callers don't change, and tests pass their own value. It's the cheapest seam and usually the first.
- **An extracted protocol** for a dependency, injected through the initialiser. That's the next-but-one lesson in this module.
- **A closure**, such as `let now: () -> Date`, for one function's worth of behaviour.
- **Subclass and override** for classes you can't otherwise reach, such as a view controller: move the awkward call into its own method, and override it in a test subclass.
- **Extract a pure function**: lift the logic out of the method that does I/O, and test the logic directly. That's [functional core, imperative shell](/design/learn/sd-functional-core-shell) applied to legacy code.

```swift check title="A seam with a default"
import Foundation

struct Coupon {
    let expires: Date
}

// Before: `coupon.expires > Date()` inside the method, so a test can't choose the time.
// After: the time is a parameter with a default. Callers don't change; tests pass a fixed date.
func isUsable(_ coupon: Coupon, now: Date = .now) -> Bool {
    coupon.expires > now
}
```

Opening a seam is itself a change to untested code, so make it the smallest, most mechanical change you can, ideally with the IDE doing it. You'll study seams systematically in D58.

## Small steps

With behaviour pinned, the refactor itself is a rhythm: make one small structural change, run the tests, and commit if they pass. If they fail, **revert**: don't debug a refactoring. A failure means the step was bigger than you thought, so undo it and take a smaller one. Step through the rhythm:

```visual states
title: The refactoring loop
states:
  - { id: untested, label: Untested code, at: [0, 0] }
  - { id: pinned, label: Behaviour pinned, at: [2, 0] }
  - { id: changing, label: One small change, at: [4, 0] }
  - { id: red, label: Tests fail, at: [4, 2] }
  - { id: committed, label: Committed, at: [2, 2] }
  - { id: done, label: Shipped, at: [0, 2] }
initial: untested
final: [done]
transitions:
  - [untested, pinned, characterise]
  - [pinned, changing, edit]
  - [changing, committed, runTests, pass]
  - [changing, red, runTests, fail]
  - [red, pinned, revert]
  - [committed, changing, edit]
  - [committed, done, ship]
events:
  - { event: characterise, say: "First, characterisation tests and a golden master pin what the code does today." }
  - { event: edit, say: "Make **one** structural change, such as extracting a method or renaming a type." }
  - { event: runTests, guard: pass, say: "The tests pass, so commit. The commit message names the refactoring." }
  - { event: edit, say: "Take the next small step from a known-good state." }
  - { event: runTests, guard: fail, say: "This step broke something. It was bigger than it looked." }
  - { event: revert, say: "**Revert** rather than debug: you're back at green in seconds, and you know the step to split." }
  - { event: edit, say: "Try a smaller version of the same step." }
  - { event: runTests, guard: pass, say: "Green again. Commit." }
  - { event: ship, say: "Ship the refactor on its own, before or after the feature that needed it, never mixed into it." }
```

Techniques that keep steps small:

- **Let the tools make the edit.** Xcode's Refactor menu (Rename, Extract to Method, Extract to Variable) changes every reference mechanically, which is safer than hand edits.
- **One refactoring per commit**, named in the message ("Extract method `tierBonus`"), and never mixed with a behaviour change: the two hats from the start of this module.
- **Parallel change** for anything with many callers: *expand* (add the new API beside the old), *migrate* callers in batches, then *contract* (delete the old one). The deprecated wrapper from the callbacks lesson was one.
- **Sprout and wrap.** When you must add behaviour to untested code, write it as a new, tested function or type (sprout) and call it from the old code, or wrap the old method in a new one that adds behaviour before or after. The old code is touched in one line.
- **The Mikado method.** When a change sets off a cascade of compile errors, revert, write down the prerequisite the errors revealed, and do that first. The prerequisites form a graph you can work through leaf by leaf, keeping the build green.
- **Feature flags for risky swaps.** Ship old and new code side by side behind a remote flag, compare their results in production if you can, and roll back by turning the flag off.

## Trade-offs

| Safety net | Setup | Catches | Brittleness | Wins when |
| --- | --- | --- | --- | --- |
| Named characterisation tests | a test per behaviour | the cases you thought of | low | logic with a few important rules |
| Golden master | low, once you have inputs | almost any change in output | high: pins everything | pure logic with many paths, before a restructure |
| Snapshot tests | moderate: fixtures, devices, Dynamic Type sizes | visual changes | medium to high | screens you're restructuring |
| UI tests | high | broken flows end to end | high: slow and often flaky | a few critical paths, such as checkout |
| A written manual checklist | none | what's on the list | n/a | the last resort, before a seam exists |

Most refactors use two: named tests for the rules people care about, and a golden master or snapshots for everything else.

<Callout kind="interview">

**What to say:** "First I'd pin the current behaviour: find a seam to call the code, write characterisation tests for each condition, and add a golden master over the boundary values. Then I'd refactor in small, committed steps, keeping the tests green, and ship the refactor separately from any behaviour change." Mention what you'd do with surprising behaviour: record it, raise it, fix it separately.

**What to ask:** Is any of this covered by tests already, even UI tests? How is it released, and can risky changes go behind a flag? Who owns the behaviour if a test reveals something that looks like a bug?

**Red flags:** refactoring with no safety net "because it's only moving code"; fixing bugs inside the refactor; one giant pull request; debugging a red step instead of reverting it.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: characterisation tests that pass only on your Mac">

Code that formats dates, prices or names usually depends on `Locale.current`, `TimeZone.current`, `Calendar.current` or `Date()`. Characterise it on your machine and the tests fail on a CI runner in another region, or after midnight. Pin those inputs in the test (through seams), so the recorded behaviour is the code's, not the machine's.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: parallel tests and legacy globals">

Swift Testing runs tests in parallel by default. Legacy code that reads or writes shared state (singletons, `UserDefaults.standard`) gives characterisation tests that pass alone and fail together. Mark such a suite `.serialized` as a stopgap, and treat removing the shared state as part of the refactor.

</Callout>

## Practice

The **delivery fee kata** is this lesson end to end: a tangled legacy function with quirks, a golden master over 7,560 orders, and named tests that pin each quirk. Rewrite it so a new country is a one-line change, without changing a single fee. Then **take apart a 3,800-line product page** asks you to plan the same discipline at the scale of a whole screen and four teams.

```cards
- id: characterisation
  front: "What does a characterisation test check?"
  back: "What the code does today, right or wrong, so a refactor can prove it changed nothing. Surprising behaviour is recorded and named, then fixed separately."
- id: golden-master
  front: "What is a golden master, and when do you retire it?"
  back: "Recorded outputs for many inputs (or the legacy code as an oracle), compared after each change. It pins everything, so retire it once the refactor has shipped; keep the named tests."
- id: red-step
  front: "A refactoring step turns the tests red. What do you do?"
  back: "Revert to the last green commit and take a smaller step. Debugging a refactor wastes time and hides what went wrong."
- id: seam
  front: "What's the cheapest seam for code that calls `Date()` or `.shared`?"
  back: "A parameter with a default value (`now: Date = .now`): callers don't change, and tests pass their own value."
```
