## Why it matters

A request with no sensible timeout is a spinner that never ends. A request that keeps running after the user has left the screen wastes battery and data, and when it finally answers, it can overwrite newer state with stale results. **Timeouts** bound how long one call may take, **deadlines** bound how long a whole operation may take, retries included, and **cancellation** stops work nobody wants any more, all the way down. Interviewers probe all three with one question: "the user taps Back while three requests and a retry are in flight; what happens?"

## Timeouts in URLSession

`URLSession` has two timeouts, and neither is "how long the user will wait":

| Setting | Default | What it limits |
| --- | --- | --- |
| `timeoutIntervalForRequest` (or `URLRequest.timeoutInterval`) | 60 s | How long to wait for **more data**. It restarts whenever bytes arrive, so a slow trickle never trips it. |
| `timeoutIntervalForResource` | 7 days | The **whole transfer**, from start to finish |

A response that sends a byte every 50 seconds never times out on the first, and finishes long before the second. Neither matches a screen whose user gives up after a few seconds. So:

- **Lower the request timeout** for interactive calls. 60 seconds of silence is far beyond anyone's patience; 10–15 s is common.
- **Choose from data, not instinct.** Look at the endpoint's latency on real networks: if 99% of responses arrive within 1.5 s, a 5 s timeout fails rarely and fails fast. A timeout below the slow tail fails users on slow networks every time.
- **Add a total limit of your own** where the user is waiting: a race between the work and a timer, shown later in this lesson.
- **Keep long transfers on idle timeouts.** A 200 MB upload legitimately takes minutes; what matters is that it keeps making progress.

## Timeouts versus deadlines

A **timeout** is per attempt: "this call gets 3 seconds". A **deadline** is an absolute moment for the whole operation: "the feed must be on screen, from cache if need be, 8 seconds after the user opened it". Every step, every retry and every nested call shares the same deadline.

Without a deadline, a retry policy multiplies the wait: four attempts with 10-second timeouts and backoff between them is close to a minute of spinner. With one, each attempt takes the smaller of its own cap and whatever time is left, and when no time is left the operation stops and the screen shows its fallback.

### Propagating a deadline in Swift

You could pass a deadline through every function, but it would touch every signature between the screen and the HTTP client. A **task-local** value is the idiomatic alternative: `@TaskLocal` declares a value that's visible to the task that sets it and inherited by its child tasks (and by `Task { }` created inside, though not by detached tasks). The screen sets the budget once; the API client reads it before every attempt.

First, the timeout itself, a race between the operation and a timer in a task group:

```swift check group=deadline title="WithTimeout.swift"
struct TimedOut: Error {}

/// Runs `operation`, cancelling it and throwing `TimedOut` if it hasn't finished within `limit`
func withTimeout<T: Sendable>(_ limit: Duration, _ operation: @escaping @Sendable () async throws -> T) async throws -> T {
    try await withThrowingTaskGroup(of: T.self) { group in
        group.addTask {
            try await operation()
        }
        group.addTask {
            try await Task.sleep(for: limit)
            throw TimedOut()
        }
        // The first child to finish decides. Cancel the other, and the group waits for it to stop.
        defer { group.cancelAll() }
        guard let first = try await group.next() else { throw CancellationError() }
        return first
    }
}
```

Then the budget that every attempt draws from:

```swift check group=deadline title="RequestBudget.swift"
import Foundation

struct DeadlineExceeded: Error {}

enum RequestBudget {
    /// When the current user-facing operation must be finished. Task-local, so every layer below can
    /// read it without changing a signature, and child tasks inherit it.
    @TaskLocal static var deadline: ContinuousClock.Instant?

    /// Runs `operation` with a deadline `duration` from now, or the caller's deadline if that's sooner
    static func within<T: Sendable>(_ duration: Duration, _ operation: @Sendable () async throws -> T) async throws -> T {
        let mine = ContinuousClock.now + duration
        let effective = deadline.map { min($0, mine) } ?? mine
        return try await $deadline.withValue(effective) {
            try await operation()
        }
    }

    /// How long the next attempt may take: its own cap or whatever is left, whichever is less
    static func timeout(cappedAt cap: Duration) throws -> Duration {
        guard let deadline else { return cap }
        let remaining = ContinuousClock.now.duration(to: deadline)
        guard remaining > .zero else { throw DeadlineExceeded() }
        return min(cap, remaining)
    }
}

// In the API client: every attempt takes its timeout from the budget
func send(_ request: URLRequest, session: URLSession) async throws -> (Data, URLResponse) {
    let timeout = try RequestBudget.timeout(cappedAt: .seconds(3))
    var request = request
    // Tell the server too, so it can stop work the app will never read
    request.setValue(String(Int(timeout / .milliseconds(1))), forHTTPHeaderField: "X-Request-Timeout-Ms")
    let attempt = request
    return try await withTimeout(timeout) {
        try await session.data(for: attempt)
    }
}

// At the top, the screen sets the budget once; retries and nested calls share it
func loadFeed(session: URLSession, request: URLRequest) async throws -> Data {
    try await RequestBudget.within(.seconds(8)) {
        try await send(request, session: session).0
    }
}
```

Two details are easy to miss. A nested `within` can only **shorten** the deadline, never extend it: an inner layer doesn't get more time than its caller has. And the header passes the budget to the server, as gRPC does with its `grpc-timeout` header, so the backend can abandon work whose answer will arrive after the app has stopped listening. The header name here is illustrative; agree one with your backend.

## Cancellation propagation

Swift's cancellation is **cooperative**. Cancelling a task doesn't stop it: it sets a flag, and the task's code notices. Most of the noticing is done for you, because the APIs you await check the flag: `Task.sleep` throws `CancellationError`, `URLSession` cancels its request and throws `URLError(.cancelled)`, and a `for await` loop over an `AsyncStream` ends. In your own long-running loops, call `try Task.checkCancellation()` or check `Task.isCancelled`.

**Structured** concurrency, which you met in [Futures and promises vs async/await](/design/learn/sd-resilience-futures-async), makes cancellation propagate. Cancelling a task cancels all of its child tasks (`async let` and task-group children), and theirs, down the tree. An **unstructured** `Task { }` isn't a child of anything, so cancelling the code that created it doesn't reach it:

The same tree in code. The screen's task is cancelled at once, and the program waits for it to finish:

```swift run title="CancellationTree.swift"
actor Log {
    private var lines: [String] = []
    func add(_ line: String) { lines.append(line) }
    var sorted: [String] { lines.sorted() }
}

// Stands in for a request that would take a minute
func load(_ name: String, log: Log) async {
    do {
        try await Task.sleep(for: .seconds(60))
        await log.add("\(name): finished")
    } catch {
        await log.add("\(name): cancelled")
    }
}

let log = Log()
let screen = Task {
    async let profile: Void = load("profile", log: log)
    async let feed: Void = withTaskGroup(of: Void.self) { group in
        for image in 1...3 {
            group.addTask { await load("image \(image)", log: log) }
        }
    }
    let analytics = Task { await load("analytics", log: log) } // unstructured: not a child
    _ = await (profile, feed)
    return analytics
}

screen.cancel()                     // the user leaves the screen
let analytics = await screen.value  // returns once every child has stopped
for line in await log.sorted {
    print(line)
}
print("Unstructured analytics task cancelled too:", analytics.isCancelled)
analytics.cancel()
```

### Where cancellation comes from on iOS

- **SwiftUI** cancels a `.task` when its view disappears, and a `.task(id:)` whenever the id changes. Starting work there gives you propagation for free.
- **UIKit** gives you nothing automatic. Store the `Task` handles a view controller starts and cancel them in `viewDidDisappear(_:)` or `deinit`.
- **Background tasks** come with a deadline from the system. A `BGTask`'s `expirationHandler` is iOS saying time is up: cancel your work there, then call `setTaskCompleted(success:)`.
- **The user**, through a Cancel button that calls `task.cancel()` on the handle you kept.

### Connecting cancellation to callback APIs

A continuation-based wrapper around an old callback API ignores cancellation unless you connect it. `withTaskCancellationHandler` runs its `onCancel` closure when the task is cancelled, and that's where you cancel the underlying request:

```swift check title="PlacesClient+Async.swift"
import Foundation
import Synchronization

/// An older SDK: a callback API whose requests can be cancelled
final class PlacesClient: Sendable {
    final class Request: Sendable {
        /// Stops the search; the SDK then calls the completion with a cancellation error
        func cancel() {}
    }

    func search(_ text: String, completion: @escaping @Sendable (Result<[String], any Error>) -> Void) -> Request {
        completion(.success([text]))
        return Request()
    }
}

extension PlacesClient {
    func search(_ text: String) async throws -> [String] {
        // Shared by the operation and the cancellation handler, which may run at the same moment
        let pending = Mutex<(request: Request?, cancelled: Bool)>((nil, false))
        return try await withTaskCancellationHandler {
            try await withCheckedThrowingContinuation { continuation in
                let request = search(text) { result in
                    continuation.resume(with: result)
                }
                let cancelledAlready = pending.withLock { state in
                    state.request = request
                    return state.cancelled
                }
                // The task was cancelled before there was a request to cancel: do it now
                if cancelledAlready { request.cancel() }
            }
        } onCancel: {
            let request = pending.withLock { state in
                state.cancelled = true
                return state.request
            }
            request?.cancel()
        }
    }
}
```

The lock and the `cancelled` flag aren't ceremony; the gotcha below explains the race they close.

### What cancelled code should do

Stop quickly, and leave things tidy: delete the half-written temporary file, release the camera. Don't update the UI, which may belong to a screen that's gone. Don't show an error: the user caused it. Don't log it as a failure or count it in a circuit breaker, and never retry it.

## Choosing timeouts and cancellation

| Mechanism | Bounds | Cost if it's wrong | Wins when |
| --- | --- | --- | --- |
| `timeoutIntervalForRequest` | Silence between bytes | Too long: endless spinners; too short: failures on slow networks | Every request, tuned per session |
| `timeoutIntervalForResource` | One whole transfer | Too short kills legitimate big transfers | Large downloads and background sessions |
| A race-based timeout | One call, total | Returns only when the work stops: needs cooperative work | A user waiting on one specific call |
| A deadline (task-local) | The whole operation, retries included | Needs every layer to read it | Screens with retries and nested calls |
| Structured cancellation | Work nobody wants | Unstructured tasks escape it | Everything tied to a screen or a user action |

<Callout kind="interview">

**Say** three things: "Interactive calls get short request timeouts chosen from real latency data; the screen gets a deadline that retries share, with a cached fallback when it passes; and all of it runs as child tasks of the view's `.task`, so leaving the screen cancels every request." Mention passing the remaining budget to the server. **Ask** what the latency distribution of the slow endpoint is, and what the screen can show when the deadline passes. **Red flags:** the default 60-second timeout on a search box, retries that each restart the clock, `Task { }` per request with no handles kept, and cancellations shown to the user as errors.

</Callout>

<Callout kind="gotcha" title="iOS gotcha: the request timeout isn't a total timeout">

`URLRequest.timeoutInterval = 10` doesn't mean "give up after 10 seconds". It means "give up after 10 seconds without receiving anything". A server that streams a byte every few seconds, or a captive portal that dribbles out a login page, keeps the request alive indefinitely. When the user is waiting on the answer, add a total limit: a race-based timeout or a deadline.

</Callout>

<Callout kind="gotcha" title="Swift gotcha: onCancel can run before the work starts">

If the task is already cancelled when `withTaskCancellationHandler` begins, `onCancel` runs straight away, before the operation has created its request, and it runs on whichever thread called `cancel()`, at the same moment as your code. A handler that only cancels "the current request" then finds nothing, the request starts anyway, and nothing ever stops it. Record the cancellation in shared state under a lock, and have the operation check it once the request exists, as `PlacesClient` does above.

</Callout>
