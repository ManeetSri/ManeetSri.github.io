<Brief>

You've joined **FreshCart**, a grocery delivery company, as a senior iOS engineer. Customers order from partner supermarkets in the customer iOS app (there are also Android and web apps). Personal **shoppers** pick the items in store with a separate Shopper iOS app, then deliver them.

The customer app lets people browse a store's catalogue (about 40,000 products), fill a basket, choose a delivery slot and pay with Apple Pay. While the order is being picked, a **Live Activity** shows its progress on the Lock Screen, and a **Home Screen widget** shows the next delivery slot. When an item is out of stock, the shopper proposes a substitute and the customer gets a **push notification** with the product's photo and Approve and Reject buttons. If the customer has push turned off, they get a text message instead.

Scale: 400,000 customers order each week; about 60,000 orders a day, peaking on Sunday evenings; up to 3,000 shoppers working at once. The backend is a set of services behind an API gateway. Stock levels come from each partner's own inventory system.

Two groups will read what you write:

- **Six iOS engineers** joining next month need an onboarding page: what the pieces are, and which ones their code talks to.
- **The security team** reviews the substitutions-by-push feature in three weeks, and wants to know where customers' personal data goes.

Write the **C4 system context and container views** as structured text: the elements and the relationships, as you'd put them into Structurizr DSL or a design doc. The workspace sections are for a component design, so use them like this:

- **Requirements and scope:** the audience, what each view must answer, and where the system boundary is.
- **Public API:** the **relationships**: every arrow, as from → to, its intent, its technology, and whether it's synchronous.
- **Internals:** the **elements**: people and external systems for the context view; each container with its type, technology and responsibility for the container view.
- **Concurrency and state:** **data ownership**: which container owns which data, what's shared between containers on the device, and the source of truth for an order.
- **Failure and edge cases:** the failure and asynchronous paths the views must show.
- **Testing:** how you'd check the views against reality now, and keep them true.
- **Trade-offs:** what you left out, and why.

Spend about 30 minutes.

</Brief>

<ModelAnswer section="requirements">

**Two readers, two questions, so two views drawn from one model.**

- New iOS engineers: *what are the parts, and which ones does the customer app talk to?* They need the container view, with the customer side in detail.
- Security: *where does personal data go, and what's new with substitutions-by-push?* The context view shows every outside party; the container view shows which containers hold or send personal data. I'd offer them a data-flow diagram of the substitution flow as a follow-up, because that's the question they really have.

**The system boundary:** FreshCart is everything we build and run: the customer and shopper iOS apps and their extensions, the Android and web apps, the API gateway, our services, their databases and our event bus. **External:** partner inventory systems, the payment provider, APNs, the SMS provider, the maps and routing provider, and the analytics vendor.

**Out of scope for these views:** the shopper app's internals, the Android and web apps' internals (shown as one box each, because they share the API and its versioning), backend infrastructure (load balancers, replicas: that's a deployment view), and individual endpoints.

Every view gets a title with scope and date: *FreshCart: containers (customer side), app 7.2, May.*

</ModelAnswer>

<ModelAnswer section="api">

**Context view relationships** (no technology at this level):

- Customer → FreshCart: orders groceries, tracks deliveries, approves substitutions.
- Shopper → FreshCart: picks and delivers orders, proposes substitutions.
- Support agent → FreshCart: refunds and resolves missing items.
- FreshCart → Payment provider: authorises payments at checkout, captures the final amount after picking.
- FreshCart → Partner inventory systems: reads stock levels and prices.
- FreshCart → APNs: sends notifications and Live Activity updates. APNs → Customer: delivers them.
- FreshCart → SMS provider: sends delivery texts when push is off.
- FreshCart → Maps and routing: gets routes and arrival times.
- FreshCart → Analytics vendor: sends product analytics events.

**Container view relationships**, direction from whoever starts the conversation:

- Customer app → API gateway: browses, fills basket, checks out, tracks orders, answers substitutions · HTTPS/JSON · synchronous.
- Customer app → Image CDN: loads product images · HTTPS.
- Customer app → App Group container: writes the next slot and the current order summary · file.
- Widget extension → App Group container: reads them · file.
- Customer app and notification service extension → shared Keychain group: read the access token.
- Notification service extension → Image CDN: downloads the substitute's photo to attach to the notification · HTTPS.
- API gateway → Catalogue, Order and Dispatch services: routes requests · HTTPS (internal).
- Order service → Orders DB: reads and writes orders · SQL. Order service → Payment provider: authorise and capture · HTTPS.
- Order service → Event bus: publishes *order updated* and *substitution proposed* · async.
- Notification service ← Event bus: consumes those events · async. Notification service → APNs: alerts and Live Activity updates · HTTP/2 · async. Notification service → SMS provider: texts · HTTPS · async.
- APNs → notification service extension (alerts with `mutable-content`) and → widget extension's Live Activity: delivers · async, not guaranteed.
- Catalogue service ← Partner inventory systems: imports stock and prices on a schedule · batch.
- Shopper app → API gateway: pick list, proposes substitutions, marks delivered · HTTPS/JSON.
- Dispatch service → Maps and routing: routes and ETAs · HTTPS.
- Customer app → Analytics vendor: events, through the vendor's SDK in the app · HTTPS, batched · async.

</ModelAnswer>

<ModelAnswer section="concurrency">

- **The source of truth for an order is the Order service and its database.** Everything on the phone is a copy: the app's cache of recent orders, the widget's summary file, and the Live Activity's content state (status and ETA only). The views should label those as copies, so nobody builds a feature on the widget's file.
- **The basket** lives on the server so it follows the customer across devices; the app keeps a local copy for instant edits, and the server wins on price and stock when they disagree.
- **A substitution decision** is owned by the Order service. It can arrive from the notification's button (the app is launched in the background to send it) or from the app's own screen, so the request carries an idempotency key and the second answer is ignored.
- **The access token** sits in the shared Keychain group because the notification extension needs it to fetch the photo from an authenticated endpoint. The widget extension doesn't get it.
- **Personal data:** names, addresses and phone numbers are in the Orders DB and go to the shopper app only for active orders; the shopper's location is shared with the customer only during delivery. The analytics vendor must receive none of them, which is the first thing security will check.

</ModelAnswer>

<ModelAnswer section="failure">

The views should show, with dashed arrows and short notes:

- **Push isn't guaranteed.** A substitution notification can arrive late or never, so the app pulls pending substitutions when opened, and the shopper app applies the customer's stated preference after a timeout. Draw both paths.
- **The notification service extension has about 30 seconds** to change a notification. If the photo download fails or runs out of time, the text-only notification is delivered.
- **Live Activity push updates are budgeted** by the system, so the Notification service sends meaningful changes (picked, out for delivery, new ETA), not every scan.
- **SMS is the fallback** when push is off: a separate arrow, so security sees the phone number leave the system.
- **Payment is two steps:** authorise at checkout, capture after picking, because substitutions change the total. A label on that arrow saves a support incident.
- **Stale stock** from a partner feed causes substitutions; a note on the import arrow says how often it runs.
- **Offline customer:** the app shows the cached order and can't answer a substitution; the timeout path covers it.

</ModelAnswer>

<ModelAnswer section="testing">

- **Check it now:** compare containers with the Xcode targets (each extension target is a container), the backend's deployment configuration (services and databases), the gateway's route table (who calls whom), and the app's package list (every SDK that sends data somewhere).
- **Keep it true:** write the model in Structurizr DSL in the repository, generate both views from it, and put the date and app version in the titles. Changes to the model are reviewed in the same pull requests as the code.
- **Automate the cheap checks:** a CI script that fails when a new extension target or a new third-party SDK appears without a matching element in the model.
- **Test it on readers:** walk one new joiner through "approve a substitution" using only the container view, and ask security which questions it didn't answer. Each gap is either an arrow to add or a separate diagram to draw.

</ModelAnswer>

<ModelAnswer section="tradeoffs">

- **Two views from one model, rather than one diagram:** the readers ask different questions, and one model keeps names consistent across views.
- **Left out:** the shopper app's internals, the Android and web internals, backend infrastructure, endpoints and event schemas. Each belongs in another view (component, deployment) or in the API docs.
- **Kept the event bus**, although it's backend detail, because it explains how an order change becomes a push, and security needs to know which services consume order data.
- **Drew the App Group, Keychain group and extensions as containers.** That's slightly more than C4's usual container, but they're the integration points that break, and the security question is about them.
- **A container view isn't the right picture for security.** I'd draw them a data-flow diagram of the substitution flow, with trust boundaries at the device, our backend and each vendor.

</ModelAnswer>

<Pitfalls>

- Drawing one "iOS app" box, so the widget, the Live Activity and the notification extension have no way to get their data.
- Putting classes, view models or endpoints on the container view.
- One "Backend" box, which hides that notifications are driven by events from the Order service.
- Leaving out the analytics SDK's arrow to its vendor: the one data flow security most needs to see.
- Arrows without labels or direction, and no date on the views.

</Pitfalls>
