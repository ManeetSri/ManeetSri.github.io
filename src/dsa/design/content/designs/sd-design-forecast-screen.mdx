<Brief>

You're the iOS engineer on a small team building a weather app. The first feature is the **forecast screen**: current conditions, the next 24 hours by the hour, and the next 7 days, for one saved place.

What matters to the product team:

- It opens **instantly**. People check the weather on the way out of the door.
- It **still works with a bad connection**, on a train or in a lift. Something sensible must show.
- The data is **fresh enough**: weather providers update forecasts about every 15 minutes.

What you know about scale: about 2 million people use the app each month, most of them between 6 and 9 in the morning. A forecast response is around 15 KB of JSON. The team already has a weather API that returns everything for one place in a single call.

Design the feature. Spend about 30 minutes, and write in the sections on the right as if explaining it to a colleague. Rough notes are fine.

</Brief>

<ModelAnswer section="requirements">

Questions worth asking first: how fresh must it be? Do we show **one** place or many? Is location detection in scope? Are there severe-weather alerts that must never be stale? Assume one saved place, no alerts yet.

- **Functional:** show current conditions, 24 hourly and 7 daily entries for the saved place; pull to refresh.
- **Non-functional:** first paint in under ~300 ms from launch on a warm device; works offline with the last forecast; data no older than ~15–30 minutes when online; small on the wire.
- **Out of scope:** multiple places, alerts, widgets (but don't design them out).

</ModelAnswer>

<ModelAnswer section="architecture">

On the device: the **Forecast screen** reads from a **ForecastRepository**, which serves the last forecast from a **disk cache** straight away and asks the **API client** for a fresh one in the background. The server already exists: one `GET /forecast?place=…` call.

The key idea is **stale-while-revalidate**: show what you have immediately, then update in place when the network answers.

</ModelAnswer>

<ModelAnswer section="client">

- **View layer:** a SwiftUI `ForecastView` that renders a `ForecastViewState` enum: `.loading`, `.loaded(Forecast, updatedAt)`, `.failed(message)`.
- **View model** (`@Observable`): asks the repository for a stream of forecasts and maps them to view state, including an "Updated 12 min ago" label.
- **Repository:** returns cached data first, then fresh data. It's the only type that knows both the cache and the API exist.
- **API client and cache** are injected, so tests replace them with stubs.

</ModelAnswer>

<ModelAnswer section="api">

`GET /forecast?lat=…&lon=…` returning current, hourly and daily arrays plus `issuedAt`. Support `ETag` / `If-None-Match`: when nothing changed the server answers `304` and the app sends no body at all, which matters for 2 million morning check-ins. Errors use standard status codes; the client treats any failure as "keep showing the cache".

</ModelAnswer>

<ModelAnswer section="data">

One cached record per place: the decoded `Forecast`, the `ETag`, and `fetchedAt`. A Codable file in the Caches directory is enough: it's small, rewritten whole, and losing it only costs one network call. No database needed for one place; revisit if the app grows to many places with search.

</ModelAnswer>

<ModelAnswer section="deepdive">

**Freshness.** On appear: render the cache, then refresh if `fetchedAt` is older than 15 minutes (the provider's update interval), so opening the app twice in a minute doesn't cost two calls. Pull to refresh always fetches.

**Instant open.** Read and decode the cached file off the main thread at launch; 15 KB decodes in a few milliseconds. Show skeleton rows only when there's no cache at all (first launch).

</ModelAnswer>

<ModelAnswer section="failure">

- **Offline or timeout:** keep the cached forecast on screen with "Offline · updated 2 h ago"; no blocking error.
- **No cache and no network:** a clear empty state with a retry button.
- **Slow network:** a short timeout (e.g. 10 s) and no retry storm: one retry with backoff, then wait for the next refresh.
- **Very old cache** (say over 12 hours): still show it, but say so plainly; a day-old forecast can mislead.

</ModelAnswer>

<ModelAnswer section="tradeoffs">

A file cache over Core Data: simpler, and enough for one place. Stale-while-revalidate over always fetching first: faster and works offline, at the cost of sometimes showing data that's minutes old (which we label). Later, multiple places and a widget would share the cache through an App Group, and background refresh could warm it before the morning peak.

</ModelAnswer>

<Pitfalls>

- Fetching on every appearance and showing a spinner first: the screen is never instant and fails offline.
- Designing a database and sync engine for one small JSON document.
- Forgetting to tell the user how old the data is when showing a cache.

</Pitfalls>
