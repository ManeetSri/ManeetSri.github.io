A diffable data source only sees identifiers. Something has to turn the model's rows into the shape of the next snapshot, and that something decides whether the list animates correctly, keeps cell state, or crashes on a repeated identifier from a paginated API. Write it as a pure function, so it's tested without UIKit and the view controller has nothing left to decide.

`UIKitSnapshotPlanner.plan(from:to:) -> Plan`

The rows arrive in display order. Each `Row` has an `id`, the `section` it belongs to, and the content a cell shows (`title` and `detail`). `old` is what the screen showed last time; `new` is what it should show now. Return a `Plan` with:

- **`sections`**: one `Section` per section identifier, in the order each section's **first** row appears in `new`, with its item identifiers in row order. A section's rows don't have to be next to each other.
- **`duplicates`**: identifiers that appear more than once in `new`. Keep the **first** row with that identifier and drop the rest. List each repeated identifier once, in the order its first repeat appears.
- **`reconfigured`**: identifiers that are in both `old` and the new snapshot whose `title` or `detail` changed, in the order they appear in the new snapshot (section by section). When `old` repeats an identifier, compare against its first row, the one the screen actually showed.

Moving to another section with the same content isn't a content change: the diff handles moves, so it isn't reconfigured. Inserted and deleted items aren't reconfigured either.

## Examples

| Old rows | New rows | Plan |
| --- | --- | --- |
| none | `a·today`, `b·today`, `c·earlier`, `d·today` | sections `today: [a, b, d]`, `earlier: [c]` |
| `a "Milk"`, `b "Eggs 6"` | `a "Milk"`, `b "Eggs 12"` | one section `[a, b]`, reconfigured `[b]` |
| none | `a·s1`, `b·s1`, `c·s2`, `b·s2`, `b·s1`, `a·s1` | `s1: [a, b]`, `s2: [c]`, duplicates `[b, a]` |
| `a "Call Sam"·todo` | `a "Call Sam"·done` | `done: [a]`, nothing reconfigured |
| some rows | none | no sections, nothing reconfigured, no duplicates |

## Constraints

- Identifiers are unique strings within a valid snapshot; inputs may break that rule, and the plan must not.
- Up to tens of thousands of rows: aim for one pass over each input, with dictionaries for lookups.
- Pure Foundation: no UIKit, no randomness, no clocks.

<Hints>
<Hint>
Build a dictionary of the old rows by identifier first, keeping only the first row for each identifier.
</Hint>
<Hint>
Walk the new rows once. A dictionary of section identifier to item identifiers, plus an array of section identifiers in first-appearance order, gives you the sections without sorting.
</Hint>
<Hint>
Compute `reconfigured` last, from the finished sections, so it comes out in snapshot order and only names identifiers that are really in the snapshot.
</Hint>
</Hints>

## Solutions

<Approach title="One pass to build the sections, then compare by identifier" time="O(n + m)" space="O(n + m)">

```swift
public static func plan(from old: [Row], to new: [Row]) -> Plan {
    var before: [String: Row] = [:]
    for row in old where before[row.id] == nil {
        before[row.id] = row
    }

    var after: [String: Row] = [:]
    var sectionOrder: [String] = []
    var itemsBySection: [String: [String]] = [:]
    var duplicates: [String] = []
    for row in new {
        guard after[row.id] == nil else {
            if !duplicates.contains(row.id) { duplicates.append(row.id) }
            continue
        }
        after[row.id] = row
        if itemsBySection[row.section] == nil { sectionOrder.append(row.section) }
        itemsBySection[row.section, default: []].append(row.id)
    }

    let sections = sectionOrder.map { Section(id: $0, items: itemsBySection[$0] ?? []) }
    let reconfigured = sections.flatMap(\.items).filter { id in
        guard let old = before[id], let new = after[id] else { return false }
        return old.title != new.title || old.detail != new.detail
    }
    return Plan(sections: sections, reconfigured: reconfigured, duplicates: duplicates)
}
```

`n` and `m` are the numbers of old and new rows. `duplicates.contains` is linear in the number of duplicates, which is tiny in practice; use a `Set` alongside it if a source could repeat thousands of identifiers.

In the app, the view controller turns the plan into an `NSDiffableDataSourceSnapshot` (append each section and its items, then `reconfigureItems(plan.reconfigured)`), applies it, and logs `plan.duplicates` with the screen's name: repeated identifiers almost always mean offset-based paging on a list that changed between pages. Everything that could crash or animate wrongly has been decided, and tested, before UIKit sees it.

</Approach>
