A ride-hailing app decides everything about a ride type with `switch type { … }` on a string from the server, and the same switch appears in the pricing code, the availability check, the picker and the receipts. The next feature is a new ride type, which today means editing every one of them. Finish replacing those switches with polymorphism: each ride type becomes a type that owns its rules, and the ride picker works with any of them.

`PolymorphicRideTypes.quotes(for:from:) -> [Quote]`, plus `price(for:)` on each ride, the default `isAvailable(for:)`, and the factory `ride(code:) -> (any RideType)?`

The `name` and `seats` switches have already been moved into `Standard`, `XL`, `Pool` and `Lux` as the first small steps. Move the other two:

```swift
func price(type: String, trip: Trip) -> Int {
    switch type {
    case "standard": return 250 + 100 * trip.metres / 1000 + 20 * trip.minutes
    case "xl":       return 400 + 150 * trip.metres / 1000 + 25 * trip.minutes
    case "pool":     return (250 + 100 * trip.metres / 1000 + 20 * trip.minutes) * 60 / 100
    case "lux":      return max(1500, 500 + 300 * trip.metres / 1000 + 40 * trip.minutes)
    default:         return 0
    }
}

func isAvailable(type: String, trip: Trip) -> Bool {
    switch type {
    case "pool": return trip.passengers <= 2 && !trip.hasLuggage
    case "xl":   return trip.passengers <= 6
    default:     return trip.passengers <= 4
    }
}
```

- `price(for:)` on each type returns its fare in pence, with the same integer arithmetic (so fractions of a penny are dropped).
- The protocol extension's `isAvailable(for:)` is the usual rule: a seat for every passenger. Override it only where a ride differs.
- `quotes(for:from:)` lists the rides that can take the trip, cheapest first, with equal fares in name order. It must work for ride types it has never heard of: the tests pass it one of their own.
- `ride(code:)` turns a server code (`"standard"`, `"xl"`, `"pool"`, `"lux"`) into a ride, and returns `nil` for a code this version of the app doesn't know. It's the one switch that stays, at the boundary where strings become types.

## Examples

| Trip | Quotes |
| --- | --- |
| 5.4 km, 18 min, 1 passenger | Pool 690, Standard 1150, XL 1660, Lux 2840 |
| 0.8 km, 3 min, 3 passengers with luggage | Standard 390, XL 595, Lux 1500 (its minimum fare; no Pool: too many people, and bags) |
| 1 km, 5 min, 5 passengers | XL only |
| 1 km, 5 min, 7 passengers | none |
| `ride(code: "xl")` | an `XL` |
| `ride(code: "bike")` | `nil` |

## Constraints

- Distances are whole metres and durations whole minutes, zero or more; there's at least one passenger.
- No switch or `if` on a ride's name or type outside `ride(code:)`. The tests can't check that, but it's the point of the kata.
- `RideType` is `Sendable`, so keep the types immutable values.

## Solutions

<Approach title="Each type owns its rules; one factory at the boundary" time="O(n log n) for n rides" space="O(n)">

```swift
struct Tariff: Sendable {
    let base: Int
    let perKilometre: Int
    let perMinute: Int

    func price(for trip: Trip) -> Int {
        base + perKilometre * trip.metres / 1000 + perMinute * trip.minutes
    }
}

public struct Standard: RideType {
    static let tariff = Tariff(base: 250, perKilometre: 100, perMinute: 20)
    public var name: String { "Standard" }
    public var seats: Int { 4 }
    public func price(for trip: Trip) -> Int { Self.tariff.price(for: trip) }
}

public struct Pool: RideType {
    public var name: String { "Pool" }
    public var seats: Int { 2 }
    public func price(for trip: Trip) -> Int { Standard().price(for: trip) * 60 / 100 }
    public func isAvailable(for trip: Trip) -> Bool { trip.passengers <= seats && !trip.hasLuggage }
}

public struct Lux: RideType {
    static let tariff = Tariff(base: 500, perKilometre: 300, perMinute: 40)
    public var name: String { "Lux" }
    public var seats: Int { 4 }
    public func price(for trip: Trip) -> Int { max(1500, Self.tariff.price(for: trip)) }
}
// XL is Standard with its own tariff and 6 seats.

public static func quotes(for trip: Trip, from rides: [any RideType]) -> [Quote] {
    rides
        .filter { $0.isAvailable(for: trip) }
        .map { Quote(name: $0.name, price: $0.price(for: trip)) }
        .sorted { ($0.price, $0.name) < ($1.price, $1.name) }
}

public static func ride(code: String) -> (any RideType)? {
    switch code {
    case "standard": Standard()
    case "xl": XL()
    case "pool": Pool()
    case "lux": Lux()
    default: nil
    }
}

extension PolymorphicRideTypes.RideType {
    public func isAvailable(for trip: PolymorphicRideTypes.Trip) -> Bool {
        trip.passengers <= seats
    }
}
```

Adding a "Bike" ride is now one new type and one line in `ride(code:)`; the picker, receipts and availability checks don't change. That's the open–closed payoff, and the tests prove it with a ride type of their own.

Notice two choices. Standard, XL and Lux differ mostly in *data*, so they share a `Tariff` rather than each re-implementing the formula: polymorphism for what differs in behaviour, a table for what differs in numbers. And `Pool` reuses `Standard` by composition instead of inheritance, so changing the Standard tariff moves the Pool fare with it, which is what the business rule says.

The alternative is an `enum RideKind` with `price(for:)` and `isAvailable(for:)` as methods that switch over `self`. That keeps the switches, but the compiler now checks every one of them is exhaustive when a case is added. It wins when the set of ride types is closed and you add operations more often than types; the protocol wins when new types arrive often, or come from other modules or the server.

</Approach>
