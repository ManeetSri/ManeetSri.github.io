When a request fails because a server is overloaded, retrying straight away makes the overload worse, and if a thousand phones failed together, they all retry together. Write the schedule a retry policy follows: delays that grow exponentially up to a cap, with jitter to spread the retries out.

`BackoffSchedule.delays(retries:base:factor:cap:jitter:using:) -> [Double]`

- Return one delay, in seconds, for each of `retries` retries.
- Before jitter, retry *n* (counting from 0) waits `base × factorⁿ`, but never more than `cap`.
- `.none` returns exactly that. `.full` returns a random delay from 0 up to it. `.equal` returns half of it plus a random amount up to the other half.
- Draw every random number from `generator`, so a seeded generator gives the same schedule every time.

## Examples

| Call | Delays |
| --- | --- |
| 6 retries, base 0.5, factor 2, cap 4, `.none` | `[0.5, 1, 2, 4, 4, 4]` |
| 4 retries, base 1, factor 3, cap 100, `.none` | `[1, 3, 9, 27]` |
| 0 retries, any jitter | `[]` |
| 6 retries, base 0.5, factor 2, cap 4, `.full` | six delays, each between 0 and `[0.5, 1, 2, 4, 4, 4]` |
| 6 retries, base 0.5, factor 2, cap 4, `.equal` | six delays, each between half and all of `[0.5, 1, 2, 4, 4, 4]` |

## Constraints

- `retries` may be zero or negative: return no delays.
- `0 < base ≤ cap` and `factor ≥ 1`.
- Use the generator you're given, never `SystemRandomNumberGenerator`: tests pass `SeededGenerator` from DesignKit and expect the same schedule for the same seed.

## Solutions

<Approach title="Map each attempt to its capped delay, then jitter it" time="O(retries)" space="O(retries)">

```swift
public static func delays<G: RandomNumberGenerator>(retries: Int, base: Double, factor: Double = 2, cap: Double, jitter: Jitter, using generator: inout G) -> [Double] {
    (0..<max(0, retries)).map { attempt in
        let exponential = min(cap, base * pow(factor, Double(attempt)))
        switch jitter {
        case .none:
            return exponential
        case .full:
            return Double.random(in: 0...exponential, using: &generator)
        case .equal:
            return exponential / 2 + Double.random(in: 0...(exponential / 2), using: &generator)
        }
    }
}
```

Full jitter spreads retries the most, so it relieves an overloaded server fastest, but a retry can come almost at once. Equal jitter guarantees at least half the delay. AWS's analysis of the variants found full jitter does the least total work in a thundering herd; equal jitter is a reasonable choice when you never want a near-immediate retry.

</Approach>
