A packing-list app needs Undo and Redo, with menu titles like "Undo Add Passport". Model every edit as a **command**: a value that makes one change and returns the command that reverses it. Then write the history that performs commands and walks back and forward through them, the way `UndoManager` does.

`PackingListUndo.Command.apply(to:) -> (any Command)?`, for `Add`, `Insert`, `Remove`, `Rename` and `Batch`, and `PackingListUndo.History`'s `perform(_:)`, `undo()`, `redo()`, `canUndo`, `canRedo`, `undoActionName` and `redoActionName`

- `apply(to:)` makes the change and returns its inverse. If the command would change nothing (an index out of range, a rename to the same name), it returns `nil` and leaves the list alone.
- `Add` appends. `Insert` accepts any index from 0 to the item count. `Remove` and `Rename` need an existing index.
- `Batch` applies its commands in order and undoes as **one** step. Its inverse must undo them in reverse order. A batch where nothing changed returns `nil`.
- `History.perform` applies a command and records it, unless it changed nothing. Recording a new change clears everything that could be redone.
- `undo()` reverses the latest change and makes it redoable; `redo()` makes it again. Both do nothing when there's nothing to undo or redo.
- `undoActionName` and `redoActionName` are the name of the command the user originally performed, both before and after undoing it.

## Examples

| Steps on `[Passport, Charger, Socks]` | List | Undo menu | Redo menu |
| --- | --- | --- | --- |
| `perform(Add("Hat"))` | Passport, Charger, Socks, Hat | Add Hat | none |
| then `undo()` | Passport, Charger, Socks | none | Add Hat |
| then `perform(Remove(at: 0))` | Charger, Socks | Remove | none (cleared) |
| `perform(Batch("Remove Packed", [Remove(at: 0), Remove(at: 0)]))` | Socks | Remove Packed | none |
| then `undo()` | Passport, Charger, Socks | none | Remove Packed |
| `perform(Rename(at: 0, to: "Passport"))` | unchanged | none (not recorded) | none |

## Constraints

- Store commands and their inverses, not copies of the whole list. (Snapshots are the memento pattern, which you'll meet in D13.)
- `History` is a value type; `perform`, `undo` and `redo` are `mutating`.
- The inverse of an inverse must redo the change. If you get the inverses right, `redo` needs no special code.

<Hints>
<Hint>
Each command's inverse comes from what it saw: `Remove` returns an `Insert` of the item it removed, at the same index; `Rename` returns a `Rename` back to the old name.
</Hint>
<Hint>
Keep two stacks of `(name, inverse)` pairs. Undo pops from one, applies the inverse, and pushes `(name, whatever that returned)` onto the other. Redo does the same in the other direction.
</Hint>
<Hint>
For `Batch`, collect the non-nil inverses as you apply each command, then reverse them. Removing items 0 and then 0 again from `[a, b, c]` must be undone by inserting `b` at 0 before `a` at 0.
</Hint>
</Hints>

## Solutions

<Approach title="Commands return their inverses; two stacks of (name, inverse)" time="O(n) per command for a list of n items" space="O(h) for h recorded changes">

```swift
public struct Remove: Command {
    public let index: Int
    public var actionName: String { "Remove" }

    public init(at index: Int) {
        self.index = index
    }

    public func apply(to list: inout Checklist) -> (any Command)? {
        guard list.items.indices.contains(index) else { return nil }
        let removed = list.items.remove(at: index)
        return Insert(removed, at: index)
    }
}

public struct Batch: Command {
    public let actionName: String
    public let commands: [any Command]

    public init(_ actionName: String, _ commands: [any Command]) {
        self.actionName = actionName
        self.commands = commands
    }

    public func apply(to list: inout Checklist) -> (any Command)? {
        let inverses = commands.compactMap { $0.apply(to: &list) }
        return inverses.isEmpty ? nil : Batch(actionName, inverses.reversed())
    }
}

public struct History {
    private struct Step {
        let name: String
        let reverse: any Command
    }

    public private(set) var list: Checklist
    private var undoStack: [Step] = []
    private var redoStack: [Step] = []

    public init(_ list: Checklist = Checklist()) {
        self.list = list
    }

    public var canUndo: Bool { !undoStack.isEmpty }
    public var canRedo: Bool { !redoStack.isEmpty }
    public var undoActionName: String? { undoStack.last?.name }
    public var redoActionName: String? { redoStack.last?.name }

    public mutating func perform(_ command: any Command) {
        guard let inverse = command.apply(to: &list) else { return }
        undoStack.append(Step(name: command.actionName, reverse: inverse))
        redoStack.removeAll()
    }

    public mutating func undo() {
        guard let step = undoStack.popLast(), let redo = step.reverse.apply(to: &list) else { return }
        redoStack.append(Step(name: step.name, reverse: redo))
    }

    public mutating func redo() {
        guard let step = redoStack.popLast(), let undo = step.reverse.apply(to: &list) else { return }
        undoStack.append(Step(name: step.name, reverse: undo))
    }
}
```

`Add`, `Insert` and `Rename` follow the same shape as `Remove`: check the command can apply, make the change, and return what reverses it (`Add` returns `Remove(at:)` of the last index; `Insert` returns `Remove(at: index)`; `Rename` returns a rename back).

Keeping the original name in each step is what makes the menus read "Undo Remove" and then "Redo Remove", even though the command that runs on undo is an `Insert`. `UndoManager` works the same way: the undo handler registers the redo, and the action name travels with the group.

Commands cost less memory than snapshots, because each records only what it changed. They need care in return: every inverse must be exactly right, and a command can only be replayed on the state it was made for. That's why `History` doesn't let anything else edit `list`.

</Approach>
