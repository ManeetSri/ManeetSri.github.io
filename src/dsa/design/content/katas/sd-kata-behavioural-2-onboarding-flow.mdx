An app's onboarding has five screens: welcome, sign in, create account, a notifications prompt and profile set-up. None of them knows about the others; each reports an output. Write the **coordinator** that mediates between them: it turns outputs into navigation commands for a `Navigator`, decides which steps to skip, and tells its parent when the flow is over.

`OnboardingFlowMediator.Coordinator`: `start()`, `handle(_:)` and `backTapped()`, with `stack`, `isFinished` and `onFinish`

The coordinator is `@MainActor`, like the screens it coordinates. It keeps `stack`, the screens it has arranged, bottom first, and sends every change to `navigator.perform(_:)`.

- **`start()`** shows `.welcome` as the root: `stack` becomes `[.welcome]` and the navigator gets `.setRoot(.welcome)`.
- **From welcome**, `.welcomeChoseSignIn` pushes `.signIn` and `.welcomeChoseCreateAccount` pushes `.createAccount`.
- **Signing in.** `.signedIn(hasProfile:)` from sign-in, or `.accountCreated` from create account (a new account has no profile), means the user is authenticated. The next step is the notifications prompt, unless it was already answered; after that, profile set-up if there's no profile yet; otherwise the flow is finished. Whatever comes next after signing in is shown with **`.setRoot`**, so Back can't return to the sign-in screens.
- **`.notificationsAnswered`** pushes `.profileSetup` if a profile is still needed, and finishes otherwise. **`.profileSaved`** finishes.
- **Finishing** sets `isFinished` and calls `onFinish` once. It sends no navigation command: the parent decides what replaces onboarding.
- **`backTapped()`** pops the top screen (`.pop`, and the stack shrinks) unless only the root is left.
- **Stale outputs are ignored.** Each output comes from one screen (the `welcome…` outputs from `.welcome`, `signedIn` from `.signIn`, and so on). If that screen isn't on top of the stack, from a double tap or a screen that has already gone, nothing happens. After finishing, everything is ignored.

## Examples

| Notifications already answered? | Outputs after `start()` | Commands sent | Finished? |
| --- | --- | --- | --- |
| no | `welcomeChoseSignIn` | `setRoot(.welcome)`, `push(.signIn)` | no |
| no | `welcomeChoseCreateAccount`, `accountCreated`, `notificationsAnswered`, `profileSaved` | `setRoot(.welcome)`, `push(.createAccount)`, `setRoot(.notificationsPrompt)`, `push(.profileSetup)` | yes |
| yes | `welcomeChoseCreateAccount`, `accountCreated` | `setRoot(.welcome)`, `push(.createAccount)`, `setRoot(.profileSetup)` | no |
| yes | `welcomeChoseSignIn`, `signedIn(hasProfile: true)` | `setRoot(.welcome)`, `push(.signIn)` | yes |
| no | `welcomeChoseCreateAccount`, `welcomeChoseCreateAccount` | `setRoot(.welcome)`, `push(.createAccount)` (the second tap is ignored) | no |

## Constraints

- Every command goes through the `navigator`; the tests pass one that records them.
- `onFinish` is called exactly once, however many outputs arrive afterwards.
- `stack` must always match what the commands you sent would show.
- Calling `start()` again, or anything at all after finishing, changes nothing.

Give `Output` a way to name the screen it comes from, such as a computed `source: Screen`, and start `handle(_:)` with `guard !isFinished, stack.last == output.source else { return }`. That one line handles double taps and stale screens.
</Hint>
<Hint>
Keep one piece of flow state of your own: whether a profile is still needed. `signedIn(hasProfile:)` and `accountCreated` set it, and one private method decides what comes after signing in.
</Hint>
<Hint>
Write three small private helpers, `setRoot(_:)`, `push(_:)` and `finish()`, that update `stack` and call the navigator together, so the two can't drift apart.
</Hint>

## Solutions

<Approach title="Outputs in, commands out, one owner for the flow" time="O(1) per output" space="O(screens)">

```swift
public func start() {
    guard stack.isEmpty, !isFinished else { return }
    setRoot(.welcome)
}

public func handle(_ output: Output) {
    // A double tap, or a screen that has already gone: only the top screen speaks for the flow
    guard !isFinished, stack.last == output.source else { return }
    switch output {
    case .welcomeChoseSignIn:
        push(.signIn)
    case .welcomeChoseCreateAccount:
        push(.createAccount)
    case .signedIn(let hasProfile):
        needsProfile = !hasProfile
        continueAfterSigningIn()
    case .accountCreated:
        needsProfile = true
        continueAfterSigningIn()
    case .notificationsAnswered:
        if needsProfile { push(.profileSetup) } else { finish() }
    case .profileSaved:
        finish()
    }
}

public func backTapped() {
    guard !isFinished, stack.count > 1 else { return }
    stack.removeLast()
    navigator.perform(.pop)
}

// Signed in: whatever comes next becomes the root, so Back can't return to the sign-in screens
private func continueAfterSigningIn() {
    if !notificationsAlreadyAnswered {
        setRoot(.notificationsPrompt)
    } else if needsProfile {
        setRoot(.profileSetup)
    } else {
        finish()
    }
}

private func setRoot(_ screen: Screen) {
    stack = [screen]
    navigator.perform(.setRoot(screen))
}

private func push(_ screen: Screen) {
    stack.append(screen)
    navigator.perform(.push(screen))
}

private func finish() {
    isFinished = true
    onFinish?()
}
```

with `source` on `Output` mapping each case to its screen, and `private var needsProfile = false` on the coordinator.

Every rule about the flow lives here: the order, the skipped prompt, "no way back after sign-in", and when it ends. The screens stay reusable, and the whole flow is tested without UIKit, because the coordinator talks to a `Navigator` protocol that a `UINavigationController` adapter implements in the app. In a real app you'd also listen for the system back swipe (the navigation controller's delegate) and call the same pop logic, so `stack` never drifts from what's on screen.

</Approach>
