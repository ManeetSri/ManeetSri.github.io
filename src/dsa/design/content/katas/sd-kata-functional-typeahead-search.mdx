A search screen that searches as you type has two classic bugs: results for an old query arriving after the results for a new one, and a cleared screen filling back up with results nobody asked for. Write the screen's reducer: a pure function that applies one action to the state and returns the side effects to run, as values. Get the rules right here and both bugs become impossible, whatever order the network answers in.

`TypeaheadSearch.reduce(_ state: inout State, _ action: Action) -> [Effect]`

- **`queryChanged(text)`**: trim whitespace and newlines from `text`. If the result equals `state.query`, nothing changes and there are no effects. Otherwise store it as the query, clear any error, and move `currentSearch` on by one. Then:
  - shorter than `minimumQueryLength` (2) characters: clear the results, stop loading, and return no effects;
  - otherwise: start loading, keep the current results on screen, and return `[.search(id: currentSearch, query: query)]`.
- **`searchFinished(id, result)`**: if `id` isn't `currentSearch`, ignore it completely. Otherwise stop loading, and on success replace the results; on failure keep the results and set `errorMessage` to `"You're offline."` or `"Search failed (503)."` (with the status code).
- **`clearTapped`**: back to an empty screen (no query, results, loading or error), with `currentSearch` moved on by one.

The reducer never calls the network, reads the clock or touches anything outside its arguments. The shell around it runs each `.search` effect and sends `searchFinished` back with the same id.

## Examples

| Actions, from a fresh state | State afterwards | Effects |
| --- | --- | --- |
| `queryChanged("swift")` | query `"swift"`, loading | `[.search(id: 1, query: "swift")]` |
| `queryChanged(" swift")`, `queryChanged("swift ")` | query `"swift"`, loading | only the first search |
| `queryChanged("sw")`, `queryChanged("swi")`, `searchFinished(id: 1, .success(["Sweden"]))` | still loading, no results: the answer to `"sw"` is stale | two searches, ids 1 and 2 |
| `queryChanged("swi")`, `searchFinished(id: 1, .failure(.server(status: 503)))` | not loading, `errorMessage` `"Search failed (503)."` | one search |
| `queryChanged("swift")`, `clearTapped`, `searchFinished(id: 1, .success(["Swift"]))` | empty, `currentSearch` 2 | one search |

## Constraints

- `reduce` is pure: the same state and action always give the same new state and effects.
- Every query change and every clear moves `currentSearch` on by one, including changes to a query too short to search. That's what makes an answer to an abandoned query recognisably stale.
- An empty `results` array after a successful search is a real answer (nothing matched), not an error.

## Solutions

<Approach title="One switch, with ids that outdate every earlier search" time="O(n) for trimming the query" space="O(1) beyond the state">

```swift
public static func reduce(_ state: inout State, _ action: Action) -> [Effect] {
    switch action {
    case .queryChanged(let text):
        let query = text.trimmingCharacters(in: .whitespacesAndNewlines)
        guard query != state.query else { return [] }
        state.query = query
        state.errorMessage = nil
        state.currentSearch += 1
        guard query.count >= minimumQueryLength else {
            state.results = []
            state.isLoading = false
            return []
        }
        state.isLoading = true
        return [.search(id: state.currentSearch, query: query)]

    case .searchFinished(let id, let result):
        guard id == state.currentSearch else { return [] }
        state.isLoading = false
        switch result {
        case .success(let results):
            state.results = results
        case .failure(.offline):
            state.errorMessage = "You're offline."
        case .failure(.server(let status)):
            state.errorMessage = "Search failed (\(status))."
        }
        return []

    case .clearTapped:
        let next = state.currentSearch + 1
        state = State()
        state.currentSearch = next
        return []
    }
}
```

The id is the whole trick. Cancelling the old request in the shell is still worth doing to save data, but it's an optimisation. Cancellation races with completion: a response that finished a moment before you cancelled is already on its way back as an action. The reducer stays correct because it never trusts the order things arrive in.

Returning effects as values is what makes every test here a plain function call: no stub network, no waiting. Keeping old results visible while loading is a product choice; another team might clear them. Either way it's one line in one place, and a test pins it down.

</Approach>
