A reading list screen loads articles, can be pulled to refresh, and must never blank good content because a refresh failed, or let a late answer overwrite a newer one. Write its reducer: a pure function that applies one event to the screen's state and says which fetch, if any, to start.

`ReadingListScreen.reduce(_ state: inout State, _ event: Event) -> Effect?`

- `State` has `content` (`.idle`, `.loading`, `.loaded([Article])`, `.empty` or `.failed(message:)`), `isRefreshing`, `banner` and `latestRequest`.
- **First load.** `.appeared` while idle sets `.loading` and returns `.fetch(request:)` with the next request number. Numbers start at 1, go up by one for every fetch, and the newest is kept in `latestRequest`. Appearing again does nothing.
- **Answers.** `.fetchSucceeded` shows `.loaded(articles)`, or `.empty` when there are none. `.fetchFailed` during a first load shows `.failed(message:)`.
- **Retry.** `.retryTapped` while failed loads again, with a new request.
- **Refresh.** `.refreshPulled` while loaded or empty keeps the content, sets `isRefreshing`, clears any banner and starts a new request. When that refresh fails, the content stays, `isRefreshing` goes back to `false` and `banner` is set to the message. When it succeeds, the new content replaces the old with no banner. Pulling again while a refresh is running does nothing.
- **Banner.** `.bannerDismissed` clears it.
- **Stale answers.** An answer only counts if it's for `latestRequest` *and* the screen is still waiting (loading, or refreshing). Any other answer changes nothing.
- Any event that doesn't fit the current state changes nothing and returns `nil`.

## Examples

| Events, from a new `State()` | State afterwards | Effects returned |
| --- | --- | --- |
| `appeared` | `.loading`, `latestRequest` 1 | `fetch(1)` |
| `appeared`, `fetchSucceeded(1, [])` | `.empty` | `fetch(1)` |
| `appeared`, `fetchFailed(1, "Offline")`, `retryTapped` | `.loading`, `latestRequest` 2 | `fetch(1)`, `fetch(2)` |
| `appeared`, `fetchSucceeded(1, [a])`, `refreshPulled`, `fetchFailed(2, "Couldn't refresh")` | `.loaded([a])`, banner "Couldn't refresh", not refreshing | `fetch(1)`, `fetch(2)` |
| `appeared`, `fetchSucceeded(1, [a])`, `refreshPulled`, `refreshPulled` | `.loaded([a])`, refreshing | `fetch(1)`, `fetch(2)` |
| `appeared`, `fetchFailed(1, "Timed out")`, `retryTapped`, `fetchSucceeded(1, [a])` | still `.loading`: request 1's answer is stale | `fetch(1)`, `fetch(2)` |

## Constraints

- The reducer is pure: no `async`, no clock, no networking, no randomness. The view model runs each effect and sends the result back as an event.
- `State`, `Event` and `Effect` are `Equatable`, and the tests compare whole states, so leave fields you don't mean to change alone.

<Hints>
<Hint>
Switch on the event, and guard on the state inside each case: `guard state.content == .idle else { return nil }` is the whole rule for appearing twice.
</Hint>
<Hint>
Two small computed properties on `State` make most rules one line: one for "has content" (loaded or empty) and one for "is waiting" (loading, or refreshing).
</Hint>
<Hint>
Put the numbering in one private helper that increments `latestRequest` and returns `.fetch(request: latestRequest)`, and call it from every case that starts a fetch.
</Hint>
</Hints>

## Solutions

<Approach title="Switch on the event, guard on the state, number every fetch" time="O(1) per event, plus copying the articles" space="O(1) extra">

```swift
public static func reduce(_ state: inout State, _ event: Event) -> Effect? {
    switch event {
    case .appeared:
        guard state.content == .idle else { return nil }
        state.content = .loading
        return nextFetch(&state)

    case .retryTapped:
        guard case .failed = state.content else { return nil }
        state.content = .loading
        return nextFetch(&state)

    case .refreshPulled:
        guard state.hasContent, !state.isRefreshing else { return nil }
        state.isRefreshing = true
        state.banner = nil
        return nextFetch(&state)

    case .bannerDismissed:
        state.banner = nil
        return nil

    case let .fetchSucceeded(request, articles):
        guard request == state.latestRequest, state.isWaiting else { return nil }
        state.content = articles.isEmpty ? .empty : .loaded(articles)
        state.isRefreshing = false
        state.banner = nil
        return nil

    case let .fetchFailed(request, message):
        guard request == state.latestRequest, state.isWaiting else { return nil }
        if state.hasContent {
            state.isRefreshing = false
            state.banner = message
        } else {
            state.content = .failed(message: message)
        }
        return nil
    }
}

private static func nextFetch(_ state: inout State) -> Effect {
    state.latestRequest += 1
    return .fetch(request: state.latestRequest)
}
```

with `hasContent` true for `.loaded` and `.empty`, and `isWaiting` true when `content == .loading || isRefreshing`.

The two guards on answers do different jobs. Checking the request number drops an answer that was overtaken by a retry. Checking that the screen is waiting drops a second answer to a request that's already been handled, so a duplicated failure can't put a banner over a successful load. Splitting `content` from `isRefreshing` and `banner` is what lets a refresh, and a failed one, leave the articles alone. The cost is a few combinations the type allows but the reducer never produces (refreshing while loading, say), which is why every transition lives in this one function.

</Approach>
