Marketing runs a new promotion most weeks. In the old checkout, each one meant another `case` in a `switch` inside the price calculation, another release of the most sensitive code in the app, and another chance to break last week's offer. Build a pricing engine that's **closed for modification and open for extension**: it applies any list of rules it's given, and a new promotion is a new type that conforms to `DiscountRule`.

`SolidCheckoutPricing.PricingEngine(rules:).quote(for:) -> Quote`, plus three rules: `PercentOffCategory`, `MultiBuy` and `SpendThreshold`

All money is whole pence (`Int`), so `£50` is `5_000`.

- **`PricingEngine`** applies its rules in the order given. Each rule gets the cart and the discounts already given by the rules before it. Keep a discount only if its amount is more than 0. The quote has the cart's subtotal, the kept discounts in order, and the total: the subtotal less every discount, but never below 0.
- **`PercentOffCategory(label:category:percent:)`**: `percent`% of the total of every line in `category`, rounded down to a whole penny. `nil` when that comes to 0.
- **`MultiBuy(label:sku:buy:payFor:)`**: "3 for 2". For every complete group of `buy` units of `sku`, the customer pays for `payFor`, so each group gives `buy − payFor` units free. `nil` when no units are free or the sku isn't in the cart.
- **`SpendThreshold(label:minimum:amount:)`**: `amount` off when the subtotal **less the discounts before this rule** is at least `minimum`, so whether it applies depends on where it sits in the list.

The engine must not mention any concrete rule. The tests add rules of their own that the engine has never seen.

## Examples

The basket: 2 × bread at 250 and 1 × croissant at 199 (both `bakery`), 7 × cola at 120 (`drinks`), 1 × coffee beans at 3,600 (`pantry`). Subtotal 5,139.

| Rules, in order | Discounts | Total |
| --- | --- | --- |
| none | none | 5,139 |
| 10% off bakery | 69 (69.9 rounded down) | 5,070 |
| cola 3 for 2 | 240 (two free colas) | 4,899 |
| 10% off bakery, cola 3 for 2, £5 off £50 | 69, 240 (5,139 − 309 = 4,830 is under 5,000, so no £5) | 4,830 |
| £5 off £50, 10% off bakery, cola 3 for 2 | 500, 69, 240 | 4,330 |
| a rule worth 10,000 | 10,000 | 0 |

## Constraints

- `percent` is 0 to 100; `buy > payFor ≥ 0`; amounts and prices are never negative in real rules, but the engine must cope with a rule that returns 0 or less (drop it).
- Each sku appears on at most one line of a cart.
- `DiscountRule` is `Sendable`, so rules can be built anywhere and shared; keep them as value types.

<Hint>
The engine is a loop: for each rule, ask for a discount with the discounts so far, and append it if its amount is positive. Sum at the end and clamp with `max(0, …)`.
</Hint>
<Hint>
`PercentOffCategory`: filter the lines by category, sum their totals, then `base * percent / 100`. Integer division rounds down.
</Hint>
<Hint>
`MultiBuy`: `quantity / buy` is the number of complete groups.
</Hint>
<Hint>
`SpendThreshold` is the only rule that reads `earlier`: subtract their amounts from the subtotal before comparing.
</Hint>

## Solutions

<Approach title="A loop over a protocol, and one small type per promotion" time="O(r × n) for r rules and n lines" space="O(r)">

```swift
public func quote(for cart: Cart) -> Quote {
    var discounts: [Discount] = []
    for rule in rules {
        if let discount = rule.discount(for: cart, after: discounts), discount.amount > 0 {
            discounts.append(discount)
        }
    }
    let taken = discounts.reduce(0) { $0 + $1.amount }
    return Quote(subtotal: cart.subtotal, discounts: discounts, total: max(0, cart.subtotal - taken))
}

// SpendThreshold
public func discount(for cart: Cart, after earlier: [Discount]) -> Discount? {
    let running = cart.subtotal - earlier.reduce(0) { $0 + $1.amount }
    return running >= minimum ? Discount(label: label, amount: amount) : nil
}
```

The engine is closed: it's written, tested and never edited again. The *rules list* is where the system is open, and that list is built in one place (the composition root, or from a server-defined promotion feed), so adding "20% off your first order" is a new type and one line of wiring.

Two decisions carry the design. Passing `earlier` to every rule makes **ordering** an explicit part of the contract instead of an accident of a `switch`; a rule that needs to know what happened before it doesn't have to reach into the engine. And the engine **drops non-positive discounts and clamps the total**, so one badly written rule can't make a basket cost less than nothing.

The trade-off is the expression problem you'll meet in the next lessons: new *rules* are cheap, but a new *operation* on every rule (say, "explain on the receipt why this rule didn't apply") means adding a requirement that every rule must implement. If operations change more often than promotions, an enum of rule kinds with functions that switch over it is the better shape.

</Approach>
