A messaging app shows unread counts in three places: the tab bar badge, the inbox header and the summary of a grouped notification. Two years ago someone noticed the three looked alike and merged them into one formatter. Support now hears that the badge says 3 while the notification says 5, and that people's own messages from their Mac show up as unread. Replace the formatter with one shared rule and three separate presentations.

Here's the code you're replacing:

```swift check title="BadgeText.swift, the wrong abstraction"
struct Conversation {
    let id: String
    let title: String
    let isMuted: Bool
}

struct Message {
    let conversationID: String
    let isRead: Bool
}

enum BadgeSurface { case tab, inboxHeader, notification }

func badgeText(messages: [Message], conversations: [Conversation], surface: BadgeSurface,
               cap: Int? = 99, includeMuted: Bool = false, showsZero: Bool = false) -> String? {
    let muted = Set(conversations.filter(\.isMuted).map(\.id))
    let count = messages.filter { !$0.isRead && (includeMuted || !muted.contains($0.conversationID)) }.count
    if count == 0 && !showsZero { return nil }
    if surface == .tab, let cap, count > cap { return "\(cap)+" }
    if surface == .tab { return "\(count)" }
    if surface == .inboxHeader && count == 0 { return "No unread messages" }
    let noun = count == 1 ? "message" : "messages"
    return surface == .notification ? "\(count) new \(noun)" : "\(count) unread \(noun)"
}

// The notification extension's call site, written by another team:
// badgeText(messages: new, conversations: all, surface: .notification, includeMuted: true)
```

The rule for what counts as unread is one piece of knowledge, but it's hidden among the presentation flags, so the notification team turned on `includeMuted` without realising it changed the rule, and nobody could see where "sent by me" or archived conversations should go. The formatting, meanwhile, is three pieces of knowledge owned by three people that only *look* alike.

Write these in `PrinciplesUnreadBadges`:

- `unreadMessages(_:in:) -> [Message]`: the one rule. A message is unread when it isn't read, wasn't sent by me, and its conversation is in the list and is neither muted nor archived. Keep the order the messages were given in.
- `tabBadge(unreadCount:) -> String?`: `nil` when nothing is unread, the number up to 99, then `"99+"`.
- `inboxHeader(unreadCount:) -> String`: `"No unread messages"`, `"1 unread message"`, `"12 unread messages"`.
- `notificationSummary(messages:conversations:) -> String?`: built on the shared rule. Name the conversation when every unread message is in one, otherwise count the conversations; `nil` when nothing is unread.

## Examples

| Call | Result |
| --- | --- |
| `tabBadge(unreadCount: 0)` | `nil` |
| `tabBadge(unreadCount: 99)` | `"99"` |
| `tabBadge(unreadCount: 100)` | `"99+"` |
| `inboxHeader(unreadCount: 1)` | `"1 unread message"` |
| `inboxHeader(unreadCount: 1500)` | `"1500 unread messages"` |
| `notificationSummary` with 3 unread messages, all in Family | `"3 new messages in Family"` |
| `notificationSummary` with 5 unread messages across Family and Work | `"5 new messages in 2 conversations"` |
| `notificationSummary` with new messages only in a muted conversation | `nil` |

## Constraints

- Messages whose conversation isn't in `conversations` (it was deleted) don't count.
- Counts of zero or less mean "nothing unread" on every surface.
- Write numbers in full, without separators: `1500`, not `1,500`.
- In a shipping app, these strings would come from a String Catalog with plural variants, so translators can handle languages whose plurals work differently. The kata uses plain English so the tests can check exact text.

<Hints>
<Hint>
Start with the rule. Collect the ids of conversations that count (not muted, not archived) into a `Set`, then filter the messages in one pass.
</Hint>
<Hint>
Resist a shared "format a count" helper. The tab caps at 99 and hides zero; the header spells zero out and never caps. They differ because different people own them, and they'll keep diverging.
</Hint>
<Hint>
`notificationSummary` should call `unreadMessages`, not repeat its conditions. `Set(unread.map(\.conversationID)).count` tells you whether to name the conversation or count them.
</Hint>
</Hints>

## Solutions

<Approach title="One rule, three small presentations" time="O(m + c)" space="O(c)">

```swift
public static func unreadMessages(_ messages: [Message], in conversations: [Conversation]) -> [Message] {
    let counted = Set(conversations.filter { !$0.isMuted && !$0.isArchived }.map(\.id))
    return messages.filter { !$0.isRead && !$0.isFromMe && counted.contains($0.conversationID) }
}

public static func tabBadge(unreadCount: Int) -> String? {
    guard unreadCount > 0 else { return nil }
    return unreadCount > 99 ? "99+" : String(unreadCount)
}

public static func inboxHeader(unreadCount: Int) -> String {
    switch unreadCount {
    case ...0: "No unread messages"
    case 1: "1 unread message"
    default: "\(unreadCount) unread messages"
    }
}

public static func notificationSummary(messages: [Message], conversations: [Conversation]) -> String? {
    let unread = unreadMessages(messages, in: conversations)
    guard let first = unread.first else { return nil }
    let noun = unread.count == 1 ? "message" : "messages"
    let conversationIDs = Set(unread.map(\.conversationID))
    if conversationIDs.count == 1, let conversation = conversations.first(where: { $0.id == first.conversationID }) {
        return "\(unread.count) new \(noun) in \(conversation.title)"
    }
    return "\(unread.count) new \(noun) in \(conversationIDs.count) conversations"
}
```

There's slightly more code than before, and every function is obvious. The rule now has exactly one home, so the surfaces can't disagree: the last test checks all three against one inbox. Each presentation can change without retesting the others. When design asks for "9+" on small screens, that's a change to `tabBadge` alone.

The notification summary runs in a notification service extension, while the tab badge is set by the app, so in a real codebase `unreadMessages` would live in a small module both targets import. That's DRY across targets: share the rule, not the formatter.

</Approach>
