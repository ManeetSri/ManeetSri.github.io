A music app's server sends playlists with their tracks nested inside, so the same track arrives in many payloads. Store each track once, keyed by id, with each playlist as an ordered list of track ids, so a track changed in one place is changed in every playlist. Then derive what screens need, totals and memberships, from those tables instead of storing it.

`NormalisedPlaylistStore.Library`, with `ingest(_:)`, `update(_:)`, `removeTrack(id:)`, `tracks(inPlaylist:)`, `totalSeconds(ofPlaylist:)` and `playlists(containingTrack:)`.

- **`ingest(_ payload:)`** stores a playlist from the server. Its name and track order replace whatever the library had for that playlist id, and each nested track is stored by the same rule as `update`.
- **`update(_ track:)`** stores one track, inserting it if it's new. If the library already has a **higher** `version` of it, the incoming copy is ignored; an equal or higher version replaces it.
- **`removeTrack(id:)`** removes the track from `tracks` and from every playlist, however many times it appears.
- **`tracks(inPlaylist:)`** returns the playlist's tracks in play order, resolved from `tracks`; an unknown playlist gives `[]`.
- **`totalSeconds(ofPlaylist:)`** is the sum of those tracks' `seconds`; **`playlists(containingTrack:)`** is the ids of the playlists that contain the track, sorted.
- The stored state is `tracks: [String: Track]`, `playlistNames: [String: String]` and `playlistTrackIDs: [String: [String]]`. The derived values are computed when asked, never stored.

## Examples

Two playlists share the anthem: Running is `[intro 90 s, anthem 240 s]` and Chill is `[ballad 300 s, anthem 240 s]`.

| Call | Result |
| --- | --- |
| `tracks.count` after ingesting both | `3`: the anthem is stored once |
| `playlistTrackIDs["chill"]` | `["t3", "t2"]` |
| `totalSeconds(ofPlaylist: "run")` | `330` |
| `update(anthem, 180 s, version 2)`, then the two totals | `270` and `480`: one change, both playlists |
| `update(intro, version 3)`, then `update(intro, version 2)` | the version 3 copy is kept |
| `playlists(containingTrack: "t2")` | `["chill", "run"]` |
| `removeTrack(id: "t2")`, then `playlistTrackIDs["run"]` | `["t1"]` |

## Constraints

- Ids are strings, unique per track and per playlist. A playlist may contain the same track more than once.
- A payload can arrive late, after a newer version of one of its tracks: the version rule must protect the newer copy.
- No stored totals or reverse indexes: the tests change tracks and expect every derived value to follow.

<Hints>
<Hint>
`ingest` is `update` for each nested track, followed by two assignments: the playlist's name, and `payload.tracks.map(\.id)` as its order.
</Hint>
<Hint>
The version rule is one line: `if let stored = tracks[track.id], stored.version > track.version { return }`.
</Hint>
<Hint>
For removal, loop over `playlistTrackIDs.keys` and call `removeAll { $0 == id }` on each list; resolving with `compactMap { tracks[$0] }` is a safety net for any id that's left dangling.
</Hint>
</Hints>

## Solutions

<Approach title="Tables by id, lists of ids, and selectors for everything else" time="ingest O(k) for k tracks; derived values O(length of the playlist), membership O(total ids)" space="O(tracks + ids)">

```swift
public mutating func ingest(_ payload: PlaylistPayload) {
    payload.tracks.forEach { update($0) }
    playlistNames[payload.id] = payload.name
    playlistTrackIDs[payload.id] = payload.tracks.map(\.id)
}

public mutating func update(_ track: Track) {
    if let stored = tracks[track.id], stored.version > track.version { return }
    tracks[track.id] = track
}

public mutating func removeTrack(id: String) {
    tracks[id] = nil
    for playlist in playlistTrackIDs.keys {
        playlistTrackIDs[playlist]?.removeAll { $0 == id }
    }
}

public func tracks(inPlaylist id: String) -> [Track] {
    (playlistTrackIDs[id] ?? []).compactMap { tracks[$0] }
}

public func totalSeconds(ofPlaylist id: String) -> Int {
    tracks(inPlaylist: id).reduce(0) { $0 + $1.seconds }
}

public func playlists(containingTrack id: String) -> [String] {
    playlistTrackIDs.filter { $0.value.contains(id) }.keys.sorted()
}
```

Tracks go into their table before the playlist's list is replaced, so no reader can resolve an id whose track isn't there yet. Because a track lives in exactly one place, a rename or a new duration needs no fan-out, and because totals and memberships are computed, they can't go stale. Computing `playlists(containingTrack:)` scans every playlist; if a screen asked it for every row of a long list, a reverse index (`[trackID: Set<playlistID>]`) maintained inside the same mutating methods would make it O(1), at the cost of one more structure to keep right.

</Approach>
