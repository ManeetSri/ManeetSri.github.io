A photo app builds its context menus from configuration: actions grouped into submenus, which can hold more submenus. Before the tree becomes a `UIMenu`, the app needs to ask it questions: how many actions are there, what's left once unavailable actions are removed, where an action lives, and whether two actions share an id. Write those operations on the composite.

`MenuTreeComposite.Element`: `actionCount`, `filtered(_:)`, `titlePath(to:)` and `duplicateActionIDs`

An `Element` is either `.action(Action)`, a leaf, or `.menu(title:children:)`, a submenu holding more elements.

- **`actionCount`**: the number of actions in the tree, at every depth. A submenu itself doesn't count.
- **`filtered(_:)`**: the tree with only the actions the closure keeps, everything in its original order. A submenu left with no actions, at any depth, is removed, so the user never opens an empty submenu. If nothing is left at all, return `nil`.
- **`titlePath(to:)`**: the titles from this element down to the action with that id, ending with the action's own title, or `nil` if there's no such action. If an id appears twice, return the first path, searching children in order.
- **`duplicateActionIDs`**: the ids used by more than one action, anywhere in the tree, sorted and each listed once.

## Examples

With this menu:

```text
Photo
├─ Favourite            (favourite)
├─ Share
│  ├─ Copy Link         (copy-link)
│  ├─ Message           (message)
│  └─ More
│     └─ AirDrop        (airdrop)
├─ Edit
│  ├─ Crop              (crop)
│  └─ Filters           (filters)
└─ Delete               (delete)
```

| Call | Result |
| --- | --- |
| `actionCount` | `7` |
| `filtered { !["message", "airdrop"].contains($0.id) }` | the same tree, with Share holding only Copy Link (More is gone) |
| `filtered { ["favourite", "copy-link"].contains($0.id) }` | Photo with Favourite, and Share holding Copy Link: Edit and Delete are gone |
| `filtered { _ in false }` | `nil` |
| `titlePath(to: "airdrop")` | `["Photo", "Share", "More", "AirDrop"]` |
| `titlePath(to: "print")` | `nil` |
| `duplicateActionIDs` | `[]` |

## Constraints

- `Element` is a value type: return new trees, don't try to change the one you're given.
- Trees in the tests are at most a few levels deep, so recursion is fine.
- An empty `.menu` counts as having no actions: filtering removes it even when the closure keeps everything.

<Hints>
<Hint>
Every operation has the same shape: `switch self`, answer directly for `.action`, and for `.menu` apply the same operation to each child and combine the answers.
</Hint>
<Hint>
For `filtered(_:)`, `children.compactMap { $0.filtered(isIncluded) }` filters the children and drops the ones that come back `nil` in one step. If what's left is empty, the submenu itself is `nil`.
</Hint>
<Hint>
For the duplicates, walk the tree once with an `inout [String: Int]` of counts, then keep the keys whose count is more than 1, and sort them.
</Hint>
</Hints>

## Solutions

<Approach title="Recurse, and combine the children's answers" time="O(n) for n elements" space="O(depth) for the recursion, plus the result">

```swift
extension MenuTreeComposite.Element {
    public var actionCount: Int {
        switch self {
        case .action:
            return 1
        case .menu(_, let children):
            return children.reduce(0) { $0 + $1.actionCount }
        }
    }

    public func filtered(_ isIncluded: (MenuTreeComposite.Action) -> Bool) -> MenuTreeComposite.Element? {
        switch self {
        case .action(let action):
            return isIncluded(action) ? self : nil
        case .menu(let title, let children):
            let kept = children.compactMap { $0.filtered(isIncluded) }
            return kept.isEmpty ? nil : .menu(title: title, children: kept)
        }
    }

    public func titlePath(to id: String) -> [String]? {
        switch self {
        case .action(let action):
            return action.id == id ? [action.title] : nil
        case .menu(let title, let children):
            for child in children {
                if let path = child.titlePath(to: id) { return [title] + path }
            }
            return nil
        }
    }

    public var duplicateActionIDs: [String] {
        var counts: [String: Int] = [:]
        countIDs(into: &counts)
        return counts.filter { $0.value > 1 }.keys.sorted()
    }

    private func countIDs(into counts: inout [String: Int]) {
        switch self {
        case .action(let action):
            counts[action.id, default: 0] += 1
        case .menu(_, let children):
            children.forEach { $0.countIDs(into: &counts) }
        }
    }
}
```

Each operation is written once and works on a single action, a submenu, or the whole menu, because a submenu answers by asking its children the same question. That uniformity is what the composite pattern buys you, and why `UIMenu` and `UIAction` share a superclass, `UIMenuElement`.

Using an enum makes the tree closed: every `switch` must handle both cases, so a new operation is easy to add and the compiler checks it. Adding a third *kind* of element (a toggle, a deferred submenu) means updating every switch, which is the trade-off you'd weigh against a protocol-based composite.

</Approach>
