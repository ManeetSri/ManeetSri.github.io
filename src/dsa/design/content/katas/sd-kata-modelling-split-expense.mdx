A shared-expenses app lets friends record who paid for what and how to split it. Its old model stored the total and each person's share as separate fields that any screen could edit, so after an edit the shares sometimes added up to £99.99 on a £100 dinner, and the group's balances never reached zero. Build the expense as an aggregate: one root that owns the total and the split, changes them only through its methods, and keeps them consistent after every one.

`ModellingSplitExpense.Expense`: `init(id:paidBy:total:split:)`, `shares`, `balances`, `change(total:split:)`, `changeTotal(to:)` and `remove(_:)`

The stub gives you `MemberID` (ids that sort alphabetically), the two kinds of `Split`, the `Problem` cases and the stored properties, which are `private(set)`. Amounts are whole pence. Write the rest:

- **A split** is `.equally(Set<MemberID>)`, which shares the total as evenly as pennies allow with leftover pennies going one each to the lowest ids, or `.exactly([MemberID: Int])`, which says each participant's share.
- **The rules**, checked whenever an expense is created or changed, reporting the first one broken, in this order: the total is at least 1p (`.totalNotPositive`); the split has at least one participant (`.noParticipants`); no exact share is negative (`.negativeShare`, with the lowest such id); exact shares add up to the total (`.sharesDontAddUp(expected:actual:)`).
- **`shares`** gives each participant's share. They always add up to `total`.
- **`balances`** says what each person owes (positive) or is owed (negative): every participant's share, minus the total for whoever paid. The payer needn't be a participant (you can pay for others), always appears, and the balances always add up to zero.
- **`change(total:split:)`** replaces both together, after checking them as a pair.
- **`changeTotal(to:)`** keeps the split. An equal split shares the new total out again. An exact split's shares still add up to the old total, so a new one throws `.sharesDontAddUp`: someone has to say who pays the difference.
- **`remove(_:)`** takes a participant out. It throws `.notAParticipant` if they aren't in the split, then `.lastParticipant` if they're the only one. An equal split shares the total among the rest; an exact split then throws `.sharesDontAddUp`, because nobody covers the removed share (unless it was 0p).
- **A refused change leaves the expense exactly as it was.**

## Examples

| Expense | Result |
| --- | --- |
| £10.00 paid by Ana, `.equally([cy, ana, ben])` | shares ana 334, ben 333, cy 333 |
| the same expense | balances ana −666, ben 333, cy 333 |
| £10.00 paid by Dan, `.equally([ana, ben])` | balances ana 500, ben 500, dan −1000 |
| £10.00, `.exactly([ana: 600, ben: 300])` | throws `.sharesDontAddUp(expected: 1000, actual: 900)` |
| £0, any split | throws `.totalNotPositive` |
| £9.00 equal split of three, then `changeTotal(to: 1500)` | shares 500 each |
| £10.00 exact split of ana 700, ben 300, then `changeTotal(to: 1200)` | throws `.sharesDontAddUp(expected: 1200, actual: 1000)`, unchanged |
| £9.00 equal split of three, then `remove(cy)` | shares ana 450, ben 450 |

## Constraints

- Keep `total` and `split` as the only stored state. Derive `shares` and `balances` from them, so they can't drift apart.
- Check a proposed change completely before assigning anything, so a refused change can't leave the expense half-updated.
- `Expense` is a struct, so "unchanged" means equal (`==`) to its value before the call.

<Hint>
Write one `private static func check(total: Int, split: Split) throws` that enforces all four rules in order, and call it from `init` and `change(total:split:)` before assigning. Every other method can then be built on `change`.
</Hint>
<Hint>
For an equal split, sort the members first. Each gets `total / count`, and the first `total % count` of them in sorted order get one penny more.
</Hint>
<Hint>
`changeTotal(to:)` can simply be `try change(total: newTotal, split: split)`: for an exact split, the check itself reports that the shares no longer add up. `remove(_:)` can build the smaller split and pass it to `change` too.
</Hint>

## Solutions

<Approach title="Check the pair, then commit; derive everything else" time="O(n log n) for an equal split's shares, where n is the number of participants" space="O(n)">

```swift
public init(id: UUID, paidBy: MemberID, total: Int, split: Split) throws {
    try Self.check(total: total, split: split)
    self.id = id
    self.paidBy = paidBy
    self.total = total
    self.split = split
}

/// The invariant, in one place: every way in goes through it before anything changes
private static func check(total: Int, split: Split) throws {
    guard total >= 1 else { throw Problem.totalNotPositive }
    switch split {
    case let .equally(members):
        guard !members.isEmpty else { throw Problem.noParticipants }
    case let .exactly(amounts):
        guard !amounts.isEmpty else { throw Problem.noParticipants }
        if let negative = amounts.filter({ $0.value < 0 }).keys.min() {
            throw Problem.negativeShare(negative)
        }
        let sum = amounts.values.reduce(0, +)
        guard sum == total else { throw Problem.sharesDontAddUp(expected: total, actual: sum) }
    }
}

public var shares: [MemberID: Int] {
    switch split {
    case let .equally(members):
        let ordered = members.sorted()
        let share = total / ordered.count
        let leftover = total % ordered.count
        return Dictionary(uniqueKeysWithValues: ordered.enumerated().map { index, member in
            (member, share + (index < leftover ? 1 : 0))
        })
    case let .exactly(amounts):
        return amounts
    }
}

public var balances: [MemberID: Int] {
    var balances = shares
    balances[paidBy, default: 0] -= total
    return balances
}

public mutating func change(total: Int, split: Split) throws {
    try Self.check(total: total, split: split)
    self.total = total
    self.split = split
}

public mutating func changeTotal(to total: Int) throws {
    try change(total: total, split: split)
}

public mutating func remove(_ member: MemberID) throws {
    let remaining: Split
    switch split {
    case var .equally(members):
        guard members.remove(member) != nil else { throw Problem.notAParticipant(member) }
        guard !members.isEmpty else { throw Problem.lastParticipant }
        remaining = .equally(members)
    case var .exactly(amounts):
        guard amounts.removeValue(forKey: member) != nil else { throw Problem.notAParticipant(member) }
        guard !amounts.isEmpty else { throw Problem.lastParticipant }
        remaining = .exactly(amounts)
    }
    try change(total: total, split: remaining)
}
```

Three habits make the aggregate trustworthy.

- **One check, one place.** Every way in (`init`, `change`, and the methods built on it) passes through `check(total:split:)` before assigning anything. Adding a fifth rule means editing one function.
- **Check, then commit.** Nothing is assigned until the proposed total and split have passed together, so a thrown error can't leave a new total with an old split.
- **Store the minimum, derive the rest.** The old model's bug was storing shares beside the total. Here shares and balances are computed from the split, so they can't disagree with it.

Notice what `changeTotal(to:)` doesn't do for an exact split: guess. It could scale every share, or give the difference to the payer, but those are product decisions the model has no business making silently. Refusing, and making the caller say what they mean with `change(total:split:)`, keeps the invariant and the intent.

On a real app this expense would be one resource on the server, saved with a version number so two friends editing it at once can't both win; the client's aggregate gives instant feedback and works offline, and the server checks the same rules again.

</Approach>
