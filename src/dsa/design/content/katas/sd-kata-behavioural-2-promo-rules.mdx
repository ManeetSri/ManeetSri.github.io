A shop runs promotions whose rules marketing changes every week: "£25 or more, and either a toy in the basket or gold tier, and not a first order". The rules arrive as a tree, so the app can evaluate them and also say *why* a basket doesn't qualify ("add £13 to get free delivery"). Write both interpretations of the tree.

`PromoEligibilityRules.Rule.isSatisfied(by:) -> Bool` and `PromoEligibilityRules.Rule.unmet(by:) -> [Rule]`

**`isSatisfied(by:)`** evaluates the rule against a `Basket`:

- `.minimumSubtotal(pence: p)` holds when the subtotal is at least `p`.
- `.containsCategory(c)` holds when the basket's categories include `c`.
- `.tierAtLeast(t)` holds when the customer's tier is `t` or higher (`standard` below `silver` below `gold`).
- `.firstOrder` holds when the customer has no previous orders.
- `.all(rules)` holds when every rule holds, so `.all([])` always holds. `.any(rules)` holds when at least one does, so `.any([])` never does. `.not(rule)` holds when `rule` doesn't.

**`unmet(by:)`** explains a failure. It returns `[]` when the rule holds. Otherwise:

- a failing leaf, or a failing `.not`, returns itself, `[self]`;
- a failing `.all` or `.any` returns its failing children's explanations joined in order (for `.any`, every child failed);
- a failing `.any([])`, which has no children to blame, returns itself.

## Examples

The basket below has a subtotal of £12.00 (1200 pence), one `garden` item, standard tier and no previous orders.

| Rule | `isSatisfied` | `unmet` |
| --- | --- | --- |
| `.minimumSubtotal(pence: 2500)` | false | `[.minimumSubtotal(pence: 2500)]` |
| `.all([.firstOrder, .containsCategory("garden")])` | true | `[]` |
| `.all([.minimumSubtotal(pence: 2500), .containsCategory("garden"), .all([.tierAtLeast(.gold), .firstOrder])])` | false | `[.minimumSubtotal(pence: 2500), .tierAtLeast(.gold)]` |
| `.any([.containsCategory("toys"), .tierAtLeast(.silver)])` | false | `[.containsCategory("toys"), .tierAtLeast(.silver)]` |
| `.not(.firstOrder)` | false | `[.not(.firstOrder)]` |
| `.any([])` | false | `[.any([])]` |

## Constraints

- Rules nest to any depth, but stay small: tens of rules, not thousands.
- `unmet(by:)` is empty exactly when `isSatisfied(by:)` is true. The tests check that on many combinations.
- Both functions are pure: no state, no clock, no network.

<Hints>
<Hint>
`isSatisfied` is one `switch self` with a line per case. For the combinators, `allSatisfy` and `contains(where:)` do the work, and both give the right answer for an empty list.
</Hint>
<Hint>
Start `unmet` with `guard !isSatisfied(by: basket) else { return [] }`. After that you know the rule failed, and each case only has to say who's to blame.
</Hint>
<Hint>
Satisfied children report `[]`, so for a failing `.all` or `.any`, `rules.flatMap { $0.unmet(by: basket) }` keeps exactly the failures. Put `case .any(let rules) where rules.isEmpty:` before the general case.
</Hint>
</Hints>

## Solutions

<Approach title="Two interpretations of one tree" time="O(n) to evaluate, O(n × depth) to explain" space="O(depth) for the recursion">

```swift
public func isSatisfied(by basket: Basket) -> Bool {
    switch self {
    case .minimumSubtotal(let pence): basket.subtotalPence >= pence
    case .containsCategory(let category): basket.categories.contains(category)
    case .tierAtLeast(let tier): basket.tier >= tier
    case .firstOrder: basket.previousOrders == 0
    case .all(let rules): rules.allSatisfy { $0.isSatisfied(by: basket) }
    case .any(let rules): rules.contains { $0.isSatisfied(by: basket) }
    case .not(let rule): !rule.isSatisfied(by: basket)
    }
}

public func unmet(by basket: Basket) -> [Rule] {
    guard !isSatisfied(by: basket) else { return [] }
    switch self {
    case .minimumSubtotal, .containsCategory, .tierAtLeast, .firstOrder, .not:
        return [self]
    case .any(let rules) where rules.isEmpty:
        return [self]
    case .all(let rules), .any(let rules):
        // Satisfied children report nothing, so only the failures remain
        return rules.flatMap { $0.unmet(by: basket) }
    }
}
```

This is the Specification pattern in its tree form: small named rules composed with `all`, `any` and `not`. It's also an interpreter (the enum is the grammar's syntax tree) and a visitor in Swift's enum style: each new operation is one more recursive switch, and the compiler checks it handles every kind of rule. With a closure-based specification you could evaluate the rule, but you couldn't explain it.

`unmet` calls `isSatisfied` at every level, so a deep tree is evaluated more than once. For promotion-sized trees that's irrelevant; for large ones, compute both in one pass by returning the explanation and deriving the answer from whether it's empty.

</Approach>
