The sign-up screen used to do everything in one `submitTapped()`: check the fields, build the JSON, pick the error text and post it. Three groups of people asked for changes to that method, and every change risked breaking the others. It's now split by **who asks for the change**: product owns the rules, the backend team owns the request body, content design owns the wording. Write the pieces, and the small flow that puts them together.

`SolidSignUp.Validator().problems(in:) -> [Problem]`, `SolidSignUp.RequestEncoder().body(for:) throws -> Data` and `SolidSignUp.Flow(send:).submit(_:) async throws -> Outcome`

- **Validator** (product's rules). Report every problem, in the order `Problem` declares its cases:
  - `.usernameLength`: the username, trimmed of spaces and newlines, isn't 3 to 20 characters long.
  - `.usernameCharacters`: the trimmed username contains anything other than the ASCII letters `a`–`z` and `A`–`Z`, the digits `0`–`9` and `_`.
  - `.emailFormat`: the trimmed email contains whitespace, or doesn't have exactly one `@` with at least one character before it, or the part after the `@` has no `.`, or starts or ends with one.
  - `.passwordLength`: the password, as typed, has fewer than 8 characters.
  - `.passwordNeedsDigit`: the password has no digit `0`–`9`.
- **RequestEncoder** (the backend's contract): a JSON object with exactly three keys. `user_name` is the trimmed username, `email` is the trimmed email in lower case, and `password` is exactly as typed.
- **Messages** (content design's copy) is already written. Leave it alone: that's the point.
- **Flow**: validate first. If there are problems, return `.invalid` with each problem's message, in order, and send nothing. Otherwise encode the body, `send` it, and return `.submitted`. An error thrown by `send` reaches the caller.

## Examples

| Form (username, email, password) | `problems(in:)` | `submit` |
| --- | --- | --- |
| `"maneet_99"`, `"maneet@example.com"`, `"rainy-day-7"` | `[]` | sends `{"email":"maneet@example.com","password":"rainy-day-7","user_name":"maneet_99"}`, returns `.submitted` |
| `"  ab_9  "`, `" Maneet@Example.COM "`, `"rainy-day-7"` | `[]` | sends `user_name` `"ab_9"` and `email` `"maneet@example.com"` |
| `"ab"`, `"maneet@example.com"`, `"password"` | `[.usernameLength, .passwordNeedsDigit]` | `.invalid(["Usernames are 3 to 20 characters.", "Add at least one number to your password."])`, nothing sent |
| `"é"`, `"maneet@example.com"`, `"rainy-day-7"` | `[.usernameLength, .usernameCharacters]` | `.invalid` with both messages |
| `"maneet_99"`, `"maneet@example"`, `"rainy-day-7"` | `[.emailFormat]` | `.invalid(["That email address doesn't look right."])` |

## Constraints

- Count lengths in `Character`s (what `String.count` gives).
- Don't trim the password: spaces are allowed in it, and they count.
- "Digit" means `0` to `9` only. `Character.isNumber` also accepts characters such as `"٣"` and `"½"`, which this backend rejects.
- `Flow` calls `send` at most once per `submit`, and never for an invalid form.
- The key order in the JSON doesn't matter to the tests; `JSONEncoder` with `.sortedKeys` makes it stable if you want to compare bodies by eye.

<Hints>
<Hint>
Each rule is one `if` that appends to an array, written in the order of `Problem`'s cases. That gives you the reporting order for free.
</Hint>
<Hint>
`("0"..."9").contains(character)` checks for an ASCII digit; build the username check the same way from `"a"..."z"`, `"A"..."Z"` and `"_"`, then use `allSatisfy`.
</Hint>
<Hint>
For the email, `split(separator: "@", omittingEmptySubsequences: false)` keeps empty parts, so `"maneet@"` splits into two parts and the empty domain is easy to catch.
</Hint>
<Hint>
A private `Encodable` struct with `CodingKeys` (`case userName = "user_name"`) keeps the backend's naming out of the rest of your code.
</Hint>
</Hints>

## Solutions

<Approach title="One type per reason to change, and a flow that only sequences them" time="O(n) in the length of the fields" space="O(n)">

```swift
public func problems(in form: Form) -> [Problem] {
    var found: [Problem] = []
    let username = form.username.trimmingCharacters(in: .whitespacesAndNewlines)
    if !(3...20).contains(username.count) { found.append(.usernameLength) }
    if !username.allSatisfy(Self.isUsernameCharacter) { found.append(.usernameCharacters) }
    if !Self.looksLikeEmail(form.email.trimmingCharacters(in: .whitespacesAndNewlines)) { found.append(.emailFormat) }
    if form.password.count < 8 { found.append(.passwordLength) }
    if !form.password.contains(where: Self.isDigit) { found.append(.passwordNeedsDigit) }
    return found
}

public func submit(_ form: Form) async throws -> Outcome {
    let problems = validator.problems(in: form)
    guard problems.isEmpty else { return .invalid(problems.map(messages.text(for:))) }
    try await send(try encoder.body(for: form))
    return .submitted
}
```

The encoder is a private `Encodable` struct with `CodingKeys` that map `userName` to `user_name`, and it trims and lower-cases on the way in.

Notice what *didn't* need a protocol. The validator, encoder and messages are plain structs: the split that matters for single responsibility is **who can change each piece without touching the others**, and you can see that in the file layout and the tests. The one seam that does need replacing in tests, the network, is a closure. When product changes the password rule, only `Validator` and its tests change. When the backend renames `user_name`, only `RequestEncoder` does. When copy changes, only `Messages` does.

A further step, if the screen grows: give `Validator` a `Rules` value (minimum password length, allowed username characters) fetched from remote config, so product can change the rules without a release.

</Approach>
