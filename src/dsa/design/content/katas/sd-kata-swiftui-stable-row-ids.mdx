A `ForEach` is only as good as its ids. Give a feed's rows ids that change between updates and SwiftUI sees every row removed and a new set inserted: state is lost, animations go wrong and the scroll position jumps. Give a sent message one id while it's pending and another once the server confirms it, and the row blinks out and back in. Build the mapping a real feed needs: identities from the data itself, stable from a draft's first appearance to its confirmation, unique even when pages overlap, plus the changes a list would animate between two sets of rows.

`FeedRowIdentity.identity(of:) -> String?`, `FeedRowIdentity.rows(from:) -> [Row]` and `FeedRowIdentity.changes(from:to:) -> Changes`

An `Item` comes from the server (`serverID`), was created on this device (`clientID`), or both: when the server confirms a draft it echoes the client id back.

- **`identity(of:)`:** `"client:"` followed by the client id when the item has a non-empty one; otherwise `"server:"` followed by the server id when it has a non-empty one; otherwise `nil`. The prefixes keep the two id spaces apart, so server item `7` and draft `7` never collide.
- **`rows(from:)`:** one `Row` per identity, in the order identities first appear. When an identity appears more than once (overlapping pages, or a draft and its confirmed copy in one list), the row keeps the **first** position and takes the title and pending flag of the **last** occurrence. Items with no identity are left out.
- **`changes(from:to:)`:** `inserted` lists ids only in the new rows, in the new order; `removed` lists ids only in the old rows, in the old order; `updated` lists ids in both whose title or pending flag changed, in the new order. Rows that only moved aren't reported.

## Examples

| Items | Row ids |
| --- | --- |
| server `s2`; client `c3` | `["server:s2", "client:c3"]` |
| server `7`; client `7` | `["server:7", "client:7"]` |
| no ids; server `s1`; empty strings for both | `["server:s1"]` |
| server `a` "Old title"; server `b`; server `a` "New title" | `["server:a", "server:b"]`, with `a` titled "New title" |
| client `c9` (pending); server `s1`; server `s42` with client `c9` | `["client:c9", "server:s1"]`, with `c9` no longer pending |

| Old rows | New rows | Changes |
| --- | --- | --- |
| `client:c9` pending | `client:c9` sent | updated `["client:c9"]` |
| `a`, `b`, `c` | `c` (edited), `a`, `d` | inserted `["d"]`, removed `["b"]`, updated `["c"]` |
| `a`, `b` | `a`, `b` | nothing |

## Constraints

- Ids must depend only on the item: the same items always give the same ids. No `UUID()`, no indexes.
- `changes(from:to:)` can assume each list's ids are unique, as `rows(from:)` guarantees.
- Feeds can hold thousands of items, so aim for linear time: a dictionary from id to position beats searching the rows for each item.

<Hints>
<Hint>
Check the client id first. A draft has only a client id; once confirmed it has both. Preferring the client id is what keeps its identity the same before and after.
</Hint>
<Hint>
Walk the items once, keeping `[String: Int]` from identity to the row's index. A new identity appends a row; one you've seen replaces the row at its stored index.
</Hint>
<Hint>
For the changes, build a dictionary of the old rows by id and a set of the new ids. Each new row is an insertion or, if its value differs from the old one, an update; each old id missing from the new set is a removal.
</Hint>
</Hints>

## Solutions

<Approach title="One pass with an index of positions, then a keyed comparison" time="O(n + m)" space="O(n + m)">

```swift
public static func identity(of item: Item) -> String? {
    if let clientID = item.clientID, !clientID.isEmpty { return "client:" + clientID }
    if let serverID = item.serverID, !serverID.isEmpty { return "server:" + serverID }
    return nil
}

public static func rows(from items: [Item]) -> [Row] {
    var rows: [Row] = []
    var position: [String: Int] = [:]
    for item in items {
        guard let id = identity(of: item) else { continue }
        let row = Row(id: id, title: item.title, isPending: item.isPending)
        if let index = position[id] {
            rows[index] = row
        } else {
            position[id] = rows.count
            rows.append(row)
        }
    }
    return rows
}

public static func changes(from old: [Row], to new: [Row]) -> Changes {
    let oldByID = Dictionary(old.map { ($0.id, $0) }, uniquingKeysWith: { first, _ in first })
    let newIDs = Set(new.map(\.id))
    var changes = Changes()
    for row in new {
        if let previous = oldByID[row.id] {
            if previous != row { changes.updated.append(row.id) }
        } else {
            changes.inserted.append(row.id)
        }
    }
    changes.removed = old.map(\.id).filter { !newIDs.contains($0) }
    return changes
}
```

The identity rule does the architectural work. Because a draft's client id is stored with it and echoed by the server, the row a user sees while sending is the same row once it's sent: `changes` reports an **update**, so SwiftUI changes the bubble's style in place rather than removing it and inserting another. Prefixing each id space is cheap insurance against two systems that both count from 1.

Dropping unidentifiable items is a deliberate choice. The alternatives, an index or a fresh UUID, would make that row's identity change on every update, which is the bug the whole kata exists to prevent; log such items instead, because they mean a server bug.

`changes(from:to:)` is a simplified version of what `ForEach` and diffable data sources compute from ids. It also shows why moves are cheap with stable ids: a row that only moved isn't inserted, removed or updated, so SwiftUI moves it and nothing more.

</Approach>
