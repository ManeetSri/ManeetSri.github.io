`UITableView` scrolls through thousands of rows while creating only about a screenful of cells, because `dequeueReusableCell(withIdentifier:for:)` hands back cells that scrolled off screen instead of making new ones. Build that pool yourself: one queue of idle elements per reuse identifier, a factory per identifier for when the queue is empty, and the rules that keep reuse safe.

`CreationalReusePool.Pool<Element: Reusable>(maxIdlePerIdentifier:)` with `register(_:make:)`, `dequeue(_:) throws(PoolError) -> Element`, `enqueue(_:for:)`, `idleCount(for:)`, `drain()` and `created`

- **`register(_:make:)`** stores how to make a new element for an identifier. Registering again replaces the factory.
- **`dequeue(_:)`**:
  - throws `.unregistered(identifier)` if nothing is registered for it;
  - otherwise, if elements are waiting for that identifier, removes the **most recently enqueued** one, calls its `prepareForReuse()`, and returns it;
  - otherwise makes a new element with the factory, adds one to `created`, and returns it **without** calling `prepareForReuse()`.
- **`enqueue(_:for:)`** puts an element back to wait. It does nothing if:
  - the identifier isn't registered;
  - that element (the same object) is already waiting for that identifier;
  - that identifier already has `maxIdlePerIdentifier` elements waiting. The extra element is simply let go.
- **`idleCount(for:)`** is how many elements are waiting for an identifier: 0 for one it has never seen.
- **`drain()`** lets go of every waiting element, for every identifier, as an app does on a memory warning. `created` doesn't change.

## Examples

| Steps (with "text" registered) | Result |
| --- | --- |
| `dequeue("text")` twice | two different elements, `created == 2`, neither prepared |
| `let a = dequeue("text")`, `enqueue(a, for: "text")`, `dequeue("text")` | `a` again, prepared once; `created == 1` |
| enqueue `a`, then `b`, then dequeue twice | `b`, then `a` |
| 1,000 rows, 10 on screen: enqueue the top row's element before dequeuing each new one | `created == 10` |
| `enqueue(a)` twice, then dequeue twice | `a`, then a new element |
| `maxIdlePerIdentifier: 2`, enqueue three elements | `idleCount(for: "text") == 2` |
| `dequeue("video")` with nothing registered | throws `.unregistered("video")` |

## Constraints

- Elements are compared by **identity** (`===`), not equality: they're objects, and two cells can look the same.
- Like UIKit's reuse queues, the pool is used from one thread or actor, so it needs no locking.
- `maxIdlePerIdentifier` is 0 or more; 0 means nothing is ever kept.

<Hints>
<Hint>
Two dictionaries keyed by identifier are enough: `[String: () -> Element]` for the factories and `[String: [Element]]` for the idle elements.
</Hint>
<Hint>
An array used as a stack gives "most recently enqueued first": `append` to enqueue, `popLast()` to dequeue.
</Hint>
<Hint>
Check `contains(where: { $0 === element })` before appending, and the count against the limit. Remember that a dictionary's array is a copy: read it, change it, and write it back (or use `idle[identifier, default: []]`).
</Hint>
</Hints>

## Solutions

<Approach title="A factory and a stack of idle elements per identifier" time="O(1) to dequeue, O(k) to enqueue for k idle elements" space="O(total idle elements)">

```swift
public final class Pool<Element: Reusable> {
    public private(set) var created = 0

    private let maxIdle: Int
    private var factories: [String: () -> Element] = [:]
    private var idle: [String: [Element]] = [:]

    public init(maxIdlePerIdentifier: Int = 8) {
        maxIdle = max(0, maxIdlePerIdentifier)
    }

    public func register(_ identifier: String, make: @escaping () -> Element) {
        factories[identifier] = make
    }

    public func dequeue(_ identifier: String) throws(PoolError) -> Element {
        guard let make = factories[identifier] else { throw .unregistered(identifier) }
        if let recycled = idle[identifier]?.popLast() {
            recycled.prepareForReuse()
            return recycled
        }
        created += 1
        return make()
    }

    public func enqueue(_ element: Element, for identifier: String) {
        guard factories[identifier] != nil else { return }
        var waiting = idle[identifier, default: []]
        guard waiting.count < maxIdle, !waiting.contains(where: { $0 === element }) else { return }
        waiting.append(element)
        idle[identifier] = waiting
    }

    public func idleCount(for identifier: String) -> Int {
        idle[identifier]?.count ?? 0
    }

    public func drain() {
        idle.removeAll()
    }
}
```

Taking the most recently returned element first keeps the "warmest" object in use, and lets the oldest idle ones be the ones a cap or a drain throws away. The duplicate check matters more than it looks: if a bug returns the same cell twice, two rows would later be handed one cell, and each would overwrite the other's content. The cap is the memory side of the bargain: idle elements are memory you choose to keep, so a pool must know when to let go. In an app, call `drain()` from `UIApplication.didReceiveMemoryWarningNotification`.

</Approach>
