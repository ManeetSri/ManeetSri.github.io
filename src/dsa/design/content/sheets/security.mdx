A MASVS-style checklist for an iOS app, grouped the way a security review reads it. Each line is a check, followed by the usual way to meet it. The lessons are in [Security engineering](/design/learn/sd-sec-threat-modelling) and [OWASP MASVS](/design/learn/sd-sec-masvs).

## Storage

| Check | How |
| --- | --- |
| Secrets live only in the keychain | Tokens, keys and passwords in Keychain, never in `UserDefaults`, plists, files or Core Data |
| The right accessibility class | `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` for most secrets; `AfterFirstUnlock` only if background work needs it |
| Sensitive files are protected | Data protection `.complete` where background access isn't needed |
| Nothing sensitive in logs | `Logger` with `privacy: .private` (the default for dynamic strings); never log tokens |
| Nothing sensitive in caches | `Cache-Control: no-store` for personal responses; clear `URLCache` on sign-out |
| The app switcher snapshot hides secrets | Cover the screen when the scene leaves the foreground |
| Copy and paste is limited for secrets | Disable copy on secret fields |
| Sign-out clears everything | Keychain items, databases, caches, cookies, in-memory state |
| Keys never leave the device | Secure Enclave keys for signing; CryptoKit for encryption |

## Crypto

| Check | How |
| --- | --- |
| No home-made crypto | CryptoKit: `AES.GCM` or `ChaChaPoly` for encryption, `SHA256`, `HMAC`, `Curve25519`/`P256` |
| Keys are random and stored safely | `SymmetricKey(size: .bits256)` kept in the keychain |
| Passwords are never stored | Send them over TLS; the server hashes them |

## Authentication

| Check | How |
| --- | --- |
| OAuth uses PKCE in a system browser | `ASWebAuthenticationSession`; never a custom web view for sign-in |
| Tokens are short-lived | Access tokens in minutes; refresh tokens rotated and revocable |
| Biometrics protect something real | A keychain item with `SecAccessControl` `.biometryCurrentSet`, not just an `LAContext` yes/no |
| Passkeys where possible | `ASAuthorizationPlatformPublicKeyCredentialProvider` |
| Server enforces authorisation | The app hides buttons; the server decides |

## Network

| Check | How |
| --- | --- |
| TLS everywhere | ATS on, no `NSAllowsArbitraryLoads`; exceptions narrow and justified |
| Pinning, if you pin, can rotate | Pin public keys, ship backup pins, have a remote way out |
| No secrets in URLs | Tokens in headers, never in query strings (they end up in logs) |
| Certificates are validated | Never accept every certificate in `urlSession(_:didReceive:)` |

## Platform interaction

| Check | How |
| --- | --- |
| Deep links are input | Validate every parameter; never act on a link without confirmation for sensitive actions |
| Universal links over custom schemes | Custom schemes can be claimed by other apps |
| Web views are locked down | Restrict navigation; expose the minimum JavaScript bridge; no `file://` access to app data |
| Pasteboard reads are deliberate | Use `UIPasteControl` or read only on user action |
| Extensions get only what they need | Separate keychain access groups and App Group data |

## Code and build

| Check | How |
| --- | --- |
| No secrets in the binary | Assume anything shipped can be extracted; keep secrets on the server |
| Dependencies are known | Pinned versions, reviewed updates, privacy manifests present |
| Release builds strip debug features | No debug menus, test endpoints or verbose logging in release |
| Integrity checks are realistic | App Attest and DeviceCheck raise the cost of abuse; jailbreak detection only slows attackers |

## Privacy (with the security review)

| Check | How |
| --- | --- |
| Permissions asked in context | At the moment of use, with a clear purpose string |
| Tracking needs consent | ATT prompt before cross-app tracking or IDFA access |
| Privacy manifest is complete | Required-reason APIs declared; SDK manifests present |
| Account deletion works in the app | Required by App Store rules when accounts can be created |

## STRIDE prompts for a threat model

| Threat | Ask |
| --- | --- |
| Spoofing | Can someone pretend to be this user, device or server? |
| Tampering | Can requests, local data or the binary be changed? |
| Repudiation | Could a user deny an action we can't prove? |
| Information disclosure | Where could data leak: logs, backups, screenshots, caches, URLs? |
| Denial of service | Can one client or one bad input exhaust the server or the app? |
| Elevation of privilege | Can a normal user reach admin functions or another user's data? |
