The steps of a mobile system design, what to cover in each, and roughly how long to spend in a 45-minute interview. The lessons behind it are [The design framework](/design/learn/sd-orientation-framework) and [The framework, step by step](/design/learn/sd-interview-framework).

## The steps

| Step | Minutes (of 45) | What you produce | Done when |
| --- | --- | --- | --- |
| 1. Clarify and scope | 5 | Who uses it, the core flows, what's out of scope | You and the interviewer agree on 2–4 features to design |
| 2. Requirements | 3 | Functional list; non-functional priorities (offline, latency, battery, privacy, scale) | Each non-functional requirement has a number or a clear "must" |
| 3. Estimates | 3 | Users, requests per second, payload and storage sizes, on device and server | Every number that changes a decision is on the board |
| 4. High-level design | 7 | Boxes and arrows: app, API, services, stores, push, CDN | One request can be traced end to end |
| 5. Client architecture | 8 | Layers, modules, state, navigation, DI, threading | You can say where each responsibility lives |
| 6. API and data model | 7 | Endpoints or messages, pagination, errors; entities and where each is stored | The app can render its main screen from what you defined |
| 7. Deep dives | 8 | The two or three hardest parts worked through | The interviewer's follow-ups are answered with mechanisms, not adjectives |
| 8. Failure, offline, security | 3 | Bad network, retries, conflicts, partial failure, auth, privacy | Each failure has a detection and a behaviour |
| 9. Trade-offs and evolution | 1–2 | What you chose over what, and what changes at 10× | You've named at least two real trade-offs |

## Questions worth asking in step 1

| About | Ask |
| --- | --- |
| Users | Who are they, and how many? Daily or occasional use? Which countries and devices? |
| Core flows | Which two or three things must work brilliantly? What can we drop? |
| Platform | iPhone only, or iPad, watch, widgets, Mac? Minimum iOS version? |
| Data | Who creates content? How big is it? Does it change after creation? Is it shared? |
| Freshness | How stale can a screen be? Seconds, minutes, a day? |
| Offline | What must work with no network? Can users create things offline? |
| Scale | Requests per user per day? Peaks (events, launches, time zones)? |
| Constraints | Existing backend, team size, deadline, compliance (health, payments, children)? |

## Non-functional requirements to put a number on

| Attribute | Typical mobile target | Lesson |
| --- | --- | --- |
| Launch | Cold launch under 400 ms to first frame on a recent device | [Launch time](/design/learn/sd-perf-launch) |
| Scrolling | No hitches: under 5 ms of hitch time per second scrolled | [Rendering and hitches](/design/learn/sd-perf-rendering) |
| Freshness | Feed under 1 minute stale; chat under 1 second | [Push vs pull](/design/learn/sd-rt-push-vs-pull) |
| Offline | Read the last session's content; queue writes | [The local database as source of truth](/design/learn/sd-sync-local-truth) |
| Data use | A screen's first payload under 100 KB compressed | [Compression and payload budgets](/design/learn/sd-net-compression-budgets) |
| Reliability | Crash-free sessions above 99.8% | [SLAs, SLOs and SLIs](/design/learn/sd-est-sla-slo-sli) |
| Privacy | Collect the minimum; no tracking before consent | [Data minimisation](/design/learn/sd-priv-minimisation) |

## The client architecture checklist

- **Layers:** presentation (views, view models or reducers), domain (models, use cases), data (repositories, API client, persistence).
- **State:** where each piece lives, who owns it, how screens observe it.
- **Navigation:** who decides the next screen; how deep links and notifications get in.
- **Dependencies:** a composition root; protocols at the boundaries you'll fake in tests.
- **Threading:** what runs on the main actor, what runs in actors or background tasks.
- **Storage:** what's cached in memory, on disk, in the database, in the keychain.
- **Modules:** feature modules and shared core, if the team or app is big.

## Deep-dive candidates by product

| Product | Usual deep dives |
| --- | --- |
| Feed | Cursor pagination, prefetching images, cache and invalidation, optimistic likes |
| Chat | Delivery and ordering, offline outbox, real-time transport, push when backgrounded |
| Maps and location | Location accuracy vs battery, streaming updates, offline tiles |
| Media | Image pipeline, HLS and adaptive bitrate, background uploads and downloads |
| Commerce | Cart sync, idempotent checkout, payment states, inventory holds |
| Productivity | Sync and conflict resolution, search, background refresh |
| SDKs | Public API, thread safety, initialisation cost, versioning |

## Red flags interviewers note

- Jumping to boxes before agreeing on scope.
- Numbers with no unit, or an estimate that never changes a decision.
- "We'll cache it" with no key, size, eviction or invalidation.
- "Retry on failure" with no backoff, limit or idempotency.
- No offline story for a mobile app.
- Designing only the backend, or only the views.
- Defending every choice: strong candidates name what they gave up.

## Phrases that help

| When | Say |
| --- | --- |
| Scoping | "I'll focus on X and Y and leave Z out unless you'd like it in. Does that work?" |
| Choosing | "There are two options here. A gives us …, B gives us …. Given our priority on …, I'd pick A." |
| Unsure | "I haven't used X in production. My understanding is …, so I'd validate it with …" |
| Running late | "I'll sketch the remaining parts quickly so we have time for a deep dive." |
| Wrapping up | "If this grew 10×, the first thing to break would be …, and I'd …" |
