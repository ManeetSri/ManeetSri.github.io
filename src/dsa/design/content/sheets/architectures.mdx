What each app architecture solves, what it costs, and when to reach for it. The comparison is worked through in [One feature built five ways](/design/learn/sd-goals-five-ways), and choosing in [A decision matrix by app and team](/design/learn/sd-evolve-decision-matrix).

## At a glance

| Architecture | Who holds logic | State lives in | Navigation | Testability | Boilerplate | Best fit |
| --- | --- | --- | --- | --- | --- | --- |
| Apple MVC | View controller | View controller and models | View controller pushes the next one | Low unless you extract services | Very low | Small apps, prototypes, simple screens |
| SwiftUI "MV" | Views and `@Observable` models | Models injected through the environment | `NavigationStack` driven by state | Medium: models test well, views don't | Very low | SwiftUI apps with thin screens and rich models |
| MVP | Presenter | Presenter and models | Presenter or a router | High: the view is a passive protocol | Medium | UIKit screens with lots of presentation logic |
| MVVM | View model | View model | Coordinator or router | High | Low to medium | Most UIKit and SwiftUI apps |
| Unidirectional (Redux, TCA) | Reducers; effects at the edges | One store per feature, composed into a tree | State-driven | Very high: exhaustive tests | Medium to high | Complex state, many interacting features, teams that value predictability |
| VIPER / VIP | Interactor (logic), presenter (formatting) | Interactor and entities | Router (wireframe) | High | High | Large UIKit teams wanting strict roles |
| RIBs | Interactors in a tree of business logic | Each RIB's interactor | Routers attach and detach children | High | High; needs code generation | Very large apps with many teams |
| Clean / hexagonal | Use cases (domain), behind ports | Domain entities; adapters at the edges | Any of the above in presentation | Very high for the domain | Medium to high | Long-lived apps with rich rules and many data sources |

Clean and hexagonal describe layers and dependency direction, so they combine with any presentation pattern: MVVM + Clean, TCA + Clean and so on.

## The responsibilities every architecture must place

| Responsibility | MVC | MVVM | TCA-style | VIPER | Clean |
| --- | --- | --- | --- | --- | --- |
| Rendering | View | View | View | View | View (presentation) |
| Presentation state | VC | View model | Feature state | Presenter | Presentation layer |
| Business rules | VC or model | View model or services | Reducer | Interactor | Use cases and entities |
| Side effects (network, disk) | VC calls services | View model calls repositories | Effects through dependencies | Interactor calls services | Use cases call ports; adapters implement them |
| Navigation | VC | Coordinator | State and navigation reducers | Router | Presentation layer |
| Wiring | Storyboards, VC init | Coordinator or composition root | Store creation | Builder (assembly) | Composition root |

## What goes wrong in each

| Architecture | Failure mode | Early warning | Fix |
| --- | --- | --- | --- |
| MVC | Massive View Controller | VC over ~500 lines; it imports networking and persistence | Child VCs, data-source objects, services ([lighter VCs](/design/learn/sd-mvc-child-vcs)) |
| MVVM | Massive view model | View model imports UIKit, navigates, formats and fetches | Split by screen section; move rules into use cases; coordinators for navigation ([massive view models](/design/learn/sd-mvvm-massive)) |
| MVVM + Combine | Binding spaghetti | Long pipelines nobody can trace; retain cycles | Inputs and outputs; `@Observable`; async functions for one-shot work |
| TCA-style | Giant state and slow tests | Every action passes through one root reducer; state copied on every change | Scope features; keep heavy data out of state; test children alone ([trade-offs](/design/learn/sd-udf-trade-offs)) |
| VIPER | Ceremony | Five files to show a label; presenters that only forward | Generate templates; collapse roles for simple screens |
| Clean | Over-engineering | Use cases that only call one repository method; mappers for identical types | Skip layers that add nothing ([when it's too much](/design/learn/sd-clean-over-engineering)) |

## Choosing

| Situation | Lean towards |
| --- | --- |
| Small app, one or two developers, SwiftUI | `@Observable` models with views ("MV"), plus a few services |
| Typical product app, 3–15 developers | MVVM + coordinators or state-driven navigation, repositories, DI |
| Complex interacting state (editors, multi-step flows, real-time) | Unidirectional, at least for those features |
| 30+ developers, many teams, UIKit | Strict roles (VIPER, RIBs) or MVVM with enforced module boundaries |
| Rich domain rules, many data sources, long life | Clean / hexagonal layers under any presentation pattern |
| Legacy MVC that works | Don't rewrite: extract services, then migrate screen by screen ([strangler fig](/design/learn/sd-evolve-strangler)) |

## Questions that decide it in an interview

1. How much logic is there beyond fetching and showing data?
2. How many developers will work in this code at once?
3. How important are fast, exhaustive tests?
4. UIKit, SwiftUI, or both?
5. How long will the app live, and how often will data sources change?
