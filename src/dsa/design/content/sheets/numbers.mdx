Round numbers for back-of-the-envelope estimates. They're orders of magnitude, not benchmarks: use them to decide, then measure. The method is in [Back-of-the-envelope maths](/design/learn/sd-est-envelope-maths) and [Latency numbers to know](/design/learn/sd-est-latency-numbers).

## Time

| Quantity | Value | Useful as |
| --- | --- | --- |
| Seconds in a day | 86,400 ≈ 10⁵ | requests per day ÷ 10⁵ = average per second |
| Seconds in a month | ≈ 2.6 million ≈ 2.5 × 10⁶ | |
| Seconds in a year | ≈ 31.5 million ≈ 3 × 10⁷ | |
| Frame at 60 Hz / 120 Hz | 16.7 ms / 8.3 ms | the budget for main-thread work per frame |
| Human "instant" | under 100 ms | tap feedback |
| Human "flow is kept" | under 1 s | screen load |
| Attention is lost | about 10 s | long operations need progress and cancel |

## Latency

| Operation | Rough time |
| --- | --- |
| L1 cache reference | 1 ns |
| Main memory reference | 100 ns |
| Read 1 MB sequentially from memory | 50 µs |
| Read 4 KB randomly from an SSD | 20–100 µs |
| Read 1 MB sequentially from an SSD | 0.5–1 ms |
| Round trip inside a data centre | 0.5 ms |
| Redis or memcached get, same region | under 1 ms |
| Indexed database query | 1–10 ms |
| Round trip, same continent | 20–50 ms |
| Round trip, across an ocean | 100–150 ms |
| Wi-Fi round trip to a nearby server | 20–50 ms |
| 4G/LTE round trip | 50–100 ms |
| 5G round trip | 20–40 ms |
| 3G or congested cellular | 200–500 ms+ |
| Cellular radio waking from idle | 0.1–2 s before the first byte |

**A new HTTPS connection costs round trips:** DNS (1, unless cached) + TCP (1) + TLS 1.3 (1) before the request's own round trip. TLS 1.2 adds one more. HTTP/3 over QUIC folds transport and TLS into 1, or 0 on resumption. On a 100 ms cellular link a cold request can take 400 ms before any work happens, which is why connection reuse matters.

## Throughput and bandwidth

| Link | Typical real-world throughput |
| --- | --- |
| 3G | 1–5 Mbit/s |
| 4G/LTE | 10–50 Mbit/s |
| 5G | 100–500 Mbit/s |
| Home Wi-Fi | 50–500 Mbit/s |
| Data-centre network | 10–100 Gbit/s |

**Bits vs bytes:** divide megabits by 8. 40 Mbit/s is 5 MB/s, so a 2 MB image takes about 0.4 s plus latency.

## Sizes

| Thing | Rough size |
| --- | --- |
| A UUID | 16 bytes binary, 36 as text |
| A typical JSON API object (post, message) | 0.5–2 KB |
| The same as protobuf | 30–60% of the JSON |
| gzip or Brotli on JSON | 70–90% smaller |
| A chat message stored server-side, with metadata | about 0.5 KB |
| A thumbnail (JPEG/HEIC, 200 px) | 10–30 KB |
| A phone photo (HEIC, 12 MP) | 1.5–3 MB |
| The same photo decoded in memory | width × height × 4 bytes: 12 MP ≈ 48 MB |
| 1 minute of 1080p video (H.264, streaming) | 40–60 MB (about 5–8 Mbit/s) |
| 1 minute of 720p video | 15–25 MB |
| 1 minute of AAC audio at 128 kbit/s | about 1 MB |
| An APNs payload limit | 4 KB (5 KB for VoIP) |

## Mobile device budgets

| Budget | Rule of thumb |
| --- | --- |
| App memory before jetsam risk | depends on device; aim for well under 1 GB on recent iPhones, much less on older ones |
| Image memory | decode at display size, not file size: a 300×300 pt cell at 3× is 900 × 900 × 4 ≈ 3.2 MB |
| In-memory image cache | 50–200 MB, cost-limited, purged on memory warnings |
| Disk cache | 100 MB–1 GB, evicted by size and age; in Caches, which the system can purge |
| Background task after leaving the app | about 30 s with `beginBackgroundTask` |
| `BGAppRefreshTask` | about 30 s, scheduled by the system |
| Pending local notifications | 64 per app |
| Monitored geofence regions | 20 per app |
| Widget timeline reloads | a daily budget, roughly 40–70 for a frequently viewed widget |

## Scale conversions

| From | To | Rule |
| --- | --- | --- |
| DAU | average QPS | DAU × requests per user per day ÷ 86,400 |
| Average QPS | peak QPS | × 2–3 for a normal daily peak; × 10 or more for events and launches |
| Writes per day | storage per year | writes × size × 365, then × replication factor (often 3) |
| QPS | bandwidth | QPS × response size; mostly media, so estimate media separately |
| Reads : writes | cache value | read-heavy (100:1) benefits most from caching |

**A quick example:** 10M DAU, 20 feed requests each per day: 2 × 10⁸ ÷ 10⁵ ≈ 2,000 QPS average, about 6,000 at peak. At 50 KB per response that's 300 MB/s at peak, before images.

## Availability

| Availability | Downtime per year | Per month |
| --- | --- | --- |
| 99% | 3.65 days | 7.3 hours |
| 99.9% | 8.8 hours | 44 minutes |
| 99.95% | 4.4 hours | 22 minutes |
| 99.99% | 53 minutes | 4.4 minutes |
| 99.999% | 5.3 minutes | 26 seconds |

Services that depend on each other in series multiply: three services at 99.9% give about 99.7%.
