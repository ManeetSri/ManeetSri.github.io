Budgets to design against, and which tool answers which question. The lessons are in [Performance architecture](/design/learn/sd-perf-budgets), with measuring in [Instruments and MetricKit](/design/learn/sd-perf-instruments).

## Budgets

| Area | Good | Investigate | Notes |
| --- | --- | --- | --- |
| Cold launch to first frame | under 400 ms | over 1 s | Measure on the oldest supported device. The watchdog kills launches that take about 20 s |
| Warm launch / resume | under 200 ms | over 500 ms | |
| Main-thread work per frame | under 8 ms (120 Hz) or 16 ms (60 Hz) | any frame over 50 ms | Anything over 250 ms is a hang |
| Hitch time ratio while scrolling | under 5 ms/s | over 10 ms/s | Xcode Organizer and `XCTOSSignpostMetric.scrollDecelerationMetric` |
| Tap to visible response | under 100 ms | over 250 ms | |
| Screen load with data | under 1 s | over 2 s | Show cached content first |
| Memory footprint | as low as possible; stable over time | steady growth, spikes on navigation | Jetsam limits vary by device |
| Energy | idle CPU near 0%; network batched | wakeups when idle, continuous location | Xcode energy gauge, MetricKit |
| App download size | under 50 MB | over 200 MB (cellular download prompts) | App Store Connect size report |

## Which tool answers which question

| Question | Tool |
| --- | --- |
| Why is launch slow? | Instruments App Launch template; `os_signpost` around launch phases |
| Why does scrolling hitch? | Instruments Animation Hitches; Core Animation commits; Time Profiler on the main thread |
| Why did the app hang? | Instruments Hangs; Xcode Organizer hang reports; MetricKit `MXHangDiagnostic` |
| What's using the CPU? | Time Profiler |
| What's using memory? Why is it growing? | Allocations (generations), Leaks, the Memory Graph Debugger |
| Why are images so big in memory? | Allocations filtered to image buffers; check decode size vs display size |
| Why is the battery draining? | Energy Log, Network and Location templates; MetricKit `MXCPUMetric` and `MXNetworkTransferMetric` |
| How are users' devices doing? | MetricKit payloads; Xcode Organizer (launch, hangs, memory, disk writes, energy) |
| Did this change make it slower? | XCTest `measure(metrics:)` with `XCTApplicationLaunchMetric`, `XCTClockMetric`, `XCTMemoryMetric`; a CI gate |
| What's happening across threads and actors? | Swift Concurrency template (tasks, actors); `os_signpost` intervals |
| How heavy is a SwiftUI view? | Instruments SwiftUI template (view body updates, cause and effect) |

## Launch: what to move out of the way

| Before first frame | Move it |
| --- | --- |
| Many dynamic frameworks | Merge them or link statically: each dynamic library costs load and bind time |
| `+load` methods, static initialisers | Lazy initialisation on first use |
| SDK initialisation (analytics, ads, crash reporting) | Only crash reporting early; the rest after the first frame |
| Reading large files, decoding JSON, migrations | Background, with a placeholder screen |
| Network requests awaited at launch | Show cached content; refresh after |

## Rendering: common causes of hitches

| Cause | Fix |
| --- | --- |
| Decoding full-size images on the main thread | Downsample off the main thread to display size (`CGImageSourceCreateThumbnailAtIndex` or `UIImage.preparingThumbnail(of:)`) |
| Offscreen passes: shadows without a path, masks, `cornerRadius` + `masksToBounds` on many layers | Set `shadowPath`; pre-render; fewer masks |
| Expensive Auto Layout in cells | Simpler constraints; cache sizes; avoid changing constraints on every scroll |
| Heavy SwiftUI bodies or broad invalidation | Smaller views; `@Observable` for finer dependency tracking; stable identity in `ForEach` |
| Synchronous work in `cellForItemAt` | Prepare view models ahead; prefetch with `UICollectionViewDataSourcePrefetching` |
| Large blending areas | Opaque views where possible |

## Memory

| Rule | Why |
| --- | --- |
| Image memory = pixels × 4 bytes | A 4032 × 3024 photo is about 48 MB decoded, whatever the file size |
| `NSCache` with a cost limit for decoded images | It evicts under pressure; a dictionary never does |
| Respond to memory warnings | Drop caches and rebuildable state |
| Break retain cycles | `[weak self]` in long-lived closures; weak delegates; cancel tasks |
| Avoid loading whole datasets | Page from the database; stream large files |

## Energy

| Drain | Better |
| --- | --- |
| Many small network requests | Batch; let the radio sleep between bursts |
| Polling | Push, or background refresh the system schedules |
| Continuous precise location | Significant-change, regions, or lower accuracy |
| Timers in the background | `BGTaskScheduler` |
| Animation when nothing changes | Stop it when off screen; respect Low Power Mode (`ProcessInfo.isLowPowerModeEnabled`) |
| Ignoring thermal state | Reduce work when `thermalState` is `.serious` or `.critical` |

## App size

| Lever | Effect |
| --- | --- |
| Asset catalogs | App thinning delivers only the right scale and device assets |
| On-demand resources and Background Assets | Download large content after install |
| Removing unused code and assets | Periphery-style dead-code checks; asset audits |
| Static linking with dead stripping | Smaller binaries than many dynamic frameworks |
| Compressed or streamed media | Don't ship what can be downloaded |
