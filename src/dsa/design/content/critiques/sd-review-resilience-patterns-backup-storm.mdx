<Brief>

A photo app backs up the camera roll overnight. Since the backup service shipped, the upload API falls over at about two every morning, the on-call engineer sees ten times the expected traffic, and some users find photos stored twice. Review the service as you would a pull request.

```swift check ios title="PhotoBackupService.swift"
import UIKit

struct PendingPhoto: Sendable {
    let id: UUID
    let fileURL: URL
}

@MainActor
final class PhotoBackupService {
    private let session = URLSession.shared
    private let endpoint = URL(string: "https://api.example.com/v1/photos")!
    private(set) var uploadedCount = 0

    // The server sends this silent push to every device at 02:00 UTC
    func didReceiveBackupPush(pending: [PendingPhoto]) {
        Task {
            await backUp(pending)
        }
    }

    func backUp(_ photos: [PendingPhoto]) async {
        await withTaskGroup(of: Void.self) { group in
            for photo in photos {
                group.addTask {
                    await self.upload(photo)
                }
            }
        }
    }

    private func upload(_ photo: PendingPhoto) async {
        guard let data = try? Data(contentsOf: photo.fileURL) else { return }
        var request = URLRequest(url: endpoint)
        request.httpMethod = "POST"
        request.setValue("image/heic", forHTTPHeaderField: "Content-Type")

        for attempt in 1...10 {
            do {
                let (_, response) = try await session.upload(for: request, from: data)
                if (response as? HTTPURLResponse)?.statusCode == 201 {
                    uploadedCount += 1
                    return
                }
            } catch {
                print("Upload \(attempt) failed: \(error)")
            }
        }
    }
}
```

<ReferenceReview>

**What matters most.** The outage and the duplicates come from three problems that multiply each other. Every device starts at 02:00 because the push arrives at 02:00. Each device then starts **every upload at once**. And each failed upload **retries ten times with no delay**. One bad minute on the server turns into a retry storm from the whole fleet. Separately, retrying a **non-idempotent POST** is why some photos are stored twice.

**How I'd fix it, in small steps:**

1. Stop the bleeding without an app release: have the server stagger the pushes across a two-hour window, and answer overload with `503` and `Retry-After`.
2. Make uploads safe to retry: send `Idempotency-Key: <photo id>` and have the server deduplicate on it. Ship this before touching retries, so every later change is safe.
3. Replace the retry loop with a policy: classify errors, back off exponentially with full jitter (base 1 s, cap 60 s, four attempts), honour `Retry-After`, and stop on cancellation.
4. Bound concurrency to three uploads with a sliding-window task group, and upload from files rather than `Data`, off the main actor.
5. Move the work to a background `URLSession` (or a `BGProcessingTask` that requires power and Wi-Fi), driven by a persistent queue that records each photo's state, so a failure is retried tomorrow rather than forgotten.

**Tests to add:** with a stub HTTP client and a test clock, a 500 response leads to exactly four attempts at the expected delays; a `400` leads to one; `Retry-After: 30` delays the next attempt by 30 seconds; every attempt for one photo carries the same idempotency key; and with 50 pending photos, no more than three uploads are ever in flight.
