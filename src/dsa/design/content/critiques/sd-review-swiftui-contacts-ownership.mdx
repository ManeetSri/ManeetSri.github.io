<Brief>

A company directory app for iPad and iPhone: a split view with contacts on the left and the selected contact on the right, including a live presence status. QA's bug list: the list sometimes empties itself and reloads; on iPad, picking a second contact still shows the first; renaming a contact "doesn't stick"; and after a long session, the app is making presence requests every few seconds. Review it as you would a pull request: for every piece of state, ask who owns it and how long it lives.

```swift check ios title="ContactsScreen.swift"
import SwiftUI

struct Contact: Identifiable, Hashable {
    let id: UUID
    var name: String
}

struct ContactsAPI: Sendable {
    var contacts: @Sendable () async throws -> [Contact]
    var presence: @Sendable (Contact.ID) async throws -> String
    static let live = ContactsAPI(contacts: { [] }, presence: { _ in "Online" })
}

@MainActor
final class ContactsStore: ObservableObject {
    @Published var contacts: [Contact] = []
    let api = ContactsAPI.live

    func load() async {
        contacts = (try? await api.contacts()) ?? []
    }
}

@MainActor
final class ContactDetailModel: ObservableObject {
    @Published var contact: Contact
    @Published var presence = "…"

    init(contact: Contact, api: ContactsAPI) {
        self.contact = contact
        Task {
            while !Task.isCancelled {
                presence = (try? await api.presence(contact.id)) ?? "Unknown"
                try? await Task.sleep(for: .seconds(30))
            }
        }
    }
}

struct ContactsScreen: View {
    @ObservedObject var store = ContactsStore()
    @State private var selection: Contact?

    var body: some View {
        NavigationSplitView {
            List(store.contacts, selection: $selection) { contact in
                Text(contact.name).tag(contact)
            }
            .onAppear { Task { await store.load() } }
        } detail: {
            if let selection {
                ContactDetail(contact: selection, api: store.api)
            }
        }
    }
}

struct ContactDetail: View {
    @StateObject private var model: ContactDetailModel
    init(contact: Contact, api: ContactsAPI) {
        _model = StateObject(wrappedValue: ContactDetailModel(contact: contact, api: api))
    }

    var body: some View {
        Form {
            TextField("Name", text: $model.contact.name)
            LabeledContent("Status", value: model.presence)
        }
    }
}
```

<ReferenceReview>

**Most important first.** Three ownership and lifetime problems cause every bug on QA's list. The screen **doesn't own the store it creates** (`@ObservedObject` with a default value), so any parent update throws away the loaded contacts. The detail pane **keeps its first model**, because a new selection doesn't give it a new identity. And each detail model **starts a polling loop nobody can cancel**, which is why the app ends up making presence requests every few seconds.

**The pattern underneath:** state and work are attached to the wrong lifetimes. The contacts must outlive any one rebuild of the screen; presence polling must live exactly as long as a pane shows one contact; edits must end up in the one place that owns contacts.

**How I'd fix it, in small steps:**

1. Create `ContactsStore` at the app root with its API injected, and pass it in. Until that lands, `@StateObject private var store = ContactsStore()` stops the data loss on its own.
2. Replace `.onAppear { Task { … } }` with `.task { await store.load() }`, add `.refreshable`, and make `load()` keep the existing contacts and set an error state when it fails.
3. Select by `Contact.ID?`, and look the contact up in the store for the detail pane.
4. Give the pane `.id(contactID)`, so each contact gets a fresh detail model, and move polling into `func pollPresence() async` on the model, started from `.task(id: contactID)` and using `try await Task.sleep` so cancellation ends it.
5. Turn the detail into a draft with an explicit Save that calls `store.rename(_:to:)`, so the store stays the single source of truth.
6. While there, migrate both models to `@Observable` with `@State`; the ownership rules are the same and invalidation gets finer.

**Tests to add:** the store's load success, failure (contacts kept, error set) and rename, with a fake `ContactsAPI`; the detail model's polling ending when its task is cancelled; and a UI test that selects two contacts in turn on iPad and checks the second one's name is shown.

</ReferenceReview>
