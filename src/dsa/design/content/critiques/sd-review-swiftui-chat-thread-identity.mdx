<Brief>

The conversation screen of a messaging app. In testing it's fine, but real users have threads with thousands of messages, and they report that opening a long thread is slow, the thread jumps back to the top whenever a message arrives, "scroll to latest" does nothing, and the phone gets warm while a conversation is open. Review it as you would a pull request, with identity and update cost in mind.

```swift check ios title="ChatThreadView.swift"
import Combine
import SwiftUI

struct Message: Hashable {
    var serverID: String?
    var text: String
    var sentAt: Date
    var isPending: Bool
}

struct MessageRow: Identifiable {
    let id = UUID()
    let message: Message
}

struct ChatThreadView: View {
    let messages: [Message]
    @State private var now = Date()
    private let ticker = Timer.publish(every: 1, on: .main, in: .common).autoconnect()

    private var rows: [MessageRow] {
        messages.sorted { $0.sentAt < $1.sentAt }.map { MessageRow(message: $0) }
    }

    var body: some View {
        ScrollViewReader { proxy in
            ScrollView {
                VStack(alignment: .leading, spacing: 8) {
                    ForEach(rows) { row in
                        bubble(for: row.message)
                    }
                }
                .padding()
            }
            .id(messages.count)
            .onChange(of: messages.count) {
                proxy.scrollTo(rows.last?.id, anchor: .bottom)
            }
        }
        .onReceive(ticker) { now = $0 }
    }

    @ViewBuilder
    private func bubble(for message: Message) -> some View {
        VStack(alignment: .leading) {
            if message.isPending {
                Text(message.text)
                    .padding(10)
                    .background(.gray.opacity(0.3), in: .rect(cornerRadius: 12))
            } else {
                Text(message.text)
                    .padding(10)
                    .background(.blue.opacity(0.3), in: .rect(cornerRadius: 12))
            }
            Text(RelativeDateTimeFormatter().localizedString(for: message.sentAt, relativeTo: now))
                .font(.caption2)
                .foregroundStyle(.secondary)
        }
    }
}
```

<ReferenceReview>

**Most important first.** Two identity bugs make the screen misbehave, and one dependency makes it expensive. **Row ids are invented while building rows**, so SwiftUI never sees the same bubble twice; **`.id(messages.count)`** throws the scroll view away on every message, which is the jump to the top; and **the ticker** re-runs the entire thread every second, multiplying the cost of everything else (sorting, new ids for every row, a formatter per bubble). "Scroll to latest" fails because of the first bug: the id it scrolls to was made a moment ago and belongs to nothing.

**How I'd fix it, in small steps:**

1. Make `Message` `Identifiable` with a stable id: the server id for synced messages and a client id, created when the user composes a message and echoed by the server, for sent ones. Delete `MessageRow` and iterate messages directly.
2. Remove `.id(messages.count)` and the `ScrollViewReader`; add `.defaultScrollAnchor(.bottom)`, or `scrollPosition(id:)` if the screen needs to scroll on command.
3. Delete the ticker and `now`. Show times with `Text(message.sentAt, style: .relative)`, which keeps itself current.
4. Switch `VStack` to `LazyVStack`.
5. Move sorting into the model: keep the thread sorted on insert, and hand the view a ready array.
6. Turn the pending and sent branches into one bubble view with the look chosen by modifiers.

**Tests to add:** a unit test that the row identity of a message doesn't change when it goes from pending to sent (the stable row ids kata is exactly this), a model test that new messages land in sorted order, and a performance check: open a 5,000-message fixture in a UI test, record with the SwiftUI instrument and confirm that a new message runs only the new row's body, and an idle thread runs no bodies at all.

</ReferenceReview>
