<Brief>

The profile screen of a subscription app. Signed-in people edit their name and email; guests (who haven't created an account yet) get the same screen through a subclass. Support tickets say guests' changes "don't stick", the badge sometimes shows **Free** for paying customers, and nobody has written a test for it because it needs the real account service. Review it as you would a pull request, naming the design principle behind each problem.

```swift check ios title="ProfileViewController.swift"
import UIKit

struct Profile: Codable, Sendable {
    var name, email, plan: String
}

protocol AccountService: Sendable {
    func fetchProfile() async throws -> Profile
    func updateProfile(_ profile: Profile) async throws
    func changePassword(from old: String, to new: String) async throws
    func exportData() async throws -> URL
    func deleteAccount() async throws
}

class ProfileViewController: UIViewController {
    let account: AccountService
    let nameField = UITextField()
    let emailField = UITextField()
    let planBadge = UILabel()
    let statusLabel = UILabel()
    var profile: Profile?

    init(account: AccountService) {
        self.account = account
        super.init(nibName: nil, bundle: nil)
    }
    required init?(coder: NSCoder) { fatalError("init(coder:) has not been implemented") }

    override func viewDidLoad() {
        super.viewDidLoad()
        navigationItem.rightBarButtonItem = UIBarButtonItem(systemItem: .save, primaryAction: UIAction { [weak self] _ in self?.saveTapped() })
        Task {
            profile = (try? await account.fetchProfile())
                ?? UserDefaults.standard.data(forKey: "profile").flatMap { try? JSONDecoder().decode(Profile.self, from: $0) }
            render()
        }
    }

    func render() {
        guard let profile else { return }
        nameField.text = profile.name
        emailField.text = profile.email
        switch profile.plan {
        case "premium": planBadge.text = "Premium"; planBadge.textColor = .systemOrange
        case "family": planBadge.text = "Family"; planBadge.textColor = .systemPurple
        default: planBadge.text = "Free"; planBadge.textColor = .secondaryLabel
        }
    }

    func saveTapped() {
        guard var profile else { return }
        let email = (emailField.text ?? "").trimmingCharacters(in: .whitespaces).lowercased()
        guard email.split(separator: "@").count == 2 else { statusLabel.text = "Enter a valid email address"; return }
        profile.name = nameField.text ?? ""
        profile.email = email
        Task {
            try await save(profile)
            statusLabel.text = "Saved"
        }
    }

    func save(_ profile: Profile) async throws {
        try await account.updateProfile(profile)
        UserDefaults.standard.set(try JSONEncoder().encode(profile), forKey: "profile")
    }
}

final class GuestProfileViewController: ProfileViewController {
    override func save(_ profile: Profile) async throws {} // guests have no server account to save to
}
```

<ReferenceReview>

**Most important first.** Two problems lose people's data today. The guest subclass's empty `save` makes the screen claim success while discarding the edit, and the signed-in path drops save errors on the floor because the throwing `Task` is never awaited. Both are invisible to the person and to us. Fix those before any restructuring, and add a test for each.

**The design problem underneath** is that the view controller is the only place where anything happens, so the guest variation had nowhere to go except a subclass override. Inheritance was used to vary *behaviour that the base class's callers rely on*, which is exactly where Liskov substitution bites.

**How I'd fix it, in small steps:**

1. Characterise today's behaviour: a test that renders the badge for each plan string, and one that drives `saveTapped` with a stub service (it'll need a fake for all five methods, which is finding five in action).
2. Introduce a `@MainActor @Observable final class ProfileModel` holding the state (`loading`, `loaded(Profile, isCached:)`, `failed`), the validation and the save. The view controller binds to it and keeps only layout.
3. Give the model two role protocols it owns, `ProfileLoading` and `ProfileSaving`, and a `ProfileRepository` that implements both on top of `AccountService` plus a file cache. The screen no longer sees `AccountService` or UserDefaults.
4. Replace the guest subclass with configuration: guests get a `LocalProfileSaver` (on-device only) and a banner explaining that changes sync once they sign up. One screen class, no override.
5. Decode `plan` into a `Plan` enum with `unknown`, and move the badge mapping into one exhaustive `switch`.
6. Move the email rule into the shared validator and handle the save error with a message and a retry.

**Tests to add:** the model's states for success, cached fallback and failure, using fakes of only the two role protocols; the guest configuration never calls the server and says so; every `Plan` case, including `unknown`, maps to a badge; and a save failure shows an error rather than "Saved".

</ReferenceReview>
