<Brief>

This is the launch path of a news app. Organizer shows its median cold launch at 2.4 seconds and rising, the crash list has a cluster of `0x8badf00d` terminations from users on poor connections, background refresh has never once run in production, and a handful of users write in to say the app "signed me out overnight". Review the app delegate and scene delegate: what blocks the first frame, what's broken outright, and how you'd restructure launch.

```swift check ios title="AppDelegate.swift and SceneDelegate.swift"
import BackgroundTasks
import UIKit

final class AppDelegate: UIResponder, UIApplicationDelegate {
    private(set) var config: [String: String] = [:]

    func application(_ application: UIApplication, didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
        let configURL = URL(string: "https://config.example.com/ios/v3.json")!
        if let data = try? Data(contentsOf: configURL),
           let decoded = try? JSONDecoder().decode([String: String].self, from: data) {
            config = decoded
        }
        Database.shared.migrateToLatestSchema()
        Analytics.start(apiKey: "an-key")
        Ads.start(appID: "ads-id")
        SupportChat.start(region: config["chatRegion"] ?? "eu")

        let profileURL = URL.applicationSupportDirectory.appending(path: "profile.json")
        if (try? Data(contentsOf: profileURL)) == nil {
            Session.shared.signOut() // no profile on disk: treat as signed out
        }

        DispatchQueue.main.async {
            BGTaskScheduler.shared.register(forTaskWithIdentifier: "com.example.feed.refresh", using: nil) { task in
                task.setTaskCompleted(success: true)
            }
        }
        return true
    }
}

final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func scene(_ scene: UIScene, willConnectTo session: UISceneSession, options connectionOptions: UIScene.ConnectionOptions) {
        guard let windowScene = scene as? UIWindowScene else { return }

        let semaphore = DispatchSemaphore(value: 0)
        Session.shared.refreshToken { semaphore.signal() }
        semaphore.wait()

        let cacheURL = URL.cachesDirectory.appending(path: "feed.json")
        let cached = (try? Data(contentsOf: cacheURL)).flatMap { try? JSONDecoder().decode([FeedItem].self, from: $0) }

        let tabs = UITabBarController()
        tabs.viewControllers = [FeedViewController(items: cached ?? []), SearchViewController(), SettingsViewController()]
        let window = UIWindow(windowScene: windowScene)
        window.rootViewController = tabs
        window.makeKeyAndVisible()
        self.window = window
    }
}

final class Session: Sendable {
    static let shared = Session()

}
final class FeedViewController: UIViewController {
    init(items: [FeedItem]) { super.init(nibName: nil, bundle: nil) }
    required init?(coder: NSCoder) { nil }
}

final class SettingsViewController: UIViewController {}
```

<ReferenceReview>

**Most important first.** Two problems are outright bugs rather than slowness. The BGTask handler is registered after launch finishes (lines 23–27), so background refresh can never run. And an unreadable profile is treated as a missing one (18–21), which signs users out whenever iOS launches the app in the background while the phone is locked. Then the two waits on the network, the synchronous config fetch (8–12) and the semaphore around the token refresh (38–40), which explain both the long tail of launch times and the watchdog kills on bad connections.

**The design problem underneath** is that launch has no tiers: everything the app might need is done, synchronously and in sequence, before anything is shown. Launch work should be sorted into what the first frame truly needs, what can wait a frame, what can wait for idle time, and what waits for first use.

**How I'd fix it, in small steps:**

1. Move `BGTaskScheduler.register` to run synchronously in `didFinishLaunchingWithOptions`. One line, and it unblocks background refresh.
2. Replace the profile check with a session read from the Keychain (after-first-unlock), and treat any read failure as "unavailable, try later", never as "signed out". Add a guard that destructive resets never run while `isProtectedDataAvailable` is false.
3. Remove both network waits: load config from the bundle and the last cached copy, then refresh it in a task after the first frame; build the UI with the stored token and let the API client's 401 handling refresh it once (single-flight).
4. Give the first screen placeholders and move cache loading into its view model, off the main actor.
5. Introduce a small launch plan: crash reporting before the first frame; analytics, ads and the config refresh right after it (from the first screen's `viewDidAppear(_:)`); the database migration off the main actor before first use; support chat on first use.
6. Add `OSSignposter` intervals around each launch step, and track the result with an `XCTApplicationLaunchMetric` test and MetricKit's `histogrammedTimeToFirstDraw`.

**Tests to add:** a launch performance test in CI with a fixed budget; a unit test of the session loader that simulates protected data being unavailable and expects no sign-out; and an integration test that `BGTaskScheduler` registration happens inside `didFinishLaunchingWithOptions` (for example by asserting the handler is registered before the method returns, using an injected scheduler).
