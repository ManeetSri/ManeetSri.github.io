<Brief>

A year ago the team built one list screen for every list in the app, configured per screen. Orders and Favourites use it today, and a third screen, Saved addresses, is next. Meanwhile support reports blank rows, duplicated orders and a favourites screen that "uses data like crazy" when it's empty. Review it as you would a pull request that adds the third screen.

```swift check ios title="GenericListViewController.swift"
import UIKit

struct Order { let number: String; let total: Double }
struct Product { let name: String; let price: Double }

protocol ListDataProvider { func fetch(page: Int, completion: @escaping ([Any]) -> Void) }
protocol ListPlugin { func listWillAppear(_ list: GenericListViewController) }

enum ListKind { case orders, favourites }

struct ListConfiguration {
    var kind: ListKind
    var title: String
    var providerKey: String
    var showsSearch = false
    var plugins: [any ListPlugin] = []
}

@MainActor
final class ProviderRegistry {
    static let shared = ProviderRegistry()
    private var providers: [String: any ListDataProvider] = [:]
    func register(_ provider: any ListDataProvider, for key: String) { providers[key] = provider }
    func provider(for key: String) -> any ListDataProvider { providers[key]! }
}

final class GenericListViewController: UITableViewController {
    let configuration: ListConfiguration
    private var rows: [Any] = []
    private var page = 0

    init(configuration: ListConfiguration) {
        self.configuration = configuration
        super.init(style: .plain)
        title = configuration.title
    }

    required init?(coder: NSCoder) { fatalError("init(coder:) has not been implemented") }

    var items: [Any] {
        if rows.isEmpty { loadNextPage() }
        return rows
    }

    func loadNextPage() {
        let provider = ProviderRegistry.shared.provider(for: configuration.providerKey)
        provider.fetch(page: page) { [weak self] newRows in
            self?.rows += newRows
            self?.page += 1
            self?.tableView.reloadData()
        }
    }

    override func tableView(_ tableView: UITableView, numberOfRowsInSection section: Int) -> Int {
        items.count
    }

    override func tableView(_ tableView: UITableView, cellForRowAt indexPath: IndexPath) -> UITableViewCell {
        let cell = UITableViewCell(style: .subtitle, reuseIdentifier: nil)
        if configuration.kind == .orders, let order = items[indexPath.row] as? Order {
            cell.textLabel?.text = "Order \(order.number)"
            cell.detailTextLabel?.text = String(format: "£%.2f", order.total)
        } else if configuration.kind == .favourites, let product = items[indexPath.row] as? Product {
            cell.textLabel?.text = product.name
            cell.detailTextLabel?.text = "£" + String(format: "%.2f", product.price)
        }
        if indexPath.row == rows.count - 1 { loadNextPage() }
        return cell
    }
}
```

<ReferenceReview>

**Most important first.** Two problems hurt users today. Reading `items` **fetches**, so an empty list requests page after page without end, and loads can **overlap**, so pages are appended twice. Both come from mixing a query with a command, and from a paging state that doesn't know a request is in flight. Close behind: the **registry** turns a typo into a crash.

**The design problem underneath** is a wrong abstraction. Orders and Favourites looked alike a year ago, so they were merged into a configurable screen. Since then each difference became a flag or an `if kind ==`, the rows lost their types to `[Any]`, and the real shared knowledge, how prices look, was never shared at all. Adding Saved addresses would add a third branch to every method.

**How I'd fix it, in small steps:**

1. Pin today's behaviour with snapshot tests of both screens with a few pages of stub data, so the refactor can't change what users see.
2. **Go back to duplication.** Copy the controller into `OrdersViewController` and `FavouritesViewController`. In each copy, delete the other screen's branch and replace `[Any]` with `[Order]` or `[Product]`. Each copy gets shorter and typed.
3. **Inject the loader** through `init`, typed per screen: `let loadPage: (Int) async throws -> [Order]`, built at the composition root. Delete `ProviderRegistry`; the crash goes with it.
4. **Make loading a command.** Load the first page from `viewDidLoad` and later pages from `tableView(_:willDisplay:forRowAt:)` or prefetching, never from a data-source method. Data-source methods become pure queries over `rows`.
5. **Extract what's really shared**, now that two honest copies sit side by side: a small `Pager<Item>` that knows the next page, whether a load is in flight and whether the end was reached; and one money formatter used by both. Neither has a branch for any screen.
6. Delete `ListConfiguration`, `ListPlugin`, `showsSearch` and `plugins`. Saved addresses becomes a third small controller that uses `Pager` and its own cell.

**Tests to add:** `Pager` never runs two loads at once, appends pages in order, and stops after an empty page; each screen's first load happens once even when the table asks for its row count repeatedly; an empty response shows the empty state and makes no further requests; the money formatter for a few values and locales.

</ReferenceReview>
