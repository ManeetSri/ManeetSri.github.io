<Brief>

Jot is a notes app for iPhone, iPad and Mac, with about a million users. A colleague has shared the design doc for the team's biggest project this year, offline editing, and asked for your review before it goes to the backend team. Review it as you'd review a pull request: what's wrong with the design and with how it's communicated, what matters most, and what you'd ask for before approving.

```markdown title="sync-v2-design.md"
# Sync v2 (new)

## Background

Jot users keep asking for offline editing. Today the editor only works
online: each batch of keystrokes is sent to the server, and notes are
read-only without a connection. Lots of users are affected and our
App Store reviews mention it every week.

## Proposal

We will make Jot offline-first. Edits are saved to Core Data first and
sent to the new Sync API in the background by the delta pipe. The Sync
API stores them in Hydra and sends a silent push through APNs to the
user's other devices, which then pull the changes.

Sync should be fast and reliable, and it has to scale to lots of users.

    flowchart LR
        NoteEditorViewController <--> CoreData
        CoreData --> App
        App <--> Backend
        App --> NotesDB[(Notes DB)]
        Backend --- AWS

Figure 1: architecture

## Conflicts

If two devices edit the same note while offline, the server merges the
changes intelligently. We'll use an LWW-ish approach for most fields,
based on the `updatedAt` timestamp each device sets. Details TBD with
the backend team.

## Data model

Each note gets a `version` integer and an `updatedAt` timestamp. The
delta pipe sends only the changed fields. When a note is deleted, it is
removed from Core Data straight away so it disappears from the list.

## Monitoring

To debug sync problems, every failed delta is sent to our analytics
vendor (Insights) as an event, with the note body as a property, so we
can replay it.

## Rollout

Sync v2 ships to everyone in 3.9. If anything goes wrong we will roll
back to 3.8 and fix forward.

## Timeline

- Weeks 1–2: delta pipe
- Week 3: Hydra integration
- Week 4: ship
```

<ReferenceReview>

**Most important first.** The doc isn't yet something a reviewer can approve, because it doesn't say what's being built. The figure and the text describe two different architectures, and the part that makes offline sync hard, what happens when two devices edit the same note, is "TBD". Two other problems would cause real harm if shipped as written: **note bodies sent to an analytics vendor**, and a rollout that depends on a **rollback iOS can't do**.

**How I'd fix it, in small steps:**

1. Add a header (author, status, reviewers, date) and a short glossary, and rename it after what it does: *Offline editing and sync*.
2. Write goals with numbers ("an offline edit reaches the user's other devices within 30 seconds of reconnecting") and non-goals (real-time co-editing, shared notes).
3. Replace Figure 1 with a labelled container view (the apps, their local store, the Sync API, Hydra, APNs) that matches the text, and add a sequence diagram of *edit offline, reconnect, push, pull*, including the conflict branch.
4. Decide the conflict rule with the backend team before anything is built: server-assigned versions with compare-and-set, and a visible conflict copy when both sides changed the body. Add tombstones for deletes.
5. Add an alternatives section: CloudKit with CKSyncEngine, a CRDT model, an operation log, and why the chosen design wins for Jot.
6. Change monitoring to IDs, versions and error codes, and get a privacy review of anything that leaves the device.
7. Rewrite the rollout: offline sync behind a server-side switch, a phased release, how 3.8 and older clients keep working against the new server, and when the old path is retired.

**Tests and safety nets to ask for:** a prototype of the conflict rule with tests of the awkward cases (both devices edit offline, one deletes while the other edits, a device clock set wrong); a compatibility test of a 3.8 build against the new server; a check in TestFlight that the server-side switch really turns sync off; and an automated check that no analytics event carries note content.

</ReferenceReview>
