<Brief>

A food delivery app replaced its singletons with a home-grown `Services` locator two years ago, "so everything is testable". The order history tab below is typical of its 120 screens. Support reports that after someone signs out and a partner signs in on the same phone, the tab can show the first person's orders. The order-status widget crashes on launch, nobody can open this screen's preview, and the tests pass alone but fail together. Review it as you would a pull request: what's wrong, what matters most, and how you'd fix it.

```swift check ios title="OrderHistory.swift"
import SwiftUI

protocol OrdersAPI: Sendable {
    func orders(for userID: String) async throws -> [Order]
    func reorder(_ orderID: String) async throws
}

protocol Analytics: Sendable { func track(_ event: String) }

struct Session: Sendable { let userID: String }

/// Filled at launch, and again whenever someone signs in; resolved wherever a service is needed
@MainActor final class Services {
    static let shared = Services()
    private var factories: [String: () -> Any] = [:]

    func register<T>(_ type: T.Type, factory: @escaping () -> T) {
        factories[String(describing: type)] = factory
    }

    func resolve<T>(_ type: T.Type = T.self) -> T {
        factories[String(describing: type)]!() as! T
    }

    func registerLive(session: Session, api: any OrdersAPI, analytics: any Analytics) {
        register(Session.self) { session }
        register((any OrdersAPI).self) { api }
        register((any Analytics).self) { analytics }
    }
}

struct Order: Identifiable, Decodable, Sendable {
    let id: String
    let totalPence: Int

    @MainActor func reorder() async throws {
        let api: any OrdersAPI = Services.shared.resolve()
        try await api.reorder(id)
        Services.shared.resolve((any Analytics).self).track("reorder:\(id)")
    }
}

@MainActor @Observable final class OrderHistoryModel {
    private(set) var orders: [Order] = []
    private let api: any OrdersAPI = Services.shared.resolve()
    private let session: Session = Services.shared.resolve()
    @ObservationIgnored private lazy var analytics: any Analytics = Services.shared.resolve()

    func load() async {
        orders = (try? await api.orders(for: session.userID)) ?? []
        analytics.track("order_history_viewed")
    }
}

struct OrderHistoryView: View {
    @State private var model = OrderHistoryModel()

    var body: some View {
        List(model.orders) { order in
            Button("Order \(order.id)") {
                Task { try? await order.reorder() }
            }
        }
        .task { await model.load() }
    }
}

}
```

<ReferenceReview>

**Most important first.** The stale-session bug is a privacy problem, not a style issue: the screen can show one person's order history to another. It comes from mixing lifetimes in a global registry. The tab's model is created once and resolves the session at that moment, while the registry is quietly re-filled at every sign-in. The crashes come from the same design: nothing in any signature says what must be registered, so every entry point that forgets crashes at run time.

**The underlying problem** is that the locator is a service locator, not dependency injection. Objects *pull* their dependencies from a global whenever they like, so dependencies are invisible, lifetimes are accidental and tests share state. Moving the same calls into a container wouldn't fix it; moving the *pulling* into one place would.

**How I'd fix it, in small steps:**

1. **Make the model honest.** Give `OrderHistoryModel` an initialiser that takes `api`, `session` (or only the user ID) and `analytics`. Keep a temporary convenience `init()` that resolves from `Services` and calls it, so the 120 screens still compile; new code and tests use the real initialiser.
2. **Strip services out of `Order`.** Move `reorder` into the view model (or a small `ReorderUseCase`) with the injected API and analytics. `Order` goes back to being plain data that a widget can decode and show.
3. **Give the session a real scope.** Build a `SignedInDependencies` value at sign-in that holds the session, the API client for that user and the analytics, and root the signed-in UI in it: `.id(session.userID)` on the signed-in root, or a fresh scene of views, so every model is rebuilt when the user changes. Sign-out drops the whole value.
4. **Wire at the composition root.** The `App` builds the app-wide services; the sign-in flow builds the session scope; screens receive what they need through initialisers or the SwiftUI environment. The preview and the widget get their own small roots with fakes or read-only services.
5. **Shrink the locator to the edges, then delete it.** While it exists, make `resolve` throw (or return an optional) instead of crashing, key it by `ObjectIdentifier`, and allow it only in files at framework-created entry points. Add a lint rule against `Services.shared` elsewhere and burn the count down screen by screen.

**Tests to add:** the view model with a fake API for loaded, empty and failed states; a sign-out then sign-in test asserting that the new session's model loads only the new user's orders; and a smoke test that builds the live composition root and the widget's root without crashing.
