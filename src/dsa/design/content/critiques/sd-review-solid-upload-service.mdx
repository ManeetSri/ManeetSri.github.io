<Brief>

A chat and social app uploads three kinds of image through one shared service: avatars, chat photos and expense receipts. A Wi-Fi-only variant was added for people on capped data plans. The bug tracker has "avatar shows a blank image", "the pending badge stops updating", "scrolling stutters while a photo sends" and "retries take ages on a bad connection". Review the service as you would a pull request, and connect each bug to the design problem behind it.

```swift check ios title="UploadService.swift"
import UIKit

enum UploadKind: String {
    case avatar, chatPhoto, receipt
}

protocol UploadObserver: AnyObject {
    func uploadDidStart(_ id: UUID)
    func uploadDidProgress(_ id: UUID, fraction: Double)
    func uploadDidFinish(_ id: UUID, url: URL)
    func uploadDidFail(_ id: UUID, error: any Error)
    func pendingCountDidChange(_ count: Int)
}

struct UploadResponse: Decodable { let url: URL }

@MainActor
class UploadService {
    static let shared = UploadService()
    weak var observer: UploadObserver?
    private var pending: Set<UUID> = []

    func upload(_ image: UIImage, kind: UploadKind) async throws -> URL {
        let id = UUID()
        observer?.uploadDidStart(id)
        let quality: CGFloat
        switch kind {
        case .avatar: quality = 0.6
        case .chatPhoto: quality = 0.8
        case .receipt: quality = 1.0
        }
        guard let data = image.jpegData(compressionQuality: quality) else { throw URLError(.cannotDecodeRawData) }
        if kind == .avatar && data.count > 2_000_000 { throw URLError(.dataLengthExceedsMaximum) }

        var request = URLRequest(url: URL(string: "https://api.example.com/uploads/\(kind.rawValue)")!)
        request.httpMethod = "POST"
        request.setValue("Bearer \(UserDefaults.standard.string(forKey: "token") ?? "")", forHTTPHeaderField: "Authorization")
        pending.insert(id)
        observer?.pendingCountDidChange(pending.count)
        defer {
            pending.remove(id)
            observer?.pendingCountDidChange(pending.count)
        }
        for attempt in 1...3 {
            do {
                let (body, _) = try await URLSession.shared.upload(for: request, from: data)
                let url = try JSONDecoder().decode(UploadResponse.self, from: body).url
                observer?.uploadDidFinish(id, url: url)
                NotificationCenter.default.post(name: .init("UploadFinished"), object: nil, userInfo: ["kind": kind.rawValue])
                return url
            } catch where attempt < 3 {
                try await Task.sleep(for: .seconds(attempt))
            }
        }
        throw URLError(.cannotConnectToHost)
    }
}

final class WiFiOnlyUploadService: UploadService {
    var isOnCellular = false

    override func upload(_ image: UIImage, kind: UploadKind) async throws -> URL {
        if isOnCellular { return URL(string: "about:blank")! } // the queue retries it later on Wi-Fi
        return try await super.upload(image, kind: kind)
    }
}
```

- id: wifi-subclass
  title: The Wi-Fi-only subclass reports success without uploading
  severity: high

  detail: "Callers of `upload` rely on its postcondition: the URL points at the uploaded image. <ReferenceReview>

**Most important first.** The Wi-Fi-only subclass loses data and corrupts state: it returns a fake URL that callers store as if it were real. Ship a hotfix that makes the cellular path throw a clear "waiting for Wi-Fi" error before anything else, so at least nothing saves `about:blank`. Then fix the main-thread encoding, which every user feels.

**The design problem underneath** is a service that is both too big and too concrete. Because everything lives in one `@MainActor` method that talks to globals, the only way to vary behaviour was to subclass and override it, and the override broke the method's promise. Because the observer protocol is one fat role with a single slot, every new screen that cares about uploads fights over it.

**How I'd fix it, in small steps:**

1. Make the outcome explicit: `func upload(_:kind:) async throws -> UploadOutcome` with `.uploaded(URL)` and `.deferred(UploadID)`. Update the callers (they must now handle deferral) and delete `WiFiOnlyUploadService`; a `NetworkPolicy` value decides whether to defer.
2. Extract an `UploadPolicy` per kind (quality, maximum size, path) from one exhaustive `switch`. The service reads the policy and never switches on the kind again.
3. Move JPEG encoding into a nonisolated `ImagePreparer`, so it runs off the main actor, and drop `@MainActor` from the service; only the published pending count is main-actor state.
4. Introduce protocols the upload code owns: `UploadTransport` (wrapping URLSession), `TokenProviding` (backed by the Keychain) and a `Clock` for retries. Inject them, and build the shared instance once at the composition root.
5. Replace `UploadObserver` with the returned outcome plus an observable `pendingCount`, so any number of screens can show it.
6. Put retries behind a retry policy that checks status codes and uses exponential backoff with jitter.

**Tests to add:** each `UploadPolicy` (size limits per kind); the service with a stub transport for success, a 413, a timeout then success, and deferral on cellular; the retry schedule with a test clock (no real waiting); and the pending count rising and falling with two observers following it at once.
