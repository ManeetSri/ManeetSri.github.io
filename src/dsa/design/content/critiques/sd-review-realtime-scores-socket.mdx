<Brief>

A football app's live match screen gets its scores from this WebSocket client. It worked in testing on office Wi-Fi. On the first big weekend, users reported scores frozen for whole halves, the app getting hot, and the backend team reported tens of thousands of open connections per thousand users and a reconnect storm after every deploy. Review it as you would a pull request.

```swift check ios title="LiveScoresClient.swift"
import UIKit

struct ScoreUpdate: Decodable {
    let matchID: String
    let home: Int
    let away: Int
    let minute: Int
}

@MainActor
final class LiveScoresClient {
    static let shared = LiveScoresClient()

    var onUpdate: (([ScoreUpdate]) -> Void)?
    private var task: URLSessionWebSocketTask?
    private var history: [ScoreUpdate] = []
    private var followed: Set<String> = []

    func connect(token: String) {
        let url = URL(string: "wss://live.example.com/scores?token=\(token)")!
        task = URLSession.shared.webSocketTask(with: url)
        task?.resume()
        listen(token: token)
    }

    func follow(_ matchID: String) {
        followed.insert(matchID)
        let message = #"{"type":"subscribe","matchID":"\#(matchID)"}"#
        task?.send(.string(message)) { _ in }
    }

    private func listen(token: String) {
        Task {
            do {
                guard let task else { return }
                let message = try await task.receive()
                if case .string(let text) = message {
                    let update = try JSONDecoder().decode(ScoreUpdate.self, from: Data(text.utf8))
                    history.append(update)
                    history.sort { $0.minute < $1.minute }
                    onUpdate?(history)
                }
                listen(token: token)
            } catch {
                connect(token: token)
            }
        }
    }

    func disconnect() {
        task?.cancel(with: .normalClosure, reason: nil)
    }
}

final class MatchViewController: UITableViewController {
    var matchID = ""
    var token = ""
    private var rows: [ScoreUpdate] = []

    override func viewDidLoad() {
        super.viewDidLoad()
        LiveScoresClient.shared.onUpdate = { [weak self] updates in
            self?.rows = updates
            self?.tableView.reloadData()
        }
        LiveScoresClient.shared.connect(token: token)
        LiveScoresClient.shared.follow(matchID)
    }
}
```

<ReferenceReview>

**Most important first.** This client fails in the three ways real-time code most often fails on phones. It **can't tell a dead connection from a quiet one** (no heartbeat), so scores freeze without an error. It **loses its subscriptions** on every reconnect and never catches up, so even when it reconnects, it shows nothing new. And it **reconnects badly**: instantly and forever, on any error including decoding errors, with receive loops and sockets that multiply. Those explain all three bug reports: frozen scores, hot phones, and the backend's connection count and deploy storms.

**How I'd fix it, in small steps:**

1. **Stop the bleeding.** Cancel the old task before creating a new one, guard `connect` against being called twice, and keep exactly one receive loop. Move the decode out of the `do` that drives reconnection, decode into an envelope with a `type`, and ignore unknown types. These are small diffs and remove the storm multiplier at once.
2. **Split the layers.** A `LiveSocket` actor owns one `URLSessionWebSocketTask` built from a `URLRequest` with an `Authorization` header, decodes off the main thread, and exposes an `AsyncThrowingStream` of typed messages. A `LiveScoresConnection` above it owns reconnection: capped exponential backoff with full jitter, a reset only after a connection delivers something, heartbeats when quiet, close codes honoured, and no retries while `NWPathMonitor` reports no path.
3. **Resume, don't restart.** The connection keeps the set of followed matches and, on every connect, resubscribes to each and fetches its current state over HTTP (or resumes from its last sequence number) before applying live updates.
4. **Replace history with state.** Keep `[matchID: MatchState]`, apply an update only when its version or sequence number is newer, and publish changes to the screen as a diffable snapshot from a main-actor view model.
5. **Give the connection a lifetime.** An app-level supervisor connects when the scene is active and a path exists, disconnects in the background, and screens subscribe and unsubscribe instead of calling `connect`. Remove the singleton callback.

**Tests to add.** Drive the connection with a fake transport and a `TestClock`: a quiet connection is closed after ping plus timeout; failures back off 1, 2, 4 s up to the cap and reset after a healthy connection; every reconnect resends every subscription; an unknown message type doesn't close the connection; `stop` leaves no task or loop running. For the state, test that duplicate and older updates are ignored and that two events in the same minute keep the server's order.

</ReferenceReview>
