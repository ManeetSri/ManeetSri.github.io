<Brief>

This is the checkout model for an event-ticketing app. People pick up to six seats, the seats are held for ten minutes, they pay, and they can get a refund until a day before the event. It shipped last month. Support now reports that refunds "do nothing", finance has found totals a penny out, and the team building the order history screen is copying rules out of this file. Review it as you would a pull request: what's wrong with the model, what matters most, and how you'd fix it.

```swift check ios title="TicketCheckout.swift"
import Foundation
import Observation

struct TicketOrder: Codable {
    var id: String
    var eventID: String
    var buyerEmail: String
    var seats: [String]
    var pricePerSeat: Double
    var currency: String
    var status: String // "reserved", "paid", "cancelled", "refunded"
    var reservedUntil: Date?
    var paymentID: String?
    var refundedAmount: Double?
}

@MainActor @Observable
final class TicketCheckoutViewModel {
    var order: TicketOrder
    var errorMessage: String?

    init(order: TicketOrder) {
        self.order = order
    }

    var total: Double {
        order.pricePerSeat * Double(order.seats.count)
    }

    var totalText: String {
        order.currency + " " + String(format: "%.2f", total)
    }

    func addSeat(_ seat: String) {
        if order.seats.count < 6 {
            order.seats.append(seat)
        }
    }

    func pay(email: String, paymentID: String) {
        guard email.contains("@") else {
            errorMessage = "Enter a valid email"
            return
        }
        if let until = order.reservedUntil, until < Date() {
            order.status = "cancelled"
            return
        }
        order.buyerEmail = email
        order.paymentID = paymentID
        order.status = "payed"
    }

    var canRefund: Bool {
        order.status == "paid" && order.paymentID != nil
    }

    func refund(eventStart: Date) {
        guard canRefund else { return }
        if eventStart.timeIntervalSinceNow > 86_400 {
            order.refundedAmount = total
            order.status = "refunded"
        }
    }
}
```

<ReferenceReview>

**Most important first.** Two problems are costing money today. The status typo (`"payed"` against `"paid"`) means **no refund can ever happen**, and the `Double` arithmetic is why **finance sees totals a penny out**. Both come from the same root cause: domain ideas held in primitives the compiler can't check. A one-line fix to the typo would stop the bleeding, but the next typo is one string away.

**The design problem underneath** is an anaemic model. `TicketOrder` has no rules of its own, its fields can combine in ways the business never allows, and every rule lives in one screen's view model. That's why another team is copying code out of this file.

**How I'd fix it, in small steps:**

1. **Pin today's behaviour with tests** around the view model (total, the seat limit, paying, refunding), injecting the clock so they run instantly. Fix the typo first, with a test that pays and then refunds.
2. **Introduce domain types** at the edges: `Money` (integer minor units and a currency), `EmailAddress`, `SeatID` and typed ids. Keep the JSON shape unchanged by decoding a DTO and converting it in one place.
3. **Replace the status string and its optionals with an enum:** `.reserved(until: Date)`, `.paid(PaymentID)`, `.refunded(PaymentID, amount: Money)`, `.cancelled(Reason)`. Write `init(from:)` to read the old fields, so stored orders and the API still decode.
4. **Move the rules into the model.** `TicketOrder` becomes an aggregate root with `private(set)` state and methods that check before they change: `addSeat(_:) throws`, `pay(paymentID:email:at:) throws`, `refund(at:eventStart:) throws`. The limits get names (`maxSeats`, `holdDuration`, `refundWindow`).
5. **Slim the view model** to holding the order, calling those methods and turning their errors into messages. Make `order` `private(set)`. The order history screen now reuses the model instead of copying rules.
6. **Keep the server authoritative.** The app's checks give instant feedback; the payment and refund endpoints check the same rules against their own clock.

**Tests to add:** the aggregate's rules (a seventh seat, a duplicate seat, paying after the hold expires, refunding just inside and just outside the window, refunding twice), each asserting the order is unchanged when refused; `Money` arithmetic and formatting for GBP, JPY and KWD; decoding stored orders from the previous release into the new enum.

</ReferenceReview>
