<Brief>

A ticketing app moved its event screen from MVC to MVVM last year. The view controller is now short, but every change to the event screen still touches this file, nobody has written a test for it, and the screen leaks: open and close ten events and ten view models are still in memory. Review the view model as you would a pull request: what's wrong, what matters most, and how you'd split it.

```swift check ios title="EventDetailViewModel.swift"
import UIKit

struct Event: Decodable {
    let id: String
    let title: String
    let startsAt: Date
    let priceInPence: Int
    let seatsLeft: Int
    let venueAddress: String
}

@MainActor
final class EventDetailViewModel {
    var viewController: UIViewController?
    var onChange: (() -> Void)?
    private(set) var event: Event?
    private(set) var isLoading = false
    private(set) var titleText = ""
    private(set) var dateText = ""
    private(set) var priceText = ""
    private(set) var seatsColor = UIColor.label
    private let eventID: String

    init(eventID: String) {
        self.eventID = eventID
    }

    func load() {
        isLoading = true
        onChange?()
        Task {
            let url = URL(string: "https://api.tickets.example/events/\(eventID)")!
            let (data, _) = try await URLSession.shared.data(from: url)
            let event = try JSONDecoder().decode(Event.self, from: data)
            self.event = event
            isLoading = false
            titleText = event.title.uppercased()
            let formatter = DateFormatter()
            formatter.dateFormat = "EEEE d MMMM, HH:mm"
            dateText = formatter.string(from: event.startsAt)
            priceText = "£" + String(format: "%.2f", Double(event.priceInPence) / 100)
            seatsColor = event.seatsLeft < 20 ? .systemRed : .label
            onChange?()
        }
    }

    func buyTapped(quantity: Int) {
        guard let event else { return }
        let limit = UserDefaults.standard.bool(forKey: "isMember") ? 8 : 4
        guard quantity <= limit, quantity <= event.seatsLeft else {
            let alert = UIAlertController(title: "Too many tickets", message: "You can buy up to \(limit).", preferredStyle: .alert)
            alert.addAction(UIAlertAction(title: "OK", style: .default))
            viewController?.present(alert, animated: true)
            return
        }
        let checkout = CheckoutViewController(eventID: event.id, quantity: quantity)
        viewController?.navigationController?.pushViewController(checkout, animated: true)
    }

    func directionsTapped() {
        guard let event else { return }
        let query = event.venueAddress.addingPercentEncoding(withAllowedCharacters: .urlQueryAllowed) ?? ""
        UIApplication.shared.open(URL(string: "maps://?q=\(query)")!)
    }
}

final class CheckoutViewController: UIViewController {
    init(eventID: String, quantity: Int) { super.init(nibName: nil, bundle: nil) }
    required init?(coder: NSCoder) { nil }
}
```

<ReferenceReview>

**Most important first.** Two bugs reach users today. The screen **leaks**, because the view model holds its view controller strongly while the view controller owns the view model. And every failure is **silent**: the throwing task drops its error before `isLoading` is reset, so a flaky network leaves a spinner that never ends.

**The design problem underneath** is that this "view model" is still a view controller. It presents alerts, pushes screens, opens Maps, makes the networking call, applies a business rule, chooses colours and formats text. MVVM only helps when the view model holds presentation logic and nothing else: it decides *what* the screen shows and *that* something should happen, and other objects decide *how*.

**How I'd fix it, in small steps:**

1. Pin today's behaviour with characterisation tests on the formatted text, using a stub that feeds the view model a fixed `Event` (this needs step 2's seam first, so do the two together).
2. Inject an `EventRepository` protocol and move the URL, the request, the status check and the decoding (with `.iso8601` dates) into its implementation.
3. Replace the loose properties with one `ViewState` (`loading`, `loaded(EventDisplay)`, `failed(message)`), and catch errors in the task so failure is a state with a retry.
4. Delete `viewController`. Give the view model an `onRoute` closure (`.checkout(eventID:quantity:)`, `.directions(address:)`), injected by a coordinator, and put the "too many tickets" alert in the state as a value the view presents.
5. Move the ticket limit into a `TicketPolicy` in the domain layer, given the account's membership rather than a `UserDefaults` key.
6. Replace `UIColor` with `isLowOnSeats: Bool` and drop `import UIKit`; format with `FormatStyle`s and an injected `Locale` and `TimeZone`.

After step 6 the view model imports Foundation only, and the view controller maps state to labels and routes to its coordinator.

**Tests to add:** loading moves to loaded with the expected display text for a fixed locale; a failing repository produces the failed state and retry recovers; buying within and beyond the limit emits a route or an alert; a `weak` reference to the view model is `nil` after the screen is dismissed.

</ReferenceReview>
