<Brief>

A note-taking app syncs the signed-in user's profile and settings when it comes to the foreground, and the settings screen shows a spinner until the sync finishes. Users report the spinner sometimes never stops, and a few say their settings "reset themselves". The sync code is below; the transport and store behind its two protocols are thin wrappers over URLSession and Core Data, and the store replaces the saved record each time it saves.

```swift check ios title="ProfileSync.swift"
import Foundation

protocol HTTPTransport {
    func send(_ method: String, _ path: String, completion: @escaping ([String: Any]?, Error?) -> Void)
}

protocol RecordStore {
    func save(_ record: [String: Any], entity: String, completion: @escaping (Error?) -> Void)
}

struct SyncOptions {
    var retryPolicy: String? = nil
    var conflictResolution = "serverWins"
    var batchSize = 50
    var onProgress: ((Double) -> Void)? = nil
}

final class ProfileSync {
    private let transport: HTTPTransport
    private let store: RecordStore
    private let options: SyncOptions

    init(transport: HTTPTransport, store: RecordStore, options: SyncOptions = SyncOptions()) {
        self.transport = transport
        self.store = store
        self.options = options
    }

    func sync(userID: String, completion: @escaping (Bool) -> Void) {
        transport.send("GET", "/users/" + userID) { profile, error in
            guard var profile = profile, error == nil else {
                completion(false)
                return
            }
            self.transport.send("GET", "/users/" + userID + "/settings") { settings, error in
                if let error = error as? URLError, error.code == .notConnectedToInternet {
                    NotificationCenter.default.post(name: Notification.Name("ProfileSyncOffline"), object: nil)
                    return
                }
                profile["settings"] = settings
                self.store.save(profile, entity: "CDProfile") { error in
                    if error == nil {
                        NotificationCenter.default.post(name: Notification.Name("profileDidSync"), object: nil, userInfo: ["userId": userID])
                    }
                    completion(error == nil)
                }
            }
        }
    }
}
```

<ReferenceReview>

**Most important first.** Both user reports trace to this file. The offline path **never calls completion** (lines 36–39), which is the spinner that never stops. And any other settings failure **saves a profile without settings and reports success** (line 40), which is the settings that "reset themselves": silent data loss. Fix those two first, in a small pull request of their own.

**The design problems underneath** are an API built from completion handlers and untyped dictionaries, behind protocols that leak what they were meant to hide. Each makes the bugs above easy to write and hard to see: a forgotten completion is invisible, a nil in a dictionary is a deletion, and the sync knows about `URLError` and Core Data entity names.

**How I'd fix it, in small steps:**

1. Characterise today's behaviour with a fake transport and store that record calls: success, offline on either request, a server error on the settings request. Two of those tests describe bugs; write them as they behave now, then change their expectations in the commit that fixes each.
2. Fix the bugs: call `completion(false)` on the offline path, and treat any settings failure as a failed sync that saves nothing.
3. Add `Codable` `Profile` and `ProfileSettings` types, and a transport method `func get<T: Decodable>(_ endpoint: Endpoint) async throws(SyncError) -> T` that maps `URLError` to `SyncError.offline` inside the transport.
4. Write `func sync(userID: String) async throws(SyncError) -> Profile`: two `async let` requests, a typed `store.save(profile)`, and a plain return. Keep the completion-handler method as a deprecated wrapper that calls it from a `Task`, move callers over, then delete the wrapper.
5. Replace the notifications with the return value (the screen awaits the sync), or with `Notification.Name` constants for the observers that remain. Delete `SyncOptions`.

**Tests to add:** offline on either request throws `.offline` and saves nothing; a settings failure saves nothing; success saves one merged profile; cancelling the sync's task before the requests finish saves nothing.
