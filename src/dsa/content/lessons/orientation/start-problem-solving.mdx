## Why it matters

Staring at a blank editor waiting for inspiration is the most common way to get stuck. Strong problem solvers aren't magically faster. They follow a process that always gives them a next step. Learn the process now, on easy problems, so it's automatic when the problems get hard.

## The seven steps

1. **Understand.** Restate the problem in your own words. What goes in, and what comes out?
2. **Examples.** Work through a small example by hand, then the awkward ones: empty input, one element, duplicates, negatives.
3. **Brute force.** Find *any* correct solution, however slow. It proves you understand the problem.
4. **Optimise.** Ask what work the brute force repeats or wastes, and whether a better structure or idea can avoid it.
5. **Code.** Write it cleanly, with names that say what things are.
6. **Test.** Run your examples through the code, by hand and then with the tests.
7. **Analyse.** State the time and space complexity, and why.

<Callout kind="tip">
Steps 1–4 happen *before* you write real code. Most bugs come from coding before you understand the problem.
</Callout>

## Walking through a real problem

> Given a list of whole numbers, return the largest one. If the list is empty, return nothing.

**Understand.** Input: an array of `Int`. Output: the biggest value, or `nil` (Swift's "nothing") when the array is empty. So the return type is `Int?`.

**Examples.**

| Input | Output | Why it matters |
| --- | --- | --- |
| `[3, 9, 4]` | `9` | the normal case |
| `[-5, -2, -8]` | `-2` | all negative: starting from 0 would be wrong |
| `[7]` | `7` | a single element |
| `[]` | `nil` | empty |

**Brute force.** Sort the numbers, then take the last one. Correct, but sorting does far more work than we need.

**Optimise.** We only need the biggest, not a full ordering. Walk through once, remembering the largest number seen so far:

```swift title="largest(in:)" run
func largest(in numbers: [Int]) -> Int? {
    guard var best = numbers.first else { return nil }
    for number in numbers {
        if number > best {
            best = number
        }
    }
    return best
}

for numbers in [[3, 9, 4], [-5, -2, -8], []] {
    if let answer = largest(in: numbers) {
        print("Largest of \(numbers) is \(answer)")
    } else {
        print("\(numbers) is empty")
    }
}
```

```output
Largest of [3, 9, 4] is 9
Largest of [-5, -2, -8] is -2
[] is empty
```

`if let` runs its block only when there *is* an answer, and the `else` handles `nil`. You'll meet it properly in M04, Optionals.

Starting `best` at the first element, not at `0`, is what makes the all-negative example work. The examples step caught that bug before it happened.

**Analyse.** We look at each number once, so the time grows in step with the input: that's written **O(n)**. We store one extra number, so the extra space is **O(1)**. You'll learn this notation properly in Part II. For now, read O(n) as "grows in proportion to the input size".

## A taste of what's ahead: thinking smarter, not harder

Sometimes a better idea changes everything. Suppose the numbers are **sorted** and you're looking for one value. Checking each in turn takes up to *n* steps. But if you check the middle first, you can rule out half the list in one comparison, then half of what's left, and so on.

Step through it below. Pick a value, press play, and watch the search range shrink:

```visual binarySearch
items: [3, 8, 12, 17, 21, 26, 30, 34, 41, 45, 52]
target: 34
```

That's **binary search**. For a million sorted items it needs about 20 checks instead of up to a million. You'll master it in Part IV. For now, notice the habit: *ask what the structure of the data lets you skip.*
