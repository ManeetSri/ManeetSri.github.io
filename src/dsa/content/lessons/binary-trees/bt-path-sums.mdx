## Why it matters

A budgeting app keeps spending in a tree of categories: Food, then Groceries, then Fruit. "Does some chain of categories, from the top down to a single item, add up to exactly £150?" "Which chains?" "How many stretches of nested categories, starting anywhere, add up to £40?" Those are path sum I, II and III, three classic problems that grow in difficulty. They teach the second way information moves through a tree. In the last three lessons, answers flowed **up** as return values. Here, a running total flows **down** as a parameter. Path sum III then reuses the prefix sum + dictionary trick from M20, with one new twist.

## The example tree

```text
            7
          /   \
         2     5
        / \     \
       4   -1    3
      /    / \
     1    6   2
```

In level order that's `[7, 2, 5, 4, -1, nil, 3, 1, nil, 6, 2]`. Its root-to-leaf paths are:

| Path | Sum |
| --- | --- |
| 7 → 2 → 4 → 1 | 14 |
| 7 → 2 → −1 → 6 | 14 |
| 7 → 2 → −1 → 2 | 10 |
| 7 → 5 → 3 | 15 |

## Path sum I: pass down what's still needed

> Is there a path from the root down to a **leaf** whose values add up to `target`?

Walk down, and subtract each node's value from the target as you go. At a leaf, the path works if nothing is left over:

```swift
func hasPathSum(_ node: TreeNode?, _ target: Int) -> Bool {
    guard let node else { return false }
    let remaining = target - node.value
    if node.left == nil && node.right == nil {
        return remaining == 0                           // a leaf: does this path add up?
    }
    return hasPathSum(node.left, remaining) || hasPathSum(node.right, remaining)
}
```

The parameter carries information **down**: each call receives what its ancestors left over. This is a **top-down** recursion, the mirror image of `height`, which built its answer on the way back **up**.

What to notice:

- **The leaf test is `left == nil && right == nil`.** A node with one child isn't the end of a path. If you tested `node == nil` instead, the missing child of such a node would count as the end of a path that stopped too early.
- **`||` stops at the first success.** Once a path works, the other side is never explored.
- **The empty tree has no paths**, so `hasPathSum(nil, 0)` is `false`, not `true`.

## Path sum II: collect the paths, and backtrack

> List **every** root-to-leaf path whose values add up to `target`.

Now each leaf that works needs the whole path, not only a yes. Keep **one** array, `path`, holding the nodes from the root to the current node. Append a node's value when the walk arrives, and remove it when the walk leaves. Undoing your own change on the way out is called **backtracking**; a later module is all about it.

```swift run
func hasPathSum(_ node: TreeNode?, _ target: Int) -> Bool {
    guard let node else { return false }
    let remaining = target - node.value
    if node.left == nil && node.right == nil {
        return remaining == 0
    }
    return hasPathSum(node.left, remaining) || hasPathSum(node.right, remaining)
}

func paths(in root: TreeNode?, summingTo target: Int) -> [[Int]] {
    var result: [[Int]] = []
    var path: [Int] = []                                // the values from the root to the current node
    func walk(_ node: TreeNode?, _ remaining: Int) {
        guard let node else { return }
        path.append(node.value)                         // arrive
        let stillNeeded = remaining - node.value
        if node.left == nil && node.right == nil {
            if stillNeeded == 0 {
                result.append(path)                     // stores a copy of path as it is now
            }
        } else {
            walk(node.left, stillNeeded)
            walk(node.right, stillNeeded)
        }
        path.removeLast()                               // leave: backtrack
    }
    walk(root, target)
    return result
}

let tree = TreeNode.make([7, 2, 5, 4, -1, nil, 3, 1, nil, 6, 2])
print(hasPathSum(tree, 14), hasPathSum(tree, 13))
print(paths(in: tree, summingTo: 14))
print(paths(in: tree, summingTo: 15))
print(paths(in: tree, summingTo: 9))

// MARK: - The TreeNode from DSAKit, cut down so this file runs on its own

final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }

    /// Builds a tree from its level order, with nil for a missing child, like TreeNode.make in DSAKit
    static func make(_ levelOrder: [Int?]) -> TreeNode? {
        guard let first = levelOrder.first, let rootValue = first else { return nil }
        let root = TreeNode(rootValue)
        var parents = [root]
        var head = 0
        var index = 1
        while index < levelOrder.count && head < parents.count {
            let parent = parents[head]
            head += 1
            if let value = levelOrder[index] {
                parent.left = TreeNode(value)
                parents.append(parent.left!)
            }
            index += 1
            if index < levelOrder.count, let value = levelOrder[index] {
                parent.right = TreeNode(value)
                parents.append(parent.right!)
            }
            index += 1
        }
        return root
    }
}
```

```output
true false
[[7, 2, 4, 1], [7, 2, -1, 6]]
[[7, 5, 3]]
[]
```

What to notice:

- **`result.append(path)` takes a snapshot.** Arrays are values in Swift, so the stored copy doesn't change when `path` changes later. (In languages where arrays are references, forgetting to copy here is a famous bug: every stored path ends up empty.)
- **Every `append` has a matching `removeLast`**, on every route out of `walk`. That's why the `removeLast` sits at the very end, after both the leaf case and the recursive case.
- One shared array means O(h) extra space for the path, instead of building a new array at every node.
- Visiting is O(n), and each path found costs O(h) to copy. In the worst case, O(n · h) overall.

## Path sum III: paths that start anywhere

> Count the **downward** paths whose values add up to `target`. A downward path starts at any node and goes down through children, stopping at any node below (or where it started).

With `target` 7 in the example tree there are three: the root 7 on its own, 2 → 4 → 1, and 2 → −1 → 6. They don't have to start at the root or end at a leaf.

### Brute force

From every node, walk every path down and count the ones that hit the target:

```swift
func countFrom(_ node: TreeNode?, _ remaining: Int) -> Int {
    guard let node else { return 0 }
    let left = remaining - node.value
    return (left == 0 ? 1 : 0) + countFrom(node.left, left) + countFrom(node.right, left)
}

func countSlowly(_ node: TreeNode?, _ target: Int) -> Int {
    guard let node else { return 0 }
    return countFrom(node, target) + countSlowly(node.left, target) + countSlowly(node.right, target)
}
```

Each node starts a walk over everything below it, so a node is visited once for each of its ancestors: O(n log n) for a balanced tree, but **O(n²)** for a long chain.

### The prefix sum view

Fix one node, and look only at the path from the root down to it, such as 7 → 2 → −1 → 6. Write those values out as an array: `[7, 2, -1, 6]`. A downward path that **ends** at 6 is a stretch of that array that ends at its last element: `[6]`, `[-1, 6]`, `[2, -1, 6]` or `[7, 2, -1, 6]`.

So "how many downward paths ending here add up to `target`?" is exactly "how many subarrays ending here add up to `target`?", which [Prefix sum + hashmap: subarray sum equals k](/dsa/learn/prefix-hashmap) answers in O(1):

- keep a **running sum** from the root down to the current node;
- a path ending here sums to `target` for every **earlier** running sum equal to `running − target`;
- a dictionary counts how many times each running sum has appeared, starting with `[0: 1]` for the empty path above the root.

### The twist: forget the branch you leave

In an array, there's only one "earlier". In a tree, the walk goes down one branch, comes back up, and goes down another. When it comes back up out of a node, that node's running sum is **no longer above** anything the walk visits next. It must leave the dictionary.

So each call adds its running sum to the dictionary on the way in, and takes it back out on the way out: backtracking again, this time on a count.

<Callout kind="analogy">
Think of the odometer from M20, on a road trip through branching valleys. Going up a side valley, you note each mileage reading. When you drive back down to the junction, you cross out the readings from that valley: journeys that end in the next valley can't start in this one.
</Callout>

```swift run
func countPaths(in root: TreeNode?, summingTo target: Int) -> Int {
    var seen: [Int: Int] = [0: 1]                       // running sums on the path above: just the empty path
    var count = 0
    func walk(_ node: TreeNode?, _ runningAbove: Int) {
        guard let node else { return }
        let running = runningAbove + node.value
        let found = seen[running - target, default: 0]  // downward paths that end at this node
        count += found
        print("at \(node.value): running \(running), look for \(running - target), found \(found)")
        seen[running, default: 0] += 1                  // arrive
        walk(node.left, running)
        walk(node.right, running)
        seen[running, default: 0] -= 1                  // leave: this sum isn't above the next nodes
    }
    walk(root, 0)
    return count
}

let tree = TreeNode.make([7, 2, 5, 4, -1, nil, 3, 1, nil, 6, 2])
print("total:", countPaths(in: tree, summingTo: 7))

at 2: running 9, look for 2, found 0
at 4: running 13, look for 6, found 0

```

Read the trace:

- **At 7**, looking for 0 finds the empty path: the root alone sums to 7.
- **At 1**, the running sum is 14 and the walk looks for 7. The running sum 7 belongs to the root, so the path **after** the root, 2 → 4 → 1, sums to 7.
- **At 6**, the same thing happens through −1: 2 → −1 → 6.
- **At 5**, the running sum is 12, and the walk looks for 5. Nothing matches. But the left branch produced running sums 9, 13, 14, 8, 14 and 10. If they were still in the dictionary, they could have produced false matches here. They were removed on the way back up.

Here's that danger made concrete. This version forgets to remove its sums, and overcounts:

```swift run
func countForgetful(in root: TreeNode?, summingTo target: Int) -> Int {
    var seen: [Int: Int] = [0: 1]
    var count = 0
    func walk(_ node: TreeNode?, _ runningAbove: Int) {
        guard let node else { return }
        let running = runningAbove + node.value
        count += seen[running - target, default: 0]
        seen[running, default: 0] += 1
        walk(node.left, running)
        walk(node.right, running)
        // missing: seen[running, default: 0] -= 1
    }
    walk(root, 0)
    return count
}

// 5 → 3 → 2 on the left, 5 → −3 → 8 on the right. Paths summing to 2: [2] and [5, −3].
let tree = TreeNode(5, left: TreeNode(3, left: TreeNode(2)), right: TreeNode(-3, right: TreeNode(8)))
print(countForgetful(in: tree, summingTo: 2))

// MARK: - The TreeNode from DSAKit, cut down so this file runs on its own

final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}
```

```output
3
```

The right answer is 2. At 8, the running sum is 10 and the walk looks for 8. The running sum 8 belongs to the node 3, on the **left** branch, which isn't above 8 at all. The forgetful version counts a "path" from the left branch over to the right one.

### What it costs

Each node does O(1) dictionary work on average: **O(n)** time. The dictionary only ever describes one root-to-node path, so it holds at most h + 1 sums, and the stack holds h frames: O(h) space. (Counts that drop to 0 stay in the dictionary as harmless zeros. You could remove them with `seen[running] = nil`, but it isn't needed.)

## Up or down?

| Information flows | How | Examples |
| --- | --- | --- |
| **Up**, bottom-up | return values, combined after the recursive calls | height, diameter, balance |
| **Down**, top-down | parameters, passed into the recursive calls | path sums, good nodes, path numbers |

Many problems use both: path sum III passes a running sum down, and a shared counter collects the answer. When you meet a new tree problem, ask: does a node need to know something about its **ancestors** (pass it down), or about its **descendants** (return it up)?

<Callout kind="gotcha" title="Three slips to avoid">
**Ending a path at a missing child.** For root-to-leaf paths, check for a leaf with `node.left == nil && node.right == nil`. Otherwise a node with one child looks like the end of a path.

**Recording before looking up.** In path sum III, look up `running - target` before adding `running` to the dictionary, exactly as in M20. With `target` 0, recording first makes every node match itself: an empty path.

**Forgetting to backtrack.** Every change you make on the way in (`path.append`, `seen[running] += 1`) needs its undo on the way out.
</Callout>
