## Why it matters

Three standard-library protocols turn your types into first-class citizens. **`Equatable`** gives you `==`, and with it `contains` and `firstIndex(of:)`. **`Comparable`** gives you `<`, and with it `sorted()`, `min()` and `max()`. **`CustomStringConvertible`** controls how a value prints. DSA leans on all three: sorting custom records, finding items, and heaps and binary search trees, which only work on values that can be compared.

## Equatable: teaching `==`

Conform a struct to `Equatable` and, if every stored property is itself `Equatable`, Swift writes `==` for you:

```swift run
struct Card: Equatable {
    var rank: Int
    var suit: String
}

let hand = [Card(rank: 10, suit: "hearts"), Card(rank: 3, suit: "spades")]
let wanted = Card(rank: 3, suit: "spades")

print(hand[1] == wanted)
print(hand.contains(wanted))
print(hand.firstIndex(of: wanted) ?? -1)
print(hand[0] != wanted)
```

```output
true
true
1
true
```

What to notice:

- The generated `==` compares every stored property. Two cards are equal when both rank and suit match.
- `!=` comes free with `==`.
- `contains(_:)` and `firstIndex(of:)` only exist for arrays whose elements are `Equatable`. Conforming unlocks them.

Enums get `Equatable` automatically when they have no associated values. With associated values, add `: Equatable` and Swift writes it, as long as the associated values are `Equatable` too.

### Writing == yourself

Sometimes "equal" should mean something narrower than "every property matches". Then write `==` yourself, as a `static func`:

```swift run
struct Username: Equatable {
    var text: String

    static func == (lhs: Username, rhs: Username) -> Bool {
        lhs.text.lowercased() == rhs.text.lowercased()
    }
}

print(Username(text: "Maneet") == Username(text: "MANEET"))
print(Username(text: "Maneet") == Username(text: "Ada"))
```

```output
true
false
```

`lhs` and `rhs` are conventional names for the left-hand side and right-hand side. An operator is a static function whose name is the symbol.

## Comparable: teaching `<`

`Comparable` builds on `Equatable` and adds one requirement: the `<` operator. Swift does **not** write it for structs, because it can't know which property should come first. Leave it out and you get `error: type 'ClockTime' does not conform to protocol 'Comparable'`.

```swift run
struct ClockTime: Comparable {
    var hour: Int
    var minute: Int

    static func < (lhs: ClockTime, rhs: ClockTime) -> Bool {
        if lhs.hour != rhs.hour {
            return lhs.hour < rhs.hour
        }
        return lhs.minute < rhs.minute
    }
}

let alarms = [ClockTime(hour: 9, minute: 30), ClockTime(hour: 7, minute: 45), ClockTime(hour: 9, minute: 5)]
let earliest = alarms.min()!
print(earliest.hour, earliest.minute)
for alarm in alarms.sorted() {
    print(alarm.hour, alarm.minute)
}
print(ClockTime(hour: 12, minute: 0) > ClockTime(hour: 11, minute: 59))
```

```output
7 45
7 45
9 5
9 30
true
```

From `<` alone, Swift provides `>`, `<=` and `>=`, plus `sorted()`, `sort()`, `min()` and `max()` on collections of `ClockTime`. You wrote one function and got all of that.

The comparison checks hours first and looks at minutes only when the hours tie. This "compare by the first key, break ties with the next" shape is called **lexicographic** order, and it's how dictionaries order words. Tuples already compare this way, which gives a handy shortcut:

```swift
static func < (lhs: ClockTime, rhs: ClockTime) -> Bool {
    (lhs.hour, lhs.minute) < (rhs.hour, rhs.minute)
}
```

This works for tuples of up to six `Comparable` elements.

### Enums can get Comparable for free

An enum without associated values can declare `Comparable` with no code. Its cases are ordered as you wrote them:

```swift run
enum Priority: Comparable {
    case low, medium, high, urgent
}

let tasks: [Priority] = [.medium, .urgent, .low, .high]
print(tasks.max()!)
print(Priority.low < Priority.high)
for priority in tasks.sorted(by: >) {
    print(priority)
}
```

```output
urgent
true
urgent
high
medium
low
```

`sorted(by: >)` passes the `>` operator itself as the comparison, sorting from largest to smallest. Operators are functions, so they can be passed around like the closures in M06.

## CustomStringConvertible: controlling print

By default, `print` shows a struct's type and every property. Conform to `CustomStringConvertible` and provide a `description` to choose the text yourself:

```swift run
struct ClockTime: CustomStringConvertible {
    var hour: Int
    var minute: Int

    var description: String {
        let paddedMinute = minute < 10 ? "0\(minute)" : "\(minute)"
        return "\(hour):\(paddedMinute)"
    }
}

let lunch = ClockTime(hour: 12, minute: 5)
print(lunch)
print("Lunch is at \(lunch)")
print([lunch, ClockTime(hour: 18, minute: 30)])
```

```output
12:05
Lunch is at 12:05
[12:05, 18:30]
```

`print`, string interpolation and even arrays of your type all use `description`. Your data structures will benefit from this: printing a stack or a tree in a readable shape makes debugging far easier.

## Putting them together: a leaderboard

```swift run
struct Player: Comparable, CustomStringConvertible {
    var name: String
    var score: Int

    // Higher scores rank first; equal scores go alphabetically
    static func < (lhs: Player, rhs: Player) -> Bool {
        if lhs.score != rhs.score {
            return lhs.score > rhs.score
        }
        return lhs.name < rhs.name
    }

    var description: String {
        "\(name) (\(score))"
    }
}

let players = [
    Player(name: "Zoe", score: 80),
    Player(name: "Ada", score: 95),
    Player(name: "Bo", score: 80),
]
for (place, player) in players.sorted().enumerated() {
    print("\(place + 1). \(player)")
}
```

```output
1. Ada (95)
2. Bo (80)
3. Zoe (80)
```

Here `<` means "ranks before", which is why it compares scores with `>`. That's allowed: `<` defines whatever order you want `sorted()` to produce, as long as it's consistent.

<Callout kind="gotcha" title="Swift gotcha: < must be strict">
Your `<` must return `false` when both values are equal. Writing `<=` inside it, or an order that contradicts itself (where `a < b` and `b < a` are both true), breaks the rules that `sorted()` and `min()` rely on, and you can get wrong results. When two values tie on every key, `<` returns `false` both ways.
</Callout>
