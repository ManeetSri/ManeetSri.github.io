## Why it matters

Suppose you want a protocol for "anything that holds items", so stacks, queues and bags can share code. What type does its `append` method take? A stack of `Int`s appends `Int`s; a stack of `String`s appends `String`s. A protocol needs a way to say "the type of item, whatever each conforming type decides". That's an **associated type**, and the standard library's most important protocols, `Sequence` and `Collection`, are built on them.

## The problem

Try writing the protocol with a fixed item type:

```swift
protocol IntContainer {
    mutating func append(_ item: Int)
    var count: Int { get }
    func item(at index: Int) -> Int
}
```

That works for integers only. A `Stack<String>` can't conform, and writing `StringContainer`, `CharacterContainer` and so on is the same duplication that generics solved for functions.

## associatedtype

An **associated type** is a placeholder name inside a protocol. Each conforming type decides what it stands for:

```swift
protocol Container {
    associatedtype Item
    mutating func append(_ item: Item)
    var count: Int { get }
    func item(at index: Int) -> Item
}
```

Read `associatedtype Item` as "every container has some type of item, called `Item`". The requirements then use `Item` wherever the item type belongs.

Here are two conforming types. One is generic, the other always holds integers:

```swift run
protocol Container {
    associatedtype Item
    mutating func append(_ item: Item)
    var count: Int { get }
    func item(at index: Int) -> Item
}

struct Stack<Element>: Container {
    private var items: [Element] = []

    mutating func push(_ item: Element) {
        items.append(item)
    }

    mutating func pop() -> Element? {
        items.popLast()
    }

    // Container requirements
    mutating func append(_ item: Element) {
        push(item)
    }

    var count: Int {
        items.count
    }

    func item(at index: Int) -> Element {
        items[index]
    }
}

struct EvenNumbers: Container {
    private var numbers: [Int] = []

    mutating func append(_ item: Int) {
        if item % 2 == 0 {
            numbers.append(item)
        }
    }

    var count: Int {
        numbers.count
    }

    func item(at index: Int) -> Int {
        numbers[index]
    }
}

var words = Stack<String>()
words.append("tea")
words.append("cake")
print(words.count, words.item(at: 1))

var evens = EvenNumbers()
for value in 1...6 {
    evens.append(value)
}
print(evens.count, evens.item(at: 0))
```

```output
2 cake
3 2
```

What to notice:

- Neither type says what `Item` is. Swift **infers** it from the methods: for `Stack<Element>`, `append` takes an `Element`, so `Item` is `Element`; for `EvenNumbers`, `Item` is `Int`.
- You can also state it explicitly with `typealias Item = Int` inside the type. That's occasionally needed when inference has nothing to go on.
- Each conforming type has exactly **one** `Item`. A `Stack<String>`'s items are always `String`s.

## Generic functions over any container

The real payoff comes when you write a generic function that accepts any `Container`. Inside it, `C.Item` names that container's item type:

```swift run
protocol Container {
    associatedtype Item
    mutating func append(_ item: Item)
    var count: Int { get }
    func item(at index: Int) -> Item
}

struct Bag<Element>: Container {
    private var items: [Element] = []
    mutating func append(_ item: Element) { items.append(item) }
    var count: Int { items.count }
    func item(at index: Int) -> Element { items[index] }
}

func lastItem<C: Container>(of container: C) -> C.Item? {
    container.count == 0 ? nil : container.item(at: container.count - 1)
}

func allItemsMatch<C1: Container, C2: Container>(_ first: C1, _ second: C2) -> Bool
    where C1.Item == C2.Item, C1.Item: Equatable {
    guard first.count == second.count else {
        return false
    }
    for index in 0..<first.count where first.item(at: index) != second.item(at: index) {
        return false
    }
    return true
}

var a = Bag<Int>()
var b = Bag<Int>()
for value in [3, 1, 4] {
    a.append(value)
    b.append(value)
}
print(lastItem(of: a) ?? -1)
print(allItemsMatch(a, b))
b.append(1)
print(allItemsMatch(a, b))
```

```output
4
true
false
```

Look closely at the `where` clause of `allItemsMatch`:

- `C1.Item == C2.Item`: the two containers may be **different types**, but they must hold the **same kind** of item. Comparing a container of `Int`s with a container of `String`s won't compile.
- `C1.Item: Equatable`: the items must support `!=`, which the loop uses.

Constraints on associated types like these are how the standard library expresses ideas such as "these two sequences have the same element type" or "the elements can be sorted".

## Associated types you already use

You've been relying on associated types since M06:

| Protocol | Associated type | For `[Int]` it's… |
| --- | --- | --- |
| `Sequence` | `Element` | `Int` |
| `Collection` | `Index` | `Int` |
| `IteratorProtocol` | `Element` | `Int` |

When you write `extension Sequence where Element: Comparable`, `Element` is that associated type. When a `String`'s index is a `String.Index` rather than an `Int`, as you learned in M08, that's `Collection`'s `Index` associated type at work: each collection chooses its own.

The next two lessons put this to use. You'll make your own types conform to `Sequence` and `Collection`, choosing their `Element` and `Index`.

## A constraint inside the protocol

A protocol can also constrain its associated type directly, so every conforming type must use an item type with some ability:

```swift
protocol SortedContainer {
    associatedtype Item: Comparable
    mutating func insert(_ item: Item)
    var smallest: Item? { get }
}
```

A sorted container makes no sense for items that can't be ordered, so the protocol demands `Comparable` items up front. A binary search tree or a heap, which you'll build later, makes exactly this demand.

<Callout kind="gotcha" title="Swift gotcha: any Container loses the item type">
You can write `let boxes: [any Container]`, but each box's `Item` could be different, so anything that returns an `Item` gives you a value of the vague type `Any`. You can't pass that back into `append`, and you can't compare it. When you need the item type, write a generic function `<C: Container>` instead. The final lesson of this module, on `some` and `any`, explains why.
</Callout>
