## Why it matters

A **protocol** is a promise: "any type that adopts me has these properties and methods". It lets code work with many different types through one shared set of abilities. Swift's standard library is built on protocols: `==` comes from one, sorting from another, `for-in` from a third. In DSA, a protocol describes *what* a data structure can do, separately from *how* it does it.

## Defining a protocol

A protocol lists **requirements**: names, types and signatures, but no bodies and no storage.

```swift
protocol Describable {
    var summary: String { get }
    func describe() -> String
}
```

This says: a `Describable` type has a readable `summary` string and a `describe()` method that returns a `String`. It doesn't say how they work. Protocol names use UpperCamelCase like other types, and often end in *-able* or *-ible* when they describe an ability.

## Conforming to a protocol

A type **conforms** to a protocol by naming it after a colon, the same place a class names its superclass, and then meeting every requirement:

```swift run
protocol Describable {
    var summary: String { get }
    func describe() -> String
}

struct Book: Describable {
    var title: String
    var pages: Int

    var summary: String {
        "\(title), \(pages) pages"
    }

    func describe() -> String {
        "Book: \(summary)"
    }
}

enum Planet: Describable {
    case earth, mars

    var summary: String {
        self == .earth ? "home" : "red and dusty"
    }

    func describe() -> String {
        "Planet: \(summary)"
    }
}

print(Book(title: "Dune", pages: 412).describe())
print(Planet.mars.describe())
```

```output
Book: Dune, 412 pages
Planet: red and dusty
```

What to notice:

- A struct and an enum both conform. Classes can too. A protocol cares only about abilities, not what kind of type has them.
- Swift checks every requirement at compile time. Leave one out and you'll see `error: type 'Book' does not conform to protocol 'Describable'`, along with a note naming what's missing.
- A type can conform to several protocols at once: `struct Book: Describable, Hashable`.

## Property requirements

A property requirement states a name, a type, and whether it must be settable:

| Requirement | Can be satisfied by |
| --- | --- |
| `var name: String { get }` | a `let`, a `var`, or a computed property |
| `var name: String { get set }` | a `var`, or a computed property with a setter |

`{ get }` means "at least readable". It never stops a conforming type from also allowing changes. A protocol always writes `var` for its properties, even when a conforming type uses `let`.

## Mutating requirements

If a requirement will change a struct or enum, the protocol must mark it `mutating`, just as the method itself would be:

```swift run
protocol Resettable {
    mutating func reset()
}

struct Counter: Resettable {
    var count = 0

    mutating func reset() {
        count = 0
    }
}

final class Timer: Resettable {
    var seconds = 90

    func reset() {
        seconds = 0
    }
}

var clicks = Counter(count: 12)
clicks.reset()
let timer = Timer()
timer.reset()
print(clicks.count, timer.seconds)
```

```output
0 0
```

The class's version doesn't write `mutating`, because class methods can always change properties. Without `mutating` in the protocol, though, no struct could conform with a method that changes it.

## Using a protocol as a type

You can use a protocol where a type is expected, for example to hold different conforming types in one array:

```swift run
protocol Describable {
    func describe() -> String
}

struct Book: Describable {
    var title: String
    func describe() -> String { "Book: \(title)" }
}

struct Song: Describable {
    var name: String
    var seconds: Int
    func describe() -> String { "Song: \(name) (\(seconds)s)" }
}

func printAll(_ items: [any Describable]) {
    for item in items {
        print(item.describe())
    }
}

printAll([Book(title: "Dune"), Song(name: "Blue", seconds: 190), Book(title: "Emma")])
```

```output
Book: Dune
Song: Blue (190s)
Book: Emma
```

`any Describable` means "a value of any type that conforms to `Describable`". The array mixes books and songs, and each element calls its own `describe()`. Through an `any Describable`, you can use only what the protocol promises: `item.title` wouldn't compile, because not every `Describable` has a title.

The word `any` makes it clear you're working with "some conforming type, decided at run time". You'll see older code leave it out, and the last lesson of this module, on `some` and `any`, explains the trade-offs.

## Protocols describe abstract data types

Here's the DSA connection. A **stack** is defined by what it can do: push a value on top, pop the top value off, and check whether it's empty. That description, separate from any implementation, is called an **abstract data type**. A protocol captures it exactly:

```swift run
protocol IntStack {
    mutating func push(_ value: Int)
    mutating func pop() -> Int?
    var isEmpty: Bool { get }
}

struct EndStack: IntStack {
    private var items: [Int] = []

    mutating func push(_ value: Int) {
        items.append(value)
    }

    mutating func pop() -> Int? {
        items.popLast()
    }

    var isEmpty: Bool {
        items.isEmpty
    }
}

struct FrontStack: IntStack {
    private var items: [Int] = []

    mutating func push(_ value: Int) {
        items.insert(value, at: 0)
    }

    mutating func pop() -> Int? {
        isEmpty ? nil : items.removeFirst()
    }

    var isEmpty: Bool {
        items.isEmpty
    }
}

var stacks: [any IntStack] = [EndStack(), FrontStack()]
for index in stacks.indices {
    for value in [1, 2, 3] {
        stacks[index].push(value)
    }
    var popped: [Int] = []
    while let top = stacks[index].pop() {
        popped.append(top)
    }
    print(popped)
}
```

```output
[3, 2, 1]
[3, 2, 1]
```

Both types keep the promise, so both behave identically from the outside: the last value pushed is the first popped. But they're not equally good. `EndStack` adds and removes at the end of its array, which is O(1). `FrontStack` inserts and removes at the front, which shifts every other element: O(n) per operation.

That's the pattern you'll see throughout the course: **one abstract data type, several possible implementations, different costs.** Choosing the implementation is where the "algorithms" part of DSA comes in.

### Protocols can build on protocols

A protocol can inherit another protocol's requirements and add its own:

```swift
protocol Peekable: IntStack {
    func peek() -> Int?
}
```

A type conforming to `Peekable` must meet all of `IntStack`'s requirements plus `peek()`. The standard library uses this heavily. You'll meet `Comparable`, which builds on `Equatable`, later in this module.

<Callout kind="gotcha" title="Swift gotcha: requirements must match exactly">
A conforming method must match the requirement's name, argument labels and types exactly. `func push(value: Int)` doesn't satisfy `func push(_ value: Int)`, because the labels differ. Swift reports that the type doesn't conform, and its note shows the requirement so you can compare them character by character.
</Callout>
