## Why it matters

An algorithm rarely cares what it's working on. Finding the largest element works the same for numbers, words or clock times; checking for duplicates works the same for anything you can put in a set. **Generics** let you write such an algorithm once and use it with every suitable type, with full type safety and no loss of speed. Swift's own `sorted()`, `max()` and `contains(_:)` are all generic.

## The duplication problem

Here's the largest-number function from the orientation module, followed by a copy for strings:

```swift
func largestInt(_ items: [Int]) -> Int? {
    guard var best = items.first else { return nil }
    for item in items where item > best {
        best = item
    }
    return best
}

func largestString(_ items: [String]) -> String? {
    guard var best = items.first else { return nil }
    for item in items where item > best {
        best = item
    }
    return best
}
```

The bodies are identical. Only the type changed. A third copy for `Double` would follow, then one for every type you write. Copies like these drift apart: fix a bug in one and the others keep it.

## Type parameters

A **generic function** takes a placeholder type, written in angle brackets after its name. Here's a simple one that works for any type at all:

```swift run
func firstAndLast<T>(_ items: [T]) -> (first: T, last: T)? {
    guard let first = items.first, let last = items.last else {
        return nil
    }
    return (first, last)
}

if let ends = firstAndLast([4, 8, 15, 16]) {
    print(ends.first, ends.last)
}
if let ends = firstAndLast(["a", "b", "c"]) {
    print(ends.first, ends.last)
}
```

```output
4 16
a c
```

What to notice:

- `<T>` declares a **type parameter** called `T`. Inside the function, `T` stands for "whatever type the caller uses".
- Swift works out `T` at each call from the arguments: `Int` for the first call, `String` for the second. You never write it yourself.
- `T` is fixed for a single call. Every element must be the same `T`, so the result is a `T` too, not something vaguer.

`T` is a common name for a single type parameter. Descriptive names like `Element` or `Key` are better when there's a meaning to name. Here's another generic function, a swap that works for any type, using `inout` from M05:

```swift run
func swapValues<T>(_ a: inout T, _ b: inout T) {
    let temporary = a
    a = b
    b = temporary
}

var x = 1
var y = 2
swapValues(&x, &y)
print(x, y)

var left = "L"
var right = "R"
swapValues(&left, &right)
print(left, right)
```

```output
2 1
R L
```

## Constraints: what T must be able to do

Now try the largest function with a plain `T`:

```swift
func largest<T>(_ items: [T]) -> T? {
    guard var best = items.first else { return nil }
    for item in items where item > best {
        best = item
    }
    return best
}
```

```text title="What you'll see"
error: binary operator '>' cannot be applied to two 'T' operands
```

Swift is right to complain. `T` could be any type, and not every type can be compared. You need to promise that `T` supports `>`. That's what a **constraint** does: `T: Comparable` means "T can be any type, as long as it conforms to `Comparable`":

```swift run
func largest<T: Comparable>(_ items: [T]) -> T? {
    guard var best = items.first else { return nil }
    for item in items where item > best {
        best = item
    }
    return best
}

struct ClockTime: Comparable {
    var hour: Int
    var minute: Int

    static func < (lhs: ClockTime, rhs: ClockTime) -> Bool {
        (lhs.hour, lhs.minute) < (rhs.hour, rhs.minute)
    }
}

print(largest([3, 9, 4]) ?? 0)
print(largest(["pear", "apple", "zucchini"]) ?? "")
print(largest([2.5, -1.0]) ?? 0)
let latest = largest([ClockTime(hour: 9, minute: 15), ClockTime(hour: 21, minute: 0)])!
print(latest.hour, latest.minute)
print(largest([Int]()) == nil)
```

```output
9
zucchini
2.5
21 0
true
```

One function, four element types, including one you wrote. Because `ClockTime` is `Comparable`, it qualifies automatically. That's the payoff of the previous lessons: protocols say what a type can do, and generics accept every type that can do it.

Notice `[Int]()` in the last line. An empty array literal `[]` would leave Swift no way to work out `T`, so the type is spelled out.

### Choosing the right constraint

Pick the weakest constraint the algorithm actually needs, so the function works with as many types as possible:

| The function needs to… | Constraint |
| --- | --- |
| only store, return or move values | none: `<T>` |
| compare values with `==` | `T: Equatable` |
| order values with `<` or `>` | `T: Comparable` |
| put values in a `Set` or use them as dictionary keys | `T: Hashable` |

For example, checking for duplicates only needs a set:

```swift run
func hasDuplicates<T: Hashable>(_ items: [T]) -> Bool {
    var seen: Set<T> = []
    for item in items {
        if !seen.insert(item).inserted {
            return true
        }
    }
    return false
}

print(hasDuplicates([1, 2, 3, 2]))
print(hasDuplicates(["a", "b", "c"]))
print(hasDuplicates([Character]("hello")))
```

```output
true
false
true
```

This is O(n): one pass with O(1) set operations. A version with two nested loops would be O(n²), but would only need `Equatable`. Constraints and complexity are linked: a stronger promise about the type can unlock a faster algorithm.

## where clauses and combined constraints

Constraints can also go in a **`where` clause** after the signature. These two declarations mean the same thing:

```swift
func largest<T: Comparable>(_ items: [T]) -> T?
func largest<T>(_ items: [T]) -> T? where T: Comparable
```

The `where` form reads better once there are several requirements. Join two protocols with `&` when a type must satisfy both:

```swift run
func sortedUnique<T>(_ items: [T]) -> [T] where T: Hashable & Comparable {
    Array(Set(items)).sorted()
}

print(sortedUnique([5, 1, 5, 3, 1]))
print(sortedUnique(["b", "a", "b"]))
```

```output
[1, 3, 5]
["a", "b"]
```

`Set` needs `Hashable` and `sorted()` needs `Comparable`, so `T` must be both. Sorting also fixes the unpredictable order of the set before printing.

A function can have several type parameters, and a `where` clause can relate them. You'll see that in the associated types lesson, for example "two containers holding the same kind of element".

## You've been using generics all along

| You wrote | Behind it |
| --- | --- |
| `[Int]` | `Array<Int>`: a generic type with `Element` = `Int` |
| `[String: Int]` | `Dictionary<String, Int>` |
| `Int?` | `Optional<Int>` |
| `numbers.max()` | a generic method, available when `Element: Comparable` |
| `items.contains(x)` | a generic method, available when `Element: Equatable` |

Generics aren't slow, either. When you build with optimisation, as in release builds, the compiler usually produces a specialised copy of a generic function for each type it's used with, as fast as writing that copy by hand.

<Callout kind="gotcha" title="Swift gotcha: one T per call">
`largest([1, "a"])` doesn't compile: `error: conflicting arguments to generic parameter 'T' ('String' vs. 'Int')`. A generic function is generic across calls, not within one. Within a single call, every `T` is the same type.
</Callout>
