## Why it matters

You've seen `any Describable` in this module, and if you've glanced at SwiftUI you've seen `some View`. Both put a protocol where a type would go, but they mean different things and behave differently. **`any`** is a box that can hold any conforming type, even a different one each time. **`some`** is one specific type that's kept secret. Choosing well affects what your code can do and how fast it runs.

## The setup

Every example in this lesson uses this protocol and two conforming types:

```swift
protocol Shape {
    func area() -> Double
}

struct Square: Shape {
    var side: Double
    func area() -> Double { side * side }
}

struct Rectangle: Shape {
    var width: Double
    var height: Double
    func area() -> Double { width * height }
}
```

## any: a box for any conforming type

`any Shape` is called an **existential** type. Think of it as a box with a label saying "contains something that conforms to `Shape`". What's inside can be a `Square` today and a `Rectangle` tomorrow:

```swift run
protocol Shape {
    func area() -> Double
}

struct Square: Shape {
    var side: Double
    func area() -> Double { side * side }
}

struct Rectangle: Shape {
    var width: Double
    var height: Double
    func area() -> Double { width * height }
}

var current: any Shape = Square(side: 3)
print(current.area())
current = Rectangle(width: 2, height: 5)
print(current.area())

let mixed: [any Shape] = [Square(side: 1), Rectangle(width: 2, height: 3), Square(side: 2)]
let total = mixed.reduce(0) { $0 + $1.area() }
print(total)
```

```output
9.0
10.0
11.0
```

That flexibility is exactly what `any` is for: a variable whose concrete type changes, or a collection that **mixes** types. It has costs, though:

- **Indirection.** Swift can't know the size of what's in the box, so a large value is stored separately in memory, and every method call is looked up at run time.
- **Lost information.** Through the box, you can only use what the protocol promises. The compiler has forgotten whether it's a square.
- **Some protocols can't be fully used.** A protocol requirement that mentions `Self` or an associated type can't be satisfied through a box, because each box may hold a different type:

```swift
let a: any Equatable = 1
let b: any Equatable = "one"
print(a == b)
```

```text title="What you'll see"
error: binary operator '==' cannot be applied to two 'any Equatable' operands
```

Comparing an `Int` with a `String` makes no sense, and Swift can't rule it out when both are hidden in boxes.

## some: one specific type, kept secret

`some Shape` is called an **opaque** type. It means "one particular type that conforms to `Shape`. The compiler knows exactly which; the code using it doesn't need to."

The most common place is a return type:

```swift run
protocol Shape {
    func area() -> Double
}

struct Square: Shape {
    var side: Double
    func area() -> Double { side * side }
}

func makeTile() -> some Shape {
    Square(side: 4)
}

let tile = makeTile()
print(tile.area())
```

```output
16.0
```

Callers of `makeTile()` know only that they get "some shape". The author can later change it to return a `Rectangle` without breaking any caller. But unlike `any`, there's no box: the compiler knows it's a `Square`, so it stores it directly and calls `area()` directly. That's why SwiftUI's `var body: some View` can describe huge, deeply nested view types without you ever writing them out, and still run fast.

The trade-off is that the type is **fixed**. Every `return` in the function must produce the same concrete type:

```swift
func makeShape(big: Bool) -> some Shape {
    if big {
        return Rectangle(width: 10, height: 5)
    }
    return Square(side: 1)
}
```

```text title="What you'll see"
error: function declares an opaque return type 'some Shape', but the return statements in its body do not have matching underlying types
```

Returning `any Shape` instead would compile, because a box can hold either.

## some in parameters: generics made short

`some` also works for parameters, where it's a shorter way to write a generic function. These two are identical:

```swift
func describe<S: Shape>(_ shape: S) -> String
func describe(_ shape: some Shape) -> String
```

```swift run
protocol Shape {
    func area() -> Double
}

struct Square: Shape {
    var side: Double
    func area() -> Double { side * side }
}

struct Rectangle: Shape {
    var width: Double
    var height: Double
    func area() -> Double { width * height }
}

func describe(_ shape: some Shape) -> String {
    "A shape with area \(shape.area())"
}

print(describe(Square(side: 2)))
print(describe(Rectangle(width: 1, height: 7)))
```

```output
A shape with area 4.0
A shape with area 7.0
```

Each call is specialised for its argument's real type, just like the generic functions earlier in this module. Use the `some` spelling when you don't need to mention the type parameter anywhere else. Use the `<S: Shape>` spelling when you do, for example to say two parameters have the *same* type: `func larger<S: Shape>(_ a: S, _ b: S) -> S`.

### some with an element type

Protocols with associated types can name their main one in angle brackets, which pairs nicely with `some`. A function can promise "some sequence of `Int`s" without revealing which:

```swift run
func evens(upTo limit: Int) -> some Sequence<Int> {
    stride(from: 0, through: limit, by: 2)
}

print(Array(evens(upTo: 10)))
print(evens(upTo: 6).reduce(0, +))
```

```output
[0, 2, 4, 6, 8, 10]
12
```

The caller knows it can loop over `Int`s. The real type, a `StrideThrough<Int>`, stays private. `Sequence<Int>` and `Collection<Int>` work this way.

## Choosing between them

| | `some Shape` | `any Shape` |
| --- | --- | --- |
| What it is | one specific type, hidden | a box holding any conforming type |
| Can the type change? | no, fixed for that function or variable | yes, at any time |
| Mixed types in one array? | no | yes |
| Speed | as fast as the concrete type | an extra lookup per call, maybe a separate allocation |
| Associated types and `Self` | fully usable | limited |

A good rule of thumb: **reach for `some` (or a generic) first, and use `any` when you genuinely need to mix types or swap them at run time.** In DSA code that's rarely needed: a `Stack<Element>` holds one element type, and generic functions are almost always the better tool. You'll meet `any` mostly in app code, for example a list of different kinds of screen.

<Callout kind="gotcha" title="Swift gotcha: older code leaves out any">
Older Swift code writes a bare protocol name as a type, like `let shapes: [Shape]`, meaning `[any Shape]`. Swift still accepts that for most protocols, but an upcoming language feature makes `any` required, and writing it keeps the cost of the box visible. This course always writes `any`.
</Callout>
