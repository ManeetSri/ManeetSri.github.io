## Why it matters

Sets and dictionaries are the workhorses of fast algorithms: "have I seen this before?" and "what's stored for this key?" in O(1) on average. Both need their elements or keys to be **`Hashable`**. `Int` and `String` already are. Once your own types are too, you can keep a set of visited grid cells, count occurrences of custom values, or remember answers you've already worked out.

## What hashing does

A set doesn't search through every element to find one. Instead it computes a **hash value** from the element: a number that acts like an address. That number picks a small group of slots, called a **bucket**, to look in. Finding an element means computing its hash and checking one bucket, which takes about the same time whether the set holds ten elements or ten million.

For that to work, one rule must always hold:

> **If two values are equal, they must have the same hash value.**

Otherwise an element could be stored in one bucket and searched for in another. (Two *different* values may share a hash value. That's called a **collision**, and the set copes with it by comparing elements with `==`.) This is why `Hashable` builds on `Equatable`. You'll learn how hash tables work inside, and how they handle collisions, in Part III.

## Synthesised Hashable

Declare `Hashable` on a struct whose stored properties are all `Hashable`, and Swift writes everything for you, both `==` and the hashing:

```swift run
struct Cell: Hashable {
    var row: Int
    var column: Int
}

var visited: Set<Cell> = []
visited.insert(Cell(row: 0, column: 0))
visited.insert(Cell(row: 0, column: 1))
visited.insert(Cell(row: 0, column: 0))

print(visited.count)
print(visited.contains(Cell(row: 0, column: 1)))
print(visited.contains(Cell(row: 5, column: 5)))
```

```output
2
true
false
```

Inserting `(0, 0)` a second time changed nothing, because a set holds each value once. Enums without associated values are `Hashable` automatically; with associated values, declare it and Swift writes it, as long as those values are `Hashable`.

Dictionaries need `Hashable` keys, so the same struct works as a key:

```swift run
struct Cell: Hashable {
    var row: Int
    var column: Int
}

var stepsTo: [Cell: Int] = [:]
stepsTo[Cell(row: 0, column: 0)] = 0
stepsTo[Cell(row: 1, column: 0)] = 1
stepsTo[Cell(row: 1, column: 1)] = 2

print(stepsTo[Cell(row: 1, column: 1)] ?? -1)
print(stepsTo[Cell(row: 9, column: 9)] ?? -1)
print(stepsTo.count)
```

```output
2
-1
3
```

A dictionary from cells to distances like this is exactly what you'll build in breadth-first search on grids, in Part VI.

<Callout kind="gotcha" title="Swift gotcha: tuples aren't Hashable">
In many languages you'd store grid positions as pairs. In Swift, `Set<(Int, Int)>` doesn't compile: `error: type '(Int, Int)' does not conform to protocol 'Hashable'`. Tuples can't conform to protocols. The fix is the tiny `Hashable` struct you just saw. It costs nothing at run time and reads better too.
</Callout>

## A walk on a grid

Here's a typical use. A robot follows a path of moves; how many different cells does it visit, and where does it first return to a cell it's already been to?

```swift run
struct Cell: Hashable {
    var row: Int
    var column: Int
}

let path = "RRDLUR"
var position = Cell(row: 0, column: 0)
var seen: Set<Cell> = [position]
var firstRevisit: Cell?

for move in path {
    switch move {
    case "U": position.row -= 1
    case "D": position.row += 1
    case "L": position.column -= 1
    default: position.column += 1
    }
    if !seen.insert(position).inserted && firstRevisit == nil {
        firstRevisit = position
    }
}

print("Different cells:", seen.count)
if let cell = firstRevisit {
    print("First revisit: (\(cell.row), \(cell.column))")
}
```

```output
Different cells: 5
First revisit: (0, 1)
```

`insert` returns whether the element was new, so one call both records the cell and tells you if it was a repeat. Checking and recording each cell is O(1), so the whole walk is O(n) for n moves. Searching an array of past cells instead would make it O(n²).

## Writing hash(into:) yourself

Sometimes equality should ignore some properties. Suppose two student records are the same student whenever their ids match, even if one has an outdated nickname. You write `==` to compare ids only, and then you **must** hash only the id too, so that equal students get equal hashes:

```swift run
struct Student: Hashable {
    var id: Int
    var nickname: String

    static func == (lhs: Student, rhs: Student) -> Bool {
        lhs.id == rhs.id
    }

    func hash(into hasher: inout Hasher) {
        hasher.combine(id)
    }
}

let records = [
    Student(id: 7, nickname: "Mo"),
    Student(id: 3, nickname: "Bea"),
    Student(id: 7, nickname: "Mohammed"),
]
let unique = Set(records)
print(unique.count)
print(unique.map { $0.id }.sorted())
```

```output
2
[3, 7]
```

`hash(into:)` receives a `Hasher`, Swift's hashing machine, as an `inout` parameter. You feed it the properties that define equality with `combine`, and it mixes them into a good hash value. You never compute the number yourself. For a type with several identifying properties, call `combine` once for each.

The rule for writing your own: **hash exactly the properties that `==` compares.** If `nickname` were combined too, two equal students could land in different buckets, and the set would wrongly keep both.

## Hash values change between runs

Swift deliberately mixes a random seed into every hash, chosen fresh each time a program starts. That's a security measure against inputs crafted to cause collisions. Two consequences:

- Never store or print `hashValue` expecting it to be the same next time.
- The order of a `Set` or `Dictionary` changes from run to run. Never rely on it. That's why the examples here print counts, single lookups or **sorted** values, never a whole set.
