## Why it matters

Some grids come with order built in: a seating chart sorted by row and by seat, a table of prices that rise with size and with quality, a leaderboard by level and by score. When every row **and** every column is sorted, you can find a value without looking at most of the grid. The **staircase search** does it by starting in the one corner where every comparison tells you something, and throwing away a whole row or column with each step. That style of argument, "each step rules out a chunk of the answer space", is the heart of binary search in Part IV and of the two-pointer pattern in M21.

## A grid sorted both ways

In this grid, every row increases from left to right and every column increases from top to bottom:

```text
 1   4   7  11  15
 2   5   8  12  19
 3   6   9  16  22
10  13  14  17  24
18  21  23  26  30
```

Notice what it doesn't promise: rows don't continue from one another. Row 1 starts at 2, which is smaller than most of row 0. So you can't simply treat the grid as one long sorted list. (A grid where each row *does* start after the previous one ends is easier still: it really is one sorted list, and M28 searches it with binary search.)

The question: is `target` somewhere in the grid?

| Approach | Time for an m × n grid |
| --- | --- |
| check every cell | O(m × n) |
| binary search each row | O(m × log n) |
| staircase search | O(m + n) |

For a 1,000 × 1,000 grid that's a million checks, about ten thousand, or at most 2,000.

## Choosing the right corner

Start at the top-left corner, holding 1, and compare it with a target of 14. It's too small, so you need something bigger. But both directions, right and down, lead to bigger values. There's no way to choose, and no way to rule anything out.

Now start at the **top-right** corner, holding 15. Moving left makes values smaller; moving down makes them bigger. Every comparison now decides something:

- **The value is bigger than the target.** Everything below it in this column is bigger still, because columns increase downwards. So the target can't be anywhere in this column: rule it out and **step left**.
- **The value is smaller than the target.** Everything to its left in this row is smaller still, because rows increase to the right. So the target can't be anywhere in this row: rule it out and **step down**.
- **The value equals the target.** Found it.

Each step discards a whole row or a whole column. The path goes left and down like a flight of stairs, which is where the name comes from.

Looking for **14**:

| --- | --- | --- | --- |
| (0, 4) | 15 | bigger | left |
| (0, 3) | 11 | smaller | down |
| (1, 3) | 12 | smaller | down |
| (2, 3) | 16 | bigger | left |
| (2, 2) | 9 | smaller | down |
| (3, 2) | 14 | equal | found |

Looking for **20**, which isn't there:

| Cell | Value | Compared with 20 | Move |
| --- | --- | --- | --- |
| (0, 4) | 15 | smaller | down |
| (1, 4) | 19 | smaller | down |
| (2, 4) | 22 | bigger | left |
| (2, 3) | 16 | smaller | down |
| (3, 3) | 17 | smaller | down |
| (4, 3) | 26 | bigger | left |
| (4, 2) | 23 | bigger | left |
| (4, 1) | 21 | bigger | left |
| (4, 0) | 18 | smaller | down, off the grid |

The search for 20 stepped off the bottom of the grid, so 20 isn't there. It checked 9 cells out of 25.

### Why it's O(m + n)

Every step either moves down a row or left a column, and never back. There are only m rows to move down through and n columns to move left through, so the walk takes at most m + n − 1 steps before it finds the target or leaves the grid. Each step is one comparison: **O(m + n) time, O(1) space**.

The bottom-left corner works just as well, with the directions swapped: too big, step **up**; too small, step **right**. The other two corners don't work, for the same reason the top-left doesn't.

## The same walk counts too

The staircase isn't only for finding one value. Here's a variation that counts how many cells hold **at most** `target`. For each row, it finds the rightmost column whose value is small enough. Because columns increase downwards, that boundary can only stay put or move left as you go down the rows, so the column index never moves right:

```swift run
// Counts the cells holding at most `target`, walking a staircase from the top-right
func countAtMost(_ target: Int, in grid: [[Int]]) -> Int {
    guard let width = grid.first?.count else { return 0 }
    var column = width - 1
    var count = 0
    for row in grid.indices {
        while column >= 0 && grid[row][column] > target {
            column -= 1          // too big here, so too big in every row below as well
        }
        count += column + 1      // grid[row][0...column] are all at most target
    }
    return count
}

let grid = [
    [1, 4, 7, 11, 15],
    [2, 5, 8, 12, 19],
    [3, 6, 9, 16, 22],
    [10, 13, 14, 17, 24],
    [18, 21, 23, 26, 30],
]
for target in [0, 5, 14, 30] {
    let bruteForce = grid.joined().filter { $0 <= target }.count
    print(target, countAtMost(target, in: grid), bruteForce)
}
```

```output
0 0 0
5 5 5
14 14 14
30 25 25
```

`column` moves left at most n times in total, and the outer loop runs m times, so it's O(m + n) again, even though there's a `while` inside a `for`. That's the same kind of argument as amortised analysis: count the total moves of the inner loop across the whole run, not the worst case of one pass. The brute force, comparing every cell, agrees.

<Callout kind="gotcha" title="Stop before you step off the grid">
The search loop must check `row < grid.count && column >= 0` **before** reading `grid[row][column]`. Stepping left from column 0 or down from the last row takes you outside the grid, and reading there crashes. Put the bounds check in the loop condition so the read only happens while both indices are valid.
</Callout>

<Callout kind="note">
The staircase needs **both** orders. If only the rows are sorted, a value that's too big tells you nothing about the cells below it, and the best you can do is binary search each row. Always check what a problem guarantees before choosing a method.
</Callout>
