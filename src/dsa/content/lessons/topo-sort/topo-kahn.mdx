## Why it matters

Kahn's algorithm is how build systems, package managers and task schedulers actually order their work: start everything that's waiting for nothing, and each time something finishes, see what it has unblocked. It finds a topological order in O(V + E) with nothing more than in-degree counts and a queue, it detects cycles for free, and because it works in waves, it also tells you what could run in parallel. It's the version interviewers expect for "course schedule", and the version to reach for whenever a graph might be large, because it uses no recursion at all.

## The idea: peel off what's ready

[DAGs and dependency ordering](/dsa/learn/topo-dags) showed that every DAG has a vertex with in-degree 0, and that you can put it first. Kahn's algorithm turns that into a loop:

1. Count every vertex's in-degree: how many edges arrive at it, which is how many things it waits for.
2. Put every vertex with in-degree 0 into a queue. They're **ready**.
3. Take a vertex from the queue and append it to the order. Then, for each edge leaving it, subtract 1 from the target's in-degree: one fewer thing to wait for. Any target that reaches 0 has now become ready, so it joins the queue.
4. Repeat until the queue is empty.

Removing a vertex's outgoing edges is done by decrementing counts, so the graph itself never changes. A vertex only joins the queue once **everything** pointing into it has been output, which is exactly what makes the order valid.

<Callout kind="analogy">
Think of getting dressed. Socks, a shirt and trousers wait for nothing, so they're on the "ready" pile. Putting on the shirt and the trousers means the belt is no longer waiting for anything, so it joins the pile. Shoes wait for socks and trousers; once both are on, shoes are ready. You're never stuck holding something you can't put on yet.
</Callout>

## Kahn's algorithm in Swift

With named vertices, a dictionary holds each vertex's outgoing list and in-degree. The `vertices` array keeps the order deterministic, as in [Build `Graph<Vertex: Hashable>`](/dsa/learn/graph-build), and the queue is an array with a head index, as in [A queue with a head index](/dsa/learn/queue-head-index):

```swift run
func topologicalOrder(_ vertices: [String], _ edges: [(String, String)]) -> [String]? {
    var after: [String: [String]] = [:]                 // u → the vertices that wait for u
    var inDegree: [String: Int] = [:]
    for vertex in vertices {
        after[vertex] = []
        inDegree[vertex] = 0
    }
    for (u, v) in edges {
        after[u]!.append(v)
        inDegree[v]! += 1
    }

    var queue = vertices.filter { inDegree[$0] == 0 }   // waiting for nothing
    var head = 0
    var order: [String] = []
    while head < queue.count {
        let vertex = queue[head]
        head += 1
        order.append(vertex)
        for next in after[vertex]! {
            inDegree[next]! -= 1                        // one fewer thing to wait for
            if inDegree[next] == 0 {
                queue.append(next)                      // everything before it is done
            }
        }
    }
    return order.count == vertices.count ? order : nil  // nil: some vertices never became ready
}

let clothes = ["shirt", "tie", "jacket", "trousers", "belt", "shoes", "socks"]
let dressing = [("shirt", "belt"), ("shirt", "tie"), ("tie", "jacket"), ("trousers", "belt"),
                ("trousers", "shoes"), ("belt", "jacket"), ("socks", "shoes")]
print(topologicalOrder(clothes, dressing)!.joined(separator: " → "))
```

```output
shirt → trousers → socks → tie → belt → shoes → jacket
```

Trace the start. Shirt, trousers and socks have in-degree 0, so the queue begins `[shirt, trousers, socks]`. Taking shirt drops belt to 1 and tie to 0, so tie joins. Taking trousers drops belt to 0 (it joins) and shoes to 1. Taking socks drops shoes to 0. And so on: jacket comes last because it waits for both tie and belt.

## Detecting a cycle

If the graph has a cycle, the vertices on it wait for each other forever: none of them ever reaches in-degree 0, so none of them ever joins the queue. Neither does anything downstream of the cycle. The loop runs out of ready vertices early, and **the order comes out shorter than the number of vertices**. That's the check on the `return` line, and it's the whole cycle detector.

The vertices left with a positive in-degree are the stuck ones:

```swift run
func kahn(_ vertices: [String], _ edges: [(String, String)]) -> (order: [String], stuck: [String]) {
    var after: [String: [String]] = [:]
    var inDegree: [String: Int] = [:]
    for vertex in vertices {
        after[vertex] = []
        inDegree[vertex] = 0
    }
    for (u, v) in edges {
        after[u]!.append(v)
        inDegree[v]! += 1
    }
    var order = vertices.filter { inDegree[$0] == 0 }   // the order doubles as the queue
    var head = 0
    while head < order.count {
        let vertex = order[head]
        head += 1
        for next in after[vertex]! {
            inDegree[next]! -= 1
            if inDegree[next] == 0 {
                order.append(next)
            }
        }
    }
    return (order, vertices.filter { inDegree[$0]! > 0 })
}

let steps = ["fetch", "resolve", "compile", "link", "test", "deploy"]
let rules = [("fetch", "resolve"), ("resolve", "compile"), ("compile", "link"),
             ("link", "test"), ("test", "compile"), ("test", "deploy")]
let result = kahn(steps, rules)
print("ordered:", result.order)
print("stuck:", result.stuck)
```

```output
ordered: ["fetch", "resolve"]
stuck: ["compile", "link", "test", "deploy"]
```

Compile, link and test form a cycle (test → compile closes it). Deploy isn't on the cycle, but it waits for test, so it's stuck too. Kahn's algorithm tells you **that** there's a cycle and which vertices are blocked, but not exactly which vertices form the cycle; finding the cycle itself is a job for depth-first search, in the next lesson.

Notice that this version uses the `order` array itself as the queue: everything that enters the queue is output in the same order, so one array does both jobs.

## Why it's O(V + E)

- Building the lists and in-degrees touches each vertex and each edge once: O(V + E).
- Each vertex joins the queue at most once, when its in-degree reaches 0, and is taken out once: O(V).
- Each edge is looked at once, when its starting vertex is taken: O(E).

So the whole algorithm is O(V + E) time and O(V + E) memory, and there's no recursion anywhere, so a chain of a million vertices is no problem.

## The queue doesn't have to be a queue

Correctness only needs "take **some** vertex with in-degree 0". A queue takes them in the order they became ready, which groups the vertices into waves, useful in [Parallel courses and levels](/dsa/learn/topo-parallel-courses). A stack (`popLast()`) takes the most recent one and gives a different, equally valid order.

Sometimes a problem wants one particular order: "if several are possible, return the one that comes first alphabetically", or "smallest number first". Then the container must always hand out the smallest ready vertex, which is a min-heap's job, from [Build a generic `Heap<T>`](/dsa/learn/heap-build):

```swift run
// A compact min-heap of Ints, as in "Build a generic Heap<T>"
struct MinHeap {
    private var items: [Int] = []
    var isEmpty: Bool { items.isEmpty }

    mutating func insert(_ value: Int) {
        items.append(value)
        var child = items.count - 1
        while child > 0 && items[child] < items[(child - 1) / 2] {
            items.swapAt(child, (child - 1) / 2)
            child = (child - 1) / 2
        }
    }

    mutating func pop() -> Int? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        var parent = 0
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var smallest = parent
            if left < items.count && items[left] < items[smallest] { smallest = left }
            if right < items.count && items[right] < items[smallest] { smallest = right }
            if smallest == parent { break }
            items.swapAt(parent, smallest)
            parent = smallest
        }
        return top
    }
}

let n = 6
let edges = [[5, 2], [4, 2], [4, 0], [2, 3], [3, 1]]
var after = Array(repeating: [Int](), count: n)
var inDegree = Array(repeating: 0, count: n)
for edge in edges {
    after[edge[0]].append(edge[1])
    inDegree[edge[1]] += 1
}

// First in, first out
var waiting = inDegree
var queue = (0..<n).filter { waiting[$0] == 0 }
var head = 0
while head < queue.count {
    let vertex = queue[head]
    head += 1
    for next in after[vertex] {
        waiting[next] -= 1
        if waiting[next] == 0 { queue.append(next) }
    }
}
print("queue:   ", queue)

// Smallest ready vertex first
waiting = inDegree
var ready = MinHeap()
for vertex in 0..<n where waiting[vertex] == 0 {
    ready.insert(vertex)
}
var smallestFirst: [Int] = []
while let vertex = ready.pop() {
    smallestFirst.append(vertex)
    for next in after[vertex] {
        waiting[next] -= 1
        if waiting[next] == 0 { ready.insert(next) }
    }
}
print("min-heap:", smallestFirst)
```

```output
queue:    [4, 5, 0, 2, 3, 1]
min-heap: [4, 0, 5, 2, 3, 1]
```

When 4 is taken, vertex 0 becomes ready. The queue puts it behind 5, which was already waiting; the heap hands it out next because it's smaller. The heap version gives the **lexicographically smallest** topological order, at a cost of O(log V) per vertex: O(V log V + E) in all.

<Callout kind="gotcha" title="Common mistakes with Kahn's algorithm">
- **Missing isolated vertices.** If you collect vertices from the edges, a vertex with no edges never appears, never joins the queue, and the "fewer than n" check reports a cycle that isn't there. Start from the full vertex list.
- **`removeFirst()` as the dequeue.** It shifts the whole array: O(V) per call and O(V²) overall, as in [Why removeFirst() is O(n)](/dsa/learn/queue-why-not-removefirst). Use a head index.
- **Treating a short order as an answer.** If the order holds fewer than V vertices, there's no valid order. Return `nil` or `[]`, not the partial list.
- **A `Set` of ready vertices.** It works, but you take them out in an order that changes from run to run, so your output does too. Use an array.
</Callout>
