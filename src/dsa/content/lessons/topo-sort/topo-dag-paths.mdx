## Why it matters

Once a graph is known to be a DAG, problems that are hard or awkward elsewhere become one pass over a topological order. Shortest paths work even with negative weights, which defeat [Dijkstra's algorithm](/dsa/learn/sp-dijkstra). **Longest** paths, a problem with no known efficient solution in general graphs, take O(V + E). And project managers use exactly this to find a project's **critical path**: the chain of tasks that decides the delivery date, where any delay delays everything. The pattern behind all three, "process vertices in topological order and push values along edges", is also how dynamic programming works, which M58 makes explicit.

## Shortest paths: relax edges in topological order

Take a weighted DAG and a source vertex. To find the cheapest path from the source to every vertex:

1. Set the source's distance to 0. Every other distance is unknown.
2. Go through the vertices in topological order. For each vertex u with a known distance, look at every edge `u → v` with weight w: if `distance[u] + w` beats v's current distance, take it. This step is called **relaxing** the edge.

That's the whole algorithm. Why is u's distance already final when you use it? Every path into u arrives along an edge from a vertex that comes **earlier** in the topological order. All of those were processed before u, so every way of reaching u has been tried. By induction, each vertex's distance is final by the time it's processed.

Nothing in that argument cares whether weights are positive. A negative edge, a discount or a refund on one leg, is fine. What breaks shortest paths in general graphs is a **negative cycle**, a loop you could go round forever getting cheaper, and a DAG has no cycles at all.

The cost is a topological sort, O(V + E), plus one look at each edge, O(E): **O(V + E)** in total, better than Dijkstra's O((V + E) log V), and with no priority queue.

## Longest paths: flip the comparison

Change "beats" from smaller to larger, start unknown distances at "nothing found yet", and the same pass finds the **longest** path from the source to every vertex. The proof is the same: by the time you reach u, every path into it has been considered.

That's remarkable, because in a graph with cycles, finding the longest simple path is one of the classic hard problems. It includes, as a special case, asking whether some path visits every vertex exactly once (a Hamiltonian path), and no efficient algorithm is known for that. You can't fix it by negating the weights and running a shortest-path algorithm either: every positive cycle would become a negative cycle. In a DAG there are no cycles, so the hard part never arises.

## Both in Swift

Here's a delivery route where some legs come with a refund, written as negative weights. The topological order comes from Kahn's algorithm, and `previous` remembers which edge gave each vertex its best value, so the path can be read back:

```swift run
let names = ["depot", "A", "B", "C", "D", "port"]
let edges = [[0, 1, 4], [0, 2, 1], [2, 1, 2], [1, 3, 3], [2, 3, 6], [1, 4, 7], [3, 4, -2], [3, 5, 5], [4, 5, 2]]
let n = names.count
var out = Array(repeating: [(to: Int, weight: Int)](), count: n)
var waitingOn = Array(repeating: 0, count: n)
for edge in edges {
    out[edge[0]].append((to: edge[1], weight: edge[2]))
    waitingOn[edge[1]] += 1
}

// A topological order, from Kahn's algorithm
var order = (0..<n).filter { waitingOn[$0] == 0 }
var head = 0
while head < order.count {
    let u = order[head]
    head += 1
    for (v, _) in out[u] {
        waitingOn[v] -= 1
        if waitingOn[v] == 0 { order.append(v) }
    }
}

func bestPaths(from source: Int, longest: Bool) -> (distance: [Int?], previous: [Int?]) {
    var distance = [Int?](repeating: nil, count: n)     // nil: not reached yet
    var previous = [Int?](repeating: nil, count: n)
    distance[source] = 0
    for u in order {
        guard let du = distance[u] else { continue }    // unreachable from the source
        for (v, weight) in out[u] {
            let candidate = du + weight
            let better = distance[v].map { longest ? candidate > $0 : candidate < $0 } ?? true
            if better {
                distance[v] = candidate                 // relax the edge u → v
                previous[v] = u
            }
        }
    }
    return (distance, previous)
}

func route(to target: Int, _ previous: [Int?]) -> String {
    var stops: [String] = []
    var current: Int? = target
    while let vertex = current {
        stops.append(names[vertex])
        current = previous[vertex]
    }
    return stops.reversed().joined(separator: " → ")
}

print("order:", order.map { names[$0] })
let cheapest = bestPaths(from: 0, longest: false)
print("cheapest:", names.indices.map { "\(names[$0]) \(cheapest.distance[$0]!)" })
print("cheapest to port:", route(to: 5, cheapest.previous))
let dearest = bestPaths(from: 0, longest: true)
print("longest to port:", dearest.distance[5]!, "via", route(to: 5, dearest.previous))
```

```output
order: ["depot", "B", "A", "C", "D", "port"]
cheapest: ["depot 0", "A 3", "B 1", "C 6", "D 4", "port 6"]
cheapest to port: depot → B → A → C → D → port
longest to port: 13 via depot → A → D → port
```

What to notice:

- **The cheapest route to the port takes five legs**, because the refund on C → D makes the detour worth it: 1 + 2 + 3 − 2 + 2 = 6.
- **A was improved after it was first reached.** The direct edge gave it 4, then B → A gave 1 + 2 = 3. B comes before A in the topological order, so A's value was final before A passed it on.
- **Unknown distances are `nil`, not `Int.max`.** Adding a weight to `Int.max` would overflow and crash; the gotcha below shows it.
- **One function does both jobs.** The only difference is which candidate counts as better.

## Critical path scheduling

Now put the weights on the vertices: each task takes some number of days, and an edge `u → v` means v can't start until u has finished. With as many people as needed, when can the whole project be finished, and which tasks can't slip?

- **Forward pass, in topological order.** A task's **earliest start** is the latest finish among the tasks it depends on (0 if none). The project's finish is the latest finish of all. This is a longest-path computation: the finish date is the length of the longest chain, measured in days.
- **Backward pass, in reverse topological order.** A task's **latest start** is the latest it can begin without moving the finish date: the earliest of its dependants' latest starts, minus its own duration. A task with no dependants may start as late as `finish - duration`.
- **Slack** is latest start minus earliest start. Tasks with zero slack are **critical**: they form the critical path, and a day lost on any of them is a day lost on the project.

```swift run
let tasks = ["design", "api", "ui", "tests", "docs", "review", "ship"]
let days = [3, 5, 4, 2, 1, 2, 1]
let dependencies = [[0, 1], [0, 2], [1, 3], [2, 3], [0, 4], [3, 5], [4, 5], [5, 6]]   // [before, after]
var next = Array(repeating: [Int](), count: tasks.count)
for pair in dependencies {
    next[pair[0]].append(pair[1])
}
let order = Array(tasks.indices)   // every dependency goes from a lower label to a higher one here

// Forward: the earliest each task can start is when the last of its dependencies finishes
var earliest = Array(repeating: 0, count: tasks.count)
for task in order {
    for after in next[task] {
        earliest[after] = max(earliest[after], earliest[task] + days[task])
    }
}
let finish = tasks.indices.map { earliest[$0] + days[$0] }.max()!

// Backward: the latest each task can start without delaying the finish
var latest = tasks.indices.map { finish - days[$0] }
for task in order.reversed() {
    for after in next[task] {
        latest[task] = min(latest[task], latest[after] - days[task])
    }
}

print("finished after", finish, "days")
for task in tasks.indices {
    let slack = latest[task] - earliest[task]
    let note = slack == 0 ? " (critical)" : ""
    print("\(tasks[task]): starts day \(earliest[task]), slack \(slack)\(note)")
}
```

```output
finished after 13 days
design: starts day 0, slack 0 (critical)
api: starts day 3, slack 0 (critical)
ui: starts day 3, slack 1
tests: starts day 8, slack 0 (critical)
docs: starts day 3, slack 6
review: starts day 10, slack 0 (critical)
ship: starts day 12, slack 0 (critical)
```

The critical path is design → api → tests → review → ship: 3 + 5 + 2 + 2 + 1 = 13 days. The UI work could start a day late, and the docs six days late, without changing anything. If you wanted to ship sooner, speeding up the UI would be wasted effort; only the critical tasks matter. In the backward pass, every dependant of a task comes later in the topological order, so walking the order in reverse finalises them first.

The same pass answers other questions about a DAG. Replace "max of" with "sum of" and it counts the paths from the source to every vertex, because the number of paths into v is the total over its incoming edges. That counting-by-relaxing is the shape of dynamic programming, which Part VII builds on.

<Callout kind="gotcha" title="Swift gotcha: Int.max is not infinity">
It's tempting to start every distance at `Int.max` and relax without checking. The first edge out of an unreachable vertex then computes `Int.max + weight`, and Swift stops the program rather than wrap around:

```text title="What you'll see"
Swift runtime failure: arithmetic overflow
```

Use `nil` for "not reached", as above, and skip vertices whose distance is still `nil`. If you prefer plain Ints, skip any vertex whose distance is `Int.max` before adding a weight. Either way, an unreachable vertex has nothing to pass on.
</Callout>
