## Why it matters

When you build an app, Swift Package Manager compiles each target only after the targets it depends on, and Xcode's build system does the same for every target in a workspace, running independent ones side by side. A university won't let you take a course before its prerequisites. A spreadsheet recalculates a cell only after the cells its formula reads. All of these are the same problem: **put things in an order that respects their dependencies**. The dependencies form a directed graph with no cycles, a **DAG**, and an order that respects every edge is a **topological order**. This module is about finding one, detecting when none exists, and what else becomes easy once you have one.

## Dependencies as edges

Here's a small package, described the way a `Package.swift` would, in plain text:

```text
Target         needs
Models         (nothing)
DesignSystem   (nothing)
Networking     Models
Widgets        Models, DesignSystem
App            Networking, Models, DesignSystem
AppTests       App
```

To make a graph, every target is a vertex, and every "needs" becomes a directed edge. The question is which way the arrow points. This course always draws it from **what must come first** to **what needs it**:

```text
Models ─────────┬──────────> Networking ──┐
   │            │                         v
   │            └─────────────────────>  App ──> AppTests
   v                                      ^
Widgets <──── DesignSystem ───────────────┘
```

So "App needs Models" is the edge `Models → App`. Read an edge `u → v` as "u before v". With that convention, an order is valid when every edge points forwards, and a vertex's **in-degree** is the number of things it waits for.

## Topological order

A **topological order** lists every vertex once, so that for every edge `u → v`, u comes before v. For the package, one valid build order is:

```text
Models, DesignSystem, Networking, Widgets, App, AppTests
```

It's not the only one. DesignSystem doesn't depend on Models, so either can go first; Widgets can go anywhere after both. Most DAGs have many topological orders, and any of them is correct. That's why tests for these problems check the order's properties rather than compare it with one answer.

Checking an order is straightforward: record each vertex's position, then confirm every edge points forwards.

```swift run
// Each target and the targets it needs, as in a Package.swift
let needs: [(target: String, needs: [String])] = [
    ("Models", []),
    ("DesignSystem", []),
    ("Networking", ["Models"]),
    ("Widgets", ["Models", "DesignSystem"]),
    ("App", ["Networking", "Models", "DesignSystem"]),
    ("AppTests", ["App"]),
]

// Edges point from what must come first to what needs it
var edges: [(before: String, after: String)] = []
for (target, requirements) in needs {
    for requirement in requirements {
        edges.append((before: requirement, after: target))
    }
}
print(edges.count, "edges")

func isTopologicalOrder(_ order: [String]) -> Bool {
    let targets = needs.map(\.target)
    guard order.count == targets.count, Set(order) == Set(targets) else { return false }  // each once
    var position: [String: Int] = [:]
    for (index, target) in order.enumerated() {
        position[target] = index
    }
    return edges.allSatisfy { position[$0.before]! < position[$0.after]! }
}

print(isTopologicalOrder(["Models", "DesignSystem", "Networking", "Widgets", "App", "AppTests"]))
print(isTopologicalOrder(["DesignSystem", "Models", "Widgets", "Networking", "App", "AppTests"]))
print(isTopologicalOrder(["Models", "Networking", "App", "DesignSystem", "Widgets", "AppTests"]))

// In-degree: how many targets each one waits for
var inDegree: [String: Int] = [:]
for (target, _) in needs {
    inDegree[target] = 0
}
for edge in edges {
    inDegree[edge.after]! += 1
}
print(needs.map { "\($0.target) \(inDegree[$0.target]!)" })
print("can start straight away:", needs.map(\.target).filter { inDegree[$0] == 0 })
```

```output
7 edges
true
true
false
["Models 0", "DesignSystem 0", "Networking 1", "Widgets 2", "App 3", "AppTests 1"]
can start straight away: ["Models", "DesignSystem"]
```

The third order fails because App comes before DesignSystem, which it needs. And the vertices with in-degree 0, waiting for nothing, are exactly the ones that can go first. Hold on to that: it's the whole idea of the next lesson.

## Why a cycle makes it impossible

Suppose three tasks depend on each other in a ring: A before B, B before C, C before A. Whichever of the three you put first in an order, there's an edge into it from one of the others, which then comes later: an edge pointing backwards. No order works. So:

**A directed graph has a topological order exactly when it has no cycles**, that is, when it's a DAG.

The other half, that every DAG has an order, rests on one fact: **every DAG has at least one vertex with in-degree 0**. Start at any vertex and walk backwards along incoming edges. You can never return to a vertex you've visited, because that would be a cycle. There are only finitely many vertices, so the walk must stop, and it can only stop at a vertex with no incoming edges. Put that vertex first, delete it, and what's left is still a DAG, so it has a source too. Repeat until nothing's left: that's a topological order, and it's exactly how Kahn's algorithm works.

This is also why build tools reject circular dependencies. If you make two Swift package targets depend on each other, SwiftPM refuses to build and reports a cycle, because no build order could exist.

## Where DAGs show up

| Situation | Vertices | An edge u → v means |
| --- | --- | --- |
| Build systems (SwiftPM, Xcode, Make) | targets or files | v needs u to be built first |
| Course planning | courses | u is a prerequisite of v |
| Spreadsheets | cells | v's formula reads u |
| CI pipelines, task schedulers | jobs | v starts after u finishes |
| Git history | commits | v's parent is u |
| Installing packages | packages | v depends on u |

Later in the course, dynamic programming turns out to be computation on a DAG of subproblems, each one depending on smaller ones, solved in a topological order.

## The two algorithms ahead

There are two standard ways to find a topological order, both O(V + E):

- **[Kahn's algorithm](/dsa/learn/topo-kahn)** repeatedly takes a vertex with in-degree 0, outputs it and removes its edges. It uses a queue, like breadth-first search.
- **[Topological sort with DFS](/dsa/learn/topo-dfs)** runs a depth-first search and lists the vertices in reverse order of when they finish.

Both also detect cycles, which is often the actual question: "can every course be completed?" is "is this graph a DAG?". You met cycle detection on its own in [Cycle detection in undirected and directed graphs](/dsa/learn/gt-cycles); this module puts it to work.

<Callout kind="gotcha" title="Which way do the arrows point?">
Problems describe dependencies in both directions: "a depends on b", "b is a prerequisite of a", or a pair `[a, b]` that could mean either. Decide your convention (this course uses "before → after") and convert the input to it on the first line. If you draw the arrows from a target to what it needs instead, every algorithm still works, but its output comes out **reversed**, and an off-by-direction bug is hard to spot because the code looks right.
</Callout>
