## Why it matters

You've now solved seven window problems, and under the details they're the same loop. Writing that loop down once, with the promise it keeps after every step, does two things for you. New window problems become a matter of filling in three blanks. And, more valuable still, you can tell quickly whether a problem is a window problem at all, before you spend twenty minutes forcing one onto it.

## The template

Every variable window in this module has this shape:

```swift
var left = 0
for right in 0..<items.count {
    // 1. Grow: add items[right] to the window's state
    while /* the window is invalid */ {
        // 2. Shrink: remove items[left] from the state
        left += 1
    }
    // 3. Use the window: record a length, a count or a position
}
```

The **state** is whatever lets you judge the window quickly: a sum, a set, a 26-slot count array with a `matches` counter, a dictionary of counts. Choosing it is most of the design work. The rule for choosing: you must be able to update it in O(1) when one element enters or leaves.

## The invariant

Write down what's true after step 2, every time:

> `items[left...right]` is valid, and it's the **longest** valid window that ends at `right`.

Why is it the longest? `left` only moves when the window is invalid. If `items[l...right]` is invalid, then every window that starts at `l` and ends later is invalid too, because adding elements can't fix it. That's the **monotonic** property, and it's why throwing away start `l` forever is safe. So `left` never skips past a start that could still work.

That one sentence explains every recording rule in the module:

| Problem asks for | Shrink while | Record | Lessons |
| --- | --- | --- | --- |
| the longest valid window | invalid | after the loop: `best = max(best, right - left + 1)` | unique run, character replacement |
| the shortest window that reaches a goal | the goal is still reached | inside the loop, before each removal | minimum size subarray, minimum window |
| how many valid windows | invalid | `total += right - left + 1` | at-most-K |
| windows of a fixed size k | (no loop) remove `items[right - k]` once `right ≥ k` | once `right ≥ k - 1` | fixed windows, anagram windows |

The shortest-window row flips the condition because its goal ("sum at least target", "covers the pattern") is monotonic the other way: once reached, growing keeps it reached. So you shrink while it's reached, and every window you see inside the loop is a candidate.

## Filling in the blanks: a new problem

Here's one you haven't seen. A row of fruit trees, each with a fruit type. You have two baskets, each holding one type of fruit. Starting at any tree and walking right, picking one fruit from every tree, how many fruits can you collect before you meet a third type?

In other words: the longest subarray with at most two distinct values. Fill in the template:

- **State:** a dictionary of counts by type.
- **Invalid:** more than two types, `counts.count > 2`.
- **Record:** the longest-window rule.

```swift run
func mostFruit(_ trees: [Int]) -> Int {
    var counts: [Int: Int] = [:]
    var left = 0
    var best = 0
    for right in 0..<trees.count {
        counts[trees[right], default: 0] += 1          // 1. grow
        while counts.count > 2 {                        // invalid: three types
            let leaving = trees[left]                   // 2. shrink
            counts[leaving, default: 0] -= 1
            if counts[leaving] == 0 {
                counts[leaving] = nil
            }
            left += 1
        }
        best = max(best, right - left + 1)              // 3. record
    }
    return best
}

print(mostFruit([1, 2, 1, 3, 3, 2, 2]))
print(mostFruit([4, 4, 4]))
print(mostFruit([]))
```

```output
4
3
0
```

The best walk in the first row is `3, 3, 2, 2`. With the template in hand, the only thinking was choosing the state and the validity test.

## How to spot a window problem

Ask three questions:

1. **Is it about contiguous stretches?** Words like *subarray*, *substring*, *consecutive* or *in a row*. A *subsequence* can skip elements, so it isn't a window.
2. **Is validity monotonic?** Shrinking a valid window keeps it valid (for "longest" and "count"), or growing a goal-reaching window keeps it reaching (for "shortest").
3. **Can you update the state in O(1)** when one element enters or leaves?

Three yeses and it's a window. When one answer is no, here's where to look instead:

| Warning sign | Why the window fails | Try instead |
| --- | --- | --- |
| A sum goal with negative numbers | shrinking can raise the sum | prefix sums with a dictionary (M20) |
| "exactly k" of something | good starts form a middle range | atMost(k) − atMost(k − 1) |
| the maximum or minimum of each window | a maximum can't be undone | a monotonic deque (M27) |
| pairs or triples anywhere in the array | not contiguous | two pointers on sorted data (M21), or hashing |
| "subsequence" | not contiguous | dynamic programming (Part VII) |

<Callout kind="tip" title="Say the invariant out loud">
In an interview, state the invariant before you code: "after each step, the window from left to right is the longest valid window ending at right". It tells the interviewer you know *why* the window works, and it tells you exactly where to put the recording line.
</Callout>
