## Why it matters

Some window rules don't look like windows at first. "What's the longest run of one letter you can make by changing at most k letters?" sounds like a search over which letters to change. The trick is to turn the rule into **arithmetic about the window's counts**, after which it's a standard longest-window problem. This one is an interview favourite because it also contains a famous shortcut that surprises people, and being able to explain why it works shows you understand windows, not only their code.

## The problem

Given a string of uppercase letters and a number k, you may change at most k characters to any letters. Return the length of the longest stretch that can be made all one letter.

For `"QQXQQYQQ"` with k = 1, the answer is 5: change the `X` to get `"QQQQQ"`. With k = 2, change the `X` and the `Y`, and all 8 match.

## Turning "can be fixed" into arithmetic

Pick any window. What's the cheapest way to make it all one letter? Keep its **most common** letter and change everything else. So the cost is:

> cost = window length − count of its most common letter

and the window is valid when that's at most k.

```swift run
func repaintCost(_ window: String) -> Int {
    var counts: [Character: Int] = [:]
    for ch in window {
        counts[ch, default: 0] += 1
    }
    return window.count - (counts.values.max() ?? 0)
}

print(repaintCost("QQXQQ"))
print(repaintCost("QQXQQYQQ"))
print(repaintCost("ABCDE"))
```

```output
1
2
4
```

Is this rule monotonic, the property windows need? Yes. Removing one letter shortens the window by one and lowers the top count by at most one, so the cost can't go up: a smaller window inside a valid one is valid. That means the longest-window shape works: grow on the right, shrink from the left while the window is invalid, record afterwards.

## Simple and safe: one target letter at a time

If you knew which letter the run would end up as, say `Q`, the question becomes: what's the longest window with at most k letters that aren't `Q`? That's the budget window from [Minimum size subarray sum](/dsa/learn/sw-min-size-subarray) with a single counter. There are only 26 possible letters, so try them all:

```swift run
func longestRun(_ text: String, changes k: Int) -> Int {
    let bytes = Array(text.utf8)
    var best = 0
    for target in UInt8(ascii: "A")...UInt8(ascii: "Z") {
        var left = 0
        var others = 0                 // letters in the window that would need changing
        for right in 0..<bytes.count {
            if bytes[right] != target {
                others += 1
            }
            while others > k {
                if bytes[left] != target {
                    others -= 1
                }
                left += 1
            }
            best = max(best, right - left + 1)
        }
    }
    return best
}

print(longestRun("QQXQQYQQ", changes: 1))
print(longestRun("QQXQQYQQ", changes: 2))
print(longestRun("ABCDE", changes: 1))
```

```output
5
8
2
```

That's 26 passes of O(n) each: O(26 · n), which is **O(n)**. It's easy to write and easy to argue is correct, which counts for a lot in an interview.

## One pass with 26 counts

To do it in a single pass, keep 26 counts for the window and test the cost directly. Finding the top count means looking at all 26 slots, which is a constant:

```swift run
func longestRun(_ text: String, changes k: Int) -> Int {
    let bytes = Array(text.utf8)
    let a = UInt8(ascii: "A")
    var counts = [Int](repeating: 0, count: 26)
    var left = 0
    var best = 0
    for right in 0..<bytes.count {
        counts[Int(bytes[right] - a)] += 1
        while (right - left + 1) - counts.max()! > k {
            counts[Int(bytes[left] - a)] -= 1
            left += 1
        }
        best = max(best, right - left + 1)
    }
    return best
}

print(longestRun("BAAAB", changes: 1))
print(longestRun("KAYAK", changes: 2))
```

```output
4
4
```

`counts.max()!` is safe because the array always has 26 elements. Each check scans 26 slots, so this is also O(26 · n).

## The famous shortcut: never lower maxCount

Here's the version you'll see in most write-ups. It keeps a running `maxCount` that only goes **up**, and it shrinks with `if`, not `while`:

```swift run
func longestRun(_ text: String, changes k: Int) -> Int {
    let bytes = Array(text.utf8)
    let a = UInt8(ascii: "A")
    var counts = [Int](repeating: 0, count: 26)
    var maxCount = 0
    var left = 0
    var best = 0
    for right in 0..<bytes.count {
        let slot = Int(bytes[right] - a)
        counts[slot] += 1
        maxCount = max(maxCount, counts[slot])
        if (right - left + 1) - maxCount > k {
            counts[Int(bytes[left] - a)] -= 1
            left += 1
        }
        best = max(best, right - left + 1)
    }
    return best
}

print(longestRun("QQXQQYQQ", changes: 1))
print(longestRun("ABCABCAB", changes: 2))
print(longestRun("", changes: 0))
```

```output
5
4
0
```

When a letter leaves, the real top count might drop, but `maxCount` doesn't. So `maxCount` can be **stale**: bigger than anything currently in the window. Why doesn't that give wrong answers?

1. **The window never shrinks.** Each step it either grows by one (the new letter kept it valid) or slides: `right` and `left` both move, and the length stays the same. So the window's length is always the longest valid length found so far.
2. **A stale `maxCount` only stops shrinking.** It can make the window look valid when it isn't, but then the window slides along at a length that *was* valid earlier. It never reports a longer answer than it has proved.
3. **Growing needs a genuinely bigger count.** The window can only get longer when some letter's count beats the old `maxCount`. At that moment `maxCount` is accurate again, and a longer valid window really exists.

So the answer is right even though the window in the middle of the run might not be a valid one. That's the price of the shortcut: the window no longer means "a valid window", only "a window as long as the best". It's O(n) with no 26-slot scans.

<Callout kind="tip" title="Which one to write in an interview">
Start with the per-letter version or the recompute-the-max version: both are O(n), and you can explain them in a sentence. Mention the `maxCount` shortcut as an optimisation, and explain the three points above if asked. A correct solution you can defend beats a clever one you can't.
</Callout>

## Comparing the three

| Version | Time | Window always valid? |
| --- | --- | --- |
| One target letter at a time | O(26 · n) | yes |
| 26 counts, recompute the max | O(26 · n) | yes |
| 26 counts, `maxCount` never lowered | O(n) | no, but its length is always the best so far |

All three use O(1) extra space: at most 26 counters.

<Callout kind="gotcha" title="Common mistakes">
- **Counting changes as "letters that differ from the first letter".** The cheapest plan keeps the window's *most common* letter, wherever it appears.
- **Treating the shortcut's window as a real answer.** With a stale `maxCount`, the window at the end may need more than k changes; only its length is meaningful. If a problem asks for the stretch itself, record `left` whenever `best` improves: the window only reaches a new record length when `maxCount` is accurate, so it's valid at those moments.
- **Byte arithmetic on lowercase input.** `byte - UInt8(ascii: "A")` gives 0 to 25 only for uppercase letters. Lowercase letters would land in slots 32 to 57 and crash a 26-slot array.
</Callout>
