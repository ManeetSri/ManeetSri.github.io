## Why it matters

Many algorithms work on *part* of an array: the left half in merge sort, the rest of the list in a recursive function, the first `k` elements in a sliding window. Swift lets you take a part of an array without copying it, which is fast. But the part keeps a surprising detail from the original array, its index numbers, and that detail causes some of the most confusing crashes beginners meet in Swift.

## Making a slice

Subscript an array with a **range** instead of a single index, and you get a slice of it:

```swift run
let numbers = [10, 20, 30, 40, 50, 60]
let middle = numbers[2...4]
print(middle)
print(numbers[..<2])
print(numbers[4...])
```

```output
[30, 40, 50]
[10, 20]
[50, 60]
```

- `numbers[2...4]` is indexes 2, 3 and 4.
- `numbers[..<2]` is "from the start up to, but not including, 2".
- `numbers[4...]` is "from 4 to the end".

These one-sided ranges save you from writing `0` or `numbers.count - 1`. Several methods also return slices, and they're safe even when the array is shorter than you asked for:

```swift run
let numbers = [10, 20, 30, 40, 50, 60]
print(numbers.prefix(2))
print(numbers.suffix(2))
print(numbers.dropFirst())
print(numbers.dropLast(2))
print(numbers.prefix(100))
```

```output
[10, 20]
[50, 60]
[20, 30, 40, 50, 60]
[10, 20, 30, 40]
[10, 20, 30, 40, 50, 60]
```

## A slice is a window, not a copy

The slice prints like an array, but it isn't one. Its type is `ArraySlice<Int>`:

```swift run
let numbers = [10, 20, 30, 40, 50, 60]
let middle = numbers[2...4]
print(type(of: middle))
```

```output
ArraySlice<Int>
```

(`type(of:)` asks Swift for a value's type. It's handy for exploring.)

An `ArraySlice` doesn't copy any elements. It **shares the original array's storage** and remembers which part of it to show. That's why making a slice is O(1), constant time, no matter how big it is.

<Callout kind="analogy">
A slice is like highlighting lines 3 to 5 of a document rather than photocopying them. The highlight is instant and costs no paper, but it's still the same document, with the same line numbers.
</Callout>

## The pitfall: a slice keeps the original indexes

Here's the surprise. The slice `numbers[2...4]` doesn't renumber its elements from 0. Its first element is still at index **2**, because that's where it lives in the original array.

```swift run
let numbers = [10, 20, 30, 40, 50, 60]
let middle = numbers[2...4]
print(middle.startIndex, middle.endIndex)
print(middle.indices)
print(middle[2])
```

```output
2 5
2..<5
30
```

- `startIndex` is the index of the first element: 2.
- `endIndex` is one **past** the last element: 5.
- `middle[2]` is the first element, 30.

So code that assumes a slice starts at 0 crashes:

```swift
let numbers = [10, 20, 30, 40, 50, 60]
let middle = numbers[2...4]
print(middle[0])
```

```text title="What you'll see"
Fatal error: Index out of bounds
```

That's what Swift reports. Index 0 belongs to the original array, but it's outside the slice's window, `2..<5`.

### Reading a slice safely

You have three good options:

1. Use `first` and `last`, which don't care about index numbers.
2. Use `startIndex` and `indices` instead of `0` and `0..<count`.
3. Convert the slice to a real array with `Array(slice)`. The new array is renumbered from 0.

```swift run
let numbers = [10, 20, 30, 40, 50, 60]
let middle = numbers[2...4]

print(middle.first ?? -1)
print(middle[middle.startIndex])
for i in middle.indices {
    print(i, middle[i])
}

let fresh = Array(middle)
print(fresh[0], fresh.indices)
```

```output
30
30
2 30
3 40
4 50
30 0..<3
```

`Array(middle)` does copy the elements, so it costs O(k) for k elements. That's usually a price worth paying for code that's simple to reason about.

<Callout kind="tip">
A good rule while you're learning: if you're going to index into a slice with numbers, convert it with `Array(...)` first. If you're only looping over it or reading `first` and `last`, keep the slice.
</Callout>

## Slices and functions

A function that takes `[Int]` won't accept an `ArraySlice<Int>`. They're different types:

```swift
func total(_ numbers: [Int]) -> Int {
    numbers.reduce(0, +)
}
let numbers = [1, 2, 3, 4]
print(total(numbers[1...]))
```

```text title="What you'll see"
error: cannot convert value of type 'Array<Int>.SubSequence' (aka 'ArraySlice<Int>') to expected argument type '[Int]'
```

That's a compile error, not a crash, so Swift catches it before the program runs. Fix it by converting at the call site, `total(Array(numbers[1...]))`. In M10 you'll learn generics, which let one function accept both arrays and slices.

### Recursion on slices

Slices shine in recursion, which you first met in M05. `dropFirst()` on a slice gives a smaller slice in O(1), without copying. Here's a recursive sum:

```swift run
func total(_ numbers: ArraySlice<Int>) -> Int {
    guard let first = numbers.first else { return 0 }
    return first + total(numbers.dropFirst())
}

let numbers = [10, 20, 30, 40]
print(total(numbers[...]))
print(total(numbers[2...]))
```

```output
100
70
```

`numbers[...]` is a slice of the whole array. Notice that the function only uses `first` and `dropFirst()`, never an index number, so the index pitfall can't bite.

## Changing a slice doesn't change the array

A slice shares storage only until you change it. If you modify a `var` slice, Swift quietly makes its own copy first, so the original array is untouched:

```swift run
let numbers = [10, 20, 30, 40, 50, 60]
var window = numbers[2...4]
window[2] = 99
print(window)
print(numbers)
```

```output
[99, 40, 50]
[10, 20, 30, 40, 50, 60]
```

Notice `window[2]`, not `window[0]`: the index rule still applies. You'll see this "share until someone writes" behaviour, called **copy-on-write**, again later in this module and in depth in M09.

<Callout kind="gotcha" title="Swift gotcha: slices keep the whole array alive">
Because a slice shares storage, keeping a tiny slice of a huge array keeps the *entire* array in memory. That's fine inside a function. If you store a slice for a long time, say in a property, convert it with `Array(...)` so the big array can be freed. Strings have exactly the same issue with `Substring`, which you'll meet in M08.
</Callout>
