## Why it matters

Recognition is a skill you build by doing it, many times, on problems that don't tell you their names. This lesson is a training session: ten short problem descriptions in three rounds, each followed by a pause for you to decide, then the pattern, the reasoning, and where the course teaches it. The first round has loud signals, the second is decided by the constraints, and the third is full of false friends: problems that look like one pattern and need another. Don't skim. The value is entirely in committing to an answer before you read on.

## The 60-second routine

Use the same routine on every drill, and later on every problem you meet:

1. **Constraints:** how big is n, and what complexity does that allow? (The table is in [Reading the pattern from constraints and wording](/dsa/learn/pat-recognition).)
2. **Shape:** what is the input really? An array, a string, a grid, a graph in disguise, intervals, a stream?
3. **Question:** what exactly is asked? Longest, shortest, count, fewest, all, kth, possible?
4. **Candidate:** name a pattern and say *which signal* points to it.
5. **Check:** test it against a tiny example, and hunt for a counterexample if it's greedy or a window.
6. **Cost:** state its complexity and compare with step 1.

If step 5 or 6 fails, go back to step 4 with what you learned. A rejected candidate is progress: it tells you which signal you misread.

## Round 1: loud signals

Read all three, decide a pattern for each, then answer the quiz before reading the explanations.

**Drill 1: The commute playlist.** A playlist has up to 100,000 songs, each between 1 and 600 seconds long. Your commute lasts `T` seconds. What's the largest number of *consecutive* songs you can listen to from start to finish during it?

**Drill 2: Waiting for a cold day.** A weather station has recorded up to 100,000 daily temperatures. For each day, how many days do you wait until a strictly colder one (0 if none comes)?

**Drill 3: Distance to the sea.** A map of 1,000 × 1,000 cells marks land and water. For every land cell, find the fewest steps (up, down, left or right) to the nearest water cell.

```quiz

- id: q2
  type: mcq
  prompt: "Drill 2, waiting for a cold day. Which pattern?"
```

### Round 1 explained

**Drill 1** is a **sliding window**. The signals are "consecutive" (contiguous) and positive lengths: adding a song only increases the total, so once a window is too long, every longer window starting at the same song is too. Grow on the right, shrink on the left while the total exceeds `T`, record the length. This is the longest-window row of [A sliding window template](/dsa/learn/sw-template). A prefix-sum array with binary search also works, in O(n log n), but the window is simpler.

**Drill 2** is a **monotonic stack**: "for each element, the next element that's smaller". Days stay on the stack until a colder day arrives, and the stack's temperatures never fall going up. It's the mirror image of [Daily temperatures and stock span](/dsa/learn/stack-temperatures-span), and the four variants are in the table in [Templates: pointers, windows, prefix sums and stacks](/dsa/learn/pat-templates-linear).

**Drill 3** is **multi-source BFS**. "Fewest steps" with equal step costs says BFS, and "to the nearest of many" says start from all of them at once, as in [Multi-source BFS](/dsa/learn/gt-multi-source). The reversal is the insight: instead of asking each land cell to search for water, let the water spread out over the land.

## Round 2: the constraints decide

In this round the story alone doesn't settle it. Read the numbers.

**Drill 4: Two machines.** Two identical machines must run `n` tasks between them, each task on one machine. Task `i` takes `t[i]` minutes. Split the tasks so the two machines finish as close together as possible.
- (a) `n ≤ 20`, and `t[i] ≤ 10⁹`.
- (b) `n ≤ 100`, and `t[i] ≤ 1,000`.

**Drill 5: Score bands.** A school has up to 200,000 exam scores, each up to 10⁹, in no particular order. Then come up to 200,000 questions, each asking how many scores lie between `low` and `high`, inclusive.

**Drill 6: Fire stations.** Up to 100,000 houses stand along a straight road, at positions up to 10⁹. You can build `k` fire stations anywhere on the road. Place them so the largest distance from any house to its nearest station is as small as possible, and report that distance.

### Round 2 explained

**Drill 4** is two problems in one story, and the constraints choose. In **(a)**, n ≤ 20 means 2²⁰ ≈ a million splits, so **try every subset** for one machine, with bitmasks from [Bitmasks for subsets and submasks](/dsa/learn/bits-subsets). The times are huge, so a table over totals is out. In **(b)**, 2¹⁰⁰ is out, but the totals are small: a **subset-sum DP** marks which totals one machine can reach, and the answer comes from the reachable total closest to half. That's [Subset sum and equal partition](/dsa/learn/dpk-subset-sum), and the identical problem in disguise is [Last stone weight II](/dsa/learn/dpk-last-stone). Same story, different numbers, different pattern: this is why you read the constraints first.

**Drill 5** is **sort, then binary search**. Each question is "count values in a range", which is `upperBound(high) - lowerBound(low)` on sorted data, from [Lower bound, upper bound, first and last occurrence](/dsa/learn/bs-bounds). The false friend is the prefix-count array: it's perfect when scores are at most, say, 100, and impossible at 10⁹. If the scores were small, that would be the better answer, with O(1) per question.

**Drill 6** is **binary search on the answer** with a greedy check. "Minimise the maximum" is one of the strongest signals in the course. The check is greedy and O(n) on the sorted houses, and the search over distances up to 10⁹ takes about 30 checks. It's the same shape as [Aggressive cows and magnetic force](/dsa/learn/bsa-aggressive-cows), turned inside out: there you maximise the minimum gap.

## Round 3: false friends

Each of these looks like a pattern you know and needs another. Decide, then read on.

### Drill 7: Freelance gigs

Up to 100,000 gigs are on offer, each with a start time, an end time and a fee. You can't work two gigs that overlap, though one may start exactly when another ends. Which gigs should you take to earn the most?

<Callout kind="tip" title="Decide before you read on">
This looks like an interval problem you've solved before. Is it the same one?
</Callout>

**It's DP with binary search, not the interval greedy.** Sorting by end time and keeping every compatible interval maximises the *number* of intervals, as in [Non-overlapping intervals](/dsa/learn/iv-non-overlapping). Fees change the question: one long, lucrative gig can beat three short ones. Sort by end time. Then `best[i]`, the most money from the first `i` gigs, either skips the `i`th gig or takes it, plus the best from the gigs that end by its start, found with a binary search.

```swift run
// Gigs that can't overlap: the earliest-end greedy against the DP that weighs the fees
typealias Gig = (start: Int, end: Int, fee: Int)

// Greedy: keep every gig that starts after the last kept one ends. Most gigs, not most money.
func greedyFees(_ gigs: [Gig]) -> Int {
    var total = 0
    var lastEnd = Int.min
    for gig in gigs.sorted(by: { $0.end < $1.end }) where gig.start >= lastEnd {
        total += gig.fee
        lastEnd = gig.end
    }
    return total
}

// DP: best[i] is the most money from the first i gigs by end time.
// Gig i - 1 is either skipped, or taken along with the best of the gigs that end by its start.
func bestFees(_ gigs: [Gig]) -> Int {
    let sorted = gigs.sorted { $0.end < $1.end }
    var best = Array(repeating: 0, count: sorted.count + 1)
    for i in 1...sorted.count {
        let gig = sorted[i - 1]
        var low = 0                               // how many gigs end by gig.start: binary search
        var high = i - 1
        while low < high {
            let mid = (low + high) / 2
            if sorted[mid].end <= gig.start { low = mid + 1 } else { high = mid }
        }
        best[i] = max(best[i - 1], gig.fee + best[low])
    }
    return best[sorted.count]
}

let gigs: [Gig] = [(1, 3, 20), (2, 9, 100), (3, 5, 20), (5, 7, 20), (8, 10, 30)]
print("greedy:", greedyFees(gigs), "DP:", bestFees(gigs))
```

```output
greedy: 90 DP: 100
```

The greedy takes four small gigs for 90 and misses the single gig worth 100. The signal to watch for: a *weight* on each interval. Unweighted means greedy; weighted means DP. You'll find the general idea in [DP on DAGs](/dsa/learn/dpa-dags), since gigs ordered by time form a DAG.

### Drill 8: Friend circles, live

A social app has up to 100,000 users. Friendships are added one at a time, up to 200,000 of them, and after each one the app shows how many separate friend circles there are (people linked directly or through friends).

<Callout kind="tip" title="Decide before you read on">
Counting connected groups is a DFS. Is a DFS the right tool here?
</Callout>

**It's union-find.** One DFS counts components in O(V + E), but the question asks after *every* new edge: 200,000 DFS runs over a graph of up to 300,000 vertices and edges is tens of billions of steps. Union-find answers each new edge in near-constant time: if `union` joins two groups, the count drops by one; if they were already together, it stays the same. The signal is "edges added over time, with a question after each". The template is in [Templates: trees, BFS, DFS, topo sort and union-find](/dsa/learn/pat-templates-trees-graphs), and [Islands rising from the sea](/dsa/practice/rising-islands) is the same idea on a grid.

### Drill 9: Passwords without triples

How many passwords of length `n` (up to 100,000) can be made from the letters `a` and `b`, if no letter may appear three times in a row? Give the answer modulo 1,000,000,007.

<Callout kind="tip" title="Decide before you read on">
"Every password with no triple" sounds like generating strings and rejecting the bad ones. Is that what's needed?
</Callout>

**It's DP, not backtracking.** The question asks *how many*, not *list them*, and there are about 1.6ⁿ of them, far too many to list for n = 100,000. What matters about a valid password, for extending it, is only the length of its last run: 1 or 2. That's a two-number state:

```swift run
// Strings of a and b with no letter three times in a row: counted by brute force, then by DP

// Brute force: build every string, keep the valid ones. 2ⁿ strings, so tiny n only.
func countByListing(_ n: Int) -> Int {
    var count = 0
    func build(_ text: [Character]) {
        let k = text.count
        if k >= 3 && text[k - 1] == text[k - 2] && text[k - 2] == text[k - 3] { return }
        if k == n {
            count += 1
            return
        }
        build(text + ["a"])
        build(text + ["b"])
    }
    build([])
    return count
}

// DP: what matters about a valid string is only how long its final run is (1 or 2).
// endsSingle: valid strings ending in a run of 1; endsDouble: ending in a run of 2.
func countByDP(_ n: Int, modulo: Int = 1_000_000_007) -> Int {
    if n <= 1 { return n == 0 ? 1 : 2 }
    var endsSingle = 2                            // "a" and "b"
    var endsDouble = 0
    for _ in 2...n {
        let single = (endsSingle + endsDouble) % modulo   // switch letter: any string can do it
        let double = endsSingle                           // repeat the letter: only after a run of 1
        endsSingle = single
        endsDouble = double
    }
    return (endsSingle + endsDouble) % modulo
}

print((1...8).map(countByListing))
print((1...8).map { countByDP($0) })
print(countByDP(100_000))
```

```output
[2, 4, 6, 10, 16, 26, 42, 68]
[2, 4, 6, 10, 16, 26, 42, 68]
935236457
```

The brute force and the DP agree on every small n, which is how you gain confidence in a recurrence before trusting it on large inputs. The counts are twice the Fibonacci numbers: a disguised [Climbing stairs](/dsa/learn/dp-stairs), where a run of 1 or 2 letters plays the part of a step of 1 or 2. The signals: "how many", a modulus (answers too big for an `Int`), and a rule that only looks back a fixed distance. [Counting with modulo](/dsa/learn/dpa-counting-mod) collects more of these.

### Drill 10: Median heart rate

A fitness app receives up to 100,000 heart-rate readings, one at a time. After each reading it must show the median of all readings so far.

<Callout kind="tip" title="Decide before you read on">
The median is the middle of the sorted readings. So should the app sort?
</Callout>

**It's two heaps.** Sorting after every reading is O(n log n) each time, about 10¹¹ steps in total. Inserting into a sorted array is O(n) per reading because of the shifting: up to about 5 × 10⁹ moves. Two heaps, a max-heap for the lower half and a min-heap for the upper half, keep the middle values on top, so each reading costs O(log n). The signal is "a stream", "after each" and "median", together. Learn it in [Two heaps: median of a stream](/dsa/learn/heap-two-heaps), with the template in [Templates: binary search, intervals and heaps](/dsa/learn/pat-templates-search-sort), and practise it in [Median of a stream](/dsa/practice/stream-median).

## What the false friends have in common

| Drill | Looked like | Was | The signal that gave it away |
| --- | --- | --- | --- |
| 4a | subset-sum DP | try every subset | n ≤ 20 with huge values |
| 5 | prefix counts | sort + binary search | values up to 10⁹ |
| 7 | interval greedy | DP + binary search | a weight on each interval |
| 8 | DFS for components | union-find | a question after every new edge |
| 9 | backtracking | DP | "how many", plus a modulus |
| 10 | sorting | two heaps | a stream, with an answer after each item |

In every case the first idea was a real technique that solves *a* version of the problem. The constraints, or one word in the question, showed it was the wrong version. That's the habit to build: after naming a candidate, ask "what would have to be true for this to work, and is it?"

## Practice

The six problems in this module are drills with tests. Each is told as a story with no hint of its technique, and they cover windows, prefix sums, binary search on the answer, DP, greedy with a heap, and union-find (or binary search with BFS). Give yourself five minutes with the 60-second routine before writing any code, and write your candidate pattern at the top of the file as a comment. Then compare it with the solution's reasoning, whether or not your code passed.

```cards
- id: weighted-intervals
  front: "Most non-overlapping intervals is greedy. What changes when each interval has a value?"
  back: "Maximising total value needs DP: sort by end, then best[i] = max(skip, value + best of the intervals ending by its start), with a binary search for that index."
- id: online-components
  front: "Groups must be counted after each of many added edges. DFS or union-find?"
  back: "Union-find: each edge costs about O(1), and a successful union lowers the count by one. A DFS per edge is O(E · (V + E))."
- id: count-not-list
  front: "A problem asks how many valid strings of length 10⁵ exist, modulo a prime. Backtracking or DP?"
  back: "DP. There are exponentially many to list; find a small state (such as the length of the last run) that's all an extension needs to know."
```
