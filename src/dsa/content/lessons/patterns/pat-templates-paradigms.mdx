## Why it matters

Part VII's paradigms are the tools for problems where you make a **sequence of choices**: which item to add, which coin to use, which house to rob, which pass to buy. Backtracking tries every sequence and undoes its choices. Greedy commits to one choice at each step and never looks back. Dynamic programming notices that different sequences lead to the same situation and solves each situation once. Recognising which of the three a problem needs is the hardest call in this module, so this lesson gives each a template, an invariant, its bugs, and, for greedy and DP, a routine for deciding between them.

## Backtracking: choose, explore, unchoose

**Use it when** the problem asks for **all** solutions (every subset, arrangement, partition or placement), or for any one solution under constraints that rule out a formula, and the input is small: n up to about 20 for subsets, about 10 for orderings. Learn it in [The decision tree and the backtracking template](/dsa/learn/bk-template), then [Subsets](/dsa/learn/bk-subsets), [Permutations](/dsa/learn/bk-permutations), [Combinations](/dsa/learn/bk-combinations) and [N-Queens](/dsa/learn/bk-n-queens).

Every backtracking function has the same skeleton, written here as pseudocode:

```text
func explore(/* where you are in the decision tree */) {
    if /* the partial solution is complete */ {
        record it
        return
    }
    for choice in /* the choices still open */ {
        if /* the choice breaks a rule, or can't lead anywhere */ { continue }   // prune
        make the choice          // choose
        explore(/* one level deeper */)
        undo the choice          // unchoose
    }
}
```

The three shapes you'll meet differ in what "the choices still open" means:

```swift run
// Backtracking, three shapes: a start index, a used array, and skipping duplicates

// Combinations that add up to target, each candidate reusable (start index, pruning by sorting)
func combinationSum(_ candidates: [Int], _ target: Int) -> [[Int]] {
    let sorted = candidates.sorted()
    var result: [[Int]] = []
    var chosen: [Int] = []
    func explore(_ start: Int, _ remaining: Int) {
        if remaining == 0 {
            result.append(chosen)                 // a copy: Swift arrays are values
            return
        }
        for i in start..<sorted.count {
            if sorted[i] > remaining { break }    // sorted, so every later candidate is too big
            chosen.append(sorted[i])              // choose
            explore(i, remaining - sorted[i])     // explore: i, not i + 1, allows reuse
            chosen.removeLast()                   // unchoose
        }
    }
    explore(0, target)
    return result
}

// Every ordering (a used array, because any unused item can come next)
func permutations(_ items: [Int]) -> [[Int]] {
    var result: [[Int]] = []
    var chosen: [Int] = []
    var used = Array(repeating: false, count: items.count)
    func explore() {
        if chosen.count == items.count {
            result.append(chosen)
            return
        }
        for i in items.indices where !used[i] {
            used[i] = true
            chosen.append(items[i])
            explore()
            chosen.removeLast()
            used[i] = false
        }
    }
    explore()
    return result
}

// Subsets when the items repeat: sort, then never start a branch with the same value twice at one level
func distinctSubsets(_ items: [Int]) -> [[Int]] {
    let sorted = items.sorted()
    var result: [[Int]] = []
    var chosen: [Int] = []
    func explore(_ start: Int) {
        result.append(chosen)
        for i in start..<sorted.count {
            if i > start && sorted[i] == sorted[i - 1] { continue }   // same choice as the last branch
            chosen.append(sorted[i])
            explore(i + 1)
            chosen.removeLast()
        }
    }
    explore(0)
    return result
}

print(combinationSum([5, 2, 3], 8))
print(permutations([1, 2, 3]).count, permutations([1, 2, 3]).last!)
print(distinctSubsets([2, 1, 2]))
```

```output
[[2, 2, 2, 2], [2, 3, 3], [3, 5]]
6 [3, 2, 1]
[[], [1], [1, 2], [1, 2, 2], [2], [2, 2]]
```

**The invariant:** `chosen` (with `used`, if any) always describes the path from the root of the decision tree to the current call, and when a call returns, everything it changed has been put back. That's what lets one array serve the whole search.

- **A start index** (`explore(i)` or `explore(i + 1)`) means items are considered in order, so `[2, 3]` and `[3, 2]` aren't both produced. Passing `i` allows reuse of the same item; `i + 1` doesn't.
- **A used array** means any unused item can come next: orderings matter.
- **Sorting plus `i > start && sorted[i] == sorted[i - 1]`** skips a value that was already tried *at this level*, which removes duplicate answers without a set.

**Common bugs:**

- Forgetting to unchoose, so later branches see stale choices.
- `i > 0` instead of `i > start` in the duplicate check, which also skips legitimate repeats deeper down, such as `[1, 2, 2]`.
- `break` when the candidates aren't sorted. Breaking early is only safe when every later choice is at least as bad.
- In languages with reference arrays you must copy `chosen` when recording it. Swift arrays are values, so `result.append(chosen)` stores a snapshot already.

Backtracking is exponential by nature: [Pruning and backtracking complexity](/dsa/learn/bk-pruning) covers how to estimate it and how to cut it down. When n is around 20 and the question asks for a count or a best value rather than every solution, a [bitmask DP](/dsa/learn/dpa-bitmask) over subsets is often the faster cousin.

## Greedy: one safe choice at a time

**Use it when** there's a natural order (by end time, by size, by deadline, by ratio) and taking the locally best option never closes off a better overall answer. Greedy solutions are usually a sort plus one pass: O(n log n). Learn the idea in [The greedy choice property](/dsa/learn/greedy-idea), and how to trust it in [Proving greedy](/dsa/learn/greedy-proofs) and [When greedy fails](/dsa/learn/greedy-counterexamples).

The danger is that a wrong greedy rule *looks* exactly like a right one. So a greedy template comes with a routine:

1. **State the rule** in one sentence: "pair the lightest with the heaviest if they fit", "take the biggest coin that fits".
2. **Try to break it.** Write a brute force or a DP, and compare them on every small input. A loop finds a counterexample in seconds, where staring at the rule might never find one. In an interview, try three or four tiny inputs by hand instead.
3. **If it survives, prove it.** The **exchange argument**: take any optimal answer that differs from the greedy one at the first choice, swap in the greedy choice, and show the answer is no worse. Or **staying ahead**: show that after each step, greedy is at least as far along as any other strategy.

```swift run
// Greedy that works: the fewest boats, each holding at most two people and at most `limit` kilograms
func fewestBoats(_ weights: [Int], limit: Int) -> Int {
    let sorted = weights.sorted()
    var light = 0
    var heavy = sorted.count - 1
    var boats = 0
    while light <= heavy {
        if sorted[light] + sorted[heavy] <= limit {
            light += 1                            // the lightest can share with the heaviest
        }
        heavy -= 1                                // the heaviest always leaves now
        boats += 1
    }
    return boats
}

// Greedy that fails: always take the biggest coin that fits
func greedyCoins(_ coins: [Int], _ amount: Int) -> Int? {
    var left = amount
    var count = 0
    for coin in coins.sorted(by: >) {
        count += left / coin
        left %= coin
    }
    return left == 0 ? count : nil
}

// The DP that's always right: fewest[a] is the fewest coins making a
func dpCoins(_ coins: [Int], _ amount: Int) -> Int? {
    var fewest = Array(repeating: Int.max, count: amount + 1)
    fewest[0] = 0
    if amount > 0 {
        for a in 1...amount {
            for coin in coins where coin <= a && fewest[a - coin] != Int.max {
                fewest[a] = min(fewest[a], fewest[a - coin] + 1)
            }
        }
    }
    return fewest[amount] == Int.max ? nil : fewest[amount]
}

print(fewestBoats([3, 5, 3, 4, 2, 1], limit: 5))

// Test the greedy rule against the DP on every small amount before trusting it
let coins = [1, 3, 4]
let broken = (1...12).filter { greedyCoins(coins, $0) != dpCoins(coins, $0) }
print("greedy is wrong for:", broken)
print("6:", greedyCoins(coins, 6)!, "coins by greedy,", dpCoins(coins, 6)!, "by DP")
```

```output
4
greedy is wrong for: [6, 10]
6: 3 coins by greedy, 2 by DP
```

The boats rule survives because of an exchange argument: the heaviest person needs a boat no matter what, and if anyone can share it, the lightest can, and pairing them never hurts anyone else. The coin rule dies at 6 and 10, found by a two-line loop. Real currencies are designed so that the greedy rule works; arbitrary coin sets aren't.

**The invariant** for a correct greedy is the proof itself: after each step, the choices made so far can be extended to some optimal answer.

**Common bugs:**

- Trusting the rule without step 2.
- Sorting by the wrong key. For "most non-overlapping intervals", sorting by start fails and sorting by end works.
- Using greedy for a problem that's "almost" a known greedy one. Fractional knapsack is greedy by value per kilogram; 0/1 knapsack, where items can't be split, needs DP, as [Activity selection and fractional knapsack](/dsa/learn/greedy-activity-selection) shows.

## Dynamic programming: the recipe

**Use it when** the problem optimises or counts over a sequence of choices, and different choice sequences lead to the **same subproblem**: the same suffix of houses, the same remaining amount, the same pair of string positions. The signals are "number of ways", "minimum cost", "maximum value", "can it be done?", together with a greedy rule that fails. Learn the foundations in [Overlapping subproblems and optimal substructure](/dsa/learn/dp-what-is-dp) and [The DP recipe](/dsa/learn/dp-recipe).

Work through these five questions, in order, on paper before any code:

1. **State.** What does one subproblem look like, and what does its value mean? Write it as a sentence: "`best(i)` is the most money from houses `i` onwards."
2. **Transition.** How does a state's value come from smaller states? List the choices at that state: "skip house `i`, or take it and skip `i + 1`".
3. **Base cases.** Which states can you answer directly? "No houses left: 0."
4. **Order.** In which order can the states be filled so that every dependency is ready? Here, from the last house backwards.
5. **Answer.** Which state, or combination of states, is the final answer? `best(0)`.

Then pick a style. The same recurrence can be written three ways:

```swift run
// One DP three ways: the most you can take from houses in a row, never two neighbours
// State: best(i) = the most from houses i, i + 1, ...  Transition: skip house i, or take it and skip i + 1.

// 1. Top-down: write the recursion, then cache it
func robMemo(_ houses: [Int]) -> Int {
    var memo = Array(repeating: -1, count: houses.count)   // -1: not computed yet
    func best(_ i: Int) -> Int {
        if i >= houses.count { return 0 }                    // base: no houses left
        if memo[i] != -1 { return memo[i] }
        let result = max(best(i + 1), houses[i] + best(i + 2))
        memo[i] = result
        return result
    }
    return best(0)
}

// 2. Bottom-up: the same recurrence, filled in an order where i + 1 and i + 2 are ready first
func robTable(_ houses: [Int]) -> Int {
    let n = houses.count
    var table = Array(repeating: 0, count: n + 2)            // table[n] and table[n + 1] are the base cases
    for i in stride(from: n - 1, through: 0, by: -1) {
        table[i] = max(table[i + 1], houses[i] + table[i + 2])
    }
    return table[0]
}

// 3. Saving space: each cell needs only the two after it
func robRolling(_ houses: [Int]) -> Int {
    var next = 0                                             // table[i + 1]
    var afterNext = 0                                        // table[i + 2]
    for value in houses.reversed() {
        let current = max(next, value + afterNext)
        afterNext = next
        next = current
    }
    return next
}

let street = [6, 1, 2, 7, 3, 1, 5]
print(robMemo(street), robTable(street), robRolling(street))
print(robMemo([]), robTable([4]), robRolling([2, 9, 3]))
```

```output
18 18 18
0 4 9
```

| | Top-down (memo) | Bottom-up (table) |
| --- | --- | --- |
| How you write it | the recursion, plus a cache | loops in a dependency order |
| States computed | only the ones reachable | all of them |
| Risk | deep recursion overflows the stack for large n | getting the fill order wrong |
| Saving space | awkward | often simple: keep only the rows you need |
| Best for | working out the recurrence; sparse or odd-shaped states | large inputs; when speed or memory matters |

A good routine is to find the recurrence top-down, then convert it to a table once it's right, as [Top-down memoisation](/dsa/learn/dp-memoisation), [Bottom-up tabulation](/dsa/learn/dp-tabulation) and [Saving space](/dsa/learn/dp-space) do step by step.

### The loop direction can change the problem

When a 2D table is squashed into one row, the order of the inner loop decides what the old values mean. In the knapsack, going **down** through the capacities means `best[c - w]` hasn't been updated for this item yet, so each item is used at most once. Going **up** lets an item build on itself: unlimited copies.

```swift run
// 0/1 knapsack in one row: the loop direction is the whole difference between "once" and "unlimited"
func bestValue(_ weights: [Int], _ values: [Int], capacity: Int, reuse: Bool) -> Int {
    var best = Array(repeating: 0, count: capacity + 1)      // best[c]: the most value within weight c
    for item in weights.indices {
        let w = weights[item]
        guard w <= capacity else { continue }
        // Downwards: best[c - w] still means "without this item", so each item is used at most once.
        // Upwards: best[c - w] may already include this item, so it can be taken again and again.
        let capacities = reuse ? Array(w...capacity) : Array((w...capacity).reversed())
        for c in capacities {
            best[c] = max(best[c], best[c - w] + values[item])
        }
    }
    return best[capacity]
}

let weights = [2, 3, 4]
let values = [3, 5, 6]
print("each item once:", bestValue(weights, values, capacity: 6, reuse: false))
print("unlimited copies:", bestValue(weights, values, capacity: 6, reuse: true))
```

```output
each item once: 9
unlimited copies: 10
```

Both loops compile, both run, and only one answers the question. [0/1 knapsack, from 2D to 1D](/dsa/learn/dpk-01) and [Unbounded knapsack](/dsa/learn/dpk-unbounded) build the two versions from their tables.

**Common bugs:**

- A state that's missing information. If two situations with the same state need different answers, the state needs another dimension, such as "holding a stock or not" in [From state diagrams to transitions](/dsa/learn/dpsm-state-diagrams).
- A sentinel that collides with a real answer, such as `0` meaning "not computed" when 0 is a valid result. Use `-1`, an optional, or a separate `Bool` array.
- Top-down recursion 10⁵ calls deep. Switch to the table.
- An off-by-one table size. Leave room for the base cases (`n + 1` or `n + 2` cells), as `robTable` does.

## The DP families

Most DP problems belong to a family, and the family tells you the state. When you recognise one, start from its usual state and adjust:

| Family | Usual state | Signals | Learn it in |
| --- | --- | --- | --- |
| linear | `dp[i]`: best for the first `i` items, or from `i` on | a row of houses, steps, days | [House robber](/dsa/learn/dp-house-robber), [Decode ways](/dsa/learn/dp-decode-squares) |
| grid | `dp[r][c]`: best way to reach a cell | moving right or down on a grid | [Unique paths](/dsa/learn/dpg-unique-paths), [Minimum path sum](/dsa/learn/dpg-min-path-sum) |
| knapsack | `dp[c]`: best within capacity or sum `c` | items with weights, a target sum, small totals | [0/1 knapsack](/dsa/learn/dpk-01), [Coin change](/dsa/learn/dpk-coin-change) |
| two strings | `dp[i][j]`: answer for prefixes of both | edit, match, common subsequence | [LCS](/dsa/learn/dps-lcs), [Edit distance](/dsa/learn/dps-edit-distance) |
| increasing subsequence | `dp[i]`: best ending at `i`, or the patience piles | "increasing", chains, nesting | [LIS in O(n log n)](/dsa/learn/lis-n-log-n) |
| intervals | `dp[l][r]`: best for the range `l...r` | merging, splitting, bursting, n ≤ 500 | [Matrix chain multiplication](/dsa/learn/dpi-matrix-chain) |
| state machine | `dp[i][state]`: best on day `i` in each state | holding or not, cooldowns, limits on actions | [State diagrams](/dsa/learn/dpsm-state-diagrams) |
| bitmask | `dp[mask][last]`: best over a set of items used | n ≤ 20, visit or assign everything | [Bitmask DP](/dsa/learn/dpa-bitmask) |
| trees | a value per node, from its children | choices at every node of a tree | [DP on trees](/dsa/learn/dpa-trees) |

<Callout kind="note" title="And divide and conquer?">
Divide and conquer also splits a problem into smaller ones, but the pieces **don't overlap**: merge sort's two halves share nothing, so there's nothing to cache. If you split a problem and find yourself solving the same piece twice, it's DP; if each piece is new, it's divide and conquer, from [Divide, conquer, combine](/dsa/learn/dc-paradigm).
</Callout>

## Deciding between the three

| The question | First try |
| --- | --- |
| "list every …", "all possible …" | backtracking |
| a natural order and a rule you can't break on small cases | greedy, then prove it |
| "how many ways", "minimum", "maximum", "is it possible", and greedy breaks | DP |
| "how many ways" or "best", but n ≤ 20 and the state is a set | bitmask DP |
| any of these, and you're unsure | brute force first, then look for repeated work (DP) or a safe rule (greedy) |
