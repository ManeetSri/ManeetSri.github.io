## Why it matters

From Part III to Part VII, every technique arrived in a module named after it, so you always knew which tool the problems wanted. Real problems don't come labelled. An interviewer describes ovens, playlists or flooded fields, and the first few minutes go on working out *what kind* of problem it is. Get that right and the rest is a template you already know. Get it wrong and you spend half an hour forcing a sliding window onto something that needed prefix sums. This lesson gives you two fast filters, **the constraints** and **the wording**, a flowchart that combines them, and six worked examples. The [Pattern chooser](/dsa/sheets/patterns) cheat sheet is the one-page summary; this lesson is the reasoning behind it.

## Filter 1: the constraints

Read the limits before the story. They tell you how fast the solution has to be, and that alone rules out most techniques. The rule of thumb from [From n to a feasible complexity](/dsa/learn/bigo-feasibility-table) is about 10⁸ simple steps per second, and problem setters pick their limits so that the intended complexity fits and the obvious slower one doesn't.

| Largest input | Budget allows | Patterns this points to |
| --- | --- | --- |
| n ≤ 10 | O(n!) | try every ordering: permutations, backtracking |
| n ≤ 20 | O(2ⁿ · n) | every subset: backtracking, bitmask enumeration, bitmask DP |
| n ≤ 100 | O(n³) or O(n⁴) | several nested loops, small DP tables |
| n ≤ 500 | O(n³) | interval DP, Floyd–Warshall, triple loops |
| n ≤ 5,000 | O(n²) | all pairs, 2D DP (two strings, LIS the slow way) |
| n ≤ 10⁵ to 10⁶ | O(n log n) or O(n) | sorting, binary search, heaps, one pass with a window, prefix sums or hashing, BFS/DFS, union-find |
| a single number up to 10⁹–10¹⁸ | O(log n) or O(√n) | binary search on the answer, maths, fast power |

Do the arithmetic rather than guessing. It takes seconds:

```swift run
// Rough step counts for the usual complexity classes, to compare against a budget of about 10⁸
import Foundation

func steps(_ n: Double) -> [(String, Double)] {
    [("n", n), ("n log n", n * log2(n)), ("n²", n * n), ("2ⁿ", pow(2, n))]
}

for n in [20.0, 5_000, 100_000] {
    let fits = steps(n).filter { $0.1 <= 1e8 }.map { $0.0 }
    print("n = \(Int(n)): fits \(fits.joined(separator: ", "))")
}
```

```output
n = 20: fits n, n log n, n², 2ⁿ
n = 5000: fits n, n log n, n²
n = 100000: fits n, n log n
```

What to notice:

- **n ≤ 20 is a loud signal.** Nobody sets such a small limit unless exponential time is the point. Think "try every subset", then [Bitmasks for subsets](/dsa/learn/bits-subsets) or [Bitmask DP](/dsa/learn/dpa-bitmask).
- **n up to 10⁵ rules out O(n²)**, so it rules out "check every pair" and "check every subarray". You need one pass, a sort, or a structure that answers each question in O(log n).
- **A single huge number** (a capacity, a deadline, a count up to 10¹²) can't be looped over. If the question is "the smallest value that works", that's [binary search on the answer](/dsa/learn/bsa-idea).

The other numbers in the constraints matter too:

- **Value ranges.** Values up to 10⁹ mean you can't make an array indexed by value: use sorting or a dictionary. Values up to 10⁴ might allow a counting array, or a DP over sums as in [Subset sum and equal partition](/dsa/learn/dpk-subset-sum).
- **Negative values.** They break sliding windows on sums and Dijkstra on graphs. Look for them every time.
- **Two sizes that multiply.** A grid with rows × cols ≤ 10⁶ has a million cells, so each can be visited only a few times. 10⁵ items with 10⁵ queries means no query can scan the items, so you'll prepare something up front.

## Filter 2: the wording

Once the constraints have narrowed the field, the words of the question usually point at one family. These are the strongest signals:

| The question says… | Think of | Learn it in |
| --- | --- | --- |
| "contiguous", "subarray", "substring", "consecutive days" | sliding window, or prefix sums | [Sliding window template](/dsa/learn/sw-template), [Prefix sums](/dsa/learn/prefix-1d) |
| "subarray sum equals k", with negatives allowed | prefix sums + dictionary | [Prefix sum + hashmap](/dsa/learn/prefix-hashmap) |
| "sorted array", "pair with sum", "palindrome" | two pointers, or binary search | [Opposite ends](/dsa/learn/tp-opposite-ends), [Binary search](/dsa/learn/bs-classic) |
| "smallest x such that …", "minimise the maximum" | binary search on the answer | [The monotonic predicate idea](/dsa/learn/bsa-idea) |
| "next greater", "previous smaller", "span" | monotonic stack | [Monotonic stack](/dsa/learn/stack-monotonic-intro) |
| "kth largest", "top k", "k closest" | heap of size k, or quickselect | [Top K](/dsa/learn/heap-top-k), [Quickselect](/dsa/learn/sort-quickselect) |
| "intervals", "meetings", "bookings", "overlap" | sort, then sweep | [Merge intervals](/dsa/learn/iv-merge-insert), [Sweep line](/dsa/learn/iv-sweep-line) |
| "shortest", "fewest moves", every step costing the same | BFS | [BFS](/dsa/learn/gt-bfs) |
| "cheapest route", with costs on the edges | Dijkstra (Bellman–Ford if negative) | [Choosing a shortest-path algorithm](/dsa/learn/sp-choosing) |
| "prerequisites", "dependencies", "build order" | topological sort | [Kahn's algorithm](/dsa/learn/topo-kahn) |
| "connected groups", "friend circles", "merge accounts" | union-find, or DFS | [Union-find](/dsa/learn/uf-provinces), [Components](/dsa/learn/gt-components) |
| "connect everything at minimum cost" | minimum spanning tree | [Kruskal](/dsa/learn/mst-kruskal) |
| "all combinations", "every arrangement", "list all" | backtracking | [The backtracking template](/dsa/learn/bk-template) |
| "number of ways", "minimum cost", "maximum profit" over a sequence of choices | dynamic programming | [The DP recipe](/dsa/learn/dp-recipe) |
| "longest increasing subsequence", "subsequence" of any kind | DP (not a window: subsequences skip) | [LIS](/dsa/learn/lis-quadratic), [LCS](/dsa/learn/dps-lcs) |
| "the most you can do", with a choice that looks obviously best | greedy, after a proof | [Proving greedy](/dsa/learn/greedy-proofs) |
| "prefix", "starts with", many words | trie | [Tries](/dsa/learn/trie-build) |

Two words deserve care. **"Minimum"** and **"maximum"** appear in DP, greedy, BFS and binary-search problems alike, so they never decide the pattern alone: ask *minimum of what, over what*. And **"subsequence"** versus **"subarray"** is the difference between DP and a window, as [Subarray vs subsequence vs subset](/dsa/learn/arrays-sub-definitions) showed.

## A flowchart

Put the two filters together and you get a short series of questions. Ask them in order and stop at the first yes. It won't catch everything, but it gets most problems to the right family in under a minute:

```text
1. Is the input tiny (n ≤ 20)?
     yes → try everything: backtracking, bitmasks, bitmask DP
2. Is it a graph, a grid or a tree, even in disguise?
     yes → name the vertices and edges, then use the graph table
           (BFS, DFS, topological sort, union-find, Dijkstra, MST)
3. Is it about contiguous stretches of an array or string?
     yes → is validity monotonic? sliding window
           sums with negatives, or "exactly k"? prefix sums + dictionary
4. Is the input sorted, or would sorting it help?
     yes → two pointers, binary search, or sort + sweep (intervals)
5. Is the answer a number where "x works" means "bigger x works"?
     yes → binary search on the answer
6. Does it ask for the kth, the top k, or a running minimum or maximum?
     yes → heap, quickselect, monotonic stack or deque
7. Is it choosing a sequence of options to optimise or count?
     list them all → backtracking
     a local choice you can prove safe → greedy
     otherwise → dynamic programming
8. None of these?
     write the brute force, then ask which work it repeats
```

Step 2 hides a whole table of its own: [Which graph algorithm when](/dsa/learn/ag-which-algorithm) is the version for graphs. Step 7 is the hardest, because greedy and DP problems look alike. The test is to hunt for a counterexample to the greedy rule on a small input. If you find one in a couple of minutes, it's DP. If you can't, try to prove the rule with an exchange argument.

## Six worked examples

Each example shows the thinking in the order you'd do it: constraints, wording, a candidate, and a check.

### 1. Transactions that net to zero

> A bank has a list of up to 200,000 transactions, positive and negative. How many stretches of consecutive transactions add up to exactly zero?

- **Constraints:** 2 × 10⁵ items, so O(n log n) or better; checking every stretch is O(n²), too slow.
- **Wording:** "consecutive" means contiguous. That suggests a window *or* prefix sums.
- **Check:** the values can be negative, so adding a transaction can raise or lower the sum. A window's validity isn't monotonic, and the window is out.
- **Pattern:** prefix sums with a dictionary counting each prefix value, from [Prefix sum + hashmap](/dsa/learn/prefix-hashmap). A stretch nets to zero when two prefix sums are equal.

### 2. Installing packages

> A package manager must install 10,000 packages. Each package lists the packages it needs installed first. Give an install order, or report that the requirements go round in a circle.

- **Wording:** "needs installed first" is a dependency, and "go round in a circle" is a cycle. Packages are vertices; "a before b" is a directed edge.
- **Pattern:** topological sort with [Kahn's algorithm](/dsa/learn/topo-kahn), which detects the cycle for free: if the order comes out shorter than the number of packages, there's a cycle.

### 3. The combination lock

> A lock has four wheels, each showing 0 to 9. One move turns one wheel by one step, either way, and 9 wraps round to 0. Some combinations jam the lock and must be avoided. What's the fewest moves from 0000 to the code?

- **Constraints:** only 10⁴ combinations exist, so visiting every one is cheap.
- **Wording:** "fewest moves", and every move costs the same.
- **Pattern:** BFS over states. Each combination is a vertex with eight neighbours. Nothing in the statement says "graph", which is exactly why it's worth asking at step 2 of the flowchart. [State-space BFS](/dsa/learn/gt-state-space) solves this shape.

### 4. Trending searches

> A search engine logged 10⁶ queries today. Show the 10 most frequent.

- **Wording:** "most frequent" means counting, and "the 10 most" is top k.
- **Pattern:** a dictionary of counts, then a min-heap of size 10 that keeps only the best seen so far: O(n log k), as in [Top K](/dsa/learn/heap-top-k). Sorting all the distinct queries works too, but costs O(n log n) for an answer of 10 items.

### 5. Splitting a sentence into words

> Given a string with the spaces removed and a dictionary of words, (a) can the string be split into dictionary words? (b) list every way to split it.

The same story with two questions, and they need different patterns.

- **(a)** asks yes or no, and the same suffix of the string gets examined again and again by different splits. Overlapping subproblems: **DP**, as in [Word break](/dsa/learn/dps-word-break).
- **(b)** asks to *list* them all, and there can be exponentially many. No DP table helps when the output itself is huge: **backtracking**, from [The backtracking template](/dsa/learn/bk-template), ideally pruned with the DP answer from (a).

"Can it?" and "how many?" point to DP. "List them all" points to backtracking.

### 6. Change from a vending machine

> A machine has coins of values `[1, 3, 4]` and must pay out 6. What's the fewest coins?

- **Wording:** "fewest coins" sounds greedy: always take the biggest coin that fits.
- **Check:** greedy takes 4, then 1, then 1: three coins. But 3 + 3 is two. A counterexample in thirty seconds.
- **Pattern:** DP over amounts, from [Coin change I and II](/dsa/learn/dpk-coin-change). Greedy works for some coin systems, such as real currencies, but not for all, and [When greedy fails](/dsa/learn/greedy-counterexamples) collects more traps like this one.

<Callout kind="gotcha" title="Recognition traps">
- **Stopping at the first match.** "Longest substring" suggests a window, but check validity is monotonic before you commit. Negative numbers, "exactly k" and "subsequence" all break it.
- **Ignoring the constraints.** If n ≤ 15, the intended solution is almost certainly exponential, however clever a polynomial idea looks.
- **Simulating when the numbers are huge.** A story about ovens or days invites a step-by-step simulation. With counts up to 10¹², simulation is out: look for a formula or a binary search.
- **Missing the graph.** Words, lock combinations, grid cells and game positions are all vertices. "Fewest moves" in any of them is BFS.
- **Trusting greedy without a check.** Spend two minutes trying to break it on a tiny input before you code it.
</Callout>

## Practice

The three problems below hide their patterns in stories, on purpose. For each one, read the constraints first, write down the pattern you think it is and why, and only then start coding. If your first idea fails on an example, that's useful too: say which signal you misread.

```cards
- id: two-filters
  front: "What two filters narrow down a problem's pattern, and in which order?"
  back: "The constraints first, which set the complexity budget and rule most techniques out; then the wording, which points at a family."
- id: n-twenty
  front: "What does n ≤ 20 in the constraints usually mean?"
  back: "Exponential time is intended: try every subset or ordering with backtracking, bitmask enumeration or bitmask DP."
- id: window-or-prefix
  front: "A problem asks about contiguous subarrays. How do you choose between a sliding window and prefix sums?"
  back: "A window needs validity to be monotonic. Sums with negative values, or \"exactly k\" conditions, break that, so use prefix sums with a dictionary."
- id: list-vs-count
  front: "\"How many ways?\" versus \"list every way\": which patterns?"
  back: "Counting (or yes/no, or best value) with overlapping subproblems is DP. Listing every solution is backtracking, because the output itself can be exponential."
```
