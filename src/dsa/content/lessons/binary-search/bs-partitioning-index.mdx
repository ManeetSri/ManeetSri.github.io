## Why it matters

Every lesson in this module rewrote the same loop, and each rewrite was a fresh chance for an off-by-one bug. In real code you'd rather call one well-tested function. Swift's standard library doesn't have one, but Apple's **swift-algorithms** package does: `partitioningIndex(where:)`, the "first index where a condition becomes true" search from [Lower bound, upper bound, first and last occurrence](/dsa/learn/bs-bounds), written once, generically, for any collection. This lesson shows what it promises, how to add the package to a project, how to write the same thing yourself, and the version waiting for you in DSAKit.

## What partitioningIndex does

A collection is **partitioned** by a yes/no question when every element that answers no comes before every element that answers yes:

```text
scores:           12   31   48   50   77   91
score >= 50?      no   no   no   yes  yes  yes
                                  ^
                     partitioningIndex { $0 >= 50 } is 3
```

`partitioningIndex(where:)` returns the index of the **first yes**, or `endIndex` if every element says no. Its parameter is named `belongsInSecondPartition`: the yes elements form the second part.

Three things to know about it:

- **The collection must already be partitioned** by your predicate. It doesn't check. If the answers aren't no…no yes…yes, you get an index, but not a meaningful one.
- **It's O(log n) on a `RandomAccessCollection`** such as `Array`, `ArraySlice` or a `Range` of integers. It's declared for any `Collection` and still gives the right answer there, but on collections that can't jump to an index in O(1), like a `String`, moving to the middle costs O(n).
- **It `rethrows`**: if your predicate can throw, so can the call, and if it can't, you don't write `try`.

It's not the same as `partition(by:)`, which *is* in the standard library. `partition(by:)` reorders a mutable collection so that the yes elements end up at the back, and returns where they start. `partitioningIndex(where:)` changes nothing: it finds that point in a collection that's already in order. Sorted data is partitioned by any question like "is it at least x?", so lower and upper bounds come straight out of it:

```swift
import Algorithms

let scores = [12, 31, 48, 50, 50, 77, 91]
let lower = scores.partitioningIndex { $0 >= 50 }     // 3: the first 50
let upper = scores.partitioningIndex { $0 > 50 }      // 5: the first score above 50
let count = upper - lower                              // 2 scores of exactly 50
let none = scores.partitioningIndex { $0 > 100 }      // 7: endIndex, nothing qualifies
```

## Adding swift-algorithms to a project

swift-algorithms isn't part of Swift itself; it's a package you add. In an Xcode app project, choose **File ▸ Add Package Dependencies…**, paste `https://github.com/apple/swift-algorithms`, and add the **Algorithms** library to your app target. In a Swift package, list it in `Package.swift`:

```swift
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "Leaderboard",
    dependencies: [
        .package(url: "https://github.com/apple/swift-algorithms", from: "1.2.0"),
    ],
    targets: [
        .executableTarget(
            name: "Leaderboard",
            dependencies: [
                .product(name: "Algorithms", package: "swift-algorithms"),
            ]
        ),
    ]
)
```

`from: "1.2.0"` accepts version 1.2.0 or any later 1.x release. Then `import Algorithms` in any file of that target. The package came up in Part III as the home of `rotate(toStartAt:)` and `permutations()`.

Each runnable example in this course is a single file that runs with `swift file.swift`, and a single file can't import a package. So the examples below write their own version. In the companion package, and in your own apps, you can use the real thing.
</Callout>

## Writing your own

Here's the same search as a generic extension. It works on anything random-access, and it never assumes indexes start at 0 or are plain `Int` offsets: it moves with `index(_:offsetBy:)` and keeps a **count** of the candidates left, the way swift-algorithms does.

```swift run
extension RandomAccessCollection {
    /// The index of the first element that satisfies the predicate, or endIndex if none does.
    /// The collection must be partitioned: every false before every true. O(log n).
    func partitionPoint(where belongsInSecondPartition: (Element) -> Bool) -> Index {
        var low = startIndex
        var remaining = count                    // the candidates are [low, low + remaining)
        while remaining > 0 {
            let half = remaining / 2
            let middle = index(low, offsetBy: half)
            if belongsInSecondPartition(self[middle]) {
                remaining = half                 // middle could be the first true: keep it
            } else {
                low = index(after: middle)       // middle and everything before it are false
                remaining -= half + 1
            }
        }
        return low
    }
}

let scores = [12, 31, 48, 50, 50, 77, 91]
print(scores.partitionPoint { $0 >= 50 }, scores.partitionPoint { $0 > 50 }, scores.partitionPoint { $0 > 100 })

let tail = scores[2...]                          // a slice: its indexes are 2 to 6
print(tail.startIndex, tail.partitionPoint { $0 >= 50 })

let firstBigSquare = (0..<1_000_000).partitionPoint { $0 * $0 >= 500_000_000 }
print(firstBigSquare)

let names = ["Ana", "Ben", "Cleo", "Dev", "Eli"]
print(names.partitionPoint { $0 >= "C" })
```

```output
3 5 7
2 3
22361
2
```

What to notice:

- **Slices keep their parent's indexes.** `tail` starts at index 2, and the answer is 3, the same position as in `scores`, not 1. As [ArraySlice and its index pitfalls](/dsa/learn/swift-array-slices) warned, code that assumed a slice starts at 0 would get this wrong; code that uses `startIndex` and `index(_:offsetBy:)` can't.
- **A `Range` is a collection of answers.** `0..<1_000_000` is random-access, so the search finds the first number whose square reaches 500,000,000 in about 20 steps, without building an array. That's binary search on the answer, the heart of M29, in one line.
- **Any element type works**: the predicate on `names` compares strings.

Try calling it on a `String` and the compiler refuses: `String` isn't a `RandomAccessCollection`, so the method doesn't exist for it. The type system is guarding the O(log n) promise. Use `Array(text)` first, as in [Binary search, iterative and recursive](/dsa/learn/bs-classic).

## When the collection isn't partitioned

Nothing stops you from passing a predicate that isn't partitioned. You get a wrong answer instead:

```swift run
extension RandomAccessCollection {
    func partitionPoint(where belongsInSecondPartition: (Element) -> Bool) -> Index {
        var low = startIndex
        var remaining = count
        while remaining > 0 {
            let half = remaining / 2
            let middle = index(low, offsetBy: half)
            if belongsInSecondPartition(self[middle]) {
                remaining = half
            } else {
                low = index(after: middle)
                remaining -= half + 1
            }
        }
        return low
    }
}

let numbers = [1, 2, 3, 4, 5, 6, 7]
print(numbers.partitionPoint { $0 == 2 })        // not partitioned: no, yes, no, no, …
print(numbers.partitionPoint { $0 >= 2 })        // partitioned: no, yes, yes, …
```

```output
7
1
```

`$0 == 2` answers no, yes, no, no, no, no, no. The search never looks at index 1, decides nothing matches, and returns `endIndex`. Ask "is it at least 2?" instead, and the answers are partitioned. If you're unsure about some data, check it in your tests: for sorted data, every predicate of the form "is it at least x?" or "is it more than x?" is safe.

## DSAKit's version

Your companion package has the same search, tested, in `dsa-swift/Sources/DSAKit/BinarySearch.swift`. It's an extension on `RandomAccessCollection`:

| Method | Returns | Needs |
| --- | --- | --- |
| `partitionPoint(where:)` | the first index where the predicate is true, or `endIndex` | a partitioned collection |
| `lowerBound(of:)` | the first index with an element ≥ the value | sorted, `Comparable` elements |
| `upperBound(of:)` | the first index with an element > the value | sorted, `Comparable` elements |
| `binarySearch(for:)` | the index of the first equal element, or `nil` | sorted, `Comparable` elements |

```swift
import DSAKit

let starts = [540, 545, 600, 600, 615, 660, 700]
starts.lowerBound(of: 600)              // 2
starts.upperBound(of: 600)              // 4: two events start at 10:00
starts.binarySearch(for: 615)           // Optional(4)
starts.binarySearch(for: 610)           // nil
starts.partitionPoint { $0 > 650 }      // 5
starts[3...].lowerBound(of: 600)        // 3: slices keep their parent's indexes
```

All four are O(log n), and all four use `index(_:offsetBy:)`, so they work on slices, ranges and any other random-access collection. The generic one is deliberately called `partitionPoint`, not `partitioningIndex`, so that a file importing both DSAKit and swift-algorithms never has two methods with the same name. Its tests cover empty and one-element collections, runs of duplicates, values below, between and above everything, slices that don't start at 0, and thousands of random sorted arrays checked against a plain linear scan.

**Which should you use?** In an app, swift-algorithms. In this course's problems, DSAKit, or your own loop when the point of the exercise is the loop. In an interview, write it by hand, since that's what's being tested, but mention that you'd use the library in production: it shows you know the difference.
