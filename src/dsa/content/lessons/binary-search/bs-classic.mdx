## Why it matters

When data is sorted, you don't have to look at most of it. Binary search checks the middle, throws away the half that can't hold the answer, and repeats: about 20 steps for a million elements, where a linear search might need a million. You use the idea without thinking every time you open a dictionary near the right letter. Programmers use it to find the commit that broke a build (`git bisect`), to look up a time in a sorted log, to find where a new item goes in a sorted list. And it's the doorway to a whole family of techniques in this part of the course.

## The guessing game

"I'm thinking of a whole number from 1 to 100. Each time you guess, I'll say higher or lower."

The smart first guess is 50. Whatever the answer, half the numbers are gone: "higher" leaves 51 to 100, "lower" leaves 1 to 49. Guess the middle of what's left, every time, and you never need more than 7 guesses: each wrong guess leaves at most half of the candidates, so after six guesses only one can remain, and the seventh names it.

That's binary search. The numbers 1 to 100 are sorted, so one comparison with the middle tells you which half to keep.

<Callout kind="analogy">
Looking up "panda" in a paper dictionary, you don't start at "aardvark". You open somewhere in the middle, see "maple", know "panda" comes later, and only ever look at the later pages again. Every glance throws away a big chunk of the book.
</Callout>

## The algorithm

Keep two indexes, `low` and `high`, marking the part of the array where the target could still be. At the start that's the whole array: `low` is 0 and `high` is the last index. Then repeat:

1. Look at the element in the middle, at `mid`.
2. If it's the target, you're done.
3. If it's **smaller** than the target, the target can only be to its right: move `low` to `mid + 1`.
4. If it's **bigger**, the target can only be to its left: move `high` to `mid - 1`.

When `low` passes `high`, there's nowhere left to look, so the target isn't there. Here it is in Swift, printing each step:

```swift run
func binarySearch(_ items: [Int], for target: Int) -> Int? {
    var low = 0
    var high = items.count - 1
    while low <= high {
        let mid = low + (high - low) / 2
        print("low \(low), high \(high), mid \(mid): items[mid] = \(items[mid])")
        if items[mid] == target {
            return mid
        } else if items[mid] < target {
            low = mid + 1                  // mid and everything left of it are too small
        } else {
            high = mid - 1                 // mid and everything right of it are too big
        }
    }
    return nil
}

let sorted = [3, 8, 12, 17, 21, 26, 30, 34, 41, 45, 52]
print(binarySearch(sorted, for: 34) as Any)
print(binarySearch(sorted, for: 20) as Any)
```

```output
low 0, high 10, mid 5: items[mid] = 26
low 6, high 10, mid 8: items[mid] = 41
low 6, high 7, mid 6: items[mid] = 30
low 7, high 7, mid 7: items[mid] = 34
Optional(7)
low 0, high 10, mid 5: items[mid] = 26
low 0, high 4, mid 2: items[mid] = 12
low 3, high 4, mid 3: items[mid] = 17
low 4, high 4, mid 4: items[mid] = 21
nil
```

What to notice:

- Searching for 34 took four looks in an array of eleven. The last look was a range of one element, `low` and `high` both 7.
- Searching for 20 also ended with a range of one, holding 21. Then `high` became 3, below `low`, and the loop stopped: 20 would have sat between 17 and 21, and there's nothing there.
- `mid` is always rounded down. In the range 6 to 7, it's 6.

## About 20 steps for a million

Each pass of the loop keeps at most half of the range: n elements, then n / 2, then n / 4, until one is left. So the number of passes is about the number of times you can halve n, which is log₂ n, the logarithm from [Series sums and logarithms](/dsa/learn/math-series-logs). Count the passes in the worst case, searching for a value bigger than everything:

```swift run
func worstCasePasses(_ count: Int) -> Int {
    let items = Array(0..<count)
    let target = count                    // bigger than every element
    var low = 0
    var high = items.count - 1
    var passes = 0
    while low <= high {
        passes += 1
        let mid = low + (high - low) / 2
        if items[mid] == target {
            break
        } else if items[mid] < target {
            low = mid + 1
        } else {
            high = mid - 1
        }
    }
    return passes
}

for count in [10, 1_000, 1_000_000] {
    print("\(count) elements: \(worstCasePasses(count)) passes")
}
```

```output
10 elements: 4 passes
1000 elements: 10 passes
1000000 elements: 20 passes
```

A million elements, 20 passes. A billion would take 30. Linear search on those arrays could take a million or a billion comparisons. Binary search is **O(log n)**, and the gap gets wider the more data you have:

```visual growthChart

```

## The recursive version

Binary search also has a natural recursive shape, which you met in [Recursion over arrays with indices](/dsa/learn/rec-arrays): searching a range means looking at the middle and then searching one half.

```swift run
func binarySearch(_ items: [Int], for target: Int, low: Int, high: Int) -> Int? {
    guard low <= high else {
        return nil                                   // an empty range: not here
    }
    let mid = low + (high - low) / 2
    if items[mid] == target {
        return mid
    } else if items[mid] < target {
        return binarySearch(items, for: target, low: mid + 1, high: high)
    } else {
        return binarySearch(items, for: target, low: low, high: mid - 1)
    }
}

let sorted = [3, 8, 12, 17, 21, 26, 30, 34, 41, 45, 52]
print(binarySearch(sorted, for: 45, low: 0, high: sorted.count - 1) as Any)
print(binarySearch(sorted, for: 4, low: 0, high: sorted.count - 1) as Any)
```

```output
Optional(9)
nil
```

The base case is the empty range, `low > high`. Each call halves the range, so the recursion is only about log₂ n calls deep: 20 for a million elements, nowhere near the stack limits from [Stack depth limits in Swift](/dsa/learn/rec-stack-limits). Passing `items` to each call doesn't copy it, because arrays are copy-on-write and nothing changes them.

Which should you write? The iterative version uses O(1) extra space instead of O(log n), and Swift doesn't promise to turn the recursive calls into a loop for you, as [Recursion vs iteration, and tail calls](/dsa/learn/rec-vs-iteration) explained. Most people write the loop. The recursive version is worth knowing because it's how binary search appears in recurrences: T(n) = T(n / 2) + O(1), which [The Master theorem](/dsa/learn/bigo-master-theorem) solves as O(log n).

## What binary search needs

Two things, and both matter.

**1. Sorted data.** The whole argument rests on "everything left of mid is smaller". On unsorted data, binary search doesn't crash. It quietly gives wrong answers:

```swift run
func binarySearch(_ items: [Int], for target: Int) -> Int? {
    var low = 0
    var high = items.count - 1
    while low <= high {
        let mid = low + (high - low) / 2
        if items[mid] == target {
            return mid
        } else if items[mid] < target {
            low = mid + 1
        } else {
            high = mid - 1
        }
    }
    return nil
}

let jumbled = [9, 2, 7, 4, 5]
print(jumbled.contains(9))
print(binarySearch(jumbled, for: 9) as Any)
```

```output
true
nil
```

The middle is 7, which is less than 9, so the search threw away the left half, including the 9 at index 0. The data must also be sorted by the **same** comparison you search with: names sorted case-insensitively won't work with a search that compares with `<`.

**2. Jumping to the middle in O(1).** Binary search makes log₂ n jumps, so each jump must be cheap. An `Array` can reach any index instantly, which is what `RandomAccessCollection` promises, as [Collection conformance and subscripts](/dsa/learn/swift-collection-subscripts) explained. A linked list can't: reaching the middle means walking node by node, about n / 2 of them, so the whole search costs at least O(n), no better than a linear scan.

`String` is the trap in between. It has no integer subscript, and moving a `String.Index` k places costs O(k), as [Array(s) and [UInt8] for fast access](/dsa/learn/swift-string-to-array) showed. Convert it to an array first. While you're at it, a generic version works for any `Comparable` element:

```swift run
func binarySearch<Element: Comparable>(_ items: [Element], for target: Element) -> Int? {
    var low = 0
    var high = items.count - 1
    while low <= high {
        let mid = low + (high - low) / 2
        if items[mid] == target {
            return mid
        } else if items[mid] < target {
            low = mid + 1
        } else {
            high = mid - 1
        }
    }
    return nil
}

let letters = Array("acdfhkmpt")                  // [Character], with O(1) indexing
print(binarySearch(letters, for: "k") as Any)
print(binarySearch(["ant", "bee", "cat", "dog"], for: "cat") as Any)
```

```output
Optional(5)
Optional(2)
```

## The middle: why not (low + high) / 2?

The obvious way to find the middle is `(low + high) / 2`. It gives the same answer as `low + (high - low) / 2`, as long as `low + high` fits in an `Int`. When it doesn't, Swift doesn't wrap round to a negative number, as some languages do: it **traps**, as you saw in [Overflow traps and overflow operators](/dsa/learn/swift-overflow).

```swift
func middle(_ low: Int, _ high: Int) -> Int {
    (low + high) / 2
}
print(middle(6_000_000_000_000_000_000, 8_000_000_000_000_000_000))
```

```text title="What you'll see"
Swift runtime failure: arithmetic overflow
```

Both numbers fit in an `Int`, whose largest value is about 9.2 × 10¹⁸, but their sum, 1.4 × 10¹⁹, doesn't. `low + (high - low) / 2` never adds two big numbers: `high - low` is a distance, and half of it added to `low` stays between `low` and `high`.

```swift run
let low = 6_000_000_000_000_000_000
let high = 8_000_000_000_000_000_000
print(low + (high - low) / 2)
```

```output
7000000000000000000
```

To be honest, an array index will never get that big. But binary search isn't only for arrays. Later in this module you'll search for square roots of numbers up to `Int.max`, and in M29 you'll binary search over ranges of possible answers that reach 10¹⁸. The safe midpoint costs nothing, so make it a habit. (In languages that wrap instead of trapping, `(low + high) / 2` gave a negative index, and that bug sat unnoticed in Java's standard library binary search for years.)

<Callout kind="gotcha" title="Common mistakes">
- **Searching unsorted data.** No crash, only wrong answers. If you're not sure the input is sorted, check with `precondition` in tests, or sort it first.
- **Binary searching a linked list or a String directly.** The jumps cost O(n) or O(k) each. Convert to an `Array` first, or use linear search.
- **`(low + high) / 2`.** Safe for array indexes, but a crash waiting to happen on big number ranges. Write `low + (high - low) / 2` everywhere.
- **`while low < high` with `high = mid - 1`.** It skips the last one-element range, so it misses targets. The next lesson is all about matching the loop condition to the updates.
</Callout>
