## Why it matters

Binary search is famously easy to get *almost* right. Jon Bentley, in *Programming Pearls*, describes asking professional programmers to write one: most of their attempts had bugs. The bugs are always the same few: a loop that never ends, an index one past the end, a target that's there but never found. They hide, too, because most inputs work fine. The cure isn't memorising one version. It's deciding exactly what `low` and `high` **mean**, writing that down as an invariant, as you learned in [Loop invariants and correctness](/dsa/learn/algo-invariants), and letting it decide every line.

## Two ways to describe a range

A range of indexes can include its upper end or exclude it. Swift has an operator for each, from [The ternary operator and ranges](/dsa/learn/swift-ternary-ranges):

| | Closed `[low, high]` | Half-open `[low, high)` |
| --- | --- | --- |
| In Swift | `low...high` | `low..<high` |
| Includes `high`? | yes | no |
| Number of indexes | `high - low + 1` | `high - low` |
| Empty when | `low > high` | `low == high` |
| The whole array | `0...(count - 1)` | `0..<count` |

Half-open ranges are everywhere in Swift: `0..<count`, `startIndex..<endIndex`, and every slice. Notice how the whole array of an empty array is `0..<0` in half-open form, but the odd-looking `0...(-1)` in closed form.

A binary search keeps one of these ranges as "where the target could still be". Choose one, and everything else follows.

## The closed version, line by line

**Invariant: if the target is in the array, its index is in `[low, high]`.**

- **Start.** `low = 0`, `high = count - 1`: the whole array, so the invariant is true.
- **Loop condition.** Keep going while the range isn't empty: `while low <= high`.
- **Too small.** If `items[mid] < target`, then mid and everything to its left are too small. The target, if present, is in `[mid + 1, high]`, so `low = mid + 1`.
- **Too big.** If `items[mid] > target`, it's in `[low, mid - 1]`, so `high = mid - 1`.
- **Finish.** The loop ends when the range is empty. The invariant says the target would be in an empty range, so it isn't in the array: return `nil`.
- **Progress.** Both updates exclude mid, so the range shrinks by at least one element every pass. The loop must end.

## The half-open version, line by line

**Invariant: if the target is in the array, its index is in `[low, high)`.**

- **Start.** `low = 0`, `high = count`: the whole array, with `high` one past the end.
- **Loop condition.** The range is empty when `low == high`, so: `while low < high`.
- **Too small.** Exactly as before: `low = mid + 1`.
- **Too big.** The target is in `[low, mid)`. Since `high` is excluded, that's `high = mid`. Not `mid - 1`: that would wrongly exclude index `mid - 1` too.
- **Safety.** When `low < high`, the middle `low + (high - low) / 2` is always less than `high`, so `items[mid]` never reads past the end.

Here are both, printing the range on each pass in its own notation:

```swift run
func closedSearch(_ items: [Int], for target: Int) -> Int? {
    var low = 0
    var high = items.count - 1                 // invariant: if present, target is in [low, high]
    while low <= high {
        let mid = low + (high - low) / 2
        print("  closed [\(low), \(high)], mid \(mid)")
        if items[mid] == target {
            return mid
        } else if items[mid] < target {
            low = mid + 1
        } else {
            high = mid - 1
        }
    }
    return nil
}

func halfOpenSearch(_ items: [Int], for target: Int) -> Int? {
    var low = 0
    var high = items.count                     // invariant: if present, target is in [low, high)
    while low < high {
        let mid = low + (high - low) / 2
        print("  half-open [\(low), \(high)), mid \(mid)")
        if items[mid] == target {
            return mid
        } else if items[mid] < target {
            low = mid + 1
        } else {
            high = mid
        }
    }
    return nil
}

let items = [4, 9, 15, 22, 31, 40]
print("closed:", closedSearch(items, for: 9) as Any)
print("half-open:", halfOpenSearch(items, for: 9) as Any)
```

```output
  closed [0, 5], mid 2
  closed [0, 1], mid 0
  closed [1, 1], mid 1
closed: Optional(1)
  half-open [0, 6), mid 3
  half-open [0, 3), mid 1
half-open: Optional(1)
```

The two describe the same sets of indexes in different words, so they can take different routes. Both are correct, because each one's updates match its own invariant. Side by side:

| | Closed `[low, high]` | Half-open `[low, high)` |
| --- | --- | --- |
| Start | `high = count - 1` | `high = count` |
| Loop while | `low <= high` | `low < high` |
| `items[mid] < target` | `low = mid + 1` | `low = mid + 1` |
| `items[mid] > target` | `high = mid - 1` | `high = mid` |

## The classic traps

Almost every broken binary search mixes the two columns of that table.

**1. Closed start, half-open loop.** With `high = count - 1` and `while low < high`, the loop stops while one element is still a candidate. Searching `[5]` for 5 never even enters the loop, and returns `nil`.

**2. Half-open start, closed loop.** With `high = count` and `while low <= high`, the loop runs once more when `low == high`, and that can read `items[count]`:

```swift
var low = 0
var high = items.count          // half-open start…
while low <= high {             // …closed loop: wrong
    let mid = low + (high - low) / 2
    if items[mid] == target { return mid }
    // …
}
```

```text title="What you'll see"
Fatal error: Index out of range
```

Searching `[1, 3]` for 9: `low` climbs to 2, which equals `high`, so the loop runs again with `mid` = 2, one past the end.

**3. Keeping mid when you know it's wrong.** With a closed range, `high = mid` instead of `high = mid - 1` doesn't shrink a range of one element. The loop spins for ever. This version has a limit on its passes, so you can watch it get stuck without hanging:

```swift run
func buggySearch(_ items: [Int], for target: Int) -> String {
    var low = 0
    var high = items.count - 1
    var passes = 0
    while low <= high {
        passes += 1
        if passes > 10 {
            return "stuck at low \(low), high \(high)"
        }
        let mid = low + (high - low) / 2
        if items[mid] == target {
            return "found at \(mid)"
        } else if items[mid] < target {
            low = mid + 1
        } else {
            high = mid                         // bug: should be mid - 1
        }
    }
    return "not found"
}

print(buggySearch([1, 3, 5, 7], for: 5))
print(buggySearch([1, 3, 5, 7], for: 7))
print(buggySearch([1, 3, 5, 7], for: 0))
```

```output
found at 2
found at 3
stuck at low 0, high 0
```

It finds 5 and 7, so a quick test would pass. Only a target that sends the search left until one element remains, here 0, exposes it: `low`, `high` and `mid` are all 0, the value is too big, and `high = mid` changes nothing.

**4. `low = mid`.** The same trap on the other side, and it bites with two elements: `mid` rounds down to `low`, so `low = mid` doesn't move. If an algorithm genuinely needs `low = mid` (you'll meet one later), round the middle **up** instead, with `low + (high - low + 1) / 2`.

<Callout kind="gotcha" title="Swift gotcha: high = count - 1 on an empty array">
For an empty array, `items.count - 1` is -1. That's fine: with `low = 0` and `high = -1`, the closed loop condition `low <= high` is false at once, and the function returns `nil` without touching the array. It only works because `count` is a signed `Int`. With a `UInt`, `0 - 1` would trap, one more reason to stick with `Int` for indexes.
</Callout>

## Test the cases that break binary searches

Bugs in binary search live at the edges, so test the edges on purpose:

- sizes **0, 1 and 2** (and 3, for good measure);
- the target at the **first** index and the **last** index;
- a missing target **below** everything, **between** two values and **above** everything;
- repeated values, if the search allows them.

Better still, let a loop do it. Compare your search with `firstIndex(of:)`, which is slow but obviously right, on every small sorted array and every interesting target:

```swift run
func correct(_ items: [Int], _ target: Int) -> Int? {
    var low = 0
    var high = items.count - 1
    while low <= high {
        let mid = low + (high - low) / 2
        if items[mid] == target { return mid }
        if items[mid] < target { low = mid + 1 } else { high = mid - 1 }
    }
    return nil
}

func stopsEarly(_ items: [Int], _ target: Int) -> Int? {
    var low = 0
    var high = items.count - 1
    while low < high {                         // bug: closed range, half-open condition
        let mid = low + (high - low) / 2
        if items[mid] == target { return mid }
        if items[mid] < target { low = mid + 1 } else { high = mid - 1 }
    }
    return nil
}

func firstFailure(_ search: ([Int], Int) -> Int?) -> String {
    for count in 0...6 {
        let items = (0..<count).map { $0 * 2 }           // 0, 2, 4, …
        for target in -1...(2 * count) {                 // every value and every gap
            if search(items, target) != items.firstIndex(of: target) {
                return "fails for \(target) in \(items)"
            }
        }
    }
    return "passes every case"
}

print("correct:", firstFailure(correct))
print("stopsEarly:", firstFailure(stopsEarly))
```

```output
correct: passes every case
stopsEarly: fails for 0 in [0]
```

Even values with odd targets give every kind of miss: below, between and above. The checker found the bug on the second array it tried. This little harness is worth keeping: you'll reuse it for every variation in this module.

## The checklist

Before you trust a binary search, walk through this:

1. **Meaning.** What do `low` and `high` mean: closed or half-open? Write the invariant as a comment.
2. **Start.** Do the initial values make it true? (`count - 1` for closed, `count` for half-open.)
3. **Loop condition.** Does it run exactly while the range is non-empty? (`<=` for closed, `<` for half-open.)
4. **Updates.** Does each branch keep the invariant, excluding mid only when mid can't be the answer?
5. **Progress.** Does every branch shrink the range, even when it holds one or two elements?
6. **Finish.** When the loop ends, what does the invariant tell you? That's what you return.
7. **Test.** Sizes 0, 1 and 2, the target at both ends, and missing below, between and above, ideally with a loop against a linear search.

## Which should you use?

Either, as long as you're consistent. Half-open matches Swift's own ranges and slices, and it shines when the answer is a **position** rather than an element: "where would 10 go?" can be any index from 0 to `count`, and `[0, count)` plus its end point covers exactly that. The next lesson's lower and upper bounds are half-open for that reason. Closed is natural when you're looking for one specific element. This module uses closed for exact matches and half-open for "first index where…" searches.

You'll also see a third style in other people's code: `low = -1`, `high = count`, `while high - low > 1`, where neither end is a candidate. It's correct too, for the same reason: its updates match its invariant.
