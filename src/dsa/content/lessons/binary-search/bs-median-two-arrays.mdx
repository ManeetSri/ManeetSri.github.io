## Why it matters

Two servers each keep their response times sorted, and you want the median across both, without copying either list. This is the most famous hard binary search problem, and for good reason: the search isn't over values or indexes in one array, but over **where to cut** two arrays at once. Get the idea and the code is short; miss one detail and it crashes or answers wrongly. Take this lesson slowly, with a pencil.

## The median, and the obvious answers

The **median** of a sorted list is its middle value. With an even count there are two middle values, and the median is their average. `[1, 2, 3, 4, 9, 10]` has median (3 + 4) ÷ 2 = 3.5.

Given two sorted arrays of sizes m and n:

- **Merge them** into one sorted array, as in [Merge sorted arrays](/dsa/learn/arrays-merge-sorted), and take the middle. O(m + n) time and space.
- **Merge only halfway**, with two pointers, keeping only the last one or two values. O(m + n) time, O(1) space.

Both are good, simple answers. The question is whether you can do it without visiting most of the values. You can, in O(log min(m, n)).

## Cutting both arrays

Imagine the merged list split into a **left half** and a **right half**, with the median at the boundary. When the total is odd, give the extra value to the left, so the left half has

```text
half = (m + n + 1) / 2
```

values. The left half is made of the first i values of `first` and the first j values of `second`, with i + j = half. So choosing i decides j.

Here's the right cut for `first = [1, 4, 9]` and `second = [2, 3, 10]`, where half = (3 + 3 + 1) / 2 = 3:

```text
first:   1 | 4  9          i = 1
second:  2  3 | 10         j = 2

left half: 1, 2, 3        right half: 4, 9, 10
```

A cut is right when **every value on the left is at most every value on the right**. Each array is already sorted, so within one array that's automatic. Only the two diagonal pairs need checking:

- `first[i - 1] ≤ second[j]`: the last left value of `first` against the first right value of `second`;
- `second[j - 1] ≤ first[i]`: the last left value of `second` against the first right value of `first`.

Here, 1 ≤ 10 and 3 ≤ 4, so the cut is right. Then:

- if the total is odd, the median is the **largest left value**, `max(first[i - 1], second[j - 1])`;
- if it's even, it's the average of that and the **smallest right value**, `min(first[i], second[j])`.

For this example, the total is 6, so the median is (max(1, 3) + min(4, 10)) ÷ 2 = 3.5.

## Which way to move the cut

If the cut is wrong, one of the two checks fails, and it tells you which way to go:

- **`first[i - 1] > second[j]`**: the left half has a value from `first` that's too big. You took **too many** from `first`, so the right i is smaller.
- **`second[j - 1] > first[i]`**: the left half has a value from `second` that's too big, which means you took too few from `first`. The right i is **bigger**.

As i grows, `first[i - 1]` can only grow and `second[j]` can only shrink (j shrinks as i grows). So "took too many" is false for small i and true for large i: a monotonic question. That's what makes a binary search over i, from 0 to m, work.

## Sentinels: when a side is empty

What is `first[i - 1]` when i is 0? There's no such value: the left half takes nothing from `first`. A missing left value should never fail a check, so treat it as smaller than everything: `Int.min`. A missing right value, like `first[i]` when i is m, counts as bigger than everything: `Int.max`. These stand-ins are called **sentinels**.

They only work if no real value equals `Int.min` or `Int.max`, so problems like this one promise a range such as ±10⁹. And they never reach the final answer: the left half always has at least one real value, so the largest left value is real, and when the total is even the right half has at least one real value too.

## Search the shorter array

i ranges over 0 to m, and j = half − i must stay between 0 and n. If `first` is the shorter array (m ≤ n), every i in that range gives a valid j. If it's the longer one, j can go negative or past the end. So if `first` is longer, swap them. As a bonus, the search is then over the smaller range: O(log min(m, n)).

## The code, traced

```swift run
func median(of first: [Int], and second: [Int]) -> Double {
    if first.count > second.count {
        return median(of: second, and: first)          // binary search the shorter array
    }
    let m = first.count
    let n = second.count
    let half = (m + n + 1) / 2                         // the left half's size
    var low = 0
    var high = m
    while low <= high {
        let i = low + (high - low) / 2                 // take i values from first…
        let j = half - i                               // …and j from second
        let firstLeft = i > 0 ? first[i - 1] : Int.min
        let firstRight = i < m ? first[i] : Int.max
        let secondLeft = j > 0 ? second[j - 1] : Int.min
        let secondRight = j < n ? second[j] : Int.max

        if firstLeft > secondRight {
            print("  i \(i), j \(j): first[\(i - 1)] = \(firstLeft) > second[\(j)] = \(secondRight): fewer from first")
            high = i - 1
        } else if secondLeft > firstRight {
            print("  i \(i), j \(j): second[\(j - 1)] = \(secondLeft) > first[\(i)] = \(firstRight): more from first")
            low = i + 1
        } else {
            print("  i \(i), j \(j): the cut is right")
            let leftMax = max(firstLeft, secondLeft)
            if (m + n) % 2 == 1 {
                return Double(leftMax)
            }
            let rightMin = min(firstRight, secondRight)
            return Double(leftMax + rightMin) / 2
        }
    }
    fatalError("unreachable when both arrays are sorted")
}

print(median(of: [4, 10, 25, 30, 40, 50, 60], and: [1, 2, 3, 5, 6, 8, 12, 15]))
print(median(of: [10, 20, 30, 40, 50, 60, 70], and: [1, 2, 3, 4, 5, 6, 7, 8]))
print(median(of: [1, 4, 9], and: [2, 3, 10]))
```

```output

  i 1, j 7: second[6] = 12 > first[1] = 10: more from first
  i 2, j 6: the cut is right
10.0
  i 3, j 5: first[2] = 30 > second[5] = 6: fewer from first
  i 1, j 7: first[0] = 10 > second[7] = 8: fewer from first
  i 0, j 8: the cut is right
8.0
  i 1, j 2: the cut is right
3.5
```

Walk through the first one. There are 15 values, so half = 8, and i can be 0 to 7.

1. **i = 3, j = 5.** The left half would hold 4, 10, 25 from `first` and 1, 2, 3, 5, 6 from `second`. But 25 is bigger than `second[5]` = 8, which would be on the right. Too many from `first`: the search moves to i in 0…2.
2. **i = 1, j = 7.** Now the left half holds only 4 from `first`, and 1, 2, 3, 5, 6, 8, 12 from `second`. But 12 is bigger than `first[1]` = 10, which would be on the right. Too few from `first`: i in 2…2.
3. **i = 2, j = 6.** Left: 4, 10 and 1, 2, 3, 5, 6, 8. Right: 25, 30, … and 12, 15. Both checks pass: 10 ≤ 12 and 8 ≤ 25. The total is odd, so the median is the largest left value, max(10, 8) = 10.

Merged, the values are 1, 2, 3, 4, 5, 6, 8, **10**, 12, 15, 25, 30, 40, 50, 60, and the eighth is indeed 10.

The second call shows the sentinels at work. Every value in `first` belongs on the right, so the search drives i down to 0. Then `firstLeft` is `Int.min`, which passes its check, and the median is the largest left value of `second`, 8.

`fatalError` at the end is never reached for valid input: some i always gives a correct cut. It's there because the compiler needs every path to return a `Double`, and it documents the assumption.

## Why it's O(log min(m, n))

Each pass does a constant amount of work and halves the range of i, which starts with m + 1 values, where m is the shorter array's length. So it takes about log₂ m passes. For two arrays of a million values each, that's about 20 passes, where merging halfway would take a million steps.

<Callout kind="gotcha" title="Common mistakes">
- **Searching the longer array.** Then j can be negative or bigger than n, and `second[j]` crashes. Swap first.
- **Sentinels that collide with real data.** If the arrays may hold `Int.min` or `Int.max`, use optionals for the missing neighbours instead.
- **Getting the halves wrong.** `(m + n + 1) / 2` puts the extra value on the left when the total is odd, so the odd-case median is the largest left value. With `(m + n) / 2` it would be the smallest right value instead. Either works, but mixing them doesn't.
- **Integer division in the average.** `(leftMax + rightMin) / 2` with `Int`s turns 3.5 into 3. Convert to `Double` before dividing. If values could be near `Int.max`, the sum could overflow too; then compute `Double(leftMax) / 2 + Double(rightMin) / 2`.
</Callout>

<Callout kind="note" title="Another route: the k-th smallest">
A different approach finds the k-th smallest value of two sorted arrays: compare the (k/2)-th value of each, and throw away the k/2 values in front of the smaller one, which can't include the k-th. Repeat with k reduced by k/2. That's O(log(m + n)), and the median is the k-th smallest for the right k (or the average of two). The cut method is usually preferred because it handles odd and even totals in one search.
</Callout>
