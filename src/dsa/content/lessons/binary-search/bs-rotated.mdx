## Why it matters

Take a sorted array, cut it somewhere, and swap the two pieces: `[10, 20, 30, 40, 50, 60, 70]` becomes `[40, 50, 60, 70, 10, 20, 30]`. That's a **rotated sorted array**. You've already built one without noticing: a full [ring buffer](/dsa/learn/queue-ring-buffer) of timestamps is sorted from its head round to its back, but its raw slots read like this, with the break wherever the head happens to be. The array isn't sorted any more, yet binary search still works, because every step only needs enough order to know which half to throw away. That shift in thinking, from "the array is sorted" to "I can always rule out half", is what makes binary search a pattern rather than a single algorithm. Rotated arrays are also among the most common binary search interview questions.

## What rotation leaves behind

Look at the rotated array:

| index | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| value | 40 | 50 | 60 | 70 | 10 | 20 | 30 |

- It's two sorted runs, `40…70` and `10…30`, and every value in the first run is bigger than every value in the second.
- There's exactly one **break**, where a value is smaller than the one before it: between 70 and 10.
- The **minimum** sits right after the break. Its index, 4, is how far the array was rotated: the original index 0 moved to index 4.

[Reverse and rotate in place](/dsa/learn/arrays-reverse-rotate) showed how to rotate an array. Here, the rotation has already happened, and you don't know by how much. (This lesson assumes the values are **distinct**. Repeated values come at the end, and they change the story.)

## Finding the minimum

Compare the middle element with the **last** element of the range, `items[high]`:

- If `items[mid] > items[high]`, the values drop somewhere between mid and high, so the break, and the minimum, is to the **right** of mid: `low = mid + 1`.
- Otherwise `mid...high` is sorted, so nothing to the right of mid is smaller than `items[mid]`. The minimum is mid or something to its **left**: `high = mid`.

Look at that second branch: `high = mid` keeps mid as a candidate. That's the "first index where a condition becomes true" search from the last lesson, and the condition is "value ≤ the last element": every value in the first run is bigger than the last element, and every value in the second run is at most the last element. The minimum is the first true.

```swift run
func minimumIndex(_ items: [Int]) -> Int {
    var low = 0
    var high = items.count - 1
    while low < high {
        let mid = low + (high - low) / 2
        if items[mid] > items[high] {
            low = mid + 1          // the values drop after mid: the minimum is to the right
        } else {
            high = mid             // mid...high is sorted: the minimum is mid or to its left
        }
    }
    return low
}

for items in [[40, 50, 60, 70, 10, 20, 30], [10, 20, 30, 40], [20, 10], [5]] {
    let index = minimumIndex(items)
    print(items, "minimum", items[index], "at index", index)
}
```

```output
[40, 50, 60, 70, 10, 20, 30] minimum 10 at index 4
[10, 20, 30, 40] minimum 10 at index 0
[20, 10] minimum 10 at index 1
[5] minimum 5 at index 0
```

An array that wasn't rotated at all, `[10, 20, 30, 40]`, is handled by the same code: every middle is smaller than the last element, so `high` walks down to 0. The function needs at least one element; an empty array has no minimum.

<Callout kind="gotcha" title="Why compare with high, not low?">
Comparing mid with `items[low]` looks equally reasonable, but it can't tell "rotated" from "not rotated". In `[10, 20, 30, 40]`, `items[mid]` is bigger than `items[low]`, which seems to say "the left part is sorted, the minimum is to the right", and the search walks away from the 10. Comparing with the last element has no such blind spot: the last element is always in the second sorted run.
</Callout>

## Searching for a target

There are two good ways to find a value.

### Find the break, then search the sorted order

Once you know the minimum's index, `shift`, you know where sorted order starts. The k-th smallest value lives at index `(shift + k) % count`, wrapping round exactly as a ring buffer does. So binary search over sorted **positions** and translate each one to a real index:

```swift run
func minimumIndex(_ items: [Int]) -> Int {
    var low = 0
    var high = items.count - 1
    while low < high {
        let mid = low + (high - low) / 2
        if items[mid] > items[high] { low = mid + 1 } else { high = mid }
    }
    return low
}

func search(_ items: [Int], for target: Int) -> Int? {
    guard !items.isEmpty else { return nil }
    let shift = minimumIndex(items)                // where sorted order begins
    var low = 0
    var high = items.count - 1                     // positions in sorted order
    while low <= high {
        let mid = low + (high - low) / 2
        let index = (shift + mid) % items.count    // sorted position → real index
        if items[index] == target {
            return index
        } else if items[index] < target {
            low = mid + 1
        } else {
            high = mid - 1
        }
    }
    return nil
}

let rotated = [40, 50, 60, 70, 10, 20, 30]
print(search(rotated, for: 20) as Any, search(rotated, for: 70) as Any, search(rotated, for: 55) as Any)
```

```output
Optional(5) Optional(3) nil
```

Two binary searches: still O(log n). This version is easy to get right, because the second search is the ordinary closed search from the last lessons, plus one line of index arithmetic.

### One pass: one half is always sorted

You can also do it in a single search. Split the range at mid. The break can only be on one side, so **at least one half is sorted**, and comparing its ends tells you which:

- If `items[low] <= items[mid]`, the left half `low...mid` is sorted. If the target lies between `items[low]` and `items[mid]`, search there; otherwise it can only be on the right.
- Otherwise the right half `mid...high` is sorted. If the target lies between `items[mid]` and `items[high]`, search there; otherwise go left.

A sorted half's values are exactly the numbers between its two ends, so "is the target in that half?" is a range check. The other half is a mess, but you don't need to understand it: if the target isn't in the tidy half, it's in the messy one.

```swift run
func search(_ items: [Int], for target: Int) -> Int? {
    var low = 0
    var high = items.count - 1
    while low <= high {
        let mid = low + (high - low) / 2
        if items[mid] == target {
            return mid
        }
        if items[low] <= items[mid] {
            print("  [\(low), \(high)], mid \(mid): left half \(items[low])...\(items[mid]) is sorted")
            if items[low] <= target && target < items[mid] {
                high = mid - 1
            } else {
                low = mid + 1
            }
        } else {
            print("  [\(low), \(high)], mid \(mid): right half \(items[mid])...\(items[high]) is sorted")
            if items[mid] < target && target <= items[high] {
                low = mid + 1
            } else {
                high = mid - 1
            }
        }
    }
    return nil
}

let rotated = [40, 50, 60, 70, 10, 20, 30]
print(search(rotated, for: 20) as Any)
print(search(rotated, for: 55) as Any)
```

```output
  [0, 6], mid 3: left half 40...70 is sorted
Optional(5)
  [0, 6], mid 3: left half 40...70 is sorted
  [0, 2], mid 1: left half 40...50 is sorted
  [2, 2], mid 2: left half 60...60 is sorted
nil
```

Step through the search for 55. The green range is the half that's sorted at each step:

```visual arrayTrace

  target: 55
```

For 20: the left half holds 40 to 70, and 20 isn't in that range, so it must be on the right. For 55: it is between 40 and 70, so the search moves left, and an ordinary binary search finishes the job.

The details that trip people up:

- `items[low] <= items[mid]` needs the `<=`. When the range has one or two elements, `low` and `mid` are the same index, and that one-element left half counts as sorted.
- The range checks leave out `items[mid]` (it was checked a moment ago) but include the far end, `items[low]` or `items[high]`, which hasn't been.

## When values repeat

Allow duplicates and something breaks. Take these two arrays:

```text
[1, 1, 1, 1, 1, 0, 1, 1]      the 0 is to the right of mid
[1, 0, 1, 1, 1, 1, 1, 1]      the 0 is to the left of mid
```

In both, `items[low]`, `items[mid]` and `items[high]` are all 1. Nothing you can compare tells you which side the break is on. The best you can do is drop one copy: if `items[mid] == items[high]`, then `high -= 1` can't lose the minimum's value, because the same value is still at mid. But that throws away one element, not half the range:

```swift run
func minimumWithRepeats(_ items: [Int]) -> (value: Int, passes: Int) {
    var low = 0
    var high = items.count - 1
    var passes = 0
    while low < high {
        passes += 1
        let mid = low + (high - low) / 2
        if items[mid] > items[high] {
            low = mid + 1
        } else if items[mid] < items[high] {
            high = mid
        } else {
            high -= 1              // can't tell which side: drop one copy
        }
    }
    return (items[low], passes)
}

let distinct = Array(300..<1_000) + Array(0..<300)       // rotated, no repeats
print("distinct:", minimumWithRepeats(distinct))

for zeroAt in [999, 600, 0] {
    var ones = Array(repeating: 1, count: 1_000)
    ones[zeroAt] = 0
    print("one 0 at \(zeroAt):", minimumWithRepeats(ones))
}
```

```output
distinct: (value: 0, passes: 10)
one 0 at 999: (value: 0, passes: 9)
one 0 at 600: (value: 0, passes: 408)
one 0 at 0: (value: 0, passes: 999)
```

With distinct values, 10 passes. With nine hundred and ninety-nine 1s and a single 0, it depends where the 0 is. At the end, every comparison with `items[high]` is informative, and 9 passes do it. At index 600, the search spends about 400 passes shaving one copy at a time off the end until `high` reaches the 0. At index 0, it takes 999: the search has degraded to O(n).

That isn't a weakness of this particular code. **No** algorithm can do better on that input. Imagine someone who decides where the 0 is only as you search, and makes every position you look at hold a 1 until you've looked at them all. Every array of 1s with one 0 is a valid rotated sorted array, so until you've checked a position, the 0 could be there. With repeats allowed, rotated search is O(log n) on typical data but **O(n) in the worst case**. In an interview, say so: it's the follow-up question everyone expects.

The one-pass target search needs the same fix: when `items[low]`, `items[mid]` and `items[high]` are all equal, you can't tell which half is sorted, so shrink both ends with `low += 1` and `high -= 1`, and accept O(n) in the worst case.
