## Why it matters

"Is 600 in the list?" is often the wrong question. With repeated values, you want to know where they start, where they end, and how many there are. A calendar app keeps events sorted by start time and asks for everything between 9:00 and 10:00. A leaderboard inserts a new score at the right place. A log viewer jumps to the first entry after a given time. All of these are answered by two searches, the **lower bound** and the **upper bound**, and both are one idea: find the first index where a condition becomes true. That idea is the most useful form of binary search there is.

## Exact search and duplicates

The search from the last two lessons stops at the first copy it happens to land on:

```swift run
func binarySearch(_ items: [Int], for target: Int) -> Int? {
    var low = 0
    var high = items.count - 1
    while low <= high {
        let mid = low + (high - low) / 2
        if items[mid] == target {
            return mid
        } else if items[mid] < target {
            low = mid + 1
        } else {
            high = mid - 1
        }
    }
    return nil
}

let readings = [1, 3, 3, 3, 5, 8]
print(binarySearch(readings, for: 3) as Any)
```

```output
Optional(2)
```

Index 2 holds a 3, but it's neither the first copy nor the last. Which copy you get depends on where the middles happen to fall. To find the edges of the run, you need a different question.

## One idea: the first index where a condition becomes true

Ask "is this value at least 3?" of every element of `[1, 3, 3, 3, 5, 8]`:

| index | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| value | 1 | 3 | 3 | 3 | 5 | 8 |
| value ≥ 3? | no | yes | yes | yes | yes | yes |

Because the array is sorted, the answers can only go **no, no, …, yes, yes**: once a value passes, every later value passes too. A yes/no question whose answers flip once like this is called **monotonic**. The interesting thing is the boundary, the first yes. Binary search finds it in O(log n), whatever the question:

```swift
/// The first index whose value makes `condition` true, or items.count if none does.
/// The answers must go false, …, false, true, …, true.
func firstIndex(in items: [Int], where condition: (Int) -> Bool) -> Int {
    var low = 0
    var high = items.count             // the answer is in [low, high]; count means "none"
    while low < high {
        let mid = low + (high - low) / 2
        if condition(items[mid]) {
            high = mid                 // mid could be the first true: keep it
        } else {
            low = mid + 1              // mid is false, and so is everything before it
        }
    }
    return low
}
```

Its invariant is about the answers, not about a target: **everything before `low` is false, and everything from `high` on is true.** At the start nothing has been checked, so that's trivially true. Each update keeps it. When `low == high`, every index is on one side or the other, and `low` is the first true, or `count` if there's none.

Compare it with the half-open exact search from the last lesson. The loop condition and `low = mid + 1` are the same. The difference is the true branch: there, a match returned at once; here, a true mid might be the answer or might have more trues before it, so it **stays** in the range with `high = mid`. That's safe because mid is always less than `high`, so the range still shrinks.

Step through it with the question "value ≥ 3?". Notice that it doesn't stop when it first sees a 3:

## Lower bound and upper bound

Two questions get names of their own:

- **Lower bound of x:** the first index whose value is **≥ x**.
- **Upper bound of x:** the first index whose value is **> x**.

```swift run
func firstIndex(in items: [Int], where condition: (Int) -> Bool) -> Int {
    var low = 0
    var high = items.count
    while low < high {
        let mid = low + (high - low) / 2
        if condition(items[mid]) {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

func lowerBound(_ items: [Int], _ x: Int) -> Int { firstIndex(in: items) { $0 >= x } }
func upperBound(_ items: [Int], _ x: Int) -> Int { firstIndex(in: items) { $0 > x } }

let readings = [1, 3, 3, 3, 5, 8]
for x in [3, 4, 0, 9] {
    print("x = \(x): lower \(lowerBound(readings, x)), upper \(upperBound(readings, x))")
}
```

```output
x = 3: lower 1, upper 4
x = 4: lower 4, upper 4
x = 0: lower 0, upper 0
x = 9: lower 6, upper 6
```

What to notice:

- For 3, the copies sit at indexes 1, 2 and 3: from the lower bound up to, but not including, the upper bound. The run is the half-open range `lower..<upper`.
- For 4, which is missing, both bounds are 4: the place 4 would go. The run is empty.
- For 0, smaller than everything, both are 0. For 9, bigger than everything, both are 6, the array's count. "Past the end" is a perfectly good answer here, which is why `high` starts at `count`.

## Everything else from two bounds

With those two numbers you can answer almost any question about sorted data:

| Question | Answer |
| --- | --- |
| Is x present? | `lower < count && items[lower] == x` |
| First occurrence of x | `lower`, if x is present |
| Last occurrence of x | `upper - 1`, if x is present |
| How many copies of x? | `upper - lower`, which is 0 when x is missing |
| Where to insert x, before equal values | `lower` |
| Where to insert x, after equal values | `upper` |
| How many values in `a...b`? | `upperBound(b) - lowerBound(a)` |
| Largest value smaller than x | `items[lower - 1]`, if `lower > 0` |
| Smallest value bigger than x | `items[upper]`, if `upper < count` |

Here are a few of them working on a day's calendar, with event start times in minutes since midnight:

```swift run
func firstIndex(in items: [Int], where condition: (Int) -> Bool) -> Int {
    var low = 0
    var high = items.count
    while low < high {
        let mid = low + (high - low) / 2
        if condition(items[mid]) {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

func lowerBound(_ items: [Int], _ x: Int) -> Int { firstIndex(in: items) { $0 >= x } }
func upperBound(_ items: [Int], _ x: Int) -> Int { firstIndex(in: items) { $0 > x } }

var starts = [540, 545, 600, 600, 615, 660, 700]     // 9:00, 9:05, 10:00, …

print("events at 10:00:", upperBound(starts, 600) - lowerBound(starts, 600))
print("events from 10:00 to 11:00:", upperBound(starts, 660) - lowerBound(starts, 600))
print("events at 9:30:", upperBound(starts, 570) - lowerBound(starts, 570))

let next = lowerBound(starts, 610)
print("first event at or after 10:10 starts at", starts[next])

starts.insert(605, at: lowerBound(starts, 605))      // stays sorted
print(starts)
```

```output
events at 10:00: 2
events from 10:00 to 11:00: 4
events at 9:30: 0
first event at or after 10:10 starts at 615
[540, 545, 600, 600, 605, 615, 660, 700]
```

The count needs no special case for a missing value: both bounds land on the same index, and their difference is 0. Each question costs O(log n). The insert itself still shifts the later elements, O(n), as [The cost of inserting and deleting](/dsa/learn/arrays-insert-delete-cost) explained, but finding the spot is cheap.

**Before or after equal values?** Inserting at the upper bound puts a new element after any equal ones. On a leaderboard sorted by score, that keeps players who tied in the order they got there, with the newest last. Keeping equal elements in their original order is called being **stable**, and you'll meet it again in [Stable, in-place, adaptive and online](/dsa/learn/sort-properties).

<Callout kind="note" title="Another way to find the first occurrence">
You'll often see the first occurrence found with the closed exact search: when `items[mid] == target`, record `mid` as the best answer so far, then carry on searching left with `high = mid - 1`. It's correct, and the last occurrence works the same way searching right. The bounds version is worth preferring because one function answers every question in the table above.
</Callout>

## Swift has no built-in binary search

Swift's standard library has no `binarySearch`, `lowerBound` or anything like them. The method that looks closest, `firstIndex(where:)`, is a **linear** scan:

```swift
let lower = readings.firstIndex { $0 >= 3 } ?? readings.count    // right answer, O(n)
```

It gives exactly the same answer as the lower bound, and on a sorted array of a million values it may look at all of them. When you need the speed, write the search yourself, use the `partitioningIndex(where:)` method from Apple's swift-algorithms package, or use your package's DSAKit, which has `lowerBound(of:)` and `upperBound(of:)`. The last lesson of this module covers both.

<Callout kind="gotcha" title="Common mistakes">
- **A condition that isn't monotonic.** The search assumes false…false true…true. `$0 == 3` isn't monotonic (false, true, true, true, false, false), so it gives nonsense. Use `$0 >= 3`.
- **A condition the wrong way round.** `$0 < 3` goes true…true false…false. Flip it, or the boundary you find is meaningless.
- **Reading `items[lower]` without checking.** The lower bound can be `count`. Check `lower < items.count` before you look.
- **Mixing up ≥ and >.** Lower bound is ≥, upper bound is >. If your "last occurrence" is off by one, this is usually why.
</Callout>

## Practice

**First and last position of a value** asks for the whole run of copies as a `ClosedRange`, in O(log n) even when the run is enormous. Finding one copy and then walking outwards works, but it's O(n) when every value is the same, and the large test is built to catch exactly that.

```cards

  front: "What are the lower bound and upper bound of x in a sorted array?"
  back: "Lower bound: the first index with a value ≥ x. Upper bound: the first index with a value > x. Either can be `count`."
- id: count-copies
  front: "How do you count the copies of x in a sorted array in O(log n)?"
  back: "`upperBound(x) - lowerBound(x)`. It's 0 when x is missing, with no special case."
- id: first-true
  front: "In the \"first index where a condition becomes true\" search, why is the true branch `high = mid` rather than `mid - 1`?"
  back: "A true mid might be the first true, so it must stay in the range. Progress is still guaranteed because mid is always less than high."
- id: monotonic-condition
  front: "What must be true of the condition you give a lower-bound style binary search?"
  back: "It must be monotonic: false for every index before some point and true from there on. `$0 >= x` works on sorted data; `$0 == x` doesn't."
```
