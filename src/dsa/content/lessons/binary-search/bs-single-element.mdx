## Why it matters

A sorted array holds pairs of equal values, except for one value that appears only once. Find it. Picture a sorted list of ticket numbers where every booking has an outbound and a return ticket, except one passenger who only bought one way, or a ledger where every transfer is recorded twice, once at each end, apart from one. The values don't tell you where the loner is; the **positions** of the pairs do. That makes it a favourite interview question, and a neat lesson in finding a monotonic yes/no question where there doesn't seem to be one.

## The problem, and the O(n) answers

```text
index   0  1  2  3  4  5  6  7  8
value   1  1  2  3  3  4  4  8  8
```

Every value appears twice, except 2.

Two quick solutions take O(n):

- **Walk the pairs.** Compare `numbers[0]` with `numbers[1]`, then `numbers[2]` with `numbers[3]`, and so on. The first pair that doesn't match starts with the single value.
- **XOR everything.** As [XOR tricks](/dsa/learn/bits-xor-tricks) showed, `numbers.reduce(0, ^)` cancels every pair and leaves the single value. It doesn't even need the array to be sorted.

Both are fine answers for small inputs. But XOR ignores the sorted order completely, and when a problem hands you sorted data and asks for something faster than O(n), that's a strong hint that binary search is possible.

## Pairs and parity

Look at **where** each pair starts:

| index | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| value | 1 | 1 | 2 | 3 | 3 | 4 | 4 | 8 | 8 |
| | pair | | single | pair | | pair | | pair | |

- **Before** the single value, pairs start at **even** indexes: the 1s fill indexes 0 and 1.
- The single value itself is at an even index, 2, because only whole pairs come before it.
- **After** it, everything is shifted along by one, so pairs start at **odd** indexes: 3 and 4, 5 and 6, 7 and 8.

So ask this question at each even index i: **"does `numbers[i]` equal `numbers[i + 1]`?"** Before the single value the answer is yes: i starts a pair. At the single value it's no. After it, i is the *second* half of a pair that started at i − 1, so `numbers[i + 1]` belongs to the next pair, and the answer is still no. Over the even indexes, the answers go yes, yes, …, no, no, no: monotonic. The single value is at the **first no**.

<Callout kind="analogy">
Couples queue for a ride, each pair holding hands, and the queue's places are numbered from 0. One person came alone. Everyone ahead of them stands in places 0 and 1, 2 and 3, and so on: every couple starts on an even place. Everyone behind them is pushed back one place, so every couple starts on an odd one. Check any even place and you know which side of the loner you're on.
</Callout>

## The search

Look only at even indexes. If the middle is odd, step back one. Then:

- If `numbers[mid] == numbers[mid + 1]`, the pairs are still intact through `mid + 1`, so the single value is further right: `low = mid + 2`.
- Otherwise the pattern has already broken: the single value is at mid or to its left, so `high = mid`.

`low` starts at 0 and `high` at the last index, which is even because the array has an odd length. Both updates keep them even, so when they meet, they meet on the single value.

```swift run
func single(in numbers: [Int]) -> Int {
    var low = 0
    var high = numbers.count - 1               // both even: the single value is in [low, high]
    while low < high {
        var mid = low + (high - low) / 2
        if mid % 2 == 1 {
            mid -= 1                           // check the pair that should start at an even index
        }
        let intact = numbers[mid] == numbers[mid + 1]
        print("  [\(low), \(high)], mid \(mid): \(numbers[mid]) and \(numbers[mid + 1])", intact ? "match" : "differ")
        if intact {
            low = mid + 2                      // whole pairs up to here: look right
        } else {
            high = mid                         // broken already: the single value is mid or earlier
        }
    }
    return numbers[low]
}

print(single(in: [1, 1, 2, 3, 3, 4, 4, 8, 8]))
print(single(in: [3, 3, 7, 7, 10, 11, 11]))
print(single(in: [42]))
```

```output
  [0, 8], mid 4: 3 and 4 differ
  [0, 4], mid 2: 2 and 3 differ
  [0, 2], mid 0: 1 and 1 match
2
  [0, 6], mid 2: 7 and 7 match
  [4, 6], mid 4: 10 and 11 differ
10
42
```

What to notice:

- `mid + 1` is always a real index: mid is even and less than `high`, which is also even, so mid is at most `high - 2`.
- A one-element array never enters the loop and returns its only value.
- Each pass halves the range, so it's O(log n) time and O(1) space.

## A compact variant with XOR

There's a well-known shortcut that avoids adjusting mid. `mid ^ 1` flips the lowest bit of mid, from [The bitwise operators and masking shifts](/dsa/learn/bits-operators): for an even index it gives the next index, and for an odd index the previous one. In other words, it's the index of mid's partner **if** the pairs still start at even indexes. So `numbers[mid] == numbers[mid ^ 1]` is true before the single value and false from it onwards, for every index, odd or even:

```swift run
func single(in numbers: [Int]) -> Int {
    var low = 0
    var high = numbers.count - 1
    while low < high {
        let mid = low + (high - low) / 2
        if numbers[mid] == numbers[mid ^ 1] {   // mid's partner, if pairs start at even indexes
            low = mid + 1
        } else {
            high = mid
        }
    }
    return numbers[low]
}

print(single(in: [1, 1, 2, 3, 3, 4, 4, 8, 8]), single(in: [3, 3, 7, 7, 10, 11, 11]), single(in: [5, 6, 6]))
```

```output
2 10 5
```

It's the "first index where a condition becomes true" search again, with the condition "mid doesn't match its expected partner". Inside the loop mid is less than `high`, so `mid ^ 1` is at most `mid + 1` and never runs off the end. It's shorter but harder to explain on a whiteboard; the even-index version makes the reasoning visible.

<Callout kind="gotcha" title="Common mistakes">
- **Comparing the wrong pair.** If mid is odd, `numbers[mid]` and `numbers[mid + 1]` straddle two pairs, and the answer means nothing. Step back to an even index first (or use the `mid ^ 1` partner).
- **`low = mid + 1` in the even-index version.** It makes `low` odd, and the "both ends even" reasoning falls apart. Jump a whole pair: `mid + 2`.
- **Applying it when values can appear three times.** The parity argument needs every other value to appear exactly twice. With other counts, fall back to a scan.
</Callout>

## Practice

**The single value among pairs** asks for exactly this. The large test walks the single value through a thousand positions in an array of two million values, calling your function each time, so an O(n) scan or XOR has to do two billion steps, while the binary search does about twenty per call.

```cards
  back: "Before it, pairs start at even indexes. After it, they start at odd indexes. The single value itself is at an even index."
- id: single-search
  front: "In the single-element search, what do you do at an even mid?"
  back: "If numbers[mid] == numbers[mid + 1], the single value is to the right: low = mid + 2. Otherwise it's at mid or before: high = mid."
- id: partner-xor
  front: "What does `mid ^ 1` give, and why is it useful in the single-element search?"
  back: "It flips the lowest bit: mid + 1 for even mid, mid − 1 for odd mid. That's mid's partner if pairs still start at even indexes, so comparing with it tells you which side of the single value you're on."
```
