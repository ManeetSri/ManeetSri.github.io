## Why it matters

Finding things is one of the most common jobs a program does: the contact called "Priya", the first unread message, whether a username is taken. The simplest way is to look at every element in turn until you find it. That's **linear search**. It's the baseline every cleverer search is measured against, and surprisingly often it's the right choice. This module is about binary search, so it starts by being clear about when you don't need it.

## Look at each element in turn

Start at the front. Compare each element with the target. Stop at the first match and return its index; if you reach the end, the target isn't there.

```swift run
func linearSearch(_ items: [Int], for target: Int) -> Int? {
    for i in items.indices {
        if items[i] == target {
            return i                  // the first match wins
        }
    }
    return nil                        // looked everywhere: not here
}

let ages = [34, 7, 19, 52, 7, 41]
if let index = linearSearch(ages, for: 7) {
    print("7 is at index \(index)")
}
print(linearSearch(ages, for: 99) == nil)
```

```output
7 is at index 1
true
```

What to notice:

- The array isn't sorted, and that doesn't matter. Linear search makes no assumptions about order.
- There are two 7s. The search returns the first one, at index 1, and never looks at the second.
- "Not found" is `nil`, not a made-up index like -1. The return type `Int?` says so, as you saw in M04.

## The standard library does it for you

You rarely write that loop yourself. Every Swift collection has linear searches built in, as [sorted(by:), min, max, contains and first(where:)](/dsa/learn/swift-sorting-searching-api) showed:

```swift run
let ages = [34, 7, 19, 52, 7, 41]
print(ages.firstIndex(of: 7) as Any)
print(ages.lastIndex(of: 7) as Any)
print(ages.contains(52))
print(ages.firstIndex { $0 > 40 } as Any)
print(ages.first { $0 > 40 } as Any)
print(ages.firstIndex(of: 99) as Any)
```

```output
Optional(1)
Optional(4)
true
Optional(3)
Optional(52)
nil
```

`firstIndex(of:)` and `contains(_:)` need the elements to be `Equatable`. The `where:` versions take a closure, so they can search for anything you can describe: the first unread message, the first price over budget. `lastIndex(of:)` searches from the back. Every one of them is a loop like the one above, so every one is O(n).

## How long it takes

How many comparisons does a linear search make on n elements?

| Case | When | Comparisons |
| --- | --- | --- |
| best | the target is first | 1 |
| worst | the target is last, or absent | n |
| average | present, at a random position | about n / 2 |

Absent targets are the expensive ones: you can only say "not here" after checking everything. As [Best, average and worst case](/dsa/learn/bigo-cases) explained, we usually quote the worst case, so linear search is **O(n)**. Double the data and you double the work.

## When linear search is the right call

Reach for linear search, without guilt, when:

- **The data is unsorted and you'll search it once.** Sorting costs O(n log n), which is more than the O(n) scan it was meant to save.
- **The collection is tiny.** For a few dozen elements, a straight scan is as fast as anything and has nothing to get wrong.
- **You can't jump to the middle.** A linked list (M25) or a stream of values arriving one at a time only lets you walk forwards, so a scan is all you can do.
- **The question isn't about order.** "The first message from Sam" is a condition, not a position in sorted order. `first(where:)` is exactly right.

## When sorting first pays off

Things change when you search the **same** data many times. Binary search, coming next, answers each question in about log₂ n steps, but it needs the data sorted first. So for q searches over n elements:

- q linear searches cost about **q × n**;
- sorting once and then binary searching costs about **n log n + q log n**.

Count both for n = 100,000, where log₂ n is about 17:

```swift run
let n = 100_000
let steps = Int.bitWidth - n.leadingZeroBitCount     // about log₂ n: 17 for 100,000

for queries in [1, 10, 100, 10_000] {
    let linear = queries * n
    let sortFirst = n * steps + queries * steps
    print("\(queries) searches: linear \(linear), sort first \(sortFirst)")
}
```

```output
1 searches: linear 100000, sort first 1700017
10 searches: linear 1000000, sort first 1700170
100 searches: linear 10000000, sort first 1701700
10000 searches: linear 1000000000, sort first 1870000
```

For one search, linear wins easily: sorting alone costs 17 times more. By 100 searches, sorting first is about six times cheaper, and by 10,000 searches it's over 500 times cheaper. The break-even point is around log₂ n searches, here about 17. These are rough step counts, not timings, but the shape is what matters.

<Callout kind="tip" title="Only need yes or no?">
If every question is "is this value present?", a `Set` from [Patterns: frequency maps and two sum](/dsa/learn/hash-frequency-two-sum) answers in O(1) on average after an O(n) build, faster than binary search. Sorting wins when the questions involve **order**: the nearest value, the first value at least x, how many values fall in a range. Those are exactly what this module teaches.
</Callout>
