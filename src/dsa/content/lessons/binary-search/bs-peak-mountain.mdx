## Why it matters

Every search so far needed some sorted order. This lesson's arrays aren't sorted at all, and binary search still works. A **peak** is a value higher than its neighbours: the summit on a hiking app's elevation profile, the loudest moment in a recording, the setting of a dial where performance stops improving and starts getting worse. You can find *a* peak in O(log n) by asking one question at the middle: which way is uphill? The lesson to take away is bigger than peaks. Binary search needs a question whose answer tells you which half is guaranteed to contain an answer, and nothing more.

## What a peak is

Index i is a **peak** if its value is bigger than each neighbour it has. The first and last elements have only one neighbour each; imagine the values beyond both ends as lower than anything. In this lesson, **neighbouring values are never equal**.

```text
index    0   1   2   3   4   5   6
height   1   3   2   4   7   6   5
             ^           ^
           peak        peak
```

Index 1 (3 beats 1 and 2) and index 4 (7 beats 4 and 6) are both peaks. Index 6 isn't: 5 is smaller than its neighbour 6.

Every non-empty array has at least one peak, because the largest value beats everything, its neighbours included. But finding the largest value means looking at every element, O(n). If **any** peak will do, you can be much faster.

## Walk uphill

Look at the middle and its right neighbour.

- **If `heights[mid] < heights[mid + 1]`**, the ground rises to the right. Keep walking right from mid. Either the values rise all the way to the end, and the last element is a peak (beyond the end counts as lower), or they turn downwards somewhere, and where they turn is a peak. Either way, there's a peak to the right of mid: `low = mid + 1`.
- **Otherwise** the ground falls to the right, and the mirror argument says there's a peak at mid or to its left: `high = mid`.

<Callout kind="analogy">
You're on a hillside in thick fog and can only see one step ahead. Keep stepping uphill and you must reach a summit eventually: the ground can't rise for ever. It may not be the highest summit in the range, but it is a summit.
</Callout>

The invariant is a little stronger than "there's a peak in `[low, high]`": **the value at `low` is higher than the one to its left, and the value at `high` is higher than the one to its right** (counting beyond the ends as lower). Both updates keep that true: `low = mid + 1` happens because `heights[mid + 1]` beats `heights[mid]`, its left neighbour, and `high = mid` happens because `heights[mid]` beats its right neighbour. When `low == high`, one element beats both neighbours, so it's a peak.

```swift run
func peakIndex(_ heights: [Int]) -> Int {
    var low = 0
    var high = heights.count - 1
    while low < high {
        let mid = low + (high - low) / 2       // mid < high, so mid + 1 is a real index
        print("  [\(low), \(high)], mid \(mid): \(heights[mid]) vs \(heights[mid + 1])")
        if heights[mid] < heights[mid + 1] {
            low = mid + 1                      // uphill to the right
        } else {
            high = mid                         // downhill: mid could be the peak
        }
    }
    return low
}

let profile = [1, 3, 2, 4, 7, 6, 5]
let peak = peakIndex(profile)
print("peak at \(peak), height \(profile[peak])")
print(peakIndex([1, 2, 3, 4, 5]), peakIndex([5, 4, 3, 2, 1]))
```

```output
  [0, 6], mid 3: 4 vs 7
  [4, 6], mid 5: 6 vs 5
  [4, 5], mid 4: 7 vs 6
peak at 4, height 7
  [0, 4], mid 2: 3 vs 4
  [3, 4], mid 3: 4 vs 5
  [0, 4], mid 2: 3 vs 2
  [0, 2], mid 1: 4 vs 3
  [0, 1], mid 0: 5 vs 4
4 0
```

What to notice:

- It found the peak at index 4 and never looked at the peak at index 1. Any peak is a correct answer.
- On a steadily rising array the peak is the last element, and on a falling one it's the first. The edge rule makes both work with no special cases.
- The loop runs while `low < high`, so `mid` is always less than `high` and `heights[mid + 1]` is never out of range.
- `print(a, b)` evaluates both calls before printing, which is why both traces appear before the line `4 0`.

## Mountain arrays

A **mountain array** rises strictly to a single summit and then falls strictly: `[120, 340, 560, 910, 780, 560, 230]`. It has exactly one peak, the summit, so `peakIndex` finds it.

There's another way to see it. Ask of each index, "is the next value lower?" On the way up the answer is no, and on the way down it's yes: no, no, no, yes, yes, yes. That's a monotonic condition, and the summit is its **first yes**. So the summit search is the "first index where a condition becomes true" search from [Lower bound, upper bound, first and last occurrence](/dsa/learn/bs-bounds), with the condition `heights[i] > heights[i + 1]`. The peak search above is the same loop. In a mountain, it's guaranteed to find the one and only summit.

## Searching a mountain

To find a value in a mountain array, split the problem into searches you already know:

1. Find the summit.
2. Binary search the rising side, from 0 to the summit, which is sorted in increasing order.
3. If it isn't there, binary search the falling side, which is sorted in **decreasing** order, so the comparisons flip.

A value can appear once on each side. Searching the rising side first returns the smaller index.

```swift run
func summit(_ heights: [Int]) -> Int {
    var low = 0
    var high = heights.count - 1
    while low < high {
        let mid = low + (high - low) / 2
        if heights[mid] < heights[mid + 1] { low = mid + 1 } else { high = mid }
    }
    return low
}

func search(_ heights: [Int], for target: Int, in range: ClosedRange<Int>, rising: Bool) -> Int? {
    var low = range.lowerBound
    var high = range.upperBound
    while low <= high {
        let mid = low + (high - low) / 2
        if heights[mid] == target {
            return mid
        }
        let goRight = rising ? heights[mid] < target : heights[mid] > target
        if goRight { low = mid + 1 } else { high = mid - 1 }
    }
    return nil
}

func find(_ target: Int, inMountain heights: [Int]) -> Int? {
    let top = summit(heights)
    if let index = search(heights, for: target, in: 0...top, rising: true) {
        return index
    }
    guard top + 1 < heights.count else { return nil }
    return search(heights, for: target, in: (top + 1)...(heights.count - 1), rising: false)
}

let trail = [120, 340, 560, 910, 780, 560, 230]
print("summit at", summit(trail))
print(find(560, inMountain: trail) as Any, find(230, inMountain: trail) as Any, find(600, inMountain: trail) as Any)
```

```output
summit at 3
Optional(2) Optional(6) nil
```

560 appears on both sides, at 2 and 5; the rising side is searched first, so the answer is 2. Three binary searches, each O(log n), make O(log n) in total.

The `guard` matters when the summit is the last element: `(top + 1)...(count - 1)` would then be a closed range whose lower end is above its upper end, and Swift traps when you create one.

<Callout kind="gotcha" title="Flat stretches break it">
Everything here relies on neighbours never being equal. If `heights[mid] == heights[mid + 1]`, you can't tell uphill from downhill. In `[5, 5, 5, 5, 6, 5, 5]`, the only peak hides in a flat sea of 5s, and, like the rotated array full of 1s, no algorithm can find it without potentially checking every element. With plateaus allowed, peak finding is O(n) in the worst case.
</Callout>
