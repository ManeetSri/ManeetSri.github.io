## Why it matters

Binary search is the workhorse, but it assumes three things: you know where the data ends, jumping anywhere is equally cheap, and you know nothing about how the values are spread. Change those assumptions and other searches appear. **Exponential search** handles data whose end you don't know, like a paged API or an endless sorted stream. **Jump search** moves backwards only once. **Interpolation search** guesses where a value should be, the way you open a phone book near the back for "Williams". **Ternary search** finds the top of a hill. This deep dive shows each one, what it costs, and why plain binary search usually still wins.

## Exponential search: when you don't know the end

Suppose you can read the value at any index, but you don't know how many there are: reading past the end returns `nil`. Binary search needs a `high` to start from. Exponential search finds one by **galloping**: check index 1, 2, 4, 8, 16, … until the value there is at least the target, or you run off the end. The target must then lie between the last two indexes checked, and a binary search between them finishes the job.

```swift run
// 999,999 sorted values whose count the search pretends not to know
let hidden = Array(stride(from: 3, to: 3_000_000, by: 3))
var probes = 0

func value(at index: Int) -> Int? {
    probes += 1
    return index < hidden.count ? hidden[index] : nil       // nil past the end
}

func exponentialSearch(for target: Int) -> Int? {
    // 1. Gallop: double the bound until it reaches the target or passes the end
    var bound = 1
    while let found = value(at: bound), found < target {
        bound *= 2
    }
    // 2. Binary search between the last two bounds
    var low = bound / 2
    var high = bound
    while low <= high {
        let mid = low + (high - low) / 2
        guard let found = value(at: mid) else {
            high = mid - 1                                   // past the end counts as too big
            continue
        }
        if found == target {
            return mid
        } else if found < target {
            low = mid + 1
        } else {
            high = mid - 1
        }
    }
    return nil
}

for target in [3, 30, 3_000, 2_999_997, 4] {
    probes = 0
    let index = exponentialSearch(for: target)
    print("\(target): index \(index.map { String($0) } ?? "none"), \(probes) probes")
}
```

```output
3: index 0, 2 probes
30: index 9, 7 probes
3000: index 999, 20 probes
2999997: index 999998, 39 probes
4: index none, 3 probes
```

If the target is at index i, galloping takes about log₂ i steps, and the binary search covers a range of about i, another log₂ i. So exponential search is **O(log i)**: it depends on where the target is, not on how much data there is. Targets near the front are found in a handful of probes, and even the very last of a million values takes 39, about double a plain binary search, without ever knowing the length. Timsort, the sort Python uses, gallops like this when merging runs, because the next value often turns out to be close by.

## Jump search: blocks of √n

Jump search moves forwards in fixed jumps of k positions, checking the last value of each block. When a block's last value reaches the target, the target can only be inside that block, so it steps back to the start of the block and walks through it.

With n values there are up to n / k jumps, then up to k steps inside a block. The total n / k + k is smallest when k = √n, giving about 2√n comparisons:

```swift run
func jumpSearch(_ items: [Int], for target: Int) -> (index: Int?, comparisons: Int) {
    let n = items.count
    let step = max(1, Int(Double(n).squareRoot()))
    var comparisons = 0
    var blockStart = 0
    // Jump while the last value of the current block is still too small
    while blockStart < n {
        let blockEnd = min(blockStart + step, n) - 1
        comparisons += 1
        if items[blockEnd] >= target { break }
        blockStart += step
    }
    // Walk through that one block
    var i = blockStart
    while i < min(blockStart + step, n) {
        comparisons += 1
        if items[i] == target { return (i, comparisons) }
        if items[i] > target { break }
        i += 1
    }
    return (nil, comparisons)
}

let items = Array(0..<1_000_000)
print(jumpSearch(items, for: 123_456))
print(jumpSearch(items, for: 999_999))
```

```output
(index: Optional(123456), comparisons: 581)
(index: Optional(999999), comparisons: 2000)
```

O(√n): far better than linear, far worse than binary search's 20. Its one advantage is that it only ever moves **backwards once**, by at most one block. That mattered for data on magnetic tape, where rewinding is slow, and the same idea of "express lanes" that skip ahead, plus a slow lane to finish, reappears in a data structure called a skip list. Today you'll rarely write it, but you should recognise it.

## Interpolation search: guess where it should be

Looking up "Williams" in a paper phone book, you don't open it in the middle. W is near the end of the alphabet, so you open it near the back. Interpolation search does the same with numbers: instead of the middle, it probes where the target **would** be if the values were spread evenly between `items[low]` and `items[high]`:

```text
position = low + (target − items[low]) × (high − low) / (items[high] − items[low])
```

```swift run
func interpolationSearch(_ items: [Int], for target: Int) -> (index: Int?, probes: Int) {
    var low = 0
    var high = items.count - 1
    var probes = 0
    while low <= high && target >= items[low] && target <= items[high] {
        probes += 1
        if items[high] == items[low] {                       // avoid dividing by zero
            return (items[low] == target ? low : nil, probes)
        }
        let position = low + (target - items[low]) * (high - low) / (items[high] - items[low])
        if items[position] == target {
            return (position, probes)
        } else if items[position] < target {
            low = position + 1
        } else {
            high = position - 1
        }
    }
    return (nil, probes)
}

let n = 100_000
let even = (0..<n).map { $0 * 10 + ($0 * 7_919) % 10 }       // evenly spread, slightly jittered
let lopsided = Array(0..<(n - 1)) + [1_000_000_000_000]       // one huge value at the end

print("even:", interpolationSearch(even, for: even[73_210]))
print("lopsided:", interpolationSearch(lopsided, for: 99_990))
```

```output
even: (index: Optional(73210), probes: 2)
lopsided: (index: Optional(99990), probes: 99991)
```

On evenly spread data, the first guess lands almost on top of the target: 2 probes where binary search needs about 17. In theory, for values spread uniformly at random, interpolation search averages **O(log log n)** probes, about 5 for a billion values.

On lopsided data it collapses. One giant value at the end makes every guess land at `low`, so each probe moves one step: 99,991 probes, **O(n)**, worse than binary search by a factor of thousands. Real data is rarely as uniform as the theory needs, which is why libraries stick to binary search. Interpolation search also has sharp edges: it must avoid dividing by zero, and `(target − items[low]) × (high − low)` can overflow for large values.

## Ternary search: the top of a hill

A function is **unimodal** if it rises to a single peak and then falls, like the mountain arrays in [Peak element and mountain arrays](/dsa/learn/bs-peak-mountain). Think of profit as you raise a price: it climbs, peaks, then drops as customers leave.

**Ternary search** finds the peak by checking two points that split the range into thirds, m1 and m2. If f(m1) < f(m2), the peak can't be at or before m1, because m1 is still on the way up, so discard the left third. Otherwise, discard the right third. Each step keeps two thirds of the range and costs two evaluations of f.

But you already know a better way. **Binary search on the slope**, comparing f(mid) with f(mid + 1) exactly as the peak lesson did, keeps half the range for the same two evaluations. Count them:

```swift run
var evaluations = 0
func profit(_ price: Int) -> Int {
    evaluations += 1
    return -(price - 6_180) * (price - 6_180)               // rises to a peak at 6,180, then falls
}

func ternaryPeak(_ low: Int, _ high: Int) -> Int {
    var low = low
    var high = high
    while low < high {
        let third = (high - low) / 3
        let m1 = low + third
        let m2 = high - third
        if profit(m1) < profit(m2) {
            low = m1 + 1                                     // m1 is on the way up
        } else {
            high = m2 - 1                                    // m2 is on the way down, or level with m1
        }
    }
    return low
}

func slopePeak(_ low: Int, _ high: Int) -> Int {
    var low = low
    var high = high
    while low < high {
        let mid = low + (high - low) / 2
        if profit(mid) < profit(mid + 1) {
            low = mid + 1                                    // uphill to the right
        } else {
            high = mid
        }
    }
    return low
}

evaluations = 0
print("ternary:", ternaryPeak(0, 10_000), "after", evaluations, "evaluations")
evaluations = 0
print("slope:", slopePeak(0, 10_000), "after", evaluations, "evaluations")
```

```output
ternary: 6180 after 42 evaluations
slope: 6180 after 26 evaluations
```

Both find the peak, but binary search on the slope needs about 40% fewer evaluations, and it's the same loop you already trust. In general, ternary search uses about 2 log₁.₅ n ≈ 3.4 log₂ n evaluations against binary search's 2 log₂ n. Ternary search still turns up for functions over **real numbers**, where "the next value to the right" isn't defined; even there, a refinement called golden-section search reuses one point each step to save evaluations. On whole numbers, search the slope.

Both need the function to be **strictly** unimodal. A flat stretch, where f(m1) equals f(m2) without the peak being between them, breaks them exactly as plateaus broke peak finding.

## Choosing a search

| Search | Needs | Time | Use it when |
| --- | --- | --- | --- |
| linear | nothing | O(n) | unsorted, tiny, or searched once |
| binary | sorted, O(1) jumps | O(log n) | almost always, on sorted data |
| exponential | sorted, O(1) jumps | O(log i) for a target at i | the end is unknown, or targets are usually near the front |
| jump | sorted | O(√n) | moving backwards is expensive |
| interpolation | sorted, evenly spread numbers | O(log log n) average, O(n) worst | rarely: only for data known to be uniform |
| ternary | a strictly unimodal function | O(log n), with more evaluations | real-valued functions; on integers, search the slope instead |
