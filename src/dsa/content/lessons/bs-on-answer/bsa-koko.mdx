## Why it matters

"What's the slowest rate that still meets the deadline?" A background sync wants the lowest network rate that finishes before morning, so it doesn't drain the battery. A render queue wants the fewest frames per second that still finishes a batch of videos on time. Going faster always helps, so "fast enough?" is a monotonic question, and the slowest rate that works is a first true. This lesson's classic version is the gentlest first application of binary search on the answer, and it brings a small arithmetic trick you'll use again and again: ceiling division without `Double`.

## The problem

The classic story goes like this. Koko has several piles of bananas and h hours before the keepers come back. She chooses an eating speed of s bananas per hour, a whole number. Each hour, she picks one pile and eats up to s bananas from it. If the pile has fewer than s left, she finishes it and rests for the rest of that hour: she never moves on to another pile within the same hour. What's the **smallest** speed that lets her finish every pile within h hours?

Take piles of 5, 9, 4 and 12 bananas, and h = 7 hours:

- At speed 4, the piles take 2, 3, 1 and 3 hours: 9 in total. Too slow.
- At speed 5, they take 1, 2, 1 and 3 hours: 7 in total. That works.

So the answer is 5. Notice how the rule "never move on within an hour" wastes time: at speed 4, the pile of 5 takes a whole second hour for its last banana.

## Hours at one speed: ceiling division

A pile of p bananas at speed s takes p / s hours, **rounded up**: ⌈p / s⌉. Swift's `/` on integers rounds down, so use the trick from [Floor and ceiling division, and overflow](/dsa/learn/math-floor-ceil-overflow): for positive p and s, ⌈p / s⌉ is `(p + s - 1) / s`. Adding s − 1 pushes any leftover past the next multiple of s.

```swift run
func hoursNeeded(_ piles: [Int], speed: Int) -> Int {
    var hours = 0
    for pile in piles {
        hours += (pile + speed - 1) / speed      // ⌈pile / speed⌉
    }
    return hours
}

let piles = [5, 9, 4, 12]
for speed in 1...7 {
    print("speed \(speed): \(hoursNeeded(piles, speed: speed)) hours")
}
```

```output
speed 1: 30 hours
speed 2: 16 hours
speed 3: 11 hours
speed 4: 9 hours
speed 5: 7 hours
speed 6: 6 hours
speed 7: 6 hours
```

The hours never go up as the speed goes up, because no single pile takes longer at a faster speed. So the predicate "finishes within 7 hours", `hoursNeeded(piles, speed: s) <= 7`, reads false, false, false, false, true, true, true. It's monotonic, and the answer is its first true.

Why not `Double`? `Int((Double(p) / Double(s)).rounded(.up))` gives the same answer for small numbers, but it converts types twice on every pile, and a `Double` stops holding whole numbers exactly past 2⁵³. The integer trick is exact, fast and needs no Foundation.

## Honest bounds

**Low is 1.** A speed must be positive. Speed 0 never finishes anything, and `(p + 0 - 1) / 0` would crash with a division by zero.

**High is the largest pile.** At that speed, every pile takes exactly one hour, so the total is the number of piles. The problem promises `h >= piles.count`, so that always fits. Going even faster can't help: a pile can't take less than one hour.

If h were smaller than the number of piles, no speed at all would work, since every pile takes at least an hour. Real code should check for that before searching.

You can tighten low, honestly: in h hours at speed s she eats at most s × h bananas, so s must be at least ⌈total / h⌉. It saves a few checks, but plain 1 is also correct. When in doubt, choose the bound you can justify in one sentence.

## The solution

```swift run
func hoursNeeded(_ piles: [Int], speed: Int) -> Int {
    var hours = 0
    for pile in piles {
        hours += (pile + speed - 1) / speed
    }
    return hours
}

func minimumSpeed(_ piles: [Int], hours h: Int) -> Int {
    var low = 1
    var high = piles.max()!              // always fast enough, because h >= piles.count
    while low < high {
        let mid = low + (high - low) / 2
        let needed = hoursNeeded(piles, speed: mid)
        print("speed \(mid): \(needed) hours")
        if needed <= h {
            high = mid                   // fast enough: the answer is mid or slower
        } else {
            low = mid + 1                // too slow
        }
    }
    return low
}

print(minimumSpeed([5, 9, 4, 12], hours: 7))
```

```output
speed 6: 6 hours
speed 3: 11 hours
speed 5: 7 hours
speed 4: 9 hours
5
```

Step through the same search. Red speeds are known to be too slow, green ones known to be fast enough, and each check shows the hours per pile:

```visual answerSearch

```

What to notice:

- This is the first-true template from [The monotonic predicate idea](/dsa/learn/bsa-idea), written inline as you would in an interview.
- `high` starts at a speed that's **known to work**, the largest pile, rather than one past it. That's fine: in the half-open view, the candidates are `1..<12`, and 12 plays the part of "past the end". If nothing slower works, the loop stops at 12, which is correct.
- The force unwrap in `piles.max()!` is safe because the problem promises at least one pile.

## Early exit, and why the range doesn't matter much

At speed 1, the total hours are the sum of all the piles: with 100,000 piles of up to 10⁹ bananas, that's up to 10¹⁴. That fits easily in a 64-bit `Int`, but there's no need to finish counting once the total passes h. Stopping early saves time on slow speeds and makes overflow impossible however large the input:

```swift
func finishes(_ piles: [Int], speed: Int, within h: Int) -> Bool {
    var hours = 0
    for pile in piles {
        hours += (pile + speed - 1) / speed
        if hours > h { return false }    // already too slow
    }
    return true
}
```

Each check is O(n) for n piles, and there are about log₂ M checks, where M is the largest pile. That's **O(n log M)** in total, with O(1) extra space. Huge piles barely cost more than small ones:

```swift run
func finishes(_ piles: [Int], speed: Int, within h: Int) -> Bool {
    var hours = 0
    for pile in piles {
        hours += (pile + speed - 1) / speed
        if hours > h { return false }
    }
    return true
}

func minimumSpeed(_ piles: [Int], hours h: Int) -> (speed: Int, checks: Int) {
    var low = 1
    var high = piles.max()!
    var checks = 0
    while low < high {
        let mid = low + (high - low) / 2
        checks += 1
        if finishes(piles, speed: mid, within: h) { high = mid } else { low = mid + 1 }
    }
    return (low, checks)
}

let piles = [1_000_000_000, 999_999_999, 123_456_789]
print(minimumSpeed(piles, hours: 7))
print(minimumSpeed(piles, hours: 1_000_000_000))
```

```output
(speed: 333333334, checks: 30)
(speed: 3, checks: 30)
```

A billion possible speeds, and 30 checks each time. Trying speeds 1, 2, 3, … in turn would need 333 million checks for the first case.

<Callout kind="gotcha" title="Rounding up the wrong way">
**`pile / speed + 1` isn't the ceiling.** It's one too many whenever the division is exact: 10 bananas at speed 5 take 2 hours, not 3. Use `(pile + speed - 1) / speed`, or `pile / speed + (pile % speed == 0 ? 0 : 1)` if the values could be close to `Int.max`.

**Starting low at 0** crashes on the first probe that reaches it:

```text title="What you'll see"
Fatal error: Division by zero
```
</Callout>
