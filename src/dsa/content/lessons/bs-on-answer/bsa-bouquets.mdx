## Why it matters

Sometimes the answer is a **time**. On what day will enough adjacent seats have been released to seat a group together? When will enough servers have finished updating to roll out a feature in blocks? Time questions are naturally monotonic, because once something has happened, it stays happened. This lesson's classic problem adds two wrinkles you'll meet again: an **impossible case** you must catch before searching, and an **overflow trap** hiding inside that check.

## The problem

A row of flowers is planted, and flower i blooms on day `bloomDay[i]`, then stays in bloom. A bouquet needs k **adjacent** bloomed flowers, and each flower can go into at most one bouquet. What's the earliest day on which you can make m bouquets? If it's never possible, return −1.

Take `bloomDay = [3, 9, 2, 8, 4, 1, 7]`, with m = 2 bouquets of k = 2 flowers each. By day 4, flowers 1, 2, 3 and 4 have bloomed, but only two of them are neighbours. Read on to see when the second bouquet appears.

## Counting bouquets on a given day

For a fixed day, walk along the row and count the current run of bloomed flowers. Each time the run reaches k, that's a bouquet, and the run starts again from zero, because those flowers are used up. A flower that hasn't bloomed breaks the run.

```swift run
func bouquets(on day: Int, _ bloomDay: [Int], size k: Int) -> Int {
    var made = 0
    var run = 0                      // adjacent bloomed flowers not yet in a bouquet
    for bloom in bloomDay {
        if bloom <= day {
            run += 1
            if run == k {
                made += 1
                run = 0
            }
        } else {
            run = 0
        }
    }
    return made
}

let bloomDay = [3, 9, 2, 8, 4, 1, 7]
for day in [3, 4, 7, 8, 9] {
    let row = bloomDay.map { $0 <= day ? "x" : "." }.joined()
    print("day \(day): \(row) makes \(bouquets(on: day, bloomDay, size: 2))")
}
```

```output
day 3: x.x..x. makes 0
day 4: x.x.xx. makes 1
day 7: x.x.xxx makes 1
day 8: x.xxxxx makes 2
day 9: xxxxxxx makes 3
```

Each `x` is a bloomed flower. On day 7, the run `xxx` holds only one bouquet of 2: the third flower has no partner. On day 8, flower 3 blooms and joins a run of five, which holds two bouquets. So the answer is **day 8**.

Is "at least m bouquets by day d" monotonic? Yes. A later day only adds bloomed flowers, which lengthens or joins runs, and a longer run never holds fewer bouquets. So the predicate is false, …, false, true, …, true, and you want the first true.

## The impossible case

Every bouquet needs k flowers of its own, so m bouquets need m × k flowers. If m × k is more than the n flowers in the row, no day will ever do: return −1 before searching. If m × k ≤ n, then on the last bloom day every flower is out, the whole row is one run, and it holds ⌊n / k⌋ ≥ m bouquets. So the answer exists.

### The overflow trap in m × k

Swift checks every multiplication and stops the program when the result doesn't fit, as you saw in [Overflow traps and overflow operators](/dsa/learn/swift-overflow). If m and k can each be as large as 10¹⁰, then m × k can reach 10²⁰, far past `Int.max`, which is about 9.2 × 10¹⁸. The innocent-looking check `m * k > n` crashes.

In languages whose integers are 32 bits, the same check overflows for much smaller inputs and quietly produces a wrong answer instead. Either way, avoid the multiplication:

- **Divide instead.** For positive whole numbers, m × k > n is the same as m > ⌊n / k⌋. If m ≤ ⌊n / k⌋, then m × k ≤ ⌊n / k⌋ × k ≤ n. And if m ≥ ⌊n / k⌋ + 1, then m × k ≥ (⌊n / k⌋ + 1) × k, which is more than n.
- **Or ask Swift.** `multipliedReportingOverflow(by:)` returns the wrapped result together with a flag saying whether it overflowed.

```swift run
let n = 7
let m = 10_000_000_000
let k = 10_000_000_000
print(m > n / k)                                   // the same as m × k > n, with no multiplication
let (product, overflow) = m.multipliedReportingOverflow(by: k)
print(overflow, product)
```

```output
true
true 7766279631452241920
```

The wrapped product is meaningless, which is exactly why the flag matters. The division form is shorter and reads well, so the solution below uses it.

## Bounds, and an answer that's always a bloom day

**Low is the earliest bloom day**: before it, nothing has bloomed. **High is the latest bloom day**: by then everything has, and the impossible case is already ruled out.

The bouquet count only changes on days when some flower blooms. So the first day that works is always one of the values in `bloomDay`, even though the search also tries days like 5 or 6 when nothing happens. That gives an alternative: sort the distinct bloom days and binary search over that array's indexes. It's equally correct, but it costs O(n log n) for the sort and O(n) extra space, so searching the range of days directly is simpler.

## The solution

```swift run
func bouquets(on day: Int, _ bloomDay: [Int], size k: Int) -> Int {
    var made = 0
    var run = 0
    for bloom in bloomDay {
        if bloom <= day {
            run += 1
            if run == k {
                made += 1
                run = 0
            }
        } else {
            run = 0
        }
    }
    return made
}

func earliestDay(_ bloomDay: [Int], bouquets m: Int, size k: Int) -> Int {
    guard m <= bloomDay.count / k else { return -1 }     // m × k > n, without multiplying
    var low = bloomDay.min()!
    var high = bloomDay.max()!                           // every flower is out by then
    while low < high {
        let mid = low + (high - low) / 2
        if bouquets(on: mid, bloomDay, size: k) >= m {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

let bloomDay = [3, 9, 2, 8, 4, 1, 7]
print(earliestDay(bloomDay, bouquets: 2, size: 2))
print(earliestDay(bloomDay, bouquets: 3, size: 2))
print(earliestDay(bloomDay, bouquets: 1, size: 3))
print(earliestDay(bloomDay, bouquets: 4, size: 2))
print(earliestDay(bloomDay, bouquets: 10_000_000_000, size: 10_000_000_000))
```

```output
8
9
7
-1
-1
```

What to notice:

- One bouquet of 3 needs day 7, when the run of three at the end appears. On days 5 and 6 nothing blooms, so they look exactly like day 4.
- Four bouquets of 2 need 8 flowers, and there are only 7. The guard returns −1 straight away, and the huge request returns −1 without crashing.
- Without the guard, the search would return the last bloom day, 9, for an impossible request. The search always returns *some* day, so impossible cases must be handled separately.

With n flowers and bloom days up to D, each check is O(n) and there are about log₂ D checks: **O(n log D)** time and O(1) extra space.

<Callout kind="gotcha" title="Three slips in the count">
**Not resetting the run after a bouquet.** Then a run of three flowers with k = 2 counts as two bouquets, at flowers 1–2 and 2–3, sharing a flower.

**Using `<` instead of `<=`.** A flower that blooms on day d is available on day d. With `<`, every answer comes out one bloom later than it should.

**Checking `m * k > bloomDay.count`.** It works in every small test and crashes on large ones. Divide instead.
</Callout>
