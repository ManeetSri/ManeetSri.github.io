## Why it matters

Not every answer is a whole number. The moment two moving objects meet, the largest average a stretch of data can reach, the radius of the biggest circle that fits, the root of an equation with no neat formula: each is a real number. Binary search works on real numbers too. The predicate is still monotonic; only the stopping rule changes, along with a few traps that come from how `Double` stores numbers. In numerical computing this is called the **bisection method**, and it's the reliable fallback when cleverer methods misbehave. This lesson also covers the whole-number nth root, where staying away from `Double` is the whole point.

## Binary search on Double

Find the cube root of 2: the number r with r × r × r = 2. The predicate "r × r × r ≥ 2" is false for small r and true for large r, so the root is where it switches. Start with an interval that must contain it, [0, 2], and halve it:

```swift run
var low = 0.0
var high = 2.0
for step in 1...8 {
    let mid = (low + high) / 2
    if mid * mid * mid >= 2 {
        high = mid
    } else {
        low = mid
    }
    print("step \(step): [\(low), \(high)]")
}
```

```output
step 1: [1.0, 2.0]
step 2: [1.0, 1.5]
step 3: [1.25, 1.5]
step 4: [1.25, 1.375]
step 5: [1.25, 1.3125]
step 6: [1.25, 1.28125]
step 7: [1.25, 1.265625]
step 8: [1.2578125, 1.265625]
```

The true root, 1.2599…, stays inside the interval at every step, and the interval halves each time. Three things differ from the integer searches:

- **No `mid + 1` or `mid - 1`.** There's no "next number" to step past, so the updates are `low = mid` and `high = mid`.
- **The loop doesn't end with `low == high`.** It ends after a chosen number of halvings, or when the interval is narrow enough.
- **The answer is an interval.** The root lies between `low` and `high`, and either end, or the midpoint, is a fine estimate.

## When to stop: a fixed count, not an epsilon

The obvious stopping rule is `while high - low > 1e-9`: keep going until the interval is narrower than some small **epsilon**. For the cube root of 2, it stops after 31 steps. But it hides a trap.

A `Double` can't represent every real number, only a finite set of them, spaced further apart as numbers get bigger. The gap from a `Double` to the next one up is its `ulp`, short for "unit in the last place":

```swift run
print((1.0).ulp)
print((1e9).ulp)
print((1e18).ulp)
let big = 1e18
print(big + 1 == big)
```

```output
2.220446049250313e-16
1.1920928955078125e-07
128.0
true
```

Near a billion, neighbouring `Double`s are about 1.2 × 10⁻⁷ apart, so no interval there can ever be narrower than 10⁻⁹. Search for the square root of 10¹⁸ with an epsilon loop, and it never stops. This version has a safety limit of 1,000 steps, so you can see what happens:

```swift run
var low = 0.0
var high = 1e18
var steps = 0
while high - low > 1e-9 && steps < 1_000 {      // the step limit is only a safety net
    let mid = (low + high) / 2
    if mid * mid >= 1e18 {
        high = mid
    } else {
        low = mid
    }
    steps += 1
}
print(steps, high - low, high)
```

```output
1000 1.1920928955078125e-07 1000000000.0
```

It found the root, 10⁹, long before step 1,000. But the interval got stuck at one `ulp` wide: the midpoint of two neighbouring `Double`s rounds to one of them, so nothing changes, and `high - low > 1e-9` stays true forever.

The fix is to **halve a fixed number of times**, such as 100. That always finishes. Each halving shrinks the interval by half, so 100 halvings shrink it by 2¹⁰⁰, about 10³⁰, which is far more than a `Double`'s 15 to 17 significant digits can show. Once the ends are neighbours, further steps change nothing, which is harmless. In contests, `for _ in 0..<100` is the standard choice: simple, safe and always precise enough. (If you prefer an epsilon, make it relative to the size of the numbers, not a fixed 10⁻⁹.)

## The nth root of any x

Generalise to the nth root of any x ≥ 0. The predicate "rⁿ ≥ x" is monotonic for r ≥ 0, since raising a bigger non-negative number to a power gives a bigger result. Now the bounds need care:

- **Low is 0.**
- **High is max(1, x).** For x ≥ 1, the root is at most x. But for x below 1 the root is *bigger* than x: the square root of 0.25 is 0.5. Using high = x there would leave the answer outside the interval. Since such roots are still at most 1, max(1, x) covers both cases.

```swift run
import Foundation

func power(_ base: Double, _ n: Int) -> Double {
    var result = 1.0
    for _ in 0..<n {
        result *= base
    }
    return result
}

func nthRoot(_ x: Double, _ n: Int) -> Double {
    var low = 0.0
    var high = max(1.0, x)               // roots of numbers below 1 are bigger than the number
    for _ in 0..<100 {
        let mid = (low + high) / 2
        if power(mid, n) >= x {
            high = mid
        } else {
            low = mid
        }
    }
    return high
}

print(nthRoot(1e18, 6))
print(String(format: "%.6f", nthRoot(2, 3)))
print(String(format: "%.6f", nthRoot(0.25, 2)))
print(String(format: "%.6f", nthRoot(1e18, 6)))
print(String(format: "%.6f", nthRoot(10, 5)))
```

```output
1000.0000000000005
1.259921
0.500000
1000.000000
1.584893
```

`power` multiplies n times, which is fine for small n. For a large n, use [fast exponentiation](/dsa/learn/math-fast-power) instead. If `power` overflows to infinity for a huge mid, the comparison `infinity >= x` is still true, which still points the search the right way.

## Printing a Double answer the same way every time

The first line above printed `1000.0000000000005`, not `1000.0`. The last digit or two of a bisection result depend on exactly which end you return and how the rounding fell. Contest judges compare text, and so does this console's example checker, so print a **fixed number of decimal places**:

- **`String(format: "%.6f", value)`** rounds to 6 decimal places and keeps trailing zeros, as in `0.500000`. It comes from Foundation, so it needs `import Foundation` at the top of the file. You met it in [Probability and expected value](/dsa/learn/math-probability).
- **Without Foundation**, round by hand: multiply by 10⁶, round to a whole number, divide back. `print` then shows the shortest form, so trailing zeros disappear: 0.5 rather than 0.500000.

```swift run
let root = 1.2599210498948732
print((root * 1_000_000).rounded() / 1_000_000)
print((0.5 * 1_000_000).rounded() / 1_000_000)
```

```output
1.259921
0.5
```

## Whole-number roots: stay with Int

Often you want the **floor** of the nth root of an `Int`: the largest whole r with rⁿ ≤ x. It's tempting to use Foundation's `pow` and convert:

```swift run
import Foundation

for x in [64, 125, 216, 343, 1_000] {
    print(x, Int(pow(Double(x), 1.0 / 3.0)))
}
```

```output
64 3
125 4
216 5
343 6
1000 9
```

Every one of those is wrong. `1.0 / 3.0` can't be stored exactly and is a tiny bit less than a third, so `pow` returns something like 3.9999999999999996 for 64, and `Int(…)` cuts that down to 3. Perfect powers, the cases you'd most expect to work, are exactly the ones that break.

Instead, binary search over whole numbers. "rⁿ ≤ x" is true, …, true, false, …, so this is a **last true**: find the first r with rⁿ > x and subtract 1, as in [The monotonic predicate idea](/dsa/learn/bsa-idea). The one danger is computing rⁿ itself, which overflows for big r. So multiply one step at a time, and stop as soon as the next step would pass x. The test `result > x / r` asks "would result × r be more than x?" without multiplying:

```swift run
/// True if baseⁿ > limit, for base ≥ 1, without overflowing.
func power(_ base: Int, _ n: Int, exceeds limit: Int) -> Bool {
    var result = 1
    for _ in 0..<n {
        if result > limit / base { return true }     // result × base would pass limit
        result *= base
    }
    return false
}

/// The largest r with rⁿ ≤ x, for x ≥ 0 and n ≥ 1.
func floorRoot(_ x: Int, _ n: Int) -> Int {
    if n == 1 || x < 2 { return x }
    var low = 1
    var high = x                         // xⁿ > x here, so the first r with rⁿ > x is at most x
    while low < high {
        let mid = low + (high - low) / 2
        if power(mid, n, exceeds: x) {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low - 1                       // the last r with rⁿ ≤ x
}

for x in [64, 125, 216, 343, 1_000, 999] {
    print(x, floorRoot(x, 3))
}
print(floorRoot(Int.max, 2), floorRoot(Int.max, 3))
```

```output
64 4
125 5
216 6
343 7
1000 10
999 9
3037000499 2097151
```

Every answer is exact, right up to `Int.max`. Using `high = x` rather than `x + 1` matters at the very top: `Int.max + 1` would overflow before the search even began. It's safe here because, for n ≥ 2 and x ≥ 2, x itself is a candidate whose nth power is already more than x.

## Other searches on real numbers

The same pattern solves any equation f(x) = target where f only increases. Suppose a savings plan's final balance rises with the interest rate: bisect on the rate until the balance matches the goal. A more advanced contest classic is the **largest average** of any stretch of at least L values. Binary search on the average a. To check whether some stretch averages at least a, subtract a from every value and ask whether some stretch of length at least L has a sum of at least 0, which [prefix sums](/dsa/learn/prefix-1d) answer in O(n).

When the answer only needs a fixed number of decimals, you can often avoid `Double` altogether. If prices are in pence, search over whole pence with an `Int`.

<Callout kind="gotcha" title="Real-number traps">
**An epsilon loop that never ends.** `while high - low > 1e-9` can spin forever when the numbers are large. Loop a fixed number of times instead.

**Bounds that miss small inputs.** For x below 1, roots and many other answers are bigger than x. Start high at max(1, x).

**Comparing with `==`.** Bisection rarely lands exactly on a value, so never test `mid * mid == x`. Compare with `>=` and let the interval shrink, as in [Double, Float and floating-point precision](/dsa/learn/swift-floating-point).

**Printing raw Doubles.** Format to a fixed number of decimals, or round by hand, so the output doesn't depend on the last binary digit.
</Callout>
