## Why it matters

Batching under a size limit is everywhere. A photo app uploads images in requests of at most a few megabytes each. An analytics library sends queued events in network batches. A warehouse loads a conveyor's parcels onto trucks. The question "what's the smallest batch size that gets everything done in d rounds?" is the second classic application of binary search on the answer. It also introduces the **greedy check**, filling each batch as full as it'll go, that the next three lessons reuse.

## The problem

Packages wait on a conveyor belt in a fixed order, with weights such as `[6, 2, 9, 3, 5, 4, 8]`. Every day, one ship leaves. It takes packages from the front of the belt, in order, as long as the total stays within its capacity, and leaves when the next package wouldn't fit. Packages can't be reordered or split. What's the **smallest capacity** that ships everything within d days?

With d = 3 days, the total weight is 37, so you might hope for a capacity of ⌈37 / 3⌉ = 13. But the order gets in the way.

## The check: load greedily

For one capacity, simulate the loading. Keep adding packages to today's load; when the next one won't fit, start a new day.

```swift run
func dailyLoads(_ weights: [Int], capacity: Int) -> [[Int]] {
    var days: [[Int]] = [[]]
    var load = 0
    for weight in weights {
        if load + weight > capacity {        // doesn't fit: it goes tomorrow
            days.append([])
            load = 0
        }
        days[days.count - 1].append(weight)
        load += weight
    }
    return days
}

let weights = [6, 2, 9, 3, 5, 4, 8]
for capacity in [13, 16, 17, 20] {
    let days = dailyLoads(weights, capacity: capacity)
    print("capacity \(capacity): \(days.count) days \(days)")
}
```

```output
capacity 13: 4 days [[6, 2], [9, 3], [5, 4], [8]]
capacity 16: 4 days [[6, 2], [9, 3], [5, 4], [8]]
capacity 17: 3 days [[6, 2, 9], [3, 5, 4], [8]]
capacity 20: 2 days [[6, 2, 9, 3], [5, 4, 8]]
```

Every capacity from 13 to 16 gets stuck the same way: 6 + 2 + 9 = 17 won't fit, so the 9 waits, and each later day is short by one package. At 17, the first day takes all three, and three days are enough. The answer for d = 3 is **17**, well above the hopeful 13.

The search only needs the number of days, not the loads themselves:

```swift
func daysNeeded(_ weights: [Int], capacity: Int) -> Int {
    var days = 1
    var load = 0
    for weight in weights {
        if load + weight > capacity {
            days += 1
            load = 0
        }
        load += weight
    }
    return days
}
```

## Why greedy loading is right

Is filling each day as full as possible really the best plan? Could holding a package back for tomorrow ever help? No, and the reason is worth knowing, because the same argument proves the checks in the next three lessons.

Compare the greedy plan with **any** other plan that respects the capacity, and look at how many packages each has shipped after every day:

- **After day 1**, greedy has shipped at least as many. Greedy kept loading until the next package didn't fit, so the other plan, which can't overfill either, stopped at the same package or earlier.
- **After each later day**, greedy is still at least as far along. Suppose it was ahead (or level) last night. Today the other plan ships a run of packages that fits in the ship. Greedy starts today at the same point or further along, so the packages it needs to catch up to the other plan's position are part of that same run, which fits. Greedy loads at least those, and maybe more.

So greedy is never behind, and if any plan finishes within d days, greedy does too. This **"greedy stays ahead"** argument is a standard way to prove a greedy algorithm correct. You'll meet it again, more formally, in the greedy algorithms module in Part VII.

It also shows the predicate is monotonic. Any plan that works with capacity C also works with C + 1, so more capacity never needs more days: "ships within d days" is false, …, false, true, …, true.

## Honest bounds

**Low is the heaviest package.** With less, that package can never be loaded at all.

**High is the total weight.** With that capacity, the ship takes everything on day 1, and d is at least 1.

Every answer lies between them. You could also start low at max(heaviest, ⌈total / d⌉), since d days at capacity C carry at most d × C. It's honest, but as the example showed, the true answer can be far above it.

## The solution

```swift run
func daysNeeded(_ weights: [Int], capacity: Int) -> Int {
    var days = 1
    var load = 0
    for weight in weights {
        if load + weight > capacity {
            days += 1
            load = 0
        }
        load += weight
    }
    return days
}

func shipWithin(_ weights: [Int], days: Int) -> Int {
    var low = weights.max()!                 // anything less can't carry the heaviest package
    var high = weights.reduce(0, +)          // one day carries everything
    while low < high {
        let mid = low + (high - low) / 2
        if daysNeeded(weights, capacity: mid) <= days {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

let weights = [6, 2, 9, 3, 5, 4, 8]
for days in 1...7 {
    print("days \(days): capacity \(shipWithin(weights, days: days))")
}
```

```output
days 1: capacity 37
days 2: capacity 20
days 3: capacity 17
days 4: capacity 12
days 5: capacity 9
days 6: capacity 9
days 7: capacity 9
```

Here's the search for 4 days. Each check loads the packages greedily, day by day:

From 5 days on, the answer stops falling: it can never drop below the heaviest package, 9.

Each check is one O(n) pass, and the search makes about log₂(total − heaviest) checks. That's **O(n log S)** for n packages with total weight S, and O(1) extra space. With 100,000 packages of up to 10⁹ each, the total is at most 10¹⁴, which fits comfortably in an `Int`, and the search needs about 47 checks.

## The low bound is load-bearing

It's tempting to start low at 1, "to be safe". But the greedy check quietly assumes every package fits. When a package is heavier than the capacity, the `if` starts a new day and then loads it anyway, so the day count comes out too small:

```swift run
func daysNeeded(_ weights: [Int], capacity: Int) -> Int {
    var days = 1
    var load = 0
    for weight in weights {
        if load + weight > capacity {
            days += 1
            load = 0
        }
        load += weight
    }
    return days
}

func shipWithin(_ weights: [Int], days: Int, low start: Int) -> Int {
    var low = start
    var high = weights.reduce(0, +)
    while low < high {
        let mid = low + (high - low) / 2
        if daysNeeded(weights, capacity: mid) <= days { high = mid } else { low = mid + 1 }
    }
    return low
}

let weights = [6, 2, 9, 3, 5, 4, 8]
print("low = heaviest:", shipWithin(weights, days: 7, low: weights.max()!))
print("low = 1:", shipWithin(weights, days: 7, low: 1))
```

```output
low = heaviest: 9
low = 1: 6
```

A ship of capacity 6 can't carry the package that weighs 9, but the broken check said it could. The bound isn't only about speed: here it keeps the predicate honest. (Another fix is to make the check return "doesn't work" when any package is heavier than the capacity. Then low = 1 would be correct too.)

<Callout kind="gotcha" title="Two slips in the day count">
**Starting the count at 0.** The first day exists before any package is loaded, so `days` starts at 1. Starting at 0 makes every capacity look one day better than it is.

**Forgetting `load = 0`.** When a new day starts, the package that didn't fit becomes the first of the new load. Without the reset, the old load carries over, so every later package seems not to fit and gets a day of its own.
</Callout>
