## Why it matters

Dividing ordered work fairly is a common chore. Split a long audiobook into k episodes so that the longest episode is as short as possible. Hand a list of jobs, in order, to k workers who each take a contiguous chunk. Break a long article into k pages of similar length. Each asks you to **minimise the maximum**: make the biggest chunk as small as it can be. This lesson's problem goes by three famous names, split array largest sum, book allocation and painter's partition, and they're all the same problem. It's the textbook case of binary search on the answer, and the place to understand *why* the greedy check works.

## The problem

Split an array of positive numbers into exactly k **non-empty, contiguous** parts, keeping the order, so that the largest part sum is as small as possible. Return that largest sum.

Take `[4, 9, 3, 7, 2, 8]` with k = 3. Some ways to split it:

| Split | Part sums | Largest |
| --- | --- | --- |
| [4] [9, 3] [7, 2, 8] | 4, 12, 17 | 17 |
| [4, 9] [3, 7] [2, 8] | 13, 10, 10 | 13 |
| [4, 9] [3, 7, 2] [8] | 13, 12, 8 | 13 |
| [4, 9, 3] [7] [2, 8] | 16, 7, 10 | 16 |

The best is 13. The total is 33, so a perfectly even split would give 11 each, but the 9 and its neighbours make that impossible.

## Brute force first

Splitting into k parts means choosing k − 1 cut positions among the n − 1 gaps between values. Recursion can try them all: choose where the first part ends, then split the rest into k − 1 parts.

```swift run
// The smallest largest sum when values[start...] is split into `parts` non-empty parts
func bestSplit(_ values: [Int], from start: Int, parts: Int) -> Int {
    if parts == 1 {
        return values[start...].reduce(0, +)
    }
    var best = Int.max
    var first = 0
    for end in start...(values.count - parts) {      // leave one value for each later part
        first += values[end]
        best = min(best, max(first, bestSplit(values, from: end + 1, parts: parts - 1)))
    }
    return best
}

print(bestSplit([4, 9, 3, 7, 2, 8], from: 0, parts: 3))
```

```output
13
```

It's correct, and it's a perfect checker for small inputs. But the number of splits is C(n − 1, k − 1): about 1.7 × 10¹² for n = 100 and k = 10, and about 2.6 × 10²¹ for n = 1,000. You'll meet a dynamic programming solution in Part VII that brings this down to O(k · n²). Binary search on the answer does better still.

## The predicate: can every part stay within x?

Turn "what's the smallest largest sum?" into a yes/no question: **can the array be split so that no part's sum is more than x?**

Check it exactly as you loaded ships in [Capacity to ship packages](/dsa/learn/bsa-shipping): fill a part until the next value would push it over x, then start a new part. Count the parts.

- **Monotonic:** if every part fits within x, it fits within x + 1 too. So the predicate is false, …, false, true, …, true, and you want the first true.
- **Low** is the largest value, which has to sit in some part.
- **High** is the total, the sum of a single part holding everything.

### At most k parts, or exactly k?

The problem wants **exactly** k parts, but greedy might use fewer. In the example, x = 17 needs only two greedy parts: [4, 9, 3] and [7, 2, 8].

That's fine. If greedy uses fewer than k parts and there are at least k values, pick any part with two or more values and split it in two. Splitting never makes a sum bigger, and each split adds one part. Repeat until there are k parts. So "fits in **at most** k parts" and "fits in **exactly** k parts" have the same answer, as long as n ≥ k. When n is smaller than k, no split exists at all, because some part would be empty.

## Why the greedy check is correct

Greedy makes each part as long as possible. Could cutting a part short ever lead to fewer parts in the end? Here's an informal proof that it can't.

Compare greedy with any other split whose parts all fit within x, and look at where each one makes its cuts:

```text
                  4   9   3   7   2   8          x = 14
greedy:         [ 4   9 ][ 3   7   2 ][ 8 ]      cuts after the 2nd and 5th values
another split:  [ 4   9 ][ 3   7 ][ 2   8 ]      cuts after the 2nd and 4th values
```

**Claim:** greedy's first cut is never to the left of the other split's first cut, its second cut is never to the left of the other's second cut, and so on.

- **The first cut.** The other split's first part fits within x. Greedy keeps adding values while they fit, so it takes at least that many.
- **Each later cut.** Suppose greedy's cut number j is at or to the right of the other split's cut number j. The other split's next part runs from its cut j to its cut j + 1 and fits within x. Greedy's next part starts at or after the other's start, so the values it needs to reach the other's cut j + 1 are part of that same run, which fits. Greedy takes at least those, so its cut j + 1 is at or to the right of the other's.

So greedy is always at least as far along. If the other split finishes in k parts, greedy finishes in k or fewer. That's the "greedy stays ahead" argument again, and it means that **the greedy count is the smallest number of parts possible** for that x.

<Callout kind="analogy">
Picture friends walking a trail with a daily distance limit. One walker always keeps going until the next stretch would break the limit; the others sometimes stop early. Each evening, the keen walker is camped at least as far along as everyone else, so they reach the end on the same day or sooner.
</Callout>

## The solution

```swift run
// Fewest parts when no part may exceed `limit`. Needs limit ≥ the largest value.
func partsNeeded(_ values: [Int], limit: Int) -> Int {
    var parts = 1
    var current = 0
    for value in values {
        if current + value > limit {
            parts += 1
            current = 0
        }
        current += value
    }
    return parts
}

/// The smallest possible largest part when values are split, in order, into at most k parts.
func smallestLargestPart(_ values: [Int], parts k: Int) -> Int {
    var low = values.max()!
    var high = values.reduce(0, +)
    while low < high {
        let mid = low + (high - low) / 2
        if partsNeeded(values, limit: mid) <= k {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

func bestSplit(_ values: [Int], from start: Int, parts: Int) -> Int {
    if parts == 1 { return values[start...].reduce(0, +) }
    var best = Int.max
    var first = 0
    for end in start...(values.count - parts) {
        first += values[end]
        best = min(best, max(first, bestSplit(values, from: end + 1, parts: parts - 1)))
    }
    return best
}

let values = [4, 9, 3, 7, 2, 8]
for k in 1...6 {
    let fast = smallestLargestPart(values, parts: k)
    let slow = bestSplit(values, from: 0, parts: k)
    print("k = \(k): \(fast) (brute force \(slow))")
}
```

```output
k = 1: 33 (brute force 33)
k = 2: 17 (brute force 17)
k = 3: 13 (brute force 13)
k = 4: 10 (brute force 10)
k = 5: 9 (brute force 9)
k = 6: 9 (brute force 9)
```

Each check is O(n), and there are about log₂ S checks for a total S. That's **O(n log S)** time and O(1) extra space. With n = 100,000 values of up to 10⁹, that's under 50 passes over the array.

Running the fast and slow versions side by side, as here, is the best way to test your own solution: generate many small random arrays and compare.

## Book allocation and painter's partition

The same function solves both of the other famous versions. Only the story, and the edge cases, change.

**Book allocation.** Books with given page counts sit on a shelf in order. Each of m students gets a contiguous run of books, **at least one each**, and the goal is to minimise the most pages any student reads. That's exactly k = m parts, so return −1 when there are more students than books.

**Painter's partition.** Boards of given lengths stand in a row. Each of k painters paints a contiguous run, all painters work at the same time, and painting one unit of length takes t minutes. The job takes as long as the busiest painter, so the answer is t × (the smallest largest run). Here a painter **may** stay idle, so "at most k" is exactly right, even when there are more painters than boards.

```swift run
func partsNeeded(_ values: [Int], limit: Int) -> Int {
    var parts = 1
    var current = 0
    for value in values {
        if current + value > limit {
            parts += 1
            current = 0
        }
        current += value
    }
    return parts
}

func smallestLargestPart(_ values: [Int], parts k: Int) -> Int {
    var low = values.max()!
    var high = values.reduce(0, +)
    while low < high {
        let mid = low + (high - low) / 2
        if partsNeeded(values, limit: mid) <= k { high = mid } else { low = mid + 1 }
    }
    return low
}

func allocateBooks(_ pages: [Int], students: Int) -> Int {
    guard students <= pages.count else { return -1 }     // someone would get no book
    return smallestLargestPart(pages, parts: students)
}

func paintingTime(_ boards: [Int], painters: Int, minutesPerUnit: Int) -> Int {
    minutesPerUnit * smallestLargestPart(boards, parts: painters)   // idle painters are fine
}

print(allocateBooks([120, 45, 300, 80, 95], students: 2))
print(allocateBooks([120, 45, 300, 80, 95], students: 6))
print(paintingTime([10, 20, 30, 40], painters: 2, minutesPerUnit: 5))
print(paintingTime([10, 20, 30, 40], painters: 6, minutesPerUnit: 5))
```

```output
465
-1
300
200
```

| Name | The array | The groups | Can a group be empty? |
| --- | --- | --- | --- |
| Split array largest sum | numbers | k parts | no |
| Book allocation | pages per book | m students | no: return −1 if m > n |
| Painter's partition | board lengths | k painters | yes: an idle painter is fine |

<Callout kind="gotcha" title="Where these solutions go wrong">
**Starting low below the largest value.** As with the ships, the greedy count then quietly places an oversized value into a part of its own and reports too few parts.

**Insisting that greedy uses exactly k parts.** Checking `partsNeeded == k` breaks monotonicity: a generous limit needs fewer parts, and the search throws it away. Use `<= k`, and handle n < k separately.

**Multiplying too early.** In the painter's version, multiply by the time per unit at the end. Multiplying every board first makes the values, and the total, t times bigger, which can overflow for large inputs.
</Callout>
