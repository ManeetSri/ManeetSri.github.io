## Why it matters

Stepping stones cross a river. From each stone you can jump forwards **up to** some number of stones. Can you reach the far bank, and in how few jumps? It's one of the most asked greedy interview questions, and it teaches two ideas you'll reuse: squeezing a whole set of possibilities into **one number**, and seeing that a greedy loop is sometimes a breadth-first search in disguise. Both versions run in one pass, O(n) time and O(1) memory.

## The puzzle

The stones are numbered from 0, and `steps[i]` is the longest jump from stone i: from stone i you can land on any stone from `i + 1` to `i + steps[i]`. You start on stone 0, and the far bank is the last stone. A stone with `steps[i] == 0` is a dead end: you can stand on it, but not leave it.

## Jump game I: can you reach the end?

You could explore every route, but there's a far simpler view. Keep one number, `farthest`: the farthest stone reachable so far. Walk the stones in order. If the current stone is beyond `farthest`, you can never stand on it, so you're stuck. Otherwise, it's reachable, and from it you can reach `i + steps[i]`.

```swift run
func canReachEnd(_ steps: [Int]) -> Bool {
    var farthest = 0                              // every stone up to here is reachable
    for i in steps.indices {
        if i > farthest {
            print("  stone \(i) is out of reach")
            return false
        }
        farthest = max(farthest, i + steps[i])
        print("  stone \(i): farthest is now \(farthest)")
    }
    return true
}

print(canReachEnd([3, 1, 0, 2, 0, 1]))
print(canReachEnd([2, 1, 0, 3]))
```

```output
  stone 0: farthest is now 3
  stone 1: farthest is now 3
  stone 2: farthest is now 3
  stone 3: farthest is now 5
  stone 4: farthest is now 5
  stone 5: farthest is now 6
true
  stone 0: farthest is now 2
  stone 1: farthest is now 2
  stone 2: farthest is now 2
  stone 3 is out of reach
false
```

`farthest` can pass the last stone, as it does at stone 5; that's fine. In the second river, every stone you can reach lands you on stone 2 at best, and stone 2 is a dead end. You could also stop early as soon as `farthest` reaches the last stone; the version above walks to the end so you can see every step.

### Why one number is enough

The loop assumes that the reachable stones are always **every stone from 0 to `farthest`**, with no gaps. Here's why. If you can reach stone j, you got there by a jump from some stone i that can reach anything from `i + 1` to `i + steps[i]`, a range with no gaps. So every stone between i and j is reachable too, and by the same argument every stone before i. A set of stones with no gaps is described by its last stone, so `farthest` captures everything.

That's the greedy insight: you never need to know **which** route got you somewhere, only how far the reachable region extends. It's the same "summarise the past in one number" trick as [Kadane's algorithm](/dsa/learn/arrays-kadane).

## Jump game II: the fewest jumps

Now assume you can reach the far bank. What's the fewest jumps?

Think in **ranges**. With 0 jumps you can stand only on stone 0. With 1 jump, on any stone from 1 to `steps[0]`. With 2 jumps, on any stone after that range, up to the farthest that any stone in it can reach. And so on: each range starts right after the previous one ends and extends to the farthest reach of the previous range.

Those ranges are exactly the **levels of a breadth-first search** from stone 0, as in [BFS and unweighted shortest paths](/dsa/learn/gt-bfs): range k holds the stones whose fewest-jumps distance is k. BFS would use a queue and could touch up to n² jump edges. Here each level is a contiguous range, so two numbers describe it, and one pass finds them all:

```swift run
func fewestJumps(_ steps: [Int]) -> Int {
    var jumps = 0
    var reachEnd = 0                   // the last stone reachable with `jumps` jumps
    var farthest = 0                   // the farthest any stone seen so far can reach
    for i in 0..<(steps.count - 1) {   // no jump is needed from the last stone
        farthest = max(farthest, i + steps[i])
        if i == reachEnd {             // this range is used up: one more jump is needed
            if farthest == i { return -1 }      // nothing in the range gets past it
            jumps += 1
            print("  jump \(jumps) can land anywhere from \(reachEnd + 1) to \(min(farthest, steps.count - 1))")
            reachEnd = farthest
        }
    }
    return jumps
}

print(fewestJumps([2, 3, 1, 1, 4, 2, 1, 3, 1]))
print(fewestJumps([1, 1, 1]))
print(fewestJumps([5]))
print(fewestJumps([1, 0, 4]))
```

```output
  jump 1 can land anywhere from 1 to 2
  jump 2 can land anywhere from 3 to 4
  jump 3 can land anywhere from 5 to 8
3
  jump 1 can land anywhere from 1 to 1
  jump 2 can land anywhere from 2 to 2
2
0
  jump 1 can land anywhere from 1 to 1
-1
```

Read the first example as levels. Stones 1 and 2 need one jump. From them, stone 1 reaches 4, so stones 3 and 4 need two. From those, stone 4 reaches 8, the last stone, so three jumps. Notice what the loop **doesn't** decide: which stone to jump from. It only counts how many ranges you pass through. If you want the actual route, remember which stone gave each range its `farthest`.

The `-1` check handles rivers you can't cross: when a range ends and nothing in it reached past its end, you're stuck. If you're told the end is always reachable, you can drop it.

### Why it's correct

This is a "greedy stays ahead" argument, from [Proving greedy](/dsa/learn/greedy-proofs). The claim: after k jumps, `reachEnd` is the farthest stone that **any** route of k jumps can land on.

- With 0 jumps, it's stone 0. True.
- Any route of k + 1 jumps makes its last jump from a stone it reached in at most k jumps, so from a stone in ranges 0 to k. The farthest any of those stones reach is exactly the next `reachEnd`. True.

So the first k whose range contains the last stone is the fewest jumps possible, which is what the loop returns.

## The two loops side by side

| | Jump game I | Jump game II |
| --- | --- | --- |
| Question | can you reach the end? | the fewest jumps |
| State | `farthest` | `farthest`, `reachEnd`, `jumps` |
| Key moment | `i > farthest`: stuck | `i == reachEnd`: one more jump |
| Why it works | reachable stones have no gaps | ranges are BFS levels |
| Cost | O(n) time, O(1) memory | O(n) time, O(1) memory |

<Callout kind="gotcha" title="Off by one: stop before the last stone">
Jump game II loops over `0..<(steps.count - 1)`. If the loop also visited the last stone, then whenever the last stone is exactly the end of a range, `i == reachEnd` would fire there and count a jump you never take. A single stone needs 0 jumps, and the empty loop gives exactly that. (An empty `steps` array would make the range `0..<-1`, which crashes, so the problem always has at least one stone.)
</Callout>

<Callout kind="warning" title="A different puzzle: jumps of exactly steps[i]">
If every jump must be **exactly** `steps[i]` long, perhaps in either direction, the reachable stones can have gaps, and one number no longer describes them. That version is a graph search: BFS or DFS over the stones, with a visited array.
</Callout>

## Practice

**Fewest hops across the river** is jump game II, including rivers that can't be crossed. Its tests have 100,000 stones, so the BFS with a queue over every possible jump is too slow when the jumps are long: make the ranges work.
