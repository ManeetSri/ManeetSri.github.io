## Why it matters

Two interview problems where the greedy idea is a single observation, and the code is short once you've seen it. **Partition labels** splits a string into as many pieces as possible so that no letter appears in two pieces; the observation is that each letter's **last occurrence** tells you how far its piece must reach. **Queue reconstruction** rebuilds a line of people from clues about who stands in front of whom; the observation is that **short people are invisible to tall ones**, so placing the tallest first makes every clue easy to satisfy. Both reward explaining why before coding.

## Partition labels: the problem

Split a string of lowercase letters into as many consecutive pieces as possible, so that each letter appears in only one piece. Return the pieces (or their lengths).

For `"abacbdedfghgih"`, the a's run from index 0 to index 2, but the b at index 1 also appears at index 4, so the first piece must reach index 4 at least. Letters keep extending the piece until, at some index, every letter seen so far has appeared for the last time. That's where you cut.

## Last occurrences, then one pass

First record each letter's last index. Then walk the string, keeping `end`: the furthest last occurrence of any letter in the current piece. When the index reaches `end`, the piece is complete.

```swift run
func letterZones(_ text: String) -> [String] {
    let letters = Array(text)
    var last: [Character: Int] = [:]
    for (i, letter) in letters.enumerated() {
        last[letter] = i                          // later positions overwrite earlier ones
    }
    var parts: [String] = []
    var start = 0
    var end = 0                                   // the piece can't end before this index
    for (i, letter) in letters.enumerated() {
        end = max(end, last[letter]!)
        if i == end {                             // every letter so far has finished: cut here
            parts.append(String(letters[start...i]))
            start = i + 1
        }
    }
    return parts
}

print(letterZones("abacbdedfghgih"))
print(letterZones("abcabc"))
print(letterZones("xyz"))
```

```output
["abacb", "ded", "f", "ghgih"]
["abcabc"]
["x", "y", "z"]
```

In `"abcabc"`, the a at index 0 reaches index 3, and by then b and c reach index 5, so the whole string is one piece. In `"xyz"`, every letter's last occurrence is where it stands, so every index is a cut. The force unwrap `last[letter]!` is safe: every letter in the string was recorded in the first loop. This is the same "extend the end until you catch up with it" loop as [merging intervals](/dsa/learn/iv-merge-insert), where each letter is the interval from its first to its last occurrence.

Two passes, O(n) time. The dictionary holds at most 26 entries, so the extra memory is O(1). An array of 26 counts, indexed by letter, works equally well.

### Why the cuts are the best possible

Here's the key fact: whether a cut between index i and index i + 1 is allowed **doesn't depend on any other cut**. It's allowed exactly when no letter appears both at or before i and after i. So the most pieces you can get comes from making every allowed cut. The greedy makes exactly those:

- **Every greedy cut is allowed.** When `i == end`, every letter in the current piece has its last occurrence at or before i, and letters from earlier pieces finished before the piece began.
- **The greedy makes every allowed cut.** If a cut after i is allowed, every letter up to i has its last occurrence at or before i, so `end` is at most i. And `end` is always at least i, because the letter at i ends there or later. So `end == i`, and the greedy cuts.

It's an unusual greedy proof: rather than an exchange, it shows that the greedy's answer and the set of allowed cuts are the same thing.

## Queue reconstruction: the problem

People stand in a queue. Each person is described by a pair `[height, k]`: their height, and the number of people **in front of them** who are at least as tall. The pairs have been shuffled. Rebuild the queue.

Look at the problem from the tallest person's point of view. Nobody is taller, so their k counts only people of the same height. Shorter people standing in front of them don't count at all. That suggests building the queue from the tallest down: when you place someone, everyone already placed is at least as tall, so they all count, and everyone placed later is shorter, so they won't count.

## Tallest first, insert at k

Sort by height, tallest first, and for equal heights by k, smallest first. Then insert each person at index k of the queue so far.

```swift run
// Each person is [height, k]: k people of the same height or taller stand in front of them
func rebuildQueue(_ people: [[Int]]) -> [[Int]] {
    // Tallest first; equal heights in increasing k
    let order = people.sorted { $0[0] != $1[0] ? $0[0] > $1[0] : $0[1] < $1[1] }
    var queue: [[Int]] = []
    for person in order {
        queue.insert(person, at: person[1])       // everyone already in the line counts
        print(person, "->", queue)
    }
    return queue
}

_ = rebuildQueue([[4, 4], [7, 0], [5, 2], [6, 0], [4, 1], [6, 2]])
```

```output
[7, 0] -> [[7, 0]]
[6, 0] -> [[6, 0], [7, 0]]
[6, 2] -> [[6, 0], [7, 0], [6, 2]]
[5, 2] -> [[6, 0], [7, 0], [5, 2], [6, 2]]
[4, 1] -> [[6, 0], [4, 1], [7, 0], [5, 2], [6, 2]]
[4, 4] -> [[6, 0], [4, 1], [7, 0], [5, 2], [4, 4], [6, 2]]
```

Watch `[5, 2]`: when it's placed, the queue holds only people taller than 5, so standing at index 2 puts exactly two of them in front. Then `[4, 1]` cuts in at index 1, in front of the 7, the 6 and the 5. That doesn't spoil their counts, because they don't count anyone shorter. Check the final queue: the person `[4, 4]` has 6, 4, 7 and 5 in front of them, four people at least as tall.

### Why it's correct

Two facts, both true at every insertion:

1. **The new person's count comes out right.** Everyone already in the queue is at least as tall, so all of them count. Standing at index k puts exactly k of them in front.
2. **Nobody else's count changes.** Taller people don't count the new, shorter person. People of the same height already placed have a **smaller** k, so they stand in front of index k and the new person lands behind them.

The second fact is why equal heights must be sorted by k ascending. In any real queue, of two people with the same height, the one further back counts the one in front, so their k values differ, and placing the smaller k first keeps everyone in order.

Each `insert(_:at:)` shifts the later elements along, O(n) each, so the whole algorithm is O(n²) after the O(n log n) sort. That's fine for a few thousand people. With an order-statistics structure, such as the Fenwick tree in M61, the same idea runs in O(n log n).

<Callout kind="gotcha" title="Swift gotchas">
- **`insert(_:at:)` crashes past the end.** The index must be at most `queue.count`. With valid input, k never exceeds the number of taller-or-equal people already placed, so it's always in range; on untrusted input, check first.
- **Sorting by two keys, one of them descending.** Swift compares tuples left to right, so `($0[0], $0[1]) < ($1[0], $1[1])` sorts both keys ascending. For height descending and k ascending, write the comparison out, as above, or compare `(-$0[0], $0[1]) < (-$1[0], $1[1])`.
</Callout>
