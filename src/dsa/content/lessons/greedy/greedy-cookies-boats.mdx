## Why it matters

Three small problems, one pattern: **sort, then let two pointers or a couple of counters make the greedy choice**. Matching biscuits to children, people to boats and change to customers are all pairing problems, and the same pattern shows up in real scheduling code, such as pairing small download tasks with big ones so each batch fits a size limit. Each problem also comes with a short "why it's safe" argument, the part interviewers care about most.

## Biscuits, from either end

You proved the biscuit greedy in [Proving greedy](/dsa/learn/greedy-proofs): give the least greedy child the smallest biscuit that satisfies them. With both lists sorted, that's two pointers moving forwards. There's a mirror-image version that works equally well: give the **biggest** biscuit to the **greediest** child it can satisfy, walking both lists from the top.

```swift run
// Smallest first: each biscuit goes to the least greedy child still waiting, if it's big enough
func happyFromSmallest(greed: [Int], biscuits: [Int]) -> Int {
    let children = greed.sorted(), sizes = biscuits.sorted()
    var child = 0
    for size in sizes where child < children.count && size >= children[child] {
        child += 1
    }
    return child
}

// Biggest first: the biggest biscuit left goes to the greediest child it satisfies
func happyFromBiggest(greed: [Int], biscuits: [Int]) -> Int {
    let children = greed.sorted(by: >), sizes = biscuits.sorted(by: >)
    var biscuit = 0
    for need in children where biscuit < sizes.count && sizes[biscuit] >= need {
        biscuit += 1                    // children no biscuit can satisfy are skipped
    }
    return biscuit
}

let greed = [5, 2, 8, 3], biscuits = [4, 1, 3, 9, 2]
print(happyFromSmallest(greed: greed, biscuits: biscuits), happyFromBiggest(greed: greed, biscuits: biscuits))
```

```output
3 3
```

In the second version, a child the biggest remaining biscuit can't satisfy can never be satisfied, so they're skipped. The child with greed 8 takes the 9, and then the child with greed 5 is skipped, because the 4 is too small: a different set of happy children, the same count. Both are O(n log n + m log m) for the sorts, then one pass.

## Boats: pair the heaviest with the lightest

People wait to be rescued. Each boat carries **at most two people** and at most `limit` kilograms, and nobody is heavier than `limit`. What's the fewest boats?

The greedy: sort by weight. Look at the heaviest person still waiting. If they can share with the lightest person still waiting, send them together; otherwise send the heaviest alone.

```swift run
func boatsNeeded(_ weights: [Int], limit: Int) -> Int {
    let people = weights.sorted()
    var light = 0
    var heavy = people.count - 1
    var boats = 0
    while light <= heavy {
        if light < heavy && people[light] + people[heavy] <= limit {
            print("boat: \(people[heavy]) and \(people[light])")
            light += 1
        } else {
            print("boat: \(people[heavy]) alone")
        }
        heavy -= 1
        boats += 1
    }
    return boats
}

print(boatsNeeded([3, 5, 3, 4, 2, 1], limit: 5))
```

```output
boat: 5 alone
boat: 4 and 1
boat: 3 and 2
boat: 3 alone
4
```

These are the opposite-ends pointers from [Opposite ends: pair sum and valid palindrome](/dsa/learn/tp-opposite-ends). The `light < heavy` check stops one person from being paired with themselves when a single person is left.

### Why it's safe

The heaviest person, h, needs a boat whatever happens. Two cases:

- **The lightest person, l, can't share with h.** Then nobody can, because everyone else is at least as heavy as l. h goes alone in every valid plan, so sending h alone loses nothing.
- **l can share with h.** Take any plan with the fewest boats. If it already pairs h with l, good. If not, suppose h shares with x (or is alone) and l shares with y (or is alone). Swap partners: pair h with l, and x with y. The pair h and l fits, by assumption. The pair x and y fits too: y is no heavier than h, and x already fitted alongside h, so `x + y ≤ x + h ≤ limit`. The number of boats doesn't go up.

Either way, some best plan makes the greedy's choice, and what's left is the same problem with fewer people. Sorting dominates: O(n log n).

<Callout kind="note" title="Why at most two per boat matters">
With up to three per boat, "heaviest with lightest" stops being safe, and the problem becomes bin packing, for which no efficient exact algorithm is known. The two-per-boat limit is what makes a simple swap of partners possible.
</Callout>

## Change at a market stall

A stall sells pies for 5 each. Customers queue and each pays with one note: a 5, a 10 or a 20. The till starts empty. Can the stall give every customer the right change, in order?

A 5 needs no change. A 10 needs a 5 back. A 20 needs 15 back, and that's the only real decision: **a 10 and a 5, or three 5s?** The greedy rule is to use the larger note first: a 10 and a 5 whenever possible.

```swift run
// Can the stall give everyone change? Each pie costs 5; the till starts empty.
// `tenFirst` chooses how to change a 20: a ten and a five if possible, or always three fives.
func canChange(_ payments: [Int], tenFirst: Bool) -> Bool {
    var fives = 0
    var tens = 0
    for (customer, note) in payments.enumerated() {
        switch note {
        case 5:
            fives += 1
        case 10:
            guard fives >= 1 else { print("  customer \(customer + 1): no five for a 10"); return false }
            fives -= 1
            tens += 1
        default:                                    // a 20 needs 15 back
            if tenFirst && tens >= 1 && fives >= 1 {
                tens -= 1
                fives -= 1
            } else if fives >= 3 {
                fives -= 3
            } else if tens >= 1 && fives >= 1 {
                tens -= 1
                fives -= 1
            } else {
                print("  customer \(customer + 1): can't change a 20")
                return false
            }
        }
    }
    return true
}

let queue = [5, 5, 5, 5, 10, 20, 10, 10]
print("ten and five first:", canChange(queue, tenFirst: true))
print("three fives first:", canChange(queue, tenFirst: false))
print("ten and five first:", canChange([5, 10, 5, 20, 20], tenFirst: true))
```

```output
ten and five first: true
  customer 7: no five for a 10
three fives first: false
  customer 5: can't change a 20
ten and five first: false
```

Spending three 5s on customer 6 leaves the till with one 10 and no 5s, and the next customer's 10 can't be changed. Paying a 10 and a 5 keeps two 5s back. The last queue fails whatever you do: at customer 5, the till holds no notes at all. Twenties never need to be counted, because they're never given as change.

### Why the larger note first is safe, for these notes

After changing a 20, compare the two tills. The greedy's has **two more 5s and one fewer 10** than the alternative's. Is that ever worse? A 10 is only useful as change for a 20, where it stands in for two 5s. So whatever the alternative till can pay later, the greedy's till can pay too, using two of its extra 5s wherever the other till would use that 10. The greedy's till is always at least as capable, so it never fails first.

This relies on the notes. A 10 is worth exactly two 5s, so the 5s can always do a 10's job, but a 10 can't break into 5s for a customer paying with a 10. Fives are the flexible note, so you save them. With other denominations, "largest first" needs its own argument, and as [When greedy fails](/dsa/learn/greedy-counterexamples) showed with \{1, 3, 4\}, it can be wrong.

<Callout kind="gotcha" title="Swift gotcha: a switch must be exhaustive">
`switch note` on an `Int` needs a `default`, because Swift can't know that only 5, 10 and 20 arrive. Here `default` handles the 20. If the input might contain other values, add `case 20:` explicitly and make `default` reject anything else, rather than silently treating a 50 as a 20.
</Callout>
