## Why it matters

Most greedy rules you can think of are wrong. That's not a reason to avoid greedy: it's a reason to get good at breaking rules quickly, so you only spend time proving the ones that survive. This lesson collects the classic failures, making change with odd coins, packing a knapsack and finding the longest route, and turns them into a method for hunting counterexamples. When greedy fails, the fix is usually dynamic programming, which starts in M51.

## Coins: \{1, 3, 4\} and the amount 6

The biggest-coin-first rule from [The greedy choice property](/dsa/learn/greedy-idea) is right for euro coins. Change the coins to \{1, 3, 4\} and pay 6: the greedy takes 4, then 1 and 1, three coins. But 3 + 3 is two.

The program below compares the greedy with the true minimum for every amount up to 12. The true minimum comes from a table, `best[total]`, filled from small totals to large: the fewest coins for `total` is one coin plus the fewest for what's left after it. That's dynamic programming, which you'll learn properly in M51; here it's a reliable referee.

```swift run
func greedyCoins(_ amount: Int, _ coins: [Int]) -> Int {
    var left = amount
    var count = 0
    for coin in coins.sorted(by: >) {
        count += left / coin            // as many of this coin as fit
        left %= coin
    }
    return count                        // every system here has a 1, so left ends at 0
}

// best[t] = the fewest coins that make t exactly
func fewestCoins(_ amount: Int, _ coins: [Int]) -> Int {
    var best = [0] + Array(repeating: Int.max, count: amount)
    for total in stride(from: 1, through: amount, by: 1) {
        for coin in coins where coin <= total && best[total - coin] != Int.max {
            best[total] = min(best[total], best[total - coin] + 1)
        }
    }
    return best[amount]
}

for amount in 1...12 where greedyCoins(amount, [1, 3, 4]) != fewestCoins(amount, [1, 3, 4]) {
    print("\(amount): greedy uses \(greedyCoins(amount, [1, 3, 4])), the best is \(fewestCoins(amount, [1, 3, 4]))")
}

// British coins before 1971, in pence: 3d, 6d, the shilling (12d), the florin (24d) and the half crown (30d)
let oldPence = [1, 3, 6, 12, 24, 30]
print("48d: greedy uses \(greedyCoins(48, oldPence)), the best is \(fewestCoins(48, oldPence))")
```

```output
6: greedy uses 3, the best is 2
10: greedy uses 4, the best is 3
48d: greedy uses 3, the best is 2
```

Most amounts are fine, which is exactly what makes the bug dangerous. 48 old pence was a half crown, a shilling and a sixpence by the greedy rule, but two florins would do. Step through the table for \{1, 3, 4\} and 6; the last frame compares it with the greedy:

```visual dpTable
program: coinChange

  coins: [1, 3, 4]
  amount: 6
```

**Why the greedy choice property fails:** for 6, the greedy commits to a 4, but no best answer contains a 4. The 4 is "a bit better" than a 3, and taking it leaves 2, an amount that only small coins can fill. Coin systems where greedy is always right, such as euro and pound coins today, are called **canonical**. [Coin change I and II](/dsa/learn/dpk-coin-change) solves any coin system.

<Callout kind="note" title="Checking a coin system">
You don't have to test every amount. A result by Kozen and Zaks (1994) says that if the greedy fails for some amount, it already fails for one below the sum of the two largest coins. For \{1, 3, 4\} that's below 7, and 6 fails. For the old British coins, it's below 54, and 48 fails.
</Callout>

## 0/1 knapsack: the best value per kilogram isn't enough

A bag holds 10 kg. Each item can be taken whole or left: you can't take half a tent. Which items give the most value?

The natural greedy rule is **value density**: value per kilogram, highest first, taking each item that still fits.

```swift run
let items = [(name: "lamp", weight: 6, value: 30), (name: "rug", weight: 5, value: 20), (name: "vase", weight: 5, value: 20)]
let capacity = 10

// Greedy by value per kg, taking each item that still fits
var room = capacity
var greedyValue = 0
for item in items.sorted(by: { $0.value * $1.weight > $1.value * $0.weight }) where item.weight <= room {
    print("greedy takes the \(item.name)")
    room -= item.weight
    greedyValue += item.value
}

// Try every subset
var best = 0
for mask in 0..<(1 << items.count) {
    let chosen = items.indices.filter { mask & (1 << $0) != 0 }
    let weight = chosen.reduce(0) { $0 + items[$1].weight }
    if weight <= capacity { best = max(best, chosen.reduce(0) { $0 + items[$1].value }) }
}
print("greedy \(greedyValue), best \(best)")
```

```output
greedy takes the lamp
greedy 30, best 40
```

The lamp is the densest at 5 per kg, so the greedy takes it, and then 4 kg are left, too little for anything else. The rug and the vase together fill the bag exactly and are worth 40. The comparison `$0.value * $1.weight > $1.value * $0.weight` compares densities without division; the next lesson explains why.

If you **could** take part of an item, density would be exactly right: take the lamp, then 4 kg of the rug, for 30 + 16 = 46. That's the fractional knapsack, and the next lesson proves it. The 0/1 version needs dynamic programming: [0/1 knapsack, from 2D to 1D](/dsa/learn/dpk-01).

## Longest path: the heaviest next step

Find the longest route from A to D in this one-way road network, where each number is the length of a road:

```text
    A --10--> B --1--> D
    |                  ^
    1                  |
    v                  |
    C ------100--------+
```

A greedy walker always takes the longest road out of where it stands:

```swift run
let roads: [Character: [(to: Character, length: Int)]] = [
    "A": [("B", 10), ("C", 1)],
    "B": [("D", 1)],
    "C": [("D", 100)],
]

// Greedy: from each place, take the longest road out
var place: Character = "A"
var greedyRoute = "A"
var greedyLength = 0
while place != "D", let next = roads[place]?.max(by: { $0.length < $1.length }) {
    greedyLength += next.length
    place = next.to
    greedyRoute.append(next.to)
}

// Exhaustive: try every route
func longest(from place: Character) -> Int {
    if place == "D" { return 0 }
    return (roads[place] ?? []).map { $0.length + longest(from: $0.to) }.max() ?? Int.min
}
print("greedy \(greedyRoute) = \(greedyLength), longest = \(longest(from: "A"))")
```

```output
greedy ABD = 11, longest = 101
```

The 10 looks great, but it leads to a dead end worth 1, while the modest 1 leads to the 100. A greedy step can't see what comes after it. The same trap catches "take the shortest road out" when you want the shortest route. [Dijkstra](/dsa/learn/sp-dijkstra) is greedy too, but its choice is different: the nearest vertex over **everything reached so far**, not the cheapest road from where you stand. That choice comes with a proof.

On a graph with cycles, the longest simple path is much harder still: no efficient algorithm is known for it at all. On a DAG like this one, it's easy with the method from [Longest and shortest paths in a DAG](/dsa/learn/topo-dag-paths).

## How to hunt for a counterexample

Every example above has the same shape: **the greedy choice is slightly better now, and it blocks something much better later.** Use that shape to attack any rule:

1. **Make the greedy's favourite barely win.** A 4 against a 3, a density of 5 against 4, a road of 10 against 1.
2. **Make it block two good things.** The 4 leaves an awkward remainder; the lamp wastes 4 kg that two items could have used.
3. **Try tiny inputs and ties.** Two or three items are usually enough. If two options tie, does it matter which one the rule picks?
4. **Let the computer search.** A brute force plus a seeded random generator, as in [Proving greedy](/dsa/learn/greedy-proofs), finds counterexamples you'd never think of.

If you can't break a rule after all that, it's time to prove it.

<Callout kind="gotcha" title="Swift gotcha: max(by:) wants a less-than closure">
`roads.max(by:)` takes the same kind of closure as `sorted(by:)`: "is the first **smaller** than the second?" Writing `{ $0.length > $1.length }` quietly returns the **shortest** road instead. Read `max(by: <)` as "the biggest, by this less-than".
</Callout>
