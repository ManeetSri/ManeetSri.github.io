## Why it matters

A **greedy algorithm** builds its answer one choice at a time. At every step it takes whatever looks best right now, and it never goes back to change its mind. When that works, it gives some of the shortest and fastest solutions in the whole course, often a sort followed by one loop. You've already met several without the name: Dijkstra settling the nearest vertex, Kruskal adding the lightest safe edge, keeping the interval that ends first. This module is about when "best right now" is also best overall, how to prove it, and how to spot the many times it isn't.

## The greedy recipe

Every greedy algorithm follows the same shape:

1. Decide what "best" means for one step: cheapest, earliest, largest, nearest.
2. Take the best option that's still allowed.
3. **Commit** to it. It's part of the answer for good.
4. Repeat with what's left until nothing more can be taken.

Making change is the classic example. To pay 68 in euro cents with as few coins as possible, take the biggest coin that fits, again and again:

```swift run
// Pay `amount` with as few coins as possible: biggest coin that fits, every time
func greedyChange(_ amount: Int, coins: [Int]) -> [Int] {
    var left = amount
    var used: [Int] = []
    for coin in coins.sorted(by: >) {     // biggest first
        while coin <= left {
            used.append(coin)
            left -= coin
        }
    }
    return used
}

let euroCents = [1, 2, 5, 10, 20, 50]
print(greedyChange(68, coins: euroCents))
print(greedyChange(99, coins: euroCents))
print(greedyChange(40, coins: euroCents))
```

```output
[50, 10, 5, 2, 1]
[50, 20, 20, 5, 2, 2]
[20, 20]
```

Each coin is chosen by looking only at the amount still to pay. The loop never asks "what if I had taken a 20 instead of that 50?" For euro coins that's fine: no way of paying 68 uses fewer than five coins. For other coin systems, as you'll see in [When greedy fails](/dsa/learn/greedy-counterexamples), the same loop gives wrong answers.

## Commit and never look back

The word that separates greedy from the paradigms around it is **commit**.

- [Backtracking](/dsa/learn/bk-template) (M48) makes a choice, explores everything that follows, then **undoes** the choice and tries the next one.
- Dynamic programming (from M51) also looks at every choice at each step, but remembers the best result for each smaller problem so nothing is solved twice.
- [Divide and conquer](/dsa/learn/dc-paradigm) (M49) splits a problem into independent parts and combines their answers.
- Greedy looks at the choices, takes **one**, and moves on. There's no undo, and no comparing of alternatives later.

That's why greedy is fast: one decision per step, usually after a sort. It's also why it's dangerous. If an early choice was a mistake, nothing ever repairs it.

## Example: the most items on a budget

You have 70 coins to spend in a shop and want to buy as many different items as possible. The greedy rule is obvious: buy the cheapest item, then the next cheapest, and stop when the next one doesn't fit.

```swift run
func mostItems(_ prices: [Int], budget: Int) -> [Int] {
    var left = budget
    var bought: [Int] = []
    for price in prices.sorted() {        // cheapest first
        if price > left { break }         // everything after this costs even more
        bought.append(price)
        left -= price
    }
    return bought
}

print(mostItems([40, 10, 25, 60, 5], budget: 70))
print(mostItems([30, 30, 30], budget: 89))
print(mostItems([100], budget: 70))
```

```output
[5, 10, 25]
[30, 30]
[]
```

After 5, 10 and 25, there are 30 coins left and the next cheapest item costs 40, so the loop stops. The `break` is safe because the prices are sorted: if this item doesn't fit, nothing after it can.

Is three really the most? It feels obvious, but "feels obvious" is exactly how wrong greedy algorithms get written. Here's why it's right.

## Why it works: two properties

A greedy algorithm is correct when the problem has two properties.

### The greedy choice property

**Some optimal answer makes the same first choice as the greedy.** Committing to the greedy choice never rules out the best answer.

For the shop: let c be the cheapest item. Take any basket with the most items. If it already contains c, good. If not, swap any item in it for c. The basket costs no more than before (c is the cheapest), so it's still within budget, and it has the same number of items. So there's a best basket containing c, and buying c first loses nothing.

### Optimal substructure

**After the greedy choice, what's left is a smaller version of the same problem, and a best answer to it plus the choice is a best answer to the whole.**

For the shop: once c is in the basket, the rest of the basket is "the most items from the other prices, on a budget of 70 − c". If you could do better on that smaller problem, adding c would give a bigger basket overall.

Put the two together and you have a proof by **induction**, the ladder argument from [Loop invariants and correctness](/dsa/learn/algo-invariants): the first choice is safe, and what's left is the same problem again, so its first choice is safe too, and so on up the ladder.

<Callout kind="analogy">
Climbing a hill in fog by always stepping uphill gets you to the top only if the hill has one peak. The greedy choice property is the guarantee that there's no second, higher peak hiding behind a dip.
</Callout>

## You've been greedy before

Several algorithms from earlier modules are greedy, and each comes with exactly this kind of argument:

| Algorithm | The greedy choice | Why it's safe |
| --- | --- | --- |
| [Fewest removals](/dsa/learn/iv-non-overlapping) | keep the interval that ends first | an exchange argument |
| [Dijkstra](/dsa/learn/sp-dijkstra) | settle the nearest unsettled vertex | no later path can be shorter, as weights aren't negative |
| [Kruskal and Prim](/dsa/learn/mst-definition) | add the lightest edge across a cut | the cut property |
| [IPO](/dsa/learn/heap-scheduling) | take the most profitable affordable project | capital never goes down |

Notice how different the arguments are. There's no single proof that covers every greedy algorithm, but two templates cover most of them, and the next lesson teaches both.

## A rule that sounds as good

Change the shop problem slightly: now you want to **spend as much of the budget as possible**. The tempting greedy rule is "most expensive first, while it fits":

```swift run
func greedySpend(_ prices: [Int], budget: Int) -> Int {
    var left = budget
    for price in prices.sorted(by: >) where price <= left {
        left -= price
    }
    return budget - left
}

// Try every subset of the items (fine for a handful)
func bestSpend(_ prices: [Int], budget: Int) -> Int {
    var best = 0
    for mask in 0..<(1 << prices.count) {
        let total = prices.indices.filter { mask & (1 << $0) != 0 }.reduce(0) { $0 + prices[$1] }
        if total <= budget { best = max(best, total) }
    }
    return best
}

print(greedySpend([6, 5, 5], budget: 10), bestSpend([6, 5, 5], budget: 10))
print(greedySpend([8, 6, 3], budget: 9), bestSpend([8, 6, 3], budget: 9))
```

```output
6 10
8 9
```

Taking the 6 leaves 4, and neither 5 fits, so the greedy spends 6 when 5 + 5 spends all 10. The greedy choice property is false here: no best answer contains the 6. This problem, subset sum, needs dynamic programming, which you'll meet in M53.

The lesson: a greedy rule needs a reason. The brute force above, which tries every subset as in [Bitmasks for subsets and submasks](/dsa/learn/bits-subsets), is how you catch a bad rule before trusting it.

## How to approach a problem that smells greedy

Problems that ask for "the most", "the fewest" or "the largest" of something, where the input can be sorted by one key, often have a greedy answer. When you suspect one:

1. **Guess a rule.** What would "best right now" mean? Earliest end, smallest size, biggest value per kilogram?
2. **Try to break it.** Write a brute force for tiny inputs and compare on many random cases. Most wrong rules die here, in minutes.
3. **Prove it.** If the rule survives, argue the greedy choice property, usually with an exchange argument.

<Callout kind="gotcha" title="Swift gotcha: reversed() doesn't give you an array">
`coins.sorted().reversed()` looks like a descending array, but it's a `ReversedCollection`, a lightweight view whose indexes aren't plain `Int`s, so `biggestFirst[0]` doesn't compile:

```text title="What you'll see"
error: no exact matches in call to subscript
```

Looping over it with `for` works fine. When you need a real descending array, write `coins.sorted(by: >)`.
</Callout>
