## Why it matters

A vending machine giving change, a payment system splitting a balance into vouchers, a postal kiosk choosing stamps: all ask how to make an amount from a set of denominations, with as many of each as you like. Two questions come up again and again. **What is the fewest number of coins?** And **in how many ways can it be done?** Both are unbounded knapsacks, and both appear in nearly every interview question bank. The second hides the most famous loop-order trap in DP: swap two `for` lines and you count something different, with no error to warn you.

## Coin change I: the fewest coins

You have coin values `coins` (each positive, unlimited supply) and an `amount`. Return the fewest coins that add up to exactly `amount`, or report that it can't be done.

In [When greedy fails](/dsa/learn/greedy-counterexamples) you saw biggest-coin-first go wrong for \{1, 3, 4\} and 6, and a small table fix it. Here's that table, built properly with [the DP recipe](/dsa/learn/dp-recipe):

- **State.** `fewest[t]` is the fewest coins that add up to exactly `t`.
- **Transition.** Think about the **last** coin. If it's `c`, the rest makes `t - c` as cheaply as possible: `fewest[t] = 1 + min(fewest[t - c])` over every coin `c ≤ t`.
- **Base case.** `fewest[0] = 0`. Every other total starts as "impossible".
- **Order.** Totals from small to large, since `t - c` is smaller than `t`.
- **Answer.** `fewest[amount]`, unless it's still impossible.

For "impossible", pick a number no real answer can reach. Any real answer uses at most `amount` coins (the smallest coin is at least 1), so `amount + 1` works, and adding 1 to it can't overflow:

```swift run
/// The fewest coins that add up to amount (unlimited coins of each value), or nil if it can't be done
func fewestCoins(_ coins: [Int], _ amount: Int) -> Int? {
    let impossible = amount + 1                          // more coins than any real answer could need
    var fewest = Array(repeating: impossible, count: amount + 1)
    fewest[0] = 0                                        // no coins make 0
    for total in stride(from: 1, through: amount, by: 1) {
        for coin in coins where coin <= total {
            fewest[total] = min(fewest[total], fewest[total - coin] + 1)   // last coin is `coin`
        }
    }
    return fewest[amount] == impossible ? nil : fewest[amount]
}

/// Greedy: the biggest coin that fits, again and again
func greedyCoins(_ coins: [Int], _ amount: Int) -> Int? {
    var left = amount
    var count = 0
    for coin in coins.sorted(by: >) {
        count += left / coin
        left %= coin
    }
    return left == 0 ? count : nil
}

for (coins, amount) in [([1, 3, 4], 6), ([1, 5, 10, 25], 63), ([5, 7], 24), ([4, 6], 9)] {
    print("\(coins) for \(amount): DP \(fewestCoins(coins, amount).map(String.init) ?? "impossible"), greedy \(greedyCoins(coins, amount).map(String.init) ?? "impossible")")
}
```

```output
[1, 3, 4] for 6: DP 2, greedy 3
[1, 5, 10, 25] for 63: DP 6, greedy 6
[5, 7] for 24: DP 4, greedy impossible
[4, 6] for 9: DP impossible, greedy impossible
```

What to notice:

- With US coins, greedy happens to be right (25 + 25 + 10 + 1 + 1 + 1). Coin systems like that are called canonical, and most real currencies are designed to be.
- With \{5, 7\} and 24, greedy takes three 7s and is stuck with 3. The DP finds 7 + 7 + 5 + 5.
- With \{4, 6\}, every total is even, so 9 is impossible, and the sentinel survives to the end.
- The time is O(amount × k) for k coin values, and the memory is O(amount).

Step through another coin system, where greedy's first coin is already a mistake. The amber cell is being filled, and the blue cells are the totals one coin below it:

### Which coins?

Record the coin that achieved each `fewest[t]`, then follow it back from the amount, as in rod cutting:

```swift run
let coins = [1, 5, 6, 9]
let amount = 11

let impossible = amount + 1
var fewest = Array(repeating: impossible, count: amount + 1)
var lastCoin = Array(repeating: 0, count: amount + 1)    // the coin that achieved fewest[total]
fewest[0] = 0
for total in stride(from: 1, through: amount, by: 1) {
    for coin in coins where coin <= total && fewest[total - coin] + 1 < fewest[total] {
        fewest[total] = fewest[total - coin] + 1
        lastCoin[total] = coin
    }
}

var used: [Int] = []
var left = amount
while left > 0 {
    used.append(lastCoin[left])
    left -= lastCoin[left]
}
print("fewest:", fewest)
print("\(amount) = " + used.map(String.init).joined(separator: " + "))
```

```output
fewest: [0, 1, 2, 3, 4, 1, 1, 2, 3, 1, 2, 2]
11 = 5 + 6
```

Only call the walk-back when the amount is possible. Otherwise `lastCoin[left]` is 0 and the `while` loop never ends.

## Coin change II: how many ways?

Now count. How many different ways can the coins make the amount? Two payments are the **same** if they use the same coins, whatever the order: 1 + 2 and 2 + 1 are one way. In maths terms, you're counting **combinations** (multisets of coins), not sequences.

The counting version of the unbounded knapsack is the subset-counting DP from [Count subsets and target sum](/dsa/learn/dpk-count-subsets) with the loop turned left to right:

```swift
var ways = Array(repeating: 0, count: amount + 1)
ways[0] = 1                                       // one way to pay 0: no coins
for coin in coins {                               // coins OUTER
    for total in stride(from: coin, through: amount, by: 1) {   // left to right: reuse allowed
        ways[total] += ways[total - coin]
    }
}
```

The fewest-coins code had the totals outside and the coins inside. What if you write the counting version that way too? It looks equally reasonable.

## The loop-order trap

Run both orders on coins \{1, 2, 3\} and amount 4:

```swift run
let coins = [1, 2, 3]
let amount = 4

// Coins outer: each coin is finished before the next starts
var combinations = Array(repeating: 0, count: amount + 1)
combinations[0] = 1
for coin in coins {
    for total in stride(from: coin, through: amount, by: 1) {
        combinations[total] += combinations[total - coin]
    }
    print("after coin \(coin):", combinations)
}

// Amount outer: every coin may be the last one, for every total
var sequences = Array(repeating: 0, count: amount + 1)
sequences[0] = 1
for total in stride(from: 1, through: amount, by: 1) {
    for coin in coins where coin <= total {
        sequences[total] += sequences[total - coin]
    }
}
print("amount outer:", sequences)
```

```output
after coin 1: [1, 1, 1, 1, 1]
after coin 2: [1, 1, 2, 2, 3]
after coin 3: [1, 1, 2, 3, 4]
amount outer: [1, 1, 2, 4, 7]
```

Same coins, same amount, two answers: 4 and 7. Neither crashes. Which is right depends on what you're counting, so list every way by hand:

```swift run
// List every way to make 4 from coins 1, 2 and 3, as an ordered sequence
func sequences(_ amount: Int, _ coins: [Int]) -> [[Int]] {
    if amount == 0 { return [[]] }
    var result: [[Int]] = []
    for coin in coins where coin <= amount {
        for rest in sequences(amount - coin, coins) {
            result.append([coin] + rest)
        }
    }
    return result
}

let all = sequences(4, [1, 2, 3])
print("ordered:", all.count)
for way in all {
    print("  " + way.map(String.init).joined(separator: " + "))
}
let unordered = Set(all.map { $0.sorted() })
print("ignoring order:", unordered.count)
for way in unordered.sorted(by: { $0.lexicographicallyPrecedes($1) }) {
    print("  " + way.map(String.init).joined(separator: " + "))
}
```

```output
ordered: 7
  1 + 1 + 1 + 1
  1 + 1 + 2
  1 + 2 + 1
  1 + 3
  2 + 1 + 1
  2 + 2
  3 + 1
ignoring order: 4
  1 + 1 + 1 + 1
  1 + 1 + 2
  1 + 3
  2 + 2
```

**Coins outer counts combinations (4). Amount outer counts ordered sequences, often called permutations (7).**

### Why the order decides

**Coins outer.** While the loop is on coin 1, only 1s exist. Then 2s are added on top of every way made of 1s, then 3s on top of those. Every payment is built in one fixed order: all its 1s, then all its 2s, then all its 3s. So each combination is built exactly once. Look at the rows: after coin 2, `ways[4]` is 3 (1+1+1+1, 1+1+2, 2+2), and coin 3 adds `ways[1]`, the single way 1 + 3.

**Amount outer.** For each total, every coin gets a turn at being the **last** one. `sequences[4]` adds `sequences[3]` (ending in 1), `sequences[2]` (ending in 2) and `sequences[1]` (ending in 3). Nothing stops 1 + 3 (ends in 3) and 3 + 1 (ends in 1) from both being counted, so every order counts separately.

<Callout kind="analogy">
Coins outer is like paying by emptying your purse one denomination at a time: all the pennies first, then the twos, then the fives. There's only one way to do that for any given handful. Amount outer is like dropping coins into the machine one by one, where each order of drops is a different event.
</Callout>

Sometimes the sequences **are** what you want. Climbing a staircase taking 1, 2 or 3 steps at a time, as in [Climbing stairs and min-cost stairs](/dsa/learn/dp-stairs), counts 1 then 3 and 3 then 1 as different climbs. That's the amount-outer loop. Read the question for the word "order" (or "different sequences"), and pick the loop to match.

### Why fewest coins didn't care

Coin change I used amount outer, and that was fine. The fewest coins for a total is a property of the **collection** of coins, and every collection appears among the sequences. Counting the same collection several times changes a count, but it can't change a minimum. For a min or a max, either order works. For a count, the order decides the meaning.

| Question | Loops | Coins \{1, 2, 3\}, amount 4 |
| --- | --- | --- |
| Fewest coins | either order | 2 (1 + 3 or 2 + 2) |
| Ways, order doesn't matter | coins outer | 4 |
| Ways, order matters | amount outer | 7 |

<Callout kind="gotcha" title="Swift gotcha: the Int.max sentinel">
It's tempting to mark "impossible" with `Int.max`. Then `fewest[total - coin] + 1` overflows as soon as `total - coin` is impossible, and Swift stops the program:

```text title="What you'll see"
Swift runtime failure: arithmetic overflow
```

Either guard it (`where fewest[total - coin] != Int.max`) or use `amount + 1`, which no answer can reach and which has room to add 1.
</Callout>

## Common mistakes

- **Wrong loop order for counting.** Coins outer for combinations, amount outer for sequences. Check with coins \{1, 2\} and amount 3: combinations give 2, sequences give 3.
- **`ways[0] = 0`.** Paying 0 has one way, with no coins. Every count grows from it.
- **Returning the sentinel.** Convert `amount + 1` back to "impossible" (here `nil`, or `-1` if the problem says so).
- **Overflowing counts.** The number of ways grows fast. Use the modulus the problem gives after every addition.
- **Amount 0.** The fewest coins is 0 and the number of ways is 1. Both fall out of the base case if your loops handle an empty range, which `stride` does.

## Practice

**Fewest coins to pay** is coin change I with large amounts, where you report `-1` for impossible ones. **Ways to make change** is coin change II, counted modulo 1,000,000,007. Its tests check the loop order: a payment counted twice gives a wrong answer.
