## Why it matters

Real budgets often come in pairs. A flight bag has a weight limit **and** a size limit. A sprint has developer hours **and** designer hours. A cloud job needs CPU **and** memory. When every item uses up two resources at once, the knapsack needs two capacities. The DP grows one dimension, and the 0/1 rule from the one-row knapsack becomes "iterate **both** capacities downward". The interview classic is about binary strings, where each string costs some 0s and some 1s.

## The problem

You have a list of strings made of `0`s and `1`s, and a budget of `zeros` 0s and `ones` 1s. Choose as many strings as possible so that, all together, they use at most `zeros` 0s and at most `ones` 1s. Each string can be chosen once.

For example, with the strings `"01"`, `"1100"`, `"0"`, `"111"` and `"00"`, and a budget of 3 zeros and 3 ones, the best is 3 strings: `"0"`, `"111"` and `"00"` use exactly 3 zeros and 3 ones. Picking the shortest strings first doesn't work: `"0"` and `"01"` look cheap, but after them only 1 zero and 2 ones remain. `"00"` needs 2 zeros, `"111"` needs 3 ones and `"1100"` needs both, so the greedy stops at 2 strings, not 3.

## Two weights, one value

Each string is a 0/1 knapsack item with:

- a first weight: its number of `0`s;
- a second weight: its number of `1`s;
- a value of 1, since you're counting strings.

So use [the DP recipe](/dsa/learn/dp-recipe) with a state that has room for both budgets:

- **State.** `best[z][o]` is the most strings, among those seen so far, that fit in `z` zeros and `o` ones.
- **Transition.** For a string costing `a` zeros and `b` ones, either skip it or take it: `best[z][o] = max(best[z][o], best[z - a][o - b] + 1)`, when `a ≤ z` and `b ≤ o`.
- **Base case.** Before any strings, every cell is 0.
- **Order.** One string at a time, and for each string, both `z` and `o` from high to low.
- **Answer.** `best[zeros][ones]`.

The full table would be three-dimensional, `best[i][z][o]` for the first `i` strings. Exactly as in [0/1 knapsack, from 2D to 1D](/dsa/learn/dpk-01), each layer reads only the one before, so one 2D table updated in place is enough, provided the loops run downward.

```swift run
/// The most strings you can choose using at most `zeros` 0s and `ones` 1s in total, each string at most once
func mostStrings(_ strings: [String], zeros: Int, ones: Int) -> Int {
    // best[z][o]: the most strings so far that fit in z zeros and o ones
    var best = Array(repeating: Array(repeating: 0, count: ones + 1), count: zeros + 1)
    for string in strings {
        let a = string.filter { $0 == "0" }.count        // this string's cost in zeros
        let b = string.count - a                         // and in ones
        if a > zeros || b > ones { continue }            // can never fit
        for z in stride(from: zeros, through: a, by: -1) {     // both capacities downward
            for o in stride(from: ones, through: b, by: -1) {
                best[z][o] = max(best[z][o], best[z - a][o - b] + 1)
            }
        }
    }
    return best[zeros][ones]
}

let strings = ["01", "1100", "0", "111", "00"]
print(mostStrings(strings, zeros: 3, ones: 3))   // "0", "111", "00"
print(mostStrings(strings, zeros: 1, ones: 1))   // "01" alone, or "0" alone
print(mostStrings(["11", "11", "0"], zeros: 0, ones: 3))
```

```output
3
1
1
```

What to notice:

- `string.count - a` works because every character is a `0` or a `1`. Counting with `filter` is O(length), done once per string.
- The `continue` skips strings that can never fit. A `stride` whose end is past its start would be empty anyway, but skipping says what you mean.
- With no zeros allowed, only strings made entirely of 1s qualify, and the two `"11"`s need 4 ones together, so only one fits.
- The cost is O(L + n · Z · O), where L is the total length of the strings, n their number, and Z and O the two budgets. Memory is O(Z · O).

## Why both loops go down

In the one-capacity knapsack, right to left meant "`best[w - weight]` hasn't been touched by this item yet". With two capacities, the cell you read is `best[z - a][o - b]`, and it must also be untouched. If both loops go down, it is: either `z - a` is a smaller row, which the outer loop reaches **later**, or (when `a` is 0) it's the same row, and `o - b` is a smaller column, which the inner loop reaches later.

That second case is why running only one loop downward isn't enough. A string like `"11"` costs **zero** 0s, so its update reads from the **same** row, and if that row's loop goes up, the string gets taken twice:

```swift run
// One string, "11": it costs 0 zeros and 2 ones. Budget: 2 zeros and 4 ones. It can be chosen once.
let a = 0
let b = 2
let zeros = 2
let ones = 4

func choose(onesDownward: Bool) -> Int {
    var best = Array(repeating: Array(repeating: 0, count: ones + 1), count: zeros + 1)
    for z in stride(from: zeros, through: a, by: -1) {
        let columns = onesDownward ? Array(stride(from: ones, through: b, by: -1)) : Array(stride(from: b, through: ones, by: 1))
        for o in columns {
            best[z][o] = max(best[z][o], best[z - a][o - b] + 1)   // z - a is z itself: the same row
        }
    }
    return best[zeros][ones]
}

print("both downward:      ", choose(onesDownward: true))
print("ones going upward:  ", choose(onesDownward: false))
```

```output
both downward:       1
ones going upward:   2
```

With the ones loop going up, `best[z][2]` becomes 1, and then `best[z][4]` reads it and adds the same string again. Only inputs with a string of all 1s (or all 0s, for the other loop) expose the bug, which is exactly the kind of bug that passes the examples and fails the hidden tests.

<Callout kind="tip" title="The rule, in general">
For a 0/1 item with several weights, every capacity loop goes **downward**. For an unbounded item, every capacity loop goes upward. Mixing directions is never right.
</Callout>

## More dimensions, and "at least"

Nothing stops at two. Three resources means a 3D table and three downward loops, with cost O(n · C₁ · C₂ · C₃). The product of the capacities grows quickly, so this is practical when each budget is small, say up to 100.

A common twist is that one dimension is a **target to reach** rather than a budget not to exceed. "Choose projects using at most 4 volunteers that raise **at least** 5" is an example. Raising 5, 6 or 50 all count the same, so clamp: give that dimension columns 0 to 5 only, and when a project would take the total past 5, put it in column 5. Column 5 then means "5 or more".

```swift run
// Projects: each needs some volunteers and raises some money. With at most 4 volunteers in total,
// how many sets of projects raise at least 5?
let needs = [2, 3, 1]
let raises = [4, 5, 1]
let volunteers = 4
let goal = 5

// ways[v][f]: sets using at most v volunteers whose money, capped at the goal, is exactly f
var ways = Array(repeating: Array(repeating: 0, count: goal + 1), count: volunteers + 1)
for v in 0...volunteers {
    ways[v][0] = 1                                       // the empty set fits any budget and raises 0
}
for (need, raise) in zip(needs, raises) {
    for v in stride(from: volunteers, through: need, by: -1) {
        for f in stride(from: goal, through: 0, by: -1) {
            let capped = min(goal, f + raise)            // "at least the goal" all lands in one column
            ways[v][capped] += ways[v - need][f]
        }
    }
}
print("plans that reach the goal:", ways[volunteers][goal])

// Brute force over every set of projects
var count = 0
for mask in 0..<(1 << needs.count) {
    let chosen = needs.indices.filter { mask & (1 << $0) != 0 }
    let people = chosen.map { needs[$0] }.reduce(0, +)
    let money = chosen.map { raises[$0] }.reduce(0, +)
    if people <= volunteers && money >= goal { count += 1 }
}
print("brute force:", count)
```

```output
plans that reach the goal: 3
brute force: 3
```

The three plans are the second project alone (3 volunteers, raising 5), the first and third (3 volunteers, raising 5) and the second and third (4 volunteers, raising 6). Here the update **pushes** from column `f` into column `capped` instead of pulling, because several columns can land in the clamped one. Both loops still go down, and `ways[v][0] = 1` for every `v` makes "at most v volunteers" work, since the empty plan fits every budget.

<Callout kind="gotcha" title="Traps with two capacities">
- **One loop up, one loop down.** It works on most inputs and fails on items that cost nothing in one dimension.
- **Swapping the dimensions.** `best[z][o]` must be indexed in the same order it was created: `Array(repeating: Array(repeating: 0, count: ones + 1), count: zeros + 1)` makes rows for zeros and columns for ones.
- **Counting characters slowly.** Work out each string's two costs once, before the loops, rather than inside them.
- **A huge table.** Z × O cells must fit in memory: 100 × 100 is nothing, but 10⁵ × 10⁵ is 10¹⁰ cells. Check the constraints before choosing this DP.
</Callout>
