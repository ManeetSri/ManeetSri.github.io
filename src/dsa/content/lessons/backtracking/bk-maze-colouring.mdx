## Why it matters

A robot planning every way across a warehouse floor, a game listing every route through a level, a timetable that must give each exam one of m time slots without clashes: these look like different problems, but they're the same backtracking template with different state. This lesson works through two classics, **rat in a maze** (every route through a grid) and **m-colouring** (give each vertex one of m colours so that neighbours differ), and then lines up every problem in the module side by side, so you can see that writing a new backtracking solution is mostly a matter of naming its four parts.

## Rat in a maze: every route

A maze is a grid of 1s (open) and 0s (walls). A rat starts at the top-left cell and wants the bottom-right one. It moves one cell down (D), left (L), right (R) or up (U) at a time, only through open cells, and never visits a cell twice on the same route. List every route as its string of moves.

Name the parts first:

- **State:** the current cell, the cells already on the route, and the moves so far.
- **Choices:** the four moves.
- **Constraint:** the next cell is inside the grid, open, and not already on the route.
- **Goal:** standing on the exit.

```swift run
func mazeRoutes(_ maze: [[Int]]) -> [String] {
    let rows = maze.count
    let columns = maze[0].count
    guard maze[0][0] == 1, maze[rows - 1][columns - 1] == 1 else { return [] }
    let moves: [(letter: Character, dRow: Int, dColumn: Int)] = [("D", 1, 0), ("L", 0, -1), ("R", 0, 1), ("U", -1, 0)]
    var visited = Array(repeating: Array(repeating: false, count: columns), count: rows)
    var route: [Character] = []
    var routes: [String] = []

    func walk(_ row: Int, _ column: Int) {
        if row == rows - 1 && column == columns - 1 {       // reached the exit
            routes.append(String(route))
            return
        }
        visited[row][column] = true                         // choose: this cell is on the route
        for move in moves {
            let nextRow = row + move.dRow
            let nextColumn = column + move.dColumn
            guard nextRow >= 0, nextRow < rows, nextColumn >= 0, nextColumn < columns,
                  maze[nextRow][nextColumn] == 1, !visited[nextRow][nextColumn] else { continue }
            route.append(move.letter)
            walk(nextRow, nextColumn)                       // explore
            route.removeLast()
        }
        visited[row][column] = false                        // unchoose: free the cell for other routes
    }

    walk(0, 0)
    return routes
}

let maze = [
    [1, 0, 0, 0],
    [1, 1, 0, 1],
    [1, 1, 0, 0],
    [0, 1, 1, 1],
]
print(mazeRoutes(maze))
print(mazeRoutes([[1, 1, 1], [1, 1, 1], [1, 1, 1]]).count, "routes across an open 3 × 3 grid")
```

```output
["DDRDRR", "DRDDRR"]
12 routes across an open 3 × 3 grid
```

What to notice:

- **It's word search again.** Mark the cell on the way in, unmark it on the way out, so that a cell used by one route is free for the next. The difference is the goal: a position instead of a letter count. The move list is a direction array, as in [Direction arrays for grid moves](/dsa/learn/matrix-directions).
- **The routes come out in alphabetical order for free.** The moves are tried in the order D, L, R, U, which is alphabetical, and a route ends the moment it reaches the exit, so no route is the start of another. Depth-first search then produces them sorted, exactly as the binary strings came out sorted in M17.
- **The cost explodes on open grids.** Every self-avoiding route counts: 2 across an open 2 × 2 grid, 12 across 3 × 3, 184 across 4 × 4, 8,512 across 5 × 5 and over 1.2 million across 6 × 6. Walls are what keep real mazes manageable.

If the rat could only move **down and right**, every move would take it further from the start, so it could never come back to a cell. Then no `visited` table is needed at all, and if you only want the **number** of routes, it's a counting problem for dynamic programming: [Unique paths I and II](/dsa/learn/dpg-unique-paths).

## m-colouring: the same template on a graph

[Graph colouring](/dsa/learn/ag-colouring) introduced colouring: give every vertex a colour so that no edge joins two vertices of the same colour. It covered greedy colouring, the chromatic number and a backtracking search that finds one colouring with m colours. Here the focus is the template itself, so let's change the question slightly and **count** every proper colouring with m colours.

- **State:** the colours of the vertices before the current one.
- **Choices:** the m colours for the current vertex.
- **Constraint:** no neighbour that's already coloured has that colour.
- **Goal:** every vertex coloured.

```swift run
func countColourings(_ n: Int, _ edges: [[Int]], colours m: Int) -> Int {
    var neighbours = [[Int]](repeating: [], count: n)
    for edge in edges {
        neighbours[edge[0]].append(edge[1])
        neighbours[edge[1]].append(edge[0])
    }
    var colour = [Int](repeating: -1, count: n)            // -1: not coloured yet

    func paint(_ vertex: Int) -> Int {
        if vertex == n { return 1 }                         // every vertex coloured: one colouring
        var total = 0
        for c in 0..<m where !neighbours[vertex].contains(where: { colour[$0] == c }) {
            colour[vertex] = c                              // choose
            total += paint(vertex + 1)                      // explore
            colour[vertex] = -1                             // unchoose
        }
        return total
    }

    return paint(0)
}

let pentagon = [[0, 1], [1, 2], [2, 3], [3, 4], [4, 0]]
let square = [[0, 1], [1, 2], [2, 3], [3, 0]]
print(countColourings(5, pentagon, colours: 2), countColourings(5, pentagon, colours: 3))
print(countColourings(4, square, colours: 2), countColourings(4, square, colours: 3))
```

```output
0 30
2 18
```

What to notice:

- **The unchoose step really matters here.** Vertex 4 of the pentagon is a neighbour of vertex 0. If vertex 4 kept a stale colour after its subtree was explored, then when the search backed up and tried a new colour for an earlier vertex, a check like `colour[4] == c` could reject a colour that's actually free. Resetting to −1 means "not coloured" stays true for every vertex the search hasn't reached.
- **Counting returns a sum,** as N-Queens did: 1 at each complete colouring, and each call adds up its children.
- **A cycle with an odd number of vertices can't be 2-coloured**, so the pentagon gives 0. With an even cycle, 2 colours give exactly 2 colourings: alternate, starting with either colour. (For checking your own code: a cycle of n vertices has (k − 1)ⁿ + (−1)ⁿ(k − 1) proper colourings with k colours, and 2⁵ − 2 = 30 and 2⁴ + 2 = 18 match the output.)
- **The tree has up to mⁿ leaves.** Checking each colour against the neighbours as soon as it's chosen, rather than checking whole colourings at the end, is what keeps it usable. The colouring lesson's two improvements, symmetry breaking and colouring the most constrained vertex first, apply to counting too; the second is the Sudoku rule again.

## One template, every problem

Here is the whole module in one table. Each row is the same function with different answers to four questions:

| Problem | State | Choices | Constraint | Goal |
| --- | --- | --- | --- | --- |
| Subsets | items chosen, next index | the next item, from `start` | skip equal siblings | every node |
| Permutations | path, `used` | any unused item | skip equal siblings | path is full |
| Combination sum | path, amount left | candidates from `start` | candidate ≤ amount left | amount left is 0 |
| Brackets | string, open and close counts | "(" or ")" | open < n, close < open | length 2n |
| Partitioning | where the next piece starts | where it ends | the piece is valid | at the end |
| Word search | cell, letters matched | 4 neighbours | right letter, unused | last letter matched |
| N-Queens | column per row so far | the next row's columns | column and diagonals free | every row filled |
| Sudoku | the grid | digits for the chosen cell | row, column and box | no empty cell |
| Rat in a maze | cell, route | 4 moves | inside, open, unvisited | at the exit |
| m-colouring | colours so far | m colours | no neighbour shares it | every vertex coloured |

When you meet a new backtracking problem, fill in this row first. The code follows almost mechanically.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting to unmark a maze cell.** The search still finds some routes, but misses every route that passes through a cell an earlier route used.
- **Marking the exit and then never unmarking it.** In the code above the goal is checked before marking, so the exit is never marked at all. If you mark first, the unmark must still run on the way out.
- **Not checking that the start and exit are open.** A walled-off start has no routes, not one empty route.
- **Leaving stale colours behind.** Reset the vertex when you unchoose, or later checks see colours that aren't really there.
</Callout>
