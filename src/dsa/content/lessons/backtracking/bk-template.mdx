## Why it matters

Some questions have no formula: list every way to seat these guests, every word you can spell with these tiles, every way to finish this Sudoku. You have to try the options. **Backtracking** tries them systematically: build an answer one decision at a time, and the moment a half-built answer breaks a rule, step back and try the next option instead. It drives puzzle solvers, word games, the "try this alternative, and if it fails, back up" logic inside many regular-expression engines, and a whole family of interview problems. This module is about doing it well: one template, many problems, and the pruning that makes it fast.

## Every answer is a path through a tree of decisions

Take a bike lock with 3 wheels, each showing 1, 2 or 3, and one rule: **neighbouring wheels must show different digits**. Which codes are allowed?

Build a code one wheel at a time. Before the first wheel there's nothing; choosing its digit gives three possibilities; each of those has two ways to choose the second wheel (anything but the digit before it); and so on. Drawn out, the choices form a tree:

```text
                           (start)
            /                 |                 \
           1                  2                  3
        /     \            /     \            /     \
      12       13        21       23        31       32
     /  \     /  \      /  \     /  \      /  \     /  \
   121  123 131  132  212  213 231  232  312  313 321  323
```

This is the **decision tree** (also called the state-space tree), and it has four parts you'll name in every problem:

- **State:** the partial answer at a node, here the digits chosen so far. The root is the empty answer.
- **Choices:** the edges leaving a node, here the next wheel's digit.
- **Constraint:** the rule that rules a choice out. "11" never appears, because the second 1 breaks the rule.
- **Goal:** when a state is a complete answer. Here, a leaf at depth 3. There are 12 of them.

Backtracking is a depth-first walk of this tree. It never builds the tree as a data structure: the tree is the shape of the recursive calls. You met that idea in [Recursion trees and their complexity](/dsa/learn/rec-recursion-trees), and in [Multiple recursion and exponential blow-up](/dsa/learn/rec-multiple-recursion), where one call per choice listed every binary string.

## The template: choose, explore, unchoose

Here is the lock in Swift. One array, `code`, holds the path from the root to wherever the search is now:

```swift run
var code: [Int] = []                       // the state: the path from the root to here
var found: [[Int]] = []

func explore() {
    if code.count == 3 {                   // goal: a complete code
        found.append(code)
        return
    }
    for digit in 1...3 {
        if code.last == digit { continue } // constraint: skip this branch entirely
        code.append(digit)                 // choose
        explore()                          // explore everything below this choice
        code.removeLast()                  // unchoose: put the state back
    }
}

explore()
print(found.count, "codes")
print(found.prefix(4).map { $0.map(String.init).joined() })
```

```output
12 codes
["121", "123", "131", "132"]
```

Every backtracking solution in this module has this shape:

```text
explore(state):
    if state is a complete answer:
        record it
        return
    for each choice available from state:
        if the choice breaks a rule: skip it          (prune)
        make the choice                               (choose)
        explore(the new state)                        (explore)
        undo the choice                               (unchoose)
```

What to notice:

- **The invariant.** Whenever `explore()` starts, `code` is exactly the path to the current node. Each call must hand the state back exactly as it received it, so after exploring everything under "1", `code` is empty again and "2" can be tried. That's the whole job of the unchoose line.
- **Pruning happens before the recursive call.** The search never enters "11", so it never wastes time on the three codes that start with it.
- **`code.last == digit` compares an optional with an `Int`.** When `code` is empty, `code.last` is `nil`, which never equals a digit, so the first wheel can be anything.

Most solutions wrap this in a function with the state as local variables and the recursion as a **nested function**. A nested function captures the variables around it, so it can change `code` and `found` directly without `inout` parameters:

```swift run
func lockCodes(wheels: Int, digits: Int) -> [[Int]] {
    var code: [Int] = []
    var found: [[Int]] = []

    func explore() {
        if code.count == wheels {
            found.append(code)
            return
        }
        for digit in 1...digits where code.last != digit {
            code.append(digit)             // choose
            explore()                      // explore
            code.removeLast()              // unchoose
        }
    }

    explore()
    return found
}

print(lockCodes(wheels: 2, digits: 3))
print(lockCodes(wheels: 4, digits: 2))
```

```output
[[1, 2], [1, 3], [2, 1], [2, 3], [3, 1], [3, 2]]
[[1, 2, 1, 2], [2, 1, 2, 1]]
```

The `where` clause is the constraint, written into the loop. You'll see this style in every lesson of the module.

Here's the same walk on another decision tree, the one for the subsets of `[1, 2, 3]`, which is the next lesson's subject. Each level decides one item: in or out. Watch the current path (the state) grow on the way down and shrink on the way back up:

## State that's copied, and state that's restored

There are two ways to give each call its state.

**Copy it.** Pass the partial answer as a parameter and build a new array for each child. Every call owns its own copy, so there's nothing to undo:

```swift run
func lockCodes(_ code: [Int], wheels: Int, digits: Int, into found: inout [[Int]]) {
    if code.count == wheels {
        found.append(code)
        return
    }
    for digit in 1...digits where code.last != digit {
        lockCodes(code + [digit], wheels: wheels, digits: digits, into: &found)   // a fresh array per child
    }
}

var found: [[Int]] = []
lockCodes([], wheels: 3, digits: 3, into: &found)
print(found.count, found.first!, found.last!)
```

```output
12 [1, 2, 1] [3, 2, 3]
```

**Mutate it and restore it.** Keep one shared array, append before the call and remove after it, as in the first example.

| | Copy per call | Mutate and restore |
| --- | --- | --- |
| Undo step | none | must match the choose step exactly |
| Cost per step | O(depth) to build the new array | O(1) |
| Easy to get wrong? | hard | forgetting to undo is the classic bug |

Small values, like a count of open brackets or the amount left to reach a target, are copied for free when you pass them as parameters: `explore(remaining - coin)` needs no undo. Arrays, grids and Bool tables are usually shared and restored, because copying them at every node costs real time. Most solutions mix the two.

Here's what happens when the undo goes missing:

```swift run
var code: [Int] = []
var found: [String] = []

func explore(_ depth: Int) {
    if depth == 2 {
        found.append(code.map(String.init).joined())
        return
    }
    for digit in 1...3 where code.last != digit {
        code.append(digit)
        explore(depth + 1)
        // Bug: the code.removeLast() is missing
    }
}

explore(0)
print(found)
```

```output
["12", "123", "12321", "123212", "1232123"]
```

Nothing is ever taken back, so the "path" keeps growing, and later branches start from leftovers of earlier ones. No crash, no warning, only wrong answers.

<Callout kind="gotcha" title="Swift gotcha: recording the answer">
`found.append(code)` stores a **copy** of `code`, because Swift arrays are values (with copy-on-write, so the copy is only made when `code` changes later). The recorded answer never changes when you `removeLast()` afterwards. In languages where arrays are references, such as Java or Python, recording the shared list without copying it is a famous bug. Swift saves you from it, but if your state lives in a **class**, you're back to sharing a reference.
</Callout>

## Counting the nodes in the tree

The cost of a backtracking search is roughly:

> (number of nodes visited) × (work done at each node)

So the first question about any backtracking solution is: how big is its tree? Count the calls:

```swift run
func countNodes(wheels: Int, digits: Int) -> (nodes: Int, leaves: Int) {
    var nodes = 0
    var leaves = 0
    func explore(_ depth: Int, _ previous: Int) {     // previous is 0 before the first wheel
        nodes += 1
        if depth == wheels {
            leaves += 1
            return
        }
        for digit in 1...digits where digit != previous {
            explore(depth + 1, digit)
        }
    }
    explore(0, 0)
    return (nodes, leaves)
}

for wheels in [3, 6, 10] {
    let (nodes, leaves) = countNodes(wheels: wheels, digits: 3)
    print("\(wheels) wheels: \(leaves) codes, \(nodes) nodes in the tree")
}
```

```output
3 wheels: 12 codes, 22 nodes in the tree
6 wheels: 96 codes, 190 nodes in the tree
10 wheels: 1536 codes, 3070 nodes in the tree
```

This time the state is a single number, `previous`, passed down as a parameter: nothing to undo.

What to notice:

- **The leaves dominate.** Each level is twice as wide as the one above, so the whole tree has fewer than twice as many nodes as leaves. That's true whenever every node has at least two children: total nodes ≈ leaves × b / (b − 1) for branching factor b.
- **Pruning shrinks the base of the exponent.** Without the rule, the tree would have 3 choices per level and 3¹⁰ = 59,049 leaves for 10 wheels. With it, each level after the first has only 2 choices: 3 × 2⁹ = 1,536.
- **Recording costs too.** Copying each answer takes O(depth), so listing all answers costs O(depth × leaves) at least.

The trees you'll meet most in this module:

| Problem | Depth | Choices per level | Leaves |
| --- | --- | --- | --- |
| Subsets of n items | n | 2 (in or out) | 2ⁿ |
| Orderings of n items | n | n, then n − 1, … | n! |
| A code of n symbols from k | n | k | kⁿ |
| The lock above | n | 3, then 2 | 3 × 2ⁿ⁻¹ |

The last lesson of the module, [Pruning and backtracking complexity](/dsa/learn/bk-pruning), comes back to these numbers and to the ways of cutting them down.

<Callout kind="analogy">
Think of exploring a hedge maze with a ball of string. At each fork you pick a path and unroll string as you go. At a dead end you wind the string back to the last fork and try the next path. The string is your state: it always runs exactly from the entrance to where you're standing. Winding it back is the unchoose step.
</Callout>

<Callout kind="gotcha" title="The classic slips">
- **Forgetting to unchoose,** or undoing something other than what you did. Each choose step needs a matching undo.
- **Undoing too late or not at all on an early exit.** If a branch can `return` from the middle of the loop, make sure the state is restored first, or that nobody uses it again. Swift's `defer` helps: put the undo in a `defer` right after the choose step.
- **Pruning after the recursive call instead of before.** Checking a rule at the leaf still works, but it explores every doomed branch to the bottom first.
- **Very deep trees.** The recursion is as deep as the answer is long, which is usually small, but see [Stack depth limits in Swift](/dsa/learn/rec-stack-limits) if it isn't.
</Callout>
