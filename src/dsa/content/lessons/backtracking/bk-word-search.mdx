## Why it matters

Word games like Boggle hide words in a grid of letters, traced from cell to neighbouring cell. The same search finds a pattern of moves on a game board or a route that spells out a sequence of required stops. It's one of the most asked interview questions, because it joins two things you know: the grid walking from [DFS, recursive and iterative](/dsa/learn/gt-dfs), and backtracking's unchoose step. That step is the whole difference from flood fill, and seeing why is the main point of this lesson.

## Tracing a word through the grid

A word is traced by starting on any cell holding its first letter, then stepping **up, down, left or right** for each next letter, never using the same cell twice in one word. Searching is a depth-first search from every cell. The neighbours are the four moves from [Direction arrays for grid moves](/dsa/learn/matrix-directions), written out here as four calls:

```swift run
func exists(_ board: [[Character]], _ word: String) -> Bool {
    var grid = board                                     // a copy we're free to mark
    let letters = Array(word)
    let rows = grid.count
    let columns = grid[0].count

    func trace(_ row: Int, _ column: Int, _ index: Int) -> Bool {
        guard row >= 0, row < rows, column >= 0, column < columns,
              grid[row][column] == letters[index] else { return false }
        if index == letters.count - 1 { return true }    // matched the last letter
        let saved = grid[row][column]
        grid[row][column] = "#"                          // choose: this cell is in use
        defer { grid[row][column] = saved }              // unchoose, however we leave
        return trace(row - 1, column, index + 1) || trace(row + 1, column, index + 1)
            || trace(row, column - 1, index + 1) || trace(row, column + 1, index + 1)
    }

    for row in 0..<rows {
        for column in 0..<columns where trace(row, column, 0) {
            return true
        }
    }
    return false
}

let board: [[Character]] = [
    ["S", "E", "A", "L"],
    ["T", "A", "R", "E"],
    ["O", "N", "E", "S"],
]
for word in ["STONE", "SEAL", "ONES", "RARE", "EARS"] {
    print(word, exists(board, word))
}
```

```output
STONE true
SEAL true
ONES true
RARE false
EARS false
```

What to notice:

- **Marking in place.** Instead of a separate `visited` grid, the cell's letter is swapped for "#", which never matches a letter, so the path can't step on it again. Restoring the saved letter afterwards is the unchoose step.
- **`defer` makes the restore automatic.** It runs whenever the function exits, whichever `return` it takes, so a successful trace can't leave a "#" behind.
- **`||` short-circuits.** As soon as one direction succeeds, the remaining directions aren't tried, and `true` travels straight back up.
- **RARE needs two Rs** next to an A, and the grid has only one R, which can't be used twice. EARS fails because no R is next to an S.
- **`var grid = board` is a copy.** Arrays are values, so the caller's board is untouched. (The trie version in M40 used a separate `used` table instead, which also leaves the grid alone. Both are fine.)

## Why the unmark matters

[Number of islands and island area](/dsa/learn/gt-islands) also walks a grid with DFS and marks cells, but it **never unmarks** them. That's correct there: a flood fill only needs to visit each cell once in total, so marks are permanent and the cost is O(cells).

Word search is different. A cell that's useless on one path can be exactly what another path needs. Suppose a trace starts at one S, passes through an E and then fails. A later trace, starting from a different S, may need that very E. If the E were still marked from the failed attempt, the later trace would be blocked, and a word that's really there would be reported missing. Unmarking turns "visited ever" into "on the current path", and that's what makes it backtracking rather than a traversal. It's also why the cost can explode: the same cell appears on many different paths.

## How much work, and two cheap prunings

From a start cell, the first step has 4 directions, and every later step at most 3, since the cell you came from is in use. So one word of length L costs up to **O(cells × 4 × 3^(L − 1))**, which is O(cells · 3^L). On ordinary grids, mismatched letters end most paths within a step or two. The trouble is grids where almost everything matches, like a grid of A's and a word of A's that ends in a B:

```swift run
func traceCalls(_ board: [String], _ word: String, pruned: Bool) -> (found: Bool, calls: Int) {
    var grid = board.map { Array($0) }
    var letters = Array(word)
    let rows = grid.count
    let columns = grid[0].count
    if pruned {
        var inGrid: [Character: Int] = [:]
        for row in grid {
            for letter in row { inGrid[letter, default: 0] += 1 }
        }
        var inWord: [Character: Int] = [:]
        for letter in letters { inWord[letter, default: 0] += 1 }
        for (letter, count) in inWord where inGrid[letter, default: 0] < count {
            return (false, 0)                            // not enough of some letter: no search at all
        }
        if inGrid[letters[0], default: 0] > inGrid[letters[letters.count - 1], default: 0] {
            letters.reverse()                            // start from the rarer end
        }
    }
    var calls = 0
    func trace(_ row: Int, _ column: Int, _ index: Int) -> Bool {
        calls += 1
        guard row >= 0, row < rows, column >= 0, column < columns,
              grid[row][column] == letters[index] else { return false }
        if index == letters.count - 1 { return true }
        let saved = grid[row][column]
        grid[row][column] = "#"
        defer { grid[row][column] = saved }
        return trace(row - 1, column, index + 1) || trace(row + 1, column, index + 1)
            || trace(row, column - 1, index + 1) || trace(row, column + 1, index + 1)
    }
    for row in 0..<rows {
        for column in 0..<columns where trace(row, column, 0) {
            return (true, calls)
        }
    }
    return (false, calls)
}

let allA = Array(repeating: "AAAAA", count: 5)
let fenced = ["BCAAA", "CAAAA", "AAAAA", "AAAAA", "AAAAA"]
let word = String(repeating: "A", count: 11) + "B"
print("no B, plain: ", traceCalls(allA, word, pruned: false))
print("no B, pruned:", traceCalls(allA, word, pruned: true))
print("fenced B, plain: ", traceCalls(fenced, word, pruned: false))
print("fenced B, pruned:", traceCalls(fenced, word, pruned: true))
```

```output
no B, plain:  (found: false, calls: 397629)
no B, pruned: (found: false, calls: 0)
fenced B, plain:  (found: false, calls: 206433)
fenced B, pruned: (found: false, calls: 29)
```

The plain search tries hundreds of thousands of paths of A's, each failing only at the very last letter. Two checks before searching fix both cases:

- **Compare letter counts.** If the word needs more of some letter than the grid holds, the answer is `false` with no search at all. Counting both costs O(cells + L). Iterating over `inWord` visits its letters in no particular order, but the answer doesn't depend on that order.
- **Start from the rarer end.** A path read backwards spells the reversed word, so searching for the reversed word gives the same answer. If the word's first letter is more common in the grid than its last, reverse it. In the fenced grid, the reversed word starts with B: there's only one starting cell, and both its neighbours are C, so the search is over in 29 calls.

Neither check changes the worst case, but together they defeat exactly the inputs that make the plain search crawl. Mentioning them in an interview shows you think about where the time goes.

<Callout kind="analogy">
Tracing a word is like walking through a house trailing a ribbon, never crossing your own ribbon. When a corridor turns out to be a dead end, you walk back, winding the ribbon up behind you, and the rooms you left are free to use on the next attempt. A flood fill is more like painting every room you enter: once painted, a room is never entered again.
</Callout>

## Many words: let a trie lead

To find **every** word from a dictionary of thousands, searching for each one separately repeats the same exploration for words with shared prefixes, like "stare", "start" and "stark". [Word search II](/dsa/learn/trie-word-search-2) puts the words in a trie and walks it alongside the grid search, so each path is explored once and only while it's still the prefix of some word.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting to restore the cell.** Later starting cells then see "#" where a letter should be, and words that are there aren't found.
- **Checking bounds after indexing.** `grid[row][column]` with `row == -1` crashes. The `guard` checks bounds first, and `&&`-style commas stop at the first failure.
- **Allowing diagonal moves** when the problem says up, down, left and right, or the reverse. Read which neighbours count.
- **Never unmarking, as in flood fill.** It looks tidier and runs faster, but it misses words whose paths cross cells that an earlier failed path touched.
</Callout>

**Trace a word on a letter grid** is this lesson's search. Its tests include a 6 × 6 grid of A's with a 24-letter word ending in B, and the fenced-in B from above: a plain search explores tens of millions of paths, while the two prunings answer at once.

```cards
  front: "Why does word search unmark cells on the way back, when flood fill doesn't?"
  back: "Flood fill visits each cell once in total. In word search a cell can lie on many different paths, so \"used\" must mean \"on the current path\", and leaving a path frees its cells."
- id: ws-cost
  front: "What is the worst-case cost of tracing one word of length L in a grid?"
  back: "O(cells × 3^L): any cell can start, the first step has 4 directions and each later step at most 3."
- id: ws-prunings
  front: "What two checks before the search defeat the worst inputs for word search?"
  back: "Compare letter counts (the grid must hold enough of every letter), and reverse the word if its first letter is more common than its last."
- id: ws-defer
  front: "How does `defer` help with marking a grid cell in place?"
  back: "Put the restore in a `defer` straight after marking. It runs on every exit from the function, so a found word can't leave a mark behind."
```
