## Why it matters

Every backtracking search is exponential in the worst case, so the real question is always: **will this one finish?** The answer depends on three things you can reason about before writing a line: how big the decision tree is, how much of it pruning cuts away, and whether the same subtrees come up again and again. This lesson gathers the tools from the whole module into one kit: estimating tree sizes, pruning by feasibility, pruning by bound for "find the best" problems, choosing a good order, and spotting when caching the answers turns backtracking into dynamic programming.

## How big is the tree?

Start every backtracking problem by naming its depth and its branching, and turning that into a count of leaves:

| Shape | Leaves | Practical up to about |
| --- | --- | --- |
| In or out for each of n items | 2ⁿ | n = 20 to 25 |
| An order of n items | n! | n = 10 or 11 |
| One of k values for each of n positions | kⁿ | 3¹⁵ ≈ 14 million, 4¹² ≈ 17 million |
| k of n items | C(n, k) | C(30, 15) ≈ 155 million is already too many |
| Balanced strings of n pairs | Catalan Cₙ | n = 15 (C₁₅ = 9,694,845) |

Multiply the number of nodes by the work per node, and compare with what a computer can do: a few hundred million simple steps per second in an optimised build, and many times fewer in a debug build, which is how the companion package's tests run. Drag n and switch to the log scale to see how quickly 2ⁿ and n! leave everything else behind:

```visual growthChart
classes: ['O(n²)', 'O(2ⁿ)', 'O(n!)']
n: 10
max: 25
```

This works in reverse too. Constraints that say n ≤ 10 hint at permutations; n ≤ 20 at subsets or bitmasks; and n in the thousands means the exponential search isn't the intended answer at all.

## Pruning by feasibility

**Feasibility pruning** cuts a branch as soon as the partial answer can no longer become a valid one. You've used two kinds:

- **A rule is already broken.** A queen attacks another, a Sudoku digit repeats, a word's letter doesn't match. Checking each choice the moment it's made, instead of checking whole answers at the leaves, is the difference between n! and a few thousand nodes for 8 queens.
- **Finishing has become impossible.** Not enough items left to reach k, too many digits left for the remaining parts of an IP address, a word needing more Es than the grid holds, a cell with no candidates. These are look-ahead checks: nothing is broken yet, but nothing can work.

**Sorting** strengthens both. When candidates are sorted, "this one is too big" becomes "every later one is too big", and one `break` cuts a whole run of siblings, as in combination sum.

## Pruning by bound: branch and bound

Some problems want **the best** answer, not all of them: the most valuable set of items that fits in a bag, the cheapest route, the fewest coins. Then a branch can be cut even when it's perfectly feasible, if it **can't beat the best answer found so far**.

The method is called **branch and bound**:

1. Keep `best`, the best complete answer found so far.
2. At each node, compute an **optimistic bound**: a number that's guaranteed to be at least as good as anything in this subtree.
3. If the bound can't beat `best`, cut the branch.

The bound must never be too pessimistic, or you'd cut the subtree holding the real answer. Within that rule, the tighter it is, the more it cuts. Here's the classic test case, 0/1 knapsack (choose items with total weight at most the capacity, maximising their value), with two bounds:

- **All remaining values:** the value so far plus every remaining item's value, as if they all fitted. Always optimistic, but loose.
- **Fractional fill:** fill the remaining room greedily by value per unit of weight, taking a **fraction** of the first item that doesn't fit. Real items can't be split, so this is still optimistic, and much tighter. It's the greedy answer to the fractional knapsack problem from [Activity selection and fractional knapsack](/dsa/learn/greedy-activity-selection).

```swift run
let weights = [12, 7, 11, 8, 9, 6, 5, 14, 3, 10, 4, 13, 2, 15, 9, 7, 6, 11, 8, 5]
let values  = [24, 13, 23, 15, 16, 11, 9, 28, 5, 19, 7, 25, 3, 30, 17, 12, 10, 21, 14, 8]
let capacity = 40

enum Bound { case none, allRemaining, fractional }

func bestValue(_ bound: Bound) -> (best: Int, nodes: Int) {
    // Most value per unit of weight first, so good answers turn up early
    let order = weights.indices.sorted { values[$0] * weights[$1] > values[$1] * weights[$0] }
    let n = order.count
    var remainingValue = Array(repeating: 0, count: n + 1)       // value of everything from position i on
    for i in stride(from: n - 1, through: 0, by: -1) {
        remainingValue[i] = remainingValue[i + 1] + values[order[i]]
    }

    // Fill `room` greedily from `position` on, with a fraction of the first item that doesn't fit
    func fractionalFill(_ position: Int, _ room: Int) -> Double {
        var room = room
        var total = 0.0
        for item in order[position...] {
            if weights[item] > room {
                return total + Double(values[item]) * Double(room) / Double(weights[item])
            }
            room -= weights[item]
            total += Double(values[item])
        }
        return total
    }

    var best = 0
    var nodes = 0
    func explore(_ position: Int, _ weight: Int, _ value: Int) {
        nodes += 1
        best = max(best, value)
        if position == n { return }
        switch bound {                                           // cut if even the bound can't beat best
        case .none:
            break
        case .allRemaining:
            if value + remainingValue[position] <= best { return }
        case .fractional:
            if Double(value) + fractionalFill(position, capacity - weight) <= Double(best) { return }
        }
        let item = order[position]
        if weight + weights[item] <= capacity {                  // feasibility: it must fit
            explore(position + 1, weight + weights[item], value + values[item])   // take it
        }
        explore(position + 1, weight, value)                     // leave it
    }

    explore(0, 0, 0)
    return (best, nodes)
}

print("no bound:            ", bestValue(.none))
print("all remaining values:", bestValue(.allRemaining))
print("fractional fill:     ", bestValue(.fractional))
```

```output
no bound:             (best: 81, nodes: 48208)
all remaining values: (best: 81, nodes: 16719)
fractional fill:      (best: 81, nodes: 43)
```

Same answer every time; the work drops from 48,208 nodes to 43. The tight bound sees almost immediately that most branches can't reach 81, so they're never opened. (For knapsack with small integer capacities, [0/1 knapsack, from 2D to 1D](/dsa/learn/dpk-01) is usually better still. Branch and bound shines when the capacity or the values are too large for a DP table.)

## Order matters: what to try first

The same tree can be cheap or expensive to search depending on the order of the choices:

- **Try the most promising choice first** when looking for the best answer. A good `best` found early makes every bound cut more. That's why the knapsack sorts items by value per unit of weight before searching.
- **Decide the most constrained variable first** when looking for any valid answer. Dead ends show up near the root, where cutting saves the most. That's the Sudoku rule, and DSatur order for colouring.
- **Start from the rarest piece.** Word search's "reverse the word if its last letter is rarer" is the same idea in miniature.

## When branches repeat: memoisation turns backtracking into DP

Count the ways to make an amount from coins of 1, 2, 5 and 10, ignoring order. A backtracking count has two choices at each node: **use the current coin once more**, or **move past it for good**. The whole state is `(index, remaining)`.

Here's the key observation: many different paths reach the **same** state. For an amount of 20, paying 4 as 2 + 2, or as 1 + 1 + 2, and then moving past the 2s, both arrive at "coin index 2, 16 left", and the number of ways to finish from there is the same whichever path arrived. So compute it once and remember it:

```swift run
let coins = [1, 2, 5, 10]

func countWays(_ amount: Int, memoise: Bool) -> (ways: Int, calls: Int) {
    var calls = 0
    var memo: [Int: Int] = [:]                                   // key: index * (amount + 1) + remaining
    func ways(_ index: Int, _ remaining: Int) -> Int {
        calls += 1
        if remaining == 0 { return 1 }
        if index == coins.count || remaining < 0 { return 0 }
        let key = index * (amount + 1) + remaining
        if memoise, let known = memo[key] { return known }
        // Use coins[index] once more (and stay on it), or move past it for good
        let total = ways(index, remaining - coins[index]) + ways(index + 1, remaining)
        if memoise { memo[key] = total }
        return total
    }
    let total = ways(0, amount)
    return (total, calls)
}

for amount in [20, 50, 100] {
    print("amount \(amount):", countWays(amount, memoise: false), countWays(amount, memoise: true))
}
```

```output
amount 20: (ways: 40, calls: 1191) (ways: 40, calls: 161)
amount 50: (ways: 341, calls: 16061) (ways: 341, calls: 401)
amount 100: (ways: 2156, calls: 157071) (ways: 2156, calls: 801)
```

Without the memo, doubling the amount from 50 to 100 multiplies the calls by almost ten. With it, each of the at most 4 × (amount + 1) states is solved once, so the calls grow in step with the amount. This is exactly what [A preview of memoisation](/dsa/learn/rec-memo-preview) did for Fibonacci, and it's the doorway into dynamic programming: [Overlapping subproblems and optimal substructure](/dsa/learn/dp-what-is-dp) starts there, and [Coin change I and II](/dsa/learn/dpk-coin-change) solves this very problem.

Memoisation works only when the answer below a node depends on a **small** state, not on the whole path:

- **It helps** when counting or optimising, and the state is a few numbers: an index and an amount, a position and a count.
- **It can't help** when you must list every answer. The output is as big as the tree's leaves, and no cache makes it smaller.
- **It needs a bigger state** when the path matters, as with permutations, where what's left depends on which items are used. That state is a set, which fits in a bitmask, giving 2ⁿ states instead of n! paths: [Bitmask DP: TSP and assignment](/dsa/learn/dpa-bitmask).

## A checklist before you code

1. **Name the four parts:** state, choices, constraint, goal.
2. **Estimate the tree:** depth and branching give the leaves; multiply by the work per node.
3. **Prune by feasibility:** check each choice as it's made, and look ahead for "can't possibly finish".
4. **For best-answer problems, prune by bound,** and try promising choices first.
5. **Order the decisions:** most constrained first.
6. **Look for repeated states.** If the answer below a node depends only on a few numbers, memoise, and you've written a DP.

<Callout kind="gotcha" title="Common mistakes">
- **A bound that's too tight to be true.** If the "optimistic" estimate can ever be worse than a real answer in the subtree, the search can cut the branch holding the best answer and return something smaller, with no error.
- **Pruning with `<` where `<=` is safe, or the reverse.** Cutting when the bound merely **equals** `best` is fine when you only need the best value, but not if you need every answer that achieves it.
- **Memoising on part of the state.** If the answer depends on something not in the key, such as which cells are visited, the cache returns answers that belong to a different situation.
- **Integer keys that collide.** `index * (amount + 1) + remaining` is unique only because `remaining` never exceeds `amount`. When in doubt, use a struct that conforms to `Hashable` as the key.
</Callout>
