## Why it matters

A function can call **itself**. That idea, **recursion**, is how you'll walk trees, explore graphs, try every possibility in backtracking and split problems in half in divide and conquer. It feels strange at first, so this lesson takes it slowly with small examples and a clear picture of what happens inside the computer. M17 goes much deeper. For now, the aim is to see that recursion is just ordinary function calls, and to know its two essential parts.

## A function that calls itself

Here's a countdown written without a loop:

```swift run
func countdown(from n: Int) {
    if n == 0 {
        print("Liftoff!")
        return
    }
    print(n)
    countdown(from: n - 1)
}

countdown(from: 3)
```

```output
3
2
1
Liftoff!
```

Follow it step by step:

1. `countdown(from: 3)` prints 3, then calls `countdown(from: 2)`.
2. That call prints 2, then calls `countdown(from: 1)`.
3. That prints 1, then calls `countdown(from: 0)`.
4. `n` is 0, so it prints "Liftoff!" and returns, without calling itself again.

Each call does a little of the work and hands the rest to a **smaller** version of the same problem.

## The two parts of every recursive function

1. **The base case.** A situation simple enough to answer directly, without recursing. In `countdown`, it's `n == 0`. The base case is what makes the recursion stop.
2. **The recursive case.** Everything else: do a little work, and call the function on a **smaller** input that's one step closer to the base case. In `countdown`, it's printing `n` and calling with `n - 1`.

If every call moves closer to the base case, the calls must eventually reach it and stop.

<Callout kind="analogy" title="Counting the people in a queue">
You're in a long queue and want to know your position. You ask the person in front, "What's your position?" They don't know either, so they ask the person in front of them, and so on. The person at the very front knows the answer without asking: 1. That's the base case. Each answer then travels back down the queue, and every person adds one before passing it on.
</Callout>

## Factorial: recursion that returns a value

The **factorial** of n, written n!, is n × (n − 1) × … × 2 × 1. So 4! = 4 × 3 × 2 × 1 = 24, and by definition 0! = 1.

Notice that 4! = 4 × 3!. A factorial is defined in terms of a smaller factorial, which makes it a perfect fit for recursion:

```swift run
func factorial(_ n: Int) -> Int {
    if n == 0 {
        return 1                      // base case
    }
    return n * factorial(n - 1)       // recursive case
}

print(factorial(0))
print(factorial(4))
print(factorial(10))
```

```output
1
24
3628800
```

The code reads almost exactly like the maths: "the factorial of 0 is 1; otherwise it's n times the factorial of n − 1".

## What really happens: the call stack

How can `factorial(4)` multiply by `factorial(3)` before it knows what that is? The answer is that every function call, recursive or not, gets its own private workspace called a **stack frame**, holding its own parameters and local variables. Frames are kept on the **call stack**:

- When a function is called, a new frame goes on top of the stack.
- When a function returns, its frame is removed, and its return value is handed to the frame below, which carries on from where it paused.

So there isn't one `n` that keeps changing. Each call has its **own** `n`. Let's make the stack visible by printing as each call starts and finishes, indented by how deep it is:

```swift run
func factorial(_ n: Int, depth: Int = 0) -> Int {
    let indent = String(repeating: "    ", count: depth)
    print("\(indent)factorial(\(n)) starts")
    if n == 0 {
        print("\(indent)factorial(0) returns 1")
        return 1
    }
    let result = n * factorial(n - 1, depth: depth + 1)
    print("\(indent)factorial(\(n)) returns \(result)")
    return result
}

print(factorial(3))
```

```output
factorial(3) starts
    factorial(2) starts
        factorial(1) starts
            factorial(0) starts
            factorial(0) returns 1
        factorial(1) returns 1
    factorial(2) returns 2
factorial(3) returns 6
6
```

What to notice:

- **Going down**, the calls pile up. `factorial(3)` is paused in the middle of `n * factorial(n - 1)`, waiting for an answer. So are 2 and 1. At the deepest point, four frames are on the stack at once.
- **At the bottom**, the base case answers directly.
- **Coming back up**, each paused call gets its answer, finishes its multiplication and returns: 1, then 1 × 1 = 1, then 2 × 1 = 2, then 3 × 2 = 6.

The `depth` parameter, with its default of 0, is only there for printing. The queue analogy is exactly this: questions travel down to the front, answers travel back.

## Before or after the recursive call

Where you put the work relative to the recursive call changes the order things happen in. Compare these two:

```swift run
func countDown(from n: Int) {
    if n == 0 { return }
    print(n)                 // work before the call
    countDown(from: n - 1)
}

func countUp(to n: Int) {
    if n == 0 { return }
    countUp(to: n - 1)
    print(n)                 // work after the call
}

countDown(from: 3)
print("---")
countUp(to: 3)
```

```output
3
2
1
---
1
2
3
```

`countUp(to: 3)` doesn't print 3 first. It goes all the way down to the base case before *any* call prints, and then each call prints as the stack unwinds, smallest first. Work done after the recursive call happens on the way back up. You'll rely on this when processing trees.

## Summing with recursion

One more pattern you'll see often. The sum 1 + 2 + … + n is n plus the sum up to n − 1:

```swift run
func sum(upTo n: Int) -> Int {
    if n <= 0 {
        return 0
    }
    return n + sum(upTo: n - 1)
}

print(sum(upTo: 4))
print(sum(upTo: 100))
```

```output
10
5050
```

The base case uses `n <= 0` rather than `n == 0`, so a negative input also stops immediately instead of recursing forever. Making the base case catch everything that should stop is a good habit.

## When the base case is missing

If the recursion never reaches a base case, the calls never stop:

```swift
func countdown(from n: Int) {
    print(n)
    countdown(from: n - 1)   // no base case
}

countdown(from: 3)
```

```text title="What you'll see"
3
2
1
0
-1
-2
...
```

It prints thousands of numbers, and then the program crashes. Every call adds a frame, the call stack has a fixed amount of memory, and eventually it runs out. That's a **stack overflow**. Depending on how you run the program, you'll see a message such as `Segmentation fault` or a long "Stack dump".

<Callout kind="gotcha" title="Swift gotcha: deep recursion and big results">
- **Depth.** Each call needs stack memory, so recursion that goes, say, a million calls deep can overflow the stack even with a correct base case. A loop doesn't have that limit. Swift doesn't promise to turn recursive calls into loops for you.
- **Overflow.** Factorials grow very fast. `factorial(20)` is 2,432,902,008,176,640,000, which just fits in an `Int`. `factorial(21)` doesn't, and Swift crashes rather than return a wrong answer.
</Callout>

## Recursion or a loop?

Anything you can write with recursion, you can also write with a loop, and for simple counting the loop is usually better: it's just as clear and uses no extra stack. `factorial` and `sum(upTo:)` are here because they're the simplest way to *learn* recursion.

Recursion shines when the problem **branches**: a folder contains folders that contain folders, a tree node has children that have children, a puzzle has several choices at each step. Writing those with loops means managing your own stack by hand. With recursion, the call stack does it for you. That's where you're heading in M17 and beyond.

A useful rule for the space cost: a recursion that goes *d* calls deep uses **O(d)** stack space, because that many frames are alive at the deepest point. `factorial(n)` uses O(n) space, where the loop version uses O(1).
