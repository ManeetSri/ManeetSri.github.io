## Why it matters

On input-output judges, every problem starts the same way: read some numbers and words, solve, print the answers. Writing that scaffolding from scratch each time wastes minutes and invites bugs, and in Swift the obvious version, `readLine()` with `split`, can be several times slower than it needs to be on big inputs. Competitive programmers keep a **template**: one file with fast input, buffered output and an empty `solve` function, copied at the start of every problem. This lesson builds yours.

## Where this builds on M12

[Fast input for competitive programming](/dsa/learn/swift-fast-input) gave you the two key ideas, so here's the recap:

- **Read everything at once, as bytes**, with `FileHandle.standardInput.readDataToEndOfFile()`, then walk the bytes with an index, building each number digit by digit. No `String`, no `split`.
- **Print once.** Collect the output and make a single `print` call at the end, instead of one per line.

[Reading input with readLine](/dsa/learn/swift-reading-input) is still the right choice for small inputs and for interactive problems. The template adds what a real contest needs on top: words as well as numbers, a whole array in one call, several test cases per input, and a fixed shape so you never think about the scaffolding.

## The template

Save this as `main.swift` and copy it for each new problem. Only the part under `MARK: Solution` changes.

```swift title="main.swift"
import Foundation

// MARK: Input: read all of standard input once, then scan the bytes
struct FastReader {
    private let bytes: [UInt8]
    private var position = 0

    init(bytes: [UInt8]) {
        self.bytes = bytes
    }

    init() {
        self.init(bytes: [UInt8](FileHandle.standardInput.readDataToEndOfFile()))
    }

    /// Skips spaces, tabs, newlines and anything else at or below ASCII 32.
    private mutating func skipSeparators() {
        while position < bytes.count && bytes[position] <= 32 {
            position += 1
        }
    }

    /// True when only separators are left.
    mutating func isAtEnd() -> Bool {
        skipSeparators()
        return position >= bytes.count
    }

    /// The next integer, with an optional leading minus sign.
    mutating func int() -> Int {
        skipSeparators()
        var isNegative = false
        if position < bytes.count && bytes[position] == UInt8(ascii: "-") {
            isNegative = true
            position += 1
        }
        var value = 0
        while position < bytes.count, bytes[position] >= 48, bytes[position] <= 57 {
            value = value * 10 + Int(bytes[position] - 48)
            position += 1
        }
        return isNegative ? -value : value
    }

    /// The next `count` integers.
    mutating func ints(_ count: Int) -> [Int] {
        (0..<count).map { _ in int() }
    }

    /// The next run of non-separator bytes, such as a word or a grid row.
    mutating func bytesToken() -> [UInt8] {
        skipSeparators()
        let start = position
        while position < bytes.count && bytes[position] > 32 {
            position += 1
        }
        return Array(bytes[start..<position])
    }

    /// The next word as a String.
    mutating func word() -> String {
        String(decoding: bytesToken(), as: UTF8.self)
    }
}

// MARK: Output: collect everything, print once at the end
struct OutputBuffer {
    private var text = ""

    mutating func line(_ value: Int) {
        text += String(value)
        text += "\n"
    }

    mutating func line(_ value: String) {
        text += value
        text += "\n"
    }

    mutating func line(_ values: [Int]) {
        text += values.map(String.init).joined(separator: " ")
        text += "\n"
    }

    func flush() {
        print(text, terminator: "")
    }
}

// MARK: Solution
func solve(_ input: inout FastReader, _ output: inout OutputBuffer) {
    let n = input.int()
    let numbers = input.ints(n)
    output.line(numbers.reduce(0, +))
}

var input = FastReader()
var output = OutputBuffer()
let testCases = input.int()          // delete this line and the loop if there's only one test
for _ in 0..<testCases {
    solve(&input, &output)
}
output.flush()
```

## How it fits together

**`FastReader`** is M12's reader with three additions:

- **`init(bytes:)`** takes the bytes from anywhere. The plain `init()` reads standard input and hands it on. That split is what lets you test the reader on a fixed string, as the next section does.
- **`ints(_:)`** reads a whole array, for the common "n, then n numbers" line.
- **`bytesToken()` and `word()`** read the next run of non-separator bytes. Keep grid rows and strings you'll index into as `[UInt8]`, since `String` can't be indexed by `Int` ([Array(s) and \[UInt8\] for fast access](/dsa/learn/swift-string-to-array) explains why). Convert to a `String` only when you need to print or hash it as text.

Every read skips separators first, so the input's line breaks never matter: numbers spread across lines, or crammed onto one, read the same way. `isAtEnd()` is for the problems that say "read until the end of input".

**`OutputBuffer`** collects lines in one `String` and prints it in a single call in `flush()`. The three `line` overloads cover what you print most: a number, a string, and a space-separated array. Building with `+=` into one string is amortised O(1) per character, the dynamic array growth from M18.

**`solve`** takes the reader and the buffer as `inout` parameters, as in [inout, swap and swapAt](/dsa/learn/swift-inout-swap): it reads one test case and writes its answers. Many problems give a count of test cases first; for those that don't, delete the `testCases` line and call `solve` once.

Keeping the logic inside a function, rather than at the top level, also helps the optimiser: local variables in a function are easier for the compiler to keep in registers than global ones.

## Trying it on a fixed input

A `run` block can't read standard input, but it doesn't need to: `init(bytes:)` accepts the bytes of any string. This is the same reader and buffer, fed a sample with deliberately untidy spacing:

```swift run
import Foundation

// MARK: Input: read all of standard input once, then scan the bytes
struct FastReader {
    private let bytes: [UInt8]
    private var position = 0

    init(bytes: [UInt8]) {

    }

    /// The next integer, with an optional leading minus sign.
    mutating func int() -> Int {

    }

    /// The next `count` integers.
    mutating func ints(_ count: Int) -> [Int] {

    }

        }
        return Array(bytes[start..<position])
    }

    /// The next word as a String.
    mutating func word() -> String {
        String(decoding: bytesToken(), as: UTF8.self)
    }
}

// MARK: Output: collect everything, print once at the end
struct OutputBuffer {
    private var text = ""

    mutating func line(_ value: Int) {
        text += String(value)
        text += "\n"
    }

    mutating func line(_ value: String) {
        text += value
        text += "\n"
    }

    mutating func line(_ values: [Int]) {
        text += values.map(String.init).joined(separator: " ")
        text += "\n"
    }

    func flush() {
        print(text, terminator: "")
    }
}

// MARK: Solution: each test case is a name, a count, then that many scores
func solve(_ input: inout FastReader, _ output: inout OutputBuffer) {
    let name = input.word()
    let count = input.int()
    let scores = input.ints(count)
    output.line("\(name) \(scores.reduce(0, +)) \(scores.max()!)")
}

// A fixed input instead of standard input, with deliberately untidy spacing
let sample = """
3
ada 3
4 -1   7
ben 2
10
20
cy 1 -6
"""
var input = FastReader(bytes: Array(sample.utf8))
var output = OutputBuffer()
let testCases = input.int()
for _ in 0..<testCases {
    solve(&input, &output)
}
output.line(input.isAtEnd() ? "all input read" : "input left over")
output.flush()
```

```output
ada 10 7
ben 30 20
cy -6 -6
all input read
```

What to notice:

- **Line breaks and extra spaces don't matter.** Ben's scores are on two lines, `4 -1   7` has three spaces, and Cy's name, count and score share a line. The reader only cares about the order of the tokens.
- **Words and numbers mix freely.** `word()` reads "ada", then `int()` reads 3.
- **Nothing is printed until `flush()`**, which makes one `print` call for all four lines.

Testing your parsing on the sample input this way, before submitting, catches most of the "wrong answer on test 1" verdicts that are really input bugs.

## Running it locally

Put the sample input from the problem statement in a file, build with optimisation as judges do, and compare your output with the expected one:

```bash
swiftc -O main.swift -o main            # build once, optimised
./main < sample.txt                     # run on the sample input
./main < sample.txt | diff - expected.txt && echo "matches"
```

`swift main.swift < sample.txt` also works for a quick check, but it compiles every time, and without `-O` it's far slower, so don't judge speed from it. [Debug, release and -Ounchecked](/dsa/learn/fs-build-settings) explains the flags.

<Callout kind="gotcha" title="Contest habits in Swift">
- **Overflow traps.** `Int` is 64 bits, and going past about 9.2 × 10¹⁸ crashes rather than wrapping. Sums of 10⁵ values up to 10⁹ are fine; products of two such values need care, and modular arithmetic should reduce after every multiplication.
- **Deep recursion can overflow the stack.** A recursive DFS over a path of 10⁵ or more nodes may crash on a judge. Use an explicit stack, as in [Stack depth limits in Swift](/dsa/learn/rec-stack-limits).
- **Interactive problems need flushing.** When the judge answers each line you print, you can't read everything up front, and your output must actually leave the program before you wait for a reply. Use `readLine()`, and after each `print`, call `fflush(stdout)` (from Foundation). Without it, output sent to a pipe can sit in a buffer while both programs wait for each other.
- **Allocate once.** With many test cases, the total input is bounded, but allocating a fresh array of the maximum size per case is not. Size arrays by each case's n.
</Callout>

It's the template with its first real `solve`, and the tests use 200,000 numbers and 200,000 queries, so both the parsing and the algorithm have to be linear.
