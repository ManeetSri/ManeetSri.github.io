## Why it matters

Parts III to V had you build the data structures Swift doesn't ship: a deque, a heap, an ordered map. That's how you learn what they cost. In an app you'd rather use versions that thousands of projects have already tested, and Apple publishes them in the open-source **swift-collections** package. This lesson tours its stable types, says which of your DSAKit structures each one replaces, and flags the names that mislead people, because two of them don't do what their names suggest.

## Adding the package

The package is split into modules, so you can import only what you use:

| Module | Types |
| --- | --- |
| `DequeModule` | `Deque` |
| `HeapModule` | `Heap` |
| `OrderedCollections` | `OrderedSet`, `OrderedDictionary` |
| `BitCollections` | `BitSet`, `BitArray` |
| `HashTreeCollections` | `TreeSet`, `TreeDictionary` |
| `Collections` | all of the above, in one import |

Recent releases add a few more specialised modules, but these are the ones you'll use for DSA. In `Package.swift`:

```swift
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "Planner",
    dependencies: [
        .package(url: "https://github.com/apple/swift-collections.git", from: "1.1.0"),
    ],
    targets: [
        .executableTarget(
            name: "Planner",
            dependencies: [
                .product(name: "Collections", package: "swift-collections"),
                // or only the modules you need, such as
                // .product(name: "DequeModule", package: "swift-collections"),
            ]
        ),
    ]
)
```

`from: "1.1.0"` asks for 1.1.0 or any later 1.x, and 1.1.0 is the release that added `Heap`, `BitSet` and the tree collections. The package moves quickly (it was at 1.7 when this lesson was written), and newer releases need newer Swift toolchains, so check its README for the version that matches your Xcode. In an Xcode app, use **File ▸ Add Package Dependencies…** with the same URL.

As with swift-algorithms, code that imports the package is shown without `run`. The `run` blocks build the same behaviour from the standard library.

## Deque: both ends in O(1)

You built `Deque` on a ring buffer in [Build Deque\<T\>](/dsa/learn/queue-build-deque), and the package's version uses the same idea. It's a `RandomAccessCollection`, a `MutableCollection` and a `RangeReplaceableCollection`, so everything that works on an array works on it.

```swift
import DequeModule

var queue: Deque = [3, 4]
queue.append(5)          // [3, 4, 5]          O(1)
queue.prepend(2)         // [2, 3, 4, 5]       O(1)
queue.popFirst()         // Optional(2)        O(1); nil when empty
queue.popLast()          // Optional(5)        O(1)
queue[1]                 // 4                  O(1), like an array
queue.insert(9, at: 1)   // [3, 9, 4]          O(n): fine occasionally, not in a loop
```

Here's BFS from [BFS and unweighted shortest paths](/dsa/learn/gt-bfs) with it. `popFirst()` is the whole point: on an `Array`, `removeFirst()` is O(n), as [Why removeFirst() is O(n)](/dsa/learn/queue-why-not-removefirst) showed.

```swift
import DequeModule

func distances(from start: Int, in graph: [[Int]]) -> [Int] {
    var distance = Array(repeating: -1, count: graph.count)
    distance[start] = 0
    var queue: Deque = [start]
    while let node = queue.popFirst() {
        for next in graph[node] where distance[next] == -1 {
            distance[next] = distance[node] + 1
            queue.append(next)
        }
    }
    return distance
}
```

For 0-1 BFS, `prepend` puts the zero-weight neighbours at the front, as in [0-1 BFS with a deque](/dsa/learn/sp-zero-one-bfs).

## Heap: a min-max priority queue

[swift-collections Heap](/dsa/learn/heap-swift-collections) covered this one in full. The short version: `Heap<Element: Comparable>` orders by the element's own `<`, gives O(1) `min` and `max` properties, and O(log n) `insert`, `popMin()` and `popMax()`. For a custom priority, wrap your data in a `Comparable` struct.

## OrderedSet: a set that remembers order

An `OrderedSet` is an array without duplicates and with O(1) membership tests. It keeps elements in **insertion order**, the order you added them. It is **not** sorted.

```swift
import OrderedCollections

var tags: OrderedSet = ["swift", "ios"]
tags.append("dsa")             // (inserted: true, index: 2)
tags.append("swift")           // (inserted: false, index: 0): already there, nothing changes
tags.contains("ios")           // true, O(1) on average: it hashes, it doesn't scan
tags[1]                        // "ios": it's a random-access collection
tags.firstIndex(of: "dsa")     // Optional(2), also found by hashing
tags.remove(at: 0)             // "swift": removing from the front is O(n), as with an array
tags.insert("algo", at: 0)     // (inserted: true, index: 0)
```

Under the hood it's an array of the elements plus a hash table of their positions. That explains the costs: appending and lookups are O(1) on average, while removing or inserting anywhere but the end shifts the array, O(n).

Two details catch people out. `==` on ordered sets compares the **order** too, so `["a", "b"]` and `["b", "a"]` are different. And for that reason it can't conform to `SetAlgebra`; it offers `union`, `intersection`, `isSubset(of:)` and friends as its own methods instead, and its `unordered` view compares like a plain `Set`.

The classic use is "deduplicate, keeping the first of each in order", or a recent-items list. Here is what it gives you, built from an array and a set:

```swift run
// What OrderedSet gives you, built from an Array and a Set
struct RecentSearches {
    private(set) var order: [String] = []
    private var members: Set<String> = []

    /// Adds the term at the end if it's new. Returns whether it was added. O(1) on average.
    mutating func append(_ term: String) -> Bool {
        guard members.insert(term).inserted else { return false }
        order.append(term)
        return true
    }

    func contains(_ term: String) -> Bool {
        members.contains(term)      // O(1), not a scan of `order`
    }
}

var searches = RecentSearches()
for term in ["swift", "heap", "swift", "deque", "heap", "bfs"] {
    print(term, searches.append(term))
}
print(searches.order)
print(searches.contains("deque"), searches.contains("trie"))
```

```output
swift true
heap true
swift false
deque true
heap false
bfs true
["swift", "heap", "deque", "bfs"]
true false
```

That pair of an array and a set, kept in step, is exactly the pattern `OrderedSet` packages up, with the bookkeeping already tested.

## OrderedDictionary: a dictionary that remembers order

`OrderedDictionary` does the same for dictionaries: O(1) average lookups by key, and iteration in the order keys were first added.

```swift
import OrderedCollections

var stock: OrderedDictionary = ["apples": 4, "pears": 0]
stock["plums"] = 7                   // a new key goes at the end
stock["apples", default: 0] += 1     // 5, updated in place; its position doesn't change
stock["pears"] = nil                 // removes it: O(n), the later entries shift down
stock.keys                           // ["apples", "plums"], an OrderedSet<String>
stock.values                         // [5, 7]
stock.elements[0]                    // (key: "apples", value: 5): access by position
stock.index(forKey: "plums")         // Optional(1)
for (fruit, count) in stock {
    print(fruit, count)              // apples 5, then plums 7: always in this order
}
```

- **Subscripting takes a key, never a position.** That's why it's only a `Sequence`, not a `Collection`: `stock[0]` would be ambiguous when the keys are `Int`s. Position-based access goes through `elements`.
- **Removing is O(n)**, like removing from the middle of an array. That rules it out for an LRU cache, which moves an entry on every access; the dictionary plus doubly linked list from [LRU cache](/dsa/learn/ll-lru-cache) is still the right tool there.

Ordered dictionaries shine when output order matters: settings shown in the order they were defined, JSON you want to write back unchanged, or counts reported in first-seen order. With the standard library, you keep the order yourself:

```swift run
// What OrderedDictionary gives you: dictionary lookups, plus the order keys first appeared
var firstSeen: [String] = []
var counts: [String: Int] = [:]
for word in "the cat sat on the mat the end".split(separator: " ").map(String.init) {
    if counts[word] == nil {
        firstSeen.append(word)
    }
    counts[word, default: 0] += 1
}
for word in firstSeen {
    print(word, counts[word]!)
}
```

```output
the 3
cat 1
sat 1
on 1
mat 1
end 1
```

## BitSet and BitArray: one bit per member

A `BitSet` is a set of small non-negative integers, stored as one bit per possible member. A `BitArray` is an array of `Bool`s packed eight to a byte.

```swift
import BitCollections

var visited: BitSet = [3, 64, 7]
visited.insert(130)
visited.contains(64)                    // true, O(1)
Array(visited)                          // [3, 7, 64, 130]: always in increasing order
visited.union([5, 130])                 // [3, 5, 7, 64, 130], a whole word at a time

var seats = BitArray(repeating: false, count: 200)    // 200 Bools in about 25 bytes
seats[17] = true
```

This is the `UInt64` bitmask trick from [Gray code and UInt64 bitsets](/dsa/learn/bits-gray-code-bitsets), extended to as many words as you need. Set operations work 64 members at a time, and iteration comes out **sorted**, because it reads the bits in order. Here's the idea in miniature:

```swift run
// The idea behind BitSet: one bit per possible member, 64 members to a UInt64 word
struct TinyBitSet {
    private var words: [UInt64] = []

    mutating func insert(_ member: Int) {
        let (word, bit) = (member / 64, member % 64)
        while words.count <= word {
            words.append(0)
        }
        words[word] |= 1 << UInt64(bit)
    }

    func contains(_ member: Int) -> Bool {
        let (word, bit) = (member / 64, member % 64)
        return word < words.count && words[word] & (1 << UInt64(bit)) != 0
    }

    func union(_ other: TinyBitSet) -> TinyBitSet {
        var result = TinyBitSet()
        result.words = (0..<max(words.count, other.words.count)).map { index in
            (index < words.count ? words[index] : 0) | (index < other.words.count ? other.words[index] : 0)
        }
        return result
    }

    var members: [Int] {
        var result: [Int] = []
        for (index, word) in words.enumerated() {
            for bit in 0..<64 where word & (1 << UInt64(bit)) != 0 {
                result.append(index * 64 + bit)
            }
        }
        return result
    }
}

var visited = TinyBitSet()
for node in [130, 3, 64, 7, 3] {
    visited.insert(node)
}
print(visited.members)
print(visited.contains(64), visited.contains(65))

var other = TinyBitSet()
other.insert(5)
other.insert(130)
print(visited.union(other).members)
```

```output
[3, 7, 64, 130]
true false
[3, 5, 7, 64, 130]
```

The catch: memory grows with the **largest** member, not with how many there are. A `BitSet` holding only 1,000,000 uses about 125 KB. For node numbers 0 to n − 1 that's perfect, a visited set in n / 8 bytes. For sparse, huge values, use `Set<Int>`.

## TreeSet and TreeDictionary: cheap copies, not sorted

These two are the most misread names in the package. They are **hashed** collections, with the same API shape as `Set` and `Dictionary` and the same `Hashable` requirement. The "tree" is the internal layout of their hash values (a structure called a CHAMP, a compressed hash-array mapped prefix tree), and they iterate in **no meaningful order**. They are not sorted sets like Java's `TreeSet` or C++'s `std::set`.

What the tree buys is **persistence**: copies share structure. With a standard `Dictionary`, the first change to a copy duplicates the whole storage, O(n), as you saw in [Copy-on-write explained](/dsa/learn/swift-copy-on-write-intro). A `TreeDictionary` copies only the few small nodes on the path to the change:

```swift
import HashTreeCollections

var current: TreeDictionary<String, Int> = ["width": 320, "height": 480]
var history: [TreeDictionary<String, Int>] = []
for step in 1...1_000 {
    history.append(current)           // O(1): shares all of current's storage
    current["step"] = step            // copies a handful of nodes, not the whole dictionary
}
```

That makes them a good fit for undo stacks and snapshots of large state, which you'll meet in M64's [TreeSet, TreeDictionary, OrderedSet and OrderedDictionary](/dsa/learn/as-swift-collections) along with what lookups cost and when they're slower than the standard types.

## Which DSAKit type each one replaces

| You built (DSAKit) | In production | Notes |
| --- | --- | --- |
| `Deque` (M27) | `Deque` | the same ring-buffer idea |
| `Queue` (M27) | `Deque` with `append` and `popFirst()` | |
| `RingBuffer` (M27) | `Deque` | it grows; a fixed-size buffer that overwrites is still yours to write |
| `Heap` (M39) | `Heap` | ordered by `Comparable`, with both min and max |
| `Stack` (M26) | `Array` | `append` and `popLast()` are already O(1) |
| `HashMap` (M24) | `Dictionary`, or `OrderedDictionary` when order matters | |
| `SortedSet`, `SortedMap` (M38) | no stable equivalent | **not** `TreeSet`, and not `OrderedSet` |
| a `[Bool]` visited array | `BitArray`, or `BitSet` of node numbers | |

The sorted row deserves care. When this lesson was written, the package's repository included `SortedSet` and `SortedDictionary`, but only behind an opt-in "unstable" flag, not as part of its supported API. Check the release notes before relying on them; until they're stable, DSAKit's `SortedSet` and `SortedMap`, or your own, remain the answer for floor and ceiling queries.

<Callout kind="gotcha" title="Gotchas with swift-collections">
- **"Ordered" means insertion order, "Tree" means hashed.** Neither `OrderedSet` nor `TreeSet` is sorted. For sorted output, sort, or use a balanced tree.
- **Removing from the front or middle of `OrderedSet` and `OrderedDictionary` is O(n).** They're arrays underneath.
- **`BitSet` memory follows the largest value.** Great for node numbers, wasteful for sparse big numbers.
- **Interview and contest sites usually can't import packages.** The next lesson covers what to do there.
</Callout>
