## Why it matters

Find in page, search in a code editor, `grep` in Terminal: all of them find every place a short **pattern** occurs in a long **text**. The first algorithm anyone writes for this is the **naive** one: try every starting position and compare. It's simple, often fast enough, and worth understanding exactly, including the inputs that make it slow. Those slow inputs are the reason the clever algorithms of M63, KMP, the Z-function and Rabin–Karp, exist.

## Try every start

Let the text have n characters and the pattern m. A match can start anywhere from 0 to n − m. At each start, compare the pattern with the text character by character, and stop at the first mismatch. If all m characters match, record the start.

```swift run
func occurrences(of pattern: String, in text: String) -> [Int] {
    let t = Array(text)
    let p = Array(pattern)
    guard !p.isEmpty, p.count <= t.count else { return [] }
    var result: [Int] = []
    for start in 0...(t.count - p.count) {
        var matched = 0
        while matched < p.count && t[start + matched] == p[matched] {
            matched += 1
        }
        if matched == p.count {
            result.append(start)
        }
    }
    return result
}

print(occurrences(of: "abra", in: "abracadabra"))
print(occurrences(of: "aa", in: "aaaa"))
print(occurrences(of: "xyz", in: "abc"))
print(occurrences(of: "longer", in: "short"))
```

```output
[0, 7]
[0, 1, 2]
[]
[]
```

What to notice:

- Matches can **overlap**: `"aa"` occurs at 0, 1 and 2 in `"aaaa"`.
- The `guard` matters. If the pattern is longer than the text, `t.count - p.count` is negative, and the range `0...(-1)` would trap. It also decides what an empty pattern means; here, no matches.
- Both strings are converted to arrays once, as M08 taught, so every `t[start + matched]` is O(1).

## How many comparisons?

On ordinary text, most starts fail on the very first character, so the work is close to n. The trouble comes when the text keeps **almost** matching. A text of `a`s and a pattern of `a`s ending in `b` makes every start compare all m characters before failing:

```swift run
func comparisons(pattern: String, text: String) -> Int {
    let t = Array(text.utf8)
    let p = Array(pattern.utf8)
    var count = 0
    for start in 0...(t.count - p.count) {
        var matched = 0
        while matched < p.count {
            count += 1
            if t[start + matched] != p[matched] {
                break
            }
            matched += 1
        }
    }
    return count
}

let english = String(repeating: "the quick brown fox jumps over the lazy dog ", count: 25)
print(english.utf8.count, comparisons(pattern: "lazy cat", text: english))

let worst = String(repeating: "a", count: 1_100)
let nearlyThere = String(repeating: "a", count: 99) + "b"
print(worst.utf8.count, comparisons(pattern: nearlyThere, text: worst))
```

```output
1100 1218
1100 100100
```

Both texts have 1,100 characters. The English one costs about one comparison per start, plus a few more wherever `lazy ` almost matches. The worst case costs (n − m + 1) · m: a hundred times more. In general, naive matching is **O(n · m)** in the worst case and O(1) extra space.

Is that a problem? Use the table from [From n to a feasible complexity](/dsa/learn/bigo-feasibility-table): if n · m stays below about 10⁸, naive matching is fine. A 10⁶-character text with a 10³-character pattern is 10⁹ steps in the worst case: too slow.

## Where the naive algorithm wastes work

Look at the worst case again. At start 0, it compares 99 `a`s and then fails on the `b`. At start 1, it compares 98 of the **same** text characters again. Everything it learned at start 0, that the text there is all `a`s, is thrown away.

The fast algorithms of M63 keep that knowledge. **KMP** works out in advance how far the pattern can safely shift after a mismatch, so it never re-reads a text character. The **Z-function** measures, for every position, how far the text agrees with the pattern's start. **Rabin–Karp** slides a fixed-size window along the text, as in [Fixed-size windows](/dsa/learn/sw-fixed), but keeps a **hash** of the window instead of a sum, and only compares characters when the hashes agree. All three are O(n + m).

## Non-overlapping matches

Sometimes overlapping matches shouldn't count, for example when replacing each match with something else. Then, after a match, jump **past** it instead of moving one step:

```swift run
func countNonOverlapping(_ pattern: String, in text: String) -> Int {
    let t = Array(text)
    let p = Array(pattern)
    guard !p.isEmpty else { return 0 }
    var count = 0
    var start = 0
    while start + p.count <= t.count {
        if t[start..<start + p.count].elementsEqual(p) {
            count += 1
            start += p.count            // jump past the match
        } else {
            start += 1
        }
    }
    return count
}

print(countNonOverlapping("aa", in: "aaaa"))
print(countNonOverlapping("aba", in: "abababa"))
```

```output
2
2
```

`"aba"` occurs three times in `"abababa"` if overlaps count (at 0, 2 and 4), but only twice without them. `elementsEqual(_:)` compares a slice with an array element by element; `==` needs both sides to be the same type.

## What Swift gives you

The standard library has string searching built in, from Swift 5.7 on:

```swift run
let text = "abracadabra"
print(text.contains("cad"))
print(text.ranges(of: "abra").map { text.distance(from: text.startIndex, to: $0.lowerBound) })
print("aaaa".ranges(of: "aa").count)
```

```output
true
[0, 7]
2
```

`ranges(of:)` returns ranges of `String.Index`, so `distance(from:to:)` turns them into integer offsets. Notice the last line: `ranges(of:)` finds **non-overlapping** matches, 2 rather than 3. In app code, use these. In an interview, expect to be asked to write the loop yourself, and to say what it costs.

<Callout kind="gotcha" title="Swift gotcha: equal characters, different bytes">
Swift compares `Character` values by what they look like, so an `é` stored as one code point equals an `e` followed by a combining accent, as [Unicode and grapheme clusters](/dsa/learn/swift-unicode) explained. Their bytes differ:

```swift run
let composed = "café"
let decomposed = "cafe\u{301}"
print(Array(composed) == Array(decomposed))
print(Array(composed.utf8) == Array(decomposed.utf8))
```

```output
true
false
```

So searching bytes for `"café"` can miss text that a reader would say contains it. Match on bytes only when the input is ASCII; otherwise use `Array(text)`.
</Callout>
