## Why it matters

Russian dolls, nested gift boxes, cards that slide inside envelopes, picture frames inside larger frames: "how many can you nest?" is LIS in two dimensions. It's a favourite interview question because the fast solution needs three ideas at once: sorting with a custom comparator, a clever tie-break, and the O(n log n) LIS from [LIS in O(n log n) with patience sorting](/dsa/learn/lis-n-log-n). Get the tie-break wrong and the code still runs, but gives answers that are too big.

## The problem

Each envelope has a width and a height. One envelope fits inside another when it is **strictly smaller in both**: narrower and shorter. No rotating. What is the longest chain of envelopes, each fitting inside the next?

Take these five, written as (width, height): (5, 4), (6, 4), (6, 7), (2, 3) and (6, 5). The best chain has three: (2, 3) inside (5, 4) inside (6, 7). The three envelopes of width 6 can't fit inside each other, however their heights compare.

## First, the O(n²) way

A chain goes up in width, so **sort by width** first. Then any chain appears left to right in the sorted list, and this is exactly the O(n²) LIS from [LIS in O(n²)](/dsa/learn/lis-quadratic), with "j can come before i" meaning "envelope j fits inside envelope i":

```swift run
struct Envelope {
    let width: Int
    let height: Int
}

func fits(_ inner: Envelope, inside outer: Envelope) -> Bool {
    inner.width < outer.width && inner.height < outer.height
}

func deepestNesting(_ envelopes: [Envelope]) -> Int {
    let sorted = envelopes.sorted { $0.width < $1.width }
    var depth = Array(repeating: 1, count: sorted.count)   // the longest chain ending with envelope i
    for i in sorted.indices {
        for j in 0..<i where fits(sorted[j], inside: sorted[i]) {
            depth[i] = max(depth[i], depth[j] + 1)
        }
    }
    return depth.max() ?? 0
}

let envelopes = [
    Envelope(width: 5, height: 4), Envelope(width: 6, height: 4), Envelope(width: 6, height: 7),
    Envelope(width: 2, height: 3), Envelope(width: 6, height: 5),
]
print(deepestNesting(envelopes))
```

```output
3
```

`fits` checks both dimensions, so equal widths are handled correctly. This is correct and simple, and for a few thousand envelopes it's all you need. For 100,000 envelopes, O(n²) is too slow.

## Reducing to one dimension

After sorting by width, it looks as if you can forget widths and find the LIS of the **heights**: each step right in the list is a step up in width, and the LIS makes each step up in height too. That's almost right. The problem is **equal widths**:

```swift run
func lisLength(_ items: [Int]) -> Int {
    var tails: [Int] = []
    for x in items {
        var low = 0
        var high = tails.count
        while low < high {
            let mid = low + (high - low) / 2
            if tails[mid] >= x {
                high = mid
            } else {
                low = mid + 1
            }
        }
        if low == tails.count {
            tails.append(x)
        } else {
            tails[low] = x
        }
    }
    return tails.count
}

let envelopes = [(width: 5, height: 4), (width: 6, height: 4), (width: 6, height: 7), (width: 2, height: 3), (width: 6, height: 5)]

// Ties broken by height ascending: equal widths can sneak into the same chain
let ascending = envelopes.sorted { ($0.width, $0.height) < ($1.width, $1.height) }.map(\.height)
print("ties ascending:", ascending, "LIS", lisLength(ascending))

// Ties broken by height descending: at most one envelope of each width can be chosen
let descending = envelopes.sorted { ($0.width, -$0.height) < ($1.width, -$1.height) }.map(\.height)
print("ties descending:", descending, "LIS", lisLength(descending))
```

```output
ties ascending: [3, 4, 4, 5, 7] LIS 4
ties descending: [3, 4, 7, 5, 4] LIS 3
```

With ties sorted by height ascending, the three width-6 envelopes come out as heights 4, 5, 7, and the LIS `[3, 4, 5, 7]` happily uses (6, 5) and (6, 7) together. That's a chain of 4 that doesn't exist.

## The tie trick: equal widths by height descending

Sort by width **ascending**, and among equal widths by height **descending**. Within a group of equal widths, the heights now go down, and a strictly increasing subsequence can never take two elements that go down. So it picks **at most one envelope of each width**, which is exactly the rule.

Why this gives the right answer, both ways round:

- **Every increasing subsequence of heights is a real chain.** Its envelopes appear in sorted order, so their widths never decrease. Two of them can't share a width, because heights within a width group decrease. So widths strictly increase, and heights strictly increase by construction.
- **Every real chain is an increasing subsequence of heights.** A chain has strictly increasing widths, so its envelopes appear in the sorted list in chain order, and their heights increase.

The two sets are the same, so their longest members have the same length. The complete solution is a sort and the O(n log n) LIS:

```swift
func maxEnvelopes(_ envelopes: [(width: Int, height: Int)]) -> Int {
    let heights = envelopes
        .sorted { $0.width != $1.width ? $0.width < $1.width : $0.height > $1.height }
        .map(\.height)
    return lisLength(heights)        // strictly increasing, so the lower bound
}
```

That's **O(n log n)** for the sort plus O(n log n) for the LIS.

## Writing the comparator in Swift

Two common ways to say "width ascending, then height descending":

```swift
// 1. Spell out the tie-break
let a = envelopes.sorted { $0.width != $1.width ? $0.width < $1.width : $0.height > $1.height }

// 2. Compare tuples, negating the field that sorts descending
let b = envelopes.sorted { ($0.width, -$0.height) < ($1.width, -$1.height) }
```

Swift compares tuples of up to six `Comparable` elements with `<`, field by field, like words in a dictionary. Negating works for ordinary sizes; with values near `Int.min` it would overflow, and the first form is safer. [How Swift sorts, and sorting custom types](/dsa/learn/sort-swift-sort) has more on comparators.

## Variations

| Rule | Sort by | Then |
| --- | --- | --- |
| Strictly smaller in both | width ascending, height **descending** | strictly increasing LIS (lower bound) |
| No bigger in both (equal allowed) | width ascending, height ascending | non-decreasing LIS (upper bound) |
| Rotating allowed | turn each one short side first, then as in the first row | strictly increasing LIS |
| Three dimensions (box stacking) | one dimension | O(n²) DP with a `fits` check |

The rotation trick works because if a can be turned to fit inside b at all, it fits with both turned short-side-first. Three dimensions break the O(n log n) trick: after sorting by one side, you'd need increasing pairs in the other two, which isn't a one-value LIS any more. The O(n²) DP still works, because it never cared what "fits" meant.

<Callout kind="gotcha" title="Common mistakes">
- **Breaking ties by height ascending.** The answer comes out too big whenever widths repeat.
- **Using the upper bound.** Equal heights can't nest, so you need the strictly increasing LIS.
- **Sorting by height and running the LIS on widths without the same tie-break.** Either dimension can go first, but the tie rule must flip the other one.
- **Forgetting that the O(n²) check needs both dimensions.** Sorting by width doesn't make widths strictly increasing.
</Callout>
