## Why it matters

The O(n²) LIS from the last lesson is fine for a few thousand elements, but a year of sensor readings or a long list of version numbers can have 100,000 or more. This lesson finds the length in **O(n log n)** by combining a card game, a greedy rule and the lower bound you wrote in [Lower bound, upper bound, first and last occurrence](/dsa/learn/bs-bounds). The same idea powers "patience diff", a diff algorithm that some version control tools offer because it lines up changes more readably.

## A card game: patience sorting

Deal a row of cards one at a time and build piles on the table with one rule:

> Put each card on the **leftmost** pile whose top card is **at least as big** as it. If there's no such pile, start a new pile on the right.

Here's the game with the readings from the last lesson:

```swift run
// Patience sorting: each card goes on the leftmost pile whose top is at least as big,
// or starts a new pile on the right
let cards = [10, 9, 2, 5, 3, 7, 101, 18]
var piles: [[Int]] = []
for card in cards {
    if let index = piles.firstIndex(where: { $0.last! >= card }) {
        piles[index].append(card)
    } else {
        piles.append([card])
    }
    print("after \(card), tops:", piles.map { $0.last! })
}
print("piles:", piles)
```

```output
after 10, tops: [10]
after 9, tops: [9]
after 2, tops: [2]
after 5, tops: [2, 5]
after 3, tops: [2, 3]
after 7, tops: [2, 3, 7]
after 101, tops: [2, 3, 7, 101]
after 18, tops: [2, 3, 7, 18]
piles: [[10, 9, 2], [5, 3], [7], [101, 18]]
```

Four piles, and the LIS has length 4. That's no coincidence: **the number of piles always equals the LIS length**. Two short arguments show why.

**An increasing subsequence uses at most one card from each pile.** A card only lands on a pile whose top is at least as big, so reading any pile from bottom to top, the cards never go up. Two cards from the same pile can't both be in a strictly increasing subsequence. So the LIS is at most the number of piles.

**There's an increasing subsequence with one card from every pile.** Whenever a card goes on pile k (counting from 0), with k at least 1, look at the top of pile k − 1 at that moment. It's smaller than the card, or the card would have gone there instead, and it was dealt earlier. Give the card a pointer back to it. Starting from any card in the last pile and following the pointers visits one card per pile, each earlier and smaller than the last: an increasing subsequence as long as the number of piles.

Both bounds meet, so piles = LIS.

## Only the tops matter

To count piles, you never look below a top card. And notice how the tops always come out **sorted**, from smallest on the left to largest on the right. A new card goes on the first top that's at least as big, which is a **lower bound** search. Binary search finds it in O(log n), instead of the linear `firstIndex(where:)` above.

Keep only the tops in an array called `tails`, and the whole algorithm is a few lines:

```swift run
/// The first index whose value is at least x, in a sorted array (the lower bound)
func lowerBound(_ sorted: [Int], _ x: Int) -> Int {
    var low = 0
    var high = sorted.count
    while low < high {
        let mid = low + (high - low) / 2
        if sorted[mid] >= x {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

func lengthOfLIS(_ items: [Int]) -> Int {
    var tails: [Int] = []          // tails[k]: the smallest end of any increasing run of length k + 1
    for x in items {
        let index = lowerBound(tails, x)
        if index == tails.count {
            tails.append(x)        // x beats every tail: the longest run grows by one
        } else {
            tails[index] = x       // a run of length index + 1 can now end lower
        }
    }
    return tails.count
}

print(lengthOfLIS([10, 9, 2, 5, 3, 7, 101, 18]))
print(lengthOfLIS([0, 8, 4, 12, 2, 10, 6, 14, 1, 9, 5, 13, 3, 11, 7, 15]))
print(lengthOfLIS([7, 7, 7]))
print(lengthOfLIS([]))
```

```output
4
6
1
0
```

Here's the binary search inside one step: the tails are `[2, 3, 7, 101]` and the next card is 18. The search finds the first tail that is at least 18, and 18 replaces it:

```visual arrayTrace

  target: 18
```

## What tails means

The piles explain why the count is right. The same array has a second meaning, which is the one to remember:

> `tails[k]` is the **smallest possible last element** of an increasing subsequence of length k + 1 among the elements seen so far.

Why keep the smallest? Because a subsequence that ends lower is easier to extend. If you've found `[2, 5]` and `[2, 3]`, both of length 2, then `[2, 3]` is the better one to keep: anything that can follow 5 can also follow 3, but 4 can follow only 3. Keeping the lowest ending for each length keeps every door open. That's the greedy part.

When x arrives, the lower bound finds the first tail that is at least x, at index i:

- **Every tail before i is smaller than x**, so x can extend the run of length i that ends at `tails[i - 1]`, making a run of length i + 1 that ends at x.
- x is no bigger than `tails[i]`, so it's at least as good an ending for length i + 1: replace `tails[i]` with x. If i is past the end, no tail is at least x, so x extends the longest run and is appended.
- x can't extend any run of length i + 1 or more, because those all end at a value that is at least x.

The array stays sorted after each step, so the next binary search still works, and its length is always the LIS length so far.

<Callout kind="analogy">
Think of `tails` as a set of records, one per length: "the lowest finishing value anyone has managed for a run of 1, of 2, of 3…". A new element either sets a new longest-run record, or beats an existing record by finishing lower. It never needs to remember how the record runs got there.
</Callout>

## Tails is not itself an LIS

It's tempting to return `tails` as the subsequence. Don't. It has the right **length**, but its values can come from different subsequences, out of order:

```swift run
func lowerBound(_ sorted: [Int], _ x: Int) -> Int {
    var low = 0
    var high = sorted.count
    while low < high {
        let mid = low + (high - low) / 2
        if sorted[mid] >= x {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

var tails: [Int] = []
for x in [3, 4, 5, 1, 2] {
    let index = lowerBound(tails, x)
    if index == tails.count {
        tails.append(x)
    } else {
        tails[index] = x
    }
    print("after \(x):", tails)
}
```

```output
after 3: [3]
after 4: [3, 4]
after 5: [3, 4, 5]
after 1: [1, 4, 5]
after 2: [1, 2, 5]
```

The answer 3 is right, and the real LIS is `[3, 4, 5]`. But `[1, 2, 5]` isn't a subsequence at all: 5 comes before 1 and 2 in the input. The 1 and 2 recorded better endings for lengths 1 and 2, in case later elements could use them. Recovering an actual LIS needs one pointer per element, which the next lesson adds.

## Strictly increasing or non-decreasing?

The choice of binary search decides whether equal values may follow each other:

| Subsequence | Replace the first tail that is | Search |
| --- | --- | --- |
| Strictly increasing | at least x (`>= x`) | lower bound |
| Non-decreasing | greater than x (`> x`) | upper bound |

With the lower bound, a repeat of x lands on the existing x and replaces it, so equal values never stack up. With the upper bound, a repeat skips past the equal tail and can extend it:

```swift run
func longestRun(_ items: [Int], allowEqual: Bool) -> Int {
    var tails: [Int] = []
    for x in items {
        var low = 0
        var high = tails.count
        while low < high {
            let mid = low + (high - low) / 2
            // Strictly increasing: the first tail >= x. Non-decreasing: the first tail > x.
            let goLeft = allowEqual ? tails[mid] > x : tails[mid] >= x
            if goLeft {
                high = mid
            } else {
                low = mid + 1
            }
        }
        if low == tails.count {
            tails.append(x)
        } else {
            tails[low] = x
        }
    }
    return tails.count
}

for items in [[2, 2, 2], [1, 3, 3, 2, 3]] {
    print(items, "strict:", longestRun(items, allowEqual: false), "non-decreasing:", longestRun(items, allowEqual: true))
}
```

```output
[2, 2, 2] strict: 1 non-decreasing: 3
[1, 3, 3, 2, 3] strict: 3 non-decreasing: 4
```

For a **decreasing** subsequence, either flip the comparisons or run the same code on the negated values: x is decreasing exactly when −x is increasing.

## A bonus from the piles

The piles answer a second question for free. Each pile, read in dealing order, never goes up, so the piles split the whole sequence into **non-increasing** subsequences. Could fewer pieces do the job? No: the elements of an increasing subsequence must all go into different pieces, so you need at least as many pieces as the LIS is long. Patience sorting uses exactly that many, so:

> The fewest non-increasing subsequences that together cover a sequence is the length of its longest strictly increasing subsequence.

For `[10, 9, 2, 5, 3, 7, 101, 18]`, the four piles `[10, 9, 2]`, `[5, 3]`, `[7]` and `[101, 18]` are such a cover, and three pieces can't work because 2, 3, 7 and 18 would need a piece each. Puzzles of the form "each lane must have every item no bigger than the one in front; how many lanes do you need?" are this fact in disguise, and the greedy pile rule even tells you which lane each item goes in. (Mathematicians know it as a special case of Dilworth's theorem.)

## Cost, and when O(n²) still wins

Each element costs one binary search over at most n tails: **O(n log n)** time and **O(n)** memory. For n = 100,000 that's under two million steps.

| n | O(n²) DP | O(n log n) |
| --- | --- | --- |
| 1,000 | 500,000 | about 10,000 |
| 100,000 | 5 × 10⁹ | about 1.7 million |

The fast version needs "can follow" to be a comparison of one sortable value, so that the tails stay in order. When the rule is something else, such as "divides" or "is one letter shorter than", you go back to the O(n²) DP. You'll meet both kinds later in this module.

<Callout kind="gotcha" title="Swift gotcha: there's no built-in lower bound">
Swift's standard library has no binary search on arrays, so you write `lowerBound` yourself, as above. `firstIndex(where:)` gives the right index but scans from the front in O(n), which quietly turns the whole algorithm back into O(n²). The swift-algorithms package has `partitioningIndex(where:)`, covered in [partitioningIndex in swift-algorithms](/dsa/learn/bs-partitioning-index), which is a binary search for the first index where a condition holds.
</Callout>

<Callout kind="gotcha" title="Common mistakes">
- **Using the upper bound for a strictly increasing subsequence.** `[2, 2, 2]` then gives 3 instead of 1.
- **Forgetting the append case.** When the index equals `tails.count`, append. Assigning to `tails[tails.count]` crashes.
- **Returning `tails` as the subsequence.** It has the right length but can mix different subsequences.
</Callout>
