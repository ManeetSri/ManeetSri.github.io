## Why it matters

A vending machine is idle, then has coins inserted, then dispenses, then is idle again. A download is queued, running, paused or finished. iOS apps live in states too: not running, inactive, active, background. Wherever behaviour depends on "what mode am I in", a **state diagram** (boxes for the modes, arrows for what can happen next) is the clearest picture. In DP it's more than a picture: every arrow becomes one term in a `max` or `min`, and the code can be read straight off the drawing. This lesson makes that translation a routine you can apply to any "sequence with modes" problem.

## The method

For a problem that runs over a sequence (days, houses, characters) where you're always in one of a few situations:

1. **States.** List the situations you can be in at the end of each step. Name each one.
2. **Arrows.** For each state, draw an arrow to every state you can reach in one step, labelled with what the step does to your score (+ price, − price, + 0, + 1 flip, …).
3. **Transitions.** Each state's new value is the best, over **arrows coming into it**, of (the source state's old value + the arrow's label). One arrow in: no `max` at all. Three arrows in: a `max` of three.
4. **Start.** Give each state its value before step 0. States you can't be in yet get "impossible": minus infinity when maximising, plus infinity when minimising.
5. **Answer.** The best over the states you're allowed to finish in.

These are the five steps of [the DP recipe](/dsa/learn/dp-recipe) in disguise: the state is (step, situation), the transition is the arrows, the base case is the start, the order is step by step, and the answer is the best allowed ending.

## The diagram for Stock II

The last lesson's two-state solution, drawn:

```text
            rest: +0                        keep: +0
           ┌────────┐                      ┌────────┐
           │        ▼                      │        ▼
         ┌────────────┐  buy: − price    ┌────────────┐
         │    free    │ ───────────────▶ │    hold    │
         │            │ ◀─────────────── │            │
         └────────────┘  sell: + price   └────────────┘
```

Read off the arrows **into** each box:

- Into **free**: the "rest" loop from free (+0) and "sell" from hold (+ price). So `free = max(free + 0, hold + price)`.
- Into **hold**: the "keep" loop from hold (+0) and "buy" from free (− price). So `hold = max(hold + 0, free − price)`.

That's exactly the code from last time. Nothing was invented: the two lines are the four arrows.

## Adding a rule: the cooldown

New rule: after you sell, you must wait one full day before buying again. Stock II's diagram can't express this, because "free" lumps together "I sold yesterday" (can't buy) and "I've been free a while" (can buy). When a rule depends on something your states don't distinguish, **split a state**.

Split free into two:

- **sold**: you sold today, so tomorrow you can't buy;
- **rest**: you hold nothing and are free to buy.

Now draw the arrows. From hold you can keep or sell (to sold). From sold you can only wait, which moves you to rest. From rest you can wait or buy.

```text
                        keep: +0
                       ┌────────┐
                       │        ▼
                    ┌────────────┐
       ┌──────────▶ │    hold    │ ──────────┐
       │            └────────────┘           │
       │ buy: − price               sell: + price
       │                                     ▼
 ┌────────────┐      wait: +0        ┌────────────┐
 │    rest    │ ◀─────────────────── │    sold    │
 └────────────┘                      └────────────┘
   │        ▲
   └────────┘
    rest: +0
```

Arrows into each box, and the transitions they give:

| State | Arrows in | Transition |
| --- | --- | --- |
| hold | keep (from hold), buy (from rest) | `hold = max(hold, rest − price)` |
| sold | sell (from hold) | `sold = hold + price` |
| rest | rest (from rest), wait (from sold) | `rest = max(rest, sold)` |

There's no arrow from sold to hold. That missing arrow **is** the cooldown: you can't buy from sold, only from rest, and getting from sold to rest takes a day.

Start: before day 0 you can't hold a share, so hold is impossible. Rest is 0. And sold? You haven't sold anything, but setting sold to 0 is harmless: its only arrow leads to rest with +0, and rest is already 0. The answer is the best of sold and rest: ending while holding a share is never better.

```swift run
func show(_ value: Int) -> String {
    value < -1_000_000 ? "−∞" : String(value)      // print "impossible" readably
}

func maxProfitWithCooldown(_ prices: [Int]) -> Int {
    var hold = Int.min / 2        // holding a share
    var sold = 0                  // sold today, so tomorrow must be a rest
    var rest = 0                  // holding nothing and free to buy
    print("start: hold \(show(hold)), sold \(sold), rest \(rest)")
    for (day, price) in prices.enumerated() {
        let (oldHold, oldSold, oldRest) = (hold, sold, rest)   // every arrow starts from yesterday
        hold = max(oldHold, oldRest - price)                   // keep, or buy from rest
        sold = oldHold + price                                 // sell: the only arrow into sold
        rest = max(oldRest, oldSold)                           // keep resting, or finish the cooldown
        print("day \(day), price \(price): hold \(show(hold)), sold \(show(sold)), rest \(rest)")
    }
    return max(sold, rest)
}

print("best:", maxProfitWithCooldown([3, 1, 4, 2, 5, 0, 3]))
```

```output
start: hold −∞, sold 0, rest 0
day 0, price 3: hold -3, sold −∞, rest 0
day 1, price 1: hold -1, sold -2, rest 0
day 2, price 4: hold -1, sold 3, rest 0
day 3, price 2: hold -1, sold 1, rest 3
day 4, price 5: hold -1, sold 4, rest 3
day 5, price 0: hold 3, sold -1, rest 4
day 6, price 3: hold 3, sold 6, rest 4
best: 6
```

Read the plan off the numbers. On day 2, sold = 3: buy at 1, sell at 4. Day 3 is the cooldown, and rest picks up the 3. On day 5, hold = 3 − 0 = 3: buy at 0 with that profit banked. On day 6, sell at 3, and sold = 6. The machine also tried holding on and selling at 5 on day 4 (sold = 4), but that sale's cooldown falls on day 5 and misses the 0, so it loses. Without any cooldown, banking every rise would give 9; the rule costs 3.

## Read from yesterday, always

Every arrow starts from a state **yesterday**. If you update the variables one by one and a later line reads a variable an earlier line already changed, you've quietly added an arrow that isn't in the diagram:

```swift run
func cooldownCorrect(_ prices: [Int]) -> Int {
    var hold = Int.min / 2, sold = 0, rest = 0
    for price in prices {
        let (oldHold, oldSold, oldRest) = (hold, sold, rest)
        hold = max(oldHold, oldRest - price)
        sold = oldHold + price
        rest = max(oldRest, oldSold)
    }
    return max(sold, rest)
}

func cooldownInPlace(_ prices: [Int]) -> Int {
    var hold = Int.min / 2, sold = 0, rest = 0
    for price in prices {
        sold = hold + price
        hold = max(hold, rest - price)
        rest = max(rest, sold)        // Bug: today's sold, so tomorrow's buy skips the cooldown
    }
    return max(sold, rest)
}

print(cooldownCorrect([1, 3, 1, 3]), cooldownInPlace([1, 3, 1, 3]))
```

```output
2 4
```

The in-place version moves today's sale straight into rest, so it can buy the very next day: buy 1, sell 3, buy 1, sell 3, for 4. The real answer is 2, because the day after the first sale is a cooldown. Snapshotting the old values first, with one tuple assignment, makes every line read yesterday and removes the whole class of bug.

<Callout kind="tip" title="When in-place is safe">
Some machines tolerate in-place updates: in Stock II, reading today's free when buying means "sell and buy back the same day", which earns nothing, so no wrong answer can win. But proving that is extra work for every problem. Snapshot first and you never need the proof.
</Callout>

## Not just stocks: house robber as a machine

A street of houses, each with some money. You can't rob two neighbours. In [House robber I and II](/dsa/learn/dp-house-robber) you wrote a recurrence over "the best up to house i". Draw it as a machine instead. At each house you either **robbed** it or **skipped** it:

```text
                       rob: + money
              ┌──────────────────────────┐
              │                          ▼
       ┌────────────┐              ┌────────────┐
       │  skipped   │              │   robbed   │
       └────────────┘              └────────────┘
         │      ▲  ▲                     │
         └──────┘  └─────────────────────┘
         skip: +0         skip: +0
```

There's no arrow from robbed to robbed: that's "never two neighbours". The transitions: `robbed = skipped + money` (one arrow in), `skipped = max(robbed, skipped)` (two arrows in).

```swift run
// House robber as a state machine: did we rob the house we're standing at?
func robHouses(_ money: [Int]) -> Int {
    var robbed = 0        // best total if we robbed this house
    var skipped = 0       // best total if we didn't
    for amount in money {
        let (oldRobbed, oldSkipped) = (robbed, skipped)
        robbed = oldSkipped + amount            // only from skipped: never two neighbours
        skipped = max(oldRobbed, oldSkipped)    // from either
    }
    return max(robbed, skipped)
}

print(robHouses([2, 7, 9, 3, 1]))
print(robHouses([5, 1, 1, 5]))
```

```output
12
10
```

Same answers as before (2 + 9 + 1 and 5 + 5). The point isn't that this is shorter, but that a rule like "never two neighbours" became a **missing arrow**. When a problem says "you can't do X right after Y", look for the arrow to delete.

## Checking a machine

Before coding, run three checks on the drawing:

- **Every rule is an arrow or a missing arrow.** If a rule needs to know something the states don't record ("did I sell yesterday?"), split a state.
- **Every state is reachable from the start**, and every allowed ending is a state you can return.
- **Each arrow's label is the change in score for that one step**, nothing more. The fee for a trade goes on exactly one arrow (buy or sell, not both).

Then the code is one line per state, one term per incoming arrow, all reading a snapshot of yesterday.

<Callout kind="gotcha" title="Common mistakes">
- **Updating in place.** Later lines read today's values instead of yesterday's, which adds arrows the diagram doesn't have. Snapshot first.
- **Starting an impossible state at 0.** Holding a share before day 0 at zero cost is a free share. Use `Int.min / 2` when maximising.
- **Adding to `Int.min`.** `Int.min + price` is fine for positive prices, but `Int.min - price` crashes; `Int.min / 2` survives both.
- **Returning a state you can't finish in.** Ending in hold means an unsold share; the answer comes from the free states.
</Callout>
