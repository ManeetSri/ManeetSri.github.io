## Why it matters

"At most two trades" and "at most k trades" are where the clever one-liners run out. The running minimum handles one trade and banking every rise handles unlimited trades, but neither can count. A state machine can: give each trade its own pair of states, chain them together, and the limit is built into the diagram. It's also a classic case for spotting when a limit **can't matter**, which turns an O(n · k) algorithm into O(n) for large k.

## Stock III: at most two trades

Same rules as before (buy, then sell, one share at a time), but at most two complete trades. Doing one or none is fine.

What do the states need to remember? Whether you hold a share, as before, and **how many trades you've started**, because that decides whether you're allowed another buy. That gives four useful states, and a chain of arrows through them:

```text
   start (profit 0)
      │  buy: − price
      ▼
    buy1     loop: +0 (keep holding)
      │  sell: + price
      ▼
    sell1    loop: +0 (stay free)
      │  buy: − price
      ▼
    buy2     loop: +0 (keep holding)
      │  sell: + price
      ▼
    sell2    loop: +0 (stay free)
```

- **buy1**: holding the first share.
- **sell1**: first trade finished, holding nothing.
- **buy2**: holding the second share, bought with the first trade's profit in hand.
- **sell2**: both trades finished.

Each state also has a loop (+0) for doing nothing. There's no arrow back from sell2: the chain is the limit. Reading off the arrows:

```swift run
func atMostTwoTrades(_ prices: [Int]) -> Int {
    var buy1 = Int.min / 2, sell1 = 0      // during and after the first trade
    var buy2 = Int.min / 2, sell2 = 0      // during and after the second
    for price in prices {
        buy1 = max(buy1, -price)            // first buy, from no profit
        sell1 = max(sell1, buy1 + price)    // first sell
        buy2 = max(buy2, sell1 - price)     // second buy, carrying the first trade's profit
        sell2 = max(sell2, buy2 + price)    // second sell
    }
    return sell2
}

print(atMostTwoTrades([2, 6, 3, 1, 5, 4, 8, 2]))
print(atMostTwoTrades([1, 2, 3, 4, 5]))
print(atMostTwoTrades([5, 4, 3]))
```

```output
11
4
0
```

For `[2, 6, 3, 1, 5, 4, 8, 2]`: buy at 2 and sell at 6 (4), then buy at 1 and sell at 8 (7), for 11. Banking every rise would give 12 (2 → 6, 1 → 5, 4 → 8), but that's three trades.

Why is `sell1` starting at 0 fine, when you haven't sold anything? Because "finished one trade with profit 0" is equivalent to "made no trade". The limit is **at most** two, so ending in sell2 covers zero, one or two real trades: the chain is allowed to pass through a state on the same day it enters it, earning nothing.

### Wait, this one updates in place

The last lesson insisted on reading yesterday's values, and this code doesn't. Here it's safe, and it's worth seeing exactly why. Reading today's `buy1` in the `sell1` line means "bought and sold on the same day", which earns 0. Reading today's `sell1` in the `buy2` line means "sold and bought back on the same day", which also earns 0. So the extra arrows the in-place version adds can never produce more profit than a legal plan, and the answer is unchanged. The cooldown machine wasn't so lucky: there the extra arrow skipped a waiting day, which **does** gain. If you're unsure, snapshot.

## Stock IV: at most k trades

For k trades, the chain has k links: arrays `buy[t]` and `sell[t]` for t = 1 to k, with `sell[0] = 0` meaning "no trades yet":

- `buy[t] = max(buy[t], sell[t − 1] − price)`: start trade t, funded by t − 1 finished trades.
- `sell[t] = max(sell[t], buy[t] + price)`: finish trade t.

The answer is `sell[k]`. That's k pairs of updates per day: **O(n · k) time and O(k) memory**.

### When k is large, the limit can't bind

How many trades can a best plan possibly use? Each trade needs a buy day and a later sell day. A plan that sells on some day and buys again on that same day can merge those two trades into one with the same profit. So an optimal plan never needs to share a day between trades, which means it uses at most n / 2 trades. If k ≥ n / 2, the limit never stops you, and the answer is plain Stock II: bank every rise, in O(n).

That matters. If k is a billion and you allocate `buy` and `sell` with k + 1 entries, the program runs out of memory before the first day.

```swift run
func atMostTrades(_ prices: [Int], _ k: Int) -> Int {
    if k == 0 || prices.count < 2 {
        return 0
    }
    if k >= prices.count / 2 {                 // the limit can't bind: bank every rise
        var profit = 0
        for day in 1..<prices.count {
            profit += max(0, prices[day] - prices[day - 1])
        }
        return profit
    }
    var buy = Array(repeating: Int.min / 2, count: k + 1)   // buy[t]: holding, during trade t
    var sell = Array(repeating: 0, count: k + 1)            // sell[t]: free, after t trades
    for price in prices {
        for t in 1...k {
            buy[t] = max(buy[t], sell[t - 1] - price)       // start trade t, funded by t - 1 trades
            sell[t] = max(sell[t], buy[t] + price)          // finish trade t
        }
    }
    return sell[k]
}

let prices = [2, 6, 3, 1, 5, 4, 8, 2]
for k in 0...4 {
    print("at most \(k):", atMostTrades(prices, k))
}
```

```output
at most 0: 0
at most 1: 7
at most 2: 11
at most 3: 12
at most 4: 12
```

The answers grow with k and then stop: with three trades you can bank all three rises, and a fourth trade has nothing left to take. k = 4 = n / 2 went through the shortcut and agrees with the DP's answer for k = 3.

What to notice:

- `k == 0` is handled first. Otherwise `1...k` would be `1...0`, which crashes in Swift.
- `sell[0]` is never written, so it stays 0: before any trade, your profit is 0.
- `Int.min / 2` as "not holding yet" leaves room for `buy[t] + price`.
- The inner loop runs t upwards and updates in place, which is safe here for the same reason as Stock III.

## The same machine, other limits

The chain-of-states idea handles any rule that **counts**: at most k purchases, at most k "skips", no more than k consecutive days of something. The count becomes part of the state, the transitions only move it forwards, and the cost is multiplied by the number of counts. The fixed-length-chain picture also explains Stock I and Stock II from the first lesson: Stock I is a chain with one link (k = 1), Stock II is the machine with no counting at all.

<Callout kind="gotcha" title="Common mistakes">
- **Allocating k + 1 entries for huge k.** Check `k >= prices.count / 2` first and bank every rise.
- **`1...k` with k = 0.** It crashes. Return 0 early.
- **Counting a trade twice.** Count it once, at the buy (as here) or at the sell, never both.
- **Assuming in-place is always safe.** It is here because same-day buy-and-sell earns nothing. With a cooldown or a fee, check, or snapshot.
</Callout>
