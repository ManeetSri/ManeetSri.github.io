## Why it matters

Real trading has friction. Brokers charge a fee per trade, and some markets make you wait before you can trade again. Both rules break the "bank every rise" shortcut, and both slot straight into the state machine: a cooldown changes **which arrows exist**, and a fee changes **an arrow's label**. Seeing the two side by side shows how little the code changes when the rules do, which is the whole reason to think in states.

## The cooldown, two ways

You drew the cooldown machine in [From state diagrams to transitions](/dsa/learn/dpsm-state-diagrams): three states, hold, sold and rest, with no arrow from sold to hold. That's the clearest version. There's a second formulation worth knowing, because it shows a general trick: instead of a new state, **look further back**.

Keep only two states, hold and free. The cooldown rule says: if you buy today, you must not have sold yesterday. In other words, a buy today must start from a free state that is **at least two days old**. Free two days ago, then at most a rest yesterday, then buy today. So:

- `free[i] = max(free[i − 1], hold[i − 1] + price)`: rest, or sell.
- `hold[i] = max(hold[i − 1], free[i − 2] − price)`: keep, or buy, skipping a day.

```swift run
// Three states: hold, sold (cooling down), rest
func threeStates(_ prices: [Int]) -> Int {
    var hold = Int.min / 2, sold = 0, rest = 0
    for price in prices {
        let (oldHold, oldSold, oldRest) = (hold, sold, rest)
        hold = max(oldHold, oldRest - price)
        sold = oldHold + price
        rest = max(oldRest, oldSold)
    }
    return max(sold, rest)
}

// Two states: hold and free. A buy must start from "free two days ago".
func twoStates(_ prices: [Int]) -> Int {
    var hold = Int.min / 2
    var free = 0                 // free at the end of yesterday
    var freeTwoDaysAgo = 0       // free at the end of the day before
    for price in prices {
        let freeYesterday = free
        free = max(free, hold + price)              // rest, or sell
        hold = max(hold, freeTwoDaysAgo - price)    // keep, or buy: skipping yesterday is the cooldown
        freeTwoDaysAgo = freeYesterday
    }
    return free
}

for prices in [[3, 1, 4, 2, 5, 0, 3], [1, 3, 1, 3], [2, 9, 1, 8, 3, 7], [5, 4, 3, 2]] {
    print(prices, threeStates(prices), twoStates(prices))
}
```

```output
[3, 1, 4, 2, 5, 0, 3] 6 6
[1, 3, 1, 3] 2 2
[2, 9, 1, 8, 3, 7] 11 11
[5, 4, 3, 2] 0 0
```

They always agree. Look at `[2, 9, 1, 8, 3, 7]`: without a cooldown you'd bank 7 + 7 + 4 = 18. With it, selling at 9 on day 1 makes day 2 (price 1) a cooldown, so the best is 2 → 9, then 3 → 7, for 11.

The variable juggling at the end of the loop is the rolling-array idea from [Saving space](/dsa/learn/dp-space) with a window of two days: `free` is yesterday, `freeTwoDaysAgo` is the day before, and each day they shift along by one. A cooldown of c days would need a window of c + 1 values.

Which formulation should you use? The three-state version maps one-to-one onto the drawing, so it's easier to get right first time. The two-state version generalises more easily to longer cooldowns. Both are O(n) time and O(1) memory.

## A fee per trade

New rule, no cooldown: every completed trade costs a fixed `fee`. Charge it once per trade, on the sell arrow (or the buy arrow, but not both):

- `free = max(free, hold + price − fee)`: rest, or sell and pay.
- `hold = max(hold, free − price)`: keep, or buy.

That's the Stock II machine with one label changed. Why not keep banking every rise and subtract the fee? Because a fee punishes **many small trades**:

```swift run
let prices = [4, 6, 5, 11, 7, 12]
let fee = 2

// Tempting but wrong: bank every rise, paying the fee each time it's worth it
var greedy = 0
for day in 1..<prices.count {
    greedy += max(0, prices[day] - prices[day - 1] - fee)
}

// Two states, with the fee paid when a trade closes
var hold = Int.min / 2
var free = 0
for price in prices {
    let freeYesterday = free
    free = max(free, hold + price - fee)       // rest, or sell and pay the fee
    hold = max(hold, freeYesterday - price)    // keep, or buy
}
print("every rise:", greedy)
print("state machine:", free)
```

```output
every rise: 7
state machine: 8
```

The rises are 4 → 6, 5 → 11 and 7 → 12. Banking each separately pays three fees and earns 0 + 4 + 3 = 7. The machine finds something better: buy at 4, **hold through the small dip** to 5, sell at 11 (7 − 2 = 5), then buy at 7 and sell at 12 (5 − 2 = 3), for 8.

The rule of thumb behind it: a dip is worth selling through only if it's **deeper than the fee**. The dip 6 → 5 is 1, less than the fee of 2, so splitting there costs more than it saves. The dip 11 → 7 is 4, more than the fee, so splitting there pays. You don't have to reason that out; the `max` in each update makes that comparison on every day.

### Fee on the buy instead

Charging the fee when you buy gives `hold = max(hold, free − price − fee)` and `free = max(free, hold + price)`, with the same answers. Just be careful with the starting `hold`: if you start it at `-prices[0] - fee` instead of "impossible", make sure the fee is included. Charging on both arrows is the classic bug: it doubles every fee.

## Both rules at once

A market with a cooldown **and** a fee needs no new ideas. Take the three-state cooldown machine and put the fee on its sell arrow:

| State | Transition |
| --- | --- |
| hold | `max(hold, rest − price)` |
| sold | `hold + price − fee` |
| rest | `max(rest, sold)` |

The answer is `max(sold, rest)`. When a new rule arrives, ask two questions: does it remove or add an arrow (cooldown, limits), or does it change what an arrow costs (fees, taxes)? Then edit the diagram, and the code follows.

<Callout kind="gotcha" title="Common mistakes">
- **Charging the fee twice.** Put it on exactly one arrow, buy or sell.
- **Misreading the cooldown.** It blocks buying the day **after** a sale. You can still sell any day you hold a share.
- **Banking every rise with a fee.** Small rises separated by shallow dips should be one trade.
- **Returning `hold`, or `max` including hold.** The answer is a free state: sold or rest, or free.
- **Updating in place.** For the cooldown it gives wrong answers (test with `[1, 3, 1, 3]`, which should give 2). Snapshot yesterday's values.
</Callout>
