## Why it matters

Kruskal looks at the whole graph's edges in weight order. **Prim's algorithm** works locally instead: it grows a single tree outwards from one vertex, always adding the cheapest edge that reaches a new vertex. With a heap it runs in O(E log V), the same as Kruskal. With a plain array it runs in O(V²), which beats every heap-based method on dense graphs, and on "complete" graphs where every pair of points could be joined it never needs to build the edges at all. Knowing both versions, and when each wins, is what interviewers look for. If Dijkstra's algorithm felt familiar, good: Prim is its close cousin.

## The idea: grow one tree

1. Start the tree with any vertex.
2. Look at every edge with one end in the tree and the other end outside. Add the lightest one, and the vertex it reaches.
3. Repeat until every vertex is in the tree.

Why is that safe? Step 2 uses the cut between **the tree so far** and **everything else**. The edge it adds is a lightest edge crossing that cut, and no tree edge crosses it, so the cut property from [Spanning trees and the cut property](/dsa/learn/mst-definition) says some MST contains the tree plus this edge. Every step keeps the tree inside an MST, and after V − 1 steps it is one.

The only question is how to find "the lightest edge leaving the tree" quickly.

## The heap version, with lazy deletion

Keep a min-heap of **candidate edges**, ordered by weight. When a vertex joins the tree, push every edge from it to a vertex outside. Then pop the lightest candidate:

- if it leads to a vertex **already in the tree**, it's stale (that vertex joined some other, cheaper way): skip it;
- otherwise, add that vertex and push its edges.

Leaving stale entries in the heap and skipping them when they surface is called **lazy deletion**. You used exactly this trick in [Dijkstra's algorithm](/dsa/learn/sp-dijkstra). It's simpler than finding and removing the stale entries, at the cost of a bigger heap.

```swift run
// The heap from "Build a generic Heap<T>", compacted
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    var count: Int { items.count }

    mutating func insert(_ element: Element) {
        items.append(element)
        var child = items.count - 1
        while child > 0 && areInIncreasingOrder(items[child], items[(child - 1) / 2]) {
            items.swapAt(child, (child - 1) / 2)
            child = (child - 1) / 2
        }
    }

    mutating func pop() -> Element? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        var parent = 0
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var first = parent
            if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
            if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
            if first == parent { return top }
            items.swapAt(parent, first)
            parent = first
        }
    }
}

let names = ["A", "B", "C", "D", "E", "F"]
let edges = [(0, 1, 4), (0, 2, 2), (1, 2, 1), (1, 3, 5), (2, 4, 10), (3, 4, 2), (3, 5, 6), (4, 5, 3)]
var neighbours = Array(repeating: [(to: Int, weight: Int)](), count: names.count)
for (a, b, weight) in edges {
    neighbours[a].append((b, weight))
    neighbours[b].append((a, weight))
}

/// The MST's total weight, growing one tree from start, or nil if some vertex can't be reached
func prim(from start: Int) -> Int? {
    var inTree = Array(repeating: false, count: names.count)
    var candidates = Heap<(weight: Int, from: Int, to: Int)>(areInIncreasingOrder: { $0.weight < $1.weight })
    candidates.insert((0, start, start))
    var total = 0
    var treeSize = 0
    while let edge = candidates.pop() {
        if inTree[edge.to] {
            print("pop \(names[edge.from])\(names[edge.to]) \(edge.weight): stale, \(names[edge.to]) is already in the tree")
            continue
        }
        inTree[edge.to] = true
        total += edge.weight
        treeSize += 1
        print(edge.to == start ? "start at \(names[start])"
              : "pop \(names[edge.from])\(names[edge.to]) \(edge.weight): add \(names[edge.to])")
        for next in neighbours[edge.to] where !inTree[next.to] {
            candidates.insert((next.weight, edge.to, next.to))
        }
    }
    return treeSize == names.count ? total : nil
}

print("total weight:", prim(from: 0)!)
```

```output
start at A
pop AC 2: add C
pop CB 1: add B
pop AB 4: stale, B is already in the tree
pop BD 5: add D
pop DE 2: add E
pop EF 3: add F
pop DF 6: stale, F is already in the tree
pop CE 10: stale, E is already in the tree
total weight: 13
```

The same total as Kruskal, 13, from a completely different order: Prim added AC first, because it was the cheapest way out of \{A\}, while Kruskal started with the globally lightest edge, BC. Step through it, watching the heap and the stale entries:

```visual graph
program: prim
graph: weighted
start: A
```

What to notice:

- **A vertex is marked when it's popped, not when it's pushed.** B was pushed via AB (4) first, but a cheaper way in, CB (1), turned up before that entry reached the top. Marking B on the push would have locked in the worse edge.
- **The start is pushed as a weight-0 "edge" to itself**, so the loop needs no special first step.
- **Three stale entries were skipped.** The heap can hold up to one entry per edge direction, which is the price of laziness.

### The cost

Every edge is pushed at most twice (once from each end) and popped at most twice, and each heap operation costs O(log E). That's **O(E log E) = O(E log V)** time and O(E) extra space for the heap.

The difference from Dijkstra is one expression. Dijkstra's heap is keyed by the **total distance from the start**, `distance[u] + weight`. Prim's is keyed by the **edge weight alone**, because it only cares about the cheapest way to attach a vertex to the tree, not how far that vertex is from the start.

An **eager** version keeps at most one heap entry per vertex and lowers its key when a cheaper edge appears. That needs an indexed priority queue, from [d-ary heaps and indexed priority queues](/dsa/learn/heap-variants), and gives O(E log V) with a heap of only V entries.

## The array version: O(V²), no heap at all

Now forget the heap. Keep two arrays:

- `inTree[v]`: has v joined the tree?
- `cheapest[v]`: the weight of the lightest known edge from the tree to v (infinity if none yet).

Each round, **scan** all the vertices for the outside vertex with the smallest `cheapest`, add it, and then update `cheapest` for every outside vertex using the new vertex's edges. With an adjacency matrix, both scans are O(V), and there are V rounds:

```swift run
let names = ["A", "B", "C", "D", "E", "F"]
let none = Int.max                                   // no edge
let weight = [
    //  A     B     C     D     E     F
    [none,    4,    2, none, none, none],          // A
    [   4, none,    1,    5, none, none],          // B
    [   2,    1, none, none,   10, none],          // C
    [none,    5, none, none,    2,    6],          // D
    [none, none,   10,    2, none,    3],          // E
    [none, none, none,    6,    3, none],          // F
]

/// O(V²) Prim: cheapest[v] is the lightest known edge from the tree to v, and via[v] its other end
func densePrim(_ weight: [[Int]]) -> Int? {
    let n = weight.count
    var inTree = Array(repeating: false, count: n)
    var cheapest = Array(repeating: none, count: n)
    var via = Array(repeating: -1, count: n)
    cheapest[0] = 0
    var total = 0
    for _ in 0..<n {
        var next = -1                                // the outside vertex with the cheapest way in
        for v in 0..<n where !inTree[v] && (next == -1 || cheapest[v] < cheapest[next]) {
            next = v
        }
        if cheapest[next] == none { return nil }    // nothing left is reachable
        inTree[next] = true
        total += cheapest[next]
        if via[next] >= 0 {
            print("add \(names[next]) via \(names[via[next]])\(names[next]) \(cheapest[next])")
        }
        for v in 0..<n where !inTree[v] && weight[next][v] < cheapest[v] {
            cheapest[v] = weight[next][v]            // a cheaper way into v, through next
            via[v] = next
        }
    }
    return total
}

print("total weight:", densePrim(weight)!)
```

```output
add C via AC 2
add B via CB 1
add D via BD 5
add E via DE 2
add F via EF 3
total weight: 13
```

Each vertex keeps only its **best** way in, so there's nothing stale to skip. `via` records which tree vertex that best edge comes from, which gives you the MST's edges if you need them, not just the total. The `Int.max` sentinel for "no edge" is safe here because it's only ever compared, never added to.

## Which one wins?

The array version always costs O(V²), however many edges there are. The heap version costs O(E log V). So it comes down to how many edges the graph has, as in [Dense vs sparse, and reading graph input](/dsa/learn/graph-dense-sparse):

| Graph | Heap Prim, O(E log V) | Array Prim, O(V²) | Winner |
| --- | --- | --- | --- |
| Sparse: V = 10,000, E = 30,000 | about 30,000 × 14 ≈ 420,000 | 100,000,000 | heap |
| Dense: V = 2,000, every pair joined (E ≈ 2,000,000) | about 2,000,000 × 11 ≈ 22,000,000, plus a 2-million-entry heap | 4,000,000 | array |

A rule of thumb: when E is close to V², use the array; when E is closer to V, use the heap (or Kruskal).

The array version has one more advantage. On a **complete graph given implicitly**, such as points on a map where any two can be joined at the cost of their distance, you don't need to build any edges at all. When vertex `next` joins the tree, compute its distance to each outside point on the spot. That's O(V²) time and **O(V) memory**, where Kruskal or heap Prim would first have to create all V(V − 1) / 2 edges. The next lesson uses exactly this.

| | Kruskal | Prim with a heap | Prim with an array |
| --- | --- | --- | --- |
| Time | O(E log E) | O(E log V) | O(V²) |
| Extra space | O(V + E) for the sorted edges | O(V + E) | O(V) |
| Needs | an edge list | adjacency lists | a matrix, or a way to compute any weight |
| Best for | sparse graphs given as edge lists | sparse graphs as adjacency lists | dense and complete graphs |

## In problems: DSAKit's Heap

In the practice problems, `import DSAKit` gives you the finished heap, so the candidates are one line:

```swift
import DSAKit

var candidates = Heap<(weight: Int, to: Int)>(areInIncreasingOrder: { $0.weight < $1.weight })
```

<Callout kind="gotcha" title="Common mistakes">
- **Marking a vertex in the tree when you push it.** Mark it when it's popped, as with Dijkstra. Otherwise the first edge found wins, not the cheapest.
- **No stale check.** Without `if inTree[edge.to] { continue }`, a vertex gets added again through a heavier edge and the total comes out too big.
- **Using Dijkstra's key.** Push the edge weight, not `distance + weight`. The second gives a shortest-path tree, not an MST.
- **Assuming the graph is connected.** If the heap empties, or the array version finds no reachable vertex, before every vertex has joined, there's no spanning tree.
</Callout>
