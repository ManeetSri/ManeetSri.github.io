## Why it matters

"This is O(n)" is the sentence you'll say and read more than any other in DSA: in interviews, in Apple's documentation, in every solution write-up. In the last lesson you counted steps exactly and got formulas like 2n + 2. Big-O notation is the precise way to throw away the details of such a formula and keep only what matters: how fast it grows. This lesson gives you the real definition and its two siblings, Big-Ω and Big-Θ, so you know exactly what those letters promise.

## From exact counts to growth rates

Exact step counts are fussy. One person counts the sum loop as 2n + 2, another as 3n + 2, and a compiler might turn it into something else entirely. What everyone agrees on is the **growth rate**: double n and the work doubles.

So we want a way to say "grows like n" that:

- ignores constant multipliers, like the 2 or 3 in front of n;
- ignores small extra terms, like the + 2;
- only cares about **large** n, because small inputs are fast whatever you do.

Big-O notation does exactly this.

## Big-O: an upper bound

Here's the definition. Read it slowly, then read the plain-English version underneath.

> **f(n) is O(g(n))** if there are positive constants **c** and **n₀** such that f(n) ≤ c · g(n) for every n ≥ n₀.

In plain English: **from some point on, f is never bigger than a fixed multiple of g.**

- **f(n)** is the thing you're measuring, such as your step count 3n + 2.
- **g(n)** is a simple comparison function, such as n or n².
- **c** is the multiple you're allowed to scale g by.
- **n₀** is the point after which the inequality must hold. Small n don't count.

### Finding c and n₀

Claim: 3n + 2 is O(n). To prove it, you only need to find one c and one n₀ that work. Try c = 4, and check the inequality 3n + 2 ≤ 4n:

```swift run
func steps(_ n: Int) -> Int {
    3 * n + 2
}

for n in [1, 2, 10, 100, 1_000] {
    let bound = 4 * n
    print("n = \(n): 3n + 2 = \(steps(n)), 4n = \(bound), within bound: \(steps(n) <= bound)")
}
```

```output
n = 1: 3n + 2 = 5, 4n = 4, within bound: false
n = 2: 3n + 2 = 8, 4n = 8, within bound: true
n = 10: 3n + 2 = 32, 4n = 40, within bound: true
n = 100: 3n + 2 = 302, 4n = 400, within bound: true
n = 1000: 3n + 2 = 3002, 4n = 4000, within bound: true
```

It fails at n = 1 but holds from n = 2 onwards. A few lines of algebra confirm it holds forever after: 3n + 2 ≤ 4n is the same as 2 ≤ n. So **c = 4 and n₀ = 2** prove that 3n + 2 is O(n). That's what n₀ is for: it lets you ignore the small cases where the constant term still matters.

A program can only check finitely many n, so the experiment is evidence; the algebra is the proof.

A second example: n² + 10n is O(n²), with c = 2 and n₀ = 10, because n² + 10n ≤ 2n² is the same as 10n ≤ n², which is true once n ≥ 10.

```swift run
func f(_ n: Int) -> Int {
    n * n + 10 * n
}

for n in [5, 10, 100, 1_000] {
    print("n = \(n): f(n) = \(f(n)), n² = \(n * n), 2n² = \(2 * n * n)")
}
```

```output
n = 5: f(n) = 75, n² = 25, 2n² = 50
n = 10: f(n) = 200, n² = 100, 2n² = 200
n = 100: f(n) = 11000, n² = 10000, 2n² = 20000
n = 1000: f(n) = 1010000, n² = 1000000, 2n² = 2000000
```

Look at how f(n) gets closer and closer to plain n² as n grows. The 10n part, which more than doubled the total at n = 5, adds only 1% at n = 1,000.

### Big-O is only an upper bound

Big-O says "at most". So 3n + 2 is O(n), but it's **also** O(n²) and O(2ⁿ), because it never exceeds those either. All three statements are true. Only the first is useful.

<Callout kind="analogy">
Big-O is like saying "the drive takes at most 3 hours". If it really takes 40 minutes, the statement is true, but not very informative. "At most 45 minutes" is the helpful version.
</Callout>

## Proving something is not O(g)

Is n² O(n)? If it were, there'd be a constant c with n² ≤ c · n for all large n. Divide both sides by n: n ≤ c. But n keeps growing and c is fixed, so this fails as soon as n passes c.

```swift run
// Whatever constant c you pick, n² eventually passes c × n
for c in [10, 100, 1_000] {
    var n = 1
    while n * n <= c * n {
        n += 1
    }
    print("c = \(c): n² beats \(c)n from n = \(n)")
}
```

```output
c = 10: n² beats 10n from n = 11
c = 100: n² beats 100n from n = 101
c = 1000: n² beats 1000n from n = 1001
```

No constant can keep up. So n² is **not** O(n). This is why constants are allowed to disappear but exponents are not: a bigger constant only delays the moment n² overtakes it.

## Big-Ω: a lower bound

Big-Omega (Ω, a Greek capital O) is the mirror image of Big-O.

> **f(n) is Ω(g(n))** if there are positive constants c and n₀ such that f(n) ≥ c · g(n) for every n ≥ n₀.

In plain English: **from some point on, f is at least a fixed multiple of g.**

3n + 2 is Ω(n), with c = 3 and n₀ = 1, since 3n + 2 ≥ 3n always. It's also Ω(1), because it's at least 1. It is **not** Ω(n²): that would need 3n + 2 ≥ c · n², which fails for large n, by the same argument as above.

Lower bounds answer questions like "how much work must *any* solution do?" For example, finding the largest element of an unsorted array is Ω(n): an algorithm that skipped an element could miss the largest one.

## Big-Θ: a tight bound

Big-Theta (Θ) means both at once.

> **f(n) is Θ(g(n))** if f(n) is O(g(n)) **and** Ω(g(n)).

In plain English: **from some point on, f sits between two fixed multiples of g.** For 3n + 2 and g(n) = n, we've shown 3n ≤ 3n + 2 ≤ 4n for n ≥ 2, so 3n + 2 is Θ(n).

Θ is the precise statement: "grows exactly like n, up to constant factors". It's what you usually mean.

| Notation | Means | Like |
| --- | --- | --- |
| f is O(g) | f grows no faster than g | ≤ |
| f is Ω(g) | f grows at least as fast as g | ≥ |
| f is Θ(g) | f grows at the same rate as g | = |

## What people mean when they say "Big-O"

In everyday use, including interviews, documentation and this course, people say "O(n)" when they really mean the tight bound Θ(n). Apple's documentation for `Array.contains` says "Complexity: O(n)", and nobody reads that as "maybe it's secretly O(1)". When someone says "this solution is O(n²)", they mean it really does about n² work.

Follow the convention: give the **tightest** bound you can, and call it Big-O. Reach for Ω and Θ when you need to be precise, such as when you want to say "no algorithm can do better than this".

<Callout kind="gotcha" title="Bounds are not cases">
A common mix-up is "Big-O means worst case, Big-Ω means best case". They're separate ideas. Best, worst and average case pick **which inputs** you're talking about; O, Ω and Θ describe **how a function grows**. You can give any bound for any case: linear search's worst case is Θ(n) and its best case is Θ(1). You'll untangle this fully in the lesson on best, average and worst case.
</Callout>

## A note on the equals sign

You'll often see "f(n) = O(n)" written with an equals sign. It's a tradition, but it doesn't behave like a real equals: 3n + 2 = O(n) and 5n = O(n), yet 3n + 2 ≠ 5n. Read "=" here as "is" or "belongs to": O(n) is really the **set** of all functions that grow no faster than n. Never write it backwards, as O(n) = f(n).
