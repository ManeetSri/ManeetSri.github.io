## Why it matters

Before you can call an algorithm fast, you need a way to measure it that doesn't depend on your laptop. In [Timing code with ContinuousClock](/dsa/learn/swift-timing-code) you saw that stopwatch times change between machines, builds and even runs. Counting the basic steps an algorithm takes doesn't change. Every idea in this module, from Big-O to the feasibility table, grows out of one habit: count the work, then watch how the count grows as the input grows.

## What counts as one step

A **step** (or **basic operation**) is anything that takes roughly the same, small amount of time no matter how big the input is:

- assigning a value: `total = 0`
- one arithmetic operation: `a + b`, `i * 2`
- comparing two numbers: `x < y`
- reading or writing one array element: `numbers[i]`
- checking an `if` condition, calling a function, returning

We pretend each of these costs exactly 1. That isn't strictly true: a division takes longer than an addition, and memory isn't equally fast everywhere. But the differences are fixed multiples, a division might cost five additions, and the next lesson shows why fixed multiples don't change the big picture.

<Callout kind="analogy">
Counting steps is like measuring a walk in paces instead of minutes. A tall person and a short person take different numbers of minutes, but if one route is twice as many paces as another, it's longer for both of them.
</Callout>

## Counting a function with no loops

```swift
func average(_ a: Int, _ b: Int, _ c: Int) -> Int {
    let total = a + b + c   // 2 additions, 1 assignment
    return total / 3        // 1 division, 1 return
}
```

That's 5 steps, whatever the three numbers are. The count doesn't depend on the input at all, so we call it **constant**.

## Counting a loop

Now a function whose work depends on the input. Call the number of elements **n**:

```swift
func sum(_ numbers: [Int]) -> Int {
    var total = 0              // 1 step
    for number in numbers {    // fetch the next element: n steps
        total += number        // add and store: n steps
    }
    return total               // 1 step
}
```

Adding it up: 1 + n + n + 1 = **2n + 2** steps.

| n | 2n + 2 |
| --- | --- |
| 10 | 22 |
| 1,000 | 2,002 |
| 1,000,000 | 2,000,002 |

Two things to notice. First, the "+ 2" stops mattering almost immediately. Second, when n doubles, the count roughly doubles.

Someone else might count `total += number` as two steps (an addition and a store) and get 3n + 2. That's fine. Every reasonable count of this function has the form *some number × n, plus a small constant*, and that shared shape is what we care about.

## Let the computer count

Counting by hand gets error-prone once loops nest. A **counting experiment** does it for you: add a `steps` variable that goes up by one every time the innermost line runs, then print it for a few sizes.

```swift run
func singleLoopSteps(_ n: Int) -> Int {
    var steps = 0
    for _ in 0..<n {
        steps += 1
    }
    return steps
}

func nestedLoopSteps(_ n: Int) -> Int {
    var steps = 0
    for _ in 0..<n {
        for _ in 0..<n {
            steps += 1
        }
    }
    return steps
}

for n in [10, 100, 1_000] {
    print("n = \(n): single \(singleLoopSteps(n)), nested \(nestedLoopSteps(n))")
}
```

```output
n = 10: single 10, nested 100
n = 100: single 100, nested 10000
n = 1000: single 1000, nested 1000000
```

What to notice:

- Each time n grows ten times, the single loop does ten times more work, and the nested loop does a **hundred** times more.
- At n = 1,000 the nested loop has already done a million steps. At n = 100,000 it would do ten billion.

You'll use counting experiments throughout this module. They're deterministic, unlike timings, so they make growth easy to see.

## The doubling test

The most useful question to ask about a step count is: **when the input doubles, what happens to the work?**

```swift run
func halvingSteps(_ n: Int) -> Int {
    var steps = 0
    var size = n
    while size > 1 {
        size /= 2
        steps += 1
    }
    return steps
}

func linearSteps(_ n: Int) -> Int {
    var steps = 0
    for _ in 0..<n {
        steps += 1
    }
    return steps
}

func quadraticSteps(_ n: Int) -> Int {
    var steps = 0
    for _ in 0..<n {
        for _ in 0..<n {
            steps += 1
        }
    }
    return steps
}

for n in [100, 200, 400, 800] {
    print("n = \(n): halving \(halvingSteps(n)), linear \(linearSteps(n)), quadratic \(quadraticSteps(n))")
}
```

```output
n = 100: halving 6, linear 100, quadratic 10000
n = 200: halving 7, linear 200, quadratic 40000
n = 400: halving 8, linear 400, quadratic 160000
n = 800: halving 9, linear 800, quadratic 640000
```

Each doubling of n adds **one** step to the halving loop, **doubles** the linear loop and **quadruples** the nested one. Those three behaviours have names you'll learn properly soon:

| When n doubles, the count… | Name |
| --- | --- |
| stays the same | constant |
| goes up by a fixed amount | logarithmic |
| doubles | linear |
| quadruples | quadratic |

The doubling test works on real timings too: if your program takes 1 second for some input and 4 seconds for an input twice as big, something quadratic is going on.

## What is n?

**n** is the size of the input, and you should always say what it measures:

- for an array, usually its number of elements;
- for a string, its number of characters;
- for a function that takes a number, such as "is x prime?", often the number itself.

When a function takes two inputs of unrelated sizes, such as two arrays, give them two letters, n and m. You'll practise that in two lessons.

## Counts can depend on the values too

The step count isn't always fixed by the size alone. A search that stops as soon as it finds its target does different amounts of work on inputs of the same size:

```swift run
func comparisons(toFind target: Int, in numbers: [Int]) -> Int {
    var count = 0
    for number in numbers {
        count += 1
        if number == target {
            return count
        }
    }
    return count
}

let numbers = Array(1...100)
print(comparisons(toFind: 1, in: numbers))
print(comparisons(toFind: 50, in: numbers))
print(comparisons(toFind: 999, in: numbers))
```

```output
1
50
100
```

Same array, same n, but 1, 50 or 100 comparisons. Which one should you report? That's the question of best, average and worst case, which gets its own lesson later in this module.

## One line is not one step

A line like `if numbers.contains(target)` reads like a single step, but `contains` walks the array, comparing as it goes. A counting experiment makes the hidden loop visible:

```swift run
let numbers = Array(1...1_000)
var checks = 0
for target in [10, 500, 2_000] {
    if numbers.contains(where: { value in
        checks += 1
        return value == target
    }) {
        print(target, "found")
    } else {
        print(target, "missing")
    }
}
print("comparisons:", checks)
```

```output
10 found
500 found
2000 missing
comparisons: 1510
```

Three innocent-looking lookups did 1,510 comparisons: 10 to find 10, 500 to find 500, and all 1,000 to learn that 2,000 isn't there.

<Callout kind="gotcha" title="Swift gotcha: lines that hide loops">
`contains`, `min()`, `max()`, `firstIndex(of:)`, `filter`, `sorted()` and `Array(text)` all walk their whole input. So does `text.count` on a `String`, which you might expect to be instant. When one of these sits inside a loop, you have a loop inside a loop. The last lesson of this module, Swift's hidden costs, lists the common culprits.
</Callout>

## Practice

**Count the loop steps** asks you to predict exactly how many times two loops run their bodies for any n, and to return the answer straight from a formula. Run a counting experiment first to check your formula against small cases.

```cards

  front: "Why count steps instead of timing code with a clock?"
  back: "Step counts don't depend on the machine, the build or what else is running, so they show how the work grows with the input."
- id: one-step
  front: "What counts as one basic step?"
  back: "Anything that takes about the same small time for any input size: an assignment, one arithmetic operation, a comparison, reading one array element, a return."
- id: doubling-test
  front: "What does the doubling test tell you about linear and quadratic code?"
  back: "When n doubles, linear work doubles and quadratic work quadruples. A halving loop gains only one step."
- id: hidden-loop
  front: "Why isn't `numbers.contains(x)` one step?"
  back: "It walks the array comparing each element, so it costs up to n steps for n elements."
```
