## Why it matters

The aggregate method from the last lesson adds up a whole sequence and divides. That works well when there's one kind of operation with a cost pattern you can sum. It gets awkward when operations are mixed, or when you want to say what each *kind* of operation costs. Two more methods handle this: the **accounting method** and the **potential method**. They're the tools behind the analyses of union-find, splay trees and Fibonacci heaps later in the course, and they make the reasoning behind "amortised O(1)" feel almost physical.

## The accounting method

Think of each operation as paying a fixed fee in coins: its **amortised cost**. Each unit of real work costs one coin.

- When an operation is cheap, it pays its fee, uses fewer coins than it paid, and deposits the change in a bank.
- When an operation is expensive, it pays its fee and withdraws the rest from the bank.

The one rule: **the bank balance must never go negative.** If that holds for every possible sequence, the total real work can never exceed the total fees paid. So the fee is a valid amortised cost.

### Three coins per append

For the doubling array from the last lesson (capacity 1 to start, doubling when full), charge every append **3 coins**:

1. One coin pays for writing the new element.
2. One coin is saved to pay for copying **this** element at the next growth.
3. One coin is saved to pay for copying an **older** element, one that was already copied at the last growth and spent its savings then.

Follow the bank through one cycle. Right after a growth to capacity 2k, the array holds k + 1 elements and the bank holds 3 coins. The next k − 1 appends are cheap, and each deposits 2 coins, bringing the bank to 2k + 1. Then the array is full, and the next append costs 2k + 1: copying 2k elements and writing one. Its own fee of 3 plus the bank covers that, with 3 coins left over for the next cycle. A simulation shows the bank balance after each append:

```swift run
// Charge every append 3 coins and keep the change in a bank
var capacity = 1
var count = 0
var bank = 0
var balances: [Int] = []
for _ in 1...17 {
    var actual = 1                // write the new element
    if count == capacity {
        actual += count           // copy everything to a block twice the size
        capacity *= 2
    }
    count += 1
    bank += 3 - actual
    balances.append(bank)
}
print(balances)
print("lowest balance:", balances.min()!)
```

```output
[2, 3, 3, 5, 3, 5, 7, 9, 3, 5, 7, 9, 11, 13, 15, 17, 3]
lowest balance: 2
```

The balance climbs by 2 on every cheap append and drops back to 3 at every growth, but it never goes negative. So 3 coins per append always covers the real work: n appends cost at most 3n, which is O(1) amortised per append.

Would 2 coins be enough? Change the 3 to a 2 in the simulation: the balance goes negative at the fifth append, the second growth. Finding the right fee is the creative part of the method.

## The potential method

The accounting method attaches savings to individual elements. The potential method instead measures how much "stored-up" work the whole data structure is holding, with a single number called its **potential**, written Φ (the Greek letter phi).

Choose a function Φ of the structure's state such that:

- Φ starts at **0**, and
- Φ is **never negative**.

Then define each operation's amortised cost as:

**amortised cost = actual cost + Φ after − Φ before**

An operation that builds up potential pays a bit extra now; one that releases potential gets a discount. Adding up a whole sequence, the Φ terms cancel in pairs, leaving

**total amortised = total actual + Φ at the end − Φ at the start**

Since Φ starts at 0 and ends at 0 or more, the total amortised cost is at least the total actual cost. So proving that every operation's amortised cost is small proves that the whole sequence is cheap.

### A potential for the doubling array

Use **Φ = 2 × count − capacity**, starting from an empty array with capacity 0 that grows to capacity 1 on its first append. A doubling array is always at least half full after an append, so 2 × count is at least the capacity and Φ never goes negative.

```swift run
// Potential: Φ = 2 × count − capacity
var capacity = 0
var count = 0
func potential() -> Int {
    2 * count - capacity
}

for _ in 1...9 {
    let before = potential()
    var actual = 1
    if count == capacity {
        actual += count
        capacity = max(1, 2 * capacity)
    }
    count += 1
    let after = potential()
    print("append \(count): actual \(actual), Φ \(before) → \(after), amortised \(actual + after - before)")
}
```

```output
append 1: actual 1, Φ 0 → 1, amortised 2
append 2: actual 2, Φ 1 → 2, amortised 3
append 3: actual 3, Φ 2 → 2, amortised 3
append 4: actual 1, Φ 2 → 4, amortised 3
append 5: actual 5, Φ 4 → 2, amortised 3
append 6: actual 1, Φ 2 → 4, amortised 3
append 7: actual 1, Φ 4 → 6, amortised 3
append 8: actual 1, Φ 6 → 8, amortised 3
append 9: actual 9, Φ 8 → 2, amortised 3
```

The actual costs jump around, 1, 1, 1, 9, but the amortised cost is a steady 3. You can prove it for every append with a little algebra:

- **Cheap append:** actual cost 1, count goes up by 1, so Φ rises by 2. Amortised: 1 + 2 = **3**.
- **Growing append** when count = capacity = k: actual cost k + 1 (k copies and one write). Before, Φ = 2k − k = k. After, count is k + 1 and capacity 2k, so Φ = 2k + 2 − 2k = 2. Amortised: (k + 1) + 2 − k = **3**.

The expensive copy is paid for by potential that the cheap appends built up.

## A second example: the odometer

Picture a car's odometer counting up from 0: each increment adds 1 to the last digit, and every 9 rolls over to 0 with a carry. Most increments change one digit, but 999 to 1,000 changes four. How many digit changes do n increments cost?

```swift run
// A decimal odometer, stored least significant digit first
func increment(_ digits: inout [Int]) -> Int {
    var changed = 0
    var position = 0
    while position < digits.count && digits[position] == 9 {
        digits[position] = 0          // a 9 rolls over to 0
        changed += 1
        position += 1
    }
    if position == digits.count {
        digits.append(1)              // a new leading digit
    } else {
        digits[position] += 1
    }
    return changed + 1
}

for n in [10, 100, 1_000, 10_000] {
    var digits = [0]
    var total = 0
    var worst = 0
    for _ in 0..<n {
        let cost = increment(&digits)
        total += cost
        worst = max(worst, cost)
    }
    print("\(n) increments: \(total) digit changes, worst single increment \(worst)")
}
```

```output
10 increments: 11 digit changes, worst single increment 2
100 increments: 111 digit changes, worst single increment 3
1000 increments: 1111 digit changes, worst single increment 4
10000 increments: 11111 digit changes, worst single increment 5
```

A single increment can cost O(number of digits), yet the total is about 1.11n.

- **Aggregate view:** the last digit changes on every increment, the tens digit on every tenth, the hundreds on every hundredth: n + n/10 + n/100 + … is less than 1.12n.
- **Potential view:** let **Φ = the number of 9s showing**. An increment that rolls over t nines has actual cost t + 1. Those t nines become zeros (Φ drops by t), and the one digit that goes up might become a new 9 (Φ rises by at most 1). Amortised cost: at most (t + 1) − t + 1 = **2**. However many 9s roll over, they were "paid for" when each one appeared.

Φ starts at 0 for a counter showing 0 and can never be negative, so n increments cost at most 2n digit changes: O(1) amortised.

## Choosing a method

| Method | How it works | Best for |
| --- | --- | --- |
| Aggregate | add up the whole sequence, divide by n | one kind of operation with a clear pattern |
| Accounting | fixed fees, savings in a bank that never goes negative | a story you can tell per operation or per element |
| Potential | Φ measures stored-up work; amortised = actual + ΔΦ | mixed operations and complex structures |

All three give the same answers when they apply. The art is in the choice of fee or potential: a good Φ is high when an expensive operation is coming, and drops when that operation happens.

<Callout kind="gotcha" title="The rules aren't optional">
Each method only works if its rule holds for **every** sequence of operations: the bank never goes negative, or Φ starts at 0 and never goes below it. Check the rule carefully, especially at the start (an empty structure) and right after the most expensive operation, which is where it usually breaks.
</Callout>
