## Why it matters

You've been told that `append` is O(1). That's not quite true: now and then, a single `append` copies the entire array. Apple's documentation is more careful, describing it as O(1) "on average, over many calls" on the same array. That careful phrase is **amortised** analysis: averaging the cost over a whole sequence of operations, so rare expensive steps are paid for by many cheap ones. It's how you'll analyse dynamic arrays, hash tables, and several data structures in Part III, and in M18 you'll build your own growable array using exactly the idea in this lesson.

## How an array grows

An array keeps its elements side by side in one block of memory. That block usually has some spare room at the end. The number of elements is the array's `count`; the number of elements the block can hold is its **capacity**.

- If there's spare room, `append` writes the new element into the next free slot: O(1).
- If the block is full, `append` must allocate a **bigger** block, copy every existing element across, free the old block, and then write the new element: O(n).

You can watch it happen with the `capacity` property:

```swift run
var numbers: [Int] = []
var lastCapacity = numbers.capacity
print("count 0, capacity \(lastCapacity)")
for value in 1...100 {
    numbers.append(value)
    if numbers.capacity != lastCapacity {
        print("count \(numbers.count), capacity \(numbers.capacity)")
        lastCapacity = numbers.capacity
    }
}
```

```output
count 0, capacity 0
count 1, capacity 2
count 3, capacity 4
count 5, capacity 8
count 9, capacity 16
count 17, capacity 36
count 37, capacity 76
count 77, capacity 156
```

Each time the array fills up, its capacity at least **doubles**. The jumps like 16 to 36 happen because the system's memory allocator hands out blocks in standard sizes, and Swift uses all the room it's given. These exact numbers come from a Mac; other systems may differ slightly, but the pattern of roughly doubling is the same.

## Counting the copies

How much copying does that cause in total? Count the elements moved at each growth:

```swift run
func appendCost(_ n: Int) -> (growths: Int, copies: Int) {
    var numbers: [Int] = []
    var growths = 0
    var copies = 0
    for value in 0..<n {
        let oldCapacity = numbers.capacity
        let oldCount = numbers.count
        numbers.append(value)
        if numbers.capacity != oldCapacity {
            growths += 1
            copies += oldCount       // every existing element moved
        }
    }
    return (growths, copies)
}

for n in [100, 1_000, 10_000, 100_000] {
    let cost = appendCost(n)
    print("\(n) appends: \(cost.growths) growths, \(cost.copies) elements copied")
}
```

```output
100 appends: 7 growths, 142 elements copied
1000 appends: 10 growths, 1250 elements copied
10000 appends: 13 growths, 11222 elements copied
100000 appends: 17 growths, 195526 elements copied
```

The number of growths is tiny, about log₂ n, and the total copying is always **less than 2n**. So even counting every expensive growth, n appends cost O(n) in total, which is O(1) each on average.

Watch the copies pile up, then fall behind. Each append costs one write, plus a burst of copies whenever the buffer is full:

```visual arrayTrace

  capacity: 1
```

## The aggregate argument

Let's prove that, for a model array that starts with capacity 1 and doubles whenever it's full. Charge 1 for writing an element and 1 for each element copied. Here are the costs of the first 17 appends:

```swift run
// A model array that starts with room for 1 element and doubles when full
var capacity = 1
var count = 0
var total = 0
var costs: [Int] = []
for _ in 1...17 {
    var cost = 1                  // writing the new element
    if count == capacity {
        cost += count             // copying every element to the new block
        capacity *= 2
    }
    count += 1
    total += cost
    costs.append(cost)
}
print(costs)
print("total \(total) for \(count) appends")
```

```output
[1, 2, 3, 1, 5, 1, 1, 1, 9, 1, 1, 1, 1, 1, 1, 1, 17]
total 48 for 17 appends
```

Most appends cost 1. The spikes, 2, 3, 5, 9 and 17, are the growths, and they get further and further apart: each one is twice as expensive as the last, but the gap before the next is twice as long.

Now add up everything for n appends. This is the **aggregate method**: total the whole sequence, then divide.

1. **Writes:** each append writes once: **n**.
2. **Copies:** growths happen when the array holds 1, 2, 4, 8, … elements, each copying that many. The largest is less than n, so the copies total 1 + 2 + 4 + … + 2ᵏ, where 2ᵏ is less than n.
3. That sum is a **geometric series**: each term is double the last, and the whole sum is 2ᵏ⁺¹ − 1, one less than the next power of two. Since 2ᵏ is less than n, the sum is less than **2n**.
4. **Total:** fewer than n + 2n = **3n** steps for n appends.

So n appends cost O(n), and each append costs at most 3 **on average over the sequence**: O(1) amortised. The run above agrees: 48 is under 3 × 17 = 51.

<Callout kind="analogy">
It's like a train pass. Most days your journey costs nothing extra, and once a month you pay a big fee. Spread the fee across the days it covered, and every journey costs a small, fixed amount.
</Callout>

## Why double? Growing by a fixed amount fails

What if the array grew by 10 slots each time instead of doubling? It would waste less memory. Count the copies for both strategies:

```swift run
// Elements copied over n appends, for two ways of growing a full array
func copies(appends n: Int, grow: (Int) -> Int) -> Int {
    var capacity = 1
    var copied = 0
    for count in 0..<n where count == capacity {
        copied += count
        capacity = grow(capacity)
    }
    return copied
}

for n in [1_000, 10_000, 100_000] {
    let doubling = copies(appends: n) { $0 * 2 }
    let plusTen = copies(appends: n) { $0 + 10 }
    print("n = \(n): doubling copies \(doubling), adding 10 copies \(plusTen)")
}
```

```output
n = 1000: doubling copies 1023, adding 10 copies 49600
n = 10000: doubling copies 16383, adding 10 copies 4996000
n = 100000: doubling copies 131071, adding 10 copies 499960000
```

Doubling stays under 2n. Adding 10 grows a hundredfold each time n grows tenfold: quadratic. Growing by 10 means a growth every 10 appends, each copying everything so far: about 1 + 11 + 21 + … + n, which is roughly n²/20. That's **O(n²)** total, O(n) per append.

The key is that the growth is **proportional** to the current size. Any factor bigger than 1 works: growing by 1.5× also gives O(1) amortised, with a larger constant and less wasted space.

## Amortised is not average case

They sound alike, but they promise different things:

| | Average case | Amortised |
| --- | --- | --- |
| Averages over | possible inputs | the operations in one sequence |
| Needs an assumption about inputs? | yes | no |
| Can an unlucky input break it? | yes | **no** |

Amortised O(1) is a worst-case guarantee for the **whole sequence**: any n appends, on any data, cost O(n) in total. Nothing is probabilistic.

## When the spike matters

Amortised analysis promises a cheap total, not a cheap every time. A single `append` that triggers a growth on a ten-million-element array copies ten million elements. In a batch job that's irrelevant. In an app drawing 60 frames a second, a sudden spike in the middle of an animation can drop a frame.

If you know how big an array will get, `reserveCapacity(_:)` allocates once, up front, and no growth happens afterwards:

```swift run
var numbers: [Int] = []
numbers.reserveCapacity(1_000)
let reserved = numbers.capacity
for value in 0..<1_000 {
    numbers.append(value)
}
print(reserved, numbers.capacity)
```

```output
1020 1020
```

Swift reserved room for at least 1,000 (the allocator rounded it up to 1,020), and all 1,000 appends fit without a single copy.

## Other amortised operations

- `removeLast()` and `popLast()` are O(1). Arrays don't shrink their capacity when you remove elements.
- Inserting into a `Set` or `Dictionary` is O(1) amortised (and on average): they also grow by moving everything into a bigger table when they get too full, which M24 explains.
- `append(contentsOf:)` with k new elements is O(k) amortised.
- `+=` on a `String` is amortised O(length of the piece), as [Building strings efficiently](/dsa/learn/swift-building-strings) showed.

<Callout kind="gotcha" title="Swift gotcha: copy-on-write breaks the guarantee">
The amortised argument assumes the array owns its storage. If another variable shares it, the next `append` must copy the whole array first, as [Copy-on-write explained](/dsa/learn/swift-copy-on-write-intro) showed. Keep a snapshot of a growing array on every pass of a loop, and every append pays O(n): the loop becomes O(n²).
</Callout>
