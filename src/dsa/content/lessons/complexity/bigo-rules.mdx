## Why it matters

You won't prove a c and an n₀ every time you analyse some code. Instead, you'll use a handful of rules that follow from the definition and turn analysis into quick, reliable bookkeeping. They're the rules you apply out loud in an interview: "this loop is O(n), the sort is O(n log n), they run one after the other, so the total is O(n log n)."

## Rule 1: drop constant factors

**O(3n) is O(n). O(n/2) is O(n). O(500) is O(1).**

The definition of Big-O lets you pick any constant c, so a fixed multiplier never changes the class. That's deliberate: a constant factor depends on the machine, the compiler and how you count, while the growth rate doesn't.

You saw this in [When a plain loop is clearer or faster](/dsa/learn/swift-loop-or-hof): four separate passes over an array are about 4n steps, and one combined loop is about n. Both are O(n). The one-pass version might be four times faster, which can be worth having, but it's the same growth class.

## Rule 2: keep only the dominant term

**O(n² + 100n + 5,000) is O(n²).**

When a formula has several terms, the fastest-growing one eventually swamps the rest:

```swift run
for n in [10, 100, 1_000, 10_000] {
    let total = n * n + 100 * n + 5_000
    let share = n * n * 100 / total
    print("n = \(n): total \(total), n² is \(share)% of it")
}
```

```output
n = 10: total 6100, n² is 1% of it
n = 100: total 25000, n² is 40% of it
n = 1000: total 1105000, n² is 90% of it
n = 10000: total 101005000, n² is 99% of it
```

At n = 10 the constant 5,000 is almost everything. By n = 10,000, the n² term is 99% of the work, and the share keeps climbing. Since Big-O is about large n, only n² survives.

Use the ladder from the last lesson to spot the dominant term: n log n beats n, n² beats n log n, 2ⁿ beats every polynomial.

## Rule 3: add steps that run one after another

When one piece of code finishes before the next starts, add their costs. Then Rule 2 usually simplifies the sum:

```swift
func summary(_ numbers: [Int]) -> Int {
    let sorted = numbers.sorted()        // O(n log n)
    var total = 0
    for number in sorted {               // O(n)
        total += number
    }
    return total + sorted[0]             // O(1)
}
```

O(n log n) + O(n) + O(1) = O(n log n + n + 1) = **O(n log n)**. The slowest step dominates.

## Rule 4: multiply steps that run inside each other

When a piece of code runs once for every pass of a loop, multiply. A loop that runs n times with an O(m) body costs O(n · m).

This includes **function calls**. A call is not one step: it costs whatever the called function costs, every time it's called.

```swift
func countShared(_ first: [Int], _ second: [Int]) -> Int {
    var shared = 0
    for value in first {                 // n passes
        if second.contains(value) {      // O(m) each
            shared += 1
        }
    }
    return shared
}
```

n passes, each doing an O(m) `contains`, is **O(n · m)**. If you made `second` a `Set` first, each lookup would be O(1) on average, and the whole function O(n + m): O(m) to build the set, then n cheap lookups.

## Rule 5: different inputs get different letters

`countShared` takes two arrays. Their sizes are unrelated, so they get two letters, n and m. Writing O(n²) would claim they're the same size. Writing O(n) would ignore the second array entirely.

Watch how differently addition and multiplication behave:

```swift run
func sequentialSteps(_ n: Int, _ m: Int) -> Int {
    var steps = 0
    for _ in 0..<n {
        steps += 1
    }
    for _ in 0..<m {
        steps += 1
    }
    return steps
}

func nestedSteps(_ n: Int, _ m: Int) -> Int {
    var steps = 0
    for _ in 0..<n {
        for _ in 0..<m {
            steps += 1
        }
    }
    return steps
}

for (n, m) in [(10, 1_000), (1_000, 10), (1_000, 1_000)] {
    print("n = \(n), m = \(m): one after the other \(sequentialSteps(n, m)), one inside the other \(nestedSteps(n, m))")
}
```

```output
n = 10, m = 1000: one after the other 1010, one inside the other 10000
n = 1000, m = 10: one after the other 1010, one inside the other 10000
n = 1000, m = 1000: one after the other 2000, one inside the other 1000000
```

O(n + m) can't be simplified to either letter, because you don't know which input is bigger. If a problem tells you, say "m is at most 26", then you can: O(n · 26) is O(n).

## Putting the rules together

Analysing a function becomes a walk through its pieces:

```swift
func analyse(_ scores: [Int], _ names: [String]) -> Int {
    let ranked = scores.sorted()               // A: O(n log n)
    var best = 0
    for name in names {                        // B: m passes…
        for score in ranked where score > 90 { // …each O(n)
            best = max(best, score + name.count)
        }
    }
    return best
}
```

1. Name the sizes: n scores, m names.
2. Cost each piece: A is O(n log n). B is m passes of an O(n) loop, so O(n · m) by Rule 4. (`name.count` on a `String` is a hidden loop over the name's characters; with short names we treat it as a small constant.)
3. Add the pieces that run in sequence: O(n log n + n · m).
4. Drop what's dominated: nothing can go, because which term is bigger depends on whether m is bigger than log n.

The answer is **O(n log n + n · m)**. It's fine for an answer to have two terms.

## Quick reads

With practice, the rules become a one-line habit. Try each of these before reading the answer:

- **A loop that prints, then a sort.** O(n) + O(n log n): add them, and the sort dominates. **O(n log n)**.
- **A loop over n words, looking each up in a dictionary.** n passes times O(1) on average: **O(n)**. (If the words are long, hashing each one costs its length, as the last lesson of this module explains.)
- **A grid of r rows and c columns, visiting every cell.** Nested loops over different sizes multiply: **O(r · c)**. If the problem tells you the grid has N cells in total, the same work is O(N). The code didn't change, only the letter, which is why you always say what each letter measures.
- **A halving loop with a fixed inner loop of 100 steps.** 100 × log n, and the 100 is a constant: **O(log n)**.

<Callout kind="gotcha" title="What you can't drop">
Constants **multiply** away, but constants in **exponents** and **bases** don't:

- O(2ⁿ⁺¹) is O(2ⁿ), because 2ⁿ⁺¹ = 2 × 2ⁿ, a constant factor.
- O(2²ⁿ) is **not** O(2ⁿ): 2²ⁿ = 4ⁿ, and 4ⁿ / 2ⁿ = 2ⁿ grows without limit.
- O(n²) is not O(n), even though "it's only a 2".

Bases of **logarithms** are the exception that does drop: log₂ n and log₁₀ n differ only by a constant factor, so both are O(log n). The next lesson shows why.
</Callout>

<Callout kind="tip" title="Constants still matter in real life">
Rule 1 is about classification, not speed. A dictionary lookup and an array read are both O(1), but in a release build on a Mac, ten million dictionary lookups took about 25 times as long as ten million array reads. Use Big-O to pick the right class, then measure if the constants matter.
</Callout>
