## Why it matters

In [Reading constraints to guess the target complexity](/dsa/learn/algo-constraints-to-complexity) you estimated budgets with a rule of thumb: about 10⁸ simple steps per second. Now that you know the growth classes precisely, this lesson builds the full **feasibility table**, works out where each boundary comes from, and covers the things that make the estimate wrong: constant factors, Swift's own costs, debug builds and memory limits. It's the table you'll consult, consciously or not, at the start of every problem from Part III on.

## The table

With a budget of roughly 10⁸ steps (about one second), these are the classes that comfortably fit each input size:

| Largest n | Comfortable class | Steps at the limit | Typical techniques |
| --- | --- | --- | --- |
| 10–11 | O(n!) | 10! ≈ 3.6 × 10⁶ | try every ordering |
| 20–25 | O(2ⁿ), O(2ⁿ · n) | 2²⁰ ≈ 10⁶, × 20 ≈ 2 × 10⁷ | try every subset, backtracking |
| 100 | O(n⁴) | 10⁸ | four nested loops (rare) |
| 500 | O(n³) | 1.25 × 10⁸ | three nested loops, interval DP |
| 5,000 | O(n²) | 2.5 × 10⁷ | all pairs, two nested loops, 2D DP |
| 10⁵ | O(n log n), O(n √n) | up to about 3 × 10⁷ | sorting, heaps, binary search per element |
| 10⁶ | O(n log n), O(n) | 2 × 10⁷ for n log n | sorting, one pass, hashing |
| 10⁸ | O(n), with very simple steps | 10⁸ | a single tight loop |
| 10⁹ to 10¹⁸ | O(√n), O(log n), O(1) | √10¹² = 10⁶, log₂ 10¹⁸ ≈ 60 | maths, binary search, halving |

Use it in both directions. **From constraints to a target:** n ≤ 5,000 says "an O(n²) solution is fine, so don't over-engineer". **From an idea to a verdict:** "my idea is O(n²) and n can be 10⁵, so it's 10¹⁰ steps, about a hundred times over budget."

## Where the boundaries come from

Each boundary is "the largest n for which the class stays within 10⁸ steps". You can compute them. This helper doubles n until the step count passes the budget, then narrows the gap by halving, a binary search, which M28 teaches properly:

```swift run
let budget = 100_000_000

func log2Floor(_ n: Int) -> Int {
    var steps = 0
    var size = n
    while size > 1 {
        size /= 2
        steps += 1
    }
    return steps
}

// The largest n whose step count still fits the budget, found by doubling then halving
func largestN(_ steps: (Int) -> Int) -> Int {
    var low = 1
    var high = 2
    while steps(high) <= budget {
        low = high
        high *= 2
    }
    while high - low > 1 {
        let mid = (low + high) / 2
        if steps(mid) <= budget {
            low = mid
        } else {
            high = mid
        }
    }
    return low
}

func factorial(_ n: Int) -> Int {
    (1...max(1, n)).reduce(1, *)
}

func twoToThe(_ n: Int) -> Int {
    (0..<n).reduce(1) { total, _ in total * 2 }
}

print("n!:", largestN(factorial))
print("2ⁿ:", largestN(twoToThe))
print("n³:", largestN { $0 * $0 * $0 })
print("n²:", largestN { $0 * $0 })
print("n log n:", largestN { $0 * log2Floor($0) })
print("n:", largestN { $0 })
```

```output
n!: 11
2ⁿ: 26
n³: 464
n²: 10000
n log n: 4545454
n: 100000000
```

Problem setters round these down to leave room for constant factors, which is why you see limits like n ≤ 20, n ≤ 500 and n ≤ 5,000 rather than 26, 464 and 10,000. Notice how the gaps shrink at the top: the jump from n² to 2ⁿ takes the limit from ten thousand to twenty-six.

## Why 10⁸, when computers are faster?

A modern processor runs a few billion simple instructions per second. The budget is lower because one "step" in your analysis is usually several instructions, plus a memory access, an array bounds check and an overflow check. Some sample release-build timings on a Mac:

```text title="Sample timings (yours will differ)"
10⁸ steps of: read an array element, add, take a remainder     0.6 s
10⁷ array reads                                                0.005 s
10⁷ dictionary lookups                                          0.11 s
the first loop again, in a debug build                         many seconds
```

So 10⁸ is a fair guess for ordinary steps, generous for the very simplest ones, and optimistic for heavy ones like dictionary lookups, which here cost more than 20 times an array read. Treat anything within a factor of 10 of the budget as "it depends", and measure.

<Callout kind="gotcha" title="Swift gotcha: measure release builds only">
`swift test` and plain `swift run` build in debug mode, which can be 10–100 times slower for loop-heavy code, as [Debug vs release builds](/dsa/learn/swift-release-builds) showed. Online judges usually compile with optimisation. A solution that takes 20 seconds in a debug build may take a fifth of a second in release, so time with `swift run -c release` before concluding anything.
</Callout>

## The constant factors that move the line

Two O(n log n) solutions can differ tenfold in speed. The usual culprits in Swift:

- **Hashing.** `Set` and `Dictionary` operations are O(1) on average, but each one hashes the key and probes a table. When the keys are small integers, an array indexed by the value is much faster.
- **Allocation.** Creating arrays or strings inside a hot loop, such as `Array(text)` or `String(substring)` on every pass, costs memory allocation each time.
- **Strings.** Character-by-character work on a `String` walks Unicode grapheme clusters. Converting once to `[Character]` or `[UInt8]` is far faster, as M08 showed.
- **Copy-on-write surprises.** A write to a shared array silently copies the whole thing.
- **Recursion.** Each call has overhead, and very deep recursion can overflow the stack.

The last lesson of this module goes through these in detail.

## Memory is a budget too

Judges also limit memory, often to 256 MB. An `Int` takes 8 bytes, so that's about 33 million of them in total:

```swift run
print(MemoryLayout<Int>.size, MemoryLayout<Bool>.size, MemoryLayout<Int32>.size)
let megabyte = 1_024 * 1_024
print(256 * megabyte / MemoryLayout<Int>.size)
for n in [1_000, 5_000, 10_000] {
    let bytes = n * n * MemoryLayout<Int>.size
    print("\(n) × \(n) grid of Int: \(bytes / megabyte) MB")
}
```

```output
8 1 4
33554432
1000 × 1000 grid of Int: 7 MB
5000 × 5000 grid of Int: 190 MB
10000 × 10000 grid of Int: 762 MB
```

An n × n table is fine at n = 1,000, tight at n = 5,000 and impossible at n = 10,000, even if the time would be fine. When a table won't fit, use smaller element types (`Int32` is 4 bytes, `Bool` is 1), or keep only the rows you need, a trick you'll use often in dynamic programming. `MemoryLayout`, from [MemoryLayout: size, stride and alignment](/dsa/learn/swift-memory-layout), gives the sizes.

## Three quick readings

- **n ≤ 300, values up to 10⁹.** n³ is 2.7 × 10⁷: three nested loops are fine. Watch for overflow if you multiply values.
- **n ≤ 2 × 10⁵, with 2 × 10⁵ queries.** Each query can't scan the array (4 × 10¹⁰ steps). Prepare something once, in O(n) or O(n log n), so each query is O(1) or O(log n).
- **A single number up to 10¹².** Counting to n is 10¹² steps, far over budget. √n is 10⁶: fine. log n is 40: instant.

**The biggest rise** allows up to 100,000 readings. Before writing anything, work out how many steps the all-pairs approach would take, and what class the table says you should aim for instead.
