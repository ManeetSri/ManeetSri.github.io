## Why it matters

Almost every algorithm you'll meet falls into one of about ten **growth classes**, and they're so different from each other that knowing which class you're in matters far more than any amount of tuning. Turning an O(n²) solution into an O(n log n) one can take a program from hours to a fraction of a second. This lesson walks up the ladder from O(1) to O(n!), with a Swift example and real numbers for each rung, so you can recognise them on sight and feel how fast each one grows.

## The ladder at a glance

Drag the slider to grow n, and switch to the log scale when the fast-growing curves leave the chart:

```visual growthChart
classes: ['O(1)', 'O(log n)', 'O(n)', 'O(n log n)', 'O(n²)', 'O(2ⁿ)', 'O(n!)']
n: 12
max: 64
```

At n = 12 everything looks manageable. By n = 30, O(2ⁿ) is over a billion and O(n!) is beyond anything a computer could ever finish.

From slowest-growing to fastest:

**O(1) → O(log n) → O(√n) → O(n) → O(n log n) → O(n²) → O(n³) → O(2ⁿ) → O(n!)**

Each class eventually grows strictly faster than the one before it, which the deep dive on little-o makes precise.

## O(1): constant

The work doesn't depend on n at all. Reading `numbers[i]`, checking `numbers.count` or `numbers.isEmpty`, appending to an array (amortised, as you'll see later in this module) and looking up a key in a dictionary (on average) are all O(1).

```swift
func isFirstEven(_ numbers: [Int]) -> Bool {
    guard let first = numbers.first else { return false }
    return first % 2 == 0
}
```

An array of ten elements or ten million, it's the same few steps.

## O(log n): logarithmic

The work grows by one step each time n **doubles** (or multiplies by any fixed amount). It comes from repeatedly cutting the problem down by a fraction. Binary search, which you'll build in M28, halves a sorted array until one element is left. Counting the digits of a number divides by 10 each time:

```swift run
func digitCount(_ number: Int) -> Int {
    var n = number
    var digits = 1
    while n >= 10 {
        n /= 10
        digits += 1
    }
    return digits
}

for number in [7, 42, 1_000, 123_456_789, Int.max] {
    print(number, digitCount(number))
}
```

```output
7 1
42 2
1000 4
123456789 9
9223372036854775807 19
```

Even the largest `Int` takes only 19 passes. Logarithms grow so slowly that log₂ of a billion is about 30. If you'd like a refresher on logarithms, M15 covers them; for now, "how many times can I halve n before reaching 1?" is all you need.

**O(√n)** sits between log n and n. It appears when a loop runs while `i * i <= n`, as in checking whether n is prime. You'll meet it in M15.

## O(n): linear

One pass over the input, doing constant work per element: summing, finding the largest, `contains`, `filter`, `map`. Doubling n doubles the work. Linear time is often the best possible, because you usually have to look at every element at least once.

## O(n log n): linearithmic

n times log n. This is the cost of good sorting: Swift's `sorted()` and `sort()` are O(n log n), and so are merge sort and heap sort, which you'll write in Part IV. It's also what you get from a loop of n passes, each doing an O(log n) halving loop.

In practice, O(n log n) behaves almost like O(n). For a million elements, log₂ n is about 20, so it's roughly 20 million steps: a fraction of a second.

## O(n²): quadratic

Every element paired with every other element: two nested loops over the same input. Comparing all pairs, the simple sorts (bubble, selection, insertion) and the `filter { other.contains($0) }` trap from M06 are all O(n²). Fine for a few thousand elements, hopeless for a million.

**O(n³)**, cubic, is three nested loops: all triples of elements, or multiplying two n × n matrices the schoolbook way.

## O(2ⁿ): exponential

The work **doubles** every time n grows by **one**. The classic source is trying every **subset**: each element is either in or out, so n elements have 2 × 2 × … × 2 = 2ⁿ subsets.

```swift run
func subsets(of items: [String]) -> [[String]] {
    guard let first = items.first else {
        return [[]]
    }
    let withoutFirst = subsets(of: Array(items.dropFirst()))
    return withoutFirst + withoutFirst.map { [first] + $0 }
}

for subset in subsets(of: ["a", "b", "c"]) {
    print(subset)
}
print(subsets(of: ["a", "b", "c", "d", "e", "f", "g", "h", "i", "j"]).count)
```

```output
[]
["c"]
["b"]
["b", "c"]
["a"]
["a", "c"]
["a", "b"]
["a", "b", "c"]
1024
```

Three items give 8 subsets; ten give 1,024; thirty would give over a billion. Each subset of the rest appears twice, once without `first` and once with it, which is exactly the doubling. You'll write subset generators properly in the backtracking module.

## O(n!): factorial

n! (n factorial) is n × (n − 1) × … × 2 × 1, the number of ways to put n things in order. Trying every ordering, such as every route through a set of cities, costs O(n!):

```swift run
func orderings(of items: [String]) -> [[String]] {
    if items.count <= 1 {
        return [items]
    }
    var result: [[String]] = []
    for (index, item) in items.enumerated() {
        var rest = items
        rest.remove(at: index)
        for ordering in orderings(of: rest) {
            result.append([item] + ordering)
        }
    }
    return result
}

for ordering in orderings(of: ["a", "b", "c"]) {
    print(ordering.joined())
}
print(orderings(of: ["a", "b", "c", "d", "e", "f", "g"]).count)
```

```output
abc
acb
bac
bca
cab
cba
5040
```

Three items have 6 orderings; seven have 5,040. Factorial grows even faster than 2ⁿ: each extra item multiplies the work by n, not by 2.

## The numbers

A counting experiment puts the classes side by side. Logarithms here are rounded down, counted by halving:

```swift run
func log2Floor(_ n: Int) -> Int {
    var steps = 0
    var size = n
    while size > 1 {
        size /= 2
        steps += 1
    }
    return steps
}

func twoToThe(_ n: Int) -> Int {
    var result = 1
    for _ in 0..<n {
        result *= 2
    }
    return result
}

func factorial(_ n: Int) -> Int {
    var result = 1
    for k in stride(from: 2, through: n, by: 1) {
        result *= k
    }
    return result
}

for n in [5, 10, 15, 20] {
    print("n = \(n): log n ≈ \(log2Floor(n)), n log n ≈ \(n * log2Floor(n)), n² = \(n * n), 2ⁿ = \(twoToThe(n)), n! = \(factorial(n))")
}
```

```output
n = 5: log n ≈ 2, n log n ≈ 10, n² = 25, 2ⁿ = 32, n! = 120
n = 10: log n ≈ 3, n log n ≈ 30, n² = 100, 2ⁿ = 1024, n! = 3628800
n = 15: log n ≈ 3, n log n ≈ 45, n² = 225, 2ⁿ = 32768, n! = 1307674368000
n = 20: log n ≈ 4, n log n ≈ 80, n² = 400, 2ⁿ = 1048576, n! = 2432902008176640000
```

At n = 20 the polynomial classes are still tiny, 2ⁿ is a million, and n! has 19 digits (21! would overflow `Int`). For bigger inputs, here are the exact values, rounded:

| n | log₂ n | n log₂ n | n² | 2ⁿ | n! |
| --- | --- | --- | --- | --- | --- |
| 10 | 3.3 | 33 | 100 | 1,024 | 3.6 × 10⁶ |
| 100 | 6.6 | 664 | 10,000 | 1.3 × 10³⁰ | 9.3 × 10¹⁵⁷ |
| 1,000 | 10 | 9,966 | 10⁶ | 1.1 × 10³⁰¹ | too big to matter |
| 10⁶ | 20 | 2 × 10⁷ | 10¹² | too big to matter | too big to matter |

A rough rule, which the feasibility lesson refines: a computer does about **10⁸ simple steps per second**. So for n = 10⁶, O(n log n) takes about 0.2 seconds, while O(n²) takes 10,000 seconds, nearly three hours. An O(2ⁿ) algorithm at n = 50 would run for about 130 days.

## Polynomial versus exponential

The classes split into two families. **Polynomial** ones, like n, n² and n³, grow by a fixed factor when n *doubles*. **Exponential** ones, like 2ⁿ and n!, grow by a factor when n merely *increases by one*.

That difference decides what faster hardware can do for you. Suppose you get a computer 1,000 times faster:

| Class | Biggest n you can handle in the same time |
| --- | --- |
| O(n) | 1,000 times bigger |
| O(n²) | about 31 times bigger (√1,000 ≈ 31.6) |
| O(2ⁿ) | about **10 more** (2¹⁰ ≈ 1,000) |

A thousandfold speed-up buys an exponential algorithm ten extra elements. Better algorithms beat better hardware.

<Callout kind="gotcha" title="Small n can flip the order">
Growth classes describe large n. For small inputs, constants decide: an O(n²) insertion sort with tiny steps can beat an O(n log n) merge sort on 10 elements, which is why real sorting libraries, Swift's included, switch to insertion sort for short runs. Pick the better class for big inputs, and don't be surprised when a "worse" one wins at n = 10.
</Callout>
