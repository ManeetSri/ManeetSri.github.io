## Why it matters

Time isn't the only thing an algorithm uses up. Memory runs out too: iOS terminates apps that use too much, judges set memory limits, and interviewers love the follow-up "can you do it with O(1) extra space?". **Space complexity** measures memory the same way time complexity measures steps. It has one twist that catches almost everyone: recursion uses memory even when your code never creates an array.

## Measuring memory like steps

Instead of counting steps, count **memory cells**: one `Int`, one `Character`, one reference. Then ask how the number of cells grows with n. The rules from earlier in this module all still apply: drop constants, keep the dominant term, use different letters for different inputs.

```swift
func total(_ numbers: [Int]) -> Int {
    var sum = 0                  // 1 cell
    for number in numbers {      // 1 cell for the current element
        sum += number
    }
    return sum
}
```

Two variables, whatever n is: **O(1)** space.

```swift
func reversedCopy(_ numbers: [Int]) -> [Int] {
    var result: [Int] = []       // grows to n cells
    for number in numbers.reversed() {
        result.append(number)
    }
    return result
}
```

`result` ends up holding n elements: **O(n)** space.

## Input, output and auxiliary space

There are three kinds of memory in play, and it matters which you count:

| Kind | What it is | Usually counted? |
| --- | --- | --- |
| Input | the data you were given | no |
| Auxiliary | extra working memory: variables, sets, copies, the call stack | **yes** |
| Output | the result you return | say so explicitly |

When people say "space complexity", they almost always mean **auxiliary space**: memory *beyond* the input. So `total` uses O(1) auxiliary space, even though its input array is O(n). For a function whose whole job is to build a result, like `reversedCopy`, say it precisely: "O(n) space for the output, O(1) besides".

Some common cases:

| Code | Auxiliary space |
| --- | --- |
| a few counters and indexes | O(1) |
| a 26-slot letter-frequency array | O(1): 26 is a constant |
| a `Set` of values seen so far | O(n) in the worst case, when all are distinct |
| `Array(text)` to index characters | O(n) |
| an n × n grid | O(n²) |

## The recursion stack

Every function call gets a **stack frame** to hold its parameters, local variables and where to return to, as you saw in [A first look at recursion](/dsa/learn/swift-first-recursion) and [Stack vs heap](/dsa/learn/swift-stack-heap). A frame stays alive until its call returns. So a recursive function uses memory proportional to how deep the calls go, even if it never allocates anything.

A counting experiment can track that depth. Here are two recursive ways to add up 1 to n. The first peels off one number per call; the second splits the range in half:

```swift run
var depth = 0
var deepest = 0

func enter() {
    depth += 1
    deepest = max(deepest, depth)
}

// Adds 1 + 2 + … + n by peeling off one number per call
func sumTo(_ n: Int) -> Int {
    enter()
    defer { depth -= 1 }
    if n == 0 {
        return 0
    }
    return n + sumTo(n - 1)
}

// Adds low + … + high by splitting the range in half
func sumRange(_ low: Int, _ high: Int) -> Int {
    enter()
    defer { depth -= 1 }
    if low == high {
        return low
    }
    let mid = (low + high) / 2
    return sumRange(low, mid) + sumRange(mid + 1, high)
}

for n in [8, 100, 1_000] {
    deepest = 0
    let first = sumTo(n)
    let peelingDepth = deepest
    deepest = 0
    let second = sumRange(1, n)
    print("n = \(n): sums \(first) and \(second), deepest stack \(peelingDepth) vs \(deepest)")
}
```

```output
n = 8: sums 36 and 36, deepest stack 9 vs 4
n = 100: sums 5050 and 5050, deepest stack 101 vs 8
n = 1000: sums 500500 and 500500, deepest stack 1001 vs 11
```

What to notice:

- `sumTo(n)` waits on `sumTo(n - 1)`, which waits on `sumTo(n - 2)`, all the way to 0. All n + 1 frames are alive at once: **O(n)** space, where a plain loop would use O(1).
- `sumRange` makes about 2n calls in total, more than `sumTo`, but each call halves the range, so the stack never gets deeper than about log₂ n + 1: **O(log n)** space.
- `defer { depth -= 1 }` runs as each call returns, which is exactly when its frame disappears.

## Time adds up, space is reused

Time counts **every** call that ever happens. Space counts only the frames alive **at the same moment**. When one call returns, its frame's memory is reused by the next. Naive Fibonacci shows the gap at its widest. Step through it and watch the call stack panel: the tree keeps growing, but the stack never gets taller than the deepest path.

```visual recursionTree
fn: fibonacci
n: 5
```

```swift run
var calls = 0
var depth = 0
var deepest = 0

func fibonacci(_ n: Int) -> Int {
    calls += 1
    depth += 1
    deepest = max(deepest, depth)
    defer { depth -= 1 }
    if n < 2 {
        return n
    }
    return fibonacci(n - 1) + fibonacci(n - 2)
}

for n in [5, 10, 20] {
    calls = 0
    deepest = 0
    let value = fibonacci(n)
    print("fibonacci(\(n)) = \(value): \(calls) calls, deepest stack \(deepest)")
}
```

```output
fibonacci(5) = 5: 15 calls, deepest stack 5
fibonacci(10) = 55: 177 calls, deepest stack 10
fibonacci(20) = 6765: 21891 calls, deepest stack 20
```

The calls grow exponentially, roughly O(2ⁿ) time, but the stack only ever holds one path from the top of the tree to the bottom: **O(n) space**.

## Trading space for time

Often you can buy speed with memory, or save memory by spending time. Take "does any value appear twice?":

| Approach | Time | Auxiliary space |
| --- | --- | --- |
| compare every pair with nested loops | O(n²) | O(1) |
| sort a copy, then compare neighbours | O(n log n) | O(n) for the copy |
| keep a `Set` of values seen so far | O(n) on average | O(n) |

None is "the right answer" in general. With a strict memory limit and small n, the first is fine. Usually the `Set` wins, because memory is cheaper than time. Knowing the trade-off is what lets you answer the follow-up questions.

## Space in Swift

- **Passing an array doesn't copy it.** Thanks to [copy-on-write](/dsa/learn/swift-copy-on-write-intro), handing a big array to a function that only reads it costs O(1) extra space. A copy happens only if someone writes to shared storage.
- **Slices share storage.** `numbers[2...]` and `numbers.dropFirst()` are O(1) space views. `Array(slice)` copies, O(k) for k elements.
- **`sorted()` makes a new array**, O(n) extra. `sort()` sorts in place, although the algorithm may use some temporary memory internally.
- **`reversed()` on an array is a view**, O(1). `Array(numbers.reversed())` is a copy, O(n).
- **A `Substring` keeps its whole original string alive**, as [Substring and memory](/dsa/learn/swift-substring) showed: tiny result, large memory.

<Callout kind="gotcha" title="Recursion isn't free">
A recursive function that allocates nothing still uses O(depth) space for its frames. So an "in-place" algorithm that recurses n levels deep isn't O(1) space. Deep enough recursion also crashes with a stack overflow, since the stack is much smaller than the heap; M17 shows Swift's limits and how to avoid them.
</Callout>
