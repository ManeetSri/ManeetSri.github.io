## Why it matters

Some costs go down as well as up. A delivery route can include a leg that pays you, an electric car regains charge going downhill, and a currency exchange can turn 100 pounds into slightly more than 100 pounds' worth of something else. Dijkstra can't handle negative weights, as you saw at the end of [Dijkstra's algorithm](/dsa/learn/sp-dijkstra). Bellman–Ford can, and it does something Dijkstra can't even attempt: it **detects negative cycles**, loops that make a path cheaper every time you go round. Old internet routing protocols (RIP and other distance-vector protocols) are Bellman–Ford spread across routers, and its "at most k edges" variant is a classic interview problem.

## Relax everything, V − 1 times

Bellman–Ford is the simplest algorithm in this module. It doesn't choose an order at all:

1. Set `distance[source] = 0` and everything else to infinity.
2. Repeat V − 1 times: relax **every** edge, in any order.

That's it. Here it is on a directed graph with a negative edge, B → A of −4, with the edges deliberately listed in an unhelpful order:

```swift run
let names = ["S", "A", "B", "C", "D"]
// Directed edges as (from, to, weight), listed in an unhelpful order: A→C, C→D, S→A, S→B, B→A
let edges = [(1, 3, 3), (3, 4, 1), (0, 1, 2), (0, 2, 5), (2, 1, -4)]
let infinity = Int.max / 2

func show(_ distance: [Int]) -> String {
    zip(names, distance).map { "\($0) \($1 == infinity ? "∞" : String($1))" }.joined(separator: ", ")
}

var distance = Array(repeating: infinity, count: names.count)
distance[0] = 0
for round in 1..<names.count {                 // V − 1 rounds
    var changed = false
    for (from, to, weight) in edges {
        guard distance[from] != infinity else { continue }   // can't extend a path that doesn't exist
        if distance[from] + weight < distance[to] {
            distance[to] = distance[from] + weight
            changed = true
        }
    }
    print("after round \(round): \(show(distance))")
    if !changed { break }                      // a quiet round means every distance is final
}
```

```output
after round 1: S 0, A 1, B 5, C ∞, D ∞
after round 2: S 0, A 1, B 5, C 4, D 5
after round 3: S 0, A 1, B 5, C 4, D 5
```

What to notice:

- In round 1, A → C and C → D come first, while A and C are still unreached, so they do nothing. Then S's edges set A to 2 and B to 5, and B → A lowers A to 1.
- Round 2 relaxes A → C and C → D again, now with A known: C gets 4 and D gets 5.
- Round 3 changes nothing, so the loop stops early. Without the `changed` check it would run all 4 rounds, harmlessly.
- These are the true distances, the ones Dijkstra got wrong.

### Why V − 1 rounds are enough

If there's no negative cycle, some shortest path to each vertex is **simple**: it never repeats a vertex, because going round a cycle of weight zero or more can't help. A simple path through V vertices has at most V − 1 edges.

Now the key claim: **after round i, every vertex whose shortest path uses at most i edges has its correct distance.** It's true after round 0 (only the source, with 0 edges). If it's true after round i, take a vertex v whose shortest path uses i + 1 edges, and call its second-to-last vertex u. The path to u uses i edges, so `distance[u]` is already correct, and round i + 1 relaxes the edge u → v, which gives v its correct distance.

So after V − 1 rounds, every shortest path, all of them at most V − 1 edges long, is found. A lucky edge order often finishes sooner, which is why the early exit is worth having.

### Cost

Each round relaxes all E edges, so Bellman–Ford is **O(V · E)** time and O(V) extra memory. That's much slower than Dijkstra's O((V + E) log V): for 10⁴ vertices and 10⁵ edges, about 10⁹ relaxations against a few million heap steps. Use it when you need what only it can do.

## Negative cycles

A **negative cycle** is a loop whose weights add up to less than zero. If one can be reached from the source, there's no shortest path to anything after it: go round once more, and it's cheaper again. The distances head towards minus infinity.

Bellman–Ford detects this with **one extra round**. After V − 1 rounds, every true shortest distance is already found, so if a V-th round still improves anything, the improvement can only come from a cycle that keeps paying.

```swift run
let infinity = Int.max / 2

/// Shortest distances from source, or nil if a negative cycle can be reached from it
func bellmanFord(vertexCount: Int, edges: [(Int, Int, Int)], source: Int) -> [Int]? {
    var distance = Array(repeating: infinity, count: vertexCount)
    distance[source] = 0
    for _ in 1..<vertexCount {
        for (from, to, weight) in edges where distance[from] != infinity {
            distance[to] = min(distance[to], distance[from] + weight)
        }
    }
    // Round V: nothing should improve now. If something does, a cycle keeps paying.
    for (from, to, weight) in edges where distance[from] != infinity {
        if distance[from] + weight < distance[to] {
            return nil
        }
    }
    return distance
}

func report(_ result: [Int]?) {
    if let distance = result {
        print(distance.map { $0 == infinity ? "∞" : String($0) })
    } else {
        print("negative cycle reachable")
    }
}

// 1 → 2 → 3 → 1 is a loop of 2 − 4 + 1 = −1, and 0 leads into it
let looping = [(0, 1, 1), (1, 2, 2), (2, 3, -4), (3, 1, 1), (3, 4, 2)]
report(bellmanFord(vertexCount: 5, edges: looping, source: 0))

// The same loop, but nothing leads into it from 0
let cutOff = [(0, 4, 7), (1, 2, 2), (2, 3, -4), (3, 1, 1)]
report(bellmanFord(vertexCount: 5, edges: cutOff, source: 0))

/// Is there a negative cycle anywhere? Start every vertex at 0, as if a new source had a 0-weight edge to each.
func hasNegativeCycle(vertexCount: Int, edges: [(Int, Int, Int)]) -> Bool {
    var distance = Array(repeating: 0, count: vertexCount)
    for _ in 1..<vertexCount {
        for (from, to, weight) in edges {
            distance[to] = min(distance[to], distance[from] + weight)
        }
    }
    return edges.contains { from, to, weight in distance[from] + weight < distance[to] }
}
print(hasNegativeCycle(vertexCount: 5, edges: cutOff))
```

```output
negative cycle reachable
["0", "∞", "∞", "∞", "7"]
true
```

### Reachable only

Look at the second graph. It has the same negative cycle, but Bellman–Ford from 0 says nothing about it. That's correct for the question it answers: the cycle can't be reached from 0, so it can't affect any distance from 0. The `distance[from] != infinity` guard is what keeps it out. Without the guard, "infinity − 4" would look like a real distance and the unreachable cycle would be reported, or worse, unreachable vertices would get fake finite distances.

If the question is "is there a negative cycle **anywhere**?", start every vertex at 0 instead. That's the same as adding a new source with a 0-weight edge to every vertex, which reaches everything, as `hasNegativeCycle` does.

### Which vertices are affected?

A detected cycle doesn't ruin every distance, only those of vertices **reachable from the cycle**. To mark them: any vertex that still improves in round V is on or after a negative cycle; everything reachable from those vertices (a BFS or DFS) has distance minus infinity, and every other distance is fine. Problems that ask "print `-inf` for the affected vertices" want exactly this.

<Callout kind="note" title="Arbitrage is a negative cycle">
Exchange rates multiply: 1 pound buys 1.17 euros, which buy 1.08 dollars, which buy 0.80 pounds, giving 1.17 × 1.08 × 0.80 ≈ 1.011 pounds. A loop with a product above 1 is free money. Taking logarithms turns products into sums, and using −log(rate) as the weight turns "product above 1" into "sum below 0". So arbitrage detection is negative cycle detection on −log weights, with a small tolerance for floating-point error.
</Callout>

### Finding the cycle itself

Sometimes "there is a negative cycle" isn't enough, and you need the loop: the sequence of trades that makes money, say. Keep a `parent` array, and whenever an edge u → v improves v, set `parent[v] = u`, exactly as for path recovery in Dijkstra.

Now take a vertex v that improved in round V. It's on a negative cycle or somewhere after one, so following its parents leads backwards into the cycle. A chain of V parents in a graph of V vertices must repeat a vertex, so after V steps back you're certainly **on** the cycle. From there, keep following parents until you come back to where you started, then reverse the list (parents point backwards):

```swift
var vertex = improvedInLastRound
for _ in 0..<vertexCount {
    vertex = parent[vertex]                    // walk back until we're inside the loop
}
var cycle = [vertex]
var current = parent[vertex]
while current != vertex {
    cycle.append(current)
    current = parent[current]
}
cycle.reverse()                                // now in the direction of the edges
```

## At most k edges: copy the array each round

The invariant gives a bonus: after round i, Bellman–Ford has found every shortest path **with at most i edges**. That's exactly what "the cheapest flight with at most k stops" asks for. A trip with k stops uses k + 1 flights, so run k + 1 rounds.

But there's a catch. The invariant says "at least as good as the best path with at most i edges". Within one round, the code above relaxes edges **in place**, so an improvement made early in the round can be used by a later edge **in the same round**. One round might then follow a chain of three edges, which is great for plain shortest paths and wrong when edges are limited.

The fix: at the start of each round, take a copy of the distances, and read only from the copy. Every round then extends paths by exactly one edge.

```swift run
let infinity = Int.max / 2
// S=0, A=1, B=2, T=3: a cheap three-edge route S→A→B→T and an expensive direct S→T
let edges = [(0, 1, 1), (1, 2, 1), (2, 3, 1), (0, 3, 10)]

/// Cheapest cost from 0 to 3 using at most `maxEdges` edges
func cheapest(maxEdges: Int, copying: Bool) -> Int {
    var distance = Array(repeating: infinity, count: 4)
    distance[0] = 0
    for _ in 0..<maxEdges {
        let before = copying ? distance : []   // the snapshot from the start of this round
        for (from, to, weight) in edges {
            let start = copying ? before[from] : distance[from]
            if start != infinity && start + weight < distance[to] {
                distance[to] = start + weight
            }
        }
    }
    return distance[3]
}

for k in 1...3 {
    print("at most \(k) edge(s): copying \(cheapest(maxEdges: k, copying: true)), in place \(cheapest(maxEdges: k, copying: false))")
}
```

```output
at most 1 edge(s): copying 10, in place 3
at most 2 edge(s): copying 10, in place 3
at most 3 edge(s): copying 3, in place 3
```

With the edges in this order, the in-place version walks S → A → B → T in a single round and claims a cost of 3 with one edge, which is impossible. The copying version only finds the cheap route once three edges are allowed. Copying costs O(V) per round, so k rounds are O(k · (V + E)), still cheap. You'll use it again later in this module for cheapest flights, and in the problem **Cheapest trip within k stops**.

<Callout kind="gotcha" title="The classic slips">
- **Relaxing from infinity.** With negative weights, `infinity + (-4)` is less than infinity, so an unreached vertex can "improve" its neighbours. Always skip edges whose start is unreached.
- **Stopping after V − 2 rounds or running V rounds by accident.** V − 1 rounds find the distances; the V-th is the check. Off-by-one here either misses paths or reports cycles that aren't there.
- **Updating in place in the k-edges variant.** Read from a copy made at the start of the round.
- **Reporting a cycle the source can't reach**, or missing one when the question is about the whole graph. Decide which question you're answering, and start at the source or at "everyone 0" accordingly.
</Callout>
