## Why it matters

Maps don't send you along the route with the fewest turns; they send you along the quickest one. A delivery app weighs roads by minutes, a network router weighs links by delay, and a game weighs swamp tiles as slower than grass. In each case the edges carry a **cost**, and "shortest" means the cheapest total, not the fewest steps. This module is about finding those cheapest paths, and every algorithm in it is built from one small move called **relaxation**.

## Weighted graphs

In [BFS and unweighted shortest paths](/dsa/learn/gt-bfs) every edge counted as one step. A **weighted graph** gives each edge a number, its **weight**: minutes, kilometres, pounds, metres of climbing. The **weight of a path** is the sum of its edges' weights, and a **shortest path** from `s` to `t` is a path with the smallest total weight.

The adjacency list from [Adjacency matrix, list and edge list](/dsa/learn/graph-representations) stores weights with one change: each entry becomes a `(to, weight)` pair instead of a bare vertex. For an undirected graph, store each edge in both directions.

Shortest-path questions come in three sizes:

| Question | Example | Called |
| --- | --- | --- |
| From one vertex to one other | "home to school" | single pair |
| From one vertex to every vertex | "how far is everything from the depot?" | single source |
| Between every pair | "a distance table for every city" | all pairs |

Single pair is rarely cheaper than single source in the worst case, so most algorithms answer the single-source question and you read off the one distance you need.

## Why BFS isn't enough

BFS finds the path with the fewest **edges**. With weights, fewest edges and cheapest can be different paths. Here's a small town where the main road from home to school takes 10 minutes, but the back streets take 7:

```swift run
// A weighted, undirected graph as an adjacency list: graph[v] holds (to, weight) pairs
let names = ["home", "park", "shop", "school"]
var graph: [[(to: Int, weight: Int)]] = Array(repeating: [], count: names.count)

func addRoad(_ a: Int, _ b: Int, minutes: Int) {
    graph[a].append((b, minutes))
    graph[b].append((a, minutes))             // undirected: store both directions
}
addRoad(0, 3, minutes: 10)                    // home – school, the busy main road
addRoad(0, 1, minutes: 2)
addRoad(1, 2, minutes: 3)
addRoad(2, 3, minutes: 2)

// BFS from home counts edges, and ignores the weights
var hops = Array(repeating: -1, count: names.count)
var minutesOnBFSPath = Array(repeating: 0, count: names.count)
hops[0] = 0
var queue = [0]
var head = 0
while head < queue.count {
    let vertex = queue[head]
    head += 1
    for edge in graph[vertex] where hops[edge.to] == -1 {
        hops[edge.to] = hops[vertex] + 1
        minutesOnBFSPath[edge.to] = minutesOnBFSPath[vertex] + edge.weight
        queue.append(edge.to)
    }
}
for vertex in 1..<names.count {
    print("\(names[vertex]): \(hops[vertex]) edge(s), \(minutesOnBFSPath[vertex]) minutes on BFS's path")
}
print("home → park → shop → school takes", 2 + 3 + 2, "minutes")
```

```output
park: 1 edge(s), 2 minutes on BFS's path
shop: 2 edge(s), 12 minutes on BFS's path
school: 1 edge(s), 10 minutes on BFS's path
home → park → shop → school takes 7 minutes
```

What to notice:

- BFS reaches school in one edge, so it never looks further: its path costs 10 minutes.
- It's worse for the shop. BFS happened to discover it from school, so its path costs 12 minutes, while home → park → shop costs 5.
- BFS's rule "the first time you reach a vertex is the best time" is only true when every edge costs the same. Weights break that rule, so we need a different one.

## Relaxation: the one move every algorithm makes

Keep a table `distance[v]`: the cheapest way to reach `v` **found so far**. At the start, the source has distance 0 and everything else is "infinity", meaning not reached yet. Then look at an edge `u → v` with weight `w` and ask one question:

> Is going to `u` and then along this edge cheaper than the best way to `v` I know?

If `distance[u] + w < distance[v]`, you've found a better path to `v`, so you lower `distance[v]`. That check-and-update is called **relaxing** the edge. The name comes from the picture of a stretched rubber band going slack as the estimate drops towards the truth.

Relaxation has two properties that make everything work:

- **It never makes an estimate wrong.** `distance[v]` only drops when a real path achieves the new value, so it's always the length of some actual path, never below the true shortest distance.
- **Enough of it finds the answer.** If you keep relaxing edges until none of them improves anything, every `distance[v]` is the true shortest distance.

So the simplest possible algorithm is: relax every edge, over and over, until a whole pass changes nothing.

```swift run
let names = ["home", "park", "shop", "school"]
// Each road once per direction, as (from, to, minutes)
let roads = [(0, 3, 10), (3, 0, 10), (0, 1, 2), (1, 0, 2), (1, 2, 3), (2, 1, 3), (2, 3, 2), (3, 2, 2)]

let infinity = Int.max / 2                    // "not reached yet", with room to add to it
var distance = Array(repeating: infinity, count: names.count)
distance[0] = 0

/// Relaxation: does going through `from` give `to` a shorter path?
func relax(_ from: Int, _ to: Int, _ weight: Int) -> Bool {
    if distance[from] + weight < distance[to] {
        distance[to] = distance[from] + weight
        return true
    }
    return false
}

var pass = 0
var changed = true
while changed {
    changed = false
    pass += 1
    for (from, to, weight) in roads {
        if relax(from, to, weight) {
            print("pass \(pass): \(names[to]) improves to \(distance[to]) via \(names[from])")
            changed = true
        }
    }
}
print("passes:", pass, "distances:", distance)
```

```output
pass 1: school improves to 10 via home
pass 1: park improves to 2 via home
pass 1: shop improves to 5 via park
pass 1: school improves to 7 via shop
passes: 2 distances: [0, 2, 5, 7]
```

School first gets 10 through the main road, then drops to 7 when the edge from the shop is relaxed. The second pass changes nothing, which proves the distances are final.

<Callout kind="analogy">
Relaxation is gossip about shortcuts. Each town tells its neighbours, "I'm 5 minutes from home, and the road to you takes 2." If a neighbour's best-known time is worse than 7, it updates. When nobody has news that beats anyone's current time, the gossip stops and every time is the true one.
</Callout>

The rest of this module is about **which edges to relax, and in what order**, so that you do as little work as possible:

| Algorithm | Order of relaxation | Lesson |
| --- | --- | --- |
| 0-1 BFS | a deque, for weights 0 and 1 | 0-1 BFS with a deque |
| Dijkstra | closest vertex first, with a heap | Dijkstra's algorithm |
| Bellman–Ford | every edge, in rounds | Bellman–Ford and negative cycles |
| Floyd–Warshall | through each middle vertex in turn | Floyd–Warshall |

## Infinity, and the overflow trap

The obvious way to write "infinity" is `Int.max`. The trouble starts the moment you relax an edge out of an unreached vertex: `Int.max + weight` doesn't fit in an `Int`.

```swift
let infinity = Int.max
var distance = [0, infinity, infinity]
let weight = 4
if distance[1] + weight < distance[2] {       // Int.max + 4
    distance[2] = distance[1] + weight
}
```

```text title="What you'll see"
Swift runtime failure: arithmetic overflow
```

That's Swift's overflow trap from [Overflow traps and overflow operators](/dsa/learn/swift-overflow). There are three common fixes:

1. **A large sentinel with headroom**, such as `Int.max / 2`. Adding one edge weight to it can't overflow, and it still beats every real distance. Make sure a path can never really cost that much: with up to 10⁵ edges of weight up to 10⁹, the largest real path is 10¹⁴, far below `Int.max / 2`, which is about 4.6 × 10¹⁸.
2. **Skip unreached vertices**: relax `u → v` only when `distance[u] != infinity`. This also stops "infinity minus something" from looking like a real distance when weights are negative, which matters in Bellman–Ford.
3. **Optionals**: `[Int?]`, with `nil` for unreached. The type system then forces you to handle the unreached case:

```swift
var distance: [Int?] = [0, nil, nil]
let (from, to, weight) = (0, 2, 4)
if let start = distance[from], start + weight < (distance[to] ?? Int.max) {
    distance[to] = start + weight
}
```

The lessons that follow use the sentinel `Int.max / 2` with an explicit check where weights can be negative. When the answer for an unreachable vertex is printed or returned, convert it to `-1` or `nil` at the end, so the sentinel never leaks out.

<Callout kind="gotcha" title="Common slips with weighted graphs">
- **Adding an undirected edge once.** Store it as `a → b` and `b → a`, or half your roads become one-way.
- **Mixing up 0-based and 1-based vertices.** Many problems number cities from 1. Either allocate `n + 1` slots or subtract 1 as you read each edge, and be consistent.
- **Returning the sentinel.** A caller who gets `4611686018427387903` back won't know it means "unreachable". Translate it.
- **Using BFS because "it's a shortest path problem".** BFS is right only when every edge has the same weight.
</Callout>
