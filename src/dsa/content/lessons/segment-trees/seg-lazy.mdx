## Why it matters

So far an update changes one item. Real updates often change a whole range: a hotel adds one booking to every night from Friday to Monday, a game deals 30 damage to every unit in a line, a spreadsheet adds 5% to a column. With point updates, a range update over k items costs k × O(log n), which is O(n log n) for a big range. **Lazy propagation** makes range updates O(log n) too, by doing the minimum work now and leaving notes for later. It's the technique that turns the segment tree from a neat structure into one that solves most range problems in contests, and it's built on the recursive version from [Build, query and update](/dsa/learn/seg-build-query-update).

## The problem

Keep an array of n integers under two operations, mixed in any order:

- `add(v, l, r)`: add v to every item in `l...r`;
- `sum(l, r)`: return the sum of `items[l...r]`.

A difference array from [Difference arrays for range updates](/dsa/learn/prefix-difference-array) does range additions in O(1), but reading a sum means rebuilding the prefix sums: O(n). It only works when all the updates come before all the reads. Here they're interleaved.

## The idea: stop at whole blocks, and leave a note

Remember why a query is fast: the range `l...r` splits into O(log n) whole blocks, and the query takes each block's stored sum without looking inside it. Do the same for an update. When `add(v, l, r)` reaches a node that lies wholly inside `l...r`:

1. **Fix the node's own sum straight away.** Every one of its `length` items goes up by v, so its sum goes up by `v × length`. No need to look at the items.
2. **Don't touch anything below it.** Its children's sums are now out of date. Instead of fixing them, leave a note on the node: "everything below me still needs + v". The note is called a **lazy tag** or **pending** value.
3. **Stop.** Don't recurse into it.

The nodes above it are recomputed from their children on the way back up, as in a point update, so every node on the path to the root is correct.

Some time later, another operation may need to go **below** a tagged node, because its range only partly overlaps the node. Before it does, the node **pushes** its tag down one level:

- each child's sum goes up by `tag × child's length`;
- each child's own tag goes up by `tag` (it might have to pass it on later);
- the node's tag goes back to 0.

Now the children are correct, and the operation can carry on into them. Tags move down only as far as something actually needs to look, which is why it's called lazy.

### The invariant

At every moment: **a node's sum is correct, except for tags still waiting on its ancestors.** Pushing before descending clears the ancestors' tags on exactly the path an operation walks, so every node an operation reads or writes is correct when it gets there.

## The code

The struct has a second array, `pending`, beside the sums. Two small helpers do all the lazy work: `apply` adds a value to one whole node (its sum and its tag), and `push` applies a node's tag to both children and clears it.

```swift run
// Lazy propagation: add to a range and sum a range, both in O(log n)
struct RangeAddTree {
    private var sums: [Int]
    private var pending: [Int]                    // added to the whole node, not yet to its children
    private let count: Int

    init(_ items: [Int]) {
        count = items.count
        sums = Array(repeating: 0, count: 4 * items.count)
        pending = Array(repeating: 0, count: 4 * items.count)
        build(items, 1, 0, count - 1)
    }

    /// Adds delta to every item in left...right.
    mutating func add(_ delta: Int, _ left: Int, _ right: Int) {
        add(delta, left, right, 1, 0, count - 1)
    }

    /// The sum of items[left...right].
    mutating func sum(_ left: Int, _ right: Int) -> Int {
        sum(left, right, 1, 0, count - 1)
    }

    private mutating func build(_ items: [Int], _ node: Int, _ low: Int, _ high: Int) {
        if low == high {
            sums[node] = items[low]
            return
        }
        let mid = (low + high) / 2
        build(items, 2 * node, low, mid)
        build(items, 2 * node + 1, mid + 1, high)
        sums[node] = sums[2 * node] + sums[2 * node + 1]
    }

    // Adds delta to every item under node (which covers low...high), and notes it for the children
    private mutating func apply(_ delta: Int, _ node: Int, _ low: Int, _ high: Int) {
        sums[node] += delta * (high - low + 1)
        pending[node] += delta
    }

    // Hands node's pending addition to its two children, before anything goes below node
    private mutating func push(_ node: Int, _ low: Int, _ mid: Int, _ high: Int) {
        if pending[node] == 0 { return }
        apply(pending[node], 2 * node, low, mid)
        apply(pending[node], 2 * node + 1, mid + 1, high)
        pending[node] = 0
    }

    private mutating func add(_ delta: Int, _ left: Int, _ right: Int, _ node: Int, _ low: Int, _ high: Int) {
        if right < low || high < left { return }
        if left <= low && high <= right {
            apply(delta, node, low, high)         // a whole block: stop here
            return
        }
        let mid = (low + high) / 2
        push(node, low, mid, high)                // the children must be up to date first
        add(delta, left, right, 2 * node, low, mid)
        add(delta, left, right, 2 * node + 1, mid + 1, high)
        sums[node] = sums[2 * node] + sums[2 * node + 1]
    }

    private mutating func sum(_ left: Int, _ right: Int, _ node: Int, _ low: Int, _ high: Int) -> Int {
        if right < low || high < left { return 0 }
        if left <= low && high <= right { return sums[node] }
        let mid = (low + high) / 2
        push(node, low, mid, high)
        return sum(left, right, 2 * node, low, mid) + sum(left, right, 2 * node + 1, mid + 1, high)
    }

    /// Prints each level as "sum(+pending)", leaves without tags. Lines up when count is a power of two.
    func show() {
        var first = 1
        while first < 2 * count {
            let isLeafLevel = first >= count
            let level = (first..<(2 * first)).map { node in
                pending[node] == 0 || isLeafLevel ? "\(sums[node])" : "\(sums[node])(+\(pending[node]))"
            }
            print("  " + level.joined(separator: " "))
            first *= 2
        }
    }
}

var tree = RangeAddTree(Array(repeating: 0, count: 8))
print("add 3 to items 2...5:")
tree.add(3, 2, 5)
tree.show()
print("sum of items 3...3:", tree.sum(3, 3))
tree.show()
print("add 1 to everything:")
tree.add(1, 0, 7)
tree.show()
print("sum of items 4...7:", tree.sum(4, 7))
tree.show()
```

Read it from the top:

- **`add(3, 2, 5)`** splits into the whole blocks 2...3 and 4...5. Each sum jumps to 6 and each gets a `+3` tag. Their parents and the root are recomputed: 6, 6 and 12. The leaves are still 0, and that's fine, because nothing has looked at them.
- **`sum(3, 3)`** has to go inside the block 2...3, so that block pushes first: both leaves become 3 and the tag disappears. The block 4...5 keeps its tag, because nothing went inside it.
- **`add(1, 0, 7)`** covers the root entirely. One `apply` at the root, and it's done: O(1) for a range of 8, or of 8 million.
- **`sum(4, 7)`** needs the root's right child, so the root pushes its `+1` to both children (6 + 1 × 4 = 10 each). The block 4...7 is fully covered, so the query stops there, with `+1` still waiting on it. The true items 4 to 7 are 4, 4, 1 and 1, which do sum to 10.

Leaves get tags from `apply` as well. They're harmless, because nothing ever goes below a leaf, which is why `show` leaves them out.

## Why it's still O(log n)

An update visits exactly the same nodes as a query on the same range: at most four per level. `push` and `apply` are O(1) each. So both operations are **O(log n)**, and the extra memory is one more array of 4n. A range update that would have cost k point updates now costs about as much as one.

## Changing the summary: range add, range minimum

The tag stays the same if the tree stores minimums instead of sums; only `apply` changes. When every item in a block goes up by v, its minimum goes up by v, whatever the block's length:

```swift
private mutating func apply(_ delta: Int, _ node: Int) {
    minimums[node] += delta          // every item rose by delta, so the smallest did too
    pending[node] += delta
}
```

That's a tree that can say "add a booking to every night from day 3 to day 9" and "how many rooms are free on the busiest night between day 1 and day 20?". A Fenwick tree, in the next module, can do range additions with range sums, but not range minimums: this is lazy propagation's territory.

## When tags meet tags: composition

A tag is a **pending change**. When a second change lands on a node that already has one, the node must hold one tag meaning "do the old change, then the new one". For additions that's easy: +3 then +2 is +5, and the order doesn't matter. Other changes are less forgiving.

Suppose there are two update kinds: **assign** (set every item in the range to v) and **add**. Now a node's tag is a pair, read as "first set everything to `assign`, if there is one, then add `add`". Two rules keep it right:

- **A new assign wipes out everything older.** Old additions don't matter once every item has been overwritten, so the add part resets to 0.
- **A new add stacks on top.** It goes into the add part, and any pending assign stays, because the assignment happened first.

And pushing must hand the parts down **in the same order**: the assignment first, then the addition.

```swift run
// Two kinds of range update. A node's tag means "set every item to assign (if any), then add".
enum Change {
    case assign(Int)
    case add(Int)
}

struct AssignAddTree {
    private var sums: [Int]
    private var assignTag: [Int?]                 // nil: no pending assignment (0 is a real value)
    private var addTag: [Int]
    private let count: Int

    init(count: Int) {
        self.count = count
        sums = Array(repeating: 0, count: 4 * count)
        assignTag = Array(repeating: nil, count: 4 * count)
        addTag = Array(repeating: 0, count: 4 * count)
    }

    mutating func update(_ change: Change, _ left: Int, _ right: Int) {
        update(change, left, right, 1, 0, count - 1)
    }

    mutating func sum(_ left: Int, _ right: Int) -> Int {
        sum(left, right, 1, 0, count - 1)
    }

    // A newer change on top of whatever the node already has pending
    private mutating func apply(_ change: Change, _ node: Int, _ length: Int) {
        switch change {
        case .assign(let value):
            sums[node] = value * length
            assignTag[node] = value
            addTag[node] = 0                      // an assignment wipes out older additions
        case .add(let delta):
            sums[node] += delta * length
            addTag[node] += delta                 // kept on top of any older assignment
        }
    }

    private mutating func push(_ node: Int, _ low: Int, _ mid: Int, _ high: Int) {
        let leftLength = mid - low + 1, rightLength = high - mid
        if let value = assignTag[node] {          // the older part of the tag goes first
            apply(.assign(value), 2 * node, leftLength)
            apply(.assign(value), 2 * node + 1, rightLength)
            assignTag[node] = nil
        }
        if addTag[node] != 0 {                    // then the newer part
            apply(.add(addTag[node]), 2 * node, leftLength)
            apply(.add(addTag[node]), 2 * node + 1, rightLength)
            addTag[node] = 0
        }
    }

    private mutating func update(_ change: Change, _ left: Int, _ right: Int, _ node: Int, _ low: Int, _ high: Int) {
        if right < low || high < left { return }
        if left <= low && high <= right {
            apply(change, node, high - low + 1)
            return
        }
        let mid = (low + high) / 2
        push(node, low, mid, high)
        update(change, left, right, 2 * node, low, mid)
        update(change, left, right, 2 * node + 1, mid + 1, high)
        sums[node] = sums[2 * node] + sums[2 * node + 1]
    }

    private mutating func sum(_ left: Int, _ right: Int, _ node: Int, _ low: Int, _ high: Int) -> Int {
        if right < low || high < left { return 0 }
        if left <= low && high <= right { return sums[node] }
        let mid = (low + high) / 2
        push(node, low, mid, high)
        return sum(left, right, 2 * node, low, mid) + sum(left, right, 2 * node + 1, mid + 1, high)
    }
}

var tree = AssignAddTree(count: 6)
tree.update(.add(5), 0, 5)                        // [5, 5, 5, 5, 5, 5]
tree.update(.assign(0), 1, 4)                     // [5, 0, 0, 0, 0, 5]
tree.update(.add(2), 3, 5)                        // [5, 0, 0, 2, 2, 7]
print(tree.sum(0, 5), tree.sum(1, 2), tree.sum(3, 4))

// Compare with a plain array over 3,000 random changes and sums
var items = Array(repeating: 0, count: 13)
var checked = AssignAddTree(count: 13)
var state: UInt64 = 42
func next(_ limit: Int) -> Int {
    state = state &* 6364136223846793005 &+ 1442695040888963407
    return Int((state >> 33) % UInt64(limit))
}
var mismatches = 0
for _ in 0..<3_000 {
    let a = next(13), b = next(13)
    let left = min(a, b), right = max(a, b)
    switch next(3) {
    case 0:
        let value = next(7) - 3
        checked.update(.assign(value), left, right)
        for i in left...right { items[i] = value }
    case 1:
        let delta = next(7) - 3
        checked.update(.add(delta), left, right)
        for i in left...right { items[i] += delta }
    default:
        if checked.sum(left, right) != items[left...right].reduce(0, +) { mismatches += 1 }
    }
}
print("mismatches:", mismatches)
```

```output
16 0 4
mismatches: 0
```

Swap the two `if` blocks in `push`, so additions go down before assignments, and the same check reports 321 mismatches. Delete the line that resets `addTag` in the assign case, and it reports 452. Both bugs pass the three hand-written sums at the top. Composition bugs are invisible on small examples, which is why a random comparison against a plain array is part of writing any lazy tree.

### The general recipe

Every lazy segment tree is the same skeleton with four answers filled in:

| Question | Range add, range sum | Assign and add, range sum |
| --- | --- | --- |
| What does a node summarise? | the sum | the sum |
| What's a pending change? | an amount to add | an optional assignment, then an amount to add |
| How does a change alter a summary? | `sum += v × length` | `sum = v × length`, or `sum += v × length` |
| How do two changes combine? | add them | a newer assign replaces everything; a newer add stacks |

If you can answer all four, and a change applied to a whole block can be worked out from the block's summary alone, the operation can be lazy. "Set every item to the larger of itself and v" fails that test for sums: the new sum depends on which items were below v, which the sum doesn't tell you.

## DSAKit's `LazySegmentTree`

DSAKit has a lazy tree for range additions over `Int`, keeping the sum, minimum and maximum of every node:

```swift
import DSAKit

var nights = LazySegmentTree([4, 0, 2, 5])
nights.add(3, to: 1...2)          // [4, 3, 5, 5]
nights.sum(in: 0..<3)             // 12
nights.minimum(in: 1...3)         // 3
nights.maximum(in: ...)           // 5
nights.values                     // [4, 3, 5, 5]
```

Its reads don't push. Instead, a query adds up the tags of the nodes above it on the way down and applies that total to the blocks it uses. The answers are the same, and reading doesn't change the tree, so its queries aren't `mutating`. Updates still push, because they have to recompute the nodes they pass through.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting to push before going down.** If `sum` recurses into a tagged node's children without pushing, it reads stale sums. Push in every function that splits a node: the update and the query.
- **Forgetting to recompute after going down.** The update's last line, `sums[node] = sums[2 * node] + sums[2 * node + 1]`, is as essential here as in a point update.
- **Using 0 to mean "no assignment".** Assigning 0 is a real update. Store the assignment as an `Int?`, as above, or keep a separate `Bool`.
- **Composing tags in the wrong order.** A tag is "old change, then new change". Push the parts down in that order, and make a new assignment clear older additions.
- **Overflow in `v × length`.** 10⁹ added to 10⁵ items is 10¹⁴ per update: fine in `Int`, too big for `Int32`. Many updates on top of each other can still grow large, so estimate the biggest possible sum.
</Callout>

## Practice

**Train seat bookings** is range add with range minimum: a booking succeeds only if every stretch of the journey has enough seats left. **Stacking crates** drops crates onto a line and asks for the tallest stack after each drop, which needs a range **assign** with range maximum, plus coordinate compression, because the positions go up to a billion.
