## Why it matters

You now have a structure that answers almost any range question. That doesn't make it the right tool for every one. A segment tree is more code than the alternatives, and more code means more places for an off-by-one to hide, in an interview or at 2 a.m. in production. This lesson lines up the range-query structures side by side: prefix sums, which you know; the **Fenwick tree**, which you'll build in the next module; the **sparse table** and square-root blocks, which M62 covers; and the segment tree. Then it gives you the questions to ask so you reach for the simplest one that works.

## The contenders, in one paragraph each

**Prefix sums** (M20). Build in O(n), answer a range sum in O(1). They need the data to stay fixed, and an operation that can be undone, like `+` with `-` or `^` with itself.

**Sparse table** (M62). For a fixed array, store the answer for every block whose length is a power of two: about n log₂ n answers. Any range is covered by **two** such blocks, which may overlap. For minimum, maximum and gcd, counting an item twice doesn't matter, so a query is O(1). Operations with that property are called **idempotent**: `min(x, x) == x`. For sums, the overlap double-counts:

```swift run
// Two overlapping blocks cover items 2...6: fine for a minimum, wrong for a sum
let items = [5, 3, 7, 9, 6, 4, 1, 2]
let first = items[2...5]                          // the block of 4 that starts at 2
let second = items[3...6]                         // the block of 4 that ends at 6
print("min:", min(first.min()!, second.min()!), "true:", items[2...6].min()!)
print("sum:", first.reduce(0, +) + second.reduce(0, +), "true:", items[2...6].reduce(0, +))
```

```output
min: 1 true: 1
sum: 46 true: 27
```

**Fenwick tree**, or binary indexed tree (M61). An array of n numbers where slot i holds the sum of a block whose length is i's lowest set bit. Prefix sums and point updates are both O(log n), in loops of about five lines each, with n slots instead of 4n. Like prefix sums, it needs an operation that can be undone to turn prefix answers into range answers. Two of them together handle range additions with range sums.

**Square-root blocks** (M62). Split the array into about √n blocks of √n items and keep one answer per block. Simple and very flexible, at O(√n) per operation: about 300 steps for n = 100,000, against 17 for a tree.

**Segment tree** (this module). Any associative operation with an identity, point or lazy range updates, all O(log n). It's also the only one here that you can **walk down**, steering left or right by what each block contains, and the only one with a persistent form.

## Walking down: something only the tree can do

Because each node summarises a block, a segment tree can answer "where?" questions, not only "how much?". To find the first index whose value is at least x, store maximums and start at the root. If the whole block's maximum is below x, there's no such index in it. Otherwise, go left if the left half's maximum is at least x, and right if not. One path from the root to a leaf: O(log n), with no binary search wrapped around it.

```swift run
// Walking down a maximum tree: the first index whose value is at least x, in O(log n)
let items = [3, 1, 4, 1, 5, 9, 2, 6]
var tree = Array(repeating: Int.min, count: 4 * items.count)

func build(_ node: Int, _ low: Int, _ high: Int) {
    if low == high {
        tree[node] = items[low]
        return
    }
    let mid = (low + high) / 2
    build(2 * node, low, mid)
    build(2 * node + 1, mid + 1, high)
    tree[node] = max(tree[2 * node], tree[2 * node + 1])
}

func descend(_ x: Int, _ node: Int, _ low: Int, _ high: Int) -> Int? {
    if tree[node] < x { return nil }              // nothing in this block is big enough
    if low == high { return low }
    let mid = (low + high) / 2
    if tree[2 * node] >= x {                      // the left half has one, and it comes first
        return descend(x, 2 * node, low, mid)
    }
    return descend(x, 2 * node + 1, mid + 1, high)
}

func firstAtLeast(_ x: Int) -> Int? {
    descend(x, 1, 0, items.count - 1)
}

build(1, 0, items.count - 1)
print(firstAtLeast(4) ?? -1, firstAtLeast(6) ?? -1, firstAtLeast(10) ?? -1)
```

```output
2 5 -1
```

The same walk finds the kth one in a 0/1 array, or the first position where a running total reaches a target. A Fenwick tree can do the running-total version, as M61 shows; neither prefix sums nor a sparse table can do any of them while the data changes.

## Side by side

| | Prefix sums | Sparse table | Fenwick tree | Segment tree |
| --- | --- | --- | --- | --- |
| Build | O(n) | O(n log n) | O(n) | O(n) |
| Range query | O(1) | O(1) | O(log n) | O(log n) |
| Point update | O(n) | rebuild | O(log n) | O(log n) |
| Range update | no | no | O(log n), two trees, sums only | O(log n), lazy |
| Memory | n | n log n | n | 2n to 4n |
| Operations | invertible (`+`, `^`) | idempotent (min, max, gcd) | invertible (`+`, `^`) | any associative |
| Code | 3 lines | 15 lines | 10 lines | 30 to 80 lines |

## Choosing

Ask these questions in order, and stop at the first structure that fits.

1. **Does the data change between queries?** If not, use **prefix sums** for sums and XORs, or a **sparse table** for minimums, maximums and gcds. O(1) queries, no tree needed.
2. **Can you read all the queries before answering any?** If so, an **offline** trick often removes the updates entirely: sort the queries, or process them in a clever order. M62 covers this, and the merge-sort tree problem in this module has an offline solution.
3. **Are the updates to single items, and the queries sums (or XORs)?** Use a **Fenwick tree**. Prefix counts, inversions and order statistics all live here.
4. **Range additions with range sums?** **Two Fenwick trees** or a **lazy segment tree**. The Fenwick version is shorter; the tree version extends further.
5. **Anything else**: range minimums with updates, range assignments, custom summaries, walking down to find a position, old versions? A **segment tree**, with lazy propagation or persistence as needed.

<Callout kind="tip" title="In interviews">
Interviewers rarely expect a lazy segment tree. If a problem needs point updates and range sums, a Fenwick tree, or a plain segment tree, is the expected answer. Mention the trade-offs from the table in a sentence, then write the shortest structure you trust.
</Callout>

<Callout kind="gotcha" title="Common mistakes">
- **A sparse table for sums.** Two overlapping blocks double-count. A sparse table can still do sums by splitting a range into non-overlapping power-of-two blocks, but that's O(log n) per query, and prefix sums do better.
- **A Fenwick tree for range minimums with arbitrary updates.** Minimums can't be undone, so a prefix minimum can't become a range minimum, and lowering a value is the only update a prefix-minimum Fenwick tree can absorb.
- **Reaching for the biggest tool first.** If nothing changes, a sorted array or prefix sums beat any tree.
</Callout>
