## Why it matters

Some range questions aren't about one number per block. "How many orders in this week cost at most £20?" or "what's the median response time between request 4,000 and request 9,000?" depend on the actual values in the range, not on a sum or a minimum. A **merge-sort tree** answers them by storing, in every node, its whole block **sorted**. It's a segment tree whose nodes are the intermediate results of merge sort, and it shows how far the "store a summary per block" idea stretches when the summary is a whole array.

## The problem

You have a fixed array of n integers and many queries, each asking: **how many of `items[l...r]` are at most x?** Sorting the range for each query costs O(k log k) for a range of k items; counting with a loop costs O(k). Either way, 100,000 queries over big ranges is billions of steps.

Prefix sums can't help directly, because x changes from query to query. A segment tree of counts can't either: a block's count of "values at most x" is different for every x.

## Sorted blocks

Store each block's values in sorted order. A leaf holds one value. An internal node holds its two children's arrays **merged**, which is exactly the merge step of [Merge sort, top-down and bottom-up](/dsa/learn/sort-merge). Printed level by level, the tree for `[5, 1, 7, 3, 8, 2, 6, 4]` is merge sort's whole history, with the finished sort at the root.

A query splits `l...r` into O(log n) whole blocks, as always. For each whole block, "how many values are at most x?" is one **upper bound** search in its sorted array, from [Lower bound, upper bound, first and last occurrence](/dsa/learn/bs-bounds): the index of the first value greater than x is the number of values at most x. Add up the counts.

The same tree also answers "what's the kth smallest value in `items[l...r]`?". Counting is monotonic in x: the larger x is, the more values are at most x. So [binary search on the answer](/dsa/learn/bsa-idea) works: search over the sorted values at the root for the first value v with at least k values at most v in the range.

```swift run
// A merge-sort tree: every node keeps its block's values in sorted order
struct MergeSortTree {
    private var sorted: [[Int]]
    private let count: Int

    init(_ items: [Int]) {
        count = items.count
        sorted = Array(repeating: [], count: 4 * items.count)
        build(items, 1, 0, count - 1)
    }

    private mutating func build(_ items: [Int], _ node: Int, _ low: Int, _ high: Int) {
        if low == high {
            sorted[node] = [items[low]]
            return
        }
        let mid = (low + high) / 2
        build(items, 2 * node, low, mid)
        build(items, 2 * node + 1, mid + 1, high)
        sorted[node] = merged(sorted[2 * node], sorted[2 * node + 1])
    }

    // The merge step of merge sort: two sorted arrays into one
    private func merged(_ a: [Int], _ b: [Int]) -> [Int] {
        var result: [Int] = []
        result.reserveCapacity(a.count + b.count)
        var i = 0, j = 0
        while i < a.count && j < b.count {
            if a[i] <= b[j] { result.append(a[i]); i += 1 } else { result.append(b[j]); j += 1 }
        }
        result.append(contentsOf: a[i...])
        result.append(contentsOf: b[j...])
        return result
    }

    /// How many of items[left...right] are at most x.
    func countAtMost(_ x: Int, _ left: Int, _ right: Int) -> Int {
        count(x, left, right, 1, 0, count - 1)
    }

    private func count(_ x: Int, _ left: Int, _ right: Int, _ node: Int, _ low: Int, _ high: Int) -> Int {
        if right < low || high < left { return 0 }
        if left <= low && high <= right { return upperBound(sorted[node], x) }   // a whole block
        let mid = (low + high) / 2
        return count(x, left, right, 2 * node, low, mid) + count(x, left, right, 2 * node + 1, mid + 1, high)
    }

    // The number of values in a sorted array that are at most x: the first index holding more than x
    private func upperBound(_ values: [Int], _ x: Int) -> Int {
        var low = 0, high = values.count
        while low < high {
            let mid = (low + high) / 2
            if values[mid] <= x { low = mid + 1 } else { high = mid }
        }
        return low
    }

    /// The kth smallest (counting from 1) of items[left...right]: binary search over every value
    /// for the first one with at least k values at most it in the range.
    func kthSmallest(_ k: Int, _ left: Int, _ right: Int) -> Int {
        let all = sorted[1]                       // the root holds every value, sorted
        var low = 0, high = all.count - 1
        while low < high {
            let mid = (low + high) / 2
            if countAtMost(all[mid], left, right) >= k { high = mid } else { low = mid + 1 }
        }
        return all[low]
    }

    /// The nodes of one level, for printing.
    func level(_ depth: Int) -> [[Int]] {
        Array(sorted[(1 << depth)..<(2 << depth)])
    }
}

let items = [5, 1, 7, 3, 8, 2, 6, 4]
let tree = MergeSortTree(items)
for depth in 0...3 {
    print(tree.level(depth))
}
print(tree.countAtMost(4, 1, 6))        // 1, 7, 3, 8, 2, 6: three of them are at most 4
print(tree.countAtMost(0, 0, 7), tree.countAtMost(9, 0, 7), tree.countAtMost(5, 2, 2))
print(tree.kthSmallest(1, 1, 6), tree.kthSmallest(3, 1, 6), tree.kthSmallest(6, 1, 6))

// Check every range, every x and every k against sorting the range
var mismatches = 0
for left in 0..<items.count {
    for right in left..<items.count {
        let range = items[left...right].sorted()
        for x in 0...9 where tree.countAtMost(x, left, right) != range.filter({ $0 <= x }).count {
            mismatches += 1
        }
        for k in 1...range.count where tree.kthSmallest(k, left, right) != range[k - 1] {
            mismatches += 1
        }
    }
}
print("mismatches:", mismatches)
```

What to notice:

- `upperBound` uses the half-open search from M28: `low` ends at the first index whose value is greater than x, which is the count of values at most x.
- The count for `1...6` comes from four whole blocks: the leaf `[1]`, the nodes `[3, 7]` and `[2, 8]`, and the leaf `[6]`. Their counts at most 4 are 1, 1, 1 and 0.
- The brute-force check covers every range, every x from 0 to 9 and every k. Small inputs, every case: the habit from the last two lessons.

## The costs

| | Time | Memory |
| --- | --- | --- |
| Build | O(n log n) | O(n log n) |
| Count of values at most x | O(log² n) | |
| Kth smallest | O(log³ n) | |
| Change one item | O(n) | |

Every value appears once per level, in about log₂ n levels, so the tree holds about n log₂ n numbers: 1.7 million for 100,000 items, which is fine. Building merges each level in O(n), so the build is O(n log n), the same as merge sort itself. A count does an O(log n) binary search in each of O(log n) blocks: **O(log² n)**. The kth smallest adds a binary search over the answer on top, so it's O(log³ n), about 5,000 steps for n = 100,000. Still fast, but the next lesson does better.

The weak spot is updates. Changing one item means removing the old value from, and inserting the new value into, a sorted array at every level, and inserting into an array is O(length). The root alone costs O(n). A merge-sort tree is for **static** arrays: build once, query many times.

<Callout kind="note" title="Making it faster">
A count does a fresh binary search in every block, but the blocks are related: each node's array is its children's arrays merged. **Fractional cascading** stores, for each position in a node's array, where that position falls in each child's array. Then one binary search at the top is enough, and each step down follows a stored pointer, making a count O(log n). It's rarely worth the extra code in practice. If the queries can be answered in any order, sorting them by x and using a Fenwick tree, which you'll meet in M61, is simpler still.
</Callout>

<Callout kind="gotcha" title="Common mistakes">
- **Lower bound instead of upper bound.** "At most x" counts values equal to x, so search for the first value **greater** than x. The first value at least x gives "less than x".
- **Merging with `+` and `sorted()`.** `(left + right).sorted()` is correct but costs O(k log k) per node, making the build O(n log² n). Merging two sorted arrays in one pass is O(k).
- **Expecting updates to be cheap.** If items change between queries, you need a different structure: a segment tree of Fenwick trees, or an offline approach.
</Callout>

## Practice

**Values at most x in a range** asks exactly this lesson's question, 100,000 times over 100,000 items, with no updates. A loop over each range is far too slow; a merge-sort tree, or sorting the queries by x and adding values to a Fenwick tree as x grows, both pass.
