## Why it matters

A fitness app shows your total steps for any week you pick, and it also lets you fix yesterday's count when your watch was off. A stock chart shows the lowest price in a window you drag, while new prices arrive every second. Both mix two operations on one array: **change an element**, and **ask about a range**. Prefix sums from M20 answer range questions in O(1), but only while the array stands still. This lesson shows exactly where they break, and the idea that fixes it: the **segment tree**, which the rest of this module builds.

## Two operations, mixed together

Here's the problem in its plainest form. You have an array of n integers and a stream of q operations, each one of:

- **update** `(i, v)`: set `items[i]` to `v`;
- **query** `(l, r)`: return the sum of `items[l...r]`.

The operations arrive one at a time, and each query must be answered before the next operation is read. That last rule matters. If you could read every operation first, you could sometimes batch them cleverly. Here you can't: this is an **online** problem.

You already know two ways to do it, and each is fast at one operation and slow at the other.

**Keep the plain array.** An update writes one slot: O(1). A query adds up the range: O(n) in the worst case.

**Keep prefix sums**, as in [1D prefix sums and range queries](/dsa/learn/prefix-1d). A query is one subtraction: O(1). But changing `items[i]` changes `prefix[i + 1]`, `prefix[i + 2]` and every slot after it, so an update is O(n).

This program counts how many slots each approach touches for the same 1,000 operations: updates near the front of the array, and queries over all of it.

```swift run
// Count the array slots each approach touches for the same mix of operations
let n = 1_000
var plain = Array(repeating: 1, count: n)
var prefix = Array(0...n)                  // prefix[i] = sum of the first i items, all 1s for now
var plainWork = 0
var prefixWork = 0

for step in 0..<1_000 {
    if step % 2 == 0 {
        let index = step / 2                // update: set items[index] to 5
        let change = 5 - plain[index]
        plain[index] = 5
        plainWork += 1
        for slot in (index + 1)...n {       // every later prefix includes items[index]
            prefix[slot] += change
            prefixWork += 1
        }
    } else {
        var total = 0                       // query: the sum of every item
        for value in plain {
            total += value
            plainWork += 1
        }
        let fromPrefix = prefix[n] - prefix[0]
        prefixWork += 2
        precondition(total == fromPrefix)
    }
}
print("plain array:", plainWork, "slots")
print("prefix sums:", prefixWork, "slots")
print("final sum:", prefix[n])
```

```output
plain array: 500500 slots
prefix sums: 376250 slots
final sum: 3000
```

What to notice:

- Both approaches give the same answers (the `precondition` checks every query), and both do hundreds of times more work than there are operations.
- The plain array loses on queries; prefix sums lose on updates. Whichever operation is slow, a mixed stream contains plenty of it.

## The cost table

With n = 100,000 and q = 100,000 mixed operations, the worst case for each approach looks like this. The "about" column uses log₂ 100,000 ≈ 17.

| Approach | Update | Query | q operations, about |
| --- | --- | --- | --- |
| Plain array | O(1) | O(n) | 10¹⁰ |
| Prefix sums | O(n) | O(1) | 10¹⁰ |
| Square-root blocks (M62) | O(1) | O(√n) | 3 × 10⁷ |
| Segment tree or Fenwick tree | O(log n) | O(log n) | 3 × 10⁶ |

Ten billion steps takes many seconds even in optimised Swift; three million is instant. The goal is to make **both** operations cheap, accepting O(log n) for each instead of O(1) for one and O(n) for the other.

## The idea: precompute sums of blocks

Prefix sums store n "long" sums, each starting at index 0. One change ruins many of them because they overlap so much. Instead, store sums of **blocks** chosen so that:

1. every item lies in only a few blocks, so an update rewrites only a few sums;
2. every range is made of only a few whole blocks, so a query adds only a few sums.

Halving does both. Take the whole array as one block, split it into two halves, split each half again, and keep going down to single items. This program builds those levels for 8 items:

```swift run
// Sums of blocks: the whole array, its halves, their halves, and so on down to single items
let items = [5, 3, 7, 9, 6, 4, 1, 2]
var levels = [items]
while levels.last!.count > 1 {
    let below = levels.last!
    let above = stride(from: 0, to: below.count, by: 2).map { below[$0] + below[$0 + 1] }
    levels.append(above)
}
for level in levels.reversed() {
    print("blocks of \(items.count / level.count):", level)
}
```

```output
blocks of 8: [37]
blocks of 4: [24, 13]
blocks of 2: [8, 16, 10, 3]
blocks of 1: [5, 3, 7, 9, 6, 4, 1, 2]
```

Now check both promises.

**A query uses a few whole blocks.** The sum of `items[2...6]` is the block of 2 covering indexes 2–3 (16), plus the block covering 4–5 (10), plus the single item at 6 (1): 16 + 10 + 1 = 27. Three additions instead of five. In general, any range splits into at most two blocks per level, so a query adds about 2 log₂ n sums.

**An update touches one block per level.** Changing `items[3]` from 9 to 1 changes the blocks covering 2–3, 0–3 and 0–7, plus the item itself: four sums, which is log₂ 8 + 1. For 100,000 items, that's 18.

Drawn as a tree, with each block's two halves as its children, this is a **segment tree**: a binary tree in which every node stores the answer for one contiguous segment of the array. It has n leaves and n − 1 internal nodes, and its height is about log₂ n, just like the complete trees of [A complete tree in an array](/dsa/learn/heap-array-index). The next lesson stores it in an array the same way a heap is stored.

<Callout kind="analogy" title="A company's sales reports">
A national sales director doesn't add up every shop's till receipts. Each shop reports a total to its region, each region reports to its country, and the director reads a handful of totals. When one shop corrects a figure, only that shop's region, country and the national total need recalculating, not every report in the company.
</Callout>

## More than sums

Prefix sums depend on subtraction: the sum of `items[l...r]` is one long sum minus another. That's why they can't do minimums, as [Prefix XOR](/dsa/learn/prefix-xor) showed: you can't "un-min" a value.

Blocks never subtract. A block's answer is built by **combining** its two halves' answers, and a query combines a few blocks. So any operation where two neighbouring answers combine into the answer for both works: sum, minimum, maximum, greatest common divisor, product, bitwise AND or OR, even "the smallest value and where it is". The lesson after next makes that precise and builds a generic tree that takes the combining function as a closure.

<Callout kind="gotcha" title="Common mistakes">
- **Reaching for a segment tree when nothing changes.** If the array is fixed, prefix sums (for sums) or a sparse table (for minimums, in M62) are simpler and answer in O(1). The tree earns its place only when updates and queries are mixed.
- **Forgetting the overflow check.** Block sums near the root add up the whole array. 100,000 items of up to 10⁹ reach 10¹⁴, fine in a 64-bit `Int` but not in an `Int32`.
</Callout>

- id: segment-tree-blocks
  front: "What does each node of a segment tree store?"
  back: "The answer (a sum, minimum and so on) for one contiguous block of the array. The root covers everything; each node's children cover its two halves."
- id: segment-tree-costs
  front: "Why are segment tree updates and queries both O(log n)?"
  back: "Each item lies in one block per level, so an update recomputes about log n blocks. Any range splits into at most two whole blocks per level, so a query combines about 2 log n."
- id: combine-not-subtract
  front: "Why can a segment tree answer range minimums when prefix sums can't?"
  back: "It only ever combines the answers of neighbouring blocks. It never needs to undo a combination, as prefix sums' subtraction does."
