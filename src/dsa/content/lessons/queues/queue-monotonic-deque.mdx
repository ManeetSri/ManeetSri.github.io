## Why it matters

"What's the largest value in each window of k consecutive values?" A stock app shows the highest price in every 30-day window. A fitness app shows peak heart rate over each rolling minute. A server dashboard plots the worst response time over the last 100 requests. Recomputing each window's maximum from scratch costs O(k) per window. A **monotonic deque** keeps the answer ready as the window slides, for O(n) in total. It's the deque's signature algorithm, a close cousin of the monotonic stack from [Monotonic stack: next greater element](/dsa/learn/stack-monotonic-intro), and one of the classic hard interview problems.

## The problem and the brute force

Given an array of values and a window size k, return the maximum of every window: values 0 to k − 1, then 1 to k, and so on. There are n − k + 1 windows.

The brute force takes each window's `max()`:

```swift run
func windowMaxima(_ values: [Int], k: Int) -> [Int] {
    var result: [Int] = []
    for start in 0...(values.count - k) {
        result.append(values[start..<(start + k)].max()!)
    }
    return result
}

print(windowMaxima([4, 2, 12, 3, 1, 8, 5], k: 3))
```

```output
[12, 12, 12, 8, 8]
```

Each window costs k − 1 comparisons, so the total is about (n − k + 1) × k: **O(n · k)**. For a year of per-minute readings (n ≈ 500,000) and a one-day window (k = 1,440), that's over 700 million comparisons. The sliding-window trick from [Fixed-size windows](/dsa/learn/sw-fixed) (add the value coming in, subtract the value going out) doesn't work for a maximum: when the maximum leaves the window, you can't tell what the next largest was without looking again.

## The key observation

Suppose the window holds a 3, and then a 9 arrives. The 3 is older, so it leaves the window **before** the 9 does. Until then, the 9 is in the window too, and it's bigger. So the 3 can **never** be the maximum of any window from now on. You can forget it.

That's the whole idea. When a new value arrives, throw away every older value that's no bigger than it. What survives, read from oldest to newest, is **strictly decreasing**: each value is smaller than every value older than it. (If one weren't, the newer, bigger value would have thrown it out on arrival.) A list kept in sorted order like this is called **monotonic**.

And a decreasing list has its largest value at the front. So the maximum of the current window is always the **oldest survivor**, as long as that survivor is still inside the window.

<Callout kind="analogy">
Think of a queue for a talent show where a judge picks the tallest contestant still waiting. Whenever someone joins, everyone ahead of them who's no taller goes home: they'll leave the queue first, and the newcomer will always outshine them. The person at the front is always the tallest left, until their turn runs out.
</Callout>

## The algorithm

The survivors sit in a deque. It holds **indexes**, not values, so you can tell when the front has slid out of the window. For each index i:

1. **Expire the front.** If the front index is i − k or earlier, it's no longer in the window. Pop it from the front.
2. **Pop smaller values from the back.** While the value at the back index is ≤ `values[i]`, pop it from the back.
3. **Push i** onto the back.
4. **Record the answer.** Once i ≥ k − 1, the first full window has formed, and its maximum is `values[front]`.

Steps 1 and 4 use the front, and steps 2 and 3 use the back: a deque. Step through the example, `[4, 2, 12, 3, 1, 8, 5]` with k = 3. The deque is listed front first, as index→value:

```visual arrayTrace

```

When 12 arrives, both 2 and 4 are popped from the back: neither can ever be a maximum again. When 8 arrives, 12 has expired (it was three places back), so it's popped from the front, and then 1 and 3 are popped from the back.

## The code

The deque only ever **adds** at the back, so an array with a head index (from [A queue with a head index](/dsa/learn/queue-head-index)) can play its part: `head += 1` pops the front, and `removeLast()` pops the back.

```swift run
func windowMaxima(_ values: [Int], k: Int) -> [Int] {
    var result: [Int] = []
    var window: [Int] = []       // indexes; their values decrease from window[head] to the end
    var head = 0                 // the front of the deque: we only ever add at the back

    for i in values.indices {
        // 1. The front index leaves the window once it's k or more places behind i
        if head < window.count && window[head] <= i - k {
            head += 1
        }
        // 2. Older values that are no bigger than the new one can never be a maximum again
        while head < window.count && values[window[window.count - 1]] <= values[i] {
            window.removeLast()
        }
        // 3. The new index joins at the back
        window.append(i)
        // 4. Once the first window is complete, its maximum is at the front
        if i >= k - 1 {
            result.append(values[window[head]])
        }
        let kept = window[head...].map { values[$0] }
        print("i \(i), value \(values[i]): deque values \(kept)")
    }
    return result
}

print(windowMaxima([4, 2, 12, 3, 1, 8, 5], k: 3))
```

```output
i 0, value 4: deque values [4]
i 1, value 2: deque values [4, 2]
i 2, value 12: deque values [12]
i 3, value 3: deque values [12, 3]
i 4, value 1: deque values [12, 3, 1]
i 5, value 8: deque values [8]
i 6, value 5: deque values [8, 5]
[12, 12, 12, 8, 8]
```

What to notice:

- After every step, the deque's values are strictly decreasing, and the front is the window's maximum.
- Step 1 uses `if`, not `while`: the window moves one place per step, so at most one index can expire. (A `while` would also be correct.)
- Step 2 checks `head < window.count` so it never pops past the front. Indexes before `head` are dead, exactly as in the head-index queue.
- The dead prefix makes this version use O(n) memory. DSAKit's `Deque` keeps only the survivors, O(k):

```swift
import DSAKit

func windowMaxima(_ values: [Int], k: Int) -> [Int] {
    var result: [Int] = []
    var window = Deque<Int>()                    // indexes, values decreasing front to back
    for i in values.indices {
        if let front = window.first, front <= i - k {
            window.popFirst()
        }
        while let back = window.last, values[back] <= values[i] {
            window.popLast()
        }
        window.append(i)
        if i >= k - 1 {
            result.append(values[window.first!])
        }
    }
    return result
}
```

## Why it's O(n)

Step 2's `while` loop can pop many indexes at once, so a single step can cost O(k). But follow one index through its life, as you did with the two-stack queue: it's **pushed once**, and **popped at most once**, either from the back (a bigger value arrived) or from the front (it expired). Never both, never twice.

So over the whole array there are at most n pushes and n pops: at most 2n deque operations, plus one failed comparison per step to stop each `while` loop. That's **O(n)** in total, whatever k is. Count it:

```swift run
// Comparisons made by the brute force and by the monotonic deque
func bruteForceComparisons(_ values: [Int], k: Int) -> Int {
    var comparisons = 0
    for start in 0...(values.count - k) {
        var best = values[start]
        for i in (start + 1)..<(start + k) {
            comparisons += 1
            if values[i] > best { best = values[i] }
        }
    }
    return comparisons
}

func dequeComparisons(_ values: [Int], k: Int) -> (comparisons: Int, removals: Int) {
    var window: [Int] = []
    var head = 0
    var comparisons = 0
    var removals = 0
    for i in values.indices {
        if head < window.count && window[head] <= i - k {
            head += 1
            removals += 1
        }
        while head < window.count {
            comparisons += 1
            if values[window[window.count - 1]] <= values[i] {
                window.removeLast()
                removals += 1
            } else {
                break
            }
        }
        window.append(i)
    }
    return (comparisons, removals)
}

let values = (0..<5_000).map { ($0 * 7_919) % 1_000 }   // varied, but the same every run
for k in [10, 100, 1_000] {
    let deque = dequeComparisons(values, k: k)
    print("k = \(k): brute force \(bruteForceComparisons(values, k: k)), deque \(deque.comparisons) comparisons and \(deque.removals) removals")
}
```

```output
k = 10: brute force 44919, deque 8231 comparisons and 4990 removals
k = 100: brute force 485199, deque 9873 comparisons and 4987 removals
k = 1000: brute force 3996999, deque 9965 comparisons and 4985 removals
```

The brute force grows with k. The deque stays under 2n = 10,000 comparisons and under n = 5,000 removals however large the window gets: each of the 5,000 indexes is removed at most once.

## Indexes, duplicates and variations

**Why indexes and not values?** With values alone, you can't tell whether the front has left the window. Some solutions store values and pop the front when the outgoing value equals it, but that needs care with duplicates. Indexes avoid the question.

**`<=` or `<` in step 2?** Both are correct with indexes. Popping equal values (`<=`) keeps the deque shorter, and the newer copy lasts longer anyway. With `<`, the deque holds equal values side by side, and the values are non-increasing rather than strictly decreasing.

**Minimum instead of maximum.** Flip the comparison: pop from the back while the back value is ≥ the new one. The deque becomes increasing, and its front is the minimum.

**Bigger cousins.** "The longest stretch where the maximum and minimum differ by at most d" keeps one decreasing and one increasing deque inside a variable-size window. "The shortest subarray with sum at least t", when values can be negative, runs a monotonic deque over prefix sums. Both use exactly the idea in this lesson: throw away what can never matter, and the survivors stay sorted.

<Callout kind="gotcha" title="The two classic slips">
**Forgetting to expire the front.** Without step 1, an old maximum stays at the front long after it has left the window, and every later answer is too big. In the example, 12 would be reported for every window.

**Recording too early.** The first k − 1 steps don't complete a window. Only start recording once `i >= k - 1`, and expect `values.count - k + 1` answers.
</Callout>
