## Why it matters

Here's a second fast queue, built from nothing but two stacks. It's one of the most-asked design questions in interviews, because it tests whether you understand amortised cost rather than whether you've memorised code. It's also genuinely useful: it never keeps dead slots, it releases each item the moment it leaves, and it's how languages with immutable lists build their queues. And on a Swift array, a stack's `append` and `popLast()` are about as cheap as operations get.

## Two stacks, one queue

A stack only gives you its newest item. A queue needs its oldest. The trick is that **pouring one stack into another reverses it**: pop everything off stack A and push it onto stack B, and the item that was at the bottom of A ends up on top of B.

So the queue keeps two stacks:

- `inbox` takes every new item. Its top (the end of the array) is the newest item.
- `outbox` hands items out. Its top is the **oldest** item.

**Enqueue** pushes onto `inbox`. **Dequeue** pops from `outbox`. If `outbox` is empty, first pour every item from `inbox` into it, which turns the oldest item into the top.

```swift run
struct TwoStackQueue<Element> {
    private var inbox: [Element] = []     // newest on top (the end)
    private var outbox: [Element] = []    // oldest on top (the end)

    var count: Int { inbox.count + outbox.count }
    var isEmpty: Bool { inbox.isEmpty && outbox.isEmpty }

    mutating func enqueue(_ element: Element) {
        inbox.append(element)
    }

    mutating func dequeue() -> Element? {
        if outbox.isEmpty {
            while let element = inbox.popLast() {
                outbox.append(element)    // pouring reverses the order
            }
        }
        return outbox.popLast()
    }

    func peek() -> Element? {
        outbox.last ?? inbox.first
    }

    var debugState: String { "inbox \(inbox), outbox \(outbox)" }
}

var queue = TwoStackQueue<Int>()
for value in 1...3 { queue.enqueue(value) }
print("enqueue 1, 2, 3 →", queue.debugState)
print("dequeue", queue.dequeue() ?? 0, "→", queue.debugState)
queue.enqueue(4)
print("enqueue 4 →", queue.debugState)
print("peek", queue.peek() ?? 0, "count", queue.count)
print("dequeue", queue.dequeue() ?? 0, "→", queue.debugState)
print("dequeue", queue.dequeue() ?? 0, "→", queue.debugState)
print("dequeue", queue.dequeue() ?? 0, "→", queue.debugState)
```

```output
enqueue 1, 2, 3 → inbox [1, 2, 3], outbox []
dequeue 1 → inbox [], outbox [3, 2]
enqueue 4 → inbox [4], outbox [3, 2]
peek 2 count 3
dequeue 2 → inbox [4], outbox [3]
dequeue 3 → inbox [4], outbox []
dequeue 4 → inbox [], outbox []
```

Follow the first dequeue. `outbox` was empty, so 3, 2 and 1 were popped from `inbox` and pushed onto `outbox` in that order, leaving 1 on top, and 1 came out. Then 4 arrived in `inbox` while 2 and 3 were still waiting in `outbox`, and the next two dequeues served 2 and 3 **without pouring**. Only when `outbox` ran dry did 4 move across.

What to notice:

- `peek` looks at the top of `outbox`, the oldest item, if there is one. Otherwise the oldest item is at the *bottom* of `inbox`, which is `inbox.first`: an O(1) read on an array.
- `dequeue` on an empty queue pours nothing and returns `outbox.popLast()`, which is `nil`. No special case needed.

## The one rule: pour only when the outbox is empty

Everything in `outbox` is older than everything in `inbox`, because it arrived earlier. That's the invariant that makes the order right. If you poured while `outbox` still had items, newer items would land on top of older ones and come out first.

Pouring only when `outbox` is empty keeps the invariant: the items you pour are the only ones left, and pouring puts the oldest of them on top.

## Counting the work

A single dequeue can be expensive: if a thousand items are waiting in `inbox`, the dequeue that pours does two thousand stack operations. But follow **one item** through its whole life. It's:

1. pushed onto `inbox` once (by `enqueue`);
2. popped from `inbox` and pushed onto `outbox` **at most once** (items never go back);
3. popped from `outbox` once (by `dequeue`).

That's at most four stack operations per item, ever. Count them over a long run with a mix of enqueues and dequeues:

```swift run
// Counts every stack push and pop that the two-stack queue makes
struct CountingQueue {
    var inbox: [Int] = []
    var outbox: [Int] = []
    var stackOperations = 0
    var mostInOneCall = 0

    mutating func enqueue(_ element: Int) {
        inbox.append(element)
        stackOperations += 1
    }

    mutating func dequeue() -> Int? {
        var thisCall = 0
        if outbox.isEmpty {
            while let element = inbox.popLast() {
                outbox.append(element)
                thisCall += 2                 // one pop and one push
            }
        }
        let front = outbox.popLast()
        if front != nil { thisCall += 1 }
        stackOperations += thisCall
        mostInOneCall = max(mostInOneCall, thisCall)
        return front
    }
}

for n in [1_000, 10_000, 100_000] {
    var queue = CountingQueue()
    for value in 1...n {
        queue.enqueue(value)
        if value % 3 != 0 {
            _ = queue.dequeue()               // dequeue after two of every three
        }
    }
    while queue.dequeue() != nil {}           // then drain what's left
    print("\(n) items: \(queue.stackOperations) stack operations, \(queue.stackOperations / n) per item, at most \(queue.mostInOneCall) in one call")
}
```

```output
1000 items: 4000 stack operations, 4 per item, at most 583 in one call
10000 items: 40000 stack operations, 4 per item, at most 5395 in one call
100000 items: 400000 stack operations, 4 per item, at most 61447 in one call
```

Exactly four operations per item, while the most expensive single call grows with n. This is the [aggregate method](/dsa/learn/bigo-amortised) again: add up the total work for the whole sequence (at most 4n for n items), then divide by the number of operations. Any sequence of m enqueues and dequeues costs O(m), so each is **O(1) amortised**, even though one unlucky dequeue is O(n).

The argument depends on items never going back to `inbox`. If they could bounce between the stacks, the "at most once" in step 2 would be false, and so would the bound.

<Callout kind="gotcha" title="The pour-every-time trap">
A common first attempt moves everything to `outbox` for each dequeue and back to `inbox` afterwards, so that `inbox` is "always the real queue". It gives the right answers, but every dequeue moves every item twice: O(n) per operation and O(n²) for n operations. Leave items in `outbox` until it's empty.
</Callout>

## Head index or two stacks?

Both are amortised O(1). They differ in the details:

| | Head index with compaction | Two stacks |
| --- | --- | --- |
| Memory | up to about 2× the items waiting | exactly the items waiting, in two arrays |
| Dequeued objects | freed at the next compaction or reset | freed straight away |
| Worst single dequeue | O(n), when it compacts | O(n), when it pours |
| `peek` | `items[head]` | `outbox.last ?? inbox.first` |
| Iterating front to back | one slice | `outbox` reversed, then `inbox` |

In practice either is fine. DSAKit's `Queue` uses a head index because iterating it is simpler; the two-stack queue is the one interviewers ask for.

## Practice

**A queue from two stacks** asks you to build exactly this, as a generic type with `enqueue`, `dequeue`, `peek`, `count` and `isEmpty`, and to keep every operation amortised O(1). The tests include 200,000 mixed operations, so the pour-every-time version will be noticeably slow.

  front: "When must a two-stack queue pour the inbox into the outbox, and why only then?"
  back: "Only when the outbox is empty. Everything in the outbox is older than everything in the inbox; pouring on top of it would put newer items above older ones."

  front: "Why is the two-stack queue O(1) amortised?"
  back: "Each item is pushed onto the inbox once, moved to the outbox at most once and popped once: at most 4 stack operations per item over its whole life."

  front: "Where is the front item of a two-stack queue?"
  back: "On top of the outbox (`outbox.last`) if the outbox isn't empty, otherwise at the bottom of the inbox (`inbox.first`)."
