## Why it matters

A **deque** (say "deck"), short for double-ended queue, adds and removes at **both** ends in O(1). It's a queue and a stack at once, and some of the neatest algorithms need exactly that: the sliding window maximum later in this module, an undo history that drops its oldest entry when it gets too long, and graph searches in Part VI that put some items at the front and others at the back. Swift's standard library doesn't include one. In this lesson you build `Deque<Element>` on a growable ring buffer, make it a proper Swift collection, and test it the way library authors do.

## What a deque does

| Operation | Meaning | Target cost |
| --- | --- | --- |
| `append(x)` | add at the back | O(1) amortised |
| `prepend(x)` | add at the front | O(1) amortised |
| `popFirst()` | remove from the front, or `nil` | O(1) |
| `popLast()` | remove from the back, or `nil` | O(1) |
| `first`, `last`, `deque[i]` | read without removing | O(1) |

Step through a few operations. Items can arrive and leave at either end:

```visual stackQueue
kind: deque
operations: ["pushBack 4", "pushBack 7", "pushFront 1", "pushFront 9", "popBack", "popFront", "pushBack 3"]
```

(The visualiser calls them `pushBack`, `pushFront`, `popBack` and `popFront`. Swift code, including the standard library's collections, usually says `append`, `prepend`, `popLast` and `popFirst`.)

None of the earlier queues extend neatly. An array with a head index can't prepend without shifting. Two stacks can't pop from the back cheaply in every case. A linked list would need links in both directions. But a ring buffer already wraps both ways: stepping `head` **back** one slot makes room at the front as cheaply as writing past the back makes room there. It only lacks one thing: the ability to grow.

## The design

Keep the ring buffer's three pieces:

- `slots`, an array of `Element?` (empty slots are `nil`);
- `head`, the slot of the front element;
- `count`, the number of elements.

The element at position i from the front lives in slot `(head + i) % capacity`, where the capacity is `slots.count`. Then:

- **append** writes into slot `(head + count) % capacity`, right after the back;
- **prepend** moves `head` one step back, `(head - 1 + capacity) % capacity`, and writes there (the `+ capacity` matters: Swift's `%` keeps the sign, as the ring buffer lesson showed);
- **popFirst** clears slot `head` and moves `head` one step forward;
- **popLast** clears the slot of position `count - 1`.

### Growing a ring

When every slot is full, the deque needs more. With an array you'd append and let it grow. With a ring, that doesn't work: the elements may wrap round the end, and a new slot added at the end of the array would land **in the middle** of the queue's order.

So growing is a fresh start: allocate twice as many slots, copy the elements across **in queue order** into slots 0, 1, 2 and so on, and set `head` back to 0. That costs O(n), but it only happens when the size doubles, so by the [aggregate argument for arrays](/dsa/learn/bigo-amortised), appends and prepends are O(1) amortised.

## The code

Here's the whole thing, with a `picture` that shows the slots. It starts with 4 slots so the wrap and the growth both happen quickly:

```swift run
struct Deque<Element> {
    private var slots: [Element?] = []
    private var head = 0                     // the slot of the front element
    private(set) var count = 0

    // The slot holding position `offset` from the front
    private func slot(_ offset: Int) -> Int {
        (head + offset) % slots.count
    }

    // Doubles the slots, copying the elements across in order so the front lands in slot 0
    private mutating func grow() {
        var bigger = [Element?](repeating: nil, count: Swift.max(4, slots.count * 2))
        for offset in 0..<count {
            bigger[offset] = slots[slot(offset)]
        }
        slots = bigger
        head = 0
    }

    mutating func append(_ element: Element) {
        if count == slots.count { grow() }
        slots[slot(count)] = element
        count += 1
    }

    mutating func prepend(_ element: Element) {
        if count == slots.count { grow() }
        head = (head - 1 + slots.count) % slots.count    // one step back, wrapping
        slots[head] = element
        count += 1
    }

    mutating func popFirst() -> Element? {
        guard count > 0 else { return nil }
        let element = slots[head]
        slots[head] = nil
        head = slot(1)
        count -= 1
        return element
    }

    mutating func popLast() -> Element? {
        guard count > 0 else { return nil }
        let index = slot(count - 1)
        let element = slots[index]
        slots[index] = nil
        count -= 1
        return element
    }

    var picture: String {
        let cells = slots.map { slot in slot.map { "\($0)" } ?? "_" }
        return cells.joined(separator: " ") + "   head \(head), count \(count)"
    }
}

var deque = Deque<Int>()
deque.append(1)
deque.append(2)
print(deque.picture)
deque.prepend(0)                 // the front wraps round to the last slot
print(deque.picture)
deque.prepend(-1)                // now every slot is in use
print(deque.picture)
deque.append(3)                  // full: grow to 8 slots, in order, then append
print(deque.picture)
print(deque.popFirst() ?? 99, deque.popLast() ?? 99)
print(deque.picture)
```

```output
1 2 _ _   head 0, count 2
1 2 _ 0   head 3, count 3
1 2 -1 0   head 2, count 4
-1 0 1 2 3 _ _ _   head 0, count 5
-1 3
_ 0 1 2 _ _ _ _   head 1, count 3
```

Read it line by line:

1. Two appends fill slots 0 and 1.
2. `prepend(0)` steps `head` back from 0, which wraps to slot 3. The deque reads 0, 1, 2 starting at `head`, even though the array reads `1 2 _ 0`.
3. `prepend(-1)` steps back to slot 2. All four slots are in use.
4. `append(3)` finds the deque full, so it grows: the four elements are copied in queue order, -1, 0, 1, 2, into slots 0 to 3 of a new 8-slot array, and `head` resets to 0. Then 3 goes into slot 4.
5. The pops take -1 from the front and 3 from the back, clearing their slots.

What to notice:

- `grow()` runs **before** anything computes a slot. On the very first insertion `slots.count` is 0, and `% 0` would crash.
- Both pops set their slot back to `nil`, so a removed object is released straight away.
- `Swift.max` instead of `max`: you'll see why in a moment.

## Making it a real collection

A deque with positions 0 to `count - 1` is a natural `RandomAccessCollection`, as [Collection conformance and subscripts](/dsa/learn/swift-collection-subscripts) showed. Three members are enough:

```swift
extension Deque: RandomAccessCollection {
    var startIndex: Int { 0 }
    var endIndex: Int { count }

    subscript(position: Int) -> Element {
        precondition(position >= 0 && position < count, "Deque index out of range")
        return slots[slot(position)]!
    }
}
```

In return you get `for`-`in`, `map`, `filter`, `contains`, `first`, `last`, `reversed()`, `firstIndex(of:)`, `max()` and the rest, all reading from the front. The force unwrap is safe: every position from 0 to `count - 1` holds an element. (If `Element` is itself optional, the slot holds `.some(nil)`, and unwrapping one level gives back the `nil` element, which is correct.)

Add `ExpressibleByArrayLiteral` ([ExpressibleByArrayLiteral](/dsa/learn/swift-array-literal)) and `CustomStringConvertible`, and the deque feels like a built-in type.

<Callout kind="gotcha" title="Swift gotcha: max inside a Sequence">
Once `Deque` conforms to `Sequence` (which `RandomAccessCollection` includes), it gains an instance method `max()`. Inside the type, a plain `max(4, slots.count * 2)` now finds that method first, and the compiler complains: "use of 'max' refers to instance method rather than global function 'max' in module 'Swift'". Write `Swift.max(…)` to mean the global function. The same goes for `min`.
</Callout>

`popFirst()` and `popLast()` don't clash with the standard library's methods of the same names. Swift only provides those for collections whose slices are the same type as the collection itself (an `ArraySlice` is its own slice; a `Deque`'s slice is a `Slice<Deque>`), so the deque's own versions are the only ones that apply.

## Testing against a model

How do you know a ring buffer with wrap-around, growth and two moving ends is right? Hand-written tests catch the cases you thought of. The bugs are in the cases you didn't.

Library authors use **model-based testing**: run a long sequence of operations on your structure and, side by side, on something slow but obviously correct, here a plain `Array`, and check after every step that they agree. The choices come from a seeded generator, so every run does exactly the same thing and a failure can be replayed.

```swift run
struct Deque<Element> {
    private var slots: [Element?] = []
    private var head = 0
    private(set) var count = 0

    init() {}

    private func slot(_ offset: Int) -> Int {
        (head + offset) % slots.count
    }

    private mutating func grow() {
        var bigger = [Element?](repeating: nil, count: Swift.max(4, slots.count * 2))
        for offset in 0..<count {
            bigger[offset] = slots[slot(offset)]
        }
        slots = bigger
        head = 0
    }

    mutating func append(_ element: Element) {
        if count == slots.count { grow() }
        slots[slot(count)] = element
        count += 1
    }

    mutating func prepend(_ element: Element) {
        if count == slots.count { grow() }
        head = (head - 1 + slots.count) % slots.count
        slots[head] = element
        count += 1
    }

    mutating func popFirst() -> Element? {
        guard count > 0 else { return nil }
        let element = slots[head]
        slots[head] = nil
        head = slot(1)
        count -= 1
        return element
    }

    mutating func popLast() -> Element? {
        guard count > 0 else { return nil }
        let index = slot(count - 1)
        let element = slots[index]
        slots[index] = nil
        count -= 1
        return element
    }
}

extension Deque: RandomAccessCollection {
    var startIndex: Int { 0 }
    var endIndex: Int { count }

    subscript(position: Int) -> Element {
        precondition(position >= 0 && position < count, "Deque index out of range")
        return slots[slot(position)]!
    }
}

extension Deque: ExpressibleByArrayLiteral {
    init(arrayLiteral elements: Element...) {
        self.init()
        for element in elements {
            append(element)
        }
    }
}

extension Deque: CustomStringConvertible {
    var description: String { "Deque(\(Array(self)))" }
}

// A deterministic stream of pseudo-random choices, so every run does the same operations
var state: UInt64 = 42
func nextChoice(below limit: Int) -> Int {
    state = state &* 6364136223846793005 &+ 1442695040888963407   // &* and &+ wrap instead of overflowing
    return Int(state >> 33) % limit
}

var deque: Deque<Int> = []
var model: [Int] = []
var mismatches = 0
for step in 0..<10_000 {
    switch nextChoice(below: 4) {
    case 0:
        deque.append(step)
        model.append(step)
    case 1:
        deque.prepend(step)
        model.insert(step, at: 0)
    case 2:
        if deque.popFirst() != (model.isEmpty ? nil : model.removeFirst()) { mismatches += 1 }
    default:
        if deque.popLast() != model.popLast() { mismatches += 1 }
    }
    if !deque.elementsEqual(model) { mismatches += 1 }
}
print("10000 operations, \(mismatches) mismatches, \(deque.count) left")

var small: Deque = [2, 3]
small.prepend(1)
print(small, small.first ?? 0, small.last ?? 0, small[1])
print(small.map { $0 * 10 }, Array(small.reversed()), small.contains(3))
```

```output
10000 operations, 0 mismatches, 22 left
Deque([1, 2, 3]) 1 3 2
[10, 20, 30] [3, 2, 1] true
```

Ten thousand operations, crossing every wrap and several growths, and the deque never disagreed with the array. The array model is slow (its `insert(_:at: 0)` and `removeFirst()` are O(n)), but that doesn't matter in a test: it only has to be right.

Try breaking the deque on purpose: drop the `+ slots.count` from `prepend`, or forget to reset `head` in `grow()`. The model test fails straight away, while a handful of hand-written cases might not.

## DSAKit's Deque, and the production one

Your package's `dsa-swift/Sources/DSAKit/Deque.swift` is this design with the edges finished:

- a minimum of 8 slots, and a slot helper that wraps with a comparison instead of `%`;
- `MutableCollection` too, so `deque[i] = x`, `swapAt` and `sort()` work;
- `Equatable` and `Hashable` that compare elements in order, ignoring where they sit in the slots;
- `removeAll(keepingCapacity:)` and an initialiser from any sequence.

Its tests run 20,000 mixed operations against an array model with three different seeds, including writes through the subscript.

For production code, Apple's open-source **swift-collections** package has a `Deque` built on the same ring-buffer idea, with more conformances (you can insert and remove in the middle too, at O(n) cost) and years of tuning. Add the package and `import DequeModule` to use it; Part IX covers packages. Knowing how it works inside tells you exactly what each operation costs.
