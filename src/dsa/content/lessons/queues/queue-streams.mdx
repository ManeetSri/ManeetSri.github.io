## Why it matters

A **stream** is data that arrives one item at a time, where you must answer after each item without seeing the future: accelerometer readings, keystrokes in a search box, login attempts, chat messages, prices. You can't store everything and recompute from scratch every time, and you don't need to. Most stream problems only care about a **recent** slice of the data, and a queue holds exactly that slice: new items join the back, and items that stop mattering leave the front. This lesson works through three classics that you'll meet again and again: a moving average, a recent-hit counter and the first unique character.

## The shape of a stream problem

All three solutions share a shape:

1. A **queue** of the items that still matter, oldest at the front.
2. A small **summary** kept up to date as items join and leave: a sum, a count, a dictionary of counts.
3. A rule for when the front item **stops mattering**, checked as each new item arrives.

Each item joins the queue once and leaves it at most once. So even when one arrival pushes several old items out, the total work over the stream is proportional to its length: **O(1) amortised per item**, the same aggregate argument as the monotonic deque.

## A moving average of the last k values

Raw sensor readings are noisy. Averaging the last k readings smooths them: a step counter, a compass heading or an FPS display shows the moving average rather than the latest jumpy value.

Recomputing the sum of k values for each reading is O(k). Instead, keep a running `sum`: add the new value, and when the window is full, subtract the value that falls out. The last k values sit in a ring buffer from [Ring buffers](/dsa/learn/queue-ring-buffer) that overwrites its oldest slot:

```swift run
struct MovingAverage {
    private var window: [Int]            // a ring of the last k values
    private var head = 0                 // the slot of the oldest value
    private var count = 0
    private var sum = 0

    init(size: Int) {
        window = Array(repeating: 0, count: size)
    }

    mutating func next(_ value: Int) -> Double {
        if count == window.count {
            sum -= window[head]                  // the oldest value leaves…
            window[head] = value                 // …and the new one takes its slot
            head = (head + 1) % window.count
        } else {
            window[(head + count) % window.count] = value
            count += 1
        }
        sum += value
        return Double(sum) / Double(count)
    }
}

var smoother = MovingAverage(size: 3)
for reading in [10, 20, 30, 40, 50, 0] {
    print(reading, "→", smoother.next(reading))
}
```

```output
10 → 10.0
20 → 15.0
30 → 20.0
40 → 30.0
50 → 40.0
0 → 30.0
```

Until the window fills, the average is over the values seen so far: 10, then (10 + 20) / 2, then (10 + 20 + 30) / 3. After that, each reading pushes out the oldest: when 40 arrives, 10 leaves, giving (20 + 30 + 40) / 3 = 30.

What to notice:

- Each reading costs O(1), however large k is, and the memory is exactly k slots.
- The sum is an `Int`, so it's exact. Dividing only at the end means no rounding error builds up.

<Callout kind="gotcha" title="A running Double sum drifts">
If the readings are `Double`s, adding and subtracting millions of them makes tiny rounding errors pile up, so after a long time the running sum no longer matches the window's true total. If that matters, keep integer units (milliseconds rather than seconds), or recompute the sum from the window every so often.
</Callout>

## Counting recent hits

"At most 5 login attempts per minute." "120 people viewed this in the last hour." Both ask: how many events happened in the last w seconds?

Timestamps arrive in order, never going backwards. Keep them in a queue. To count at time t, first drop from the front every timestamp that's too old (at or before t − w), then the answer is the queue's length.

```swift run
struct HitCounter {
    private var times: [Int] = []        // a head-index queue of hit times, oldest first
    private var head = 0
    let window: Int

    init(window: Int) {
        self.window = window
    }

    mutating func hit(at time: Int) {
        times.append(time)
    }

    // Hits in the last `window` seconds, counting `time` itself: from time - window + 1 to time
    mutating func count(at time: Int) -> Int {
        while head < times.count && times[head] <= time - window {
            head += 1                    // too old: it will never count again
        }
        return times.count - head
    }
}

var logins = HitCounter(window: 60)
for time in [1, 2, 2, 30, 61] {
    logins.hit(at: time)
}
print(logins.count(at: 61))
print(logins.count(at: 62))
print(logins.count(at: 90))
print(logins.count(at: 121))
```

```output
4
2
1
0
```

At time 61, the last 60 seconds are 2 to 61, so the hit at 1 is dropped and four remain. At 62, the two hits at time 2 go too. Once a timestamp is dropped, it never comes back, because time only moves forward. That's what makes the queue work: the oldest timestamp is always the next one to expire.

This version never compacts, so it's fine for a short run but not for a counter that lives as long as an app; DSAKit's `Queue` handles that for you. And if thousands of hits can share one second, store `(time, count)` pairs instead of one entry per hit, so the queue holds at most w entries.

## The first unique character in a stream

Characters arrive one at a time. After each one, report the **first** character so far that has appeared **exactly once**, or `#` if there isn't one. A chat app might use the same idea to find the oldest message nobody has replied to yet.

Two pieces of state:

- `counts`, a dictionary from character to how many times it has appeared;
- `candidates`, a queue of characters in the order they first appeared.

When a character arrives, count it, and if it's new, enqueue it. Then clean the front: while the front character's count is more than 1, dequeue it. It's repeated, and it can never become unique again. The front of the queue is the answer.

```swift run
struct FirstUnique {
    private var counts: [Character: Int] = [:]
    private var candidates: [Character] = []     // a head-index queue, in arrival order
    private var head = 0

    mutating func add(_ character: Character) {
        counts[character, default: 0] += 1
        if counts[character] == 1 {
            candidates.append(character)         // a new candidate joins the back
        }
        // Repeated characters at the front can never be unique again
        while head < candidates.count && counts[candidates[head], default: 0] > 1 {
            head += 1
        }
    }

    var firstUnique: Character? {
        head < candidates.count ? candidates[head] : nil
    }
}

var watcher = FirstUnique()
var answers: [String] = []
for character in "aabcbd" {
    watcher.add(character)
    answers.append(watcher.firstUnique.map { String($0) } ?? "#")
}
print(answers.joined(separator: " "))
```

```output
a # b b c c
```

Follow it. After `a`, the answer is `a`. The second `a` makes its count 2, so it's dequeued and the queue is empty: `#`. Then `b` and `c` join, and `b` is first. The second `b` pushes `b` out, leaving `c`. Finally `d` joins behind `c`.

What to notice:

- A repeated character **in the middle** of the queue stays there for now. It only matters once it reaches the front, and then the cleaning loop removes it. This "lazy deletion" is what keeps every operation cheap.
- Each character is enqueued at most once (only on its first appearance) and dequeued at most once: amortised O(1) per character, plus the dictionary's O(1) average.
- The queue never holds more distinct characters than the alphabet has, so for letters it's tiny.

## Three problems, one pattern

| Problem | The queue holds | An item leaves when | Summary kept |
| --- | --- | --- | --- |
| Moving average | the last k values | k newer values have arrived | running sum |
| Recent hits | timestamps, oldest first | it's older than the window | none: the count is the queue's length |
| First unique | first appearances, in order | it reaches the front and has been repeated | counts per character |

<Callout kind="warning" title="Order matters">
The recent-hit counter assumes timestamps never go backwards. If events can arrive out of order, for example from several devices, the oldest event is no longer at the front, and you'll need a structure ordered by time, such as the heaps in Part V.
</Callout>
