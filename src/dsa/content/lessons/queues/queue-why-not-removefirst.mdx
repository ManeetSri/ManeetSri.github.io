## Why it matters

A **queue** hands things out in the order they arrived: print jobs, network requests waiting for a free connection, messages waiting to be processed, songs in an "up next" list. In DSA, queues drive breadth-first search, scheduling simulations and every "process things in arrival order" problem. The obvious Swift queue, an array with `append` and `removeFirst()`, is correct but quietly O(n) per removal. This lesson counts exactly why, so the rest of the module can fix it.

## First in, first out

A queue has a **back**, where new items join, and a **front**, where items leave. The item that has waited longest always leaves first: **first in, first out**, or FIFO for short. A stack, from M26, is the opposite: last in, first out.

Three operations make a queue:

| Operation | Meaning |
| --- | --- |
| `enqueue(x)` | add `x` at the back |
| `dequeue()` | remove and return the front item, or `nil` if there's none |
| `peek()` | look at the front item without removing it |

## The obvious queue: an array

An array already has both ends. `append` adds at the back, `first` peeks at the front and `removeFirst()` takes it away:

```swift run
var line: [String] = []
line.append("Ana")                 // enqueue
line.append("Ben")
line.append("Cleo")
print(line.first ?? "nobody")      // peek
let served = line.removeFirst()    // dequeue
print(served, line)
line.append("Dev")
print(line.removeFirst(), line)
```

```output
Ana
Ana ["Ben", "Cleo"]
Ben ["Cleo", "Dev"]
```

It behaves exactly like a queue. The problem is what `removeFirst()` costs.

## What removeFirst() really does

An array keeps its elements side by side, and element 0 must always sit at the start of that block of memory. That's what makes `array[i]` O(1), as [Removing elements](/dsa/learn/swift-array-mutation) explained. So when the first element leaves, every other element **moves one place to the left** to close the gap.

Here's a version of `removeFirst()` that does the shifting by hand and counts the moves. Draining a queue of n items calls it n times:

```swift run
// Removes the first element the way Array does: every later element moves one place left
func dequeueCountingMoves(_ items: inout [Int]) -> Int {
    var moves = 0
    for index in items.indices.dropFirst() {
        items[index - 1] = items[index]
        moves += 1
    }
    items.removeLast()
    return moves
}

for n in [10, 100, 1_000] {
    var queue = Array(1...n)
    var moves = 0
    while !queue.isEmpty {
        moves += dequeueCountingMoves(&queue)
    }
    print("\(n) dequeues: \(moves) moves")
}
```

```output
10 dequeues: 45 moves
100 dequeues: 4950 moves
1000 dequeues: 499500 moves
```

The first dequeue moves n − 1 elements, the next n − 2, and so on down to 0. That's the triangle from [Analysing nested, halving and dependent loops](/dsa/learn/bigo-analysing-loops): (n − 1) + (n − 2) + … + 0 = n(n − 1)/2. Ten times more items means a hundred times more moves: **O(n²)** to drain the queue, **O(n)** per dequeue.

For 100,000 items that's about 5 billion moves. [Swift's hidden costs](/dsa/learn/bigo-swift-hidden-costs) timed it: well over half a second in a release build, against a few microseconds for the fix you'll write in the next lesson.

## The cost follows the queue's size

You might think this only hurts when the queue gets huge. Not quite. Each `removeFirst()` costs one move for every item **still waiting**. A server that always has about 1,000 requests queued, and processes a million of them in a day, makes about 1,000 moves per request: a billion moves in total, even though the queue never holds more than a thousand items.

Compare the back of the array. `popLast()` and `removeLast()` take the last element, and nothing has to move, so they're O(1). Arrays are fast at the back and slow at the front.

## Fixes that don't quite work

**Reverse, then pop from the back.** If every item is known before you start, reverse the array once (O(n)) and take items with `popLast()` (O(1) each):

```swift run
var jobs = ["A", "B", "C", "D"]
jobs.reverse()                      // O(n), once
var order: [String] = []
while let job = jobs.popLast() {    // O(1) each
    order.append(job)
}
print(order)
```

```output
["A", "B", "C", "D"]
```

That's a fine trick for a fixed batch. It breaks as soon as new items arrive while you're dequeuing, which is what queues are usually for: a newcomer belongs at the back of the line, which is now the *front* of the reversed array, so adding it means `insert(_:at: 0)`. O(n) again.

**Insert at the front instead.** Enqueueing with `insert(_:at: 0)` and dequeueing with `popLast()` only moves the problem: now every enqueue shifts the whole array.

<Callout kind="gotcha" title="Swift gotcha: Array has popLast() but no popFirst()">
`queue.popFirst()` doesn't compile on an `Array`. Swift only offers `popFirst()` on types whose slices are the same type, such as `ArraySlice`, so the compiler reports something like:

```text title="What you'll see"
error: referencing instance method 'popFirst()' on 'Collection' requires the types '[Int]' and 'Array<Int>.SubSequence' (aka 'ArraySlice<Int>') be equivalent
```

And `removeFirst()` on an empty array crashes with `Fatal error: Can't remove first element from an empty collection`. If you do use it, check `isEmpty` first.
</Callout>

## When removeFirst() is fine

Big-O describes growth, and small queues don't grow. Shifting five elements is nothing. A queue of menu actions, the next three onboarding screens or a handful of retries can use an array and `removeFirst()` happily. Reach for a real queue when the queue can hold more than a few hundred items, or when you dequeue inside a loop that runs many times, as BFS does.
