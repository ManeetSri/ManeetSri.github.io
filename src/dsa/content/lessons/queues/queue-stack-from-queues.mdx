## Why it matters

You built a queue from two stacks, and it was genuinely good: O(1) amortised. Interviewers like to flip the question round: build a **stack** using only queues. Here the answer is never efficient, and that's the interesting part. Working out *why* sharpens exactly the reasoning you need for amortised analysis and invariants. In real code, though, a stack is an array with `append` and `popLast()`, so treat this lesson as a puzzle, not a pattern to use.

## The rules

You may use queues, and only their operations: `enqueue`, `dequeue`, `peek`, `count` and `isEmpty`. No indexing, no looking at the back, no reversing. From those, build `push`, `pop` and `top` with last-in, first-out behaviour.

The difficulty is plain: a queue gives you its **oldest** item, and a stack needs its **newest**.

## One queue, expensive push

Keep this invariant: **the queue's front is the stack's top**, and the queue, read from front to back, lists the stack from newest to oldest.

- `pop` is then `dequeue`, and `top` is `peek`: O(1).
- `push` must put the new item at the **front**. A queue can only add at the back, so enqueue it there, then **rotate**: dequeue each of the older items and enqueue it again behind the new one. After `count - 1` rotations, the new item has reached the front and the older items are behind it, still newest to oldest.

```swift run
// A minimal queue: the only operations the stack below may use
struct SimpleQueue<Element> {
    private var items: [Element] = []
    private var head = 0

    var count: Int { items.count - head }
    func peek() -> Element? { head < items.count ? items[head] : nil }
    mutating func enqueue(_ element: Element) { items.append(element) }
    mutating func dequeue() -> Element? {
        guard head < items.count else { return nil }
        head += 1
        return items[head - 1]
    }
    var contents: [Element] { Array(items[head...]) }   // front first, for printing
}

struct QueueStack<Element> {
    private var queue = SimpleQueue<Element>()
    private(set) var rotations = 0

    mutating func push(_ element: Element) {
        queue.enqueue(element)
        // Rotate the older items behind the new one, so it reaches the front
        for _ in 0..<(queue.count - 1) {
            queue.enqueue(queue.dequeue()!)
            rotations += 1
        }
    }

    mutating func pop() -> Element? { queue.dequeue() }
    func top() -> Element? { queue.peek() }
    var contents: [Element] { queue.contents }
}

var stack = QueueStack<Int>()
for value in 1...4 {
    stack.push(value)
    print("push \(value): queue front to back \(stack.contents)")
}
print("pop:", stack.pop() ?? 0, "then top:", stack.top() ?? 0)

for n in [10, 100, 1_000] {
    var counted = QueueStack<Int>()
    for value in 0..<n {
        counted.push(value)
    }
    print("\(n) pushes: \(counted.rotations) rotations")
}
```

```output
push 1: queue front to back [1]
push 2: queue front to back [2, 1]
push 3: queue front to back [3, 2, 1]
push 4: queue front to back [4, 3, 2, 1]
pop: 4 then top: 3
10 pushes: 45 rotations
100 pushes: 4950 rotations
1000 pushes: 499500 rotations
```

Pushing 3 onto `[2, 1]` went like this: enqueue 3 to get `[2, 1, 3]`, rotate 2 to get `[1, 3, 2]`, rotate 1 to get `[3, 2, 1]`. The newest item is at the front, so `pop` returns it.

The counts are the triangle numbers again: the k-th push rotates the k − 1 items already there, so n pushes cost n(n − 1)/2 rotations. **Push is O(n)**, and there's no amortising it away: every push really does rotate the whole stack.

The force unwrap in `queue.dequeue()!` is safe: the loop only runs while there are older items to rotate.

## Two queues, expensive pop

The other classic answer moves the cost to `pop`:

- `push` enqueues onto the main queue: O(1).
- `pop` dequeues all but the last item from the main queue, enqueueing each one onto a helper queue. The last item left is the newest, so dequeue and return it. Then swap the two queues' roles.

```swift
mutating func pop() -> Element? {
    while main.count > 1 {
        helper.enqueue(main.dequeue()!)      // move everything except the newest
    }
    let newest = main.dequeue()
    swap(&main, &helper)                     // the helper is now the main queue
    return newest
}
```

Now push is O(1) and pop is O(n). `top` has the same problem as `pop`, unless you also keep the most recent push in a separate variable. Pick whichever suits the expected mix: lots of pushes and few pops favour this version.

## Why this one doesn't amortise

The two-stack queue moved each item **at most once**. Why can't the queue-built stack do the same?

The difference is what moving does to order:

- Pouring a **stack** into a stack **reverses** it. That reversal turns newest-first into oldest-first, which is exactly what a queue needs, and it's permanent. Once an item is in the outbox, it never has to move again.
- Moving a **queue** into a queue **preserves** its order. Nothing is ever fixed for good. In the rotating version, every item gets rotated again on every later push; in the two-queue version, every item still waiting gets moved again on every later pop.

So the work per item grows with the number of operations that follow it, not with a constant. Both standard designs pay O(n) on one of the two operations, and the clever-sounding variations still end up moving items over and over.

| | Queue from two stacks | Stack from queues |
| --- | --- | --- |
| Moving items | reverses the order: fixes it for good | keeps the order: fixes nothing |
| Moves per item | at most one | one per later push (or pop) |
| Cost | O(1) amortised for both | O(n) for push or for pop |
| Useful in practice? | yes | no: use an array |

<Callout kind="gotcha" title="Rotate count − 1 times, not count">
After enqueueing the new item, the queue holds `count` items, and only the `count - 1` older ones should move behind it. Rotate `count` times and the new item goes round too, ending up back at the **end**: the stack quietly turns into a queue.
</Callout>

## Why interviewers ask it anyway

Nobody ships this. The question tests three things: whether you can state an invariant ("the front is the top") and keep it true, whether you can analyse a cost honestly ("push is O(n) every time, not amortised"), and whether you can explain the difference from the two-stack queue. If you can say "moving between queues preserves order, so nothing gets fixed", you've answered the real question.
