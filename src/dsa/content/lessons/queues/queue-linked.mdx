## Why it matters

Before arrays could grow cheaply, the textbook queue was a linked list, and it's still the version most algorithm books show first. Every operation is O(1) in the worst case, not only on average, and the queue holds exactly as many nodes as it has items. It's also a good test of the linked-list skills from M25: two pointers that must stay in step, and an empty case that's easy to get wrong. In Swift, though, it's rarely the fastest choice, and this lesson shows why.

## Which end is which?

A singly linked list (from [building `LinkedList<T>`](/dsa/learn/ll-build-singly)) can cheaply remove its **first** node: move `head` to `head.next`. With a `tail` pointer, it can cheaply **add** after its last node. What it can't do cheaply is remove its last node, because that needs the node *before* it, and finding that means walking the whole list.

So the list's head is the queue's front, and its tail is the queue's back:

- **enqueue**: make a node, link it after `tail`, and make it the new `tail`;
- **dequeue**: take the value at `head`, and move `head` to the next node.

Both are a handful of pointer updates: O(1), with no shifting and no "occasionally expensive" step.

## The code

The queue is a class here, for a reason the next section explains.

```swift run
final class Node<Element> {
    let value: Element
    var next: Node?

    init(_ value: Element) {
        self.value = value
    }
}

final class LinkedQueue<Element> {
    private var head: Node<Element>?     // the front: dequeue here
    private var tail: Node<Element>?     // the back: enqueue here
    private(set) var count = 0

    var isEmpty: Bool { head == nil }

    func enqueue(_ value: Element) {
        let node = Node(value)
        if let tail {
            tail.next = node                 // link it after the current back
        } else {
            head = node                      // empty queue: it's also the front
        }
        tail = node
        count += 1
    }

    func dequeue() -> Element? {
        guard let front = head else { return nil }
        head = front.next
        if head == nil {
            tail = nil                       // that was the last node
        }
        count -= 1
        return front.value
    }

    func peek() -> Element? {
        head?.value
    }

    var values: [Element] {
        var result: [Element] = []
        var node = head
        while let current = node {
            result.append(current.value)
            node = current.next
        }
        return result
    }
}

let queue = LinkedQueue<String>()
queue.enqueue("a")
queue.enqueue("b")
print(queue.values, queue.count)
print(queue.dequeue() ?? "-", queue.dequeue() ?? "-", queue.dequeue() ?? "-")
queue.enqueue("c")
queue.enqueue("d")
print(queue.values, queue.peek() ?? "-")
```

```output
["a", "b"] 2
a b -
["c", "d"] c
```

What to notice:

- **The empty case touches both pointers.** Enqueueing into an empty queue sets `head` as well as `tail`. Dequeueing the last node clears `tail` as well as `head`.
- Forget the second half, and `tail` keeps pointing at a node that's no longer in the queue. The next enqueue links its node onto that detached node, `head` stays `nil`, and the item vanishes. It's the classic linked-queue bug, and it's why the test above dequeues until empty and then enqueues again.
- When the front node leaves, nothing refers to it any more, so ARC frees it straight away.
- A sentinel node (from [Dummy and sentinel nodes](/dsa/learn/ll-sentinel)) can remove the special cases: with a dummy node that's always there, `tail` is never `nil`.

## Why a class, not a struct?

Part I taught you to prefer structs, so why is `LinkedQueue` a class? Because the nodes are classes, and a struct holding class references copies the **references**, not the nodes. Two copies of the struct would share the same chain of nodes:

```swift run
final class Node {
    let value: Int
    var next: Node?
    init(_ value: Int) { self.value = value }
}

// A struct this time: copies share the same nodes
struct SharedQueue {
    var head: Node?
    var tail: Node?

    mutating func enqueue(_ value: Int) {
        let node = Node(value)
        if let tail { tail.next = node } else { head = node }
        tail = node
    }

    var values: [Int] {
        var result: [Int] = []
        var node = head
        while let current = node {
            result.append(current.value)
            node = current.next
        }
        return result
    }
}

var original = SharedQueue()
original.enqueue(1)
original.enqueue(2)
var copy = original
copy.enqueue(3)                    // changes the node both copies share
print("copy:", copy.values)
print("original:", original.values)
```

```output
copy: [1, 2, 3]
original: [1, 2, 3]
```

Enqueueing on `copy` set `next` on the node holding 2, which `original` also uses, so the "independent" original grew too. A struct that *looks* like a value but secretly shares state is worse than an honest class. You could fix it with the copy-on-write technique from [Writing your own copy-on-write](/dsa/learn/swift-implementing-cow), copying the whole chain before the first change, but for a queue that's rarely worth it. Making the queue a class says plainly that copies share.

## What a node costs

On paper, the linked queue beats the array queues: O(1) worst case for everything. In practice, in Swift, array-based queues are usually faster:

- **One allocation per item.** Every enqueue asks for a new heap object, and every dequeue frees one. An array allocates rarely, in big doubling steps.
- **Overhead per item.** Each node carries a 16-byte object header (type information and reference counts) plus its `next` pointer, on top of the value. A queue of `Int`s uses several times the memory of an array of them.
- **Reference counting.** Moving `head` and `tail` around updates reference counts, as [Automatic Reference Counting](/dsa/learn/swift-arc) described.
- **Scattered memory.** Array slots sit side by side, so the processor reads them in fast, predictable runs. Nodes can be anywhere on the heap, and following `next` from one to the next is much slower than reading the next array slot.

So when do you reach for a linked queue? When you need a guarantee that **no single operation** is ever expensive (no growth step, no compaction, no pour), or when items need to be unlinked from the middle as well, which you'll see in the [LRU cache](/dsa/learn/ll-lru-cache). For everyday queues in Swift, use DSAKit's `Queue` or a ring buffer.

| | Linked list | Head index | Two stacks | Ring buffer |
| --- | --- | --- | --- | --- |
| enqueue | O(1) | O(1) amortised | O(1) amortised | O(1), fixed capacity |
| dequeue | O(1) | O(1) amortised | O(1) amortised | O(1) |
| allocations | one per item | rare | rare | one, up front |
| memory per item | node header + pointer + value | value (up to 2×) | value | value (whole capacity) |
