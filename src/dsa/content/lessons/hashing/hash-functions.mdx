## Why it matters

Since M07 you've used `Set` and `Dictionary` as magic boxes that answer "is this here?" and "what's stored for this key?" in O(1) on average. This module opens the box. Inside every hash table is a **hash function**: a recipe that turns a key into a number, so the key can be stored at a predictable position in an array. Understanding it explains why your keys must be `Hashable`, why a dictionary's order changes every run, and how to build one yourself later in this module.

## An array you can index by anything

Arrays are fast because `items[7]` jumps straight to position 7. If your keys were small integers, an array would already be a perfect lookup table:

```swift run
// Seats 0 to 9 in a small cinema: the seat number is the index
var bookedBy = Array(repeating: "", count: 10)
bookedBy[3] = "Maneet"
bookedBy[7] = "Asha"
print(bookedBy[3])
print(bookedBy[5].isEmpty)
```

```output
Maneet
true
```

This is called **direct addressing**: the key *is* the index. It stops working as soon as the keys aren't small integers. A key might be a name, a phone number with ten digits, or a grid cell. You can't make an array with a slot for every possible name.

The fix is to turn each key into a number, then squeeze that number into the range of a smallish array:

1. A **hash function** turns the key into an integer, its **hash value**.
2. The **modulo step** turns the hash value into an index: `hash % capacity`, where `capacity` is the number of slots, often called **buckets**.

An array plus those two steps is a **hash table**. Looking up a key means computing its index and checking one bucket, however many keys the table holds.

## What makes a good hash function

A hash function has three jobs:

- **Deterministic.** The same key must give the same hash value every time it's asked, at least while the program runs. Otherwise you'd store a key in one bucket and look for it in another.
- **Spreads keys out.** Different keys should land in different buckets as often as possible. When two keys land in the same bucket, that's a **collision**. A few are fine, and the next lessons show how tables cope. Lots of them make lookups slow.
- **Fast.** It runs on every insert and every lookup, so it should take time proportional to the size of the key and no more.

### A bad hash: adding up the letters

Here's a hash function you might invent first: add up the character codes. Each `Character` is made of one or more **Unicode scalars**, numbers that identify characters, which you met in [Unicode and grapheme clusters](/dsa/learn/swift-unicode). Watch what happens with six words made of the same letters:

```swift run
func letterSum(_ word: String) -> Int {
    var total = 0
    for scalar in word.unicodeScalars {
        total += Int(scalar.value)
    }
    return total
}

let words = ["stop", "pots", "tops", "spot", "opts", "post"]
for word in words {
    print(word, letterSum(word) % 11)
}
```

```output
stop 3
pots 3
tops 3
spot 3
opts 3
post 3
```

Every word lands in bucket 3. Addition doesn't care about order, so every anagram collides. A table full of words would be a few overflowing buckets and lots of empty ones.

### A better hash: polynomial hashing

Make position matter by treating the string like a number written in base 31. Start at 0, and for each scalar, multiply what you have by 31 and add the scalar:

`h = ((s₀ × 31 + s₁) × 31 + s₂) × 31 + s₃`

This is **Horner's rule**, the same trick that turns the digits 4, 7, 2 into 472 by multiplying by 10 each step. Taking the remainder after every step keeps the number small, as you learned in [Modular arithmetic](/dsa/learn/math-modular-arithmetic), so it never overflows:

```swift run
func polynomialHash(_ word: String, modulus: Int) -> Int {
    var hash = 0
    for scalar in word.unicodeScalars {
        hash = (hash * 31 + Int(scalar.value)) % modulus
    }
    return hash
}

let words = ["stop", "pots", "tops", "spot", "opts", "post"]
for word in words {
    print(word, polynomialHash(word, modulus: 11))
}
```

```output
stop 6
pots 3
tops 1
spot 5
opts 4
post 6
```

Five different buckets out of six words, from the same letters. One collision remains, because 11 buckets can't keep every word apart, but the keys are spread out. Java's `String.hashCode` uses the same recipe with base 31 (it lets the number overflow instead of taking a remainder), and the visualiser later in this module uses it for string keys.

## The modulo step

The second step looks harmless, but it has two traps.

**Negative hash values.** Real hash values use the full range of `Int`, so about half of them are negative. In Swift, `%` keeps the sign of the left-hand side, so a negative hash gives a negative index, and using it crashes with "Index out of range":

```swift run
let hash = -7
print(hash % 4)
print(((hash % 4) + 4) % 4)
```

```output
-3
1
```

The second line is the standard fix: add the capacity back and take the remainder again, which always lands in `0..<4`.

**Choosing the capacity.** Textbooks often pick a prime number of buckets, because a prime shares no factors with patterns in the keys. Many real tables, Swift's among them, use a **power of two** instead, because then `hash % capacity` can be replaced by a bit mask, `hash & (capacity - 1)`, which you met in [The bitwise operators and masking shifts](/dsa/learn/bits-operators). The mask keeps only the lowest bits, and it's never negative. The price is that keys whose low bits are all the same collide:

```swift run
var buckets = Array(repeating: 0, count: 8)
for key in stride(from: 0, to: 64, by: 8) {     // 0, 8, 16, ..., 56
    buckets[key & 7] += 1
}
print(buckets)
```

```output
[8, 0, 0, 0, 0, 0, 0, 0]
```

Every multiple of 8 ends in three zero bits, so all eight keys pile into bucket 0. A power-of-two table only works well with a hash function that **mixes** every bit of the key into the low bits. That's exactly what Swift's hasher does.

## Swift's Hasher

In Swift you never write the hash function itself. You write `hash(into:)`, as [Hashable and hash(into:)](/dsa/learn/swift-hashable) showed, and feed your properties to a `Hasher`, which does the mixing. You can also drive one by hand:

```swift run
var first = Hasher()
first.combine("swift")
first.combine(42)

var second = Hasher()
second.combine("swift")
second.combine(42)

print(first.finalize() == second.finalize())
print("swift".hashValue == "swift".hashValue)
```

```output
true
true
```

`combine` mixes a value in; `finalize()` produces the hash value, an `Int`. The algorithm is currently **SipHash-1-3**, designed to spread keys well and resist attackers, though Apple reserves the right to change it.

Notice the program printed comparisons, not the hash values themselves. Swift mixes a **random seed**, chosen fresh each time a program starts, into every hash. Within one run, the same input always gives the same hash, which is all a hash table needs. Across runs, the values change, and so does the order of every `Set` and `Dictionary`. The pitfalls lesson at the end of this module explains why that's a security feature.

<Callout kind="gotcha" title="Swift gotcha: equal strings can have different scalars">
`"é"` can be stored as one scalar (U+00E9) or as `"e"` followed by a combining accent (U+0301). Swift says they're equal, `"\u{E9}" == "e\u{301}"` is `true`, so its hasher works on a normalised form and gives them the same hash. The `polynomialHash` above hashes raw scalars, so it would put two equal strings in different buckets. That breaks the one rule every hash must keep: **equal keys, equal hashes**. Toy hashes are for learning. Real code uses `Hasher`.
</Callout>
