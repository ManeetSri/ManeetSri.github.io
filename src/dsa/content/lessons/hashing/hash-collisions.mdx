## Why it matters

A hash table squeezes a huge world of keys into a small array, so sometimes two keys want the same bucket. What the table does next decides how fast it is, how much memory it uses, and even whether deleting works. There are two families of answer: **separate chaining**, where each bucket keeps a list, and **open addressing**, where a key that finds its bucket taken looks for another one. Swift's `Dictionary` uses the second; the `HashMap` you'll build uses the first.

## Collisions are unavoidable

There are far more possible strings than buckets in any table, so by [the pigeonhole principle](/dsa/learn/math-pigeonhole) some keys must share a bucket. Worse, collisions turn up much sooner than intuition says. This is the **birthday problem**: in a room of 23 people, it's more likely than not that two share a birthday. Think of the 365 days as buckets:

```swift run
func chanceOfCollision(keys: Int, buckets: Int) -> Double {
    var allDifferent = 1.0
    for k in 0..<keys {
        allDifferent *= Double(buckets - k) / Double(buckets)   // the next key avoids the k taken buckets
    }
    return 1 - allDifferent
}

for (keys, buckets) in [(23, 365), (50, 365), (40, 1_000), (120, 10_000)] {
    let percent = Int((chanceOfCollision(keys: keys, buckets: buckets) * 100).rounded())
    print("\(keys) keys in \(buckets) buckets: \(percent)% chance of a collision")
}
```

```output
23 keys in 365 buckets: 51% chance of a collision
50 keys in 365 buckets: 97% chance of a collision
40 keys in 1000 buckets: 55% chance of a collision
120 keys in 10000 buckets: 51% chance of a collision
```

With a perfectly random hash, a collision is likely once you have about √m keys in m buckets: 120 keys in 10,000 buckets, barely 1% full. So every hash table needs a plan for collisions from the very first few keys.

## Separate chaining

In **separate chaining**, each bucket holds a small list of every entry that hashed there. To insert, append to the bucket's list. To look up, walk that one list comparing keys with `==`.

Here's a tiny table with integer keys, hashed with `key % 7` to keep the arithmetic easy to follow:

```swift run
struct ChainedTable {
    var buckets: [[(key: Int, value: String)]] = Array(repeating: [], count: 7)

    mutating func insert(_ key: Int, _ value: String) {
        let index = key % buckets.count
        if let position = buckets[index].firstIndex(where: { $0.key == key }) {
            buckets[index][position].value = value       // the key is already here: replace
        } else {
            buckets[index].append((key, value))          // new key: join the chain
        }
    }

    func lookup(_ key: Int) -> String? {
        let index = key % buckets.count
        return buckets[index].first(where: { $0.key == key })?.value
    }
}

var table = ChainedTable()
table.insert(10, "ten")
table.insert(3, "three")
table.insert(17, "seventeen")
table.insert(5, "five")

print(table.buckets[3].map { $0.key })
print(table.lookup(17) ?? "missing")
print(table.lookup(24) ?? "missing")
```

```output
[10, 3, 17]
seventeen
missing
```

Keys 10, 3 and 17 all leave remainder 3, so they share bucket 3 in the order they arrived. Looking up 17 walks that chain, comparing keys until it finds a match; looking up 24 also starts at bucket 3, walks the whole chain, and gives up.

Step through it to see chains grow, this time with 24 joining bucket 3 as well:

```visual hashTable
mode: chaining
keys: [10, 3, 17, 24, 5, 12]
size: 7
```

A lookup costs O(1 + length of the chain it walks). If n keys spread evenly over m buckets, the average chain has n/m keys. That ratio is the **load factor**, written α (alpha), and the next lesson is all about it.

## Open addressing

In **open addressing**, there are no lists. Every entry lives directly in the array, one per slot. If a key's home slot is taken, it tries other slots in a fixed order, its **probe sequence**, until it finds a free one. A lookup follows the same sequence until it finds the key, or reaches an empty slot, which proves the key isn't there.

### Linear probing

The simplest probe sequence tries the next slot, then the next, wrapping around at the end: slot `(home + i) % size` for i = 0, 1, 2, …

```swift run
var slots: [Int?] = Array(repeating: nil, count: 7)

func insert(_ key: Int) {
    var index = key % slots.count
    while slots[index] != nil {
        index = (index + 1) % slots.count     // taken: try the next slot
    }
    slots[index] = key
}

func contains(_ key: Int) -> Bool {
    var index = key % slots.count
    while let stored = slots[index] {         // an empty slot ends the search
        if stored == key {
            return true
        }
        index = (index + 1) % slots.count
    }
    return false
}

for key in [10, 3, 17, 5] {
    insert(key)
}
print(slots.map { $0.map(String.init) ?? "-" })
print(contains(17), contains(24))
```

```output
["-", "-", "-", "10", "3", "17", "5"]
true false
```

10 took its home, slot 3. Then 3 found slot 3 taken and moved to 4, 17 moved along to 5, and 5, whose home is slot 5, was pushed on to 6, even though it never collided with another key's home. That's **primary clustering**: occupied slots clump into runs, every key that lands in a run makes it longer, and long runs mean long probes. Watch it happen:

```visual hashTable
mode: probing
keys: [10, 3, 17, 5, 24, 12]
size: 7
```

Linear probing's great strength is speed in practice: the probes walk through neighbouring memory, which modern processors read very efficiently. That's why Swift's `Dictionary` uses it.

### Quadratic probing

To break up clusters, jump further each time: slot `(home + i²) % size`, trying offsets 0, 1, 4, 9, 16, … Keys from a crowded neighbourhood scatter instead of queuing in a line. Keys with the *same* home still follow identical paths, a milder problem called **secondary clustering**.

There's a catch: the squares don't always reach every slot. You'll see it below, where in a table of 7 slots the sequence never visits slots 1, 2 or 6. With a prime size and a table kept less than half full, quadratic probing always finds a free slot, which is why it's usually paired with those rules.

Here's that failure. Keys 10, 17, 24, 31 and 38 all have home slot 3, and the fifth one has nowhere to go:

```visual hashTable
mode: quadratic
keys: [10, 17, 24, 31, 38]
size: 7
```

### Double hashing

**Double hashing** uses a second hash function to choose the step size: slot `(home + i × step) % size`. Two keys with the same home usually get different steps, so they follow different paths. The step must never be 0, and it must share no factor with the size, so that the sequence visits every slot. With a prime size, any step from 1 to size − 1 works.

Here are all three probe sequences for keys 10 and 17, which share home slot 3:

```swift run
let size = 7

func linear(_ key: Int, _ i: Int) -> Int {
    (key % size + i) % size
}

func quadratic(_ key: Int, _ i: Int) -> Int {
    (key % size + i * i) % size
}

func double(_ key: Int, _ i: Int) -> Int {
    let step = 1 + key % (size - 1)       // the second hash: 1 to 6, never 0
    return (key % size + i * step) % size
}

for key in [10, 17] {
    print("key \(key)")
    print("  linear:   ", (0..<size).map { linear(key, $0) })
    print("  quadratic:", (0..<size).map { quadratic(key, $0) })
    print("  double:   ", (0..<size).map { double(key, $0) })
}
```

```output
key 10
  linear:    [3, 4, 5, 6, 0, 1, 2]
  quadratic: [3, 4, 0, 5, 5, 0, 4]
  double:    [3, 1, 6, 4, 2, 0, 5]
key 17
  linear:    [3, 4, 5, 6, 0, 1, 2]
  quadratic: [3, 4, 0, 5, 5, 0, 4]
  double:    [3, 2, 1, 0, 6, 5, 4]
```

Linear and quadratic probing send both keys down the same path. Double hashing gives each its own path, and both visit all seven slots.

## Deleting from an open-addressing table

Chaining makes deletion easy: remove the entry from its list. Open addressing has a trap. A lookup stops at the first empty slot, so emptying a slot in the middle of a probe sequence cuts it in two:

```swift run
enum Slot {
    case empty
    case occupied(Int)
    case deleted                  // a tombstone: "something was here"
}

var slots: [Slot] = Array(repeating: .empty, count: 7)
slots[3] = .occupied(10)          // 10 is at home
slots[4] = .occupied(17)          // 17's home is 3 too, so it probed on to 4

func contains(_ key: Int) -> Bool {
    var index = key % slots.count
    while true {
        switch slots[index] {
        case .empty:
            return false          // the probe sequence has ended
        case .occupied(let stored) where stored == key:
            return true
        default:
            index = (index + 1) % slots.count    // a different key or a tombstone: keep going
        }
    }
}

slots[3] = .empty                 // delete 10 by emptying its slot
print("emptied:", contains(17))
slots[3] = .deleted               // delete 10 with a tombstone instead
print("tombstone:", contains(17))
```

```output
emptied: false
tombstone: true
```

Emptying slot 3 made 17 unreachable: the search for 17 starts at 3, sees an empty slot, and gives up. A **tombstone** marks the slot as "deleted, but keep probing". Inserts may reuse tombstones, but they still pile up and lengthen probes, so tables clean them out when they rebuild. Swift's `Dictionary` avoids tombstones altogether with a cleverer trick, which [Inside Swift's Dictionary](/dsa/learn/hash-swift-dictionary) describes.

Watch tombstones at work. 24 probes past 17 to reach slot 5. After 17 is deleted, 24 is still found by probing past the tombstone, and the next insert reuses it:

```visual hashTable
mode: probing
size: 7
operations: ["insert 10", "insert 17", "insert 24", "delete 17", "find 24", "insert 31"]
```

## Chaining or open addressing?

| | Separate chaining | Open addressing |
| --- | --- | --- |
| Where entries live | lists hanging off buckets | in the array itself |
| Can the load factor pass 1? | yes, chains grow longer | no, the array fills up |
| Memory | an extra list per bucket | one flat array |
| Cache friendliness | jumps to each list | probes neighbouring slots |
| Deletion | remove from the list | tombstones or shifting |
| Simplicity | easier to get right | more subtle |

Both give O(1) average operations while the load factor stays reasonable. Chaining degrades gracefully as the table fills; open addressing is faster when it's kept well under full.

<Callout kind="gotcha" title="Common mistake: stopping at the first mismatch">
In open addressing, a lookup that finds a *different* key in a slot must keep probing. Only an empty slot proves the key is absent. Stopping at the first mismatch makes every key that was pushed along by a collision vanish.
</Callout>
