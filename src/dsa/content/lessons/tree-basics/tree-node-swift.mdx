## Why it matters

Before you can write a single tree algorithm, you need a type for a node. Swift gives you two natural choices, an **indirect enum** or a **class**, and they behave very differently: one is a value that never changes, the other is an object you can rewire in place. Interview problems, LeetCode and this course all use a class called `TreeNode`. Knowing why, and what the enum would have given you instead, saves you from the classic class bugs: a change through one reference showing up somewhere unexpected, or a copy that isn't one.

## Why not a struct?

The obvious first try is a struct with optional children:

```swift
struct Node {
    var value: Int
    var left: Node?
    var right: Node?
}
```

```text title="What you'll see"
error: value type 'Node' cannot have a stored property that recursively contains it
```

A struct stores its properties inline, inside itself. A `Node` would have to contain a whole `Node` inside it, which contains another, forever, so its size can't be worked out. Something has to add a level of indirection: a reference to a node stored elsewhere, rather than the node itself. The two ways to get that are `indirect` enum cases and classes.

## Option 1: an indirect enum

You met this in [Indirect enums for recursive data](/dsa/learn/swift-indirect-enums). A binary tree is either empty or a node with a left tree, a value and a right tree, and the enum says exactly that:

```swift
indirect enum Tree {
    case empty
    case node(Tree, Int, Tree)
}
```

`indirect` tells Swift to store each case's associated values in a separate box on the heap. The enum value itself holds a reference to that box, so its size is fixed. Functions over it use `switch`, and the cases mirror the recursive definition of a tree:

```swift run
indirect enum Tree {
    case empty
    case node(Tree, Int, Tree)
}

func values(_ tree: Tree) -> [Int] {             // left subtree, root, right subtree
    switch tree {
    case .empty:
        return []
    case let .node(left, value, right):
        return values(left) + [value] + values(right)
    }
}

// A new tree with an extra leaf at the far left. Only the nodes on the way down are rebuilt.
func addingLeftmost(_ newValue: Int, to tree: Tree) -> Tree {
    switch tree {
    case .empty:
        return .node(.empty, newValue, .empty)
    case let .node(left, value, right):
        return .node(addingLeftmost(newValue, to: left), value, right)
    }
}

let original = Tree.node(.node(.empty, 2, .empty), 5, .node(.empty, 8, .empty))
let bigger = addingLeftmost(1, to: original)
print("original:", values(original))
print("bigger:  ", values(bigger))
```

```output
original: [2, 5, 8]
bigger:   [1, 2, 5, 8]
```

What to notice:

- **Nothing changed.** `original` is exactly as it was. An enum value can't be modified in place; you build a new tree instead.
- **Building a new tree is cheaper than it looks.** `addingLeftmost` creates new nodes only along the path it walks: here, 5 and 2. The right subtree, 8, is reused as is. Both trees refer to the same box for 8, which is safe because nobody can ever change it. This is called **structural sharing**, and it's how persistent data structures work in functional languages.
- **There's no identity.** Two `.node(.empty, 8, .empty)` values are indistinguishable. You can't ask "is this the same node?", only "does it hold the same values?".

## Option 2: a class

A class instance lives on the heap, and a variable of class type holds a **reference** to it. An optional reference to another node is a fixed size, so a class can refer to its own type freely:

```swift
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}
```

`final` says nothing will subclass it, as in [Classes, inheritance and final](/dsa/learn/swift-classes). The default arguments let you write `TreeNode(4)` for a leaf, and nest calls to build small trees by hand. With a class, you change trees **in place**, and several references can reach the same node. That's both the power and the danger, as [Value vs reference semantics](/dsa/learn/swift-value-vs-reference) warned:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

let root = TreeNode(5, left: TreeNode(2), right: TreeNode(8))

// Two references to the same node: a change through one is seen through the other
let node = root.left!
node.value = 3
print("root.left now holds", root.left!.value)
print("same node?", node === root.left!)

// Rewire the tree in place, even though root is a let
root.right!.right = TreeNode(9)
root.left = nil
print("right child's right:", root.right!.right!.value, "| left is nil:", root.left == nil)

// The same node placed in two spots is ONE node
let shared = TreeNode(7)
let odd = TreeNode(0, left: shared, right: shared)
shared.value = 70
print("left \(odd.left!.value), right \(odd.right!.value)")
```

```output
root.left now holds 3
same node? true
right child's right: 9 | left is nil: true
left 70, right 70
```

What to notice:

- **`let` fixes the reference, not the object.** `root` can't be pointed at a different node, but the node's properties can change freely.
- **`===` asks about identity**, from [Identity with ===](/dsa/learn/swift-identity): are these the same object? That question only makes sense for classes.
- **A node in two places is one node.** In a real tree, every node has exactly one parent. Hanging the same object in two spots makes something that isn't a tree any more, and a change in one spot appears in the other. With the enum, this would have been harmless.

## Which one, and why problems use the class

| | Indirect enum | Class |
| --- | --- | --- |
| Changing a tree | build a new one (sharing what's unchanged) | rewire nodes in place |
| Sharing subtrees | always safe | surprising unless intended |
| "Is it the same node?" | can't ask | `===` |
| Pointing back up to a parent | impossible without rebuilding | a `weak var parent` |
| Code style | `switch` on cases | `if let`, `guard let` and property access |

The enum is the better fit when a tree is built once and only read, especially if you want old versions to survive: expression trees, JSON, undo history, a compiler's syntax tree. The class wins for the algorithms in the rest of this part, for three reasons:

1. **Many algorithms change the tree in place.** Inverting a tree, flattening it into a list or linking nodes on the same level (all in M36) rewire existing nodes. With the enum, every change rebuilds a path.
2. **Many problems are about particular nodes.** "Find the lowest common ancestor of these two nodes" hands you two nodes and expects one back. Only a class has identity to make that meaningful.
3. **It's the shared language.** Interview questions and LeetCode give you exactly this `TreeNode`, and it has the same shape as the `ListNode` you used for linked lists.

## The course's TreeNode in DSAKit

From here on, every binary tree problem uses one shared node type, `TreeNode`, in the companion package's DSAKit library, just as linked-list problems share `ListNode`. It's the class above with some helpers for building and checking trees:

```swift
import DSAKit

let root = TreeNode.make([1, 2, 3, 4, 5, nil, 6, nil, nil, 7])   // build from level order
print(root!)                    // [1, 2, 3, 4, 5, nil, 6, nil, nil, 7]
print(root!.count)              // 7: the number of nodes
print(root!.height)             // 4: the number of levels
print(root!.inorder)            // [4, 2, 7, 5, 1, 3, 6]
print(root!.find(5)!.left!.value)   // 7: find a node by value, level by level
print(root!.levelOrder)         // [Optional(1), Optional(2), ...]: an [Int?] for comparing in tests
```

| Member | What it does |
| --- | --- |
| `TreeNode(_:left:right:)` | a node, with optional children |
| `value`, `left`, `right` | the stored properties, all `var` |
| `TreeNode.make(_:)` | builds a tree from a level-order `[Int?]`; returns `nil` for an empty array |
| `levelOrder` | the reverse: the tree as a level-order `[Int?]` |
| `description` | the level order as text, so `print(root)` is readable |
| `count`, `height`, `inorder` | measurements for checking answers |
| `find(_:)` | the first node holding a value, for picking out nodes in tests |
| `diagram` | a sideways drawing of the tree (see [Printing trees](/dsa/learn/tree-printing)) |

Problems take a `TreeNode?`, where `nil` is the empty tree, and usually return plain Swift values such as `Int` or `[[Int]]`. Tests build their inputs with `TreeNode.make`. You'll write `make` yourself in the next lesson, and the traversals behind `inorder` in M35, so treat DSAKit as the finished reference and your own code as the exercise.

The lessons' runnable examples can't import DSAKit, because each one runs as a single file. So they define the small `TreeNode` class above at the top. It has the same `value`, `left` and `right` and the same initialiser, so code moves between the two unchanged.

<Callout kind="note" title="Why DSAKit's TreeNode has a deinit">
When the last reference to a node goes away, ARC frees it, and that releases its children, which release theirs: one nested call per level, as in [Automatic Reference Counting](/dsa/learn/swift-arc). For a degenerate tree 100,000 levels deep, that chain of releases can overflow the stack. DSAKit's `TreeNode` has a `deinit` that unhooks the children with a loop instead, so even enormous test trees are freed safely. The little class in the lessons doesn't need one, because its trees are tiny.
</Callout>

## Parent pointers

Children are reached from their parent, but sometimes you need to go **up**: from a node to its parent, or all the way to the root. You could add a `parent` property, but if it were a normal (strong) reference, every parent and child would keep each other alive: a retain cycle, from [Retain cycles](/dsa/learn/swift-retain-cycles). The fix is to make the upward link `weak`, from [weak and unowned references](/dsa/learn/swift-weak-unowned): parents own their children, and children only point back.

```swift run
final class Node {
    let value: Int
    var children: [Node] = []
    weak var parent: Node?                    // doesn't keep the parent alive

    init(_ value: Int) {
        self.value = value
    }

    func add(_ child: Node) {
        children.append(child)
        child.parent = self
    }
}

let root = Node(1)
let two = Node(2)
let five = Node(5)
let seven = Node(7)
root.add(two)
two.add(five)
five.add(seven)

var path: [Int] = []
var current: Node? = seven
while let node = current {
    path.append(node.value)
    current = node.parent
}
print("from 7 up to the root:", path)
```

```output
from 7 up to the root: [7, 5, 2, 1]
```

DSAKit's `TreeNode` has no parent pointer, and most problems don't need one. When one does, the usual trick is to walk the tree once and record each node's parent in a dictionary keyed by `ObjectIdentifier(node)`, which works with any class.

<Callout kind="gotcha" title="Swift gotchas with TreeNode">
- **`node.left == nil` works, but `a == b` doesn't compile.** Any optional can be compared with `nil`. But `TreeNode` isn't `Equatable`, so two nodes can't be compared with `==`. Use `===` to ask "same node?", or compare `a.value == b.value` to ask "same value?".
- **`let copy = root` is not a copy.** It's a second reference to the same tree. Copying a class-based tree means building new nodes for every node: a traversal.
- **A `let` node can still change.** `let root = TreeNode(1)` followed by `root.left = TreeNode(2)` compiles and runs, because `let` only fixes which object `root` refers to.
</Callout>
