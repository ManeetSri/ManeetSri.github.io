## Why it matters

Tree problems need a way to write a tree down as plain data: in a problem statement, in a test, or in a file. The standard way, used by LeetCode, interview platforms and every test in this course, is a **level-order array with `nil` gaps**, such as `[1, 2, 3, 4, 5, nil, 6, nil, nil, 7]`. You need to read it fluently, and building a tree from it is a neat first use of a queue on a tree. It's also exactly how saved tree data gets loaded back in an app.

## Reading the format

The array lists the tree **level by level, left to right**. The first entry is the root. After that, every node that exists gets **two entries** for its children, left then right, in the same order the nodes themselves appeared. A missing child is written `nil`. Here's the running example and its array:

```text
        1
       / \
      2   3            [1, 2, 3, 4, 5, nil, 6, nil, nil, 7]
     / \   \
    4   5   6
       /
      7
```

Read the array two entries at a time, handing each pair to the next node waiting for children:

| Entries | Belong to |
| --- | --- |
| `1` | the root |
| `2, 3` | children of 1 |
| `4, 5` | children of 2 |
| `nil, 6` | children of 3: no left child, a right child 6 |
| `nil, nil` | children of 4: it's a leaf |
| `7` | left child of 5 |

The array stops there, although 5's right child and the children of 6 and 7 still haven't been listed. They're all `nil`, and **trailing `nil`s are left off**. Writing them out, `[1, 2, 3, 4, 5, nil, 6, nil, nil, 7, nil, nil, nil, nil, nil]`, describes the same tree.

The order of the real values, 1 to 7, is exactly the tree's level order. Watch a level-order walk visit the nodes in the same order as the array:

```visual binaryTree
program: traversal
input:
  tree: [1, 2, 3, 4, 5, null, 6, null, null, 7]
  order: levelorder
```

## Missing nodes get no entries

The rule that trips people up: a `nil` is a missing node, and a missing node has **no children to list**. So nothing is written for them. Take `[1, nil, 2, nil, 3]`:

- 1 is the root, and its children are `nil` and 2.
- The missing left child gets no entries, so the next pair, `nil, 3`, belongs to **2**.

```text
    1
     \
      2
       \
        3
```

That's different from the **array layout of a complete tree**, which heaps use (M39). There, every position has a fixed slot: the children of index i are always at 2i + 1 and 2i + 2, whether or not anything is there. The same chain would need `[1, nil, 2, nil, nil, nil, 3]`, with slots for the missing node's missing children. For a chain 30 levels deep, that layout needs over a billion slots; the level-order format needs about 60 entries. Always check which format a problem means.

## Building the tree with a queue

The table above was a process: take the next node waiting for children, hand it the next two entries, and any new children join the end of the line to wait for theirs. Nodes receive their children in the same order they were created: **first in, first out**. That's a queue, the same structure that drives breadth-first search in [A preview of BFS](/dsa/learn/queue-bfs-preview).

1. If the array is empty or starts with `nil`, the tree is empty.
2. Make the root from the first entry and put it in the queue.
3. While entries remain: take the next parent from the front of the queue. Read one entry: if it's a value, make it the parent's left child and add that child to the queue. Read the next entry and do the same for the right child.

The queue is an array with a head index, as in [A queue with a head index](/dsa/learn/queue-head-index), so taking from the front is O(1). This version prints what each parent receives:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func text(_ value: Int?) -> String {
    value.map(String.init) ?? "nil"
}

func build(_ levelOrder: [Int?]) -> TreeNode? {
    guard let first = levelOrder.first, let rootValue = first else { return nil }
    let root = TreeNode(rootValue)
    var queue = [root]                       // nodes waiting for their children
    var head = 0
    var index = 1                            // the next entry to read
    while index < levelOrder.count && head < queue.count {
        let parent = queue[head]
        head += 1
        let leftEntry = levelOrder[index]
        let rightEntry = index + 1 < levelOrder.count ? levelOrder[index + 1] : nil
        if let value = leftEntry {
            parent.left = TreeNode(value)
            queue.append(parent.left!)
        }
        if let value = rightEntry {
            parent.right = TreeNode(value)
            queue.append(parent.right!)
        }
        index += 2
        let waiting = queue[head...].map { String($0.value) }.joined(separator: ", ")
        print("\(parent.value) gets \(text(leftEntry)) and \(text(rightEntry)); waiting: [\(waiting)]")
    }
    return root
}

let root = build([1, 2, 3, 4, 5, nil, 6, nil, nil, 7])!
print("root \(root.value), 3's right child \(root.right!.right!.value), 5's left child \(root.left!.right!.left!.value)")
```

```output
1 gets 2 and 3; waiting: [2, 3]
2 gets 4 and 5; waiting: [3, 4, 5]
3 gets nil and 6; waiting: [4, 5, 6]
4 gets nil and nil; waiting: [5, 6]
5 gets 7 and nil; waiting: [6, 7]
root 1, 3's right child 6, 5's left child 7
```

What to notice:

- The loop stops when the entries run out, even though 6 and 7 are still waiting. Their children were trailing `nil`s, left off the end.
- `guard let first = levelOrder.first, let rootValue = first` unwraps twice. `levelOrder.first` is an `Int??`: the outer optional is "is there a first entry?", the inner one is "is that entry `nil`?".
- `head < queue.count` protects against a malformed array with more entries than there are parents to receive them. Those extra entries are ignored rather than crashing.
- Every entry is read once and every node joins the queue once: **O(n) time** and O(n) space for n entries.

## Writing a tree back out

The reverse walks the tree in level order too, but queues **optional** nodes, `TreeNode?`. A real node writes its value and queues both of its children, even missing ones. A `nil` writes `nil` and queues nothing, because a missing node has no children to list. Finally, trailing `nil`s are trimmed:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func levelOrder(_ root: TreeNode?) -> [Int?] {
    guard let root else { return [] }
    var result: [Int?] = []
    var queue: [TreeNode?] = [root]
    var head = 0
    while head < queue.count {
        let node = queue[head]
        head += 1
        if let node {
            result.append(node.value)
            queue.append(node.left)
            queue.append(node.right)
        } else {
            result.append(nil)
        }
    }
    while let last = result.last, last == nil {
        result.removeLast()
    }
    return result
}

func text(_ entries: [Int?]) -> String {
    "[" + entries.map { $0.map(String.init) ?? "nil" }.joined(separator: ", ") + "]"
}

let chain = TreeNode(1, right: TreeNode(2, right: TreeNode(3)))
let example = TreeNode(1,
                       left: TreeNode(2, left: TreeNode(4), right: TreeNode(5, left: TreeNode(7))),
                       right: TreeNode(3, right: TreeNode(6)))
print(text(levelOrder(chain)))
print(text(levelOrder(example)))
print(levelOrder(TreeNode(8, left: TreeNode(4))))
```

```output
[1, nil, 2, nil, 3]
[1, 2, 3, 4, 5, nil, 6, nil, nil, 7]
[Optional(8), Optional(4)]
```

The last line shows why `text` exists: printing an `[Int?]` directly shows every value wrapped in `Optional(…)`. Tests don't mind, because they compare arrays, but for reading, map each entry to a string first.

Building and writing are inverses: build any array without trailing `nil`s, write it back out, and you get the same array. That round trip is how the tests check your builder.

## DSAKit's TreeNode.make

DSAKit's `TreeNode` has both directions built in, with the same algorithms: `TreeNode.make(_:)` builds, and the `levelOrder` property writes back. `description` uses the level order too, so printing a tree shows its array:

```swift
import DSAKit

let root = TreeNode.make([3, 9, 20, nil, nil, 15, 7])
print(root!)                          // [3, 9, 20, nil, nil, 15, 7]
print(root!.right!.left!.value)       // 15
print(TreeNode.make([]) == nil)       // true: the empty tree
print(TreeNode.make([1, 2, nil, nil, nil])!.levelOrder == [1, 2])   // true: trailing nils dropped
```

Every test in Part V builds its trees this way, so when a test fails, you can paste its array into a drawing like the ones above and see the tree it meant.

<Callout kind="gotcha" title="Common mistakes">
- **Writing entries for a missing node's children.** In this format, `nil` children of a `nil` node are never written. If you write them, every later pair shifts to the wrong parent.
- **Forgetting to queue the new children.** A child that never joins the queue never gets its own children, and the tree comes out too shallow.
- **Using `removeFirst()` as the queue.** It shifts every element, so building a big tree becomes O(n²), as [Why removeFirst() is O(n)](/dsa/learn/queue-why-not-removefirst) showed. Use a head index.
- **Printing `[Int?]` and reading `Optional(…)`.** It's not a bug in your tree. Map the entries to strings before printing.
</Callout>
