## Why it matters

Most tree operations walk from the root down one path, so they cost time proportional to the tree's **height**. The same seven values can sit in a tree three levels tall or seven levels tall, and that difference becomes 20 steps versus a million when there are a million values. The shape names in this lesson are how people talk about that difference. A heap is a *complete* tree, which is why it fits in an array (M39). AVL and red-black trees stay *balanced* (M38). And a binary search tree fed sorted data turns *degenerate*, which is why balancing exists at all (M37).

## Full trees

A binary tree is **full** when every node has either **no children or two**. Nobody has exactly one child.

```text
  Full                 Not full: 3 has one child
        1                    1
       / \                  / \
      2   3                2   3
     / \                  / \   \
    4   5                4   5   6
```

Full trees have a neat counting fact: **the leaves outnumber the internal nodes by exactly one**. Each internal node has two edges going down, so there are 2 × internal edges. But every node except the root has one edge going up, so there are also internal + leaves − 1 edges. Setting them equal gives leaves = internal + 1. The full tree above has 2 internal nodes (1 and 2) and 3 leaves.

Expression trees built from operators like `+` and `*` are full: every operator has exactly two operands, and every number is a leaf. That's why `2 + 3 * 4` has three numbers and two operators.

## Perfect trees

A tree is **perfect** when every internal node has two children **and** all the leaves are on the same level. Every level is completely filled:

```text
  Perfect, height 3
          1
        /   \
       2     3
      / \   / \
     4   5 6   7
```

Each level holds twice as many nodes as the one above it: 1, 2, 4, 8, and so on. Level d holds 2^d nodes. Add up the levels of a perfect tree of height h and you get 1 + 2 + 4 + … + 2^(h−1), which is **2^h − 1 nodes**, of which 2^(h−1) are leaves. That's the series sum from [Series sums and logarithms](/dsa/learn/math-series-logs), and it says something surprising: the bottom level holds just over half of all the nodes.

```swift run
for height in 1...6 {
    let nodes = (1 << height) - 1          // 2^h - 1
    let leaves = 1 << (height - 1)         // 2^(h-1)
    print("height \(height): \(nodes) nodes, \(leaves) leaves")
}
print("height 20:", (1 << 20) - 1, "nodes")
```

```output
height 1: 1 nodes, 1 leaves
height 2: 3 nodes, 2 leaves
height 3: 7 nodes, 4 leaves
height 4: 15 nodes, 8 leaves
height 5: 31 nodes, 16 leaves
height 6: 63 nodes, 32 leaves
height 20: 1048575 nodes
```

Twenty levels hold over a million nodes. That's the whole promise of trees: a path from the root to any node in a well-shaped tree is very short.

## Complete trees

A tree is **complete** when every level is completely filled **except possibly the last**, and the last level's nodes are packed as far **left** as possible.

```text
  Complete               Not complete: a gap before 6
          1                      1
        /   \                  /   \
       2     3                2     3
      / \   /                / \     \
     4   5 6                4   5     6
```

Read a complete tree level by level, left to right, and there are never any gaps until the nodes run out. That's what makes it fit perfectly in an array: put the nodes in level order, and the children of the node at index i are always at indexes 2i + 1 and 2i + 2. No pointers needed. Heaps use exactly this layout, as you'll see in [A complete tree in an array](/dsa/learn/heap-array-index).

The gap test is also how you check completeness in code: walk the tree level by level, counting missing children as gaps, and fail if a real node ever comes after a gap.

Every perfect tree is complete. A complete tree is perfect only when its last level happens to be full.

## Balanced trees

A tree is **balanced** (strictly, *height-balanced*) when, at **every** node, the heights of the left and right subtrees differ by at most 1.

```text
  Balanced                  Not balanced
        1                         1
       / \                      /   \
      2   3                    2     3
     / \   \                  /     /
    4   5   6                4     6
         \                  /     /
          7                5     7
```

On the left, every node's two subtrees differ in height by at most 1: at 2, for example, the left subtree has height 1 and the right has height 2. On the right, the root looks fine, because both of its subtrees are 3 levels tall. But at 2, the left subtree has height 2 and the right subtree height 0. They differ by 2, so the tree isn't balanced. Balance has to hold at every node, not only the root.

Balance matters because it caps the height: a balanced tree of n nodes is at most about 1.44 × log₂ n levels tall, so it stays O(log n). Complete trees are always balanced. Checking balance is a problem in [Balanced, same and symmetric trees](/dsa/learn/bt-balanced-same-symmetric), and keeping a tree balanced as you insert is what AVL trees do in [AVL trees: insert and delete](/dsa/learn/bal-avl).

## Degenerate trees

A tree is **degenerate** when no node has two children. It's a single chain: in effect, a linked list with extra `nil` pointers. When every node's child is on the same side, the tree is also called **skewed** (left-skewed or right-skewed).

```text
  Right-skewed         Zigzag
  1                    1
   \                  /
    2                2
     \                \
      3                3
       \              /
        4            4
```

A degenerate tree of n nodes has height n, the worst possible. Every operation that walks down the tree becomes O(n), and every recursive function on it recurses n levels deep. Insert the values 1, 2, 3, 4 in that order into a binary search tree and you get exactly the right-skewed tree above: [Why unbalanced BSTs degrade to O(n)](/dsa/learn/bst-degenerate) is about that trap.

## How tall can a tree of n nodes be?

Put the extremes together. The tallest tree with n nodes is a chain, with height **n**. The shortest packs every level full. A tree of height h holds at most 2^h − 1 nodes, so n ≤ 2^h − 1, which rearranges to h ≥ log₂(n + 1). Heights are whole numbers, so:

**A binary tree with n nodes has height between ⌈log₂(n + 1)⌉ and n.**

```swift run
// The smallest height that can hold n nodes: the first h with 2^h - 1 >= n
func shortestHeight(_ n: Int) -> Int {
    var height = 0
    while (1 << height) - 1 < n {
        height += 1
    }
    return height
}

for n in [1, 7, 8, 100, 1_000, 1_000_000] {
    print("\(n) nodes: height between \(shortestHeight(n)) and \(n)")
}
```

```output
1 nodes: height between 1 and 1
7 nodes: height between 3 and 7
8 nodes: height between 4 and 8
100 nodes: height between 7 and 100
1000 nodes: height between 10 and 1000
1000000 nodes: height between 20 and 1000000
```

Seven nodes fit exactly in 3 full levels; the eighth needs a fourth level. And for a million nodes, the gap between the best shape and the worst is 20 versus 1,000,000. Every O(height) tree operation inherits that gap.

## How the shapes relate

| | Every node 0 or 2 children | Levels filled left to right | Heights differ ≤ 1 everywhere | Height |
| --- | --- | --- | --- | --- |
| **Perfect** | yes | yes | yes | exactly log₂(n + 1) |
| **Complete** | not always | yes | yes | ⌈log₂(n + 1)⌉ |
| **Balanced** | not always | not always | yes | O(log n) |
| **Full** | yes | not always | not always | anywhere from log to about n/2 |
| **Degenerate** | no (beyond tiny trees) | no (beyond tiny trees) | no (beyond 2 nodes) | n |

A tree can have several of these properties at once: a perfect tree is full, complete and balanced. Tiny trees blur the lines, too: a root with one left child is complete, degenerate and balanced all at the same time.

Here are the full-tree test and the leaf-counting fact, checked on two full trees and one that isn't:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func isFull(_ node: TreeNode?) -> Bool {
    guard let node else { return true }
    if (node.left == nil) != (node.right == nil) {
        return false                         // exactly one child
    }
    return isFull(node.left) && isFull(node.right)
}

func counts(_ node: TreeNode?) -> (inner: Int, leaves: Int) {
    guard let node else { return (0, 0) }
    if node.left == nil && node.right == nil { return (0, 1) }
    let left = counts(node.left)
    let right = counts(node.right)
    return (1 + left.inner + right.inner, left.leaves + right.leaves)
}

let trees = [
    TreeNode(1, left: TreeNode(2, left: TreeNode(4), right: TreeNode(5)), right: TreeNode(3)),
    TreeNode(1, left: TreeNode(2), right: TreeNode(3, left: TreeNode(4), right: TreeNode(5, left: TreeNode(6), right: TreeNode(7)))),
    TreeNode(1, left: TreeNode(2, left: TreeNode(4), right: TreeNode(5)), right: TreeNode(3, right: TreeNode(6))),
]
for tree in trees {
    let (inner, leaves) = counts(tree)
    print("full: \(isFull(tree)), internal \(inner), leaves \(leaves)")
}
```

```output
full: true, internal 2, leaves 3
full: true, internal 3, leaves 4
full: false, internal 3, leaves 3
```

What to notice:

- `(node.left == nil) != (node.right == nil)` is true exactly when one child is missing and the other isn't: an "exclusive or" of the two tests.
- The tuple label is `inner` rather than `internal`, because `internal` is a Swift keyword: it's an access level, from [Access control](/dsa/learn/swift-access-control).
- Both full trees have one more leaf than internal node, whatever their shape. The third tree breaks the rule because node 3 has a single child.

<Callout kind="gotcha" title="Common mistakes">
- **Checking balance only at the root.** The root's subtrees can have equal heights while a node further down is badly lopsided. Balance is a property of every node.
- **Confusing full with complete.** Full is about each node's number of children. Complete is about levels filling from the left. `[1, 2, 3, 4]` (1 with children 2 and 3, and 4 under 2) is complete but not full; a full tree can have big gaps on the left.
- **Names vary between books.** Some call a perfect tree "full" or "complete". When a problem uses one of these words, check its definition or its examples.
</Callout>
