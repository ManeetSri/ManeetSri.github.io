## Why it matters

A 1920 × 1080 screen has an aspect ratio of 16:9 because both sides share a factor of 120. A recipe that serves 18 out of 48 guests is 3/8 of a batch. Two repeating timers, one every 4 seconds and one every 6, fire together every 12 seconds. The first two are the **greatest common divisor** at work and the third is the **least common multiple**. In DSA they appear in fraction and ratio problems, in rotating arrays, and in plenty of number puzzles. Best of all, Euclid's algorithm for the GCD is short, very fast, and the oldest algorithm still in everyday use.

## The greatest common divisor

The **greatest common divisor**, written gcd(a, b), is the largest number that divides both a and b.

Take 48 and 18:

- Divisors of 48: 1, 2, 3, 4, 6, 8, 12, 16, 24, 48
- Divisors of 18: 1, 2, 3, 6, 9, 18
- Common divisors: 1, 2, 3, 6

So gcd(48, 18) = 6. When the gcd is 1, as for 8 and 15, the numbers are called **coprime**: they share no factor except 1.

You could find the gcd by trying every number from min(a, b) downwards until one divides both. That's O(min(a, b)), and for numbers near 10¹⁸ it would never finish. Euclid found something far better.

## Euclid's idea

The key fact is:

> gcd(a, b) = gcd(b, a % b)

Why is that true? Write a = q × b + r, where r is `a % b`.

- Anything that divides both a and b also divides r = a − q × b.
- Anything that divides both b and r also divides a = q × b + r.

So the pairs (a, b) and (b, r) have exactly the same common divisors, and therefore the same greatest one. But (b, r) is a smaller pair, since r is less than b. Keep replacing (a, b) with (b, a % b) until the second number is 0. Then stop, because gcd(a, 0) = a: every number divides 0, so the largest common divisor is a itself.

For 48 and 18: gcd(48, 18) = gcd(18, 12) = gcd(12, 6) = gcd(6, 0) = 6.

## Watching it run

Step through Euclid's algorithm and watch each remainder become the next divisor:

```visual traceTable
program: gcd
input: { first: 48, second: 18 }
```

Each row is one pass. The remainder moves left into `b`, and `b` moves into `a`. Here's a bigger example, gcd(1071, 462), as a trace table:

| a | b | a % b |
| --- | --- | --- |
| 1071 | 462 | 147 |
| 462 | 147 | 21 |
| 147 | 21 | 0 |
| 21 | 0 | stop |

Three passes, and the answer is 21. Checking by hand: 1071 = 21 × 51 and 462 = 21 × 22.

## The code

Swift's standard library has no `gcd` function, so you'll write this one often. It's worth knowing by heart:

```swift run
func gcd(_ first: Int, _ second: Int) -> Int {
    var a = abs(first)
    var b = abs(second)
    while b != 0 {
        (a, b) = (b, a % b)
    }
    return a
}

print(gcd(48, 18), gcd(1071, 462), gcd(17, 5))
print(gcd(18, 48), gcd(0, 9), gcd(0, 0), gcd(-12, 18))
```

```output
6 21 1
6 9 0 6
```

`(a, b) = (b, a % b)` updates both variables at once using a tuple. The right-hand side is worked out completely, using the old values, before either variable changes. It's a shorter way to write the three lines with `remainder` in the visualiser.

What to notice:

- **Order doesn't matter.** For gcd(18, 48), the first pass gives (48, 18 % 48), which is (48, 18). The numbers swap themselves.
- **Zero.** gcd(0, 9) is 9, and gcd(0, 0) is 0 by convention.
- **Negative numbers.** Divisors don't care about signs, so `abs` makes both values non-negative first.

The recursive version is a direct translation of Euclid's fact:

```swift
func gcd(_ a: Int, _ b: Int) -> Int {
    b == 0 ? a : gcd(b, a % b)
}
```

## Why it's so fast

Every **two** passes, the larger number at least halves. Here's why: after one pass you have (b, a % b), and `a % b` is always less than half of a.

- If b is at most a / 2, then `a % b` is less than b, so it's less than a / 2.
- If b is more than a / 2, then b goes into a once, and `a % b` is a − b, which is less than a / 2.

Halving every two steps means at most about 2 log₂ n passes, so Euclid's algorithm is **O(log min(a, b))**. The slowest inputs are neighbouring Fibonacci numbers, and even for two numbers near 3 × 10¹⁸ that's only 88 passes.

## The GCD of a list

The gcd of several numbers can be built up one at a time: gcd(a, b, c) = gcd(gcd(a, b), c). Since gcd(0, x) = x, 0 is a natural starting value, which makes this a perfect fit for `reduce`:

```swift run
func gcd(_ first: Int, _ second: Int) -> Int {
    var a = abs(first)
    var b = abs(second)
    while b != 0 {
        (a, b) = (b, a % b)
    }
    return a
}

print([12, 18, 30].reduce(0, gcd))
print([7, 14, 22].reduce(0, gcd))
```

```output
6
1
```

Once the running gcd reaches 1, it stays 1, so a loop version can stop early.

## The least common multiple

The **least common multiple**, lcm(a, b), is the smallest positive number that both a and b divide. The multiples of 4 are 4, 8, 12, 16… and of 6 are 6, 12, 18… The first they share is 12, so lcm(4, 6) = 12.

There's no need to search. For positive a and b:

```text
gcd(a, b) × lcm(a, b) = a × b
```

Check it with 4 and 6: 2 × 12 = 24 = 4 × 6. So lcm(a, b) = a × b / gcd(a, b). But write it in a different order in code:

```swift run
func gcd(_ first: Int, _ second: Int) -> Int {
    var a = abs(first)
    var b = abs(second)
    while b != 0 {
        (a, b) = (b, a % b)
    }
    return a
}

func lcm(_ a: Int, _ b: Int) -> Int {
    a / gcd(a, b) * b
}

print(lcm(4, 6), lcm(21, 6))
print(lcm(3_000_000_000_000, 3_000_000_000_000))
```

```output
12 42
3000000000000
```

**Divide first, then multiply.** `a / gcd(a, b)` is always a whole number, so nothing is lost. The order matters for overflow: in the last line, `a * b` would be 9 × 10²⁴, far beyond `Int.max`, and would trap, even though the lcm itself is only 3 × 10¹².

## LCMs grow fast

Each new number can multiply the lcm, so the lcm of a list quickly gets huge. lcm(1, 2, …, 10) is 2,520 and lcm(1, …, 20) is 232,792,560. When the result might not fit, check each multiplication:

```swift run
func gcd(_ first: Int, _ second: Int) -> Int {
    var a = abs(first)
    var b = abs(second)
    while b != 0 {
        (a, b) = (b, a % b)
    }
    return a
}

var total = 1
var n = 1
while true {
    let next = n + 1
    let step = (total / gcd(total, next)).multipliedReportingOverflow(by: next)
    if step.overflow {
        print("lcm(1...\(next)) overflows")
        break
    }
    total = step.partialValue
    n = next
}
print("lcm(1...\(n)) = \(total)")
```

```output
lcm(1...43) overflows
lcm(1...42) = 219060189739591200
```

Even with 64 bits, the lcm of the numbers 1 to 43 doesn't fit.

## Reducing fractions

To write a fraction in its lowest terms, divide the top and bottom by their gcd. gcd(18, 48) = 6, so 18/48 = 3/8. The same move turns 1920 × 1080 into 16:9, because gcd(1920, 1080) = 120. You'll use this in *Probability and expected value*, near the end of this module, to keep answers exact.

<Callout kind="gotcha" title="Common mistakes">
- **`a * b / gcd(a, b)`** overflows long before the answer does. Write `a / gcd(a, b) * b`.
- **Forgetting that Swift has no `gcd`.** It isn't in the standard library or Foundation, so keep the five-line version in your head.
- **Recursion on the wrong argument.** `gcd(b, a % b)` stops when `b == 0`. Testing `a == 0` instead, or writing `b % a`, gives wrong answers or divides by zero.
</Callout>
