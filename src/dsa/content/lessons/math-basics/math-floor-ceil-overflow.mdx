## Why it matters

How many pages do 10 search results need at 3 per page? How many 50-seat buses for 120 people? Which 256-pixel map tile holds the point at x = −1? Each is a division that has to round in a particular direction, and Swift's `/` doesn't always round the way the problem wants. Rounding questions also go hand in hand with overflow, because the standard rounding tricks add numbers together. This lesson pins down **floor** and **ceiling** division for every sign, then gathers the overflow traps of this module into one checklist.

## Floor and ceiling

Two ways to turn any number into a whole number:

- The **floor** of x, written ⌊x⌋, is the largest whole number that's at most x. It rounds **down**, towards minus infinity.
- The **ceiling** of x, written ⌈x⌉, is the smallest whole number that's at least x. It rounds **up**, towards plus infinity.

| x | ⌊x⌋ | ⌈x⌉ |
| --- | --- | --- |
| 3.5 | 3 | 4 |
| 4 | 4 | 4 |
| −3.5 | −4 | −3 |

Picture a number line. Floor steps left to the nearest whole number; ceiling steps right. Whole numbers stay where they are. For negative numbers, "down" means *more* negative, which is where mistakes creep in.

## What Swift's / actually does

Integer division in Swift **truncates towards zero**: it drops the fraction, whatever the sign. That's neither floor nor ceiling in general:

- For a **positive** result, truncating is the same as the floor: 7 / 2 = 3.
- For a **negative** result, truncating is the same as the ceiling: −7 / 2 = −3, while the floor of −3.5 is −4.

So you get the floor for free only when both numbers have the same sign. Everything else needs a small correction.

## Ceiling division for positive numbers

You met the classic trick in [Arithmetic, integer division and remainder](/dsa/learn/swift-arithmetic): for positive a and b, ⌈a / b⌉ is `(a + b - 1) / b`. Adding `b - 1` pushes any leftover past the next multiple of b.

It has a hidden flaw: the addition can overflow when a is close to `Int.max`. Checking the remainder instead never adds anything big:

```swift run
func pages(_ items: Int, _ perPage: Int) -> Int {
    items / perPage + (items % perPage == 0 ? 0 : 1)
}

print(pages(10, 3), pages(9, 3), pages(0, 3))
print(pages(Int.max - 1, 3))
print((Int.max - 1).addingReportingOverflow(3 - 1).overflow)
```

```output
4 3 0
3074457345618258602
true
```

10 items need 4 pages; 9 fit exactly in 3. The last line confirms that `(a + b - 1)` would overflow for that huge a, while the remainder version is fine. In everyday problems `(a + b - 1) / b` is perfectly good. Just know where it breaks.

Ceiling division turns up whenever you count containers: buses for people, pages for items, and the hours to finish a job at a given speed. That last one is the heart of "binary search on the answer" problems in M29, where you'll compute ⌈pile / speed⌉ thousands of times.

## Floor and ceiling for any signs

When a or b can be negative, start from Swift's truncated quotient and correct it:

- Truncation and floor differ only when the division isn't exact **and** the true answer is negative, meaning a and b have opposite signs. Then the floor is one less.
- Truncation and ceiling differ only when the division isn't exact **and** the answer is positive, meaning a and b have the same sign. Then the ceiling is one more.

```swift run
func floorDiv(_ a: Int, _ b: Int) -> Int {
    var q = a / b
    if a % b != 0 && (a < 0) != (b < 0) {
        q -= 1
    }
    return q
}

func ceilDiv(_ a: Int, _ b: Int) -> Int {
    var q = a / b
    if a % b != 0 && (a < 0) == (b < 0) {
        q += 1
    }
    return q
}

for (a, b) in [(7, 2), (-7, 2), (7, -2), (-7, -2), (-6, 3)] {
    print(a, b, a / b, floorDiv(a, b), ceilDiv(a, b))
}
```

```output
7 2 3 3 4
-7 2 -3 -4 -3
7 -2 -3 -4 -3
-7 -2 3 3 4
-6 3 -2 -2 -2
```

Each row shows a, b, then the truncated, floor and ceiling quotients. When the division is exact, as for −6 / 3, all three agree.

`(a < 0) != (b < 0)` is a neat way to say "exactly one of them is negative". Comparing two `Bool` values with `!=` gives true when they differ.

### Where negative floors matter

A map is split into tiles 10 units wide: tile 0 covers x from 0 to 9, tile −1 covers −10 to −1. Which tile holds x = −1?

```swift run
func floorDiv(_ a: Int, _ b: Int) -> Int {
    var q = a / b
    if a % b != 0 && (a < 0) != (b < 0) {
        q -= 1
    }
    return q
}

print(-1 / 10, floorDiv(-1, 10))
print(floorDiv(-10, 10), floorDiv(-11, 10), floorDiv(25, 10))
```

```output
0 -1
-1 -2 2
```

Plain `/` puts x = −1 in tile 0, alongside x = 5, so tile 0 would be 19 units wide. The floor gives tile −1, which is right. Floor division always pairs with the "safe modulo" from [Modular arithmetic](/dsa/learn/math-modular-arithmetic): for positive b, `((a % b) + b) % b` is the position *within* the tile, and `floorDiv(a, b) * b + ((a % b) + b) % b == a` always holds.

Python's `//` operator is floor division, so code translated from Python needs `floorDiv` wherever negatives are possible.

## What about Double?

For `Double`, Swift can round directly with `rounded(.down)` and `rounded(.up)`, and Foundation has `floor` and `ceil`:

```swift run
print((7.0 / 2).rounded(.down), (-7.0 / 2).rounded(.down), (-7.0 / 2).rounded(.up))
print(Int(Double(9_007_199_254_740_993)))
```

```output
3.0 -4.0 -3.0
9007199254740992
```

That's tempting for integers too: convert, divide, round, convert back. Don't. A `Double` holds whole numbers exactly only up to 2⁵³, about 9 × 10¹⁵, as the second line shows: converting 9,007,199,254,740,993 to `Double` loses the final 1. Beyond that, results can be off by one or more. Integer `floorDiv` and `ceilDiv` are exact for every `Int`.

## The overflow checklist

This module has met overflow again and again. Here's the full list in one place, to run through whenever a problem's numbers are large. `Int.max` is about 9.2 × 10¹⁸.

| Situation | Risk | Safe version |
| --- | --- | --- |
| Sum of many values | 10⁵ values up to 10⁹ is 10¹⁴: fine in `Int`, not in `Int32` | Use `Int` everywhere |
| Product of values | Two values up to 10⁹ fit; three don't | Reduce modulo m after each multiplication |
| Midpoint | `(low + high) / 2` adds two large values | `low + (high - low) / 2` |
| Triangle numbers | `n * (n + 1) / 2` for n in the billions | Halve the even factor first |
| Ceiling | `(a + b - 1) / b` with a near `Int.max` | `a / b + (a % b == 0 ? 0 : 1)` |
| LCM | `a * b / gcd(a, b)` | `a / gcd(a, b) * b`, and check the multiply |
| Factorials and powers | 21! and 2⁶³ don't fit | Work modulo m, or check with `multipliedReportingOverflow` |
| Square root loops | `i * i <= n` for n near `Int.max` | `i <= n / i` |
| Comparing by subtracting | `a - b < 0` overflows for distant values | Compare directly: `a < b` |

Three operations trap on a single special value: `abs(Int.min)`, `-Int.min` and `Int.min / -1`. Each would produce +9,223,372,036,854,775,808, which is one more than `Int.max`. If `Int.min` can reach your code, use `.magnitude`, which returns a `UInt`, or handle it separately.

<Callout kind="tip" title="Estimate before you code">
Before writing a loop, write down the largest value each variable can hold. "n is up to 10⁵ and values up to 10⁹, so the sum is at most 10¹⁴" takes ten seconds and catches most overflow bugs before they exist. If an estimate comes close to 10¹⁸, look for a safer formula or a modulus. Recent Swift versions also have a 128-bit `Int128` type, but it needs macOS 15 or iOS 18 and later, so check before relying on it.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: truncation, not floor">
`-7 / 2` is −3 in Swift, not −4. If a formula or a translated solution assumes floor division, test it with a negative input, such as a negative coordinate or a time before midnight.
</Callout>
