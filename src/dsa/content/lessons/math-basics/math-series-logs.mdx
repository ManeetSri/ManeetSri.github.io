## Why it matters

When you analyse an algorithm, a few sums come up again and again. A loop whose inner part runs 1, then 2, then 3… times adds up to an **arithmetic series**, and that's where O(n²) comes from. An array that doubles its storage when full costs a **geometric series**, which is why `append` is cheap on average. And anything that halves its problem at every step, like binary search, Euclid's algorithm and fast power, takes a **logarithmic** number of steps. This lesson gives you those three tools, each with a formula, a worked example and the Swift to check it.

## Arithmetic series: 1 + 2 + … + n

The story goes that a young Carl Friedrich Gauss was told to add up the numbers from 1 to 100 to keep him busy. He was done in seconds. Write the sum forwards and backwards and pair the columns:

```text
  1 +  2 +  3 + … + 99 + 100
100 + 99 + 98 + … +  2 +   1
---------------------------
101 + 101 + 101 + … + 101 + 101     (100 columns)
```

Each of the 100 columns adds to 101, so twice the sum is 100 × 101, and the sum is 5,050. In general:

```text
1 + 2 + 3 + … + n = n × (n + 1) / 2
```

The same pairing works for any **arithmetic series**, where each term goes up by the same step: the sum is (first + last) × count / 2. For 3 + 7 + 11 + … + 39, the step is 4, the count is (39 − 3) / 4 + 1 = 10, and the sum is (3 + 39) × 10 / 2 = 210.

```swift run
var total = 0
for i in 1...100 {
    total += i
}
print(total, 100 * 101 / 2)

var sum = 0
for x in stride(from: 3, through: 39, by: 4) {
    sum += x
}
print(sum, (3 + 39) * 10 / 2)
```

```output
5050 5050
210 210
```

### Where it shows up

**Triangular loops.** This loop visits every pair of positions i before j:

```swift run
let n = 10
var pairs = 0
for i in 0..<n {
    for _ in (i + 1)..<n {
        pairs += 1
    }
}
print(pairs)
```

```output
45
```

The inner loop runs 9, 8, 7, …, 0 times, a total of 0 + 1 + … + 9 = 9 × 10 / 2 = 45. In general it's n(n − 1) / 2, which is about n² / 2, so the loop is **O(n²)**. Halving the work of a full n × n loop doesn't change its growth class. (It's also C(n, 2), the number of pairs, from the previous lesson.)

**The missing number.** An array holds every number from 0 to n except one. Which is missing? The full set adds to n(n + 1) / 2, so the gap is that minus the actual sum, in O(n) time and O(1) space:

```swift run
let numbers = [3, 0, 4, 1, 5]
let n = numbers.count
print(n * (n + 1) / 2 - numbers.reduce(0, +))
```

```output
2
```

### Watch for overflow

`n * (n + 1) / 2` multiplies before it halves. For n = 4,000,000,000, the answer, 8 × 10¹⁸, fits in an `Int`, but n × (n + 1), about 1.6 × 10¹⁹, doesn't. One of n and n + 1 is always even, so halve that one first:

```swift run
func triangle(_ n: Int) -> Int {
    n % 2 == 0 ? (n / 2) * (n + 1) : n * ((n + 1) / 2)
}

print(triangle(100))
print(triangle(4_000_000_000))
```

```output
5050
8000000002000000000
```

## Geometric series: doubling and halving

In a **geometric series** each term is the previous one times a fixed ratio. The most important one doubles:

```text
1 + 2 + 4 + … + 2ᵏ = 2ᵏ⁺¹ − 1
```

1 + 2 + 4 + 8 = 15 = 16 − 1. In binary it's obvious: 1111₂ is one less than 10000₂. The general formula, for any ratio r other than 1, is (r^(k+1) − 1) / (r − 1).

The useful takeaway is that **a doubling series is less than twice its last term**. Run it backwards and you get the halving version:

```text
n + n/2 + n/4 + n/8 + … < 2n
```

Two places you'll use this:

**Growing arrays.** When a Swift array runs out of room, it allocates storage about twice as big and copies everything across. Appending 1,000 elements, starting from a capacity of 1, copies 1 + 2 + 4 + … + 512 elements in total:

```swift run
var capacity = 1
var count = 0
var copies = 0
for _ in 0..<1000 {
    if count == capacity {
        copies += count
        capacity *= 2
    }
    count += 1
}
print(copies, capacity)
```

```output
1023 1024
```

Fewer than 2 copies per element, so each `append` is O(1) on average. That's the amortised analysis from [Amortised analysis](/dsa/learn/bigo-amortised), and the geometric series is why it works. (Swift's real growth factor and starting capacity differ a little, but the idea is the same.)

**Loops whose work halves.** If an algorithm does n steps of work, then n / 2, then n / 4, and so on, the total is less than 2n, so it's O(n), not O(n log n). Quickselect, in Part IV, relies on this.

## Logarithms: counting halvings

A **logarithm** answers the question "how many times?".

> log₂ n is the number of times you double 1 to reach n, which is the same as the number of times you halve n to reach 1.

2¹⁰ = 1,024, so log₂ 1,024 = 10: halve 1,024 ten times and you're at 1. When n isn't a power of two, log₂ n isn't a whole number, but the halving count is still close to it:

```swift run
var m = 1_000_000
var halvings = 0
while m > 1 {
    m /= 2
    halvings += 1
}
print(halvings)
```

```output
19
```

log₂ 1,000,000 is about 19.93, and integer halving takes 19 steps: the whole-number part, written ⌊log₂ n⌋.

Because 2¹⁰ is about 1,000, every factor of 1,000 adds about 10 to log₂ n. That gives a table worth memorising:

| n | log₂ n, roughly |
| --- | --- |
| 1,000 | 10 |
| 1,000,000 | 20 |
| 1,000,000,000 | 30 |
| 10¹⁸ | 60 |

That's why binary search through a billion sorted items needs only about 30 comparisons, and fast power with exponent 10¹⁸ needs about 60 squarings. Drag the slider and switch to the log scale to see how flat O(log n) is next to O(n):

### Rules worth knowing

You won't need much algebra, but these three come up in analysis:

- **Products become sums:** log(a × b) = log a + log b.
- **Powers become multiples:** log(aᵏ) = k × log a. So log₂ (n²) = 2 log₂ n.
- **Changing base is a constant factor:** log₁₀ n = log₂ n / log₂ 10, and log₂ 10 is about 3.32. That's why Big-O writes O(log n) without saying which base: they differ only by a constant, and Big-O drops constants.

The number of digits of n in base b is one more than the whole-number part of its base-b logarithm. A million has ⌊log₁₀ 10⁶⌋ + 1 = 7 decimal digits and ⌊19.93⌋ + 1 = 20 binary digits, matching what you saw in [Number systems and conversion](/dsa/learn/math-number-systems).

## Logarithms in Swift

Foundation provides `log2`, `log10` and `log` (the natural logarithm, base e ≈ 2.718), all working on `Double`:

```swift run
import Foundation

print(log2(1024.0), log10(1000.0))
print(log(1000.0) / log(10.0))
print(Int(log(1000.0) / log(10.0)))
```

```output
10.0 3.0
2.9999999999999996
2
```

The last two lines are a trap. Mathematically log(1000) / log(10) is exactly 3, but floating-point rounding gives a hair less, and `Int(...)` truncates it to 2. Whenever you need a whole-number logarithm, compute it with integers: count halvings with a loop, as above, or count digits with the peel loop from [Digit manipulation](/dsa/learn/math-digits). There's also a one-line bit trick, `Int.bitWidth - n.leadingZeroBitCount - 1`, which gives ⌊log₂ n⌋ for positive n and which M16 explains.

## The harmonic series

One more sum explains a pattern you've already seen twice:

```text
1 + 1/2 + 1/3 + 1/4 + … + 1/n  ≈  ln n
```

It grows without limit, but only as fast as the natural logarithm. For a million terms it's about 14.4, while ln 10⁶ is about 13.8. Multiply through by n:

```text
n/1 + n/2 + n/3 + … + n/n  ≈  n ln n
```

That's exactly the loop in [Divisors in O(√n)](/dsa/learn/math-divisors) that visits every multiple of every d up to n, and why it's O(n log n). The Sieve of Eratosthenes does the same but only for primes d, and the sum over primes of 1/p grows even more slowly, like ln ln n, which gives the sieve its O(n log log n).

<Callout kind="gotcha" title="Common mistakes">
- **Truncating a floating-point log.** `Int(log10(Double(n)))` can be off by one for exact powers of the base. Count with integers instead.
- **Multiplying before halving.** `n * (n + 1) / 2` overflows for n in the billions even when the answer fits. Halve the even factor first.
- **Halvings versus digits.** Halving n down to 1 takes ⌊log₂ n⌋ steps, but n has ⌊log₂ n⌋ + 1 binary digits. Check which one a problem needs with a small case, like n = 8.
</Callout>
