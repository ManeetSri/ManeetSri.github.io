## Why it matters

Some range questions have no neat summary to store. "How many **different** species were seen between survey point 300 and point 9,000?" You can't combine the answers for two halves: a species seen in both halves would be counted twice, and knowing the counts doesn't tell you which species overlap. No segment tree, no sparse table, no prefix sums. But one thing is easy: if you already know the answer for a range, **adding or removing one element at either end** changes it in O(1), with a count per species. **Mo's algorithm** exploits that. It reorders all the queries so that a sliding window, moving from one query's range to the next, travels a total distance of only O((n + q)√n). It's offline (you need every query before you start), it's a staple of competitive programming, and it turns "impossible to summarise" into "a few lines".

## A window that slides between queries

Keep a **window** `currentLeft...currentRight` and the answer for it. To answer a query `left...right`, move the window's ends there one step at a time, updating the answer as each element enters or leaves:

- `add(i)`: element i enters the window.
- `remove(i)`: element i leaves it.

For distinct values, keep `count[v]`, how many copies of v are in the window, plus `distinct`, how many values have a count above zero:

- `add`: increment `count[v]`; if it became 1, a new value arrived, so `distinct += 1`.
- `remove`: decrement `count[v]`; if it became 0, its last copy left, so `distinct -= 1`.

Both are O(1). The cost of a query is the number of steps its two ends move. So the cost of the whole batch depends entirely on the **order** of the queries. In the order given, every query could send both ends across the whole array: O(n) per query, O(n · q) in total, no better than scanning each range.

## Mo's order: by block, then by right end

Cut the indexes into blocks of size b ≈ √n, as in the last lesson, and sort the queries by:

1. the block their **left** end falls in, then
2. their **right** end, increasing.

Then answer them in that order, and write each answer back to the query's **original** position.

```swift run
// Mo's algorithm: the number of distinct values in each range, answered offline
func distinctCounts(_ values: [Int], _ queries: [(left: Int, right: Int)]) -> [Int] {
    var blockSize = 1
    while blockSize * blockSize < values.count { blockSize += 1 }

    // Sort the query numbers by (block of left, right)
    let order = queries.indices.sorted { a, b in
        let blockA = queries[a].left / blockSize, blockB = queries[b].left / blockSize
        return blockA != blockB ? blockA < blockB : queries[a].right < queries[b].right
    }
    print("block size \(blockSize), order:", order.map { "\(queries[$0].left)...\(queries[$0].right)" })

    var count = [Int](repeating: 0, count: (values.max() ?? 0) + 1)   // how often each value is in the window
    var distinct = 0
    func add(_ index: Int) {
        count[values[index]] += 1
        if count[values[index]] == 1 { distinct += 1 }       // a value we didn't have
    }
    func remove(_ index: Int) {
        count[values[index]] -= 1
        if count[values[index]] == 0 { distinct -= 1 }       // its last copy left
    }

    var answers = [Int](repeating: 0, count: queries.count)
    var currentLeft = 0
    var currentRight = -1                                    // the window starts empty
    for q in order {
        let (left, right) = queries[q]
        while currentLeft > left { currentLeft -= 1; add(currentLeft) }      // grow first...
        while currentRight < right { currentRight += 1; add(currentRight) }
        while currentLeft < left { remove(currentLeft); currentLeft += 1 }   // ...then shrink
        while currentRight > right { remove(currentRight); currentRight -= 1 }
        answers[q] = distinct                                // stored in the query's original place
    }
    return answers
}

let birds = [3, 1, 3, 2, 1, 3, 4, 2]
let surveys = [(left: 0, right: 4), (left: 5, right: 7), (left: 1, right: 3), (left: 2, right: 6), (left: 0, right: 7)]
print("answers:", distinctCounts(birds, surveys))
```

```output
block size 3, order: ["1...3", "0...4", "2...6", "0...7", "5...7"]
answers: [3, 3, 3, 4, 4]
```

What to notice:

- With 8 elements the block size is 3. Four queries start in block 0 (left ends 0, 1, 2, 0), and they're answered in order of their right ends: 3, 4, 6, 7. Then the one query in block 1.
- Within block 0, the **right end only moves forward**: 3, 4, 6, 7. The left end jumps around, but only inside one block, a few steps at a time.
- The answers come back in the order the queries were asked: `[3, 3, 3, 4, 4]` matches `0...4`, `5...7`, `1...3`, `2...6`, `0...7`. That's why the sort works on query **numbers** (`indices`), not on the queries themselves.
- `currentRight` starts at −1, so the window `0...-1` is empty. The first query's loops add exactly its elements.

### Follow the window

Here is every step the window takes in that run. "add 0, 1, 2, 3" means the right end moved over indexes 0 to 3, adding each one:

```text
query   window before   steps                          window after   distinct
1...3   empty           add 0, 1, 2, 3; remove 0       1...3          3
0...4   1...3           add 0; add 4                   0...4          3
2...6   0...4           add 5, 6; remove 0, 1          2...6          4
0...7   2...6           add 1, 0; add 7                0...7          4
5...7   0...7           remove 0, 1, 2, 3, 4           5...7          3
```

That's 19 steps for five answers. In the order the queries were asked, the same window would take 28 steps, because it would swing from `0...4` out to `5...7` and back to `1...3`. With eight elements the saving is small; the next section shows how it grows.

### Grow before you shrink

The four `while` loops come in a deliberate order: the two that **grow** the window run before the two that **shrink** it. If you shrink first, the left end can overtake the right end, the window becomes "negative", and `remove` takes out elements that were never added: counts go below zero, and `distinct` goes wrong. Growing first means the window always contains the new query's range before anything leaves, so every `remove` matches an earlier `add`.

## Why the order makes it fast

Count the total movement of each end separately, with b = √n:

- **The right end.** Inside one block of left ends, queries are sorted by right end, so the right end only moves forward: at most n steps per block. Moving to the next block it may jump back, another n at most. There are about n / b = √n blocks, so the right end moves **O(n√n)** in total.
- **The left end.** Between two queries in the same block, it moves less than b steps, because both left ends are in that block. That's O(√n) per query, **O(q√n)** in total. Crossing into the next block costs at most 2b, and that happens at most √n times: O(n).

Altogether the ends move **O((n + q)√n)** steps, and each step is one O(1) `add` or `remove`. Add O(q log q) for the sort. For n = q = 100,000 that's about 6 × 10⁷ steps, against 10¹⁰ for answering in the given order. Measure it on 20,000 random queries over 20,000 positions:

```swift run
// How far the two ends travel in total: queries in the order given, against Mo's order
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

func travel(_ queries: [(left: Int, right: Int)], order: [Int]) -> Int {
    var currentLeft = 0
    var currentRight = -1
    var moves = 0
    for q in order {
        moves += abs(queries[q].left - currentLeft) + abs(queries[q].right - currentRight)
        currentLeft = queries[q].left
        currentRight = queries[q].right
    }
    return moves
}

var dice = Dice(seed: 62)
let n = 20_000
let queries = (0..<20_000).map { _ -> (left: Int, right: Int) in
    let a = dice.roll(0...(n - 1)), b = dice.roll(0...(n - 1))
    return (min(a, b), max(a, b))
}
let blockSize = 142                                   // about √20,000
let given = Array(queries.indices)
let mo = queries.indices.sorted { a, b in
    let blockA = queries[a].left / blockSize, blockB = queries[b].left / blockSize
    return blockA != blockB ? blockA < blockB : queries[a].right < queries[b].right
}
print("in the order given:", travel(queries, order: given))
print("in Mo's order:     ", travel(queries, order: mo))
print("n × q:             ", n * queries.count)
print("(n + q) × √n:      ", (n + queries.count) * blockSize)
```

```output
in the order given: 213228905
in Mo's order:      3712989
n × q:              400000000
(n + q) × √n:       5680000
```

The same 20,000 answers, with the window travelling 57 times less far. (The `Dice` is the small seeded generator from [Quickselect](/dsa/learn/sort-quickselect), so the "random" queries are the same every run.) The measured total sits comfortably under the (n + q)√n bound.

<Callout kind="analogy" title="A delivery driver's route">
A driver with 50 parcels for one long street doesn't deliver them in the order they were ordered, zigzagging from one end to the other. They split the street into neighbourhoods and sweep each one. Mo's algorithm is the same: the queries are the stops, the two window ends are the van, and the sort is the route.
</Callout>

## Making it work in practice

**Values must be small indexes.** The `count` array is indexed by value, so values up to 10⁹ won't do. Replace each value by its rank among the distinct values first, so they become 0 to k − 1. That's coordinate compression, the lesson after next. A `Dictionary` of counts also works, but it's several times slower inside the hottest loop of the algorithm.

**The block size.** √n is the textbook choice. When there are far fewer queries than elements, n / √q balances the two ends' movements better; either is fine for tests here.

**The odd–even trick.** In Mo's order, the right end sweeps forward through a block, then jumps all the way back for the next one. Sorting odd-numbered blocks by right end **decreasing** lets it sweep back instead, which roughly halves its travel:

```swift
let order = queries.indices.sorted { a, b in
    let blockA = queries[a].left / blockSize, blockB = queries[b].left / blockSize
    if blockA != blockB { return blockA < blockB }
    return blockA % 2 == 0 ? queries[a].right < queries[b].right : queries[a].right > queries[b].right
}
```

It changes the constant, not the O((n + q)√n).

**What makes a problem fit Mo's algorithm:**

- All queries are known in advance (offline), and the array doesn't change between them.
- `add` and `remove` are cheap, ideally O(1): distinct counts, the number of pairs of equal values in a range (adding a value v creates `count[v]` new pairs), the most frequent count with a little extra bookkeeping.
- Combining two halves is hard, so the usual trees don't work.

Variants exist for arrays with updates (sort by a third coordinate, time, for O(n^(5/3))) and for paths in trees. They're rare outside contests; the plain version is the one to know.

<Callout kind="gotcha" title="Common mistakes">
- **Answers in sorted order.** Store each answer at the query's original index. Returning them in Mo's order gives right answers to the wrong questions.
- **Shrinking before growing.** The window can turn inside out and counts go negative. Grow both ends first.
- **Starting the window at 0...0.** That window already holds element 0, which nobody added. Start at `currentLeft = 0`, `currentRight = -1`.
- **Off-by-one in the loops.** When growing, move first and then add (`currentRight += 1; add(currentRight)`). When shrinking, remove first and then move.
- **Using it online.** If each query depends on the previous answer, you can't reorder them, and Mo's algorithm doesn't apply.
</Callout>
