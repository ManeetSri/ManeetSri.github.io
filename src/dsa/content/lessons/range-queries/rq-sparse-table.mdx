## Why it matters

A stock chart that lets you drag across any stretch of days and shows the lowest price in it. A weather app that answers "what was the coldest day between these two dates?" for a decade of readings. A suffix array (you'll build one in M63) that needs the smallest value in a range of its LCP array millions of times. All three ask the same question, the **range minimum query** (RMQ), on data that **never changes**. A segment tree answers it in O(log n). A **sparse table** answers it in **O(1)**, after an O(n log n) build, using nothing more than precomputed answers for blocks whose lengths are powers of two. It's one of the most-used tricks in competitive programming, and it teaches a lesson you'll reuse: some operations let you count an element twice without harm, and that freedom is worth a lot.

## The problem, and what you already have

You're given an array of n values, then q queries. Each query names a range `left...right` and asks for its smallest value. The array is **static**: no updates between queries.

What you know so far:

| Approach | Build | Per query | Memory | Updates? |
| --- | --- | --- | --- | --- |
| Scan the range | none | O(n) | O(1) | yes |
| Precompute every range | O(n²) | O(1) | O(n²) | no |
| Prefix sums | O(n) | O(1) | O(n) | no, and sums only |
| Segment tree | O(n) | O(log n) | O(n) | yes, O(log n) |
| **Sparse table** | O(n log n) | **O(1)** | O(n log n) | no |

Scanning costs O(n · q): with 100,000 values and 100,000 queries that's ten billion steps. Precomputing all n² ranges is ten billion **entries**. And [prefix sums](/dsa/learn/prefix-1d) don't help: they work because a range sum is `prefix[right + 1] - prefix[left]`, a **subtraction**, and there's no way to "subtract" a minimum. Knowing the minimum of `0...9` and of `0...3` tells you nothing about `4...9`.

The sparse table sits between the scan and the full precomputation: it stores answers for only n log n carefully chosen ranges, and every query is built from two of them.

## Blocks whose lengths are powers of two

Store the answer for every block that starts anywhere and has length 1, 2, 4, 8, … up to n. Call `table[j][i]` the minimum of the 2^j values starting at index i, so it covers `i...(i + 2^j - 1)`.

- **Level 0** is the array itself: blocks of length 1.
- **Level j** comes from level j − 1: a block of length 2^j is two blocks of length 2^(j − 1) side by side, so

```text
table[j][i] = min(table[j - 1][i], table[j - 1][i + 2^(j - 1)])
```

Each entry is one `min` of two entries already computed. That's dynamic programming in its simplest form: each answer is built from two smaller answers already stored.

```swift run
// Build the levels of a sparse table for range minimums and print them
let prices = [7, 2, 9, 4, 8, 1, 6, 3]
var table = [prices]                       // level 0: blocks of length 1
var length = 2
while length <= prices.count {
    let previous = table[table.count - 1]
    let half = length / 2
    var level: [Int] = []
    for start in 0...(prices.count - length) {
        level.append(min(previous[start], previous[start + half]))
    }
    table.append(level)
    length *= 2
}
for (j, level) in table.enumerated() {
    print("level \(j), blocks of \(1 << j):", level)
}
```

```output
level 0, blocks of 1: [7, 2, 9, 4, 8, 1, 6, 3]
level 1, blocks of 2: [2, 2, 4, 4, 1, 1, 3]
level 2, blocks of 4: [2, 2, 1, 1, 1]
level 3, blocks of 8: [1]
```

What to notice:

- Each level is shorter than the one before: a block of length 2^j can start at indexes 0 through n − 2^j only, so the loop stops at `prices.count - length`. Getting this bound wrong is the classic build bug: one more and you read past the end of the previous level.
- Level 2, entry 2 is the minimum of `2...5`, the values 9, 4, 8, 1. It came from level 1's entries 2 and 4: min(4, 1) = 1.
- There are ⌊log₂ n⌋ + 1 levels, each with at most n entries: **O(n log n)** entries, each computed in O(1).

## A query is two overlapping blocks

Now the key idea. Take a range of length `len = right - left + 1`, and let 2^k be the **largest power of two that fits**: 2^k ≤ len < 2^(k + 1). Two blocks of that length cover the whole range:

- one that **starts** at `left`: `table[k][left]`, and
- one that **ends** at `right`: `table[k][right - 2^k + 1]`.

Because 2^k is more than half of `len`, the two blocks meet or overlap, so together they cover every index. For the range `1...6` (length 6), k = 2 and the blocks have length 4:

```text
index:   0   1   2   3   4   5   6   7
value:   7   2   9   4   8   1   6   3
             [ block 1...4  ]
                     [ block 3...6  ]
```

Indexes 3 and 4 are in both blocks. For a minimum that doesn't matter: min(min(2, 9, 4, 8), min(4, 8, 1, 6)) is still 1. Seeing the 4 and the 8 twice can't change which value is smallest.

### Finding k: the log table

The query needs ⌊log₂ len⌋. Computing it with `log2` on a `Double` works, but it's slow, and floating point makes people nervous near exact powers of two. Two integer ways:

- **A log table**, built once: `floorLog[1] = 0`, and `floorLog[x] = floorLog[x / 2] + 1`. Halving a number removes one binary digit, so this counts the digits after the first. O(n) to build, one array lookup per query.
- **The highest set bit**: `Int.bitWidth - 1 - x.leadingZeroBitCount`. `leadingZeroBitCount` counts the zero bits in front of the first 1, which the processor does in a single instruction. It's the same family of tricks as [Counting bits and Kernighan's trick](/dsa/learn/bits-counting).

Both appear in real code. The log table is the traditional one, and the one you'll see in most competitive programming solutions.

### The whole structure

```swift run
// A sparse table for range minimums: O(n log n) to build, O(1) per query
struct MinSparseTable {
    private var table: [[Int]]
    private var floorLog: [Int]              // floorLog[x] = ⌊log₂ x⌋

    init(_ values: [Int]) {
        let n = values.count
        floorLog = [Int](repeating: 0, count: n + 1)
        if n >= 2 {
            for x in 2...n {
                floorLog[x] = floorLog[x / 2] + 1
            }
        }
        table = [values]
        var j = 1
        while (1 << j) <= n {
            let previous = table[j - 1]
            let half = 1 << (j - 1)
            table.append((0...(n - (1 << j))).map { min(previous[$0], previous[$0 + half]) })
            j += 1
        }
    }

    /// The smallest value in values[left...right]
    func minimum(_ left: Int, _ right: Int) -> Int {
        let j = floorLog[right - left + 1]                       // the largest 2^j that fits
        return min(table[j][left], table[j][right - (1 << j) + 1])
    }
}

let prices = [7, 2, 9, 4, 8, 1, 6, 3]
let rmq = MinSparseTable(prices)
for (left, right) in [(0, 0), (2, 4), (1, 6), (2, 7), (6, 7)] {
    print("min of \(left)...\(right):", rmq.minimum(left, right))
}
```

```output
min of 0...0: 7
min of 2...4: 4
min of 1...6: 1
min of 2...7: 1
min of 6...7: 3
```

Follow two of them:

- **`2...4`** has length 3, so j = 1 (blocks of 2): `table[1][2]` covers `2...3` (min 4) and `table[1][3]` covers `3...4` (min 4). The answer is 4. Index 3 is in both.
- **`6...7`** has length 2, an exact power of two, so both blocks are the same block, `table[1][6]`. Overlapping completely is still fine.

Every query does one table lookup for j, two for the blocks and one `min`: **O(1)**, however long the range.

## Idempotent operations only

Counting an element twice is harmless for `min` because min(x, x) = x. An operation with that property is called **idempotent**. The sparse table's O(1) query works for any operation that's idempotent and associative (grouping doesn't matter):

| Operation | Idempotent? | O(1) sparse table query? |
| --- | --- | --- |
| `min`, `max` | yes | yes |
| gcd | yes: gcd(x, x) = x | yes |
| bitwise `&`, `\|` | yes: x & x = x | yes |
| `+` (sum), count | no: x + x = 2x | **no** |
| `*` (product), `^` (XOR) | no | **no** |

Watch what happens if you build the same table with `+`:

```swift run
// The same table with + instead of min: the overlapping trick double-counts
let values = [7, 2, 9, 4, 8, 1, 6, 3]
var table = [values]
var j = 1
while (1 << j) <= values.count {
    let previous = table[j - 1]
    let half = 1 << (j - 1)
    table.append((0...(values.count - (1 << j))).map { previous[$0] + previous[$0 + half] })
    j += 1
}

func floorLog2(_ x: Int) -> Int {
    Int.bitWidth - 1 - x.leadingZeroBitCount     // the position of the highest set bit
}

/// Wrong: the two blocks overlap, so the middle is added twice
func overlappingSum(_ left: Int, _ right: Int) -> Int {
    let j = floorLog2(right - left + 1)
    return table[j][left] + table[j][right - (1 << j) + 1]
}

/// Right: split the length into powers of two (its binary digits) and add disjoint blocks
func disjointSum(_ left: Int, _ right: Int) -> Int {
    var total = 0
    var start = left
    var remaining = right - left + 1
    while remaining > 0 {
        let j = floorLog2(remaining)
        total += table[j][start]
        print("  block \(start)...\(start + (1 << j) - 1)")
        start += 1 << j
        remaining -= 1 << j
    }
    return total
}

print("true sum of 1...6:", values[1...6].reduce(0, +))
print("overlapping blocks:", overlappingSum(1, 6))
print("disjoint blocks:")
print("sum:", disjointSum(1, 6))
```

```output
true sum of 1...6: 30
overlapping blocks: 42
disjoint blocks:
  block 1...4
  block 5...6
sum: 30
```

The overlapping answer is off by 12, the sum of indexes 3 and 4, which were added twice. To get a correct sum, the blocks must **not** overlap. Split the length into powers of two (6 = 4 + 2, its binary digits 110) and add one block per set bit. That's correct, but a length can have up to log₂ n set bits, so the query is **O(log n)**, not O(1). That's why sums need O(log n) from a sparse table.

In practice you'd never use a sparse table for static sums: prefix sums already do them in O(1) with O(n) memory, because addition **can** be undone by subtraction. The two structures complement each other:

- **Invertible** operations (sum, XOR): prefix sums, O(1).
- **Idempotent** operations (min, max, gcd): sparse table, O(1).
- **Neither, or with updates**: a segment tree or a Fenwick tree, O(log n). [Segment tree vs BIT vs sparse table](/dsa/learn/seg-vs-others) compares all three.

<Callout kind="analogy" title="Two torches on a dark corridor">
You want to know if anything is lying anywhere along a corridor. You have torches with beams of fixed lengths: 1 metre, 2, 4, 8. Shine the longest beam that fits from one end, and the same beam from the other end. Between them, every bit of floor is lit, some of it twice. Seeing a patch twice doesn't make you miss anything. But if you were **counting** the objects, the ones in the doubly lit patch would be counted twice.
</Callout>

## The cost: memory

A sparse table stores about n log₂ n values. For n = 1,000,000 Ints that's 20 levels of up to a million 8-byte values: about 160 MB. A segment tree for the same array needs about 2n values, 16 MB. So sparse tables shine for "many queries, moderate n": up to a few hundred thousand values with millions of queries. When memory is tight, or the array changes, reach for a segment tree.

Two small savings help:

- Build each level with `reserveCapacity` or `map`, as above, so arrays don't grow piece by piece.
- If you only need the **position** of the minimum (which you will for lowest common ancestors), store indexes instead of values and compare `values[a] < values[b]` in the combine. Ties go to the smaller index if you write `values[a] <= values[b] ? a : b`.

## DSAKit's SparseTable

DSAKit has a generic version. You pass the array and an idempotent combine closure, and `query` takes a closed range:

```swift
import DSAKit

let temperatures = [14, 9, 17, 5, 12, 20, 8]
let coldest = SparseTable(temperatures, combine: min)
print(coldest.query(1...4))                       // 5
print(SparseTable.maximum(temperatures).query(0...2))   // 17

func gcd(_ a: Int, _ b: Int) -> Int { b == 0 ? a : gcd(b, a % b) }
let shared = SparseTable([12, 18, 30, 45], combine: gcd)
print(shared.query(0...2))                        // 6
```

It works out ⌊log₂ len⌋ with `leadingZeroBitCount`, traps on a range outside the array (like an array index does), and its documentation warns that the combine must be idempotent. Nothing in Swift's type system can check that for you: `SparseTable(values, combine: +)` compiles and gives wrong answers.

<Callout kind="gotcha" title="Common mistakes">
- **Using the log of `right` instead of the log of the length.** k depends on `right - left + 1`.
- **An off-by-one in the second block.** It starts at `right - (1 << k) + 1`, so that it **ends** at `right`.
- **Building past the end.** Level j has `n - 2^j + 1` entries; a loop up to `n - 1` reads outside the previous level.
- **`1 << k` precedence.** In Swift, `<<` binds tighter than `+` and `-`, so `right - 1 << k + 1` means `right - (1 << k) + 1`. Swift's precedence differs from C's here, and the parentheses cost nothing, so write them.
- **A combine that isn't idempotent.** Sums, counts, products and XOR all give silently wrong answers.
</Callout>
