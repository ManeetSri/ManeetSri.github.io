## Why it matters

When a batch of questions arrives all at once, you don't have to answer them in the order they were asked. A nightly report that runs 100,000 price queries over a year of data, a contest problem that hands you every query in the input, a test suite that checks a million lookups: in all of them you can **sort the queries** into whatever order makes each answer cheapest, then put the answers back in the original order. That's **offline query processing**. Mo's algorithm was one example. This lesson shows the more common shape, a sort and a single **sweep**, and how it turns a hard two-dimensional question ("days in this range **and** under this price") into a one-dimensional one that a Fenwick tree handles in O(log n).

## Online and offline

- An **online** algorithm must answer each query before it sees the next one. A search box, an API endpoint, a game reacting to the player.
- An **offline** algorithm sees all queries first, then answers them in any order it likes.

Online is the harder setting: every structure in this module so far (sparse tables, segment trees, Fenwick trees) can answer online. Offline gives you an extra freedom, the order, and exploiting it often makes a problem much simpler. You'll look at the online world more closely in M67.

The recipe is always the same:

1. **Number the queries** in input order.
2. **Sort the numbers** by whatever key makes a sweep possible.
3. **Sweep**, maintaining a structure, and answer each query when the sweep reaches it.
4. **Write each answer to its query's number**, so the output is in input order.

## A first sweep: sort both sides

A shop has n prices and q customers, each with a budget. How many items can each customer afford? Online, you'd sort the prices once and [binary search](/dsa/learn/bs-bounds) for each budget: O(log n) per query. Offline, sort the budgets too, and one pointer walks through the sorted prices as the budgets grow:

```swift run
// For each budget, how many prices are within it? Offline: sort both, sweep once, answer in input order
func affordableCounts(prices: [Int], budgets: [Int]) -> [Int] {
    let sortedPrices = prices.sorted()
    let order = budgets.indices.sorted { budgets[$0] < budgets[$1] }    // query numbers, smallest budget first
    var answers = [Int](repeating: 0, count: budgets.count)
    var affordable = 0                                                  // prices ≤ the current budget
    for q in order {
        while affordable < sortedPrices.count && sortedPrices[affordable] <= budgets[q] {
            affordable += 1
        }
        answers[q] = affordable
    }
    return answers
}

print(affordableCounts(prices: [5, 2, 8, 6, 3, 9, 1, 7], budgets: [5, 0, 10, 6, 1]))
```

```output
[4, 0, 8, 5, 1]
```

The pointer only ever moves forward, so the sweep is O(n + q) after the two sorts. Here the gain over binary search is small. The point is the **shape**: as the sweep moves through the queries in sorted order, the set of "relevant" items only grows. Every offline sweep relies on that.

## Two conditions at once

Now a harder question. `prices[i]` is the price of a flight on day i. Each query asks: **how many days in `left...right` have a price ≤ `budget`?**

There are two conditions, one on the day and one on the price. A prefix sum handles a range of days, but only for one fixed budget. A sorted list handles a budget, but not a range of days. Answering online needs heavy machinery: a merge-sort tree, a persistent segment tree, or sqrt decomposition with sorted blocks.

Offline, the sweep removes one of the conditions:

- Sort the **days by price**, and the **queries by budget**.
- Sweep the budgets from smallest to largest. Before answering a query, **mark** every day whose price is ≤ its budget. Days only ever get marked, never unmarked, because budgets only grow.
- Now the price condition is built in: the marked days are exactly the affordable ones. The query is just "how many marked days in `left...right`?", a range count, which is a prefix-sum question on a changing array.

A changing array with prefix sums is what a Fenwick tree does, as in [Point update and prefix query](/dsa/learn/bit-point-update): mark a day by adding 1 at its position, and count with `prefix(right + 1) - prefix(left)`. Each step is O(log n).

```swift run
// How many days in left...right have a price ≤ budget? Offline, with a Fenwick tree over days
struct Fenwick {
    private var tree: [Int]
    init(count: Int) { tree = [Int](repeating: 0, count: count + 1) }

    /// Adds delta at position index (0-based)
    mutating func add(_ index: Int, _ delta: Int) {
        var i = index + 1
        while i < tree.count {
            tree[i] += delta
            i += i & -i
        }
    }

    /// The total of positions 0..<count
    func prefix(_ count: Int) -> Int {
        var i = count
        var total = 0
        while i > 0 {
            total += tree[i]
            i -= i & -i
        }
        return total
    }
}

func cheapDays(prices: [Int], queries: [(left: Int, right: Int, budget: Int)]) -> [Int] {
    let days = prices.indices.sorted { prices[$0] < prices[$1] }             // cheapest day first
    let order = queries.indices.sorted { queries[$0].budget < queries[$1].budget }
    var marked = Fenwick(count: prices.count)                                 // 1 at each day ≤ budget
    var answers = [Int](repeating: 0, count: queries.count)
    var next = 0
    for q in order {
        let (left, right, budget) = queries[q]
        while next < days.count && prices[days[next]] <= budget {
            marked.add(days[next], 1)                                         // this day is now affordable
            next += 1
        }
        answers[q] = marked.prefix(right + 1) - marked.prefix(left)
        print("budget \(budget): \(next) days marked, \(left)...\(right) has \(answers[q])")
    }
    return answers
}

let prices = [5, 2, 8, 6, 3, 9, 1, 7]
let queries = [(left: 0, right: 7, budget: 5), (left: 2, right: 5, budget: 6), (left: 1, right: 3, budget: 1), (left: 4, right: 7, budget: 8)]
print("answers:", cheapDays(prices: prices, queries: queries))
```

```output
budget 1: 1 days marked, 1...3 has 0
budget 5: 4 days marked, 0...7 has 4
budget 6: 5 days marked, 2...5 has 2
budget 8: 7 days marked, 4...7 has 3
answers: [4, 2, 0, 3]
```

What to notice:

- The queries are processed in budget order, 1, 5, 6, 8, but the answers come back in input order: the first query (`0...7`, budget 5) gets 4.
- With budget 1, only day 6 (price 1) is marked, and it's outside `1...3`, so the answer is 0.
- With budget 5, the days priced 1, 2, 3 and 5 are marked (days 6, 1, 4 and 0), all inside `0...7`.
- The `while` uses `<=`, so a day priced exactly at the budget counts. For "strictly below", use `<`. Equal values are where offline sweeps most often go wrong, so decide which side ties fall on and test a query whose budget equals a price.

The cost: two sorts, O(n log n + q log q); each day is marked once, O(n log n); each query is two prefix sums, O(q log n). In total **O((n + q) log n)**, against O(n · q) for scanning every range. With 100,000 days and 100,000 queries, that's a few million steps instead of ten billion.

<Callout kind="analogy" title="Filling a reservoir">
Picture the days as a landscape with heights equal to their prices, and the queries as water levels. Answering in budget order is raising the water slowly: each day goes under once, and stays under. At each level you only count the flooded days in a stretch, and the Fenwick tree does that counting.
</Callout>

## More offline tricks

The same "sort so that something only grows" idea appears in many forms:

- **Distinct values in ranges, again.** Sort the queries by right end and sweep the array from left to right. Keep a Fenwick tree with a 1 at only the **last** position where each value has appeared so far: when value v shows up again at i, remove the 1 at its previous position and add one at i. A query `left...right`, answered when the sweep reaches `right`, is the number of 1s in `left...right`. O((n + q) log n), faster than Mo's algorithm.
- **Deleting edges backwards.** A union-find structure from [Disjoint sets and the parent array](/dsa/learn/uf-idea) can merge sets but can't split them. If a problem deletes edges and asks about connectivity in between, process everything **in reverse**: deletions become insertions, which union-find handles.
- **Values instead of positions.** Swap the roles above, sweeping positions and counting by value, and you need the values as Fenwick indexes. That's where the previous lesson's coordinate compression comes in.

Offline processing doesn't work when a query depends on an earlier answer (some contest problems encrypt each query with the previous answer precisely to force an online solution), or when updates and queries are interleaved and the order of updates matters to each answer.

<Callout kind="gotcha" title="Common mistakes">
- **Returning answers in sorted order.** Always write to `answers[q]` with the query's original number.
- **Sorting the queries instead of their numbers.** Once sorted, you no longer know where each answer belongs. Sort `indices`, or store the number inside each query.
- **Ties between items and queries.** Decide whether an item equal to the query value counts (`<=`) or not (`<`), and check that the sweep's `while` agrees.
- **Fenwick off-by-ones.** The tree here is 1-based inside and 0-based outside. A range `left...right` is `prefix(right + 1) - prefix(left)`.
</Callout>
