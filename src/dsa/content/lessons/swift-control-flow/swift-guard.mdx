## Why it matters

Good code deals with the problems first and then gets on with the real work. "If there's no input, stop. If the age is negative, stop. Now do the job." Swift has a statement built for exactly this: `guard`. You'll see it at the top of almost every function in iOS apps, and in DSA it's how you handle edge cases like an empty array before the main algorithm starts.

## A quick look at functions

`guard` is most useful inside a **function**, a named piece of code you can run whenever you need it. Functions get a whole module, M05, but you only need the basic shape to follow this lesson:

```swift run
func square(of number: Int) -> Int {
    return number * number
}

print(square(of: 7))
print(square(of: -3))
```

```output
49
9
```

- `func square` names the function.
- `(of number: Int)` says it takes one `Int`. Callers write the label `of`, and inside the function the value is called `number`.
- `-> Int` says it gives back an `Int`.
- `return` sends a value back and **leaves the function immediately**. Nothing after it runs.

That last point is what `guard` builds on.

## guard: make sure, or leave

A `guard` statement states something that must be true for the code below it to make sense. If it's false, the `else` block runs, and that block **must leave**:

```swift run
func describe(age: Int) -> String {
    guard age >= 0 else {
        return "That isn't a valid age"
    }

    if age < 13 {
        return "Child"
    } else if age < 20 {
        return "Teenager"
    } else {
        return "Adult"
    }
}

print(describe(age: 8))
print(describe(age: -5))
print(describe(age: 42))
```

```output
Child
That isn't a valid age
Adult
```

Read `guard age >= 0 else { … }` as "make sure the age is at least 0, otherwise leave". After the guard, every line can rely on `age` being valid.

It's the opposite way round from `if`. An `if` runs its block when the condition is **true**. A `guard` runs its `else` block when the condition is **false**. You write the condition you *want*, and the `else` handles the case you don't.

## The else block must leave

Swift checks that a guard's `else` block can't carry on past the guard. It must end with something that leaves the current scope:

- `return` inside a function;
- `break` or `continue` inside a loop;
- `throw`, which you'll meet with errors in M12;
- or a call that stops the program, like `fatalError("…")`.

Forget, and the code won't compile:

```swift
func half(of n: Int) -> Int {
    guard n % 2 == 0 else {
        print("Odd number")
    }
    return n / 2
}
```

```text title="What you'll see"
error: 'guard' body must not fall through, consider using a 'return' or 'throw' to exit the scope
```

This rule is what makes `guard` trustworthy. If execution reaches the line after a guard, its condition **was** true. There's no other way to get there.

## Why not if?

You could write every guard as an `if`. The difference shows up when there are several things to check. Here's a function that classifies a triangle from its three side lengths, written with nested `if`s:

```swift
func triangleKind(a: Int, b: Int, c: Int) -> String {
    if a > 0 && b > 0 && c > 0 {
        if a + b > c && a + c > b && b + c > a {
            if a == b && b == c {
                return "Equilateral"
            } else if a == b || b == c || a == c {
                return "Isosceles"
            } else {
                return "Scalene"
            }
        } else {
            return "Not a triangle"
        }
    } else {
        return "Sides must be positive"
    }
}
```

The real work is buried three levels deep, and each `else` is far from the `if` it belongs to. Programmers call this shape the *pyramid of doom*. The same logic with `guard`:

```swift run
func triangleKind(a: Int, b: Int, c: Int) -> String {
    guard a > 0 && b > 0 && c > 0 else {
        return "Sides must be positive"
    }
    guard a + b > c && a + c > b && b + c > a else {
        return "Not a triangle"
    }

    if a == b && b == c {
        return "Equilateral"
    } else if a == b || b == c || a == c {
        return "Isosceles"
    } else {
        return "Scalene"
    }
}

print(triangleKind(a: 3, b: 3, c: 3))
print(triangleKind(a: 3, b: 4, c: 5))
print(triangleKind(a: 1, b: 2, c: 8))
print(triangleKind(a: 0, b: 2, c: 2))
```

```output
Equilateral
Scalene
Not a triangle
Sides must be positive
```

Each problem is handled right next to the check that finds it, and the main logic sits at the left edge where it's easy to read. That's called **early exit**: leave as soon as you know you can't continue, so the rest of the code only deals with the happy path.

## guard in loops

Inside a loop, a guard's `else` can use `continue` to skip to the next item, or `break` to stop the loop:

```swift run
let orders = [12, 0, 7, -3, 20]
var shipped = 0

for quantity in orders {
    guard quantity > 0 else {
        print("Skipping an order of \(quantity)")
        continue
    }
    shipped += quantity
}
print("Items shipped: \(shipped)")
```

```output
Skipping an order of 0
Skipping an order of -3
Items shipped: 39
```

It reads well: "make sure the quantity is positive, otherwise skip it", followed by the work for good orders.

<Callout kind="gotcha" title="Swift gotcha: guard needs somewhere to leave">
A guard needs a function or loop to exit. In top-level code outside any function or loop, its `else` can't use `return` (Swift reports "return invalid outside of a func"). That's why this lesson's guards live inside functions and loops.
</Callout>

## Edge cases first: a DSA habit

Many algorithms only work once there's enough input. Guarding against the small cases at the top keeps the main loop simple, and can stop a crash.

This function checks whether an array is sorted from smallest to largest, by comparing each element with the one before it:

```swift run
func isSorted(_ numbers: [Int]) -> Bool {
    guard numbers.count > 1 else {
        return true // zero or one element is always sorted
    }
    for i in 1..<numbers.count {
        guard numbers[i - 1] <= numbers[i] else {
            return false
        }
    }
    return true
}

print(isSorted([1, 3, 3, 8]))
print(isSorted([4, 2, 9]))
print(isSorted([]))
```

```output
true
false
true
```

The `_` before `numbers` means callers don't write a label: `isSorted([1, 3])`, not `isSorted(numbers: [1, 3])`.

The first guard isn't only for neatness. For an empty array, `1..<numbers.count` would be `1..<0`, a backwards range, and the program would crash. The guard returns before the loop ever sees it.

The second guard shows another habit: as soon as one pair is out of order, the answer is `false`, so return straight away. There's no need to check the rest.

## A preview: guard let

`guard` becomes even more useful with **optionals**, values that might be missing, which you'll meet in the next module. `guard let` checks that a value exists and gives it a name for the rest of the function:

```swift
guard let first = numbers.first else {
    return 0
}
// from here on, `first` is a plain Int
```

You'll learn exactly how that works in M04. For now, notice the same shape: check, leave if it fails, then carry on knowing it's true.
