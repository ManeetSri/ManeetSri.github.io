## Why it matters

Randomness can buy you two different things. Randomised quickselect uses it to be **fast on every input**, and its answer is always right. Other algorithms use it to be **fast, full stop**, and accept a tiny, controllable chance of a wrong or approximate answer: checking whether a huge number is prime, whether two files are identical, whether a matrix product was computed correctly, or estimating a quantity that's too expensive to compute exactly. These two families have names, **Las Vegas** and **Monte Carlo**, and knowing which one you're holding tells you what to promise: "always right, usually fast" or "always fast, almost always right". This lesson shows both, with a Monte Carlo estimate of π and Freivalds' check for matrix multiplication.

## Two kinds of gamble

| | Las Vegas | Monte Carlo |
| --- | --- | --- |
| Answer | always correct | correct with high probability, or approximate |
| Running time | random (you bound the **expected** time) | bounded (you choose how long) |
| Examples | randomised quickselect and quick sort, treaps, hash tables with random seeds | estimating π, Freivalds' check, Miller–Rabin primality, Bloom filters |

- **Randomised quickselect** is Las Vegas. It returns the true kth smallest every time; only the number of comparisons depends on the pivots, as the last lesson measured.
- A [treap](/dsa/learn/bal-treap) is Las Vegas too: its random priorities affect its shape, and so its speed, never which keys it holds.

Monte Carlo algorithms come in two flavours:

- **Approximate:** the answer is a number that's close to the truth, and gets closer the longer you run. Estimating π below.
- **Decision with error:** the answer is yes or no, and might be wrong with a small probability you can push down as far as you like. Freivalds' check below, and the Miller–Rabin primality test in [Miller–Rabin and Pollard's rho](/dsa/learn/nt-primality).

## Monte Carlo estimation: π from random points

Throw points uniformly at random into the unit square, from (0, 0) to (1, 1). The quarter circle x² + y² < 1 covers π/4 of the square's area, so the fraction of points that land inside it approaches π/4. Multiply by 4:

```swift run
import Foundation

// Estimating π: throw random points at a square and count those inside the quarter circle
struct SeededGenerator: RandomNumberGenerator {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func next() -> UInt64 {          // SplitMix64
        state &+= 0x9E37_79B9_7F4A_7C15
        var z = state
        z = (z ^ (z >> 30)) &* 0xBF58_476D_1CE4_E5B9
        z = (z ^ (z >> 27)) &* 0x94D0_49BB_1331_11EB
        return z ^ (z >> 31)
    }
    /// A Double in 0..<1 from the top 53 bits
    mutating func unit() -> Double {
        Double(next() >> 11) / 9_007_199_254_740_992.0
    }
}

var generator = SeededGenerator(seed: 2026)
var inside = 0
var thrown = 0
for target in [1_000, 10_000, 100_000, 1_000_000] {
    while thrown < target {
        let x = generator.unit(), y = generator.unit()
        if x * x + y * y < 1 { inside += 1 }
        thrown += 1
    }
    let estimate = 4 * Double(inside) / Double(thrown)
    print(String(format: "%9d points: π ≈ %.4f, error %.4f", thrown, estimate, abs(estimate - Double.pi)))
}
```

```output
     1000 points: π ≈ 3.1520, error 0.0104
    10000 points: π ≈ 3.1504, error 0.0088
   100000 points: π ≈ 3.1457, error 0.0041
  1000000 points: π ≈ 3.1401, error 0.0015
```

What to notice:

- `unit()` turns the top 53 bits of a random `UInt64` into a `Double` in `0..<1`. A `Double` has 53 bits of precision, so every value it can produce is exact. (`Double.random(in: 0..<1, using: &generator)` does the same job.)
- The estimate wanders towards π, but slowly. The typical error is about 1.6 / √N, so **100 times more points buys one more correct digit**. That 1/√N rate is the signature of Monte Carlo estimation, and it doesn't depend on the dimension, which is why Monte Carlo is the method of choice for high-dimensional problems like pricing options or rendering light in films.
- Any single run is luckier or unluckier than "typical": this one was lucky at 1,000 points. Error **bars**, not single numbers, are the honest way to report an estimate.

Nobody computes π this way: formulas give billions of digits. But the same pattern estimates things with no formula at all: the area of a complicated shape, the probability a card game is winnable, the chance a network stays connected when links fail at random.

## Monte Carlo decisions: Freivalds' check

Someone hands you three n × n matrices A, B and C, and claims A × B = C. Multiplying A by B yourself takes O(n³) operations: a billion for n = 1,000. **Freivalds' algorithm** checks the claim in **O(n²)**.

Pick a random vector r of 0s and 1s. Compute A(Br), which is two matrix-vector products, and Cr, one more. Each product is O(n²). Then:

- If A × B = C, then A(Br) = (AB)r = Cr. The check **always passes**.
- If A × B ≠ C, the check **fails with probability at least 1/2**: at least half of all 0/1 vectors expose the difference.

Why at least half? Let D = AB − C, which has some nonzero entry, say in column j. Pair up the vectors that differ only in position j. For each pair, Dr changes by exactly column j of D, which isn't zero, so the two vectors can't both give Dr = 0. At most one vector in each pair hides the difference: at least half expose it.

```swift run
// Freivalds' check: is A × B == C? Test with random 0/1 vectors in O(n²) instead of multiplying in O(n³)
struct SeededGenerator: RandomNumberGenerator {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func next() -> UInt64 {          // SplitMix64
        state &+= 0x9E37_79B9_7F4A_7C15
        var z = state
        z = (z ^ (z >> 30)) &* 0xBF58_476D_1CE4_E5B9
        z = (z ^ (z >> 27)) &* 0x94D0_49BB_1331_11EB
        return z ^ (z >> 31)
    }
}

func times(_ m: [[Int]], _ v: [Int]) -> [Int] {        // matrix × vector: O(n²)
    m.map { row in zip(row, v).reduce(0) { $0 + $1.0 * $1.1 } }
}

/// One trial: false means "definitely not equal"; true means "probably equal"
func trial(_ a: [[Int]], _ b: [[Int]], _ c: [[Int]], using generator: inout SeededGenerator) -> Bool {
    let r = (0..<b.count).map { _ in Int(generator.next() & 1) }    // a random vector of 0s and 1s
    return times(a, times(b, r)) == times(c, r)                       // A(Br) against Cr
}

func probablyEqual(_ a: [[Int]], _ b: [[Int]], _ c: [[Int]], trials: Int, using generator: inout SeededGenerator) -> Bool {
    for _ in 0..<trials where !trial(a, b, c, using: &generator) {
        return false                                                  // a witness: certainly different
    }
    return true
}

let a = [[2, 0, 1], [1, 3, 0], [0, 1, 4]]
let b = [[1, 2, 0], [0, 1, 1], [3, 0, 2]]
let right = [[5, 4, 2], [1, 5, 3], [12, 1, 9]]        // the true product
var wrong = right
wrong[1][2] = 4                                        // one entry off by one

var generator = SeededGenerator(seed: 99)
print("right product:", probablyEqual(a, b, right, trials: 20, using: &generator))
print("wrong product:", probablyEqual(a, b, wrong, trials: 20, using: &generator))

var caught = 0
for _ in 0..<1_000 where !trial(a, b, wrong, using: &generator) {
    caught += 1
}
print("single trials that caught the wrong product: \(caught) of 1000")
```

```output
right product: true
wrong product: false
single trials that caught the wrong product: 503 of 1000
```

With one wrong entry, in column 2, a trial catches it exactly when r has a 1 in position 2: probability 1/2, and 503 of 1,000 trials did. One trial lets a wrong product through half the time. But the trials are **independent**, so k trials all miss with probability at most (1/2)^k. Twenty trials: less than one in a million. Fifty: less than the chance of a cosmic ray flipping a bit in your computer's memory during the check. Each trial is O(n²), so k trials cost O(k n²), still far below O(n³).

### One-sided error

Freivalds' check can only be wrong in **one direction**. "Not equal" is always true: the vector r that failed is a **witness**, a concrete proof you could show someone. Only "equal" might be wrong, and repetition shrinks that chance exponentially. Miller–Rabin is the same: "composite" comes with a witness; "probably prime" has a tiny chance of error that each extra round cuts by at least a factor of four. A [Bloom filter](/dsa/learn/as-bloom-sketch) is one-sided the other way: "not in the set" is certain, "maybe in the set" can be a false positive.

<Callout kind="analogy" title="Spot-checking a long receipt">
To check a long restaurant bill, you could re-add every line (the O(n³) way). Or you could pick a few random lines and check each against the menu. If they're all right, the bill is probably right; a single wrong line is proof that it isn't. Each extra spot check makes a sloppy bill less likely to slip through.
</Callout>

## Converting between the two

- **Las Vegas to Monte Carlo:** run the Las Vegas algorithm with a time limit, and answer "don't know" if it runs out. Markov's inequality says the chance of needing more than t times the expected time is at most 1/t.
- **Monte Carlo to Las Vegas:** if you can **check** an answer cheaply, repeat the Monte Carlo algorithm until a candidate passes the check. The answer is now always right, and the expected number of repeats is 1/p, where p is the chance a candidate is right.

Many practical algorithms are designed this way: a fast randomised guess, plus a cheap deterministic check.

<Callout kind="gotcha" title="Common mistakes">
- **Reporting an estimate without its error.** 3.1401 means little without "± about 0.0016".
- **Repeating with the same random numbers.** Repetition only helps if the trials are independent. Re-creating a seeded generator inside the loop runs the same trial again and again.
- **Fixed seeds in production.** If an attacker knows your seed, they know which vectors you'll test and can craft a wrong C that passes. Seeds are for tests.
- **Comparing `Double`s with `==`.** Monte Carlo estimates are floating-point; compare against a tolerance, and print with fixed decimals.
</Callout>
