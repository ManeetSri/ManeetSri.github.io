## Why it matters

A music app's shuffle button, a card game dealing a hand, a quiz app showing questions in a random order, an A/B test splitting users into groups: they all need a **random permutation**, an ordering in which every possible arrangement is equally likely. Randomised algorithms need it too: shuffling the input first is the simplest way to make quick sort's worst case vanishingly unlikely. Getting it right takes four lines, the **Fisher–Yates shuffle**. Getting it slightly wrong also takes four lines, and the result looks random but quietly favours some orders over others. This lesson builds the correct loop, measures the classic mistakes, and shows how Swift's `shuffle()` lets you plug in your own generator so tests are reproducible.

## What "random order" means

Three songs, A, B and C, can be arranged in 3! = 6 orders: ABC, ACB, BAC, BCA, CAB and CBA. A shuffle is **uniform** (or **unbiased**) when each of the six comes out with probability exactly 1/6. With n items there are n! orders, so each must have probability 1/n!.

"Every song can end up anywhere" isn't enough. A shuffle that only ever produced the three rotations, ABC, BCA and CAB, would put each song in each position exactly a third of the time, yet it would never produce ACB or the other two orders. Uniform means every **whole order** is equally likely, not just every position.

## Fisher–Yates

The idea is the way you'd deal from a hat. Put all n songs in a hat. Draw one at random for the **last** slot. Draw one of the n − 1 left for the slot before it. Continue until the hat is empty.

In an array, the "hat" is the front part that hasn't been placed yet: `items[0...i]`. Each step picks a random index j from `0...i`, **including i itself**, and swaps it into slot i, which then never changes again:

```swift run
// Fisher–Yates: fill the last slot from everything, the next-to-last from what's left, and so on
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 67)

func fisherYates(_ items: inout [String]) {
    guard items.count > 1 else { return }
    for i in stride(from: items.count - 1, through: 1, by: -1) {
        let j = dice.roll(0...i)             // any position from 0 to i, including i itself
        items.swapAt(i, j)
    }
}

var deck = ["A", "B", "C", "D", "E"]
for _ in 1...4 {
    fisherYates(&deck)
    print(deck)
}
```

```output
["C", "A", "B", "D", "E"]
["E", "B", "C", "A", "D"]
["D", "E", "B", "A", "C"]
["E", "B", "D", "A", "C"]
```

`Dice` is the small seeded generator from [Random pivots and 3-way partitioning](/dsa/learn/sort-quick-pivots): the same seed gives the same "random" numbers every run, so this page can show real output. The first shuffle happened to leave D and E where they were. That's allowed: a fair shuffle keeps the original order 1 time in 120 for five cards, and leaves any particular card in place 1 time in 5.

What to notice:

- The loop runs from the **last** index down to 1. When i reaches 0, there's one item left in the hat, and it can only go in slot 0, so there's nothing to do.
- `j` ranges over `0...i`, so `j == i` is possible: "the item already in slot i stays there". Leaving that out is the most common bug, below.
- It's **O(n)** time, with one random number and one swap per item, and **O(1)** extra memory: it shuffles in place.

### Why it's exactly uniform

Count the ways the loop can run. The first step has n choices for j, the next n − 1, then n − 2, down to 2: n × (n − 1) × … × 2 = **n!** equally likely sequences of choices. Each sequence produces a **different** order, because each step decides which remaining item goes into the next slot. n! equally likely sequences, n! orders, one each: every order has probability exactly 1/n!. That's the counting from [Probability and expected value](/dsa/learn/math-probability), and it's the whole proof.

## Two classic mistakes, measured

Here are two loops that look almost the same:

- **"Anywhere":** for each position i, swap it with a random position from the **whole** array, `0...(n - 1)`.
- **"Never stays":** like Fisher–Yates, but j comes from `0...(i - 1)`, so the item in slot i always moves.

Shuffle [0, 1, 2] 60,000 times with each, and count the six orders. A fair shuffle should give about 10,000 each:

```swift run
// Shuffle [0, 1, 2] 60,000 times three ways, and count how often each of the 6 orders comes out
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 2026)

func fisherYates(_ items: inout [Int]) {
    for i in stride(from: items.count - 1, through: 1, by: -1) {
        items.swapAt(i, dice.roll(0...i))
    }
}

func anywhere(_ items: inout [Int]) {            // the bug: swap every position with any position
    for i in 0..<items.count {
        items.swapAt(i, dice.roll(0...(items.count - 1)))
    }
}

func neverStays(_ items: inout [Int]) {          // the other bug: j from 0..<i, never i itself
    for i in stride(from: items.count - 1, through: 1, by: -1) {
        items.swapAt(i, dice.roll(0...(i - 1)))
    }
}

let orders = [[0, 1, 2], [0, 2, 1], [1, 0, 2], [1, 2, 0], [2, 0, 1], [2, 1, 0]]
print("order    ", orders.map { $0.map(String.init).joined() }.joined(separator: "   "))
for (name, shuffle) in [("correct  ", fisherYates), ("anywhere ", anywhere), ("0..<i    ", neverStays)] {
    var counts = [Int](repeating: 0, count: orders.count)
    for _ in 0..<60_000 {
        var items = [0, 1, 2]
        shuffle(&items)
        counts[orders.firstIndex(of: items)!] += 1
    }
    print(name, counts.map { String($0) }.joined(separator: " "))
}
```

```output
order     012   021   102   120   201   210
correct   10060 9921 9994 9980 10125 9920
anywhere  9024 11157 11085 10959 8846 8929
0..<i     0 0 0 30098 29902 0
```

The correct shuffle wobbles around 10,000, as random counts should. The other two are visibly broken.

### Why "anywhere" is biased

It makes n random choices of n options each: n^n equally likely sequences. For three items that's 27, and 27 sequences can't be shared out evenly among 6 orders, because 27 isn't a multiple of 6. Some orders must get more sequences than others. Count them all:

```swift run
// Count exactly: every sequence of choices the "anywhere" shuffle can make for three items
let orders = [[0, 1, 2], [0, 2, 1], [1, 0, 2], [1, 2, 0], [2, 0, 1], [2, 1, 0]]
var counts = [Int](repeating: 0, count: orders.count)
for first in 0..<3 {
    for second in 0..<3 {
        for third in 0..<3 {
            var items = [0, 1, 2]
            items.swapAt(0, first)
            items.swapAt(1, second)
            items.swapAt(2, third)
            counts[orders.firstIndex(of: items)!] += 1
        }
    }
}
print(counts, counts.reduce(0, +))
```

```output
[4, 5, 5, 5, 4, 4] 27
```

Three orders have probability 5/27 (about 18.5%) and three have 4/27 (about 14.8%), instead of 1/6 (16.7%). Multiply by 60,000 and you get the 11,111 and 8,889 the simulation was circling. For larger n the bias gets worse, not better: n^n is never a multiple of n! for n ≥ 3, and some orders end up several times likelier than others.

### Why "never stays" is broken

Excluding j == i means the item in slot i **always** moves. It's a real algorithm, **Sattolo's algorithm**, and it produces only orders that form one big cycle: no item ever ends where it started. For three items, that's just 120 and 201, as the table shows. Useful if you want a random cyclic order (say, a Secret Santa where nobody draws themselves, all in one loop); wrong for a shuffle.

<Callout kind="gotcha" title="Don't shuffle by sorting with a random comparison">
`items.sorted { _, _ in Bool.random() }` is a well-known broken shuffle. A sort assumes its comparison is consistent (if a comes before b, b doesn't come before a), and a coin flip isn't. Swift won't crash, but the result is biased in ways that depend on the sorting algorithm. Sorting by a random **key** per item (give each item a random `UInt64` and sort by it) is fair, apart from vanishingly rare ties, but it's O(n log n) for an O(n) job.
</Callout>

## Swift's shuffle(), and your own generator

You rarely write Fisher–Yates in an app. Swift's arrays have it built in:

- `items.shuffle()` shuffles in place.
- `items.shuffled()` returns a shuffled copy.

Both use the **system random number generator**, `SystemRandomNumberGenerator`, which is seeded from the operating system and is different every run. That's what you want in an app: an unpredictable order. It's what you **don't** want in a test, where a failure must happen again when you rerun it.

So every random API in Swift has a twin that takes a generator: `shuffle(using:)`, `shuffled(using:)`, `Int.random(in:using:)`, `randomElement(using:)`, `Bool.random(using:)`. The generator is anything that conforms to the `RandomNumberGenerator` protocol, which asks for a single method, `mutating func next() -> UInt64`. Write a seeded one, and the "random" choices become reproducible:

```swift run
// A seeded generator: any type with a mutating next() -> UInt64 can drive Swift's random APIs
struct SeededGenerator: RandomNumberGenerator {
    private var state: UInt64
    init(seed: UInt64) { state = seed }

    mutating func next() -> UInt64 {          // SplitMix64: a fast, well-mixed 64-bit generator
        state &+= 0x9E37_79B9_7F4A_7C15
        var z = state
        z = (z ^ (z >> 30)) &* 0xBF58_476D_1CE4_E5B9
        z = (z ^ (z >> 27)) &* 0x94D0_49BB_1331_11EB
        return z ^ (z >> 31)
    }
}

let songs = ["Intro", "Rain", "Neon", "Drift", "Echo", "Coda"]

var first = SeededGenerator(seed: 42)
var second = SeededGenerator(seed: 42)
var other = SeededGenerator(seed: 7)

let a = songs.shuffled(using: &first)
let b = songs.shuffled(using: &second)
let c = songs.shuffled(using: &other)
print("same seed, same order:", a == b)
print("different seed, same order:", a == c)
print("still the same songs:", a.sorted() == songs.sorted())

// The same generator works for single random values too
var dice = SeededGenerator(seed: 1)
let rolls = (1...5).map { _ in Int.random(in: 1...6, using: &dice) }
var again = SeededGenerator(seed: 1)
let rollsAgain = (1...5).map { _ in Int.random(in: 1...6, using: &again) }
print("rolls repeat:", rolls == rollsAgain, "all in 1...6:", rolls.allSatisfy { (1...6).contains($0) })
```

```output
same seed, same order: true
different seed, same order: false
still the same songs: true
rolls repeat: true all in 1...6: true
```

The generator is passed `inout` (with `&`), because drawing a number changes its state. This page prints comparisons rather than the shuffled songs themselves: the exact order depends on how the standard library turns generator output into indexes, which Swift doesn't promise to keep the same between versions. Your own Fisher–Yates loop, driven by your own generator, is the only way to get an order that never changes.

### Designing for tests

The pattern for your own randomised code: take the generator as a parameter, and offer a convenience version that uses the system generator.

```swift
/// A random order of `items`. Pass a seeded generator in tests.
func shuffledPlaylist<T>(_ items: [T], using generator: inout some RandomNumberGenerator) -> [T] {
    var result = items
    guard result.count > 1 else { return result }
    for i in stride(from: result.count - 1, through: 1, by: -1) {
        result.swapAt(i, Int.random(in: 0...i, using: &generator))
    }
    return result
}

/// The everyday version: unpredictable every time.
func shuffledPlaylist<T>(_ items: [T]) -> [T] {
    var system = SystemRandomNumberGenerator()
    return shuffledPlaylist(items, using: &system)
}
```

`inout some RandomNumberGenerator` means "any generator type, chosen by the caller". In tests you pass a seeded generator and get the same result every run; the app calls the short version. Every randomised problem in this module takes a generator this way.

`Int.random(in: 0...i, using:)` is also more careful than `Dice`. Taking a 64-bit number `% count` favours small results very slightly whenever 2^64 isn't a multiple of the count: harmless for picking pivots, but the standard library removes even that tiny bias. Prefer it whenever you have a real `RandomNumberGenerator`.

<Callout kind="gotcha" title="Seeded generators are not for secrets">
A seeded generator is completely predictable: anyone who knows the seed (or sees a few outputs) knows every number that follows. Use them for tests, simulations and reproducible demos. For anything an attacker might want to guess, such as tokens, passwords or a gambling app's shuffle, use `SystemRandomNumberGenerator`, which is cryptographically secure on Apple platforms.
</Callout>
