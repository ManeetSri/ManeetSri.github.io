## Why it matters

You built quickselect in [Quickselect](/dsa/learn/sort-quickselect): partition around a random pivot, keep only the side that holds index k, repeat. That lesson argued informally that it's O(n) "on average", because the range shrinks geometrically. This lesson makes the claim precise, because the same reasoning powers every randomised algorithm you'll meet: what "expected O(n)" promises (and what it doesn't), two proofs of it, one rough and one exact, and how much a single run can stray from its average. That's the difference between "it seems fast" and "it's fast, and here's how sure I am", which is what a code review or an interviewer wants to hear.

## Expected over coin flips, for every input

Two different "averages" hide behind the word:

- **Average-case analysis** averages over **inputs**. Quickselect with a fixed last-element pivot is fast on average over random inputs, but someone can hand it a sorted array, every time, and it takes O(n²).
- **Expected running time** of a **randomised** algorithm averages over the algorithm's own **coin flips**, for one fixed input. The promise is: whatever input you give it, even one chosen by an adversary who has read the code, the expected number of steps is O(n).

The second is far stronger. It doesn't assume anything about the data; it only assumes the random numbers are random. That's why [Random pivots and 3-way partitioning](/dsa/learn/sort-quick-pivots) chose pivots at random instead of hoping the input was well mixed.

Everything below assumes **distinct values** and a **uniformly random pivot** from the current range, with the Lomuto partition from M31, which compares every other element of the range with the pivot once.

## A first proof: good pivots come often

Call a pivot **good** if it lands in the middle half of its range: at least a quarter of the range is on each side of it. Half the elements of any range are in its middle half, so a random pivot is good with probability **1/2**.

After a good pivot, whichever side the search keeps holds at most **3/4** of the range. So split the run into **phases**: phase j lasts while the range has between (3/4)^(j + 1) · n and (3/4)^j · n elements.

- Each partition in phase j costs at most (3/4)^j · n comparisons.
- A phase ends at the latest when a good pivot arrives. Each pivot is good with probability 1/2, so by the waiting-time rule from [Probability and expected value](/dsa/learn/math-probability), a phase lasts **2 partitions** on average.

By linearity of expectation, add up the phases' expected costs:

```text
E[comparisons] ≤ 2n + 2(3/4)n + 2(3/4)²n + …  =  2n × 1 / (1 − 3/4)  =  8n
```

So the expected number of comparisons is at most **8n**: O(n), for every input. The constant 8 is loose (the argument ignores every pivot that's better than "good"), but the shape is exactly the geometric series from M31, now with the probability spelt out.

## An exact count: which pairs get compared?

For the true constant, count **pairs** instead of partitions. Name the values by their sorted position, their **rank**: 0 is the smallest, n − 1 the largest, and t is the target rank you're looking for.

Take two ranks a < b. Look at the **span** of ranks from min(a, t) to max(b, t). While no pivot has been chosen from that span, a and b are both still in the search range (the range always contains t, and it's contiguous). The first pivot chosen from the span decides their fate:

- If it's **a or b**, the two are compared (the pivot is compared with everything in its range).
- If it's anything else in the span, they're either separated (pivot between them) or thrown away together (pivot between them and t), and never compared.

Every rank in the span is equally likely to be that first pivot, so a and b are compared with probability **2 / (span length)**. By linearity of expectation, the expected number of comparisons is the sum of that over all pairs. Check the formula against real runs:

```swift run
import Foundation

// Expected comparisons of randomised quickselect: the pair formula against an average of real runs
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 31)

/// Comparisons made by one run of quickselect (Lomuto, random pivot) looking for index k
func comparisons(_ numbers: [Int], _ k: Int) -> Int {
    var items = numbers
    var low = 0
    var high = items.count - 1
    var count = 0
    while true {
        items.swapAt(dice.roll(low...high), high)
        let pivot = items[high]
        var boundary = low
        for j in low..<high {
            count += 1
            if items[j] < pivot {
                items.swapAt(boundary, j)
                boundary += 1
            }
        }
        items.swapAt(boundary, high)
        if boundary == k { return count }
        if k < boundary { high = boundary - 1 } else { low = boundary + 1 }
    }
}

/// The exact expected count: ranks a < b are compared only if one of them is the first pivot chosen
/// from the span between min(a, target) and max(b, target)
func expected(n: Int, target: Int) -> Double {
    var total = 0.0
    for a in 0..<n {
        for b in (a + 1)..<n {
            let span = max(b, target) - min(a, target) + 1
            total += 2.0 / Double(span)
        }
    }
    return total
}

let n = 1_000
let numbers = (0..<n).map { ($0 * 7_919) % n }       // 0..<1000 in a scrambled order
for (name, target) in [("smallest", 0), ("median", n / 2)] {
    let runs = 400
    var sum = 0
    for _ in 0..<runs {
        sum += comparisons(numbers, target)
    }
    let average = Double(sum) / Double(runs)
    print(name + ":", String(format: "formula %.1f, average of %d runs %.1f", expected(n: n, target: target), runs, average))
}
print(String(format: "2n = %d, 2n(1 + ln 2) = %.1f", 2 * n, 2 * Double(n) * (1 + log(2.0))))
```

```output
smallest: formula 1985.0, average of 400 runs 1945.4
median: formula 3336.3, average of 400 runs 3336.8
2n = 2000, 2n(1 + ln 2) = 3386.3
```

What to notice:

- The formula and the measured averages agree to within the noise of 400 random runs. (`String(format:)` from Foundation rounds the `Double`s to one decimal place, so the output is the same every run.)
- Finding the **smallest** costs about **2n** comparisons. Summing the formula gives exactly 2(n − Hₙ), where Hₙ is the harmonic number from M15, about 7.5 for n = 1,000.
- Finding the **median** is the most expensive target, about **2n(1 + ln 2) ≈ 3.39n** as n grows. Every target costs between 2n and 3.39n on average: far better than the 8n bound, and far better than sorting's n log₂ n ≈ 10n for 1,000 values.

This "indicator per pair" trick, "compared or not?" with a probability for each pair and linearity to add them up, is the standard way to analyse randomised algorithms. Apply it to quick sort, where the span is just a...b, and it gives the famous 2n ln n ≈ 1.39 n log₂ n expected comparisons.

## How far can one run stray?

An expected value is an average. A single run can be slower, so how much slower, how often?

```swift run
// How much do runs vary? 200 runs of quickselect for the median of 5,000 values
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 67)

func comparisons(_ numbers: [Int], _ k: Int) -> (comparisons: Int, partitions: Int) {
    var items = numbers
    var low = 0
    var high = items.count - 1
    var count = 0
    var partitions = 0
    while true {
        partitions += 1
        items.swapAt(dice.roll(low...high), high)
        let pivot = items[high]
        var boundary = low
        for j in low..<high {
            count += 1
            if items[j] < pivot {
                items.swapAt(boundary, j)
                boundary += 1
            }
        }
        items.swapAt(boundary, high)
        if boundary == k { return (count, partitions) }
        if k < boundary { high = boundary - 1 } else { low = boundary + 1 }
    }
}

let n = 5_000
let numbers = (0..<n).map { ($0 * 7_919) % n }
var results: [Int] = []
var partitionTotal = 0
for _ in 0..<200 {
    let run = comparisons(numbers, n / 2)
    results.append(run.comparisons)
    partitionTotal += run.partitions
}
let average = results.reduce(0, +) / results.count
print("fewest \(results.min()!), average \(average), most \(results.max()!)")
print("runs over 1.5 × average: \(results.filter { 2 * $0 > 3 * average }.count) of \(results.count)")
print("partitions per run on average: \(partitionTotal / results.count)")
```

```output
fewest 8121, average 16319, most 32889
runs over 1.5 × average: 14 of 200
partitions per run on average: 15
```

The slowest of 200 runs took about twice the average; 7% of runs took more than 1.5 times it. Nothing came near the 12.5 million comparisons of the worst case, n(n − 1)/2. About 15 partitions per run: the range shrinks geometrically, so there are O(log n) rounds.

Two facts make this precise:

- **Markov's inequality**, which holds for anything that can't be negative: the chance of taking at least t times the expected value is at most 1/t. So a run that's 10 times slower than average happens at most 1 time in 10. That's a weak bound, but it needs no knowledge of the algorithm.
- For quickselect, the real tail is far thinner: the chance of exceeding c times the expected cost falls **exponentially** in c. A quadratic run on a million values would need hundreds of consecutive bad pivots, which is less likely than every computer on Earth failing at the same moment.

<Callout kind="analogy" title="A bus that's usually on time">
"Expected O(n)" is like a bus timetable that's right on average. Markov's inequality promises the bus is rarely ten times late. Quickselect's actual record is better than that: it's sometimes twice as late, almost never three times, and the case where it never comes is possible on paper and has never been seen.
</Callout>

## When "almost never" isn't enough

Some systems can't accept even a tiny chance of a slow run, and some face attackers who can influence the random numbers (if your seed is fixed or predictable, the adversary is back). The standard fixes:

- **Introselect**, used by common implementations of C++'s `std::nth_element`: run quickselect, but count the partitions. If they exceed a limit such as 2 log₂ n, the pivots have been unlucky, so switch to [median of medians](/dsa/learn/sort-median-of-medians), which is O(n) in the worst case. You get quickselect's speed with a guaranteed bound.
- **Sampling** (the Floyd–Rivest algorithm): pick the pivots from a small random sample so they land very close to the target, cutting the expected comparisons towards n + min(k, n − k).
- **Three-way partitioning** for duplicates. With many equal values, a two-way partition is quadratic whatever the pivot, as M31 showed; random pivots fix bad orders, not bad values.

Swift's standard library has no selection algorithm. The swift-algorithms package offers `min(count:)` and `max(count:)` for the k smallest or largest elements, and DSAKit has `kthSmallest(_:)` from M31.

Randomised quickselect is the textbook **Las Vegas** algorithm: its answer is always right, and only its running time is random. The next lesson contrasts it with algorithms that are always fast but only *probably* right.

<Callout kind="gotcha" title="Common mistakes">
- **Claiming O(n) worst case.** Randomised quickselect is O(n) **expected** and O(n²) in the worst case. Say both.
- **Confusing "expected" with "average input".** The expectation is over the pivots, for any input. That's what makes it robust.
- **A fixed seed in production.** A seeded generator makes the pivots predictable, so a crafted input can force the quadratic case again. Seed for tests, use the system generator in shipping code.
- **Ignoring duplicates.** Random pivots don't help when all values are equal; partition three ways.
</Callout>
