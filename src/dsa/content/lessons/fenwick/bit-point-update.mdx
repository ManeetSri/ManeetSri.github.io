## Why it matters

Point updates with prefix sums are everywhere once you look: a leaderboard that counts how many players scored below you, a log that counts events before a timestamp, an inventory where items arrive and leave and you need running totals. A sum segment tree handles them, but a **Fenwick tree** does it in two five-line loops over an array of n + 1 integers, with no recursion and a small, fast inner loop. It's the structure competitive programmers type from memory, and the one this module builds on for range updates, inversions and order statistics.

## The array

Count positions from 1. Slot i of the array `tree` holds the sum of the items index i is responsible for, from [The lowest set bit, i & -i](/dsa/learn/bit-lowbit): the `lowbit(i)` items ending at position i.

| Slot | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Covers items | 1 | 1–2 | 3 | 1–4 | 5 | 5–6 | 7 | 1–8 |

So odd slots hold single items, slot 4 holds the sum of the first four, and slot 8 holds everything. Slot 0 is never used. There's no tree of nodes and pointers: the "tree" is in the index arithmetic.

## The two loops

**Prefix query**: the sum of items 1 through i. Add `tree[i]`, which covers the last `lowbit(i)` of those items, then jump to the slot just before that range, `i - lowbit(i)`, and repeat until i reaches 0. The ranges you visit sit end to end and cover 1...i exactly once.

**Point update**: add `delta` to item p. Every slot whose range contains p must change, and those are exactly the slots visited by climbing `p`, `p + lowbit(p)`, and so on, while the index is at most n.

Step through both on 8 items. The query adds up the first 7 items, and the update adds 2 to item 3. Each entry shows its index and the items it covers.

```visual fenwick
items: [3, 2, -1, 6, 5, 4, -3, 3]
query: 7
update: [3, 2]
```

Here are the same loops in Swift, building the tree with one `add` per item:

```swift run
// A Fenwick tree for 8 items, built with one add per item. Positions count from 1; slot 0 is unused.
let items = [3, 2, -1, 6, 5, 4, -3, 3]
let n = items.count
var tree = Array(repeating: 0, count: n + 1)

func add(_ delta: Int, at position: Int) {
    var i = position
    while i <= n {
        tree[i] += delta
        i += i & -i                               // the next slot whose range covers position
    }
}

func prefixSum(_ position: Int) -> Int {          // the sum of items 1...position
    var i = position
    var total = 0
    while i > 0 {
        total += tree[i]
        i -= i & -i                               // the range just before this one
    }
    return total
}

for (offset, value) in items.enumerated() {
    add(value, at: offset + 1)
}
print("tree:", Array(tree[1...]))
print("first 7 items:", prefixSum(7))
print("items 3...6:", prefixSum(6) - prefixSum(2))
add(2, at: 3)                                     // item 3 goes from -1 to 1
print("first 7 items:", prefixSum(7))
```

```output
tree: [3, 5, -1, 10, 5, 9, -3, 19]
first 7 items: 16
items 3...6: 14
first 7 items: 18
```

What to notice:

- The first 7 items add up from three slots: `tree[7]` (item 7), `tree[6]` (items 5–6) and `tree[4]` (items 1–4): −3 + 9 + 10 = 16.
- **A range sum is two prefix sums**: items 3...6 are the first 6 minus the first 2. That subtraction is the Fenwick tree's one real limitation: it works for sums and XORs, which can be undone, but not for minimums or maximums.
- Adding 2 to item 3 touched slots 3, 4 and 8, the slots whose ranges contain item 3, and nothing else.

Both loops take at most about log₂ n steps, so both operations are **O(log n)**. The memory is n + 1 integers, against 2n to 4n for a segment tree.

## Why the two walks are exactly right

**The query never misses or double-counts an item.** Slot i covers positions `i − lowbit(i) + 1` through `i`. After adding it, the loop moves to `i − lowbit(i)`, the position just before that range starts. The next slot's range ends there, so it sits immediately to the left: no gap, no overlap. The walk ends at 0, so the ranges cover 1 through i exactly once. Each step clears one set bit, which bounds the steps by about log₂ n.

**The update finds every slot that covers position p, and only those.** Start at slot p, which covers p. Look at the indexes between i and `i + lowbit(i)`. Each has a lowest set bit **smaller** than `lowbit(i)`, so its range is short and starts after i: it can't reach back to p. The index `i + lowbit(i)` itself is different. Adding the lowest set bit carries into a higher bit, so its lowbit is at least twice as big, and its range stretches back far enough to include everything i covered, p included. So the walk jumps straight from one covering slot to the next.

For p = 5 in a tree of 16: slot 5 covers 5, slot 6 covers 5–6, slot 7 covers only 7 (skipped, correctly), slot 8 covers 1–8, and slot 16 covers 1–16. The walk visits 5, 6, 8 and 16, exactly the slots whose sums include item 5.

## An O(n) build

Calling `add` once per item builds the tree in O(n log n). There's a neater way. Start with each slot holding its own item. Then go through the slots in increasing order, and let each one add its total into its **parent**, the next slot up whose range contains it, `i + lowbit(i)`. By the time the loop reaches slot i, every smaller slot that feeds into it has already passed its total up, so slot i is complete and ready to pass its own total on. Each slot passes up exactly once: **O(n)**.

## A struct with a 0-indexed API

Swift arrays count from 0, and a Fenwick tree has to count from 1. The clean answer is to keep the conversion in one place: the public methods take 0-indexed positions and add 1 on the way in.

```swift run
// A Fenwick tree with an O(n) build and a 0-indexed API (1-indexed inside)
struct Fenwick {
    private var tree: [Int]                       // tree[i] covers positions i - lowbit(i) + 1 ... i

    init(_ items: [Int]) {
        tree = [0] + items                        // each slot starts with its own item...
        for i in 1..<tree.count {
            let parent = i + (i & -i)             // ...then passes its finished total up once
            if parent < tree.count {
                tree[parent] += tree[i]
            }
        }
    }

    /// Adds delta to items[index].
    mutating func add(_ delta: Int, at index: Int) {
        var i = index + 1
        while i < tree.count {
            tree[i] += delta
            i += i & -i
        }
    }

    /// The sum of items[0...index]. An index of -1 gives 0.
    func prefixSum(through index: Int) -> Int {
        var i = index + 1
        var total = 0
        while i > 0 {
            total += tree[i]
            i -= i & -i
        }
        return total
    }

    /// The sum of items[left...right].
    func sum(_ left: Int, _ right: Int) -> Int {
        prefixSum(through: right) - prefixSum(through: left - 1)
    }
}

var scores = Fenwick([3, 2, -1, 6, 5, 4, -3, 3])
print(scores.sum(0, 6), scores.sum(2, 5), scores.sum(7, 7))
scores.add(2, at: 2)
print(scores.sum(0, 6), scores.sum(2, 2))

// Check every range against plain addition, after each of 1,000 updates on 11 items
var items = [4, -2, 8, 0, 3, 3, 9, -5, 1, 6, 2]
var checked = Fenwick(items)
var mismatches = 0
for step in 0..<1_000 {
    let index = (step * 7) % items.count
    let delta = (step * 13) % 21 - 10
    items[index] += delta
    checked.add(delta, at: index)
    for left in 0..<items.count {
        for right in left..<items.count where checked.sum(left, right) != items[left...right].reduce(0, +) {
            mismatches += 1
        }
    }
}
print("mismatches:", mismatches)
```

```output
16 14 3
18 1
mismatches: 0
```

`prefixSum(through: -1)` returns 0 without a special case: `i` starts at 0 and the loop never runs. That makes `sum(left, right)` work for `left == 0` too, much like the leading 0 in the prefix-sum arrays of M20.

### Setting a value instead of adding to it

A Fenwick tree only knows how to **add**. To set item i to a new value, add the difference: `add(newValue - current, at: i)`. The tree doesn't store the items directly, so either keep a copy of the items array alongside it, or read the current value as `sum(i, i)`, which costs O(log n).

## DSAKit's `FenwickTree`

`dsa-swift/Sources/DSAKit/FenwickTree.swift` is this struct with Swift-style names and range expressions. Like `Array.prefix(upTo:)` and `prefix(through:)`, it has both an exclusive and an inclusive prefix:

```swift
import DSAKit

var counts = FenwickTree([3, 2, -1, 6, 5])   // O(n) build; FenwickTree(count: n) starts at zeros
counts.prefixSum(through: 2)                 // 4: items 0...2
counts.prefixSum(upTo: 2)                    // 5: items 0..<2, and upTo: 0 is 0
counts.add(10, at: 1)                        // items are now [3, 12, -1, 6, 5]
counts.sum(in: 1...3)                        // 17: any range expression
counts[1]                                    // 12, in O(log n)
counts.set(0, at: 3)                         // adds the difference
counts.values                                // [3, 12, -1, 0, 5], in O(n)
```

## Fenwick tree or segment tree?

For point updates and range sums, both are O(log n). The Fenwick tree is shorter, uses a quarter of the memory of a recursive segment tree, and its loops run faster in practice. The segment tree handles operations that can't be undone (minimum, maximum, gcd), custom summaries and lazy range assignments. When a problem only needs sums, counts or XORs, reach for the Fenwick tree.

<Callout kind="gotcha" title="Common mistakes">
- **Starting at index 0.** `0 & -0` is 0, so an update from slot 0 loops forever. Convert 0-indexed positions with `+ 1` in exactly one place.
- **An array of n instead of n + 1.** Slot n is real; slot 0 is the unused one. Make the array one longer than the items.
- **The wrong loop bound.** The update climbs while `i <= n` (or `i < tree.count`). Stopping at `i < n` silently skips slot n, which is the total for powers of two.
- **Setting instead of adding.** `add(5, at: i)` adds 5; it doesn't make the item 5. Add the difference to set.
- **Expecting range minimums.** A prefix minimum can't be "subtracted" away, so `min(items[l...r])` isn't available. Use a segment tree.
</Callout>
