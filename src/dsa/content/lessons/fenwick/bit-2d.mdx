## Why it matters

A map app counts the cafés inside the rectangle you've zoomed to while new ones keep opening. A game totals the damage dealt in a region of the board as units move. A farm-management tool sums the yield over any block of fields as harvest figures come in. Each is a grid with **point updates** and **rectangle sums**. [2D prefix sums and difference arrays](/dsa/learn/prefix-2d) answer rectangle sums in O(1), but one changed cell spoils every prefix value below and to the right of it. A 2D Fenwick tree makes both operations O(log n × log m), and the code is the 1D tree with a second loop inside the first.

## A Fenwick tree of Fenwick trees

In one dimension, slot i covers a range of positions. In two, slot `(i, j)` covers a **rectangle**: the rows that i is responsible for, crossed with the columns that j is responsible for. In 1-indexed terms, it holds the sum of rows `i − lowbit(i) + 1 ... i` and columns `j − lowbit(j) + 1 ... j`.

The two loops follow:

- **Update** cell `(r, c)` by `delta`: climb the rows with `i += lowbit(i)`, and for each of those rows climb the columns with `j += lowbit(j)`, adding `delta` to `tree[i][j]`. Those are exactly the rectangles that contain the cell.
- **Prefix query** for the rectangle from `(1, 1)` to `(r, c)`: walk down the rows with `i -= lowbit(i)`, and for each, walk down the columns with `j -= lowbit(j)`, adding up `tree[i][j]`. The row ranges tile `1...r` and the column ranges tile `1...c`, so their products tile the rectangle exactly once.

Each loop is O(log n) steps of an O(log m) loop: **O(log n × log m)** per operation. For a 1,000 × 1,000 grid that's at most 100 slots, against up to a million cells for a direct sum.

## Any rectangle from four prefixes

A prefix query always starts at the top-left corner. Any other rectangle comes from four of them, by the inclusion–exclusion you used for 2D prefix sums: take the big rectangle down to the bottom-right corner, remove the strip above the rectangle and the strip to its left, and add back the corner piece that was removed twice.

```text
sum(top...bottom, left...right) = P(bottom, right) − P(top − 1, right) − P(bottom, left − 1) + P(top − 1, left − 1)
```

The code below uses a 0-indexed API with an exclusive prefix, `prefixSum(rows: r, columns: c)` for the cells in rows `0..<r` and columns `0..<c`, so the formula has no `− 1`s, and a prefix with 0 rows or columns is 0 without a special case.

```swift run
// A 2D Fenwick tree: point additions and rectangle sums on a grid, 1-indexed inside
struct Fenwick2D {
    private var tree: [[Int]]
    let rows: Int
    let columns: Int

    init(rows: Int, columns: Int) {
        self.rows = rows
        self.columns = columns
        tree = Array(repeating: Array(repeating: 0, count: columns + 1), count: rows + 1)
    }

    /// Adds delta to the cell (row, column), both 0-indexed.
    mutating func add(_ delta: Int, row: Int, column: Int) {
        var i = row + 1
        while i <= rows {
            var j = column + 1
            while j <= columns {                  // the 1D update, once per row-range i covers
                tree[i][j] += delta
                j += j & -j
            }
            i += i & -i
        }
    }

    /// The sum of every cell in rows 0..<row and columns 0..<column.
    func prefixSum(rows row: Int, columns column: Int) -> Int {
        var total = 0
        var i = row
        while i > 0 {
            var j = column
            while j > 0 {                         // the 1D query, once per row-range
                total += tree[i][j]
                j -= j & -j
            }
            i -= i & -i
        }
        return total
    }

    /// The sum of the rectangle from (top, left) to (bottom, right), inclusive.
    func sum(top: Int, left: Int, bottom: Int, right: Int) -> Int {
        prefixSum(rows: bottom + 1, columns: right + 1)
            - prefixSum(rows: top, columns: right + 1)
            - prefixSum(rows: bottom + 1, columns: left)
            + prefixSum(rows: top, columns: left)
    }
}

var field = Fenwick2D(rows: 4, columns: 5)
let start = [
    [3, 0, 1, 4, 2],
    [5, 6, 3, 2, 1],
    [1, 2, 0, 1, 5],
    [4, 1, 0, 1, 7],
]
for (r, row) in start.enumerated() {
    for (c, value) in row.enumerated() {
        field.add(value, row: r, column: c)
    }
}
print(field.sum(top: 1, left: 1, bottom: 2, right: 3))      // 6 + 3 + 2 + 2 + 0 + 1
field.add(10, row: 2, column: 2)
print(field.sum(top: 1, left: 1, bottom: 2, right: 3))
print(field.sum(top: 0, left: 0, bottom: 3, right: 4), field.sum(top: 3, left: 4, bottom: 3, right: 4))

// Compare with adding up the rectangle cell by cell, over 2,000 random operations on a 6 × 7 grid
var grid = Array(repeating: Array(repeating: 0, count: 7), count: 6)
var checked = Fenwick2D(rows: 6, columns: 7)
var state: UInt64 = 2
func next(_ limit: Int) -> Int {
    state = state &* 6364136223846793005 &+ 1442695040888963407
    return Int((state >> 33) % UInt64(limit))
}
var mismatches = 0
for _ in 0..<2_000 {
    if next(2) == 0 {
        let r = next(6), c = next(7), delta = next(21) - 10
        grid[r][c] += delta
        checked.add(delta, row: r, column: c)
    } else {
        let r1 = next(6), r2 = next(6), c1 = next(7), c2 = next(7)
        let top = min(r1, r2), bottom = max(r1, r2), left = min(c1, c2), right = max(c1, c2)
        var expected = 0
        for r in top...bottom {
            for c in left...right { expected += grid[r][c] }
        }
        if checked.sum(top: top, left: left, bottom: bottom, right: right) != expected { mismatches += 1 }
    }
}
print("mismatches:", mismatches)
```

```output
14
24
59 7
mismatches: 0
```

What to notice:

- `add` and `prefixSum` are the 1D loops from [Point update and prefix query](/dsa/learn/bit-point-update), nested. Nothing else is new.
- The build here adds each cell once: O(n × m × log n × log m). A 2D version of the O(n) parent-passing build exists (pass along the rows, then along the columns), but for most problems the simple build is fast enough.
- The check compares 1,000 rectangles against a cell-by-cell sum, with updates in between. In two dimensions, sign and off-by-one errors in the inclusion–exclusion are the usual bugs, and this finds them at once.

## The costs, and when the grid is too big

| | 2D prefix sums | 2D Fenwick tree | Plain grid |
| --- | --- | --- | --- |
| Point update | O(n × m) | O(log n × log m) | O(1) |
| Rectangle sum | O(1) | O(log n × log m) | O(n × m) |
| Memory | n × m | n × m | n × m |

The memory is the limit. A 2,000 × 2,000 grid is four million `Int`s, 32 MB, which is about as far as a dense 2D tree goes comfortably. When the coordinates are huge but the points are few, say 100,000 points with coordinates up to a billion, there are two standard ways out:

- **Offline**: if all the updates and queries can be read first, compress the coordinates (M62), or sweep along one axis and keep a 1D Fenwick tree over the other.
- **Online**: keep, for each row slot, only the column positions that will ever be updated there, sorted, with a small Fenwick tree over them. Each lookup becomes a binary search plus a 1D walk.

Both go beyond this lesson, but they're the same idea: never allocate cells nobody uses.

<Callout kind="gotcha" title="Common mistakes">
- **Restarting the inner index.** The column loop must start again from `column + 1` for every row slot. Declaring `j` outside the row loop makes the second row start where the first stopped.
- **Inclusion–exclusion signs.** Two subtractions and one addition. Getting the corner's sign wrong double-counts or removes it; a random check against a brute-force sum catches it immediately.
- **Rows and columns swapped.** `tree[i][j]` with i for rows and j for columns, everywhere. If the grid isn't square, a swap crashes or, worse, quietly reads the wrong cells when the index happens to fit.
- **Allocating too much.** A 100,000 × 100,000 grid is 10¹⁰ cells. Check n × m before you allocate.
</Callout>
