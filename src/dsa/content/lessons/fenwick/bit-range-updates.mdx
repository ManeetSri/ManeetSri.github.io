## Why it matters

A plain Fenwick tree changes one item at a time. Plenty of problems change whole ranges: add a booking to every night of a stay, give everyone in a department a raise, add rainfall to every square of a strip of farmland. In [Lazy propagation](/dsa/learn/seg-lazy) a segment tree handled this with tags and push-downs. For **sums**, there's a lighter way: keep the **difference array** from M20 inside a Fenwick tree. One tree gives range updates with point queries; two trees give range updates with range sums, in about twenty lines and no recursion.

## Range add, point query: one tree

Recall [Difference arrays for range updates](/dsa/learn/prefix-difference-array). Instead of the items, store how much each item differs from the one before it: `d[p] = item[p] − item[p − 1]`, counting from 1 with `item[0] = 0`. Then:

- an item is a **prefix sum** of the differences: `item[p] = d[1] + d[2] + … + d[p]`;
- adding v to every item in `l...r` changes only **two** differences: `d[l]` goes up by v (the step up into the range) and `d[r + 1]` goes down by v (the step back down after it).

In M20 the catch was that reading an item meant rebuilding the prefix sums, so all updates had to come before all reads. Put the differences in a Fenwick tree and the catch disappears: each range update is two point updates, and each item is one prefix query. Both are O(log n), in any order.

```swift run
// Range add, point query: a Fenwick tree over the difference array
struct Fenwick {
    private var tree: [Int]
    init(count: Int) { tree = Array(repeating: 0, count: count + 1) }

    /// Adds delta at position (1-indexed); positions past the end are ignored.
    mutating func add(_ delta: Int, at position: Int) {
        var i = position
        while i < tree.count {
            tree[i] += delta
            i += i & -i
        }
    }

    /// The sum of positions 1...position.
    func prefixSum(_ position: Int) -> Int {
        var i = position, total = 0
        while i > 0 {
            total += tree[i]
            i -= i & -i
        }
        return total
    }
}

let n = 8
var changes = Fenwick(count: n)                   // changes holds d, where item p = d[1] + ... + d[p]
func addToRange(_ delta: Int, _ left: Int, _ right: Int) {
    changes.add(delta, at: left)                  // from left onwards, everything rises
    changes.add(-delta, at: right + 1)            // ...and stops rising after right
}
func item(_ position: Int) -> Int { changes.prefixSum(position) }

addToRange(5, 2, 6)
addToRange(-2, 4, 8)
addToRange(1, 1, 1)
print((1...n).map(item))
```

```output
[1, 5, 5, 3, 3, 3, -2, -2]
```

When `right` is the last position, `right + 1` is past the end. The update loop starts beyond the array and never runs, which is exactly right: there are no items after the range to restore.

## Range add, range sum: two trees

Now ask for the **sum** of items 1 through p, call it `S(p)`, while range additions keep arriving. Each item is a prefix sum of differences, so S(p) is a sum of prefix sums. Count how often each difference appears in it. `d[j]` is part of `item[j]`, `item[j + 1]`, and so on up to `item[p]`: that's `p − j + 1` items. So:

```text
S(p) = Σ over j ≤ p of d[j] × (p − j + 1)
     = (p + 1) × Σ d[j]  −  Σ j × d[j]           (both sums over j ≤ p)
```

Both of those sums are **prefix sums**, one of `d[j]` and one of `j × d[j]`, and each can live in its own Fenwick tree:

- `plain` holds `d[j]`;
- `weighted` holds `j × d[j]`.

A range addition of v to `l...r` changes `d[l]` by +v and `d[r + 1]` by −v, so it makes the matching changes in both trees: +v and −v in `plain`, and `+v × l` and `−v × (r + 1)` in `weighted`. A prefix sum is `(p + 1) × plain.prefixSum(p) − weighted.prefixSum(p)`, and a range sum is two of those, as usual.

```swift run
// Range add, range sum: two Fenwick trees over the difference array
struct Fenwick {
    private var tree: [Int]
    init(count: Int) { tree = Array(repeating: 0, count: count + 1) }

    mutating func add(_ delta: Int, at position: Int) {
        var i = position
        while i < tree.count {
            tree[i] += delta
            i += i & -i
        }
    }

    func prefixSum(_ position: Int) -> Int {
        var i = position, total = 0
        while i > 0 {
            total += tree[i]
            i -= i & -i
        }
        return total
    }
}

struct RangeFenwick {
    private var plain: Fenwick                    // the changes d[j]
    private var weighted: Fenwick                 // the changes times their position, j × d[j]

    init(count: Int) {
        plain = Fenwick(count: count)
        weighted = Fenwick(count: count)
    }

    /// Adds delta to every item in left...right (1-indexed).
    mutating func add(_ delta: Int, _ left: Int, _ right: Int) {
        plain.add(delta, at: left)
        plain.add(-delta, at: right + 1)
        weighted.add(delta * left, at: left)
        weighted.add(-delta * (right + 1), at: right + 1)
    }

    /// The sum of items 1...position: (position + 1) × Σ d[j] − Σ j × d[j].
    func prefixSum(_ position: Int) -> Int {
        (position + 1) * plain.prefixSum(position) - weighted.prefixSum(position)
    }

    /// The sum of items left...right.
    func sum(_ left: Int, _ right: Int) -> Int {
        prefixSum(right) - prefixSum(left - 1)
    }
}

var days = RangeFenwick(count: 8)
days.add(5, 2, 6)                                 // items: [0, 5, 5, 5, 5, 5, 0, 0]
days.add(-2, 4, 8)                                // items: [0, 5, 5, 3, 3, 3, -2, -2]
print(days.sum(1, 8), days.sum(3, 5), days.sum(7, 7))

// Compare with a plain array over 3,000 random operations on 13 items
var items = Array(repeating: 0, count: 14)        // items[1...13]; items[0] is unused
var checked = RangeFenwick(count: 13)
var state: UInt64 = 61
func next(_ limit: Int) -> Int {
    state = state &* 6364136223846793005 &+ 1442695040888963407
    return Int((state >> 33) % UInt64(limit))
}
var mismatches = 0
for _ in 0..<3_000 {
    let a = next(13) + 1, b = next(13) + 1
    let left = min(a, b), right = max(a, b)
    if next(2) == 0 {
        let delta = next(21) - 10
        checked.add(delta, left, right)
        for p in left...right { items[p] += delta }
    } else if checked.sum(left, right) != items[left...right].reduce(0, +) {
        mismatches += 1
    }
}
print("mismatches:", mismatches)
```

```output
15 11 -2
mismatches: 0
```

What to notice:

- Every operation is four Fenwick updates or four Fenwick queries: still O(log n), with tiny constants.
- The formula has no special cases. Positions past the end are skipped by the update loop, and `prefixSum(0)` is 0.
- The brute-force check mixes 3,000 additions and sums on 13 items, which is how you'd find a sign error in the `weighted` updates.

### Seeing why the formula works

Take 8 items, all zero, and add 5 to items 2...6. Then `d[2] = 5` and `d[7] = −5`, and everything else is 0.

- For p = 4, the true sum is 5 + 5 + 5 = 15 (items 2, 3 and 4). The formula gives `(4 + 1) × 5 − 2 × 5 = 15`. The first term counts the +5 at all five positions 0 through 4; the second takes away the two positions before the range starts, 0 and 1. That leaves the three positions that really rose.
- For p = 8, both changes are included: `9 × (5 − 5) − (2 × 5 − 7 × 5) = 0 + 25 = 25`, which is 5 items × 5. The step back down at 7 cancels everything after the range.

## Which tool when

| Updates | Queries | Structure |
| --- | --- | --- |
| Point | Range sums | One Fenwick tree over the items |
| Range additions | Single items | One Fenwick tree over the differences |
| Range additions | Range sums | Two Fenwick trees, or a lazy segment tree |
| Range additions | Range minimums or maximums | Lazy segment tree |
| Range assignments | Anything | Lazy segment tree |

The two-tree trick depends on additions combining by adding, and on sums being "undoable" by subtraction. An assignment is neither, and a minimum can't be built from prefix pieces, so for those the segment tree from M60 is still the tool.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting the `r + 1` half.** Adding v at `l` without subtracting it at `r + 1` raises every item from `l` to the end of the array.
- **Weighting by the wrong position.** The second tree gets `v × l` at `l` and `−v × (r + 1)` at `r + 1`: each change is weighted by the position where it's recorded, not by `r`.
- **Mixing up `p` and `p + 1`.** The multiplier is `p + 1`, from counting `p − j + 1` items. Test the formula on a single addition by hand, as above, before trusting it.
- **Overflow.** The `weighted` tree holds position × value. With positions up to 10⁵ and additions up to 10⁹, single entries reach 10¹⁴ and sums go higher: fine in `Int`, but not in `Int32`.
</Callout>
