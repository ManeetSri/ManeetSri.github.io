## Why it matters

The Fenwick tree, also called a **binary indexed tree** or BIT, does the job of a sum segment tree in about ten lines, using an array of n + 1 slots and no recursion. Its whole trick rests on one bit expression, `i & -i`, which picks out the lowest set bit of i. You met it in [Powers of two and the lowest set bit](/dsa/learn/bits-power-of-two). This lesson recaps why it works and then looks at the two walks it creates through the numbers, one downwards and one upwards, which are exactly a Fenwick tree's query and update.

## Recap: why `i & -i` keeps only the lowest set bit

In two's complement, from [Binary and two's complement](/dsa/learn/bits-binary-twos-complement), `-i` is "flip every bit of i, then add 1". Follow that for 24, which is `00011000` in 8 bits:

| Step | Bits | Value |
| --- | --- | --- |
| `i` | `00011000` | 24 |
| flip every bit, `~i` | `11100111` | -25 |
| add 1, giving `-i` | `11101000` | -24 |
| `i & -i` | `00001000` | 8 |

Adding 1 to `~i` turns the run of 1s at the bottom (where i had 0s) back into 0s, and the carry stops at the first 0, exactly where i has its lowest 1. So:

- **below** the lowest set bit, both i and `-i` have 0s;
- **at** it, both have a 1;
- **above** it, `-i` has the opposite of every bit of i.

AND keeps only the bit that's 1 in both: the lowest set bit. Try other values here. The playground is set to `Int8`, with `a` = 24 and `b` = -24; change both to see that `a & b` is always a power of two (or 0):

```visual bitPlayground

```

We'll write `lowbit(i)` for `i & -i` from now on. It's always a power of two, and it's i itself exactly when i is a power of two.

```swift run
// Each number, its last four bits, and its lowest set bit
for i in 1...12 {
    let binary = String(i, radix: 2)
    let padded = String(repeating: "0", count: 4 - binary.count) + binary
    print(i, padded, i & -i)
}
```

```output

2 0010 2
3 0011 1
4 0100 4
5 0101 1
6 0110 2
7 0111 1
8 1000 8
9 1001 1
10 1010 2
11 1011 1
12 1100 4
```

Odd numbers have lowbit 1. Numbers ending in `10` have 2; ending in `100`, 4. Half the numbers have lowbit 1, a quarter have 2, an eighth have 4, and so on.

## Each index is responsible for a range

Here's the idea a Fenwick tree is built on. Count positions from **1**, and make index i **responsible** for the `lowbit(i)` positions that end at i: positions `i - lowbit(i) + 1` through `i`.

```swift run
// The range each index is responsible for: the lowbit(i) positions ending at i
for i in 1...8 {
    let size = i & -i
    print("\(i): positions \(i - size + 1)...\(i)")
}
```

```output
1: positions 1...1
2: positions 1...2
3: positions 3...3
4: positions 1...4
5: positions 5...5
6: positions 5...6
7: positions 7...7
8: positions 1...8
```

Odd indexes cover only themselves. Index 4 covers four positions, and index 8 covers all eight. If slot i of an array stores the **sum** of the items in its range, that array is a Fenwick tree. The next lesson builds it; this one makes sure the walks through it make sense.

## Two walks

**Walking down: `i -= lowbit(i)`.** Removing the lowest set bit of i lands on `i - lowbit(i)`, which is exactly one position before i's range starts. So the ranges of i, then `i - lowbit(i)`, then the next, and so on, sit end to end and cover positions 1 through i with no gaps and no overlaps. For 13, which is `1101`: index 13 covers 13...13, index 12 covers 9...12, index 8 covers 1...8. Three ranges, all of 1...13. That's a **prefix query**.

**Walking up: `i += lowbit(i)`.** Adding the lowest set bit makes it carry into a higher bit, so the lowbit strictly grows at every step. The indexes visited are exactly the ones whose ranges **contain** position i. For 5: 5 covers 5...5, 6 covers 5...6, 8 covers 1...8, 16 covers 1...16. Those are the slots that must change when item 5 changes. That's an **update**.

```swift run
// Stripping the lowest set bit walks down; adding it walks up
func strip(_ start: Int) -> [Int] {
    var path: [Int] = []
    var i = start
    while i > 0 {
        path.append(i)
        i -= i & -i                               // remove the lowest set bit
    }
    return path
}

func climb(_ start: Int, through limit: Int) -> [Int] {
    var path: [Int] = []
    var i = start
    while i <= limit {
        path.append(i)
        i += i & -i                               // add the lowest set bit: it carries upwards
    }
    return path
}

print(strip(13), strip(16), strip(7))
print(climb(5, through: 16), climb(1, through: 16), climb(9, through: 16))
print(13.nonzeroBitCount, strip(13).count)
```

```output
[13, 12, 8] [16] [7, 6, 4]
[5, 6, 8, 16] [1, 2, 4, 8, 16] [9, 10, 12, 16]
3 3
```

### Why both walks are short

Walking down removes one set bit per step, so it takes as many steps as i has 1 bits, `i.nonzeroBitCount`, which is at most ⌊log₂ i⌋ + 1. Walking up moves the lowest set bit at least one place left per step, so it also takes at most about log₂ n steps before passing n. For n = 1,000,000, both walks take at most 20 steps.

<Callout kind="gotcha" title="Swift gotchas">
- **Index 0 never moves.** `0 & -0` is 0, so `i += i & -i` starting from 0 adds 0 forever: an infinite loop. This is the real reason Fenwick trees are **1-indexed**. A 0-indexed public API converts with `+ 1` on the way in.
- **`-i` can trap.** Negating `Int.min` overflows and crashes, and unsigned types have no unary minus at all. Fenwick indexes are small and positive, so `i & -i` is safe there; in general code, `i & (0 &- i)` gives the same bits without the trap.
- **An alternative spelling.** `1 << i.trailingZeroBitCount` is also the lowest set bit. It's clearer to some readers, and equally fast.
</Callout>
