## Why it matters

Some constraints look **forward**: "never let the battery drop below 10% on the way", "the account must never go overdrawn", "the hero's health must stay above zero at every step". The best route isn't the one that ends with the most; it's the one whose **worst moment** is least bad. This lesson's puzzle is a favourite interview question precisely because the obvious forward DP gives wrong answers, and the fix is to fill the table from the far end.

## The puzzle

A knight enters a dungeon grid at the top-left cell and must reach the princess at the bottom-right, moving only right or down. Each cell changes the knight's health: a negative number is a trap that takes health away, a positive number is a potion that adds health, and 0 does nothing. The first and last cells count too.

The knight dies the instant their health drops to 0 or below. What is the **smallest starting health** that lets the knight reach the princess alive?

```text
   0   -8   20
  -1   -1   -1
  -1   -1    0
```

## Forward thinking fails

Try every path through that dungeon, and for each work out its total and the starting health it needs. A path needs enough health that its running total never sinks to 0: if the lowest running total is L, it needs `max(1, 1 − L)`.

```swift run
let dungeon = [
    [0, -8, 20],
    [-1, -1, -1],
    [-1, -1, 0],
]
let rows = dungeon.count, cols = dungeon[0].count

// Try every right/down path. For each, find its total and the health it needs at the start:
// enough that the running total never drops to 0 or below.
func explore(_ r: Int, _ c: Int, _ moves: String, _ total: Int, _ lowest: Int) {
    let total = total + dungeon[r][c]
    let lowest = min(lowest, total)
    if r == rows - 1 && c == cols - 1 {
        print(moves, "total", total, "needs", max(1, 1 - lowest))
        return
    }
    if c + 1 < cols {
        explore(r, c + 1, moves + "R", total, lowest)
    }
    if r + 1 < rows {
        explore(r + 1, c, moves + "D", total, lowest)
    }
}

explore(0, 0, "", 0, 0)
```

```output
RRDD total 11 needs 9
RDRD total -10 needs 11
RDDR total -10 needs 11
DRRD total -3 needs 4
DRDR total -3 needs 4
DDRR total -3 needs 4
```

The path with the best total (RRDD, ending 11 up) needs 9, more than twice the answer, because it opens with the −8 trap. The answer is 4, from paths that lose 3 overall but never dip deeply.

So a forward table can't store "the best health so far" at each cell. Two things matter about the route into a cell: how much health it has left **and** how low it dipped on the way. A route with more health now but a deeper dip isn't better or worse than one with less health and a shallower dip; it depends on what lies ahead. One number per cell isn't enough when you go forwards.

## Backwards: what does the rest of the trip demand?

Turn it around. Ask, for each cell: **how much health must the knight have on entering this cell to survive from here to the princess?** That depends only on the cells ahead, and it's a single number.

Say the knight enters (r, c) with health h. After the cell's effect it has `h + dungeon[r][c]`, and it needs that to be at least what the next cell demands, choosing the less demanding of right and down. It also needs `h + dungeon[r][c]` to be at least 1 just to survive the cell itself. So:

> `need[r][c] = max(1, min(need[r + 1][c], need[r][c + 1]) − dungeon[r][c])`

| Step | Dungeon game |
| --- | --- |
| State | `need[r][c]` = the least health on entering (r, c) that still reaches the princess alive |
| Transition | `max(1, min(need below, need right) − dungeon[r][c])` |
| Base case | after the princess's cell the knight only needs to be alive: 1 |
| Order | from the bottom-right, backwards to the top-left |
| Answer | `need[0][0]` |

The `max(1, …)` is the heart of it. A huge potion makes `min(…) − dungeon[r][c]` negative, but the knight still has to walk into this cell alive, with at least 1. Health can't be borrowed from a potion you haven't reached yet.

```swift run
func minimumStartHealth(_ dungeon: [[Int]]) -> Int {
    let rows = dungeon.count, cols = dungeon[0].count
    let impossible = Int.max / 2
    // need[r][c]: the least health you can enter (r, c) with and still reach the goal alive.
    // An extra row and column of "impossible" saves bounds checks.
    var need = Array(repeating: Array(repeating: impossible, count: cols + 1), count: rows + 1)
    need[rows][cols - 1] = 1          // just past the goal you only need to be alive
    need[rows - 1][cols] = 1
    for r in stride(from: rows - 1, through: 0, by: -1) {
        for c in stride(from: cols - 1, through: 0, by: -1) {
            let onward = min(need[r + 1][c], need[r][c + 1])    // the easier way on
            need[r][c] = max(1, onward - dungeon[r][c])
        }
    }
    for row in need.dropLast() {
        print(row.dropLast().map(String.init).joined(separator: " "))
    }
    return need[0][0]
}

print("start with", minimumStartHealth([[0, -8, 20], [-1, -1, -1], [-1, -1, 0]]))
print("start with", minimumStartHealth([[-4, 3], [-2, -6]]))
```

```output
4 9 1
4 3 2
3 2 1
start with 4
8 4
9 7
start with 8
```

Read the first table from the bottom-right. The princess's cell is 0, so entering it with 1 is enough. The cell left of it is −1, so it needs 2. Look at the top-right cell: the knight needs 2 after it, but it's a +20 potion, so 2 − 20 = −18, clamped to 1. Then the −8 trap to its left needs 1 + 8 = 9. At the start, going down needs 4 and going right needs 9, so the answer is 4.

What to notice:

- The extra row and column hold a huge "impossible" value, except the two cells next to the goal, which hold 1. That's what makes the goal cell's formula, `max(1, 1 − dungeon[goal])`, come out of the same line as every other cell.
- `Int.max / 2`, not `Int.max`: the code subtracts `dungeon[r][c]`, and `Int.max - (-5)` would overflow. With the minimum taken first, the impossible value is only used when both directions are impossible, which never happens inside the grid, but the margin costs nothing.
- It rolls into one row from the bottom up, exactly like the minimum path sum, for O(cols) memory.

## Why backwards works and forwards doesn't

Going backwards, the state is "what the future demands", and the future from a cell is the same no matter how you got there. Going forwards, the state would have to be "what the past did to you", and the past has two dimensions (current health and lowest dip). When a constraint looks **forward** along the path, fill from the end.

There's another way out, which shows exactly what was missing. **Fix the starting health**, and forwards works again: with a known start, more health is always at least as good, so one number per cell (the most health you can have there while alive) is enough. And if the knight survives starting with h, they survive starting with anything more. That's a monotonic yes/no question, so binary search on h, as in [The monotonic predicate idea](/dsa/learn/bsa-idea):

```swift run
// With the starting health fixed, forwards works: more health is always at least as good
func survives(_ dungeon: [[Int]], startingWith health: Int) -> Bool {
    let cols = dungeon[0].count
    // best[c]: the most health you can have after cell (r, c), or 0 if you can't get there alive
    var best = Array(repeating: 0, count: cols)
    for r in dungeon.indices {
        for c in 0..<cols {
            let arriving = r == 0 && c == 0 ? health : max(r > 0 ? best[c] : 0, c > 0 ? best[c - 1] : 0)
            let after = arriving + dungeon[r][c]
            best[c] = arriving > 0 && after > 0 ? after : 0
        }
    }
    return best[cols - 1] > 0
}

func minimumStartHealth(_ dungeon: [[Int]]) -> Int {
    var low = 1
    var high = 1 + dungeon.joined().filter { $0 < 0 }.reduce(0) { $0 - $1 }   // enough for every trap
    while low < high {
        let mid = low + (high - low) / 2
        if survives(dungeon, startingWith: mid) {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

let dungeon = [[0, -8, 20], [-1, -1, -1], [-1, -1, 0]]
print((1...5).map { survives(dungeon, startingWith: $0) })
print(minimumStartHealth(dungeon))
print(minimumStartHealth([[-4, 3], [-2, -6]]))
```

```output
[false, false, false, true, true]
4
8
```

It agrees, at a cost of O(rows × cols × log S), where S is the total damage. The backwards DP is faster and shorter, but the binary search version is a useful second method for checking, and the idea ("fix the hard parameter, then the rest is easy") comes up again and again.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting the clamp.** Without `max(1, …)`, a potion lets `need` go to 0 or below, as if the knight could enter a cell dead and be revived.
- **Forgetting the princess's cell.** It counts. A trap on the goal must still be survived, which is why the base is 1 *after* the goal, not on it.
- **Starting health 0.** The answer is always at least 1: the knight has to be alive to walk in.
- **Subtracting before taking the minimum.** `min(below - value, right - value)` subtracts from the sentinel too, and `Int.max - (-3)` crashes. Take the minimum first, and keep a margin with `Int.max / 2`.
</Callout>
