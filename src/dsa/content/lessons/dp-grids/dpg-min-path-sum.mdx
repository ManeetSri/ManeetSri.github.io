## Why it matters

Counting routes was a warm-up. Most grid questions want the **best** route: the cheapest delivery across a city of toll roads, the least tiring hike over a height map, the lowest-energy path for a game character. Swap "add the two ways in" for "take the cheaper way in" and the unique-paths table becomes a minimum-cost table. Then a triangle of numbers shows a second lesson: choosing **which end to fill from** can delete all your edge cases.

## Minimum path sum

Each cell of a grid holds a cost (zero or more). Moving only right or down from the top-left to the bottom-right, find the smallest possible total of the cells you pass through, both ends included.

The last move into (r, c) came from above or from the left, as before. Whichever it was, the route up to that neighbour should itself be as cheap as possible: a cheaper way to the neighbour would make a cheaper way to (r, c). That's **optimal substructure**. So:

| Step | Minimum path sum |
| --- | --- |
| State | `cost[r][c]` = the cheapest right/down path from (0, 0) to (r, c), both ends included |
| Transition | `cost[r][c] = grid[r][c] + min(cost[r − 1][c], cost[r][c − 1])` |
| Base case | `cost[0][0] = grid[0][0]`; the top row and left column have only one way in |
| Order | row by row, left to right |
| Answer | `cost[rows − 1][cols − 1]` |

```swift run
let grid = [
    [2, 3, 1, 4],
    [1, 7, 1, 2],
    [5, 2, 3, 1],
]
let rows = grid.count, cols = grid[0].count

// cost[r][c]: the cheapest total of any right/down path from the start to (r, c), both ends included
var cost = grid
for c in 1..<cols {
    cost[0][c] += cost[0][c - 1]                      // top row: only from the left
}
for r in 1..<rows {
    cost[r][0] += cost[r - 1][0]                      // left column: only from above
    for c in 1..<cols {
        cost[r][c] += min(cost[r - 1][c], cost[r][c - 1])
    }
}
for row in cost {
    print(row)
}

// Walk back from the goal, always to the neighbour the cell's cost came from
var (r, c) = (rows - 1, cols - 1)
var path = [grid[r][c]]
while r > 0 || c > 0 {
    if c == 0 || (r > 0 && cost[r - 1][c] <= cost[r][c - 1]) {
        r -= 1
    } else {
        c -= 1
    }
    path.append(grid[r][c])
}
print("cheapest:", cost[rows - 1][cols - 1], "via", Array(path.reversed()))
```

```output
[2, 5, 6, 10]
[3, 10, 7, 9]
[8, 10, 10, 10]
cheapest: 10 via [2, 3, 1, 1, 2, 1]
```

Step through it. Each cell takes its own cost plus the cheaper of its two blue neighbours, and the final frame traces the path back:

```visual dpTable

```

What to notice:

- The cheap-looking start down the left column (2, 1) leads into 7 or 5. The table weighs that automatically: (1, 1) costs 10 either way.
- Walking back works because each cell's value came from one of its two neighbours. Wherever `cost[r][c] − grid[r][c]` equals a neighbour's cost, that neighbour is on a cheapest path. This is the idea of [Reconstructing the answer, not just its value](/dsa/learn/dp-reconstruct).
- Ties (here at the goal, where both neighbours cost 9) mean more than one cheapest path. Any of them is correct.

### Rolling it into one row

The same trick as before: in a single array, `cost[c]` still holds the value **above** until you overwrite it, and `cost[c − 1]` already holds the value **to the left**:

```swift run
func cheapestPath(_ grid: [[Int]]) -> Int {
    let cols = grid[0].count
    var cost = Array(repeating: 0, count: cols)
    for r in grid.indices {
        for c in 0..<cols {
            if r == 0 && c == 0 {
                cost[c] = grid[0][0]
            } else if r == 0 {
                cost[c] = grid[r][c] + cost[c - 1]                 // top row: from the left only
            } else if c == 0 {
                cost[c] = grid[r][c] + cost[c]                     // left column: from above only
            } else {
                cost[c] = grid[r][c] + min(cost[c], cost[c - 1])   // cost[c] is still "above"
            }
        }
    }
    return cost[cols - 1]
}

print(cheapestPath([[2, 3, 1, 4], [1, 7, 1, 2], [5, 2, 3, 1]]))
print(cheapestPath([[5]]))
print(cheapestPath([[1, 2, 3]]))
print(cheapestPath([[1], [2], [3]]))
```

```output
10
5
6
6
```

O(rows × cols) time and O(cols) memory. The one-row version gives up the path, though: to walk back you need the whole table, or a separate record of each choice.

## Right and down only: DP. Any direction: Dijkstra

In [Dijkstra's algorithm](/dsa/learn/sp-dijkstra) you found cheapest paths through weighted graphs, and a grid is a graph. Why is DP enough here?

With only right and down moves, every path into (r, c) comes from cells that are filled **earlier** in row order. The grid is a DAG, and filling row by row is relaxing the edges in topological order, the method from [Longest and shortest paths in a DAG](/dsa/learn/topo-dag-paths). Each cell is final the moment it's computed.

Let the robot move up and left as well, and that breaks. A cheap route might go down, across, and back **up** to reach a cell. Now (r, c) can depend on cells below it, which depend on (r, c): there's no order that has every neighbour ready. That's a job for Dijkstra on the grid (non-negative costs), as in the minimum-effort problem in [Network delay, cheapest flights and minimum effort](/dsa/learn/sp-problems).

| Moves allowed | Graph | Algorithm |
| --- | --- | --- |
| right and down | DAG | DP in row order, O(rows × cols) |
| all four, unweighted | cycles | BFS |
| all four, non-negative costs | cycles | Dijkstra, O(rows × cols × log) |

## The triangle

A triangle of numbers has one number in its first row, two in its second, and so on. From position i in one row you can step to position i or i + 1 in the row below. Find the smallest total from the apex to any number in the bottom row.

```text
       5
      4 7
     9 8 1
    2 6 3 4
```

Greedy ("step to the smaller number below") fails at once: from 5 it takes 4, which leads only to the 9 and the 8, and it finishes on 20. The cheapest path goes 5 → 7 → 1 → 3 instead, for 16.

### Top-down: edge cases at both ends

The natural first attempt fills from the apex. `cost[r][i]` is the cheapest way from the apex down to (r, i). It has two possible parents, (r − 1, i − 1) and (r − 1, i), except that the left end of a row has no parent above-left and the right end has no parent straight above. And the answer is the minimum over the whole bottom row.

### Bottom-up: no edge cases at all

Turn the question around: let `best[r][i]` be the cheapest way from (r, i) **down to the base**. Every position has exactly two children, (r + 1, i) and (r + 1, i + 1), with no exceptions. The base row is its own answer, and the apex holds the final answer, with no minimum to take.

```swift run
let triangle = [
    [5],
    [4, 7],
    [9, 8, 1],
    [2, 6, 3, 4],
]

// Greedy: always step to the smaller of the two numbers below
var position = 0
var greedyTotal = triangle[0][0]
for r in 1..<triangle.count {
    if triangle[r][position + 1] < triangle[r][position] {
        position += 1
    }
    greedyTotal += triangle[r][position]
}
print("greedy:", greedyTotal)

// Top-down: cost of the cheapest way from the apex to each position
var cost = [triangle[0][0]]
for r in 1..<triangle.count {
    var next = Array(repeating: 0, count: r + 1)
    for i in 0...r {
        let aboveLeft = i > 0 ? cost[i - 1] : Int.max     // the left end has no parent above-left
        let above = i < r ? cost[i] : Int.max             // the right end has no parent straight above
        next[i] = triangle[r][i] + min(aboveLeft, above)
    }
    cost = next
}
print("top-down:", cost.min()!, "from the last row", cost)

// Bottom-up: the base row is its own answer; climb towards the apex
var best = triangle[triangle.count - 1]
for r in stride(from: triangle.count - 2, through: 0, by: -1) {
    for i in 0...r {
        best[i] = triangle[r][i] + min(best[i], best[i + 1])
    }
}
print("bottom-up:", best[0])
```

```output
greedy: 20
top-down: 16 from the last row [20, 23, 16, 17]
bottom-up: 16
```

The bottom-up loop is two lines, and it rolls into one array for free: `best[i]` reads `best[i]` and `best[i + 1]`, and since i goes left to right, `best[i + 1]` hasn't been overwritten yet. Its length starts as the base row's and simply stops being used at the right as the rows get shorter. O(n²) time for n rows (that's every number once), O(n) memory.

<Callout kind="tip" title="Pick the end with one answer">
When a DP has many possible endings (any cell in the last row) but one start, filling **from the endings back to the start** often removes both the boundary checks and the final minimum. You'll use this again in the next lessons.
</Callout>

<Callout kind="gotcha" title="Swift gotchas">
- **`Int.max + cost` crashes.** Using `Int.max` as "no parent" is safe only because `min` picks the real parent first, and every cell after the first has at least one. Never add to the sentinel itself.
- **`var cost = grid` copies.** Arrays are values in Swift, so updating `cost` never changes `grid`. Still, the one-row version is clearer than overwriting the input.
- **Triangle rows have different lengths.** `triangle[r].count` is `r + 1`; indexing `triangle[r][r + 1]` crashes.
</Callout>
