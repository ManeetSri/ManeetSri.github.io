## Why it matters

When you know both where you start and where you want to end up, you can search from **both ends at once** and stop when the two searches meet in the middle. It sounds like it should halve the work. It does far better than that: in a graph where every state has many neighbours, two half-depth searches can explore a tiny fraction of what one full-depth search does. Social networks use the idea to find how two people are connected, route planners use a version of it on road maps, and it turns word ladders and puzzle searches that would take minutes into ones that take milliseconds. This is an advanced lesson: it builds directly on [BFS and unweighted shortest paths](/dsa/learn/gt-bfs) and [State-space BFS: word ladder and open the lock](/dsa/learn/gt-state-space).

## Why two small searches beat one big one

Suppose each state has about b neighbours (the **branching factor**) and the target is d moves away. One BFS explores every state within d moves: roughly b^d of them, since each level is about b times bigger than the last. Two searches that each go d/2 moves deep explore about b^(d/2) each, so 2 × b^(d/2) in total.

| Branching b | Depth d | One BFS, about b^d | From both ends, about 2 × b^(d/2) |
| --- | --- | --- | --- |
| 3 | 10 | 59,049 | 486 |
| 10 | 6 | 1,000,000 | 2,000 |

Halving the **exponent** is what makes the difference: b^(d/2) is the square root of b^d. On a grid, where the number of states within distance d grows only like d², the saving is a modest factor of about 2. On word ladders, puzzles and social networks, where each level is several times bigger than the last, it's enormous.

<Callout kind="analogy">
Two friends digging a tunnel through a hill start from opposite sides and meet in the middle. Each digs half as far. In a graph, the "hill" grows wider with every step, so digging half as far from each side means moving vastly less earth.
</Callout>

## The algorithm

Keep two frontiers: the states at the edge of the search from the start, and the states at the edge of the search from the target. Mark every state with which side has seen it. Then repeat:

1. Pick the **smaller** frontier.
2. Expand it by one whole level: for each of its states, look at each neighbour.
   - If the **other** side has seen the neighbour, the searches have met. The answer is the number of levels expanded so far, on both sides together, plus 1 for this last edge.
   - If nobody has seen it, mark it as this side's and add it to the next frontier.
3. If either frontier becomes empty, the target can't be reached.

Here's a lock with six wheels, a million combinations each with 12 neighbours, searched both ways. Both functions count how many states they marked as seen:

```swift run
// A lock with 6 wheels: 1,000,000 combinations, each with 12 neighbours
let wheels = 6
let stateCount = 1_000_000

func neighbours(of state: Int) -> [Int] {
    var result: [Int] = []
    var place = 1
    for _ in 0..<wheels {
        let digit = (state / place) % 10
        result.append(state + ((digit + 1) % 10 - digit) * place)
        result.append(state + ((digit + 9) % 10 - digit) * place)
        place *= 10
    }
    return result
}

/// Plain BFS: returns the number of moves and how many states it marked as seen
func bfs(from start: Int, to target: Int) -> (moves: Int, seen: Int) {
    var distance = Array(repeating: -1, count: stateCount)
    distance[start] = 0
    var queue = [start]
    var head = 0
    while head < queue.count {
        let state = queue[head]
        head += 1
        if state == target { return (distance[state], queue.count) }
        for next in neighbours(of: state) where distance[next] == -1 {
            distance[next] = distance[state] + 1
            queue.append(next)
        }
    }
    return (-1, queue.count)
}

/// Bidirectional BFS: grow whichever frontier is smaller by one whole level, until they touch
func bidirectional(from start: Int, to target: Int) -> (moves: Int, seen: Int) {
    if start == target { return (0, 1) }
    var side = Array(repeating: 0, count: stateCount)   // 0: unseen, 1: seen from start, 2: from target
    side[start] = 1
    side[target] = 2
    var frontiers = [[start], [target]]                // frontiers[0] grows from start, [1] from target
    var seen = 2
    var levels = 0                                      // levels expanded so far, on both sides
    while !frontiers[0].isEmpty && !frontiers[1].isEmpty {
        let grow = frontiers[0].count <= frontiers[1].count ? 0 : 1
        let mine = grow + 1
        var next: [Int] = []
        for state in frontiers[grow] {
            for neighbour in neighbours(of: state) {
                if side[neighbour] == 3 - mine { return (levels + 1, seen) }   // the searches meet
                if side[neighbour] == 0 {
                    side[neighbour] = mine
                    seen += 1
                    next.append(neighbour)
                }
            }
        }
        frontiers[grow] = next
        levels += 1
    }
    return (-1, seen)
}

for target in [33, 1_234, 123_321] {
    let plain = bfs(from: 0, to: target)
    let both = bidirectional(from: 0, to: target)
    let code = String(repeating: "0", count: wheels - String(target).count) + String(target)
    print("000000 to \(code): \(plain.moves) moves; BFS saw \(plain.seen) states, bidirectional \(both.seen)")
}
```

```output
000000 to 000033: 6 moves; BFS saw 9131 states, bidirectional 523
000000 to 001234: 10 moves; BFS saw 114389 states, bidirectional 5618
000000 to 123321: 12 moves; BFS saw 286646 states, bidirectional 15291
```

Both find the same number of moves, but the bidirectional search marks roughly 17 to 20 times fewer states, and the gap grows with the distance. (For a target 30 moves away, the farthest any combination can be, both end up seeing all million states: when the answer is as long as the space is wide, there's nothing to save.)

What to notice:

- **`side` replaces the visited set**, and records whose search reached each state: 1 for the start's, 2 for the target's. `3 - mine` is "the other side".
- **`levels` counts levels from both sides together.** When the searches meet, the path is every level the start side expanded, then the meeting edge, then every level the target side expanded: `levels + 1` in total.
- **Each side grows a whole level at a time.** That's what keeps the meeting point honest, as the next section explains.

## Why the first meeting gives the shortest path

Say the start side has expanded a levels and the target side b levels, and they haven't met yet. Then no path from start to target has a + b edges or fewer. If one did, the state a steps along it would be within a of the start (seen by the start side) and within b of the target (seen by the target side), but no state has been seen by both. So the shortest path has **at least a + b + 1** edges.

Now the start side expands one more level. If it finds a neighbour that the target side has seen, it has a path with a edges, one more edge, and at most b edges back to the target: at most a + b + 1. That can't be shorter than the shortest path, so it **is** a shortest path, and it's safe to stop at the first meeting. The same argument shows that any state the other side has seen and that you reach from your frontier must be on the other side's frontier, which is why the code only needs `side`, not a separate record of each side's frontier.

Expanding whole levels matters. If you interleaved single states from the two sides, a meeting could be found through a state that was added late on one side, giving a path that's one edge too long.

## Choosing which side to grow

Growing the **smaller** frontier keeps the work balanced. Usually the two frontiers grow at similar rates, but not always: if the target sits in a sparse corner of the graph, its side stays small and cheap, and it does more of the levels. A bad choice can't make the answer wrong, only slower.

## When it applies, and when it doesn't

- **You need a single, known target.** For "the nearest of many targets", run a multi-source BFS from all the targets instead, as in [Multi-source BFS: rotting oranges and 01 matrix](/dsa/learn/gt-multi-source).
- **You must be able to search backwards.** In an undirected graph, or a state space where every move can be undone (lock wheels, one-letter word changes), the backward search uses the same neighbours. In a directed graph, the target's side must follow edges **in reverse**, which needs a list of each vertex's incoming edges.
- **Edges should be unweighted.** Bidirectional versions of Dijkstra's algorithm exist, but knowing when it's safe to stop is subtler than "the first meeting".
- **Getting the path, not only its length,** needs a parent record on each side. At the meeting edge, walk back through the start side's parents to the start (and reverse), then forwards through the target side's parents to the target.

<Callout kind="gotcha" title="Bidirectional slips">
- **Checking only the start side for the target.** The searches meet in the middle, usually long before either reaches the far end. Check every new neighbour against the other side.
- **Counting the meeting edge twice, or not at all.** With levels counted from both sides, the answer is `levels + 1`.
- **Stopping mid-level with a `Set` and printing what was seen.** Iterating a `Set` gives a different order each run, so "how many states were seen" changes from run to run. The answer itself doesn't. Use arrays for frontiers when you need repeatable output.
- **Forgetting `start == target`.** The loop assumes the two sides start apart. Return 0 first.
</Callout>
