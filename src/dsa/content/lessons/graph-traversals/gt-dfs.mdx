## Why it matters

**Depth-first search** (DFS) explores a graph the way you'd explore a maze with a ball of string: follow one path as far as it goes, and only when you hit a dead end, back up to the last junction with an unexplored turning. It doesn't find shortest paths, but it answers a huge range of other questions: is everything reachable, how many separate pieces are there, is there a cycle, what order must these tasks run in. A file browser adding up folder sizes walks the folder tree depth-first, and so does a build tool checking which targets a changed file affects. This lesson writes DFS recursively, then without recursion, and shows why the two versions don't visit vertices in the same order unless you're careful.

## Recursive DFS

The recursive version is the shortest graph algorithm you'll write. To visit a vertex: mark it, then visit each neighbour that isn't marked yet.

```swift run
let edges = [[0, 1], [0, 2], [1, 3], [2, 3], [2, 4], [3, 5], [4, 5], [5, 6], [6, 7]]
var neighbours = Array(repeating: [Int](), count: 8)
for edge in edges {
    neighbours[edge[0]].append(edge[1])
    neighbours[edge[1]].append(edge[0])
}
for vertex in neighbours.indices {
    neighbours[vertex].sort()
}

func dfs(from start: Int) -> [Int] {
    var visited = Array(repeating: false, count: neighbours.count)
    var order: [Int] = []
    func visit(_ vertex: Int) {
        visited[vertex] = true
        order.append(vertex)
        for next in neighbours[vertex] where !visited[next] {   // checked as the loop reaches it
            visit(next)
        }
    }
    visit(start)
    return order
}

print(dfs(from: 0))
print(dfs(from: 7))
```

```output
[0, 1, 3, 2, 4, 5, 6, 7]
[7, 6, 5, 3, 1, 0, 2, 4]
```

This is the graph from [BFS and unweighted shortest paths](/dsa/learn/gt-bfs), without vertex 8. From 0, DFS goes to 1, then 3, then **2**, because 2 is 3's first unvisited neighbour, even though 2 is right next to 0. BFS visited `0, 1, 2, 3, …` in rings; DFS dives. Watch the call stack grow and shrink:

```visual graph

  edges: [["0", "1"], ["0", "2"], ["1", "3"], ["2", "3"], ["2", "4"], ["3", "5"], ["4", "5"], ["5", "6"], ["6", "7"]]
```

What to notice:

- **The `where` clause is checked as the loop reaches each neighbour**, not all at once at the start. When the call on 0 finally gets round to its second neighbour, 2, the dive through 1 has already visited it, so it's skipped.
- **Every vertex is visited once** and every adjacency list is scanned once: **O(V + E)** time, like BFS.
- **The extra space is the call stack**, as deep as the longest path DFS follows: up to V calls.
- `visit` is a nested function, as in [Nested helper functions](/dsa/learn/swift-nested-functions), that changes `visited` and `order` from the enclosing function. It captures them, as in [Capturing values](/dsa/learn/swift-capturing), so they don't need passing in.

Each vertex has two moments: when DFS **enters** it (marks it and starts on its neighbours) and when it **finishes** it (every neighbour is done and the call returns). The visiting order above is the order of entering. The finishing order matters too: you'll use it for cycle detection at the end of this module, and for [Topological sort with DFS](/dsa/learn/topo-dfs) in M43.

## Without recursion: an explicit stack

As [Turning recursion into an explicit stack](/dsa/learn/rec-explicit-stack) showed, any recursion can become a loop over a stack you manage yourself. For DFS, push the start; then repeatedly pop a vertex, skip it if it's already visited, otherwise visit it and push its unvisited neighbours. A vertex can be pushed more than once (by different neighbours) before it's popped, which is why the skip is needed.

There's a catch. The stack is last in, first out, so if you push the neighbours in their natural order, the **last** one comes off first. The recursion tries the **first** neighbour first. Push them in reverse, and the orders match:

```swift run
let edges = [[0, 1], [0, 2], [1, 3], [2, 3], [2, 4], [3, 5], [4, 5], [5, 6], [6, 7]]
var neighbours = Array(repeating: [Int](), count: 8)
for edge in edges {
    neighbours[edge[0]].append(edge[1])
    neighbours[edge[1]].append(edge[0])
}
for vertex in neighbours.indices {
    neighbours[vertex].sort()
}

func recursiveOrder(from start: Int) -> [Int] {
    var visited = Array(repeating: false, count: neighbours.count)
    var order: [Int] = []
    func visit(_ vertex: Int) {
        visited[vertex] = true
        order.append(vertex)
        for next in neighbours[vertex] where !visited[next] {
            visit(next)
        }
    }
    visit(start)
    return order
}

func stackOrder(from start: Int, pushReversed: Bool) -> [Int] {
    var visited = Array(repeating: false, count: neighbours.count)
    var order: [Int] = []
    var stack = [start]
    while let vertex = stack.popLast() {
        if visited[vertex] { continue }                 // pushed twice: already handled
        visited[vertex] = true
        order.append(vertex)
        let next = pushReversed ? Array(neighbours[vertex].reversed()) : neighbours[vertex]
        for neighbour in next where !visited[neighbour] {
            stack.append(neighbour)
        }
    }
    return order
}

print("recursive:          ", recursiveOrder(from: 0))
print("stack, in order:    ", stackOrder(from: 0, pushReversed: false))
print("stack, reversed:    ", stackOrder(from: 0, pushReversed: true))
```

```output
recursive:           [0, 1, 3, 2, 4, 5, 6, 7]
stack, in order:     [0, 2, 4, 5, 6, 7, 3, 1]
stack, reversed:     [0, 1, 3, 2, 4, 5, 6, 7]
```

Pushed in order, the stack version still dives (0, 2, 4, 5, 6, 7 is a single path) and still visits everything, but it starts with 0's **last** neighbour. Both are valid depth-first searches; they just make different choices at each junction. It matters when a test or a problem expects one particular order, and when an algorithm relies on the exact order.

Notice also where the marking happens. Marking on **pop** is what makes this a true DFS: a vertex is visited from the most recently pushed path. It costs some duplicates on the stack, up to one per edge. If all you need is "which vertices are reachable" (flood fill, counting islands, the problems in this module), you can mark on **push** instead, exactly like BFS:

```swift
var stack = [start]
visited[start] = true
while let vertex = stack.popLast() {
    for next in neighbours[vertex] where !visited[next] {
        visited[next] = true                 // mark on push: each vertex is pushed once
        stack.append(next)
    }
}
```

Each vertex is then pushed exactly once, so the stack never holds more than V entries. The visiting order is no longer a strict depth-first order, but every reachable vertex is still visited exactly once. This is the version this module's reference solutions use for reachability.

| Version | Visiting order | Stack size | Use it for |
| --- | --- | --- | --- |
| Recursive | true DFS | up to V calls | small graphs, clear code |
| Stack, mark on pop, push reversed | same as recursive | up to E entries | when the order matters |
| Stack, mark on push | neither BFS nor DFS | up to V entries | reachability on big inputs |

## How deep is too deep?

The recursive version uses one call-stack frame per vertex on the current path. As [Stack depth limits in Swift](/dsa/learn/rec-stack-limits) measured, that's fine for around a hundred thousand calls on the main thread, but only about **8,000 inside a Swift Testing test**, whose threads get a 512 KB stack. Graphs that are long and thin break that easily:

- a chain of 100,000 vertices, such as rooms each holding the next room's key;
- a 1000 × 1000 grid with a snake-shaped region, where the recursion follows the snake for half a million cells;
- even a big open grid, where DFS tends to wander along long winding paths rather than spreading out.

When it happens, the test run stops in the middle of a test, with no pass or fail line for it, and SwiftPM reports that the test process died:

```text title="What you'll see"
Test chain() started.
error: Process '…/swiftpm-testing-helper …' exited with unexpected signal code 10
```

The explicit stack lives on the heap, which can hold millions of entries. So the rule for this module: **write DFS iteratively, or use BFS, whenever the input can be large.** The problem statements say so when it applies, and their tests are built to catch it.

<Callout kind="gotcha" title="Swift gotchas with DFS">
- **Marking too late in the recursive version.** Mark a vertex at the start of `visit`, before looping over its neighbours. Marking at the end lets a cycle lead back into a vertex that's still being visited, and the recursion never ends.
- **`while let vertex = stack.popLast()`** is the idiomatic loop: `popLast()` returns `nil` when the stack is empty. Don't use `removeFirst()`, which turns the stack into a slow queue and the search into a BFS.
- **Capturing `inout` parameters.** A nested function can capture the enclosing function's local `var`s, but not its `inout` parameters if the nested function might escape. Keep `visited` as a local variable of the outer function, as above.
</Callout>

## DFS or BFS?

| Question | Use | Why |
| --- | --- | --- |
| Fewest edges from A to B | BFS | it reaches vertices in order of distance |
| Is B reachable from A? | either | both visit everything reachable |
| How many separate pieces? | either | run one search per piece |
| Is there a cycle? Which order do tasks go in? | DFS | the entering and finishing moments carry the answer |
| Explore every path, or build up choices | DFS (backtracking) | you'll meet backtracking in Part VII |
