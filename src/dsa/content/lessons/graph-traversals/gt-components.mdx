## Why it matters

How many separate friend groups are in this contact list? Which devices can talk to each other on this network? Which pixels does the magic wand select when you tap a patch of sky? Each question asks for a **connected component**: a group of vertices that can all reach each other, with no edges to anything outside the group. One BFS or DFS finds the component around a vertex; a loop that starts a new search from every vertex not yet visited finds them all, in O(V + E) total. On a grid, that same search is called **flood fill**, and it's the paint bucket in every drawing app.

## Counting the pieces

In an undirected graph, the vertices split into components: every vertex belongs to exactly one, and two vertices are in the same component exactly when there's a path between them. A search from any vertex visits precisely its component, no more, no less.

So to find them all:

1. Keep a label for every vertex, starting at `-1` (not visited).
2. Loop over the vertices. Whenever you meet one still labelled `-1`, it belongs to a component you haven't seen: give it the next component number and search from it, labelling everything you reach with that number.
3. The number of searches you started is the number of components.

```swift run
let vertexCount = 10
let edges = [[0, 1], [1, 2], [3, 4], [5, 6], [6, 7], [7, 5], [2, 8]]
var neighbours = Array(repeating: [Int](), count: vertexCount)
for edge in edges {
    neighbours[edge[0]].append(edge[1])
    neighbours[edge[1]].append(edge[0])
}

var component = Array(repeating: -1, count: vertexCount)    // -1: not visited yet
var count = 0
for start in 0..<vertexCount where component[start] == -1 {
    component[start] = count                           // a new piece starts here
    var stack = [start]
    while let vertex = stack.popLast() {
        for next in neighbours[vertex] where component[next] == -1 {
            component[next] = count                     // mark on push
            stack.append(next)
        }
    }
    count += 1
}

print("pieces:", count)
print("labels:", component)
for id in 0..<count {
    print("piece \(id):", component.indices.filter { component[$0] == id })
}
```

```output
pieces: 4
labels: [0, 0, 0, 1, 1, 2, 2, 2, 0, 3]
piece 0: [0, 1, 2, 8]
piece 1: [3, 4]
piece 2: [5, 6, 7]
piece 3: [9]
```

What to notice:

- **The labels are the visited mark.** `component[v] == -1` means "not visited", and anything else says which piece v is in. Afterwards, "are a and b connected?" is one comparison, `component[a] == component[b]`, answered in O(1) for as many pairs as you like.
- **Vertex 9 has no edges, and it's still a component**: a piece of one. Forgetting isolated vertices is the most common counting bug, and it's why the outer loop runs over every vertex rather than over the edges.
- **The search is the mark-on-push DFS** from [DFS, recursive and iterative](/dsa/learn/gt-dfs). BFS works identically. Only reachability matters here, not the order.
- **The `where` clause is checked on every pass of the outer loop**, so vertices labelled by an earlier search are skipped.

### Why it's O(V + E), not more

The outer loop looks as if it could start V searches, each costing O(V + E). But each search only visits vertices that are still unlabelled, and labels them. So across **all** the searches put together, every vertex is pushed once and every adjacency list is scanned once. Add the outer loop's V checks and the total is O(V + E), the same as a single search over the whole graph.

<Callout kind="note" title="Directed graphs are different">
In a directed graph, "connected" splits in two. **Weakly** connected ignores the arrows: treat every edge as two-way and count components exactly as above. **Strongly** connected means every vertex can reach every other following the arrows, which needs a cleverer algorithm. You'll meet it in [Strongly connected components: Kosaraju and Tarjan](/dsa/learn/ag-scc), in M47.
</Callout>

## Flood fill: components on a grid

A grid is a graph where each cell is a vertex and neighbouring cells with the same value are joined, as in [Implicit graphs: grids and state spaces](/dsa/learn/graph-implicit). The component around one cell is its **region**, and repainting it is flood fill. There's no adjacency list: the neighbours come from a direction array, as in [Direction arrays for grid moves](/dsa/learn/matrix-directions), and "same value" decides which neighbours count.

Here the picture is an outline of a diamond, filled from its centre. The same fill runs twice: once moving only up, down, left and right (4-way), and once allowing diagonal moves too (8-way):

```swift run
let fourWay = [(-1, 0), (1, 0), (0, -1), (0, 1)]
let eightWay = fourWay + [(-1, -1), (-1, 1), (1, -1), (1, 1)]

func fill(_ picture: [[Character]], from start: (Int, Int), with paint: Character, moves: [(Int, Int)]) -> [[Character]] {
    var picture = picture
    let original = picture[start.0][start.1]
    if original == paint { return picture }            // nothing to do, and no endless loop
    picture[start.0][start.1] = paint
    var stack = [start]
    while let cell = stack.popLast() {
        for (dr, dc) in moves {
            let r = cell.0 + dr
            let c = cell.1 + dc
            guard r >= 0, r < picture.count, c >= 0, c < picture[r].count else { continue }
            guard picture[r][c] == original else { continue }
            picture[r][c] = paint                       // the new colour is the visited mark
            stack.append((r, c))
        }
    }
    return picture
}

let diamond = [
    "....##....",
    "...#..#...",
    "..#....#..",
    "...#..#...",
    "....##....",
].map { Array($0) }

for (name, moves) in [("4-way", fourWay), ("8-way", eightWay)] {
    print(name)
    for row in fill(diamond, from: (2, 4), with: "o", moves: moves) {
        print(String(row))
    }
}
```

```output
4-way
....##....
...#oo#...
..#oooo#..
...#oo#...
....##....
8-way
oooo##oooo
ooo#oo#ooo
oo#oooo#oo
ooo#oo#ooo
oooo##oooo
```

The outline's walls only touch at their corners. To a 4-way fill, corners are solid, so the paint stays inside. An 8-way fill slips diagonally through every corner, out of the diamond, and paints the whole background. **Which moves count as "connected" changes the answer**, so every grid problem has to say which it means. Most say 4-way.

What to notice:

- **The new colour is the visited mark.** Only cells with the original colour are pushed, and each is repainted as it's pushed, so none is pushed twice. No separate visited grid is needed.
- **That trick breaks if the new colour equals the original.** Repainted cells would still match `original`, so they'd be pushed again and again, forever. The early `return` handles it.
- **`var picture = picture`** makes a local copy to change: Swift parameters are constants. Arrays are values, so the caller's picture is untouched, and the copy is only made when the first cell is written, thanks to copy-on-write.

<Callout kind="analogy">
Flood fill is ink dropped on blotting paper. It spreads into every touching patch of the same paper and stops at the lines. Whether it can seep through a point where two lines only touch at a corner is exactly the 4-way versus 8-way question.
</Callout>

## A different tool for the same job

Union-find, in [Disjoint sets and the parent array](/dsa/learn/uf-idea), also groups vertices into components. It shines when edges arrive one at a time and you need to answer "are these connected yet?" after each one, without searching again. For a graph you're given all at once, a search with labels, as here, is simpler and just as fast.

<Callout kind="gotcha" title="Component-counting slips">
- **Looping over edges instead of vertices** misses vertices with no edges, which are components of one.
- **Painting with the same colour** loops forever when the colour is also the visited mark. Check for it first.
- **Recursive flood fill on a big image** can run out of stack: a thin winding region makes the recursion as deep as the region is long. Use an explicit stack, as above.
- **Reading a cell before checking the bounds.** Put the bounds check first in the `guard`, so `picture[r][c]` is never read outside the grid.
</Callout>

## Practice

**Paint bucket fill** is the flood fill above on an image of numbers, including the same-colour trap and a 500,500-pixel snake that recursion can't survive. **Unlock every room** is the one-component question for a directed graph: is everything in room 0's component?
