## Why it matters

A delivery van leaves the depot, stops at every address once, and comes back. Which order is shortest? That's the **travelling salesperson problem** (TSP), and it turns up in route planning, in the order a machine drills holes in a circuit board, and in scheduling jobs with set-up costs between them. It asks for a walk through **every vertex exactly once**, which sounds like a small change from the previous lesson's every edge once. It isn't: no one knows a fast algorithm, and there probably isn't one. This lesson shows the brute force, then the bitmask DP that makes up to about 16 cities practical, and where the line between feasible and hopeless falls.

## Every vertex exactly once

- A **Hamiltonian path** visits every vertex of a graph exactly once.
- A **Hamiltonian cycle** is a Hamiltonian path whose last vertex has an edge back to the first.
- The **travelling salesperson problem** gives every pair of vertices a distance and asks for the shortest Hamiltonian cycle.

Compare that with Euler paths:

| | Euler path | Hamiltonian path |
| --- | --- | --- |
| Uses each | edge exactly once | vertex exactly once |
| Quick test for existence | yes: count odd degrees | none known |
| Best known algorithm | O(E), Hierholzer | exponential |

## Why it's hard

For Euler paths, a local fact (each vertex's degree) settles a global question. For Hamiltonian paths, no local fact does. Whether a vertex can be fitted in depends on the order of everything else.

Hamiltonian cycle is **NP-complete**, and TSP is **NP-hard**. Informally, that puts them in a family of thousands of problems (scheduling, packing, satisfiability and many more) with two properties: no one has found a polynomial-time algorithm for any of them, and a polynomial-time algorithm for any one would give one for all the others. Most computer scientists believe none exists. In practice, "NP-hard" means: **expect exponential time for exact answers**, and choose between exact algorithms on small inputs and good-enough answers on large ones.

## Brute force: every order

Fix the start city (every tour is a loop, so where it starts doesn't matter), then try every order of the other n − 1 cities. That's (n − 1)! tours, each costing up to n additions.

```swift run
// Brute force: fix city 0 first, try every order of the rest
func bruteForceTour(_ distance: [[Int]]) -> (length: Int, tours: Int) {
    let n = distance.count
    var best = Int.max
    var tours = 0
    var order: [Int] = []
    var used = [Bool](repeating: false, count: n)
    func extend(_ length: Int) {
        if order.count == n - 1 {
            tours += 1
            best = min(best, length + distance[order.last!][0])   // close the loop
            return
        }
        for city in 1..<n where !used[city] {
            let from = order.last ?? 0
            used[city] = true
            order.append(city)
            extend(length + distance[from][city])
            order.removeLast()
            used[city] = false
        }
    }
    extend(0)
    return (best, tours)
}

let distance = [
    [0, 12, 10, 19, 8],
    [12, 0, 3, 7, 2],
    [10, 3, 0, 6, 20],
    [19, 7, 6, 0, 4],
    [8, 2, 20, 4, 0],
]
let result = bruteForceTour(distance)
print("shortest tour:", result.length, "after trying", result.tours, "tours")
for cities in [5, 10, 13, 16] {
    let tours = (1..<cities).reduce(1, *)        // (cities - 1)! orders of the other cities
    print("\(cities) cities: \(tours) tours")
}
```

```output
shortest tour: 32 after trying 24 tours
5 cities: 24 tours
10 cities: 362880 tours
13 cities: 479001600 tours
16 cities: 1307674368000 tours
```

Ten cities is instant and thirteen takes a noticeable while. Sixteen would take over 20 minutes even at a billion tours a second, which is far faster than this code runs, and every extra city multiplies the time again.
 That's O(n!) growth from [Growth classes from O(1) to O(n!)](/dsa/learn/bigo-growth-classes) in action. (This brute force is a backtracking search, which M48 covers properly, with pruning tricks that help a lot in practice but don't change the worst case.)

## Held–Karp: remember sets, not orders

Look at what the brute force repeats. The partial tours 0 → 1 → 2 → 3 and 0 → 2 → 1 → 3 have visited the same cities and both stand at city 3. Whatever happens next, they can be finished in exactly the same ways. Only the shorter of the two can be part of the best tour, so there's no point carrying both.

That suggests a state that forgets the order and keeps only what matters for the future:

> `best[mask][last]` = the length of the shortest path that starts at city 0, visits **exactly** the cities in the set `mask`, and ends at city `last`.

The set is a bitmask, as in [Bitmasks for subsets and submasks](/dsa/learn/bits-subsets): bit i is 1 when city i has been visited. With n cities there are 2ⁿ masks and n possible last cities.

- **Start:** `best[1][0] = 0`. The mask `1` is binary `0…01`: only city 0 visited, standing there.
- **Step:** from a state `(mask, last)`, extend the path to any city `next` not in `mask`:
  `best[mask | (1 << next)][next] = min(itself, best[mask][last] + distance[last][next])`.
- **Order:** adding a city always makes the mask bigger as a number, so looping over masks from small to large fills every state before anything reads it.
- **Answer:** every city visited is `full = (1 << n) - 1`; close the loop with the smallest `best[full][last] + distance[last][0]`.

Each of the 2ⁿ · n states tries up to n next cities: **O(2ⁿ · n²) time** and **O(2ⁿ · n) memory**. For 16 cities that's about 16.8 million steps instead of 1.3 trillion tours. Storing which `last` led to each state lets you rebuild the tour itself:

```swift run
// Held–Karp: best[mask][last] = shortest path from city 0 through exactly the cities in mask, ending at last
func shortestTour(_ distance: [[Int]]) -> (length: Int, tour: [Int]) {
    let n = distance.count
    let full = 1 << n
    let unreached = Int.max / 2
    var best = [[Int]](repeating: [Int](repeating: unreached, count: n), count: full)
    var previous = [[Int]](repeating: [Int](repeating: -1, count: n), count: full)
    best[1][0] = 0                                  // only city 0 visited, standing at city 0

    for mask in 1..<full where mask & 1 == 1 {      // every path starts at city 0
        for last in 0..<n where mask & (1 << last) != 0 && best[mask][last] < unreached {
            for next in 0..<n where mask & (1 << next) == 0 {
                let grown = mask | (1 << next)
                let candidate = best[mask][last] + distance[last][next]
                if candidate < best[grown][next] {
                    best[grown][next] = candidate
                    previous[grown][next] = last    // remember how we got here
                }
            }
        }
    }

    // Close the loop back to city 0 from the best last city
    var length = unreached
    var last = 0
    for city in 1..<n where best[full - 1][city] + distance[city][0] < length {
        length = best[full - 1][city] + distance[city][0]
        last = city
    }
    // Walk the `previous` links back to rebuild the tour
    var tour: [Int] = []
    var mask = full - 1
    while last != -1 {
        tour.append(last)
        let before = previous[mask][last]
        mask &= ~(1 << last)
        last = before
    }
    return (length, tour.reversed() + [0])
}

let distance = [
    [0, 12, 10, 19, 8],
    [12, 0, 3, 7, 2],
    [10, 3, 0, 6, 20],
    [19, 7, 6, 0, 4],
    [8, 2, 20, 4, 0],
]
let small = shortestTour(distance)
print("5 cities:", small.length, "via", small.tour)

// 15 cities with distances from a fixed formula: 2^15 · 15 · 15 ≈ 7.4 million steps
let n = 15
let big = (0..<n).map { i in (0..<n).map { j in i == j ? 0 : (i * 37 + j * 91) % 50 + 1 } }
let answer = shortestTour(big)
print("15 cities:", answer.length, "via", answer.tour)
print("states in the table:", (1 << n) * n)
```

```output
5 cities: 32 via [0, 4, 3, 1, 2, 0]
15 cities: 105 via [0, 11, 6, 13, 9, 14, 7, 12, 10, 2, 8, 4, 5, 3, 1, 0]
states in the table: 491520
```

What to notice:

- The DP agrees with the brute force on five cities: 8 + 4 + 7 + 3 + 10 = 32.
- Fifteen cities, 87 billion possible tours, about half a million table entries.
- Rebuilding the tour walks the `previous` links backwards, removing each city from the mask with `mask &= ~(1 << last)` as it goes, until it reaches city 0, whose `previous` is -1.
- `mask & 1 == 1` skips masks without city 0: no path starting at city 0 can be in one, so half the table is never used.

This is your first taste of **bitmask DP**: a dynamic-programming table indexed by a subset. You'll meet dynamic programming properly in Part VII, and bitmask DP again in M58, its advanced DP module, with TSP and problems like assigning n people to n tasks in O(2ⁿ · n).
 The idea is always the same: when the future depends only on *which* items are used, not their order, a mask replaces n! orders with 2ⁿ sets.

## Just "is there a path?"

To ask only whether a Hamiltonian path exists, replace lengths with true or false. `reach[mask][v]` says some path visits exactly `mask` and ends at v; start with `reach[1 << v][v] = true` for every v, so the path may start anywhere, and extend along edges only. There's a Hamiltonian path if `reach[full][v]` is true for any v. Same O(2ⁿ · n²) time, and you can pack each `reach[mask]` row into the bits of one `Int`.

## Where the line falls

| Cities | Approach | Work |
| --- | --- | --- |
| up to about 10 | every order | (n − 1)!: under 400,000 at n = 10 |
| up to about 16–20 | Held–Karp | 2ⁿ · n²: 16.8 million at 16, 420 million at 20 |
| beyond that | heuristics | near-optimal answers, no guarantee |

Memory limits Held–Karp before time does: 2²⁰ · 20 entries of 8 bytes is about 170 MB. For bigger instances, real route planners use heuristics: **nearest neighbour** (always go to the closest unvisited city) builds a decent tour fast, and **2-opt** improves it by reversing any segment that makes the tour shorter, until none does. When distances obey the triangle inequality, **Christofides' algorithm** is guaranteed to be within 1.5 times the optimum.

<Callout kind="gotcha" title="Swift gotchas">
**Overflow in the sentinel.** `Int.max + distance` overflows and crashes. Use a large-but-safe value like `Int.max / 2` for "unreached", or skip unreached states before adding, as the code does.

**Precedence, the friendly way round.** In Swift, `&` has the same precedence as `*`, higher than `!=`, so `mask & (1 << j) != 0` means `(mask & (1 << j)) != 0`, as intended. In C it doesn't, so code ported from C often has extra parentheses. They're harmless; keep them if they help you read it.

**Memory layout.** `[[Int]]` with 2¹⁶ inner arrays works, but each inner array is a separate allocation. One flat array indexed by `mask * n + last` is more compact and faster, which is what the practice problem's solution does.
</Callout>
