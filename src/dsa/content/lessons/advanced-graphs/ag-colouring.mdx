## Why it matters

When the Swift compiler turns your code into machine instructions, it must keep values in the CPU's few registers. Two values that are needed at the same time can't share a register. Draw a vertex for each value and an edge between any two that are alive at once, and assigning registers becomes **colouring** the graph: give each vertex a colour so that no edge joins two vertices of the same colour, using as few colours as possible. The same model schedules exams so no student has two at once, gives neighbouring Wi-Fi access points different channels, and colours maps. Two colours is easy; three is already NP-hard. This lesson covers the fast greedy method and how its answer depends on order, and exact backtracking for small graphs.

## Proper colourings

A **proper colouring** gives every vertex a colour (a number 0, 1, 2, …) so that the two ends of every edge differ. The fewest colours a graph can be properly coloured with is its **chromatic number**.

- A graph with no edges needs 1 colour.
- A graph with at least one edge needs at least 2.
- n vertices all joined to each other (a **complete graph**) need n: every vertex clashes with every other.
- A cycle needs 2 colours if its length is even, and 3 if it's odd: colours must alternate around the cycle, and an odd cycle can't alternate all the way round.

**Two colours is the same question as "is the graph bipartite?"**, which you answered in [Bipartite check](/dsa/learn/gt-bipartite) with a BFS in O(V + E): colour the start 0, its neighbours 1, their neighbours 0, and fail if an edge ever joins two vertices of the same colour. So 2-colouring is easy. Deciding whether **3** colours are enough is NP-complete, like the Hamiltonian cycle from [the previous lesson](/dsa/learn/ag-hamiltonian), and so is every fixed number from 3 up.

A famous special case: any map drawn on a flat sheet, with regions as vertices and shared borders as edges, can be coloured with **4** colours. That's the four colour theorem, proved in 1976 with a computer checking nearly two thousand cases, the first major theorem proved that way.

## Greedy colouring

The fast heuristic: go through the vertices in some order, and give each one **the smallest colour that none of its already-coloured neighbours uses**. It's O(V + E) with a little care, and it never produces a clash.

How many colours can it need? When a vertex is coloured, at most `degree` of its neighbours already have colours, so at least one of the colours 0 to `degree` is free. So greedy never uses more than **Δ + 1** colours, where Δ is the largest degree in the graph.

That's a guarantee, not a good answer. Greedy's result depends heavily on the order:

```swift run
// Greedy colouring: each vertex, in the given order, takes the smallest colour its coloured neighbours don't use
func greedyColouring(_ n: Int, _ edges: [[Int]], order: [Int]) -> [Int] {
    var neighbours = [[Int]](repeating: [], count: n)
    for edge in edges {
        neighbours[edge[0]].append(edge[1])
        neighbours[edge[1]].append(edge[0])
    }
    var colour = [Int](repeating: -1, count: n)
    for v in order {
        let taken = Set(neighbours[v].map { colour[$0] })
        var c = 0
        while taken.contains(c) { c += 1 }
        colour[v] = c
    }
    return colour
}

// Four left vertices 0–3 and four right vertices 4–7; i is joined to 4 + j whenever i ≠ j
var edges: [[Int]] = []
for i in 0..<4 {
    for j in 0..<4 where i != j {
        edges.append([i, 4 + j])
    }
}
let leftThenRight = greedyColouring(8, edges, order: [0, 1, 2, 3, 4, 5, 6, 7])
let alternating = greedyColouring(8, edges, order: [0, 4, 1, 5, 2, 6, 3, 7])
print("left side first:", leftThenRight, "uses", leftThenRight.max()! + 1, "colours")
print("alternating:    ", alternating, "uses", alternating.max()! + 1, "colours")
```

```output
left side first: [0, 0, 0, 0, 1, 1, 1, 1] uses 2 colours
alternating:     [0, 1, 2, 3, 0, 1, 2, 3] uses 4 colours
```

The graph is bipartite (every edge joins the left side to the right), so 2 colours are enough. Taking the left side first finds that. Alternating sides is a trap: vertex 0 gets colour 0, vertex 4 isn't joined to 0 so it also gets 0, then vertex 1 is joined to 4 and needs colour 1, vertex 5 isn't joined to 1 so it reuses 1, and so on, each pair forced one colour higher. With k vertices on each side, this order uses k colours where 2 would do. (The `taken` set includes −1 for uncoloured neighbours, which is harmless: no vertex is ever given colour −1.)

**There's always some order that makes greedy optimal**: list the vertices by colour class of a best colouring, and greedy reproduces it. The catch is that finding that order is as hard as the original problem. Practical orders that usually help:

- **Largest degree first** (Welsh–Powell): the most constrained vertices pick before their options shrink.
- **DSatur**: next, colour the vertex whose neighbours already use the most *different* colours, its "saturation". It's exact for bipartite graphs and very good in general.
- **Interval graphs**: when vertices are time intervals and edges mean "overlap", greedy in order of **start time** is optimal, using exactly as many colours as the most intervals overlapping at one moment. That's the meeting-rooms answer from [Meeting rooms I and II](/dsa/learn/iv-meeting-rooms), seen as colouring: rooms are colours.

## Exact answers for small graphs: backtracking

To decide whether m colours are enough, and find a colouring if so, try every option with pruning. Colour the vertices in order. For each one, try each colour that no already-coloured neighbour uses, and move on. If a vertex has no colour left, undo it and go back to change an earlier choice. This **choose, explore, unchoose** shape is backtracking, which M48 develops in full; m-colouring is one of its classic examples.

```swift run
// m-colouring by backtracking: colour vertices in order, undo when a later vertex has no colour left
func colour(_ n: Int, _ edges: [[Int]], colours m: Int) -> [Int]? {
    var neighbours = [[Int]](repeating: [], count: n)
    for edge in edges {
        neighbours[edge[0]].append(edge[1])
        neighbours[edge[1]].append(edge[0])
    }
    var colour = [Int](repeating: -1, count: n)
    var attempts = 0

    func place(_ v: Int) -> Bool {
        if v == n { return true }                   // every vertex coloured
        for c in 0..<m {
            attempts += 1
            if neighbours[v].contains(where: { colour[$0] == c }) { continue }
            colour[v] = c                           // choose
            if place(v + 1) { return true }         // explore
        }
        colour[v] = -1                              // unchoose, and report failure
        return false
    }

    let found = place(0)
    print("  \(attempts) colour attempts")
    return found ? colour : nil
}

// The Petersen graph: an outer five-cycle, spokes, and an inner five-pointed star
let petersen = [[0, 1], [1, 2], [2, 3], [3, 4], [4, 0],
                [0, 5], [1, 6], [2, 7], [3, 8], [4, 9],
                [5, 7], [7, 9], [9, 6], [6, 8], [8, 5]]
for m in [2, 3] {
    print("Petersen with \(m) colours:")
    print(" ", colour(10, petersen, colours: m) as Any)
}
let k4 = [[0, 1], [0, 2], [0, 3], [1, 2], [1, 3], [2, 3]]
print("Four mutual neighbours with 3 colours:")
print(" ", colour(4, k4, colours: 3) as Any)
```

```output
Petersen with 2 colours:
  18 colour attempts
  nil
Petersen with 3 colours:
  20 colour attempts
  Optional([0, 1, 0, 1, 2, 1, 0, 2, 2, 1])
Four mutual neighbours with 3 colours:
  48 colour attempts
  nil
```

What to notice:

- The Petersen graph contains a five-cycle, which is odd, so 2 colours fail. With 3, backtracking finds a colouring almost at once.
- The worst case is mⁿ: every colour for every vertex. The neighbour check prunes a bad choice the moment it's made, instead of after all n vertices are coloured, which is what makes it usable for small graphs.
- Proving "impossible" is the expensive case: every branch has to be explored. Four vertices all joined to each other take 48 attempts with 3 colours, and much of that work is repeated with the colours merely renamed.

Two cheap improvements help a lot on the "impossible" side:

- **Symmetry breaking.** Colours are interchangeable, so a vertex never needs a colour more than one above the largest used so far. Vertex 0 always gets colour 0, and only one "new" colour is ever tried at each step. That removes the m! renamings of every colouring.
- **Most constrained first.** Colour vertices in DSatur order rather than 0, 1, 2, …: conflicts show up near the top of the search tree, where cutting a branch saves the most work.

## Where colouring shows up

| Problem | Vertices | Edge means | Colours are |
| --- | --- | --- | --- |
| Register allocation | values in a function | alive at the same time | CPU registers |
| Exam timetabling | exams | a student takes both | time slots |
| Wi-Fi channels | access points | close enough to interfere | radio channels |
| Sudoku | the 81 cells | same row, column or box | the digits 1 to 9 |
| Map colouring | regions | share a border | inks |

Real register allocators use greedy colouring with clever orders, because a function can have thousands of values and the compiler has to be fast. When the colours run out, a value is **spilled** to memory, which is slower but always works. That's the usual pattern for NP-hard problems in practice: a fast heuristic with a fallback, rather than an exact answer.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting to undo.** Backtracking must reset `colour[v] = -1` before reporting failure. Otherwise the stale colour stays behind, and when the previous vertex tries its next colour, the neighbour check can reject a valid choice.

- **Checking all neighbours, coloured or not.** Uncoloured neighbours hold −1, which never equals a real colour, so the check is safe, but only if "uncoloured" really is a value no colour uses.
- **Trusting greedy for "the minimum".** Greedy gives *a* proper colouring with at most Δ + 1 colours, not the chromatic number. For an exact answer on a small graph, try m = 1, 2, 3, … with backtracking until it succeeds.
</Callout>
