## Why it matters

How much water per second can a city's pipes carry from the reservoir to the treatment plant? How much data can a network push from one data centre to another, when every link has a bandwidth limit? These are **maximum flow** problems, and the algorithms that solve them are among the most reusable in computer science. Bipartite matching (the next lesson), assigning jobs to machines, separating an image's foreground from its background, and deciding whether a sports team can still win its league can all be rewritten as flow problems. This lesson builds the core idea, augmenting paths in a residual graph, then Ford–Fulkerson, Edmonds–Karp and Dinic, and the max-flow min-cut theorem that ties flows to bottlenecks.

## Flow networks

A **flow network** is a directed graph where each edge u → v has a **capacity** c(u, v) ≥ 0: the most it can carry. One vertex is the **source** s, where everything starts, and one is the **sink** t, where everything ends. Think of pipes, with capacities in litres per second.

A **flow** assigns each edge an amount f(u, v) with two rules:

1. **Capacity:** `0 ≤ f(u, v) ≤ c(u, v)`. No pipe carries more than it can.
2. **Conservation:** at every vertex except s and t, what flows in equals what flows out. Stations don't store or leak water.

The **value** of a flow is the net amount leaving s, which by conservation equals the net amount arriving at t. The **maximum flow** problem asks for a flow of the largest possible value.

Here's the network this lesson uses:

```text
            7               6
     S ──────────► A ──────────────► C ─────┐
     │             │                 ▲      │ 8
     │ 9           │ 3               │ 2    ▼
     │             ▼                 │      T
     └───────────► B ──────────────► D ─────┘
                           8               7
```

| Pipe | S→A | S→B | A→B | A→C | B→D | D→C | C→T | D→T |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Capacity | 7 | 9 | 3 | 6 | 8 | 2 | 8 | 7 |

Its maximum flow is 14. By the end of the lesson you'll be able to find that number, and prove that nothing beats it.

## Greedy paths get stuck

The natural first idea: find any path from s to t whose pipes all have spare capacity, push as much as its tightest pipe allows (its **bottleneck**), and repeat until no path is left.

It can fail. Take this small network, where every pipe has capacity 1:

```text
       ┌──► A ─────────► E ──┐
       │      ╲              ▼
       S        ╲            T
       │          ▼          ▲
       └──► C ──► D ─────────┘

```

The pipes are S→A, S→C, A→D, A→E, C→D, D→T and E→T. If the first path is S → A → D → T, then S→A and D→T are full. From S, the only way out is S → C → D, and D's only exit, D→T, is full. Stuck, with a flow of 1. But 2 is possible: S → A → E → T and S → C → D → T. The first path made a bad choice by sending A's water to D, and greedy has no way to take it back.

## The residual graph: room to change your mind

The fix is to let later paths **undo** earlier choices. For a flow f, build the **residual graph**. For each pipe u → v:

- a **forward** edge u → v with residual capacity `c(u, v) − f(u, v)`: how much more it can carry;
- a **backward** edge v → u with residual capacity `f(u, v)`: how much of its flow could be pushed back, cancelled.

An **augmenting path** is a path from s to t in the residual graph using only edges with residual capacity above 0. Pushing its bottleneck along it raises the flow's value by that much: on forward edges, flow goes up; on backward edges, flow on the original pipe goes down, which reroutes it.

In the small network, after S → A → D → T, the residual graph has a backward edge D → A (A→D carries 1, so 1 can be undone). Now there's an augmenting path S → C → D → A → E → T. Pushing 1 along it adds 1 to S→C, C→D, A→E and E→T, and *cancels* the 1 on A→D. The net result: A's water now goes to E, C's goes to D, and the total is 2. Step through it, and watch the second path use A→D backwards:

The same thing in code, with an adjacency matrix of residual capacities. Pushing f units along u → v does `residual[u][v] -= f` and `residual[v][u] += f`: the second line is what creates the backward edge.

```swift run
// Edmonds–Karp again, on the network where the first path has to be partly undone
func maxFlow(_ capacity: [[Int]], from source: Int, to sink: Int, names: [String]) -> Int {
    var residual = capacity
    var total = 0
    while true {
        var parent = [Int](repeating: -1, count: capacity.count)
        parent[source] = source
        var queue = [source], head = 0
        while head < queue.count && parent[sink] == -1 {
            let u = queue[head]
            head += 1
            for v in residual.indices where parent[v] == -1 && residual[u][v] > 0 {
                parent[v] = u
                queue.append(v)
            }
        }
        if parent[sink] == -1 { return total }
        var steps: [String] = []
        var bottleneck = Int.max
        var v = sink
        while v != source {
            let u = parent[v]
            bottleneck = min(bottleneck, residual[u][v])
            // An edge with no capacity of its own can only be carrying flow back: a cancellation
            steps.append(capacity[u][v] > 0 ? "\(names[u])→\(names[v])" : "\(names[u])→\(names[v]) (undoes \(names[v])→\(names[u]))")
            v = u
        }
        v = sink
        while v != source {
            residual[parent[v]][v] -= bottleneck
            residual[v][parent[v]] += bottleneck
            v = parent[v]
        }
        total += bottleneck
        print("push \(bottleneck): \(steps.reversed().joined(separator: ", "))")
    }
}

let names = ["S", "A", "C", "D", "E", "T"]
var capacity = [[Int]](repeating: [Int](repeating: 0, count: 6), count: 6)
for (from, to) in [("S", "A"), ("S", "C"), ("A", "D"), ("A", "E"), ("C", "D"), ("D", "T"), ("E", "T")] {
    capacity[names.firstIndex(of: from)!][names.firstIndex(of: to)!] = 1
}
print("max flow:", maxFlow(capacity, from: 0, to: 5, names: names))
```

```output
push 1: S→C, C→D, D→A (undoes A→D), A→E, E→T
max flow: 2
```

## Ford–Fulkerson

That's the whole method, due to Ford and Fulkerson (1956):

1. Start with zero flow everywhere.
2. While the residual graph has an augmenting path, push its bottleneck along it.
3. When there's none, the flow is maximum.

Why is "no augmenting path" enough to stop? That's the max-flow min-cut theorem, coming up shortly. First, how long does it take? With **integer** capacities, every push adds at least 1, so it stops after at most F pushes, where F is the maximum flow's value. Each push needs one search, O(E), so it's **O(E · F)**.

That bound depends on the *capacities*, not just the graph's size, and it can be dreadful. Here's the classic bad case:

```text
          1,000,000,000         1,000,000,000
     S ──────────────────► A ──────────────────► T
     │                     │                     ▲
     │                     │ 1                   │
     │                     ▼                     │
     └──────────────────►  B ────────────────────┘
          1,000,000,000         1,000,000,000
```

The answer is two billion: one billion over the top, one billion along the bottom. But a search that happens to pick S → A → B → T, then S → B → A → T (using A→B backwards), then S → A → B → T again, and so on, pushes **1** each time through the middle pipe: two billion augmentations. Plain DFS can fall into this. (With irrational capacities, Ford–Fulkerson can even run forever without reaching the maximum; integers at least guarantee it stops.)

## Edmonds–Karp: always the shortest path

Edmonds and Karp's fix (1972) is one word: find each augmenting path with **BFS**, so it has the fewest edges. On the bad case above, BFS finds the two-edge paths S → A → T and S → B → T first, and it's done in two pushes.

The guarantee holds for every network. With shortest paths, the BFS distance from s to every vertex never decreases from one push to the next. Each push saturates at least one edge (its bottleneck), and before that edge can be the bottleneck again, the distance to its start must grow by at least 2. Distances are at most V, so each edge is the bottleneck O(V) times, giving O(V · E) pushes of O(E) each:

**Edmonds–Karp runs in O(V · E²), whatever the capacities.**

Here it is on the lesson's network, printing each augmenting path, and then reading off the minimum cut (explained in the next section) from what's left reachable:

```swift run
// Edmonds–Karp on an adjacency matrix: BFS for the shortest augmenting path, push its bottleneck, repeat
func maxFlow(_ capacity: [[Int]], from source: Int, to sink: Int, names: [String]) -> Int {
    var residual = capacity                       // residual[u][v]: how much more can go u→v
    var total = 0
    while true {
        var parent = [Int](repeating: -1, count: capacity.count)
        parent[source] = source
        var queue = [source], head = 0
        while head < queue.count && parent[sink] == -1 {      // BFS: the shortest augmenting path
            let u = queue[head]
            head += 1
            for v in residual.indices where parent[v] == -1 && residual[u][v] > 0 {
                parent[v] = u
                queue.append(v)
            }
        }
        if parent[sink] == -1 { break }           // no path left: the flow is maximum

        var path = [sink]
        var bottleneck = Int.max
        var v = sink
        while v != source {
            bottleneck = min(bottleneck, residual[parent[v]][v])
            v = parent[v]
            path.append(v)
        }
        v = sink
        while v != source {
            residual[parent[v]][v] -= bottleneck
            residual[v][parent[v]] += bottleneck  // so this flow can be pushed back later
            v = parent[v]
        }
        total += bottleneck
        print("push \(bottleneck) along \(path.reversed().map { names[$0] }.joined(separator: "→")), total \(total)")
    }

    // The minimum cut: everything still reachable from the source in the residual graph
    var reachable = [Bool](repeating: false, count: capacity.count)
    reachable[source] = true
    var stack = [source]
    while let u = stack.popLast() {
        for v in residual.indices where !reachable[v] && residual[u][v] > 0 {
            reachable[v] = true
            stack.append(v)
        }
    }
    var cut: [String] = []
    for u in capacity.indices where reachable[u] {
        for v in capacity.indices where !reachable[v] && capacity[u][v] > 0 {
            cut.append("\(names[u])→\(names[v]) (\(capacity[u][v]))")
        }
    }
    print("source side:", capacity.indices.filter { reachable[$0] }.map { names[$0] }, "cut:", cut.joined(separator: ", "))
    return total
}

func network(_ names: [String], _ pipes: [(String, String, Int)]) -> [[Int]] {
    var capacity = [[Int]](repeating: [Int](repeating: 0, count: names.count), count: names.count)
    for (from, to, amount) in pipes {
        capacity[names.firstIndex(of: from)!][names.firstIndex(of: to)!] += amount
    }
    return capacity
}

let names = ["S", "A", "B", "C", "D", "T"]
let pipes = [("S", "A", 7), ("S", "B", 9), ("A", "B", 3), ("A", "C", 6),
             ("B", "D", 8), ("D", "C", 2), ("C", "T", 8), ("D", "T", 7)]
print("max flow:", maxFlow(network(names, pipes), from: 0, to: 5, names: names))
```

```output
push 6 along S→A→C→T, total 6
push 7 along S→B→D→T, total 13
push 1 along S→B→D→C→T, total 14
source side: ["S", "A", "B"] cut: A→C (6), B→D (8)
max flow: 14
```

An adjacency matrix makes residual edges trivial (`residual[v][u]` is always there) and costs O(V²) memory and O(V²) per BFS, which is fine for a few hundred vertices. The helper uses `+=`, not `=`, so two parallel pipes between the same stations add up instead of the second overwriting the first.

## The max-flow min-cut theorem

An **s-t cut** splits the vertices into two sides: S containing the source, and T containing the sink. Its **capacity** is the total capacity of the pipes going **from the S side to the T side**. (Pipes going back from T to S don't count.)

Every unit of flow has to cross from the S side to the T side somewhere, so **any flow's value is at most any cut's capacity**. In the lesson's network, the cut whose S side is S, A and B has capacity A→C + B→D = 6 + 8 = 14, so no flow can exceed 14.

The theorem says the two meet:

> **The maximum flow's value equals the minimum cut's capacity.**

And Ford–Fulkerson's stopping point proves it. When no augmenting path is left, let the S side be every vertex still reachable from s in the residual graph; t isn't, or there'd be a path. Then:

- every pipe from the S side to the T side is **full** (otherwise its forward residual would reach across);
- every pipe from the T side back to the S side carries **nothing** (otherwise its backward residual would reach across).

So the flow across this cut is exactly the cut's capacity, and since no flow can beat any cut, both are optimal. That's why "no augmenting path" means "maximum", and it's what the last lines of the code compute: the reachable set S, A, B and its full pipes A→C and B→D. The minimum cut is often the answer people actually want: **the cheapest set of pipes to cut** to separate s from t, or the network's true bottleneck.

## Dinic's algorithm

Edmonds–Karp does a whole BFS for each single path. Dinic's algorithm (1970) gets far more out of each BFS. It works in **phases**:

1. **BFS** from s in the residual graph, giving every vertex a **level**: its distance from s. Stop if t has no level.
2. **Blocking flow:** using only edges that go from one level to the very next, push flow with DFS again and again until no more gets through. Every shortest path of the current length is used up.
3. Repeat. Each phase makes the shortest s-t path strictly longer, so there are at most V phases.

One trick keeps step 2 fast: each vertex remembers `nextEdge`, the first of its edges that hasn't yet been found useless in this phase. An edge that leads to a dead end, or is full, is skipped for the rest of the phase, so no edge is retried in vain.

Dinic needs an **adjacency list** with residual edges. The standard layout stores every pipe as a pair of edges side by side: forward at an even index e, backward at e + 1. Then the partner of any edge e is `e ^ 1`, as XOR with 1 flips the lowest bit, which you saw in [XOR tricks](/dsa/learn/bits-xor-tricks).

```swift run
// Dinic's algorithm: BFS levels, then a blocking flow along edges that go one level further
struct FlowNetwork {
    var head: [Int] = []                          // head[e]: where edge e leads
    var residual: [Int] = []                      // residual[e]: how much more e can carry
    var edgesOut: [[Int]]

    init(vertices: Int) {
        edgesOut = [[Int]](repeating: [], count: vertices)
    }

    // Edge e and its reverse are stored side by side, at e and e ^ 1
    mutating func addPipe(_ from: Int, _ to: Int, _ capacity: Int) {
        edgesOut[from].append(head.count)
        head.append(to)
        residual.append(capacity)
        edgesOut[to].append(head.count)
        head.append(from)
        residual.append(0)
    }

    mutating func maxFlow(from source: Int, to sink: Int) -> Int {
        let n = edgesOut.count
        var total = 0
        var phase = 0
        while true {
            // 1. BFS: each vertex's level is its distance from the source in the residual graph
            var level = [Int](repeating: -1, count: n)
            level[source] = 0
            var queue = [source], front = 0
            while front < queue.count {
                let u = queue[front]
                front += 1
                for e in edgesOut[u] where residual[e] > 0 && level[head[e]] == -1 {
                    level[head[e]] = level[u] + 1
                    queue.append(head[e])
                }
            }
            if level[sink] == -1 { return total }

            // 2. DFS: push flow along level-increasing edges until none gets through
            var nextEdge = [Int](repeating: 0, count: n)   // edges before this are useless this phase
            func push(_ u: Int, _ limit: Int) -> Int {
                if u == sink { return limit }
                while nextEdge[u] < edgesOut[u].count {
                    let e = edgesOut[u][nextEdge[u]]
                    if residual[e] > 0 && level[head[e]] == level[u] + 1 {
                        let pushed = push(head[e], min(limit, residual[e]))
                        if pushed > 0 {
                            residual[e] -= pushed
                            residual[e ^ 1] += pushed
                            return pushed
                        }
                    }
                    nextEdge[u] += 1
                }
                return 0
            }
            var phaseFlow = 0
            while true {
                let pushed = push(source, Int.max)
                if pushed == 0 { break }
                phaseFlow += pushed
            }
            phase += 1
            total += phaseFlow
            print("phase \(phase): sink at level \(level[sink]), pushed \(phaseFlow), total \(total)")
        }
    }
}

// S=0, A=1, B=2, C=3, D=4, T=5: the lesson's network
var network = FlowNetwork(vertices: 6)
for (from, to, capacity) in [(0, 1, 7), (0, 2, 9), (1, 2, 3), (1, 3, 6), (2, 4, 8), (4, 3, 2), (3, 5, 8), (4, 5, 7)] {
    network.addPipe(from, to, capacity)
}
print("max flow:", network.maxFlow(from: 0, to: 5))
```

```output
phase 1: sink at level 3, pushed 13, total 13
phase 2: sink at level 4, pushed 1, total 14
max flow: 14
```

Phase 1 sends 13 units along every three-pipe path at once; phase 2 finds the one four-pipe path. Two BFS runs instead of three. On big networks the gap is huge.

Dinic is **O(V² · E)** in general, and much faster on special networks: on the unit-capacity networks that bipartite matching produces, it's O(E √V). It's the usual choice in competitive programming. The DFS is at most one call per level deep, so at most V calls.

| Algorithm | Finds paths with | Time |
| --- | --- | --- |
| Ford–Fulkerson | any search (often DFS) | O(E · F), F the max flow |
| Edmonds–Karp | BFS, one shortest path per search | O(V · E²) |
| Dinic | BFS levels plus a blocking flow per phase | O(V² · E); O(E √V) for unit-capacity matching |

## Modelling with flows

The real skill is noticing that a problem is a flow problem. A few standard tricks:

- **Several sources or sinks:** add a super source with a pipe of unlimited capacity to each source, and likewise a super sink.
- **Undirected pipes:** add both directions with the same capacity. The residual edges handle the rest.
- **Capacities on vertices:** split each vertex v into `v_in` and `v_out`, joined by a pipe with v's capacity; edges into v go to `v_in`, edges out leave from `v_out`.
- **Edge-disjoint paths:** give every edge capacity 1. The max flow is the largest number of s-t paths sharing no edge, and the min cut is the fewest edges whose removal disconnects s from t.
- **Matching:** source → left side → right side → sink, every capacity 1. That's the next lesson.

<Callout kind="gotcha" title="Common mistakes">
- **No backward edges.** Without `residual[v][u] += f` (or the `e ^ 1` partner), the algorithm can't undo a bad path and returns a smaller flow, as greedy did.
- **Overwriting parallel pipes.** In a matrix, two pipes from u to v must add up: `capacity[u][v] += c`, not `= c`.
- **Plain DFS on big capacities.** Correct, but O(E · F) can mean billions of augmentations. Use BFS.
- **The wrong partner.** With edge pairs, the partner is `e ^ 1` only if every pipe adds its two edges consecutively, starting at an even index. Add them together, always forward first.
- **Overflow.** Use `Int.max` as the starting limit but never add to it. Total flow with capacities up to a billion fits easily in Swift's 64-bit `Int`.
</Callout>
