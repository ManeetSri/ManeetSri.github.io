## Why it matters

An office has to put each meeting in the morning or the afternoon, and people send in rules: "the design review or the standup has to be in the morning", "if the review is in the morning, the client call must be too". Each choice is yes or no, and each rule ties two choices together. That's **2-SAT**. Feature flags that must be on or off together, placing a label above or below each point on a map so no labels overlap, and choosing which of two venues each team plays at all fit the same shape. General satisfiability is NP-complete, but when every rule mentions at most two choices, the problem collapses into a graph and is solved in linear time with the [strongly connected components](/dsa/learn/ag-scc) from the start of this module.

## Variables, literals and clauses

- A **variable** is a yes/no choice: x₀ means "meeting 0 is in the morning".
- A **literal** is a variable or its negation: x₀, or ¬x₀ ("meeting 0 is *not* in the morning", so it's in the afternoon).
- A **clause** is "a or b" for two literals a and b. It's satisfied when at least one of them is true.
- A **2-SAT formula** is a list of clauses that must all hold at once.

The question: is there an assignment of true and false to the variables that satisfies every clause, and if so, what is it?

With three or more literals per clause, the problem is 3-SAT, the original NP-complete problem: no known algorithm beats exponential time in the worst case. With two, it's O(n + m) for n variables and m clauses. The difference is that a two-literal clause is really a pair of **implications**, and implications form a graph.

## From clauses to an implication graph

"a or b" means: if a is false, b must be true; and if b is false, a must be true.

**(a ∨ b) is the same as (¬a → b) and (¬b → a).**

So build a directed graph with **two vertices per variable**, one for x and one for ¬x, and add both implications for every clause. A path from u to w means: if u is true, w is forced to be true.

A tidy numbering makes negation free: variable x is vertex `2 * x` and ¬x is vertex `2 * x + 1`. Then the negation of any vertex v is `v ^ 1`, because XOR with 1 flips between 2x and 2x + 1. In code, clauses usually arrive with a non-negative number for a plain variable and Swift's bitwise NOT, `~x` (which is −x − 1), for its negation, as in [The bitwise operators and masking shifts](/dsa/learn/bits-operators). Then `code >= 0 ? 2 * code : 2 * ~code + 1` turns either form into a vertex.

Here are the meeting rules from the opening, with the standup and client call as meetings 1 and 2:

| Rule | Clause | Implications |
| --- | --- | --- |
| Review or standup in the morning | x₀ ∨ x₁ | ¬x₀ → x₁, ¬x₁ → x₀ |
| If review is in the morning, so is the client call | ¬x₀ ∨ x₂ | x₀ → x₂, ¬x₂ → ¬x₀ |
| Standup and client call not both in the morning | ¬x₁ ∨ ¬x₂ | x₁ → ¬x₂, x₂ → ¬x₁ |

Every clause gives a pair of edges that mirror each other: u → w comes with ¬w → ¬u. That symmetry (each implication together with its contrapositive) is what makes the algorithm below work.

## When is it impossible?

Suppose x and ¬x are in the **same strongly connected component**. Then there's a path from x to ¬x and a path from ¬x to x. Setting x true forces ¬x true, a contradiction; setting x false makes ¬x true, which forces x true, another contradiction. No assignment works.

The remarkable part is the converse: **if no variable shares a component with its own negation, the formula is satisfiable**, and the components tell you an assignment. So:

**A 2-SAT formula is unsatisfiable exactly when some x and ¬x lie in the same SCC.**

## Reading off an assignment

Condense the implication graph into its components, which form a DAG. For each variable, x and ¬x are in different components; one of them comes **later in topological order** (nearer the sinks). Make that literal true.

Why does that never break an implication? Write `topo(c)` for a component's position in topological order. Suppose there's an edge u → w and u was made true, so `topo(u) > topo(¬u)`. The mirror edge ¬w → ¬u means `topo(¬w) ≤ topo(¬u)`, and the edge itself means `topo(u) ≤ topo(w)`. Chaining them: `topo(w) ≥ topo(u) > topo(¬u) ≥ topo(¬w)`. So w is also later than ¬w, and w was made true too. Every true literal only implies true literals, so every clause holds.

Tarjan's algorithm closes components in **reverse** topological order: sinks first, numbered 0, 1, 2, …. So "later in topological order" means "**smaller Tarjan number**": set x true when `component[x] < component[¬x]`. (With Kosaraju's numbering, which is topological order, the comparison flips.)

## The code

```swift run
// 2-SAT: variable x is node 2x, its negation node 2x + 1. A code c ≥ 0 means x_c; ~c means ¬x_c.
func node(_ code: Int) -> Int { code >= 0 ? 2 * code : 2 * ~code + 1 }
func name(_ v: Int) -> String { v % 2 == 0 ? "x\(v / 2)" : "¬x\(v / 2)" }

func solve(_ n: Int, _ clauses: [[Int]]) -> [Bool]? {
    // Each clause (a or b) gives two implications: not a → b, and not b → a
    var implies = [[Int]](repeating: [], count: 2 * n)
    for clause in clauses {
        let a = node(clause[0]), b = node(clause[1])
        implies[a ^ 1].append(b)
        implies[b ^ 1].append(a)
    }
    let edges = (0..<(2 * n)).flatMap { v in implies[v].map { "\(name(v)) → \(name($0))" } }
    print("implications:", edges.joined(separator: ", "))

    // Tarjan's algorithm numbers components in the order they close: reverse topological order
    var index = [Int](repeating: -1, count: 2 * n)
    var low = [Int](repeating: 0, count: 2 * n)
    var component = [Int](repeating: -1, count: 2 * n)
    var onStack = [Bool](repeating: false, count: 2 * n)
    var stack: [Int] = []
    var nextIndex = 0
    var components = 0
    func visit(_ v: Int) {
        index[v] = nextIndex
        low[v] = nextIndex
        nextIndex += 1
        stack.append(v)
        onStack[v] = true
        for w in implies[v] {
            if index[w] == -1 {
                visit(w)
                low[v] = min(low[v], low[w])
            } else if onStack[w] {
                low[v] = min(low[v], index[w])
            }
        }
        if low[v] == index[v] {
            while true {
                let w = stack.removeLast()
                onStack[w] = false
                component[w] = components
                if w == v { break }
            }
            components += 1
        }
    }
    for v in 0..<(2 * n) where index[v] == -1 {
        visit(v)
    }

    var value = [Bool](repeating: false, count: n)
    for x in 0..<n {
        if component[2 * x] == component[2 * x + 1] {
            print("x\(x) and ¬x\(x) are in the same component: impossible")
            return nil
        }
        // Pick the literal whose component comes later in topological order: the smaller Tarjan number
        value[x] = component[2 * x] < component[2 * x + 1]
    }
    print("components:", (0..<(2 * n)).map { "\(name($0))=\(component[$0])" }.joined(separator: " "))
    return value
}

// Meetings 0, 1, 2; true means morning
let rules = [[0, 1], [~0, 2], [~1, ~2]]
if let plan = solve(3, rules) {
    print("plan:", plan)
    let kept = rules.allSatisfy { rule in rule.contains { $0 >= 0 ? plan[$0] : !plan[~$0] } }
    print("every rule kept:", kept)
}
print()
print(solve(3, [[0, 0], [~0, 1], [~1, 2], [~2, ~0]]) as Any)
```

```output
implications: x0 → x2, ¬x0 → x1, x1 → ¬x2, ¬x1 → x0, x2 → ¬x1, ¬x2 → ¬x0
components: x0=0 ¬x0=1 x1=1 ¬x1=0 x2=0 ¬x2=1
plan: [true, false, true]
every rule kept: true

implications: x0 → x1, x0 → ¬x2, ¬x0 → x0, ¬x0 → x0, x1 → x2, ¬x1 → ¬x0, x2 → ¬x0, ¬x2 → ¬x1
x0 and ¬x0 are in the same component: impossible
nil
```

What to notice:

- In the first formula, x₀ → x₂ → ¬x₁ → x₀ is a cycle, and so is its mirror image ¬x₀ → x₁ → ¬x₂ → ¬x₀. Two components, with no edges between them. Tarjan closed the component of x₀, x₂ and ¬x₁ first, so those literals are true: review and client call in the morning, standup in the afternoon. (The mirror plan, with every choice flipped, works too.)
- The second formula starts with the clause `[0, 0]`, "x₀ or x₀", which forces x₀ true: both of its implications are ¬x₀ → x₀. Then x₀ → x₁ → x₂ → ¬x₀ closes a loop through both x₀ and ¬x₀, so they share a component, and no plan exists.
- Building the graph is O(n + m), Tarjan is O(n + m), and the final loop is O(n). The whole solver is **linear**.
- For large inputs, the recursion in `visit` is as deep as the longest chain of implications. Use the iterative Tarjan from the SCC lesson; the rest of the code doesn't change.

## Writing constraints as clauses

Most of the work in a 2-SAT problem is translating the rules. Every rule has to become clauses of exactly two literals:

| Rule | Clauses |
| --- | --- |
| a must be true | a ∨ a |
| a or b | a ∨ b |
| not both a and b | ¬a ∨ ¬b |
| if a then b | ¬a ∨ b |
| exactly one of a and b | a ∨ b, and ¬a ∨ ¬b |
| a and b are equal | ¬a ∨ b, and a ∨ ¬b |

If a rule needs three literals at once, such as "at least one of a, b and c", it isn't 2-SAT any more, and there's no known way to rewrite general 3-SAT as 2-SAT.


<Callout kind="gotcha" title="Common mistakes">
- **Adding only one implication per clause.** "a or b" needs both ¬a → b and ¬b → a. With one, the graph loses its mirror symmetry and the answer can be wrong in both directions.
- **Comparing components the wrong way.** With Tarjan's numbering, pick x when `component[x] < component[¬x]`. With Kosaraju's, it's `>`. Mixing them up produces an assignment that breaks clauses, so always check a few small cases against brute force.
- **Getting `~` wrong.** `~x` is −x − 1, not −x. That's what lets 0 have a negation: `~0` is −1. Writing `-x` would make "not meeting 0" the same as "meeting 0".
- **Deep recursion.** Implication chains can be as long as the number of variables. In tests, use the explicit-stack Tarjan.
</Callout>
