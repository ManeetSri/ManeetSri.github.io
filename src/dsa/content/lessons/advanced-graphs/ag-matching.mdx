## Why it matters

A ride-hailing app pairs waiting riders with nearby drivers. A university assigns students to project supervisors who can take them. A film crew hands out the day's jobs to people qualified for them. Each is a **bipartite matching** problem: two groups, a list of allowed pairs, and the goal of pairing up as many as possible, with nobody used twice. The obvious greedy approach gets stuck, and the fix is the same idea as in [max flow](/dsa/learn/ag-max-flow): augmenting paths that let later choices undo earlier ones. This lesson builds Kuhn's algorithm, a short DFS that finds maximum matchings, shows the reduction to max flow, and outlines the faster Hopcroft–Karp.

## Matchings

A graph is **bipartite** when its vertices split into two sides with every edge going from one side to the other, as in [Bipartite check](/dsa/learn/gt-bipartite). Here, workers on the left and jobs on the right, with an edge whenever a worker is qualified for a job.

A **matching** is a set of edges where no two share a vertex: each worker gets at most one job, and each job at most one worker. A **maximum matching** has as many edges as possible.

Here's the crew for this lesson, with who can do what:

| Worker | Qualified for |
| --- | --- |
| Ana | camera, lights |
| Ben | lights, sound |
| Caz | sound, edit |
| Dev | camera |

## Greedy gets stuck

Let each worker in turn take the first free job on their list. Ana takes camera, Ben takes lights, Caz takes sound, and Dev, who can only do camera, gets nothing. Three of four placed. But all four can work: Dev on camera, Ana on lights, Ben on sound, Caz on edit.

The greedy result is **maximal**: no edge can be *added* to it. It isn't **maximum**: a bigger matching exists, but reaching it means *changing* earlier assignments, not just adding to them.

## Augmenting paths

Look at how the better matching differs. Dev takes camera from Ana, Ana moves to lights, which bumps Ben, who moves to sound, which bumps Caz, who moves to the free edit job:

```text
   Dev ─── camera ═══ Ana ─── lights ═══ Ben ─── sound ═══ Caz ─── edit
  (free)                                                          (free)
```

Double lines are edges in the current matching; single lines are edges not in it. The path starts at a **free** worker, ends at a **free** job, and **alternates** between unmatched and matched edges. That's an **augmenting path**. Flip every edge on it, matched to unmatched and unmatched to matched, and the matching gains exactly one edge: the path had one more unmatched edge than matched ones.

**Berge's theorem** (1957): a matching is maximum **exactly when no augmenting path exists**. So a correct algorithm only needs to keep finding augmenting paths and flipping them until there are none.

## Kuhn's algorithm

Kuhn's algorithm (1955) finds augmenting paths with a DFS that reads almost like the story above. To find a job for worker w, try each job on w's list:

- if the job is **free**, take it;
- if it's taken, ask its current holder to **find another job**, recursively. If they can, take this one.

A `seen` array, reset for each worker's search, stops the search from trying the same job twice and going round in circles.

```swift run
let workers = ["Ana", "Ben", "Caz", "Dev"]
let jobs = ["camera", "lights", "sound", "edit"]
let canDo = [[0, 1], [1, 2], [2, 3], [0]]          // Ana: camera or lights, … Dev: camera only

// Greedy: each worker takes the first free job on their list
var takenBy = [Int](repeating: -1, count: jobs.count)
for worker in workers.indices {
    if let job = canDo[worker].first(where: { takenBy[$0] == -1 }) {
        takenBy[job] = worker
    }
}
print("greedy places", takenBy.filter { $0 != -1 }.count, "workers")

// Kuhn's algorithm: for each worker, search for an augmenting path with DFS
var workerOfJob = [Int](repeating: -1, count: jobs.count)
var seen = [Bool](repeating: false, count: jobs.count)
var steps: [String] = []

func findJob(for worker: Int) -> Bool {
    for job in canDo[worker] where !seen[job] {
        seen[job] = true
        let holder = workerOfJob[job]
        steps.append(holder == -1 ? "\(jobs[job]) is free" : "\(jobs[job]) is \(workers[holder])'s")
        if holder == -1 || findJob(for: holder) {
            workerOfJob[job] = worker               // flip: this job now goes to this worker
            return true
        }
    }
    return false
}

for worker in workers.indices {
    seen = [Bool](repeating: false, count: jobs.count)   // a fresh search for each worker
    steps = []
    let placed = findJob(for: worker)
    print("\(workers[worker]): \(steps.joined(separator: " → "))\(placed ? "" : " → no luck")")
}
for job in jobs.indices where workerOfJob[job] != -1 {
    print("  \(workers[workerOfJob[job]]) does \(jobs[job])")
}
```

```output
greedy places 3 workers
Ana: camera is free
Ben: lights is free
Caz: sound is free
Dev: camera is Ana's → lights is Ben's → sound is Caz's → edit is free
  Dev does camera
  Ana does lights
  Ben does sound
  Caz does edit
```

The first three workers find free jobs straight away, just like greedy. Dev's search is the augmenting path: camera is Ana's, so the DFS asks Ana to move; lights is Ben's, so it asks Ben; sound is Caz's, so it asks Caz; edit is free. As the recursion returns, each `workerOfJob[job] = worker` flips one edge, from the far end back to Dev.

**Cost.** Each worker's search visits each edge at most once, O(E), and there are V workers: **O(V · E)**. A worker whose search fails can be skipped for good: if no augmenting path starts at them now, none will appear later. The recursion is at most one call per worker deep.

## Matching as a max flow

Bipartite matching is a special case of max flow:

```text
               ┌─► Ana ──► camera ──┐
               ├─► Ben ──► lights ──┤
   source ─────┼─► Caz ──► sound  ──┼────► sink
               └─► Dev ──► edit   ──┘
          (plus every qualified worker → job edge; every capacity is 1)
```

Add a source with a pipe of capacity 1 to every worker, a pipe of capacity 1 from each worker to each job they can do, and a pipe of capacity 1 from every job to a sink. A flow sends at most 1 unit into each worker and at most 1 unit out of each job, so the worker → job pipes carrying flow form a matching, and the max flow's value is the maximum matching's size. With integer capacities, the augmenting-path algorithms always produce integer flows, so no pipe ever carries half a unit.

```swift run
// The same matching as a max flow: source → workers → jobs → sink, every capacity 1
let canDo = [[0, 1], [1, 2], [2, 3], [0]]
let workerCount = 4, jobCount = 4
let source = 0, sink = workerCount + jobCount + 1
func workerNode(_ w: Int) -> Int { 1 + w }
func jobNode(_ j: Int) -> Int { 1 + workerCount + j }

var residual = [[Int]](repeating: [Int](repeating: 0, count: sink + 1), count: sink + 1)
for w in 0..<workerCount {
    residual[source][workerNode(w)] = 1
    for j in canDo[w] { residual[workerNode(w)][jobNode(j)] = 1 }
}
for j in 0..<jobCount { residual[jobNode(j)][sink] = 1 }

var flow = 0
while true {
    var parent = [Int](repeating: -1, count: sink + 1)
    parent[source] = source
    var queue = [source], head = 0
    while head < queue.count && parent[sink] == -1 {
        let u = queue[head]
        head += 1
        for v in residual.indices where parent[v] == -1 && residual[u][v] > 0 {
            parent[v] = u
            queue.append(v)
        }
    }
    if parent[sink] == -1 { break }
    var v = sink
    while v != source {                              // every bottleneck is 1
        residual[parent[v]][v] -= 1
        residual[v][parent[v]] += 1
        v = parent[v]
    }
    flow += 1
}
print("max flow:", flow)
// A worker → job edge carries flow exactly when its backward residual is 1
for w in 0..<workerCount {
    for j in canDo[w] where residual[jobNode(j)][workerNode(w)] == 1 {
        print("worker \(w) → job \(j)")
    }
}
```

```output
max flow: 4
worker 0 → job 1
worker 1 → job 2
worker 2 → job 3
worker 3 → job 0
```

Same answer: Ana (worker 0) on lights, Ben on sound, Caz on edit, Dev on camera. An augmenting path in this flow network, source → free worker → … → free job → sink, using worker → job pipes forwards and matched ones backwards, is exactly an augmenting path of the matching. Kuhn's algorithm is this flow algorithm with the source, sink and capacities left implicit.

The flow view earns its keep when the problem grows: a job that needs **two** workers is a job → sink pipe of capacity 2; a worker who can do up to three jobs is a source → worker pipe of capacity 3. Kuhn's algorithm doesn't stretch to those; flow does.

## Hopcroft–Karp, in outline

Kuhn's algorithm finds one augmenting path per search. **Hopcroft–Karp** (1973) finds many at once, in phases, like Dinic's algorithm:

1. **BFS** from *all* free workers at once, layering the graph by alternating-path distance, until some layer reaches a free job.
2. **DFS** to find a maximal set of augmenting paths of exactly that shortest length that share no vertex, and flip them all.
3. Repeat until a BFS finds no free job.

The shortest augmenting path gets longer every phase, and only O(√V) phases are needed, each O(E): **O(E √V)** in total. It's exactly Dinic's algorithm run on the unit-capacity network above. For a few hundred workers, Kuhn's simpler code is plenty; for a hundred thousand, Hopcroft–Karp is the one to reach for.

## Related results worth knowing

- **Hall's theorem.** Every worker can be placed exactly when every group of k workers is qualified, between them, for at least k different jobs. When placement fails, some group of workers is competing for too few jobs, and that group is a certificate you can show someone.
- **König's theorem.** In a bipartite graph, the size of a maximum matching equals the fewest vertices needed to touch every edge (a minimum vertex cover). It's the max-flow min-cut theorem in disguise.
- **Weighted assignment.** If each worker–job pair has a cost and every worker must be placed, minimising the total cost is the assignment problem, solved by the Hungarian algorithm in O(n³).
- **Not bipartite?** Matching in general graphs, such as pairing up people for a kidney exchange where anyone might pair with anyone, needs Edmonds' blossom algorithm, which handles the odd cycles that break Kuhn's search.

<Callout kind="gotcha" title="Common mistakes">
- **Not resetting `seen` between workers.** Jobs marked during one worker's search must be tried again in the next one. Reset the array per worker, or stamp each job with the current worker's number and compare, which avoids an O(jobs) reset per search.
- **Recording the assignment only in one direction.** Keep `workerOfJob` while searching (that's what the DFS needs), and build each worker's job from it at the end.
- **Trusting greedy.** First-free-job greedy gives a maximal matching, which can be much smaller than the maximum: in the worst case, half its size.
</Callout>
