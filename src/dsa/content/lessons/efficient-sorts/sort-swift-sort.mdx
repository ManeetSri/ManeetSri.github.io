## Why it matters

In real Swift code you'll almost never write merge sort or quick sort yourself: you'll call `sort()` or `sorted(by:)`. What you **will** write, constantly, is the part that decides the order: a `Comparable` conformance for your own types, or a closure that compares two values by several fields. Get that closure subtly wrong and the sort can quietly give a different order than you meant, a classic bug in table views and leaderboards. This lesson pulls the module together: how to describe any order to Swift, the one rule your comparison must obey, and what Swift's sort actually does with it.

## sort() and sorted(): a quick recap

You met the basics in [sorted(by:), min, max, contains and first(where:)](/dsa/learn/swift-sorting-searching-api):

- `sort()` rearranges a `var` array **in place**; `sorted()` returns a **new** array and leaves the original alone.
- Both use `<` for elements that are `Comparable`, such as numbers and strings.
- `sort(by:)` and `sorted(by:)` take a closure that answers one question: **should the first element come before the second?** `sorted(by: >)` gives decreasing order.

The rest of this lesson builds on that.

## Sorting your own types with Comparable

To make plain `sort()`, `min()` and `max()` work on your own type, conform it to `Comparable`, as in [Equatable, Comparable and CustomStringConvertible](/dsa/learn/swift-standard-protocols). You write one function, `<`, and Swift provides `>`, `<=` and `>=` from it:

```swift run
struct Runner: Comparable {
    let name: String
    let seconds: Int

    // Fastest first; equal times in alphabetical order
    static func < (lhs: Runner, rhs: Runner) -> Bool {
        (lhs.seconds, lhs.name) < (rhs.seconds, rhs.name)
    }
}

var results = [
    Runner(name: "Mo", seconds: 1_581),
    Runner(name: "Ada", seconds: 1_602),
    Runner(name: "Kip", seconds: 1_581),
    Runner(name: "Zoe", seconds: 1_544),
]
results.sort()
for runner in results {
    print(runner.name, runner.seconds)
}
print(results.min()!.name, results.max()!.name)
print(Runner(name: "Mo", seconds: 1_581) < Runner(name: "Kip", seconds: 1_581))
```

```output
Zoe 1544
Kip 1581
Mo 1581
Ada 1602
Zoe Ada
false
```

What to notice:

- `Comparable` builds on `Equatable`, and Swift writes `==` for you here: two runners are equal when **both** fields match.
- The `<` compares the time **and then the name**. That keeps it consistent with `==`: for any two runners, exactly one of `a < b`, `a == b` or `b < a` is true. If `<` looked only at the time, Kip and Mo would be neither less, nor greater, nor equal, which breaks what `Comparable` promises and can confuse code that relies on it.
- Conform to `Comparable` when your type has one **natural** order, like dates, versions or race times. When different screens need different orders, pass a closure to `sorted(by:)` instead.

## Several keys at once: tuple comparison

Swift compares tuples (of up to six elements) element by element, left to right, like words in a dictionary. That makes multi-key sorting one line: put the most important key first.

```swift run
struct Contact {
    let first: String
    let last: String
}

let contacts = [
    Contact(first: "Ravi", last: "Shah"),
    Contact(first: "Ana", last: "Lima"),
    Contact(first: "Dev", last: "Shah"),
    Contact(first: "Ben", last: "Lima"),
]

// By last name, then first name: tuples compare element by element, left to right
let byName = contacts.sorted { ($0.last, $0.first) < ($1.last, $1.first) }
print(byName.map { "\($0.first) \($0.last)" })

// Last name Z to A, then first name A to Z: swap only the parts that go downwards
let mixed = contacts.sorted { ($1.last, $0.first) < ($0.last, $1.first) }
print(mixed.map { "\($0.first) \($0.last)" })
```

```output
["Ana Lima", "Ben Lima", "Dev Shah", "Ravi Shah"]
["Dev Shah", "Ravi Shah", "Ana Lima", "Ben Lima"]
```

The second sort uses a neat trick for mixed directions: to make one key go **downwards**, swap `$0` and `$1` for that key only. It's compact, but easy to misread. For anything beyond two keys, the explicit `if first.x != second.x { return … }` style from M07 is clearer, and clarity wins.

## Descending order, and why not reversed()

To sort in decreasing order, use `>` (or swap the operands in your closure). Don't sort upwards and call `reversed()`, because reversing also reverses the order of **equal** elements:

```swift run
struct Task {
    let title: String
    let priority: Int
}

let inbox = [
    Task(title: "reply to Sam", priority: 1),
    Task(title: "fix login bug", priority: 3),
    Task(title: "book flights", priority: 1),
    Task(title: "review PR", priority: 3),
    Task(title: "water plants", priority: 2),
]

// Highest priority first. Equal priorities keep their inbox order: the sort is stable.
print(inbox.sorted { $0.priority > $1.priority }.map { $0.title })

// Sorting upwards and then reversing also reverses the order of equal priorities
print(inbox.sorted { $0.priority < $1.priority }.reversed().map { $0.title })
```

```output
["fix login bug", "review PR", "water plants", "reply to Sam", "book flights"]
["review PR", "fix login bug", "water plants", "book flights", "reply to Sam"]
```

The first version keeps "fix login bug" ahead of "review PR", as they were in the inbox. The second swaps them. With a stable sort, `>` gives you a stable descending order; `reversed()` throws that away.

## The rule: a strict weak ordering

Every sort in this module asks the same question over and over: should a come before b? For the answers to make sense together, Swift's documentation requires the closure to be a **strict weak ordering**. In plain words:

1. **Never true for equal elements.** `areInIncreasingOrder(a, a)` must be `false`. This is the "strict" part.
2. **Consistent chains.** If a comes before b, and b before c, then a comes before c.
3. **Consistent ties.** If a and b are tied (neither comes before the other), and b and c are tied, then a and c are tied too.

`<` and `>` obey all three. **`<=` breaks the first rule**: it says every element comes before itself, and that two equal elements each come before the other. Here's what that does on today's Swift:

```swift run
let arrivals = [(priority: 1, id: "a"), (priority: 1, id: "b"), (priority: 1, id: "c"),
                (priority: 0, id: "d"), (priority: 1, id: "e")]

print(arrivals.sorted { $0.priority < $1.priority }.map { $0.id })
print(arrivals.sorted { $0.priority <= $1.priority }.map { $0.id })
```

```output
["d", "a", "b", "c", "e"]
["d", "e", "c", "b", "a"]
```

The numbers still come out in order, so a quick test passes. But with `<=`, the equal elements come out **backwards**. Here's why: Swift's sort looks for runs, and it treats a stretch where each element "comes before" the previous one as a descending run, which it reverses. With `<=`, a stretch of equal elements looks descending, so it gets reversed. Other sort implementations react differently: some lose stability in other ways, and in some languages a bad comparator can even read past the end of the array. The fix is always the same: use `<` (or `>`), never `<=` (or `>=`).

The rule also explains why you need it: three-way partitioning, merging and run detection all decide "equal" by checking that **neither** element comes before the other. A comparator that's true for ties makes "equal" impossible to detect.

<Callout kind="gotcha" title="Comparators that break the rule">
- **`<=` or `>=`** instead of `<` or `>`: true for equal elements.
- **Random or changing answers**, such as `{ _, _ in Bool.random() }` to "shuffle". Use `shuffled()` instead.
- **Inconsistent keys**, like comparing by a value that changes while the sort runs, or a "closeness" rule where a ties with b and b ties with c, but a doesn't tie with c (for example, "times within 5 seconds count as equal").
</Callout>

## What Swift's sort actually does

Swift's `sort()` has changed once, and the change matters:

- **Before Swift 5** (2019), it was an **introsort**: quick sort with a heap sort fallback and insertion sort for small ranges, as in [Random pivots and 3-way partitioning](/dsa/learn/sort-quick-pivots). It was **not stable**.
- **Since Swift 5**, it's a **modified Timsort**: an adaptive merge sort that finds natural runs (reversing descending ones), extends short runs with insertion sort and merges them, the ideas from [Shell sort and Timsort ideas](/dsa/learn/sort-shell-timsort). That's why already-sorted input costs only n − 1 comparisons. Exactly which Timsort tricks it keeps is an implementation detail that can change.
- **Stability:** for several years the new sort was stable in practice but not officially promised. Apple's documentation now states that the sorting algorithm is guaranteed to be stable, so you can rely on it.
- **Cost:** O(n log n) comparisons in the worst case, and it uses temporary memory for merging, so it isn't strictly in place.

Stability is what makes **sorting by two keys in two passes** work: sort by the less important key first, then by the more important one. The second sort keeps the first sort's order among its ties:

```swift run
// Two stable sorts in a row: the second key wins, and the first key breaks its ties
struct Employee {
    let name: String
    let team: String
}

let staff = [
    Employee(name: "Priya", team: "Mobile"),
    Employee(name: "Leo", team: "Web"),
    Employee(name: "Amara", team: "Mobile"),
    Employee(name: "Chen", team: "Web"),
    Employee(name: "Bea", team: "Mobile"),
]

let byName = staff.sorted { $0.name < $1.name }
let byTeamThenName = byName.sorted { $0.team < $1.team }   // stable: names stay A to Z within a team
print(byTeamThenName.map { "\($0.team) \($0.name)" })
```

```output
["Mobile Amara", "Mobile Bea", "Mobile Priya", "Web Chen", "Web Leo"]
```

This is exactly what happens when a user taps one column header in a table and then another: the earlier order survives inside the groups of the new one. A single sort with a tuple key, `($0.team, $0.name) < ($1.team, $1.name)`, gives the same result in one pass.

## Expensive keys: compute them once

The comparison closure runs about n log₂ n times, and it computes the key of **both** elements every time. If computing the key is expensive, such as lowercasing a string, parsing a date or measuring text, that's a lot of repeated work. Count it:

```swift run
// Computing an expensive key inside the comparison repeats the work on every comparison
var keyComputations = 0

func sortKey(_ word: String) -> String {
    keyComputations += 1
    return word.lowercased()
}

let words = (0..<1_000).map { "Word\(($0 * 7_919) % 1_000)" }

let slow = words.sorted { sortKey($0) < sortKey($1) }
print("inside the comparison: \(keyComputations) key computations")

keyComputations = 0
let fast = words
    .map { (key: sortKey($0), word: $0) }    // compute each key once
    .sorted { $0.key < $1.key }
    .map { $0.word }
print("computed once each: \(keyComputations) key computations")
print(slow == fast)
```

```output
inside the comparison: 40658 key computations
computed once each: 1000 key computations
true
```

Pairing each element with its key first, sorting the pairs, then dropping the keys does the expensive part exactly n times. The pattern even has a name, "decorate, sort, undecorate". For cheap keys, like an `Int` property, don't bother: the plain closure is clearer.

## Checking that something is sorted

There's no built-in `isSorted`, but `zip` makes one easy: pair each element with the next one, and check every pair:

```swift run
func isSorted(_ items: [Int]) -> Bool {
    zip(items, items.dropFirst()).allSatisfy { $0 <= $1 }    // every neighbouring pair in order
}

func isSorted<T>(_ items: [T], by areInIncreasingOrder: (T, T) -> Bool) -> Bool {
    !zip(items, items.dropFirst()).contains { areInIncreasingOrder($1, $0) }   // no step down
}

print(isSorted([1, 2, 2, 5]), isSorted([1, 3, 2]), isSorted([]))
print(isSorted(["kiwi", "fig", "banana"]) { $0.count < $1.count })
print(isSorted([9, 7, 7, 1], by: >))
```

```output
true false true
false
true
```

Here `<=` is correct, because this isn't a sort comparator: it's asking "is this pair in order?", and equal neighbours are fine. The generic version takes a sort-style closure and checks that no element should come before the one in front of it. It's O(n), and a handy `assert` in your own sorting code, or in tests.
