## Why it matters

The simple sorts from M30 take about n² steps, which is fine for 100 elements and hopeless for a million. **Merge sort**, described by John von Neumann in 1945, was one of the first sorts to break that barrier, and it still has the strongest guarantees of any common sort: O(n log n) on every input, and **stable**, so equal elements keep their order. Swift's own `sort()` is a merge sort at heart, as you'll see at the end of this module. Merge sort is also how databases sort data too big to fit in memory: sort chunks that fit, then merge the sorted chunks. And it's your first full example of **divide and conquer**, a design you'll use again and again.

## Divide and conquer

Divide and conquer solves a problem in three steps:

1. **Divide** it into smaller problems of the same kind.
2. **Conquer** each smaller problem, by solving it recursively.
3. **Combine** their answers into an answer for the whole.

For sorting: split the array into two halves, sort each half recursively, and combine the two sorted halves into one sorted array. The recursion stops at arrays of 0 or 1 elements, which are already sorted.

Here's the splitting for `[38, 27, 43, 3, 9, 82, 10]`. Each half is split again until only single elements are left:

```text
              [38, 27, 43, 3, 9, 82, 10]
            /                            \
      [38, 27, 43]                 [3, 9, 82, 10]
      /         \                  /            \
   [38]      [27, 43]          [3, 9]        [82, 10]
             /     \           /    \        /     \
          [27]    [43]       [3]    [9]    [82]    [10]
```

Splitting is easy. All the real work is in the combine step: **merging** two sorted arrays into one.

## The merge step

You've merged sorted arrays before, in [Merge sorted arrays](/dsa/learn/arrays-merge-sorted), and sorted linked lists in [Merge two sorted lists](/dsa/learn/ll-merge-sorted). Keep an index into each array. Compare the two front elements, take the smaller, and move that index on. When one array runs out, copy the rest of the other.

```swift run
func merge(_ left: [Int], _ right: [Int]) -> [Int] {
    var merged: [Int] = []
    merged.reserveCapacity(left.count + right.count)
    var i = 0
    var j = 0
    while i < left.count && j < right.count {
        if left[i] <= right[j] {         // a tie takes the left element
            merged.append(left[i])
            i += 1
        } else {
            merged.append(right[j])
            j += 1
        }
    }
    merged += left[i...]                 // one side is used up: copy the rest of the other
    merged += right[j...]
    return merged
}

print(merge([3, 27, 38, 43], [9, 10, 82]))
print(merge([1, 5, 5], [2, 5, 6]))
print(merge([], [4, 7]))
```

```output
[3, 9, 10, 27, 38, 43, 82]
[1, 2, 5, 5, 5, 6]
[4, 7]
```

Every comparison places one element, so merging a total of n elements takes at most n − 1 comparisons: **O(n)**.

### Why `<=` and not `<`

On a tie, the merge takes the element from the **left** array. Elements in the left half started out before elements in the right half, so equal elements come out in their original order. That's what makes merge sort **stable**, a property you met in [Stable, in-place, adaptive and online](/dsa/learn/sort-properties). It matters when you sort records by one field:

```swift run
struct Player {
    let name: String
    let score: Int
}

func merge(_ left: [Player], _ right: [Player]) -> [Player] {
    var merged: [Player] = []
    var i = 0
    var j = 0
    while i < left.count && j < right.count {
        if left[i].score <= right[j].score {
            merged.append(left[i])
            i += 1
        } else {
            merged.append(right[j])
            j += 1
        }
    }
    merged += left[i...]
    merged += right[j...]
    return merged
}

let morning = [Player(name: "Ana", score: 70), Player(name: "Ben", score: 85)]
let evening = [Player(name: "Cleo", score: 70), Player(name: "Dev", score: 90)]
print(merge(morning, evening).map { "\($0.name) \($0.score)" })
```

```output
["Ana 70", "Cleo 70", "Ben 85", "Dev 90"]
```

Ana and Cleo tie on 70. Ana came from the left, so she stays first. With `<` in place of `<=`, the tie would take Cleo first, and the sort would quietly stop being stable. It would still sort the scores correctly, which is why this bug is so easy to miss.

## Top-down merge sort

Now the whole algorithm. Split at the middle, sort each half, merge. This version prints every merge, indented by how deep in the recursion it happens:

```swift run
func merge(_ left: [Int], _ right: [Int]) -> [Int] {
    var merged: [Int] = []
    var i = 0
    var j = 0
    while i < left.count && j < right.count {
        if left[i] <= right[j] {
            merged.append(left[i])
            i += 1
        } else {
            merged.append(right[j])
            j += 1
        }
    }
    merged += left[i...]
    merged += right[j...]
    return merged
}

func mergeSort(_ items: [Int], depth: Int = 0) -> [Int] {
    let indent = String(repeating: "  ", count: depth)
    guard items.count > 1 else {
        return items                          // 0 or 1 elements: already sorted
    }
    let mid = items.count / 2
    let left = mergeSort(Array(items[..<mid]), depth: depth + 1)
    let right = mergeSort(Array(items[mid...]), depth: depth + 1)
    let merged = merge(left, right)
    print("\(indent)\(left) + \(right) → \(merged)")
    return merged
}

print(mergeSort([38, 27, 43, 3, 9, 82, 10]))
```

```output
    [27] + [43] → [27, 43]
  [38] + [27, 43] → [27, 38, 43]
    [3] + [9] → [3, 9]
    [82] + [10] → [10, 82]
  [3, 9] + [10, 82] → [3, 9, 10, 82]
[27, 38, 43] + [3, 9, 10, 82] → [3, 9, 10, 27, 38, 43, 82]
[3, 9, 10, 27, 38, 43, 82]
```

What to notice:

- The merges happen **on the way back up**. The deepest merges come first, and the last merge, at depth 0, combines the two halves of the whole array.
- The left half is completely sorted before the right half starts. That's the call stack at work, exactly as in [The call stack, visualised](/dsa/learn/rec-call-stack).
- `Array(items[..<mid])` turns each slice into a fresh array. That keeps the code simple, but every call allocates new arrays. You'll fix that shortly.

## Why it's O(n log n)

Write the cost as a recurrence, as in [Recurrences: substitution and recursion trees](/dsa/learn/bigo-recurrences): sorting n elements means sorting two halves and merging in O(n), so **T(n) = 2T(n/2) + n**.

Draw the recursion tree. The top level merges n elements. The next level has two merges of n/2 each: n in total. The next has four merges of n/4: n again. Every level does about n work, and halving n until it reaches 1 takes about log₂ n levels. So the total is about **n log₂ n**. The [Master theorem](/dsa/learn/bigo-master-theorem) gives the same answer in one line: a = 2, b = 2 and f(n) = n, the "balanced" case.

Here's the striking part: the splitting never looks at the values. Sorted, reversed or scrambled, the tree has the same shape, so merge sort is O(n log n) in the **best, average and worst case**. Count the comparisons and see:

```swift run
// Comparisons made by top-down merge sort, on three kinds of input
var comparisons = 0

func merge(_ left: [Int], _ right: [Int]) -> [Int] {
    var merged: [Int] = []
    var i = 0
    var j = 0
    while i < left.count && j < right.count {
        comparisons += 1
        if left[i] <= right[j] {
            merged.append(left[i])
            i += 1
        } else {
            merged.append(right[j])
            j += 1
        }
    }
    merged += left[i...]
    merged += right[j...]
    return merged
}

func mergeSort(_ items: [Int]) -> [Int] {
    guard items.count > 1 else { return items }
    let mid = items.count / 2
    return merge(mergeSort(Array(items[..<mid])), mergeSort(Array(items[mid...])))
}

for n in [1_000, 10_000] {
    let ascending = Array(0..<n)
    let descending = Array(ascending.reversed())
    let mixed = (0..<n).map { ($0 * 7_919) % n }
    var line = "n = \(n):"
    for (name, input) in [("sorted", ascending), ("reversed", descending), ("mixed", mixed)] {
        comparisons = 0
        _ = mergeSort(input)
        line += " \(name) \(comparisons)"
    }
    var log2n = 0
    while (1 << log2n) < n { log2n += 1 }
    print(line + ", n × ⌈log₂ n⌉ = \(n * log2n)")
}
```

```output
n = 1000: sorted 4932 reversed 5044 mixed 8415, n × ⌈log₂ n⌉ = 10000
n = 10000: sorted 64608 reversed 69008 mixed 121146, n × ⌈log₂ n⌉ = 140000
```

Every count is within a factor of about two of n log₂ n. Sorted input is cheaper (each merge empties its left half first and then copies the right half without comparing), but it's still O(n log n). Insertion sort, by contrast, needs 999 comparisons on sorted input and 499,500 on reversed input at n = 1,000.

To see what that difference means as n grows, compare the two curves:

```visual growthChart

```

At n = 1,000, n² is a million and n log₂ n is about 10,000. At a million elements, it's 10¹² against 2 × 10⁷: the difference between hours and a blink.

## One shared buffer

The version above is correct and O(n log n), but wasteful. Each call makes two new arrays from slices and a third for the merged result: about 3n small arrays for n elements, each one a trip to the memory allocator, which is slow next to a comparison.

The fix is to sort **index ranges** of one array, as you learnt in [Recursion over arrays with indices](/dsa/learn/rec-arrays), and to make a single scratch buffer, the same size as the array, once at the start. Each merge copies its range into the matching part of the buffer and merges back into the array:

```swift run
// Merge sort on index ranges of one array, with one buffer shared by every merge
func mergeSort(_ items: inout [Int]) {
    var buffer = items                       // made once, the same size as items
    sortRange(&items, &buffer, 0, items.count)
}

/// Sorts items[low..<high]
func sortRange(_ items: inout [Int], _ buffer: inout [Int], _ low: Int, _ high: Int) {
    guard high - low > 1 else { return }
    let mid = low + (high - low) / 2
    sortRange(&items, &buffer, low, mid)
    sortRange(&items, &buffer, mid, high)

    // Copy the two sorted halves into the buffer, then merge them back into items
    for index in low..<high {
        buffer[index] = items[index]
    }
    var left = low
    var right = mid
    for write in low..<high {
        if right == high || (left < mid && buffer[left] <= buffer[right]) {
            items[write] = buffer[left]
            left += 1
        } else {
            items[write] = buffer[right]
            right += 1
        }
    }
}

var numbers = [38, 27, 43, 3, 9, 82, 10]
mergeSort(&numbers)
print(numbers)

var empty: [Int] = []
mergeSort(&empty)
print(empty)
```

```output
[3, 9, 10, 27, 38, 43, 82]
[]
```

What to notice:

- The ranges are **half-open**, `low..<high`, so a range holds `high - low` elements and the base case is "fewer than 2".
- The merge loop writes exactly `high - low` elements. It takes from the left when the right half is used up, **or** when the left half still has elements and its front is `<=` the right's front. The `<=` keeps it stable.
- The extra memory is the buffer, O(n), plus the recursion stack, O(log n) deep. Merge sort is **not in place**: that O(n) buffer is its price. Sorting a linked list avoids it, because merging relinks nodes instead of copying them, as M25 showed.

## Bottom-up merge sort

You can also run merge sort **without recursion**. Every element on its own is a sorted run of width 1. Merge neighbouring runs into sorted runs of width 2, then merge those into runs of width 4, then 8, and so on, until one run covers the whole array:

```swift run
// Bottom-up merge sort: merge runs of width 1, then 2, then 4, … until one run covers everything
func mergeSortBottomUp(_ items: inout [Int]) {
    let n = items.count
    var buffer = items
    var width = 1
    while width < n {
        for low in stride(from: 0, to: n, by: 2 * width) {
            let mid = min(low + width, n)            // the last pair can be short…
            let high = min(low + 2 * width, n)       // …or have no right run at all
            for index in low..<high {
                buffer[index] = items[index]
            }
            var left = low
            var right = mid
            for write in low..<high {
                if right == high || (left < mid && buffer[left] <= buffer[right]) {
                    items[write] = buffer[left]
                    left += 1
                } else {
                    items[write] = buffer[right]
                    right += 1
                }
            }
        }
        print("width \(width): \(items)")
        width *= 2
    }
}

var numbers = [38, 27, 43, 3, 9, 82, 10]
mergeSortBottomUp(&numbers)
```

```output
width 1: [27, 38, 3, 43, 9, 82, 10]
width 2: [3, 27, 38, 43, 9, 10, 82]
width 4: [3, 9, 10, 27, 38, 43, 82]
```

After the width-1 pass, every pair is sorted: `27 38`, `3 43`, `9 82`, and `10` on its own. After width 2, every group of four is sorted. One more pass finishes it. Seven elements need ⌈log₂ 7⌉ = 3 passes, and each pass touches every element once: O(n log n) again, the same tree as the top-down version walked level by level from the leaves.

The `min` calls handle the ragged end. When n isn't a power of two, the last pair of runs can have a short right run, or no right run at all, in which case `mid == high` and the "merge" just copies the left run back.

Step through bottom-up merge sort and watch the runs double in width:

```visual arrayTrace

  items: [38, 27, 43, 3, 9, 82, 10]
```

Top-down or bottom-up? They do the same comparisons in a different order. Top-down is easier to write and to reason about. Bottom-up needs no recursion stack, and it's the natural shape for merging runs that already exist, which is exactly the idea behind Timsort later in this module.

## Where merge sort shines

Merge sort reads its runs **front to back** and writes the output front to back. It never needs to jump around. That makes it the sort of choice whenever jumping around is expensive:

- **Data too big for memory.** To sort a 50 GB log file on a machine with 8 GB of memory, sort 4 GB pieces one at a time and write each to disk as a sorted run. Then merge all the runs in one pass, reading each file in order. Databases and tools like the Unix `sort` command do this, and it's called **external sorting**.
- **Linked lists.** You can't jump to the middle of a list in O(1), which ruins quick sort's partitioning, but merging only ever walks forwards and relinks nodes, so it needs no buffer at all. [Merge two sorted lists](/dsa/learn/ll-merge-sorted) showed exactly this sort.
- **Merging sorted streams.** Combining sorted results from several servers, or several sorted feeds in an app, is the merge step on its own.
- **When ties must keep their order.** Stability is built in, so sorting a table by one column keeps the previous order inside each group of equal values.

<Callout kind="gotcha" title="Merge sort's classic slips">
- **`<` instead of `<=` in the merge.** The output is still sorted, but equal elements can swap places, so the sort is no longer stable.
- **Forgetting the leftovers.** When one side runs out, the rest of the other side must still be copied. Without it, elements vanish.
- **Splitting so one side is empty.** With `mid = low + (high - low) / 2` and the base case `high - low <= 1`, both halves of a range of 2 or more are non-empty. Get either wrong and the recursion never shrinks.
- **Slices keep their indexes.** `items[mid...]` is an `ArraySlice` whose first index is `mid`, not 0. Wrap it in `Array(...)` before indexing from 0, or use index ranges throughout.
</Callout>

## DSAKit's mergeSorted

Your package has a finished version in `dsa-swift/Sources/DSAKit/EfficientSorts.swift`: `mergeSorted(by:)` returns a new, stably sorted array, using one shared buffer. It also hands short ranges to insertion sort, and skips a merge when the two halves are already in order, which makes already-sorted input cost about n comparisons.

```swift
import DSAKit

let words = ["pear", "fig", "plum", "kiwi"]
print(words.mergeSorted { $0.count < $1.count })   // ["fig", "pear", "plum", "kiwi"]
print([5, 2, 9, 1].mergeSorted())                  // [1, 2, 5, 9]
```

"pear", "plum" and "kiwi" all have four letters, and they stay in their original order.
