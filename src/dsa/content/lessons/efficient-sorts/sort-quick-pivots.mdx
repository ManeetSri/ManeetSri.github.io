## Why it matters

Quick sort is only as good as its pivots. With "always the last element", sorted input costs n²/2 comparisons, and an attacker who knows your pivot rule can feed any server that sorts their data an input that makes it crawl. This lesson covers the four fixes real libraries use: **random pivots**, **median-of-three**, **three-way partitioning** for inputs with many duplicates, and **introsort**, the hybrid that turns quick sort's worst case into a guaranteed O(n log n).

## Random pivots

The worst case comes from pivots that are always the smallest or largest element of their range. A fixed rule, like "the last element", lets one particular input trigger that every time. So stop using a fixed rule: pick the pivot at **random** from the range, swap it to the end, and partition as before.

Now no input is bad in advance. Whether a run is slow depends on the coin flips made during the sort, not on the input, so even an adversary who knows your code can't build a slow input. The run time becomes **expected** O(n log n) for **every** input, the kind of promise you met in [Best, average and worst case](/dsa/learn/bigo-cases). An O(n²) run is still possible, but it needs a long streak of terrible pivots, and for large n the chance of that is far smaller than the chance of the computer failing during the sort.

Run blocks must print the same thing every time, so this example uses a tiny seeded generator. In real code you'd write `Int.random(in: low...high)`.

```swift run
// A tiny seeded generator, so this example prints the same thing every run.
// Real code would write Int.random(in: low...high) instead.
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 42)
var comparisons = 0

/// Lomuto partition, after moving the chosen pivot to the end
func partition(_ items: inout [Int], _ low: Int, _ high: Int, pivotIndex: Int) -> Int {
    items.swapAt(pivotIndex, high)
    let pivot = items[high]
    var boundary = low
    for j in low..<high {
        comparisons += 1
        if items[j] < pivot {
            items.swapAt(boundary, j)
            boundary += 1
        }
    }
    items.swapAt(boundary, high)
    return boundary
}

func quickSort(_ items: inout [Int], _ low: Int, _ high: Int, choose: (Int, Int) -> Int) {
    guard low < high else { return }
    let p = partition(&items, low, high, pivotIndex: choose(low, high))
    quickSort(&items, low, p - 1, choose: choose)
    quickSort(&items, p + 1, high, choose: choose)
}

let n = 2_000
let sorted = Array(0..<n)
let mixed = (0..<n).map { ($0 * 7_919) % n }
for (name, input) in [("sorted", sorted), ("mixed", mixed)] {
    var lastPivot = input
    comparisons = 0
    quickSort(&lastPivot, 0, n - 1) { _, high in high }
    let fixed = comparisons

    var randomPivot = input
    comparisons = 0
    quickSort(&randomPivot, 0, n - 1) { low, high in dice.roll(low...high) }
    print("\(name): last-element pivot \(fixed), random pivot \(comparisons)")
}
```

```output
sorted: last-element pivot 1999000, random pivot 23617
mixed: last-element pivot 26834, random pivot 24164
```

The random pivot costs about the same on both inputs. That's the point: it doesn't care what order the data arrives in. The generator itself is a **linear congruential generator**, one multiply and one add per number. It's fine for picking pivots, and useless for anything security-related.

## Median-of-three

Random numbers cost a little time, and some code wants the same steps every run. A popular deterministic alternative is **median-of-three**: look at the first, middle and last elements of the range, and use the middle one of those three values as the pivot.

```swift run
var comparisons = 0

/// The index of the median of items[low], items[mid] and items[high]
func medianOfThree(_ items: [Int], _ low: Int, _ high: Int) -> Int {
    let mid = low + (high - low) / 2
    let a = items[low], b = items[mid], c = items[high]
    if (a <= b) == (b <= c) { return mid }    // b is between a and c
    if (b <= a) == (a <= c) { return low }    // a is between b and c
    return high
}

func partition(_ items: inout [Int], _ low: Int, _ high: Int, pivotIndex: Int) -> Int {
    items.swapAt(pivotIndex, high)
    let pivot = items[high]
    var boundary = low
    for j in low..<high {
        comparisons += 1
        if items[j] < pivot {
            items.swapAt(boundary, j)
            boundary += 1
        }
    }
    items.swapAt(boundary, high)
    return boundary
}

func quickSort(_ items: inout [Int], _ low: Int, _ high: Int) {
    guard low < high else { return }
    let p = partition(&items, low, high, pivotIndex: medianOfThree(items, low, high))
    quickSort(&items, low, p - 1)
    quickSort(&items, p + 1, high)
}

print(medianOfThree([5, 9, 1], 0, 2), medianOfThree([1, 5, 9], 0, 2), medianOfThree([9, 1, 5], 0, 2))

let n = 2_000
for (name, input) in [("sorted", Array(0..<n)), ("reversed", Array((0..<n).reversed())), ("mixed", (0..<n).map { ($0 * 7_919) % n })] {
    var items = input
    comparisons = 0
    quickSort(&items, 0, n - 1)
    print("\(name): \(comparisons) comparisons")
}
```

```output
0 1 2
sorted: 17964 comparisons
reversed: 33670 comparisons
mixed: 22509 comparisons
```

What to notice:

- In each of the three test triples, 5 is the median, and the function returns its index: 0, 1, then 2.
- On sorted input, the middle element **is** the median of the whole range, so every partition splits perfectly. The old worst case has become the best case.
- The median of three samples is also less likely to be extreme on random data than one sample, so partitions are a little more even on average.

Median-of-three is not a guarantee, though. Inputs exist that are built so that the three samples are always among the smallest values, the so-called "median-of-three killers", and they push it back to O(n²). It's a good heuristic, and real libraries combine it with a safety net, as you'll see below.

## Many duplicates break two-way partitions

Partition an array where **every value is equal**. With Lomuto's `<`, nothing is smaller than the pivot, so the pivot lands at the start of the range and the other side gets everything else. That's the worst case again, and no pivot choice can help, because every pivot is the same value. (With `<=` instead, everything is "smaller", and it's the same problem on the other side.)

This isn't an exotic input. Sorting a million orders by status, with five possible statuses, or people by age, means huge runs of equal keys.

## Three-way partitioning

The cure is to stop forcing equal elements onto one side or the other. Partition into **three** parts: smaller than the pivot, **equal** to it, and larger. The equal block is finished: every element in it is in its final place, and neither recursive call looks at it again.

You already know the algorithm. It's the [Dutch national flag](/dsa/learn/tp-dutch-flag) from M21, with "less than", "equal to" and "greater than" the pivot playing the parts of 0, 1 and 2:

```swift run
// Three-way partition around pivot: the Dutch national flag with "less", "equal" and "greater"
func partition3(_ items: inout [Int], _ low: Int, _ high: Int, pivot: Int) -> (lessEnd: Int, greaterStart: Int) {
    var less = low                           // low..<less: smaller than the pivot
    var scan = low                           // less..<scan: equal to it
    var greater = high + 1                   // scan..<greater: not looked at yet
    while scan < greater {                   // greater...high: larger than it
        if items[scan] < pivot {
            items.swapAt(less, scan)
            less += 1
            scan += 1
        } else if items[scan] > pivot {
            greater -= 1
            items.swapAt(scan, greater)      // the element swapped in hasn't been looked at
        } else {
            scan += 1
        }
    }
    return (less, greater)
}

var numbers = [4, 9, 4, 1, 4, 7, 2, 4]
let (lessEnd, greaterStart) = partition3(&numbers, 0, numbers.count - 1, pivot: 4)
print(numbers)
print("smaller:", numbers[..<lessEnd], "equal:", numbers[lessEnd..<greaterStart], "larger:", numbers[greaterStart...])
```

```output
[1, 2, 4, 4, 4, 4, 7, 9]
smaller: [1, 2] equal: [4, 4, 4, 4] larger: [7, 9]
```

Quick sort then recurses only on `low..<lessEnd` and `greaterStart...high`. Compare it with two-way partitioning, counting every comparison (the three-way version can make two per element: "smaller?" and then "larger?"):

```swift run
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 7)
var comparisons = 0

func isLess(_ a: Int, _ b: Int) -> Bool {
    comparisons += 1
    return a < b
}

// Two-way (Lomuto) with a random pivot
func quickSortTwoWay(_ items: inout [Int], _ low: Int, _ high: Int) {
    guard low < high else { return }
    items.swapAt(dice.roll(low...high), high)
    let pivot = items[high]
    var boundary = low
    for j in low..<high where isLess(items[j], pivot) {
        items.swapAt(boundary, j)
        boundary += 1
    }
    items.swapAt(boundary, high)
    quickSortTwoWay(&items, low, boundary - 1)
    quickSortTwoWay(&items, boundary + 1, high)
}

// Three-way with a random pivot: the equal block is finished and never looked at again
func quickSortThreeWay(_ items: inout [Int], _ low: Int, _ high: Int) {
    guard low < high else { return }
    let pivot = items[dice.roll(low...high)]
    var less = low
    var scan = low
    var greater = high + 1
    while scan < greater {
        if isLess(items[scan], pivot) {
            items.swapAt(less, scan)
            less += 1
            scan += 1
        } else if isLess(pivot, items[scan]) {
            greater -= 1
            items.swapAt(scan, greater)
        } else {
            scan += 1
        }
    }
    quickSortThreeWay(&items, low, less - 1)
    quickSortThreeWay(&items, greater, high)
}

let n = 2_000
let inputs = [
    ("all equal", Array(repeating: 5, count: n)),
    ("3 distinct values", (0..<n).map { $0 % 3 }),
    ("all different", (0..<n).map { ($0 * 7_919) % n }),
]
for (name, input) in inputs {
    var a = input
    comparisons = 0
    quickSortTwoWay(&a, 0, n - 1)
    let twoWay = comparisons
    var b = input
    comparisons = 0
    quickSortThreeWay(&b, 0, n - 1)
    print("\(name): two-way \(twoWay), three-way \(comparisons), both sorted: \(a == input.sorted() && b == a)")
}
```

```output
all equal: two-way 1999000, three-way 4000, both sorted: true
3 distinct values: two-way 670330, three-way 5999, both sorted: true
all different: two-way 22564, three-way 37948, both sorted: true
```

What to notice:

- **All equal:** two-way is quadratic even with random pivots. Three-way finishes in a single pass of 2n comparisons: the first pivot's equal block is the whole array.
- **Three distinct values:** three-way needs one partition per distinct value, so k distinct values cost about O(n · k) at most, and with random pivots more like O(n log k).
- **All different:** three-way makes more comparisons, because each element larger than the pivot costs two. That's the trade: a modest cost on distinct data buys immunity to duplicates. Hoare-style partitions (from the last lesson) are a middle way: they stop on elements equal to the pivot and swap them, which splits a run of equal values evenly.

<Callout kind="note" title="Comparing with a closure">
Written with a closure `areInIncreasingOrder` instead of `<`, the three-way test asks two questions: `areInIncreasingOrder(x, pivot)` means "smaller", `areInIncreasingOrder(pivot, x)` means "larger", and if neither is true, x counts as **equal**. That's why sort closures must be strict: if they returned true for equal elements, "equal" could never be detected. The last lesson in this module comes back to this.
</Callout>

## Introsort: the hybrid real libraries use

Random pivots make the worst case unlikely; they don't make it impossible. When a library has to **guarantee** O(n log n), it uses **introsort** ("introspective sort", David Musser, 1997), which watches itself as it runs:

1. Run quick sort, with a good pivot rule such as median-of-three.
2. Count the recursion depth. If it passes about 2 log₂ n, the pivots are going badly: switch that range to **heap sort**, which is O(n log n) in every case. You'll build heaps and heap sort in M39.
3. When a range is small, say 16 elements or fewer, stop recursing and leave it. At the end, one pass of **insertion sort** finishes all the small ranges at once. On nearly sorted data, insertion sort is very fast, and it avoids the overhead of many tiny recursive calls.

In outline (with heap sort and insertion sort written elsewhere):

```swift
func introSort(_ items: inout [Int], _ low: Int, _ high: Int, depthLimit: Int) {
    if high - low < 16 {
        return                               // left for the final insertion sort pass
    }
    if depthLimit == 0 {
        heapSort(&items, low, high)          // too many bad pivots: guaranteed O(n log n)
        return
    }
    let p = partition(&items, low, high, pivotIndex: medianOfThree(items, low, high))
    introSort(&items, low, p - 1, depthLimit: depthLimit - 1)
    introSort(&items, p + 1, high, depthLimit: depthLimit - 1)
}
```

Quick sort does the work almost every time, heap sort is the insurance, and insertion sort tidies up. The result is O(n log n) in the worst case, in place, and as fast as quick sort in practice. C++'s `std::sort` is usually an introsort, and Swift's `sort()` was one until Swift 5, when it switched to a stable merge-based sort (the last lesson of this module has the details). Like quick sort, introsort is not stable.

## DSAKit's quickSort

`dsa-swift/Sources/DSAKit/EfficientSorts.swift` has `quickSort(by:)`, an in-place quick sort that uses everything in this lesson and the last: a random pivot, three-way partitioning, recursion into the smaller side, and insertion sort for ranges of 16 or fewer.

```swift
import DSAKit

var scores = [72, 38, 91, 50, 38]
scores.quickSort(by: >)
print(scores)                                // [91, 72, 50, 38, 38]

var statuses = Array(repeating: 2, count: 200_000)
statuses.quickSort()                         // one pass: every element equals the first pivot
```

Its tests sort 200,000 equal values, and check that all-equal input costs at most 2n comparisons.
