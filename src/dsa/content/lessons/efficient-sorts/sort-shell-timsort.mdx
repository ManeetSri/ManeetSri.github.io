## Why it matters

Insertion sort has a split personality: superb on nearly sorted data, hopeless on scrambled data. This lesson is about two famous ways to keep the good half. **Shell sort** (1959) gives insertion sort long-distance moves, and shows how much a single design choice, the **gap sequence**, can matter. **Timsort** (2002) goes further and builds a whole sort around the order that real data already has. Timsort, or a close variant of it, sorts lists in Python, objects in Java and arrays in Chrome's JavaScript engine, and a modified version of it is inside Swift's `sort()`.

## Shell sort

Insertion sort is slow on scrambled data because it moves elements **one step at a time**. An element that belongs 1,000 places to the left needs 1,000 shifts to get there. Donald Shell's idea: first run insertion sort on elements that are far apart, so elements can travel long distances in few moves, then on elements closer together, and finish with an ordinary insertion sort.

Running insertion sort on elements a **gap** h apart is called **h-sorting**: afterwards every element is ≤ the one h places after it. Here's a 4-sort followed by a 1-sort:

```swift run
// Shell sort: insertion sort on elements gap apart, for shrinking gaps that end with 1
func shellSort(_ items: inout [Int], gaps: [Int]) {
    for gap in gaps where gap < items.count {
        for next in gap..<items.count {
            let value = items[next]
            var slot = next
            while slot >= gap && items[slot - gap] > value {
                items[slot] = items[slot - gap]      // shift the bigger element gap places right
                slot -= gap
            }
            items[slot] = value
        }
        print("gap \(gap): \(items)")
    }
}

var numbers = [62, 83, 18, 53, 7, 17, 95, 86, 47, 69, 25, 28]
shellSort(&numbers, gaps: [4, 1])
```

```output
gap 4: [7, 17, 18, 28, 47, 69, 25, 53, 62, 83, 95, 86]
gap 1: [7, 17, 18, 25, 28, 47, 53, 62, 69, 83, 86, 95]
```

After the 4-sort, the four interleaved sequences (positions 0, 4, 8; then 1, 5, 9; and so on) are each sorted, and the array is **nearly** sorted: 7 jumped from index 4 to index 0 in a single move. The final pass with gap 1 is plain insertion sort, so the result is always correct, and it's fast because there's little left to fix.

Shell sort is in place, needs no recursion and is only a few lines long. It isn't stable: long jumps can carry an element past an equal one.

## Why the gap sequence matters

The last gap must be 1, for correctness. Everything else is up to you, and the choice changes the speed dramatically. Count the comparisons for the same 5,000 numbers with four sequences:

```swift run
// Comparisons made by Shell sort with different gap sequences, on the same 5,000 numbers
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ limit: Int) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return Int((state >> 33) % UInt64(limit))
    }
}

func shellSortComparisons(_ numbers: [Int], gaps: [Int]) -> Int {
    var items = numbers
    var comparisons = 0
    for gap in gaps where gap < items.count {
        for next in gap..<items.count {
            let value = items[next]
            var slot = next
            while slot >= gap {
                comparisons += 1
                if items[slot - gap] <= value { break }
                items[slot] = items[slot - gap]
                slot -= gap
            }
            items[slot] = value
        }
    }
    return comparisons
}

let n = 5_000
var dice = Dice(seed: 1)
let numbers = (0..<n).map { _ in dice.roll(1_000_000) }

let halving = Array(sequence(first: n / 2) { $0 > 1 ? $0 / 2 : nil })     // 2500, 1250, …, 1
var knuth = [1]                                                            // 1, 4, 13, 40, …
while knuth.last! * 3 + 1 < n { knuth.append(knuth.last! * 3 + 1) }
let ciura = [1, 4, 10, 23, 57, 132, 301, 701, 1750]                       // found by experiment

print("gap 1 only (insertion sort):", shellSortComparisons(numbers, gaps: [1]))
print("halving (Shell, 1959):", shellSortComparisons(numbers, gaps: halving))
print("3k + 1 (Knuth):", shellSortComparisons(numbers, gaps: knuth.reversed()))
print("Ciura:", shellSortComparisons(numbers, gaps: ciura.reversed()))
```

```output
gap 1 only (insertion sort): 6267861
halving (Shell, 1959): 115891
3k + 1 (Knuth): 97079
Ciura: 86402
```

Any sensible sequence beats plain insertion sort by a factor of 50 or more here. Among the sequences, the differences look modest on random data, but they matter a great deal on **bad** data. Shell's original halving gaps have a weakness: when n is a power of two, every gap except the last is even, so elements at odd positions are never compared with elements at even positions until the final pass. Put the small values at odd positions and the large ones at even positions, and all the work lands on that final insertion sort:

```swift run
// A bad input for halving gaps: small values at odd positions, large values at even positions
func shellSortComparisons(_ numbers: [Int], gaps: [Int]) -> Int {
    var items = numbers
    var comparisons = 0
    for gap in gaps where gap < items.count {
        for next in gap..<items.count {
            let value = items[next]
            var slot = next
            while slot >= gap {
                comparisons += 1
                if items[slot - gap] <= value { break }
                items[slot] = items[slot - gap]
                slot -= gap
            }
            items[slot] = value
        }
    }
    return comparisons
}

let n = 4_096
let interleaved = (0..<n).map { $0 % 2 == 0 ? n / 2 + $0 / 2 : $0 / 2 }
print(interleaved.prefix(8))

let halving = Array(sequence(first: n / 2) { $0 > 1 ? $0 / 2 : nil })
var knuth = [1]
while knuth.last! * 3 + 1 < n { knuth.append(knuth.last! * 3 + 1) }
print("halving:", shellSortComparisons(interleaved, gaps: halving))
print("3k + 1:", shellSortComparisons(interleaved, gaps: knuth.reversed()))
```

```output
[2048, 0, 2049, 1, 2050, 2, 2051, 3]
halving: 2143232
3k + 1: 45536
```

The halving gaps degrade to O(n²): over 2 million comparisons for 4,096 values, almost all in the last pass. Knuth's sequence 1, 4, 13, 40, …, where each gap is 3 × the previous + 1, mixes odd and even positions early and needs 47 times fewer. It's proven to be O(n^1.5) in the worst case. Marcin Ciura's 2001 sequence was found by computer experiments and is among the best known in practice. Remarkably, no one knows the exact average-case complexity of Shell sort with the best sequences: it's still an open problem.

Shell sort has been overtaken by the O(n log n) sorts for large inputs, but its tiny code and lack of recursion keep it useful where memory and code size are tight.

## Timsort's ideas

Tim Peters designed Timsort for Python in 2002, starting from an observation about real data rather than random data: **it's usually partly sorted already**.

### Real data has runs

A **natural run** is a stretch that's already in order. Real data is full of them: a log sorted by time with today's entries appended, a sorted list that had a few items edited, two sorted lists concatenated, data that was sorted by a related key:

```swift run
// Natural runs: stretches that are already in non-decreasing order
func runs(_ items: [Int]) -> [Int] {
    guard !items.isEmpty else { return [] }
    var lengths: [Int] = []
    var start = 0
    for i in 1...items.count where i == items.count || items[i] < items[i - 1] {
        lengths.append(i - start)            // the run ends before a step down
        start = i
    }
    return lengths
}

let yesterday = Array(stride(from: 10, through: 100, by: 10))
let appended = yesterday + [35, 90, 5]                       // a sorted list plus new arrivals
let twoFeeds = [3, 8, 15, 21, 40] + [1, 9, 12, 30, 33, 41]    // two sorted lists end to end
let scrambled = [42, 7, 19, 88, 3, 56, 23, 71, 12, 64]

print(runs(appended))
print(runs(twoFeeds))
print(runs(scrambled))
```

```output
[10, 2, 1]
[5, 6]
[1, 3, 2, 2, 2]
```

The first two inputs are a handful of long runs, and merging a few long runs is cheap: two sorted runs of any length merge in one linear pass. Only truly scrambled data is made of runs of length 1 or 2. Classic merge sort ignores all this and splits at the middle regardless; Timsort is built on it. It's an example of an **adaptive** sort, as defined in [Stable, in-place, adaptive and online](/dsa/learn/sort-properties): the more order the input has, the less work it does.

Timsort works like this:

1. **Find the runs.** Scan from the left. A run is either non-decreasing, or **strictly** decreasing, in which case Timsort reverses it in place. (Strictly, so that reversing never swaps two equal elements: the sort stays stable.)
2. **Make short runs longer.** If a run is shorter than a **minimum run length** (between 32 and 64, chosen from n), extend it to that length with **insertion sort**, the best algorithm for short pieces. On scrambled data, this turns the input into sorted chunks of about 32 to 64 elements.
3. **Merge runs on a stack.** Each new run is pushed on a stack. Rules about the lengths of the top three runs decide when to merge, so that runs of **similar size** get merged together. That keeps the merges balanced, like the levels of merge sort's tree, and guarantees O(n log n) overall.
4. **Gallop when one run is winning.** During a merge, if one run supplies many elements in a row, Timsort switches to **galloping**: it checks 1, 3, 7, 15, … places ahead, an exponential search like the one in [Exponential, jump, interpolation and ternary search](/dsa/learn/bs-other-searches), to find how far the winning streak goes, then copies that whole block at once. Merging two runs that barely overlap then costs far fewer comparisons.

### Why it pays off

Swift's `sort()` is built on the same ideas (more on that in the next lesson). Count its comparisons on data arranged in different ways:

```swift run
// Comparisons Swift's own sort makes on 10,000 values arranged in different ways
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ limit: Int) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return Int((state >> 33) % UInt64(limit))
    }
}

func comparisonsToSort(_ numbers: [Int]) -> Int {
    var comparisons = 0
    _ = numbers.sorted { a, b in
        comparisons += 1
        return a < b
    }
    return comparisons
}

let n = 10_000
var dice = Dice(seed: 4)
let sorted = Array(0..<n)
let inputs = [
    ("sorted", sorted),
    ("sorted, then 10 new values", Array(sorted.dropLast(10)) + (0..<10).map { _ in dice.roll(n) }),
    ("4 sorted blocks", (0..<n).map { ($0 % 2_500) * 4 + $0 / 2_500 }),
    ("reversed", Array(sorted.reversed())),
    ("random", (0..<n).map { _ in dice.roll(n) }),
]
for (name, input) in inputs {
    print("\(name): \(comparisonsToSort(input))")
}
```

```output
sorted: 9999
sorted, then 10 new values: 19993
4 sorted blocks: 29995
reversed: 9999
random: 185632
```

Sorted and reversed input cost n − 1 comparisons: one run, found in a single scan (the reversed one is reversed in place). Four sorted blocks cost about 3n: n to find the runs, then two levels of merging. Appending 10 values costs about 2n. Only random data pays the full n log n price, about 18.6 comparisons per element here. Those exact counts are details of today's standard library, but the shape is the point: work in proportion to the disorder.

<Callout kind="note" title="Stable, adaptive and O(n log n), with a price">
Timsort is stable (it only merges neighbouring runs, and its merges prefer the left run on ties), adaptive, and O(n log n) in the worst case. Its price is complexity, a few hundred lines in most implementations, and an O(n) temporary buffer for merging. Getting the stack rules exactly right is subtle: in 2015, researchers using formal verification found a case where the original rules didn't guarantee the balance they were meant to, and the implementations in Python and Java were patched.
</Callout>
