## Why it matters

How far from sorted is an array? One good answer is its number of **inversions**: pairs that are in the wrong order. The count tells you exactly how much work insertion sort will do, and it measures how much two rankings disagree, which is how music and film apps compare people's tastes, and how search engines compare two orderings of results. Counting inversions is also a classic interview question with a satisfying answer: merge sort, with one extra line.

## What an inversion is

An **inversion** is a pair of positions i < j where the earlier value is bigger: `numbers[i] > numbers[j]`. Equal values aren't an inversion: they're not out of order.

```swift run
func inversions(_ numbers: [Int]) -> [(Int, Int)] {
    var pairs: [(Int, Int)] = []
    for i in numbers.indices {
        for j in (i + 1)..<numbers.count where numbers[i] > numbers[j] {
            pairs.append((numbers[i], numbers[j]))
        }
    }
    return pairs
}

for numbers in [[2, 4, 1, 3, 5], [1, 2, 3, 4], [4, 3, 2, 1], [3, 1, 3, 2]] {
    let pairs = inversions(numbers)
    let shown = pairs.map { "(\($0.0), \($0.1))" }.joined(separator: " ")
    print(numbers, pairs.count, shown.isEmpty ? "none" : shown)
}
```

```output
[2, 4, 1, 3, 5] 3 (2, 1) (4, 1) (4, 3)
[1, 2, 3, 4] 0 none
[4, 3, 2, 1] 6 (4, 3) (4, 2) (4, 1) (3, 2) (3, 1) (2, 1)
[3, 1, 3, 2] 3 (3, 1) (3, 2) (3, 2)
```

What to notice:

- A sorted array has **0** inversions.
- A reversed array has an inversion for **every** pair: n(n − 1)/2 of them, the most possible. For 4 elements that's 6, as you counted in [Factorials, permutations and combinations](/dsa/learn/math-counting).
- In `[3, 1, 3, 2]`, the two 3s don't form an inversion with each other, but each 3 that comes before the 2 does.

So the count runs from 0 (sorted) to n(n − 1)/2 (reversed). It's a ruler for "how unsorted".

## What the count tells you

### Insertion sort's work

[Insertion sort](/dsa/learn/sort-insertion) moves each element left, one step at a time, past every bigger element before it. Each step swaps an adjacent pair that was out of order, which removes **exactly one** inversion and creates none. Insertion sort stops when there are no inversions left, so its number of shifts **equals** the number of inversions:

```swift run
// Insertion sort shifts each element left past every bigger element before it.
// Each shift fixes exactly one inversion, so shifts = inversions.
func insertionSortShifts(_ numbers: [Int]) -> Int {
    var items = numbers
    var shifts = 0
    for next in 1..<items.count {
        let value = items[next]
        var slot = next
        while slot > 0 && items[slot - 1] > value {
            items[slot] = items[slot - 1]
            slot -= 1
            shifts += 1
        }
        items[slot] = value
    }
    return shifts
}

func bruteForceInversions(_ numbers: [Int]) -> Int {
    var count = 0
    for i in numbers.indices {
        for j in (i + 1)..<numbers.count where numbers[i] > numbers[j] {
            count += 1
        }
    }
    return count
}

for numbers in [[2, 4, 1, 3, 5], [5, 4, 3, 2, 1], [1, 2, 3, 5, 4], [3, 1, 3, 2]] {
    print(numbers, "shifts \(insertionSortShifts(numbers)), inversions \(bruteForceInversions(numbers))")
}
```

```output
[2, 4, 1, 3, 5] shifts 3, inversions 3
[5, 4, 3, 2, 1] shifts 10, inversions 10
[1, 2, 3, 5, 4] shifts 1, inversions 1
[3, 1, 3, 2] shifts 3, inversions 3
```

That explains why insertion sort is fast on nearly sorted data: few inversions, few shifts. Bubble sort's swaps equal the inversion count too. More generally, **any** sort that only swaps neighbours needs at least as many swaps as there are inversions, which is why such sorts are O(n²) on average: a random array has about n(n − 1)/4 inversions.

### How much two rankings agree

Ana and Ben each rank the same five films. To compare them, write Ben's list using Ana's positions. If they agreed completely, the result would be sorted; every inversion is a pair of films they order differently:

```swift run
// Two people rank the same five films, 1 being their favourite
let films = ["Arrival", "Brave", "Coco", "Dune", "Elf"]
let ana = ["Coco", "Arrival", "Dune", "Brave", "Elf"]
let ben = ["Arrival", "Coco", "Brave", "Elf", "Dune"]

// Write Ben's list using Ana's positions: where does each of Ben's films sit in Ana's ranking?
var anaPosition: [String: Int] = [:]
for (position, film) in ana.enumerated() {
    anaPosition[film] = position
}
let relabelled = ben.map { anaPosition[$0]! }
print(relabelled)

var disagreements = 0
for i in relabelled.indices {
    for j in (i + 1)..<relabelled.count where relabelled[i] > relabelled[j] {
        disagreements += 1
    }
}
let pairs = films.count * (films.count - 1) / 2
print("They disagree on \(disagreements) of \(pairs) pairs")
```

```output
[1, 0, 3, 4, 2]
They disagree on 3 of 10 pairs
```

They disagree about Arrival versus Coco, Brave versus Dune, and Elf versus Dune. This count is called the **Kendall tau distance**. Recommendation systems use it, and statistics uses a version of it to measure how strongly two rankings are related.

## The brute force is O(n²)

The nested loops check every pair: n(n − 1)/2 comparisons. For 100,000 elements, that's about 5 billion. You can do much better.

## Counting while merging

Split the array into a left half and a right half. Every inversion is one of three kinds:

1. both elements in the **left** half;
2. both in the **right** half;
3. **across**: a bigger element in the left half, a smaller one in the right.

The first two kinds are the same problem on smaller arrays: count them recursively. That leaves the across pairs, and here's the key observation: **sorting each half doesn't change how many across pairs there are**. Sorting only reorders elements within a half, and "this left element is bigger than that right element" doesn't depend on where they sit inside their halves.

So sort both halves, recursively, while counting. Then count the across pairs while you merge. When the merge takes an element from the **right** half, that element is smaller than every element still waiting in the left half: they're sorted, and the merge took the right one because it was smaller than the left's front. Each of those waiting elements forms one across inversion with it. There are `mid - left` of them, so add that in one step:

```swift run
// Count inversions while merge sorting, and show each merge's "across" count
func sortAndCount(_ items: inout [Int], _ buffer: inout [Int], _ low: Int, _ high: Int) -> Int {
    guard high - low > 1 else { return 0 }
    let mid = low + (high - low) / 2
    var inversions = sortAndCount(&items, &buffer, low, mid) + sortAndCount(&items, &buffer, mid, high)
    for index in low..<high {
        buffer[index] = items[index]
    }
    var across = 0
    var left = low
    var right = mid
    for write in low..<high {
        if right == high || (left < mid && buffer[left] <= buffer[right]) {
            items[write] = buffer[left]
            left += 1
        } else {
            items[write] = buffer[right]
            right += 1
            across += mid - left             // it jumps ahead of everything left in the left half
        }
    }
    print("merge \(Array(buffer[low..<mid])) + \(Array(buffer[mid..<high])): \(across) across")
    inversions += across
    return inversions
}

func countInversions(_ numbers: [Int]) -> Int {
    var items = numbers
    var buffer = numbers
    return sortAndCount(&items, &buffer, 0, items.count)
}

print("total:", countInversions([5, 2, 6, 1, 3, 4]))
```

```output
merge [2] + [6]: 0 across
merge [5] + [2, 6]: 1 across
merge [3] + [4]: 0 across
merge [1] + [3, 4]: 0 across
merge [2, 5, 6] + [1, 3, 4]: 7 across
total: 8
```

Look at the last merge. When 1 is taken from the right, all three of 2, 5 and 6 are waiting on the left: 3 inversions. Next, 2 is taken from the left (no count). Then 3 is taken from the right with 5 and 6 still waiting: 2 more. Then 4, also behind 5 and 6: 2 more. That's 7. Together with (5, 2) from a smaller merge, the total is 8.

<Callout kind="gotcha" title="Ties must take the left element">
The merge must use `<=`, exactly as stable merge sort does. If a tie took the right element, the equal elements waiting on the left would be counted as inversions, and `[2, 2]` would report 1 instead of 0.
</Callout>

## Why it's O(n log n)

The counting adds one subtraction to each step of the merge, so the work is exactly merge sort's: **O(n log n)** time and O(n) extra space. Compare the number of comparisons:

```swift run
// Operations to count inversions: every pair vs merge sort
func bruteForceComparisons(_ n: Int) -> Int {
    n * (n - 1) / 2                          // the loops check every pair once
}

func mergeComparisons(_ numbers: [Int]) -> Int {
    var items = numbers
    var buffer = numbers
    var comparisons = 0
    func sortRange(_ low: Int, _ high: Int) {
        guard high - low > 1 else { return }
        let mid = low + (high - low) / 2
        sortRange(low, mid)
        sortRange(mid, high)
        for index in low..<high { buffer[index] = items[index] }
        var left = low
        var right = mid
        for write in low..<high {
            if right < high && left < mid { comparisons += 1 }
            if right == high || (left < mid && buffer[left] <= buffer[right]) {
                items[write] = buffer[left]
                left += 1
            } else {
                items[write] = buffer[right]
                right += 1
            }
        }
    }
    sortRange(0, items.count)
    return comparisons
}

for n in [1_000, 10_000, 100_000] {
    let mixed = (0..<n).map { ($0 * 7_919) % n }
    print("n = \(n): every pair \(bruteForceComparisons(n)), merge sort \(mergeComparisons(mixed))")
}
```

```output
n = 1000: every pair 499500, merge sort 8415
n = 10000: every pair 49995000, merge sort 121146
n = 100000: every pair 4999950000, merge sort 1493143
```

At 100,000 elements, merge sort makes about 3,300 times fewer comparisons.

Notice that a single merge can add a huge count in one step: the algorithm counts inversions **without listing them**. Listing them would take time proportional to the count itself, which can be n²/2. Counting is cheaper than listing.

## Watch the size of the answer

The count can reach n(n − 1)/2. For 100,000 elements:

```swift run
let n = 100_000
let mostInversions = n * (n - 1) / 2
print(mostInversions)
print(Int32.max)
print(Int.max)
```

```output
4999950000
2147483647
9223372036854775807
```

Nearly 5 billion doesn't fit in an `Int32`, whose largest value is about 2.1 billion. Swift's `Int` is 64 bits on every Apple platform, so it has room to spare, and if a count ever did overflow, Swift would stop the program instead of quietly wrapping round, as [Overflow traps and overflow operators](/dsa/learn/swift-overflow) showed. In languages where integers are 32 bits by default, this is the bug that sinks most first attempts. Always estimate the largest possible answer before choosing a type.

**Count the inversions** is this lesson's algorithm, with 100,000-element tests that the brute force can't finish quickly. **Lopsided pairs** counts pairs where the earlier value is more than **twice** the later one. The merge alone can't count those, so you'll add a separate two-pointer pass before each merge.
