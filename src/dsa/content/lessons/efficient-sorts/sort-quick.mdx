## Why it matters

**Quick sort** is the other great O(n log n) sort, and for decades it was the one inside most standard libraries: C++'s `std::sort` is built on it, and so was Swift's own `sort()` before Swift 5. It sorts **in place**, with no buffer, and its inner loop is a tight scan through memory that processors handle very fast. Its central step, **partitioning** an array around a pivot, is worth knowing for its own sake: it powers quickselect later in this module, and it's a close relative of the Dutch national flag from M21. Quick sort also has a famous weakness, and understanding it is half of understanding quick sort.

## The idea: partition, then recurse

Pick one element, the **pivot**. Rearrange the array so that everything smaller than the pivot comes before it, and everything else comes after it. Now the pivot is exactly where it belongs in the sorted array: it never needs to move again. Sort the part before it and the part after it, recursively, and you're done.

Compare it with merge sort:

| | Merge sort | Quick sort |
| --- | --- | --- |
| The hard work | combining (merging) | dividing (partitioning) |
| When it happens | after the recursive calls | before the recursive calls |
| The split | always in the middle | wherever the pivot lands |
| Extra memory | an O(n) buffer | none besides the call stack |

There's no combine step at all. Once both sides are sorted, the whole range is sorted, because every element on the left is smaller than every element on the right.

## Lomuto partitioning

The simplest way to partition is named after Nico Lomuto. It takes the **last** element as the pivot and scans the range once, keeping three regions:

| Range | Holds |
| --- | --- |
| `low..<boundary` | elements smaller than the pivot |
| `boundary..<j` | elements greater than or equal to the pivot |
| `j..<high` | not looked at yet |
| `high` | the pivot |

When `items[j]` is smaller than the pivot, swap it to `boundary`, the first element of the "bigger" region, and move the boundary on. Otherwise leave it. At the end, swap the pivot into `boundary`, between the regions:

```swift run
// Lomuto partition: the pivot is the last element of items[low...high]
func lomutoPartition(_ items: inout [Int], _ low: Int, _ high: Int) -> Int {
    let pivot = items[high]
    var boundary = low                       // low..<boundary: smaller than the pivot
    for j in low..<high {
        if items[j] < pivot {
            items.swapAt(boundary, j)
            boundary += 1
        }
    }
    items.swapAt(boundary, high)             // the pivot goes between the two sides
    return boundary
}

var numbers = [7, 2, 9, 4, 3, 8, 5]
let p = lomutoPartition(&numbers, 0, numbers.count - 1)
print(numbers, "pivot at index \(p)")
print("smaller:", numbers[..<p], "bigger or equal:", numbers[(p + 1)...])
```

```output
[2, 4, 3, 5, 9, 8, 7] pivot at index 3
smaller: [2, 4, 3] bigger or equal: [9, 8, 7]
```

The pivot 5 lands at index 3, its final position: three elements are smaller than it. Neither side is sorted yet, and that's fine. Partitioning is one pass, n − 1 comparisons for n elements: **O(n)**.

## Quick sort with Lomuto

Quick sort partitions the range, then sorts each side. With closed ranges `low...high`, the sides are `low...(p - 1)` and `(p + 1)...high`, leaving out the pivot, which is already in place:

```swift run
func lomutoPartition(_ items: inout [Int], _ low: Int, _ high: Int) -> Int {
    let pivot = items[high]
    var boundary = low
    for j in low..<high where items[j] < pivot {
        items.swapAt(boundary, j)
        boundary += 1
    }
    items.swapAt(boundary, high)
    return boundary
}

/// Sorts items[low...high], a closed range
func quickSort(_ items: inout [Int], _ low: Int, _ high: Int, depth: Int = 0) {
    guard low < high else { return }         // 0 or 1 elements
    let p = lomutoPartition(&items, low, high)
    let indent = String(repeating: "  ", count: depth)
    print("\(indent)\(low)...\(high) around \(items[p]): \(items[low...high])")
    quickSort(&items, low, p - 1, depth: depth + 1)
    quickSort(&items, p + 1, high, depth: depth + 1)
}

var numbers = [7, 2, 9, 4, 3, 8, 5]
quickSort(&numbers, 0, numbers.count - 1)
print(numbers)
```

```output
0...6 around 5: [2, 4, 3, 5, 9, 8, 7]
  0...2 around 3: [2, 3, 4]
  4...6 around 7: [7, 8, 9]
    5...6 around 9: [8, 9]
[2, 3, 4, 5, 7, 8, 9]
```

What to notice:

- Each partition fixes one pivot for good: 5, then 3, then 7, then 9. Ranges of 0 or 1 elements stop at the `guard`.
- `guard low < high` also handles an empty array: the first call is `quickSort(&items, 0, -1)`, and the guard returns at once.
- In "4...6 around 7", nothing is smaller than 7, so the pivot lands at the start of its range and the left side is empty. Keep that picture in mind: it's the seed of quick sort's worst case.

## Hoare partitioning

Tony Hoare, who invented quick sort in 1959, partitioned differently. Two indexes start at the ends and move **towards each other**. The left one stops at an element that belongs on the right (≥ pivot); the right one stops at an element that belongs on the left (≤ pivot). Swap those two, and carry on. When the indexes meet or cross, the range is split.

```swift run
// Hoare partition of items[low...high]. Returns a split index s: afterwards every element in
// low...s is ≤ pivot and every element in (s + 1)...high is ≥ pivot. The pivot needn't be at s.
func hoarePartition(_ items: inout [Int], _ low: Int, _ high: Int) -> Int {
    let pivot = items[low + (high - low) / 2]    // the middle element (rounding down)
    var i = low - 1
    var j = high + 1
    while true {
        repeat { i += 1 } while items[i] < pivot   // find an element that belongs on the right
        repeat { j -= 1 } while items[j] > pivot   // find an element that belongs on the left
        if i >= j { return j }                     // the scans have met: done
        items.swapAt(i, j)
    }
}

var numbers = [3, 9, 5, 1, 7, 2]
let split = hoarePartition(&numbers, 0, numbers.count - 1)
print(numbers, "split at \(split)")
print("left:", numbers[...split], "right:", numbers[(split + 1)...])
```

```output
[3, 2, 1, 5, 7, 9] split at 2
left: [3, 2, 1] right: [5, 7, 9]
```

The pivot is 5, the middle element. First 9 and 2 swap, then 5 and 1. The scans cross with `j` at 2, so the split is after index 2: everything up to it is ≤ 5, and everything after is ≥ 5.

Step through the two scans:

```visual arrayTrace

  items: [3, 9, 5, 1, 7, 2]
```

`repeat { … } while` runs its body **once** before checking the condition, so each scan always moves at least one step. That's what stops the loop from swapping the same pair forever when both elements equal the pivot.

### The recursion ranges are different

Here's the trap. Hoare's partition returns a **split point**, not the pivot's position. In the example, the pivot 5 ended up at index **3**, on the right of the split, not at index 2. Hoare's partition doesn't put the pivot in its final place, so the recursion must include index `split` in the left part:

```swift
/// Sorts items[low...high]
func quickSort(_ items: inout [Int], _ low: Int, _ high: Int) {
    guard low < high else { return }
    let split = hoarePartition(&items, low, high)
    quickSort(&items, low, split)            // split, not split - 1: the pivot isn't fixed in place
    quickSort(&items, split + 1, high)
}
```

Mix the two schemes up and it breaks in one of two ways:

- Recursing on `low...(split - 1)` and `(split + 1)...high`, Lomuto-style, **skips** the element at `split`, which may not be in its place yet. The output is wrong.
- Using Hoare's ranges with a pivot chosen as the **last** element can return `split == high`, so the left call gets the whole range again and recurses forever. That's why this version picks the middle element, rounding down: then the split is always strictly less than `high`.

### Why bother with Hoare?

It does far fewer swaps. Lomuto swaps every smaller element, even ones already on the correct side; Hoare only swaps pairs that are both on the wrong side. Sorting the same 10,000 numbers with each:

```swift run
// Swaps made by Lomuto and Hoare partitioning while quick sorting the same input
var swaps = 0

func lomutoPartition(_ items: inout [Int], _ low: Int, _ high: Int) -> Int {
    let pivot = items[high]
    var boundary = low
    for j in low..<high where items[j] < pivot {
        items.swapAt(boundary, j)
        swaps += 1
        boundary += 1
    }
    items.swapAt(boundary, high)
    swaps += 1
    return boundary
}

func hoarePartition(_ items: inout [Int], _ low: Int, _ high: Int) -> Int {
    let pivot = items[low + (high - low) / 2]
    var i = low - 1
    var j = high + 1
    while true {
        repeat { i += 1 } while items[i] < pivot
        repeat { j -= 1 } while items[j] > pivot
        if i >= j { return j }
        items.swapAt(i, j)
        swaps += 1
    }
}

func lomutoSort(_ items: inout [Int], _ low: Int, _ high: Int) {
    guard low < high else { return }
    let p = lomutoPartition(&items, low, high)
    lomutoSort(&items, low, p - 1)
    lomutoSort(&items, p + 1, high)
}

func hoareSort(_ items: inout [Int], _ low: Int, _ high: Int) {
    guard low < high else { return }
    let split = hoarePartition(&items, low, high)
    hoareSort(&items, low, split)
    hoareSort(&items, split + 1, high)
}

let mixed = (0..<10_000).map { ($0 * 7_919) % 10_000 }
var a = mixed
swaps = 0
lomutoSort(&a, 0, a.count - 1)
print("Lomuto: \(swaps) swaps")
var b = mixed
swaps = 0
hoareSort(&b, 0, b.count - 1)
print("Hoare: \(swaps) swaps")
print(a == b, a == mixed.sorted())
```

```output
Lomuto: 81904 swaps
Hoare: 31157 swaps
true true
```

Both sort correctly, and Hoare does well under half the swaps. Lomuto is easier to get right, which is why textbooks (and this module's visualiser) use it; production code tends to use Hoare-style scans from both ends.

## In place, but not stable

Quick sort needs no buffer: it only swaps elements within the array. Its extra memory is the call stack, which you'll come to in a moment.

The long-distance swaps have a cost, though: quick sort is **not stable**. Equal elements can jump past each other:

```swift run
// Quick sort isn't stable: watch two cards with the same rank
struct Card {
    let rank: Int
    let suit: String
}

func partition(_ items: inout [Card], _ low: Int, _ high: Int) -> Int {
    let pivot = items[high].rank
    var boundary = low
    for j in low..<high where items[j].rank < pivot {
        items.swapAt(boundary, j)
        boundary += 1
    }
    items.swapAt(boundary, high)
    return boundary
}

func quickSort(_ items: inout [Card], _ low: Int, _ high: Int) {
    guard low < high else { return }
    let p = partition(&items, low, high)
    quickSort(&items, low, p - 1)
    quickSort(&items, p + 1, high)
}

var hand = [Card(rank: 7, suit: "♠"), Card(rank: 7, suit: "♥"), Card(rank: 9, suit: "♣")]
quickSort(&hand, 0, hand.count - 1)
print(hand.map { "\($0.rank)\($0.suit)" })
```

```output
["7♥", "7♠", "9♣"]
```

7♠ came first, but 7♥ was the pivot of the range `0...1`, and partitioning swapped it to the front. When you need stability, use merge sort, or Swift's `sort()`, which is stable.

## The best, average and worst cases

Each partition costs O(n) for its range. What decides the total is **where the pivot lands**.

- **Best case:** every pivot lands in the middle. The ranges halve, just like merge sort: about log₂ n levels of O(n) work, **O(n log n)**.
- **Worst case:** every pivot is the smallest or largest element of its range. One side is empty and the other has everything else, so the ranges shrink by only one each time: n + (n − 1) + (n − 2) + … ≈ n²/2. **O(n²)**.
- **Average case:** over all possible orders of the input, pivots land "somewhere reasonable" most of the time, and the total is **O(n log n)**, about 1.39 n log₂ n comparisons.

With "the last element" as the pivot, the worst case is an **already sorted** array: the last element is always the largest. Sorted input is not rare. It's what you get when you sort something twice, or add one item to a sorted list and sort again. Count the work:

```swift run
// Quick sort with a fixed pivot (the last element): comparisons and recursion depth
var comparisons = 0
var deepest = 0

func partition(_ items: inout [Int], _ low: Int, _ high: Int) -> Int {
    let pivot = items[high]
    var boundary = low
    for j in low..<high {
        comparisons += 1
        if items[j] < pivot {
            items.swapAt(boundary, j)
            boundary += 1
        }
    }
    items.swapAt(boundary, high)
    return boundary
}

func quickSort(_ items: inout [Int], _ low: Int, _ high: Int, depth: Int) {
    deepest = max(deepest, depth)
    guard low < high else { return }
    let p = partition(&items, low, high)
    quickSort(&items, low, p - 1, depth: depth + 1)
    quickSort(&items, p + 1, high, depth: depth + 1)
}

let n = 2_000
let inputs = [
    ("mixed", (0..<n).map { ($0 * 7_919) % n }),
    ("sorted", Array(0..<n)),
    ("reversed", Array((0..<n).reversed())),
]
for (name, input) in inputs {
    var items = input
    comparisons = 0
    deepest = 0
    quickSort(&items, 0, items.count - 1, depth: 1)
    print("\(name): \(comparisons) comparisons, recursion depth \(deepest)")
}
```

```output
mixed: 26834 comparisons, recursion depth 26
sorted: 1999000 comparisons, recursion depth 2000
reversed: 1999000 comparisons, recursion depth 2000
```

Sorted and reversed input each take n(n − 1)/2 = 1,999,000 comparisons, about 75 times more than the mixed input. Worse, the recursion goes **2,000 calls deep**, one level per element. The next lesson fixes the pivot choice. First, the depth.

## Recursion depth: recurse into the smaller side

Every unfinished call holds a frame on the call stack, and as [Stack depth limits in Swift](/dsa/learn/rec-stack-limits) showed, the stack is limited. With a bad pivot, the depth equals n: sorting 1,000,000 already-sorted elements this way would crash with a stack overflow long before the O(n²) time became the problem.

The fix is a classic trick. After partitioning, **recurse into the smaller side** and handle the larger side with a loop instead of a second call. Each recursive call gets at most half of its parent's range, so the depth can never exceed log₂ n, whatever the pivots do:

```swift run
// Recurse into the smaller side, loop on the larger: the depth stays O(log n)
var deepest = 0

func partition(_ items: inout [Int], _ low: Int, _ high: Int) -> Int {
    let pivot = items[high]
    var boundary = low
    for j in low..<high where items[j] < pivot {
        items.swapAt(boundary, j)
        boundary += 1
    }
    items.swapAt(boundary, high)
    return boundary
}

func quickSort(_ items: inout [Int], _ low: Int, _ high: Int, depth: Int = 1) {
    deepest = max(deepest, depth)
    var low = low
    var high = high
    while low < high {
        let p = partition(&items, low, high)
        if p - low < high - p {
            quickSort(&items, low, p - 1, depth: depth + 1)    // the smaller side: recurse
            low = p + 1                                        // the larger side: loop
        } else {
            quickSort(&items, p + 1, high, depth: depth + 1)
            high = p - 1
        }
    }
}

let n = 2_000
for (name, input) in [("mixed", (0..<n).map { ($0 * 7_919) % n }), ("sorted", Array(0..<n))] {
    var items = input
    deepest = 0
    quickSort(&items, 0, items.count - 1)
    print("\(name): recursion depth \(deepest), sorted correctly: \(items == input.sorted())")
}
```

```output
mixed: recursion depth 8, sorted correctly: true
sorted: recursion depth 2, sorted correctly: true
```

On sorted input the smaller side is always empty, so the depth stays at 2. The **time** is still O(n²) there: this trick protects the stack, not the clock. Quick sort's extra memory is now O(log n) in every case. It's the loop-for-the-last-call idea from [Recursion vs iteration, and tail calls](/dsa/learn/rec-vs-iteration), applied to whichever call is bigger.

<Callout kind="gotcha" title="Quick sort's classic slips">
- **Hoare's split isn't the pivot's index.** Recurse on `low...split` and `(split + 1)...high`. Lomuto's ranges, `low...(p - 1)` and `(p + 1)...high`, are only right for Lomuto.
- **Off-by-one on the first call.** With closed ranges, sort the whole array with `quickSort(&items, 0, items.count - 1)`. The `guard low < high` makes the empty array (`high` = −1) safe.
- **`<=` in Lomuto's scan.** It still sorts, but every element equal to the pivot is swapped across for no benefit. With many duplicates, both `<` and `<=` give lopsided partitions, which the next lesson fixes.
- **Expecting stability.** Quick sort reorders equal elements. Sort by a second key as a tie-break, or use a stable sort.
</Callout>
