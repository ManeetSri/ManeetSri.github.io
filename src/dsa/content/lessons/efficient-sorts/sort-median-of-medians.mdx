## Why it matters

Quickselect is O(n) on average, but its worst case is O(n²), and random pivots only make that unlikely. In 1973, Blum, Floyd, Pratt, Rivest and Tarjan showed you can select the kth smallest in **O(n) in the worst case**, with a pivot rule called **median of medians**. It's rarely the fastest choice in practice, but it's a landmark: it proves selection is genuinely easier than sorting, it's the standard fallback when a library must guarantee linear time, and its analysis is a beautiful example of a recurrence that the Master theorem can't handle.

## The idea: a pivot that's guaranteed to be decent

Quickselect goes wrong when a pivot lands near either end of its range. It doesn't need the **exact** median to be fast; it needs a pivot with a **guaranteed fraction** of the elements on each side. Median of medians finds one like this:

1. Split the n elements into groups of **5** (the last group may be smaller).
2. Find the median of each group. A group of 5 can be sorted with a handful of comparisons, so this step is O(n) in total.
3. Find the median of those n/5 medians, **recursively**, using this same selection algorithm. That's the pivot.
4. Partition around the pivot, and continue in the side that holds index k, exactly as quickselect does.

Step 3 is the clever part: the algorithm uses itself to choose its own pivot.

## The pivot guarantee

Why is the median of medians a good pivot? Picture the groups as columns, each sorted with its smallest value at the top, and the columns arranged in order of their medians. M is the median of medians:

```text
           groups, ordered by their medians →
row 1        ≤    ≤    ≤    ≤    ?    ?    ?
row 2        ≤    ≤    ≤    ≤    ?    ?    ?
medians      ≤    ≤    ≤    M    ≥    ≥    ≥
row 4        ?    ?    ?    ≥    ≥    ≥    ≥
row 5        ?    ?    ?    ≥    ≥    ≥    ≥
```

Look at the top-left block. The medians to the left of M are ≤ M, because M is their median. In each of those columns, the two values above the median are smaller still. So every **≤** in the picture really is ≤ M: three values from each of about half the groups. That's about 3/5 × 1/2 = **3n/10** values that are ≤ M. By the same reasoning, the bottom-right block holds about 3n/10 values that are ≥ M.

So at least about 3n/10 elements sit on each side of the pivot, and **neither side can hold more than about 7n/10**. (The `?` values can fall either way, which is why the guarantee is 3/10 and not 1/2.) A partial last group and M's own column shave a few elements off these counts, a constant that doesn't matter for large n.

## The recurrence: why it's O(n)

Count the work for n elements:

- sorting the groups of 5 and partitioning: O(n), call it cn;
- finding the median of the n/5 medians: T(n/5);
- continuing in one side, which has at most 7n/10 elements: T(7n/10).

**T(n) ≤ T(n/5) + T(7n/10) + cn**

The two recursive calls are on **different** sizes, so the [Master theorem](/dsa/learn/bigo-master-theorem) doesn't apply. Draw the recursion tree instead, as in [Recurrences: substitution and recursion trees](/dsa/learn/bigo-recurrences). The root does cn work. Its two children work on n/5 and 7n/10 elements, together 9n/10, so their level does at most (9/10)cn. Each level does at most 9/10 of the level above:

cn × (1 + 9/10 + 81/100 + …) = cn × 10 = **10cn**

That's a geometric series with ratio 9/10, so the total is O(n). The key fact is that 1/5 + 7/10 is **less than 1**: the subproblems together are a constant fraction smaller than the problem, so the work shrinks level by level.

<Callout kind="note" title="Why groups of 5?">
With groups of 3, the guarantee drops to n/3 on each side, and the recurrence becomes T(n/3) + T(2n/3) + cn. Now 1/3 + 2/3 = 1: every level of the tree does a full cn of work, and with about log n levels the total is O(n log n). Groups of 7 work too (1/7 + 5/7 is less than 1), but each group costs more to sort. Five is the smallest odd group size that gives linear time.
</Callout>

## The code

This version favours clarity: it builds new arrays for the medians and for each side of the partition, and partitions three ways so duplicates are handled. It counts comparisons, and checks itself against sorting for every k:

```swift run
// Median of medians: select the value for index k (0-based) in worst-case O(n)
var comparisons = 0

func isLess(_ a: Int, _ b: Int) -> Bool {
    comparisons += 1
    return a < b
}

func select(_ numbers: [Int], _ k: Int) -> Int {
    if numbers.count <= 5 {
        return numbers.sorted(by: isLess)[k]         // tiny: sort it directly
    }
    // 1. Split into groups of 5 and take the median of each group
    var medians: [Int] = []
    for start in stride(from: 0, to: numbers.count, by: 5) {
        let group = numbers[start..<min(start + 5, numbers.count)].sorted(by: isLess)
        medians.append(group[group.count / 2])
    }
    // 2. The median of those medians, found by calling select recursively, is the pivot
    let pivot = select(medians, medians.count / 2)

    // 3. Partition three ways around it, and continue in the part that holds index k
    var smaller: [Int] = []
    var larger: [Int] = []
    for value in numbers {
        if isLess(value, pivot) {
            smaller.append(value)
        } else if isLess(pivot, value) {
            larger.append(value)
        }
    }
    let equal = numbers.count - smaller.count - larger.count
    if k < smaller.count {
        return select(smaller, k)
    } else if k < smaller.count + equal {
        return pivot
    } else {
        return select(larger, k - smaller.count - equal)
    }
}

let numbers = [42, 7, 19, 88, 3, 56, 23, 71, 12, 64, 35, 90, 5]
let sortedNumbers = numbers.sorted()
print((0..<numbers.count).allSatisfy { select(numbers, $0) == sortedNumbers[$0] })

for n in [1_000, 10_000, 100_000] {
    var line = "n = \(n):"
    for (name, input) in [("sorted", Array(0..<n)), ("mixed", (0..<n).map { ($0 * 7_919) % n }), ("all equal", Array(repeating: 1, count: n))] {
        comparisons = 0
        let median = select(input, n / 2)
        line += " \(name) \(comparisons / n) per element (median \(median));"
    }
    print(line)
}
```

```output
true
n = 1000: sorted 6 per element (median 500); mixed 8 per element (median 500); all equal 3 per element (median 1);
n = 10000: sorted 7 per element (median 5000); mixed 3 per element (median 5000); all equal 3 per element (median 1);
n = 100000: sorted 7 per element (median 50000); mixed 7 per element (median 50000); all equal 3 per element (median 1);
```

What to notice:

- The comparisons per element stay small and steady as n grows a hundredfold. There's no randomness, and no input can push the count past a fixed constant times n: that's what worst-case O(n) means.
- Sorted input, quickselect's nightmare with a fixed pivot, is nothing special here.
- All-equal input finishes after the first partition: every value equals the pivot, so index k lands in the equal block. That's the three-way partition at work.
- The medians of the groups are found by sorting 5 elements, which is fine: sorting a fixed-size group is O(1).

## Why it's rarely used in practice

Linear in the worst case sounds unbeatable. Here's the same experiment against plain quickselect with random pivots, on pseudo-random data:

```swift run
// Comparisons per element: median of medians against random-pivot quickselect
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: Range<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 2)
var comparisons = 0

func isLess(_ a: Int, _ b: Int) -> Bool {
    comparisons += 1
    return a < b
}

/// Splits numbers three ways around pivot
func split(_ numbers: [Int], around pivot: Int) -> (smaller: [Int], equal: Int, larger: [Int]) {
    var smaller: [Int] = []
    var larger: [Int] = []
    for value in numbers {
        if isLess(value, pivot) {
            smaller.append(value)
        } else if isLess(pivot, value) {
            larger.append(value)
        }
    }
    return (smaller, numbers.count - smaller.count - larger.count, larger)
}

func medianOfMedians(_ numbers: [Int], _ k: Int) -> Int {
    if numbers.count <= 5 {
        return numbers.sorted(by: isLess)[k]
    }
    var medians: [Int] = []
    for start in stride(from: 0, to: numbers.count, by: 5) {
        let group = numbers[start..<min(start + 5, numbers.count)].sorted(by: isLess)
        medians.append(group[group.count / 2])
    }
    let pivot = medianOfMedians(medians, medians.count / 2)
    let parts = split(numbers, around: pivot)
    if k < parts.smaller.count { return medianOfMedians(parts.smaller, k) }
    if k < parts.smaller.count + parts.equal { return pivot }
    return medianOfMedians(parts.larger, k - parts.smaller.count - parts.equal)
}

func randomSelect(_ numbers: [Int], _ k: Int) -> Int {
    let pivot = numbers[dice.roll(0..<numbers.count)]
    let parts = split(numbers, around: pivot)
    if k < parts.smaller.count { return randomSelect(parts.smaller, k) }
    if k < parts.smaller.count + parts.equal { return pivot }
    return randomSelect(parts.larger, k - parts.smaller.count - parts.equal)
}

func perElement(_ n: Int) -> String {
    let tenths = comparisons * 10 / n
    return "\(tenths / 10).\(tenths % 10)"
}

var data = Dice(seed: 99)
for n in [1_000, 10_000, 100_000] {
    let numbers = (0..<n).map { _ in data.roll(0..<1_000_000) }
    comparisons = 0
    let a = medianOfMedians(numbers, n / 2)
    let guaranteed = perElement(n)
    comparisons = 0
    let b = randomSelect(numbers, n / 2)
    print("n = \(n): median of medians \(guaranteed), random pivot \(perElement(n)) comparisons per element (same answer: \(a == b))")
}
```

```output
n = 1000: median of medians 8.8, random pivot 2.6 comparisons per element (same answer: true)
n = 10000: median of medians 9.6, random pivot 4.6 comparisons per element (same answer: true)
n = 100000: median of medians 9.8, random pivot 5.2 comparisons per element (same answer: true)
```

Median of medians makes about twice as many comparisons or more, and comparisons aren't its only cost: it sorts thousands of tiny groups and copies elements around. Random quickselect's count wobbles with its luck, but it's reliably lower, and its worst case is so improbable that it never happens in practice.

So median of medians is used as **insurance**, not as the main algorithm. The usual design, sometimes called **introselect** (the selection cousin of introsort), runs quickselect and switches to a guaranteed method only if the partitions keep coming out lopsided. The same pivot rule could make quick sort O(n log n) in the worst case, but for sorting, introsort's heap sort fallback is simpler and faster.

<Callout kind="gotcha" title="Two different 'medians'">
The pivot is the median of the **group medians**, not the median of the whole array. It's usually close to the true median, but it's only guaranteed to be somewhere between the 30th and 70th percentiles. That's all the analysis needs, and it's why the algorithm must still recurse after partitioning.
</Callout>
