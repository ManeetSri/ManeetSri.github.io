## Why it matters

Often all the data is there before the heap is: a day's worth of orders to process by priority, an array to heap-sort, a list of numbers handed to a heap's initialiser. Inserting them one at a time costs O(n log n). A cleverer method, **bottom-up heapify** (published by Robert Floyd in 1964), builds the same kind of heap in **O(n)**. Heap sort, DSAKit's `Heap(_:areInIncreasingOrder:)` and the swift-collections `Heap(_:)` initialiser all use it. The reason it's linear is one of the nicest arguments in the course: most of a tree is near the bottom.

## The slow way: n inserts

Start with an empty heap and push each value, as in the last lesson. Each push sifts up at most ⌊log₂ n⌋ levels, so n pushes are O(n log n). That's not a loose estimate: in a heap, half of all values sit on the bottom level, and if each new value is the smallest so far, every one of them climbs the whole height.

## The fast way: sift down from the bottom up

Look at the array as a complete tree **as it already is**, out of order. The second half of the array holds the leaves, and a single leaf is already a perfectly good heap of one value. So there's nothing to do for them.

Now take the last **parent**, at index `count / 2 - 1`. Its children are leaves, so they're heaps already. Sift the parent down, and that whole subtree becomes a heap. Move one index left to the previous parent, and do the same. Keep going back to index 0. Every time you sift down an index, both of its subtrees are heaps already, because their roots have larger indexes and were handled first. When you finish at the root, the whole array is a heap.

```swift run
func siftDown(_ items: inout [Int], from index: Int) {
    var parent = index
    while true {
        let left = 2 * parent + 1
        let right = left + 1
        var smaller = parent
        if left < items.count && items[left] < items[smaller] { smaller = left }
        if right < items.count && items[right] < items[smaller] { smaller = right }
        if smaller == parent { return }
        items.swapAt(parent, smaller)
        parent = smaller
    }
}

var items = [9, 4, 7, 1, 8, 2, 6, 3, 5]
for index in stride(from: items.count / 2 - 1, through: 0, by: -1) {
    siftDown(&items, from: index)
    print("after sifting down index \(index): \(items)")
}
```

```output
after sifting down index 3: [9, 4, 7, 1, 8, 2, 6, 3, 5]
after sifting down index 2: [9, 4, 2, 1, 8, 7, 6, 3, 5]
after sifting down index 1: [9, 1, 2, 3, 8, 7, 6, 4, 5]
after sifting down index 0: [1, 3, 2, 4, 8, 7, 6, 9, 5]
```

Nine values, so the parents are indexes 3, 2, 1 and 0, and indexes 4 to 8 are leaves.

- **Index 3** holds 1, already smaller than its children 3 and 5. Nothing moves.
- **Index 2** holds 7. Its smaller child is 2, so they swap.
- **Index 1** holds 4. It swaps with 1, then keeps going: at index 3, it swaps with 3.
- **Index 0** holds 9, the largest value, and it sinks three levels to index 7.

Only the root travelled far. That's the pattern that makes heapify fast.

Step through it. Green subtrees are finished heaps; each sift-down only ever works on a node whose subtrees are already green:

```visual heap
program: heapify
items: [9, 4, 7, 1, 8, 2, 6, 3, 5]
```

<Callout kind="gotcha" title="The loop runs backwards">
Sift down from the **last parent towards the root**: `stride(from: count / 2 - 1, through: 0, by: -1)`. Going forwards from 0 is a classic bug. When you sift the root first, its subtrees aren't heaps yet, so a small value deeper down can end up below a larger one, and the result isn't a heap. For an empty or one-element array, `count / 2 - 1` is −1, and the stride is empty, which is exactly right.
</Callout>

## Why it's O(n)

A sift down can travel at most from its starting level to the **bottom**. A sift up (an insert) can travel at most from the bottom to the **top**. That small difference is everything, because a complete tree is bottom-heavy: half its nodes are leaves, a quarter are one level up, an eighth two levels up, and so on.

So in heapify, the many nodes near the bottom do almost no work, and only the few nodes near the top travel far. With inserts it's the reverse: the many nodes near the bottom may each climb the whole height. Count the worst case, level by level, in a full heap of 1,023 values:

```swift run
// The most swaps each method can need, level by level, in a full heap of 1,023 values
let levels = 10                                      // 1 + 2 + 4 + … + 512 = 1,023 values
var siftDownTotal = 0
var siftUpTotal = 0
for depth in 0..<levels {
    let nodes = 1 << depth                           // 2 to the power depth
    let toBottom = levels - 1 - depth                // most swaps sifting down from this level
    let toTop = depth                                // most swaps sifting up from this level
    siftDownTotal += nodes * toBottom
    siftUpTotal += nodes * toTop
    print("depth \(depth): \(nodes) × \(toBottom) swaps down, \(nodes) × \(toTop) swaps up")
}
print("bottom-up heapify: at most \(siftDownTotal) swaps")
print("1,023 inserts:     at most \(siftUpTotal) swaps")
```

```output

depth 1: 2 × 8 swaps down, 2 × 1 swaps up
depth 2: 4 × 7 swaps down, 4 × 2 swaps up
depth 3: 8 × 6 swaps down, 8 × 3 swaps up
depth 4: 16 × 5 swaps down, 16 × 4 swaps up
depth 5: 32 × 4 swaps down, 32 × 5 swaps up
depth 6: 64 × 3 swaps down, 64 × 6 swaps up
depth 7: 128 × 2 swaps down, 128 × 7 swaps up
depth 8: 256 × 1 swaps down, 256 × 8 swaps up
depth 9: 512 × 0 swaps down, 512 × 9 swaps up
bottom-up heapify: at most 1013 swaps
1,023 inserts:     at most 8194 swaps
```

Heapify's biggest rows are the small ones. Write its total from the bottom: no work for half the nodes, at most 1 swap for a quarter of them, 2 for an eighth, 3 for a sixteenth:

n × (0/2 + 1/4 + 2/8 + 3/16 + 4/32 + …)

The fractions shrink much faster than the top numbers grow, and the series in brackets adds up to exactly 1. (Each term is at most three-quarters of the one before, once you're past the first few, so it behaves like the geometric series from [Series sums and logarithms](/dsa/learn/math-series-logs).) So heapify makes **fewer than n swaps**, whatever the input: O(n). The insert total, by contrast, is dominated by the bottom row: n/2 nodes times log₂ n levels, which is Θ(n log n).

It's the same idea as the amortised analysis in [Amortised analysis](/dsa/learn/bigo-amortised): a few operations are expensive (the root may sink all the way down), but they're rare enough that the average cost per element is a constant.

### See it on real inputs

Values in decreasing order are the worst case for building a min-heap by inserts: every new value is the smallest so far and climbs to the root.

```swift run
// Swaps to build a min-heap from values in decreasing order: n inserts against bottom-up heapify
func insertAll(_ values: [Int]) -> Int {
    var heap: [Int] = []
    var swaps = 0
    for value in values {
        heap.append(value)
        var child = heap.count - 1
        while child > 0 && heap[child] < heap[(child - 1) / 2] {
            heap.swapAt(child, (child - 1) / 2)
            child = (child - 1) / 2
            swaps += 1
        }
    }
    return swaps
}

func heapify(_ values: [Int]) -> Int {
    var items = values
    var swaps = 0
    for index in stride(from: items.count / 2 - 1, through: 0, by: -1) {
        var parent = index
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var smaller = parent
            if left < items.count && items[left] < items[smaller] { smaller = left }
            if right < items.count && items[right] < items[smaller] { smaller = right }
            if smaller == parent { break }
            items.swapAt(parent, smaller)
            parent = smaller
            swaps += 1
        }
    }
    return swaps
}

for n in [1_000, 10_000, 100_000] {
    let values = Array((1...n).reversed())
    print("n = \(n): inserts \(insertAll(values)) swaps, heapify \(heapify(values)) swaps")
}
```

```output
n = 1000: inserts 7987 swaps, heapify 992 swaps
n = 10000: inserts 113631 swaps, heapify 9992 swaps
n = 100000: inserts 1468946 swaps, heapify 99990 swaps
```

Heapify stays just under n, for every size. The inserts' swaps per element keep growing: about 8, then 11, then 15, tracking log₂ n. The gap between the two curves is the gap between O(n) and O(n log n):

## When each one fits

- **All the values up front:** heapify. It's faster, and it's in place: no second array.
- **Values arriving over time:** insert them one by one. Each insert is O(log n), which is the best a priority queue can do per operation.
- **A heap that already exists, plus a batch of new values:** append the batch and re-heapify the whole array if the batch is large compared with the heap; insert them one by one if it's small. (swift-collections' `Heap` has `insert(contentsOf:)` for exactly this case.)

Heapify builds **a** heap, not **the** heap: the same values can form many valid heaps. Heapify and repeated inserts often produce different arrays. Both pop the same values in the same order, which is all that matters.
