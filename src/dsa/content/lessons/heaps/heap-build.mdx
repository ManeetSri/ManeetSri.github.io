## Why it matters

Swift's standard library has arrays, sets and dictionaries, but no priority queue. Yet the rest of the course leans on one constantly: top-K problems, merging sorted streams, scheduling, and in Part VI the shortest-path and spanning-tree algorithms. In this lesson you'll turn the sift loops into a reusable, generic `Heap<Element>` that works for numbers, strings, tasks or anything else, with a closure deciding the order. It's the version DSAKit ships, and the version you'll write from memory in interviews.

## The design decisions

Before writing code, settle four questions.

**What does it store?** An array, laid out as in [A complete tree in an array](/dsa/learn/heap-array-index), plus the comparison. Nothing else: the count is the array's count.

**Struct or class?** A struct. Its only stored data is an array and a closure, so copies are independent for free, and copying is cheap until one copy changes, thanks to the array's copy-on-write (see [Writing your own copy-on-write](/dsa/learn/swift-implementing-cow)). A heap has no shared identity that a class would model better.

**How is the order chosen?** Two common designs:

| Design | Example | Pros | Cons |
| --- | --- | --- | --- |
| `Element: Comparable`, min-heap only | swift-collections' `Heap` | Simple API, no closure to store | A max-heap or "order tasks by deadline" needs a wrapper type |
| A closure, `areInIncreasingOrder` | DSAKit's `Heap`, C++'s `priority_queue` | Any order for any type, chosen at the call site | One stored closure, called on every comparison |

This course uses the closure. It's the same idea as `sorted(by:)` from [sorted(by:), min, max, contains and first(where:)](/dsa/learn/swift-sorting-searching-api): `areInIncreasingOrder(a, b)` returns true when `a` should come out **first**. So `<` gives a min-heap and `>` a max-heap, and a convenience for each saves typing when the elements are `Comparable`.

**What are the operations called?** `insert(_:)` adds, `peek()` looks at the top without removing it, and `pop()` removes and returns the top, or `nil` when the heap is empty. `count` and `isEmpty` answer the obvious questions.

## Step 1: storage and initialisers

```swift
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }
}
```

Three details:

- `Element` is a generic placeholder, exactly like `Stack<Element>` in [Generic types: `Stack<Element>`](/dsa/learn/swift-generic-types). The heap never needs to know what an element is: it only ever hands two of them to the closure.
- Both properties are `private`. Code outside the heap must not touch `items`, because one careless `items.append` would break the heap property.
- The closure parameter is `@escaping`, because the heap **stores** it and calls it long after `init` returns. Without the attribute, Swift refuses to compile the assignment ([Escaping and non-escaping closures](/dsa/learn/swift-escaping)).

## Step 2: reading the top

```swift
var count: Int { items.count }
var isEmpty: Bool { items.isEmpty }

func peek() -> Element? {
    items.first
}
```

`first` is already an optional: `nil` for an empty array. Using it means `peek()` can never crash, unlike `items[0]`.

## Step 3: insert and sift up

```swift
mutating func insert(_ element: Element) {
    items.append(element)
    siftUp(from: items.count - 1)
}

private mutating func siftUp(from index: Int) {
    var child = index
    while child > 0 {
        let parent = (child - 1) / 2
        guard areInIncreasingOrder(items[child], items[parent]) else { return }
        items.swapAt(child, parent)
        child = parent
    }
}
```

This is the loop from [Sift up and sift down](/dsa/learn/heap-sift) with the comparison replaced by the closure. The test reads naturally: keep going while the child **should come before** its parent. `insert` is `mutating` because it changes `items`; calling it on a heap declared with `let` is a compile error.

## Step 4: pop and sift down

```swift
@discardableResult
mutating func pop() -> Element? {
    guard !items.isEmpty else { return nil }
    items.swapAt(0, items.count - 1)
    let top = items.removeLast()
    siftDown(from: 0)
    return top
}

private mutating func siftDown(from index: Int) {
    var parent = index
    while true {
        let left = 2 * parent + 1
        let right = left + 1
        var first = parent
        if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
        if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
        if first == parent { return }
        items.swapAt(parent, first)
        parent = first
    }
}
```

`first` tracks whichever of the three (parent, left, right) should come first. `@discardableResult` lets you write `heap.pop()` on its own line just to throw the top away, without a warning.

## Step 5: building from an array in O(n)

```swift
init(_ elements: [Element], areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
    self.items = elements
    self.areInIncreasingOrder = areInIncreasingOrder
    for index in stride(from: items.count / 2 - 1, through: 0, by: -1) {
        siftDown(from: index)
    }
}
```

That's bottom-up heapify from [O(n) heapify](/dsa/learn/heap-heapify). Calling `siftDown`, a mutating method, inside an initialiser is fine once every stored property has a value.

## Step 6: conveniences for Comparable elements

```swift
extension Heap where Element: Comparable {
    static func minHeap() -> Heap { Heap(areInIncreasingOrder: <) }
    static func maxHeap() -> Heap { Heap(areInIncreasingOrder: >) }
}
```

The `where` clause makes these exist only when elements can be compared with `<`. For a heap of tasks, they don't appear at all. Inside the extension, `Heap` alone means `Heap<Element>`, so `Heap<Int>.minHeap()` returns a `Heap<Int>`.

## The whole heap

Here it is in one piece, used three ways: plain numbers, words by length, and tasks by priority. Run it, then try changing the closures.

```swift run
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    init(_ elements: [Element], areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.items = elements
        self.areInIncreasingOrder = areInIncreasingOrder
        for index in stride(from: items.count / 2 - 1, through: 0, by: -1) {
            siftDown(from: index)
        }
    }

    var count: Int { items.count }
    var isEmpty: Bool { items.isEmpty }

    func peek() -> Element? {
        items.first
    }

    mutating func insert(_ element: Element) {
        items.append(element)
        siftUp(from: items.count - 1)
    }

    @discardableResult
    mutating func pop() -> Element? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        siftDown(from: 0)
        return top
    }

    private mutating func siftUp(from index: Int) {
        var child = index
        while child > 0 {
            let parent = (child - 1) / 2
            guard areInIncreasingOrder(items[child], items[parent]) else { return }
            items.swapAt(child, parent)
            child = parent
        }
    }

    private mutating func siftDown(from index: Int) {
        var parent = index
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var first = parent
            if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
            if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
            if first == parent { return }
            items.swapAt(parent, first)
            parent = first
        }
    }
}

extension Heap where Element: Comparable {
    static func minHeap() -> Heap { Heap(areInIncreasingOrder: <) }
    static func maxHeap() -> Heap { Heap(areInIncreasingOrder: >) }
}

// 1. Plain numbers, smallest first
var numbers = Heap<Int>.minHeap()
for value in [42, 7, 19, 3, 25] {
    numbers.insert(value)
}
print(numbers.peek()!, numbers.count)

// 2. Words, longest first, built from an array in O(n)
var words = Heap(["fig", "banana", "kiwi", "apple"], areInIncreasingOrder: { $0.count > $1.count })
print(words.pop()!, words.pop()!)

// 3. Tasks by priority (1 is most urgent), ties broken by arrival order
struct Task {
    let name: String
    let priority: Int
    let arrival: Int
}

var tasks = Heap<Task>(areInIncreasingOrder: { a, b in
    a.priority != b.priority ? a.priority < b.priority : a.arrival < b.arrival
})
let incoming = [("write tests", 2), ("fix crash", 1), ("review PR", 2), ("update docs", 3), ("reply to Sam", 1)]
for (arrival, (name, priority)) in incoming.enumerated() {
    tasks.insert(Task(name: name, priority: priority, arrival: arrival))
}
while let task = tasks.pop() {
    print("P\(task.priority) \(task.name)")
}

// 4. The same priority for everything, with no tie-break: not arrival order
var sameUrgency = Heap<Task>(areInIncreasingOrder: { $0.priority < $1.priority })
for (arrival, name) in ["a", "b", "c"].enumerated() {
    sameUrgency.insert(Task(name: name, priority: 1, arrival: arrival))
}
var order: [String] = []
while let task = sameUrgency.pop() {
    order.append(task.name)
}
print(order)

// 5. Copies are independent
var original = Heap([5, 1, 3], areInIncreasingOrder: <)
var copy = original
copy.insert(0)
original.pop()
print(original.peek()!, copy.peek()!, original.count, copy.count)
```

```output
3 5
banana apple
P1 fix crash
P1 reply to Sam
P2 write tests
P2 review PR
P3 update docs
["a", "c", "b"]
3 0 2 4
```

What to notice:

- **Part 3** breaks ties by arrival, so equal priorities come out first come, first served. The closure compares priorities and only looks at `arrival` when they're equal.
- **Part 4** shows why that matters. Three tasks of equal priority come out as a, c, b. The first pop moves c to the top, and since b doesn't come strictly before c, c stays there. A heap is **not stable**: equal elements leave in an order that depends on the heap's internal layout. When order among equals matters, put the tie-breaker in the closure.
- **Part 5** is value semantics: inserting into the copy and popping the original don't affect each other.

<Callout kind="gotcha" title="Swift gotcha: the closure must be strict">
Use `<` or `>`, never `<=` or `>=`. The closure answers "must a come out **before** b?", and for equal elements the answer is no. With `<=`, sift up swaps equal elements for nothing, and code that assumes a strict order, like `sorted(by:)`, can misbehave. The same rule applies to every `areInIncreasingOrder` in Swift.
</Callout>

## Testing it like a professional

How do you know the heap is right, beyond a few examples? Compare it against something **obviously** correct, on thousands of random operations. A sorted array is slow but simple: insert at the right place, and the smallest is always at one end. Drive both with the same seeded random numbers (random, but the same every run), and count the times they disagree:

```swift run
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    var count: Int { items.count }

    func peek() -> Element? {
        items.first
    }

    mutating func insert(_ element: Element) {
        items.append(element)
        var child = items.count - 1
        while child > 0 {
            let parent = (child - 1) / 2
            guard areInIncreasingOrder(items[child], items[parent]) else { return }
            items.swapAt(child, parent)
            child = parent
        }
    }

    mutating func pop() -> Element? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        var parent = 0
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var first = parent
            if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
            if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
            if first == parent { break }
            items.swapAt(parent, first)
            parent = first
        }
        return top
    }
}

// A seeded random generator, so the test does the same thing every run
struct Dice {
    private var state: UInt64
    init(seed: UInt64) { state = seed }
    mutating func roll(_ range: ClosedRange<Int>) -> Int {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        return range.lowerBound + Int((state >> 33) % UInt64(range.count))
    }
}

var dice = Dice(seed: 7)
var heap = Heap<Int>(areInIncreasingOrder: <)
var model: [Int] = []                                // sorted from largest to smallest
var mismatches = 0
for _ in 0..<10_000 {
    if dice.roll(0...9) < 6 {
        let value = dice.roll(-100...100)
        heap.insert(value)
        let position = model.firstIndex { $0 < value } ?? model.count
        model.insert(value, at: position)            // slow, but obviously right
    } else if heap.pop() != model.popLast() {
        mismatches += 1
    }
    if heap.peek() != model.last || heap.count != model.count {
        mismatches += 1
    }
}
print("10000 operations, \(heap.count) values left, \(mismatches) mismatches")
```

```output
10000 operations, 2077 values left, 0 mismatches
```

Six in ten operations are inserts, so the heap grows to a couple of thousand values, with many duplicates in the range −100 to 100. Try breaking `pop` on purpose, say by always swapping with the left child, and watch the mismatch count jump. DSAKit's own tests do exactly this with 100,000 operations. This technique, comparing a clever implementation with a slow, obvious **model**, catches bugs that hand-picked examples miss.

## DSAKit's Heap

DSAKit's version is the heap from this lesson, with a few additions:

| Member | What it does | Cost |
| --- | --- | --- |
| `Heap(areInIncreasingOrder:)` | an empty heap with your order | O(1) |
| `Heap(_:areInIncreasingOrder:)` | from any sequence, with heapify | O(n) |
| `Heap<Int>()`, `.minHeap()`, `.maxHeap()` | conveniences for `Comparable` elements; an array literal makes a min-heap | O(1), or O(n) with elements |
| `insert(_:)` | add an element | O(log n) |
| `peek()` (or `top`) | the element that comes first, or nil | O(1) |
| `pop()` | remove and return it, or nil | O(log n) |
| `replaceTop(with:)` | swap the top for a new element in one sift, returning the old top | O(log n) |
| `count`, `isEmpty`, `unordered` | size, and the array in heap order | O(1) |

```swift
import DSAKit

var tasks = Heap<(priority: Int, name: String)>(areInIncreasingOrder: { $0.priority < $1.priority })
tasks.insert((2, "review PR"))
tasks.insert((1, "fix crash"))
print(tasks.peek()?.name ?? "none")       // fix crash

var largest: Heap = .maxHeap([5, 3, 8])
largest.replaceTop(with: 1)               // 8 leaves, 1 sifts down
print(largest.pop() ?? 0)                 // 5
```

`replaceTop(with:)` is the "pop, then push" in one go, used constantly in the next lessons: when a better candidate turns up, it replaces the worst of the current ones with a single sift down.

`Heap` deliberately isn't a `Sequence`. Which order would `for x in heap` use? The array order isn't sorted, and sorted order would cost O(n log n) and isn't what a loop suggests. swift-collections made the same choice. When you want every element in order, pop until `nil`; when you just want them all, read `unordered`.

<Callout kind="gotcha" title="Common mistakes when writing a heap">
- **Forgetting `@escaping`.** The compiler says the closure "may escape". It does: you're storing it.
- **Exposing `items`.** If callers can modify the array directly, nothing protects the heap property. Keep it `private`, and offer a read-only view if needed (DSAKit's `unordered`).
- **`items[0]` in `peek`.** It crashes on an empty heap. `items.first` returns `nil` instead.
- **Popping into a sorted result and calling it stable.** Equal elements come out in no reliable order. Add a tie-breaker to the closure.
</Callout>
