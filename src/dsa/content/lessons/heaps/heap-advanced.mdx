## Why it matters

Binary heaps are hard to beat in practice, but they're bad at one thing: **melding**, combining two heaps into one. The best a binary heap can do is concatenate the arrays and heapify, O(n). And decrease-key, as you saw in the last lesson, costs O(log n). From the late 1970s, researchers designed **mergeable heaps** that meld cheaply, culminating in the **Fibonacci heap**, which does decrease-key in O(1) amortised time. That single improvement gives the best known theoretical bounds for Dijkstra's shortest paths and Prim's spanning trees (M44 and M46): O(E + V log V). This lesson is conceptual: how these heaps are shaped, why their bounds hold, and why you'll rarely code one.

## Binomial trees

A **binomial tree** of order k, written B_k, is defined recursively:

- B_0 is a single node.
- B_k is two B_(k−1) trees **linked**: the root of one becomes the leftmost child of the root of the other.

```text
B0      B1        B2              B3
 o       o         o               o
         |        / \           /  |  \
         o       o   o         o   o   o
                 |            / \  |
                 o           o   o o
                             |
                             o
```

Doubling at every order gives B_k some neat properties:

- It has exactly **2^k nodes** and height k.
- Its root has **k children**, which are roots of B_(k−1), B_(k−2), …, B_0.
- It has C(k, d) nodes at depth d, the binomial coefficient from [Factorials, permutations and combinations](/dsa/learn/math-counting): that's where the name comes from. B_3 has 1, 3, 3, 1 nodes at depths 0 to 3.

**Linking** two trees of the same order is O(1): compare the two roots, and make the one with the larger key a child of the other. Heap order (every parent ≤ its children) survives.

## Binomial heaps: n in binary

A **binomial heap** is a collection of heap-ordered binomial trees, **at most one of each order**. Since B_k has 2^k nodes, the trees present are exactly the 1 bits of n in binary. A heap of 13 = 1101₂ values holds a B_3, a B_2 and a B_0. With n values there are at most ⌊log₂ n⌋ + 1 trees, and the minimum is one of their roots.

- **Meld** two binomial heaps by adding them like binary numbers: go up the orders, and whenever two trees of the same order meet, link them into one tree of the next order, a **carry**. O(log n).
- **Insert** is a meld with a one-node heap, B_0: adding 1 to a binary counter.
- **Delete-min:** find the root with the smallest key, remove it, and its children (a B_(k−1), …, B_0) form a binomial heap of their own. Meld it back in. O(log n).
- **Decrease-key:** lower the key and sift up within its tree, O(log n), as in a binary heap.

Watch the shapes follow the binary digits as values are inserted, and count the links:

```swift run
// A binomial heap's shape is n in binary: hasTree[k] is true when the heap holds a tree of order k.
// Inserting adds a single node (order 0), and equal orders link, carrying like binary addition.
var hasTree: [Bool] = []
var links = 0

func insertOne() {
    var order = 0
    while order < hasTree.count && hasTree[order] {
        hasTree[order] = false                   // two trees of this order link into one…
        links += 1
        order += 1                               // …of the next order up: the carry
    }
    if order == hasTree.count { hasTree.append(false) }
    hasTree[order] = true
}

for n in 1...13 {
    insertOne()
    let orders = hasTree.indices.filter { hasTree[$0] }.map { "B\($0)" }
    if [1, 2, 3, 4, 7, 8, 13].contains(n) {
        print("n = \(n) (\(String(n, radix: 2)) in binary): \(orders.reversed().joined(separator: ", "))")
    }
}
print("links for 13 inserts: \(links)")

hasTree = []
links = 0
for _ in 0..<1_000_000 {
    insertOne()
}
print("links for 1000000 inserts: \(links), fewer than 1 per insert")
```

```output
n = 1 (1 in binary): B0
n = 2 (10 in binary): B1
n = 3 (11 in binary): B1, B0
n = 4 (100 in binary): B2
n = 7 (111 in binary): B2, B1, B0
n = 8 (1000 in binary): B3
n = 13 (1101 in binary): B3, B2, B0
links for 13 inserts: 10
links for 1000000 inserts: 999993, fewer than 1 per insert
```

One insert can cause a cascade of links (going from 7 to 8 links three times), so the worst case is O(log n). But that's the binary counter from [Amortised analysis](/dsa/learn/bigo-amortised): each link permanently reduces the number of trees by one, and each insert adds only one tree, so n inserts make fewer than n links. Insert is **O(1) amortised**.

## Fibonacci heaps: be lazy, tidy up later

A **Fibonacci heap** relaxes the binomial heap's rules and postpones work until it has to be done:

- **Insert:** add the new node as a new root in the list of roots. Don't link anything. O(1).
- **Meld:** splice the two root lists together. O(1).
- **Find-min:** keep a pointer to the smallest root. O(1).
- **Delete-min:** remove the minimum root and make its children roots. Now, at last, **consolidate**: link roots of equal degree (number of children) until all degrees differ, and find the new minimum. A long root list makes this slow once, but every link removes a root, and each root was paid for when it was created. O(log n) amortised.
- **Decrease-key:** lower the key. If it's still ≥ its parent's, done. Otherwise **cut** the node from its parent and make it a root, O(1). To stop trees from becoming too thin, each node is **marked** when it loses a child; if a marked node loses a second child, it's cut too, and so on up the tree (a **cascading cut**). The amortised cost is O(1).

Why "Fibonacci"? The cutting rule guarantees that a node with k children still has at least F(k + 2) nodes in its subtree, where F is the Fibonacci sequence. Fibonacci numbers grow exponentially (by a factor of about φ ≈ 1.618 per step), so no node can have more than about log_φ n children. That keeps consolidation, and therefore delete-min, at O(log n).

```swift run
// In a Fibonacci heap, a node with k children has at least F(k + 2) nodes in its subtree,
// so with n nodes no node can have more than about log_φ n children.
var fib = [0, 1]                                 // F(0), F(1), …
while fib.count < 40 {
    fib.append(fib[fib.count - 1] + fib[fib.count - 2])
}
for k in [0, 1, 2, 3, 4, 5, 10, 20] {
    print("degree \(k): subtree size at least \(fib[k + 2])")
}
let n = 1_000_000
var k = 0
while fib[k + 3] <= n {                          // the next degree, k + 1, still fits in n nodes
    k += 1
}
print("with \(n) nodes, the largest possible degree is \(k)")
```

```output
degree 0: subtree size at least 1
degree 1: subtree size at least 2
degree 2: subtree size at least 3
degree 3: subtree size at least 5
degree 4: subtree size at least 8
degree 5: subtree size at least 13
degree 10: subtree size at least 144
degree 20: subtree size at least 17711
with 1000000 nodes, the largest possible degree is 28
```

## The amortised bounds

| Operation | Binary heap | Binomial heap | Fibonacci heap | Pairing heap |
| --- | --- | --- | --- | --- |
| Insert | O(log n) | O(1) amortised | O(1) | O(1) |
| Find-min | O(1) | O(log n), or O(1) with a min pointer | O(1) | O(1) |
| Delete-min | O(log n) | O(log n) | O(log n) amortised | O(log n) amortised |
| Decrease-key | O(log n) | O(log n) | **O(1) amortised** | below O(log n) amortised, not O(1) |
| Meld | O(n) | O(log n) | **O(1)** | O(1) |

The **pairing heap** in the last column is a simpler, self-adjusting relative of the Fibonacci heap: a single tree with a clever two-pass rule for delete-min. It's often the fastest mergeable heap in practice. Its exact decrease-key cost took decades of research; it's proven to be faster than O(log n) amortised, but not O(1).

## Why Dijkstra cares, and why you'll rarely build one

Dijkstra's algorithm on V places and E connections does V delete-mins and up to E decrease-keys:

- With a binary heap: O((V + E) log V).
- With a Fibonacci heap: O(V log V + E), because each decrease-key is O(1) amortised.

For dense graphs, where E is close to V², that's a real asymptotic improvement, and it's the textbook bound you'll see quoted in M44 and M46.

In practice, though, Fibonacci heaps are usually **slower**. Each node needs a parent pointer, a child pointer, sibling pointers, a degree and a mark; memory is scattered; and the constant factors are large. A binary or 4-ary heap in an array, with the lazy decrease-key from [d-ary heaps and indexed priority queues](/dsa/learn/heap-variants), wins on almost all real inputs. The Fibonacci heap's lasting value is in theory: it proves what's possible, and its amortised analysis is a masterclass in the potential method.

<Callout kind="note" title="Amortised, not worst case">
"O(1) amortised" for Fibonacci decrease-key means any sequence of m operations costs O(m) for the decrease-keys in total. A single decrease-key can trigger a long cascade of cuts. For real-time systems that can't tolerate an occasional slow operation, there are worst-case variants (such as Brodal queues), which are even more complex.
</Callout>
