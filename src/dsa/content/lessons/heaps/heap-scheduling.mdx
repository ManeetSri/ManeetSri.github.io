## Why it matters

Many scheduling problems have the same shape: at every step, several choices are available, and you take the **best one right now**. Assign a meeting to the room that frees up first. Run the task kind with the most work left. Take the most profitable project you can afford. Each of these "take the best available" rules is a **greedy** strategy, and the heap is what makes it fast: it hands you the best available option in O(log n), as options appear and disappear. You'll study greedy algorithms properly in M50; this lesson covers the heap-powered ones that interviews love, with an informal argument for why each greedy choice is safe.

## Meeting rooms, revisited

In [Meeting rooms I and II](/dsa/learn/iv-meeting-rooms) you counted the rooms needed for a day of half-open meetings with a sweep over start and end times, and that lesson promised a heap version. Here it is. Sort the meetings by start time. Keep the **end times of the rooms in use** in a min-heap, so the room that frees up first is on top. For each meeting, if that room is free by the meeting's start, reuse it (replace its end time); otherwise open a new room.

```swift run
// The heap from "Build a generic Heap<T>", compacted, plus replaceTop
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    var count: Int { items.count }
    var isEmpty: Bool { items.isEmpty }
    func peek() -> Element? { items.first }

    mutating func insert(_ element: Element) {
        items.append(element)
        var child = items.count - 1
        while child > 0 && areInIncreasingOrder(items[child], items[(child - 1) / 2]) {
            items.swapAt(child, (child - 1) / 2)
            child = (child - 1) / 2
        }
    }

    mutating func pop() -> Element? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        siftDownFromTop()
        return top
    }

    /// Replaces the top (the heap must not be empty) with one sift down
    mutating func replaceTop(with element: Element) {
        items[0] = element
        siftDownFromTop()
    }

    private mutating func siftDownFromTop() {
        var parent = 0
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var first = parent
            if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
            if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
            if first == parent { return }
            items.swapAt(parent, first)
            parent = first
        }
    }
}

// Fewest rooms for half-open meetings: a min-heap of the end times of rooms in use
func roomsNeeded(_ meetings: [(start: Int, end: Int)]) -> Int {
    let byStart = meetings.sorted { $0.start < $1.start }
    var endTimes = Heap<Int>(areInIncreasingOrder: <)        // the earliest-free room on top
    var most = 0
    for meeting in byStart {
        if let earliest = endTimes.peek(), earliest <= meeting.start {
            endTimes.replaceTop(with: meeting.end)            // reuse the room that's free
        } else {
            endTimes.insert(meeting.end)                      // every room is busy: open another
        }
        most = max(most, endTimes.count)
        print("\(meeting.start)-\(meeting.end): rooms in use \(endTimes.count), next free at \(endTimes.peek()!)")
    }
    return most
}

print(roomsNeeded([(9, 10), (9, 12), (10, 11), (11, 13), (12, 13)]))
```

```output
9-10: rooms in use 1, next free at 10
9-12: rooms in use 2, next free at 10
10-11: rooms in use 2, next free at 11
11-13: rooms in use 2, next free at 12
12-13: rooms in use 2, next free at 13
2
```

The 10-11 meeting takes over the room freed at 10, and 11-13 the room freed at 11. `earliest <= meeting.start` uses `<=` because meetings are half-open: a room freed at 10 is available to a meeting starting at 10.

**Why greedy works:** if even the earliest-free room is busy at the start time, every room is busy, so a new room is unavoidable. And when some room is free, reusing one can never hurt later meetings, because all rooms are interchangeable. Unlike the sweep, the heap version also tells you **which** room each meeting gets, if you store room numbers alongside the end times. It's O(n log n).

## Task scheduler with a cooldown

A CPU runs tasks of several kinds, one per time slot. Two tasks of the same kind need at least `cooldown` slots between them; if nothing is allowed to run, the slot is idle. What's the shortest schedule?

**The greedy rule:** in each slot, run the allowed kind with the **most tasks left**. The kind with the most work is the bottleneck: its tasks must be spread out, with gaps between them. Starting it early, and filling its gaps with other kinds, leaves the least idle time at the end. Putting it off can only push its last task later.

Implement it with a max-heap of the allowed kinds by tasks left, and a waiting line for kinds that are cooling down. Kinds join the line in the order they ran, so it's sorted by the slot when each is allowed again:

```swift run
// The heap from "Build a generic Heap<T>", compacted, plus replaceTop
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    var count: Int { items.count }
    var isEmpty: Bool { items.isEmpty }
    func peek() -> Element? { items.first }

            child = (child - 1) / 2

            parent = first
        }

}

// Greedy task scheduling: each slot runs the allowed kind with the most tasks left
func schedule(_ tasks: [Character], cooldown: Int) -> String {
    var counts: [Character: Int] = [:]
    for task in tasks {
        counts[task, default: 0] += 1
    }
    // Most tasks left first; ties alphabetical, so the schedule is the same every run
    var ready = Heap<(kind: Character, left: Int)>(areInIncreasingOrder: {
        $0.left != $1.left ? $0.left > $1.left : $0.kind < $1.kind
    })
    for (kind, left) in counts {
        ready.insert((kind, left))
    }
    var cooling: [(kind: Character, left: Int, readyAt: Int)] = []   // in the order they ran
    var slots: [String] = []
    var slot = 0
    while !ready.isEmpty || !cooling.isEmpty {
        while let first = cooling.first, first.readyAt <= slot {
            ready.insert((first.kind, first.left))
            cooling.removeFirst()
        }
        if let task = ready.pop() {
            slots.append(String(task.kind))
            if task.left > 1 {
                cooling.append((task.kind, task.left - 1, slot + cooldown + 1))
            }
        } else {
            slots.append("_")                             // nothing is allowed to run: idle
        }
        slot += 1
    }
    return slots.joined(separator: " ")
}

print(schedule(Array("AAABBC"), cooldown: 2))
print(schedule(Array("AAABBBCCD"), cooldown: 2))
print(schedule(Array("AAAA"), cooldown: 1))
```

```output
A B C A B _ A
A B C A B C A B D
A _ A _ A _ A
```

In the first schedule, A runs at slot 0 and is allowed again at slot 3. At slot 5, A is still cooling (until 6) and nothing else is left, so the slot is idle. The heap's tie-break (alphabetical among equal counts) only makes the printed schedule the same every run; any choice among ties gives the same length. The waiting line is a plain array here, and `removeFirst()` shifts the rest along, which is fine for a few kinds. With many kinds, a `Deque` from [Build `Deque<T>`](/dsa/learn/queue-build-deque) makes it O(1), as in the practice problem's solution.

The length also has a closed form. If the busiest kind has `most` tasks and `busiest` kinds share that count, the answer is `max(tasks.count, (most - 1) × (cooldown + 1) + busiest)`: `most - 1` frames of `cooldown + 1` slots for the busiest kinds, plus a final slot for each of them, unless there are enough tasks to fill every gap. The simulation is the version that still works when the rules change, for example when you need the actual order, or when tasks arrive over time.

## Reorganise a string

Rearrange the letters of a string so that no two neighbours are the same, or report that it's impossible. It's the scheduler with a cooldown of 1, where idle slots aren't allowed.

**When is it impossible?** If one letter appears more than `(n + 1) / 2` times, there aren't enough other letters to separate its copies. Otherwise, the greedy rule always succeeds: take the most frequent letter that isn't the one you just used.

The trick for "isn't the one you just used": after placing a letter, keep it **out of the heap** for one turn, and put it back after the next letter is placed.

```swift run
// The heap from "Build a generic Heap<T>", compacted, plus replaceTop
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    var count: Int { items.count }
    var isEmpty: Bool { items.isEmpty }
    func peek() -> Element? { items.first }

    mutating func insert(_ element: Element) {
        items.append(element)
        var child = items.count - 1
        while child > 0 && areInIncreasingOrder(items[child], items[(child - 1) / 2]) {
            items.swapAt(child, (child - 1) / 2)
            child = (child - 1) / 2
        }
    }

    mutating func pop() -> Element? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        siftDownFromTop()
        return top
    }

    /// Replaces the top (the heap must not be empty) with one sift down
    mutating func replaceTop(with element: Element) {
        items[0] = element
        siftDownFromTop()
    }

    private mutating func siftDownFromTop() {
        var parent = 0
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var first = parent
            if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
            if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
            if first == parent { return }
            items.swapAt(parent, first)
            parent = first
        }
    }
}

// Rearrange letters so no two neighbours match, or return "" if that's impossible
func reorganise(_ text: String) -> String {
    var counts: [Character: Int] = [:]
    for letter in text {
        counts[letter, default: 0] += 1
    }
    if let most = counts.values.max(), most > (text.count + 1) / 2 {
        return ""                                         // too many copies of one letter
    }
    var heap = Heap<(letter: Character, left: Int)>(areInIncreasingOrder: {
        $0.left != $1.left ? $0.left > $1.left : $0.letter < $1.letter
    })
    for (letter, left) in counts {
        heap.insert((letter, left))
    }
    var result = ""
    var resting: (letter: Character, left: Int)? = nil  // the letter just used sits out one turn
    while let next = heap.pop() {
        result.append(next.letter)
        if let previous = resting, previous.left > 0 {
            heap.insert(previous)                         // its turn out is over
        }
        resting = (next.letter, next.left - 1)
    }
    return result
}

for text in ["aaabbc", "aab", "vvvlo", "aaab"] {
    print("\(text) -> \"\(reorganise(text))\"")
}
```

```output
aaabbc -> "ababac"
aab -> "aba"
vvvlo -> "vlvov"
aaab -> ""
```

**Why greedy works, informally:** the most frequent letter is the one in danger of running out of separators. Placing it whenever it's allowed keeps its remaining count from getting too large compared with everything else, and the `(n + 1) / 2` check guarantees it never does. Each step is O(log k) for k distinct letters, so the whole thing is O(n log k): with 26 letters, effectively O(n).

## Maximise capital: the IPO problem

A small company starts with some capital and can complete at most k projects, one at a time. Each project needs a minimum capital to start, which isn't spent (think of it as a credit check), and adds its profit when done. Which projects should it pick?

**The greedy rule:** each time, take the most profitable project you can **currently afford**. Capital never goes down, so a project affordable now stays affordable. Taking the biggest profit first leaves you with the most money, which can only unlock more projects, and every other affordable project is still available afterwards. Nothing is ever lost by taking the best one now.

Two structures make it fast. Sort the projects by requirement once, and walk a pointer along them, moving each newly affordable project into a **max-heap by profit**:

```swift run
// The heap from "Build a generic Heap<T>", compacted, plus replaceTop

    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {

            child = (child - 1) / 2

            parent = first
        }
    }
}

// Take up to k projects; each needs capital >= its requirement (not spent) and adds its profit
func bestCapital(start: Int, k: Int, projects: [(name: String, requirement: Int, profit: Int)]) -> Int {
    let byRequirement = projects.sorted { $0.requirement < $1.requirement }
    var affordable = Heap<(name: String, requirement: Int, profit: Int)>(areInIncreasingOrder: { $0.profit > $1.profit })
    var capital = start
    var next = 0
    for _ in 0..<k {
        while next < byRequirement.count && byRequirement[next].requirement <= capital {
            affordable.insert(byRequirement[next])          // newly affordable
            next += 1
        }
        guard let best = affordable.pop() else { break }  // nothing affordable: stop early
        capital += best.profit
        print("take \(best.name) (needs \(best.requirement), earns \(best.profit)): capital \(capital)")
    }
    return capital
}

let projects = [
    (name: "logo", requirement: 0, profit: 2),
    (name: "website", requirement: 3, profit: 10),
    (name: "poster", requirement: 0, profit: 1),
    (name: "app", requirement: 12, profit: 30),
    (name: "video", requirement: 2, profit: 5),
]
print(bestCapital(start: 1, k: 3, projects: projects))
```

```output
take logo (needs 0, earns 2): capital 3
take website (needs 3, earns 10): capital 13
take app (needs 12, earns 30): capital 43
43
```

At the start, with capital 1, only the logo and the poster are affordable, and the logo pays more. Its profit brings capital to 3, which unlocks the website and the video; the website pays more. That brings capital to 13, enough for the app. The poster and the video are never needed.

Each project enters the heap once and leaves at most once, so after the O(n log n) sort, the picks cost O(n log n) in total, instead of O(n · k) for scanning every project on every pick. When the heap is empty, nothing will ever become affordable (capital has stopped growing), so the loop stops early.

## Spotting the pattern

All four problems share a shape:

- Options **become available** over time (meetings start, cooldowns end, capital grows).
- At each step you want the **best available** option by one measure (earliest end, most tasks left, most frequent, most profit).
- Taking it now **never hurts later**, which is the informal greedy argument you should be able to say out loud.

When you see that shape, reach for a heap keyed by the measure, plus something (a sorted list and a pointer, or a waiting line) that releases options into the heap as they become available.

<Callout kind="gotcha" title="Greedy needs a reason">
A heap makes any greedy rule fast, including wrong ones. Before coding, test the rule on small cases, or argue why taking the best option now can't block a better plan later. For example, "take the project with the best profit-to-requirement ratio" sounds clever but is wrong: requirements aren't spent, so only profit matters once a project is affordable.
</Callout>
