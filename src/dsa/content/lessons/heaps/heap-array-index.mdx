## Why it matters

Lots of programs keep asking one question: "what's the most urgent thing right now?" A download manager starts the highest-priority file next. A game's event loop runs whichever timer fires soonest. A map app's route finder (you'll build one in Part VI) always explores the closest unexplored place. A structure that answers that question quickly, while things keep arriving, is a **priority queue**. The classic way to build one is a **binary heap**, and its secret is that a tree can live inside a plain array, with no pointers at all.

## The problem with the obvious structures

You need three operations: add an item, look at the most urgent one, and remove it. Here's what the structures you already know cost, with "most urgent" meaning "smallest":

| Structure | Add | Look at the smallest | Remove the smallest |
| --- | --- | --- | --- |
| Unsorted array | O(1) | O(n) scan | O(n) |
| Sorted array | O(n) to shift | O(1) | O(1) from the right end |
| Binary heap | O(log n) | O(1) | O(log n) |

The sorted array does too much work: it keeps **every** item in order, when you only ever ask for one. A heap keeps just enough order to find the smallest instantly, and repairs itself in O(log n).

## The heap property

A **min-heap** is a binary tree where every parent is **less than or equal to** its children. Follow that rule down from the root, and the root must be the smallest value of all. Here's a min-heap of seven values:

```text
          1
       /     \
      3       2
     / \     / \
    7   4   5   9
```

Every parent is ≤ its children: 1 ≤ 3 and 2, 3 ≤ 7 and 4, 2 ≤ 5 and 9. Notice what the rule **doesn't** say. Siblings can be in any order (3 is left of 2), and a value deep on the left (7) can be bigger than one on the right (5). A heap is only partly ordered, and that's exactly why it's cheap to maintain.

A **max-heap** flips the rule: every parent is ≥ its children, so the root is the largest. Everything in this module works for both; only the comparison changes.

## A complete tree

A heap has a second rule, about its **shape**: it's a **complete** binary tree. Every level is full, except possibly the last, which fills from left to right with no gaps. You met complete trees in [Full, complete, perfect, balanced and degenerate trees](/dsa/learn/tree-types).

Completeness is what makes the array trick work. Read the tree level by level, left to right, and write the values down:

```text
index:   0   1   2   3   4   5   6
value:   1   3   2   7   4   5   9
         ^   ^---^   ^-----------^
       level 0  level 1     level 2
```

Because there are no gaps, the shape is decided entirely by the count. Seven values always make this shape. Add an eighth, and it goes in the only possible place: the leftmost free spot on the bottom level, which is the end of the array.

## Parent and child arithmetic

With the root at index 0, the positions follow a pattern you can compute:

| From index `i` | Index |
| --- | --- |
| left child | `2 * i + 1` |
| right child | `2 * i + 2` |
| parent | `(i - 1) / 2`, for `i > 0` |

The parent formula uses integer division, which drops the remainder, so both children of index 1 (indexes 3 and 4) lead back to 1. Check it on the heap above:

```swift run
let heap = [1, 3, 2, 7, 4, 5, 9]

for i in heap.indices {
    let left = 2 * i + 1
    let right = 2 * i + 2
    var line = "index \(i) holds \(heap[i])"
    if i > 0 {
        line += ", parent \(heap[(i - 1) / 2])"
    }
    if left < heap.count {
        line += ", children \(heap[left])"
    }
    if right < heap.count {
        line += " and \(heap[right])"
    }
    print(line)
}
```

```output
index 0 holds 1, children 3 and 2
index 1 holds 3, parent 1, children 7 and 4
index 2 holds 2, parent 1, children 5 and 9
index 3 holds 7, parent 3
index 4 holds 4, parent 3
index 5 holds 5, parent 2
index 6 holds 9, parent 2
```

A child exists only if its index is less than `count`. Indexes 3 to 6 have no children: they're the **leaves**, and in any heap the leaves are the second half of the array.

With the formulas, checking the heap property is one loop: every index except the root must be ≥ its parent.

```swift run
func isMinHeap(_ items: [Int]) -> Bool {
    for child in items.indices.dropFirst() {
        if items[(child - 1) / 2] > items[child] {
            return false
        }
    }
    return true
}

print(isMinHeap([1, 3, 2, 7, 4, 5, 9]))
print(isMinHeap([1, 2, 3, 4, 5, 6, 7]))
print(isMinHeap([2, 1, 3]))
print(isMinHeap([1, 5, 2, 4]))
```

```output
true
true
false
false
```

A sorted array is always a valid min-heap: every parent comes earlier, so it's no bigger. The reverse isn't true. `[1, 5, 2, 4]` fails because index 3 holds 4, and its parent at index 1 holds 5.

## Why no pointers?

You could build a heap from tree nodes with `left` and `right` references, like the `TreeNode` from [TreeNode in Swift: class vs indirect enum](/dsa/learn/tree-node-swift). The array is better here, for four reasons:

- **The shape is fixed by the count**, so positions can be calculated instead of stored. A node-based heap would spend memory on two references per value, plus reference counting.
- **"The next free spot"** is just the end of the array, and appending is amortised O(1). With nodes, finding the bottom level's next free spot takes work.
- **Contiguous memory** is fast to walk: the processor loads neighbouring values together.
- **Value semantics for free.** A struct around an array copies like any other Swift value, as you saw in [Collections are values](/dsa/learn/swift-collections-are-values).

Watch values arrive in a heap. The tree and the array are the same data drawn two ways: each new value lands at the end of the array, which is the next spot on the bottom row. (The swaps that follow are the next lesson's subject.)

```visual heap
operations: [5, 3, 8, 1, 9, 2]
```

## How tall is a heap?

A complete tree is as short as a binary tree can be. Each level holds twice as many nodes as the one above, so n nodes need only about log₂ n levels. Walk up from the last index to the root, counting steps, and you get the height:

```swift run
func height(ofHeapWith count: Int) -> Int {
    var steps = 0
    var index = count - 1                    // the last node
    while index > 0 {
        index = (index - 1) / 2              // up to its parent
        steps += 1
    }
    return steps
}

for count in [1, 2, 3, 7, 8, 1_000, 1_000_000] {
    print("\(count) values: height \(height(ofHeapWith: count))")
}
```

```output
1 values: height 0
2 values: height 1
3 values: height 1
7 values: height 2
8 values: height 3
1000 values: height 9
1000000 values: height 19
```

The height is ⌊log₂ n⌋. A million values are only 19 levels deep. Every heap operation in this module walks a single path between the root and a leaf, so that's where O(log n) comes from.

<Callout kind="gotcha" title="Swift gotcha: the root's 'parent'">
Swift's integer division rounds toward zero, so `(0 - 1) / 2` is `0`, not `-1`. The formula quietly says the root is its own parent. Code that walks upward must stop at index 0 explicitly (`while child > 0`), or it will compare the root with itself forever.
</Callout>

<Callout kind="gotcha" title="0-based or 1-based?">
Many textbooks put the root at index **1** and leave index 0 empty. Then the children of i are `2i` and `2i + 1`, and the parent is `i / 2`. Both layouts work, but mixing them is a classic bug: with a 0-based array, `2 * i` for the left child makes the root its own child. Swift arrays start at 0, so this course uses `2i + 1`, `2i + 2` and `(i - 1) / 2` throughout.
</Callout>
