## Why it matters

A monitoring dashboard shows the **median** response time of a service, updated with every request. A fitness app shows your median pace as a run goes on. The median (the middle value once sorted) is popular because one wild outlier can't drag it around the way it drags an average. But keeping it up to date is awkward: sorting after every new value costs O(n log n) per value. The **two heaps** pattern keeps the median ready in O(1) and updates it in O(log n), and it's a classic hard interview problem that teaches a reusable idea: split the data into two halves, each held by the heap that exposes its middle edge.

## The idea: two halves, each facing the middle

Sort the values so far and cut them in the middle. The median depends only on the values next to the cut: the **largest** of the lower half and the **smallest** of the upper half. So keep:

- the **lower half** in a **max-heap**, so its largest value is on top, and
- the **upper half** in a **min-heap**, so its smallest value is on top.

Both middle values are then one `peek()` away. You never need the rest of either half in order, which is exactly the kind of partial order a heap is good at.

Two rules keep the halves meaningful:

1. **Order:** every value in `lower` is ≤ every value in `upper`.
2. **Balance:** `lower` holds as many values as `upper`, or exactly one more.

With both rules holding, the median is easy:

| Count | Sizes | Median |
| --- | --- | --- |
| Odd | `lower` has one more | `lower`'s top |
| Even | equal | the mean of both tops |

<Callout kind="analogy">
Picture a line of people sorted by height, split into two rooms. In the left room, everyone faces the door and the tallest stands nearest it. In the right room, the shortest stands nearest. Whoever is nearest the doors is the middle of the whole line. When a newcomer arrives, they go into the right room for their height, and if one room gets too crowded, the person nearest its door steps across.
</Callout>

## Adding a value

1. **Pick the half.** If the value is bigger than `lower`'s top, it belongs in `upper`; otherwise in `lower`. (When `lower` is empty, it goes into `lower`.)
2. **Rebalance.** If `lower` now has two more than `upper`, move `lower`'s top across. If `upper` now has more than `lower`, move `upper`'s top across.

Moving a **top** across never breaks the order rule: `lower`'s top is the largest value on the lower side, so it can join the upper side and still be ≤ everything there. Here it is, with the halves printed after each value:

```swift run
// The heap from "Build a generic Heap<T>", compacted, plus unordered and replaceTop
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    var count: Int { items.count }
    var isEmpty: Bool { items.isEmpty }
    var unordered: [Element] { items }
    func peek() -> Element? { items.first }

    mutating func insert(_ element: Element) {
        items.append(element)
        var child = items.count - 1
        while child > 0 && areInIncreasingOrder(items[child], items[(child - 1) / 2]) {
            items.swapAt(child, (child - 1) / 2)
            child = (child - 1) / 2
        }
    }

    mutating func pop() -> Element? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        siftDownFromTop()
        return top
    }

    /// Replaces the top (the heap must not be empty) with one sift down
    mutating func replaceTop(with element: Element) {
        items[0] = element
        siftDownFromTop()
    }

    private mutating func siftDownFromTop() {
        var parent = 0
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var first = parent
            if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
            if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
            if first == parent { return }
            items.swapAt(parent, first)
            parent = first
        }
    }
}

struct MedianTracker {
    private var lower = Heap<Int>(areInIncreasingOrder: >)    // the smaller half, largest on top
    private var upper = Heap<Int>(areInIncreasingOrder: <)    // the larger half, smallest on top

    mutating func add(_ value: Int) {
        // 1. Put it in the right half
        if let top = lower.peek(), value > top {
            upper.insert(value)
        } else {
            lower.insert(value)
        }
        // 2. Rebalance: lower holds as many values as upper, or one more
        if lower.count > upper.count + 1 {
            upper.insert(lower.pop()!)
        } else if upper.count > lower.count {
            lower.insert(upper.pop()!)
        }
    }

    var median: Double? {
        guard let middle = lower.peek() else { return nil }
        if lower.count > upper.count {
            return Double(middle)                                 // odd count: the middle value
        }
        return (Double(middle) + Double(upper.peek()!)) / 2       // even count: mean of the two middles
    }

    var halves: String {
        "\(lower.unordered.sorted()) | \(upper.unordered.sorted())"
    }
}

var tracker = MedianTracker()
print(tracker.median as Any)
for value in [5, 15, 1, 3, 8, 7, 9, 10] {
    tracker.add(value)
    print("add \(value): \(tracker.halves), median \(tracker.median!)")
}
```

```output
nil
add 5: [5] | [], median 5.0
add 15: [5] | [15], median 10.0
add 1: [1, 5] | [15], median 5.0
add 3: [1, 3] | [5, 15], median 4.0
add 8: [1, 3, 5] | [8, 15], median 5.0
add 7: [1, 3, 5] | [7, 8, 15], median 6.0
add 9: [1, 3, 5, 7] | [8, 9, 15], median 7.0
add 10: [1, 3, 5, 7] | [8, 9, 10, 15], median 7.5
```

Follow two steps:

- **add 3:** 3 ≤ 5 (`lower`'s top), so it joins `lower`, which becomes [1, 3, 5] against [15]: two more. `lower`'s top, 5, crosses to `upper`. The halves are [1, 3] and [5, 15], and the median is (3 + 5) / 2 = 4.0.
- **add 7:** 7 > 5, so it joins `upper`: [7, 8, 15] against [1, 3, 5]. `upper` has more, so its top, 7, crosses back. The median is (5 + 7) / 2 = 6.0.

Each add does at most three heap operations (one insert, then possibly one pop and one insert), so it's **O(log n)**. Reading the median is two peeks: **O(1)**. The memory is O(n): every value is kept, because any of them might become the median later.

<Callout kind="gotcha" title="Swift gotcha: averaging two Ints">
`(a + b) / 2` with `Int`s drops the .5, so the median of 3 and 4 would come out as 3. Convert first: `(Double(a) + Double(b)) / 2`. Converting first also avoids overflow: two `Int`s near `Int.max` overflow when added, but their `Double` values don't.
</Callout>

## Why both rules are needed

**Without the order rule**, the tops aren't the middle values. If 100 sits in `lower` and 1 in `upper`, `lower`'s top is not the largest of the smaller half. Step 1, comparing with `lower`'s top, is what maintains it.

**Without the balance rule**, the cut isn't in the middle. If `lower` held 10 values and `upper` 2, `lower`'s top would be the 10th smallest, not the median. Step 2 maintains it.

Choosing "`lower` gets the extra one" is a convention. Letting `upper` have the extra one works just as well, as long as the median code agrees.

## Beyond the median

**Any percentile.** To track the 90th percentile, keep `lower` at 90% of the values instead of half, and rebalance to that ratio. The top of `lower` is then the 90th percentile.

**A sliding window median** (the median of the last k values) needs to **remove** the value leaving the window, which might be deep inside either heap. Heaps can't remove from the middle cheaply. The usual answer is **lazy deletion**.

## Lazy deletion: removing without searching

You met this idea in [First unique in a stream](/dsa/learn/queue-streams): instead of removing an item now, note that it's dead, and throw it away only when it reaches the front. For a heap:

- To delete a value, **record it** in a dictionary of pending removals (a count, because values can repeat). O(1).
- Before trusting the top, **clean it**: while the top has a pending removal, pop it and decrement its count.

Stale values buried deep in the heap do no harm: you never look at them until they surface. Every value is pushed once and popped at most once, so the extra work over a whole run is O(n log n). The price is memory: the heap may hold stale values for a while.

### The skyline, in O(n log n)

In [The skyline problem](/dsa/learn/iv-skyline), the sweep needed the tallest **active** building, with buildings starting and ending as it went. A sorted array made each update O(n), for O(n²) in the worst case. A max-heap with lazy deletion fixes that: push a height when its building starts, record it as pending when the building ends, and clean the top before reading it.

```swift run
// The heap from "Build a generic Heap<T>", compacted, plus unordered and replaceTop
struct Heap<Element> {
    private var items: [Element] = []
    private let areInIncreasingOrder: (Element, Element) -> Bool

    init(areInIncreasingOrder: @escaping (Element, Element) -> Bool) {
        self.areInIncreasingOrder = areInIncreasingOrder
    }

    var count: Int { items.count }
    var isEmpty: Bool { items.isEmpty }
    var unordered: [Element] { items }
    func peek() -> Element? { items.first }

    mutating func insert(_ element: Element) {
        items.append(element)
        var child = items.count - 1
        while child > 0 && areInIncreasingOrder(items[child], items[(child - 1) / 2]) {
            items.swapAt(child, (child - 1) / 2)
            child = (child - 1) / 2
        }
    }

    mutating func pop() -> Element? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        siftDownFromTop()
        return top
    }

    /// Replaces the top (the heap must not be empty) with one sift down
    mutating func replaceTop(with element: Element) {
        items[0] = element
        siftDownFromTop()
    }

    private mutating func siftDownFromTop() {
        var parent = 0
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var first = parent
            if left < items.count && areInIncreasingOrder(items[left], items[first]) { first = left }
            if right < items.count && areInIncreasingOrder(items[right], items[first]) { first = right }
            if first == parent { return }
            items.swapAt(parent, first)
            parent = first
        }
    }
}

// The skyline from M33, with a max-heap and lazy deletion: O(n log n)
func skyline(_ buildings: [[Int]]) -> [[Int]] {
    // A start is (left, -height) and an end is (right, height): the same tie-breaking order as before
    var events: [(x: Int, key: Int)] = []
    for building in buildings {
        events.append((building[0], -building[2]))
        events.append((building[1], building[2]))
    }
    events.sort { ($0.x, $0.key) < ($1.x, $1.key) }

    var active = Heap<Int>(areInIncreasingOrder: >)      // heights, tallest on top, maybe some stale
    var pendingRemoval: [Int: Int] = [:]                 // height -> copies that have ended
    var points: [[Int]] = []
    for event in events {
        if event.key < 0 {
            active.insert(-event.key)
        } else {
            pendingRemoval[event.key, default: 0] += 1   // don't search for it: just note it
        }
        // Only the top matters, so only clean up stale heights when they reach the top
        while let top = active.peek(), let pending = pendingRemoval[top], pending > 0 {
            _ = active.pop()
            pendingRemoval[top] = pending - 1
        }
        let height = active.peek() ?? 0
        if points.last?[1] != height {
            points.append([event.x, height])
        }
    }
    return points
}

print(skyline([[1, 5, 3], [2, 4, 6], [3, 8, 4], [10, 12, 2]]))
print(skyline([[0, 3, 5], [3, 6, 5]]))
print(skyline([[1, 4, 2], [1, 4, 7], [1, 4, 5]]))
```

```output
[[1, 3], [2, 6], [4, 4], [8, 0], [10, 2], [12, 0]]
[[0, 5], [6, 0]]
[[1, 7], [4, 0]]
```

The answers match M33's. Each of the n heights is pushed once and popped at most once, and the sort costs O(n log n), so the whole sweep is **O(n log n)** in the worst case. When the 6-high building ends at x = 4, its height is on top, so it's cleaned off at once and the outline drops to 4. If a short building ends while a taller one is still standing, its height stays buried in the heap, harmlessly, until it surfaces.

(`_ = active.pop()` throws the result away on purpose. This compact heap's `pop()` isn't marked `@discardableResult`, so without `_ =`, Swift warns about an unused result.)

For the sliding window median, lazy deletion gets one more wrinkle: the balance rule must count only the **live** values in each heap, so you track the live sizes separately from `count`. The idea is the same.

<Callout kind="gotcha" title="Common mistakes">
- **Inserting into the wrong half.** Compare with `lower`'s top, not `upper`'s, and handle an empty `lower` (the first value).
- **Rebalancing with `if` in the wrong order, or not at all.** After one insert, at most one value needs to move, but it must be the right one: `lower`'s top goes up, `upper`'s top comes down.
- **Integer averaging.** Convert to `Double` before adding.
- **Lazy deletion without counts.** A `Set` of deleted values breaks with duplicates: removing one 5 must leave the other 5 alive.
</Callout>
