## Why it matters

Popping a heap until it's empty gives its values in order. Turn that into an algorithm and you get **heap sort**: O(n log n) in the **worst** case, like merge sort, but **in place**, with O(1) extra memory, like quick sort. No other simple comparison sort has both. That pairing is why heap sort is the safety net inside introsort, which you met in [Random pivots and 3-way partitioning](/dsa/learn/sort-quick-pivots), and why the Linux kernel's general-purpose `sort()` is a heap sort: the kernel wants a guaranteed bound and no memory allocation.

## The idea: the heap and the sorted part share the array

A simple version would pop a min-heap into a second array. Heap sort avoids the second array with a trick:

1. **Heapify the array into a max-heap**, in place, in O(n). The largest value is now at index 0.
2. The largest value belongs at the **end**. Swap index 0 with the last index. The last slot is now final: it holds the largest value, in its sorted position.
3. Treat the heap as **one slot shorter**, and sift the new root down within that shorter heap, O(log n). The next largest value rises to index 0.
4. Repeat until the heap has one element left.

At every moment the array is two parts: a max-heap at the front, shrinking, and a sorted run at the back, growing. A **max**-heap gives increasing order, because the largest value is removed first and placed last.

```swift run
/// Sifts items[index] down a max-heap that occupies items[0..<end]
func siftDown(_ items: inout [Int], from index: Int, end: Int) {
    var parent = index
    while true {
        let left = 2 * parent + 1
        let right = left + 1
        var largest = parent
        if left < end && items[left] > items[largest] { largest = left }
        if right < end && items[right] > items[largest] { largest = right }
        if largest == parent { return }
        items.swapAt(parent, largest)
        parent = largest
    }
}

func heapSort(_ items: inout [Int]) {
    for index in stride(from: items.count / 2 - 1, through: 0, by: -1) {
        siftDown(&items, from: index, end: items.count)
    }
    print("max-heap:", items)
    var end = items.count - 1
    while end > 0 {
        items.swapAt(0, end)                     // the largest joins the sorted part
        siftDown(&items, from: 0, end: end)      // repair the smaller heap
        print("heap \(Array(items[..<end])) | sorted \(Array(items[end...]))")
        end -= 1
    }
}

var numbers = [5, 2, 9, 1, 6, 3]
heapSort(&numbers)
print(numbers)
```

```output
max-heap: [9, 6, 5, 1, 2, 3]
heap [6, 3, 5, 1, 2] | sorted [9]
heap [5, 3, 2, 1] | sorted [6, 9]
heap [3, 1, 2] | sorted [5, 6, 9]
heap [2, 1] | sorted [3, 5, 6, 9]
heap [1] | sorted [2, 3, 5, 6, 9]
[1, 2, 3, 5, 6, 9]
```

Watch the two parts trade places. The tree shows only the heap; green array slots are the sorted part:

```visual heap
program: heapSort
items: [5, 2, 9, 1, 6, 3]
```

What to notice:

- The `end` parameter is the whole trick. `siftDown` treats `items[0..<end]` as the heap and never looks past it, so the sorted part at the back is safe.
- In the first round, 9 swaps with the 3 at the end. Then 3 sinks: its children are 6 and 5, so it swaps with 6. At index 1, its children are 1 and 2, both smaller, so it stops. The heap is `[6, 3, 5, 1, 2]`, with 6 on top.
- When one element is left in the heap, it's the smallest, and it's already at index 0. The loop stops at `end > 0`.

## The cost

- **Heapify:** O(n), from [O(n) heapify](/dsa/learn/heap-heapify).
- **n − 1 rounds**, each one swap and one sift down of at most log₂ n levels: O(n log n).

That's **O(n log n) in every case**, and the extra memory is a handful of `Int` variables: **O(1)**. No recursion either, so no call stack to worry about.

Unlike insertion sort or Timsort, heap sort is **not adaptive**: already-sorted input gets no discount, because heapify scrambles it into a heap before sorting begins.

```swift run
// Comparisons heap sort makes on 10,000 values in different starting orders
var comparisons = 0

func siftDown(_ items: inout [Int], from index: Int, end: Int) {
    var parent = index
    while true {
        let left = 2 * parent + 1
        let right = left + 1
        var largest = parent
        if left < end {
            comparisons += 1
            if items[left] > items[largest] { largest = left }
        }
        if right < end {
            comparisons += 1
            if items[right] > items[largest] { largest = right }
        }
        if largest == parent { return }
        items.swapAt(parent, largest)
        parent = largest
    }
}

func heapSort(_ items: inout [Int]) {
    for index in stride(from: items.count / 2 - 1, through: 0, by: -1) {
        siftDown(&items, from: index, end: items.count)
    }
    var end = items.count - 1
    while end > 0 {
        items.swapAt(0, end)
        siftDown(&items, from: 0, end: end)
        end -= 1
    }
}

let n = 10_000
let inputs = [
    ("already sorted", Array(0..<n)),
    ("reversed", Array((0..<n).reversed())),
    ("scrambled", (0..<n).map { ($0 * 7_919) % n }),
    ("all equal", Array(repeating: 7, count: n)),
]
for (name, values) in inputs {
    var items = values
    comparisons = 0
    heapSort(&items)
    print("\(name): \(comparisons) comparisons, sorted: \(items == values.sorted())")
}
```

```output
already sorted: 244460 comparisons, sorted: true
reversed: 226682 comparisons, sorted: true
scrambled: 235547 comparisons, sorted: true
all equal: 29994 comparisons, sorted: true
```

Sorted, reversed and scrambled input all cost about the same, roughly 1.8 × n log₂ n (n log₂ n is about 133,000 here). Equal values are the one cheap case: with strict comparisons, no child is ever larger than its parent, so every sift down stops at once.

## Not stable

Heap sort moves elements in long jumps, from the root to the end and down the tree, so equal elements can change their relative order. Sort orders by total, and watch the three orders of 20:

```swift run
// Heap sort by a key, compared with Swift's stable sorted(by:)
func heapSort<T>(_ items: inout [T], by key: (T) -> Int) {
    func siftDown(from index: Int, end: Int) {
        var parent = index
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var largest = parent
            if left < end && key(items[left]) > key(items[largest]) { largest = left }
            if right < end && key(items[right]) > key(items[largest]) { largest = right }
            if largest == parent { return }
            items.swapAt(parent, largest)
            parent = largest
        }
    }
    for index in stride(from: items.count / 2 - 1, through: 0, by: -1) {
        siftDown(from: index, end: items.count)
    }
    var end = items.count - 1
    while end > 0 {
        items.swapAt(0, end)
        siftDown(from: 0, end: end)
        end -= 1
    }
}

let orders = [(total: 20, id: "A"), (total: 10, id: "B"), (total: 20, id: "C"), (total: 20, id: "D")]
var heapSorted = orders
heapSort(&heapSorted, by: { $0.total })
print("heap sort:  ", heapSorted.map { "\($0.total)\($0.id)" })
print("sorted(by:):", orders.sorted { $0.total < $1.total }.map { "\($0.total)\($0.id)" })
```

```output
heap sort:   ["10B", "20C", "20D", "20A"]
sorted(by:): ["10B", "20A", "20C", "20D"]
```

Order A was first among the 20s, and heap sort put it last. Swift's `sort` keeps A, C, D in their original order, as [How Swift sorts, and sorting custom types](/dsa/learn/sort-swift-sort) explained. When stability matters, such as sorting a table by one column after another, heap sort is the wrong tool (unless you add the original index as a tie-breaker, which costs O(n) memory and gives up the main advantage).

(The nested `siftDown` function changes `items`, an `inout` parameter of the outer function. That's allowed because the nested function never escapes: it's only called while `heapSort` is running.)

## Why it's not everyone's default

If it's O(n log n) worst case and in place, why isn't heap sort the standard library sort everywhere? Two practical reasons:

- **More comparisons.** Two per level of each sift down adds up to nearly 2 n log₂ n (the run above measured about 1.8 n log₂ n), against quick sort's roughly 1.4 n log₂ n on average.
- **Scattered memory access.** A sift down jumps from index i to 2i + 1: far apart in a big array. Quick sort and merge sort sweep through memory in order, which modern processors handle much faster.

So heap sort is usually slower than a good quick sort, but never catastrophically slower. That makes it ideal insurance.

## Heap sort inside introsort

Introsort runs quick sort, counts its recursion depth, and if the depth passes about 2 log₂ n (the pivots are going badly), it heap-sorts the current range instead. That needs a heap sort on part of the array, `items[low...high]`. The only change is an offset: heap index i lives at `items[low + i]`.

```swift run
// Heap sort on items[low...high] only: heap index i lives at items[low + i]
func heapSort(_ items: inout [Int], _ low: Int, _ high: Int) {
    let count = high - low + 1
    func siftDown(from index: Int, end: Int) {
        var parent = index
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var largest = parent
            if left < end && items[low + left] > items[low + largest] { largest = left }
            if right < end && items[low + right] > items[low + largest] { largest = right }
            if largest == parent { return }
            items.swapAt(low + parent, low + largest)
            parent = largest
        }
    }
    for index in stride(from: count / 2 - 1, through: 0, by: -1) {
        siftDown(from: index, end: count)
    }
    var end = count - 1
    while end > 0 {
        items.swapAt(low, low + end)
        siftDown(from: 0, end: end)
        end -= 1
    }
}

var items = [99, 98, 7, 3, 9, 1, 5, 0, -1]
heapSort(&items, 2, 6)              // sorts only indexes 2 to 6
print(items)
```

```output
[99, 98, 1, 3, 5, 7, 9, 0, -1]
```

Everything outside indexes 2 to 6 is untouched. That's the `heapSort(&items, low, high)` call in the introsort outline from M31.

## Comparing the O(n log n) sorts

| Sort | Worst case | Extra memory | Stable | Adaptive |
| --- | --- | --- | --- | --- |
| Merge sort | O(n log n) | O(n) | Yes | No |
| Quick sort (random pivot) | O(n²), very unlikely | O(log n) stack | No | No |
| Heap sort | O(n log n) | O(1) | No | No |
| Introsort | O(n log n) | O(log n) stack | No | No |
| Swift's `sort` | O(n log n) | O(n) | Yes | Yes |

None of them can beat O(n log n) comparisons in the worst case, as [The Ω(n log n) lower bound](/dsa/learn/sort-lower-bound) proved. Heap sort reaches the bound with the least memory.

DSAKit has heap sort as an `Array` method, built on the same sift down as its `Heap`:

```swift
import DSAKit

var scores = [72, 95, 61, 88]
scores.heapSort()                   // [61, 72, 88, 95]
scores.heapSort(by: >)              // [95, 88, 72, 61]
```

<Callout kind="gotcha" title="Common mistakes">
- **Using a min-heap for increasing order.** Swapping the smallest value to the end puts it in the wrong place. In-place heap sort into increasing order needs a **max**-heap.
- **Sifting down over the whole array.** After the first swap, the back of the array is sorted, and sifting down past `end` drags sorted values back into the heap. Pass the heap's current size.
- **Stopping one round late or early.** The loop runs while `end > 0`: when the heap has one element left, it's already in place.
</Callout>
