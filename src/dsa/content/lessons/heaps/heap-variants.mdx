## Why it matters

The binary heap is the default priority queue, but two variations matter once performance gets serious. A **d-ary heap** gives each node d children instead of 2, making the tree shorter, which speeds up inserts at some cost to pops. An **indexed priority queue** lets you find an item that's already in the heap and change its priority, the **decrease-key** operation. Both exist mainly for one famous customer: Dijkstra's shortest-path algorithm, which you'll meet in M44, where a priority queue holds the tentative distance to every place and keeps lowering them. They also turn up in competitive programming, event simulations and network routers.

## d-ary heaps

Nothing about the array trick needs exactly two children. With d children per node, still 0-based:

| From index `i` | Index |
| --- | --- |
| children | `d * i + 1` through `d * i + d` |
| parent | `(i - 1) / d`, for `i > 0` |

With d = 2 these are the familiar formulas. A complete d-ary tree with n nodes is only about log_d n levels tall, where log_d means the logarithm to base d: with d = 4, half as many levels as a binary heap, since log₄ n = (log₂ n) / 2.

The trade-off is in the two sifts:

- **Sift up** compares a node with its single parent at each level. Fewer levels, fewer comparisons: O(log_d n).
- **Sift down** must find the smallest of **d children** at each level, d comparisons per level: O(d log_d n).

So bigger d makes inserts (and decrease-keys, which sift up) cheaper, and pops dearer. Count them on 50,000 values, pushed in the worst order for sift up:

```swift run
// A min-heap where every node has up to d children, counting comparisons
struct DaryHeap {
    let d: Int
    var items: [Int] = []
    var comparisons = 0

    mutating func push(_ value: Int) {
        items.append(value)
        var child = items.count - 1
        while child > 0 {
            let parent = (child - 1) / d
            comparisons += 1
            if items[child] >= items[parent] { break }
            items.swapAt(child, parent)
            child = parent
        }
    }

    mutating func pop() -> Int? {
        guard !items.isEmpty else { return nil }
        items.swapAt(0, items.count - 1)
        let top = items.removeLast()
        var parent = 0
        while true {
            let firstChild = d * parent + 1
            if firstChild >= items.count { break }
            var smallest = firstChild                    // find the smallest of up to d children
            for child in (firstChild + 1)..<min(firstChild + d, items.count) {
                comparisons += 1
                if items[child] < items[smallest] { smallest = child }
            }
            comparisons += 1
            if items[smallest] >= items[parent] { break }
            items.swapAt(parent, smallest)
            parent = smallest
        }
        return top
    }
}

let n = 50_000
let values = Array((0..<n).reversed())             // each push is the smallest so far: the worst case
for d in [2, 4, 8, 16] {
    var heap = DaryHeap(d: d)
    for value in values {
        heap.push(value)
    }
    let pushComparisons = heap.comparisons
    heap.comparisons = 0
    var inOrder = true
    for expected in 0..<n where heap.pop() != expected {
        inOrder = false
    }
    print("d = \(d): pushes \(pushComparisons), pops \(heap.comparisons) comparisons, in order: \(inOrder)")
}
```

```output
d = 2: pushes 684481, pops 1293963 comparisons, in order: true
d = 4: pushes 370876, pops 1358505 comparisons, in order: true
d = 8: pushes 257202, pops 1832617 comparisons, in order: true
d = 16: pushes 195340, pops 2700441 comparisons, in order: true
```

Going from d = 2 to d = 4 nearly halves the push comparisons, while pops cost only about 5% more. Past that, pops get expensive quickly. In practice, **d = 4** is a popular choice, and not only because of the counts: a node's four children sit next to each other in the array, so finding the smallest touches one small region of memory, which modern processors handle very efficiently.

**When to pick a bigger d:** when inserts and decrease-keys greatly outnumber pops. Dijkstra on a dense graph with V places and E connections does up to E decrease-keys but only V pops. With d around E / V, its running time becomes O(E log_(E/V) V), which approaches O(E) as the graph gets denser.

## The problem with changing a priority

A plain heap supports insert, peek and pop. But suppose the item "Cork, tentative distance 9" is somewhere inside the heap, and you find a shorter route: distance 5. To lower its key, you'd need to **find** it first, and a heap has no idea where anything is except the top. Searching the array is O(n).

There are two standard fixes.

## Fix 1: an indexed priority queue

Give every item a small integer **id** (0 to n − 1: town numbers, node numbers), and keep a second array, `position`, recording **where each id currently sits** in the heap. Then finding an item is O(1), and decrease-key is: set the new key, then sift up from that position, O(log n). A smaller key can only need to move **up**.

The price is bookkeeping: **every swap must update the positions** of both items it moves.

```swift run
// A min-heap of ids 0..<capacity, each with a key, supporting decreaseKey
struct IndexedMinHeap {
    private var heap: [Int] = []          // ids, arranged as a binary heap by their keys
    private var position: [Int]           // position[id]: where id sits in heap, or -1 if absent
    private var key: [Int]

    init(capacity: Int) {
        position = Array(repeating: -1, count: capacity)
        key = Array(repeating: 0, count: capacity)
    }

    var isEmpty: Bool { heap.isEmpty }

    func contains(_ id: Int) -> Bool {
        position[id] != -1
    }

    mutating func insert(_ id: Int, key newKey: Int) {
        key[id] = newKey
        heap.append(id)
        position[id] = heap.count - 1
        siftUp(from: heap.count - 1)
    }

    /// Lowers the key of an id already in the heap. A smaller key can only move up. O(log n)
    mutating func decreaseKey(_ id: Int, to newKey: Int) {
        precondition(contains(id) && newKey <= key[id], "decreaseKey needs a smaller key for an id in the heap")
        key[id] = newKey
        siftUp(from: position[id])
    }

    mutating func popMin() -> (id: Int, key: Int)? {
        guard let top = heap.first else { return nil }
        swapNodes(0, heap.count - 1)
        heap.removeLast()
        position[top] = -1
        siftDown(from: 0)
        return (top, key[top])
    }

    /// Every swap must update both ids' positions
    private mutating func swapNodes(_ i: Int, _ j: Int) {
        heap.swapAt(i, j)
        position[heap[i]] = i
        position[heap[j]] = j
    }

    private mutating func siftUp(from index: Int) {
        var child = index
        while child > 0 && key[heap[child]] < key[heap[(child - 1) / 2]] {
            swapNodes(child, (child - 1) / 2)
            child = (child - 1) / 2
        }
    }

    private mutating func siftDown(from index: Int) {
        var parent = index
        while true {
            let left = 2 * parent + 1
            let right = left + 1
            var smallest = parent
            if left < heap.count && key[heap[left]] < key[heap[smallest]] { smallest = left }
            if right < heap.count && key[heap[right]] < key[heap[smallest]] { smallest = right }
            if smallest == parent { return }
            swapNodes(parent, smallest)
            parent = smallest
        }
    }
}

let towns = ["Ayr", "Bath", "Cork", "Derry", "Ely"]
var queue = IndexedMinHeap(capacity: towns.count)
for (id, distance) in [0, 7, 9, 14, 20].enumerated() {
    queue.insert(id, key: distance)
}

func popAndPrint() {
    let (id, distance) = queue.popMin()!
    print("pop \(towns[id]) at \(distance)")
}

popAndPrint()
queue.decreaseKey(2, to: 5)               // a shorter way to Cork
queue.decreaseKey(4, to: 11)              // and to Ely
popAndPrint()
queue.decreaseKey(3, to: 8)               // and to Derry
print("Bath still queued:", queue.contains(1), "| Ayr still queued:", queue.contains(0))
while !queue.isEmpty {
    popAndPrint()
}
```

```output
pop Ayr at 0
pop Cork at 5
Bath still queued: true | Ayr still queued: false
pop Bath at 7
pop Derry at 8
pop Ely at 11
```

What to notice:

- The heap array stores **ids**, and comparisons look up `key[id]`. The keys live in their own array indexed by id.
- `swapNodes` is the only place that swaps, so it's the only place that has to keep `position` correct. Funnelling every swap through one function is what keeps an indexed heap bug-free.
- `contains` is O(1): an id that has been popped has position −1. Dijkstra uses this to skip places that are already finished.
- Cork started at 9, was lowered to 5, and popped before Bath (7), exactly as a shortest-path search needs.

With the same bookkeeping, you can also **delete** any id (swap it with the last item, remove it, then sift the moved item up or down, whichever it needs) and **increase** a key (sift down).

## Fix 2: lazy decrease-key

The other approach skips the index entirely, and it's what most Swift Dijkstra implementations use. To lower a key, **insert a new entry** (id, new key) and leave the old one in the heap. When you pop an entry, check whether it's stale: if its key is bigger than the best known key for that id, or the id is already finished, throw it away and pop again.

```swift
// Lazy decrease-key: duplicates are allowed, and stale entries are skipped when popped
var best = Array(repeating: Int.max, count: towns.count)
var heap = Heap<(id: Int, key: Int)>(areInIncreasingOrder: { $0.key < $1.key })
// To improve town 2 to distance 5:
if 5 < best[2] {
    best[2] = 5
    heap.insert((2, 5))
}
// When popping:
while let entry = heap.pop() {
    if entry.key > best[entry.id] { continue }      // stale: a better entry came out earlier
    // … process entry.id at distance entry.key
}
```

It's the same trick as lazy deletion in [Two heaps: median of a stream](/dsa/learn/heap-two-heaps). The heap can grow to one entry per decrease, up to E entries instead of V, but log E ≤ 2 log V for a simple graph, so the running time is still O((V + E) log V), and the code is far simpler.

| | Indexed priority queue | Lazy duplicates |
| --- | --- | --- |
| Decrease-key | O(log n), in place | O(log n), a new entry |
| Heap size | at most the number of ids | up to one entry per update |
| Needs | integer ids `0..<n`, a position array | nothing extra |
| Extra operations | delete any item, increase a key | only what a plain heap does |
| Typical use | memory-tight code, CP libraries, Prim's algorithm (M46) | most Dijkstra implementations |

<Callout kind="gotcha" title="Indexed heap pitfalls">
- **A swap that forgets `position`.** One missed update, and decrease-key sifts the wrong item. Route every swap through a single helper.
- **Sifting the wrong way.** A decreased key in a min-heap moves up; an increased key moves down. Calling the wrong sift silently leaves the heap broken.
- **Decreasing an id that isn't there.** Check `contains` first (or insert instead). Popped ids have position −1, and using −1 as an index crashes.
</Callout>
