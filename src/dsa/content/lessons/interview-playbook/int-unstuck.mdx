## Why it matters

Everyone gets stuck in interviews, including people who get the offer. What separates them is what happens next. Freezing in silence for ten minutes ends most rounds. Working through a few deliberate moves, out loud, usually finds a way forward, and even when it doesn't, it shows the interviewer exactly the kind of engineer they want: someone who has a method when they don't know the answer.

## Notice that you're stuck

The first move is admitting it. You're stuck if, for two or three minutes, you've had no new idea, or you keep circling back to the same one. Say so, calmly, and say what you're going to do: "I'm not seeing it yet. Let me work a bigger example by hand." That sentence alone turns dead time into visible process.

## The moves, in order

Try these roughly in this order. Each takes a minute or two.

1. **Re-read the problem and its constraints.** A detail you skimmed is often the key: "sorted", "values from 1 to n", "n ≤ 20", "at most one transaction".
2. **Work a bigger example by hand, slowly.** Don't think about code. Solve it as a person would, and watch what *you* do. Your hands often run the algorithm before your head names it.
3. **Simplify the problem.** Make n tiny, drop a constraint, or solve a special case: k = 1, no duplicates, one row instead of a grid. Solve that, then add the complication back.
4. **Run the patterns checklist** below. Ask each question about this problem.
5. **Fall back to brute force,** then look for its repeated work, as in [From brute force to optimal](/dsa/learn/int-optimising).
6. **Ask for a hint,** precisely.

## A worked example

> A sorted array of distinct numbers was rotated: some prefix was moved to the end. Find the smallest number in O(log n).

Suppose nothing comes to mind. Here's how the moves play out.

**Re-read.** "Sorted", "rotated", "distinct", "O(log n)". O(log n) on an array almost always means binary search, but binary search for what? There's no target.

**Example by hand.** `[15, 18, 22, 3, 7, 9, 11]`. Doing it as a person, you look for the place where the numbers *drop*: 22 to 3. Everything before the drop is bigger than everything after it.

**Simplify.** What if it isn't rotated at all, like `[3, 7, 9, 11]`? Then the first element is the minimum, and the last element is bigger than the middle. In the rotated example, the middle (3) is smaller than the last (11) too. What if the middle were 22? Then the middle is *bigger* than the last, so the drop must be to its right.

That's the idea: compare the middle with the last element. If the middle is bigger, the minimum is to the right of it; otherwise it's the middle or to its left. Each comparison halves the range.

```swift run
func rotatedMinimum(_ values: [Int]) -> Int {
    var low = 0
    var high = values.count - 1
    while low < high {
        let mid = low + (high - low) / 2
        if values[mid] > values[high] {
            low = mid + 1          // the drop is to the right of mid
        } else {
            high = mid             // mid itself might be the minimum
        }
    }
    return values[low]
}

print(rotatedMinimum([15, 18, 22, 3, 7, 9, 11]))
print(rotatedMinimum([3, 7, 9, 11]))
print(rotatedMinimum([9, 4]))
print(rotatedMinimum([5]))
```

```output
3
3
4
5
```

No flash of insight was needed: the constraint suggested the tool, the hand example showed the drop, and the simpler case showed which comparison finds it. [Rotated sorted arrays](/dsa/learn/bs-rotated) covers the family in full.

## The patterns checklist

When nothing comes, ask these questions about the problem. Each "yes" suggests something to try:

| Ask yourself | If yes, consider |
| --- | --- |
| Is it sorted, or would sorting help? | Binary search, two pointers |
| Is it about a contiguous subarray or substring? | Sliding window, prefix sums |
| Do I need "have I seen this before?" | A hash set or dictionary |
| Next greater or smaller, or nested brackets? | A stack, often monotonic |
| Top k, kth smallest, or repeatedly the minimum? | A heap |
| Ranges, meetings or bookings? | Sort by start or end, then sweep |
| Connections, regions or fewest steps? | BFS, DFS, union-find |
| Every combination, order or subset? | Backtracking |
| The best total over choices that interact? | Dynamic programming |
| A numeric answer with a yes/no check that flips once? | Binary search on the answer |

It's a short version of [Reading the pattern from constraints and wording](/dsa/learn/pat-recognition). Going through it out loud is useful in itself: "It's not sorted, and sorting would lose the order… it is about contiguous ranges, so prefix sums might help."

## Asking for a hint

A hint is not a failure. Interviewers expect to give some, and many rubrics only ask whether you used them well. What matters is *how* you ask. A vague request makes the interviewer guess where you are; a precise one shows that you've narrowed the problem down.

- Instead of "I don't know", try: "I can do it in O(n²) by checking every pair. The slow part is the inner search for a matching value, and I'm not sure how to avoid it. Am I looking in the right place?"
- Instead of "Can you give me a hint?", try: "Would sorting help here, or does the original order matter?"
- Instead of "Is this right?", try: "I'm thinking of a min-heap of size k. Does that sound reasonable before I code it?"

Each one says what you know, where you're stuck, and asks a question the interviewer can answer in a sentence.

When the hint comes, take it visibly: repeat it in your own words, then say how it changes your plan ([Thinking out loud](/dsa/learn/int-thinking-aloud)). If you don't understand it, say so and ask; a hint you pretend to understand is worth nothing.

<Callout kind="gotcha" title="Stuck mistakes">
- **Silent staring.** The interviewer can't help with a problem they can't see.
- **Abandoning a working plan late.** At minute 30, a correct brute force is worth more than a half-finished clever idea. Finish it, then talk about the better one.
- **Panic-coding.** Typing something, anything, without a plan usually produces code you'll have to delete.
- **Refusing hints.** Insisting on solving it alone wastes the interviewer's attempt to help, and they notice.
</Callout>
