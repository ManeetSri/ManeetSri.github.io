## Why it matters

In many interviews you can't run your code: it's a shared document, a whiteboard or an editor with no compiler. Even when you can, the interviewer is watching whether you check your own work. Finding your own bug and fixing it calmly is one of the strongest signals you can give. Leaving it for the interviewer to find is one of the weakest. Testing is a phase of the interview with its own minutes, not something you do if there's time.

## A testing routine

When the code is written, go through these in order. It takes five to seven minutes.

1. **Read it once, slowly.** Look at loop bounds, starting values, what's returned and every index expression. Many bugs are visible without tracing.
2. **Trace a small, normal example** through the code as written, with a trace table.
3. **Run the edge cases** past it, from the [edge-case checklist](/dsa/learn/algo-edge-cases).
4. **Fix out loud**, then re-check the case that failed.
5. **State the complexity.**

## A trace that finds a bug

Here's code a candidate might write for "return the length of the longest run of equal neighbouring values":

```swift
func longestRun(_ values: [Int]) -> Int {
    var best = 0
    var current = 1
    for i in 1..<values.count {
        if values[i] == values[i - 1] {
            current += 1
        } else {
            best = max(best, current)
            current = 1
        }
    }
    return best
}
```

It looks fine. Trace it on `[1, 1, 2, 2, 2]`, whose answer is 3, one row per pass, exactly as written ([Dry runs and trace tables](/dsa/learn/algo-dry-runs)):

| `i` | `values[i - 1]` | `values[i]` | equal? | `current` | `best` |
| --- | --- | --- | --- | --- | --- |
| start | | | | 1 | 0 |
| 1 | 1 | 1 | yes | 2 | 0 |
| 2 | 1 | 2 | no | 1 | 2 |
| 3 | 2 | 2 | yes | 2 | 2 |
| 4 | 2 | 2 | yes | 3 | 2 |

It returns 2. `current` reached 3, but `best` only learns about a run when the run *ends*, and the last run never ends inside the loop. Say exactly that: "The final run is never compared with `best`. I'll compare on every step instead."

This is why you pick an example whose answer you know, and why it helps when the interesting part is at the **end**: the first and last passes are where bugs live.

## Edge cases find the rest

Now the checklist, applied to this function:

- **Empty:** `1..<values.count` becomes `1..<0`, and Swift crashes on a range whose lower bound is above its upper bound.
- **One element:** the loop doesn't run, so it returns 0. The answer is 1.
- **All equal**, like `[4, 4, 4]`: the final-run bug again, returning 0.
- **All different, negatives:** fine once the rest is fixed.

Three bugs in eleven lines, all found without a compiler. Here's the fixed version, with the cases written as quick checks:

```swift run
func longestRun(_ values: [Int]) -> Int {
    guard !values.isEmpty else { return 0 }
    var best = 1
    var current = 1
    for i in values.indices.dropFirst() {
        current = values[i] == values[i - 1] ? current + 1 : 1
        best = max(best, current)
    }
    return best
}

let checks = [
    (longestRun([1, 1, 2, 2, 2]), 3, "longest run at the end"),
    (longestRun([]), 0, "empty"),
    (longestRun([7]), 1, "one element"),
    (longestRun([4, 4, 4]), 3, "all equal"),
    (longestRun([1, 2, 3]), 1, "all different"),
    (longestRun([-1, -1, 0]), 2, "negatives"),
]
var failures = 0
for (got, expected, label) in checks where got != expected {
    print("FAIL \(label): got \(got), expected \(expected)")
    failures += 1
}
print(failures == 0 ? "All \(checks.count) checks passed" : "\(failures) failed")
```

```output
All 6 checks passed
```

`values.indices.dropFirst()` is empty for an empty or one-element array, so it never builds an invalid range. Each check has a label, so a failure says which case broke.

## Quick checks in an interview editor

If the editor can run code, a few lines of checks at the bottom are worth writing. Three ways, from lightest to most informative:

```swift
precondition(longestRun([]) == 0)                    // stops the program if false, says nothing if true
assert(longestRun([7]) == 1, "one element")          // the same, but only in debug builds
print(longestRun([4, 4, 4]), "expected 3")           // you compare by eye
```

`assert` disappears in optimised builds, and `precondition` stays, as you saw in [precondition, assert, fatalError and defer](/dsa/learn/swift-assertions-defer). In an interview either is fine. A labelled table, like the one above, is best when there are several cases.

## Stress testing: fast against slow

When you have a brute force and a fast version, you can let the computer find the counterexamples. Generate many small random inputs and compare the two. A seeded generator makes the "random" inputs the same every run, so a failure is reproducible:

```swift run
struct SeededRandom: RandomNumberGenerator {
    var state: UInt64
    mutating func next() -> UInt64 {
        state = state &* 6_364_136_223_846_793_005 &+ 1_442_695_040_888_963_407
        return state ^ (state >> 29)
    }
}

func longestRun(_ values: [Int]) -> Int {
    guard !values.isEmpty else { return 0 }
    var best = 1
    var current = 1
    for i in values.indices.dropFirst() {
        current = values[i] == values[i - 1] ? current + 1 : 1
        best = max(best, current)
    }
    return best
}

// Obviously right, but O(n²): from every start, count how far the same value continues
func longestRunSlow(_ values: [Int]) -> Int {
    var best = 0
    for start in values.indices {
        var end = start
        while end < values.count && values[end] == values[start] {
            end += 1
        }
        best = max(best, end - start)
    }
    return best
}

var random = SeededRandom(state: 42)
var mismatches = 0
for _ in 0..<1_000 {
    let length = Int.random(in: 0...8, using: &random)
    let values = (0..<length).map { _ in Int.random(in: 0...2, using: &random) }
    if longestRun(values) != longestRunSlow(values) {
        mismatches += 1
    }
}
print("1000 random arrays, \(mismatches) mismatches")
```

```output
1000 random arrays, 0 mismatches
```

Small inputs with few distinct values (here 0, 1 and 2, up to 8 long) hit the edge cases far more often than big random ones. Run against the first version, the first empty array would have crashed it. There's rarely time for this in an interview, but it's how the tests in this course's companion package check your solutions, and it's a great habit for practice.

## Saying it out loud

The routine sounds like this:

> "Let me read it through once… the loop starts at 1, so I need to check the empty case. Now a trace of `[1, 1, 2, 2, 2]`… `best` ends at 2 but should be 3: the last run is never compared. I'll update `best` on every step instead. Now the edge cases: empty returns 0 thanks to the guard, a single element returns 1, all equal returns the count. Time is O(n), one pass; space O(1)."

<Callout kind="gotcha" title="Testing mistakes">
- **Tracing what you meant, not what you wrote.** Read each line as the computer would. The bug is usually in the gap between the two.
- **Only testing the statement's example.** It was chosen to explain the problem, not to break your code.
- **Skipping rows.** "And so on" is where the last-pass bug hides.
- **Fixing silently.** Say what was wrong and why the fix works; it's evidence of understanding.
</Callout>
