## Why it matters

A coding interview isn't a test of whether you can produce the right code eventually. It's 45 minutes in which someone watches *how* you get there. Candidates who know the material still fail because they spend 25 minutes on the wrong idea, or start typing in minute two and never recover. A plan for the clock is the cheapest improvement you can make, and it's the frame for everything else in this module.

## What the interviewer is scoring

Most companies score a coding round on roughly the same five things. They're the five criteria on the console's [Mock interview](/dsa/mock) page, so you'll practise against them:

| Criterion | What they want to see |
| --- | --- |
| Understanding | You restated the problem and asked about edge cases before coding |
| Approach | You started from something correct and reasoned towards something better |
| Correctness | The code works, edge cases included |
| Complexity | You stated the time and space cost, and why |
| Communication | They could follow your thinking the whole way |

Only one of the five is about whether the code works. A candidate who reaches a working O(n log n) solution while explaining every step often scores higher than one who silently types an O(n) solution with a bug they never find.

## The timeline

Here's a plan for a 45-minute round with one problem:

| Clock | Phase | You're done when |
| --- | --- | --- |
| 0–5 | Clarify | You've restated the problem, asked your questions and written two or three examples |
| 5–13 | Approach | You've described a brute force, found something better, and the interviewer agrees with the plan |
| 13–33 | Code | The solution is written, top to bottom |
| 33–40 | Test and analyse | You've traced an example, checked edge cases and stated the complexity |
| 40–45 | Your questions | You've asked them something you actually want to know |

These are the seven steps from [The problem-solving framework](/dsa/learn/start-problem-solving), squeezed onto a clock. Understand and Examples become Clarify. Brute force and Optimise become Approach. Code is Code. Test and Analyse come last.

If you like, the plan is a small program. Changing the numbers shows how the phases shift for a different round:

```swift run
let plan = [("Clarify", 5), ("Approach", 8), ("Code", 20), ("Test and analyse", 7), ("Your questions", 5)]
var clock = 0
for (phase, minutes) in plan {
    print("\(clock)–\(clock + minutes) min: \(phase)")
    clock += minutes
}
print("Total: \(clock) min")
```

```output
0–5 min: Clarify
5–13 min: Approach
13–33 min: Code
33–40 min: Test and analyse
40–45 min: Your questions
Total: 45 min
```

Notice where the time goes: less than half of it is typing. The other half is the part candidates skip.

## Each phase, briefly

The next lessons take these one at a time. Here's what each is for.

### Clarify (about 5 minutes)

Restate the problem in your own words and ask the questions whose answers change your solution: how big the input is, whether it can be empty, whether there are duplicates. Then write a couple of examples in the editor as comments. [Clarifying questions](/dsa/learn/int-clarifying) gives you the checklist.

### Approach (5 to 10 minutes)

Say the brute force out loud, with its complexity, even if it's obviously slow. Then look for the work it repeats and the pattern that removes it, as in [From brute force to optimal](/dsa/learn/int-optimising). Before writing anything, check with the interviewer: "I'm going to use a dictionary of counts, which makes this O(n). Shall I code that?" That one question protects you from coding the wrong thing for twenty minutes.

### Code (about 20 minutes)

Write clean code with good names, talking as you go ([Thinking out loud](/dsa/learn/int-thinking-aloud)). Leave small helpers for later if they're obvious: "I'll write `isValid` after the main loop." Twenty minutes is tight, which is why the approach must be settled first.

### Test and analyse (5 to 10 minutes)

Trace one small example through the code you actually wrote, then run the edge cases past it ([Testing your own code](/dsa/learn/int-testing)). Fix what you find, out loud. Then state the time and space complexity and the reason for each.

### Your questions (the last few minutes)

Have two real questions ready: about the team's codebase, how they review code, what a first project might be. It's also a moment to show you're someone they'd like to work with.

## Checkpoints, and what to do when you're behind

Two clock checks matter most:

- **At about 15 minutes, you should have an agreed approach.** If you don't, say so and commit to the best idea you have, even the brute force. A working brute force beats an unfinished clever idea.
- **At about 35 minutes, you should have code.** If you're not there, finish the main path and describe what's missing: "This doesn't handle the empty array yet; I'd add a guard at the top."

Being behind is normal. Saying it calmly, with a plan, scores well on Communication. Silently hoping to catch up doesn't.

<Callout kind="tip" title="The interview usually starts late">
Many rounds spend the first five minutes on introductions and leave five for questions, so the problem gets 35 minutes, not 45. Practise with the compressed plan too: 4 to clarify, 6 on the approach, 18 coding, 7 testing.
</Callout>

## Other formats

| Format | What changes |
| --- | --- |
| Phone screen in a shared editor | Often no way to run the code: your dry run is the only test |
| Whiteboard or an iPad | Writing is slow, so plan more and write less; skip boilerplate |
| Two problems in 45 to 60 minutes | Budget each one, and move on from the first at its time limit |
| Take-home or online assessment | No one to talk to; tests and hidden cases decide everything |

Two problems in one session is its own skill, and you'll practise it in M73.

<Callout kind="gotcha" title="Common timing mistakes">
- **Coding in minute two.** It feels efficient, but you're coding before you know what the problem wants.
- **Polishing the brute force.** Say it, give its complexity, and move on. Don't code it unless you're stuck or the interviewer asks.
- **No time left to test.** Testing is a scored phase, not a bonus. If coding runs long, cut the questions at the end, not the testing.
</Callout>
