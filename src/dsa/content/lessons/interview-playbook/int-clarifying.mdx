## Why it matters

Interview problems are short on purpose. The missing details, like whether the input can be empty or how big it gets, are left out to see whether you notice. Asking the right two or three questions shows care, catches edge cases before they become bugs, and often tells you which algorithm the interviewer expects. It's the "Understanding" line of the rubric, earned in the first five minutes.

## What a clarifying question is for

A good clarifying question has an answer that **changes what you'll do**. "Can the array be empty?" decides whether you need a guard. "How many elements?" decides whether O(n²) is acceptable. "Is it sorted?" might turn a hash map solution into two pointers. A question whose answer changes nothing ("What's the array called?") wastes time.

There are two kinds:

- **About the input:** size, range of values, duplicates, order, special cases.
- **About the output:** what exactly to return, in what format, and what to do when there's no answer.

## The checklist

Run down this list in your head and ask the ones the statement leaves open. Most problems need three to six.

| Ask about | Example question | What it can change |
| --- | --- | --- |
| Input size | "How many elements, roughly?" | Which complexity is fast enough |
| Empty input | "Can the list be empty?" | A guard, and what to return |
| Duplicates | "Can values repeat?" | Sets vs counts, `<` vs `<=` |
| Negatives and zero | "Can values be negative?" | Sliding windows, products, starting values |
| Sortedness | "Is the input sorted?" | Binary search and two pointers become possible |
| Output format | "Indexes or values? Any order?" | The return type, and whether you must sort |
| No answer | "What if nothing matches?" | `nil`, `-1` or an empty array |
| In place | "May I modify the input?" | O(1) extra space becomes possible |
| Strings | "ASCII only, or any Unicode?" | Bytes vs `Character`s, and speed |
| Ties | "If several answers work, which one?" | Extra comparisons, or "any is fine" |

These are the [edge-case checklist](/dsa/learn/algo-edge-cases) from M13 turned into questions, plus a few about the output.

## Input size picks the algorithm

The size question is the most valuable one, because the answer tells you how fast your solution must be. A compiled Swift program does about 10⁸ simple steps per second, so:

| If n is up to about | Aim for |
| --- | --- |
| 10 | O(n!): try every order |
| 20 | O(2ⁿ): try every subset |
| 500 | O(n³) |
| 5,000 | O(n²) |
| 10⁵ to 10⁶ | O(n log n) or O(n) |
| 10⁹ or more | O(log n) or a formula |

You built this table in [From n to a feasible complexity](/dsa/learn/bigo-feasibility-table). In an interview, say the conclusion out loud: "A million elements, so I'm aiming for O(n) or O(n log n)." It shows the interviewer you're reasoning, not guessing.

## Unicode: the Swift-specific question

In Swift, a `Character` is what a person sees as one letter, which can be several Unicode scalars and several bytes. `count` counts characters, so it has to walk the whole string, and `"é"` can be written two different ways that Swift treats as equal:

```swift run
let word = "caf\u{E9}"                  // café, with é as one scalar
print(word.count, word.utf8.count)
let thumbs = "\u{1F44D}\u{1F3FD}"       // a thumbs-up with a skin tone
print(thumbs.count, thumbs.unicodeScalars.count, thumbs.utf8.count)
print(word == "cafe\u{301}")            // e followed by a combining accent
```

```output
4 5
1 2 8
true
```

So ask: "Can the strings contain any Unicode, or just ASCII letters?" If it's ASCII, you can work on `s.utf8` bytes or a 26-slot count array, which is fast and simple ([Frequency counting with 26 slots](/dsa/learn/swift-frequency-arrays)). If it's any Unicode, use `Array(s)` of `Character`s, or `Set<String>` and `Dictionary` with `String` keys, which handle equal-looking strings correctly. Either answer is fine; not asking is the mistake.

## An example dialogue

Here's a problem as an interviewer might give it:

> Given the usernames people tried to register, in order, return the first one that was already taken.

Five questions are hiding in that sentence. Here's how the first minutes might go.

**You:** So I get an array of usernames in sign-up order, and I return the first attempt that repeats an earlier name. Is that right?

**Interviewer:** Yes.

**You:** "First" meaning the earliest repeat as I scan from the left? With `["ana", "bo", "cy", "bo", "ana"]`, that's `"bo"`, because it repeats before `"ana"` does.

**Interviewer:** Exactly.

**You:** How many usernames can there be?

**Interviewer:** Up to a million.

**You:** Then I'm aiming for O(n) or O(n log n). Can the list be empty, and what should I return if nothing repeats?

**Interviewer:** It can be empty. Return `nil` when nothing repeats.

**You:** Are `"Maneet"` and `"maneet"` the same username?

**Interviewer:** Yes, usernames ignore case.

**You:** Can they contain any Unicode, like accented letters or emoji?

**Interviewer:** Any Unicode.

**You:** Then I'll lowercase each name and compare `String`s, which treats different ways of writing the same accented letter as equal. Should I return the name as it was typed in the repeat?

**Interviewer:** Yes.

Notice what happened. The "first" question settled an ambiguity with an example, which is faster than arguing about wording. The size question set the target. Empty, no answer, case and Unicode were all edge cases that would have been bugs. And each question took a sentence.

## Restate, then write examples down

Finish the clarifying phase by writing the agreed facts at the top of the editor. It takes a minute and gives you test cases for later:

```swift
// Usernames in sign-up order, up to 1,000,000. Case-insensitive, any Unicode.
// Return the first attempt that repeats an earlier name, as typed; nil if none.
// ["ana", "bo", "cy", "bo", "ana"] -> "bo"
// ["Maneet", "sam", "maneet"]       -> "maneet"
// []                                -> nil
```

With that settled, the solution is short. `insert` on a `Set` returns whether the value was new, so it checks and records in one step:

```swift run
func firstTaken(_ names: [String]) -> String? {
    var seen: Set<String> = []
    for name in names {
        if !seen.insert(name.lowercased()).inserted {
            return name
        }
    }
    return nil
}

print(firstTaken(["ana", "bo", "cy", "bo", "ana"]) ?? "none")
print(firstTaken(["Maneet", "sam", "maneet"]) ?? "none")
print(firstTaken([]) ?? "none")
print(firstTaken(["zo\u{EB}", "zoe\u{308}"]) != nil)
```

```output
bo
maneet
none
true
```

The last line is the Unicode case: two spellings of "zoë" that are equal as `String`s, so the second counts as taken. That's O(n) time and O(n) space, matching the target the size question set.

## When the answer is "you decide"

Sometimes the interviewer says "What do you think?" That's an invitation, not a trap. Pick the reasonable option, say why, and write it down: "I'll return `nil` for an empty list, since there's no repeat. I'll note that at the top." A stated assumption is a decision; an unstated one is a bug waiting to happen.

<Callout kind="gotcha" title="Clarifying mistakes">
- **Asking about what the statement already says.** It suggests you didn't read it. Restate it instead.
- **Twenty questions.** Ask the ones that change your solution. Three to six is typical.
- **Asking, then ignoring the answer.** If they said the list can be empty, your code needs that guard, and your tests need that case.
- **Assuming ASCII in Swift.** Indexing tricks and 26-slot arrays are only right if the interviewer agrees the input is plain letters.
</Callout>
