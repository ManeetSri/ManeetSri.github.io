## Why it matters

The middle of an interview, between the brute force and the code, is where the "Approach" score is earned. Interviewers rarely expect you to see the optimal solution at once. They want to watch you get there: start from something correct, find what it wastes, and remove the waste with a known technique. That move is learnable, and it's the same few moves again and again.

## The move: bottleneck, then pattern

You met the first half in [Brute force first](/dsa/learn/algo-brute-force-first). Here's the whole move:

1. **Write or describe the brute force**, with its complexity.
2. **Find the bottleneck:** the innermost loop, the line that runs the most. Ask what it's *for*. Usually it's recomputing something, or searching for something.
3. **Name the repeated work** in one sentence: "For every end, I re-add the whole range." "For every day, I scan ahead past days I've already passed."
4. **Match it to a pattern** that does that work once, or faster.
5. **Check the pattern's preconditions** against the problem: sorted? non-negative? monotonic?

Step 4 gets easier with a table in your head:

| The brute force keeps… | Pattern | Learned in |
| --- | --- | --- |
| searching for a value it has already seen | Hash set or dictionary | [Patterns: frequency maps and two sum](/dsa/learn/hash-frequency-two-sum) |
| re-adding overlapping ranges | Prefix sums | [Prefix sum + hashmap](/dsa/learn/prefix-hashmap) |
| recomputing a window from scratch as it moves | Sliding window | [A sliding window template](/dsa/learn/sw-template) |
| comparing all pairs in a sorted array | Two pointers | [Opposite ends](/dsa/learn/tp-opposite-ends) |
| scanning ahead for the next bigger or smaller value | Monotonic stack | [Next greater element](/dsa/learn/stack-monotonic-intro) |
| trying every candidate answer in order | Binary search on the answer | [The monotonic predicate idea](/dsa/learn/bsa-idea) |
| finding the smallest or largest of a changing set | Heap | [Top K](/dsa/learn/heap-top-k) |
| solving the same subproblem again | Memoisation or DP | [Top-down memoisation](/dsa/learn/dp-memoisation) |
| exploring the same state again | A visited set | [BFS](/dsa/learn/gt-bfs) |

[Reading the pattern from constraints and wording](/dsa/learn/pat-recognition) turns this into a full map. Here it's used the other way round: not "which pattern does this problem look like?" but "which pattern removes *this* waste?". That's the version you can explain out loud.

## Best conceivable runtime

Before optimising, ask how fast any solution could possibly be. If you must read all n elements, nothing beats O(n). If the output has n² pairs, nothing beats O(n²). This **best conceivable runtime** tells you when to stop: if the brute force is O(n²) and the floor is O(n), there's room; if you've reached the floor, you're done. It also gives you something to say: "I have to look at every element, so O(n) is the best possible. I'm at O(n log n), so let me see whether the sort is necessary."

## Example 1: count subarrays with a given sum

> Count the contiguous subarrays whose elements add up to `k`. Values can be negative.

**Brute force.** Try every start, extend the end, keep a running sum: O(n²).

**Bottleneck.** For each end, the inner loop asks, "which starts make the sum exactly `k`?" by re-adding ranges. With prefix sums, the sum from `start` to `end` is `prefix[end + 1] - prefix[start]`, so the question becomes "how many earlier prefix sums equal `prefix - k`?". That's a **lookup**: a dictionary of prefix-sum counts answers it in O(1).

**Preconditions.** A sliding window would be the first guess for "contiguous subarray with a sum", but it needs non-negative values: with negatives, growing the window can shrink the sum, so you can't tell which way to move. That's why it's prefix sums plus a dictionary here.

```swift run
func countSlow(_ numbers: [Int], _ k: Int) -> Int {
    var count = 0
    for start in numbers.indices {
        var sum = 0
        for end in start..<numbers.count {
            sum += numbers[end]
            if sum == k { count += 1 }
        }
    }
    return count
}

func countFast(_ numbers: [Int], _ k: Int) -> Int {
    var seen: [Int: Int] = [0: 1]      // prefix sum -> how many times it has occurred
    var prefix = 0
    var count = 0
    for number in numbers {
        prefix += number
        count += seen[prefix - k, default: 0]
        seen[prefix, default: 0] += 1
    }
    return count
}

let numbers = [3, 4, -7, 1, 3, 3, 1, -4]
print(countSlow(numbers, 7), countFast(numbers, 7))
```

```output
4 4
```

O(n²) to O(n). The `[0: 1]` start stands for the empty prefix, so a subarray starting at index 0 is counted.

## Example 2: days until a warmer day

> For each day, how many days until a warmer temperature? 0 if none comes.

**Brute force.** From each day, scan forwards until something warmer: O(n²) on a falling sequence.

**Bottleneck.** The scans overlap. When day 3 scans forwards past several colder days, it repeats work that those days will do again. Flip it around: instead of each day searching ahead, let each new day *resolve* the earlier days it's warmer than. The days still waiting form a stack with falling temperatures, which is a **monotonic stack**.

```swift run
func waitSlow(_ temps: [Int]) -> [Int] {
    var answer = Array(repeating: 0, count: temps.count)
    for day in temps.indices {
        for later in (day + 1)..<temps.count where temps[later] > temps[day] {
            answer[day] = later - day
            break
        }
    }
    return answer
}

func waitFast(_ temps: [Int]) -> [Int] {
    var answer = Array(repeating: 0, count: temps.count)
    var waiting: [Int] = []            // days still waiting, temperatures falling
    for (day, temp) in temps.enumerated() {
        while let last = waiting.last, temps[last] < temp {
            answer[last] = day - last
            waiting.removeLast()
        }
        waiting.append(day)
    }
    return answer
}

let temps = [13, 12, 15, 11, 9, 12, 16]
print(waitSlow(temps))
print(waitFast(temps))
```

```output
[2, 1, 4, 2, 1, 1, 0]
[2, 1, 4, 2, 1, 1, 0]
```

Each day is pushed once and popped at most once, so the fast version is O(n), from [Daily temperatures and stock span](/dsa/learn/stack-temperatures-span).

## Example 3: the smallest capacity that ships in time

> Packages with these weights must ship in order within `days` days. What's the smallest daily capacity that works?

**Brute force.** Try capacity = the heaviest package, then one more, then one more, checking each by simulating the days. If the weights add up to S, that's up to S checks of O(n) each.

**Bottleneck.** The candidates are tried in order, one at a time, but the check is **monotonic**: if a capacity works, every bigger one works too. Searching an ordered yes/no line one step at a time is exactly what **binary search on the answer** replaces, cutting S checks to about log₂ S.

```swift run
func daysNeeded(_ weights: [Int], capacity: Int) -> Int {
    var days = 1
    var load = 0
    for weight in weights {
        if load + weight > capacity {
            days += 1
            load = 0
        }
        load += weight
    }
    return days
}

func capacitySlow(_ weights: [Int], days: Int) -> Int {
    var capacity = weights.max()!
    while daysNeeded(weights, capacity: capacity) > days {
        capacity += 1
    }
    return capacity
}

func capacityFast(_ weights: [Int], days: Int) -> Int {
    var low = weights.max()!
    var high = weights.reduce(0, +)
    while low < high {
        let mid = low + (high - low) / 2
        if daysNeeded(weights, capacity: mid) <= days {
            high = mid
        } else {
            low = mid + 1
        }
    }
    return low
}

let weights = [4, 8, 3, 7, 2, 6, 5]
print(capacitySlow(weights, days: 3), capacityFast(weights, days: 3))
```

```output
12 12
```

O(n · S) to O(n log S), as in [Capacity to ship packages](/dsa/learn/bsa-shipping). The check didn't change at all: only the order in which candidates are tried.

## Saying it in the interview

All three examples follow one script, and saying it out loud is half the score:

> "The brute force is O(n²) because for every *end* I re-add the range. The repeated work is finding starts with the right sum, which is a lookup. A dictionary of prefix sums makes each lookup O(1), so the whole thing is O(n). Values can be negative, so a sliding window wouldn't work here."

Brute force and cost, the repeated work in one sentence, the pattern, the new cost, and a precondition checked. If you can't find the pattern, saying the first two parts still shows the interviewer exactly where you are, and that's when hints arrive.

<Callout kind="gotcha" title="Optimising mistakes">
- **Pattern by keyword.** "Subarray" doesn't always mean sliding window: check that the window's validity changes in one direction as it grows. With negative values it often doesn't.
- **Skipping the brute force.** Without it you can't name the repeated work, and you have nothing to fall back on.
- **Optimising past the floor.** If you're already at the best conceivable runtime, say so and move on to coding.
- **Forgetting space.** A dictionary that makes time O(n) costs O(n) memory. Say it, since it's often the trade-off the interviewer wants to hear.
</Callout>
