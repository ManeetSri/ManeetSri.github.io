## Why it matters

Interviewers who use Swift know its sharp edges, and a few of them are exactly where interview code breaks: strings you can't index with an `Int`, queues that are secretly O(n), recursion that crashes a test. Each one costs minutes if it surprises you in the middle of a round, and almost nothing if you've met it before. This lesson collects the ten that come up most, each with the fix in a few lines. You've seen most of them earlier in the course; here they're in one place, for revision before a round.

## 1. Strings don't take Int indexes

`word[0]` doesn't compile, because a Swift `Character` can be several bytes long, so finding the nth one means walking from the start ([String.Index and why s[i] does not exist](/dsa/learn/swift-string-index)):

```text title="What you'll see"
error: 'subscript(_:)' is unavailable: cannot subscript String with an Int, use a String.Index instead.
```

In an interview, convert once with `Array(word)`, then index freely:

```swift run
let word = "level"
let letters = Array(word)          // convert once: O(n), then each access is O(1)
var left = 0
var right = letters.count - 1
var isPalindrome = true
while left < right {
    if letters[left] != letters[right] {
        isPalindrome = false
        break
    }
    left += 1
    right -= 1
}
print(letters[0], letters[2], isPalindrome)
print(word[word.index(word.startIndex, offsetBy: 2)])   // fine once, O(n²) inside a loop
```

```output
l v true
v
```

`index(_:offsetBy:)` walks from the start every time, so calling it inside a loop quietly makes the loop O(n²). If the interviewer agrees the input is ASCII, `Array(word.utf8)` gives you bytes, which are even faster ([Array(s) and [UInt8] for fast access](/dsa/learn/swift-string-to-array)).

## 2. Character and String are different types

A literal like `"a"` can be either, but a `Character` variable and a `String` variable can't be compared:

```text title="What you'll see"
error: binary operator '==' cannot be applied to operands of type 'Character' and 'String'
```

Convert one side, and remember which operations give which type:

```swift run
let letter: Character = "a"
let text: String = "a"
print(letter == "a", String(letter) == text)       // a literal can be either type
print(letter.isLetter, letter.asciiValue ?? 0)
let next = Character(UnicodeScalar(letter.asciiValue! + 1))
print(next)
let parts = "swift is fun".split(separator: " ")
print(parts.count, type(of: parts[0]))
let firstWord = String(parts[0])                   // convert before storing or returning
print(firstWord.uppercased())
```

```output
true true
true 97
b
3 Substring
SWIFT
```

Iterating a `String` gives `Character`s, `first` and `last` give `Character?`, and `split` gives `Substring`s that share the original's memory. Return `String(part)` when the function's type says `String`.

## 3. Arithmetic overflow traps

Swift checks every `+`, `-` and `*`, and stops the program if the result doesn't fit in an `Int` ([Overflow traps and overflow operators](/dsa/learn/swift-overflow)):

```text title="What you'll see"
Swift runtime failure: arithmetic overflow
```

`Int` reaches about 9.2 × 10¹⁸. Products of two values up to 10⁹ fit; three don't. The classic trap is the binary search midpoint:

```swift run
let big = 3_000_000_000
print(big * big)                                   // 9 × 10¹⁸ just fits below Int.max
let (_, overflowed) = big.multipliedReportingOverflow(by: big * big)
print(overflowed)                                  // a third factor wouldn't fit
let low = Int.max - 5
let high = Int.max - 1
print(low + (high - low) / 2)                      // (low + high) / 2 would trap
print(Int.max &+ 1 == Int.min)                     // &+ wraps on purpose, for hashing
```

```output
9000000000000000000
true
9223372036854775804
true
```

Write `low + (high - low) / 2` by habit, use `&+` and `&*` only where wrapping is intended (hashes), and when a problem says "return it modulo 10⁹ + 7", take the remainder after every step.

## 4. removeFirst() is O(n)

`removeFirst()` on an `Array` shifts every remaining element left, so a BFS that uses it is O(n²) ([Why removeFirst() is O(n)](/dsa/learn/queue-why-not-removefirst)). Keep a head index instead:

```swift run
let children = [[1, 2], [3], [4, 5], [], [], []]
var queue = [0]
var head = 0
var order: [Int] = []
while head < queue.count {
    let node = queue[head]
    head += 1                      // O(1): removeFirst() would shift every element left
    order.append(node)
    queue.append(contentsOf: children[node])
}
print(order)
```

```output
[0, 1, 2, 3, 4, 5]
```

`removeLast()` and `popLast()` are O(1), so a stack is a plain array. If the interviewer allows packages, swift-collections' `Deque` is O(1) at both ends.

## 5. Dictionary lookups: default:, and a ?? trap

A dictionary lookup returns an optional. Force unwrapping a missing key crashes:

```text title="What you'll see"
Fatal error: Unexpectedly found nil while unwrapping an Optional value
```

The `default:` subscript is the clean way to count or group. Watch out for the tempting alternative with `??`, which has *lower* precedence than `+`:

```swift run
var wrong: [Character: Int] = [:]
for c in "banana" {
    wrong[c] = wrong[c] ?? 0 + 1                   // means wrong[c] ?? (0 + 1)
}
var counts: [Character: Int] = [:]
for c in "banana" {
    counts[c, default: 0] += 1
}
print(wrong["a"] ?? 0, counts["a"] ?? 0)
var byLength: [Int: [String]] = [:]
for word in ["hi", "yo", "hey"] {
    byLength[word.count, default: []].append(word)  // appends in place, no copy
}
print(byLength[2] ?? [], byLength[3] ?? [])
```

```output
1 3
["hi", "yo"] ["hey"]
```

The wrong version never counts past 1, and it compiles without a warning. `(wrong[c] ?? 0) + 1` would work, but `default:` is shorter and mutates the stored value in place ([Counting with default: and grouping(by:)](/dsa/learn/swift-counting-grouping)).

## 6. Sort stability and tie-breaks

Swift's `sort()` and `sorted()` are stable: elements that compare equal keep their original order ([How Swift sorts](/dsa/learn/sort-swift-sort)). Two traps remain: reversing an ascending sort also reverses the ties, and an interviewer may not know Swift's guarantee. A tie-break in the comparator makes the order explicit:

```swift run
struct Player {
    let name: String
    let score: Int
}
let players = [Player(name: "Ana", score: 30), Player(name: "Bo", score: 25),
               Player(name: "Cy", score: 30), Player(name: "Di", score: 25)]
let byScore = players.sorted { $0.score > $1.score }          // stable: ties keep input order
print(byScore.map(\.name))
let reversedAscending = Array(players.sorted { $0.score < $1.score }.reversed())
print(reversedAscending.map(\.name))                          // reversing flips the ties too
let explicit = players.sorted { $0.score != $1.score ? $0.score > $1.score : $0.name < $1.name }
print(explicit.map(\.name))                                   // a tie-break states the order
```

```output
["Ana", "Cy", "Bo", "Di"]
["Cy", "Ana", "Di", "Bo"]
["Ana", "Cy", "Bo", "Di"]
```

Never pass `>=` or `<=` as the comparator: it must say "strictly comes before". With `<=`, equal elements each claim to come first, which breaks the sort's assumptions.

## 7. Value and reference surprises

`Array(repeating:count:)` copies the *value* it's given. For a struct that's a fresh copy each time; for a class it's the same reference, repeated:

```swift run
final class Counter {
    var value = 0
}
let shared = Array(repeating: Counter(), count: 3)    // one Counter, three references to it
shared[0].value = 7
print(shared.map(\.value))
let separate = (0..<3).map { _ in Counter() }         // three Counters
separate[0].value = 7
print(separate.map(\.value))

struct Point {
    var x = 0
}
var points = [Point(), Point()]
for point in points {
    var moved = point                                 // a copy: the array doesn't change
    moved.x = 5
}
print(points.map(\.x))
for index in points.indices {
    points[index].x = 5                               // writes into the array itself
}
print(points.map(\.x))
```

```output
[7, 7, 7]
[7, 0, 0]
[0, 0]
[5, 5]
```

The first trap bites with class nodes, such as an array of graph or tree nodes. The second bites when you "update" structs in a `for` loop: the loop variable is a copy, so write through the index ([Value vs reference semantics](/dsa/learn/swift-value-vs-reference)). A grid made with `Array(repeating: Array(repeating: 0, count: 3), count: 2)` is fine, because arrays are values.

## 8. Recursion depth

Each recursive call uses stack space. Swift Testing runs tests on threads with a 512 KB stack, so a recursive DFS on a 100,000-node path, or a recursive walk down a long linked list, can crash where the same code is fine on small inputs ([Stack depth limits in Swift](/dsa/learn/rec-stack-limits)). There's no Swift error message: the process just dies.

```text title="What you'll see"
zsh: segmentation fault
```

When depth can reach the input size, use an explicit stack:

```swift run
let n = 100_000
let children = (0..<n).map { $0 + 1 < n ? [$0 + 1] : [] }   // one long path: 0 → 1 → … → 99,999
var stack = [(node: 0, depth: 1)]
var deepest = 0
while let (node, depth) = stack.popLast() {
    deepest = max(deepest, depth)
    for child in children[node] {
        stack.append((child, depth + 1))
    }
}
print(deepest)
```

```output
100000
```

In an interview, recursion on a balanced tree (depth about log n) is fine and usually clearer. Say so: "Recursion depth is the tree's height. If the tree could be a long chain, I'd switch to an explicit stack."

## 9. Optional chaining pitfalls

Optional chaining turns any `nil` along the way into a `nil` result. That's convenient, but comparisons with optionals can be true for the wrong reason:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    init(_ value: Int) {
        self.value = value
    }
}
let root = TreeNode(1)
print(root.left?.value == root.left?.left?.value)   // nil == nil is true
let names: [String]? = nil
print(names?.isEmpty == true, names?.isEmpty ?? true)
if let leftValue = root.left?.value {
    print("left child holds", leftValue)
} else {
    print("no left child")
}
```

```output
true
false true
no left child
```

Two missing children compare equal, which can make a "same tree" or "symmetric tree" check pass when it shouldn't. And `names?.isEmpty == true` is false for `nil`, while `?? true` treats `nil` as empty: decide which you mean. Unwrap with `if let` or `guard let` when the `nil` case needs its own handling ([Optional chaining](/dsa/learn/swift-optional-chaining)).

## 10. Ranges whose lower bound is above the upper

`a...b` and `a..<b` crash when `a > b`, which happens at exactly the edge cases interviews love: an empty array, `n = 0`, a loop to `count - 1`.

```text title="What you'll see"
Fatal error: Range requires lowerBound <= upperBound
```

`stride` is simply empty instead, and `indices` with `dropFirst()` or `dropLast()` never builds a bad range:

```swift run
let empty: [Int] = []
for i in stride(from: 0, to: empty.count - 1, by: 1) {   // stride is just empty
    print(i)
}
for i in empty.indices.dropLast() {                      // every index but the last
    print(i)
}
let n = 0
if n >= 1 {
    for i in 1...n { print(i) }                          // only built when it's valid
}
print(Array(stride(from: 1, through: n, by: 1)), (0..<0).isEmpty)
```

```output
[] true
```

`0..<0` is fine: an empty range is allowed, a backwards one isn't. Whenever you write `..<count - 1` or `1...n`, ask what happens when the count is 0.

<Callout kind="tip" title="Say the gotcha before it bites">
Mentioning one of these out loud is a quick way to show Swift fluency: "I'll convert to an array first, since String indexing is O(n)." "I'll use a head index rather than `removeFirst()`." "The midpoint is `low + (high - low) / 2` to avoid overflow." Each takes five seconds and tells the interviewer you know the language, not only the algorithm.
</Callout>
