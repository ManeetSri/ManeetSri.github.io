## Why it matters

An interviewer can only score what they can see. If you think silently for ten minutes and then type a perfect answer, they've learned almost nothing about how you work, and if you get stuck in silence they can't help you. Thinking out loud turns your reasoning into evidence. It's a skill like any other: awkward at first, natural after a few mocks.

## What to say at each stage

You don't need to narrate everything. At each stage there are one or two things worth saying:

| Stage | Say | For example |
| --- | --- | --- |
| Clarify | Your restatement and your questions | "So the input is… Can it be empty?" |
| Brute force | The simplest idea and its cost | "Sorting, then scanning, is O(n log n)." |
| Optimise | What's wasted, and what removes it | "The sort is the bottleneck. A set avoids it." |
| Agree | A direct question | "Shall I code the set version?" |
| Code | What the next few lines are for | "Now I only start counting at the first day of a streak." |
| Test | What you're checking, and what you find | "Tracing `[5, 1, 3, 2]`… `best` ends at 3. Good." |
| Analyse | The cost and the reason | "Each day is looked at most twice, so O(n)." |

The common thread: say **what** you're doing and **why**, not every keystroke.

## Narrating trade-offs

Interviewers love trade-offs because they show judgement. A simple shape works almost every time:

1. Name the options.
2. Give each one's cost, in time and space.
3. Pick one, with the reason that tips it.

"I could sort the array, which is O(n log n) time and no extra space if I may change the input. Or I could put the values in a set, which is O(n) time but O(n) extra space. You said the input shouldn't be modified and there's plenty of memory, so I'll use the set."

That's three sentences, and it earns credit on Approach, Complexity and Communication at once. Notice that it uses the clarifying answers: the trade-off is decided by facts you gathered at the start.

## A transcript, annotated

Here's how the first part of a round might sound. The problem:

> A user opens an app on various days, given as day numbers in any order. Return the length of their longest streak of consecutive days.

**Clarifying.**

> "So I get an array of day numbers, in no particular order, and I return the longest run like 4, 5, 6 where every day is present. Can a day appear twice, if they opened the app twice that day? And can the array be empty?"

*It restates with details the candidate inferred ("in no particular order", "like 4, 5, 6"), which the interviewer can correct in a word. Then it asks only the questions that matter: duplicates and empty input.*

The interviewer says duplicates are possible, the array can be empty (answer 0), and there can be up to 10⁵ days.

**Brute force.**

> "The simplest thing I can think of is to sort the days, then walk through counting runs, skipping duplicates. That's O(n log n) for the sort. With 10⁵ days that's fast enough, so it's a safe fallback."

*It gives a correct plan with its cost, and checks it against the size, so there's a solution on the table before anything clever happens.*

**Optimising.**

> "Can I avoid the sort? I only sort so I can ask 'is the next day present?'. A set answers that in O(1). But if I count a streak from every day, a long streak gets counted again from each of its days, which is O(n²) in the worst case. So I'll only start counting from a day whose previous day is *missing*: the first day of each streak."

*The candidate names the bottleneck (the sort exists only to answer one question), the pattern that removes it (a hash set), and the new problem it creates (recounting), then fixes that too. The interviewer can follow every step.*

**Agreeing.**

> "That's O(n) time and O(n) space for the set. Shall I go ahead with that?"

**Coding**, with a sentence per block:

> "First, a set of the days, which also drops the duplicates… Now loop over the distinct days, skipping any day whose previous day is present… From a streak start, count upwards while the next day exists… and keep the best."

```swift run
func longestStreak(_ days: [Int]) -> Int {
    let opened = Set(days)
    var best = 0
    for day in opened where !opened.contains(day - 1) {   // a streak starts here
        var length = 1
        while opened.contains(day + length) {
            length += 1
        }
        best = max(best, length)
    }
    return best
}

print(longestStreak([5, 1, 3, 2, 9, 2, 10]))
print(longestStreak([]))
print(longestStreak([7, 7, 7]))
```

```output
3
0
1
```

**Testing and analysing.**

> "Let me trace the first example. The set is \{1, 2, 3, 5, 9, 10\}. Day 1 has no day 0, so it's a start: 2 and 3 exist, length 3. Days 2 and 3 are skipped because their previous days exist. Day 5 is a start with length 1, day 9 a start with length 2. Best is 3. Empty input gives 0, and duplicates vanish in the set. Each day is checked once as a possible start and once while counting up, so it's O(n) time, O(n) space."

*Tracing out loud is where many candidates catch their own bugs, and the interviewer sees it happen.* [Testing your own code](/dsa/learn/int-testing) goes deeper.

## Talking while you code

This is the hardest stage to narrate, because typing takes concentration. Two contrasting styles:

- **Keystrokes (unhelpful):** "for day in opened, where, not, opened dot contains, day minus one, open brace…"
- **Intent (helpful):** "Now I loop over the distinct days, but only from days whose previous day is missing, so each streak is counted once."

Say the intent of a block, type it, then say the next intent. Short pauses while typing are fine.

## Silence, hints and bugs

**When you need to think,** say so: "Let me think about this for a moment." Twenty or thirty seconds of announced silence is completely normal. Several minutes of unannounced silence makes the interviewer wonder whether to step in.

**When you get a hint,** take it visibly. Repeat it in your own words, then use it: "So if I compare the middle with the right end, I can tell which half is sorted. Let me try that." Arguing with a hint, or ignoring it, scores badly.

**When you spot a bug,** say it: "Wait, this misses the last run, because I only update `best` when the value changes. I'll update it after the loop too." Finding your own bug is a positive signal, not a failure.

<Callout kind="gotcha" title="Communication mistakes">
- **Narrating syntax instead of ideas.** The interviewer can read the code; they want the reasoning.
- **Asking "is that right?" after every line.** Check in at decision points, like the approach, not constantly.
- **Going quiet when it gets hard.** That's exactly when talking helps most, because the interviewer can only nudge you if they know where you are.
- **Talking without listening.** If the interviewer speaks, stop typing. Their comments are usually hints.
</Callout>

## Practise it alone

Thinking out loud feels strange without a listener, so practise it on purpose. During a mock on the [Mock interview](/dsa/mock) page, talk to the empty room, or record yourself on your phone and play back two minutes. You'll hear the long silences and the "um, so, basically" quickly. Score yourself on Communication afterwards, honestly.
