## Why it matters

Your phone's Contacts app links cards that turn out to be the same person. Customer databases merge duplicate records, and sign-in systems discover that two accounts belong to one user. The rule is usually the same: if two records share an identifier, such as an email address, they're the same person, and so is anything linked to either of them through a chain of shared identifiers. "Accounts merge" is the interview version, and it's a favourite because it tests three skills at once: mapping strings to indexes with a dictionary, union-find, and producing tidy, deterministic output.

## The problem

Each card is an array of strings: a name, then one or more emails. Two cards belong to the same person if they share at least one email. That's transitive: if card A shares an email with B, and B shares one with C, all three are one person, even if A and C have nothing in common. Return one card per person, with the name first and then all their emails in sorted order.

| Cards | Merged |
| --- | --- |
| Priya: priya@home.net, p.shah@work.com | Priya: p.shah@work.com, priya@home.net, shah.p@club.org |
| Tom: tom@mail.org | Priya: priya.s@uni.edu |
| Priya: priya.s@uni.edu | Tom: tom@mail.org, tommy@games.io |
| Priya: p.shah@work.com, shah.p@club.org | |
| Tom: tommy@games.io, tom@mail.org | |

Notice the two Priyas in the result. The third card shares no email with the others, so it stays separate: **names never decide anything**. Two different people can share a name. The problem promises only that cards sharing an email have the same name.

## The plan

Think of every email as a node. Emails written on the same card are connected. A merged person is a connected group of emails. That's union-find:

1. **Give every distinct email an index**, with a dictionary from email to index. Remember each email's owner's name too.
2. **Union the emails on each card.** Joining each one to the card's **first** email is enough: k emails need only k − 1 unions to become one group, not every pair.
3. **Group the emails by root.** A dictionary from root to a list of emails collects each person.
4. **Tidy up.** Sort each person's emails, put the name in front, and sort the cards themselves, so the output is the same on every run.

```swift run
// The UnionFind from "Path compression and union by rank"
struct UnionFind {
    private var parent: [Int]
    private var size: [Int]

    init(count: Int) {
        parent = Array(0..<count)
        size = Array(repeating: 1, count: count)
    }

    mutating func find(_ x: Int) -> Int {
        var root = x
        while parent[root] != root { root = parent[root] }
        var node = x
        while node != root {
            let next = parent[node]
            parent[node] = root
            node = next
        }
        return root
    }

    @discardableResult
    mutating func union(_ a: Int, _ b: Int) -> Bool {
        var rootA = find(a)
        var rootB = find(b)
        if rootA == rootB { return false }
        if size[rootA] < size[rootB] { swap(&rootA, &rootB) }
        parent[rootB] = rootA
        size[rootA] += size[rootB]
        return true
    }
}

func mergeCards(_ cards: [[String]]) -> [[String]] {
    // 1. An index for every distinct email, and who owns it
    var indexOf: [String: Int] = [:]
    var emails: [String] = []
    var owner: [String] = []
    for card in cards {
        for email in card.dropFirst() where indexOf[email] == nil {
            indexOf[email] = emails.count
            emails.append(email)
            owner.append(card[0])
        }
    }

    // 2. Join every email on a card to the card's first email
    var sets = UnionFind(count: emails.count)
    for card in cards where card.count > 1 {
        let first = indexOf[card[1]]!
        for email in card.dropFirst(2) {
            sets.union(first, indexOf[email]!)
        }
    }

    // 3. Collect each group under its root
    var groups: [Int: [String]] = [:]
    for (index, email) in emails.enumerated() {
        groups[sets.find(index), default: []].append(email)
    }

    // 4. Name first, emails sorted, cards sorted by name and then first email
    let merged = groups.map { root, group in [owner[root]] + group.sorted() }
    return merged.sorted { $0[0] != $1[0] ? $0[0] < $1[0] : $0[1] < $1[1] }
}

let cards = [
    ["Priya", "priya@home.net", "p.shah@work.com"],
    ["Tom", "tom@mail.org"],
    ["Priya", "priya.s@uni.edu"],
    ["Priya", "p.shah@work.com", "shah.p@club.org"],
    ["Tom", "tommy@games.io", "tom@mail.org"],
]
for person in mergeCards(cards) {
    print(person[0] + ":", person.dropFirst().joined(separator: ", "))
}
```

```output
Priya: p.shah@work.com, priya@home.net, shah.p@club.org
Priya: priya.s@uni.edu
Tom: tom@mail.org, tommy@games.io
```

What to notice:

- **The dictionary does the deduplication.** p.shah@work.com appears on two cards but gets one index, the first time it's seen. That shared index is what links the two Priya cards.
- **`owner[root]`** works because every email in a group has the same owner's name, so any member's name will do.
- **Step 3 builds a dictionary**, `groups`, and a dictionary's order changes between runs. Step 4's sort is what makes the output stable. Never return or print a dictionary's contents in the order you find them.
- **Single-email cards** like Tom's first one need no unions at all, but their email still gets an index in step 1, so it still turns up in step 3.

## The cost

Let E be the total number of emails across all cards, counting repeats.

| Step | Cost |
| --- | --- |
| Indexing | O(E) dictionary operations |
| Unions | O(E α(E)), effectively O(E) |
| Grouping | O(E α(E)) |
| Sorting emails and cards | O(E log E) comparisons |

The sorting dominates: **O(E log E)** overall, where each comparison costs up to the length of the strings. The extra memory is O(E). In an interview, say that the union-find part is near-linear and the sort is what costs log E.

## Other ways to build it

**Union the cards instead of the emails.** Make the elements the cards, 0 to n − 1. Keep a dictionary from each email to the first card that had it. When a later card has the same email, union the two cards. Then group the cards by root, and collect each group's emails into a set before sorting:

```swift
var firstCard: [String: Int] = [:]
var sets = UnionFind(count: cards.count)
for (index, card) in cards.enumerated() {
    for email in card.dropFirst() {
        if let earlier = firstCard[email] {
            sets.union(earlier, index)
        } else {
            firstCard[email] = index
        }
    }
}
```

It needs fewer elements (one per card rather than one per email), but each person's emails then need deduplicating.

**A graph search.** Build an adjacency list linking each card's first email to its other emails, then find the connected components with a DFS or BFS, exactly as in [Connected components and flood fill](/dsa/learn/gt-components). The complexity is the same. Union-find skips building the adjacency list, and it has no recursion to overflow on a person with a huge number of emails.

<Callout kind="tip" title="In the interview">
Ask before you code. Can a card list the same email twice? Is the first string always the name? Must the output be in a particular order? Then say the plan in one sentence: "emails are nodes, emails on the same card are connected, and each connected group is one person, so I'll use union-find over email indexes."
</Callout>

<Callout kind="gotcha" title="Common mistakes">
- **Merging by name.** Two people called Sam with different emails are different people. Only shared emails merge cards.
- **Unioning every pair on a card.** k emails need k − 1 unions, all to the first one. Every pair is k(k − 1) / 2, which is quadratic on a card with many emails.
- **Forgetting emails that never get unioned.** Group every indexed email in step 3, not just the ones that appeared in a union.
- **Trusting dictionary order.** The groups dictionary comes out in a different order on every run. Sort the result.
</Callout>
