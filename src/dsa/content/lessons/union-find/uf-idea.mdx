## Why it matters

Some questions are about groups that only ever merge. Two people become friends, so their friend circles join. A cable goes in, so two parts of a network can now talk. Two contact cards share an email, so they're the same person. After every change you want to ask "are these two in the same group?" and get an answer at once. **Union-find** (also called a **disjoint-set union**, or DSU) is the data structure built for exactly this. It's short, it's fast, and it powers Kruskal's minimum spanning tree algorithm later in Part VI.

## The question: are these two connected?

In [Connected components and flood fill](/dsa/learn/gt-components) you answered "are a and b connected?" with a DFS or BFS. That's perfect when the graph is fixed: one O(V + E) pass labels every component, and then every question is a lookup.

Now suppose the edges arrive one at a time, with questions in between:

| Event | Question | Answer |
| --- | --- | --- |
| 0 and 1 become friends | | |
| 2 and 3 become friends | Are 0 and 3 in one group? | no |
| 1 and 3 become friends | Are 0 and 3 in one group? | yes |

Rerunning a search after every new edge costs O(V + E) each time. With a million events, that's far too slow. You want two operations that are both fast:

- **find(x)**: which group is x in? It returns one member of the group, the **representative**, so "are a and b together?" becomes `find(a) == find(b)`.
- **union(a, b)**: merge the group containing a with the group containing b.

The groups are **disjoint sets**: every element belongs to exactly one of them. The elements are numbered 0 to n − 1, so plain arrays can hold everything.

## A first try: a label on every element

The obvious design gives every element a label, the name of its group. find reads the label. union relabels every member of one group:

```swift run
var label = Array(0..<6)            // everyone starts in a group of their own

func union(_ a: Int, _ b: Int) {
    let from = label[a]
    let to = label[b]
    for index in label.indices where label[index] == from {
        label[index] = to           // move a's whole group across
    }
}

union(0, 1)
union(2, 3)
print(label)
union(1, 3)
print(label)
print("0 and 3 together?", label[0] == label[3])
```

```output
[1, 1, 3, 3, 4, 5]
[3, 3, 3, 3, 4, 5]
0 and 3 together? true
```

find is O(1), but every union scans the whole array: O(n). Joining n elements into one group takes n − 1 unions, so O(n²) in total. This version is slow, but it's so obviously correct that it makes a great **model** for testing a faster one, as DSAKit's tests do.

## Each set is a tree

The better idea: don't store the group's name on every element. Store a **parent** instead, and let each group be a tree, as in [Tree terminology](/dsa/learn/tree-terminology). The root of the tree represents the group, and a root is its own parent.

- **find(x)** follows parents up from x until it reaches a node that is its own parent. That's the root.
- **union(a, b)** finds both roots. If they're the same, a and b are already together. Otherwise it makes one root the parent of the other, and the two trees become one.

All the trees live in one array, `parent`, where `parent[x]` is x's parent. At the start, `parent[x] == x` for every x: n trees of one node each.

```swift run
struct NaiveUnionFind {
    var parent: [Int]

    init(count: Int) {
        parent = Array(0..<count)     // every element is its own root
    }

    func find(_ x: Int) -> Int {
        var node = x
        while parent[node] != node {  // walk up until a node is its own parent
            node = parent[node]
        }
        return node
    }

    mutating func union(_ a: Int, _ b: Int) -> Bool {
        let rootA = find(a)
        let rootB = find(b)
        if rootA == rootB { return false }   // already in one set
        parent[rootA] = rootB                 // a's whole tree hangs under b's root
        return true
    }
}

var sets = NaiveUnionFind(count: 6)
print("start:", sets.parent)
for (a, b) in [(0, 1), (2, 3), (1, 3), (4, 5), (0, 2)] {
    let joined = sets.union(a, b)
    print("union(\(a), \(b)) -> \(joined), parent = \(sets.parent)")
}
print("find(0) =", sets.find(0), "and find(5) =", sets.find(5))
```

```output
start: [0, 1, 2, 3, 4, 5]
union(0, 1) -> true, parent = [1, 1, 2, 3, 4, 5]
union(2, 3) -> true, parent = [1, 1, 3, 3, 4, 5]
union(1, 3) -> true, parent = [1, 3, 3, 3, 4, 5]
union(4, 5) -> true, parent = [1, 3, 3, 3, 5, 5]
union(0, 2) -> false, parent = [1, 3, 3, 3, 5, 5]
find(0) = 3 and find(5) = 5
```

The final parent array describes this **forest** (a collection of trees):

```text
index:  0  1  2  3  4  5
parent: 1  3  3  3  5  5

      3          5
     / \         |
    1   2        4
    |
    0
```

What to notice:

- **union links roots, never the elements themselves.** `union(1, 3)` found roots 1 and 3 and set `parent[1] = 3`, which brought 0 along too, because 0 hangs under 1.
- **union(0, 2) returned false.** Walking up from 0 (0 → 1 → 3) and from 2 (2 → 3) reaches the same root, so they were already together. That false is how you'll detect cycles in two lessons' time.
- **The representative is whichever node happens to be the root.** Only equality of roots means anything: never print a root and treat it as a stable group name, because a later union can change it.

A useful extra is a running count of sets. It starts at n, and every union that returns true lowers it by one.

<Callout kind="analogy">
Think of a company where everyone knows only their own manager. To find out which company someone works for, you go up the chain until you reach the person with no manager: the CEO. Two companies merge when one CEO starts reporting to the other. Nobody else's line manager changes.
</Callout>

## The trouble: trees can become chains

The cost of find is the number of steps up to the root, the depth of the node. Nothing in the naive union keeps trees shallow. Join the elements in order, `union(0, 1)`, `union(1, 2)`, `union(2, 3)` and so on, and each union hangs the whole tree under the next element:

```text
union(0, 1):  0 → 1
union(1, 2):  0 → 1 → 2
union(2, 3):  0 → 1 → 2 → 3      a chain: find(0) walks the whole thing
```

Counting the steps shows how bad it gets:

```swift run
struct NaiveUnionFind {
    var parent: [Int]

    init(count: Int) {
        parent = Array(0..<count)
    }

    func find(_ x: Int) -> Int {
        var node = x
        while parent[node] != node { node = parent[node] }
        return node
    }

    /// How many parent links find(x) follows
    func steps(_ x: Int) -> Int {
        var node = x
        var count = 0
        while parent[node] != node {
            node = parent[node]
            count += 1
        }
        return count
    }

    mutating func union(_ a: Int, _ b: Int) {
        let rootA = find(a)
        let rootB = find(b)
        if rootA != rootB { parent[rootA] = rootB }
    }
}

for n in [10, 100, 1_000] {
    var sets = NaiveUnionFind(count: n)
    for i in 0..<(n - 1) {
        sets.union(i, i + 1)
    }
    let total = (0..<n).reduce(0) { $0 + sets.steps($1) }
    print("n = \(n): find(0) takes \(sets.steps(0)) steps; one find on every element takes \(total)")
}
```

```output
n = 10: find(0) takes 9 steps; one find on every element takes 45
n = 100: find(0) takes 99 steps; one find on every element takes 4950
n = 1000: find(0) takes 999 steps; one find on every element takes 499500
```

A single find is O(n) in the worst case, and n finds cost n(n − 1) / 2 steps: O(n²), no better than the labels. union calls find twice, so it suffers too. The tree idea is right; the shape is the problem. The next lesson adds two small changes that keep every tree almost flat.

## Keys that aren't 0 to n − 1

Union-find works on array indices. When your elements are emails, usernames or grid cells, give each one an index first. For strings, a dictionary from key to index does it, exactly as in [Dictionaries and lookups](/dsa/learn/swift-dictionaries):

```swift
var indexOf: [String: Int] = [:]
for email in ["ana@x.com", "ben@y.com", "ana@x.com"] where indexOf[email] == nil {
    indexOf[email] = indexOf.count          // 0, 1, …: the next free index
}
// indexOf["ana@x.com"] is 0 and indexOf["ben@y.com"] is 1
```

A grid cell (row, column) becomes `row * columns + column`, as in [Direction arrays for grid moves](/dsa/learn/matrix-directions).

## Union-find or a graph search?

| Situation | Better tool |
| --- | --- |
| The graph is fixed, and you want every component once | DFS or BFS: one O(V + E) pass |
| Edges keep arriving, with questions in between | Union-find |
| You're given a bare list of edges, with no adjacency list | Union-find: no need to build one |
| You need the actual path between a and b | DFS or BFS: union-find only says whether one exists |
| Edges are removed as well as added | Neither directly: union-find can't split a set |

<Callout kind="gotcha" title="Common mistakes">
- **Comparing parents instead of roots.** `parent[a] == parent[b]` misses nodes at different depths of the same tree. Compare `find(a) == find(b)`.
- **Linking the element instead of its root.** `parent[a] = b` cuts a out of its old tree and leaves the rest of its group behind. Always link `parent[find(a)] = find(b)`.
- **Starting with zeros.** `Array(repeating: 0, count: n)` makes element 0 the parent of everyone: one big set before any union. Start with `Array(0..<n)`.
</Callout>
