## Why it matters

There are two very different ways a function can use a closure you hand it. `sorted(by:)` uses your closure **right now**, while it sorts, and is finished with it by the time it returns. A button, on the other hand, keeps its action closure **for later** and runs it whenever someone taps. So does code that fetches data and calls you back when it arrives. Swift makes you mark the "for later" kind with `@escaping`, and you'll see that word all over Apple's APIs. Knowing what it means makes those signatures readable, and explains a whole class of compiler errors.

## Non-escaping: used now

By default, a closure parameter is **non-escaping**. The function may call it any number of times, but only **while the function is running**. When the function returns, the closure is gone:

```swift run
func withBorder(_ drawContent: () -> Void) {
    print("+------+")
    drawContent()
    print("+------+")
}

withBorder {
    print("| Hi!  |")
}
```

```output
+------+
| Hi!  |
+------+
```

`withBorder` calls the closure between its two lines and then forgets it. Every closure you passed to `sorted(by:)` in the last two lessons was used this way, and so is every closure you'll pass to `map`, `filter` and `reduce`.

## Escaping: kept for later

A closure **escapes** when it's still around after the function returns. That happens when the function:

- stores it somewhere outside itself, such as a variable or an array; or
- returns it.

Swift requires you to mark such a parameter with `@escaping`, written before its type. Here's a list of callbacks to run when a document is saved:

```swift run
var onSave: [() -> Void] = []

func whenSaved(_ callback: @escaping () -> Void) {
    onSave.append(callback)
}

whenSaved { print("Update the title bar") }
whenSaved { print("Show a tick") }
print("Callbacks registered: \(onSave.count)")

print("Saving...")
for callback in onSave {
    callback()
}
```

```output
Callbacks registered: 2
Saving...
Update the title bar
Show a tick
```

What to notice:

- `whenSaved` doesn't call the closure at all. It stores it in `onSave` and returns.
- The closures run much later, after both calls to `whenSaved` have finished. That's what "escaping" means: the closure outlives the call.
- `@escaping` goes on the **parameter's type**, in the function's signature.

### Without @escaping

Leave the annotation off and Swift refuses to compile the function:

```swift
func whenSaved(_ callback: () -> Void) {
    onSave.append(callback)
}
```

```text title="What you'll see"
error: converting non-escaping parameter 'callback' to generic parameter 'Element' may allow it to escape
```

In plain words: "you're putting this closure into an array, where it could be kept after the function returns, but you didn't say it was allowed to escape." Storing it in an ordinary variable gives a similar error: `assigning non-escaping parameter 'callback' to an '@escaping' closure`. The fix is the same: add `@escaping`.

## A closure that runs after the function has returned

The classic escaping closure is a **completion handler**: "do this work, and call me back with the result when you're done". Real apps use it for network requests. Here's a simulation, with no networking, that shows the order things happen in:

```swift run
var pendingWork: [() -> Void] = []

func loadScore(for player: String, completion: @escaping (Int) -> Void) {
    pendingWork.append {
        let score = player.count * 10   // pretend this came from a server
        completion(score)
    }
    print("Asked for \(player)'s score")
}

loadScore(for: "Ada") { score in
    print("Ada scored \(score)")
}
loadScore(for: "Maneet") { score in
    print("Maneet scored \(score)")
}

print("Doing other things...")

// Later, the work finishes
for work in pendingWork {
    work()
}
```

```output
Asked for Ada's score
Asked for Maneet's score
Doing other things...
Ada scored 30
Maneet scored 60
```

What to notice:

- Both calls to `loadScore` return straight away. The scores are printed only when the pending work runs at the end.
- The `completion` closures had to escape, because they're called from inside closures that were stored in `pendingWork`.
- Each completion still remembers which player it was for, thanks to capturing from the last lesson.

## Why Swift makes the distinction

**For readers.** `@escaping` in a signature warns you that your closure might run later, after the code around it has moved on, so any variables it captured may have changed by then. No `@escaping` means "this runs now, or not at all".

**For safety.** A non-escaping closure can safely use things that only exist during the call. For example, it can capture an `inout` parameter, as the nested `reverse(from:to:)` helper did in M05. An escaping closure can't, because the `inout` value is copied back when the function returns, and the closure might run after that. Swift reports `escaping closure captures 'inout' parameter`.

**For speed.** Because a non-escaping closure can't outlive the call, Swift doesn't need to keep its captured variables alive afterwards, which lets it skip some bookkeeping. That's one reason non-escaping is the default.

## Two cases that escape without the keyword

| Situation | Escaping? | Do you write `@escaping`? |
| --- | --- | --- |
| A closure parameter that's only called during the function | No | No |
| A closure parameter that's stored or returned | Yes | Yes |
| A closure the function creates itself and returns, like `makeCounter` | Yes | No: it's not a parameter |
| An optional closure parameter, `(() -> Void)?` | Yes, automatically | No |

`@escaping` only ever appears on **parameters**. In [Capturing values](/dsa/learn/swift-capturing), `makeCounter` returned a closure it had created itself, so there was nothing to annotate. And an optional closure parameter is treated as escaping automatically, because it's wrapped inside an optional value that could be stored anywhere.

<Callout kind="note" title="Escaping closures in classes">
When an escaping closure is written inside a class's method and uses the class's own properties, Swift makes you write `self.` explicitly, as a reminder that the closure keeps the object alive. You'll build classes in M09, and meet the `[weak self]` capture list that often goes with this in M11, Memory, ARC and references.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: don't add @escaping everywhere">
It's tempting to sprinkle `@escaping` on every closure parameter to silence errors. Don't. It removes the "runs now" guarantee, stops the closure capturing `inout` parameters and costs a little speed. Add it only when the function really stores or returns the closure. In DSA code you'll rarely need it at all: almost every closure you write there is used immediately.
</Callout>
