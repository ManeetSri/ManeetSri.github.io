## Why it matters

After a module of `map`, `filter` and `reduce`, it's tempting to write every loop as a chain. Often that's the clearest code. Sometimes it isn't: a chain can do far more work than needed, walk the data several times, or hide simple logic behind clever closures. Good Swift developers switch between the two styles freely. This lesson gives you the questions to ask, and connects them to the work your code really does, which is the heart of DSA.

## Question 1: can it stop early?

Suppose you want the first number over 100. Here are three ways, each counting how many numbers it checks:

```swift run
let numbers = Array(1...1_000)

var checks = 0
let viaFilter = numbers.filter { n in
    checks += 1
    return n > 100
}.first
print(viaFilter ?? -1, "after", checks, "checks")

checks = 0
let viaFirst = numbers.first { n in
    checks += 1
    return n > 100
}
print(viaFirst ?? -1, "after", checks, "checks")

func firstOver(_ limit: Int, in values: [Int]) -> Int? {
    for value in values {
        if value > limit {
            return value
        }
    }
    return nil
}
print(firstOver(100, in: numbers) ?? -1)
```

```output
101 after 1000 checks
101 after 101 checks
101
```

What to notice:

- `filter { … }.first` checks **all 1,000** numbers and builds an array of 900, then throws all but one away.
- `first(where:)` stops at the first match: 101 checks.
- The plain loop with `return` stops at the same place. It's longer, but it's the version to reach for when the stopping rule gets complicated.

The lesson: when you're **searching**, use a tool that stops early, such as `first(where:)`, `contains(where:)` or `firstIndex(where:)`, or a loop with `return` or `break`. A chain that builds a whole array to look at one element is a common, quiet waste.

## Question 2: how many passes?

Say you want several facts about some temperatures: the lowest, the highest, the total and how many were below zero. The higher-order way is short:

```swift run
let temperatures = [4, -2, 9, 0, -5, 7]

let lowest = temperatures.min() ?? 0
let highest = temperatures.max() ?? 0
let total = temperatures.reduce(0, +)
let belowZero = temperatures.filter { $0 < 0 }.count
print(lowest, highest, total, belowZero)
```

```output
-5 9 13 2
```

That's four separate passes over the data, plus a temporary array for the filter. One loop can collect everything at once:

```swift run
let temperatures = [4, -2, 9, 0, -5, 7]

var lowest = temperatures[0]
var highest = temperatures[0]
var total = 0
var belowZero = 0
for t in temperatures {
    lowest = min(lowest, t)
    highest = max(highest, t)
    total += t
    if t < 0 {
        belowZero += 1
    }
}
print(lowest, highest, total, belowZero)
```

```output
-5 9 13 2
```

Both versions are **O(n)**: four passes is about 4n steps, and Big O ignores the constant 4. For six temperatures the difference is nothing, and the first version is easier to read. For ten million readings, one pass instead of four is a real saving, and it's the kind of optimisation interviewers like to hear you mention. (The loop version also assumes the array isn't empty, because it starts from `temperatures[0]`.)

Chains have the same cost. `filter`, then `map`, then `reduce` walks the data three times and builds two temporary arrays. Usually that's fine. When it isn't, `lazy` (from the previous lesson) or a single loop removes the extra arrays.

## Question 3: which is easier to read?

Higher-order functions read best when each step is a simple, independent rule: keep these, transform each, add them up. They get awkward when the logic needs to **remember things between elements**. Here's the length of the longest run of rising temperatures, written both ways:

```swift run
let temps = [3, 5, 6, 2, 4, 7, 9, 1]

// A loop: the state is plain variables
var longest = 1
var current = 1
for i in 1..<temps.count {
    if temps[i] > temps[i - 1] {
        current += 1
    } else {
        current = 1
    }
    longest = max(longest, current)
}
print(longest)

// reduce: the state has to be squeezed into a tuple
let result = temps.dropFirst().reduce((longest: 1, current: 1, previous: temps[0])) { state, t in
    let current = t > state.previous ? state.current + 1 : 1
    return (max(state.longest, current), current, t)
}
print(result.longest)
```

```output
4
4
```

Both give 4, for the run 2, 4, 7, 9. The loop says plainly what it tracks. The `reduce` version is correct, but you have to decode it. When the clever version needs a comment to explain it, write the loop.

## The hidden nested loop

One trap matters more than any other, because it changes the Big O. Each of these lines looks like a single step:

```swift
let shared = listA.filter { listB.contains($0) }
```

But `contains` walks `listB` for **every** element of `listA`. With n elements in one and m in the other, that's up to n × m steps: **O(n·m)**, or O(n²) when they're the same size. A closure that calls something that loops is a loop inside a loop. In M07 you'll fix this with a `Set`, whose `contains` is O(1) on average, bringing the whole thing down to O(n + m).

Whenever a closure calls `contains`, `firstIndex`, `filter` or anything else that walks a collection, ask how big that collection can get.

## A rule of thumb

| Situation | Prefer |
| --- | --- |
| Transform, select or combine with simple rules | `map`, `filter`, `reduce` |
| Find the first match, or check whether one exists | `first(where:)`, `contains(where:)`, or a loop with `return` |
| Several results from one pass over big data | a single loop, or one `reduce(into:)` |
| Logic that depends on the previous element or running state | a loop |
| Only part of a long chain's result is needed | `lazy` |

<Callout kind="tip" title="Both are tools, not rules">
Neither style is "more advanced". Write whichever makes the intent clearest, then check the work: does it stop when it can, does it walk the data more often than needed, and is there a loop hiding inside a closure?
</Callout>
