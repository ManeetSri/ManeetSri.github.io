## Why it matters

When you practise a module's problems in order, you know the pattern before you read the first line: it's the sliding-window module, so it's a sliding window. Interviews never tell you. The hardest part of a real problem is often the first five minutes, recognising what kind of problem it is, and that only gets practised when problems arrive at random from everything you know. This lesson explains how the console draws those problems, and what "mastered" means for them. Most of its 45 minutes is for running a random mock.

## How the Mock page chooses a problem

When you press "Start the mock" on the [Mock interview](/dsa/mock) page, it builds a pool and draws from it:

1. **Only topics you've finished.** A problem is eligible if it practises at least one lesson you've finished: marked complete, or tested out (after passing a checkpoint, or in the placement when you started).
2. **The difficulty filter.** Any, Easy, Medium or Hard narrows the pool. The page shows how many problems are left to draw from.
3. **Unsolved first.** If the pool has problems you haven't solved yet, it draws only from those, so the mock is a real test. Once you've solved everything in the pool, any of them can come up.
4. **Random.** One problem is drawn from what's left.

Here are those steps as code, on a small made-up problem bank:

```swift run
struct Problem {
    let title: String
    let difficulty: String
    let lessons: [String]
}

let problems = [
    Problem(title: "Two sum with indexes", difficulty: "easy", lessons: ["hash-frequency-two-sum"]),
    Problem(title: "Longest unique run", difficulty: "medium", lessons: ["sw-longest-no-repeat"]),
    Problem(title: "Count and measure the islands", difficulty: "medium", lessons: ["gt-islands"]),
    Problem(title: "Signal spread time", difficulty: "medium", lessons: ["sp-dijkstra", "sp-problems"]),
    Problem(title: "Smallest covering window", difficulty: "hard", lessons: ["sw-min-window"]),
]
let finishedLessons: Set<String> = ["hash-frequency-two-sum", "sw-longest-no-repeat", "gt-islands", "sw-min-window"]
let solved: Set<String> = ["Longest unique run"]

func choices(difficulty: String) -> [String] {
    // 1. Only problems that practise at least one lesson you've finished
    let learned = problems.filter { $0.lessons.contains(where: finishedLessons.contains) }
    // 2. The difficulty filter
    let pool = learned.filter { difficulty == "any" || $0.difficulty == difficulty }
    // 3. Prefer problems you haven't solved, if there are any
    let fresh = pool.filter { !solved.contains($0.title) }
    return (fresh.isEmpty ? pool : fresh).map(\.title)
}

print(choices(difficulty: "any"))
print(choices(difficulty: "medium"))
print(choices(difficulty: "hard"))
```

```output
["Two sum with indexes", "Count and measure the islands", "Smallest covering window"]
["Count and measure the islands"]
["Smallest covering window"]
```

"Signal spread time" never appears, because its lessons aren't finished. "Longest unique run" is left out while an unsolved medium exists. The real page then picks one of the choices at random.

## What "mastered" means in the console

Three different signals are easy to mix up:

| Signal | How you earn it | Where you see it |
| --- | --- | --- |
| A lesson is finished | "Mark complete", or testing out at a checkpoint or placement | "Done" or "Tested out" on the Path page |
| A module is mastered | Passing its checkpoint: 12 questions from its lessons, 80% to pass | A "Mastered" chip on the Path page |
| A problem is solved | Logging an attempt as "Solved" | The Practice page's Status |

The Mock page only looks at the first: finished lessons. It doesn't check checkpoints. So a topic can be in your mock pool before you're really comfortable with it.

A sensible working definition: **a topic is mastered when you've passed its module checkpoint and can re-solve its problems from scratch when the Review page brings them back.** Checkpoints test recognition and recall; re-solves test that you can still produce the code. Before relying on random mocks for a part of the course, retake the checkpoints for its modules. They draw different questions each time, so retaking them is good revision too.

## Why random, mixed practice works

Practising one pattern ten times in a row feels smooth, but much of that smoothness comes from knowing which tool to use before you start. Mixing topics, called **interleaving**, feels harder and is slower at first, but it trains the step blocked practice skips: deciding *which* tool. It also improves how long you remember, as you saw in [How to learn DSA so it sticks](/dsa/learn/start-how-to-learn).

Random mocks are interleaving at full strength. On days without a mock, the Practice page's "Random from what I've learned" button gives you the same mix without a timer: it opens a random unsolved problem from lessons you've marked complete.

## The recognition step

When a random problem appears, spend the first two minutes on a short written triage, as comments in your editor, before any code:

- **Input and output:** the types, and what exactly is returned.
- **Size:** the largest n, and the complexity it allows ([From n to a feasible complexity](/dsa/learn/bigo-feasibility-table)).
- **Signal words:** "contiguous", "sorted", "fewest steps", "all combinations", "k largest", "intervals".
- **Two candidate patterns**, and which one you'll try first and why.

Here's that triage for three short statements:

> Buildings stand in a row. For each one, count how many buildings to its right it can see over before a taller one blocks the view. Up to 10⁵ buildings.

Arrays of heights, 10⁵ so O(n) or O(n log n). "To its right… before a taller one" is next-greater-element language. Candidates: a monotonic stack, or a brute-force scan. Try the stack.

> A robot crosses a warehouse grid with walls. Moving onto a conveyor cell is free; any other move costs 1. Find the cheapest route to the dock.

A grid as a graph, edge weights 0 and 1. Candidates: Dijkstra, or 0-1 BFS with a deque. 0-1 BFS is simpler and O(V + E) ([0-1 BFS with a deque](/dsa/learn/sp-zero-one-bfs)).

> Split an array of up to 10⁵ positive numbers into k contiguous parts so that the largest part sum is as small as possible.

"Minimise the maximum", with a yes/no check (can I split with every part at most X?) that flips once as X grows. Candidates: DP, or binary search on the answer. With 10⁵ elements, binary search on the answer ([Split array largest sum](/dsa/learn/bsa-split-array)).

Each triage took a few sentences, and each ended with a plan to say out loud. [Reading the pattern from constraints and wording](/dsa/learn/pat-recognition) has the full map, and [Mixed-pattern drills](/dsa/learn/pat-mixed-drills) is more practice at exactly this step.

## A weekly rhythm

Random mocks work best as a steady habit rather than a cram:

| Day | Mock | Why |
| --- | --- | --- |
| Early in the week | 45 min, Any difficulty | A realistic round |
| Midweek | 30 min, Medium | Speed on the most common level |
| Weekend | 60 min, Hard, when you're ready | Stretch, and stamina |

Two or three a week, each followed by the rubric and a note, is plenty alongside the rest of the course. Two rules make them honest:

- **Don't re-roll a draw you don't like.** Interviews don't let you. The problem you'd rather skip is usually the one you most need.
- **A repeat is still worth doing.** Once you've solved everything in the pool, old problems come back. Re-solving one under a timer, without looking at your old code, is valuable spaced practice.

## Run one now

Open the [Mock interview](/dsa/mock) page, choose 45 minutes and Any difficulty, and start. Before writing code, do the written triage above. Talk out loud as you work. When the time is up or you press "I'm done", score yourself with the rubric, then read the next lesson to check your scores were fair.

<Callout kind="gotcha" title="Random-mock mistakes">
- **Mocking topics you haven't really learned.** Finishing a lesson puts its problems in the pool, but passing the checkpoint is what shows you know it.
- **Skipping the triage.** Jumping straight to code on a random problem is how you end up twenty minutes deep in the wrong pattern.
- **Only drawing Easy.** Comfortable mocks don't build the skill. Most draws should be Medium.
- **No follow-up.** Saving the rubric schedules a re-solve; actually do it when the Review page brings it back.
</Callout>
