## Why it matters

Many interview rounds hold two problems in 45 to 60 minutes, and online assessments often give two or three problems in an hour or more. Solving one problem well isn't the same skill as managing a clock across several: you have to decide which to do first, when to stop and move on, and how to leave something useful behind when time runs out. This lesson shows how to build and run a timed set with the console. Most of its 60 minutes is for running your first set.

## What a timed set is

A **timed set** is two or three problems, one fixed block of time, and interview rules: no hints, no solutions, no looking things up, and no running the tests until the time is up. After the clock stops, you test, score and review.

It differs from a single mock in three ways:

- **Budgeting.** Each problem gets a share of the time, and you stop at the end of its share.
- **Ordering.** When you can see all the problems at once, the order you do them in matters.
- **Triage.** Something correct and simple for every problem usually beats a perfect answer to one and nothing for the others.

## Choosing the mix

A set should feel like a real round: mostly medium, from topics you've finished, with **different patterns** in each problem. Two sliding-window problems in one set tell you the pattern of the second before you read it.

| Set | Total | Mix | Budgets |
| --- | --- | --- | --- |
| Warm-up | 45 min | easy + medium | 15 + 25, 5 spare |
| Standard | 60 min | medium + medium | 25 + 25, 10 spare |
| Assessment | 60 min | easy + medium + medium | 11 + 22 + 22, 5 spare |
| Stretch | 60 min | medium + hard | 20 + 35, 5 spare |

As rough guides, an easy problem deserves 10 to 15 minutes, a medium 20 to 25, and a hard one 35 to 40. Every problem page shows an estimate like "~25 min"; in a set, aim to beat it.

Splitting time by weight is simple arithmetic, so here it is as code. Easy counts 1, medium 2, hard 3:

```swift run
enum Difficulty: Int {
    case easy = 1, medium = 2, hard = 3        // the raw value is the weight
}

// Splits the time between the problems by weight, keeping a buffer at the end
func plan(_ problems: [(title: String, level: Difficulty)], minutes: Int, buffer: Int) -> [String] {
    let totalWeight = problems.reduce(0) { $0 + $1.level.rawValue }
    var clock = 0
    var lines: [String] = []
    for problem in problems {
        let share = (minutes - buffer) * problem.level.rawValue / totalWeight
        lines.append("\(clock)–\(clock + share) min: \(problem.title) (\(problem.level))")
        clock += share
    }
    lines.append("\(clock)–\(minutes) min: buffer, then stop")
    return lines
}

let set: [(title: String, level: Difficulty)] = [
    ("Balanced brackets", .easy),
    ("Longest unique run", .medium),
    ("Count and measure the islands", .medium),
]
print(plan(set, minutes: 60, buffer: 5).joined(separator: "\n"))
```

```output
0–11 min: Balanced brackets (easy)
11–33 min: Longest unique run (medium)
33–55 min: Count and measure the islands (medium)
55–60 min: buffer, then stop
```

Write the plan down before you start, as clock times. "At 33 minutes I move to the islands, whatever state the window problem is in" is a decision you make calmly beforehand, not in a panic at minute 40.

## Building a set on the Practice page

The [Practice](/dsa/practice) page has everything you need to pick problems without spoiling them:

1. Set **Status** to "Not tried", so the set is a real test. For a revision set, use "Due for a re-solve" instead.
2. Set **Difficulty** to the first level in your mix.
3. Optionally set **List** to "Core 75" for interview classics, or "Patterns 150" for breadth.
4. Pick a problem from a topic you've finished. Note its title, but don't open it yet.
5. Change the difficulty and pick the next one, **from a different topic**.

Leave the **Pattern** filter on "Any" and don't press the pattern chips at the top: choosing by pattern gives the game away. On a problem page the pattern is hidden behind "Show pattern" for the same reason; during a set, never press it.

## Running a set with the Mock page

The [Mock interview](/dsa/mock) page runs one problem at a time under interview conditions. You choose a **time limit** (30, 45 or 60 minutes) and a **difficulty** (Any, Easy, Medium or Hard), and it draws a problem from lessons you've finished, preferring ones you haven't solved. The statement shows; hints and solutions are hidden. The countdown turns red in the last five minutes, "I'm done" ends early, and either way you land on the scoring rubric ([Scoring yourself with a rubric](/dsa/learn/mock-rubric)).

So a two-problem, 60-minute set is two mocks back to back:

1. Start a 30-minute mock at Easy or Medium. Work it, then press "I'm done" or let time run out.
2. Score it quickly and save. Don't read the solutions yet.
3. Start a second 30-minute mock at Medium straight away.
4. Review both at the end.

The Mock page's shortest limit is 30 minutes, so for three problems in an hour, use the problems you chose on the Practice page instead. Set a timer for the whole hour, open each problem in turn, and use the stopwatch on its page to see how long each one took. When you finish, log each attempt there with "How did it go?" and "When should it come back?".

## Rules for the clock

- **When you can see every problem, read them all first.** Spend two minutes skimming, then start with the one you're surest of. Banking an early solve calms the rest of the set.
- **Stop at the budget.** When a problem's time is up, write two or three comment lines saying what you'd do next, and move on. You can come back if there's time left at the end.
- **Use the triage rule.** A third of the way into a problem's budget with no approach? Write the brute force. Two thirds in with no working code? Simplify and finish something that handles the main case.
- **Carry spare time forward.** If one problem finishes early, the extra goes to the next problem, not to polishing.
- **Don't run the tests during the set.** Dry run instead, as you would in an interview ([Testing your own code](/dsa/learn/int-testing)). The tests are for afterwards.
- **Talk out loud anyway.** Communication is still on the rubric.

<Callout kind="tip" title="Partial credit is real">
In interviews, a clear brute force with its complexity, or a correct solution missing one edge case, scores far better than a blank. In online assessments, hidden tests often include small cases that a brute force passes. Never leave a problem with nothing.
</Callout>

## After the set

The review isn't on the clock, and it's where most of the learning happens. Allow 15 to 20 minutes:

1. **Run each problem's tests** in the companion package, with `swift test --filter` and the suite name shown on the problem page.
2. **Log every attempt** honestly. The Mock page does this when you save the rubric; on a problem page, press "Log this attempt". Either way, the problem is scheduled for a re-solve.
3. **Read the solutions with fresh eyes**, especially the approaches you didn't think of.
4. **Write one line in each problem's Notes**: the key insight or the mistake. These appear on the Notes page, and they feed your weekly review ([The weekly mistakes review](/dsa/learn/mock-mistakes-review)).
5. **Compare the plan with what happened.** Where did the time actually go: understanding, choosing an approach, coding or debugging?

Each set mixes patterns, so recognising the pattern is part of the test. When you're done, review it with the steps above. Next time, build your own set with the Practice page filters, or use two Mock page draws.

<Callout kind="gotcha" title="Timed set mistakes">
- **Sinking the whole set into one problem.** The budget exists so the last problem gets its time too. Stop when it's up.
- **Reviewing between problems.** Reading the first solution before starting the second breaks the clock and the conditions. Review at the end.
- **Choosing by pattern.** Filtering by pattern turns a recognition test into a recall test.
- **Skipping the review.** An unreviewed set is just a stressful hour. The learning is in the 20 minutes afterwards.
</Callout>
