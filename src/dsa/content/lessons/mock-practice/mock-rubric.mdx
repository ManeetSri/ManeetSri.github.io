## Why it matters

A mock without honest scoring is only half a mock. The rubric is how you find out *what* to practise: maybe your code is fine but you never state complexity, or you explain beautifully but miss edge cases. It's also roughly how interviewers write their feedback, so learning to see your own work through it is learning to see it through theirs. Scores you inflate teach you nothing, and in this console they also bring problems back on the wrong schedule.

## The five criteria, level by level

After each mock, the [Mock interview](/dsa/mock) page asks you to rate five criteria as **Not yet**, **Getting there**, **Solid** or **Strong**. Here's what each level looks like in practice.

### Understanding

Restated the problem and asked about edge cases before coding.

| Level | Looks like |
| --- | --- |
| Not yet | Started coding at once; misread what to return |
| Getting there | Restated it, but missed an edge case the tests then caught |
| Solid | Restated it, asked about size and empty input, wrote two examples |
| Strong | All of that, and settled an ambiguity with an example |

### Approach

Started from brute force and reasoned towards something better.

| Level | Looks like |
| --- | --- |
| Not yet | No working plan; jumped between half-ideas |
| Getting there | Reached a brute force but couldn't improve it |
| Solid | Brute force, then the right pattern, with a reason |
| Strong | Compared two approaches by cost and chose deliberately |

### Correctness

The code works, including the edge cases.

| Level | Looks like |
| --- | --- |
| Not yet | Doesn't compile, or fails ordinary cases |
| Getting there | Ordinary cases pass; an edge case fails |
| Solid | All tests pass after a bug you found yourself by tracing |
| Strong | All tests pass first time, and you had traced the edge cases |

### Complexity

Stated the time and space cost, and why.

| Level | Looks like |
| --- | --- |
| Not yet | Didn't say it, or got it wrong |
| Getting there | Right time, but no space or no reason |
| Solid | Time and space, each with its reason |
| Strong | Also named the bottleneck and whether better is possible |

### Communication

Explained the thinking out loud as you went.

| Level | Looks like |
| --- | --- |
| Not yet | Long silences; code appeared without explanation |
| Getting there | Explained afterwards, not while working |
| Solid | Narrated each phase and announced pauses |
| Strong | Easy to follow throughout; a listener could have helped at any moment |

A useful test for **Strong**: would an interviewer have written it in their notes as a highlight? If you have to argue with yourself about it, it was Solid.

## The outcome

Alongside the five criteria you choose an outcome:

- **Solved it:** working code, with no help.
- **Solved with a nudge:** you peeked at something, such as a hint, a solution, the pattern or an algorithm you looked up, or you ran the tests to find the bug. In an interview, those would have been the interviewer's hints.
- **Didn't finish:** no working solution when time ran out.

## What the console does with your scores

Saving the mock does three things:

1. It stores the scores and your note.
2. It lists the mock under "Past mocks" with the **average** of the five scores out of 4, coloured green at 3 or more, amber from 2, and red below 2.
3. It logs an attempt at the problem and **schedules a re-solve**, choosing the rating from your scores.

That third step is why honesty matters. Here's the rule the console uses, as code:

```swift run
enum Outcome {
    case solved, solvedWithNudge, didNotFinish
}

// How the console turns a mock into a re-solve rating
func rating(_ outcome: Outcome, scores: [Int]) -> String {
    let average = Double(scores.reduce(0, +)) / Double(scores.count)
    if outcome == .didNotFinish || average < 2 { return "Again" }
    if average < 2.75 { return "Hard" }
    if average < 3.5 { return "Good" }
    return "Easy"
}

let mocks: [(Outcome, [Int])] = [
    (.solved, [3, 3, 4, 2, 3]),
    (.solved, [4, 4, 4, 3, 4]),
    (.solvedWithNudge, [2, 3, 2, 2, 3]),
    (.didNotFinish, [4, 4, 1, 4, 4]),
]
for (outcome, scores) in mocks {
    let average = Double(scores.reduce(0, +)) / Double(scores.count)
    print(scores, average, rating(outcome, scores: scores))
}
```

```output
[3, 3, 4, 2, 3] 3.0 Good
[4, 4, 4, 3, 4] 3.8 Easy
[2, 3, 2, 2, 3] 2.4 Hard
[4, 4, 1, 4, 4] 3.4 Again
```

The scores count 1 for Not yet up to 4 for Strong. "Didn't finish" always means Again, however good the rest was: the problem comes back in about ten minutes, so it's in today's Review queue. Hard brings it back soon, Easy much later. Inflate your scores and a problem you struggled with disappears for weeks.

## Scoring honestly

- **Score what happened, not what you knew.** If you knew the complexity but didn't say it, Complexity is Not yet. Interviewers can only score what they hear.
- **Let the tests decide Correctness.** After "I'm done", the rubric stays open while you run `swift test --filter` with the suite name in Terminal. Fill in Correctness after you've seen the result.
- **Peeking caps the scores.** If you looked at a hint, Approach can't be Strong, and the outcome is "Solved with a nudge".
- **Silence caps Communication.** If you didn't talk out loud, it's Not yet, however good the code.
- **Write one concrete next step** in "What to practise next": "Trace the last loop pass before saying I'm done", not "be more careful".

## Seeing the trend

The Past mocks list shows each mock's average, which is the quickest way to see whether mocks are getting easier. For per-criterion trends, add your five scores to the problem's Notes after saving, for example "Mock: 3 3 2 3 2, complexity and communication weak". Every few weeks, look across those notes: your lowest criterion is where the next week's practice should go. [The weekly mistakes review](/dsa/learn/mock-mistakes-review) builds that into a routine.

<Callout kind="gotcha" title="Scoring mistakes">
- **Scoring the idea instead of the performance.** "I would have got there" isn't a score.
- **Everything Solid.** If every criterion is always the same level, you're not really scoring. Some will be weaker; find them.
- **Scoring before testing.** Correctness without the tests is a guess.
- **Being harsh to be safe.** Underscoring wastes re-solves on problems you know. Aim for accurate, not modest.
</Callout>
