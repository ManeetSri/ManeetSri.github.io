## Why it matters

Every integer type has a largest and smallest value, as you saw in [Integers: Int, UInt and sized integers](/dsa/learn/swift-integers). **Overflow** is what happens when a calculation goes past one of those limits. Some languages quietly wrap around to a wrong answer. Swift stops the program instead. In DSA, overflow is a real risk whenever you add up many large values, multiply, or compute a middle position. Some algorithms, such as hash functions, want wrapping on purpose, and Swift has special operators for that.

## What overflow is

Picture a car's mileage counter with three digits. It reads 999, you drive one more mile, and it shows 000. The real distance didn't go back to zero. The counter simply has nowhere to store the extra digit.

Integer types work the same way, in binary. `Int8.max` is 127. Adding 1 needs a value the type can't hold. Many languages, such as C and Java, wrap around to the most negative value and carry on, giving you a wrong answer with no warning. That kind of silent bug can survive for years.

## Swift traps on overflow

Swift takes the opposite approach: **overflow is an error**. If the compiler can see the overflow, for example in arithmetic on literal values, it refuses to build:

```swift
let small: Int8 = 127 + 1
```

```text title="What you'll see"
error: arithmetic operation '127 + 1' (on type 'Int8') results in an overflow
```

More often, the values aren't known until the program runs. Then Swift checks every `+`, `-` and `*` as it happens, and **traps**, stopping the program immediately, if the result doesn't fit. Here a loop, which you'll learn in M03, adds 1 to `level` ten times:

```swift
var level: Int8 = 120
for _ in 1...10 {
    level += 1
}
```

```text title="What you'll see"
Swift runtime failure: arithmetic overflow
```

The eighth addition would make 128, one more than `Int8.max`, so the program stops there. That's the message Xcode shows beside the line that overflowed. Run from Terminal, the program stops with a crash report instead of printing anything further. Unsigned types trap in the other direction too: for a `UInt` holding 0, subtracting 1 overflows, because there are no negative values to go to.

It might seem harsh to crash, but compare the alternatives. A crash points straight at the line with the problem. A silently wrong number might corrupt a user's data, or make a test pass by accident.

## Wrapping on purpose: `&+`, `&-` and `&*`

Sometimes wrapping around is exactly what you want. Swift's **overflow operators** put an `&` in front of the usual operator, and they wrap instead of trapping:

```swift run
print(Int8.max &+ 1)
print(UInt8.min &- 1)
print(UInt8(200) &* 2)
```

```output
-128
255
144
```

- `127 &+ 1` wraps past the top of `Int8` to the bottom: -128.
- `0 &- 1` wraps below the bottom of `UInt8` to the top: 255.
- `200 &* 2` is 400, which is 144 more than 256, so it wraps to 144.

The wrapped result is the true answer with the bits that don't fit thrown away. For `UInt8`, that's the same as taking the remainder after dividing by 256.

### Where wrapping is useful

**Hash functions** turn data into a number by mixing it with lots of multiplication and addition. The exact size of the result doesn't matter, only that it's always computed the same way, so wrapping is fine and avoids crashes:

```swift run
var hash: UInt8 = 17
hash = hash &* 31 &+ 65
print(hash)
```

```output
80
```

`17 &* 31` is 527, which wraps to 15, and then `15 &+ 65` is 80. You'll write real hash functions in Part III. Checksums and random number generators use the same trick.

<Callout kind="warning">
Don't use `&+` just to make a crash go away. If a sum overflows in a problem that needs the real total, wrapping gives a wrong answer silently, which is the very bug Swift was protecting you from. Use a bigger type, or a different approach.
</Callout>

## Checking before it happens

If overflow is possible and you want to *handle* it rather than crash, every integer type has methods that report it:

```swift run
let big = Int.max
let result = big.addingReportingOverflow(1)
print(result.overflow)
print(result.partialValue == Int.min)
let safe = 40.addingReportingOverflow(2)
print(safe.overflow, safe.partialValue)
```

```output
true
true
false 42
```

`addingReportingOverflow` gives back two values together: `partialValue`, the wrapped result, and `overflow`, a `Bool` that's `true` if the real answer didn't fit. Two values grouped like this form a **tuple**, which you'll meet properly in *Tuples and typealias*, the last lesson of this module.

There's one for each operator:

| Method | Checks |
| --- | --- |
| `a.addingReportingOverflow(b)` | `a + b` |
| `a.subtractingReportingOverflow(b)` | `a - b` |
| `a.multipliedReportingOverflow(by: b)` | `a * b` |

Once you can make decisions with `if` (M03), you'll check `overflow` and do something sensible, like reporting an error, instead of crashing.

## Overflow in DSA

You rarely overflow a 64-bit `Int` by accident, but these situations come up:

1. **Sums of many large values.** 10⁵ values of up to 10⁹ sum to at most 10¹⁴: safe in `Int`, but it would overflow `Int32`. This is one more reason to use `Int` everywhere.
2. **Products.** Two values up to 10⁹ multiply to 10¹⁸, which just fits. A third multiplication won't. Problems that say "return the answer modulo 1,000,000,007" expect you to take the remainder after *every* multiplication, to keep numbers small. You'll learn that in Part II.
3. **Middle positions.** `(low + high) / 2` adds two numbers that might both be huge. `low + (high - low) / 2` gives the same middle without the risky addition. It's the standard way to write binary search.
4. **Subtracting from unsigned values.** `UInt` can't go below zero, so `count - 1` traps when `count` is 0. Another reason to prefer `Int`.

<Callout kind="gotcha" title="Swift gotcha: the crash is in debug and release">
In C and C++, signed overflow is undefined behaviour, and the wrong answer may only appear with optimisation turned on. In Swift, `+` traps in both debug and release builds, so an overflow bug shows up the same way wherever you run it. Only the `&` operators wrap.
</Callout>
