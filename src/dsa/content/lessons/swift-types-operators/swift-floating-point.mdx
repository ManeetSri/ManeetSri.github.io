## Why it matters

Not everything is a whole number. Prices, averages, distances, percentages and screen coordinates all need a fractional part. Swift's **floating-point** types handle them, but with a catch that surprises every programmer once: most decimal fractions can't be stored exactly. Understanding why, and how to compare such numbers safely, saves you from bugs that look impossible. In algorithms you'll meet floating point in averages, geometry and some binary searches.

## Double: numbers with a fractional part

A **floating-point number** has a fractional part, like `3.14` or `-0.5`. Any number literal with a decimal point is inferred as a `Double`:

```swift run
let price = 4.99
let distance = 42.195
let whole = 3.0
print(price, distance, whole)
print(7.0 / 2)
```

```output
4.99 42.195 3.0
3.5
```

Notice that `3.0` prints as `3.0`, not `3`. A `Double` always prints with a decimal point, which is a handy clue to a value's type. And dividing doubles keeps the fraction: `7.0 / 2` is `3.5`. In that line, the literal `2` is treated as a `Double` too, because it's being combined with one.

## Double vs Float

Swift has two main floating-point types:

| Type | Bits | Precision | Use it for |
| --- | --- | --- | --- |
| `Double` | 64 | about 15–16 significant digits | almost everything |
| `Float` | 32 | about 6–7 significant digits | graphics, or saving memory in huge arrays |

**Significant digits** are the digits that carry meaning, starting from the first non-zero one. You can see the difference in precision by dividing 1 by 3 in each:

```swift run
let third: Double = 1.0 / 3.0
let rougherThird: Float = 1.0 / 3.0
print(third)
print(rougherThird)
```

```output
0.3333333333333333
0.33333334
```

The `Float` runs out of digits much sooner, and its last digit is already off. Use `Double` unless you have a specific reason not to. Swift picks `Double` by default for exactly this reason.

<Callout kind="note">
In iOS code you'll also see `CGFloat`, used by UIKit and Core Graphics for positions and sizes. On modern devices it's a 64-bit floating-point number like `Double`, but it's a separate type. Swift makes one rare exception for it: it converts between `CGFloat` and `Double` automatically, so you can pass one where the other is expected.
</Callout>

## Why 0.1 + 0.2 isn't 0.3

Here's the surprise:

```swift run
print(0.1 + 0.2)
print(0.1 + 0.2 == 0.3)
```

```output
0.30000000000000004
false
```

This isn't a bug in Swift. Every mainstream language gives the same answer. Floating-point numbers are stored in **binary**, and most decimal fractions don't have an exact binary form.

<Callout kind="analogy">
Try writing 1/3 as a decimal: 0.3333…, and you have to stop somewhere, so what you write is slightly too small. Binary has the same problem with 1/10. The number `0.1` in your code is stored as the nearest binary fraction, which is very slightly off. Add two slightly-off numbers and the tiny errors can show up in the last digit.
</Callout>

Fractions built from halves, quarters and eighths, like `0.5`, `0.25` and `0.375`, *are* exact in binary. Values like `0.1`, `0.2` and `0.3` aren't.

## Comparing doubles safely

Because of these tiny errors, **never check two computed doubles with `==`**. Check whether they're close enough instead: subtract them, take the **absolute value** (the size of a number without its sign) with `abs`, and compare the result with a small **tolerance**:

```swift run
let total = 0.1 + 0.2
let tolerance = 1e-9
print(abs(total - 0.3) < tolerance)
```

```output
true
```

`1e-9` is **scientific notation** for 1 × 10⁻⁹, or 0.000000001. Any number can be written this way: `2.5e3` is 2,500. The right tolerance depends on the problem, but `1e-9` is a common choice for values of everyday size. The tests for this module's floating-point problems compare answers in exactly this way.

<Callout kind="gotcha" title="Swift gotcha: money in Double">
Because `0.1` isn't exact, adding up prices as `Double` slowly collects rounding errors. Real apps store money as a whole number of the smallest unit, like pence or cents, in an `Int`, or use Foundation's `Decimal` type. For learning, `Double` is fine, as long as you never compare with `==`.
</Callout>

## Special values: infinity and NaN

Dividing an **integer** by zero crashes your program, as you'll see later in this module. Floating-point division by zero doesn't crash. It produces special values instead:

```swift run
let zero = 0.0
print(1.0 / zero)
print(-1.0 / zero)
print((0.0 / zero).isNaN)
print(Double.infinity > 1e300)
```

```output
inf
-inf
true
true
```

- `inf` is **infinity**, larger than every other number. `Double.infinity` is a handy starting value when you're searching for the smallest of several doubles.
- `0.0 / 0.0` is **NaN**, short for "not a number": the result of a calculation with no sensible answer. Check for it with `.isNaN`. A NaN isn't equal to anything, not even itself.

## Big numbers and lost precision

A `Double` can hold enormous values, up to about 1.8 × 10³⁰⁸, far beyond `Int.max`. But it keeps only about 16 significant digits. Beyond 2⁵³, roughly 9 × 10¹⁵, it can no longer represent every whole number, so adding 1 may change nothing at all.

For DSA this gives a clear rule: **use `Int` for counting, sums of whole numbers and anything that must be exact.** Use `Double` only when the values really have fractions, like an average or a distance.
