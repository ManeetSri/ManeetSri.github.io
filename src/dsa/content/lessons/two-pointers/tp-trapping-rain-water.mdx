## Why it matters

Trapping rain water is a classic hard interview problem, and a great one to study because it has **three** good solutions, each teaching something different. This lesson builds two: prefix and suffix maximums, which reuse the left-and-right sweeps from [Product of array except self](/dsa/learn/prefix-product-except-self), and then two pointers, which get the space down to O(1) with a careful argument about what each pointer already knows. The third, with a stack, comes in M26.

## The problem

> Bars of width 1 stand side by side, with the given heights. After it rains, water collects in the dips between bars. How many units of water are trapped?

For heights `[4, 1, 3, 0, 2, 5, 1, 2]`, the answer is 11. Here `#` is a bar and `~` is water:

```text
level 5            #
level 4  # ~ ~ ~ ~ #
level 3  # ~ # ~ ~ #
level 2  # ~ # ~ # # ~ #
level 1  # # # ~ # # # #
index    0 1 2 3 4 5 6 7
```

Unlike [Container with most water](/dsa/learn/tp-container-water), every bar counts here: the water sits on top of the bars, in every dip.

## Water above one bar

Think about a single position `i`, not the whole landscape. Water above it is held in by the tallest bar somewhere to its **left** and the tallest bar somewhere to its **right**. It rises to the **lower** of those two, and the bar itself takes up its own height:

> water at `i` = `min(tallest on the left, tallest on the right) − heights[i]`

Include bar `i` itself in both "tallest" values. Then the minimum is always at least `heights[i]`, so the water is never negative. A bar that's taller than everything on one side holds nothing.

Check position 3 in the picture. The tallest bar on its left is 4 (index 0), the tallest on its right is 5 (index 5). The water rises to `min(4, 5) = 4`, and the bar has height 0, so position 3 holds 4 units. Position 6: the tallest on its left is 5, on its right is 2, so `min(5, 2) − 1 = 1`.

## Brute force

For each position, scan left and right for the tallest bars: O(n) per position, O(n²) total.

```swift run
func trappedSlowly(_ heights: [Int]) -> Int {
    var total = 0
    for i in heights.indices {
        let tallestLeft = heights[...i].max()!
        let tallestRight = heights[i...].max()!
        total += min(tallestLeft, tallestRight) - heights[i]
    }
    return total
}

print(trappedSlowly([4, 1, 3, 0, 2, 5, 1, 2]))
```

```output
11
```

The force unwraps are safe: `heights[...i]` and `heights[i...]` both contain `heights[i]`, so neither is empty.

## Prefix and suffix maximums

The brute force recomputes "tallest on the left" from scratch for every position, but it only ever grows as you move right. That's a running maximum: a prefix array with `max` in place of `+`. As [Prefix XOR](/dsa/learn/prefix-xor) noted, `max` has no undo, so it can't answer arbitrary ranges, but these ranges always start at an end, which is exactly what a prefix array can do.

```swift run
func trappedWithArrays(_ heights: [Int]) -> Int {
    let n = heights.count
    guard n > 0 else { return 0 }

    var leftMax = Array(repeating: 0, count: n)
    leftMax[0] = heights[0]
    for i in 1..<n {
        leftMax[i] = max(leftMax[i - 1], heights[i])
    }

    var rightMax = Array(repeating: 0, count: n)
    rightMax[n - 1] = heights[n - 1]
    for i in stride(from: n - 2, through: 0, by: -1) {
        rightMax[i] = max(rightMax[i + 1], heights[i])
    }

    var water: [Int] = []
    for i in 0..<n {
        water.append(min(leftMax[i], rightMax[i]) - heights[i])
    }
    print("leftMax: ", leftMax)
    print("rightMax:", rightMax)
    print("water:   ", water)
    return water.reduce(0, +)
}

print(trappedWithArrays([4, 1, 3, 0, 2, 5, 1, 2]))
```

```output
leftMax:  [4, 4, 4, 4, 4, 5, 5, 5]
rightMax: [5, 5, 5, 5, 5, 5, 2, 2]
water:    [0, 3, 1, 4, 2, 0, 1, 0]
11
```

Three passes, **O(n) time and O(n) space**. This is the version to reach for first in an interview: it's quick to write and easy to explain. The `guard` matters, because `heights[0]` would crash on an empty array.

## Two pointers: O(1) space

Can you do without the two arrays? At each position you need `min(leftMax, rightMax)`, and here's the key observation: **you don't need both values exactly, only the smaller one.**

Run two pointers from the ends, each keeping the tallest bar it has seen so far, `leftMax` and `rightMax`:

- `leftMax` is the **exact** tallest bar on the left of `left`, since the left pointer has seen every one of them.
- `rightMax` is the tallest bar on the right side **seen so far**. The true tallest on the right of `left` can only be bigger, because there are unseen bars between the pointers too.

So if `leftMax ≤ rightMax`, then at position `left`:

> true tallest on the right ≥ `rightMax` ≥ `leftMax`, so `min(true left, true right) = leftMax`

The water at `left` is `leftMax − heights[left]`, **decided**, whatever the unseen bars turn out to be. Record it and move `left` on. The other case is the mirror image: if `rightMax < leftMax`, the water at `right` is decided.

```swift run
func trappedWater(_ heights: [Int]) -> Int {
    var left = 0
    var right = heights.count - 1
    var leftMax = 0
    var rightMax = 0
    var total = 0
    while left <= right {
        leftMax = max(leftMax, heights[left])
        rightMax = max(rightMax, heights[right])
        if leftMax <= rightMax {
            print("position \(left): leftMax \(leftMax) <= rightMax \(rightMax), water \(leftMax - heights[left])")
            total += leftMax - heights[left]
            left += 1
        } else {
            print("position \(right): rightMax \(rightMax) < leftMax \(leftMax), water \(rightMax - heights[right])")
            total += rightMax - heights[right]
            right -= 1
        }
    }
    return total
}

print(trappedWater([4, 1, 3, 0, 2, 5, 1, 2]))
```

```output
position 7: rightMax 2 < leftMax 4, water 0
position 6: rightMax 2 < leftMax 4, water 1
position 0: leftMax 4 <= rightMax 5, water 0
position 1: leftMax 4 <= rightMax 5, water 3
position 2: leftMax 4 <= rightMax 5, water 1
position 3: leftMax 4 <= rightMax 5, water 4
position 4: leftMax 4 <= rightMax 5, water 2
position 5: leftMax 5 <= rightMax 5, water 0
11
```

Each position is settled exactly once, in whatever order the pointers reach it: **O(n) time, O(1) space**.

What to notice:

- **The side with the smaller maximum moves.** That's the side whose water level is already certain. It's the same spirit as container with most water, where the shorter wall moved, but the reason here is different: it's about what each side *knows*, not about discarding pairs.
- **`left <= right`.** Every position holds water, possibly zero, so every position must be visited, including the one where the pointers meet. Each pointer updates its maximum before using it, so the bar under the pointer is always included, and the water is never negative.
- **An empty array** starts with `right = -1`, so the loop never runs and the answer is 0.

<Callout kind="analogy">
Imagine two people walking inwards from the two ends of the landscape, each remembering the tallest bar they've passed. Whoever remembers the **lower** wall knows exactly how high the water stands at their feet: the other person has already seen something at least as tall, so the water can't spill out on that side. That person takes a step. The other waits.
</Callout>

## Three solutions compared

| Approach | Time | Extra space | Idea |
| --- | --- | --- | --- |
| Scan both ways at each bar | O(n²) | O(1) | the definition |
| Prefix and suffix maximums | O(n) | O(n) | precompute both tallest values |
| Two pointers | O(n) | O(1) | only the smaller tallest value matters |
| Monotonic stack (M26) | O(n) | O(n) | fill water layer by layer as bars close each dip |

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting to subtract the bar.** The water above position `i` is the level minus `heights[i]`, not the level itself.
- **Excluding bar `i` from the maximums.** If "tallest on the left" leaves out `heights[i]`, a tall bar can give negative water. Include it, or clamp with `max(0, …)`.
- **Moving the pointer with the bigger maximum.** That side's water level isn't certain yet, because something taller might be waiting between the pointers on the other side.
</Callout>
