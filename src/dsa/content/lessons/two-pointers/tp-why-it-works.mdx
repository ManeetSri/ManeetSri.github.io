## Why it matters

You've now seen two pointers solve pair sum, palindromes, containers, 3Sum, compaction, the Dutch flag, sorted squares and rain water. Memorising each one isn't the goal. The goal is to recognise, in a problem you've never seen, **whether** two pointers can work, and to be able to say **why** your version doesn't skip the answer. This short lesson gives you the picture behind opposite-end pointers, the one-sentence test for any pointer move, and the signs that a problem needs something else.

## All the pairs, as a grid

Take pair sum on the sorted array `[1, 3, 4, 6, 8]` with target 10. The brute force checks every pair `i < j`. Lay those sums out as a grid, with `i` down the side and `j` along the top:

| | 3 | 4 | 6 | 8 |
| --- | --- | --- | --- | --- |
| **1** | 4 | 5 | 7 | 9 |
| **3** | | 7 | 9 | 11 |
| **4** | | | 10 | 12 |
| **6** | | | | 14 |

Because the array is sorted, the grid is sorted too: sums **grow to the right** along a row and **grow downwards** along a column. That's the **monotonic property**: moving in one direction only ever increases (or only ever decreases) the value.

Now watch what two pointers do. `left` picks a row, `right` picks a column, and they start at the **top-right corner**, the pair (1, 8):

1. `1 + 8 = 9`, too small. Everything else in row 1 is to the left, so it's even smaller. **The whole row is eliminated**: `left` moves down.
2. `3 + 8 = 11`, too big. Everything else still in column 8 is below, so it's even bigger. **The whole column is eliminated**: `right` moves left.
3. `3 + 6 = 9`, too small. Row 3 is eliminated.
4. `4 + 6 = 10`. Found.

Each comparison throws away an entire row or column of the grid, not a single pair. The grid has about n²/2 cells, but there are only n rows and columns to throw away, so the search takes at most n steps. That's why two pointers turn O(n²) into O(n).

If this feels familiar, it should: it's the same walk as [Staircase search in a sorted matrix](/dsa/learn/matrix-staircase-search), starting from the corner where one direction goes up and the other goes down.

## Counting with the same picture

The grid view does more than find one pair. **How many pairs add up to less than 10?** When `items[left] + items[right]` is below the target, every pair in that row from `left + 1` up to `right` is smaller still. That's `right − left` pairs, all counted in one step:

```swift run
func pairsBelow(_ sorted: [Int], _ target: Int) -> Int {
    var left = 0
    var right = sorted.count - 1
    var count = 0
    while left < right {
        if sorted[left] + sorted[right] < target {
            count += right - left      // left pairs with every index from left + 1 to right
            left += 1
        } else {
            right -= 1
        }
    }
    return count
}

print(pairsBelow([1, 3, 4, 6, 8], 10))
print(pairsBelow([-2, 0, 1, 5], 3))
```

```output
6
3
```

The six pairs below 10 in the grid are 4, 5, 7, 9, 7 and 9. The algorithm never lists them one by one: it counts row 1's four in a single step, then row 3's two. O(n) to count something there can be O(n²) of.

## The one-sentence test

Every correct pointer move comes with a sentence of this form:

> "When I move this pointer, every candidate I give up is **impossible** or **no better** than one I've already seen."

Here's that sentence for each problem in this module:

| Problem | The move | Why nothing is lost |
| --- | --- | --- |
| Pair sum | sum too small: move `left` | `items[left]` plus the largest remaining value is too small, so it's in no answer |
| Container with most water | move the shorter wall | every other container using it is narrower and no taller |
| 3Sum | fix `nums[i]`, then pair sum | each fixed value reduces to pair sum on the values to its right |
| Read/write | skip an element | it isn't kept, and every kept element is already in front of `write` |
| Dutch flag | swap into a region | each step shrinks the unknown region, and the known regions stay correct |
| Sorted squares | take the larger end square | the largest remaining square is always at one of the ends |
| Trapping rain water | move the smaller maximum | that side's water level is already certain |

If you can't finish the sentence for your move, you don't yet have a proof, and there's probably an input that breaks your code. Container with most water's "move the taller wall" fails exactly this test.

## When two pointers don't apply

The pattern needs that monotonic property: moving a pointer must push the value **predictably** in one direction. Watch for these signs that something's missing:

- **The data isn't sorted and you need original positions.** Pair sum on an unsorted array that asks for indexes can't sort without losing them. A dictionary of values seen so far solves it in O(n), which M24 covers.
- **Negative numbers in a subarray sum.** A window or pointer that shrinks when the sum is too big assumes removing values lowers the sum. Negatives break that, as [Prefix sum + hashmap](/dsa/learn/prefix-hashmap) showed. Use prefix sums and a dictionary.
- **No single direction helps.** If moving either pointer could make things better or worse, the comparison tells you nothing, and you can't eliminate anything.

## The three families

| Family | Pointers start | They move | Typical invariant | Examples |
| --- | --- | --- | --- | --- |
| Opposite ends | first and last index | towards each other | everything outside the pointers is settled | pair sum, palindromes, containers, rain water |
| Same direction | both at the start | `write` trails `read` | `items[0..<write]` is the answer so far | removing values, deduplication, Dutch flag |
| Two sequences | one at the start of each | each through its own sequence | the parts already passed are fully handled | subsequence check, merging sorted arrays |

M22's **sliding window** is the same-direction family with a twist: the two pointers mark the two ends of a window, and what matters is the stretch **between** them.
