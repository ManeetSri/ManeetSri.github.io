## Why it matters

Sorting is O(n log n) in general. But when every element falls into one of only **three** groups, such as low, medium and high priority, or "less than", "equal to" and "greater than" some value, you can sort in **one pass** with O(1) extra space. The algorithm is the **Dutch national flag** partition, named by Edsger Dijkstra after the flag's three horizontal stripes. It uses three pointers, and it's the heart of fast quicksort implementations that cope well with many repeated values, which you'll meet in Part IV.

## The problem

> An array holds only 0s, 1s and 2s. Rearrange it in place so all the 0s come first, then the 1s, then the 2s.

`[2, 0, 2, 1, 1, 0, 1, 2, 0]` becomes `[0, 0, 0, 1, 1, 1, 2, 2, 2]`.

**Counting first** is a fine answer: count each value in one pass, then overwrite the array with that many 0s, 1s and 2s in a second pass. It's O(n). But it only works because one 0 is the same as any other. If the elements were tasks with a priority, rewriting them from counts would lose the tasks. The flag algorithm **moves** the elements themselves, in one pass.

## Four regions

The idea is to grow three sorted regions while a region of unknown elements shrinks. Three pointers mark the boundaries:

| Range | Holds |
| --- | --- |
| `0..<low` | 0s |
| `low..<mid` | 1s |
| `mid...high` | not looked at yet |
| `(high + 1)...` | 2s |

At the start, `low` and `mid` are 0 and `high` is the last index, so everything is unknown. Each step looks at `items[mid]`, the first unknown element, and moves it into the right region:

- **A 0:** swap it with `items[low]`, the first 1 (or `mid` itself if there are no 1s yet). Both regions shift right: `low += 1`, `mid += 1`.
- **A 1:** it's already in the right place. `mid += 1`.
- **A 2:** swap it with `items[high]`, the last unknown element, and shrink the 2s' boundary: `high -= 1`. **Don't move `mid`**: the value that just arrived from `high` hasn't been looked at yet.

When `mid` passes `high`, nothing is unknown, and the array is sorted. Step through it and watch the regions grow:

## The code

```swift run
func sortColours(_ items: inout [Int]) {
    var low = 0
    var mid = 0
    var high = items.count - 1
    while mid <= high {
        if items[mid] == 0 {
            items.swapAt(low, mid)
            low += 1
            mid += 1
        } else if items[mid] == 1 {
            mid += 1
        } else {
            items.swapAt(mid, high)
            high -= 1
        }
    }
}

var a = [2, 0, 2, 1, 1, 0, 1, 2, 0]
sortColours(&a)
print(a)

var b = [2, 2, 0]
sortColours(&b)
print(b)

var c: [Int] = []
sortColours(&c)
print(c)
```

```output
[0, 0, 0, 1, 1, 1, 2, 2, 2]
[0, 2, 2]
[]
```

`swapAt` swaps two positions of an array in place, as you saw in [inout, swap and swapAt](/dsa/learn/swift-inout-swap). Swapping a position with itself is allowed and does nothing, which happens whenever `low == mid`.

## Why mid moves after one swap but not the other

This is the step people get wrong, so it's worth slowing down.

- **Swapping with `low`:** the element that comes back to `mid` is from the 1s region, `low..<mid`, so it's a 1. Or, if that region is empty, `low == mid` and it's the 0 itself, now in place. Either way it's **known**, so `mid` can move on.
- **Swapping with `high`:** the element that comes back is from the unknown region. It could be a 0, 1 or 2. It **must** be examined, so `mid` stays put.

Try `[2, 2, 0]` from the run above with `mid += 1` wrongly added to the 2 branch: the first swap brings the 0 to the front, `mid` skips past it, and the 0 is left stranded behind a 2.

## Why it's O(n)

Every pass of the loop either increases `mid` or decreases `high`. Either way, the unknown region `mid...high` shrinks by one. It starts with n elements, so there are exactly n passes, each O(1). Total: **O(n) time, O(1) space**, one pass.

It's the read/write pattern from [the last lesson](/dsa/learn/tp-read-write), doubled: `low` is a write pointer for 0s working forward from the front, `high` is a write pointer for 2s working backward from the end, and `mid` is the reader between them.

## It's not stable

A sort is **stable** if equal elements keep their original order. The flag algorithm isn't: swapping with `high` can jump an element over others with the same key. With tasks sorted by priority:

```swift run
struct Task {
    let name: String
    let priority: Int    // 0 urgent, 1 normal, 2 later
}

func sortByPriority(_ tasks: inout [Task]) {
    var low = 0
    var mid = 0
    var high = tasks.count - 1
    while mid <= high {
        switch tasks[mid].priority {
        case 0:
            tasks.swapAt(low, mid)
            low += 1
            mid += 1
        case 1:
            mid += 1
        default:
            tasks.swapAt(mid, high)
            high -= 1
        }
    }
}

var tasks = [
    Task(name: "email", priority: 2),
    Task(name: "deploy", priority: 0),
    Task(name: "review", priority: 1),
    Task(name: "backup", priority: 2),
    Task(name: "hotfix", priority: 0),
    Task(name: "lunch", priority: 1),
]
sortByPriority(&tasks)
print(tasks.map { $0.name })
```

```output
["deploy", "hotfix", "review", "lunch", "backup", "email"]
```

The priorities are grouped correctly, but "email" came before "backup" in the input and after it in the output. If the original order matters within each group, use a stable approach instead, such as `sorted(by:)` on the priority, which Swift guarantees to be stable, at O(n log n).

## Beyond 0, 1 and 2

Nothing in the algorithm depends on the values being 0, 1 and 2. It only needs a way to put each element into one of three groups. The most useful version is a **three-way partition around a pivot**: everything less than the pivot, then everything equal to it, then everything greater. Replace the three tests with `items[mid] < pivot`, `items[mid] == pivot` and the rest, and the same pointer moves work unchanged.

When it finishes, `low` and `high` tell you exactly where the "equal" block sits: from `low` through `high`. Quicksort uses that to skip the whole block of equal values instead of sorting it again.

<Callout kind="gotcha" title="Common mistakes">
- **Moving `mid` after swapping with `high`.** The incoming element is unknown and must be checked.
- **`while mid < high`.** The element at `mid == high` is still unknown, so the loop needs `<=`. With `<`, `[1, 0]` comes out unsorted: the 1 is skipped, and the loop stops before the 0 is ever seen.
- **Empty arrays.** `high` starts at `-1`, so `mid <= high` is false straight away, and nothing breaks.
</Callout>

## Practice

**Three-way partition** asks you to partition an array around any pivot value in one pass, and return the range where the pivot's copies end up. It's the generalisation described above, so think carefully about what `low` and `high` hold when the loop stops.
