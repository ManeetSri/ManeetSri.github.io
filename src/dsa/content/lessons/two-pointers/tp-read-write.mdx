## Why it matters

The second pointer pattern has both pointers moving in the **same direction**. A `read` pointer visits every element; a `write` pointer marks where the next element worth keeping should go. Together they filter an array **in place**: no second array, O(1) extra space, one pass. It's how you remove values, compact data, and drop duplicates, and it's the idea inside Swift's own `removeAll(where:)`. You met two examples in [Remove duplicates and move zeroes](/dsa/learn/arrays-dedupe-move-zeroes); this lesson names the pattern, shows why it's correct, and extends it.

## The pattern

```swift
var write = 0
for read in items.indices {
    if shouldKeep(items[read]) {
        items[write] = items[read]
        write += 1
    }
}
// items[0..<write] now holds the kept elements, in their original order
```

The **invariant**, the fact that's true after every pass (from [Loop invariants and correctness](/dsa/learn/algo-invariants)):

> `items[0..<write]` holds exactly the kept elements from `items[0..<read]`, in their original order.

It's true at the start, when both ranges are empty. Each pass keeps it true: a kept element is copied to `write`, and the range grows by one; a dropped element is skipped. When `read` reaches the end, the invariant says the front of the array is the answer.

Why is writing safe? `write` never gets ahead of `read`, so the slot being overwritten has always been read already. You never destroy an element you still need.

## Removing every copy of a value

```swift run
func removeAll(_ value: Int, from items: inout [Int]) -> Int {
    var write = 0
    for read in items.indices {
        if items[read] != value {
            items[write] = items[read]
            write += 1
        }
    }
    return write
}

var items = [3, 1, 3, 2, 3, 4]
let kept = removeAll(3, from: &items)
print(kept, items)
items.removeLast(items.count - kept)
print(items)
```

```output
3 [1, 2, 4, 2, 3, 4]
[1, 2, 4]
```

After the loop, the first 3 slots hold the answer and the rest is leftover junk: the old values that were never overwritten. Many problems only want the count and the front of the array. If you want the array itself trimmed, `removeLast(_:)` drops the tail in O(k) for k elements, without moving anything else.

This uses `inout` from [inout, swap and swapAt](/dsa/learn/swift-inout-swap), so the function changes the caller's array.

## Removing duplicates from a sorted array

In a sorted array, equal values sit together. Keep an element only if it differs from the **last kept** element, `items[write - 1]`:

```visual arrayTrace
program: dedupe
input:
  items: [1, 1, 2, 2, 2, 3, 5, 5]
```

Notice the comparison is with `items[write - 1]`, the last value *kept*, rather than `items[read - 1]`, the last value *read*. For plain deduplication both work, but comparing with what you've kept is the version that generalises. To allow each value **up to twice**, compare with `items[write - 2]`: if the element two slots back in the kept part is the same value, two copies are already kept. That's the problem at the end of this lesson.

## When order doesn't matter: fill holes from the end

If the problem says the remaining elements can be in **any order**, there's an alternative that writes less. Each time you find an element to remove, overwrite it with the **last** element and shrink the array's end. It's an opposite-ends algorithm:

```swift run
func removeUnordered(_ value: Int, from items: inout [Int]) -> Int {
    var left = 0
    var right = items.count            // items[right...] is the discarded tail
    while left < right {
        if items[left] == value {
            right -= 1
            items[left] = items[right] // fill the hole; check this slot again next pass
        } else {
            left += 1
        }
    }
    return right
}

var items = [3, 1, 3, 2, 3, 4]
let kept = removeUnordered(3, from: &items)
print(kept, Array(items[..<kept]))
```

```output
3 [4, 1, 2]
```

Read/write copies every kept element once, even when there's nothing to remove before it. Filling from the end writes once per **removed** element, so when removals are rare, it does far less work. The price is that the order changes. Read the statement to see which you're allowed.

## Two sequences, one pointer each

Same-direction pointers also work across **two** sequences. Is `pattern` a **subsequence** of `text`, meaning its characters appear in `text` in the same order, though not necessarily next to each other?

```swift run
func isSubsequence(_ pattern: String, of text: String) -> Bool {
    let wanted = Array(pattern)
    var next = 0                        // the next character of pattern to find
    for character in text where next < wanted.count && character == wanted[next] {
        next += 1
    }
    return next == wanted.count
}

print(isSubsequence("wit", of: "swift"))
print(isSubsequence("fit", of: "swift"))
print(isSubsequence("", of: "swift"))
```

```output
true
false
true
```

One pointer walks through `text` one character at a time. The other, `next`, only moves when its character turns up. Taking the **earliest** match is always safe: matching a character as soon as possible leaves the most text for the rest of the pattern. It's O(n + m) for the two lengths. Merging two sorted arrays, from [Merge sorted arrays](/dsa/learn/arrays-merge-sorted), is another member of this family.

## Swift's own version

For everyday code, the standard library already does this:

```swift run
var items = [3, 1, 3, 2, 3, 4]
items.removeAll { $0 == 3 }
print(items)
```

```output
[1, 2, 4]
```

`removeAll(where:)` on an array is O(n): one pass that slides the kept elements forward, then a single cut at the end. A naive loop that calls `remove(at:)` for each match is O(n²), because every removal shifts everything after it, as [The cost of inserting and deleting](/dsa/learn/arrays-insert-delete-cost) showed. Knowing the pattern lets you see why one is fast and the other isn't, and lets you write it yourself when the rule for keeping an element depends on what's been kept so far, which `removeAll(where:)` can't express.

<Callout kind="gotcha" title="Common mistakes">
- **Calling `remove(at:)` in a loop.** Each call shifts the rest of the array: O(n²) overall. And if you loop over indexes while removing, the indexes shift under you.
- **Forgetting the tail.** After read/write, `items[write...]` still holds old values. Return `write`, or trim the array, depending on what the problem asks.
- **Starting `write` in the wrong place.** For deduplication, the first element is always kept, so the loop can start with `write = 1` and `read = 1`. For "at most two copies", the first two are always kept.
</Callout>
