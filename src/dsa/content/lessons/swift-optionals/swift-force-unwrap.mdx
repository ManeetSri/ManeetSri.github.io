## Why it matters

Every safe way of unwrapping you've learned makes you deal with the empty box. The `!` operator skips that: it takes the value out and **crashes the program** if there isn't one. Crashes in apps are what users remember, so you need to know exactly when `!` is a reasonable promise and when it's a bug waiting to happen. You'll also see it often in other people's code, competitive programming and quick tests.

## Force unwrapping with !

Put `!` after an optional to get the value out directly. It's called **force unwrapping**:

```swift run
let text = "128"
let number = Int(text)!

print(number + 1)
```

```output
129
```

`Int(text)` is an `Int?`. Adding `!` turns it into a plain `Int`, with no `if let` and no default. It works here because `"128"` really is a number.

The `!` is a promise to the compiler: "I know there's a value here, so don't make me check". Swift takes you at your word.

## When the promise is broken

If the optional is nil, there's nothing to take out, and the program stops immediately:

```swift
let text = "12a"
let number = Int(text)!
print(number + 1)
```

This is what Swift reports when it runs:

```text title="What you'll see"
Fatal error: Unexpectedly found nil while unwrapping an Optional value
```

(The real message starts with the file name and line number, which helps you find the culprit.) The `print` never runs. In an iOS app, this is the app vanishing from the user's screen.

Learn to recognise this message. It's one of the most common crashes in Swift code, and it always means the same thing: a `!` was used on an optional that turned out to be nil.

<Callout kind="gotcha" title="Swift gotcha: three different exclamation marks">
`!` means three unrelated things depending on where it sits. Before a `Bool`, `!isReady` means "not". In `!=`, it's part of "not equal". **After** an optional, `value!` means "force unwrap". Only the last one can crash.
</Callout>

## When force unwrapping is fine

Force unwrapping is reasonable when nil would mean the **program itself** is wrong, not the data it was given. In those cases a crash is honest: it points straight at a bug, during development, instead of letting the program carry on with nonsense.

**Values you wrote yourself.** Text typed directly into your code can't change:

```swift run
let maxPlayers = Int("4")!
let sizes = [3, 9, 2]
let biggest = sizes.max()!

print(maxPlayers, biggest)
```

```output
4 9
```

`"4"` is always a number, and `sizes` is never empty, so neither `!` can fail. In iOS code you'll often see the same idea with web addresses typed into the code, `URL(string: "https://www.apple.com")!`.

**Right after a check that guarantees it.** If you've just made sure an array isn't empty, its `first` can't be nil:

```swift
guard !scores.isEmpty else { return 0 }
let lowest = scores.min()!
```

This is acceptable, but notice that `guard let lowest = scores.min() else { return 0 }` does the same in one line without the `!`. When a check and a `!` sit next to each other, an `if let` or `guard let` is usually cleaner.

**Tests and quick experiments.** In a test, a crash is simply a failed test, which is what you want to know about. In competitive programming, where input is guaranteed to be well-formed, you'll see lines like `Int(readLine()!)!` all the time; M12 covers reading input.

## When force unwrapping is a bug

Never force unwrap a value that depends on the outside world:

- **user input**: anything typed into a text field;
- **files and network responses**: they can be missing, empty or malformed;
- **dictionary lookups** whose keys come from data rather than from your own code;
- **`first`, `last`, `min()` and `max()`** of an array that might be empty.

Each of these can be nil on a perfectly ordinary day. A `!` turns that ordinary day into a crash.

## Choosing the right tool

You now know every way to deal with an optional. Here they are side by side:

| You want to… | Use |
| --- | --- |
| run some code only when there's a value | `if let` |
| stop early when there's no value | `guard let` |
| use a default when there's no value | `??` |
| reach a property or method, if there's a value | `?.` |
| crash, because nil means a bug | `!` |

The table also gives a good order of preference: reach for the tools at the top first, and treat `!` as the last resort it's meant to be.

```swift run
let input = "seven"

// Safe options, each handling the nil case differently
if let n = Int(input) {
    print("if let: \(n)")
} else {
    print("if let: not a number")
}
print("?? gives \(Int(input) ?? 0)")
print("?. gives \(Int(input)?.description ?? "nil")")
```

```output
if let: not a number
?? gives 0
?. gives nil
```

`description` turns a number into text, so `Int(input)?.description` is a `String?`. None of these lines can crash, whatever `input` holds. `Int(input)!` would have crashed on `"seven"`.

## Implicitly unwrapped optionals

You might see types written with `!` instead of `?`, like `String!`. This is an **implicitly unwrapped optional**: an optional that Swift force unwraps automatically every time you use it.

```swift
@IBOutlet var titleLabel: UILabel!
```

They exist mainly for iOS interface code, where a value can't be set when the object is created but is guaranteed to be set before anyone uses it. If it's nil when used, you get the same "Unexpectedly found nil" crash. Recognise them, but don't write them in your own algorithms: use a normal optional or a plain type.
