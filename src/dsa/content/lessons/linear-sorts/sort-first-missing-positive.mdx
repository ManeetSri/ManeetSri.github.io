## Why it matters

"Find the smallest positive whole number that isn't in this array" sounds like a warm-up. The array, though, is unsorted, and may hold zeros, negative numbers, duplicates and numbers in the billions, and the target is O(n) time with O(1) extra memory. That combination rules out every obvious approach, and it's why this is one of the best-known hard interview questions. The trick is cyclic sort from [the last lesson](/dsa/learn/sort-cyclic), plus one observation that shrinks the problem. The same thinking assigns the next free ID, ticket number or table number in an app: the smallest one not already in use.

## The answer is between 1 and n + 1

Take an array of n values. Which positive numbers could possibly be missing first?

- If the array holds exactly 1, 2, …, n, in any order, then n + 1 is the first one missing.
- Otherwise at least one of 1 to n is absent, and the first missing positive is the smallest of those.

Either way the answer is somewhere from **1 to n + 1**. n values can't cover more than n numbers, so the pigeonhole principle guarantees a gap by n + 1 at the latest.

That has a big consequence: **any value below 1 or above n can be ignored**. A −7 or a 1,000,000 in an array of six values can never affect the answer. Only the values from 1 to n matter, and those are exactly the values cyclic sort knows how to put away.

## The obvious approaches, and why they fall short

| Approach | Time | Extra memory | Problem |
| --- | --- | --- | --- |
| Sort, then scan for the first gap | O(n log n) | O(1) to O(n) | too slow |
| Put every value in a `Set`, then try 1, 2, 3, … | O(n) | O(n) | too much memory |
| An array of n + 1 `Bool` flags, one per candidate | O(n) | O(n) | too much memory |
| Cyclic sort, ignoring out-of-range values | O(n) | O(1) | rearranges the array |

The flag array is worth noticing: it's the clearest O(n) solution, and if you're allowed O(n) memory, it's the one to write. Cyclic sort does the same job, but uses the array itself as the flags.

## Cyclic sort, ignoring what doesn't fit

Run cyclic sort, but only send a value home if it's between 1 and n, and its home doesn't already hold it. Everything else (zeros, negatives, huge values, spare copies) stays wherever it ends up. Then scan for the first index i that doesn't hold i + 1:

```swift run
func firstMissingPositive(_ numbers: inout [Int]) -> Int {
    let n = numbers.count
    var i = 0
    while i < n {
        let value = numbers[i]
        if value >= 1 && value <= n && numbers[value - 1] != value {
            numbers.swapAt(i, value - 1)          // send it home
        } else {
            i += 1                                // out of range, a spare copy, or already home
        }
    }
    print("after:", numbers)
    for index in 0..<n where numbers[index] != index + 1 {
        return index + 1
    }
    return n + 1
}

var a = [7, 3, -2, 1, 9, 2]
print(firstMissingPositive(&a))
var b = [2, 1, 3]
print(firstMissingPositive(&b))
var c = [0, -5, 8]
print(firstMissingPositive(&c))
```

```output
after: [1, 2, 3, 7, 9, -2]
4
after: [1, 2, 3]
4
after: [0, -5, 8]
1
```

Walk through the first array. 7 and 9 are above n = 6, so they never move. 3 goes to index 2, 1 to index 0 and 2 to index 1, and the values they displace land wherever there's room. After the loop, indexes 0 to 2 hold 1, 2 and 3, and index 3 holds a 7. So 4 is the first number nobody brought home.

What to notice:

- The range check comes **before** `numbers[value - 1]`. `&&` stops at the first false condition, so an out-of-range value is never used as an index. It also means `value - 1` is never computed for `Int.min`, where it would overflow.
- It's still O(n): every swap puts a value home for good, so there are at most n swaps, plus n moves of i.
- In the second example nothing is missing from 1 to 3, so the scan finds no gap and the answer is n + 1 = 4.

## The sign-marking alternative

There's a second O(n), O(1) approach that doesn't move values at all. It uses the **sign** of each element as a flag: "is the number i + 1 present?" becomes "is `numbers[i]` negative?". It's the flag array from the table, hidden inside the input:

1. Replace every value that can't matter (below 1 or above n) with n + 1, so every value is positive.
2. For each value v from 1 to n, mark index v − 1 by making it negative. Use `abs` when reading, since earlier steps may already have flipped the value you're looking at.
3. The first index that's still positive was never marked, so its number is missing.

```swift run
func firstMissingPositiveByMarking(_ numbers: inout [Int]) -> Int {
    let n = numbers.count
    // 1. Values that can't matter become n + 1, so every value is positive
    for i in 0..<n where numbers[i] < 1 || numbers[i] > n {
        numbers[i] = n + 1
    }
    // 2. Each value v from 1 to n marks index v - 1 by making it negative
    for i in 0..<n {
        let value = abs(numbers[i])
        if value <= n && numbers[value - 1] > 0 {
            numbers[value - 1] = -numbers[value - 1]
        }
    }
    // 3. The first index that's still positive was never marked
    for i in 0..<n where numbers[i] > 0 {
        return i + 1
    }
    return n + 1
}

var a = [7, 3, -2, 1, 9, 2]
print(firstMissingPositiveByMarking(&a), a)
```

```output
4 [-7, -3, -7, 1, 7, 2]
```

After step 1 the array was `[7, 3, 7, 1, 7, 2]`. The 3 marked index 2, the 1 marked index 0 and the 2 marked index 1. Index 3 stayed positive, so 4 is missing. The array is left full of minus signs, so this version rearranges the caller's data too, just differently.

Step 1 matters: without it, an original negative value would look like a mark. It also makes `abs` safe, because no `Int.min` survives step 1.

## Edge cases to test

| Input | Answer | Why |
| --- | --- | --- |
| `[]` | 1 | nothing is present |
| `[1]` | 2 | 1 to n is complete |
| `[2]` | 1 | 1 itself is missing |
| `[1, 1]` | 2 | the spare 1 sits at index 1 |
| `[-3, 0, Int.min]` | 1 | nothing in range |
| `[Int.max, 2, 1]` | 3 | `Int.max` is out of range and ignored |
| `[3, 4, 1, 2]` | 5 | a permutation: answer n + 1 |

Run your solution on all of them. The empty array and `Int.min` catch the most bugs.

## Both versions change the input

Each approach reaches O(1) memory by writing into the array. In Swift, make that visible with an `inout` parameter, as above, so the caller knows. If the caller needs the array unchanged, you have to copy it, which costs O(n) memory, and then the `Bool` flag array is just as good and easier to read. Interviewers often ask exactly this follow-up: "what if you can't modify the input?"

<Callout kind="gotcha" title="Swift gotcha: value - 1 can overflow">
Writing the condition in the other order, `numbers[value - 1] != value && value >= 1 && value <= n`, crashes in two ways. For a value of 0 or less, or above n, `numbers[value - 1]` is out of range. And for `Int.min`, `value - 1` itself overflows, and Swift stops the program before any index is used. Always check the range first; `&&` guarantees the rest is skipped.
</Callout>
