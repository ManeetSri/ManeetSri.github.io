## Why it matters

Counting sort needs a small range of keys. Nine-digit customer IDs, 64-bit timestamps and IP addresses have enormous ranges, but each **digit** of them has a tiny one: ten values in base 10, 256 values per byte. **Radix sort** sorts by one digit at a time, with a stable counting sort for each, and gets O(n) time for fixed-size integers. It's one of the oldest algorithms in computing: punched-card sorting machines in the early 1900s sorted cards one column at a time, exactly like this. Today it's used for large arrays of integers, in graphics code that sorts millions of keys, and in database engines.

## One digit at a time, least significant first

**LSD radix sort** (least significant digit first) makes one pass per digit, starting from the ones digit:

1. Stable-sort all the numbers by their ones digit.
2. Stable-sort the result by the tens digit.
3. Then the hundreds digit, and so on, up to the largest number's highest digit.

Each pass is the stable counting sort from [Counting sort](/dsa/learn/sort-counting), with the digit as the key and k = 10. The digit of `number` at `place` (1, 10, 100, …) is `(number / place) % 10`.

```swift run
func countingPass(_ numbers: [Int], place: Int) -> [Int] {
    var next = [Int](repeating: 0, count: 10)
    for number in numbers {
        next[(number / place) % 10] += 1
    }
    var total = 0                                // counts become starting positions
    for digit in 0..<10 {
        let count = next[digit]
        next[digit] = total
        total += count
    }
    var result = numbers
    for number in numbers {                      // place in input order: stable
        let digit = (number / place) % 10
        result[next[digit]] = number
        next[digit] += 1
    }
    return result
}

func radixSort(_ numbers: [Int]) -> [Int] {
    guard let largest = numbers.max() else { return [] }
    var result = numbers
    var place = 1
    while true {
        result = countingPass(result, place: place)
        print("by the \(place)s digit:", result)
        if place > largest / 10 { break }        // no higher digits left
        place *= 10
    }
    return result
}

let sorted = radixSort([512, 38, 204, 97, 731, 45, 260, 8])
```

```output
by the 1s digit: [260, 731, 512, 204, 45, 97, 38, 8]
by the 10s digit: [204, 8, 512, 731, 38, 45, 260, 97]
by the 100s digit: [8, 38, 45, 97, 204, 260, 512, 731]
```

Look at the second line. 204 and 8 both have a tens digit of 0 (8 is 008), and they're in the order the first pass left them: 204 before 8, because 4 is less than 8. So after two passes the numbers are sorted by their **last two digits**: 04, 08, 12, 31, 38, 45, 60, 97. After three passes, by all three. That's the invariant: after the pass for digit d, the numbers are sorted by their last d digits.

## Why every pass must be stable

The tens pass sees 731 and 38 as equal: both have tens digit 3. The ones pass already put 731 before 38, because 1 is less than 8, and that's correct, since 31 is less than 38. A stable tens pass keeps them in that order. An unstable one might swap them, and the work of the first pass would be lost.

This is the multi-pass idea from [Stable, in-place, adaptive and online](/dsa/learn/sort-properties): sort by the least important key first, then stable-sort by each more important key in turn. Here the "keys" are digits, from least to most significant.

## The cost: O(d · (n + b))

With numbers of up to d digits in base b, there are d passes, and each pass is a counting sort costing O(n + b). So radix sort is **O(d · (n + b))**. For a fixed number of digits and a fixed base, that's O(n).

The base is a trade-off:

| Base | Passes for 64-bit numbers | Counters per pass |
| --- | --- | --- |
| 10 | up to 20 | 10 |
| 256 (one byte) | 8 | 256 |
| 65,536 (two bytes) | 4 | 65,536 |

A bigger base means fewer passes but a bigger counts array to clear and scan each time. Base 256 is a popular middle ground, and it avoids division entirely: a byte is pulled out with a shift and a mask, using the operators from [The bitwise operators](/dsa/learn/bits-operators):

```swift
let byte = (value >> shift) & 0xFF           // shift = 0, 8, 16, …, 56
```

## Negative numbers

`(number / place) % 10` gives negative digits for negative numbers, so the version above only works for values ≥ 0. There are three common fixes:

- **Split them.** Sort the negatives by their absolute value, reverse that, and put it in front of the sorted non-negatives. Watch out: `abs(Int.min)` overflows.
- **Shift by the minimum**, as counting sort does. That fails when `max - min` overflows.
- **Flip the sign bit.** In [two's complement](/dsa/learn/bits-binary-twos-complement), negative numbers have their top bit set, so read as unsigned numbers they look bigger than every positive number. Flipping that one bit swaps the two halves, and the order comes out right for every `Int`:

```swift run
let signBit: UInt = 1 << 63
for value in [Int.min, -1, 0, 1, Int.max] {
    let key = UInt(bitPattern: value) ^ signBit
    print(value, "->", key)
}
```

```output
-9223372036854775808 -> 0
-1 -> 9223372036854775807
0 -> 9223372036854775808
1 -> 9223372036854775809
9223372036854775807 -> 18446744073709551615
```

`UInt(bitPattern:)` reads the same 64 bits as an unsigned number, and `^` flips the top one. The keys increase exactly as the values do, from `Int.min` up to `Int.max`, so you radix-sort the keys and flip the bit back at the end. That's what DSAKit's `radixSorted()` does, in base 256: eight passes for any `Int` values, `Int.min` included, with no special cases.

```swift
import DSAKit

print([170, -45, 75, 0, -802, 24].radixSorted())       // [-802, -45, 0, 24, 75, 170]
```

It also skips any pass where every number has the same byte, which is most of the passes when the numbers are small.

## MSD radix sort for strings

LSD needs every key to have the same number of digits. Numbers can be padded with leading zeros, and fixed-length strings like dates written as `2026-11-27` work directly. But words have different lengths, and "cab" must come before "cabin".

**MSD radix sort** (most significant digit first) goes the other way. Split the words into buckets by their **first** character, then sort each bucket the same way using the second character, and so on. A word that runs out of characters goes before every word that continues, which gives dictionary order:

```swift run
func msdSort(_ words: [[UInt8]], position: Int = 0) -> [[UInt8]] {
    guard words.count > 1 else { return words }
    var finished: [[UInt8]] = []                 // words with no character at this position
    var buckets = [[[UInt8]]](repeating: [], count: 256)
    for word in words {
        if position < word.count {
            buckets[Int(word[position])].append(word)
        } else {
            finished.append(word)
        }
    }
    var result = finished
    for bucket in buckets where !bucket.isEmpty {
        result += msdSort(bucket, position: position + 1)
    }
    return result
}

let words = ["cab", "ca", "bad", "cabin", "a", "bat"]
let sorted = msdSort(words.map { Array($0.utf8) })
print(sorted.map { String(decoding: $0, as: UTF8.self) })
```

```output
["a", "bad", "bat", "ca", "cab", "cabin"]
```

The words are turned into arrays of bytes first (`Array($0.utf8)`, as in [the lesson on fast string access](/dsa/learn/swift-string-to-array)), so each character is a number from 0 to 255. Each level of recursion only looks at the words that share a prefix so far. Real implementations switch to insertion sort for small buckets, because scanning 256 buckets to sort three words is wasteful. Byte order matches alphabetical order for plain lowercase ASCII, but not for capitals or accented letters, which is why real text sorting uses locale-aware comparison instead.

## Radix sort in practice

O(n) sounds like it should always beat O(n log n). In practice:

- It only works on keys made of digits: integers, fixed-length strings, or things you can turn into them.
- It needs O(n) extra memory for each pass's output.
- Each pass reads and writes the whole array, so for small or medium arrays a good comparison sort is often just as fast.

It wins for **large** arrays of integers with a wide range, where counting sort can't go and n log n starts to hurt. For everyday code, `sort()` is still the right default.

<Callout kind="gotcha" title="Swift gotcha: the digit place can overflow">
A natural way to write the loop is `while place <= largest { …; place *= 10 }`. If `largest` is above 10¹⁸, `place` reaches 10¹⁸, the loop body runs, and `place *= 10` tries to make 10¹⁹, which doesn't fit in an `Int`: Swift stops the program. The version above checks `place > largest / 10` **before** multiplying, so it stops one step earlier. Base 256 with shifts avoids the problem completely.
</Callout>
