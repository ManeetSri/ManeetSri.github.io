## Why it matters

The last two lessons kept data safe by never sharing it, or by locking it inside an actor. But values still have to travel: an order handed to an actor, a configuration captured by a child task, a result returned from one. Some values are safe to hand over and some aren't. A struct of numbers can go anywhere; a class instance with a mutable property, shared between two tasks, is a data race waiting to happen. **`Sendable`** is how Swift tells the two apart, at compile time, before your users find out. It's also the heart of what changes when a project moves to Swift 6 language mode.

## What Sendable means

Swift thinks of concurrent code in **isolation domains**: each actor is one, the main actor is one, and code that belongs to no actor, such as a child task's body, runs outside them all. Values that cross from one domain to another, by being passed to an actor, captured by a child task or returned from one, end up reachable from two places that run at the same time.

A type is **`Sendable`** when its values can cross that boundary safely. `Sendable` is a **marker protocol**: it has no methods to implement. Conforming to it is a claim the compiler checks against the type's contents.

## Which types are Sendable

| Kind of type | Sendable? |
| --- | --- |
| `Int`, `Double`, `Bool`, `String` and the other basic value types | yes |
| `Array`, `Dictionary`, `Set` and `Optional` of Sendable elements | yes |
| Your structs and enums whose stored properties are all Sendable | yes, inferred automatically |
| Actors | always: they protect their own state |
| A `final` class whose stored properties are all `let`s of Sendable types | yes, when you declare `: Sendable` |
| A class with a `var` property | no, unless it's protected internally |
| Closures | only those marked `@Sendable`, which can't capture mutable variables |

Value types are the easy case. Passing a struct copies it, so the sender and receiver each have their own, and neither can see the other's changes. That's [Collections are values](/dsa/learn/swift-collections-are-values) paying off again. Swift infers `Sendable` for your structs and enums when every stored property is Sendable. The one exception is a `public` type in a library, which has to say `: Sendable` explicitly, so that adding a property later can't silently break code in other modules.

A class is shared by reference, so it's only safe if nothing about it can change: `final`, so no subclass can add a `var`, and only `let` properties of Sendable types.

```swift run
struct Order {                      // Sendable automatically: every stored property is Sendable
    let id: Int
    var items: [String]
}

final class ShopInfo: Sendable {    // allowed: final, and every property is a let of a Sendable type
    let name: String
    let currency: String

    init(name: String, currency: String) {
        self.name = name
        self.currency = currency
    }
}

actor Kitchen {
    private var received: [Order] = []

    func receive(_ order: Order) {
        received.append(order)
    }

    var itemCount: Int {
        received.reduce(0) { $0 + $1.items.count }
    }
}

let shop = ShopInfo(name: "Corner Café", currency: "GBP")
let kitchen = Kitchen()

var order = Order(id: 1, items: ["tea", "toast"])
await kitchen.receive(order)        // the kitchen stores its own copy
order.items.append("jam")           // changes only this copy

await withTaskGroup(of: Void.self) { group in
    for id in 2...4 {
        group.addTask {
            await kitchen.receive(Order(id: id, items: ["coffee in \(shop.currency)"]))
        }
    }
}
print(shop.name, order.items.count, await kitchen.itemCount)
```

```output
Corner Café 3 5
```

What to notice:

- **`Order` crosses into the actor as a copy.** Appending "jam" afterwards changes only the local `order`, so the kitchen still counts 2 items for it, plus one coffee from each of the three child tasks: 5.
- **`ShopInfo` is a class, shared by reference with every child task**, and that's fine: nothing about it can ever change.
- Neither type needed any concurrency code. Choosing value types and immutable classes is most of the work.

## What Swift says when a type isn't Sendable

Here's a mutable class handed to an actor, then changed afterwards:

```swift
final class Draft {
    var text = ""
}

actor Outbox {
    private var drafts: [Draft] = []

    func add(_ draft: Draft) {
        drafts.append(draft)
    }
}

func send(_ outbox: Outbox) async {
    let draft = Draft()
    await outbox.add(draft)
    draft.text = "edited after sending"     // the actor holds the same object: two domains, one var
}
```

The actor and the caller now share one mutable object, and Swift 6 language mode rejects it:

```text title="What Swift 6 language mode reports"
error: sending 'draft' risks causing data races
note: sending 'draft' to actor-isolated instance method 'add' risks causing data races between
actor-isolated and local nonisolated uses
note: access can happen concurrently
```

Delete the last line of `send`, and the error goes away. Swift 6 tracks whether a non-Sendable value is still used after it's been sent: if the caller never touches `draft` again, handing it over is safe, and the compiler allows it. (This analysis is called **region-based isolation**, and you'll see the keyword `sending` in APIs that rely on it.)

Declaring a conformance the type can't honour is caught too:

```swift
final class Counter: Sendable {
    var count = 0           // error: stored property 'count' of 'Sendable'-conforming class 'Counter' is mutable
}

class Settings: Sendable {  // error: non-final class 'Settings' cannot conform to the 'Sendable' protocol
    let name = "default"
}
```

## @unchecked Sendable: a promise the compiler can't check

Some classes are mutable **and** thread-safe, because every access goes through a lock. The compiler can't see that a lock is used correctly, so it can't verify the conformance. `@unchecked Sendable` tells it: "trust me, I've made this safe myself."

```swift run
import Foundation

/// Thread-safe because every access to `counts` holds the lock. The compiler can't verify that,
/// so the conformance is @unchecked: a promise you make.
final class HitCounter: @unchecked Sendable {
    private let lock = NSLock()
    private var counts: [String: Int] = [:]

    func record(_ page: String) {
        lock.lock()
        defer { lock.unlock() }
        counts[page, default: 0] += 1
    }

    func count(for page: String) -> Int {
        lock.lock()
        defer { lock.unlock() }
        return counts[page, default: 0]
    }
}

let hits = HitCounter()
await withTaskGroup(of: Void.self) { group in
    for visitor in 0..<300 {
        group.addTask {
            hits.record(visitor.isMultiple(of: 3) ? "home" : "search")
        }
    }
}
print(hits.count(for: "home"), hits.count(for: "search"), hits.count(for: "cart"))
```

```output
100 200 0
```

Three hundred tasks record visits at once, and the counts are exact on every run, because each access takes the lock (`NSLock`, from Foundation) and `defer` releases it on every path out of the method.

The word **unchecked** is literal. If you add a method next month that forgets the lock, the compiler stays silent and the race is back. Treat `@unchecked Sendable` as a last resort, keep the class small, and keep every access to the protected state in one place. In Swift 6 there's a better option for exactly this class: wrap the dictionary in a `Mutex`, and the class becomes checked `Sendable` with no `@unchecked` at all. That's in [Mutex and atomics in Swift 6](/dsa/learn/cc-mutex-atomics).

## Swift 5 mode and Swift 6 mode

The companion package says `swiftLanguageModes: [.v5]` in its `Package.swift`, and the `run` blocks run in Swift 5 mode too. The compiler is Swift 6 in both cases; the **language mode** decides how strictly concurrency is checked. Here's how the examples in this module fare:

| Code | Swift 5 mode | Swift 5 mode, complete checking | Swift 6 mode |
| --- | --- | --- | --- |
| A class declared `Sendable` with a `var` | warning | warning | error |
| A `@Sendable` closure that changes a captured `var` | warning | warning | error |
| A non-Sendable value sent to an actor, then used again | nothing | warning | error |
| Child tasks capturing the same mutable class instance | nothing | warning | error |
| A non-Sendable type passed where `Sendable` is required | nothing | warning | error |

In short: **Swift 6 language mode turns data-race safety into a compile-time guarantee.** Code that compiles in Swift 6 mode, without `@unchecked` or other escape hatches, has no data races. Swift 5 mode lets most of these through silently, which is why the package used it while Parts I to VIII were teaching other things.

To change modes:

- **A whole package:** `swiftLanguageModes: [.v6]` in `Package.swift` (it's the default for packages whose tools version is 6.0, unless they say otherwise, as this one does).
- **One target:** `.target(name: "Cache", swiftSettings: [.swiftLanguageMode(.v6)])`.
- **An Xcode project:** the **Swift Language Version** build setting.
- **Warnings first, in Swift 5 mode:** set Xcode's **Strict Concurrency Checking** to Complete, or add `swiftSettings: [.enableUpcomingFeature("StrictConcurrency")]` to a target. That shows every Swift 6 error as a warning, so you can fix them gradually.

Every concurrent problem in this module is written to compile cleanly in both modes, so you can try switching your own copy of the package to Swift 6 and see.

<Callout kind="gotcha" title="Swift gotchas with Sendable">
- **Silence in Swift 5 mode isn't safety.** Turn on complete checking, or Swift 6 mode, before trusting concurrent code.
- **`let` doesn't make a class instance safe.** `let draft = Draft()` means the variable can't point elsewhere, but `draft.text` can still change. Sendability is about the type, not the variable.
- **`@unchecked Sendable` switches the checking off for the whole type**, including methods you add later. Prefer an actor or a `Mutex`.
- **Public types aren't inferred.** In a library, write `public struct Point: Sendable` explicitly.
</Callout>
