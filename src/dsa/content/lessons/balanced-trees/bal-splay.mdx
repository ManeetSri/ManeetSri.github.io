## Why it matters

Every balanced tree so far stores extra information (a height, a colour, a priority) and uses it to stay short. A **splay tree**, invented by Daniel Sleator and Robert Tarjan in 1985, stores nothing extra and has no balance rule at all. Instead, every time you touch a key, it moves that key to the root with a particular pattern of rotations called **splaying**. A single operation can be slow, but any sequence of m operations costs O(m log n) in total: **O(log n) amortised**. And because recently used keys sit near the root, a splay tree adapts to the way it's used, behaving like a cache. When a few keys are looked up far more often than the rest, which is common in real workloads, it can beat every tree that keeps a fixed shape.

## Splaying: three steps

To splay a node x, repeat one of three steps until x is the root. Each step looks at x, its parent p and, if there is one, its grandparent g. A, B, C and D are subtrees.

**Zig: p is the root.** One rotation at p lifts x to the top. This only ever happens as the final step.

```text
      p              x
     / \            / \
    x   C    →     A   p
   / \                / \
  A   B              B   C
```

**Zig-zig: x and p are both left children (or both right children).** Rotate at **g first**, then at p. x rises two levels.

```text
          g                x
         / \              / \
        p   D            A   p
       / \       →          / \
      x   C                B   g
     / \                      / \
    A   B                    C   D
```

**Zig-zag: x is a right child and p a left child (or the mirror).** Rotate at p, then at g: the double rotation you know from AVL trees. x rises two levels and ends up with p and g as its children.

```text
        g                    x
       / \                /     \
      p   D              p       g
     / \        →       / \     / \
    A   x              A   B   C   D
       / \
      B   C
```

All three are made of rotations, so the tree stays a valid BST throughout, as you saw in [Why balance matters, and rotations](/dsa/learn/bal-why-rotations).

Every operation splays:

- **Search** for a key, then splay the node you found. If the key isn't there, splay the **last node visited** instead. Skipping that splay would let someone search for a missing key at the bottom of a long path over and over, at full price every time.
- **Insert** by splaying the nearest key to the root, then making the new key the root, with the old root on one side.
- **Delete** by splaying the key to the root and removing it. That leaves two subtrees, every key on the left smaller than every key on the right. Splay the largest key of the left subtree to its root (it then has no right child) and hang the right subtree there.

## Why zig-zig rotates the grandparent first

The obvious way to move a node to the root is to rotate at its parent, again and again. That's called **move-to-root**, and it's what zig-zig would do if it rotated at p first. It moves x to the root, but it barely helps the rest of the path. Splaying's zig-zig, by rotating at g first, roughly **halves the depth** of every node on the path it walks. That small difference is the whole trick.

The code below builds both kinds of tree from the same input, 1 to 1,000 in order. Inserting each new largest key makes the tree a long chain (insert splays the old largest key, which is already at the root, so nothing rotates). Then it accesses the deepest key, 1:

```swift run
final class Node {
    let key: Int
    var left: Node?
    var right: Node?
    init(_ key: Int) { self.key = key }
}

var rotations = 0

func rotateRight(_ y: Node) -> Node {
    rotations += 1
    let x = y.left!
    y.left = x.right
    x.right = y
    return x
}

func rotateLeft(_ x: Node) -> Node {
    rotations += 1
    let y = x.right!
    x.right = y.left
    y.left = x
    return y
}

// Brings key to the root if it's in the tree; otherwise the last node on its search path.
// Each call handles two levels: a zig-zig or a zig-zag, or a final zig.
func splay(_ root: Node?, _ key: Int) -> Node? {
    guard let root, root.key != key else { return root }
    if key < root.key {
        guard let child = root.left else { return root }           // not found: stop here
        if key < child.key {                                       // zig-zig (left-left)
            child.left = splay(child.left, key)
            let lifted = rotateRight(root)                         // grandparent first…
            return lifted.left == nil ? lifted : rotateRight(lifted)   // …then parent
        } else if key > child.key {                                // zig-zag (left-right)
            child.right = splay(child.right, key)
            if child.right != nil { root.left = rotateLeft(child) }
            return root.left == nil ? root : rotateRight(root)
        }
        return rotateRight(root)                                   // zig: child holds key
    } else {
        guard let child = root.right else { return root }
        if key > child.key {                                       // zig-zig (right-right)
            child.right = splay(child.right, key)
            let lifted = rotateLeft(root)
            return lifted.right == nil ? lifted : rotateLeft(lifted)
        } else if key < child.key {                                // zig-zag (right-left)
            child.left = splay(child.left, key)
            if child.left != nil { root.right = rotateRight(child) }
            return root.right == nil ? root : rotateLeft(root)
        }
        return rotateLeft(root)
    }
}

// The naive alternative: rotate key up one level at a time, always at its parent
func moveToRoot(_ root: Node?, _ key: Int) -> Node? {
    guard let root, root.key != key else { return root }
    if key < root.key {
        guard root.left != nil else { return root }
        root.left = moveToRoot(root.left, key)
        return rotateRight(root)
    } else {
        guard root.right != nil else { return root }
        root.right = moveToRoot(root.right, key)
        return rotateLeft(root)
    }
}

// Insert: splay the nearest key to the root, then put the new key above it
func insert(_ key: Int, into root: Node?) -> Node {
    let node = Node(key)
    guard let top = splay(root, key) else { return node }
    if top.key == key { return top }
    if key < top.key {
        node.left = top.left
        node.right = top
        top.left = nil
    } else {
        node.right = top.right
        node.left = top
        top.right = nil
    }
    return node
}

// The number of levels, with an explicit stack: this tree can be a long chain
func height(_ root: Node?) -> Int {
    var tallest = 0
    var stack: [(Node, Int)] = root.map { [($0, 1)] } ?? []
    while let (node, depth) = stack.popLast() {
        tallest = max(tallest, depth)
        if let left = node.left { stack.append((left, depth + 1)) }
        if let right = node.right { stack.append((right, depth + 1)) }
    }
    return tallest
}

var root: Node? = nil
var naive: Node? = nil
for key in 1...1_000 {
    root = insert(key, into: root)
    naive = insert(key, into: naive)
}
print("after inserting 1...1000 in order: height \(height(root))")
root = splay(root, 1)
naive = moveToRoot(naive, 1)
print("after accessing 1: splay height \(height(root)), move-to-root height \(height(naive))")
root = splay(root, 2)
naive = moveToRoot(naive, 2)
print("after accessing 2: splay height \(height(root)), move-to-root height \(height(naive))")

rotations = 0
for key in 1...1_000 {
    root = splay(root, key)
}
print("splaying 1...1000 in order: \(rotations) rotations")
rotations = 0
for key in 1...1_000 {
    naive = moveToRoot(naive, key)
}
print("moving 1...1000 to the root in order: \(rotations) rotations")
```

```output
after inserting 1...1000 in order: height 1000
after accessing 1: splay height 501, move-to-root height 1000
after accessing 2: splay height 253, move-to-root height 999
splaying 1...1000 in order: 3762 rotations
moving 1...1000 to the root in order: 498503 rotations
```

What to notice:

- Both trees start as a chain 1,000 levels tall: accessing key 1 costs 1,000 steps either way. A splay tree's single operations really can be O(n).
- After that one expensive access, the splay tree is **501** levels tall. The next access, to key 2, leaves it **253** tall. Each long walk halves the tree's height. Move-to-root brings 1 to the top but leaves a chain hanging below it: 1,000, then 999.
- Accessing every key in order costs the splay tree 3,762 rotations in total, under 4 per access. Move-to-root needs 498,503: about n² / 2.
- `splay` is recursive and, on a chain, recurses once for every two levels: 500 calls here. Production splay trees use an iterative **top-down** version instead, which splays while walking down and needs no stack at all.

## Amortised O(log n)

That's the pattern in general: an expensive splay leaves the tree much shorter along the path it walked, paying in advance for later operations. The precise argument uses the potential method from [Accounting and potential methods](/dsa/learn/bigo-amortised-methods). Give each node a **rank**, log2 of the size of its subtree, and let the tree's potential be the sum of all ranks. A chain has a high potential, a bushy tree a low one. Sleator and Tarjan's **access lemma** shows that splaying a node costs at most 3 × (rank of the root − rank of the node) + 1, once you count the change in potential: deep walks are paid for by the potential they release. Since a rank is at most log2 n, every splay costs O(log n) amortised, and any sequence of m operations on a tree of up to n keys costs O((m + n) log n) in total.

As in [Amortised analysis](/dsa/learn/bigo-amortised), "amortised" is a promise about the total, not about each step. A single access can still take O(n).

## A tree that acts like a cache

Splaying does more than keep the average down. Because every access moves a key to the root, the keys you've used recently sit near the top, and the ones you haven't drift down. Several proven properties follow:

- **Working set.** Accessing a key costs about O(log t), where t is the number of distinct keys accessed since the last time this key was used. If your program keeps returning to the same hundred keys out of a million, those accesses cost about log2 100, not log2 1,000,000.
- **Static optimality.** Over a long run, a splay tree is within a constant factor of the best fixed BST for the access frequencies, even though it never knows those frequencies.
- **Sequential access.** Visiting every key in sorted order costs O(n) in total, as the 3,762 rotations above suggest.

That makes splay trees attractive when access is skewed, such as caches and lookup tables where a few keys get most of the traffic. There's also a famous open question, the **dynamic optimality conjecture**, which asks whether splay trees are within a constant factor of the best possible BST algorithm on *every* access sequence. It has been open since 1985.

## The costs

- **Reads write.** Even a lookup restructures the tree, so a splay tree can't be shared by several threads reading at once without locking, and every lookup writes to memory, which is slower than only reading it. In Swift, `contains` has to be a `mutating` method, so you can't call it on a `let` tree, and on a copied value type it triggers a copy-on-write.
- **No worst-case bound.** One operation can take O(n). That's unacceptable for code with hard deadlines, like audio processing or a real-time system.
- **Uniform access gains nothing.** If every key is equally likely, the restructuring is pure overhead, and an AVL or red-black tree is faster.

<Callout kind="gotcha" title="Splay on a miss, too">
Searching for a key that isn't there still walks a path, possibly a long one. If you return `false` without splaying the last node on that path, the amortised analysis no longer holds: the same expensive miss can be repeated forever. Splay the last node visited, whether or not you found the key.
</Callout>

<Callout kind="analogy">
A splay tree is like the pile of papers on a busy desk. Whatever you used last goes back on top. Things you need often are always near the top; things you never touch sink to the bottom. Finding something buried is slow, but you only pay that price once before it's on top again.
</Callout>
