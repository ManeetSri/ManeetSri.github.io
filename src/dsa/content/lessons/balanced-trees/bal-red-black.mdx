## Why it matters

The **red-black tree** is the balanced BST that won in practice. Java's `TreeMap` is documented as a red-black tree, and its `TreeSet` is built on `TreeMap`. The C++ standard only sets the complexity of `std::map` and `std::set`, but the major implementations (GCC's libstdc++, LLVM's libc++ and Microsoft's) all build them as red-black trees. The Linux kernel ships its own red-black tree library, used in places such as its process scheduler and its high-resolution timers. Red-black trees allow a little more lopsidedness than AVL trees, and in exchange they do less restructuring: an insert needs at most two rotations, and a delete at most three. This lesson builds the insert completely, proves the height bound, and outlines the delete.

## The five properties

Every node carries one extra bit: a **colour**, red or black. The tree is a BST, and the colours obey five rules. To keep them short, treat every missing child (`nil`) as a real leaf, called a **nil leaf**.

1. Every node is red or black.
2. The root is black.
3. Every nil leaf is black.
4. A red node's children are both black. In other words, **no two reds in a row** on any path.
5. For each node, every path from it down to a nil leaf passes through the **same number of black nodes**.

Properties 4 and 5 do all the work. Property 5 forces the black nodes to be perfectly balanced. Property 4 limits how many red nodes can be squeezed in between them. Here's a valid red-black tree, with R and B after each value:

```text
               4B
            /      \
          2B        6B
         /  \      /   \
       1B    3B  5B     8R
                       /   \
                     7B     9B
                              \
                              10R
```

Count black nodes from the root down to any nil leaf, not counting the nil: 4, 2, 1 is three; 4, 6, 8, 9 is three (8 is red, so it doesn't count); 4, 6, 8, 9, 10 is still three. Every path has three. The longest path, 4 → 6 → 8 → 9 → 10, has five nodes and the shortest, 4 → 2 → 1, has three. That gap is allowed.

## Why the rules keep the tree short

Define the **black-height** b(x) of a node x as the number of black nodes on any path from x down to a nil leaf, counting x itself if it's black and not counting the nil. Property 5 says every path gives the same count, so this is well defined. In the tree above, b(root) = 3.

**Step 1: a subtree with black-height b has at least 2ᵇ − 1 nodes.** Prove it by induction on the subtree's height. A nil leaf has b = 0 and 0 nodes, and 2⁰ − 1 = 0. For a real node x, each child c has black-height b(x) or b(x) − 1 (one less if x itself is black, since x no longer counts). So each child's subtree has at least 2^(b(x) − 1) − 1 nodes, and with x itself, the total is at least 2 × (2^(b(x) − 1) − 1) + 1 = 2^b(x) − 1.

**Step 2: at least half the nodes on any root-to-leaf path are black.** The root is black (property 2) and no two reds are adjacent (property 4), so the colours along a path go black, then at most one red, then black, and so on. In a tree of height h, the longest path has h nodes, and at least h / 2 of them are black. So b(root) ≥ h / 2.

**Put them together.** The whole tree has n ≥ 2^b(root) − 1 ≥ 2^(h/2) − 1 nodes. Rearranging: 2^(h/2) ≤ n + 1, so h / 2 ≤ log2(n + 1), and

**h ≤ 2 log2(n + 1).**

A red-black tree with a million nodes is at most 39 levels tall. An AVL tree with a million nodes is at most 28. That's the trade:

| | AVL | Red-black |
| --- | --- | --- |
| Height | at most about 1.44 log2 n | at most 2 log2(n + 1) |
| Lookups | slightly faster (shallower) | slightly slower |
| Rotations per insert | at most 2 (one double rotation) | at most 2 |
| Rotations per delete | up to O(log n) | at most 3 |
| Extra per node | a height (or 2-bit balance) | 1 bit of colour |

In practice both are fast, and the difference is small. One reason red-black trees became the library standard is that every update does a small, bounded amount of restructuring: at most three rotations, whatever the tree's size.

## Inserting: start red

Insert the new node exactly as in a plain BST, and colour it **red**. Why red? A red node doesn't change any path's black count, so property 5 stays true. Only two things can break:

- **Property 2**, if the new node is the root. Fix: colour it black.
- **Property 4**, if the new node's parent is also red: a red-red clash.

Everything else in the insert is about fixing that clash. Call the new node N, its parent P, its grandparent G, and P's sibling U, the **uncle**. When P is red, G exists and is black (P is red, so it isn't the root, and the tree was valid before). The fix depends on the uncle's colour. Here are the three cases when P is G's left child. When P is a right child, swap left and right everywhere.

**Case 1: the uncle is red.** Recolour: P and U become black, G becomes red. Every path through G still has the same number of blacks (one black moved down from G into both of its children), and N's clash is gone. But G is now red, and its own parent might be red too. So treat G as the new N and repeat, two levels higher. If G is the root, the final "colour the root black" step finishes it.

```text
         G(B)                      G(R)   ← may clash with its parent: repeat from here
        /    \                    /    \
     P(R)    U(R)       →      P(B)    U(B)
     /                         /
  N(R)                      N(R)
```

**Case 2: the uncle is black, and N is an inner grandchild** (P's right child, while P is G's left child). Rotate left at P. Now P is below N, in the outer position, and you're in case 3 with the roles of N and P swapped.

```text
       G(B)                    G(B)
      /    \                  /    \
   P(R)    U(B)     →      N(R)    U(B)
      \                    /
      N(R)              P(R)
```

**Case 3: the uncle is black, and N is an outer grandchild** (P's left child). Rotate right at G, then swap the colours of P and G. P, now black, is the subtree's root; G, now red, is its right child. The subtree's black count is unchanged, the clash is gone, and its root is black, so nothing above can clash. Done.

```text
          G(B)                    P(B)
         /    \                  /    \
      P(R)    U(B)     →      N(R)    G(R)
      /                                  \
   N(R)                                  U(B)
```

So an insert does some number of case 1 recolourings, each moving the problem two levels up, and then at most one case 2 rotation and one case 3 rotation. **At most two rotations per insert**, and O(log n) recolourings in the worst case, which works out to O(1) on average across many inserts.

If you know the AVL cases, cases 2 and 3 are the left-right and left-left rotations again. What's new is case 1: when the uncle is red, there's room to push the imbalance upward by recolouring, without moving any nodes at all.

## The code

Red-black fix-up walks **up** the tree from the new node, so it's easiest with **parent pointers**. A child holding a strong reference to its parent, while the parent holds strong references to its children, would be a retain cycle, as in [Retain cycles](/dsa/learn/swift-retain-cycles). So the parent link is `weak`. Rotations now have to fix three parent links as well as the child links.

```swift run
enum Colour { case red, black }

final class RBNode {
    let value: Int
    var colour = Colour.red              // every new node starts red
    var left: RBNode?
    var right: RBNode?
    weak var parent: RBNode?             // weak: a child mustn't keep its parent alive (no cycle)

    init(_ value: Int) { self.value = value }
}

func isRed(_ node: RBNode?) -> Bool {
    node?.colour == .red                 // nil leaves count as black
}

struct RedBlackTree {
    var root: RBNode?

    // Lifts x's right child y above x, fixing all three parent links
    mutating func rotateLeft(_ x: RBNode) {
        let y = x.right!
        x.right = y.left
        y.left?.parent = x
        y.parent = x.parent
        if let parent = x.parent {
            if parent.left === x { parent.left = y } else { parent.right = y }
        } else {
            root = y
        }
        y.left = x
        x.parent = y
    }

    mutating func rotateRight(_ y: RBNode) {
        let x = y.left!
        y.left = x.right
        x.right?.parent = y
        x.parent = y.parent
        if let parent = y.parent {
            if parent.left === y { parent.left = x } else { parent.right = x }
        } else {
            root = x
        }
        x.right = y
        y.parent = x
    }

    mutating func insert(_ value: Int) {
        // 1. An ordinary BST insert of a red node
        let node = RBNode(value)
        var parent: RBNode? = nil
        var current = root
        while let here = current {
            parent = here
            if value == here.value { return }            // already there
            current = value < here.value ? here.left : here.right
        }
        node.parent = parent
        if let parent {
            if value < parent.value { parent.left = node } else { parent.right = node }
        } else {
            root = node
        }
        // 2. Fix any red node with a red parent, working up the tree
        fixUp(node)
    }

    mutating func fixUp(_ start: RBNode) {
        var node = start
        while let parent = node.parent, parent.colour == .red {
            let grandparent = parent.parent!             // a red parent is never the root
            if parent === grandparent.left {
                let uncle = grandparent.right
                if isRed(uncle) {
                    // Case 1: red uncle. Recolour and move the problem up two levels.
                    parent.colour = .black
                    uncle!.colour = .black
                    grandparent.colour = .red
                    node = grandparent
                } else {
                    if node === parent.right {
                        // Case 2: black uncle, node is an inner grandchild. Rotate it outward.
                        node = parent
                        rotateLeft(node)
                    }
                    // Case 3: black uncle, node is an outer grandchild. Rotate and recolour.
                    node.parent!.colour = .black
                    grandparent.colour = .red
                    rotateRight(grandparent)
                }
            } else {
                // The mirror image, with left and right swapped
                let uncle = grandparent.left
                if isRed(uncle) {
                    parent.colour = .black
                    uncle!.colour = .black
                    grandparent.colour = .red
                    node = grandparent
                } else {
                    if node === parent.left {
                        node = parent
                        rotateRight(node)
                    }
                    node.parent!.colour = .black
                    grandparent.colour = .red
                    rotateLeft(grandparent)
                }
            }
        }
        root?.colour = .black                            // property 2: the root is black
    }
}

// The black-height of node's subtree if properties 4 and 5 hold there, or nil if not
func blackHeight(_ node: RBNode?) -> Int? {
    guard let node else { return 0 }                     // count black nodes, not the nil leaves
    if isRed(node) && (isRed(node.left) || isRed(node.right)) { return nil }   // red-red
    guard let left = blackHeight(node.left), let right = blackHeight(node.right),
          left == right else { return nil }              // unequal black counts
    return left + (node.colour == .black ? 1 : 0)
}

func height(_ node: RBNode?) -> Int {
    guard let node else { return 0 }
    return 1 + max(height(node.left), height(node.right))
}

// Each level, with R or B after each value
func levels(_ root: RBNode?) -> String {
    var lines: [String] = []
    var level = root.map { [$0] } ?? []
    while !level.isEmpty {
        lines.append(level.map { "\($0.value)\($0.colour == .red ? "R" : "B")" }.joined(separator: " "))
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return lines.joined(separator: " | ")
}

var tree = RedBlackTree()
for value in 1...10 {
    tree.insert(value)
}
print(levels(tree.root))
print("black-height:", blackHeight(tree.root) ?? -1, "height:", height(tree.root))

var big = RedBlackTree()
for value in 1...1_000 {
    big.insert(value)
}
print("1,000 sorted inserts: height", height(big.root), "valid:", blackHeight(big.root) != nil)
```

```output
4B | 2B 6B | 1B 3B 5B 8R | 7B 9B | 10R
black-height: 3 height: 5
1,000 sorted inserts: height 17 valid: true
```

What to notice:

- Inserting 1 to 10 in order gives exactly the tree drawn earlier. Sorted input, a plain BST's worst case, ends 5 levels tall.
- `blackHeight` is a checker in the spirit of the AVL one: it returns `nil` the moment it finds a red-red pair or two paths with different black counts.
- `isRed(nil)` is false. Treating nil leaves as black (property 3) is what lets the code ask "is the uncle red?" without special cases when the uncle doesn't exist.
- A thousand sorted values give height 17. The guarantee is 2 log2(1,001), about 19.9. An AVL tree fed the same values was 10 levels tall: red-black trees really are a little taller.

## Walking through a few inserts

Following the first four inserts shows every case:

1. **Insert 1.** It's the root, so it's coloured black.
2. **Insert 2.** It goes right of 1, red. Its parent is black: nothing to fix.
3. **Insert 3.** Red, right of 2, and 2 is red: a clash. The uncle (1's left) is nil, so black. 3 is an outer grandchild (right of a right child): case 3, mirrored. Rotate left at 1 and swap colours: 2 becomes the black root with red children 1 and 3.
4. **Insert 4.** Red, right of 3, which is red. The uncle, 1, is red: case 1. Recolour 1 and 3 black and 2 red, then move up to 2. It's the root, so the last line colours it black again. The tree is now one black level deeper, with 4 still red.

Every time the root's colour is forced back to black after a case 1, the black-height of the whole tree grows by one. That's the only way it ever grows, which is why every path's black count stays equal.

## Deleting, in outline

Deletion is the hard part of red-black trees, and most courses (and interviews) stop at an outline. Here it is.

1. Delete as in a plain BST. If the node has two children, copy its successor's value in and delete the successor instead, so the node actually removed has at most one child.
2. If the removed node was **red**, nothing breaks: no black count changes, and no red-red pair can appear.
3. If it was **black**, every path through its old position is now one black short. If the child that moved up is red, colour it black and you're done. Otherwise that position carries a "double black" debt, and the fix-up looks at its **sibling** S:
   - **S is red:** rotate at the parent and swap colours, so the new sibling is black. Then use one of the cases below.
   - **S is black with two black children:** colour S red. Now the parent's subtree is balanced but one black short overall, so the debt moves up to the parent. (If the parent is red, colour it black and stop.)
   - **S is black and its far child is red:** rotate at the parent, give S the parent's old colour, and colour the parent and the far child black. The debt is paid. Done.
   - **S is black, its near child is red and its far child black:** rotate at S to swing the red child to the far side, then finish with the previous case.

Each case either finishes with at most a couple of rotations or moves the debt one level up by recolouring alone, so a delete does **at most three rotations** and O(log n) work. The code is about twice the length of the insert, with mirror images throughout, which is why library implementations are written once, tested very hard, and reused.

## Where the colours come from

The rules can feel arbitrary: why red, why black, why exactly these cases? There's a beautiful answer. A red-black tree is a binary encoding of a **2-3-4 tree**, a kind of B-tree whose nodes hold one, two or three keys. A black node together with its red children forms one 2-3-4 node, and the recolouring in case 1 is that node splitting in two. You'll see the correspondence properly in 2-3-4 trees, later in this module, and after that the cases stop looking like magic.

<Callout kind="gotcha" title="Rotations must fix parent links too">
With parent pointers, a rotation changes up to six links, not three: the two child links, the moved subtree's parent, the new top's parent, the old top's parent, and the link from above (or `root`). Missing one leaves a node whose `parent` points at the wrong place, which won't crash until a later fix-up walks up through it. Write a checker that verifies `child.parent === node` for every node while you're testing.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: weak parents and who keeps nodes alive">
`weak var parent` is right, but it means only the downward links keep nodes alive. In `fixUp`, `let grandparent = parent.parent!` is safe because the grandparent is still in the tree and so owned from above. But a node you've unlinked from the tree, held only by a `weak` reference, is gone at once: keep a strong `let` while you work on it.
</Callout>
