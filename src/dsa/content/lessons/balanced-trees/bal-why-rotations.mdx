## Why it matters

A binary search tree promises fast search, insert and delete, but only if it stays bushy. Feed it values in sorted order, which happens all the time (timestamps, auto-incrementing ids, names read from an already sorted file), and it collapses into a chain where every operation is O(n). Every ordered map you'll use, from Java's `TreeMap` to C++'s `std::map` to the B-tree indexes inside the SQLite database under Core Data, is built to stop that collapse. The binary ones rely on one small move, the **rotation**, and this lesson is about why it's needed and how it works.

## Height decides everything

You saw in [Why unbalanced BSTs degrade to O(n)](/dsa/learn/bst-degenerate) that a BST operation walks one path from the root down. Each step visits one node and makes one comparison. So the cost of a search, insert or delete is the number of levels on that path, and in the worst case the tree's **height**: the number of levels from the root down to the deepest node. (As with DSAKit's `TreeNode.height`, a single node has height 1 and the empty tree height 0. Some books count edges instead, which is one less.)

The same n values can make trees of wildly different heights, depending only on the order they arrive in. Here's the plain BST insert from [The BST property, search and insert](/dsa/learn/bst-property-search-insert), written with a loop, fed 1,000 values in three different orders. For each tree, it searches for every value and counts the nodes visited:

```swift run
final class Node {
    let value: Int
    var left: Node?
    var right: Node?
    init(_ value: Int) { self.value = value }
}

// A plain BST insert with a loop, so a very deep tree can't overflow the stack
func insert(_ value: Int, into root: inout Node?) {
    guard var node = root else {
        root = Node(value)
        return
    }
    while true {
        if value < node.value {
            guard let next = node.left else { node.left = Node(value); return }
            node = next
        } else {
            guard let next = node.right else { node.right = Node(value); return }
            node = next
        }
    }
}

// How many nodes a search visits before it finds value
func visits(toFind value: Int, in root: Node?) -> Int {
    var count = 0
    var current = root
    while let node = current {
        count += 1
        if value == node.value { break }
        current = value < node.value ? node.left : node.right
    }
    return count
}

func report(_ label: String, _ order: [Int]) {
    var root: Node? = nil
    for value in order {
        insert(value, into: &root)
    }
    let costs = order.map { visits(toFind: $0, in: root) }
    let average = Double(costs.reduce(0, +)) / Double(costs.count)
    print("\(label): worst search \(costs.max()!), average \(average)")
}

// The middle value first, then the middles of each half, and so on
func middleFirst(_ low: Int, _ high: Int) -> [Int] {
    guard low <= high else { return [] }
    let mid = (low + high) / 2
    return [mid] + middleFirst(low, mid - 1) + middleFirst(mid + 1, high)
}

let n = 1_000
report("sorted      ", Array(0..<n))
report("scrambled   ", (0..<n).map { ($0 * 7_919) % n })
report("middle first", middleFirst(0, n - 1))
```

```output
sorted      : worst search 1000, average 500.5
scrambled   : worst search 26, average 14.86
middle first: worst search 10, average 8.987
```

What to notice:

- **Sorted input** builds a chain: every value goes to the right of the one before. The worst search visits all 1,000 nodes, and the average is half of that. This is a linked list with extra steps.
- **Scrambled input** (multiplying by 7,919 and taking the remainder visits every value once, in a jumbled order) gives a tree 26 levels tall. Random orders usually do this well, but nothing guarantees it.
- **Middle first** builds the best possible tree: 10 levels, because 2¹⁰ = 1,024 is the first power of two above 1,000.

The gap grows with n. For a million values, the chain is a million levels tall and a perfectly bushy tree is 20. That's the difference between O(n) and O(log n) from [Growth classes from O(1) to O(n!)](/dsa/learn/bigo-growth-classes), and it's the whole reason balanced trees exist.

## What "balanced" means

You can't control the order values arrive in. And you can't rebuild a perfect tree after every insert: that would cost O(n) each time. So balanced trees settle for **good enough**: a height that's always O(log n), maintained with a small amount of repair work after each change.

Each kind of balanced tree in this module has its own rule for "good enough":

| Tree | Its balance rule | Height guarantee |
| --- | --- | --- |
| AVL | at every node, the two subtrees' heights differ by at most 1 | about 1.44 log2 n |
| Red-black | no path from the root is more than twice as long as another | at most 2 log2(n + 1) |
| B-tree | nodes hold many keys; every leaf is at the same depth | about log base m of n, for m children per node |
| Treap | random priorities make the shape a random BST | O(log n) expected |
| Splay | no rule at all: recently used keys move to the root | O(log n) amortised per operation |

AVL, red-black and splay trees are binary search trees that stay short by **rotating**. (Treaps can rotate too, though the version in this module uses two other operations, split and merge.) B-trees take a different route, with wide nodes, which you'll see later in the module.

## Rotations

A **rotation** rearranges a parent and one of its children so the child moves up a level and the parent moves down, while the tree stays a valid BST. Here's a **right rotation** at node y, whose left child is x. A, B and C stand for whole subtrees, possibly empty:

```text
        y                    x
       / \                  / \
      x   C      →         A   y
     / \                      / \
    A   B                    B   C
```

Read both trees in inorder (left subtree, node, right subtree, as in [Preorder, inorder and postorder](/dsa/learn/trav-dfs-recursive)) and you get the same sequence: A, x, B, y, C. That's the key fact. **A rotation never changes the inorder order**, so a valid BST stays valid. Check B in particular: every key in B is bigger than x (it was in x's right subtree) and smaller than y (it was in y's left subtree). After the rotation it sits to the right of x and to the left of y, exactly where those facts say it belongs.

A **left rotation** is the mirror image, and undoes a right rotation:

```text
      x                        y
     / \                      / \
    A   y        →           x   C
       / \                  / \
      B   C                A   B
```

Three things change in a rotation, and nothing else:

1. The child (x) moves up and becomes the root of this subtree.
2. The parent (y) moves down to become the child's child.
3. The middle subtree (B) moves across, from the child to the parent.

Everything in A moves up one level, everything in C moves down one level, and B stays at the same depth. So when A is the tall subtree, a right rotation makes the whole subtree shorter. That's how rotations fix balance.

<Callout kind="analogy">
Picture a mobile hanging from the ceiling, with x and y as two hooks. A rotation lifts x up to the ceiling and lets y hang from it instead. The ornaments keep their left-to-right order; only the hook that the middle ornament (B) hangs from changes.
</Callout>

## Rotations in Swift

With class nodes, a rotation is three pointer changes. The function returns the new root of the subtree, because whoever pointed at y must now point at x:

```swift run
final class Node {
    let value: Int
    var left: Node?
    var right: Node?
    init(_ value: Int, _ left: Node? = nil, _ right: Node? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

// Lifts y's left child x above y, and returns x: the new root of this subtree
func rotateRight(_ y: Node) -> Node {
    let x = y.left!
    y.left = x.right        // B moves across from x to y
    x.right = y             // y goes down to x's right
    return x
}

// The mirror image: lifts x's right child y above x, and returns y
func rotateLeft(_ x: Node) -> Node {
    let y = x.right!
    x.right = y.left
    y.left = x
    return y
}

func inorder(_ node: Node?) -> [Int] {
    guard let node else { return [] }
    return inorder(node.left) + [node.value] + inorder(node.right)
}

// The values level by level, top first
func levels(_ root: Node) -> [[Int]] {
    var result: [[Int]] = []
    var level = [root]
    while !level.isEmpty {
        result.append(level.map { $0.value })
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return result
}

// y = 40 with left child x = 20. A = 10, B = 30 and C = 50.
let tree = Node(40, Node(20, Node(10), Node(30)), Node(50))
print("before:", levels(tree), inorder(tree))
let rotated = rotateRight(tree)
print("right: ", levels(rotated), inorder(rotated))
let back = rotateLeft(rotated)
print("left:  ", levels(back), inorder(back))
```

```output
before: [[40], [20, 50], [10, 30]] [10, 20, 30, 40, 50]
right:  [[20], [10, 40], [30, 50]] [10, 20, 30, 40, 50]
left:   [[40], [20, 50], [10, 30]] [10, 20, 30, 40, 50]
```

What to notice:

- The level-by-level shape changes, but the inorder list is identical every time.
- 30 (subtree B) moved from 20's right to 40's left.
- A rotation touches a fixed number of pointers whatever the tree's size, so it's **O(1)**.
- The left rotation exactly undid the right rotation.

## Fixing a chain: one rotation or two

The smallest lopsided tree is three nodes in a chain. There are two shapes, and they need different fixes.

A **straight** chain (30, its left child 20, and 20's left child 10) is fixed by one right rotation at the top. A **bent** chain (30, its left child 10, and 10's *right* child 20) isn't: rotating right at 30 only bends it the other way. The fix is to straighten the bend first, with a left rotation at 10, and then rotate right at 30:

```text
   30              30              20
   /               /              /  \
  10      →      20       →     10    30
    \            /
    20         10
 (bent)     (rotate 10 left)  (rotate 30 right)
```

```swift run
final class Node {
    let value: Int
    var left: Node?
    var right: Node?
    init(_ value: Int, _ left: Node? = nil, _ right: Node? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func rotateRight(_ y: Node) -> Node {
    let x = y.left!
    y.left = x.right
    x.right = y
    return x
}

func rotateLeft(_ x: Node) -> Node {
    let y = x.right!
    x.right = y.left
    y.left = x
    return y
}

func levels(_ root: Node) -> [[Int]] {
    var result: [[Int]] = []
    var level = [root]
    while !level.isEmpty {
        result.append(level.map { $0.value })
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return result
}

// A straight chain: 30, then 20 on its left, then 10 on the left of that
let straight = Node(30, Node(20, Node(10)))
print("straight:", levels(straight), "→", levels(rotateRight(straight)))

// A bent chain: 30, then 10 on its left, then 20 on the right of 10
let bent = Node(30, Node(10, nil, Node(20)))
print("bent, one rotation: ", levels(rotateRight(bent)))

let bentAgain = Node(30, Node(10, nil, Node(20)))
bentAgain.left = rotateLeft(bentAgain.left!)      // straighten the bend first
print("bent, two rotations:", levels(rotateRight(bentAgain)))
```

```output
straight: [[30], [20], [10]] → [[20], [10, 30]]
bent, one rotation:  [[10], [30], [20]]
bent, two rotations: [[20], [10, 30]]
```

Those two patterns, a **single rotation** for a straight line and a **double rotation** for a bend, plus their mirror images, are all the repairs an AVL tree ever needs. You'll name them left-left, right-right, left-right and right-left in the next lesson. Watch them work as an AVL tree takes the values 1 to 7 in sorted order, the input that built a chain above. The number beside each node is its balance factor, which the next lesson defines; for now, read "2" or "−2" as "too lopsided here":

```visual avl
values: [1, 2, 3, 4, 5, 6, 7]
```

Seven sorted inserts end in a perfect tree of height 3, not a chain of height 7.

<Callout kind="gotcha" title="Re-attach the subtree you rotated">
`rotateRight(y)` returns a new subtree root, but the node above y still points at y. You must store the result where y was: `parent.left = rotateRight(parent.left!)`, or `root = rotateRight(root)` at the top. Forget, and the parent keeps pointing at y, which is now x's child: x and the whole subtree A are silently cut off. The recursive style in the next lesson (`node.left = insert(…)`, returning each subtree's root) makes this hard to get wrong.
</Callout>

<Callout kind="gotcha" title="Save the child before you change any pointers">
In `rotateRight`, the first line, `let x = y.left!`, matters. If you wrote `y.left = y.left!.right` first, you'd lose your only reference to x. With class nodes, nothing else may be holding it, and ARC would free it on the spot.
</Callout>
