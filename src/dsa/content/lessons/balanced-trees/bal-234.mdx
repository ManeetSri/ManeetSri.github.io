## Why it matters

A **2-3-4 tree** is the smallest interesting B-tree: every node holds one, two or three keys. You'd rarely use one directly, but it's the key that unlocks red-black trees. Every red-black tree is a 2-3-4 tree written down with binary nodes, and once you see the correspondence, the red-black rules and fix-up cases stop being a list to memorise and become obvious consequences. It also leads to the shortest balanced-tree code there is, the left-leaning red-black tree, which this lesson ends with.

## Three kinds of node

A 2-3-4 tree is a search tree with three node types, named by how many children they have:

- a **2-node** holds 1 key and has 2 children;
- a **3-node** holds 2 keys and has 3 children;
- a **4-node** holds 3 keys and has 4 children.

Keys in a node are sorted, and they separate the children, as in any B-tree from the last lesson: in a 3-node [a b], the left child holds keys below a, the middle child keys between a and b, and the right child keys above b. And, the balance rule, **every leaf is at the same depth**. A 2-3-4 tree is exactly a B-tree whose nodes hold at most 3 keys.

```text
                [ 20 | 40 ]
             /       |       \
   [ 5 | 10 | 15 ]  [ 25 | 30 ]  [ 50 | 60 | 70 ]
```

Every node is at least a 2-node, and all leaves are at depth 2, so a tree of height h holds at least 2ʰ − 1 keys (all 2-nodes) and at most 4ʰ − 1 (all 4-nodes). The height is between log4(n + 1) and log2(n + 1): perfectly balanced, every time.

## Inserting: split on the way down

As in any B-tree, a new key goes into a leaf, and an overfull node splits, sending its middle key up. The last lesson split on the way back **up**, which can cascade. A 2-3-4 tree is usually taught with a neat alternative: split on the way **down**.

While walking down to the leaf, **split every 4-node you meet** before stepping into it. Its middle key moves up into the parent, and its other two keys become two 2-nodes. This is always possible, because the parent can't be a 4-node: if it had been, you'd have split it a step earlier. If the root is a 4-node, split it first, making a new root above it. That's the only way the tree gets taller.

By the time you reach the leaf, it isn't a 4-node either, so it has room for the new key. A single pass down, no going back up.

```text
  Insert 25 into this tree. The child on 25's path, [10 20 30], is a 4-node, so split it first:

        [ 40 ]                       [ 20 | 40 ]                     [ 20 | 40 ]
        /    \                      /     |     \                   /     |     \
 [10 20 30]  [50]      →        [10]    [30]    [50]      →     [10]  [25 30]   [50]
                                 (20 moves up into the root)     (25 goes into the leaf)
```

## The correspondence with red-black trees

Now the important part. Write each 2-3-4 node as a little cluster of binary nodes: one **black** node on top, with its other keys as **red** children.

```text
  2-node             3-node                     4-node

   [ b ]             [ a | b ]                 [ a | b | c ]
                                                     
    bB                  bB                          bB
                       /                           /  \
                     aR                          aR    cR
```

A 3-node can lean either way (black a with a red right child b works equally well), so one 2-3-4 tree can have several red-black encodings. The children of the 2-3-4 node hang below the cluster in their usual left-to-right order.

Check the red-black properties against this picture:

| Red-black property | What it says in 2-3-4 terms |
| --- | --- |
| The root is black | every cluster has a black top |
| No red node has a red child | reds only appear inside a cluster, and a red's children are the tops of other clusters, which are black |
| Every path down has the same number of black nodes | each 2-3-4 node contributes exactly one black node to a path, and every leaf is at the same depth |

So a valid 2-3-4 tree always turns into a valid red-black tree, and every red-black tree can be read as a 2-3-4 tree by gluing each red node to its black parent. The **black-height** is the 2-3-4 tree's height.

That also gives a second, cleaner proof of the red-black height bound. The 2-3-4 tree is at most log2(n + 1) levels tall, and each of its levels becomes at most two binary levels (a black node and a red child). So the red-black tree is at most **2 log2(n + 1)** tall.

## The fix-up cases, explained

With the correspondence in mind, look again at red-black insertion. A new key is a red node: a key joining an existing cluster, the binary version of adding a key to a 2-3-4 node.

- **Joining a 2-node** (black parent): the cluster becomes a 3-node. Nothing to fix.
- **Joining a 3-node** (red parent, with a black or missing uncle): the cluster becomes a 4-node, but drawn crooked, two reds in a row. Cases 2 and 3, the rotations, redraw it in the standard shape: black middle key on top, red keys either side. One cluster, rearranged.
- **Joining a 4-node** (red parent **and** red uncle: the cluster already has two red children): the cluster would hold four keys, too many. Case 1, the recolouring, is a **split**: the black top turns red (the middle key moving up to join its parent's cluster) and its two red children turn black (becoming separate 2-nodes). If that pushes the parent's cluster over too, the fix continues upward, exactly as a split can cascade in a B-tree.

So case 1 is a 4-node splitting, and cases 2 and 3 are a 3-node growing into a 4-node. The textbook red-black insert splits on the way back up, like the B-tree code in the last lesson; the 2-3-4 code below splits on the way down. Both give valid trees.

This program builds a 2-3-4 tree with top-down splits, converts it to a red-black tree cluster by cluster, and checks the red-black properties:

```swift run
// A 2-3-4 tree: every node holds 1, 2 or 3 keys, and every leaf is at the same depth
final class Node234 {
    var keys: [Int]
    var children: [Node234]             // empty for a leaf; otherwise keys.count + 1 of them
    init(_ keys: [Int], _ children: [Node234] = []) {
        self.keys = keys
        self.children = children
    }
}

// Splits the full child at children[i] of parent: its middle key moves up into parent
func splitChild(_ parent: Node234, _ i: Int) {
    let full = parent.children[i]
    let left = Node234([full.keys[0]], Array(full.children.prefix(2)))
    let right = Node234([full.keys[2]], Array(full.children.dropFirst(2)))
    parent.keys.insert(full.keys[1], at: i)
    parent.children[i] = left
    parent.children.insert(right, at: i + 1)
}

// Top-down insertion: split every 4-node on the way down, so the leaf always has room
func insert(_ key: Int, into root: Node234?) -> Node234 {
    guard var root else { return Node234([key]) }
    if root.keys.count == 3 {                       // a full root splits: the tree grows at the top
        let newRoot = Node234([], [root])
        splitChild(newRoot, 0)
        root = newRoot
    }
    var node = root
    while true {
        var i = 0
        while i < node.keys.count && node.keys[i] < key { i += 1 }
        if i < node.keys.count && node.keys[i] == key { return root }   // already there
        if node.children.isEmpty {
            node.keys.insert(key, at: i)            // a leaf with room, guaranteed
            return root
        }
        if node.children[i].keys.count == 3 {      // full child: split it before stepping down
            splitChild(node, i)                     // its middle key is now node.keys[i]
            if key == node.keys[i] { return root }
            if key > node.keys[i] { i += 1 }       // carry on into the correct half
        }
        node = node.children[i]
    }
}

// The same tree as a red-black tree: each 2-3-4 node becomes a black node with 0, 1 or 2 red children
final class RBNode {
    let value: Int
    let isRed: Bool
    var left: RBNode?
    var right: RBNode?
    init(_ value: Int, red: Bool, _ left: RBNode?, _ right: RBNode?) {
        self.value = value
        self.isRed = red
        self.left = left
        self.right = right
    }
}

func redBlack(_ node: Node234?) -> RBNode? {
    guard let node else { return nil }
    let kids = node.children.map { redBlack($0) }
    let child = { (i: Int) in i < kids.count ? kids[i] : nil }
    switch node.keys.count {
    case 1:                                         // 2-node: one black node
        return RBNode(node.keys[0], red: false, child(0), child(1))
    case 2:                                         // 3-node: black, with a red left child
        let red = RBNode(node.keys[0], red: true, child(0), child(1))
        return RBNode(node.keys[1], red: false, red, child(2))
    default:                                        // 4-node: black, with two red children
        let left = RBNode(node.keys[0], red: true, child(0), child(1))
        let right = RBNode(node.keys[2], red: true, child(2), child(3))
        return RBNode(node.keys[1], red: false, left, right)
    }
}

// Black nodes from here down to a nil, if properties 4 and 5 hold; nil if they don't
func blackHeight(_ node: RBNode?) -> Int? {
    guard let node else { return 0 }
    if node.isRed && (node.left?.isRed == true || node.right?.isRed == true) { return nil }
    guard let left = blackHeight(node.left), let right = blackHeight(node.right), left == right else { return nil }
    return left + (node.isRed ? 0 : 1)
}

func levels234(_ root: Node234) -> String {
    var lines: [String] = []
    var level = [root]
    while !level.isEmpty {
        lines.append(level.map { "[" + $0.keys.map(String.init).joined(separator: " ") + "]" }.joined(separator: " "))
        level = level.flatMap { $0.children }
    }
    return lines.joined(separator: " / ")
}

func levelsRB(_ root: RBNode?) -> String {
    var lines: [String] = []
    var level = root.map { [$0] } ?? []
    while !level.isEmpty {
        lines.append(level.map { "\($0.value)\($0.isRed ? "R" : "B")" }.joined(separator: " "))
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return lines.joined(separator: " / ")
}

var tree: Node234? = nil
for key in [10, 20, 30, 40, 50, 60, 70, 5, 15, 25] {
    tree = insert(key, into: tree)
}
print("2-3-4:    ", levels234(tree!))
let rb = redBlack(tree)
print("red-black:", levelsRB(rb))

var depth = 0                                       // every leaf of a 2-3-4 tree is at this depth
var node = tree
while let current = node {
    depth += 1
    node = current.children.first
}
print("2-3-4 height \(depth), black-height \(blackHeight(rb) ?? -1)")
```

```output
2-3-4:     [20 40] / [5 10 15] [25 30] [50 60 70]
red-black: 40B / 20R 60B / 10B 30B 50R 70R / 5R 15R 25R
2-3-4 height 2, black-height 2
```

What to notice:

- The 3-node [20 40] became black 40 with red 20 on its left; 20's own children are the black tops of the clusters below.
- Each 4-node, [5 10 15] and [50 60 70], became a black middle key with two red children.
- The red-black tree is 4 levels tall, but every path from the root down passes exactly 2 black nodes: the 2-3-4 tree's height.

## Left-leaning red-black trees

In 2008 Robert Sedgewick noticed that if you restrict the encoding (a 3-node's red key **always** on the left, and 4-nodes split straight away, so they never last), a red-black tree corresponds one-to-one with a **2-3 tree**, and the insert shrinks to three rules applied on the way back up:

1. If the right child is red and the left isn't, **rotate left** (make it lean left).
2. If the left child and its left child are both red, **rotate right** (a crooked 4-node).
3. If both children are red, **flip the colours** (split the 4-node).

```swift run
// A left-leaning red-black tree: a 2-3 tree in binary form, where a red link joins
// the two keys of a 3-node and always leans left
final class LLRBNode {
    let key: Int
    var left: LLRBNode?
    var right: LLRBNode?
    var isRed = true                     // the link from the parent to this node is red

    init(_ key: Int) { self.key = key }
}

func isRed(_ node: LLRBNode?) -> Bool { node?.isRed ?? false }

func rotateLeft(_ h: LLRBNode) -> LLRBNode {
    let x = h.right!
    h.right = x.left
    x.left = h
    x.isRed = h.isRed
    h.isRed = true
    return x
}

func rotateRight(_ h: LLRBNode) -> LLRBNode {
    let x = h.left!
    h.left = x.right
    x.right = h
    x.isRed = h.isRed
    h.isRed = true
    return x
}

func flipColours(_ h: LLRBNode) {        // split a temporary 4-node: its middle key moves up
    h.isRed = true
    h.left!.isRed = false
    h.right!.isRed = false
}

func insert(_ key: Int, into h: LLRBNode?) -> LLRBNode {
    guard let h else { return LLRBNode(key) }
    if key < h.key {
        h.left = insert(key, into: h.left)
    } else if key > h.key {
        h.right = insert(key, into: h.right)
    }
    var node = h
    if isRed(node.right) && !isRed(node.left) { node = rotateLeft(node) }        // lean left
    if isRed(node.left) && isRed(node.left?.left) { node = rotateRight(node) }   // two reds in a row
    if isRed(node.left) && isRed(node.right) { flipColours(node) }               // a 4-node: split it
    return node
}

func height(_ node: LLRBNode?) -> Int {
    guard let node else { return 0 }
    return 1 + max(height(node.left), height(node.right))
}

// Black links from here down to a nil, if no red link leans right, no two reds are in a row and
// every path has the same number of black links; nil otherwise
func blackHeight(_ node: LLRBNode?) -> Int? {
    guard let node else { return 0 }
    if isRed(node.right) || (node.isRed && isRed(node.left)) { return nil }
    guard let left = blackHeight(node.left), let right = blackHeight(node.right), left == right else { return nil }
    return left + (node.isRed ? 0 : 1)
}

var root: LLRBNode? = nil
for key in 1...1_000 {
    root = insert(key, into: root)
    root!.isRed = false                  // the root is always black
}
print("1,000 sorted inserts: height \(height(root)), black-height \(blackHeight(root) ?? -1)")

var scrambled: LLRBNode? = nil
for i in 0..<1_000 {
    scrambled = insert((i * 7_919) % 1_000, into: scrambled)
    scrambled!.isRed = false
}
print("1,000 scrambled inserts: height \(height(scrambled)), black-height \(blackHeight(scrambled) ?? -1)")
```

```output
1,000 sorted inserts: height 10, black-height 9
1,000 scrambled inserts: height 12, black-height 8
```

The whole insert is a dozen lines, with no parent pointers and no mirror cases. It's a lovely piece of code to know. Its delete is still fiddly, though, and libraries that need speed use the classic version, which does fewer rotations.

<Callout kind="gotcha" title="One 2-3-4 tree, several red-black trees">
Because a 3-node can lean either way, the same set of keys can form different valid red-black trees. Don't compare two implementations by their exact shapes; compare their contents and check each one's properties separately.
</Callout>

<Callout kind="gotcha" title="Recolouring the root">
In the left-leaning version, a colour flip at the root turns it red. The line `root!.isRed = false` after every insert puts it back. Forget it and the tree is still searchable, but its colours stop meaning anything and later inserts can go wrong.
</Callout>
