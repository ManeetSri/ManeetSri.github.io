## Why it matters

A calendar app warns you when a new event clashes with one you already have. An office booking system needs to know how many rooms a day's meetings will take. The same question in other clothes: how many gates does an airport need for a day of flights, how many servers for a log of jobs, how many ambulances for a night of call-outs? These are the two **meeting rooms** problems. The first is a warm-up for sorting. The second introduces the idea of sweeping through time, counting as you go, which the rest of this module builds on.

## Half-open, all the way through

Every meeting in this lesson is **half-open**, `[start, end)`. A meeting from 9 to 10 is over at 10:00, so a meeting from 10 to 11 can use the same room, and one person can attend both. Two meetings clash when `a[0] < b[1] && b[0] < a[1]`, the half-open test from [Merge and insert intervals](/dsa/learn/iv-merge-insert).

## Meeting rooms I: can one person attend everything?

Given a list of meetings, can one person attend all of them? Checking every pair works, but costs O(n²). Instead, sort by start and compare **neighbours** only: there's a clash exactly when some meeting starts before the previous one ends.

```swift run
func canAttendAll(_ meetings: [[Int]]) -> Bool {
    let sorted = meetings.sorted { $0[0] < $1[0] }
    for i in sorted.indices.dropFirst() {
        if sorted[i][0] < sorted[i - 1][1] {          // starts before the previous one ends
            print("clash:", sorted[i - 1], sorted[i])
            return false
        }
    }
    return true
}

print(canAttendAll([[9, 10], [13, 14], [10, 12]]))
print(canAttendAll([[9, 10], [13, 15], [10, 12], [14, 16]]))
```

```output
true
clash: [13, 15] [14, 16]
false
```

Why are neighbours enough? Suppose every neighbouring pair is fine. Then each meeting ends at or before the next one starts, and that one ends after it starts, and so on down the list. Chaining those together, each meeting ends before **every** later meeting starts, so no pair clashes. And if some pair does clash, then some neighbouring pair must, or the chain would hold.

That's O(n log n) for the sort and O(n) for the check.

<Callout kind="gotcha" title="Swift gotcha: 1..<count on an empty array">
`for i in 1..<sorted.count` looks like the natural loop, but when `sorted` is empty it builds the range `1..<0`, and Swift stops with `Range requires lowerBound <= upperBound`. `sorted.indices.dropFirst()` is empty for an empty array, so it's safe without a special case.
</Callout>

## Meeting rooms II: how many rooms?

Now the meetings are fixed and you have to house them all. What's the fewest rooms that will do?

The answer is the **largest number of meetings happening at the same moment**. At that moment, each of those meetings needs its own room, so you can't use fewer. And that many is always enough: go through the meetings in order of start, and give each one any room that's free when it starts. A room is only ever missing if more meetings than that were running at once, which never happens.

So the question becomes: what's the peak number of meetings in progress? Here are two ways to find it, both O(n log n).

## Approach 1: sorted starts and sorted ends

To count meetings in progress, you don't need to know **which** meeting is which. You only need to know when meetings start and when they end. So split the meetings into two separately sorted arrays, `starts` and `ends`, and walk the starts in order. Before counting each new start, first release every meeting that has already ended, using a second pointer into `ends`:

```swift run
func minRooms(_ meetings: [[Int]]) -> Int {
    let starts = meetings.map { $0[0] }.sorted()
    let ends = meetings.map { $0[1] }.sorted()
    var rooms = 0
    var most = 0
    var e = 0                                         // the next end to process
    for start in starts {
        while e < ends.count && ends[e] <= start {    // half-open: ending at `start` frees a room
            rooms -= 1
            e += 1
        }
        rooms += 1
        most = max(most, rooms)
        print("start \(start): \(rooms) in use")
    }
    return most
}

print(minRooms([[0, 30], [5, 10], [15, 20], [10, 15], [25, 35], [8, 12]]))
```

```output
start 0: 1 in use
start 5: 2 in use
start 8: 3 in use
start 10: 3 in use
start 15: 2 in use
start 25: 2 in use
3
```

Look at the start at 10. The meeting `[5, 10)` ends exactly then, so its room is released first, and the new meeting takes it: still 3 in use, not 4. That's the `<=` in `ends[e] <= start`, and it's where half-open intervals show up in the code. At 15, two meetings end before the new one starts.

The end that's released might not belong to the meeting that started first. That doesn't matter: a room is a room. Each pointer only moves forwards, so after the two sorts, the walk is O(n). It's the two-pointer idea from [Merge sorted arrays](/dsa/learn/arrays-merge-sorted), merging two sorted streams of times.

## Approach 2: a sweep of +1 and −1 events

Here's the same count, said differently. Every meeting creates two **events**: at its start, one more room is in use (+1); at its end, one room is freed (−1). Sort all the events by time and add them up as you go. The running total is the number of rooms in use, and its peak is the answer:

```swift run
func minRooms(_ meetings: [[Int]]) -> Int {
    var events: [(time: Int, change: Int)] = []
    for meeting in meetings {
        events.append((meeting[0], 1))      // a meeting starts: one more room in use
        events.append((meeting[1], -1))     // a meeting ends: one room freed
    }
    // By time; at the same time, -1 sorts before +1, so ends come first
    events.sort { ($0.time, $0.change) < ($1.time, $1.change) }
    var rooms = 0
    var most = 0
    for event in events {
        rooms += event.change
        most = max(most, rooms)
    }
    return most
}

print(minRooms([[0, 30], [5, 10], [15, 20], [10, 15], [25, 35], [8, 12]]))
print(minRooms([[1, 5], [5, 10], [10, 15]]))
print(minRooms([]))
```

```output
3
1
0
```

Swift compares tuples element by element, so `(10, -1) < (10, 1)` is true: at the same time, an end sorts before a start, which is exactly what half-open meetings need. That one comparison carries the whole touching rule. If starts came first instead, `[[1, 5], [5, 10], [10, 15]]` would briefly count two meetings at time 5 and answer 2.

If you've done [Difference arrays for range updates](/dsa/learn/prefix-difference-array), this is the same +1 at the start and −1 at the end, followed by a running sum. A difference array needs the times to be small array indexes. Sorting the events works for **any** times, such as seconds since 1970, at the price of the sort. Two lessons from now, the sweep-line lesson takes this idea much further.

## Approach 3, for later: a heap of end times

A third classic approach sorts the meetings by start and keeps the **end times of the rooms in use** in a min-heap, a structure that always hands you its smallest value quickly. For each meeting, if the room that frees up earliest is free by the meeting's start, reuse it (remove its end time); then add the new meeting's end time. The heap's largest size is the answer. It's also O(n log n), and it tells you which room each meeting gets. Heaps arrive in M39, and this problem is a good one to revisit then.
