## Why it matters

An **interval** is a stretch between a start and an end: a meeting from 9 to 11, the seconds of a video that have finished downloading, the characters a user has selected in a text view. Calendar apps merge your busy blocks before showing "free" and "busy" to colleagues. A video player keeps its downloaded stretches merged so it can tell at a glance whether the next ten seconds are ready. In DSA, interval problems are a family of their own, and nearly all of them begin the same way: **sort, then make one pass**. This module's first lesson teaches the two that everything else builds on, merging and inserting.

## Writing an interval in Swift

An interval is two numbers that belong together. Swift gives you three reasonable ways to hold them:

```swift run
struct Interval {
    let start: Int
    let end: Int
}

let asStructs = [Interval(start: 1, end: 3), Interval(start: 5, end: 8)]
let asTuples = [(start: 1, end: 3), (start: 5, end: 8)]
let asPairs = [[1, 3], [5, 8]]

print(asStructs[1].end, asTuples[1].end, asPairs[1][1])
print(asStructs[0])
print(asPairs)
print(asPairs == [[1, 3], [5, 8]])
```

```output
8 8 8
Interval(start: 1, end: 3)
[[1, 3], [5, 8]]
true
```

| Form | Good at | Costs |
| --- | --- | --- |
| a small struct, as in [Structs, properties and methods](/dsa/learn/swift-structs) | clear names; can conform to `Comparable` and other protocols | wordier to write and print |
| a named tuple `(start: Int, end: Int)` | light, and still named | an array of tuples isn't `Equatable`, so you can't `==` two results; tuples can't conform to protocols |
| a pair `[start, end]` in an `[[Int]]` | what interview problems use; prints neatly; `==` works | nothing stops `[1]` or `[1, 2, 3]`, and `slot[0]` reads worse than `slot.start` |

**This module's convention is the pair:** an interval is a two-element `[Int]`, a list of them is `[[Int]]`, and `interval[0]` is the start and `interval[1]` the end. Every problem in the module uses it. In your own app code, prefer the struct: the names are worth it.

## Closed or half-open: do touching intervals overlap?

Before any interval code, settle one question: is the end **included**?

- A **closed** interval `[1, 4]` contains both ends: 1, 4 and everything between. Inclusive ranges of whole seconds or days work like this. Swift writes these as `1...4`.
- A **half-open** interval `[9, 11)` contains its start but not its end. A meeting from 9 to 11 is over at 11:00, so a meeting from 11 to 12 doesn't clash with it. Swift writes these as `9..<11`.

The difference only shows when two intervals **touch**, one ending exactly where the other starts. You met the same choice in [Invariants and off-by-one: closed vs half-open](/dsa/learn/bs-invariants), and it causes the same bugs here.

The overlap test is easiest to build backwards. Two closed intervals **don't** overlap when one finishes before the other begins: `a[1] < b[0]` or `b[1] < a[0]`. Flip that around and you get the test for when they **do**. For half-open intervals, "finishes before" includes finishing exactly when the other begins, so the `<=` becomes `<`:

```swift run
// Closed: [start, end] includes both ends
func overlapClosed(_ a: [Int], _ b: [Int]) -> Bool {
    a[0] <= b[1] && b[0] <= a[1]
}

// Half-open: [start, end) includes the start but not the end
func overlapHalfOpen(_ a: [Int], _ b: [Int]) -> Bool {
    a[0] < b[1] && b[0] < a[1]
}

for (a, b) in [([1, 4], [4, 6]), ([1, 4], [3, 6]), ([1, 4], [5, 6]), ([1, 9], [3, 4])] {
    print(a, b, "closed:", overlapClosed(a, b), "half-open:", overlapHalfOpen(a, b))
}
```

```output
[1, 4] [4, 6] closed: true half-open: false
[1, 4] [3, 6] closed: true half-open: true
[1, 4] [5, 6] closed: false half-open: false
[1, 9] [3, 4] closed: true half-open: true
```

Only the first pair, which touches at 4, gets different answers. Every problem in this module states which kind it uses. When a problem doesn't, look at its examples, or in an interview, ask.

## Merging overlapping intervals

Given intervals in any order, combine every group that overlaps into one interval. In this section they're closed, so touching intervals merge too: `[2, 6]` and `[6, 7]` become `[2, 7]`.

Comparing every interval with every other would be O(n²), and merging one pair can create a new overlap with a third. Sorting fixes both problems. Once the intervals are **sorted by start**, anything that overlaps the interval you're building comes straight after it in the list. As soon as one starts after the current end, every later one starts even later, so the current interval is finished.

So the algorithm is one pass over the sorted list:

1. If the next interval starts at or before the **last merged interval's** end, they overlap: stretch that end to the larger of the two ends.
2. Otherwise there's a gap: the next interval starts a new merged interval.

```swift run
func merge(_ intervals: [[Int]]) -> [[Int]] {
    let sorted = intervals.sorted { $0[0] < $1[0] }
    var merged: [[Int]] = []
    for interval in sorted {
        if let last = merged.last, interval[0] <= last[1] {
            merged[merged.count - 1][1] = max(last[1], interval[1])   // overlap: stretch the last one
        } else {
            merged.append(interval)                                   // a gap: start a new one
        }
        print(interval, "->", merged)
    }
    return merged
}

print(merge([[8, 10], [1, 3], [2, 6], [15, 18], [6, 7], [17, 20]]))
```

```output
[1, 3] -> [[1, 3]]
[2, 6] -> [[1, 6]]
[6, 7] -> [[1, 7]]
[8, 10] -> [[1, 7], [8, 10]]
[15, 18] -> [[1, 7], [8, 10], [15, 18]]
[17, 20] -> [[1, 7], [8, 10], [15, 20]]
[[1, 7], [8, 10], [15, 20]]
```

What to notice:

- Compare with the **last merged** interval, not with the previous input interval. After `[1, 10]` and `[2, 3]`, the next interval must be compared with 10, not 3.
- The `max` matters. When an interval sits entirely inside the current one, like `[2, 3]` inside `[1, 10]`, the end must stay 10.
- `if let last = merged.last, …` handles the first interval, when there's nothing to compare with yet.
- Sorting costs **O(n log n)** and the pass is O(n), so the whole merge is O(n log n), with O(n) space for the sorted copy and the result.

## Inserting into a sorted list

Now suppose the list is **already** merged: sorted by start, with no two intervals overlapping or touching. A calendar keeps its busy blocks this way. A new interval arrives. You could append it, sort again and merge again, but that's O(n log n) and throws away the order you already have. One pass does it in **O(n)**, in three phases:

1. **Before:** copy every interval that ends before the new one starts. They can't touch it.
2. **Overlapping:** every interval that starts at or before the new one's end overlaps it. Absorb each one: the new interval becomes `[min of the starts, max of the ends]`. Then add it.
3. **After:** copy everything that's left.

```swift run
func insert(_ newInterval: [Int], into intervals: [[Int]]) -> [[Int]] {
    var result: [[Int]] = []
    var merged = newInterval
    var i = 0
    // 1. Everything that ends before the new interval starts
    while i < intervals.count && intervals[i][1] < merged[0] {
        result.append(intervals[i])
        i += 1
    }
    // 2. Everything that starts at or before its end overlaps it: absorb them
    while i < intervals.count && intervals[i][0] <= merged[1] {
        merged = [min(merged[0], intervals[i][0]), max(merged[1], intervals[i][1])]
        i += 1
    }
    result.append(merged)
    // 3. Everything after it, unchanged
    while i < intervals.count {
        result.append(intervals[i])
        i += 1
    }
    return result
}

let calendar = [[1, 2], [3, 5], [6, 7], [8, 10], [12, 16]]
print(insert([4, 8], into: calendar))
print(insert([0, 0], into: calendar))
print(insert([0, 20], into: calendar))
print(insert([5, 6], into: [[1, 2], [3, 5], [6, 7]]))
```

```output
[[1, 2], [3, 10], [12, 16]]
[[0, 0], [1, 2], [3, 5], [6, 7], [8, 10], [12, 16]]
[[0, 20]]
[[1, 2], [3, 7]]
```

In the first call, `[4, 8]` absorbs `[3, 5]`, `[6, 7]` and `[8, 10]` (which touches it at 8) and becomes `[3, 10]`. In the second, phase 2 absorbs nothing, so `[0, 0]` goes in at the front. In the last, `[5, 6]` touches a neighbour at each end and joins them both.

Phase 2's test needs no check against the new interval's start: phase 1 already skipped everything that ends before it, so each interval reaching phase 2 ends at or after the new start. If it also starts at or before the new end, the two overlap.

<Callout kind="gotcha" title="Swift gotcha: editing a copy">
Arrays are values, so taking an element out of one gives you a copy. Changing the copy leaves the array alone:

```swift run
var merged = [[1, 3]]
var last = merged[merged.count - 1]
last[1] = 6
print(merged, last)
merged[merged.count - 1][1] = 6
print(merged)
```

```output
[[1, 3]] [1, 6]
[[1, 6]]
```

Write through the array's subscript, as the merge code does, to change the element in place.
</Callout>

## Aside: finding the spot with binary search

In a sorted list with no overlaps, the **ends** are sorted too: each interval ends before the next one starts, so before the next one ends. That makes phase 1's stopping point, the first interval that ends at or after the new start, a job for a lower bound, from [Lower bound, upper bound, first and last occurrence](/dsa/learn/bs-bounds):

```swift run
// The first index whose end is at least `value`. Ends are sorted in a non-overlapping list.
func firstEnding(atOrAfter value: Int, in intervals: [[Int]]) -> Int {
    var low = 0
    var high = intervals.count             // search the half-open range low..<high
    while low < high {
        let mid = low + (high - low) / 2
        if intervals[mid][1] < value {
            low = mid + 1
        } else {
            high = mid
        }
    }
    return low
}

let calendar = [[1, 2], [3, 5], [6, 7], [8, 10], [12, 16]]
print(firstEnding(atOrAfter: 4, in: calendar))
print(firstEnding(atOrAfter: 11, in: calendar))
print(firstEnding(atOrAfter: 20, in: calendar))
```

```output
1
4
5
```

That finds the spot in O(log n), and `replaceSubrange` can swap phase 2's run for the merged interval in place. But the array still shifts every later element, so the whole insert stays O(n). The search pays off when you only need the position, for example to answer "does this clash with anything?", or when the intervals live in a balanced search tree, which you'll meet in Part V.
