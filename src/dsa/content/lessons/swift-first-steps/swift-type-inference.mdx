## Why it matters

Every value in Swift has a **type**, and the type decides what you can do with it: you can multiply numbers but not names, and you can make text uppercase but not numbers. Swift checks types before your program runs, which catches mistakes like adding a price to a name. Usually you never write the type yourself, because Swift works it out. Knowing when it can't, and when its guess isn't what you want, saves you from confusing errors and from subtle maths bugs.

## Every value has a type

A **type** is a kind of value. You'll use these four constantly:

| Type | Holds | Examples |
| --- | --- | --- |
| `Int` | whole numbers | `42`, `-7`, `0` |
| `Double` | numbers with a fractional part | `3.14`, `-0.5`, `2.0` |
| `String` | text | `"Swift"`, `""` |
| `Bool` | true or false | `true`, `false` |

You can ask Swift for a value's type with `type(of:)`:

```swift run
let lessons = 627
let price = 4.99
let language = "Swift"
let isFun = true
print(type(of: lessons))
print(type(of: price))
print(type(of: language))
print(type(of: isFun))
```

```output
Int
Double
String
Bool
```

You never wrote `Int` or `Double`, yet Swift knows. M02 covers each type in depth. This lesson is about how Swift decides.

## Type inference: Swift works it out

**Type inference** means Swift looks at the value you assign and works out the type for you. It goes by the form of the **literal**, the value typed straight into your code:

- A whole number, like `627`, becomes an `Int`.
- A number with a decimal point, like `4.99`, becomes a `Double`.
- Text in double quotes becomes a `String`.
- `true` or `false` becomes a `Bool`.

Inference also works through expressions. If `width` and `height` are both `Int`, then `let area = width * height` is an `Int` too, because multiplying two `Int` values gives an `Int`.

Once the type is decided, it's fixed for good. This is called **static typing**: every name has one type, known before the program runs. That's why the earlier lesson's `score = "ten"` failed when `score` was an `Int`.

## Type annotations: saying the type yourself

A **type annotation** states the type explicitly. Write a colon after the name, then the type:

```swift run
let lives: Int = 3
let name: String = "Ada"
print(lives, name)
```

```output
3 Ada
```

Read `let lives: Int = 3` as "`lives`, of type `Int`, is 3". Here the annotations add nothing, since Swift would infer the same types. Swift style is to leave them out when inference already gives the right answer. You need them in three situations.

### 1. When the default isn't what you want

A whole-number literal becomes an `Int` unless you say otherwise. If you want a `Double`, annotate it:

```swift run
let ratio: Double = 3
let count = 3
print(ratio)
print(count)
```

```output
3.0
3
```

Both lines use the literal `3`, but `ratio` is a `Double`, so it prints as `3.0`. Writing `let ratio = 3.0` has the same effect. The same goes for other types you'll meet in M02, like a single `Character`, which you must annotate because a literal in double quotes is a `String` by default.

### 2. When there's no value yet

If you declare a name before giving it a value, Swift has nothing to infer from, so the type is required:

```swift
let answer: Int
answer = 42
```

### 3. To make your intent clear

Sometimes an annotation helps the reader, for example when a value comes from a long expression. Use this sparingly.

<Callout kind="note">
Later you'll create empty collections, like an empty list of names. An empty list gives Swift nothing to infer from, so you'll write `var names: [String] = []`. You'll meet arrays properly in M07.
</Callout>

## Swift never converts types silently

In many languages, mixing a whole number and a decimal number "just works". Swift refuses:

```swift
let apples = 3
let pricePerApple = 0.5
let total = apples * pricePerApple
```

```text title="What you'll see"
error: binary operator '*' cannot be applied to operands of type 'Int' and 'Double'
```

`apples` is an `Int` and `pricePerApple` is a `Double`, and Swift's `*` only works on two values of the **same** type. To mix them, convert one explicitly. `Double(apples)` makes a `Double` from the `Int`:

```swift run
let apples = 3
let pricePerApple = 0.5
let total = Double(apples) * pricePerApple
print(total)
```

```output
1.5
```

This strictness feels fussy at first, but it prevents real bugs. Every conversion is visible in the code, so you can never lose precision by accident. You'll learn all the conversions in M02.

## Literals adapt to their context

There's a subtlety that trips up even experienced developers. A literal has no fixed type until Swift sees where it's used. So these two lines give different answers:

```swift run
let half: Double = 3 / 2
let whole = 3 / 2
print(half)
print(whole)
```

```output
1.5
1
```

- In the first line, the annotation says the result is a `Double`, so Swift treats `3` and `2` as `Double` values and divides them properly: `1.5`.
- In the second, there's no annotation, so `3` and `2` are `Int` values. Dividing two `Int` values gives a whole number, dropping the fractional part: `1`.

<Callout kind="gotcha" title="Swift gotcha: converting too late">
Once a value *is* an `Int`, converting the result doesn't bring back the lost part. With `let three = 3`, `Double(three / 2)` is `1.0`, because `three / 2` is worked out as `Int` division first. Convert before dividing: `Double(three) / 2` is `1.5`. This bug shows up whenever you compute an average, so watch for it in every problem that needs one.
</Callout>
