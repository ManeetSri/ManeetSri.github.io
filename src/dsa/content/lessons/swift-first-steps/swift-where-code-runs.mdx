## Why it matters

The same Swift code can run in several places, and each one suits a different job. Picking the right one saves time: a playground answers "what does this do?" in seconds, while a package gives you tests that prove your solution works. In this course you'll use all of them, often in the same study session.

You set these tools up in [Install Xcode and the Swift tools](/dsa/learn/start-install-swift). This lesson explains how each one runs your code, so you know what to expect from it.

## One language, four ways to run it

| Tool | How you run code | Best for |
| --- | --- | --- |
| **Playground** | Press Run in Xcode | Trying ideas and seeing values as you go |
| **REPL** | Type a line in Terminal, press Return | One-line questions |
| **Script file** | `swift file.swift` in Terminal | Short complete programs, like the lesson examples |
| **Package** | `swift build`, `swift test`, `swift run` | Anything with tests, and longer code |

The language is identical everywhere. What changes is how much setup there is, and how much help you get around the code.

## Playgrounds: a scratchpad that shows its working

In Xcode, choose **File › New › Playground…** and pick **Blank**. A playground is a single page of Swift. Press **Run** and it runs your code from top to bottom, like any program.

What makes playgrounds special is the **results sidebar** on the right. Next to each line, it shows the value that line produced. Write `let total = 12 * 3` and you'll see `36` beside it without needing a `print`. It's a quick way to watch values change as you experiment.

Apple's **Swift Playgrounds** app, on the Mac and iPad, works in a similar way and is handy away from your desk.

<Callout kind="warning">
Playgrounds record the value of every line as it runs, which makes them slow for heavy work. A loop that runs a million times can take a long time in a playground and a fraction of a second in a package. Use playgrounds for small experiments, not for timing algorithms.
</Callout>

## The REPL: one line at a time

**REPL** stands for *Read, Evaluate, Print, Loop*: it reads a line you type, works it out, prints the result and waits for the next line. Start it in Terminal:

```bash
swift repl
```

Then type expressions and press Return after each one:

```text title="A REPL session"
  1> 7 / 2
$R0: Int = 3
  2> let name = "Ada"
name: String = "Ada"
  3> :quit
```

The REPL shows each result with its **type**, here `Int` and `String`. `$R0` is a temporary name the REPL gives to a result you didn't name yourself. It's perfect for questions like "what does `7 / 2` give for whole numbers?" (The answer, `3`, is explained in M02.) Type `:quit` to leave.

## Script files: a whole program in one file

A **script** is a single `.swift` file that you run with the `swift` command. Save this as `hello.swift`:

```swift run
let language = "Swift"
print("Hello from a \(language) script!")
print("Lines run from top to bottom.")
```

```output
Hello from a Swift script!
Lines run from top to bottom.
```

Then run it from the folder that contains it:

```bash
swift hello.swift
```

`swift` compiles the file and runs it straight away. This is exactly how every runnable example in these lessons works. Each one is copied into the companion package's `Examples` folder, and its **Run command** button gives you a command like `swift Examples/swift-first-steps/swift-where-code-runs-1.swift`.

In a script, you can write statements directly in the file, as above. Code written outside any function like this is called **top-level code**, and Swift runs it from the first line down.

## Packages: real projects with tests

A **Swift package** is a folder with a standard layout and a `Package.swift` file describing it. It's how Swift code is organised for anything bigger than a single file. You already have one: the `dsa-swift` companion package from [The companion Swift package](/dsa/learn/start-companion-package).

| Command | What it does |
| --- | --- |
| `swift build` | Compiles everything and reports any errors |
| `swift test` | Builds, then runs the tests |
| `swift test --filter ProfileLineTests` | Runs only the tests whose name matches |
| `swift run` | Builds and runs a package that's an app or command-line tool |

You can create a new package of your own with `swift package init --type executable` in an empty folder. The exact files it generates change between Swift versions, but you'll always get a `Package.swift`, a `Sources` folder and usually a `Tests` folder.

<Callout kind="gotcha" title="Swift gotcha: top-level code in packages">
Top-level statements are only allowed in scripts, playgrounds and an app's entry file. Most files in a package, including everything in `Sources/Exercises`, may only contain declarations, such as functions and types. A stray `print("hi")` at the top of an exercise file gives `expressions are not allowed at the top level`. That's why every practice problem lives inside a function, which you'll learn to write in M05.
</Callout>

## Which one should you reach for?

- **"What does this line do?"** Use the REPL or a playground.
- **"Let me try an idea for a few minutes."** Use a playground or a script file.
- **"Does my solution pass?"** Use the package: `swift test --filter …`.
- **"How fast is this?"** Use the package, in release mode, as you'll learn in M12.

A good study rhythm is to read a lesson with a scratch playground open, predict each example's output, then check it. When you reach the practice problems, switch to the package.
