## Why it matters

Code is read far more often than it's written, including by you, three weeks from now, when you've forgotten why you did something. **Comments** are notes in your code that Swift ignores completely. Used well, they explain the *why* behind a tricky line, such as why a loop starts at 1 or why a sum can't overflow. Used badly, they repeat the code and go stale.

## Single-line comments: //

Two slashes start a comment that runs to the end of the line. It can sit on its own line or after some code:

```swift run
// Work out the price of a cinema trip
let ticketPrice = 12
let tickets = 3   // two adults and a child
print(ticketPrice * tickets)
```

```output
36
```

Swift skips everything from `//` to the end of the line, so the comments change nothing about what runs.

## Block comments: /* */

For a longer note, start with `/*` and end with `*/`. Everything between them is ignored, even across many lines:

```swift run
/*
 Prints a short welcome message.
 Written while learning Swift.
 */
print("Welcome!")
```

```output
Welcome!
```

Unlike many languages, Swift lets you **nest** block comments: a `/* … */` inside another one works correctly. That means you can safely wrap a block comment around code that already contains one.

## Commenting out code

Comments are also handy for switching code off without deleting it. Put `//` in front of a line and it stops running:

```swift run
print("Step 1")
// print("Step 2")
print("Step 3")
```

```output
Step 1
Step 3
```

In Xcode, select some lines and press `⌘/` to comment or uncomment them all at once. It's useful while experimenting. Just don't leave piles of commented-out code behind: that's what version control is for.

## Documentation comments: ///

A comment that starts with **three** slashes is a **documentation comment**. It describes the thing declared right after it, and Xcode shows it in **Quick Help** when you Option-click that name. Every exercise in the companion package has one:

```swift title="Sources/Exercises/orientation/HelloSwift.swift"
public enum HelloSwift {
    /// Returns "Hello, <name>!", or "Hello, world!" when the name is empty.
    public static func greet(_ name: String) -> String {
        // Write your solution here, then run:
        // swift test --filter HelloSwiftTests
        return ""
    }
}
```

Doc comments can use Markdown, plus a few special fields that Xcode lays out neatly:

```swift
/// Splits a number of seconds into minutes and seconds.
///
/// - Parameter totalSeconds: A number of seconds, zero or more.
/// - Returns: The whole minutes and the seconds left over.
```

You won't write functions until M05, but you'll *read* doc comments from the very first practice problem. They're the specification: read them before you start.

## What makes a good comment

The best comments explain **why**, not **what**. The code already says what it does.

```swift title="Not helpful: repeats the code"
let total = price * quantity   // multiply price by quantity
```

```swift title="Helpful: explains a decision the code can't"
let total = price * quantity   // tax is added later, at checkout
```

Before writing a comment, ask whether a better name would make it unnecessary. `let t = 86400 // seconds in a day` is fine, but `let secondsPerDay = 86400` needs no comment at all. You'll learn more about this in *Naming things well*, later in this module.

In DSA code, good comments usually explain an **invariant** or a **non-obvious step**: "everything left of `low` is smaller than the target" or "start at 1 because the first element is already counted". Those are exactly the details that are hard to recover from the code alone.

<Callout kind="tip" title="Two comments Xcode understands">
`// MARK: - Helpers` adds a heading to Xcode's jump bar, so long files are easy to navigate. `// TODO: handle empty input` marks unfinished work, and Xcode lists it in the same menu.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: comments go stale">
Swift checks your code, but it never checks your comments. If you change `tickets = 3` to `tickets = 4` and leave `// two adults and a child`, the comment is now wrong, and nothing will tell you. A wrong comment is worse than none, so update comments whenever you change the code beside them.
</Callout>
