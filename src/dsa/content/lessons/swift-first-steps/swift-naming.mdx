## Why it matters

Names are the main way code explains itself. `let x = 86400` makes the reader stop and think. `let secondsPerDay = 86400` explains itself instantly. In DSA, clear names make the difference between an algorithm you can follow and one you have to decode. In interviews, good names show you understand what each value is for.

## The rules Swift enforces

A name, which programmers call an **identifier**, must follow a few rules:

- It can contain letters, digits and underscores, but **no spaces**.
- It **can't start with a digit**: `player2` is fine, `2player` isn't.
- It's **case-sensitive**: `score`, `Score` and `SCORE` are three different names.
- It can't be a **keyword**, one of Swift's reserved words like `let`, `var`, `class` or `if`.

Break a rule and the code doesn't compile:

```swift
let first name = "Ada"
let class = 3
```

```text title="What you'll see"
error: found an unexpected second identifier in constant declaration; is there an accidental break?
error: keyword 'class' cannot be used as an identifier here
```

Swift also allows letters from any language, and even symbols such as `π`. That's occasionally nice for maths, but stick to plain English letters in shared code so everyone can type your names.

## The conventions everyone follows

Beyond the rules, Swift code follows strong **conventions**: habits that aren't enforced but that every Swift programmer expects.

| What you're naming | Style | Examples |
| --- | --- | --- |
| Constants, variables, functions | lowerCamelCase | `score`, `maximumLives`, `secondsPerDay` |
| Types (you'll create these in M09) | UpperCamelCase | `String`, `Int`, `ShoppingList` |

**Camel case** joins words without spaces and starts each new word with a capital, like the humps of a camel. Lower camel case starts with a small letter, upper camel case with a capital. Swift doesn't use underscores between words, so it's `maximumLives`, not `maximum_lives`.

## Descriptive names

A good name says **what the value means**, not what kind of thing it is:

| Unclear | Clear |
| --- | --- |
| `n` | `numberOfStudents` |
| `str` | `greeting` |
| `temp` | `celsius` |
| `flag` | `isLoggedIn` |
| `d` | `daysUntilDeadline` |

A few patterns help:

- **True-or-false values read like a statement**: `isEmpty`, `hasDiscount`, `canEdit`. Then code like "if `isLoggedIn`" reads as plain English.
- **Counts say what they count**: `studentCount` or `numberOfStudents`, not `number`.
- **Units go in the name when they matter**: `timeoutSeconds`, `distanceInKm`. A whole class of bugs comes from mixing up units.

```swift run
let secondsPerMinute = 60
let minutesPerHour = 60
let secondsPerHour = secondsPerMinute * minutesPerHour
print("An hour has \(secondsPerHour) seconds.")
```

```output
An hour has 3600 seconds.
```

No comments needed: the names carry the meaning.

## Short names that are fine

Long isn't always better. A name should be as long as it needs to be for its **scope**, the stretch of code where it's used.

- Inside a three-line loop, `i` is a perfectly good name for a counter. Everyone reads it as "index".
- Algorithms have traditional names that experienced readers recognise: `n` for the input size, `left` and `right` for two positions moving towards each other, `low`, `mid` and `high` in binary search.
- A value used across a whole file deserves a full, descriptive name.

You'll see all of these in the algorithm modules. The rule of thumb: the further a name travels from where it's declared, the more descriptive it should be.

## Swift's own naming style

Apple publishes **API Design Guidelines** for Swift, and the standard library follows them closely. Three ideas are worth knowing now:

1. **Clarity at the point of use matters most.** Names are chosen so the line where they're *used* reads clearly, like `names.contains("Ada")`.
2. **Omit needless words.** `greeting` is better than `greetingString`: the type already says it's text.
3. **Read like English.** Calls such as `list.insert(item, at: 0)` read almost as a sentence. You'll write functions like this in M05.

<Callout kind="gotcha" title="Swift gotcha: case-sensitive names">
`let score = 10` followed by `print(Score)` fails with `cannot find 'Score' in scope`. Swift sees `Score` as a completely different name. When the compiler says it can't find something you're sure you declared, check the capital letters first.
</Callout>
