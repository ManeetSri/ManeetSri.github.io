## Why it matters

Once you can walk a tree level by level, a whole family of interview questions becomes a small twist on the same loop. Read the levels in a zigzag. Report what you'd see standing to the right of the tree, or to the left, or looking down from above, or up from below. Each is level order plus one extra rule about *which* nodes to keep, and the top and bottom views add one new idea, a node's **column**, which the next lesson builds on.

The examples use the running example again:

```text
        1
       / \
      2   3
     / \   \
    4   5   6
       /
      7
```

## Zigzag order

Zigzag (sometimes called spiral) order reads level 0 left to right, level 1 right to left, level 2 left to right again, and so on. For the running example: `[[1], [3, 2], [4, 5, 6], [7]]`.

The simplest way is to collect each level left to right, as in [Level-order traversal with a queue](/dsa/learn/trav-level-order), and reverse every odd-numbered level before recording it. Reversing a level costs as much as building it, so the whole thing is still O(n).

A tempting alternative is to keep the levels in the zigzag direction by pushing children right-first on alternate levels. It works, but it's easy to tangle: the order you *visit* a level in and the order you *queue* its children in interact. Reversing the finished level keeps those two concerns apart. If you'd rather not reverse, build each level's values in a `Deque` instead, appending at the back on even levels and at the front on odd ones.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func zigzag(_ root: TreeNode?) -> [[Int]] {
    var result: [[Int]] = []
    var level = [root].compactMap { $0 }
    var leftToRight = true
    while !level.isEmpty {
        let values = level.map(\.value)                  // always built left to right
        result.append(leftToRight ? values : values.reversed())
        leftToRight.toggle()
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return result
}

let root = TreeNode(1,
                    left: TreeNode(2, left: TreeNode(4), right: TreeNode(5, left: TreeNode(7))),
                    right: TreeNode(3, right: TreeNode(6)))
print(zigzag(root))
```

```output
[[1], [3, 2], [4, 5, 6], [7]]
```

## Right and left views

Stand to the right of the tree and look at it. On each level you see one node: the **rightmost**, which hides everything behind it. The right view lists those nodes from the top down. The left view is the same from the other side: the **leftmost** node of each level.

| View | Running example | Why |
| --- | --- | --- |
| Right | `[1, 3, 6, 7]` | the last node on each level |
| Left | `[1, 2, 4, 7]` | the first node on each level |

The right view includes 7, even though 7 hangs on the left side of the tree. Nothing on its level is further right, so from the right-hand side you can see it. That's the classic trap: following `right` pointers down from the root gives `[1, 3, 6]` and misses 7.

There are two good ways to compute a view:

- **Level order:** keep the last (or first) node of each level.
- **Depth-first, right child first:** walk node, right, left, carrying the depth. The first node you reach on each new depth is the rightmost on that level, so record a node when `depth == result.count`, meaning "this is the first visit to this depth".

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func rightViewByLevels(_ root: TreeNode?) -> [Int] {
    var result: [Int] = []
    var level = [root].compactMap { $0 }
    while let last = level.last {
        result.append(last.value)                       // the rightmost on this level
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return result
}

func view(_ root: TreeNode?, fromRight: Bool) -> [Int] {
    var result: [Int] = []
    func walk(_ node: TreeNode?, _ depth: Int) {
        guard let node else { return }
        if depth == result.count {
            result.append(node.value)                   // first node reached on this depth
        }
        let (near, far) = fromRight ? (node.right, node.left) : (node.left, node.right)
        walk(near, depth + 1)
        walk(far, depth + 1)
    }
    walk(root, 0)
    return result
}

let root = TreeNode(1,
                    left: TreeNode(2, left: TreeNode(4), right: TreeNode(5, left: TreeNode(7))),
                    right: TreeNode(3, right: TreeNode(6)))
print("right, by levels:", rightViewByLevels(root))
print("right, by depth: ", view(root, fromRight: true))
print("left, by depth:  ", view(root, fromRight: false))
```

```output
right, by levels: [1, 3, 6, 7]
right, by depth:  [1, 3, 6, 7]
left, by depth:   [1, 2, 4, 7]
```

`while let last = level.last` ends the loop when a level is empty, and hands you its last node otherwise. The depth-first version uses only O(h) memory, but it recurses, so it needs an explicit stack for very deep trees.

## Columns

For the top and bottom views you need to know which nodes line up **vertically**. Give each node a **column**, its horizontal distance from the root: the root is in column 0, a left child is one column left of its parent, and a right child one column right.

```text
column:  -2  -1   0   1   2
                  1
                /   \
               2     3
              / \     \
             4   5     6
                /
               7
```

So 4 is in column −2; 2 and 7 in column −1; 1 and 5 in column 0; 3 in column 1; and 6 in column 2. Notice 5 sits directly under the root, and 7 under 2: a left child of a right child ends up back where it started.

## Top and bottom views

Look down at the tree from above, and in each column you see the **highest** node; the ones below are hidden. That's the **top view**. Looking up from below, you see the **lowest** node in each column: the **bottom view**. Both are listed from the leftmost column to the rightmost.

Two nodes can be in the same column **and** on the same level, so each view needs a rule for ties. This lesson and its problems use these:

- **Top view:** the highest node in each column; if two are equally high, the one further left, which is the one level order meets first.
- **Bottom view:** the lowest node in each column; if two are equally low, the one further right, which is the one level order meets last.

Other books and sites pick differently, so always check a problem's tie rule. With these rules, level order makes both views easy. Walk the tree with each node's column. For the top view, keep the **first** node seen in each column; for the bottom view, keep the **last**, overwriting as you go.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func topAndBottom(_ root: TreeNode?) -> (top: [Int], bottom: [Int]) {
    guard let root else { return ([], []) }
    var top: [Int: Int] = [:]                    // column -> value
    var bottom: [Int: Int] = [:]
    var queue: [(node: TreeNode, column: Int)] = [(root, 0)]
    var head = 0
    while head < queue.count {
        let (node, column) = queue[head]
        head += 1
        if top[column] == nil {
            top[column] = node.value             // the first, so the highest, in this column
        }
        bottom[column] = node.value              // the last so far, so the lowest
        if let left = node.left { queue.append((left, column - 1)) }
        if let right = node.right { queue.append((right, column + 1)) }
    }
    let columns = top.keys.sorted()              // dictionary order is random: sort the keys
    return (columns.map { top[$0]! }, columns.map { bottom[$0]! })
}

let root = TreeNode(1,
                    left: TreeNode(2, left: TreeNode(4), right: TreeNode(5, left: TreeNode(7))),
                    right: TreeNode(3, right: TreeNode(6)))
let views = topAndBottom(root)
print("top:   ", views.top)
print("bottom:", views.bottom)

// 4 and 5 share column 0 and level 2: a tie
let tied = TreeNode(1, left: TreeNode(2, right: TreeNode(4)), right: TreeNode(3, left: TreeNode(5)))
print("tie, bottom:", topAndBottom(tied).bottom)
```

```output
top:    [4, 2, 1, 3, 6]
bottom: [4, 7, 5, 3, 6]
tie, bottom: [2, 5, 3]
```

What to notice:

- Column 0 holds 1 and 5. The top view keeps 1, the bottom view keeps 5. Column −1 holds 2 and 7, and the bottom view keeps 7, the deepest.
- In the tie, 4 (under 2) and 5 (under 3) are both in column 0 on level 2. Level order meets 4 first and 5 last, so the bottom view keeps 5, the right-hand one.
- The dictionary is never printed whole: its order changes from run to run. Sorting the keys gives the columns left to right. Because the columns form an unbroken range (every column between the leftmost and the rightmost has a node), you could also track the smallest and largest column and loop over that range instead of sorting.

<Callout kind="gotcha" title="Why level order, not depth-first, for top and bottom views">
A depth-first walk doesn't meet nodes in order of depth. Suppose the root's left child has a right child with a right child: that grandchild of a grandchild is in column +1, three levels down. Preorder finishes the whole left subtree first, so it reaches that deep node before the root's own right child, which is also in column +1 but only one level down. "Keep the first node seen" would then pick the wrong one. A depth-first version must store each column's depth and compare, which is more code for the same answer. Level order gets the order right for free.
</Callout>

<Callout kind="gotcha" title="Common mistakes">
- **Following only `right` pointers for the right view.** That misses nodes on the left side that stick out below a shorter right side, like 7 in the running example.
- **Zigzag by reversing the children's order.** Reversing which child is queued first changes the order of the *next* level's children too, and the levels quickly come out scrambled. Reverse the finished level's values instead.
- **Forgetting the tie rule.** Without one, two correct-looking solutions give different bottom views on the same tree.
</Callout>
