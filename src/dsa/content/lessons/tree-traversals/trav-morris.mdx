## Why it matters

Every traversal so far needs O(h) extra memory, as call frames or as an explicit stack, to remember the way back up. **Morris traversal** needs **O(1)**: no recursion, no stack, only a couple of variables. It does it by borrowing the tree's own unused pointers to leave itself a trail back, then tidying them up as it goes. It's rarely the right tool in an app, but it's a beautiful idea, a favourite "can you do better?" interview follow-up, and a lesson in changing a structure temporarily and restoring it exactly.

## Where the memory goes

Why does an ordinary inorder traversal need a stack at all? Because after finishing a node's left subtree, it has to get back **up** to that node, and nodes only point down. The stack is a list of "places to come back to".

But a binary tree is full of pointers that point nowhere. Each of its n nodes has two child pointers, 2n in total, and only n − 1 of them are used: there are **n + 1 `nil` pointers**. Morris traversal uses some of those spare `nil`s as temporary signposts back up the tree.

## The inorder predecessor

In inorder, which node is visited just before a node `current`? Everything in `current`'s left subtree comes before it, so it's the **last** node of that subtree in inorder: its **rightmost** node. Start at `current.left` and follow `right` pointers until there are no more. That node is `current`'s **inorder predecessor**.

The rightmost node of any subtree has, by definition, no right child. Its `right` pointer is `nil`: a free pointer, sitting exactly where the walk will need a way back to `current`. So Morris traversal points it at `current`. A temporary pointer like this is called a **thread**.

```text
  Before                   Thread from 5 back to 1
        1                          1  <───┐
       / \                        / \     │
      2   3                      2   3    │
     / \   \                    / \   \   │
    4   5   6                  4   5───┘  6
       /                          /
      7                          7
```

In the running example, the rightmost node of 1's left subtree is 5, so 5's empty `right` pointer becomes a thread to 1. Once the walk has visited 5, following its `right` pointer leads straight back to 1, with no stack involved.

## The algorithm

Start with `current` at the root, and repeat while `current` isn't `nil`:

1. **No left subtree?** Then nothing comes before `current`. Visit it and move to `current.right`. That might be a real right child, or a thread leading back up.
2. **Otherwise, find the predecessor**: step to `current.left`, then go right while there's a right child that **isn't `current`**.
3. **If the predecessor's `right` is `nil`**, this is the first time we've reached `current`. Make the thread, `predecessor.right = current`, and move to `current.left` to do the left subtree.
4. **If the predecessor's `right` is already `current`**, we've come back by the thread, so the left subtree is finished. Remove the thread, `predecessor.right = nil`, visit `current`, and move to `current.right`.

Step 2's extra test, "isn't `current`", matters. On the second arrival, the rightmost node's `right` points back at `current`, and without the test the search would follow the thread round and round for ever.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func morrisInorder(_ root: TreeNode?) -> [Int] {
    var result: [Int] = []
    var current = root
    while let node = current {
        guard let left = node.left else {
            result.append(node.value)            // 1. nothing on the left: visit, go right
            print("visit \(node.value)")
            current = node.right
            continue
        }
        var predecessor = left                   // 2. rightmost node of the left subtree
        while let next = predecessor.right, next !== node {
            predecessor = next
        }
        if predecessor.right == nil {
            predecessor.right = node             // 3. first arrival: leave a thread back
            print("thread \(predecessor.value) -> \(node.value)")
            current = left
        } else {
            predecessor.right = nil              // 4. back via the thread: tidy up, visit
            print("unthread \(predecessor.value) -> \(node.value), visit \(node.value)")
            result.append(node.value)
            current = node.right
        }
    }
    return result
}

let root = TreeNode(1,
                    left: TreeNode(2, left: TreeNode(4), right: TreeNode(5, left: TreeNode(7))),
                    right: TreeNode(3, right: TreeNode(6)))
print(morrisInorder(root))
```

```output
thread 5 -> 1
thread 4 -> 2
visit 4
unthread 4 -> 2, visit 2
thread 7 -> 5
visit 7
unthread 7 -> 5, visit 5
unthread 5 -> 1, visit 1
visit 3
visit 6
[4, 2, 7, 5, 1, 3, 6]
```

Follow a few steps. At 1, the predecessor is 5, so `5.right` becomes a thread to 1 and the walk goes left to 2. At 2, the predecessor is 4: another thread. 4 has no left child, so it's visited, and its `right`, the thread, leads back to 2. This time 2's predecessor already points at 2, so the thread is removed and 2 is visited. Later, visiting 5 and following its `right` lands on 1 the same way. Every thread that was made is removed, and the output is an ordinary inorder.

## The tree comes back unchanged

Morris traversal changes the tree while it runs. That's only acceptable because it **puts everything back**: each thread is created on the first arrival at a node and removed on the second. Moving one line also turns it into a **preorder** traversal: visit a node on its *first* arrival, just before making the thread, instead of on its second. This version does both and checks the tree's shape afterwards:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

// The shape in preorder, with "-" for a missing child
func shape(_ node: TreeNode?) -> String {
    guard let node else { return "-" }
    return "\(node.value)(\(shape(node.left)) \(shape(node.right)))"
}

func morris(_ root: TreeNode?, preorder: Bool) -> [Int] {
    var result: [Int] = []
    var current = root
    while let node = current {
        guard let left = node.left else {
            result.append(node.value)
            current = node.right
            continue
        }
        var predecessor = left
        while let next = predecessor.right, next !== node {
            predecessor = next
        }
        if predecessor.right == nil {
            if preorder { result.append(node.value) }     // preorder: visit on the way down
            predecessor.right = node
            current = left
        } else {
            if !preorder { result.append(node.value) }    // inorder: visit on the way back
            predecessor.right = nil
            current = node.right
        }
    }
    return result
}

let root = TreeNode(1,
                    left: TreeNode(2, left: TreeNode(4), right: TreeNode(5, left: TreeNode(7))),
                    right: TreeNode(3, right: TreeNode(6)))
let before = shape(root)
print("inorder: ", morris(root, preorder: false))
print("preorder:", morris(root, preorder: true))
print("shape:   ", before)
print("restored:", shape(root) == before)
```

```output
inorder:  [4, 2, 7, 5, 1, 3, 6]
preorder: [1, 2, 4, 5, 7, 3, 6]
shape:    1(2(4(- -) 5(7(- -) -)) 3(- 6(- -)))
restored: true
```

Nodes without a left child are visited the moment they're reached in both versions: with no left subtree, "before it" and "after it" are the same moment. Postorder can be done the Morris way too, but it needs extra tricks (reversing chains of right pointers and back again), and it's rarely worth it.

## Why it's still O(n)

Finding each predecessor walks down a chain of right pointers, which looks expensive. But each such chain is the right edge of one node's left subtree, and it's walked exactly **twice**: once to make the thread, once to remove it. Different nodes' chains don't overlap, so in total every edge is walked a small, fixed number of times. The traversal is **O(n) time and O(1) extra space**: three variables, however big or deep the tree.

| | Recursive | Explicit stack | Morris |
| --- | --- | --- | --- |
| Extra space | O(h) call stack | O(h) array | O(1) |
| Changes the tree? | no | no | yes, temporarily |
| Safe to stop early? | yes | yes | only after undoing the threads |
| Speed in practice | fast | fast | slower: each predecessor search is extra pointer chasing |

<Callout kind="warning" title="When not to use it">
While Morris traversal runs, the tree contains loops: follow `right` pointers from 5 and you come back to 1. Anything else that reads the tree mid-walk can go round in circles. And if you **stop early**, say with `return` as soon as you find a value, the remaining threads stay in place and the tree is left broken. Either finish the walk, or keep going to remove the threads before returning.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: threads are strong references">
`predecessor.right = node` is an ordinary strong reference, pointing from a descendant back up to an ancestor: a retain cycle, as in [Retain cycles](/dsa/learn/swift-retain-cycles). While the walk is running, that's fine. If the walk is abandoned with threads still in place, though, those nodes keep each other alive, and the tree is leaked as well as broken. One more reason always to finish the walk. Compare nodes with `!==`, too: two different nodes can hold the same value.
</Callout>
