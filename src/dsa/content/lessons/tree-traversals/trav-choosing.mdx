## Why it matters

You now know six ways to walk a binary tree: preorder, inorder and postorder, each recursive or with a stack; level order; and Morris. Every one of them visits every node in O(n) time. What differs is **what you know when you reach a node**, and how much memory the walk needs. Choosing well is most of the work in a tree problem. The binary tree problems in M36 and the binary search tree problems in M37 are, almost all of them, "pick the right traversal, then do a little work at each node".

## Ask what a node needs to know

Start from a single node and ask what it needs before it can do its part:

- **Its children's answers?** (The height below it, the size of its subtree, whether its subtree contains something.) Then the children must finish first: **postorder**, with the answers coming back as return values.
- **Something from its ancestors?** (Its depth, the path from the root, the largest value above it, a running sum.) Then the parent must go first and hand it down: **preorder**, with the information passed as parameters.
- **Its place in sorted order, in a binary search tree?** Then **inorder**, which visits a BST's values smallest first.
- **Its distance from the root, or its level-mates?** (The nearest match, each level's values, what's visible from the side.) Then **level order**, which meets nodes in rings of increasing depth.

When the answer is "nothing in particular", as in counting nodes, summing values or swapping every node's children, any order works. Pick the simplest one to write.

## A map of the problems ahead

| Task | Traversal | Why |
| --- | --- | --- |
| Height, or the maximum depth | postorder, or level order counting levels | a node's height is 1 + the taller child's |
| Diameter, balanced check | postorder | each needs both children's heights |
| Path sums from the root | preorder | carry the sum so far down to each node |
| Nodes larger than everything above them | preorder | carry the largest value seen so far down |
| Lowest common ancestor | postorder | each subtree reports whether it contains either node |
| Serialise and rebuild a tree | preorder or level order | each node is written before its children need it |
| Sorted values, kth smallest, validating a BST | inorder | a BST's inorder is sorted |
| Right side view, each level's values, linking level-mates | level order | the answer is organised by depth |
| Shallowest leaf | level order | stop at the first one found |
| Vertical order, top and bottom views | level order with columns | columns plus depth order |

You'll meet these in M36 and M37, in lessons such as [Depth and diameter](/dsa/learn/bt-depth-diameter), [Path sum I, II and III](/dsa/learn/bt-path-sums), [Lowest common ancestor](/dsa/learn/bt-lca), [Serialise and deserialise](/dsa/learn/bt-serialize) and [Validate a BST](/dsa/learn/bst-validate).

## One question, two good answers

Often more than one traversal works, with different trade-offs. Take "what's the value of the leftmost node on the deepest level?". In the running example, the deepest level holds only 7, so that's the answer.

- **Level order:** the first node of the last level. Simple, and it uses O(w) memory for the widest level.
- **Preorder carrying the depth:** preorder meets each level's nodes left to right, so the first node reached at a new greatest depth is the leftmost one there. It uses O(h) memory but recurses.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func bottomLeftByLevels(_ root: TreeNode) -> Int {
    var level = [root]
    var answer = root.value
    while !level.isEmpty {
        answer = level[0].value                          // leftmost on this level
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return answer
}

func bottomLeftByDepth(_ root: TreeNode) -> Int {
    var deepest = -1
    var answer = root.value
    func walk(_ node: TreeNode?, _ depth: Int) {
        guard let node else { return }
        if depth > deepest {                             // first node seen at a new depth
            deepest = depth
            answer = node.value
        }
        walk(node.left, depth + 1)
        walk(node.right, depth + 1)
    }
    walk(root, 0)
    return answer
}

let root = TreeNode(1,
                    left: TreeNode(2, left: TreeNode(4), right: TreeNode(5, left: TreeNode(7))),
                    right: TreeNode(3, right: TreeNode(6)))
let other = TreeNode(1, left: TreeNode(2), right: TreeNode(3, left: TreeNode(5), right: TreeNode(6)))
print(bottomLeftByLevels(root), bottomLeftByDepth(root))
print(bottomLeftByLevels(other), bottomLeftByDepth(other))
```

```output
7 7
5 5
```

In the second tree, the deepest level is 5 and 6, both under 3, so the leftmost is 5, even though it's in the root's right subtree. Both methods agree. The `depth > deepest` test, rather than `>=`, is what makes the depth-first version keep the **first**, leftmost, node on each level.

## Memory, depth and safety

| Traversal | Time | Extra space | Safe on a 100,000-level chain? |
| --- | --- | --- | --- |
| Recursive pre/in/postorder | O(n) | O(h) call stack | no |
| Explicit-stack pre/in/postorder | O(n) | O(h) heap array | yes |
| Level order | O(n) | O(w), the widest level | yes |
| Morris | O(n) | O(1), but changes the tree temporarily | yes |

A practical rule for choosing between recursion and a loop:

- **Recursion** when the depth is known to be small: balanced trees, trees you built yourself, or tests that promise a few hundred levels. It's shorter and easier to get right.
- **A loop** when the tree could be deep: user data, a binary search tree that isn't kept balanced, or any problem whose constraints allow a degenerate tree of many thousands of nodes. Remember that a recursion that's fine on the main thread can crash inside a test, as [Stack depth limits in Swift](/dsa/learn/rec-stack-limits) showed.
- **Morris** only when O(1) extra memory is genuinely required, or an interviewer asks for it.

## Down and up at once

The hardest tree problems pass information in **both** directions in the same function: something comes down as a parameter, and something different goes back up as a return value. The diameter, for example, returns each subtree's height upwards while keeping track of the best path seen so far. When a problem feels stuck, ask separately: "what does each node need from above?" and "what should each node report to its parent?". The answers are your parameters and your return value.

```cards
- id: choose-up-down
  front: "When should a tree solution be postorder, and when preorder?"
  back: "Postorder when each node needs its children's answers (heights, sizes), returned upwards. Preorder when each node needs something from its ancestors (depth, path so far), passed down as parameters."
- id: choose-inorder
  front: "When is inorder the natural choice?"
  back: "When the tree is a binary search tree and you need its values in sorted order: kth smallest, validating, or walking it like a sorted list."
- id: choose-level
  front: "Which kinds of question point to level order?"
  back: "Anything organised by depth or distance from the root: each level's values, side views, the shallowest match, linking nodes on the same level."
- id: choose-recursion
  front: "When should you write a tree traversal with a loop instead of recursion?"
  back: "When the tree could be very deep, such as user data or an unbalanced BST, because recursion uses one call-stack frame per level and can overflow."
```
