## Why it matters

You have two lists that are each already sorted: two feeds of messages ordered by time, two pages of search results ordered by score. You want one sorted list. Throwing them together and sorting again works, but it ignores the work already done. **Merging** walks both lists once, side by side, and produces the combined order in linear time. It's the step that makes merge sort work in Part IV, and it's a pattern you'll reuse for linked lists in M25 and for intervals in M33.

## Merging into a new array

Put one finger at the start of each array. The smallest element overall must be under one of your two fingers, because each array's smallest element is at its front. Take the smaller of the two, move that finger on, and repeat. When one array runs out, everything left in the other is bigger than anything taken so far, so it goes on the end as it is.

```swift run
func merge(_ first: [Int], _ second: [Int]) -> [Int] {
    var result: [Int] = []
    result.reserveCapacity(first.count + second.count)
    var i = 0
    var j = 0
    while i < first.count && j < second.count {
        if first[i] <= second[j] {
            result.append(first[i])
            i += 1
        } else {
            result.append(second[j])
            j += 1
        }
    }
    result.append(contentsOf: first[i...])       // at most one of these
    result.append(contentsOf: second[j...])      // still has elements
    return result
}

print(merge([1, 4, 7], [2, 3, 9]))
print(merge([5, 6], [1, 2, 3]))
print(merge([], [4, 8]))
```

```output
[1, 2, 3, 4, 7, 9]
[1, 2, 3, 5, 6]
[4, 8]
```

Here's the first merge step by step:

| `first[i]` | `second[j]` | take | `result` |
| --- | --- | --- | --- |
| 1 | 2 | 1 | 1 |
| 4 | 2 | 2 | 1 2 |
| 4 | 3 | 3 | 1 2 3 |
| 4 | 9 | 4 | 1 2 3 4 |
| 7 | 9 | 7 | 1 2 3 4 7 |
| (done) | 9 | leftovers | 1 2 3 4 7 9 |

Every pass of the loop places exactly one element, and the leftovers are copied once. For arrays of length m and n, that's **O(m + n) time**. The result array is O(m + n) space, which is unavoidable when you're building a new array.

`first[i...]` is safe even when `i` has reached `first.count`: a slice starting at the end index is simply empty.

### Why it's correct

The invariant: `result` always holds the smallest `i + j` elements of both arrays, in sorted order, and `first[i]` and `second[j]` are the smallest elements not yet taken from each. The smaller of those two is the smallest of everything remaining, so appending it keeps the invariant true. When the loop ends, the invariant says `result` is the sorted merge of everything taken, and the leftovers are all bigger.

Compare that with `(first + second).sorted()`, which is O((m + n) log(m + n)). For two 50,000-element lists, merging does about 100,000 steps; sorting does well over a million.

## Ties, and keeping the order

When `first[i]` and `second[j]` are equal, the code above takes from `first`, because it uses `<=`. That choice matters when elements carry more than the value they're sorted by:

```swift run
typealias Score = (name: String, points: Int)

func mergeByPoints(_ first: [Score], _ second: [Score]) -> [Score] {
    var result: [Score] = []
    var i = 0
    var j = 0
    while i < first.count && j < second.count {
        if first[i].points <= second[j].points {
            result.append(first[i])
            i += 1
        } else {
            result.append(second[j])
            j += 1
        }
    }
    result.append(contentsOf: first[i...])
    result.append(contentsOf: second[j...])
    return result
}

let monday: [Score] = [("Ana", 10), ("Ben", 30)]
let tuesday: [Score] = [("Cy", 10), ("Di", 20)]
for score in mergeByPoints(monday, tuesday) {
    print(score.name, score.points)
}
```

```output
Ana 10
Cy 10
Di 20
Ben 30
```

Ana and Cy both scored 10. With `<=`, the one from the first list comes first; with `<`, Cy would jump ahead of Ana. Taking from the first array on ties keeps equal elements in their original order, which makes the merge **stable**, the same word you met for in-place filtering. Merge sort is stable precisely because its merge uses `<=`.

## Merging in place when the first array has room

A classic variation: the first array has spare slots at its end, exactly enough for the second array, and you must merge **into** it without creating another array. For example, `first` is `[1, 4, 7, _, _, _]` with 3 real values, and `second` is `[2, 3, 9]`.

Merging from the front fails at once. The second-smallest value is 2, and it belongs in slot 1, where the 4 is still waiting to be placed. Writing the 2 there destroys the 4.

The free space is at the **back**, so merge from the back. Compare the **largest** remaining values, the last unplaced one in each array, and write the bigger one into the last free slot:

| `first[i]` | `second[j]` | write slot | `first` after |
| --- | --- | --- | --- |
| 7 | 9 | 5 | 1 4 7 _ _ 9 |
| 7 | 3 | 4 | 1 4 7 _ 7 9 |
| 4 | 3 | 3 | 1 4 7 4 7 9 |
| 1 | 3 | 2 | 1 4 3 4 7 9 |
| 1 | 2 | 1 | 1 2 3 4 7 9 |
| 1 | (done) | | 1 2 3 4 7 9 |

Old values like the 7 at slot 2 linger for a moment after they've been copied, but they're overwritten before anyone needs the slot. And when `second` runs out, the elements of `first` that haven't moved are already exactly where they belong, so there's nothing left to do. If `first` runs out first, the rest of `second` still needs copying in.

Why can't the writing slot ever overwrite a value of `first` that hasn't been placed? At every moment, the next slot to write is `i + j + 1`, where `i` and `j` are the indices of the last unplaced values. While `second` has values left, `j` is at least 0, so the writing slot is always past `i`. It's the same O(m + n) time, with **O(1) extra space**.

You'll write this one yourself in the practice problem, with three indices: `i`, `j` and `write`.

<Callout kind="gotcha" title="Don't forget the leftovers">
The most common merge bug is ending the loop when either array runs out and forgetting what's left in the other. `merge([5, 6], [1, 2, 3])` would return `[1, 2, 3]` and silently lose the 5 and the 6. Test with one array entirely smaller than the other, and with one empty.
</Callout>

**Merge into the first array** is the in-place version: the first array has spare room at its end, and you must fill it from the back with O(1) extra space.
