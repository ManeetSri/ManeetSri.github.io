## Why it matters

"Remove every X from this array" sounds like a loop of `remove(at:)` calls, and the last lesson showed that's O(n²). There's a far better way: walk the array once with two indices, one **reading** every element and one **writing** each element you keep into its final place. It's how `removeAll(where:)` works inside, and it solves a whole family of problems in O(n) time and O(1) extra space: removing a value, removing duplicates, moving zeroes to the end, and more. M21 builds a whole pattern on it; this lesson gives you the core.

## The read/write pattern

Keep two indices into the same array:

- **`read`** visits every element, once, from left to right.
- **`write`** is where the next element you decide to keep will go.

The rule that makes it work is an **invariant**, a fact that's true after every step: `numbers[0..<write]` holds exactly the elements kept so far, in their original order. Each time `read` finds an element worth keeping, copy it to `write` and move `write` on.

Why is it safe to write into the same array you're reading? Because `write` never gets ahead of `read`. Every slot `write` overwrites has already been read, so nothing you still need is ever destroyed.

Here's the simplest use, removing every copy of one value:

```swift run
func removeAll(_ target: Int, from numbers: inout [Int]) -> Int {
    var write = 0
    for read in 0..<numbers.count where numbers[read] != target {
        numbers[write] = numbers[read]
        write += 1
    }
    return write
}

var values = [3, 1, 3, 3, 2, 3, 4]
let kept = removeAll(3, from: &values)
print(kept, Array(values[..<kept]))
print(values)
```

```output
3 [1, 2, 4]
[1, 2, 4, 3, 2, 3, 4]
```

The function returns the new length, and the first `kept` elements are the answer. Look at the last line: everything after them is leftover junk from before. Many problems are set up exactly this way ("return the new length; what's beyond it doesn't matter"), because it avoids shrinking the array. If you do want the array trimmed, `values.removeLast(values.count - kept)` drops the leftovers.

Each element is read once and written at most once, so this is **O(n)** however many copies of the target there are.

## Removing duplicates from a sorted array

In a sorted array, copies of the same value sit next to each other. So an element is new exactly when it differs from the **last element you kept**, `numbers[write - 1]`. The first element is always kept, so `write` starts at 1:

```visual arrayTrace
program: dedupe
input:
  items: [1, 1, 2, 2, 2, 3, 5, 5]
```

```swift run
func removeDuplicates(_ numbers: inout [Int]) -> Int {
    guard !numbers.isEmpty else { return 0 }
    var write = 1
    for read in 1..<numbers.count where numbers[read] != numbers[write - 1] {
        numbers[write] = numbers[read]
        write += 1
    }
    return write
}

var sorted = [1, 1, 2, 2, 2, 3, 5, 5]
let unique = removeDuplicates(&sorted)
sorted.removeLast(sorted.count - unique)
print(unique, sorted)

var single = [7]
print(removeDuplicates(&single))
var nothing: [Int] = []
print(removeDuplicates(&nothing))
```

```output
4 [1, 2, 3, 5]
1
0
```

The guard isn't decoration. Without it, an empty array would make the loop range `1..<0`, and a range whose start is after its end crashes.

Sorting is what makes this possible in one pass with no extra memory. For an unsorted array, "have I seen this value before?" can't be answered by looking at one neighbour. You'd need a `Set` of values seen so far, which is O(n) extra space, as the ordered-dedupe problem in M07 did.

## Move zeroes to the end

Here's a slightly different task: move every 0 to the end of the array, keeping the other elements in their original order. `[0, 1, 0, 3, 12]` should become `[1, 3, 12, 0, 0]`.

The read/write pattern handles it in two ways.

**Compact, then fill.** Keep the non-zero elements exactly as before, then write zeros into every slot from `write` to the end.

**Swap as you go.** Instead of copying `numbers[read]` to `write`, *swap* them. The kept element moves forward, and whatever was at `write` (always a 0, once the two indices have separated) moves back to `read`:

| `read` | value | action | array after | `write` after |
| --- | --- | --- | --- | --- |
| 0 | 0 | skip | 0 1 0 3 12 | 0 |
| 1 | 1 | swap slots 1 and 0 | 1 0 0 3 12 | 1 |
| 2 | 0 | skip | 1 0 0 3 12 | 1 |
| 3 | 3 | swap slots 3 and 1 | 1 3 0 0 12 | 2 |
| 4 | 12 | swap slots 4 and 2 | 1 3 12 0 0 | 3 |

```swift run
func moveZeroesByFilling(_ numbers: inout [Int]) {
    var write = 0
    for read in 0..<numbers.count where numbers[read] != 0 {
        numbers[write] = numbers[read]
        write += 1
    }
    for index in write..<numbers.count {
        numbers[index] = 0
    }
}

func moveZeroesBySwapping(_ numbers: inout [Int]) {
    var write = 0
    for read in 0..<numbers.count where numbers[read] != 0 {
        numbers.swapAt(read, write)
        write += 1
    }
}

var first = [0, 1, 0, 3, 12]
var second = first
moveZeroesByFilling(&first)
moveZeroesBySwapping(&second)
print(first)
print(second)
```

```output
[1, 3, 12, 0, 0]
[1, 3, 12, 0, 0]
```

Both are O(n) with O(1) extra space. The filling version only works because every zero is identical, so you can write fresh ones. The swapping version never invents a value: every element ends up somewhere in the array. That matters when the elements you're moving aside carry data of their own, like tasks marked "done" that still need to be kept, just at the back.

## Keeping the order: stability

All of these keep the surviving elements in their original order. An algorithm that does that is called **stable**. Stability is why the read/write pattern can't be replaced with "swap each unwanted element with the last one" here: swap-remove from the last lesson is O(1) per removal, but it scrambles the order. When a problem says "keep the relative order", reach for read/write.

<Callout kind="gotcha" title="Swift gotcha: Array(Set(numbers)) loses the order">
It's tempting to remove duplicates with `Array(Set(numbers))`. It does remove them, but a `Set` has no order, so the result comes out in an unpredictable order that can even change between runs. Use the read/write pass for sorted arrays, or a `Set` of seen values plus a result array when the order matters.
</Callout>

<Callout kind="tip">
In everyday Swift, `numbers.removeAll { $0 == 0 }` or `numbers.removeAll(where: isUnwanted)` is the read/write pass, written for you. Interviews usually ask you to write it yourself, often with a twist the built-in can't express, like keeping up to two copies of each value.
</Callout>

## Practice

**Zeroes to the front** turns this lesson's problem around: the zeroes go to the front instead of the back, still keeping the other values in order. The read/write pattern still works, once you choose the right direction to scan. In M21, **Cap the duplicates** takes the duplicate-removal side further, keeping up to a given number of copies of each value.
