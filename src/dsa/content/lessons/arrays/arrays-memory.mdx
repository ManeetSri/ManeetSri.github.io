## Why it matters

You've used arrays since M07, and you've been told that `numbers[i]` is O(1). This lesson shows **why**. An array's elements sit side by side in one block of memory, so the computer can work out where any element lives with one multiplication and one addition. That single fact explains why arrays are the default collection in Swift, why image buffers and audio samples are stored in them, and why a later structure like the linked list (M25) is slower to walk even when its Big-O looks the same.

## Memory is a long row of numbered bytes

Your program's memory behaves like one enormous row of boxes. Each box holds one **byte** (8 bits), and each box has a number, its **address**. An `Int` takes 8 bytes, so it occupies 8 neighbouring boxes, and its address is the number of the first one.

When you create an array, Swift asks for one **contiguous** block: a single unbroken run of bytes, big enough for all the elements. "Contiguous" just means touching, with no gaps between elements and nothing else in the middle. The address of the first byte of that block is the array's **base address**.

<Callout kind="analogy">
Think of a row of numbered lockers in a corridor, each the same width. If locker 0 is at the 100 cm mark and each locker is 8 cm wide, locker 5 starts at 100 + 5 × 8 = 140 cm. You walk straight there. You never need to open lockers 0 to 4 to find it.
</Callout>

## Seeing the gaps between elements

Swift normally hides addresses from you, and for good reason: using them directly is unsafe. But you can peek. `withUnsafeBufferPointer` hands you a view of the array's block, and `baseAddress` is its first address. Don't worry about the details of the unsafe API; it's only here so you can see the layout.

```swift run
let numbers = [10, 20, 30, 40]
numbers.withUnsafeBufferPointer { buffer in
    let base = Int(bitPattern: buffer.baseAddress!)
    for index in 0..<buffer.count {
        let address = Int(bitPattern: buffer.baseAddress! + index)
        print("element \(index) starts \(address - base) bytes after the base")
    }
}
```

```output
element 0 starts 0 bytes after the base
element 1 starts 8 bytes after the base
element 2 starts 16 bytes after the base
element 3 starts 24 bytes after the base
```

The real addresses change every run, so the example prints each one relative to the base. The pattern never changes: each element starts exactly 8 bytes after the previous one, because each `Int` is 8 bytes wide.

## The formula behind O(1) indexing

That pattern gives a formula. For an array whose elements are each `stride` bytes apart:

> **address of element i = base address + i × stride**

When you write `numbers[i]`, the compiled code does exactly that sum, then reads the bytes at the result. One multiplication and one addition, whether the array holds 4 elements or 4 million. That's why indexing is **O(1)**: the cost doesn't depend on n at all.

`stride` is a word you met in [MemoryLayout: size, stride and alignment](/dsa/learn/swift-memory-layout): the distance from the start of one element to the start of the next, including any padding. `MemoryLayout<T>.stride` tells you its value for any type:

```swift run
struct Pixel {
    var red: UInt8
    var green: UInt8
    var blue: UInt8
}

print(MemoryLayout<Int>.stride)
print(MemoryLayout<Double>.stride)
print(MemoryLayout<Bool>.stride)
print(MemoryLayout<Pixel>.stride)
print(MemoryLayout<String>.stride)

let index = 1_000_000
print("element \(index) of an [Int] is \(index * MemoryLayout<Int>.stride) bytes past the base")
```

```output
8
8
1
3
16
element 1000000 of an [Int] is 8000000 bytes past the base
```

A `[Pixel]` packs three bytes per element with no padding, which is how image data is stored. A million-pixel image needs about 3 MB.

### Every element must be the same size

The formula only works because every slot in the array is the same width. That's guaranteed: an array holds a single type, so every element has the same stride.

But a `String` can be 3 characters or 3,000, so how can a `[String]` have a fixed stride of 16 bytes? Because the 16 bytes in each slot are a small, fixed-size **handle**. Short strings fit inside it; a long string's characters live in a separate block elsewhere, and the handle points to them. Classes work the same way: a `[UIView]` holds 8-byte references, and each view object lives somewhere else. Either way, the slots are equal-sized, so indexing stays O(1).

## Why side by side is fast in practice

Big-O counts steps. Real hardware adds a twist that rewards contiguous memory even more.

The processor doesn't fetch memory one byte at a time. It fetches a whole **cache line**, a chunk of 64 or 128 bytes depending on the chip, and keeps recently used lines in the **cache**, a small, very fast memory right next to it. Reading from the cache is many times faster than reading from main memory.

So when you read `numbers[0]`, the processor brings in the bytes around it too, which hold `numbers[1]`, `numbers[2]` and several more. Walking an array in order means most reads find their data already waiting. The processor also notices the steady pattern and starts fetching the next lines before you ask. Code that walks memory in order like this is called **cache-friendly**.

Jumping around breaks both tricks. Here's the same work, adding up ten million `Int`s, done in two orders on a Mac:

```text title="Sample timings: summing 10 million Ints, release build"
in index order 0, 1, 2, …               0.007 s
the same indices, shuffled               0.035 s
```

Both loops are O(n) and do exactly the same additions. The shuffled one is about five times slower purely because of where its reads land in memory. You'll see the same effect with grids in M19, where walking a grid row by row beats walking it column by column.

<Callout kind="note">
This is also why linked lists (M25) are slower than arrays to walk, even though both are O(n). A list's nodes are scattered across memory, so every step to the next node is a jump the cache can't predict.
</Callout>

## What contiguous memory costs

The same layout that makes indexing fast makes some things slow:

- **The block has a fixed size.** Memory right after the array may already belong to something else, so an array can't simply stretch. To grow beyond its block, it has to get a new, bigger block and copy every element across. The next lesson builds exactly that, and [Amortised analysis](/dsa/learn/bigo-amortised) showed why doubling keeps it cheap on average.
- **No gaps allowed.** Inserting or removing in the middle means shifting every later element to keep the run unbroken: O(n). Lesson 3 counts those shifts.

<Callout kind="gotcha" title="Swift gotcha: a slice keeps the original indices">
`numbers[2...]` is an `ArraySlice` that shares the same block of memory, as [ArraySlice and its index pitfalls](/dsa/learn/swift-array-slices) showed. Its first element is at index 2, not 0, because the address formula still uses the original array's base. `slice[0]` crashes.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: out of range still crashes">
The formula would happily compute an address for `numbers[10]` in a 4-element array, and in C, reading it would return whatever bytes happened to be there. Swift checks every index against `count` first and stops the program instead. That check costs a comparison, and it's what keeps a bad index from silently reading someone else's memory.
</Callout>
