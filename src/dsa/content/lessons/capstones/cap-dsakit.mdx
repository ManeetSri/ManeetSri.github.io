## Why it matters

Every structure you built in this course ended up in DSAKit: `Heap`, `Trie`, `Graph`, `UnionFind`, `Deque` and the rest, each with tests. Right now they live inside the course's companion package, next to your exercises. In this project you lift them out into a **package of their own**, with a version number, documentation, tests that run on every push, and a GitHub release that any app can depend on. Swift Package Manager (SwiftPM) is how iOS teams share code between apps, so knowing how a good package is put together, tagged and consumed is everyday iOS work. You also get a public repository you can point to: tested, documented data structures you wrote yourself.

## What you'll build

A public Git repository called `DSAKit` that:

- builds and tests with `swift build` and `swift test` on macOS and Linux;
- documents every public type and method, including its complexity, with DocC;
- runs its tests on every push and pull request with GitHub Actions;
- is released with semantic version tags (`0.1.0`, `0.2.0`, …) and a changelog;
- is used by a small SwiftUI app, added with **File ▸ Add Package Dependencies…**, exactly as you'd add a third-party package.

Budget about two hours. Most of it goes on milestones 2 and 3: deciding what's public and testing it properly.

## The architecture

The new repository holds one library target and one test target. Nothing else from the course package comes along: no exercises, no solutions, no examples.

```text title="DSAKit/ (a new Git repository)"
Package.swift                  one product: the DSAKit library
README.md                      what it is, how to add it, a short example per type
CHANGELOG.md                   what changed in each version
LICENSE                        MIT or Apache 2.0, so others may use it
.github/workflows/ci.yml       build and test on every push
Sources/DSAKit/
  Heap.swift, Trie.swift, Graph.swift, UnionFind.swift, Deque.swift, ...
  Documentation.docc/
    DSAKit.md                  the landing page of the documentation
Tests/DSAKitTests/
  HeapTests.swift, TrieTests.swift, ...
```

How the pieces connect:

```text
 your Mac ──git push──▶ GitHub ──▶ GitHub Actions: swift build, swift test (macOS + Linux)
                          │
                    git tag 0.2.0
                          │
                          ▼
 an app's Package.swift or Xcode project:  .package(url: ".../DSAKit", from: "0.2.0")
                          │
              SwiftPM resolves the newest allowed tag,
              records it in Package.resolved, builds DSAKit
                          │
                          ▼
                 import DSAKit  →  Heap, Trie, Graph, ...
```

The `Package.swift` is short:

```swift title="Package.swift"
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "DSAKit",
    platforms: [.macOS(.v14), .iOS(.v17)],
    products: [
        .library(name: "DSAKit", targets: ["DSAKit"]),
    ],
    targets: [
        .target(name: "DSAKit"),
        .testTarget(name: "DSAKitTests", dependencies: ["DSAKit"]),
    ],
    swiftLanguageModes: [.v5]
)
```

The `platforms` line sets the oldest OS versions the package supports. An app that targets an older iOS than this can't add it, so don't set it higher than your code needs.

## Milestones

### 1. Extract the package

Create the repository with `swift package init --type library --name DSAKit`, then copy in `dsa-swift/Sources/DSAKit/` and `dsa-swift/Tests/DSAKitTests/`, replacing the generated files. Fix whatever doesn't compile. A common surprise: helpers that the course's other targets used, or anything that relied on the course's folder layout.

- **Acceptance:** `swift build` and `swift test` pass in the new repository, with no warnings. The first commit is pushed to GitHub.
- **Exercises:** module boundaries. A library target is a module, and only what's marked `public` crosses the boundary.

### 2. Audit the public API

Open each file and ask of every declaration: should an app see this? Then make the answers consistent.

- **Internal stays internal.** `AVLCore`, the tree that `AVLTree`, `SortedSet` and `SortedMap` share, isn't public, and shouldn't become public. Every public name is a promise you have to keep in every later version.
- **One vocabulary.** `insert`, `remove`, `contains`, `count`, `isEmpty` and `peek()`/`pop()` mean the same thing on every type. If one type says `push` and another `insert`, pick one now: renaming after 1.0.0 is a breaking change.
- **A library doesn't print.** The course's `measure(_:_:)` helper prints timings. Leave it out of the published package, or move it to a separate target.
- **Extensions on standard types are global.** DSAKit adds `quickSort()`, `mergeSorted()` and `lowerBound(of:)` to arrays and collections. Every file in an app that imports DSAKit sees them, and if another package adds a `lowerBound(of:)` too, calls become ambiguous. Keep them, but document them, and consider whether a namespaced function would be kinder.
- **Every public member gets a doc comment** that says what it does, what it returns for edge cases (empty, missing), and its complexity.

When you've been through every file:

- **Acceptance:** every public declaration has a doc comment with a `- Complexity:` line; no type, method or property is public without a reason you could say out loud.
- **Exercises:** access control, and API design as a contract. You'll see in the key code below how removing a name forces a major version.

### 3. Tests you'd trust

DSAKit already has tests. Make them the kind you'd bet a release on:

- **Model-based tests** for every structure with state: thousands of seeded random operations applied to your structure and to a slow, obviously correct model (a sorted array for `Heap` and `SortedSet`, a `Set<String>` for `Trie`, a `[Key: Value]` for `HashMap`), checking they agree after every step.
- **Invariant checks:** a test-only function that walks the structure and verifies its rule, such as the heap property, BST order, AVL balance factors, or that union-find's sizes add up.
- **Edge cases:** empty, one element, growth past the initial capacity, duplicates, removing the last element.

Run `swift test --enable-code-coverage`, and `swift test --show-codecov-path` prints where the coverage report was written. Read it for public methods that no test calls.

- **Acceptance:** every public type has a model-based test; line coverage is above 90%, and you've looked at every uncovered line and decided whether it needs a test.
- **Exercises:** invariants. Each structure's correctness is one rule that must survive every operation.

### 4. Documentation with DocC

DocC turns your `///` comments into browsable documentation, the same format as Apple's. In Xcode, **Product ▸ Build Documentation** works with no setup. To build it from the command line, add the DocC plugin as a dependency of the package:

```swift
dependencies: [
    .package(url: "https://github.com/swiftlang/swift-docc-plugin", from: "1.3.0"),
],
```

Then `swift package generate-documentation --target DSAKit` builds it, and the plugin's `preview-documentation` command serves it locally while you write. Add a `Documentation.docc` folder with a landing page, `DSAKit.md`, that groups the types into topics: linear structures, trees, priority queues, graphs.

A good doc comment for a public method says what happens in the edge cases and what it costs. DocC shows `- Returns:` and `- Complexity:` as labelled sections:

```swift
/// Removes and returns the element that comes first, or `nil` if the heap is empty.
///
/// The last element moves to the top and sifts down, so equal elements
/// come out in no particular order.
///
/// - Returns: The top element, or `nil` when the heap has no elements.
/// - Complexity: O(log n), where n is the number of elements.
@discardableResult
public mutating func pop() -> Element? {
```

A fenced code block inside a doc comment becomes an example in the documentation, and the type-level comments in DSAKit already have one per type. Keep them.

- **Acceptance:** the documentation builds with no warnings about missing or broken symbol links; the landing page lists every public type under a topic.
- **Exercises:** explaining complexity precisely, for an audience who didn't take the course.

### 5. Continuous integration

A workflow file makes GitHub build and test the package on every push and pull request. In outline:

```yaml title=".github/workflows/ci.yml"
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  macos:
    runs-on: macos-15            # pick an image whose Xcode has Swift 6 or later
    steps:
      - uses: actions/checkout@v4
      - run: swift --version
      - run: swift test

  linux:
    runs-on: ubuntu-latest
    container: swift:6.0         # the official Swift Docker image
    steps:
      - uses: actions/checkout@v4
      - run: swift test
```

Runner images and action versions change over time, so check GitHub's documentation for current names when you set it up. Linux matters because it catches accidental dependencies on Apple-only frameworks: anything that imports UIKit, or Foundation APIs that behave differently there. Add the workflow's status badge to the README.

- **Acceptance:** both jobs pass on `main`; a pull request with a deliberately broken test shows a red cross before you merge it.
- **Exercises:** testing as a habit, not an event.

### 6. Version, tag, release, and use it

SwiftPM finds versions through **Git tags**. A tag such as `0.1.0` marks a commit, and SwiftPM reads the tags as semantic versions: MAJOR.MINOR.PATCH.

| Change since the last release | Bump | Example |
| --- | --- | --- |
| Bug fix, same API | PATCH | 1.2.0 → 1.2.1 |
| New API, nothing removed or changed | MINOR | 1.2.1 → 1.3.0 |
| Anything that can break a caller: a removed or renamed method, a changed signature or behaviour | MAJOR | 1.3.0 → 2.0.0 |

Before 1.0.0, the convention is that anything may change, and a breaking change bumps the minor number. Release `0.1.0` first, and promise stability with `1.0.0` once the API has settled.

```bash
git tag 0.1.0
git push origin 0.1.0
gh release create 0.1.0 --generate-notes      # optional: a GitHub release with notes
```

SwiftPM can also check a release for you: `swift package diagnose-api-breaking-changes 0.1.0` compares the public API of your working copy with the API at that tag, and lists anything removed or changed.

Then use it. Create a SwiftUI app in Xcode, choose **File ▸ Add Package Dependencies…**, paste the repository URL, and pick "Up to Next Major Version". In a package instead of an app, the same thing is one line:

```swift
.package(url: "https://github.com/<you>/DSAKit", from: "0.1.0"),
```

A view that uses it:

```swift title="TaskQueueView.swift"
import SwiftUI
import DSAKit

struct TaskQueueView: View {
    @State private var tasks = Heap<(priority: Int, title: String)>(areInIncreasingOrder: { $0.priority < $1.priority })
    @State private var done: [String] = []

    var body: some View {
        NavigationStack {
            List {
                Section("Next up") {
                    Text(tasks.peek()?.title ?? "Nothing left")
                }
                Section("Done") {
                    ForEach(done, id: \.self) { Text($0) }
                }
            }
            .toolbar {
                Button("Do next") {
                    if let task = tasks.pop() { done.append(task.title) }
                }
            }
        }
        .onAppear {
            tasks.insert((2, "Write the README"))
            tasks.insert((1, "Tag 0.1.0"))
            tasks.insert((3, "Submit to the Swift Package Index"))
        }
    }
}
```

While you're developing the package alongside the app, drag the package's folder into the Xcode project: a local copy overrides the remote one, so you can edit both at once.

- **Acceptance:** `0.1.0` is tagged and released; a fresh app resolves it from GitHub and runs; `Package.resolved` in the app records the exact version.
- **Exercises:** semantic versioning, which the next section turns into code.

## Key code: semantic versions

Version resolution is a small algorithm. When an app asks for `from: "1.2.0"`, SwiftPM lists the repository's tags, parses the ones that are valid versions, keeps those the requirement allows, and picks the **newest**. "Newest" means comparing versions number by number, not as text. Deciding your own next version is a set comparison: if any public name disappeared, it's a major release.

```swift run
/// A semantic version: MAJOR.MINOR.PATCH, compared number by number
struct Version: Comparable, CustomStringConvertible {
    let major: Int
    let minor: Int
    let patch: Int

    init(_ major: Int, _ minor: Int, _ patch: Int) {
        (self.major, self.minor, self.patch) = (major, minor, patch)
    }

    /// Parses "1.4.2" or "v1.4.2". Anything else, such as "beta" or "1.4", gives nil.
    init?(_ tag: String) {
        let text = tag.hasPrefix("v") ? tag.dropFirst() : Substring(tag)
        let parts = text.split(separator: ".", omittingEmptySubsequences: false)
        guard parts.count == 3, parts.allSatisfy({ !$0.isEmpty && $0.allSatisfy { $0 >= "0" && $0 <= "9" } }) else {
            return nil
        }
        self.init(Int(parts[0])!, Int(parts[1])!, Int(parts[2])!)
    }

    static func < (a: Version, b: Version) -> Bool {
        (a.major, a.minor, a.patch) < (b.major, b.minor, b.patch)
    }

    var description: String { "\(major).\(minor).\(patch)" }
}

/// The three kinds of release, and the version each one leads to
enum Change {
    case fix, addition, breaking

    /// Compares the public API before and after: removing anything breaks callers
    init(oldAPI: Set<String>, newAPI: Set<String>) {
        if !oldAPI.isSubset(of: newAPI) {
            self = .breaking
        } else if newAPI.count > oldAPI.count {
            self = .addition
        } else {
            self = .fix
        }
    }

    func next(after v: Version) -> Version {
        switch self {
        case .breaking: return Version(v.major + 1, 0, 0)
        case .addition: return Version(v.major, v.minor + 1, 0)
        case .fix: return Version(v.major, v.minor, v.patch + 1)
        }
    }
}

/// What SwiftPM's `from:` and `.upToNextMinor(from:)` accept
enum Requirement {
    case upToNextMajor(from: Version)
    case upToNextMinor(from: Version)

    func allows(_ v: Version) -> Bool {
        switch self {
        case .upToNextMajor(let low): return v >= low && v < Version(low.major + 1, 0, 0)
        case .upToNextMinor(let low): return v >= low && v < Version(low.major, low.minor + 1, 0)
        }
    }
}

/// The newest tag the requirement allows, as the package resolver picks it
func resolve(_ requirement: Requirement, tags: [String]) -> Version? {
    tags.compactMap(Version.init).filter(requirement.allows).max()
}

let tags = ["0.9.0", "0.10.0", "1.0.0", "1.2.0", "1.10.0", "1.9.3", "v1.10.1", "2.0.0", "nightly"]
print("as strings: ", tags.sorted().joined(separator: " "))
print("as versions:", tags.compactMap(Version.init).sorted().map(\.description).joined(separator: " "))

print(resolve(.upToNextMajor(from: Version(1, 2, 0)), tags: tags)!)
print(resolve(.upToNextMinor(from: Version(1, 9, 0)), tags: tags)!)
print(resolve(.upToNextMajor(from: Version(0, 9, 0)), tags: tags)!)

let v1: Set = ["Heap.insert", "Heap.pop", "Heap.peek", "Trie.insert"]
let fixed: Set = ["Heap.insert", "Heap.pop", "Heap.peek", "Trie.insert"]
let grown: Set = ["Heap.insert", "Heap.pop", "Heap.peek", "Heap.replaceTop", "Trie.insert"]
let renamed: Set = ["Heap.insert", "Heap.pop", "Heap.top", "Heap.replaceTop", "Trie.insert"]

let current = Version(1, 2, 0)
for (label, api) in [("fixed a bug", fixed), ("added replaceTop", grown), ("renamed peek to top", renamed)] {
    let change = Change(oldAPI: v1, newAPI: api)
    print("\(label): \(change) -> \(change.next(after: current))")
}
print("the rename removed", v1.subtracting(renamed).sorted())
```

```output
as strings:  0.10.0 0.9.0 1.0.0 1.10.0 1.2.0 1.9.3 2.0.0 nightly v1.10.1
as versions: 0.9.0 0.10.0 1.0.0 1.2.0 1.9.3 1.10.0 1.10.1 2.0.0
1.10.1
1.9.3
0.10.0
fixed a bug: fix -> 1.2.1
added replaceTop: addition -> 1.3.0
renamed peek to top: breaking -> 2.0.0
the rename removed ["Heap.peek"]
```

What to notice:

- **Text order is wrong.** As strings, `"1.10.0"` sorts before `"1.2.0"`, because the character `1` comes before `2`. Comparing tuples of numbers, `(1, 10, 0) > (1, 2, 0)`, gets it right. The invalid tag `nightly` is ignored, and `v1.10.1` counts as 1.10.1.
- **`from: "1.2.0"` picked 1.10.1**, the newest 1.x, and never 2.0.0. That's the deal semantic versioning offers: an app gets your fixes and additions automatically, but never a breaking release it didn't ask for.
- **`from: "0.9.0"` picked 0.10.0.** SwiftPM's `from:` means "up to the next major version", even before 1.0.0, so a pre-1.0 dependency can pull in a minor release that, by the pre-1.0 convention, may break things. Depend on pre-1.0 packages with `.upToNextMinor(from:)`.
- **Renaming is removing.** To callers, `peek` disappearing is a breaking change, even though `top` does the same job. The kind way to rename is to add `top`, mark `peek` as `@available(*, deprecated, renamed: "top")` in a minor release, and remove it only in the next major one.

## Tests to write

Beyond the existing DSAKit tests, add a model-based test for each stateful type. Here's the shape for `Heap`, with a seeded generator like the one in [Fisher–Yates and shuffle()](/dsa/learn/rand-shuffle), so a failure reproduces every time:

```swift title="Tests/DSAKitTests/HeapModelTests.swift"
import Testing
import DSAKit

@Suite struct HeapModelTests {
    @Test("Heap agrees with a sorted array", arguments: [1, 2, 3, 42] as [UInt64])
    func matchesModel(seed: UInt64) {
        var random = SeededGenerator(seed: seed)          // defined in the test target
        var heap = Heap<Int>()
        var model: [Int] = []
        for _ in 0..<5_000 {
            if model.isEmpty || Int.random(in: 0..<10, using: &random) < 6 {
                let value = Int.random(in: -50...50, using: &random)
                heap.insert(value)
                model.append(value)
            } else {
                model.sort()
                #expect(heap.pop() == model.removeFirst())
            }
            #expect(heap.count == model.count)
            #expect(heap.peek() == model.min())
        }
    }
}
```

Notice that the test imports `DSAKit` without `@testable`. Tests that use only the public API are tests of what apps will actually see. Keep `@testable import DSAKit` for invariant checks that need internal details, and put those in a separate file.

Other tests worth writing:

- `Trie` against a `Set<String>`: after every insert or remove, `contains`, `count` and `words(withPrefix:)` match a filter over the set.
- `UnionFind` against a naive model that relabels a whole group on each union.
- `Graph`: adding the same edge twice, removing a vertex's last edge, `inDegree` on directed graphs.
- **A documentation test:** copy each doc comment's example into a test, so the examples in your documentation can't go stale.

## Stretch goals

- **Swift 6 language mode.** Remove `swiftLanguageModes: [.v5]` and fix what the compiler reports. Add conditional conformances such as `extension Deque: Sendable where Element: Sendable {}`. The types that store a comparison closure, like `Heap`, need thought: a stored closure isn't `Sendable` unless it's `@Sendable`.
- **Benchmarks across the module boundary.** Time `Heap` from the app in a release build, as in [Benchmarking properly](/dsa/learn/fs-benchmarking). Generic code called from another module may not be specialised for your element type; measure before reaching for `@inlinable`, which makes a function's body part of what clients compile against.
- **The Swift Package Index.** Submit the repository to swiftpackageindex.com. It builds your package against several Swift versions and platforms, shows a compatibility matrix, and can host your DocC documentation.
- **A release checklist** in the README, and a second workflow that runs `diagnose-api-breaking-changes` against the latest tag on every pull request.
