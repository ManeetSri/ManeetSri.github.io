## Why it matters

The step-through diagrams in this console are the fastest way to *see* an algorithm: bars swapping, a frontier spreading across a grid. In this project you build your own, as a SwiftUI app for iPhone and iPad: pick a sort or a pathfinding algorithm, press play, and watch it work, with a scrubber to go back and forth. Under the hood it uses the same architecture as the console's visualisers: **algorithms produce frames, and a view renders them**. That split, a pure model that knows nothing about the screen and a view that only draws state, is the core of every well-built SwiftUI app. You'll also reuse half the course: five sorts, BFS, Dijkstra, A\* and a heap.

## What you'll build

An app with two screens:

- **Sorting.** An array of bars. Choose bubble, selection, insertion, merge, quick or heap sort, and a starting order: random (seeded), sorted, reversed or nearly sorted. Play, pause, step, scrub, change the speed. Counters show comparisons and swaps so far.
- **Pathfinding.** A grid you can draw walls and "mud" on, with a start and a goal. Choose BFS, Dijkstra or A\* and watch cells being explored, then the shortest path drawn. A counter shows how many cells each algorithm expanded.

Budget about three hours: one for the frame model and the sorting screen, one for the grid, one for the weighted searches and polish.

## The architecture

Three layers, and data flows one way:

```text
 ┌────────────────────┐   [Frame]   ┌─────────────────────┐  current frame  ┌────────────────────┐
 │ Algorithms         │ ──────────▶ │ Player              │ ──────────────▶ │ Views              │
 │ pure Swift, tested │             │ frames, index,      │                 │ BarsView, GridView │
 │ insertionSort(...) │             │ step, back, seek    │ ◀── controls ── │ PlaybackControls   │
 └────────────────────┘             └─────────────────────┘                 └────────────────────┘
```

- **Algorithms** take an input and return an array of frames. A frame is a snapshot: for sorting, the array plus which indexes are active and a caption; for grids, the distances found so far and, at the end, the path. Algorithms never import SwiftUI.
- **The player** holds the frames and an index. Play, pause, step and scrub only change the index. It's generic, so the same player drives both screens.
- **Views** draw `player.current` and send button presses back. They never run an algorithm step themselves.

Recording every frame up front, rather than running the algorithm live, buys three things: scrubbing backwards is free, the algorithm code stays an ordinary function you can test, and the animation speed has nothing to do with how fast the algorithm runs. JavaScript, which the console's visualisers use, has generator functions that `yield` frames one at a time; Swift doesn't, and an array of frames is the simplest Swift equivalent.

Put the first two layers in a local Swift package, so `swift test` checks them in seconds without a simulator:

## Milestones

### 1. Frames for one sort

Write `insertionSortFrames(_:)` as in the key code below: the plain algorithm, with a frame appended at each comparison and each swap.

- **Acceptance:** tests show that the last frame is sorted, that every frame holds a permutation of the input, and that the frame count is 2 plus the number of comparisons plus the number of swaps.
- **Exercises:** instrumenting an algorithm without changing what it does. If adding frames changes the result, the instrumentation is wrong.

### 2. The player and the bars

Wrap the player in an observable model, draw the bars, and add the controls: play/pause, step back, step forward, a scrubber, and a speed slider. Show the frame's caption under the bars.

- **Acceptance:** playing runs to the end and stops; scrubbing to any frame shows exactly that frame; the controls disable themselves at the ends.
- **Exercises:** keeping the model and the view apart. The view is a function of the current frame.

### 3. Five more sorts

Add bubble, selection, merge (bottom-up is easiest to animate), quick (Lomuto, so the pivot is easy to colour) and heap sort, behind an `enum SortAlgorithm: CaseIterable`. Count comparisons and swaps (or writes, for merge sort) in each frame. Generate inputs with a seeded generator: random, sorted, reversed and nearly sorted.

- **Acceptance:** all six pass the same tests; on 30 values, the counters show insertion sort winning on nearly sorted input and losing badly on reversed input, and merge and heap sort barely caring.
- **Exercises:** complexity you can see. O(n²) against O(n log n), adaptive sorts, and why quick sort hates sorted input with a last-element pivot.

### 4. The grid and BFS

Draw a grid with `Canvas`. Let a drag toggle walls, and long-press to move the start or the goal. Record a BFS frame per distance layer, with the distances so far, and a last frame with the path traced back through `previous`.

- **Acceptance:** the path length equals the goal's BFS distance; with the goal walled off, the last frame says "no path" instead of crashing.
- **Exercises:** BFS layers are shortest paths when every step costs the same.

### 5. Dijkstra and A\*

Add a "mud" brush: a mud cell costs 5 to enter instead of 1. Record a frame per cell popped from the heap. Implement Dijkstra with a heap, then A\* with the Manhattan distance as the heuristic, and show both counters side by side.

- **Acceptance:** Dijkstra and A\* always report the same path cost; on open grids A\* expands visibly fewer cells; BFS, which ignores costs, happily walks through mud, so on a grid with mud in the way its path costs more.
- **Exercises:** priority queues, and admissible heuristics. Manhattan distance never overestimates here, because every step costs at least 1.

### 6. Polish

A seed field, so an interesting run can be reproduced exactly. VoiceOver reads the caption of the current frame. When Reduce Motion is on, frames change without animation. On iPad, show the two screens side by side.

- **Acceptance:** the same seed gives the same frames on every launch; the app is usable with VoiceOver.
- **Exercises:** reproducibility, the reason every random choice in the course goes through a seeded generator.

## Key code: frames and a player

Here's the whole model in miniature: insertion sort and BFS each return frames, and one generic `Player` steps through either. The text rendering stands in for the SwiftUI views.

```swift run
// A frame is one picture of the algorithm. Algorithms record frames; a player steps through them.
struct SortFrame {
    let values: [Int]
    let active: [Int]          // the indexes being compared or swapped
    let note: String
}

struct GridFrame {
    let distance: [[Int?]]     // nil: not reached yet
    let path: [Point]          // filled in on the last frame only
    let note: String
}

struct Point: Hashable {
    let row: Int
    let col: Int
}

/// Insertion sort, recording a frame for every comparison and every swap
func insertionSortFrames(_ input: [Int]) -> [SortFrame] {
    var items = input
    var frames = [SortFrame(values: items, active: [], note: "start")]
    for i in 1..<items.count {
        var j = i
        while j > 0 {
            frames.append(SortFrame(values: items, active: [j - 1, j], note: "compare"))
            guard items[j - 1] > items[j] else { break }
            items.swapAt(j - 1, j)
            frames.append(SortFrame(values: items, active: [j - 1, j], note: "swap"))
            j -= 1
        }
    }
    frames.append(SortFrame(values: items, active: [], note: "sorted"))
    return frames
}

/// BFS from S to G, recording a frame each time a whole distance layer is finished
func bfsFrames(_ rows: [String]) -> [GridFrame] {
    let grid = rows.map { Array($0) }
    var start = Point(row: 0, col: 0), goal = start
    for (r, line) in grid.enumerated() {
        for (c, cell) in line.enumerated() {
            if cell == "S" { start = Point(row: r, col: c) }
            if cell == "G" { goal = Point(row: r, col: c) }
        }
    }
    var distance: [[Int?]] = grid.map { $0.map { _ in nil } }
    var previous: [Point: Point] = [:]
    distance[start.row][start.col] = 0
    var frames = [GridFrame(distance: distance, path: [], note: "start")]
    var layer = [start]
    while !layer.isEmpty && distance[goal.row][goal.col] == nil {
        var next: [Point] = []
        for point in layer {
            for (dr, dc) in [(-1, 0), (0, 1), (1, 0), (0, -1)] {
                let r = point.row + dr, c = point.col + dc
                guard grid.indices.contains(r), grid[r].indices.contains(c),
                      grid[r][c] != "#", distance[r][c] == nil else { continue }
                distance[r][c] = distance[point.row][point.col]! + 1
                previous[Point(row: r, col: c)] = point
                next.append(Point(row: r, col: c))
            }
        }
        layer = next
        frames.append(GridFrame(distance: distance, path: [], note: "layer \(frames.count)"))
    }
    var path: [Point] = []
    var step: Point? = distance[goal.row][goal.col] == nil ? nil : goal
    while let point = step {
        path.append(point)
        step = previous[point]
    }
    frames.append(GridFrame(distance: distance, path: path.reversed(), note: "path"))
    return frames
}

/// Knows nothing about sorting or grids: it only moves through an array of frames
struct Player<Frame> {
    let frames: [Frame]
    private(set) var index = 0

    init(_ frames: [Frame]) {
        self.frames = frames
    }

    var current: Frame { frames[index] }
    var isAtEnd: Bool { index == frames.count - 1 }

    mutating func step() { index = min(index + 1, frames.count - 1) }
    mutating func back() { index = max(index - 1, 0) }
    mutating func seek(to position: Int) { index = min(max(position, 0), frames.count - 1) }
}

func render(_ frame: SortFrame) -> String {
    let bars = frame.values.indices.map { i in
        frame.active.contains(i) ? "(\(frame.values[i]))" : " \(frame.values[i]) "
    }
    return bars.joined() + "  " + frame.note
}

func render(_ frame: GridFrame, walls rows: [String]) -> [String] {
    let onPath = Set(frame.path)
    return rows.enumerated().map { r, line in
        String(line.enumerated().map { c, cell -> Character in
            if cell == "#" || cell == "S" || cell == "G" { return cell }
            if onPath.contains(Point(row: r, col: c)) { return "*" }
            if let d = frame.distance[r][c] { return Character(String(d % 10)) }
            return "."
        })
    }
}

var sorting = Player(insertionSortFrames([4, 2, 3, 1]))
print("\(sorting.frames.count) frames")
while true {
    let label = String(sorting.index)
    print(label + String(repeating: " ", count: 3 - label.count) + render(sorting.current))
    if sorting.isAtEnd { break }
    sorting.step()
}

let maze = [
    "S..#.",
    ".#...",
    ".#.#.",
    "...#G",
]
var search = Player(bfsFrames(maze))
print("\(search.frames.count) frames")
search.seek(to: 3)
print(search.current.note)
render(search.current, walls: maze).forEach { print($0) }
search.seek(to: search.frames.count - 1)
print(search.current.note, search.current.path.count - 1, "steps")
render(search.current, walls: maze).forEach { print($0) }
search.back()
print("back to", search.current.note)
```

What to notice:

- **The algorithms are ordinary functions.** `insertionSortFrames` is insertion sort with two `append` calls added. Delete them and the sort still works.
- **The player doesn't know what a frame is.** `Player<SortFrame>` and `Player<GridFrame>` are the same code. Going back is `index - 1`, because every frame already exists.
- **BFS records a frame per layer, not per cell**, so the animation shows the frontier advancing one step at a time. Seeking to frame 3 shows every cell within three steps of S. Recording per cell would be equally easy; choose whichever teaches better.
- **13 frames for 4 values.** Snapshots cost memory: a frame per comparison and swap of bubble sort on 100 values is about 7,400 frames of 100 numbers, roughly 6 MB. On 1,000 values it would be several gigabytes, so cap the array size, or store only what changed (see the stretch goals).

## The SwiftUI layer

The player becomes an observable model. Playback is a `.task(id:)` loop: SwiftUI starts it when `isPlaying` changes, and cancels it when it changes again or the view disappears.

```swift title="PlayerModel.swift"
import Observation
import VisualiserCore

@MainActor @Observable
final class PlayerModel<Frame> {
    var player: Player<Frame>
    var isPlaying = false
    var framesPerSecond = 8.0

    init(frames: [Frame]) {
        player = Player(frames)
    }

    func load(_ frames: [Frame]) {
        isPlaying = false
        player = Player(frames)
    }
}
```

```swift title="SortingScreen.swift"
import SwiftUI
import VisualiserCore

struct SortingScreen: View {
    @State private var algorithm = SortAlgorithm.insertion
    @State private var model = PlayerModel(frames: SortAlgorithm.insertion.frames(for: [5, 2, 8, 1, 9, 3]))

    var body: some View {
        VStack(spacing: 16) {
            Picker("Algorithm", selection: $algorithm) {
                ForEach(SortAlgorithm.allCases, id: \.self) { Text($0.name) }
            }
            .pickerStyle(.segmented)

            BarsView(frame: model.player.current)
            Text(model.player.current.note).font(.callout.monospaced())
            PlaybackControls(model: model)
        }
        .padding()
        .onChange(of: algorithm) {
            model.load(algorithm.frames(for: model.player.frames[0].values))
        }
        .task(id: model.isPlaying) {
            guard model.isPlaying else { return }
            while !model.player.isAtEnd {
                do {
                    try await Task.sleep(for: .seconds(1 / model.framesPerSecond))
                } catch {
                    return                                  // cancelled: paused or left the screen
                }
                model.player.step()
            }
            model.isPlaying = false
        }
    }
}
```

```swift title="BarsView.swift"
struct BarsView: View {
    let frame: SortFrame

    var body: some View {
        GeometryReader { proxy in
            let tallest = CGFloat(max(frame.values.max() ?? 1, 1))
            HStack(alignment: .bottom, spacing: 2) {
                ForEach(frame.values.indices, id: \.self) { index in
                    RoundedRectangle(cornerRadius: 3)
                        .fill(frame.active.contains(index) ? Color.orange : Color.accentColor)
                        .frame(height: proxy.size.height * CGFloat(frame.values[index]) / tallest)
                }
            }
        }
        .accessibilityElement()
        .accessibilityLabel(frame.note)
    }
}
```

The grid draws itself with `Canvas`, which is much faster than hundreds of separate views, and turns drags into cell edits:

```swift title="GridView.swift"
struct GridView: View {
    let frame: GridFrame
    let onPaint: (Point) -> Void

    var body: some View {
        GeometryReader { proxy in
            let rows = frame.walls.count, columns = frame.walls[0].count
            let side = min(proxy.size.width / CGFloat(columns), proxy.size.height / CGFloat(rows))
            Canvas { context, _ in
                for row in 0..<rows {
                    for column in 0..<columns {
                        let cell = CGRect(x: CGFloat(column) * side, y: CGFloat(row) * side,
                                          width: side - 1, height: side - 1)
                        context.fill(Path(cell), with: .color(colour(row, column)))
                    }
                }
            }
            .gesture(DragGesture(minimumDistance: 0).onChanged { drag in
                let point = Point(row: Int(drag.location.y / side), col: Int(drag.location.x / side))
                if (0..<rows).contains(point.row), (0..<columns).contains(point.col) { onPaint(point) }
            })
        }
    }

    private func colour(_ row: Int, _ column: Int) -> Color {
        if frame.walls[row][column] { return .primary }
        if frame.path.contains(Point(row: row, col: column)) { return .yellow }
        if frame.distance[row][column] != nil { return .teal.opacity(0.5) }
        return frame.cost[row][column] > 1 ? .brown.opacity(0.4) : .secondary.opacity(0.15)
    }
}
```

Here `GridFrame` has grown `walls` and `cost` arrays, so a frame carries everything needed to draw it. When the user paints, the screen re-runs the chosen algorithm on the new grid and loads the new frames into the player.

## Tests to write

```swift title="Tests/VisualiserCoreTests/SortFrameTests.swift"
import Testing
@testable import VisualiserCore

@Suite struct SortFrameTests {
    @Test("Every sort ends sorted and only ever rearranges", arguments: SortAlgorithm.allCases)
    func endsSorted(algorithm: SortAlgorithm) {
        var random = SeededGenerator(seed: 7)
        let input = (0..<30).map { _ in Int.random(in: 1...50, using: &random) }
        let frames = algorithm.frames(for: input)
        #expect(frames.first?.values == input)
        #expect(frames.last?.values == input.sorted())
        for frame in frames {
            #expect(frame.values.sorted() == input.sorted())
        }
    }

    @Test("Insertion sort makes n - 1 comparisons on sorted input")
    func insertionIsAdaptive() {
        let frames = SortAlgorithm.insertion.frames(for: Array(1...20))
        #expect(frames.last?.comparisons == 19)
        #expect(frames.last?.swaps == 0)
    }
}
```

More worth writing:

- **A\* agrees with Dijkstra** on 200 seeded random grids with walls and mud: same cost every time, and A\* never expands more cells.
- **BFS path checks:** consecutive cells on the path are neighbours, none is a wall, and the length equals the goal's distance.
- **Player bounds:** `back()` at frame 0 and `step()` at the end leave the index unchanged; `seek(to: -5)` clamps to 0.
- **Single and empty inputs:** a one-value array gives two frames (start and sorted); a grid where start equals goal gives a path of length 0.

## Stretch goals

- **Bars that move.** Bars are drawn by index, so a swap animates as two bars changing height. Give each value an identity (`struct Bar: Identifiable { let id: Int; let value: Int }`) and use it in `ForEach`; SwiftUI then animates swaps as bars sliding past each other.
- **Store changes, not snapshots.** Record only what each step changed (a swap of i and j, or a cell's new distance), and rebuild any frame by replaying from the nearest stored snapshot. Memory drops from O(frames × n) to O(frames), and scrubbing stays fast with a snapshot every few hundred steps.
- **Lazy frames for huge inputs.** Write an algorithm as an `IteratorProtocol` state machine that produces the next frame on demand, so a 10,000-value sort can play without recording everything first.
- **More algorithms:** shell sort, counting sort, radix sort; bidirectional BFS; the maze generators from [A maze generator and solver](/dsa/learn/cap-maze).
- **Sound.** Play a short tone whose pitch follows the value being compared. It's surprisingly good at revealing the patterns of each sort.
