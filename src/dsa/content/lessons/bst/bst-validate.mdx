## Why it matters

Every BST algorithm in this module trusts the BST property. If one node is out of place, a search walks confidently down the wrong side and reports "not found" for a value that's right there. So "is this tree really a BST?" is a question worth answering well: in tests for your own tree code, when loading a tree from a file or a server, and in interviews, where it's one of the most asked tree problems of all. It's also the cleanest example of a pattern you'll use again: **passing information down** a recursion, not only returning it up.

## The tempting wrong answer

The obvious check compares each node with its children: left child smaller, right child bigger, recursively. It's wrong, for the reason you saw in [The BST property, search and insert](/dsa/learn/bst-property-search-insert): the rule is about whole subtrees.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

// Wrong: only compares each node with its own children
func childrenLookFine(_ node: TreeNode?) -> Bool {
    guard let node else { return true }
    if let left = node.left, left.value >= node.value { return false }
    if let right = node.right, right.value <= node.value { return false }
    return childrenLookFine(node.left) && childrenLookFine(node.right)
}

//      10
//     /  \
//    5    15
//        /  \
//       6    20
let tricky = TreeNode(10, left: TreeNode(5), right: TreeNode(15, left: TreeNode(6), right: TreeNode(20)))
print(childrenLookFine(tricky))
```

```output
true
```

It says `true`, but 6 is in the right subtree of 10 and smaller than 10. The check never compares 6 with 10, because 10 isn't 6's parent.

## Every node has a range

Think about what a node is **allowed** to hold. The root can hold anything. Its left child must be less than the root. That child's right child must be less than the root **and** greater than the child. Each step down narrows the range from one side:

- going **left** from a node with value v: everything below must be **less than v**, so v becomes the new upper bound;
- going **right**: everything below must be **greater than v**, so v becomes the new lower bound.

The other bound is inherited unchanged. In the tricky tree, 15's range is "greater than 10", and 6, as 15's left child, gets "greater than 10 and less than 15". 6 fails.

So pass the range down. Each call checks one node against its two bounds, then hands narrower bounds to its children:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

// low and high are exclusive bounds; nil means "no limit on this side"
func isValid(_ node: TreeNode?, low: Int? = nil, high: Int? = nil) -> Bool {
    guard let node else { return true }
    if let low, node.value <= low { return false }
    if let high, node.value >= high { return false }
    return isValid(node.left, low: low, high: node.value)
        && isValid(node.right, low: node.value, high: high)
}

let tricky = TreeNode(10, left: TreeNode(5), right: TreeNode(15, left: TreeNode(6), right: TreeNode(20)))
let good = TreeNode(10, left: TreeNode(5), right: TreeNode(15, left: TreeNode(12), right: TreeNode(20)))
let repeated = TreeNode(10, left: TreeNode(5, right: TreeNode(10)))
let extremes = TreeNode(0, left: TreeNode(Int.min), right: TreeNode(Int.max))
print(isValid(tricky), isValid(good), isValid(repeated), isValid(extremes), isValid(nil))
```

```output
false true false true true
```

What to notice:

- `repeated` is invalid: the second 10 is in the first 10's left subtree, and the comparisons are strict (`<=` and `>=` reject equal values). That matches this module's policy that a BST holds each value once.
- The empty tree is valid. So is every subtree of a valid tree, which is why the recursion works.
- `&&` short-circuits: once the left side fails, the right side isn't even checked.
- Every node is visited once: **O(n)** time, and O(h) stack for the recursion.

## Why the bounds are optional

Many solutions you'll see online start the bounds at `Int.min` and `Int.max`, meaning "no limit". It looks harmless, and it's a bug: those are real values a tree can hold.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

// Buggy: uses real Int values to mean "no limit"
func isValidSentinel(_ node: TreeNode?, low: Int = Int.min, high: Int = Int.max) -> Bool {
    guard let node else { return true }
    if node.value <= low || node.value >= high { return false }
    return isValidSentinel(node.left, low: low, high: node.value)
        && isValidSentinel(node.right, low: node.value, high: high)
}

print(isValidSentinel(TreeNode(5)))
print(isValidSentinel(TreeNode(Int.min)))
print(isValidSentinel(TreeNode(0, right: TreeNode(Int.max))))
```

```output
true
false
false
```

A single node holding `Int.min` is obviously a valid BST, but `Int.min <= Int.min` rejects it. `nil` means "no bound" and can't be confused with any value, which is exactly what an optional is for ([Why nil exists](/dsa/learn/swift-why-nil)). In languages whose node values are 32-bit, people make room by widening the bounds to 64 bits. Swift's `Int` is already 64-bit, so there's nothing wider to switch to, and optional bounds work for any `Comparable` type anyway.

## The inorder way

There's a second, quite different check. An inorder walk of a BST visits values in increasing order, and only a BST does that: if some node broke the rule, it would appear out of order in the walk. So:

> A binary tree is a BST exactly when its inorder traversal is **strictly increasing**.

Walk inorder, remember the previous value, and fail the moment a value isn't bigger than the previous one. The iterative walk from [Iterative traversals with a stack](/dsa/learn/trav-dfs-iterative) makes the early exit easy:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func isValidInorder(_ root: TreeNode?) -> Bool {
    var stack: [TreeNode] = []
    var current = root
    var previous: Int? = nil                       // optional again: no fake starting value
    while current != nil || !stack.isEmpty {
        while let node = current {
            stack.append(node)
            current = node.left
        }
        let node = stack.removeLast()
        print("visit \(node.value)")
        if let previous, node.value <= previous {
            return false
        }
        previous = node.value
        current = node.right
    }
    return true
}

let tricky = TreeNode(10, left: TreeNode(5), right: TreeNode(15, left: TreeNode(6), right: TreeNode(20)))
print(isValidInorder(tricky))
```

```output
visit 5
visit 10
visit 6
false
```

The walk visits 5, 10, then 6: a drop, so it stops without visiting 15 or 20.

| | Bounds passed down | Inorder strictly increasing |
| --- | --- | --- |
| Idea | each node lies in the range its ancestors allow | the sorted-order view of a BST |
| Time | O(n) | O(n) |
| Space | O(h) | O(h) |
| Finds the first problem | in the order nodes are visited | at the first drop in sorted order |

Both are correct, and interviewers accept either. The bounds version teaches the more reusable idea; the inorder version leads straight into [Recover, trim and greater-sum trees](/dsa/learn/bst-recover-trim), where the drops say which nodes were swapped.

<Callout kind="gotcha" title="Three ways to get it wrong">
**Children only.** Comparing each node with its children misses grandchildren and beyond, as the tricky tree shows.

**Sentinel bounds.** `Int.min` and `Int.max` as "no limit" reject trees that really hold those values. Use `Int?`.

**`<` instead of `<=`.** `if node.value < low` lets a node equal to its bound through, so a repeated value passes. Decide your duplicates policy and match the comparisons to it.
</Callout>

**Validate a binary search tree** includes trees that only break the rule several levels down, trees holding `Int.min` and `Int.max`, and trees with repeated values. Write the bounds version first. Then write the inorder version and check that both agree on the examples.
