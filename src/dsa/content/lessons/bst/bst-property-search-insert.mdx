## Why it matters

A sorted array finds any value in O(log n) with binary search, but inserting a value means shifting everything after it: O(n). A linked list inserts in O(1) once you're in the right place, but finding that place is O(n). A **binary search tree** (BST) gets the best of both: when it's in good shape, finding, inserting and deleting all take O(log n), and the values are always available in sorted order. Ordered maps in other languages (C++'s `std::map`, Java's `TreeMap`) are balanced BSTs, database indexes are their wide cousins, and an app that keeps calendar events sorted by start time while they're added and removed is doing BST work. Swift's standard library has no sorted set, so in this module you'll build one.

## The BST property

A binary search tree is a binary tree (from [Tree terminology](/dsa/learn/tree-terminology)) with one rule, which must hold at **every** node:

- every value in the node's **left subtree** is smaller than the node's value;
- every value in the node's **right subtree** is bigger.

Here's one:

```text
             50
          /      \
        30        70
       /  \      /  \
     20    40  60    80
          /
        35
```

Check the rule at 50: everything on the left (30, 20, 40, 35) is smaller, and everything on the right (70, 60, 80) is bigger. Check it at 30: 20 is smaller; 40 and 35 are bigger. Every node passes, so this is a BST.

### Whole subtrees, not only children

The rule talks about whole subtrees, and that's the classic mistake: checking only that each child is on the correct side of its parent. This tree passes that weaker test everywhere, but it **isn't** a BST:

```text
        10
       /  \
      5    15
          /  \
         6    20
```

6 is smaller than its parent 15, so it's fine as a left child. But 6 is in the **right** subtree of 10, so it must be bigger than 10, and it isn't. If you searched this tree for 6, you'd compare with 10, go left (6 is smaller), and never find it. You'll write a correct check in [Validate a BST](/dsa/learn/bst-validate).

### Inorder means sorted

An inorder traversal (from [Preorder, inorder and postorder](/dsa/learn/trav-dfs-recursive)) visits the left subtree, then the node, then the right subtree. In a BST, that's "everything smaller, then this value, then everything bigger", at every level. So an inorder walk of a BST visits its values in **increasing order**:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func inorder(_ node: TreeNode?, _ visit: (Int) -> Void) {
    guard let node else { return }
    inorder(node.left, visit)
    visit(node.value)
    inorder(node.right, visit)
}

let root = TreeNode(50,
                    left: TreeNode(30, left: TreeNode(20), right: TreeNode(40, left: TreeNode(35))),
                    right: TreeNode(70, left: TreeNode(60), right: TreeNode(80)))
var values: [Int] = []
inorder(root) { values.append($0) }
print(values)
```

```output
[20, 30, 35, 40, 50, 60, 70, 80]
```

That's the fact most BST algorithms lean on. A BST is a sorted list arranged as a tree.

## Duplicates: pick a policy

What if a value arrives twice? There are three common answers:

1. **Ignore it.** The tree is a *set*: each value appears at most once. Inserting a value that's already there changes nothing.
2. **Count it.** Each node stores a count, and a second copy increments it.
3. **Send equal values one way**, say to the right, so the rule becomes "left smaller, right bigger or equal". It works, but every algorithm then has to remember that equal values can sit on the right.

This module uses policy 1 throughout, like Swift's `Set`: a BST holds each value once. Whatever you choose, state it, because it changes what "insert", "delete" and "valid" mean.

## Searching

To find a value, start at the root and compare:

- equal: found it;
- smaller: it can only be in the left subtree, so go left;
- bigger: go right.

If you fall off the tree (reach `nil`), the value isn't there. Each comparison throws away a whole subtree, as each step of [binary search](/dsa/learn/bs-classic) throws away half an array.

<Callout kind="analogy">
It's the "higher or lower" guessing game, with the tree as the list of guesses. The root is your first guess. "Lower" sends you to the left child, the best next guess among the smaller numbers.
</Callout>

Step through a search for 65. Watch the path: one node per level, and everything off the path is never looked at.

```visual bst
program: search
input:
  values: [50, 30, 70, 20, 40, 60, 80, 35, 65]
  target: 65
```

The recursive version reads like the definition. The iterative one moves a `current` reference down the tree, which needs no call stack:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func searchRecursive(_ target: Int, in node: TreeNode?) -> TreeNode? {
    guard let node else { return nil }
    if target == node.value { return node }
    return target < node.value ? searchRecursive(target, in: node.left) : searchRecursive(target, in: node.right)
}

func search(_ target: Int, in root: TreeNode?) -> TreeNode? {
    var current = root
    while let node = current {
        print("  at \(node.value)")
        if target == node.value { return node }
        current = target < node.value ? node.left : node.right
    }
    return nil
}

let root = TreeNode(50,
                    left: TreeNode(30, left: TreeNode(20), right: TreeNode(40, left: TreeNode(35))),
                    right: TreeNode(70, left: TreeNode(60), right: TreeNode(80)))
print("search 35:", search(35, in: root)?.value as Any)
print("search 65:", search(65, in: root)?.value as Any)
print("recursive 60:", searchRecursive(60, in: root)?.value as Any)
```

```output
  at 50
  at 30
  at 40
  at 35
search 35: Optional(35)
  at 50
  at 70
  at 60
search 65: nil
recursive 60: Optional(60)
```

What to notice:

- Finding 35 looked at 4 nodes out of 8, one per level. Missing 65 cost 3.
- Returning the **node**, not only `true`, lets the caller read or change it. That's what the practice problem asks for.
- The recursive version uses O(h) stack space, where h is the height; the loop uses O(1).

## Inserting

Inserting is a search that fails on purpose. Walk down exactly as if searching for the new value. When the side you want to go to is empty, that's the one place the value can go: hang a new leaf there. Existing nodes never move.

Step through inserting nine values in order. The first becomes the root, and each later one walks down and becomes a leaf:

```visual bst
program: insert
input:
  values: [50, 30, 70, 20, 40, 60, 80, 35, 30]
```

The last 30 finds a node already holding 30 and, under our policy, does nothing.

### Recursive insert: return the subtree's root

The recursive version has a pattern you'll use all through this module. `insert(value, into: node)` **returns the root of the subtree after inserting**. For an empty subtree, that's the new node. Otherwise it's the same node, after its left or right child has been replaced by whatever the recursive call returned:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func insert(_ value: Int, into node: TreeNode?) -> TreeNode {
    guard let node else { return TreeNode(value) }       // an empty spot: the new leaf
    if value < node.value {
        node.left = insert(value, into: node.left)
    } else if value > node.value {
        node.right = insert(value, into: node.right)
    }                                                     // equal: already there, do nothing
    return node
}

// Sideways: the root on the left, the right subtree above it. Tilt your head left to see it.
func draw(_ node: TreeNode?, _ indent: String = "") {
    guard let node else { return }
    draw(node.right, indent + "    ")
    print(indent + String(node.value))
    draw(node.left, indent + "    ")
}

var root: TreeNode? = nil
for value in [50, 30, 70, 20, 40, 60, 80, 35, 30] {
    root = insert(value, into: root)
}
draw(root)
```

```output
        80
    70
        60
50
        40
            35
    30
        20
```

`node.left = insert(value, into: node.left)` reassigns the same child on the way back up in every call but one: the call at the empty spot, which returns the new node, so its parent's link changes. And `root = insert(value, into: root)` handles the empty tree, where the new node becomes the root.

### Iterative insert: stop at the parent

The loop version needs no stack. It looks at the child **before** stepping onto it, so when the child is `nil` it still holds the parent and can attach the new leaf:

```swift
func insert(_ value: Int, into root: TreeNode?) -> TreeNode {
    guard let root else { return TreeNode(value) }
    var node = root
    while true {
        if value < node.value {
            guard let left = node.left else {
                node.left = TreeNode(value)
                return root
            }
            node = left
        } else if value > node.value {
            guard let right = node.right else {
                node.right = TreeNode(value)
                return root
            }
            node = right
        } else {
            return root                                   // already there
        }
    }
}
```

## How fast is it?

Search and insert both walk one path from the root: **O(h)**, where h is the height. That's the whole story, and h depends on the tree's shape:

| Shape | Height for n values | Search and insert |
| --- | --- | --- |
| Balanced (every level full, or nearly) | about log₂ n | O(log n) |
| Random insertion order | O(log n) on average: a typical node is about 1.39 log₂ n deep | O(log n) on average |
| Values inserted in sorted order | n: a chain | O(n) |

A million values in a balanced BST is 20 levels: any value in 20 comparisons. The same million inserted in sorted order makes a "tree" that's one long chain, and a search can cost a million comparisons. You'll measure this in [Why unbalanced BSTs degrade to O(n)](/dsa/learn/bst-degenerate), and M38 fixes it with trees that rebalance themselves.

<Callout kind="gotcha" title="Swift gotcha: the forgotten reassignment">
With the recursive insert, writing `insert(value, into: node.left)` without `node.left =` in front compiles (with an "unused result" warning) but loses every new node: the call creates it, returns it, and nobody keeps it. The same goes for the top level: `insert(9, into: root)` on an empty tree builds a node and throws it away. Read that compiler warning: it's telling you about a bug.
</Callout>

<Callout kind="gotcha" title="The node must be a class">
`TreeNode` is a `final class`, as in [TreeNode in Swift: class vs indirect enum](/dsa/learn/tree-node-swift). The iterative insert changes `node.left` on a node it reached through a local variable. With a struct, `node` would be a copy, and the change would never reach the tree.
</Callout>
