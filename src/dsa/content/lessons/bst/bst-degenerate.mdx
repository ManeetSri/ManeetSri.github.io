## Why it matters

Every BST operation in this module costs O(h), and all along there's been a catch in the small print: h depends on the order the values arrived in. In the best case h is about log₂ n, and a million values sit 20 levels deep. In the worst case h is n, and the "tree" is a linked list in disguise. The worst case isn't exotic, either. Timestamps, auto-incrementing IDs and alphabetical imports all arrive in sorted order, which is exactly the input that breaks a plain BST. This short lesson measures the damage, and sets up the fix in M38.

## Measuring heights

The experiment inserts the numbers 1 to n into an empty BST in three orders, and records the height and the total number of comparisons the inserts made:

- **sorted**: 1, 2, 3, …, n;
- **scrambled**: the same values shuffled, with a fixed formula standing in for randomness so every run gives the same numbers;
- **middle first**: the order that builds the perfectly balanced tree from [A balanced BST from a sorted array](/dsa/learn/bst-from-sorted).

Heights and comparison counts are measured rather than timed: they don't depend on the machine, and they explain the timings anyway.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?
    init(_ value: Int) { self.value = value }
}

// Inserts value and returns how many nodes it was compared with on the way down
func insert(_ value: Int, into root: inout TreeNode?) -> Int {
    guard var node = root else {
        root = TreeNode(value)
        return 0
    }
    var comparisons = 1
    while true {
        if value < node.value {
            guard let left = node.left else { node.left = TreeNode(value); return comparisons }
            node = left
        } else {
            guard let right = node.right else { node.right = TreeNode(value); return comparisons }
            node = right
        }
        comparisons += 1
    }
}

func height(_ root: TreeNode?) -> Int {
    var levels = 0
    var level = [root].compactMap { $0 }
    while !level.isEmpty {
        levels += 1
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return levels
}

// The same "random" order every run: a Fisher–Yates shuffle driven by a fixed formula
func scrambled(_ n: Int) -> [Int] {
    var values = Array(1...n)
    var state: UInt64 = 2024
    for i in stride(from: n - 1, to: 0, by: -1) {
        state = state &* 6364136223846793005 &+ 1442695040888963407
        values.swapAt(i, Int((state >> 33) % UInt64(i + 1)))
    }
    return values
}

// The middle, then the middle of each half, and so on
func middleFirst(_ low: Int, _ high: Int, into order: inout [Int]) {
    guard low <= high else { return }
    let mid = (low + high) / 2
    order.append(mid)
    middleFirst(low, mid - 1, into: &order)
    middleFirst(mid + 1, high, into: &order)
}

for n in [100, 1_000, 3_000] {
    var balanced: [Int] = []
    middleFirst(1, n, into: &balanced)
    for (name, order) in [("sorted", Array(1...n)), ("scrambled", scrambled(n)), ("middle first", balanced)] {
        var root: TreeNode? = nil
        var total = 0
        for value in order {
            total += insert(value, into: &root)
        }
        print("n = \(n), \(name): height \(height(root)), about \(total / n) comparisons per insert")
    }
}
```

```output
n = 100, scrambled: height 11, about 6 comparisons per insert
n = 100, middle first: height 7, about 4 comparisons per insert
n = 1000, sorted: height 1000, about 499 comparisons per insert
n = 1000, scrambled: height 22, about 12 comparisons per insert
n = 1000, middle first: height 10, about 7 comparisons per insert
n = 3000, sorted: height 3000, about 1499 comparisons per insert
n = 3000, scrambled: height 27, about 12 comparisons per insert
n = 3000, middle first: height 12, about 9 comparisons per insert
```

What to notice:

- **Sorted** input gives height exactly n: every value is bigger than all before it, so it hangs off the right of the previous one. The kth insert walks k − 1 nodes, so n inserts cost 0 + 1 + … + (n − 1) = n(n − 1)/2 comparisons: **O(n²)** to build, and O(n) for every later search.
- **Scrambled** input stays shallow. Going from 1,000 to 3,000 values added only 5 levels, and the average insert barely changed. A BST built in random order has an average depth of about 1.39 log₂ n, so it's O(log n) on average, though with no guarantee for any particular order.
- **Middle first** gives the minimum height, ⌈log₂(n + 1)⌉. That's the ideal every balanced tree tries to stay close to.

## Why it happens so often

A random insertion order is the friendly case, but real data is rarely random:

- **Time-ordered data**: log entries, messages, sensor readings and events all arrive with increasing timestamps.
- **Generated IDs**: database rows with auto-incrementing keys, invoice numbers, ticket numbers.
- **Already-sorted sources**: a file exported in alphabetical order, an API response sorted by date, the output of `sorted()`.
- **Nearly sorted data**: a list that's sorted except for a few late arrivals is almost as bad. So is a zig-zag order like 1, 100, 2, 99, 3, 98, which also builds a tree one node wide.

Deletions can unbalance a tree too, as you saw in [Deleting from a BST](/dsa/learn/bst-delete). And an attacker who knows your server stores their input in a plain BST can send sorted keys on purpose, the same trick as the hash flooding in [Hashing pitfalls](/dsa/learn/hash-pitfalls).

## Three ways out

1. **Shuffle first.** If you have all the values up front, shuffle them (`values.shuffled()`) before inserting. The expected height is O(log n), though an unlucky shuffle could still be tall.
2. **Build from sorted.** Better still, sort the values and build the tree from the middle, as in [A balanced BST from a sorted array](/dsa/learn/bst-from-sorted): guaranteed minimum height, in O(n) after sorting. Neither of these helps when values arrive one at a time, though.
3. **Rebalance as you go.** A **self-balancing** BST checks the shape after every insert and delete, and repairs any part that has become too lopsided with small, local moves called **rotations**. AVL trees and red-black trees both guarantee a height of O(log n) **whatever** the order, so every operation is O(log n) in the worst case. That's M38, starting with [Why balance matters, and rotations](/dsa/learn/bal-why-rotations).

| | Plain BST | Shuffled, then plain BST | Self-balancing BST |
| --- | --- | --- | --- |
| Values arrive one at a time | works | no: needs all values first | works |
| Height for sorted input | n | O(log n) expected | O(log n) guaranteed |
| Worst-case search | O(n) | O(n), but very unlikely | O(log n) |

<Callout kind="gotcha" title="The ArrayLiteral trap">
`let tree: BinarySearchTree = [1, 2, 3, 4, 5]` reads nicely, but DSAKit's tree inserts literal elements in the order written. Writing them sorted builds a chain of height 5. For a few elements it doesn't matter. For thousands, build from a shuffled array, or wait for M38's balanced trees.
</Callout>
