## Why it matters

"Find the first free appointment at or after 2:30" is a **ceiling** query. "What was the exchange rate at or before this timestamp?" is a **floor**. Both ask for the nearest value on one side, even when the exact value isn't stored, and a BST answers them in O(h). The second half of this lesson builds a **BST iterator**: a way to step through the values in sorted order one at a time, using memory proportional to the height rather than the size. It's what makes `for value in tree` work, and it's a popular design question because the analysis (amortised O(1) per step) is subtle.

## Floor and ceiling

For a value x:

- the **floor** of x is the largest value in the tree that's **≤ x**;
- the **ceiling** of x is the smallest value that's **≥ x**.

If x is in the tree, both are x itself. In the tree holding 20, 30, 35, 40, 50, 60, 70 and 80, the floor of 45 is 40 and its ceiling is 50. The floor of 10 doesn't exist (nothing is ≤ 10), and neither does the ceiling of 90.

If you've met [lower bound](/dsa/learn/bs-bounds) in a sorted array, the ceiling is the element at the lower bound index, and the floor is the element immediately before the upper bound. A BST answers the same questions without needing the values packed in an array.

The walk is the "remember a candidate" idea from [Min, max, successor and predecessor](/dsa/learn/bst-min-max-successor). For the floor: at each node,

- equal to x: that's the floor, stop;
- smaller than x: it's a candidate, but a bigger one might be to the right, so remember it and go **right**;
- bigger than x: it can't be the floor, and neither can anything to its right, so go **left**.

When you fall off the tree, the last candidate is the answer. The ceiling is the mirror image.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func floor(_ x: Int, in root: TreeNode?) -> Int? {
    var best: Int? = nil
    var current = root
    while let node = current {
        if node.value == x {
            return x
        } else if node.value < x {
            best = node.value                      // a candidate; a bigger one may be to the right
            current = node.right
        } else {
            current = node.left
        }
    }
    return best
}

func ceiling(_ x: Int, in root: TreeNode?) -> Int? {
    var best: Int? = nil
    var current = root
    while let node = current {
        if node.value == x {
            return x
        } else if node.value > x {
            best = node.value                      // a candidate; a smaller one may be to the left
            current = node.left
        } else {
            current = node.right
        }
    }
    return best
}

//            50
//         /      \
//       30        70
//      /  \      /  \
//    20    40  60    80
//         /
//       35
let root = TreeNode(50,
                    left: TreeNode(30, left: TreeNode(20), right: TreeNode(40, left: TreeNode(35))),
                    right: TreeNode(70, left: TreeNode(60), right: TreeNode(80)))
for x in [45, 35, 10, 90, 55] {
    print(x, "floor:", floor(x, in: root) as Any, "ceiling:", ceiling(x, in: root) as Any)
}
```

```output
45 floor: Optional(40) ceiling: Optional(50)
35 floor: Optional(35) ceiling: Optional(35)
10 floor: nil ceiling: Optional(20)
90 floor: Optional(80) ceiling: nil
55 floor: Optional(50) ceiling: Optional(60)
```

What to notice:

- Floor of 45: 50 is too big (left), 30 is a candidate (right), 40 is a better candidate (right), and 40 has no right child. Answer 40.
- The walk never backtracks: one path, **O(h)**, O(1) space.
- The strict versions, "the largest value **less than** x" and "the smallest value **greater than** x", are the predecessor and successor from the last lesson: drop the `==` case and treat equal as "wrong side".

## A BST iterator

Now suppose you want the values one at a time, in sorted order: to show the first page of results, to merge two trees, or to write `for value in tree`. The easy answer copies the inorder traversal into an array and hands out its elements. That costs O(n) memory, and O(n) work before the first value appears, even if you only ever want the first three.

The better answer is the iterative inorder walk from [Iterative traversals with a stack](/dsa/learn/trav-dfs-iterative), **paused between values**. Its whole state is the stack: the nodes whose left subtrees are finished but which haven't been returned yet. The top of the stack is always the next smallest value.

- **Start:** push the root, its left child, its left child's left child, and so on: the **left spine**. The minimum ends up on top.
- **`next()`:** pop the top node. Its left subtree is done, so its value is next. Before returning it, push the left spine of its **right** child: those values come next.
- **Done** when the stack is empty.

In Swift, "something with a `mutating func next() -> Element?`" is exactly [`IteratorProtocol`](/dsa/learn/swift-sequence-iterator). Conform to it, and a small `Sequence` wrapper makes `for`-`in`, `map` and friends work:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

struct InorderIterator: IteratorProtocol {
    private var stack: [TreeNode] = []

    init(_ root: TreeNode?) {
        pushLeftSpine(from: root)
    }

    private mutating func pushLeftSpine(from start: TreeNode?) {
        var current = start
        while let node = current {
            stack.append(node)
            current = node.left
        }
    }

    mutating func next() -> Int? {
        guard let node = stack.popLast() else { return nil }
        pushLeftSpine(from: node.right)
        return node.value
    }

    var waiting: [Int] { stack.map(\.value) }       // for printing only
}

struct SortedValues: Sequence {
    let root: TreeNode?
    func makeIterator() -> InorderIterator { InorderIterator(root) }
}

let root = TreeNode(50,
                    left: TreeNode(30, left: TreeNode(20), right: TreeNode(40, left: TreeNode(35))),
                    right: TreeNode(70, left: TreeNode(60), right: TreeNode(80)))

var iterator = InorderIterator(root)
print("start, stack \(iterator.waiting)")
while let value = iterator.next() {
    print("next() -> \(value), stack \(iterator.waiting)")
}

for value in SortedValues(root: root) where value > 45 {
    print(value, terminator: " ")
}
print()
print(SortedValues(root: root).prefix(3).map { $0 * 10 })
```

```output
start, stack [50, 30, 20]
next() -> 20, stack [50, 30]
next() -> 30, stack [50, 40, 35]
next() -> 35, stack [50, 40]
next() -> 40, stack [50]
next() -> 50, stack [70, 60]
next() -> 60, stack [70]
next() -> 70, stack [80]
next() -> 80, stack []
50 60 70 80 
[200, 300, 350]
```

What to notice:

- The stack never holds more than one node per level: here at most 3, the height. So the iterator uses **O(h)** memory, not O(n).
- After 30 is returned, its right child 40 and 40's left spine (35) are pushed. After 50, the spine 70, 60. This is how the walk "turns the corner" into a right subtree.
- `prefix(3)` stops asking after three values, so the right half of the tree is never touched. That laziness is the point of an iterator.

## Why next() is amortised O(1)

Most `next()` calls push nothing or one node, but some push a whole left spine. Returning 50 above pushed two nodes; in a tall tree it could push h. So a single call is O(h) in the worst case.

Look at the whole walk instead, as in [Amortised analysis](/dsa/learn/bigo-amortised). Every node is **pushed exactly once** (when the spine it belongs to is pushed) and **popped exactly once** (when it's returned). Over n calls that's n pushes and n pops: O(n) in total, so **O(1) per call on average**, however the tree is shaped.

| | Copy into an array | Stack-based iterator |
| --- | --- | --- |
| Before the first value | O(n) | O(h) |
| Each `next()` | O(1) | amortised O(1), worst O(h) |
| Memory | O(n) | O(h) |
| Stop early | already paid for everything | pay only for what you use |

## Two iterators at once: two sum in a BST

Does the tree hold two values that add up to a target? In a sorted array you'd use [two pointers](/dsa/learn/tp-opposite-ends), one at each end, moving inwards. A BST has no indexes, but two iterators do the same job: one walking up from the smallest value, and a mirrored one (right spine first) walking down from the largest:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

// Visits values in increasing order, or decreasing order when `reversed` is true
struct BSTWalker: IteratorProtocol {
    private var stack: [TreeNode] = []
    private let reversed: Bool

    init(_ root: TreeNode?, reversed: Bool) {
        self.reversed = reversed
        pushSpine(from: root)
    }

    private mutating func pushSpine(from start: TreeNode?) {
        var current = start
        while let node = current {
            stack.append(node)
            current = reversed ? node.right : node.left
        }
    }

    mutating func next() -> Int? {
        guard let node = stack.popLast() else { return nil }
        pushSpine(from: reversed ? node.left : node.right)
        return node.value
    }
}

func pairSum(_ target: Int, in root: TreeNode?) -> (Int, Int)? {
    var up = BSTWalker(root, reversed: false)
    var down = BSTWalker(root, reversed: true)
    var low = up.next()
    var high = down.next()
    while let small = low, let big = high, small < big {
        let sum = small + big
        if sum == target {
            return (small, big)
        } else if sum < target {
            low = up.next()                        // need more: move the small end up
        } else {
            high = down.next()                     // need less: move the big end down
        }
    }
    return nil
}

let root = TreeNode(50,
                    left: TreeNode(30, left: TreeNode(20), right: TreeNode(40, left: TreeNode(35))),
                    right: TreeNode(70, left: TreeNode(60), right: TreeNode(80)))
print(pairSum(95, in: root) as Any)
print(pairSum(100, in: root) as Any)
print(pairSum(41, in: root) as Any)
```

```output
Optional((35, 60))
Optional((20, 80))
nil
```

Each step moves one end inwards, and `small < big` stops them when they meet, so a value is never paired with itself. Two O(h) stacks and O(n) total steps: **O(n) time, O(h) space**, with no array of values and no hash set.

<Callout kind="gotcha" title="Don't change the tree while an iterator is walking it">
The stack holds references to real nodes. Insert or delete while iterating and the stack can point at a node that's been unlinked, or miss a node that was added: the results depend on exactly where the change happened. Finish iterating first, or collect the changes and apply them afterwards. DSAKit's `BinarySearchTree` in [Build a generic BST](/dsa/learn/bst-generic) avoids the problem entirely: its iterator keeps the tree's storage alive, so changing the tree during a loop copies it first.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: next() must be mutating">
`IteratorProtocol` requires `mutating func next() -> Element?`. Forget `mutating` on a struct and the compiler stops you: popping the stack changes the iterator. It also means the iterator must be a `var`. A `let` iterator can't call `next()`.
</Callout>

## Practice

**Design a BST iterator** asks for exactly this iterator, with `hasNext` and `peek()` as well as `next()`. Both extras read the top of the stack without changing it. Copying the values into an array in `init` passes the tests, so treat it as a first draft: the stack version is what an interviewer is looking for.
