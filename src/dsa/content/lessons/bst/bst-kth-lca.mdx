## Why it matters

Two classic questions show what the BST ordering buys you. "What's the 3rd cheapest flight?" or "who's 10th on the leaderboard?" is a **kth smallest** query: in a BST, sorted order is an inorder walk away, so you can stop after k steps. "Which category contains both of these products?" in a sorted hierarchy is a **lowest common ancestor** query: in an ordinary binary tree it means searching everywhere, but in a BST the values tell you which way to go, so you walk one path. Both are among the most asked BST interview problems.

## Kth smallest: inorder, and stop early

An inorder walk visits a BST's values in increasing order. So the kth value it visits is the kth smallest. The simplest version collects the whole walk into an array and reads index `k - 1`. That's correct, but it visits all n nodes and stores all n values, even when k is 1.

Better: count as you go, and stop when the count reaches k. The iterative inorder walk from [Iterative traversals with a stack](/dsa/learn/trav-dfs-iterative) makes stopping easy, because the walk is a loop you can return from at any point:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func kthSmallest(_ k: Int, in root: TreeNode?) -> Int? {
    var stack: [TreeNode] = []
    var current = root
    var visited = 0
    while current != nil || !stack.isEmpty {
        while let node = current {                 // slide down the left spine
            stack.append(node)
            current = node.left
        }
        let node = stack.removeLast()              // the next value in sorted order
        visited += 1
        print("  visit \(node.value) (#\(visited))")
        if visited == k {
            return node.value
        }
        current = node.right
    }
    return nil                                     // fewer than k values
}

//            50
//         /      \
//       30        70
//      /  \      /  \
//    20    40  60    80
//         /
//       35
let root = TreeNode(50,
                    left: TreeNode(30, left: TreeNode(20), right: TreeNode(40, left: TreeNode(35))),
                    right: TreeNode(70, left: TreeNode(60), right: TreeNode(80)))
print("k = 3:", kthSmallest(3, in: root) as Any)
print("k = 9:", kthSmallest(9, in: root) as Any)
```

```output
  visit 20 (#1)
  visit 30 (#2)
  visit 35 (#3)
k = 3: Optional(35)
  visit 20 (#1)
  visit 30 (#2)
  visit 35 (#3)
  visit 40 (#4)
  visit 50 (#5)
  visit 60 (#6)
  visit 70 (#7)
  visit 80 (#8)
k = 9: nil
```

What to notice:

- For k = 3 the walk stopped after three visits. 70, 60 and 80 were never touched.
- Before the first visit, the walk slides down the left spine: O(h) work. After that, each visit costs amortised O(1). So the total is **O(h + k)** time and O(h) space for the stack.
- Asking for more values than the tree has returns `nil`. The practice problem promises k is in range, so it can return a plain `Int`.

### The recursive version needs shared state

You can write it recursively too, but the count has to survive across calls, and the recursion needs a way to stop. A nested function that captures two local variables does both:

```swift
func kthSmallest(_ k: Int, in root: TreeNode?) -> Int? {
    var visited = 0
    var answer: Int? = nil
    func walk(_ node: TreeNode?) {
        guard let node, answer == nil else { return }      // stop once found
        walk(node.left)
        guard answer == nil else { return }
        visited += 1
        if visited == k {
            answer = node.value
            return
        }
        walk(node.right)
    }
    walk(root)
    return answer
}
```

The `answer == nil` checks keep the walk from wandering on after it has found the value. Forgetting them is harmless for correctness but throws away the early exit.

### Kth largest, and many queries

**Kth largest** is the same walk mirrored: right subtree, node, left subtree visits values in **decreasing** order. Swap every `left` for `right` in the code.

If a tree is queried for kth smallest often while values come and go, even O(h + k) is too slow when k is large. The fix is to store in each node the **size of its subtree**. At a node whose left subtree holds L values: if k ≤ L, the answer is on the left; if k = L + 1, it's this node; otherwise look right for the (k − L − 1)th smallest. That's one path, O(h), at the cost of updating sizes on every insert and delete. Trees that carry extra facts like this are called **augmented** trees, and they come back in later parts of the course.

## LCA in a BST: let the values steer

The **lowest common ancestor** (LCA) of two nodes is the deepest node that has both of them in its subtree. A node counts as part of its own subtree, so if one node is an ancestor of the other, the ancestor is the answer. In [Lowest common ancestor](/dsa/learn/bt-lca) you solved this for any binary tree, by searching both subtrees of every node: O(n).

A BST lets you do far less. Stand at the root with two values p and q:

- if **both are smaller** than the node, both are in its left subtree, so their LCA is too: go left;
- if **both are bigger**, go right;
- otherwise they're on **different sides** of this node, or one of them **is** this node. No deeper node can have both below it, so this node is the answer.

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func lowestCommonAncestor(_ p: Int, _ q: Int, in root: TreeNode?) -> TreeNode? {
    var current = root
    while let node = current {
        if p < node.value && q < node.value {
            current = node.left
        } else if p > node.value && q > node.value {
            current = node.right
        } else {
            return node                            // they split here, or one of them is here
        }
    }
    return nil
}

let root = TreeNode(50,
                    left: TreeNode(30, left: TreeNode(20), right: TreeNode(40, left: TreeNode(35))),
                    right: TreeNode(70, left: TreeNode(60), right: TreeNode(80)))
for (p, q) in [(20, 35), (35, 80), (60, 80), (30, 35), (40, 40)] {
    print("LCA(\(p), \(q)) =", lowestCommonAncestor(p, q, in: root)!.value)
}
```

```output
LCA(20, 35) = 30
LCA(35, 80) = 50
LCA(60, 80) = 70
LCA(30, 35) = 30
LCA(40, 40) = 40
```

What to notice:

- 20 and 35 are both smaller than 50, so the walk goes left to 30. At 30, 20 is smaller and 35 is bigger: they split, so 30 is the answer.
- For 30 and 35, the walk stops at 30 itself: one value **is** the node. 30 is an ancestor of 35, so it's their LCA.
- It's one walk down: **O(h)** time and O(1) space. The order of p and q doesn't matter.

<Callout kind="note" title="Values are enough">
The general LCA problem takes node references, because in an arbitrary tree values can repeat and say nothing about position. In a BST, a value tells you exactly where its node is, so this version takes values. If your function is handed nodes, compare their `value`s and the code is the same.
</Callout>

<Callout kind="gotcha" title="Two slips to avoid">
**Strict comparisons.** The tests are `p < node.value && q < node.value` and `p > node.value && q > node.value`. Using `<=` would walk past a node equal to p or q, and then fail to find the answer below it.

**Assuming both values exist.** This walk returns the node where the values would split, whether or not they're really in the tree: for 33 and 37, neither of which is there, it returns 35. When presence isn't guaranteed, search for both values first.
</Callout>

## Practice

**Kth smallest value in a BST** is the first half of this lesson, with trees large enough that the early exit matters for small k. **Lowest common ancestor in a BST** is the second half: aim for the loop, not a recursive search of both subtrees.

```cards

  front: "How do you find the kth smallest value in a BST?"
  back: "Walk it inorder (increasing order), counting nodes as you visit them, and stop at the kth. With an iterative walk that's O(h + k)."
- id: kth-largest
  front: "How do you adapt kth smallest to kth largest?"
  back: "Walk in reverse inorder, right subtree, node, left subtree, which visits values in decreasing order."
- id: lca-bst-rule
  front: "How do you find the LCA of p and q in a BST?"
  back: "Walk down from the root: if both are smaller than the node, go left; if both are bigger, go right; otherwise this node is the LCA."
- id: lca-bst-cost
  front: "Why is LCA in a BST O(h) while LCA in a general binary tree is O(n)?"
  back: "The ordering says which subtree holds each value, so one path from the root suffices. A general tree gives no hint, so both subtrees must be searched."
```
