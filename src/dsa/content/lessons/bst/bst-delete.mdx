## Why it matters

A set that can only grow isn't much use. A to-do list sorted by due date loses items when they're done, a game's leaderboard drops players, and a cache evicts old entries. Deleting from a BST is the operation that trips most people up: removing a node can leave a hole in the middle of the tree, and the hole has to be filled without breaking the BST property. There are exactly three cases, and once you see why the hardest one works, the code is short. It's also a favourite interview question, because it tests recursion that returns a new subtree root.

## First, find it

Deletion starts with a search: walk left or right until you reach the node holding the value, remembering how you got there. If you fall off the tree, the value isn't there and nothing changes.

What happens next depends on how many children the node has. Throughout this lesson, the example tree is this one:

```text
              50
           /      \
         30        70
        /  \      /  \
      20    40  60    80
           /  \   \
         35   45   65
```

## Case 1: a leaf

A leaf has no children, so nothing hangs below it. Its parent points at `nil` instead, and the leaf is gone. Deleting 35 clears 40's left link, and that's all. Nothing else moves, so the BST property still holds everywhere.

## Case 2: one child

A node with one child has a single subtree below it. Its parent can point **straight at that child**, skipping the node. Deleting 60 makes 70's left link point at 65.

Is that safe? Every value in the child's subtree was already in the parent's subtree on the same side as the deleted node. 65 was in 70's left subtree (via 60), so it's smaller than 70, and it's still in 70's left subtree. The ancestors' rules don't change, because the same values are below them, minus one.

Step through it:

```visual bst
program: remove
input:
  values: [50, 30, 70, 20, 40, 60, 80, 35, 45, 65]
  target: 60
```

## Case 3: two children

Now delete 30. It has two subtrees, and its parent 50 has only one link to give. You can't hang both 20 and 40 from 50's left.

The trick is to **move a value, not a node**. Find a value that could sit where 30 is, copy it into 30's node, and delete that value from where it was instead. Which value fits? It must be bigger than everything left in the left subtree and smaller than everything in the right subtree. Two values qualify:

- the **inorder successor**: the smallest value in the right subtree (35). Go right once, then left as far as possible.
- the **inorder predecessor**: the largest value in the left subtree (20). Go left once, then right as far as possible.

They're the values immediately after and immediately before 30 in sorted order, so either can take 30's place without anything else noticing. This course uses the successor.

Here's the part that makes it easy: **the successor never has a left child.** If it had one, that child would be in the right subtree and smaller than the successor, so the successor wouldn't be the smallest. A node with no left child is case 1 or case 2. So deleting the successor from the right subtree is always easy.

```visual bst
program: remove
input:
  values: [50, 30, 70, 20, 40, 60, 80, 35, 45, 65]
  target: 30
```

After the copy, the node that held 30 holds 35, and the old 35 (a leaf) is removed. The inorder walk was `20 30 35 40 45 …` and is now `20 35 40 45 …`: still sorted.

## The code: return the new subtree root

The recursive version uses the pattern from insert. `remove(value, from: node)` returns the root of the subtree **after** the deletion, and each caller re-links whatever comes back:

```swift run
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?

    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value
        self.left = left
        self.right = right
    }
}

func insert(_ value: Int, into node: TreeNode?) -> TreeNode {
    guard let node else { return TreeNode(value) }
    if value < node.value {
        node.left = insert(value, into: node.left)
    } else if value > node.value {
        node.right = insert(value, into: node.right)
    }
    return node
}

func remove(_ value: Int, from node: TreeNode?) -> TreeNode? {
    guard let node else { return nil }                    // not in the tree
    if value < node.value {
        node.left = remove(value, from: node.left)
    } else if value > node.value {
        node.right = remove(value, from: node.right)
    } else {
        guard let left = node.left else { return node.right }    // case 1, or case 2 with a right child
        guard let right = node.right else { return left }        // case 2 with a left child
        var successor = right                                    // case 3
        while let smaller = successor.left {
            successor = smaller
        }
        node.value = successor.value
        node.right = remove(successor.value, from: right)
    }
    return node
}

func levels(_ root: TreeNode?) -> String {
    var level = [root].compactMap { $0 }
    var rows: [String] = []
    while !level.isEmpty {
        rows.append(level.map { String($0.value) }.joined(separator: " "))
        level = level.flatMap { [$0.left, $0.right].compactMap { $0 } }
    }
    return rows.joined(separator: " | ")
}

func build() -> TreeNode? {
    var root: TreeNode? = nil
    for value in [50, 30, 70, 20, 40, 60, 80, 35, 45, 65] {
        root = insert(value, into: root)
    }
    return root
}

print("start:    ", levels(build()))
for value in [35, 60, 30, 50, 99] {
    print("remove \(value):", levels(remove(value, from: build())))
}
```

```output
start:     50 | 30 70 | 20 40 60 80 | 35 45 65
remove 35: 50 | 30 70 | 20 40 60 80 | 45 65
remove 60: 50 | 30 70 | 20 40 65 80 | 35 45
remove 30: 50 | 35 70 | 20 40 60 80 | 45 65
remove 50: 60 | 30 70 | 20 40 65 80 | 35 45
remove 99: 50 | 30 70 | 20 40 60 80 | 35 45 65
```

Each line shows the tree level by level, separated by `|`. Read the cases off it:

- **35** (a leaf) vanishes from the bottom level.
- **60** (one child) is replaced by 65, which moves up a level.
- **30** (two children) becomes 35, and 35's old spot empties.
- **50**, the root, has two children. Its successor is 60 (right to 70, then left to 60). 60 moves up into the root, and 60's own child, 65, takes 60's old place: the successor had one child, so removing it was case 2.
- **99** isn't there: the search falls off the tree, every call returns its node unchanged, and the tree is untouched.

What to notice:

- Two `guard` lines handle cases 1 and 2 together. With no left child, the right child takes over, and for a leaf that's `nil`. With no right child, the left child takes over.
- Returning the new subtree root makes deleting the root need no special code. The caller writes `root = remove(value, from: root)`, and gets back a different node, or `nil` when the last value goes.
- The second recursive call starts at `right`, not at the root. The successor is somewhere in the right subtree, and its value now appears twice in the tree (in `node` and in the successor), so starting from the top would find `node` first.

## Without recursion

Recursion costs O(h) stack, and a degenerate tree can be thousands of levels deep (see [Stack depth limits in Swift](/dsa/learn/rec-stack-limits)). The loop version walks down remembering the **parent**, then re-links the parent's left or right pointer itself. For case 3 it finds the successor and the successor's parent, copies the value up, and removes the successor, which has at most a right child:

```swift
func remove(_ value: Int, from root: TreeNode?) -> TreeNode? {
    var parent: TreeNode? = nil
    var current = root
    while let node = current, node.value != value {
        parent = node
        current = value < node.value ? node.left : node.right
    }
    guard var target = current else { return root }        // not there
    if let right = target.right, target.left != nil {      // two children
        var successorParent = target
        var successor = right
        while let smaller = successor.left {
            successorParent = successor
            successor = smaller
        }
        target.value = successor.value
        parent = successorParent                           // now remove the successor instead
        target = successor
    }
    let child = target.left ?? target.right                // at most one child now
    guard let parent else { return child }                 // removing the root
    if parent.left === target {
        parent.left = child
    } else {
        parent.right = child
    }
    return root
}
```

`===` compares identity, from [Identity with ===](/dsa/learn/swift-identity): it asks whether `parent.left` is this very node, not whether it holds an equal value. DSAKit's `BinarySearchTree`, which you'll build in [Build a generic BST](/dsa/learn/bst-generic), removes this way.

## Cost, and a subtle drift

Deletion walks down to the node, and in case 3 carries on down to the successor: one path, so **O(h)**. The tree never gets taller, because the only node that actually disappears is a leaf or a node replaced by its only child.

Always choosing the successor has a side effect: case 3 always removes a node from the right subtree, so over many deletions right subtrees shrink and trees drift lopsided. Experiments with long runs of random insertions and successor-only deletions found trees noticeably taller than random insertions alone produce. Some implementations alternate between successor and predecessor. Self-balancing trees (M38) make the question disappear.

<Callout kind="gotcha" title="Copying values moves data under other references">
Case 3 changes `node.value` instead of moving nodes. That's fine inside a BST, but if any other code holds a reference to a node (a cache of nodes, an iterator, a UI cell), the node it holds now has a different value. Libraries that hand out node references therefore re-link the successor **node** into the deleted node's place instead of copying its value. In this module, nodes stay private, so copying is safe.
</Callout>

<Callout kind="gotcha" title="Three easy slips">
**Ignoring the return value.** `remove(value, from: node.left)` without `node.left =` deletes nothing visible: the parent still points at the old subtree.

**Deleting the successor from the wrong place.** After the copy, two nodes hold the successor's value. Delete it from `node.right`, never from `root`.

**Grafting instead of replacing.** Hanging the whole left subtree under the successor also gives a valid BST, but it can make the tree much taller. Copying the successor's value keeps the height the same or lower.
</Callout>

## Practice

**Delete a value from a BST** is exactly this operation, and its tests insist that the tree doesn't grow taller. Write the recursive version first; then try the loop version, which is fiddlier because you have to track parents yourself.
