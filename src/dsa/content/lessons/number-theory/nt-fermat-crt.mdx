## Why it matters

The last lesson found inverses with extended Euclid. When the modulus is prime, which it almost always is in contest problems, there's an even shorter route: **Fermat's little theorem** turns an inverse into one call of the fast power you already know. The same theorem shrinks absurd exponents like 3^(10¹⁰⁰) down to size. The second half of this lesson is the **Chinese remainder theorem** (CRT), which rebuilds a number from its remainders. It's how you find when several repeating events line up, how big-number libraries split one huge modulus into several small ones, and how the FFT lesson at the end of this module multiplies polynomials modulo more than one prime.

## Fermat's little theorem

Raise 3 to successive powers modulo 7 and something tidy happens:

```swift run
func modPow(_ base: Int, _ exponent: Int, _ m: Int) -> Int {
    var result = 1 % m
    var square = ((base % m) + m) % m
    var e = exponent
    while e > 0 {
        if e % 2 == 1 {
            result = result * square % m
        }
        square = square * square % m
        e /= 2
    }
    return result
}

// Powers of 3 modulo 7 cycle back to 1 after p - 1 = 6 steps
print((1...6).map { modPow(3, $0, 7) })
print((1...6).map { modPow(2, $0, 7) })
print((1..<7).map { modPow($0, 6, 7) })
```

```output
[3, 2, 6, 4, 5, 1]
[2, 4, 1, 2, 4, 1]
[1, 1, 1, 1, 1, 1]
```

Every number from 1 to 6, raised to the 6th power, leaves remainder 1 modulo 7. That's the theorem:

> If p is prime and a is not a multiple of p, then **a^(p − 1) ≡ 1 (mod p)**.

The powers of 2 return to 1 early, after 3 steps, but 3 divides 6, so 2⁶ = (2³)² ≡ 1 all the same.

### Why it's true

Take p = 7 and a = 3, and multiply 3 by each of 1, 2, …, 6:

```text
3, 6, 9, 12, 15, 18   ≡   3, 6, 2, 5, 1, 4   (mod 7)
```

The remainders are 1 to 6 again, shuffled. That always happens: if i × a ≡ j × a for two different i and j below p, then p would divide (i − j) × a. But p doesn't divide a, and i − j is too small to be a multiple of p, so the products are all different, and none of them is 0. Now multiply the six products together. On one side it's a⁶ × (1 × 2 × … × 6); on the other it's 1 × 2 × … × 6 in a different order. So a⁶ × 6! ≡ 6!, and since 6! has an inverse modulo 7 (it's a product of numbers coprime to 7), you can cancel it: a⁶ ≡ 1. Nothing depended on 7 and 3 except that 7 is prime and doesn't divide 3.

## Inverses by fast power

Split a^(p − 1) as a × a^(p − 2):

```text
a × a^(p − 2) ≡ 1 (mod p)
```

So **a^(p − 2) is the inverse of a** modulo a prime p. For a = 3 and p = 7, that's 3⁵. Here's fast power computing it; the visualiser shows the exact power, and you reduce at the end:

```visual traceTable
program: fastPower
input:
  base: 3
  exponent: 5
```

3⁵ = 243 = 34 × 7 + 5, and indeed 3 × 5 = 15 ≡ 1 (mod 7). In code, you reduce after every multiplication, as in [Fast exponentiation](/dsa/learn/math-fast-power):

```swift run
func modPow(_ base: Int, _ exponent: Int, _ m: Int) -> Int {
    var result = 1 % m
    var square = ((base % m) + m) % m
    var e = exponent
    while e > 0 {
        if e % 2 == 1 {
            result = result * square % m
        }
        square = square * square % m
        e /= 2
    }
    return result
}

print((1..<7).map { modPow($0, 5, 7) })
let p = 1_000_000_007
print(modPow(2, p - 2, p), 2 * modPow(2, p - 2, p) % p)
print(modPow(4, 3, 5), 12 * modPow(4, 3, 5) % 5)
```

```output
[1, 4, 5, 2, 3, 6]
500000004 1
4 3
```

The first line is the same table of inverses modulo 7 that extended Euclid produced in the last lesson, and 500,000,004 is the inverse of 2 again. The last line divides 12 by 4 modulo 5 one more time, getting 3.

Which should you use?

| | Fermat: a^(p − 2) | Extended Euclid |
| --- | --- | --- |
| Modulus | must be prime | anything coprime to a |
| Cost | O(log p) multiplications | O(log m) steps |
| Code to remember | `modPow`, which you have anyway | a few more lines |
| a ≡ 0 | silently returns 0 | reports no inverse |

With a prime modulus, Fermat is the usual choice because `modPow` is already in your toolkit. Reach for extended Euclid when the modulus isn't prime, or when you need to know an inverse doesn't exist.

## Shrinking huge exponents

Since a^(p − 1) ≡ 1, every block of p − 1 factors of a contributes nothing. So for a not divisible by p, you can **reduce the exponent modulo p − 1**:

```text
a^e ≡ a^(e mod (p − 1))   (mod p)
```

That lets you handle exponents that don't even fit in an `Int`. To find 3^(10¹⁰⁰) modulo 1,000,000,007, first find 10¹⁰⁰ modulo 1,000,000,006, which is itself a modular power:

```swift run
func modPow(_ base: Int, _ exponent: Int, _ m: Int) -> Int {
    var result = 1 % m
    var square = ((base % m) + m) % m
    var e = exponent
    while e > 0 {
        if e % 2 == 1 {
            result = result * square % m
        }
        square = square * square % m
        e /= 2
    }
    return result
}

let p = 1_000_000_007
let e = modPow(10, 100, p - 1)          // 10¹⁰⁰ reduced modulo p - 1
print(e, modPow(3, e, p))

// On an exponent that does fit, both routes agree
print(modPow(3, 1_000_000_000_000_000_000, p), modPow(3, 1_000_000_000_000_000_000 % (p - 1), p))
```

```output
372029464 9102203
246336683 246336683
```

<Callout kind="gotcha" title="Modulo p − 1, not p">
The exponent is reduced modulo **p − 1**, while the base is reduced modulo p. Mixing them up is the classic mistake. And the rule needs a to be coprime to p: 7⁶ ≡ 0 (mod 7), not 1, so "reducing" that exponent 6 to 0 would wrongly give 7⁰ = 1. For a composite modulus m, the exponent shrinks modulo φ(m) instead, which is the next lesson's topic.
</Callout>

Fermat's theorem also gives a quick way to prove a number is **not** prime: if a^(n − 1) mod n isn't 1, then n is composite. The converse fails, which is the story of the Miller–Rabin lesson, two lessons on.

## The Chinese remainder theorem

An old puzzle, from the Chinese mathematician Sunzi: a number leaves remainder 2 when divided by 3, remainder 3 when divided by 5, and remainder 2 when divided by 7. What is it?

```text
x ≡ 2 (mod 3)
x ≡ 3 (mod 5)
x ≡ 2 (mod 7)
```

The answer is 23, and also 23 + 105, 23 + 210 and so on: one answer in every block of 3 × 5 × 7 = 105. The **Chinese remainder theorem** says this always works when the moduli share no factors:

> If m₁, m₂, …, m_k are **pairwise coprime** (no two share a factor), then for any remainders r₁, …, r_k there's exactly one x from 0 to M − 1 with x ≡ rᵢ (mod mᵢ) for every i, where M = m₁ × m₂ × … × m_k.

**Why there's at most one.** If x and y both work, every mᵢ divides x − y. Pairwise coprime moduli dividing the same number means their product divides it too, so M divides x − y. Two different numbers below M can't differ by a multiple of M.

**Why there's at least one.** Count: there are M numbers below M, and M possible lists of remainders (m₁ choices for the first, m₂ for the second, and so on). Different numbers give different lists, as you just saw, so every list is used exactly once.

### The constructive formula

The counting argument doesn't say how to *find* x. This does. Let Mᵢ = M / mᵢ, the product of all the other moduli. Then build x out of one term per congruence:

```text
x = Σ rᵢ × Mᵢ × (Mᵢ⁻¹ mod mᵢ)      (mod M)
```

Each term is designed to do one job. Modulo mᵢ, the factor Mᵢ × Mᵢ⁻¹ is 1, so term i leaves rᵢ. Modulo any other mⱼ, Mᵢ is a multiple of mⱼ, so term i vanishes. Add them up, and each congruence sees only its own term. The inverse exists because Mᵢ is a product of moduli coprime to mᵢ.

```swift run
func extendedGCD(_ a: Int, _ b: Int) -> (g: Int, x: Int, y: Int) {
    var (oldR, r) = (a, b)
    var (oldS, s) = (1, 0)
    var (oldT, t) = (0, 1)
    while r != 0 {
        let q = oldR / r
        (oldR, r) = (r, oldR - q * r)
        (oldS, s) = (s, oldS - q * s)
        (oldT, t) = (t, oldT - q * t)
    }
    return (oldR, oldS, oldT)
}

func modInverse(_ a: Int, _ m: Int) -> Int? {
    let (g, x, _) = extendedGCD(((a % m) + m) % m, m)
    return g == 1 ? ((x % m) + m) % m : nil
}

// The constructive formula, for pairwise coprime moduli whose product is small
func crt(_ remainders: [Int], _ moduli: [Int]) -> Int {
    let total = moduli.reduce(1, *)
    var x = 0
    for (r, m) in zip(remainders, moduli) {
        let rest = total / m                      // the product of the other moduli
        let inverse = modInverse(rest, m)!        // exists because they're coprime
        x = (x + r * rest % total * inverse) % total
        print("m = \(m): rest = \(rest), inverse = \(inverse), term = \(r * rest * inverse)")
    }
    return x
}

print(crt([2, 3, 2], [3, 5, 7]))
```

```output
m = 3: rest = 35, inverse = 2, term = 140
m = 5: rest = 21, inverse = 1, term = 63
m = 7: rest = 15, inverse = 1, term = 30
23
```

140 + 63 + 30 = 233, and 233 − 2 × 105 = 23. Check the first term: 140 is 2 modulo 3, and a multiple of both 5 and 7.

This version only works while the products stay small: `r * rest * inverse` can be as big as M², and with M near 10¹⁸ that's far beyond an `Int`. Big moduli need a different shape.

## Merging two congruences at a time

In practice, CRT is done **one pair at a time**: merge the first two congruences into one, merge that with the third, and so on. This version handles big moduli safely, and it doesn't even need the moduli to be coprime.

To merge x ≡ a (mod m) with x ≡ b (mod n):

1. Every solution of the first is x = a + m × t for some whole number t.
2. Substitute into the second: a + m × t ≡ b, so **m × t ≡ b − a (mod n)**. That's a linear congruence in t, exactly the kind the last lesson solved.
3. With g = gcd(m, n), it's solvable only if g divides b − a. If not, the two congruences contradict each other. x ≡ 1 (mod 4) says x is odd, x ≡ 2 (mod 6) says it's even: no solution.
4. Otherwise t ≡ ((b − a) / g) × (m / g)⁻¹ (mod n / g), and x = a + m × t is the answer modulo **lcm(m, n)** = m / g × n.

When the moduli are coprime, g = 1 and the lcm is m × n, the ordinary CRT.

```swift run
func extendedGCD(_ a: Int, _ b: Int) -> (g: Int, x: Int, y: Int) {
    var (oldR, r) = (a, b)
    var (oldS, s) = (1, 0)
    var (oldT, t) = (0, 1)
    while r != 0 {
        let q = oldR / r
        (oldR, r) = (r, oldR - q * r)
        (oldS, s) = (s, oldS - q * s)
        (oldT, t) = (t, oldT - q * t)
    }
    return (oldR, oldS, oldT)
}

// a·b mod m for 0 ≤ a, b < m, through the full 128-bit product
func mulMod(_ a: Int, _ b: Int, _ m: Int) -> Int {
    m.dividingFullWidth(a.multipliedFullWidth(by: b)).remainder
}

// Combine x ≡ a (mod m) and x ≡ b (mod n), with 0 ≤ a < m and 0 ≤ b < n, into x ≡ value (mod lcm)
func merge(_ a: Int, _ m: Int, _ b: Int, _ n: Int) -> (value: Int, modulus: Int)? {
    let (g, p, _) = extendedGCD(m, n)          // m·p + n·q = g
    let difference = b - a
    guard difference % g == 0 else { return nil }
    let step = n / g                            // x = a + m·t, and t only matters modulo n / g
    let target = ((difference / g) % step + step) % step
    let inverse = ((p % step) + step) % step    // (m / g)·p ≡ 1 (mod n / g)
    let t = mulMod(target, inverse, step)
    return (a + m * t, m / g * n)               // a + m·t < lcm, so this can't overflow
}

print(merge(2, 3, 3, 5)!)
print(merge(8, 15, 2, 7)!)
print(merge(2, 4, 4, 6)!)
print(merge(1, 4, 2, 6) as Any)

let big = merge(5, 1_000_003, 777, 999_999_999_989)!
print(big)
print(big.value % 1_000_003, big.value % 999_999_999_989)
```

```output
(value: 8, modulus: 15)
(value: 23, modulus: 105)
(value: 10, modulus: 12)
nil
(value: 385999999996531, modulus: 1000002999988999967)
5 777
```

What to notice:

- **Sunzi's puzzle in two merges.** 2 (mod 3) and 3 (mod 5) give 8 (mod 15); that and 2 (mod 7) give 23 (mod 105).
- **Shared factors are fine.** x ≡ 2 (mod 4) and x ≡ 4 (mod 6) agree on parity, so they merge to 10 (mod 12). x ≡ 1 (mod 4) and x ≡ 2 (mod 6) don't, so the result is `nil`.
- **The extended Euclid coefficient p is the inverse.** m × p + n × q = g, divided by g, says (m / g) × p ≡ 1 (mod n / g). No separate inverse call is needed.
- **Every value stays below the lcm.** a is below m and t is below n / g, so a + m × t is at most (m − 1) + m × (n / g − 1), one less than the lcm. As long as the final lcm fits in an `Int`, nothing in the merge overflows, except one product.

### The one product that needs 128 bits

`target` and `inverse` are both below n / g. In the last example, n / g is about 10¹², so their product is about 10²⁴. Written as `target * inverse % step`, Swift traps:

```text title="What you'll see with target * inverse % step"
Swift runtime failure: arithmetic overflow
```

`mulMod` forms the exact 128-bit product with `multipliedFullWidth` and divides it with `dividingFullWidth`, as in [Modular arithmetic](/dsa/learn/math-modular-arithmetic). The order of the merge matters for how big that product gets, but rather than reason about it each time, always use the safe multiply.

<Callout kind="gotcha" title="Common mistakes with CRT">
- **Using the formula on moduli that share a factor.** The product formula needs pairwise coprime moduli; Mᵢ has no inverse otherwise. Merging handles every case, and reports contradictions.
- **Forgetting the answer is a congruence.** CRT gives x modulo the lcm. "The smallest non-negative solution" is the value in 0 to lcm − 1; every other solution differs by a multiple of the lcm.
- **Overflowing the intermediate product.** Remainders and moduli near 10¹⁸ need the full-width multiply, even though the final answer fits.
- **Negative differences.** b − a can be negative. Reduce `(b - a) / g` into 0 to n / g − 1 before multiplying.
</Callout>
