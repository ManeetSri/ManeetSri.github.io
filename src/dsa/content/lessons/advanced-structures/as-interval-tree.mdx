## Why it matters

A video editor's timeline is full of intervals: each clip, title and music track occupies a range of frames. As the playhead moves, the app must answer "which clips are on screen at frame 450?" many times a second, while the user keeps adding, trimming and deleting clips. A calendar asks "what clashes with 2pm to 3pm?", a genome browser asks which genes overlap a region, and a game asks which time-limited power-ups are active. An **interval tree** answers these questions in about O(log n) per result, and keeps doing so as intervals come and go. It's also the clearest example of **augmenting** a search tree: storing one extra number per node that lets whole subtrees be skipped.

## The overlap test

Two closed intervals `[a, b]` and `[c, d]` **overlap**, sharing at least one point, exactly when each starts before the other ends:

```text
a ≤ d  and  c ≤ b
```

You met this in [Interval intersections and free time](/dsa/learn/iv-intersections). It's easier to see from the opposite side: two intervals **don't** overlap only if one ends before the other starts (`b < c` or `d < a`). A single point p is the interval `[p, p]`, so "which intervals contain p?" is the same question.

## When sorting isn't enough

In M33 you answered interval questions by sorting and sweeping, as in [Sweep-line events](/dsa/learn/iv-sweep-line). That works when every interval and every question is known up front: an **offline** problem. A timeline is **online**: queries arrive one at a time, mixed with inserts and deletes. Re-sorting after every change costs O(n log n), and scanning every interval for each query costs O(n). With 20,000 clips and a query per frame, that's too slow.

Could a BST ordered by start help? It finds the intervals that **start** before frame 450 quickly, but that's not the question: an interval starting at frame 0 might end at 100 or at 10,000. Starts alone can't tell you which subtrees to skip.

## The augmentation: the latest end below

Build a BST ordered by **start**, and give every node one extra field: **`maxEnd`, the largest end of any interval in its subtree**, itself included.

```text
                      [240, 719] max 1199
                     /                   \
       [0, 239] max 239                  [1080, 1199] max 1199
               \                        /                    \
          [0, 47] max 47     [400, 520] max 520      [1100, 1199] max 1199
```

(That's the timeline from the next section, without its music track.) Now a search for the intervals overlapping a query `[start, end]` can rule out whole subtrees with two tests:

1. **If a subtree's `maxEnd` is less than `start`**, every interval in it ends before the query begins. Skip the whole subtree.
2. **If a node's own start is greater than `end`**, then so is every start in its right subtree, because the right side holds larger starts. None of them can overlap: skip the right subtree.

Everything else might hold an answer, so the search visits it. Querying frame 450 in the tree above: the left subtree's `maxEnd` is 239, which is less than 450, so it's skipped entirely, without looking at `[0, 47]` at all. Add the music track, `[0, 1199]`, and it lands in that left subtree, raising its `maxEnd` to 1199: now the search must go in, and it finds the music.

## Building it

Here's the timeline as an interval tree. Intervals with the same start are ordered by label, so equal starts are no problem:

```swift run
struct SeededGenerator: RandomNumberGenerator {
    var state: UInt64
    mutating func next() -> UInt64 {
        state &+= 0x9E37_79B9_7F4A_7C15
        var z = state
        z = (z ^ (z >> 30)) &* 0xBF58_476D_1CE4_E5B9
        z = (z ^ (z >> 27)) &* 0x94D0_49BB_1331_11EB
        return z ^ (z >> 31)
    }
}

// A BST of closed intervals ordered by start, where every node also knows the latest end below it
final class IntervalTree {
    final class Node {
        let start: Int
        let end: Int
        let label: String
        var maxEnd: Int                          // the largest end in this node's subtree
        var left: Node?
        var right: Node?

        init(_ start: Int, _ end: Int, _ label: String) {
            self.start = start
            self.end = end
            self.label = label
            maxEnd = end
        }
    }

    private var root: Node?
    var visited = 0                              // nodes looked at by queries

    func insert(_ start: Int, _ end: Int, _ label: String) {
        root = insert(Node(start, end, label), into: root)
    }

    private func insert(_ new: Node, into node: Node?) -> Node {
        guard let node else { return new }
        if (new.start, new.label) < (node.start, node.label) {
            node.left = insert(new, into: node.left)
        } else {
            node.right = insert(new, into: node.right)
        }
        node.maxEnd = max(node.maxEnd, new.end)  // the new interval is now below this node
        return node
    }

    // Every interval that shares at least one point with start...end, in order of start
    func overlapping(_ start: Int, _ end: Int) -> [String] {
        var result: [String] = []
        func search(_ node: Node?) {
            guard let node else { return }
            visited += 1
            if node.maxEnd < start { return }    // everything here ends too early: skip it all
            search(node.left)
            if node.start <= end && start <= node.end {
                result.append(node.label)
            }
            if node.start <= end {               // the right side starts at node.start or later
                search(node.right)
            }
        }
        search(root)
        return result
    }
}

// Clips on a video timeline, by frame number
let timeline = IntervalTree()
let clips = [(240, 719, "interview"), (0, 239, "intro"), (1080, 1199, "credits"), (0, 1199, "music"),
             (400, 520, "b-roll"), (0, 47, "title"), (1100, 1199, "logo")]
for (start, end, label) in clips {
    timeline.insert(start, end, label)
}
print("frame 450:", timeline.overlapping(450, 450))
print("frames 700...1090:", timeline.overlapping(700, 1090))
print("frame 1200:", timeline.overlapping(1200, 1200))

// 20,000 random intervals: how much of the tree does a query look at?
var generator = SeededGenerator(state: 33)
var all: [(Int, Int)] = []
let big = IntervalTree()
for index in 0..<20_000 {
    let start = Int(generator.next() % 1_000_000)
    let end = start + Int(generator.next() % 1_000)
    all.append((start, end))
    big.insert(start, end, String(index))
}
var matches = true
var found = 0
for _ in 0..<1_000 {
    let point = Int(generator.next() % 1_000_000)
    let answer = big.overlapping(point, point)
    let expected = all.indices.filter { all[$0].0 <= point && point <= all[$0].1 }.count
    found += answer.count
    if answer.count != expected { matches = false }
}
print("matches brute force:", matches)
print("average found:", found / 1_000, " average nodes visited:", big.visited / 1_000, "of", all.count)
```

```output
frame 450: ["music", "interview", "b-roll"]
frames 700...1090: ["music", "interview", "credits"]
frame 1200: []
matches brute force: true
average found: 9  average nodes visited: 41 of 20000
```

What to notice:

- **The results come out sorted by start**, because the search is an inorder walk with pieces cut off.
- **`maxEnd` is updated on the way back up** from every insert: each node on the path now has the new interval somewhere below it.
- **Frame 1200 returns nothing**, and quickly: the root's `maxEnd` is 1199, so the very first test skips the whole tree.
- **A query looked at 41 of 20,000 nodes on average** while reporting about 9 intervals. A scan of every interval would look at all 20,000, every time.

## How fast is it?

Each test either reports an interval or prunes, but the pruning isn't perfect: the search sometimes walks into a subtree whose `maxEnd` promised an overlap that turns out to lie deeper. The textbook analysis gives:

- **Is anything overlapping?** O(log n) in a balanced tree: one path, choosing a side at each node.
- **Report all k overlaps:** O(min(n, k log n)). Each reported interval costs at most one root-to-leaf path. In practice, as the measurement shows, it's far closer to O(log n + k).

A different design, the **centred interval tree**, guarantees O(log n + k), but it's built once from a fixed set of intervals; the augmented BST is the one that handles inserts and deletes gracefully.

## Keeping maxEnd right

Every change must leave each node's `maxEnd` equal to the largest of three numbers: its own end, and its children's `maxEnd` values. One helper does it:

```swift
func update(_ node: Node) {
    node.maxEnd = max(node.end, node.left?.maxEnd ?? Int.min, node.right?.maxEnd ?? Int.min)
}
```

- **Insert** can update on the way back up, as above.
- **Delete** changes the subtrees along one path, so call `update` on every node of that path, bottom up.
- **Rotations** change two nodes' subtrees. After a rotation, update the node that moved **down** first, then the one that moved up, since the new parent's value depends on its new child. It's the same order you used for heights in [AVL trees: insert and delete](/dsa/learn/bal-avl).

That last point matters, because the tree above is only fast if it's **balanced**. The demo inserted intervals in random order, which keeps a plain BST shallow. Insert clips in timeline order, as an editor often does, and it degenerates into a chain, exactly as in [Why unbalanced BSTs degrade to O(n)](/dsa/learn/bst-degenerate). A real interval tree is an AVL tree, red-black tree or treap, ordered by start, with `update` called wherever the balancing code recalculates a height or a size. With a treap from [Treaps: split and merge](/dsa/learn/bal-treap), that's one line inside split and merge.

## Choosing a tool for intervals

| Situation | Tool | Cost |
| --- | --- | --- |
| A handful of intervals | check each one | O(n) per query |
| All intervals and queries known up front | sort and sweep (M33) | O(n log n) in total |
| Intervals never change, queries online | sorted array of starts, or a centred interval tree | O(log n + k) per query |
| Intervals added and removed, queries online | **interval tree** (augmented balanced BST) | O(log n) per change |
| Only counts, over a fixed range of coordinates | difference array, or a segment tree from M60 | O(log n) per change |

<Callout kind="gotcha" title="Closed, half-open, and the off-by-one">
This lesson uses closed intervals, so `[0, 239]` and `[239, 300]` overlap at frame 239. Calendars usually use half-open ones, `[start, end)`, where a meeting ending at 11:00 doesn't clash with one starting at 11:00. For half-open intervals, the overlap test becomes `a < d && c < b`, and both pruning tests change from `<` to `<=` (skip a subtree whose `maxEnd <= start`). Decide which you have before writing any comparisons, and test the touching case.
</Callout>

<Callout kind="gotcha" title="Common mistakes">
- **A stale `maxEnd`.** Forgetting to recompute it after a delete or a rotation makes the search skip subtrees that hold answers. The bug is silent: queries quietly miss intervals.
- **Pruning the left subtree by start.** The left side's starts are all smaller, so they say nothing about overlap. Only `maxEnd` can rule out a left subtree.
- **Equal starts.** Several intervals can share a start. Break ties with something unique, such as an id, so insert and delete agree on where an interval lives.
</Callout>
