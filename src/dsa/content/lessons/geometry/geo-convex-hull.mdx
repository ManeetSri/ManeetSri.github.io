## Why it matters

The **convex hull** of a set of points is the smallest convex polygon that contains them all. It's the first step of a surprising number of geometry algorithms: the two points farthest apart are always corners of the hull, collision checks get cheap once shapes are convex (SpriteKit's `SKPhysicsBody(polygonFrom:)` expects a convex path, for example), and the outline of a cluster of map pins or a blob in an image is a hull. It's also the classic O(n log n) geometry algorithm. This lesson builds **Andrew's monotone chain**, the version to reach for, makes its policy on collinear points explicit, and then sketches **Graham's scan**, the older algorithm you'll see in textbooks.

## What the hull is

<Callout kind="analogy" title="A rubber band round nails">
Hammer a nail into a board at every point, stretch a rubber band round all of them and let go. The band snaps tight against the outermost nails. The shape it makes is the convex hull, and the nails it bends round are the hull's corners.
</Callout>

Every corner of the hull is one of the input points, an **extreme** point that sticks out in some direction. Every other point is inside the hull or on its boundary. Here's the set of points this lesson uses:

```text
y
5   .  .  #  .  o  #  .
4   .  .  .  .  .  .  .         # a corner of the hull
3   #  .  .  o  .  .  .         o another input point
2   .  .  o  .  o  .  #
1   .  .  .  .  .  .  .
0   .  #  .  o  #  .  .
    0  1  2  3  4  5  6   x
```

The hull's corners, counterclockwise from the leftmost, are (0, 3), (1, 0), (4, 0), (6, 2), (5, 5) and (2, 5). Three points are strictly inside: (2, 2), (3, 3) and (4, 2). Two more sit **on** the boundary without being corners: (3, 0) is on the bottom edge between (1, 0) and (4, 0), and (4, 5) is on the top edge between (5, 5) and (2, 5).

### The collinear policy

Those last two raise a question that every hull problem answers differently: are points on an edge, but not at a corner, part of the hull? A fence needs posts only at its corners, so a "corners only" hull leaves them out. A question like "which trees touch the fence?" keeps them. **Decide before you code**, because the difference is one character. This lesson's main version returns **corners only**; a later section keeps the rest.

## Andrew's monotone chain

The idea is to build the hull in two halves. The **lower hull** runs along the bottom of the point set from the leftmost point to the rightmost; the **upper hull** runs along the top from the rightmost back to the leftmost. Together they go round counterclockwise.

1. Sort the points by x, and by y when x ties. Drop duplicates.
2. **Lower hull:** go through the points from left to right, keeping a stack. Before pushing each point p, look at the top two points of the stack, a and b. If a → b → p doesn't turn strictly left (orientation ≤ 0), b can't be a corner of the lower hull, so pop it. Repeat until the top two do turn left with p (or fewer than two remain), then push p.
3. **Upper hull:** exactly the same, going through the points from right to left.
4. Join the two, dropping the last point of each: the lower hull ends at the rightmost point, which the upper hull starts with, and vice versa.

Why popping is right: walking left to right along the bottom of a convex shape, you only ever turn left. If a → b → p turns right or goes straight on, b lies above or on the segment from a to p, so p and a "see under" b, and b can't be on the bottom boundary. Removing b may expose another right turn behind it, which is why the pops repeat.

Here's the lower hull being built for the lesson's points, sorted by (x, y):

| Point | Popped (and why) | Stack afterwards |
| --- | --- | --- |
| (0, 3) | | (0, 3) |
| (1, 0) | | (0, 3) (1, 0) |
| (2, 2) | | (0, 3) (1, 0) (2, 2) |
| (2, 5) | | (0, 3) (1, 0) (2, 2) (2, 5) |
| (3, 0) | (2, 5), then (2, 2): right turns | (0, 3) (1, 0) (3, 0) |
| (3, 3) | | (0, 3) (1, 0) (3, 0) (3, 3) |
| (4, 0) | (3, 3): right turn; (3, 0): **straight on** | (0, 3) (1, 0) (4, 0) |
| (4, 2) | | (0, 3) (1, 0) (4, 0) (4, 2) |
| (4, 5) | (4, 2): straight on (vertical) | (0, 3) (1, 0) (4, 0) (4, 5) |
| (5, 5) | (4, 5): right turn | (0, 3) (1, 0) (4, 0) (5, 5) |
| (6, 2) | (5, 5): right turn | (0, 3) (1, 0) (4, 0) (6, 2) |

Notice the row for (4, 0). The turn (1, 0) → (3, 0) → (4, 0) is straight on, orientation 0, and `≤ 0` pops (3, 0). That's the corners-only policy at work.

```swift run
struct Point: Comparable {
    var x: Int
    var y: Int

    static func < (lhs: Point, rhs: Point) -> Bool {
        (lhs.x, lhs.y) < (rhs.x, rhs.y)
    }

    static func - (lhs: Point, rhs: Point) -> Point {
        Point(x: lhs.x - rhs.x, y: lhs.y - rhs.y)
    }

    func cross(_ other: Point) -> Int {
        x * other.y - y * other.x
    }
}

extension Point: CustomStringConvertible {
    init(_ x: Int, _ y: Int) {
        self.init(x: x, y: y)
    }

    var description: String { "(\(x), \(y))" }
}

func orientation(_ a: Point, _ b: Point, _ c: Point) -> Int {
    (b - a).cross(c - a)
}

/// One chain of Andrew's algorithm: pop until the last two points and p turn strictly left
func chain(_ ordered: [Point]) -> [Point] {
    var stack: [Point] = []
    for p in ordered {
        while stack.count >= 2 && orientation(stack[stack.count - 2], stack[stack.count - 1], p) <= 0 {
            stack.removeLast()
        }
        stack.append(p)
    }
    return stack
}

/// The corners of the convex hull, counterclockwise from the smallest (x, y)
func convexHull(_ input: [Point]) -> [Point] {
    var points: [Point] = []
    for p in input.sorted() where points.last != p {
        points.append(p)                     // sorted, so duplicates are neighbours
    }
    if points.count < 3 {
        return points
    }
    let lower = chain(points)
    let upper = chain(points.reversed())
    print("lower:", lower)
    print("upper:", upper)
    return lower.dropLast() + upper.dropLast()
}

let points = [Point(2, 2), Point(4, 0), Point(1, 0), Point(6, 2), Point(3, 3), Point(5, 5),
              Point(0, 3), Point(3, 0), Point(4, 2), Point(2, 5), Point(4, 5)]
print("hull:", convexHull(points))
```

```output
lower: [(0, 3), (1, 0), (4, 0), (6, 2)]
upper: [(6, 2), (5, 5), (2, 5), (0, 3)]
hull: [(0, 3), (1, 0), (4, 0), (6, 2), (5, 5), (2, 5)]
```

What to notice:

- `Comparable` with a tuple comparison gives the (x, y) order, so `sorted()` needs no closure. That's the [tuple trick from sorting custom types](/dsa/learn/sort-swift-sort).
- The two chains are the same function. Reversing the sorted points turns "along the bottom, left to right" into "along the top, right to left", and left turns are still what a counterclockwise walk makes.
- `lower.dropLast() + upper.dropLast()` removes (6, 2) from the end of the lower chain and (0, 3) from the end of the upper, so every corner appears once.
- The result starts at the smallest (x, y) and runs counterclockwise. Many problems ask for exactly that order, and Andrew's gives it for free.

### How long it takes

Sorting costs O(n log n). Each chain pushes every point once, and a point can be popped at most once after it's pushed, so the pops across the whole loop number at most n: the chains are **O(n)** in total, even though one step can pop many points. (That's the same amortised argument as the [monotonic stack](/dsa/learn/stack-monotonic-intro).) So Andrew's algorithm is **O(n log n)** time and O(n) space, all in the sort.

You can't do better in general. Put the numbers you want to sort onto the curve y = x², as points (x, x²). Every one of them is a hull corner, and walking the hull visits them in sorted order. So a hull algorithm that beat O(n log n) would sort faster than any comparison sort can.

The O(n²) curve is what the simplest alternative, **gift wrapping** (Jarvis march), costs when most points are corners: it finds each corner by checking every point. It costs O(n × h) for h corners, so it's fine when the hull is small and hopeless on the parabola above.

## Edge cases

Three inputs break careless hull code:

- **Duplicates.** Without the dedupe step, three copies of one point come out as `[p, p]`: each chain keeps two copies, since popping needs two points below the new one. Sorting puts duplicates next to each other, so `points.last != p` removes them in the same pass.
- **Fewer than three distinct points.** Zero, one or two points are their own hull. The chains would mangle a single point (each chain's only point is dropped by `dropLast`), so return early.
- **All points on one line.** Every middle point is "straight on" and gets popped, so the lower chain is `[first, last]`, the upper chain `[last, first]`, and the hull is the two ends. Whether a "polygon" with two corners is acceptable depends on the problem; the corners-only policy makes it the natural answer.

With the debugging prints taken out, the function above gives:

```swift
print(convexHull([Point(4, 4), Point(4, 4), Point(4, 4)]))           // [(4, 4)]
print(convexHull([Point(5, 0), Point(1, 2)]))                        // [(1, 2), (5, 0)]
print(convexHull([Point(1, 1), Point(3, 3), Point(2, 2), Point(5, 5)]))   // [(1, 1), (5, 5)]
```

## Keeping points on the edges

To keep boundary points that aren't corners, pop only on **right** turns: change `<= 0` to `< 0`, so straight-on points stay. Two things then need care:

- **Deduplicate first**, as before. Two copies of a point make a "straight on" turn, so with `< 0` both would stay.
- **All points collinear.** Now nothing is ever popped: the lower chain holds every point, and the upper chain holds them all again, backwards. Detect the straight line first and return the sorted points once.

```swift run
struct Point: Comparable {
    var x: Int
    var y: Int

    static func < (lhs: Point, rhs: Point) -> Bool {
        (lhs.x, lhs.y) < (rhs.x, rhs.y)
    }

    static func - (lhs: Point, rhs: Point) -> Point {
        Point(x: lhs.x - rhs.x, y: lhs.y - rhs.y)
    }

    func cross(_ other: Point) -> Int {
        x * other.y - y * other.x
    }
}

extension Point: CustomStringConvertible {
    init(_ x: Int, _ y: Int) {
        self.init(x: x, y: y)
    }

    var description: String { "(\(x), \(y))" }
}

func orientation(_ a: Point, _ b: Point, _ c: Point) -> Int {
    (b - a).cross(c - a)
}

/// The hull counterclockwise from the smallest (x, y). With keepCollinear, points on an edge between
/// two corners are included too.
func convexHull(_ input: [Point], keepCollinear: Bool) -> [Point] {
    var points: [Point] = []
    for p in input.sorted() where points.last != p {
        points.append(p)
    }
    if points.count < 3 {
        return points
    }
    if keepCollinear && points.allSatisfy({ orientation(points[0], points[1], $0) == 0 }) {
        return points                        // one straight line: every point is on the boundary
    }
    func chain(_ ordered: [Point]) -> [Point] {
        var stack: [Point] = []
        for p in ordered {
            while stack.count >= 2 {
                let turn = orientation(stack[stack.count - 2], stack[stack.count - 1], p)
                guard turn < 0 || (turn == 0 && !keepCollinear) else { break }
                stack.removeLast()
            }
            stack.append(p)
        }
        return stack
    }
    return chain(points).dropLast() + chain(points.reversed()).dropLast()
}

let points = [Point(2, 2), Point(4, 0), Point(1, 0), Point(6, 2), Point(3, 3), Point(5, 5),
              Point(0, 3), Point(3, 0), Point(4, 2), Point(2, 5), Point(4, 5)]
print(convexHull(points, keepCollinear: false))
print(convexHull(points, keepCollinear: true))
print(convexHull([Point(0, 0), Point(2, 2), Point(1, 1), Point(1, 1)], keepCollinear: true))
```

```output
[(0, 3), (1, 0), (4, 0), (6, 2), (5, 5), (2, 5)]
[(0, 3), (1, 0), (3, 0), (4, 0), (6, 2), (5, 5), (4, 5), (2, 5)]
[(0, 0), (1, 1), (2, 2)]
```

(3, 0) and (4, 5) now appear, each in its place along its edge. Points on a vertical edge at the far left or right work too: the ones on the right edge come out in the lower chain going up, and the ones on the left edge in the upper chain going down.

## Graham's scan, in outline

Graham's scan (1972) predates Andrew's (1979) and uses the same stack, but sorts by **angle** instead of by x:

1. Pick a **pivot**: the lowest point, taking the leftmost if several tie. It's certainly a hull corner.
2. Sort the other points by the angle they make with the pivot, counterclockwise. No trigonometry needed: a comes before b when cross(a − pivot, b − pivot) > 0, and if they're collinear with the pivot, the nearer one first.
3. Scan them in that order with a stack, popping while the last two and the new point fail to turn left, exactly as in one of Andrew's chains.

```swift
let pivot = points.min { ($0.y, $0.x) < ($1.y, $1.x) }!
let rest = points.filter { $0 != pivot }.sorted { a, b in
    let (u, v) = (a - pivot, b - pivot)
    let turn = u.cross(v)
    if turn != 0 { return turn > 0 }                    // b is counterclockwise of a: a comes first
    return u.x * u.x + u.y * u.y < v.x * v.x + v.y * v.y    // same direction: nearer first
}
// then one stack pass over [pivot] + rest, popping while orientation ≤ 0
```

On the lesson's points, the pivot is (1, 0) and Graham's scan finds the same six corners, starting from (1, 0) instead of (0, 3).

Why is a cross-product comparison a valid sort order? Because the pivot is the lowest point, every other point is above it or level with it to the right, so all their directions lie within half a turn. Within half a turn, "counterclockwise of" never goes round in a circle, so the comparison is a strict weak ordering, the rule from [How Swift sorts, and sorting custom types](/dsa/learn/sort-swift-sort). Without that half-turn guarantee it isn't, and the sort misbehaves.

| | Andrew's monotone chain | Graham's scan |
| --- | --- | --- |
| Sort by | (x, y): plain tuple comparison | angle around the lowest point |
| Collinear points | one `<` or `≤` | also needs the last ray sorted farthest first |
| Output starts at | the leftmost point | the lowest point |
| Time | O(n log n) | O(n log n) |

They're equally fast. Andrew's is easier to get right: its sort is trivial, and Graham's angle sort has a well-known trap when you keep collinear points (the points on the final ray must come farthest first, or they're scanned in the wrong order). That's why it's the version in this course's practice problem.

## What a hull is good for

- **The farthest pair** of points is always two hull corners. After building the hull, a technique called **rotating calipers** finds it in O(h) more time, by walking two pointers round the hull together.
- **Point in a convex polygon** takes O(log n) instead of O(n): fan the polygon into triangles from one corner, binary search for the triangle whose wedge contains the point, then do one orientation test.
- **Area and perimeter** of the region a point set spans: the shoelace formula from [Polygon area and point in polygon](/dsa/learn/geo-polygons), applied to the hull.

<Callout kind="gotcha" title="Hull bugs that pass the first test">
- **`<= 0` or `< 0`?** That single character is your collinear policy. Write down which one the problem wants.
- **Sorting by x alone.** Points with equal x must be ordered by y too, or vertical edges come out wrong.
- **No dedupe.** Duplicates survive into the output, or break the collinear version.
- **Fewer than three points.** `dropLast()` on two one-point chains returns an empty hull.
- **Overflow.** Orientation multiplies coordinate differences: fine up to 10⁹, as [Cross product and orientation](/dsa/learn/geo-cross-orientation) worked out, and not beyond.
</Callout>
