## Why it matters

Whole-number geometry is exact, but some answers aren't whole: crossing points, distances, angles, rotations. And plenty of real data arrives as `Double` from the start: CoreGraphics measures everything in `CGFloat`, a 64-bit floating-point number on iPhone, iPad and Mac, and MapKit hands you latitudes and longitudes in degrees. Once `Double`s are involved, `==` stops meaning what you want, and geometry is full of exactly-zero questions. [Double, Float and floating-point precision](/dsa/learn/swift-floating-point) gave the basic fix, comparing with a tolerance. This lesson makes it work for geometry: which tolerance, when it breaks, and how to avoid needing one at all.

## Why == fails in geometry

```swift run
import Foundation

let angle = Double.pi / 2
let turned = (x: cos(angle), y: sin(angle))        // (1, 0) turned a quarter-turn counterclockwise
print(turned.x == 0, turned.y == 1)
print(String(format: "%.3e", turned.x))

// The crossing point of the lines through (1, 2)–(9, 5) and (2, 8)–(7, 1), computed in Double
let (ax, ay, rx, ry) = (1.0, 2.0, 8.0, 3.0)        // first line: a + t·r
let (cx, cy, sx, sy) = (2.0, 8.0, 5.0, -7.0)       // second line: c + u·s
let t = ((cx - ax) * sy - (cy - ay) * sx) / (rx * sy - ry * sx)
let (px, py) = (ax + t * rx, ay + t * ry)
let onFirstLine = rx * (py - ay) - ry * (px - ax)  // the orientation of p: exactly 0 in real maths
print(onFirstLine == 0, abs(onFirstLine) < 1e-9)
print(String(format: "%.2e", onFirstLine))
```

```output
false true
6.123e-17
false true
1.78e-15
```

π isn't exactly representable, so `cos(π/2)` comes out as 6 × 10⁻¹⁷ instead of 0. And the crossing point, computed by the formula from [Segment intersection](/dsa/learn/geo-segment-intersection), lands about 10⁻¹⁵ off the very line it was computed from. An orientation test that asks `== 0` would say p isn't on its own line. The errors are tiny, but `==` doesn't care how tiny.

## Absolute tolerance

The first fix is the one you know: call two numbers equal when they differ by at most a small **tolerance**, often written ε (epsilon):

```swift
abs(a - b) <= 1e-9
```

That's an **absolute** tolerance, and it works well when you know the size of the numbers in advance, say coordinates between 1 and 1,000. It goes wrong when the numbers are much bigger or much smaller, because a `Double` keeps about 16 significant digits wherever the decimal point is. The gap between a `Double` and the next one up, its **ulp** (unit in the last place), grows with the number:

```swift run
import Foundation

for value in [1e-12, 1.0, 1_000.0, 1e9] {
    print(String(format: "%-6g gap to the next Double: %.2e", value, value.ulp))
}
```

```output
1e-12  gap to the next Double: 2.02e-28
1      gap to the next Double: 2.22e-16
1000   gap to the next Double: 1.14e-13
1e+09  gap to the next Double: 1.19e-07
```

Near 10⁹, neighbouring `Double`s are more than 10⁻⁷ apart, so "within 10⁻⁹" is just `==` again. Near 10⁻¹², a tolerance of 10⁻⁹ is a thousand times bigger than the numbers themselves, so everything is "equal".

## Relative tolerance

A **relative** tolerance scales with the numbers: equal when they differ by at most, say, a billionth of the larger one, |a − b| ≤ ε × max(|a|, |b|). That handles big and small numbers alike, but it fails at zero: nothing except 0 is within a billionth of 0, and geometry constantly compares with 0. So the usual rule combines the two, and accepts whichever allows more:

```swift run
func isClose(_ a: Double, _ b: Double, relative: Double = 1e-9, absolute: Double = 1e-12) -> Bool {
    abs(a - b) <= max(absolute, relative * max(abs(a), abs(b)))
}

print(isClose(0.1 + 0.2, 0.3))                       // everyday sizes
print(isClose(1e9 + 0.1, 1e9), abs((1e9 + 0.1) - 1e9) <= 1e-9)   // relative copes; absolute doesn't
print(isClose(1e-15, 0), isClose(1e-6, 0))           // near zero, the absolute part decides
print(isClose(2.0, 2.000001))                        // a real difference stays a difference
```

```output
true
true false
true false
false
```

Pick the tolerances for your data: the relative one from how many digits you trust (about 16 at best, fewer after long calculations), the absolute one from the smallest difference that's meaningful. Apple's open-source Swift Numerics package has the same idea built in, as `isApproximatelyEqual(to:relativeTolerance:)`.

## Signs with a tolerance

Geometry mostly needs **signs**: left or right, inside or outside. With `Double`s, treat anything within the tolerance of zero as zero:

```swift
func sign(_ value: Double, tolerance: Double = 1e-9) -> Int {
    value > tolerance ? 1 : (value < -tolerance ? -1 : 0)
}
// orientation of a, b, c with Double coordinates:
// sign((b.x - a.x) * (c.y - a.y) - (b.y - a.y) * (c.x - a.x))
```

Mind the units. A cross product multiplies two lengths, so with coordinates around 1,000 its values, and its rounding errors, are around a million times bigger than with coordinates around 1. Scale the tolerance to match, or make it relative to the coordinates' size.

### Tolerance isn't equality

One property of `==` doesn't survive: **transitivity**. With a tolerance of 10⁻⁹, 0 is close to 0.6 × 10⁻⁹, which is close to 1.2 × 10⁻⁹, but 0 isn't close to 1.2 × 10⁻⁹. So:

- **Don't hash with it.** `Hashable` needs a real equality. To group nearly equal points, **snap** them to a grid first, `((x * 1e6).rounded(), (y * 1e6).rounded())`, and hash that, accepting that two very close points can still land either side of a grid line.
- **Don't sort with it.** A comparator like "less than by more than ε" breaks the strict weak ordering from [How Swift sorts, and sorting custom types](/dsa/learn/sort-swift-sort). Sort by the exact values; use the tolerance only when you compare neighbours afterwards.

## Better still: stay in integers

The tolerance is a patch. The cure is not to need one, which is what every lesson in this module has done:

- **Decide with integers, compute with Doubles at the end.** Orientation, intersection tests, inside or outside, the convex hull and the closest pair were all exact `Int` arithmetic. Only final answers, like a crossing point or a distance, became `Double`.
- **Scale fixed decimals to integers.** Coordinates given to two decimal places become whole numbers of hundredths: 12.34 becomes 1234. Convert with rounding, though: `Int(0.29 * 100)` is 28, because `0.29 * 100` is 28.999999999999996. Write `Int((0.29 * 100).rounded())`.
- **Keep fractions as fractions.** A crossing parameter t = p / q can be stored as the pair (p, q), with q positive, and two of them compared by cross-multiplying: p₁ × q₂ < p₂ × q₁, exact in `Int`.

## Apple platforms

User interfaces are the friendliest place for floating point: Apple recommends tap targets at least 44 points across, so a target's size is its own tolerance, and CoreGraphics' `CGRect.intersects(_:)`, `CGRect.contains(_:)` and `CGPath.contains(_:using:transform:)` (with the fill rules from [Polygon area and point in polygon](/dsa/learn/geo-polygons)) are all floating point, and fine for it. Maps are trickier: latitude and longitude are angles on a sphere, so this module's flat formulas only approximate small areas. For real distances use `CLLocation`'s `distance(from:)`, which measures in metres along the Earth's surface, or convert coordinates to `MKMapPoint`s, which live on a flat map projection, before doing plane geometry.

<Callout kind="gotcha" title="Floating-point geometry traps">
- **Negative zero.** A result that should be 0 can come out as a tiny negative number, and `String(format: "%.2f", -0.001)` prints `-0.00`. Snap values within your tolerance to exactly 0 before printing.
- **Dividing by a near-zero denominator.** Parallel lines give a denominator of 0 (and 0 / 0 is NaN), or nearly parallel ones a huge, meaningless crossing point. Decide "parallel?" first, exactly if you can.
- **One tolerance for everything.** Lengths, areas and angles have different sizes and units; a tolerance chosen for one can be far too big or too small for another.
- **A tolerance that's too big.** It merges points that really are different. Too small, and it's `==` with extra steps.
</Callout>
