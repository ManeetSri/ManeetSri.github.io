## Why it matters

**Dynamic programming** (DP) is behind a surprising amount of everyday software. The "did you mean" suggestion in a search box measures how many edits separate two words. Diff tools, like the one behind `git diff`, line up the longest sequence of lines two files share. Text layout engines choose where to break lines so a paragraph looks even. All of them are built on DP. In interviews, DP is the largest single family of medium and hard problems.

DP isn't a data structure or one particular algorithm. It's a way of noticing that a problem keeps asking the same smaller questions, and answering each of them once. This lesson is about *when* that works. The rest of the module is about *how*, and it builds a five-word vocabulary that every later DP module uses: **state, transition, base case, order, answer**.

## The waste in plain recursion

You met this in [Multiple recursion and exponential blow-up](/dsa/learn/rec-multiple-recursion): the plain recursive Fibonacci function is exponential. Here's exactly where the time goes. The program counts how many times each `fib(k)` is computed during one call to `fib(10)`:

```swift run
var asked = Array(repeating: 0, count: 11)

func fib(_ n: Int) -> Int {
    asked[n] += 1
    if n < 2 {
        return n
    }
    return fib(n - 1) + fib(n - 2)
}

print("fib(10) =", fib(10))
for k in stride(from: 10, through: 0, by: -1) {
    print("fib(\(k)) computed", asked[k], asked[k] == 1 ? "time" : "times")
}
print("total calls:", asked.reduce(0, +), "for", asked.count, "different questions")
```

```output
fib(10) = 55
fib(10) computed 1 time
fib(9) computed 1 time
fib(8) computed 2 times
fib(7) computed 3 times
fib(6) computed 5 times
fib(5) computed 8 times
fib(4) computed 13 times
fib(3) computed 21 times
fib(2) computed 34 times
fib(1) computed 55 times
fib(0) computed 34 times
total calls: 177 for 11 different questions
```

There are only 11 different questions, `fib(0)` to `fib(10)`, yet the recursion asks 177. The repeat counts are themselves Fibonacci numbers, so they grow by about 1.6 times with every step up in n. For `fib(30)` it's 2,692,537 calls for 31 questions.

Watch the repeats in the call tree. `fib(3)` appears twice, `fib(2)` three times, and each copy redoes all the work beneath it:

```visual recursionTree
fn: fibonacci
n: 5
```

## Overlapping subproblems

A **subproblem** is a smaller instance of the same question: `fib(8)` is a subproblem of `fib(10)`. A problem has **overlapping subproblems** when a plain recursion meets the same subproblem many times. That's the first of two properties that make DP work, and it's what makes it *pay*.

The tell-tale sign is a gap between two numbers:

- the number of **calls** the plain recursion makes, which is exponential; and
- the number of **different subproblems**, which is small: here n + 1.

When that gap is large, answering each different subproblem once, and looking it up every other time, turns an exponential algorithm into a polynomial one. You did exactly that with a dictionary in [A preview of memoisation](/dsa/learn/rec-memo-preview).

## The subproblem graph is a DAG

Draw each *different* subproblem once, as a vertex, with an arrow from a problem to each subproblem it needs:

```text
fib(5) → fib(4), fib(3)
fib(4) → fib(3), fib(2)
fib(3) → fib(2), fib(1)
fib(2) → fib(1), fib(0)
fib(1)            (no arrows: a base case)
fib(0)            (no arrows: a base case)
```

Six vertices and eight arrows, against 15 calls in the tree above. The tree is this graph *unfolded*: every time two arrows point at the same vertex, the tree makes a separate copy of everything below it.

Every arrow points to a smaller n, so you can never follow arrows round in a circle. The subproblem graph is a **directed acyclic graph**, a DAG, exactly the kind of graph you sorted in [DAGs and dependency ordering](/dsa/learn/topo-dags). That gives you two ways to answer every vertex once:

1. **Top-down.** Start at the big question and explore the DAG with a depth-first search, recording each vertex's answer when you finish it. A finished vertex is never explored again. That's memoisation, and it's the next lesson.
2. **Bottom-up.** Answer the vertices in a **topological order**, so every subproblem's answer is ready before anything needs it. For Fibonacci, that's `fib(0)`, `fib(1)`, `fib(2)` and upwards, with a loop. That's tabulation, the lesson after.

It's the same idea as [Longest and shortest paths in a DAG](/dsa/learn/topo-dag-paths): process vertices in topological order and build each value from values already known. Every DP is that, on a DAG whose vertices are subproblems.

<Callout kind="note" title="Where the name comes from">
Richard Bellman named the method in the 1950s, when "programming" meant planning, as in a timetable or a TV programme. Filling in a table of answers was the planning. It has nothing to do with writing code, and "dynamic" mostly sounded good.
</Callout>

## Optimal substructure

Counting Fibonacci numbers needs only overlap. Most DP problems ask for the **best** of something: the cheapest, the longest, the most. Those need a second property.

Take a hiker crossing a river on stepping stones of different heights. She starts on stone 0, and from any stone she can jump to the next stone or the one after. A jump costs energy equal to the difference in height. What's the cheapest way to reach the last stone?

```text
stone:    0   1   2   3   4   5
height:  10  30  40  20  50  10
```

The cheapest route to stone 5 must arrive from stone 4 or stone 3. Suppose it arrives from stone 3. Then the part of the route up to stone 3 must itself be a **cheapest** route to stone 3. If it weren't, you could swap in a cheaper route to stone 3, keep the final jump, and get a cheaper route to stone 5, which contradicts it being the cheapest.

That's **optimal substructure**: a best solution to the problem is made of best solutions to its subproblems. It means you can write the cheapest cost to reach stone i as

> cost(i) = the smaller of cost(i − 1) + jump from i − 1, and cost(i − 2) + jump from i − 2

and trust it, without ever looking at routes that are worse somewhere in the middle. Here cost(5) works out at 40, along stones 0, 1, 3, 5. The argument above, "if a part weren't best, swap in a better part", is called **cut and paste**, and it's how DP solutions are usually justified.

### When it fails

Optimal substructure needs the subproblems to be **independent**: the best answer to one mustn't restrict what the other may use. Here's a famous case where they aren't. Take three towns A, B and C, every pair joined by a road of length 1, and ask for the **longest** route from A to C that never visits a town twice.

The answer is A → B → C, length 2. But its first part, A → B, isn't the longest route from A to B: that's A → C → B, also length 2. And you can't glue that onto B → C, because C would appear twice. The best route to B uses up a town the rest of the journey needs. Longest simple paths have no optimal substructure, and no efficient algorithm is known for them in general graphs. (In a DAG there are no cycles to worry about, which is why M43 could solve them.)

## DP against divide and conquer and greedy

All three paradigms of Part VII break a problem into smaller ones. They differ in what the pieces look like:

| Paradigm | The subproblems | The choice at each step | Example |
| --- | --- | --- | --- |
| Divide and conquer | Disjoint, each solved once | None: always split the same way | Merge sort |
| Greedy | Only one remains after each choice | Take the locally best option, never reconsider | Activity selection |
| Dynamic programming | Overlapping, each answer stored | Try every option, keep the best | Stepping stones |

[Divide, conquer, combine](/dsa/learn/dc-paradigm) splits a range into halves that never share work, so there's nothing to reuse. You can measure the difference. This program counts how often each recursion meets a subproblem it has seen before:

```swift run
// How often does each recursion meet a subproblem it has already met?
var fibCount: [Int: Int] = [:]

func fib(_ n: Int) -> Int {
    fibCount[n, default: 0] += 1
    if n < 2 {
        return n
    }
    return fib(n - 1) + fib(n - 2)
}

struct Piece: Hashable {
    let low: Int
    let high: Int
}
var sumCount: [Piece: Int] = [:]

// Divide and conquer: split the range in half, as merge sort does
func rangeSum(_ items: [Int], _ low: Int, _ high: Int) -> Int {
    sumCount[Piece(low: low, high: high), default: 0] += 1
    if high - low == 1 {
        return items[low]
    }
    let mid = (low + high) / 2
    return rangeSum(items, low, mid) + rangeSum(items, mid, high)
}

_ = fib(20)
print("fib(20):", fibCount.values.reduce(0, +), "calls,", fibCount.count, "different subproblems, most repeated:", fibCount.values.max()!)
_ = rangeSum(Array(1...1000), 0, 1000)
print("rangeSum:", sumCount.values.reduce(0, +), "calls,", sumCount.count, "different subproblems, most repeated:", sumCount.values.max()!)
```

```output
fib(20): 21891 calls, 21 different subproblems, most repeated: 6765
rangeSum: 1999 calls, 1999 different subproblems, most repeated: 1
```

Every one of `rangeSum`'s 1,999 calls is a different range, so a cache would never be read. Fibonacci's 21,891 calls cover just 21 subproblems, and `fib(1)` alone is computed 6,765 times. Same recursive shape, opposite verdicts.

And against greedy: [When greedy fails](/dsa/learn/greedy-counterexamples) showed problems where the locally best choice paints you into a corner. DP doesn't guess. At each step it tries **every** option, and stored answers make trying them all cheap.

<Callout kind="gotcha" title="DP isn't about tables">
It's easy to come away thinking DP means "make a 2D array". The table is only storage. What makes something DP is the reasoning: a subproblem graph with overlap, and, for best-of questions, optimal substructure. If you can't say what one entry of your table *means* in a sentence, you don't have a DP yet, whatever the code looks like.
</Callout>

## How to spot a DP problem

Some signals in the wording:

- **Count the ways** to do something, or **find the best** (minimum, maximum, longest, cheapest) way.
- A **sequence of decisions**, each limiting what comes next: take this house and you can't take its neighbour.
- A brute-force recursion that tries every choice is easy to write, but it would make exponentially many calls, and the arguments of those calls come from a small range.

That last signal is the practical test. Write the brute-force recursion (you know how, from M17), then count the different argument values it can be called with. If that's small, you have a DP.

**Token exchange machine** has a three-way recursion that makes trillions of calls for its biggest inputs. Before writing any code, work out which values it can ever ask about, and how many there are. That count is the whole solution's cost; the next lesson shows how to cash it in.

```cards
- id: dp-vs-dc
  front: "How does dynamic programming differ from divide and conquer?"

  front: "What is the cut-and-paste argument for optimal substructure?"
  back: "If part of a best solution weren't itself best for its subproblem, you could swap in a better part and improve the whole, contradicting that it was best."
```
