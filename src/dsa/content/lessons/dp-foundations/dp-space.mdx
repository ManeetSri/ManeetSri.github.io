## Why it matters

A DP table holds one answer per subproblem, but the loop usually reads only the last row or two of it. Keeping just those turns O(n) memory into O(1), and an n × m grid into a single row of m. For a million stones that's 8 MB down to 16 bytes. For a 20,000 × 20,000 grid it's the difference between 3.2 GB, far too much for a single problem, and 160 KB. Interviewers often ask "can you do it in less space?" as the follow-up to a working DP. This lesson is how to answer, and when the honest answer is no.

## Rolling variables

Look at what the Fibonacci loop reads: `table[i - 1]` and `table[i - 2]`, nothing older. So keep two variables and **roll** them forward each time round:

```swift run
func fib(_ n: Int) -> Int {
    if n < 2 {
        return n
    }
    var (previous, current) = (0, 1)          // fib(i - 2) and fib(i - 1), starting at i = 2
    for _ in 2...n {
        (previous, current) = (current, previous + current)
    }
    return current
}

print(fib(10), fib(92))

// The same shift written as two separate assignments, in the wrong order
var previous = 0
var current = 1
for _ in 2...10 {
    previous = current
    current = previous + current              // previous was just overwritten
}
print(current)
```

```output
55 7540113804746346429
512
```

The tuple assignment `(previous, current) = (current, previous + current)` works out the whole right-hand side, using the **old** values, before assigning anything. The two-line version overwrites `previous` first, so `current` just doubles each time and the answer is 512 instead of 55. When you roll variables by hand, either use a tuple or save the new value in a temporary first:

```swift
let next = previous + current
previous = current
current = next
```

The stepping-stones crossing rolls the same way. Name the variables after what they hold, relative to the stone being filled:

```swift run
func cheapestCrossing(_ heights: [Int]) -> Int {
    var twoBack = 0                    // the cheapest way to reach stone i - 2
    var oneBack = 0                    // the cheapest way to reach stone i - 1
    for i in 1..<heights.count {
        var best = oneBack + abs(heights[i] - heights[i - 1])
        if i >= 2 {
            best = min(best, twoBack + abs(heights[i] - heights[i - 2]))
        }
        (twoBack, oneBack) = (oneBack, best)
    }
    return oneBack
}

print(cheapestCrossing([10, 30, 40, 20, 50, 10]))
print(cheapestCrossing([7]))
print(cheapestCrossing((0..<1_000_000).map { ($0 * 7919) % 1000 }))
```

```output
40
0
135755919
```

O(n) time and **O(1)** extra memory. After the last pass, `oneBack` holds the answer for the last stone. With a single stone the loop never runs, and the answer is the starting value, 0.

## A window of k values

If entry i reads the last k entries, keep k of them. A neat way is a small array used as a ring, the same trick as [Ring buffers](/dsa/learn/queue-ring-buffer): store entry i at position `i % size`, so each new entry overwrites one too old to be needed. Here's the number of ways to climb n stairs taking 1, 2 or 3 at a time, which reads the three entries before it:

```swift run
/// Ways to climb n stairs taking 1, 2 or 3 at a time, keeping only four answers
func climbWays(_ n: Int) -> Int {
    var recent = [1, 0, 0, 0]                  // recent[i % 4] holds ways(i); ways(0) = 1
    for i in stride(from: 1, through: n, by: 1) {
        var total = 0
        for step in 1...3 where step <= i {
            total += recent[(i - step) % 4]
        }
        recent[i % 4] = total
    }
    return recent[n % 4]
}

print((0...10).map(climbWays))
```

```output
[1, 1, 2, 4, 7, 13, 24, 44, 81, 149, 274]
```

A ring of four makes the slot being written different from the three being read, which keeps the code easy to check. (`where step <= i` skips stairs below the ground floor.)

## Rolling arrays

In a grid DP, a whole row often depends only on the row above. Then you need two rows, `previous` and `current`, swapped after each row. Often you can go further and keep **one** row, updated in place, if you're careful about the direction.

Pascal's triangle from the last lesson is the classic case. `ways[n][k]` reads `ways[n - 1][k - 1]` and `ways[n - 1][k]`. In a single row, `row[k]` already holds the old `ways[n - 1][k]`, so the update is `row[k] += row[k - 1]`. The question is whether `row[k - 1]` is still the old value when you read it:

```swift run
let size = 7

// One row, updated from right to left: row[k - 1] still holds the previous row's value when it's read
var row = Array(repeating: 0, count: size)
row[0] = 1
for n in 1..<size {
    for k in stride(from: n, through: 1, by: -1) {
        row[k] += row[k - 1]
    }
}
print("right to left:", row)

// The same update from left to right reads row[k - 1] after it has already changed
var wrong = Array(repeating: 0, count: size)
wrong[0] = 1
for n in 1..<size {
    for k in 1...n {
        wrong[k] += wrong[k - 1]
    }
}
print("left to right:", wrong)
```

```output
right to left: [1, 6, 15, 20, 15, 6, 1]
left to right: [1, 6, 20, 48, 90, 132, 132]
```

Going right to left, every entry to the left of k is still from the previous row when k reads it. Going left to right, `row[k - 1]` has already been updated to the **current** row, so each entry mixes two rows and the numbers run away.

The general rule: **each entry must read the values it needs before anything overwrites them.** Draw which old entries each new entry reads; if they're to its left, sweep right to left, and vice versa. You'll use exactly this to squeeze 0/1 knapsack into one row in [0/1 knapsack, from 2D to 1D](/dsa/learn/dpk-01), where getting the direction wrong silently changes which problem you've solved.

<Callout kind="tip" title="Shrink last">
Write the full table first, test it, and only then roll it. The full table is much easier to debug: you can print it and check entries by hand. Rolling is a mechanical change once the table is right, and a confusing one to get right first time.
</Callout>

## When you can't roll

Rolling throws answers away, so it only works when nothing needs them later. Keep the full table when:

- **You need to reconstruct the solution**, not just its value: which houses were robbed, which route was taken. Walking back from the answer needs every entry (or a record of every decision) along the way. That's the subject of [Reconstructing the answer, not just its value](/dsa/learn/dp-reconstruct).
- **Entries read far back.** In the perfect-squares problem later in this module, entry t reads t − 1, t − 4, t − 9 and so on, all the way back. There's no small window to keep.
- **You're memoising top-down.** The recursion can ask for any subproblem at any time, so the memo must hold them all.
- **Several queries share one table.** If you'll be asked for `fib(k)` for many different k, keep the table and answer each in O(1).

There's a middle ground for reconstruction: roll the **values** but keep a compact array of **decisions**, such as one `Bool` per house for "taken". A `[Bool]` costs one byte per entry against eight for `[Int]`, so you save most of the memory and can still walk back.

<Callout kind="gotcha" title="Rolling slips">
- **Assigning in the wrong order**: `a = b; b = a + b` uses the new `a`. Use a tuple assignment or a temporary.
- **Sweeping a single row in the wrong direction**: no crash, just wrong numbers.
- **Forgetting the starting values**: the rolled variables must start as the base cases (here `0` and `1` for `fib`, or `0` and `0` for the stones).
- **Returning the wrong variable**: after the loop, decide which one holds the last entry.
</Callout>
