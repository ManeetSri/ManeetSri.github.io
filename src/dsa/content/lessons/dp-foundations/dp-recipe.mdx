## Why it matters

DP problems look endlessly varied: stairs, robberies, coded messages, grids, strings, knapsacks. Underneath, every one of them is answered by the same five questions. This lesson names them and works through three problems step by step. Every later DP module builds on them, so they're worth learning by heart now.

## The five steps

1. **State.** What does one entry of the table mean? Write it as a sentence: "`ways[i]` is the number of ways to tile the first i columns." Name the variables that pick out a subproblem (an index, a remaining amount, a position in two strings) and the quantity stored (a count, a cost, a yes or no).
2. **Transition.** How is a state's answer built from smaller states? Think about the **last decision** (or the first): what could the final step have been, and what subproblem is left after it? Combine the options.
3. **Base case.** Which states are small enough to answer directly, without the transition? Fill those in by hand.
4. **Order.** In what order can the table be filled so that every state comes after the states it reads? That's a topological order of the subproblem DAG: usually increasing or decreasing indexes.
5. **Answer.** Which entry, or combination of entries, answers the original question? Often the last entry, sometimes the first, sometimes the best over all of them.

Then two quick checks: the **cost** is the number of states times the work per transition, and the **memory** is the size of the table (before any rolling).

In code, the five steps become five comments, and the solution fills in around them:

```swift
// 1. State: dp[i] = ...
var dp = Array(repeating: 0, count: n + 1)
// 3. Base case
dp[0] = ...
// 4. Order
for i in stride(from: 1, through: n, by: 1) {
    // 2. Transition
    dp[i] = ...
}
// 5. Answer
return dp[n]
```

The steps are numbered in the order you *think* about them, not the order they appear in code. The state comes first because everything else depends on it; the base case is easiest to see once you know the transition.

<Callout kind="tip" title="Most DP bugs are a fuzzy state">
If you can't finish the sentence "dp[i] is the ...", stop and fix that before writing any code. Is it "the first i items" or "item i"? "Ending exactly at i" or "anywhere up to i"? Including position i's cost or not? Each choice gives a different, valid DP, but mixing two of them in one solution gives nonsense.
</Callout>

## Example 1: tiling a path (counting)

A garden path is 2 units wide and n units long. You can tile it with 1 × 2 dominoes, laid across or along the path, and 2 × 2 squares. How many different tilings are there?

**State.** `ways[i]` = the number of ways to tile the first i columns of the path exactly.

**Transition.** Look at the last column. Either:

- one domino stands across it, covering exactly that column, and the first i − 1 columns are tiled any way: `ways[i − 1]`; or
- the last column's two cells are covered by tiles that also cover column i − 1. That's two dominoes lying along the path, one above the other, or one square. Both cover exactly the last two columns, so each leaves `ways[i − 2]` ways for the rest.

So `ways[i] = ways[i − 1] + 2 × ways[i − 2]`.

**Base case.** `ways[0] = 1`: an empty path has exactly one tiling, the one with no tiles. (That's not a trick. It's what makes `ways[2]` come out right: the two-column patterns each count once.)

**Order.** `ways[i]` reads smaller indexes, so i increases.

**Answer.** `ways[n]`.

```text
The three tilings of a 2 × 2 path:

 two across     two along     one square
  ┌─┬─┐          ┌───┐          ┌───┐
  │ │ │          ├───┤          │   │
  └─┴─┘          └───┘          └───┘
```

```swift run
/// The number of ways to tile a 2 × n path with dominoes (either way round) and 2 × 2 squares
func tilings(_ n: Int) -> Int {
    // 1. State: ways[i] = the number of ways to tile the first i columns
    var ways = Array(repeating: 0, count: n + 1)
    // 3. Base case: one way to tile nothing (place no tiles)
    ways[0] = 1
    // 4. Order: i increases, because ways[i] reads ways[i - 1] and ways[i - 2]
    for i in stride(from: 1, through: n, by: 1) {
        // 2. Transition: what covers the last column?
        ways[i] = ways[i - 1]                          // one domino across it
        if i >= 2 {
            ways[i] += 2 * ways[i - 2]                 // two dominoes along, or one square, over the last two columns
        }
    }
    // 5. Answer
    return ways[n]
}

print((0...10).map(tilings))
```

```output
[1, 1, 3, 5, 11, 21, 43, 85, 171, 341, 683]
```

Check the small ones by hand: 3 tilings for n = 2 (drawn above), and 5 for n = 3. **Cost:** n states, O(1) each, so O(n) time and O(n) memory, or O(1) after rolling. The numbers roughly double each time, so for large n you'd keep them modulo a big prime, as in [Modular arithmetic](/dsa/learn/math-modular-arithmetic): `(ways[i - 1] + 2 * ways[i - 2]) % 1_000_000_007`.

## Example 2: an exam with recovery time (best total, filled backwards)

An exam has questions in a fixed order. Answering question i scores `points[i]`, but it takes so long that you must then skip the next `rest[i]` questions. Passing a question costs nothing. What's the highest score?

Here the decision at question i affects what comes **after** it. So the natural state is about the rest of the exam.

**State.** `best[i]` = the most points available from questions i to the end.

**Transition.** At question i, either pass it, leaving `best[i + 1]`, or answer it, scoring `points[i]` and jumping to question `i + 1 + rest[i]`. If that jump goes past the end, nothing is left: treat it as n.

`best[i] = max(best[i + 1], points[i] + best[min(n, i + 1 + rest[i])])`

**Base case.** `best[n] = 0`: no questions left, no points.

**Order.** `best[i]` reads **larger** indexes, so i decreases, from n − 1 down to 0.

**Answer.** `best[0]`: the whole exam is ahead of you at the start.

```swift run
/// Questions must be taken in order. Answering question i scores points[i], but uses up the time
/// for the next rest[i] questions, which must be skipped. Passing a question costs nothing.
func bestScore(points: [Int], rest: [Int]) -> Int {
    let n = points.count
    // 1. State: best[i] = the most points available from questions i...n - 1
    // 3. Base case: best[n] = 0, with no questions left (the array starts at 0)
    var best = Array(repeating: 0, count: n + 1)
    // 4. Order: i decreases, because best[i] reads larger indexes
    for i in stride(from: n - 1, through: 0, by: -1) {
        // 2. Transition: pass question i, or answer it and jump past the ones it rules out
        let pass = best[i + 1]
        let answer = points[i] + best[min(n, i + 1 + rest[i])]
        best[i] = max(pass, answer)
    }
    print("best:", best)
    // 5. Answer: everything is still available at the start
    return best[0]
}

print(bestScore(points: [5, 2, 6, 1, 4, 3], rest: [1, 0, 2, 0, 1, 0]))
```

```output
best: [14, 11, 9, 5, 4, 3, 0]
14
```

The best plan answers questions 0, 2 and 5 for 5 + 6 + 3. Answering question 0 rules out question 1; answering question 2 rules out 3 and 4.

Why not fill this one forwards? A forwards state would be "the best score after deciding questions 0 to i − 1", but then you'd also need to know whether you're still resting, and for how long. The backwards state needs nothing extra, because a jump simply lands on a later state. **When a choice constrains the future, define the state as "from here to the end".**

## Example 3: exact egg boxes (yes or no)

Eggs come in boxes of 6, 9 and 20. Which totals can you buy exactly?

**State.** `possible[t]` = true if exactly t eggs can be bought.

**Transition.** If t is possible, some box was bought last. Removing it leaves t − 6, t − 9 or t − 20, which must be possible. So `possible[t]` is true if any of those is.

**Base case.** `possible[0] = true`: buy nothing.

**Order.** Increasing t.

**Answer.** `possible[n]` for a single total. Here, the list of totals that can't be made.

```swift run
/// Which totals can be bought exactly with boxes of 6, 9 and 20 eggs?
let boxes = [6, 9, 20]
let limit = 50

// 1. State: possible[t] = true if exactly t eggs can be bought
var possible = Array(repeating: false, count: limit + 1)
// 3. Base case: zero eggs, by buying nothing
possible[0] = true
// 4. Order: t increases, because possible[t] reads smaller totals
for t in stride(from: 1, through: limit, by: 1) {
    // 2. Transition: is there a box whose removal leaves a possible total?
    for box in boxes where box <= t && possible[t - box] {
        possible[t] = true
    }
}
// 5. Answer: here, every total that can't be made
print((1...limit).filter { !possible[$0] })
```

```output
[1, 2, 3, 4, 5, 7, 8, 10, 11, 13, 14, 16, 17, 19, 22, 23, 25, 28, 31, 34, 37, 43]
```

43 is the largest total you can't buy. From 44 to 49 every total is possible, six in a row, and adding a box of 6 to each of those reaches every larger total. **Cost:** `limit` states, 3 options each.

## Three kinds of question, three ways to combine

The examples asked three different kinds of question, and that decides how the transition combines its options and what the base case holds:

| Question | Combine the options with | Typical base case | Example |
| --- | --- | --- | --- |
| How many ways? | `+` (add the counts) | `1` for the empty case | tilings |
| What's the best? | `min` or `max` | `0`, or "impossible" as infinity | exam score |
| Is it possible? | logical or: any option works | `true` for the empty case | egg boxes |

Counting needs the options to be **distinct**: two different last moves must never describe the same tiling, or you'd count it twice. Optimising doesn't care about overlaps, since taking the best twice changes nothing. Keep that difference in mind; it's behind several bugs in [Coin change I and II](/dsa/learn/dpk-coin-change).

## Checking your recipe

Before trusting a DP, run three checks:

1. **Trace the smallest cases by hand.** Fill in the first few entries yourself and compare with the program, as with the 2 × 2 tilings.
2. **Compare against brute force** on small inputs. The plain recursion that tries every choice, from [Brute force first](/dsa/learn/algo-brute-force-first), is slow but obviously right. Every problem in this module's tests does exactly this.
3. **Work out the cost.** States times work per state. If that's too big for the constraints, the state is too detailed. [Reading constraints to guess the target complexity](/dsa/learn/algo-constraints-to-complexity) tells you what's affordable: n up to 10⁵ wants O(n) or O(n log n) overall.

<Callout kind="gotcha" title="Recipe slips">
- **A state that leaves something out.** If the best choice at i depends on something the state doesn't record (like "am I still resting?"), the table can't be right. Add it to the state, or change the state's direction.
- **The wrong base case for counting.** `ways[0] = 0` makes every count 0. The empty arrangement counts once.
- **Options that overlap when counting.** Two transitions describing the same arrangement double-count it.
- **Filling in the wrong order.** The code still runs; it just reads entries that are still 0.
</Callout>
