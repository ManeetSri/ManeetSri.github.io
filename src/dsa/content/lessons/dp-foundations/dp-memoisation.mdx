## Why it matters

**Top-down memoisation** is usually the quickest route from "I can write the brute-force recursion" to "it runs fast". You keep the recursion exactly as you'd naturally write it and add a memo: a store of answers already worked out. You met the idea in [A preview of memoisation](/dsa/learn/rec-memo-preview). This lesson makes it a dependable tool: choosing the right memo, the shape that keeps it tidy, and the one way it bites in Swift, running out of stack.

## Start from the plain recursion

Back to the hiker on stepping stones from the last lesson. She starts on stone 0, jumps one or two stones forward each time, and a jump costs the difference in height. The plain recursion follows the optimal-substructure argument directly: the cheapest way to reach stone i ends with a jump from i − 1 or from i − 2.

```swift run
var calls = 0

/// The cheapest energy to reach stone i, starting from stone 0
func cost(_ heights: [Int], _ i: Int) -> Int {
    calls += 1
    if i == 0 {
        return 0
    }
    var best = cost(heights, i - 1) + abs(heights[i] - heights[i - 1])
    if i >= 2 {
        best = min(best, cost(heights, i - 2) + abs(heights[i] - heights[i - 2]))
    }
    return best
}

let river = [10, 30, 40, 20, 50, 10]
print(cost(river, river.count - 1), "in", calls, "calls")

let wideRiver = (0..<30).map { ($0 * 37) % 50 }
calls = 0
print(cost(wideRiver, wideRiver.count - 1), "in", calls, "calls")
```

```output
40 in 20 calls
361 in 2178308 calls
```

It's correct, and that matters: get the recursion right first, on small inputs, before making it fast. But 30 stones already takes over two million calls, and every extra stone multiplies that by about 1.6. Yet there are only 30 different questions: "the cheapest way to stone i" for each i.

## Add a memo

The recipe from M17 still applies. The arguments that decide the answer are the **key**: here just `i`, since `heights` never changes. Check the memo after the base case, and store the answer before returning:

```swift run
func cheapestCrossing(_ heights: [Int]) -> (cost: Int, calls: Int) {
    var memo = [Int?](repeating: nil, count: heights.count)   // memo[i]: the answer for stone i, once known
    var calls = 0

    func cost(_ i: Int) -> Int {
        calls += 1
        if i == 0 {
            return 0
        }
        if let known = memo[i] {
            return known
        }
        var best = cost(i - 1) + abs(heights[i] - heights[i - 1])
        if i >= 2 {
            best = min(best, cost(i - 2) + abs(heights[i] - heights[i - 2]))
        }
        memo[i] = best
        return best
    }

    return (cost(heights.count - 1), calls)
}

print(cheapestCrossing([10, 30, 40, 20, 50, 10]))
print(cheapestCrossing((0..<30).map { ($0 * 37) % 50 }))
print(cheapestCrossing((0..<1000).map { ($0 * 37) % 50 }))
```

```output
(cost: 40, calls: 10)
(cost: 361, calls: 58)
(cost: 12467, calls: 1998)
```

From 2,178,308 calls to 58. Each stone is computed once, and looked up at most once more, so the calls are about 2n: **O(n)** time.

What to notice:

- **The memo lives in the wrapper**, `cheapestCrossing`, and the nested function `cost` captures it, as in [Capturing values](/dsa/learn/swift-capturing). Each call to `cheapestCrossing` gets a fresh memo, and nothing leaks out to the rest of the program.
- **`heights` isn't a parameter of `cost` any more.** The nested function captures it too. Only the arguments that change between calls belong in the key.
- **The function returns a named tuple** so the example can show the call count. A real solution returns just the cost.

## Choosing the memo: array or dictionary

The memo maps each key to its answer. Two choices cover nearly everything:

| Memo | Use it when | Lookup |
| --- | --- | --- |
| `[Int?]` of size n | keys are small whole numbers, 0 to n − 1 | direct index: fast, no hashing |
| `[[Int?]]` | two small whole-number keys, like `(i, j)` | two indexes |
| `[Key: Int]` | keys are large, sparse, negative, or not numbers at all | hashing, as in [Dictionaries and lookups](/dsa/learn/swift-dictionaries) |

For keys made of several values, a small `Hashable` struct is the cleanest dictionary key, as you saw in [Custom Hashable keys](/dsa/learn/hash-custom-keys).

An array is faster and uses less memory per entry, so it's the default whenever the keys fit. A dictionary wins when only a few of a huge range of keys are ever reached. Here's a recursion where the key can be as large as a trillion, so an array memo is out of the question:

```swift run
// f(0) = 1, and f(n) = f(n / 2) + f(n / 3), rounding down
var memo: [Int: Int] = [0: 1]

func f(_ n: Int) -> Int {
    if let known = memo[n] {
        return known
    }
    let result = f(n / 2) + f(n / 3)
    memo[n] = result
    return result
}

print(f(1_000_000_000_000))
print("different subproblems:", memo.count)
```

```output
4266563557
different subproblems: 438
```

Dividing by 2 and 3 over and over only ever reaches numbers of the form n ÷ (2ᵃ × 3ᵇ), so a trillion possible keys collapse to 438. The recursion is also only about 40 calls deep, because each call at least halves n. This is where top-down really shines: it computes **only the subproblems the question needs**.

### `nil` or a sentinel?

`[Int?]` uses `nil` for "not computed yet". You'll also see memos filled with `-1`, which saves the optional, but only works if −1 can never be a real answer. Costs and counts are never negative, so −1 is safe there. A problem whose answers can be negative needs `nil` (or a dictionary). When in doubt, use `Int?`: the compiler then stops you from using an answer you never computed.

## The catch: memoised recursion is still recursion

Memoisation fixes the time, not the depth. The first call to `cost(n - 1)` still recurses down through `cost(n - 2)`, `cost(n - 3)` and so on to `cost(0)` before anything is stored. That's n frames on the call stack at once.

[Stack depth limits in Swift](/dsa/learn/rec-stack-limits) gave the numbers for the simplest recursion: around a hundred thousand frames on the main thread, but only a few thousand inside a test, because **Swift Testing runs tests on threads with a 512 KB stack**. A nested function with a captured memo needs bigger frames than that, so the limits come sooner. A memoised `cheapestCrossing` with 10,000 stones runs happily as a script, then kills the test process when the same call runs inside `swift test`:

```text title="What you'll see"
error: Process '.../swiftpm-testing-helper ...' exited with unexpected signal code 10
```

Push it to 50,000 stones and even the script crashes. Estimate the depth before you run: it's the **longest chain of subproblems** in the DAG, the most arrows you can follow from the top question to a base case. For the stepping stones that's n. For `f(n / 2) + f(n / 3)` it's about log₂ n. If the chain can reach the tens of thousands, a top-down solution is living on borrowed time.

### Two ways out

**Warm the memo from the bottom.** Call the function for the smallest keys first. By the time you ask for stone i, stones i − 1 and i − 2 are already stored, so no call goes more than a level or two deep:

```swift run
func cheapestCrossing(_ heights: [Int]) -> Int {
    var memo = [Int?](repeating: nil, count: heights.count)
    var depth = 0
    var deepest = 0

    func cost(_ i: Int) -> Int {
        depth += 1
        defer { depth -= 1 }
        deepest = max(deepest, depth)
        if i == 0 {
            return 0
        }
        if let known = memo[i] {
            return known
        }
        var best = cost(i - 1) + abs(heights[i] - heights[i - 1])
        if i >= 2 {
            best = min(best, cost(i - 2) + abs(heights[i] - heights[i - 2]))
        }
        memo[i] = best
        return best
    }

    // Warm the memo from the smallest subproblem up, so no call recurses more than a step or two
    for i in 0..<heights.count {
        _ = cost(i)
    }
    print("deepest recursion:", deepest)
    return memo[heights.count - 1] ?? 0
}

print(cheapestCrossing((0..<200_000).map { ($0 * 7919) % 1000 }))
```

```output
deepest recursion: 2
27151119
```

Two hundred thousand stones, never more than two frames deep. (`?? 0` covers a river of one stone, where the answer is the base case and nothing is stored.)

**Switch to tabulation.** Look at that warm-up loop: it visits the subproblems smallest first, and each one only needs answers already stored. At that point the recursion isn't doing anything a plain loop couldn't. Writing the loop directly is **bottom-up tabulation**, the next lesson. As a rule of thumb:

- recursion depth up to a few hundred: top-down is fine anywhere, tests included;
- depth in the thousands or more: warm the memo, or tabulate;
- only a sparse handful of a huge key range is reached: top-down with a dictionary, as long as the depth is small.

<Callout kind="gotcha" title="Memo slips that cost an afternoon">
- **A memo declared inside the recursive function** is created fresh in every call, so it never finds anything. It must live outside: in the wrapper, as here.
- **Forgetting to store** the answer before returning. The code still gives correct answers, just as slowly as before. Count calls on a small input to catch it.
- **A key that leaves something out.** If the answer depends on two arguments but you key on one, different questions share an entry and you get wrong answers.
- **Checking the memo before the base cases** is fine, as long as the base cases can't be confused with "not computed yet".
</Callout>

## Practice

**Token exchange machine** is made for top-down: the values can reach a trillion, but only a few hundred are ever asked about, and the recursion is shallow. A dictionary memo is the whole trick.
