## Why it matters

You've spent Part I learning to *say* things in Swift. Part II is about deciding *what* to say. An algorithm is the plan behind the code: the idea that sorts your photos by date, finds the fastest route home, or autocompletes a search. Every problem in this course is really a request for an algorithm, and knowing exactly what counts as one tells you what you have to get right.

## Problem, instance, algorithm, program

Four words get mixed up all the time, so pin them down first:

| Word | Meaning | Example |
| --- | --- | --- |
| Problem | a general question, for every possible input | find the largest number in a list |
| Instance | one particular input | `[3, 9, 4]` |
| Algorithm | a step-by-step method that solves every instance | look at each number, remembering the biggest so far |
| Program | an algorithm written in a real language | a Swift function with a `for` loop |

The algorithm is the idea; a program is one way of writing it down. In Swift, Python or plain English, it's still the same algorithm.

## What makes something an algorithm

An **algorithm** is a finite list of clear steps that turns any valid input into the right output. Each part of that sentence matters:

1. **Input.** It works on something: a list, a number, a piece of text. Sometimes the input is empty.
2. **Output.** It produces an answer, such as a value, a yes or no, or a changed list.
3. **Clear steps.** Every step is precise and something you can actually do. "Compare the two numbers" is clear. "Pick a good one" is not.
4. **Finite.** It always stops, after a limited number of steps, for every valid input.
5. **Correct.** The answer is right for *every* valid input, not only the ones you tried.

<Callout kind="analogy" title="A recipe, almost">
A recipe is close to an algorithm: ingredients go in, a cake comes out, and the steps are in order. But "season to taste" or "bake until golden" are not clear steps. Two cooks would do different things. An algorithm can't leave anything to judgement.
</Callout>

## One algorithm, in English and in Swift

Here's a small problem: **is a list in order, smallest to largest?** Repeated values are allowed, so `[2, 2, 5]` counts as in order.

In plain English, the algorithm is:

1. Look at each pair of neighbours, from left to right.
2. If any left number is bigger than its right neighbour, the answer is no.
3. If you reach the end without finding such a pair, the answer is yes.

And in Swift:

```swift run
func isInOrder(_ numbers: [Int]) -> Bool {
    if numbers.count < 2 {
        return true
    }
    for index in 1..<numbers.count {
        if numbers[index - 1] > numbers[index] {
            return false
        }
    }
    return true
}

print(isInOrder([2, 2, 5, 8]))
print(isInOrder([1, 5, 3, 9]))
print(isInOrder([7]))
print(isInOrder([]))
```

```output
true
false
true
true
```

Each English step became a line or two of Swift. The first `if` exists because `1..<numbers.count` would be `1..<0` for an empty list, and Swift stops the program on a range whose start is after its end. Thinking about *every* input, including the empty one, is part of designing the algorithm.

It ticks all five boxes. It's finite because it makes one pass. It's correct because if no neighbouring pair is out of order, each number is at most the next one, so the whole list is in order.

## An algorithm must stop

A method that sometimes runs forever never gives an answer, so it isn't an algorithm. This loop is meant to check whether a number is even by counting down in twos:

```swift
var n = start
while n != 0 {
    n -= 2
}
```

For an even starting number, `n` lands exactly on 0 and the loop ends. For an odd number, `n` jumps from 1 to -1 and keeps falling. In Swift, it keeps going until it runs past `Int.min`, and then the program crashes with an overflow. Changing the condition to `while n > 0` makes it finish for every input: each pass makes `n` smaller, and it can't fall forever without dropping to 0 or below.

That's the usual way to see that a loop stops: find something that gets strictly smaller on every pass and can't go below some floor. You'll use this idea again in the lesson on invariants.

<Callout kind="note" title="An open question">
Nobody has proved that the hailstone sequence from M10's practice reaches 1 for every start. It always has, for enormous numbers, but strictly speaking no one knows whether it's an algorithm for every input.
</Callout>

## One problem, many algorithms

Most problems can be solved in more than one way. To add up the whole numbers from 1 to `n`, you could loop, or you could use the formula `n × (n + 1) / 2`, which the mathematician Gauss is said to have spotted as a schoolboy:

```swift run
func sumByLoop(upTo n: Int) -> Int {
    var total = 0
    for number in 1...n {
        total += number
    }
    return total
}

func sumByFormula(upTo n: Int) -> Int {
    n * (n + 1) / 2
}

print(sumByLoop(upTo: 100))
print(sumByFormula(upTo: 100))
```

```output
5050
5050
```

Both are correct. The loop does 100 additions for `n = 100` and a million for `n = 1,000,000`. The formula does three operations whatever `n` is. Choosing between correct algorithms by how their work grows is what complexity analysis is about, and you'll make it precise in M14.

## Correct means every valid input

Here's a tempting shortcut for `isInOrder`: only compare the first and last numbers.

```swift
func isInOrderShortcut(_ numbers: [Int]) -> Bool {
    guard let first = numbers.first, let last = numbers.last else { return true }
    return first <= last
}
```

It gives the right answer for `[2, 2, 5, 8]` and `[9, 4]`. It's still wrong. `[1, 5, 3, 9]` starts small and ends big, so the shortcut says `true`.

An input that makes an algorithm give the wrong answer is called a **counterexample**. One counterexample is enough to prove an algorithm wrong. No number of passing examples proves it right: for that you need an argument for why it works, which is what the rest of this module teaches you to build.

<Callout kind="gotcha" title="Swift gotcha: a crash is a wrong answer">
An algorithm that crashes on some valid input isn't correct for that input. In Swift, the usual culprits are `numbers[0]` on an empty array, a range like `1..<0`, and arithmetic that overflows. When an input is allowed by the problem, your code has to handle it.
</Callout>
