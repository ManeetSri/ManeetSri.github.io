## Why it matters

The constraints in a problem statement are a hint in disguise. Before you've designed anything, the input sizes tell you roughly how fast your solution has to be, which rules whole families of ideas in or out. M00 gave you a table of sizes and targets. This lesson shows you how to work the numbers out yourself, and what the *other* constraints are telling you. M14 will make the notation precise; here, the goal is a quick, reliable estimate.

## Counting steps roughly

To estimate how long code takes, count roughly how many times its innermost line runs, for the largest allowed input:

| Code shape | Innermost line runs about | Written |
| --- | --- | --- |
| one loop over n items | n times | O(n) |
| two nested loops over n items | n × n times | O(n²) |
| a loop that halves n each time | log₂ n times | O(log n) |
| sort, then one pass | n × log₂ n times | O(n log n) |
| try every subset of n items | 2ⁿ times | O(2ⁿ) |

**log₂ n** is the number of times you can halve n before reaching 1. It grows astonishingly slowly:

```swift run
var n = 1_000_000
var halvings = 0
while n > 1 {
    n /= 2
    halvings += 1
}
print(halvings)
```

```output
19
```

A million halves down to 1 in under 20 steps, and a billion in about 30. That's why O(log n) and O(n log n) algorithms are so fast.

## The budget: about 10⁸ steps

A useful rule of thumb: compiled, optimised code does somewhere around **100 million (10⁸) simple steps per second**. Online judges usually allow one or two seconds. So:

> Plug the largest n into each candidate complexity. If the result is well under 10⁸, that approach is fast enough.

It's a rough guide. Real speed depends on what each step does, and remember from [Debug vs release builds](/dsa/learn/swift-release-builds) that a debug build can be 10–100 times slower. But it's right often enough to steer your thinking.

## Working through some constraints

**`1 ≤ n ≤ 2,000`.** n² is 4 million: comfortably fast. Two nested loops are fine, so the brute force may be the whole answer.

**`1 ≤ n ≤ 100,000`.** n² is 10¹⁰, a hundred times over budget. n log n is about 100,000 × 17 ≈ 1.7 million: fine. Think sorting, a single pass, or a set or dictionary.

**`1 ≤ n ≤ 20`.** Suspiciously small. 2²⁰ is about a million, so trying every subset is affordable, and the problem is probably asking you to. You'll learn a neat way to do it with bits in M16.

**`1 ≤ n ≤ 10⁹`, and n is a single number.** You can't even count to n inside the budget. The answer must come from a formula, a loop that halves (about 30 steps), or something like √n (about 31,623 steps).

| Largest n | n² | n log₂ n | 2ⁿ | Fits in 10⁸? |
| --- | --- | --- | --- | --- |
| 20 | 400 | about 90 | about 10⁶ | everything up to 2ⁿ |
| 2,000 | 4 × 10⁶ | about 22,000 | far too big | n² |
| 100,000 | 10¹⁰ | about 1.7 × 10⁶ | far too big | n log n |
| 10⁹ | 10¹⁸ | about 3 × 10¹⁰ | far too big | only log n or √n |

## The other numbers in the constraints

Sizes aren't the only clue. The rest of the small print matters too.

**Value ranges warn you about overflow.** If n can be 100,000 and each value up to 10⁹, a sum can reach 10¹⁴. An `Int` holds up to about 9.2 × 10¹⁸, so that's fine. A product of two values reaches 10¹⁸, which still fits, just. A product of three doesn't. When a statement asks for the answer "modulo 10⁹ + 7", it's telling you the true answer is too big for any integer type. You'll learn to handle that in M15.

**Small value ranges suggest counting.** If every value is a lowercase letter, or between 0 and 100, you can count occurrences in a small fixed-size array, as in [Frequency counting with 26 slots](/dsa/learn/swift-frequency-arrays), instead of sorting.

**Several sizes multiply.** A grid of n rows and m columns with `n × m ≤ 10⁶` has a million cells: visiting each a few times is fine. An array of 100,000 numbers with 100,000 questions about it means each question can't scan the whole array (that's 10¹⁰ steps), so you'll need to prepare something up front. Part III has the tools.

**Many test cases.** When there are many inputs in one run, statements often bound the *total* size, such as "the sum of n over all test cases is at most 200,000". Budget against the total.

## Reading a whole problem

> Given up to 200,000 prices, each between 1 and 10⁹, and a number k ≥ 1, decide whether two prices differ by exactly k.

- The brute force checks every pair: 200,000² = 4 × 10¹⁰. Correct, and about 400 times over budget, so useful for testing only.
- The target is O(n log n) or O(n). One idea: put the prices in a set, then for each price ask whether `price + k` is in it.
- Overflow? `price + k` is at most about 2 × 10⁹. No problem.

```swift run
func hasPairWithDifference(_ prices: [Int], _ k: Int) -> Bool {
    let seen = Set(prices)
    for price in prices where seen.contains(price + k) {
        return true
    }
    return false
}

print(hasPairWithDifference([8, 3, 15, 11], 4))
print(hasPairWithDifference([8, 3, 15, 11], 6))
```

```output
true
false
```

The constraints did most of the design work: they ruled out the pairs loop and pointed at a one-pass idea before any code was written.

<Callout kind="tip" title="Not sure? Measure.">
If you can't tell whether an approach is fast enough, build the largest allowed input and time it in a release build, using `ContinuousClock` from [Timing code with ContinuousClock](/dsa/learn/swift-timing-code). A minute of measuring beats an hour of optimising code that was already fast enough.
</Callout>

## Common mistakes

- **Over-engineering small inputs.** If n is at most 100, write the simplest correct code. Nobody needs O(n log n) for 100 items.
- **Forgetting that the tests use the limits.** If n can be 100,000, at least one test has 100,000 items.
- **Checking only n.** The value range decides whether your sums overflow and whether counting beats sorting.
- **Overestimating log n.** log₂ of a billion is only about 30.
