## Why it matters

Tests and dry runs show that code works on the inputs you tried. They can't show it works on *every* input. A **loop invariant** lets you argue that it does, in a few plain sentences. It's how you'll convince yourself that binary search, two pointers and sliding windows are right, how you'll design them in the first place, and what interviewers mean when they ask "why does this work?"

## What stays true each pass

A **loop invariant** is a statement about the loop's variables that is true before the loop starts and is still true after every pass. The variables change, but the statement about them keeps holding.

Take the simplest loop there is:

```swift
var total = 0
for i in 0..<numbers.count {
    total += numbers[i]
}
```

Its invariant: **at the start of each pass, `total` is the sum of the first `i` numbers.** Before pass 0 that's the sum of no numbers, 0. Before pass 2, it's `numbers[0] + numbers[1]`. Step through it and watch the invariant hold on every row:

```visual traceTable
program: sum
input:
  numbers: [4, 7, 1, 9]
```

After each row, `total` is the sum of the numbers seen so far: 4, then 4 + 7 = 11, then 12, then 21. That's the invariant, made visible.

## The three checks

To show a loop is correct with an invariant, check three things:

1. **Start.** It's true before the first pass. Here, `i` is 0 and `total` is 0, the sum of no numbers.
2. **Keep.** If it's true at the start of a pass, it's still true at the start of the next. The pass adds `numbers[i]`, so `total` becomes the sum of the first `i + 1` numbers, exactly what the invariant says for the next value of `i`.
3. **Finish.** When the loop ends, the invariant gives you the answer. The loop ends when `i` reaches `numbers.count`, so `total` is the sum of *all* the numbers.

And, as you saw in [What an algorithm is](/dsa/learn/algo-what-is-an-algorithm), the loop has to actually end. A `for` loop over a range always does.

<Callout kind="analogy" title="Climbing a ladder">
If you can get onto the bottom rung (start), and from any rung you can always reach the next one (keep), then you can reach every rung, however tall the ladder. The finish check is noticing that the top rung is where you wanted to be. Mathematicians call this kind of argument induction.
</Callout>

You never traced a particular input, so the argument works for 3 numbers, 3 million, or none.

## The largest so far

Here's the loop from M00 that finds the largest number. Its invariant: **`best` is the largest of the numbers looked at so far.**

```visual traceTable
program: largest
input:
  numbers: [3, 8, 5, 12, 7]
```

- **Start.** `best` is `numbers[0]`, and the first number is the largest of the one number seen.
- **Keep.** A new number either beats `best`, and replaces it, or it doesn't, and `best` is still the largest. Either way, `best` is the largest of everything seen, now including the new number.
- **Finish.** When the loop ends, every number has been seen, so `best` is the largest of them all.

Now you can say exactly why `var best = 0` is a bug. It breaks the start check: before any number has been looked at, 0 isn't "the largest number seen", because it might not be in the list at all. For `[-5, -2]`, it never gets replaced.

## Checking an invariant in code

You can make Swift check an invariant while your code runs. `assert`, from M12, stops the program in a debug build if its condition is false:

```swift run
func total(of numbers: [Int]) -> Int {
    var total = 0
    for i in 0..<numbers.count {
        assert(total == numbers[..<i].reduce(0, +), "invariant broken at pass \(i)")
        total += numbers[i]
    }
    return total
}

print(total(of: [4, 7, 1, 9]))
print(total(of: []))
```

```output
21
0
```

The check re-adds the first `i` numbers on every pass, which makes the function much slower, so it's a testing tool. Release builds skip `assert` entirely. When a tricky loop misbehaves, an assert on its invariant tells you which pass broke it.

## A harder one: reversing in place

Invariants really earn their keep on loops with more moving parts. This reverses an array in place by swapping from both ends towards the middle:

```swift run
func reverseInPlace(_ items: inout [Int]) {
    var left = 0
    var right = items.count - 1
    while left < right {
        items.swapAt(left, right)
        left += 1
        right -= 1
    }
}

var odd = [1, 2, 3, 4, 5]
reverseInPlace(&odd)
print(odd)

var even = [1, 2, 3, 4]
reverseInPlace(&even)
print(even)

var empty: [Int] = []
reverseInPlace(&empty)
print(empty)
```

```output
[5, 4, 3, 2, 1]
[4, 3, 2, 1]
[]
```

The invariant: **everything before `left` and everything after `right` is already in its final place. The elements from `left` to `right` are still untouched.**

| pass | `left` | `right` | `items` |
| --- | --- | --- | --- |
| start | 0 | 4 | `[1, 2, 3, 4, 5]` |
| 1 | 1 | 3 | `[5, 2, 3, 4, 1]` |
| 2 | 2 | 2 | `[5, 4, 3, 2, 1]` |

- **Start.** Nothing is outside the range from 0 to the last index, so the statement is true with nothing in it.
- **Keep.** The swap puts the element at `left` and the element at `right` exactly where the reversed array needs them. Moving both inward keeps "outside is finished, inside is untouched".
- **Finish.** The loop stops when `left` is no longer less than `right`. At most one element sits between them, and the middle of a list stays put when you reverse it. So everything is in place.
- **Ends.** `right - left` shrinks by 2 every pass, so it must eventually stop being positive.

For the empty array, `right` starts at -1, the condition is false straight away, and nothing happens: the argument covered that case too. You'll meet this two-pointer shape again in Part III.

## When the keep check fails

This should return the index of the *first* largest value:

```swift
func indexOfFirstLargest(_ numbers: [Int]) -> Int? {
    guard !numbers.isEmpty else { return nil }
    var bestIndex = 0
    for i in 1..<numbers.count {
        if numbers[i] >= numbers[bestIndex] {
            bestIndex = i
        }
    }
    return bestIndex
}
```

The intended invariant is "`bestIndex` points at the first occurrence of the largest value seen so far". Check keep: when `numbers[i]` *equals* the best, `>=` moves `bestIndex` to the later copy, which isn't the first occurrence. For `[2, 9, 4, 9]`, it returns 3 instead of 1. Changing `>=` to `>` repairs it, and the invariant told you exactly which case to test: a tie.

## Finding an invariant

When you're designing a loop rather than checking one, ask: **after handling part of the input, what does my loop know?** The answer is usually "the answer for the part seen so far", such as the sum, the best, or the count. Then:

- write it as one precise sentence using the loop's variables;
- make sure it's strong enough to give the answer at the finish. "`total` is an `Int`" is true on every pass, and useless;
- be exact about *when* it holds. "At the start of pass `i`, the first `i` elements" and "after pass `i`, the first `i + 1` elements" are both fine. Mixing them up is an off-by-one error waiting to happen.

<Callout kind="gotcha" title="Invariants hold between passes">
An invariant can be briefly false *in the middle* of a pass. Between `total += numbers[i]` and moving on to the next `i`, the sum covers one more element than "the first `i`". That's fine. What matters is that it's true each time the loop is about to begin a pass, and when it exits.
</Callout>
