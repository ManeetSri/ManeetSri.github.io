## Why it matters

Planning in Swift means thinking about two things at once: the idea and the syntax. Pseudocode lets you plan the idea alone, then translate. Interviewers often ask you to outline your approach before you code, engineers sketch algorithms in design documents and on whiteboards, and textbooks describe almost every algorithm this way. It's the bridge between "I think I know how" and working code.

## What pseudocode is

**Pseudocode** is a plan written in plain language with the *shape* of code: steps in order, indented blocks for loops and decisions, and a clear answer at the end. It has no official rules, so no compiler will complain. What matters is that it's clear and consistent.

Here's a plan for counting the passing scores in a list:

```text
count ← 0
for each score in scores:
    if score ≥ 50:
        count ← count + 1
return count
```

Read `←` as "becomes": `count ← count + 1` means "count becomes one more than it was". Indentation shows what's inside the loop and the `if`, just as braces do in Swift.

Most pseudocode phrases have an obvious Swift partner:

| Pseudocode | Swift |
| --- | --- |
| `count ← 0` | `var count = 0` |
| for each score in scores | `for score in scores` |
| repeat while n is above 0 | `while n > 0` |
| append x to result | `result.append(x)` |
| best is nothing | `best == nil`, with `best` an optional |
| return count | `return count` |

## From problem to plan to Swift

Here's a problem worth planning: **squash each run of repeated letters into the letter and its count**, so `"aaabccdddd"` becomes `"a3b1c2d4"`. This is a simple form of compression called run-length encoding.

Start with the idea in a sentence: walk along the text, remembering the current letter and how many times in a row you've seen it, and write out each run when it ends. Now turn that into steps:

```text
if text is empty:
    return ""
result ← ""
current ← the first character
count ← 1
for each character c after the first:
    if c is the same as current:
        count ← count + 1
    else:
        append current and count to result
        current ← c
        count ← 1
append current and count to result
return result
```

Writing the steps out exposed two details that are easy to miss when you jump straight into code. Empty text has no first character, so it needs handling first. And the last run never meets a different letter, so the loop never writes it out: the second-to-last line exists for exactly that reason.

Each line now becomes a line or two of Swift:

```swift run
func runLengthEncoded(_ text: String) -> String {
    guard let first = text.first else { return "" }
    var result = ""
    var current = first
    var count = 1
    for character in text.dropFirst() {
        if character == current {
            count += 1
        } else {
            result += "\(current)\(count)"
            current = character
            count = 1
        }
    }
    result += "\(current)\(count)"
    return result
}

print(runLengthEncoded("aaabccdddd"))
print(runLengthEncoded("z"))
print("Empty text gives \"\(runLengthEncoded(""))\"")
```

```output
a3b1c2d4
z1
Empty text gives ""
```

The translation needed a few Swift decisions the plan didn't care about: `guard let` for the possibly missing first character, `dropFirst()` for "each character after the first", and string interpolation to append a letter and a number. The thinking was already done.

<Callout kind="tip" title="Keep the plan as signposts">
For longer functions, a few of your pseudocode lines make good comments above the blocks they became, such as `// Write out the final run`. Don't keep every line, though: a comment that repeats the code word for word adds nothing.
</Callout>

## How much detail?

Pseudocode can be too vague or too detailed:

- **Too vague:** "compress the text". That's the problem, not a plan.
- **Too detailed:** `for i in 1..<chars.count where chars[i] != chars[i - 1]`. That's Swift with the planning skipped, and it drags you back into syntax.
- **About right:** each line turns into one to three lines of code, and every decision has been made.

A good test: could someone else turn your plan into code without asking you a single question? If they'd have to ask "and what happens when the letters differ?", the plan isn't finished.

<Callout kind="warning" title="Don't hide the hard part">
"Find the two numbers that add up to the target" is not a step, it's the whole problem. When one line of your plan is much harder than the others, it needs its own plan.
</Callout>

## Big steps get their own plans

When a step is a problem in its own right, plan the top level first and give that step a name. Then plan it separately, and it becomes a helper function, like the ones you wrote in [Nested helper functions](/dsa/learn/swift-nested-functions).

**Find the longest word that reads the same backwards (a palindrome), or nothing if there isn't one.** The top level:

```text
best ← nothing
for each word in words:
    if word is a palindrome:
        if best is nothing or word is longer than best:
            best ← word
return best
```

"Word is a palindrome" gets its own small plan: compare the word with its reverse. In Swift, the top level and the helper stay separate:

```swift run
func isPalindrome(_ word: String) -> Bool {
    word == String(word.reversed())
}

func longestPalindrome(in words: [String]) -> String? {
    var best: String? = nil
    for word in words where isPalindrome(word) {
        if best == nil || word.count > best!.count {
            best = word
        }
    }
    return best
}

print(longestPalindrome(in: ["kayak", "swift", "racecar", "noon"]) ?? "none")
print(longestPalindrome(in: ["apple", "pear"]) ?? "none")
```

```output
racecar
none
```

"Nothing" in the plan became an optional, `String?`. The force unwrap `best!` is safe here because `||` only looks at its right side when `best == nil` is false. And "longer than" means strictly longer, so when two palindromes tie, the first one wins. A plan forces you to decide that kind of detail; code written in a hurry decides it by accident.

## Common mistakes

- **Writing Swift and calling it pseudocode.** If you're worrying about types and brackets, you're coding, not planning.
- **Leaving out the edge cases.** The plan is the cheapest place to decide what happens with empty input or one element.
- **Not translating exactly.** When a problem describes an algorithm step by step, follow it to the letter. A "small improvement" during translation is a common source of wrong answers.
