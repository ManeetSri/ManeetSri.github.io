## Why it matters

A **dry run** is running an algorithm by hand, on paper or in your head, before or instead of running it on a computer. It catches mistakes in a plan before you've written any code, finds bugs when there's no debugger to hand, and lets you show an interviewer that your solution works. You met trace tables in [Nested loops and trace tables](/dsa/learn/swift-nested-loops). This lesson turns them into a habit you'll use on every problem.

## Playing the computer

To dry run, you pretend to be the computer. Pick one input, then follow the steps **exactly as written**, not as you meant them. Keep every variable in a **trace table**:

- one column for each variable that changes, plus any condition the loop tests;
- a first row, or a note, for the starting values;
- one new row for each pass of the loop.

The rule that makes it work: never skip a row because "it obviously does the same thing". Bugs live in the rows you skip, and most of all in the first and last passes.

## A worked dry run

This program reverses the digits of a number. Before you press play, predict what it prints for `1230`:

```swift
var n = number
var reversed = 0
while n > 0 {
    let digit = n % 10
    reversed = reversed * 10 + digit
    n /= 10
}
print(reversed)
```

Now step through it. Each pass of the loop adds a row to the table:

```visual traceTable
program: reverseDigits
input:
  number: 1230
```

| pass | `digit` | `reversed` | `n` |
| --- | --- | --- | --- |
| start | | 0 | 1230 |
| 1 | 0 | 0 | 123 |
| 2 | 3 | 3 | 12 |
| 3 | 2 | 32 | 1 |
| 4 | 1 | 321 | 0 |

It prints `321`, not `0321`, because a number can't hold a leading zero. Is that right? It depends on the problem. If you needed the digits as text, this algorithm would be wrong for numbers ending in 0. A dry run doesn't only check code: it raises questions you need to answer.

Notice the work each row shows. `n % 10` reads the last digit, `reversed * 10` shifts the reversed number one place left to make room, and `n /= 10` drops the digit that's been used. The loop runs once per digit, then stops when `n` reaches 0.

## Choosing inputs to trace

Tracing takes time, so choose inputs that teach you something:

- **Small.** Three to five elements, or a three- or four-digit number. A longer input takes more time without telling you more.
- **Typical first.** Make sure the normal case works before hunting for the strange ones.
- **Then the edges.** Empty input, one element, zero, negatives, the values where an `if` changes its mind. The edge-case lesson later in this module turns this into a checklist.
- **With an answer you already know.** If you can't tell whether the final value is right, the trace can't tell you either.

## Finding a bug

This function should add up the digits of a number, so `digitSum(472)` should give 4 + 7 + 2 = 13:

```swift
func digitSum(_ number: Int) -> Int {
    var n = number
    var total = 0
    while n > 0 {
        n /= 10
        total += n % 10
    }
    return total
}
```

It returns 11. Rather than staring at the code, trace it:

| pass | `n` after `n /= 10` | `n % 10` | `total` |
| --- | --- | --- | --- |
| start | 472 | | 0 |
| 1 | 47 | 7 | 7 |
| 2 | 4 | 4 | 11 |
| 3 | 0 | 0 | 11 |

The table points straight at the problem. The 2 is never added: the first line of the loop throws away the last digit before the second line reads it. Swap the two lines and trace again:

```swift run
func digitSum(_ number: Int) -> Int {
    var n = number
    var total = 0
    while n > 0 {
        total += n % 10
        n /= 10
    }
    return total
}

print(digitSum(472))
print(digitSum(5))
print(digitSum(0))
```

```output
13
5
0
```

The order of two lines was the entire bug. That's typical: dry runs are best at exactly the mistakes that look fine when you read the code.

## Check the boundaries

The first and last passes of a loop deserve the most care. For each, write down the loop variable's value and what it touches. This function counts how many times a number is bigger than the one before it:

```swift run
func countRises(_ numbers: [Int]) -> Int {
    guard numbers.count > 1 else { return 0 }
    var rises = 0
    for i in 1..<numbers.count {
        if numbers[i] > numbers[i - 1] {
            rises += 1
        }
    }
    return rises
}

print(countRises([3, 5, 4, 8, 9]))
print(countRises([7]))
```

```output
3
0
```

Check the boundaries for `[3, 5, 4, 8, 9]`:

| pass | `i` | compares | rise? |
| --- | --- | --- | --- |
| first | 1 | `numbers[0]` and `numbers[1]`: 3, 5 | yes |
| last | 4 | `numbers[3]` and `numbers[4]`: 8, 9 | yes |

Both are valid indices, and every neighbouring pair is compared once. If the loop started at 0, the first pass would read `numbers[-1]` and crash. And without the `guard`, an empty array would make the range `1..<0`, which also crashes. Two rows of a table caught both.

## Tracing what you don't understand yet

You can dry run an algorithm without knowing *why* it works. This is Euclid's algorithm for the greatest common divisor, the largest number that divides both inputs exactly. You'll see why it works in M15. For now, follow the steps:

```visual traceTable
program: gcd
input:
  first: 252
  second: 105
```

The table shows `a % b` shrinking, 42, then 21, then 0, and the answer is the last non-zero value, 21. Sure enough, 252 = 21 × 12 and 105 = 21 × 5. Tracing an unfamiliar algorithm is often the fastest way to start understanding it.

<Callout kind="tip" title="Let the program check your trace">
Your hand-made table is a prediction. To compare it with reality, print the same columns from inside the loop, as you did in M03, or step through with the debugger from M12. The first row where they differ is where the bug is.
</Callout>

## Common mistakes

- **Tracing what you meant.** Read each line as the computer will, not as you hoped it would. This is why it helps to trace someone else's code, or your own after a break.
- **Skipping the starting values.** Many bugs are in the setup, like a total that starts at 1, or a best value that starts at 0 when everything is negative.
- **Updating in the wrong order.** When a step changes two variables, use the old values exactly as the code does. In Euclid's algorithm, `remainder` is worked out before `a` and `b` change.
- **Stopping too early.** The final pass, and the check that ends the loop, are where off-by-one errors hide.
