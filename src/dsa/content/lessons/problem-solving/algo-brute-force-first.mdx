## Why it matters

When a problem looks hard, the temptation is to hunt for the clever trick straight away. Strong problem solvers do the opposite: they write the simplest correct solution first, however slow. It proves they understand the problem, it's often fast enough, and it becomes the yardstick every faster version is tested against. This is step 3 of the framework from M00, and this lesson shows how to get the most out of it.

## What brute force means

A **brute-force** solution tries every possible candidate answer, straight from the problem's definition, and checks each one. Every element, every pair, every subset, every ordering: whatever the candidates are, it tries them all. There's no cleverness, and that's the point. Its correctness is easy to see.

Here's a problem to try it on: **return the smallest positive whole number that isn't in the array.**

| Input | Output |
| --- | --- |
| `[3, 1, 5]` | `2` |
| `[1, 2, 3]` | `4` |
| `[-4, 0, 7]` | `1` |

The candidates are 1, 2, 3, and so on. Try each in turn, and stop at the first one that's missing:

```swift run
func smallestMissing(_ numbers: [Int]) -> Int {
    var candidate = 1
    while numbers.contains(candidate) {
        candidate += 1
    }
    return candidate
}

print(smallestMissing([3, 1, 5]))
print(smallestMissing([1, 2, 3]))
print(smallestMissing([-4, 0, 7]))
print(smallestMissing([]))
```

```output
2
4
1
1
```

Can you see it's correct? It returns the first positive number that isn't present, which is exactly the definition. It even handles the empty array without any special code.

### Make sure it stops

Trying candidates one by one only works if the search is bounded. Here it is: an array of `n` numbers can't contain all of 1, 2, …, n + 1, because that's n + 1 different values. So the answer is at most n + 1, and the loop runs at most n + 1 times. Each `contains` scans the whole array, up to `n` steps, so the total is roughly n × n steps.

When the candidates seem endless, finding a bound like this is part of the brute-force design.

## Why start with brute force

1. **It proves you understand the problem.** If you can't write *any* correct solution, you aren't ready to optimise. Writing the brute force often surfaces questions, such as "what if the array is empty?", that you'd otherwise meet halfway through a clever version.
2. **It's a baseline for testing.** A slow answer you trust lets you check a fast answer you don't trust yet, on thousands of inputs.
3. **It might be enough.** If the array has at most 1,000 numbers, n² is about a million steps, which runs in a blink. The next lessons show how to read that from the constraints.
4. **It shows you what to optimise.** Look at what the brute force does over and over. That repeated work is your target.

## Spotting the repeated work

In `smallestMissing`, every candidate triggers a fresh scan of the whole array. The array never changes, yet the code searches it again and again. That's the waste.

The fix uses a tool from [Sets and set algebra](/dsa/learn/swift-sets): put the numbers in a `Set` once, and each `contains` check becomes fast instead of a full scan.

```swift run
func smallestMissingFast(_ numbers: [Int]) -> Int {
    let present = Set(numbers)
    var candidate = 1
    while present.contains(candidate) {
        candidate += 1
    }
    return candidate
}

print(smallestMissingFast([3, 1, 5]))
print(smallestMissingFast([1, 2, 3]))
```

```output
2
4
```

Building the set takes about `n` steps, and each check is quick on average, so the whole thing takes roughly `n` steps instead of n². The algorithm is the same; only the repeated work changed. You'll learn even better approaches, using no extra memory, in Part III.

## Testing the fast version against the slow one

Suppose someone suggests a shortcut: "if 1 is missing, the answer is 1; otherwise it's one more than the largest number". It sounds plausible, and it works for `[1, 2, 3]`. Instead of arguing, test it against the brute force on every small array you can think of. Here that's *every* array of up to four numbers, each from -1 to 4:

```swift run
func smallestMissing(_ numbers: [Int]) -> Int {
    var candidate = 1
    while numbers.contains(candidate) {
        candidate += 1
    }
    return candidate
}

func smallestMissingShortcut(_ numbers: [Int]) -> Int {
    if !numbers.contains(1) {
        return 1
    }
    return numbers.max()! + 1
}

// Every array of length 0 to 4 with values from -1 to 4
var inputs: [[Int]] = [[]]
var layer: [[Int]] = [[]]
for _ in 1...4 {
    var next: [[Int]] = []
    for array in layer {
        for value in -1...4 {
            next.append(array + [value])
        }
    }
    inputs += next
    layer = next
}

var mismatches = 0
for input in inputs {
    let expected = smallestMissing(input)
    let actual = smallestMissingShortcut(input)
    if expected != actual {
        if mismatches == 0 {
            print("First mismatch: \(input), expected \(expected), got \(actual)")
        }
        mismatches += 1
    }
}
print("Checked \(inputs.count) inputs, \(mismatches) mismatches")
```

```output
First mismatch: [1, 3], expected 2, got 4
Checked 1555 inputs, 440 mismatches
```

In a fraction of a second, the checker found a small counterexample: `[1, 3]` is missing 2, not 4. Swap in `smallestMissingFast` and the same checker reports 0 mismatches out of 1,555.

This is one of the most useful habits in the whole course. Small inputs are where bugs show up, and a computer can try thousands of them faster than you can try one. In a Swift Testing suite you can do the same with random arrays:

```swift
@Test func fastMatchesBruteForce() {
    for _ in 0..<1_000 {
        let numbers = (0..<Int.random(in: 0...8)).map { _ in Int.random(in: -3...10) }
        #expect(smallestMissingFast(numbers) == smallestMissing(numbers))
    }
}
```

When a random test fails, `#expect` shows you the values involved, so you can copy the failing input into a test of its own.

## When brute force is the answer

Sometimes you never need anything faster. If the input is tiny, the simplest correct code is the best code: easier to read, easier to trust. And for some problems, nobody knows a way that's fundamentally faster than trying almost every possibility. For those, the skill is making the brute force as tidy and quick as possible, which you'll practise in Part VII with backtracking.

<Callout kind="warning" title="Keep the brute force dumb">
A brute force is only a trustworthy yardstick if it's obviously correct. Don't put shortcuts in it. If it needs a clever argument to be right, it's not a baseline any more, it's a second thing that might be wrong.
</Callout>

## Common mistakes

- **Skipping it because it's "too slow".** You haven't checked the constraints yet, and even if it is too slow, you'll still want it for testing.
- **Forgetting to bound the search.** "Try 1, 2, 3, …" needs a reason to believe it stops.
- **Stopping there when it isn't enough.** If the constraints say n can be 100,000, an n² brute force is about ten billion steps. Write it, test with it, then optimise.
