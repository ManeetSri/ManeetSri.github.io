## Why it matters

This is the most important idea in this module. When you copy a struct, you get a second, independent value. When you copy a class variable, you get a second *name* for the same object. Mixing the two up causes some of the most confusing bugs in Swift. It also decides how data structures behave: a linked list's nodes must point at each other, which only references can do.

## Two families of types

Every Swift type belongs to one of two families:

| Value types | Reference types |
| --- | --- |
| `struct`, `enum`, tuples | `class` |
| `Int`, `Double`, `Bool`, `String` | closures (M06) |
| `Array`, `Set`, `Dictionary` | most iOS framework types, like `UIView` |

The family decides what happens when a value is **assigned** to a new variable, **passed** to a function or **stored** in a collection.

- A **value type** is copied. Each variable holds its own value.
- A **reference type** is shared. Each variable holds a *reference*, an arrow pointing at one object that lives elsewhere in memory.

You met the first half in [Collections are values](/dsa/learn/swift-collections-are-values). Now you'll see both side by side.

## Copying a struct gives an independent copy

```swift run
struct PointValue {
    var x: Int
    var y: Int
}

var a = PointValue(x: 1, y: 2)
var b = a
b.x = 100

print("a.x =", a.x)
print("b.x =", b.x)
```

```output
a.x = 1
b.x = 100
```

`var b = a` made a complete copy. Changing `b` left `a` alone. Here's what memory looks like at each step:

| After… | `a` holds | `b` holds |
| --- | --- | --- |
| `var a = PointValue(x: 1, y: 2)` | x 1, y 2 | (not yet created) |
| `var b = a` | x 1, y 2 | x 1, y 2, a separate copy |
| `b.x = 100` | x 1, y 2 | x 100, y 2 |

## Copying a class variable shares one object

Now the identical code with `class` instead of `struct`:

```swift run
class PointObject {
    var x: Int
    var y: Int

    init(x: Int, y: Int) {
        self.x = x
        self.y = y
    }
}

var a = PointObject(x: 1, y: 2)
var b = a
b.x = 100

print("a.x =", a.x)
print("b.x =", b.x)
```

```output
a.x = 100
b.x = 100
```

Changing `b` changed `a` too, because there's only one object. `var b = a` copied the *reference*, the arrow, not the object:

| After… | `a` holds | `b` holds | The one object |
| --- | --- | --- | --- |
| `var a = PointObject(…)` | arrow to the object | (not yet created) | x 1, y 2 |
| `var b = a` | arrow to the object | arrow to the same object | x 1, y 2 |
| `b.x = 100` | arrow to the object | arrow to the same object | x 100, y 2 |

<Callout kind="analogy">
Copying a struct is like photocopying a document: scribble on your copy and the original is untouched. Copying a class reference is like sharing a link to an online document: whoever edits it, everyone with the link sees the change.
</Callout>

## let means different things

You've already seen hints of this. For a struct, `let` freezes the entire value. For a class, `let` freezes only the arrow, so it can never point at a different object, but the object it points at can still change:

```swift run
struct ScoreValue {
    var points = 0
}

class ScoreObject {
    var points = 0
}

let board = ScoreObject()
board.points = 10
board.points += 5
print(board.points)

var other = ScoreValue()
other.points = 3
print(other.points)
```

```output
15
3
```

| | `let` struct | `let` class reference |
| --- | --- | --- |
| Change a property? | no | yes |
| Point at a different instance? | no | no |

If you want a class whose objects can never change, make all its properties `let`.

## Passing to functions

The same rule applies when you pass a value to a function. A struct parameter is a copy (and a constant one), so the function can't change the caller's value. A class parameter is another reference to the caller's object, so the function **can** change it:

```swift run
struct WalletValue {
    var coins = 10
}

class WalletObject {
    var coins = 10
}

func spendAll(_ wallet: WalletObject) {
    wallet.coins = 0
}

func spentVersion(of wallet: WalletValue) -> WalletValue {
    var copy = wallet
    copy.coins = 0
    return copy
}

let shared = WalletObject()
spendAll(shared)
print("Object after the call:", shared.coins)

let mine = WalletValue()
let changed = spentVersion(of: mine)
print("Value after the call:", mine.coins)
print("Returned copy:", changed.coins)
```

```output
Object after the call: 0
Value after the call: 10
Returned copy: 0
```

With a value type, the only ways for a function to change the caller's data are to **return** a new value or to take an **`inout`** parameter, which you met in [inout, swap and swapAt](/dsa/learn/swift-inout-swap). Both are visible at the call site (`&wallet` or an assignment), so you always know when something may change. With a class, any function you hand the object to might change it, silently.

## Collections hold copies or references

An array of structs holds independent values. An array of class instances holds references. This difference causes a classic bug:

```swift run
struct TaskValue {
    var done = false
}

class TaskObject {
    var done = false
}

var values = [TaskValue(), TaskValue()]
let backupValues = values
values[0].done = true
print("Value backup changed?", backupValues[0].done)

let objects = [TaskObject(), TaskObject()]
let backupObjects = objects
objects[0].done = true
print("Object backup changed?", backupObjects[0].done)
```

```output
Value backup changed? false
Object backup changed? true
```

Copying `objects` copied the array of **arrows**, not the objects they point at. Both arrays point at the same two tasks, so the "backup" isn't a backup at all. This is called a **shallow copy**.

There's an opposite surprise when looping. A `for-in` loop variable is a constant copy of each element:

```swift
for task in values {
    task.done = true      // error: cannot assign to property: 'task' is a 'let' constant
}
```

For an array of structs, change the elements through their indices instead: `for i in values.indices { values[i].done = true }`. For an array of objects, `task.done = true` compiles, because `task` is a copied *arrow* to an object that can change.

<Callout kind="gotcha" title="Swift gotcha: a copy out of a dictionary is a copy">
`var p = positions["robot"]!` gives you a **copy** of a struct stored in the dictionary. Changing `p` doesn't change the dictionary. Write the result back with `positions["robot"] = p`, or change it in place with `positions["robot"]?.x += 1`.
</Callout>

## Why linked structures need references

Here's where the difference really matters for DSA. A **linked list** is a chain of **nodes**, where each node holds a value and points at the next node. Try it with a struct:

```swift
struct Node {
    var value: Int
    var next: Node?
}
```

```text title="What you'll see"
error: value type 'Node' cannot have a stored property that recursively contains it
```

A struct stores its properties *inside itself*. A `Node` containing a whole `Node`, containing a whole `Node`… would need infinite space. A class property only stores an arrow, which is always the same small size, so a class works:

```swift run
final class Node {
    var value: Int
    var next: Node?

    init(value: Int, next: Node? = nil) {
        self.value = value
        self.next = next
    }
}

let third = Node(value: 30)
let second = Node(value: 20, next: third)
let head = Node(value: 10, next: second)

var current: Node? = head
while let node = current {
    print(node.value)
    current = node.next
}

second.value = 25
print("Through head:", head.next!.value)
```

```output
10
20
30
Through head: 25
```

What to notice:

- `while let node = current` keeps going until `current` is `nil`, the end of the chain. That's how you'll walk every linked list in M25.
- Changing `second` was visible through `head.next`, because they're the same object. With references, many arrows can lead to one node. Trees, graphs and linked lists all depend on that.

You'll meet another way to build recursive data, the **indirect enum**, later in this module.

## Choosing between them

| You need… | Choose |
| --- | --- |
| A simple piece of data: a point, a colour, a move | struct |
| Copies that can't affect each other | struct |
| One shared thing that many parts of the program see change | class |
| Nodes that point at each other (lists, trees, graphs) | class |
| Inheritance, or `deinit` | class |

Start with a struct. Switch to a class only when you can name the reason.

