## Why it matters

Classes are Swift's other way to build a type. They look a lot like structs, but they add **inheritance** (one class building on another) and a **deinitialiser** that runs when an object is destroyed. In iOS, every screen is a class (`UIViewController`). In DSA, the nodes of linked lists and trees are usually classes, for reasons the next lesson makes clear.

## Defining a class

A class has properties, methods and initialisers, just like a struct:

```swift run
class BankAccount {
    var owner: String
    var balance: Int

    init(owner: String, balance: Int) {
        self.owner = owner
        self.balance = balance
    }

    func deposit(_ amount: Int) {
        balance += amount
    }
}

let account = BankAccount(owner: "Maneet", balance: 100)
account.deposit(50)
print(account.balance)
```

```output
150
```

Two differences from structs already show:

1. **You write the initialiser.** Classes get no memberwise initialiser. Leave it out and Swift complains:

   ```text title="What you'll see"
   error: class 'BankAccount' has no initializers
   note: stored property 'owner' without initial value prevents synthesized initializers
   ```

   If every property has a default value, you get a free `init()` with no parameters.
2. **No `mutating`.** `deposit` changes `balance` without any keyword. And `account` is a `let`, yet its balance changed. For a class, `let` fixes *which object* the name refers to, not the object's contents. The next lesson explains exactly why.

<Callout kind="note">
An instance of a class is usually called an **object**. The words "instance" and "object" are often used interchangeably.
</Callout>

## Inheritance

A class can **inherit** from another class. The new class, the **subclass**, gets all the properties and methods of the **superclass**, and can add its own:

```swift run
class Animal {
    let name: String

    init(name: String) {
        self.name = name
    }

    func describe() -> String {
        "\(name) is an animal"
    }
}

class Dog: Animal {
    var tricks: [String] = []

    func learn(_ trick: String) {
        tricks.append(trick)
    }
}

let rex = Dog(name: "Rex")
rex.learn("sit")
print(rex.name)
print(rex.describe())
print(rex.tricks)
```

```output
Rex
Rex is an animal
["sit"]
```

`class Dog: Animal` reads "Dog is a kind of Animal". `Dog` never declared `name`, `init(name:)` or `describe()`; it inherited them. Because `tricks` has a default value, `Dog` also inherits `Animal`'s initialiser unchanged.

Only classes can inherit. Structs and enums can't.

### Overriding

A subclass can replace an inherited method with its own version. Mark it `override`, so Swift knows you meant to:

```swift run
class Animal {
    let name: String

    init(name: String) {
        self.name = name
    }

    func sound() -> String {
        "..."
    }

    func speak() -> String {
        "\(name) says \(sound())"
    }
}

class Dog: Animal {
    override func sound() -> String {
        "Woof"
    }
}

class Cat: Animal {
    override func sound() -> String {
        "Meow"
    }
}

let pets: [Animal] = [Dog(name: "Rex"), Cat(name: "Tom"), Animal(name: "Generic")]
for pet in pets {
    print(pet.speak())
}
```

```output
Rex says Woof
Tom says Meow
Generic says ...
```

What to notice:

- The array's type is `[Animal]`, yet it holds a `Dog` and a `Cat`. A subclass instance can be used anywhere its superclass is expected.
- `speak()` is written once, in `Animal`. When it calls `sound()`, Swift runs the version belonging to the actual object, so each pet makes its own noise. This is called **polymorphism**: one call, different behaviour depending on the real type.
- Forgetting `override` is a compile error (`overriding declaration requires an 'override' keyword`), which protects you from replacing a method by accident.

### Calling the superclass with super

Inside a subclass, **`super`** refers to the superclass's version. Use it to extend a method rather than replace it, and to call the superclass's initialiser:

```swift run
class Vehicle {
    let wheels: Int

    init(wheels: Int) {
        self.wheels = wheels
    }

    func summary() -> String {
        "\(wheels) wheels"
    }
}

class Bicycle: Vehicle {
    let hasBell: Bool

    init(hasBell: Bool) {
        self.hasBell = hasBell
        super.init(wheels: 2)
    }

    override func summary() -> String {
        super.summary() + (hasBell ? ", with a bell" : ", no bell")
    }
}

print(Bicycle(hasBell: true).summary())
```

```output
2 wheels, with a bell
```

The order inside `Bicycle`'s `init` matters: first set the subclass's own properties (`hasBell`), *then* call `super.init`. Swift enforces this so that no method ever sees a half-built object.

<Callout kind="gotcha" title="Swift gotcha: super.init comes last">
In a subclass initialiser, assign every new stored property **before** calling `super.init(...)`. Calling it first is a compile error, the opposite of what some other languages require.
</Callout>

## final: no more subclassing

Mark a class `final` and nobody can subclass it. Mark a method `final` and no subclass can override it:

```swift
final class ListNode {
    var value: Int
    var next: ListNode?

    init(value: Int) {
        self.value = value
    }
}

class SpecialNode: ListNode {}   // error: inheritance from a final class 'ListNode'
```

Why bother? Two reasons:

- **Clarity.** `final` says "this class isn't designed to be extended", so readers don't have to wonder.
- **Speed.** When Swift knows a method can't be overridden, it can call it directly instead of looking up which version to run. In tight loops this matters a little.

In this course, node classes like `ListNode` are always `final`. You'll build linked lists from exactly this class in M25.

## deinit: when an object is destroyed

A class can have a **deinitialiser**, `deinit`, which Swift runs automatically just before the object is destroyed. Swift destroys an object as soon as nothing refers to it any more. You'll learn how Swift counts those references in M11, but you can watch it happen now:

```swift run
class Ticket {
    let id: Int

    init(id: Int) {
        self.id = id
        print("Ticket \(id) created")
    }

    deinit {
        print("Ticket \(id) destroyed")
    }
}

var current: Ticket? = Ticket(id: 1)
current = nil
print("After setting to nil")

do {
    let first = Ticket(id: 2)
    let second = Ticket(id: 3)
    print("Using tickets \(first.id) and \(second.id)")
}
print("After the do block")
```

```output
Ticket 1 created
Ticket 1 destroyed
After setting to nil
Ticket 2 created
Ticket 3 created
Using tickets 2 and 3
Ticket 3 destroyed
Ticket 2 destroyed
After the do block
```

What to notice:

- `current` is an optional `Ticket?`. Setting it to `nil` removes the only reference, so ticket 1 is destroyed immediately.
- A `do { }` block creates a scope. When it ends, `first` and `second` stop existing, and so do their objects. Here they go in reverse order of creation.
- `deinit` takes no parameters and you never call it yourself.

Structs have no `deinit`: they're values, not objects with a lifetime of their own. A `deinit` is useful for cleanup, such as closing a file, and later for spotting memory leaks.

## Structs or classes?

Here's a side-by-side summary of what you've seen so far:

| | Struct | Class |
| --- | --- | --- |
| Memberwise initialiser | yes, automatic | no, write `init` |
| Changing methods | need `mutating` | no keyword |
| Inheritance | no | yes |
| `deinit` | no | yes |
| `let` instance | fully frozen | contents can still change |

Swift's advice, which this course follows: **use a struct by default**, and choose a class when you need what only a class gives you, such as inheritance or one shared object that several parts of the program refer to. That last point, sharing, is the biggest difference of all, and the whole of the next lesson.
