## Why it matters

Data structures change: you push onto a stack, insert into a heap, move a player on a grid. In a struct, a method that changes the instance must say so with the `mutating` keyword. And when the memberwise initialiser isn't enough, for example because input needs checking, you write your own initialiser. Both show up in every data structure you'll build.

## Methods can't change a struct by default

Try writing a method that moves a point:

```swift
struct Point {
    var x: Int
    var y: Int

    func move(dx: Int, dy: Int) {
        x += dx
        y += dy
    }
}
```

```text title="What you'll see"
error: left side of mutating operator isn't mutable: 'self' is immutable
note: mark method 'mutating' to make 'self' mutable
```

Inside an ordinary struct method, `self` is a constant. Swift does this on purpose: a method that only reads is safe to call on any instance, including one stored in a `let`. Changing the instance has to be declared openly.

## mutating methods

Add `mutating` before `func` and the method may change any `var` property:

```swift run
struct Point {
    var x: Int
    var y: Int

    mutating func move(dx: Int, dy: Int) {
        x += dx
        y += dy
    }
}

var robot = Point(x: 0, y: 0)
robot.move(dx: 2, dy: 1)
robot.move(dx: -1, dy: 4)
print(robot)
```

```output
Point(x: 1, y: 5)
```

Because a mutating method changes the instance, you can only call it on a `var`:

```swift
let parked = Point(x: 0, y: 0)
parked.move(dx: 1, dy: 1)
```

```text title="What you'll see"
error: cannot use mutating member on immutable value: 'parked' is a 'let' constant
```

The rule is consistent with what you already know: `numbers.append(4)` fails on a `let` array because `append` is a mutating method on `Array`.

### Replacing self entirely

A mutating method can even assign a brand new value to `self`:

```swift run
struct Point {
    var x: Int
    var y: Int

    mutating func reset() {
        self = Point(x: 0, y: 0)
    }
}

var cursor = Point(x: 7, y: 9)
cursor.reset()
print(cursor)
```

```output
Point(x: 0, y: 0)
```

<Callout kind="analogy">
Think of `mutating` as a "this edits the document" label on a button. Swift greys the button out when the document is read-only, which is what a `let` instance is.
</Callout>

## Writing your own initialiser

An **initialiser** is written with `init`, with no `func` and no return type. Its job is to give **every stored property a value** before the instance can be used:

```swift run
struct Temperature {
    var celsius: Double

    init(fahrenheit: Double) {
        celsius = (fahrenheit - 32) * 5 / 9
    }
}

let boiling = Temperature(fahrenheit: 212)
print(boiling.celsius)
```

```output
100.0
```

When a parameter has the same name as a property, use `self.` to tell them apart. `self.name` is the property, plain `name` is the parameter:

```swift run
struct Player {
    var name: String
    var level: Int

    init(name: String, level: Int) {
        self.name = name
        self.level = max(1, min(level, 99))
    }
}

print(Player(name: "Ada", level: 150).level)
print(Player(name: "Bo", level: -3).level)
```

```output
99
1
```

This initialiser **clamps** the level into the range 1...99, something the memberwise initialiser can't do. Checking or tidying input as the value is created means every `Player` that exists is valid. That's the idea of an **invariant**: a rule that's always true for an instance. Data structures rely on invariants, such as "a heap's smallest element is at the top".

<Callout kind="gotcha" title="Swift gotcha: your init replaces the memberwise one">
As soon as you write an `init` inside a struct, Swift stops generating the memberwise initialiser. After adding `init(fahrenheit:)`, the call `Temperature(celsius: 20)` no longer compiles. If you want both, write the memberwise one yourself too, or put your custom `init` in an **extension**, which keeps the generated one. You'll meet extensions in M10.
</Callout>

## Several initialisers

A type can have as many initialisers as you like, as long as their parameter labels differ. One initialiser can hand the work to another with `self.init(...)`, which is called **delegating**:

```swift run
struct Rectangle {
    var width: Int
    var height: Int

    init(width: Int, height: Int) {
        self.width = width
        self.height = height
    }

    init(side: Int) {
        self.init(width: side, height: side)
    }
}

let wide = Rectangle(width: 5, height: 2)
let square = Rectangle(side: 3)
print(wide.width, wide.height)
print(square.width, square.height)
```

```output
5 2
3 3
```

Delegation keeps the real work in one place, so a later fix only needs making once.

## Failable initialisers

Sometimes input can't make a valid instance at all. A **failable initialiser**, written `init?`, can give up by returning `nil`. The result is an optional, exactly like `Int("abc")` in M04:

```swift run
struct Percentage {
    let value: Int

    init?(_ value: Int) {
        guard value >= 0 && value <= 100 else {
            return nil
        }
        self.value = value
    }
}

if let score = Percentage(85) {
    print("Valid:", score.value)
}
if Percentage(140) == nil {
    print("140 is not a percentage")
}
```

```output
Valid: 85
140 is not a percentage
```

What to notice:

- The `_` before `value` removes the argument label, so you write `Percentage(85)`.
- `return nil` is the only kind of `return` allowed in an initialiser.
- `value` is a `let` property: once set in `init`, it can never change. Combined with the check, a `Percentage` can never hold 140.

## Putting it together: a tiny inventory

Here's a struct that uses a custom initialiser, a mutating method and a computed property together:

```swift run
struct Inventory {
    var counts: [String: Int]

    init() {
        counts = [:]
    }

    mutating func add(_ item: String, quantity: Int = 1) {
        counts[item, default: 0] += quantity
    }

    mutating func remove(_ item: String) -> Bool {
        guard let current = counts[item], current > 0 else {
            return false
        }
        counts[item] = current - 1
        return true
    }

    var totalItems: Int {
        counts.values.reduce(0, +)
    }
}

var bag = Inventory()
bag.add("apple", quantity: 3)
bag.add("pear")
print(bag.remove("apple"))
print(bag.remove("plum"))
print(bag.totalItems)
print(bag.counts["apple"] ?? 0)
```

```output
true
false
3
2
```

`remove` is mutating because it might change `counts`, and it returns a `Bool` to say whether it worked. Mutating methods can return values like any other method. You'll see the same shape soon: a stack's `pop()` changes the stack *and* returns the removed element.
