## Why it matters

With references, two different questions can be asked about two variables. "Do they hold equal values?" and "Do they point at the very same object?" Linked-list and graph algorithms ask the second question constantly: has the fast pointer caught up with the slow one, have we come back to the start, have we visited this node before? Swift's answer is the **identity operator**, `===`.

## Same object, or just equal?

Picture two identical twins. They look the same in every way, but they're two different people. Now picture one person with two nicknames. However you refer to them, it's the same person.

For class instances:

- `===` asks "are these the **same object**?" (one person, two nicknames).
- `!==` asks the opposite: "are these **different objects**?"

```swift run
final class Robot {
    var name: String

    init(name: String) {
        self.name = name
    }
}

let first = Robot(name: "R2")
let twin = Robot(name: "R2")
let nickname = first

print(first === nickname)
print(first === twin)
print(first !== twin)
```

```output
true
false
true
```

`first` and `twin` have the same name, but they're two separate objects, so `===` is `false`. `nickname` is another reference to `first`'s object, so `===` is `true`.

Identity is a fact about objects, not their contents. Change the name through one reference and they're still the same object, while the twin stays a different one:

```swift run
final class Robot {
    var name: String

    init(name: String) {
        self.name = name
    }
}

let first = Robot(name: "R2")
let nickname = first
nickname.name = "C3"
print(first.name)
print(first === nickname)
```

```output
C3
true
```

## `===` only works on classes

Structs and enums have no identity. A value is just a value, and every copy is its own. Asking whether two values are "the same object" doesn't make sense, and Swift refuses:

```swift
struct Point {
    var x: Int
}

let a = Point(x: 1)
let b = a
print(a === b)
```

```text title="What you'll see"
error: argument type 'Point' expected to be an instance of a class or class-constrained type
```

## `==` needs to be taught

The other question, "are these **equal**?", uses `==`. Swift knows how to compare `Int`s and `String`s, but it doesn't know what "equal" means for your class. Is a robot equal to another robot with the same name? Maybe, maybe not: you decide. Until you do, `==` doesn't compile:

```text title="What you'll see"
error: binary operator '==' cannot be applied to two 'Robot' operands
```

You teach a type `==` by making it conform to the `Equatable` protocol, which M10 covers properly. Here's a preview, so you can see the two questions side by side:

```swift run
final class Robot: Equatable {
    var name: String

    init(name: String) {
        self.name = name
    }

    static func == (lhs: Robot, rhs: Robot) -> Bool {
        lhs.name == rhs.name
    }
}

let first = Robot(name: "R2")
let twin = Robot(name: "R2")

print(first == twin)
print(first === twin)
```

```output
true
false
```

The twins are **equal** (same name) but not **identical** (two objects).

| Operator | Question | Works on | Who decides |
| --- | --- | --- | --- |
| `==` | equal values? | types that conform to `Equatable` | you, or Swift for simple types |
| `===` | the same object? | classes only | always memory identity |

## Identity in a linked structure

Here's identity doing real work. In a **circular list** the last node points back to the first. To visit each node once, walk forward until you arrive back where you started, an identity check:

```swift run
final class Node {
    let value: Int
    var next: Node?

    init(value: Int) {
        self.value = value
    }
}

let a = Node(value: 1)
let b = Node(value: 2)
let c = Node(value: 3)
a.next = b
b.next = c
c.next = a

var current = a
repeat {
    print(current.value)
    current = current.next!
} while current !== a
print("Back at the start")
```

```output
1
2
3
Back at the start
```

Why not compare values with `current.value != a.value`? Because values can repeat. Two different nodes might both hold `1`, and the loop would stop too early. Identity is the only reliable way to recognise *that particular node*.

<Callout kind="note">
Nodes that point at each other in a circle never get destroyed, because each is always referred to by another. That's a memory leak called a **retain cycle**. It doesn't matter in a short script, and M11 shows how to avoid it.
</Callout>

### Remembering objects you've seen

Graph algorithms often need "have I visited this object already?". `ObjectIdentifier(object)` turns an object's identity into a value you can store in a `Set`:

```swift run
final class Room {
    let name: String

    init(name: String) {
        self.name = name
    }
}

let hall = Room(name: "Hall")
let kitchen = Room(name: "Kitchen")
let route = [hall, kitchen, hall, hall, kitchen]

var visited = Set<ObjectIdentifier>()
for room in route {
    let isNew = visited.insert(ObjectIdentifier(room)).inserted
    print(room.name, isNew ? "(new)" : "(seen before)")
}
print("Different rooms:", visited.count)
```

```output
Hall (new)
Kitchen (new)
Hall (seen before)
Hall (seen before)
Kitchen (seen before)
Different rooms: 2
```

`insert` on a set returns whether the element was new, which saves a separate `contains` check.

<Callout kind="gotcha" title="Swift gotcha: === works with optionals">
`===` accepts optional references, so `node.next === nil` and `slow === fast` (both `Node?`) compile without unwrapping. Two `nil`s count as identical. This is handy in linked-list loops, but remember that `nil === nil` is `true`.
</Callout>
