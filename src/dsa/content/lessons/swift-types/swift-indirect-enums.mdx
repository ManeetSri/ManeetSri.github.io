## Why it matters

Some data is built out of smaller pieces of the same kind. An arithmetic expression contains smaller expressions; a folder contains folders; a tree contains smaller trees. This is **recursive data**, and it's everywhere in DSA. An **indirect enum** lets you describe it in a few lines, and recursive functions then process it naturally. This lesson is your first real taste of trees.

## An expression is a tree

Think about the expression `2 + 3 * 4`. Multiplication happens first, so it really means "2 plus (3 times 4)". Drawn as a picture, it's a tree: each operator has two smaller expressions beneath it, and the numbers sit at the bottom.

```text
      +
     / \
    2   *
       / \
      3   4
```

Every piece of this picture is itself an expression. The whole thing is an addition. Its right side, `3 * 4`, is a multiplication. And `2`, `3` and `4` are plain numbers. So an expression is **one of**:

- a number, or
- an addition of two expressions, or
- a multiplication of two expressions.

"One of" means enum, and "two expressions" means associated values. Let's write that.

## The indirect keyword

The natural first attempt fails:

```swift
enum Expr {
    case number(Int)
    case add(Expr, Expr)
    case multiply(Expr, Expr)
}
```

```text title="What you'll see"
error: recursive enum 'Expr' is not marked 'indirect'
```

This is the same problem you saw with a recursive struct in [Value vs reference semantics](/dsa/learn/swift-value-vs-reference). An enum value stores its associated values inside itself, so an `Expr` containing two whole `Expr`s, each containing two more, would need infinite space.

The fix is one keyword. **`indirect`** tells Swift to store those associated values somewhere else in memory and keep only a reference to them, just like a class property does. The size of each `Expr` becomes small and fixed:

```swift
indirect enum Expr {
    case number(Int)
    case add(Expr, Expr)
    case multiply(Expr, Expr)
}

let tree = Expr.add(.number(2), .multiply(.number(3), .number(4)))
```

Notice how the code mirrors the picture: `.add` at the top, `.number(2)` on its left, `.multiply(...)` on its right. Printing `tree` directly gives a long, hard-to-read description, so the next sections teach the tree to evaluate and describe itself.

You can mark the whole enum `indirect`, as here, or only the cases that recurse, with `indirect case add(Expr, Expr)`. Either way, an indirect enum is still a **value type**: copies are independent, and nothing about using it changes. `indirect` only changes how it's stored.

## Evaluating it recursively

How do you work out a tree's value? Ask each case:

- A number's value is the number itself. This is the **base case**: no recursion needed.
- An addition's value is the value of its left side plus the value of its right side. Those sides are expressions too, so you get their values by calling the same function again.

A recursive function over a recursive enum almost writes itself, one `switch` case per enum case:

```swift run
indirect enum Expr {
    case number(Int)
    case add(Expr, Expr)
    case multiply(Expr, Expr)
}

func evaluate(_ expression: Expr) -> Int {
    switch expression {
    case .number(let value):
        return value
    case let .add(left, right):
        return evaluate(left) + evaluate(right)
    case let .multiply(left, right):
        return evaluate(left) * evaluate(right)
    }
}

let tree = Expr.add(.number(2), .multiply(.number(3), .number(4)))
print(evaluate(tree))
print(evaluate(.multiply(.add(.number(2), .number(3)), .number(4))))
```

```output
14
20
```

The second tree is `(2 + 3) * 4`. With a tree, there's no need for brackets or precedence rules: the shape itself says what happens first. That's exactly how compilers and calculators represent expressions internally.

Trace the first one by hand, as in [A first look at recursion](/dsa/learn/swift-first-recursion):

| Order finished | Call | Returns |
| --- | --- | --- |
| 1 | `evaluate(.number(2))` | 2 |
| 2 | `evaluate(.number(3))` | 3 |
| 3 | `evaluate(.number(4))` | 4 |
| 4 | `evaluate(.multiply(3, 4))` | 3 × 4 = 12 |
| 5 | `evaluate(.add(2, multiply))` | 2 + 12 = 14 |

The top call starts first but finishes last: each call waits for its children's answers, and those answers flow back up to the top. Swift evaluates the left side of `+` before the right, so the `2` finishes before anything on the right.

## Turning the tree back into text

The same pattern renders an expression as readable text. Each operator wraps its two sides in brackets:

```swift run
indirect enum Expr {
    case number(Int)
    case add(Expr, Expr)
    case multiply(Expr, Expr)
    case negate(Expr)
}

func render(_ expression: Expr) -> String {
    switch expression {
    case .number(let value):
        return "\(value)"
    case let .add(left, right):
        return "(\(render(left)) + \(render(right)))"
    case let .multiply(left, right):
        return "(\(render(left)) * \(render(right)))"
    case .negate(let inner):
        return "-\(render(inner))"
    }
}

let tree = Expr.multiply(.negate(.add(.number(1), .number(2))), .number(5))
print(render(tree))
```

```output
(-(1 + 2) * 5)
```

`negate` has just one sub-expression, which shows the cases don't all have to look alike. Each case recurses into whatever children it has.

## Measuring a tree

Two questions come up with every tree you'll ever meet, and both are answered with the same three-part recipe: **handle the base case, recurse into each child, combine the answers**.

```swift run
indirect enum Expr {
    case number(Int)
    case add(Expr, Expr)
    case multiply(Expr, Expr)
}

func countNumbers(in expression: Expr) -> Int {
    switch expression {
    case .number:
        return 1
    case let .add(left, right), let .multiply(left, right):
        return countNumbers(in: left) + countNumbers(in: right)
    }
}

func height(of expression: Expr) -> Int {
    switch expression {
    case .number:
        return 1
    case let .add(left, right), let .multiply(left, right):
        return 1 + max(height(of: left), height(of: right))
    }
}

let tree = Expr.add(.number(2), .multiply(.number(3), .number(4)))
print(countNumbers(in: tree))
print(height(of: tree))
```

```output
3
3
```

What to notice:

- `case .number:` matches the case without binding its value, because we don't need it.
- `case let .add(left, right), let .multiply(left, right):` handles two cases in one go. That's allowed because both bind the same names with the same types.
- **Height** counts the levels on the longest path from the top to the bottom: `+`, then `*`, then a number, so 3. You'll compute exactly this for binary trees in M34, with the same `1 + max(left, right)` shape.

## A linked list as an enum

A list is recursive too: it's either empty, or a first value followed by the rest of the list.

```swift run
indirect enum IntList {
    case empty
    case node(Int, IntList)
}

func sum(_ list: IntList) -> Int {
    switch list {
    case .empty:
        return 0
    case let .node(value, rest):
        return value + sum(rest)
    }
}

let numbers = IntList.node(1, .node(2, .node(3, .empty)))
print(sum(numbers))
```

```output
6
```

This is elegant, but because an enum is a value, you can't reach into the middle of `numbers` and change one node in place. Building a modified list means building new nodes. For the in-place insertions and deletions linked-list problems need, M25 uses `final class` nodes instead, as you saw in the value vs reference lesson.

<Callout kind="gotcha" title="Swift gotcha: every recursion needs a base case">
Each recursive function here has a case that returns without calling itself: `.number` or `.empty`. Forget it, or build a tree with no leaves, and the function calls itself forever until the program crashes with a stack overflow. Very deep trees (hundreds of thousands of levels) can overflow too, which is why some tree algorithms are later rewritten with loops.
</Callout>

```cards
  back: "Without it, an enum stores associated values inside itself, so an enum containing itself would need infinite space. `indirect` stores them elsewhere behind a reference."
- id: recursive-recipe
  front: "What's the three-part recipe for a recursive function over a tree?"
  back: "Handle the base case (a leaf), recurse into each child, then combine the children's answers."
- id: tree-height
  front: "How do you compute the height of a tree recursively?"
  back: "A leaf has height 1. Any other node has height `1 + max(height of left, height of right)`."
- id: indirect-still-value
  front: "Is an indirect enum a value type or a reference type?"
  back: "Still a value type. `indirect` changes only how its associated values are stored, not how copies behave."
```
