## Why it matters

A data structure has rules that must always hold: a stack's count matches its elements, a sorted array stays sorted. If any code anywhere can reach in and change the storage, one careless line breaks those rules. **Access control** lets a type hide its insides and expose only safe operations. It's also why every exercise in the companion package is marked `public`.

## Modules and files

Access control is about *who can see* a declaration, measured in two units:

- A **source file**: one `.swift` file.
- A **module**: a bundle of files built together. An app is a module. In the companion package, `Exercises`, `Solutions` and the test target `DSATests` are three separate modules.

Code in one module can only use another module's declarations if that module allows it.

## The five levels

From most open to most closed:

| Level | Visible to |
| --- | --- |
| `open` | any module, which may also subclass and override it (classes only) |
| `public` | any module that imports this one |
| `internal` | anywhere in the same module. **This is the default.** |
| `fileprivate` | only the same source file |
| `private` | only the enclosing declaration (and its extensions in the same file) |

If you write no keyword, a declaration is `internal`. That's why none of the code in these lessons needed any: a single-file program is one module, so everything sees everything.

## private: hiding the insides

Here's a stack-like type that hides its storage. Code outside can push and peek, but can't touch `items` directly:

```swift run
struct NumberStack {
    private var items: [Int] = []

    mutating func push(_ value: Int) {
        items.append(value)
    }

    func peek() -> Int? {
        items.last
    }
}

var stack = NumberStack()
stack.push(4)
stack.push(9)
print(stack.peek() ?? -1)
```

```output
9
```

Try to reach in from outside the type, even in the same file:

```swift
stack.items.removeAll()
```

```text title="What you'll see"
error: 'items' is inaccessible due to 'private' protection level
```

Now the only way to change a `NumberStack` is through its methods, and the methods are where you guarantee the rules. If you later swap the array for a different storage, no outside code breaks, because none of it could depend on `items`. This idea, keeping the inside hidden behind a small set of operations, is called **encapsulation**, and it's what makes a data structure a data structure rather than a loose array.

### private(set): read from anywhere, write from inside

Often you want outsiders to *read* a property but not *change* it. `private(set)` keeps the getter at its normal level and makes only the setter private:

```swift run
struct StepCounter {
    private(set) var steps = 0

    mutating func walk(_ count: Int) {
        guard count > 0 else { return }
        steps += count
    }
}

var counter = StepCounter()
counter.walk(500)
counter.walk(-20)
counter.walk(250)
print(counter.steps)
```

```output
750
```

`counter.steps` can be read anywhere, but `counter.steps = -5` won't compile outside the type. The only way in is `walk`, which ignores negative counts, so `steps` can never go down.

<Callout kind="gotcha" title="Swift gotcha: private properties shrink the memberwise initialiser">
If any stored property is `private`, the generated memberwise initialiser becomes `private` too, so code outside the type can't call it. When every property has a default value you still get the plain `init()`, which is how `NumberStack()` works. Otherwise, write your own `init`. (`private(set)` doesn't cause this: only fully `private` properties do.)
</Callout>

### fileprivate

`fileprivate` is between the two: visible to everything in the same file, hidden from other files. It's occasionally useful when two small types in one file work closely together. You'll rarely need it.

## Why the companion package uses public

Here's the key fact: **the tests are in a different module from your code.** The test suite for a problem lives in `DSATests` and imports `Exercises`. If your solution were `internal`, the default, the tests simply couldn't see it.

So every problem marks its API `public`:

```swift
public enum PlanePoint {
    public struct Point {
        public var x: Int
        public var y: Int

        public init(x: Int, y: Int) {
            self.x = x
            self.y = y
        }

        public mutating func move(dx: Int, dy: Int) {
            // ...
        }
    }
}
```

Every piece the tests touch is `public`: the namespace enum, the struct inside it, its properties, its methods and its initialiser. Helper functions you add for yourself can stay `internal` or `private`, because the tests never call them.

<Callout kind="gotcha" title="Swift gotcha: the memberwise initialiser is never public">
Swift's generated memberwise initialiser is at most `internal`, even for a `public` struct. Other modules can't call it, so a `public` struct that other modules create needs a hand-written `public init`. That's why every struct in this course's problems spells out its `init`.
</Callout>

You might also see `@testable import Exercises` in other projects. It lets tests see `internal` declarations too. This course uses `public` instead, so the API each problem promises is explicit.

## open vs public

For classes there's one more distinction, and it only matters across modules:

- A `public` class can be **used** by other modules, but not subclassed there, and its `public` methods can't be overridden there.
- An `open` class can be used **and** subclassed by other modules, and its `open` methods can be overridden.

Apple's UIKit marks `UIViewController` `open` precisely so that your app, a different module, can subclass it. For DSA code, you'll almost never need `open`.

## A sensible default

1. Write everything `internal` (no keyword) while you work.
2. Make storage and helpers `private` as soon as a type has rules worth protecting.
3. Mark something `public` only when another module must use it, as the companion package's tests do.
