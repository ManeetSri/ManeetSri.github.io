## Why it matters

A drawing of circles and lines is easy for you to read and useless to a program. Before any algorithm can run, the graph has to live in memory, and there are three standard ways to store it: an **edge list**, an **adjacency matrix** and an **adjacency list**. They hold the same information, but each makes different questions cheap. Pick badly and an O(V + E) algorithm quietly becomes O(V²), or a 100,000-vertex graph needs 10 GB of memory. Knowing all three, and when to switch between them, is the first practical skill of graph work.

## One graph, three ways

Every example in this lesson uses the same undirected graph. Its vertices are numbered 0 to 4, which is how most problems hand them to you:

```text
    0 ----- 1 ----- 3
     \     /        |
      \   /         |
        2           4
```

It has 5 vertices and 5 edges: 0–1, 0–2, 1–2, 1–3 and 3–4.

## The edge list

The simplest form is a list of the edges themselves:

```swift
let edges = [[0, 1], [0, 2], [1, 2], [1, 3], [3, 4]]
```

That's exactly how problem statements give you a graph ("`n` vertices and an array of edges"), and it's how you'd read one from a file. It's compact, O(E) memory, and adding an edge is an append.

But it answers almost nothing quickly. "What are the neighbours of 1?" means scanning every edge: O(E). "Is there an edge between 2 and 4?" is another full scan. An edge list is the right shape for algorithms that look at every edge in some order regardless of where it is, such as sorting edges by weight for [Kruskal's algorithm](/dsa/learn/mst-kruskal), or Bellman–Ford's rounds over all edges. For anything that explores from a vertex, convert it first.

## The adjacency matrix

An **adjacency matrix** is a V × V grid, a 2D array as in [2D arrays](/dsa/learn/swift-2d-arrays), where `matrix[u][v]` says whether there's an edge from u to v. Vertex numbers are the row and column indices:

```text
      0  1  2  3  4
  0   .  1  1  .  .
  1   1  .  1  1  .
  2   1  1  .  .  .
  3   .  1  .  .  1
  4   .  .  .  1  .
```

Its strengths and weaknesses are both extreme:

- **"Is there an edge from u to v?" is O(1)**: one lookup.
- **Memory is O(V²)**, however few edges there are. 100,000 vertices need 10 billion entries.
- **Listing u's neighbours is O(V)**: you scan the whole row, even if u has one neighbour.

For an undirected graph the matrix is **symmetric**: `matrix[u][v] == matrix[v][u]`, mirrored across the diagonal. The diagonal itself holds self-loops. For a weighted graph, store weights instead of `true`, with a special value (say `nil` in an `[[Int?]]`) for "no edge". Don't use 0 for "no edge" if an edge can weigh 0.

## The adjacency list

An **adjacency list** gives every vertex a list of its neighbours. With vertices numbered 0 to n − 1, that's an array of arrays, `[[Int]]`, indexed by vertex:

```text
  0: [1, 2]
  1: [0, 2, 3]
  2: [0, 1]
  3: [1, 4]
  4: [3]
```

Memory is O(V + E): one list per vertex, plus one entry per edge end (two per undirected edge). Listing u's neighbours costs exactly its degree, which is what nearly every graph algorithm needs. Checking for one particular edge means scanning u's list, O(degree of u). This is the default representation, and the one the rest of the course uses unless a lesson says otherwise. You saw its shape in M34's **N-ary trees**, where each node had an array of children.

Here's an edge list turned into both of the others:

```swift run
let n = 5
let edges = [[0, 1], [0, 2], [1, 2], [1, 3], [3, 4]]

// Adjacency matrix: n × n, every entry false to start
var matrix = Array(repeating: Array(repeating: false, count: n), count: n)
// Adjacency list: one empty list per vertex
var adjacency = Array(repeating: [Int](), count: n)

for edge in edges {
    let (u, v) = (edge[0], edge[1])
    matrix[u][v] = true
    matrix[v][u] = true                  // undirected: mirror it
    adjacency[u].append(v)
    adjacency[v].append(u)               // undirected: both ends
}

for u in 0..<n {
    let row = matrix[u].map { $0 ? "1" : "." }.joined(separator: " ")
    print(u, "|", row, "|", adjacency[u])
}
print("edge 1–3?", matrix[1][3], " edge 2–4?", matrix[2][4])
print("neighbours of 1:", adjacency[1])
print("list entries:", adjacency.map(\.count).reduce(0, +), "for", edges.count, "edges")
```

```output
0 | . 1 1 . . | [1, 2]
1 | 1 . 1 1 . | [0, 2, 3]
2 | 1 1 . . . | [0, 1]
3 | . 1 . . 1 | [1, 4]
4 | . . . 1 . | [3]
edge 1–3? true  edge 2–4? false
neighbours of 1: [0, 2, 3]
list entries: 10 for 5 edges
```

What to notice:

- Each undirected edge is written **twice**: `matrix[u][v]` and `matrix[v][u]`, and an entry in both lists. Forgetting the second half is the most common graph-building bug.
- The adjacency list holds 10 entries for 5 edges, 2E, the handshake lemma again.
- `Array(repeating: [Int](), count: n)` is safe in Swift: arrays are values, so the five lists are independent. (In some languages this line creates five references to one list.)

## Weights and names

Two variations cover almost everything else.

For a **weighted** graph, each list entry carries the weight too. A tuple with labels reads well. For **named** vertices, such as cities or package names, use a dictionary from vertex to list, `[String: [String]]`, instead of an array:

```swift run
// Weighted and directed: flight prices, out of each airport
var flights = Array(repeating: [(to: Int, price: Int)](), count: 4)
flights[0].append((to: 1, price: 120))
flights[0].append((to: 2, price: 80))
flights[2].append((to: 1, price: 30))
flights[1].append((to: 3, price: 200))
for (to, price) in flights[0] {
    print("0 → \(to) costs \(price)")
}

// Named vertices: which Swift package targets each target depends on
var dependsOn: [String: [String]] = [:]
dependsOn["App", default: []].append("Networking")
dependsOn["App", default: []].append("Models")
dependsOn["Networking", default: []].append("Models")
for target in dependsOn.keys.sorted() {
    print(target, "depends on", dependsOn[target]!)
}
print("Models depends on", dependsOn["Models", default: []])
```

```output
0 → 1 costs 120
0 → 2 costs 80
App depends on ["Networking", "Models"]
Networking depends on ["Models"]
Models depends on []
```

What to notice:

- `for (to, price) in flights[0]` takes each labelled tuple apart, so the loop reads like the problem.
- The dictionary's keys are printed **sorted**. Printing `dependsOn` itself would show the keys in an order that changes from run to run.
- `Models` never got a key, because it depends on nothing. `dependsOn["Models", default: []]` returns an empty list instead of crashing, but a loop over `dependsOn.keys` would skip `Models` entirely. A dictionary only knows the vertices that were put in it, so when you need **every** vertex, including ones with no edges, keep a separate list of them. [Build `Graph<Vertex: Hashable>`](/dsa/learn/graph-build) does exactly that.

## Comparing the costs

For a graph with V vertices and E edges, where "deg u" is the degree of u:

| Operation | Edge list | Adjacency matrix | Adjacency list |
| --- | --- | --- | --- |
| Memory | O(E) | O(V²) | O(V + E) |
| Add an edge | O(1) | O(1) | O(1) |
| Is there an edge u → v? | O(E) | **O(1)** | O(deg u) |
| List the neighbours of u | O(E) | O(V) | **O(deg u)** |
| Visit every edge | O(E) | O(V²) | O(V + E) |
| Remove an edge | O(E) | O(1) | O(deg u) |
| Add a vertex | O(1) | O(V): a new row and column | O(1) |

Visiting every vertex's neighbours, which is what breadth-first and depth-first search do, costs O(V + E) with lists and O(V²) with a matrix. For a sparse graph that's the difference between instant and impossible.

## Which one to choose

- **Adjacency list**: the default. Traversals, shortest paths, topological sort, almost everything.
- **Adjacency matrix**: when the graph is dense, when V is small (a few thousand at most), or when the algorithm keeps asking "is u joined to v?". Floyd–Warshall, in M44, works on a matrix.
- **Edge list**: how input arrives, and what algorithms that process edges in a sorted order want.

If you need fast edge checks **and** fast neighbour lists on a big sparse graph, combine them: adjacency lists plus a `Set` of edges, or a set of neighbours per vertex. That costs more memory, but each question becomes cheap.

<Callout kind="gotcha" title="Common mistakes">
- **One direction only.** For an undirected graph, every edge goes into both endpoints' lists, or both cells of the matrix.
- **A matrix for a big sparse graph.** `Array(repeating: Array(repeating: false, count: n), count: n)` with n = 100,000 asks for 10 billion `Bool`s and runs out of memory, even if the graph has 100,000 edges.
- **Printing a dictionary of lists.** Its order changes from run to run. Print its sorted keys, or use `[[Int]]` when vertices are numbered.
- **Vertices with no edges vanish** from a dictionary-based list. Keep a separate array of vertices if you need all of them.
</Callout>
