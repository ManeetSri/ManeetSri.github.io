## Why it matters

Almost every graph problem starts the same way: "There are `n` vertices and a list of edges." Turning that into an adjacency list is the first ten lines of your solution, and those ten lines hide most of the easy-to-miss bugs: vertices numbered from 1 instead of 0, an undirected edge stored in one direction, the same edge listed twice. Getting them right on autopilot, and knowing when a matrix would be the better choice, frees your attention for the algorithm itself.

## How dense is dense?

A simple undirected graph with V vertices has at most V(V − 1)/2 edges; a directed one at most V(V − 1). How close E gets to that decides the representation, because a matrix always costs V² entries while a list costs V + 2E:

| V | E | Matrix entries | List entries (V lists, 2E entries) |
| --- | --- | --- | --- |
| 1,000 | 3,000 | 1,000,000 | 7,000 |
| 1,000 | 400,000 | 1,000,000 | 801,000 |
| 100,000 | 300,000 | 10,000,000,000 | 700,000 |

The first row is **sparse**: the matrix is 99% empty and a traversal would waste nearly all its time scanning blanks. The second row is **dense**, with 80% of all possible edges, and the matrix is no bigger than the lists. The third row is the usual interview or contest size, and a matrix is out of the question: 10 billion entries is about 10 GB even as `Bool`s.

The rule of thumb: **use adjacency lists unless V is at most a few thousand and E is a sizeable fraction of V²**, or the algorithm needs constant-time "is u joined to v?" checks. Road maps, social networks, the web and dependency graphs are all sparse.

## From n and an edge list to adjacency lists

Problems give you the vertex count separately from the edges, and that matters: a vertex with no edges never appears in the edge list, but it's still a vertex. Allocate the lists from `n`, never from the largest label you happen to see.

Labels are the other trap. Most problems number vertices from 0, but many, especially ones based on a real-world description or a contest, number from 1. Two clean ways to handle 1-based labels:

```swift run
// "4 stations, numbered 1 to 4" and four tracks, as a problem might give them
let n = 4
let edges = [[1, 2], [2, 3], [3, 1], [3, 4]]

// Option 1: shift every label down by one as you read it, and back up when you report
var shifted = Array(repeating: [Int](), count: n)
for edge in edges {
    let (u, v) = (edge[0] - 1, edge[1] - 1)
    shifted[u].append(v)
    shifted[v].append(u)
}
print("shifted:", shifted)

// Option 2: allocate n + 1 lists and leave slot 0 unused
var padded = Array(repeating: [Int](), count: n + 1)
for edge in edges {
    padded[edge[0]].append(edge[1])
    padded[edge[1]].append(edge[0])
}
print("padded:", padded)
print("station 3's neighbours:", padded[3], "or", shifted[2].map { $0 + 1 })
```

```output
shifted: [[1, 2], [0, 2], [1, 0, 3], [2]]
padded: [[], [2, 3], [1, 3], [2, 1, 4], [3]]
station 3's neighbours: [2, 1, 4] or [2, 1, 4]
```

Both are fine; pick one and stick to it within a solution. Shifting keeps every array exactly `n` long, which matches loops like `for v in 0..<n`. Padding keeps the problem's numbers everywhere, so there's nothing to convert back, but every loop must run `1...n`. Mixing the two styles in one solution is where off-by-one errors come from.

Notice too that each undirected edge went into both lists. The lists hold 8 entries for 4 edges: 2E, as always.

## Repeated edges and self-loops

Unless the problem promises a simple graph, expect repeats: the same pair listed twice, perhaps in the other order, or an edge from a vertex to itself. What to do depends on the question:

| The question | What to do with repeats |
| --- | --- |
| Can you get from u to v? Connected pieces? | nothing: a second copy changes no answer, only adds a little work |
| How many distinct neighbours? Degrees? | remove repeats: sort each list and skip equal neighbours, or use a set |
| The cheapest route, with weights | keep only the cheapest copy of each pair |
| In-degrees for a topological sort | either keep every copy or none, but count and process them the same way |

Here's the weighted case, keeping the cheapest price per pair and dropping self-loops, which never help a route:

```swift run
// Undirected roads [from, to, price]; some pairs are listed more than once
let n = 3
let roads = [[0, 1, 7], [1, 2, 4], [1, 0, 5], [0, 1, 9], [2, 2, 1]]

var cheapest = Array(repeating: [Int: Int](), count: n)     // cheapest[u][v] is the best price
for road in roads {
    let (u, v, price) = (road[0], road[1], road[2])
    if u == v { continue }                                   // a self-loop is never on a best route
    cheapest[u][v] = min(cheapest[u][v] ?? Int.max, price)
    cheapest[v][u] = min(cheapest[v][u] ?? Int.max, price)
}
for u in 0..<n {
    let listed = cheapest[u].keys.sorted().map { "\($0) for \(cheapest[u][$0]!)" }
    print(u, listed)
}
```

```output
0 ["1 for 5"]
1 ["0 for 5", "2 for 4"]
2 ["1 for 4"]
```

Three listings of the road between 0 and 1, at 7, 5 and 9, became one road at 5, in both directions. The dictionary per vertex is printed through sorted keys, so the output never changes.

## Reading a graph from standard input

Competitive programming sites send the graph as text: a first line with n and m, then m lines of two labels each. With `readLine()` from [Reading input with readLine](/dsa/learn/swift-reading-input), the conversion looks like this (it reads input, so it isn't a runnable example here):

```swift
let header = readLine()!.split(separator: " ").map { Int($0)! }
let (n, m) = (header[0], header[1])
var adjacency = Array(repeating: [Int](), count: n + 1)    // labels are 1...n: slot 0 unused
for _ in 0..<m {
    let pair = readLine()!.split(separator: " ").map { Int($0)! }
    adjacency[pair[0]].append(pair[1])
    adjacency[pair[1]].append(pair[0])
}
```

For 200,000 lines, the faster byte-level reader from M12's **Fast input for competitive programming** pays off.

<Callout kind="gotcha" title="Off by one, and other input traps">
- **1-based labels in an array of n lists.** The edge `[3, 4]` with `n = 4` indexes `adjacency[4]` in an array whose last index is 3, and Swift stops with `Fatal error: Index out of range`. Shift the labels or allocate `n + 1` lists.
- **Sizing from the edges.** `edges.map { max($0[0], $0[1]) }.max()` misses vertices with no edges, and crashes on an empty edge list. The problem gives you `n`: use it.
- **Reporting in the wrong numbering.** If you shifted labels down to read them, shift your answer back up before returning it.
- **Assuming the graph is simple.** Unless the statement promises no repeats and no self-loops, decide what they mean for your question before you write the loop.
</Callout>
