## Why it matters

Many graphs are never written down. A maze in a game is a graph whose vertices are open squares, but the level stores a grid, not an adjacency list. A puzzle such as a combination lock or a Rubik's cube is a graph whose vertices are positions and whose edges are moves, and the cube has more positions than any computer could store. In these **implicit graphs**, you never build the edges: a function works out a vertex's neighbours the moment an algorithm asks. Spotting that a grid or a puzzle *is* a graph, and writing that function correctly, is the step that turns half of all BFS and DFS interview problems into routine work.

## A grid is a graph

Take a maze where `.` is open and `#` is a wall, and you can step up, down, left or right. Every open cell is a vertex. Two open cells side by side, or one above the other, are joined by an edge. Nobody stores those edges, because the grid already encodes them: the neighbours of a cell are whichever of its four adjacent cells exist and are open.

The direction arrays from [Direction arrays for grid moves](/dsa/learn/matrix-directions) generate the candidates, and two checks keep the real ones:

```swift run
let maze = [
    "..#.",
    ".##.",
    "....",
]
let cells = maze.map { Array($0) }
let directions = [(-1, 0), (1, 0), (0, -1), (0, 1)]     // up, down, left, right

// The edges of the implicit graph, worked out on demand
func neighbours(of row: Int, _ column: Int) -> [(Int, Int)] {
    var result: [(Int, Int)] = []
    for (dr, dc) in directions {
        let r = row + dr
        let c = column + dc
        guard r >= 0, r < cells.count, c >= 0, c < cells[r].count else { continue }  // off the grid
        guard cells[r][c] == "." else { continue }                                    // a wall
        result.append((r, c))
    }
    return result
}

print("(0, 0):", neighbours(of: 0, 0))
print("(2, 3):", neighbours(of: 2, 3))
print("(0, 1):", neighbours(of: 0, 1))

var openCells = 0
var degreeTotal = 0
for r in cells.indices {
    for c in cells[r].indices where cells[r][c] == "." {
        openCells += 1
        degreeTotal += neighbours(of: r, c).count
    }
}
print("vertices:", openCells, "edges:", degreeTotal / 2)
```

```output
(0, 0): [(1, 0), (0, 1)]
(2, 3): [(1, 3), (2, 2)]
(0, 1): [(0, 0)]
vertices: 9 edges: 8
```

What to notice:

- **The bounds check comes first.** `cells[r][c]` with `r = -1` would crash, so the `guard` that keeps you on the grid runs before the one that reads the cell.
- **(0, 1) has degree 1**: the wall below it and the edge of the maze leave only one way out. It's a dead end, a vertex of degree 1.
- **The handshake lemma still holds.** The degrees add up to 16, twice the 8 edges. These 9 cells and 8 edges form one long path: a tree, in fact.
- **Nothing was built.** The "graph" costs no memory beyond the grid, and each call does a constant amount of work: at most 4 candidates.

## Naming a cell

Algorithms need to remember vertices: which cells are visited, how far each one is from the start. That needs a cell to be a dictionary key or a set member, and here Swift has a catch: **tuples aren't `Hashable`**, so `Set<(Int, Int)>` doesn't compile. Two good fixes:

```swift run
// Fix 1: a tiny struct. Swift writes == and hash(into:) for you.
struct Cell: Hashable {
    let row: Int
    let column: Int
}
var visited: Set<Cell> = [Cell(row: 0, column: 0)]
visited.insert(Cell(row: 2, column: 3))
print(visited.contains(Cell(row: 2, column: 3)), visited.count)

// Fix 2: one Int per cell, numbering the grid row by row
let columns = 4
func id(_ row: Int, _ column: Int) -> Int { row * columns + column }
func position(of id: Int) -> (row: Int, column: Int) { (id / columns, id % columns) }
print(id(2, 3), position(of: 11))

// With ids, a flat array of Bool replaces the set
var seen = Array(repeating: false, count: 3 * columns)
seen[id(2, 3)] = true
print(seen.filter { $0 }.count)
```

```output
true 2
11 (row: 2, column: 3)
1
```

The struct is clearer and works with any grid shape. The integer id is faster and lets a plain array stand in for a set or dictionary, which matters for grids with millions of cells. Both are common; the conversion `row * columns + column` and back with `/` and `%` is the same row-major numbering as in [Row-major, column-major, diagonal and snake traversals](/dsa/learn/matrix-traversals).

## State spaces: puzzles as graphs

The vertices don't have to be places. In a **state space**, a vertex is a complete description of a situation, and an edge is one legal move from it.

Take a lock with four wheels, each showing a digit from 0 to 9. One move turns one wheel one step up or down, and 9 goes round to 0. A state is the four digits, such as `"0000"`, and every state has exactly 8 neighbours: 4 wheels × 2 directions.

```swift run
// The neighbours of a combination: turn one wheel one step, up or down
func neighbours(of combination: String) -> [String] {
    let digits = combination.map { $0.wholeNumberValue! }
    var result: [String] = []
    for wheel in digits.indices {
        for step in [1, 9] {                         // +1, or −1 written as +9 so it stays positive
            var next = digits
            next[wheel] = (digits[wheel] + step) % 10
            result.append(next.map(String.init).joined())
        }
    }
    return result
}

print(neighbours(of: "0000"))
print(neighbours(of: "2909"))
```

```output
["1000", "9000", "0100", "0900", "0010", "0090", "0001", "0009"]
["3909", "1909", "2009", "2809", "2919", "2999", "2900", "2908"]
```

The whole graph has 10,000 vertices and 40,000 undirected edges, and the program stores none of them. "What's the fewest number of moves from `0000` to `2909`?" is now a shortest-path question on this graph, which breadth-first search answers in M42. Notice `+ 9` for "one step down": that's the wrap-around trap in the gotcha below.

Word puzzles work the same way. In a **word ladder**, you change one letter at a time and every step must be a real word: cold → cord → word → worm → warm. The vertices are the words in a dictionary; two words are joined if they differ in exactly one position. To find a word's neighbours, try every letter in every position and keep the candidates that are real words:

```swift run
let dictionary: Set<String> = ["cold", "cord", "card", "ward", "warm", "word", "worm", "bold", "colt", "core"]

func neighbours(of word: String) -> [String] {
    var letters = Array(word)
    var result: [String] = []
    for index in letters.indices {
        let original = letters[index]
        for letter in "abcdefghijklmnopqrstuvwxyz" where letter != original {
            letters[index] = letter
            let candidate = String(letters)
            if dictionary.contains(candidate) {
                result.append(candidate)
            }
        }
        letters[index] = original                    // put the letter back before the next position
    }
    return result
}

for word in ["cold", "word", "warm"] {
    print(word, "→", neighbours(of: word))
}
```

```output
cold → ["bold", "cord", "colt"]
word → ["cord", "ward", "worm"]
warm → ["worm", "ward"]
```

For a word of length L, that's 25 × L candidates, each one a set lookup. The alternative, comparing the word with every word in the dictionary, costs n comparisons; for a dictionary of 50,000 words and words of 5 letters, generating 125 candidates is far cheaper than 50,000 comparisons. Choosing **how** to generate neighbours is part of designing the solution.

## How big these graphs are

| Graph | Vertices | Neighbours per vertex | What's stored |
| --- | --- | --- | --- |
| A 1,000 × 1,000 maze | up to 1,000,000 | at most 4 | the grid |
| A four-wheel lock | 10,000 | 8 | nothing |
| A word ladder over 50,000 five-letter words | 50,000 | up to 125 candidates to check | the word set |
| A Rubik's cube | about 4.3 × 10¹⁹ | 18 | nothing: it could never fit |

A search on an implicit graph usually stops early, when it reaches its goal, so it only ever touches the part of the graph it needs. That's the other reason not to build the whole thing first: for the cube, you couldn't; for a big grid, building an adjacency list would cost more time and memory than the search itself.

## Searching without building the graph

Every graph algorithm in the coming modules asks one question over and over: "what are the neighbours of this vertex?" Whether the answer comes from an adjacency list or from a function like the ones above makes no difference to the algorithm. Here's breadth-first search, which you previewed in [A preview of BFS](/dsa/learn/queue-bfs-preview), spreading across a maze whose edges are generated cell by cell:

```visual grid
rows: ["S..#....", ".#.#.##.", ".#...#..", "...#...G"]
```

M42 starts with exactly this, in [BFS and unweighted shortest paths](/dsa/learn/gt-bfs).

<Callout kind="gotcha" title="Swift gotchas in implicit graphs">
- **`%` can be negative.** In Swift, `(0 - 1) % 10` is `-1`, not `9`: the remainder takes the sign of the left side. Wrap downwards with `(digit + 9) % 10`, or `(digit - 1 + 10) % 10`.
- **Tuples aren't `Hashable`.** `Set<(Int, Int)>` and `[(Int, Int): Int]` don't compile. Use a small `Hashable` struct or an integer id.
- **Bounds before contents.** Check that a candidate cell is on the grid before you read it. `guard r >= 0, r < rows, ...` in that order, then the wall check.
- **Forgetting to undo a change.** In the word ladder, `letters[index] = original` restores the word before trying the next position. Without it, later candidates change two letters at once.
</Callout>
