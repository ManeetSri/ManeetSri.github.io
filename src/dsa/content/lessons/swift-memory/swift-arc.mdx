## Why it matters

Class instances live on the heap, so something has to free them when they're no longer needed. In Swift that something is **Automatic Reference Counting**, or **ARC**. It's why a screen's view controller disappears from memory when you close the screen, and why removing a node from a linked list frees it without you writing any clean-up code. Knowing how ARC counts is also the key to the next lesson's bug, the retain cycle.

## Every object keeps a count

When you assign a class instance to a variable, constant or property, that creates a **strong reference** to it. Strong is the default kind of reference, and it means "keep this object alive while I hold it".

ARC keeps a **reference count** for every class instance: how many strong references point at it right now.

- A new strong reference makes the count go **up** by one.
- A strong reference going away makes it go **down** by one.
- When the count reaches **zero**, nothing can reach the object any more, so Swift frees it immediately.

Swift inserts the code that changes the counts for you when it compiles your program. You never write it, which is what "automatic" means.

<Callout kind="analogy" title="Guests at a party">
Think of an object as a party and each strong reference as a guest. Guests arrive and leave at any time. The host doesn't clean up while anyone is still there, but the moment the last guest leaves, the lights go off and the room is cleared.
</Callout>

## Watching it happen with deinit

A class can have a **deinitialiser**, written `deinit`. Swift runs it just before freeing the object. It takes no parameters, and you never call it yourself. Printing from `deinit` is the easiest way to see exactly when ARC frees something:

```swift run
final class Player {
    let name: String

    init(name: String) {
        self.name = name
        print("\(name) created")
    }

    deinit {
        print("\(name) freed")
    }
}

print("before the scope")
do {
    let player = Player(name: "Ada")
    print("playing as \(player.name)")
}
print("after the scope")
```

```output
before the scope
Ada created
playing as Ada
Ada freed
after the scope
```

A `do { }` block creates a **scope**: a region of code whose local constants and variables disappear at its closing brace. When `player` disappears, the count drops from one to zero, `deinit` runs, and only then does the program continue past the brace.

## What adds and removes a reference

| The count goes up when you… | The count goes down when… |
| --- | --- |
| assign the object to a variable or constant | that variable goes out of scope |
| store it in a property | the variable is set to `nil` or to another object |
| put it in an array or dictionary | it's removed from the collection, or the collection is freed |
| capture it in a closure | the closure is freed |

Here's a single object with two references. It survives until *both* are gone:

```swift run
final class Player {
    let name: String
    init(name: String) { self.name = name }
    deinit { print("\(name) freed") }
}

var first: Player? = Player(name: "Bo")    // count: 1
var second = first                         // count: 2
first = nil                                // count: 1
print("first is nil")
second = nil                               // count: 0, so Bo is freed
print("second is nil")
```

```output
first is nil
Bo freed
second is nil
```

Setting `first` to `nil` removed one reference, but `second` still held the object, so nothing was freed. The variables are optionals (`Player?`) only so that we can set them to `nil`.

## Collections and properties hold references too

An array of class instances holds a strong reference to each element. So does a property in another object:

```swift run
final class Ticket {
    let id: Int
    init(id: Int) { self.id = id }
    deinit { print("ticket \(id) freed") }
}

final class Queue {
    var waiting: [Ticket] = []
}

do {
    let queue = Queue()
    queue.waiting.append(Ticket(id: 7))
    print("ticket stored")
    queue.waiting.removeAll()
    print("queue emptied")
}
```

```output
ticket stored
ticket 7 freed
queue emptied
```

The new `Ticket` had no variable of its own. Its only strong reference was the array's, so removing it from the array freed it straight away.

## ARC in a data structure: unlinking frees nodes

This is where ARC helps with DSA. In a linked list (Part III), each node holds a strong reference to the next one. Moving `head` forward drops the only reference to the old first node, so ARC frees it. Freeing a node also releases its `next` reference, which can free the next node, and so on down the chain:

```swift run
final class Node {
    let value: Int
    var next: Node?

    init(_ value: Int, next: Node? = nil) {
        self.value = value
        self.next = next
    }

    deinit {
        print("node \(value) freed")
    }
}

var head: Node? = Node(1, next: Node(2, next: Node(3)))
print("remove the first node")
head = head?.next
print("head is now \(head!.value)")
print("clear the list")
head = nil
print("done")
```

```output
remove the first node
node 1 freed
head is now 2
clear the list
node 2 freed
node 3 freed
done
```

What to notice:

- `head = head?.next` made `head` point at node 2. Node 1's count fell to zero, so it was freed on that line.
- `head = nil` freed node 2. Its `next` property went with it, which dropped node 3's last reference, so node 3 was freed too.
- No "delete" or "free" call appears anywhere. Removing a node *is* unlinking it.

## ARC is not a garbage collector

Some languages, like Java, Kotlin and JavaScript, use a **garbage collector**: a background process that now and then searches memory for objects nobody uses and frees them in batches. ARC works differently:

- **Deterministic.** An object is freed at the moment its last strong reference disappears, not at some later moment chosen by a collector.
- **No pauses.** There's no collector stopping your app to scan memory.
- **A small cost per reference.** Every count change is a tiny bit of work. In tight loops over class instances, that work shows up. Optimised builds remove many count changes they can prove aren't needed, which you'll see in M12.
- **One weakness.** ARC only counts. It can't spot a group of objects that keep each other alive, which is the next lesson.

<Callout kind="gotcha" title="Swift gotcha: an object may be freed before the closing brace">
Swift guarantees an object lives until its **last use**, not until the end of its scope. The examples here run unoptimised, so objects die at the closing brace. In an optimised build, an object can be freed right after the line that last uses it. Never write code whose correctness depends on `deinit` running at an exact line. When you need an object kept alive, `withExtendedLifetime(object) { … }` guarantees it.
</Callout>

<Callout kind="note">
Ordinary structs and enums have no reference count and no `deinit`, because each copy is independent. But a struct that *contains* a class reference, or an array, does change counts when it's copied: copying an array adds a reference to its shared buffer. That count is exactly how copy-on-write knows whether a buffer is shared.
</Callout>
