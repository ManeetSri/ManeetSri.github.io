## Why it matters

Every value your program creates has to live somewhere in memory. Swift mostly hides this from you, which is a gift, but it explains things you've already seen: why copying a struct gives an independent value, why two class variables can share one object, and why a linked list of class nodes is slower than an array holding the same numbers. When you build data structures in later parts of the course, "where does this live, and what does it cost?" becomes a question you ask every day.

## Two kinds of memory

A running program uses two main regions of memory for its data.

The **stack** is where function calls keep their local values. Each time you call a function, Swift sets aside a block of stack memory for it, called a **call frame** (or stack frame). The frame holds that call's parameters and local variables. When the function returns, its frame is thrown away in one step. The next call reuses the same space.

The **heap** is a big pool of memory for things whose size or lifetime isn't tied to one function call. Asking for heap memory is called **allocating**. Something has to find a free block of the right size, keep track of it, and later give it back, which is called **freeing** (or deallocating) it.

<Callout kind="analogy" title="A desk and a warehouse">
The stack is your desk. Whatever you're working on right now sits on top, and when you finish a task you sweep its papers away all at once. The heap is a warehouse. You can store anything there for as long as you like, but every item needs a shelf found, a label written, and someone to clear it out later.
</Callout>

| | Stack | Heap |
| --- | --- | --- |
| Holds | local values of active calls | objects that outlive a call |
| Allocating | moving one marker: very cheap | finding free space: slower |
| Freeing | automatic when the call returns | when nothing uses it any more |
| Size | small (a few megabytes) | large |

## Value types usually live inline

A struct, enum, `Int`, `Double` or `Bool` is a **value type**: you met these in M09. A value type is usually stored **inline**, meaning right where the variable is. A local `Point` sits inside the call frame. A `Point` stored as a property of another struct sits inside that struct's bytes. An array of `Point` values stores the points side by side in its buffer.

```swift run
struct Point {
    var x: Int
    var y: Int
}

final class Marker {
    var x = 0
    var y = 0
}

print(MemoryLayout<Point>.size)
print(MemoryLayout<Marker>.size)
```

```output
16
8
```

`MemoryLayout<T>.size` reports how many bytes a type takes where it's stored. You'll explore it properly later in this module, in "MemoryLayout: size, stride and alignment". For now, notice the two numbers:

- A `Point` is 16 bytes because it *is* its two 8-byte `Int` values, stored inline.
- A `Marker` variable is only 8 bytes, even though the class also holds two `Int` values. The variable doesn't contain the object at all.

## Class instances live on the heap

When you create a class instance, Swift allocates it on the heap. The variable you assign it to holds a **reference**: the address of the object in the heap, which is 8 bytes on a 64-bit Mac or iPhone.

That's why classes behave the way M09 described. Copying a class variable copies the *address*, not the object, so both variables reach the same object:

```swift run
final class Counter {
    var count = 0
}

let first = Counter()
let second = first      // copies the reference, not the object
second.count += 1
print(first.count)
print(first === second)
```

```output
1
true
```

There's one `Counter` in the heap and two references pointing at it. `===` checks whether two references point at the same object, as you saw in [Identity with ===](/dsa/learn/swift-identity).

## Collections are small values with a heap buffer

An `Array` is a struct, but its elements don't sit inside the struct. The array value holds a reference to a **buffer** on the heap, and the elements live in that buffer. So the array variable itself is tiny, however many elements it has:

```swift run
let few = [1, 2, 3]
let many = Array(repeating: 0, count: 1_000)

print(MemoryLayout.size(ofValue: few))
print(MemoryLayout.size(ofValue: many))
```

```output
8
8
```

Both are 8 bytes: one reference to a buffer. `Dictionary` and `Set` work the same way. A `String` is 16 bytes, and short strings can fit entirely inside those 16 bytes with no buffer at all.

This is how arrays can be value types and still be cheap to pass around. Copying an array copies 8 bytes and shares the buffer. Copy-on-write, which you met in [Copy-on-write explained](/dsa/learn/swift-copy-on-write-intro), makes a real copy of the buffer only when one of the arrays is changed. You'll write your own version at the end of this module.

## Why the heap costs more

Heap memory is flexible, but every allocation does real work:

1. **Finding space.** The allocator searches for a free block of the right size and records that it's in use.
2. **Freeing it later.** When the object is no longer needed, the block has to be handed back.
3. **Keeping count.** Swift tracks how many references point at each object, so it knows when to free it. That's the next lesson's topic.
4. **Scattered data.** Objects allocated at different times can end up far apart in memory. The processor reads memory fastest when the data it needs is close together.

None of this is slow for one object. It adds up when a data structure allocates millions of them. This is the main reason an array of `Int` usually beats a linked list of class nodes holding the same numbers: the array makes one buffer with every number side by side, while the list makes one heap object per number. You'll build both in Part III.

## The compiler is allowed to do better

"Value types inline, class instances on the heap" is the model to think with, but it describes what Swift *promises to behave like*, not exactly where every byte goes. The optimiser can change the details as long as your program behaves the same:

- A local value may live only in the processor's registers and never touch the stack.
- A class instance that never leaves a function can sometimes be placed on the stack instead of the heap.
- A local variable captured by an escaping closure (M06) may be moved to the heap, because it has to outlive the function call.

So rely on the *semantics*, copying for value types and sharing for classes, rather than on exact locations.

## Too many frames: stack overflow

The stack is small, a few megabytes (8 MB for the main thread on macOS). Each nested function call adds a frame, and the frame is only removed when the call returns. A recursive function that calls itself a million times deep needs a million frames at once, runs out of stack, and crashes. This is a **stack overflow**. You'll learn to reason about recursion depth in Part II.

<Callout kind="gotcha" title="Swift gotcha: 'struct means stack' is a myth">
A struct is stored wherever its *container* is. A struct inside a class instance lives in the heap with that object. A struct that holds an array keeps only the array's 8-byte reference inline; the elements are in a heap buffer. What a struct guarantees is value semantics, not a location.
</Callout>
