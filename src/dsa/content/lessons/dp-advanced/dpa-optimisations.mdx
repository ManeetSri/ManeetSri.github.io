## Why it matters

Many DPs have the right states but a slow transition: each state scans a long list of earlier states for the best one. That's O(n²) for a one-dimensional table, or O(n³) for an interval DP, and it's too slow once n reaches 10⁵ or a few thousand. Four classic techniques speed up the scan when the transition has a special shape: a **monotonic queue** when the candidates form a sliding window, the **convex hull trick** when each candidate acts like a straight line, **Knuth's optimisation** for certain interval DPs, and **divide-and-conquer optimisation** when the best choice only ever moves one way. Each one needs a condition to hold. Learning to spot the shape, and to check the condition, is most of the skill.

This lesson gives one concrete example of each, tested against the slow DP it speeds up.

## Monotonic queue: a window of candidates

### The shape

> `best[i] = cost[i] + min (or max) of best[j]` for j in a window `i − k ... i − 1`

As i moves right, the window of candidate j's slides right by one: one index joins, one leaves. Scanning the whole window is O(k) per state, O(n · k) in all.

This is exactly [Monotonic deque: sliding window maximum](/dsa/learn/queue-monotonic-deque), except the array whose window you're taking the maximum of is the DP table itself, being filled as you go. Step through the deque on a plain array to remind yourself how it works:

### An example: hopping along stones

A row of stones each has a score, some negative. You start on the first stone and must end on the last, and each hop moves forward at most k stones. You collect the score of every stone you land on. What's the largest total?

> `best[i] = score[i] + max(best[i − k], …, best[i − 1])`

Keep a deque of indexes whose `best` values **decrease** from front to back. When stone i is finished, any index at the back with a `best` no larger than `best[i]` can never be the maximum again: i is at least as good and will stay in the window longer. Pop those, then push i. The front is always the window's maximum; pop it when it falls out of reach.

```swift run
// Hop along stones from the first to the last, at most k stones per hop, collecting every score you land on
// best[i] = score[i] + the largest best[j] among the k stones before i
func bestScoreSlow(_ score: [Int], k: Int) -> Int {
    var best = [Int](repeating: 0, count: score.count)
    best[0] = score[0]
    for i in 1..<score.count {
        var top = Int.min
        for j in max(0, i - k)..<i {                  // scan the whole window: O(k) per stone
            top = max(top, best[j])
        }
        best[i] = score[i] + top
    }
    return best[score.count - 1]
}

func bestScore(_ score: [Int], k: Int) -> Int {
    var best = [Int](repeating: 0, count: score.count)
    best[0] = score[0]
    var window = [0]                                  // indexes, their best values decreasing front to back
    var head = 0                                      // window[head...] is the live part
    for i in 1..<score.count {
        while window[head] < i - k { head += 1 }      // the front fell out of reach
        best[i] = score[i] + best[window[head]]       // the front is the window's maximum
        while window.count > head && best[window[window.count - 1]] <= best[i] {
            window.removeLast()                       // never better than i again: i is at least as good and newer
        }
        window.append(i)
    }
    return best[score.count - 1]
}

let score = [3, -5, -2, 4, -10, -1, 6, -7, -3, 2]
print(bestScoreSlow(score, k: 3), bestScore(score, k: 3))
let long = (0..<200_000).map { ($0 * 7_919 + 17) % 201 - 100 }
print(bestScoreSlow(Array(long.prefix(3_000)), k: 500), bestScore(Array(long.prefix(3_000)), k: 500))
print(bestScore(long, k: 50_000))
```

```output

75300 75300
5024780
```

On the first row, the best route lands on 3, 4, 6 and 2, hopping exactly three stones each time to skip every negative score. On 200,000 stones with hops of up to 50,000, the slow version would scan ten billion candidates; the deque does about 400,000 pushes and pops.

**Condition:** the candidates for state i must be a **contiguous window** whose two ends only move right. Each index then joins once and leaves once, so the whole pass is **O(n)**. If the window can be any shape, or its ends jump backwards, use a heap or a segment tree instead.

## The convex hull trick: candidates that are lines

### The shape

> `best[i] = min over j of (m[j] · x[i] + c[j])`, plus terms that depend only on i

Read each candidate j as a **straight line** `y = m[j] · x + c[j]`. Then state i asks: at the point `x = x[i]`, which line is lowest? A minimum of lines is a convex, downward-bending chain called the **lower envelope** (or hull). Most lines never appear on it at all, and the ones that do take turns being lowest from left to right.

### An example: printing in batches

Print jobs must go through in order, in batches. A batch whose pages add up to s costs `s² + setup`: big batches jam the printer, and every batch pays a fixed set-up cost. With `S[i]` the total pages of the first i jobs, the obvious DP is O(n²):

> `best[i] = min over j < i of best[j] + (S[i] − S[j])² + setup`

Expand the square: `(S[i] − S[j])² = S[i]² − 2 · S[j] · S[i] + S[j]²`. Group the parts by what they depend on:

> `best[i] = min over j of ( (−2 · S[j]) · S[i] + (best[j] + S[j]²) ) + S[i]² + setup`

Inside the min, j contributes a line with **slope** `−2 · S[j]` and **intercept** `best[j] + S[j]²`, evaluated at `x = S[i]`. The `S[i]² + setup` part doesn't depend on j, so it's added after the min.

### Two monotone directions make it O(n)

Pages are positive, so `S[j]` grows with j: each new line is **steeper downwards** than all the earlier ones. And the query points `S[i]` also grow. Both together give the simplest version:

- **Adding a line.** The new line has the smallest slope so far, so it belongs at the right end of the envelope. Before adding it, look at the last two lines on the hull, a and b. If the new line overtakes a no later than b does, b is never the lowest anywhere: pop it. Repeat, then push.
- **Querying.** Queries only move right, so the lowest line only moves right along the hull. Keep a pointer, and advance it while the next line is at least as low at the query point.

Each line is pushed once and popped at most once, and the pointer only moves forward, so all n states take **O(n)**.

The "useless middle line" test comes from where lines meet. Lines a and b meet at `x = (c[b] − c[a]) / (m[a] − m[b])`, and a and the new line at `x = (c − c[a]) / (m[a] − m)`. b is useless when the second point is no later than the first. Both denominators are positive (slopes decrease), so multiplying out removes the division:

> `(c − c[a]) · (m[a] − m[b]) ≤ (c[b] − c[a]) · (m[a] − m)`

```swift run
// Split jobs (in order) into batches. A batch whose pages add up to s costs s² + setup.
// best[i] = cheapest way to print the first i jobs = min over j < i of best[j] + (S[i] - S[j])² + setup
func batchCostSlow(_ pages: [Int], setup: Int) -> Int {
    let n = pages.count
    var prefix = [0]
    for p in pages { prefix.append(prefix.last! + p) }
    var best = [Int](repeating: Int.max, count: n + 1)
    best[0] = 0
    for i in 1...n {
        for j in 0..<i {
            let s = prefix[i] - prefix[j]
            best[i] = min(best[i], best[j] + s * s + setup)
        }
    }
    return best[n]
}

// The same DP with the convex hull trick. Each j is a line: slope -2·S[j], intercept best[j] + S[j]²,
// and best[i] = (the lowest line at x = S[i]) + S[i]² + setup.
func batchCost(_ pages: [Int], setup: Int) -> Int {
    let n = pages.count
    var prefix = [0]
    for p in pages { prefix.append(prefix.last! + p) }
    var best = [Int](repeating: 0, count: n + 1)
    var slopes: [Int] = [], intercepts: [Int] = []    // the hull: slopes decreasing
    var head = 0                                      // the line that answered the last query

    func value(_ line: Int, _ x: Int) -> Int { slopes[line] * x + intercepts[line] }
    // Is the middle line b useless once c arrives? True when c overtakes a before b does.
    func useless(_ a: Int, _ b: Int, _ m: Int, _ c: Int) -> Bool {
        (c - intercepts[a]) * (slopes[a] - slopes[b]) <= (intercepts[b] - intercepts[a]) * (slopes[a] - m)
    }
    func add(_ m: Int, _ c: Int) {
        while slopes.count - head >= 2 && useless(slopes.count - 2, slopes.count - 1, m, c) {
            slopes.removeLast()
            intercepts.removeLast()
        }
        slopes.append(m)
        intercepts.append(c)
    }

    add(0, 0)                                         // j = 0: slope -2·0, intercept 0 + 0
    for i in 1...n {
        let x = prefix[i]                             // queries only grow, so the best line only moves right
        while head + 1 < slopes.count && value(head + 1, x) <= value(head, x) {
            head += 1
        }
        best[i] = value(head, x) + x * x + setup
        add(-2 * x, best[i] + x * x)
    }
    return best[n]
}

print(batchCostSlow([1, 3, 2, 4, 1], setup: 10), batchCost([1, 3, 2, 4, 1], setup: 10))
let jobs = (0..<2_000).map { ($0 * 37 + 5) % 10 + 1 }
print(batchCostSlow(jobs, setup: 300), batchCost(jobs, setup: 300))
let many = (0..<100_000).map { ($0 * 37 + 5) % 10 + 1 }
print(batchCost(many, setup: 1_000))
```

```output
75 75
382642 382642
34903342
```

For `[1, 3, 2, 4, 1]` with set-up 10, the best plan is three batches, `[1, 3]`, `[2]` and `[4, 1]`: 16 + 4 + 25 plus three set-ups, 75. The two versions agree on 2,000 jobs, and the hull handles 100,000 jobs, where the slow version would need five billion steps.

What to notice:

- Lines that fall **behind the pointer** are never removed from the arrays. They're dead, because queries only move right, and `slopes.count - head >= 2` makes sure the popping never reaches them.
- `add` runs **after** the query for i, because line i is only a candidate for later states.

**Conditions:**

| Slopes added in order? | Queries in order? | Method |
| --- | --- | --- |
| yes | yes | deque and pointer, O(n) (above) |
| yes | no | the same hull, but binary search it for each query: O(n log n) |
| no | either | a structure that takes lines in any order, such as a Li Chao tree: O(n log C) |

A Li Chao tree is a segment tree over the x-coordinates where each node keeps the line that's lowest at its midpoint; segment trees arrive in Part VIII, M60.

<Callout kind="gotcha" title="Swift gotcha: the cross-multiplication overflows">
The useless-line test multiplies an intercept difference by a slope difference. Intercepts here are about S², and slopes about S, so the product is about S³. With S up to 10⁶ that's 10¹⁸, just inside an `Int`; any bigger and Swift crashes on the overflow. Check the bound for your problem. If it doesn't fit, compare the meeting points with floor division instead (exact for whole-number queries), or with `Double`s, accepting a small risk on near-ties.
</Callout>

## Knuth's optimisation: interval DPs with a shrinking search

### The shape

> `cost[i][j] = min over i ≤ k < j of (cost[i][k] + cost[k + 1][j]) + w(i, j)`

This is the interval DP from [Matrix chain multiplication](/dsa/learn/dpi-matrix-chain) and its relatives: split the range i…j at k, solve both halves, pay `w(i, j)` for joining. There are O(n²) ranges and up to n splits each, so O(n³).

Let `opt[i][j]` be the split k that gives the minimum. **Knuth's optimisation** says that, when w is well behaved, the best split moves only a little as the range grows:

> `opt[i][j − 1] ≤ opt[i][j] ≤ opt[i + 1][j]`

So instead of trying every k from i to j − 1, try only the k's between the best splits of the two ranges one shorter, which are already known when ranges are filled by length. Adding up the sizes of those windows along each diagonal telescopes to O(n) per length, so the whole table costs **O(n²)**.

**Conditions**, stated carefully. The bound on `opt` is guaranteed when the joining cost w satisfies both:

1. the **quadrangle inequality**: `w(a, c) + w(b, d) ≤ w(a, d) + w(b, c)` whenever `a ≤ b ≤ c ≤ d` (two overlapping ranges cost no more than the outer one plus the inner one);
2. **monotonicity**: `w(b, c) ≤ w(a, d)` whenever `a ≤ b ≤ c ≤ d` (a range costs no more than any range containing it).

And the recurrence must have exactly the shape above: the extra cost depends on i and j, **not on k**.

### An example: merging piles

A row of piles must be merged into one, two neighbours at a time, and each merge costs the size of the new pile. Here `w(i, j)` is the total size of piles i to j, a range sum. A range sum satisfies the quadrangle inequality with equality (both sides add up the same piles), and with positive sizes it's monotone. So Knuth applies:

```swift run
// Merge a row of piles into one, two neighbours at a time. Each merge costs the size of the new pile.
// cost[i][j] = min over split k of cost[i][k] + cost[k + 1][j], plus sum(i...j)
func mergeCost(_ piles: [Int], knuth: Bool) -> (cost: Int, steps: Int) {
    let n = piles.count
    var prefix = [0]
    for p in piles { prefix.append(prefix.last! + p) }
    var cost = [[Int]](repeating: [Int](repeating: 0, count: n), count: n)
    var opt = [[Int]](repeating: [Int](repeating: 0, count: n), count: n)   // the best split k for i...j
    for i in 0..<n { opt[i][i] = i }
    var steps = 0
    for length in 2...n {
        for i in 0...(n - length) {
            let j = i + length - 1
            // Knuth: the best split lies between the best splits of the two ranges one shorter
            let low = knuth ? opt[i][j - 1] : i
            let high = knuth ? min(opt[i + 1][j], j - 1) : j - 1
            cost[i][j] = Int.max
            for k in low...high {
                steps += 1
                let candidate = cost[i][k] + cost[k + 1][j]
                if candidate < cost[i][j] {
                    cost[i][j] = candidate
                    opt[i][j] = k
                }
            }
            cost[i][j] += prefix[j + 1] - prefix[i]
        }
    }
    return (cost[0][n - 1], steps)
}

let piles = [4, 1, 3, 6, 2]
print(mergeCost(piles, knuth: false).cost, mergeCost(piles, knuth: true).cost)
let row = (0..<200).map { ($0 * 53 + 7) % 40 + 1 }
let plain = mergeCost(row, knuth: false), fast = mergeCost(row, knuth: true)
print(plain.cost, fast.cost)
print("splits tried:", plain.steps, "vs", fast.steps)
```

```output
36 36
30755 30755
splits tried: 1333300 vs 39555
```

The answers match, and for 200 piles Knuth tries 39,555 splits instead of 1,333,300: about n² against n³ / 6.

**Where it does and doesn't apply.** The original use is [Optimal BST](/dsa/learn/dpi-optimal-bst), where w is a range sum of search frequencies, exactly like the piles. Matrix chain multiplication looks similar, but its cost, `d[i − 1] · d[k] · d[j]`, depends on the split k, so it isn't in Knuth's form and the bound on `opt` can fail. Never assume the bound; when in doubt, test the fast version against the O(n³) one on random inputs.

## Divide-and-conquer optimisation: a best choice that moves one way

### The shape

> `best[g][i] = min over j < i of (best[g − 1][j] + C(j, i))`

This is a **layered** DP: g counts groups (or days, or machines), and each layer is computed entirely from the one before. A layer costs O(n²) done directly, so k layers cost O(k · n²).

Let `opt(i)` be the j that gives the minimum for i (the leftmost, if there's a tie). **Divide-and-conquer optimisation** applies when `opt` never decreases: `opt(i) ≤ opt(i + 1)`. Then:

1. Compute `best[g][mid]` for the middle index `mid` by trying every j in the allowed range, and note `opt(mid)`.
2. Every i left of `mid` has its best j at or before `opt(mid)`; every i right of `mid` has it at or after.
3. Recurse on both halves with those narrower ranges.

Each level of the recursion tries O(n) candidates in total, and there are log n levels, so a layer costs **O(n log n)**, and k layers **O(k · n log n)**.

**Conditions:** `opt(i) ≤ opt(i + 1)` within each layer. A sufficient condition is that the cost C satisfies the quadrangle inequality, `C(a, c) + C(b, d) ≤ C(a, d) + C(b, c)` for `a ≤ b ≤ c ≤ d`. Costs like "the square of a group's sum" (with positive numbers) or "the number of pairs inside a group" satisfy it.

### An example: splitting into k groups

Split a row of positive numbers into exactly k non-empty groups of neighbours, where a group with sum s costs s². Minimise the total. `C(j, i) = (S[i] − S[j])²` satisfies the quadrangle inequality because squaring is convex and the prefix sums grow.

```swift run
// Split numbers (in order) into exactly k non-empty groups; a group with sum s costs s². Minimise the total.
// layer g: best[g][i] = min over j < i of best[g - 1][j] + (S[i] - S[j])², for the first i numbers
func splitCost(_ numbers: [Int], groups k: Int, divideAndConquer: Bool) -> (cost: Int, steps: Int) {
    let n = numbers.count
    var prefix = [0]
    for x in numbers { prefix.append(prefix.last! + x) }
    func groupCost(_ j: Int, _ i: Int) -> Int {       // numbers j..<i as one group
        let s = prefix[i] - prefix[j]
        return s * s
    }
    let unreached = Int.max / 2
    var previous = (0...n).map { $0 == 0 ? 0 : unreached }   // zero groups: only "nothing" is possible
    var steps = 0
    for _ in 1...k {
        var current = [Int](repeating: unreached, count: n + 1)
        // Fill current[i] for i in lo...hi, knowing the best j lies in optLo...optHi
        func solve(_ lo: Int, _ hi: Int, _ optLo: Int, _ optHi: Int) {
            if lo > hi { return }
            let mid = (lo + hi) / 2
            var bestJ = optLo
            for j in optLo...min(mid - 1, optHi) where previous[j] < unreached {
                steps += 1
                let candidate = previous[j] + groupCost(j, mid)
                if candidate < current[mid] {
                    current[mid] = candidate
                    bestJ = j
                }
            }
            solve(lo, mid - 1, optLo, bestJ)          // to the left, the best j is no later
            solve(mid + 1, hi, bestJ, optHi)          // to the right, it's no earlier
        }
        if divideAndConquer {
            solve(1, n, 0, n - 1)
        } else {
            for i in 1...n {
                for j in 0..<i where previous[j] < unreached {
                    steps += 1
                    current[i] = min(current[i], previous[j] + groupCost(j, i))
                }
            }
        }
        previous = current
    }
    return (previous[n], steps)
}

print(splitCost([3, 1, 4, 1, 5, 9, 2, 6], groups: 3, divideAndConquer: false).cost,
      splitCost([3, 1, 4, 1, 5, 9, 2, 6], groups: 3, divideAndConquer: true).cost)
let numbers = (0..<600).map { ($0 * $0 * 7 + $0 * 13 + 5) % 97 + 1 }
let plain = splitCost(numbers, groups: 6, divideAndConquer: false)
let fast = splitCost(numbers, groups: 6, divideAndConquer: true)
print(plain.cost, fast.cost)
print("candidates tried:", plain.steps, "vs", fast.steps)
```

```output
341 341
142488029 142488029
candidates tried: 893120 vs 28109
```

For `[3, 1, 4, 1, 5, 9, 2, 6]` in three groups, the best split is `[3, 1, 4, 1]`, `[5, 9]` and `[2, 6]`: 81 + 196 + 64 = 341. On 600 numbers in 6 groups, the divide-and-conquer version tries 28,109 candidates instead of 893,120. The recursion is only log n deep, so it's safe in any thread.

## Choosing a technique

| Technique | Transition shape | Condition | Speed-up |
| --- | --- | --- | --- |
| Monotonic queue | min or max over a sliding window of j | window ends only move right | O(n · k) to O(n) |
| Convex hull trick | min of `m[j] · x[i] + c[j]` | lines and queries in order (or a Li Chao tree) | O(n²) to O(n) or O(n log n) |
| Knuth | interval DP, split k, extra cost `w(i, j)` | w has the quadrangle inequality and is monotone | O(n³) to O(n²) |
| Divide and conquer | layered: `best[g − 1][j] + C(j, i)` | `opt(i)` never decreases (C has the quadrangle inequality) | O(k · n²) to O(k · n log n) |

The first two are about **how the candidates look** (a window, a set of lines). The last two are about **where the best candidate is** (between known bounds). That's why the first two need only a recognisable formula, while the last two need a condition you should prove, or at least test hard.

## Swift gotchas and common mistakes

<Callout kind="gotcha" title="Applying Knuth or D&C without the condition">
If the condition fails, both optimisations still run, still return a number, and that number is sometimes wrong, with nothing to warn you. Before trusting either, compare it with the slow DP on a few hundred random small inputs, as every example in this lesson does.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: removeFirst on an array is O(n)">
A monotonic queue needs to remove from the front. `Array.removeFirst()` shifts every element, which turns the O(n) algorithm back into O(n²). Keep a `head` index instead (as the examples do), or use DSAKit's `Deque`.
</Callout>

- **Equal slopes** in the convex hull trick make the meeting-point formula divide by zero. If slopes can repeat, keep only the line with the smaller intercept (for a minimum) before running the test.
- **Off-by-one windows.** "At most k back" means j from `i − k` to `i − 1`. Pop the front while it's **less than** `i − k`, not less than or equal.

## Practice

**The cheapest baton relay** is a monotonic-queue DP with a twist: every leg must be at least `shortest` and at most `longest` checkpoints, so the index that joins the window at step i is `i − shortest`, not `i − 1`, and some checkpoints can't be reached at all.

**Ordering panels in bulk** needs two ideas before the convex hull trick appears. First, panels that another panel covers can ride along for free; drop them and sort the rest. Then the cost of a batch of neighbours is a product of one panel's width and another's height, which is a line. The tests use 50,000 panels that all survive the first step, so only an O(n) or O(n log n) DP passes.
