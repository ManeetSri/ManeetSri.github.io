## Why it matters

Counting DPs produce enormous numbers. The ways to tile a strip, the paths through a grid, the orders in which to roll a running total: they grow exponentially, and an `Int` holds only up to about 9.2 × 10¹⁸. So problems say "return the answer **modulo 1,000,000,007**". That turns a correct DP into a correct DP **with a few traps**: an addition that overflows before you reduce, a subtraction that goes negative, a comparison between reduced numbers that means nothing, a division that isn't allowed. This lesson collects the rules from [Modular arithmetic](/dsa/learn/math-modular-arithmetic) and shows where each one bites inside a DP.

## When exact counts run out

Here's a simple counting DP: the number of ways a running total of dice rolls can hit exactly n, where the order of the rolls matters. The last roll was some face from 1 to 6, so `ways[n] = ways[n − 1] + … + ways[n − 6]`, with `ways[0] = 1`. The counts roughly double each step. `addingReportingOverflow` from [Overflow traps and overflow operators](/dsa/learn/swift-overflow) tells you exactly when they stop fitting:

```swift run
// Ways to roll a running total of exactly n with a six-sided die (order matters): exact, until it overflows
var exact = [1]                                       // one way to total 0: roll nothing
var n = 0
var overflowed = false
while !overflowed {
    n += 1
    var ways = 0
    for face in 1...6 where n - face >= 0 {
        let (sum, overflow) = ways.addingReportingOverflow(exact[n - face])
        if overflow { overflowed = true }
        ways = sum
    }
    exact.append(ways)
}
print("exact counts work up to n =", n - 1, "with", exact[n - 1])

// The same DP modulo 1,000,000,007: reduce after every addition
let mod = 1_000_000_007
var ways = [Int](repeating: 0, count: 1_001)
ways[0] = 1
for total in 1...1_000 {
    for face in 1...6 where total - face >= 0 {
        ways[total] = (ways[total] + ways[total - face]) % mod
    }
}
print("n = 10:", ways[10], exact[10])
print("n = 1000:", ways[1_000])
```

```output
exact counts work up to n = 64 with 5679409090080257133
n = 10: 492 492
n = 1000: 937196411
```

Exact counting dies at n = 65. With a modulus, n = 1,000 (or a million) is no trouble, and for small n the reduced count equals the exact one, because it never reached the modulus.

## The rules, inside a DP

M15's rules say you can reduce after **every** addition, subtraction and multiplication without changing the final remainder. In a DP that becomes four habits.

### 1. Reduce after every step, not at the end

"Compute the count, then take `% mod`" doesn't work: the count overflowed long before the end, and Swift stops the program on overflow rather than wrapping. Reduce **every time you store** a table entry. Then every stored value is between 0 and mod − 1.

How many reduced values can you add before reducing? Each is below 1.000000007 × 10⁹, and an `Int` holds 9.2 × 10¹⁸, so about nine billion of them. In practice, reducing after each addition is simplest and cheap. A **product** of two reduced values is below 10¹⁸, which fits, so `(a * b) % mod` is safe when `a` and `b` are already reduced. A product of **three** is not: reduce in between.

### 2. Subtraction needs `+ mod`

DPs often subtract, most often to take a **window sum** from prefix sums. Swift's `%` keeps the sign of the left side, so a negative difference stays negative. When both values are already reduced, adding `mod` once before the `%` is enough:

> `(prefix[t] - prefix[low] + mod) % mod`

Here's a DP that needs it. Generalise the dice to steps of 1 up to k, with k as large as 100,000. The direct transition adds k terms, O(n · k) in all. But those k terms are a **window** of the table, so keep a running prefix sum and subtract, as in [1D prefix sums and range queries](/dsa/learn/prefix-1d). Under a modulus, the prefix sums are reduced too, and a later one can be **smaller** than an earlier one:

```swift run
let mod = 1_000_000_007

// ways[t] = ways[t - 1] + … + ways[t - k]: the sum of a window, kept with a running prefix sum
func waysWithSteps(upTo k: Int, total n: Int) -> Int {
    var ways = [Int](repeating: 0, count: n + 1)
    var prefix = [Int](repeating: 0, count: n + 2)    // prefix[i] = ways[0] + … + ways[i - 1], reduced
    ways[0] = 1
    prefix[1] = 1
    for t in 1...n {
        let low = max(0, t - k)
        ways[t] = (prefix[t] - prefix[low] + mod) % mod   // the window sum; + mod keeps it non-negative
        prefix[t + 1] = (prefix[t] + ways[t]) % mod
    }
    return ways[n]
}

// The direct O(n · k) version, for checking
func waysDirect(upTo k: Int, total n: Int) -> Int {
    var ways = [Int](repeating: 0, count: n + 1)
    ways[0] = 1
    for t in 1...n {
        for step in 1...min(k, t) {
            ways[t] = (ways[t] + ways[t - step]) % mod
        }
    }
    return ways[n]
}

print(waysWithSteps(upTo: 6, total: 1_000), waysDirect(upTo: 6, total: 1_000))
print(waysWithSteps(upTo: 50, total: 2_000), waysDirect(upTo: 50, total: 2_000))
print(waysWithSteps(upTo: 100_000, total: 200_000))

// Without the + mod, a reduced prefix can be smaller than an earlier one, and the difference goes negative
let a = 1_000_000_010 % mod, b = 5
print(a - b, (a - b + mod) % mod)
```

```output
937196411 937196411
938508316 938508316
848123119
-2 1000000005
```

The prefix-sum version matches the direct one and handles k = 100,000 with n = 200,000 in O(n). The last line shows the trap: 1,000,000,010 reduces to 3, and 3 − 5 is −2. Used as a count, or as an array index, that −2 is a bug. `(−2 + mod) % mod` is 1,000,000,005, the right remainder.

### 3. Never compare reduced counts

Once counts are reduced, their **size means nothing**. 10⁹ + 8 ways reduces to 1, which looks smaller than 5. So:

- Don't take `max` or `min` of reduced counts. If a problem needs the **largest** count, or to compare two counts, you need the exact values (or a different idea).
- Don't use "count is 0" to mean "impossible". A count can be a multiple of the modulus and reduce to 0 while millions of ways exist. Track reachability separately, as [DP on DAGs](/dsa/learn/dpa-dags) did with its `longest` array.

A DP that **optimises** (min cost, max value) and **counts** at the same time, such as "the number of cheapest paths", keeps the cost exact and only the count reduced: compare costs, add counts.

### 4. No division

`(a / b) % mod` can't be computed from `a % mod` and `b % mod`: M15 showed `(12 % 5) / (4 % 5)` giving 0 instead of 3. Modular division multiplies by a **modular inverse** instead, which you'll meet in M66, Number theory and combinatorics. Inside a DP you rarely need it. When a formula divides (an average, a binomial coefficient), look for a version that only adds and multiplies, such as Pascal's triangle for combinations from [Factorials, permutations and combinations](/dsa/learn/math-counting).

## Checking a modular DP

Bugs in modular code hide well, because wrong answers look just as random as right ones. Two checks catch most of them:

1. **Small cases, exactly.** For small n the counts never reach the modulus, so the reduced DP must equal an exact count or a brute force. The first run example does this at n = 10.
2. **A tiny modulus.** Run the DP with mod = 7 and compare it with the exact count `% 7` for n up to 60 or so. Values wrap around constantly, so every missed reduction and every negative subtraction shows up at once.

| Trap | Symptom | Fix |
| --- | --- | --- |
| Reducing only at the end | crash: overflow | `% mod` on every store |
| `a - b` on reduced values | negative results, crashes on indexing | `(a - b + mod) % mod` |
| Multiplying three values | overflow | reduce after each product |
| Comparing reduced counts | wrong max, wrong "impossible" | keep exact values for comparisons |
| Dividing | wrong answer | modular inverse (M66), or avoid division |

<Callout kind="gotcha" title="Swift gotcha: % keeps the sign">
In Swift, `-2 % 7` is `-2`, not `5`. Python's `%` would give 5, so solutions translated from Python lose their safety net. The `+ mod` is not optional in Swift.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: writing the modulus">
`1e9 + 7` is a `Double`, and `Int(1e9) + 7` works but reads badly. Write `1_000_000_007`: underscores make the digits easy to check, and a constant like `let mod = 1_000_000_007` at the top keeps the value in one place.
</Callout>

## Practice

**Counting trail routes** counts the routes through a one-way trail map, modulo 1,000,000,007. One test is a chain with two trails at every step, so the true count is 2⁹⁹⁹⁹⁹: only a DP that reduces after every addition survives it.

```cards
- id: mod-reduce-every-step
  front: "Why reduce after every step in a counting DP, rather than once at the end?"
  back: "The exact count overflows long before the end, and Swift stops the program on overflow. Reducing each stored value keeps everything below the modulus."
- id: mod-subtraction
  front: "How do you subtract two reduced values a and b safely in Swift?"
  back: "(a - b + mod) % mod. Swift's % keeps the sign, so a negative difference would stay negative."
- id: mod-no-compare
  front: "Why can't you take the max of counts reduced modulo p?"
  back: "Reduction scrambles size: p + 1 ways reduces to 1. Comparisons, and tests like 'count is 0 means impossible', need exact values or separate tracking."
- id: mod-product
  front: "Is (a * b) % 1,000,000,007 safe for reduced a and b?"
  back: "Yes: both are below about 10⁹, so the product is below about 10¹⁸, which fits in an Int. A product of three reduced values doesn't."
```
