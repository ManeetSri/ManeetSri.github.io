## Why it matters

Every DP you've written is secretly a graph problem. Draw one dot per state and an arrow from each state to the states it feeds, and you get a **directed acyclic graph**: directed because information flows one way, acyclic because no state can depend on itself. Seeing DP this way explains why "fill in the right order" works, tells you what to do when a problem hands you an explicit DAG (a build graph, a course plan, a pipeline of tasks), and warns you when a recurrence secretly has a cycle and no fill order exists. The two workhorse questions on a DAG, the **longest path** and the **number of paths**, are each one loop over a topological order.

## Every DP is a DAG

Take climbing stairs from [Climbing stairs and min-cost stairs](/dsa/learn/dp-stairs): `ways[i] = ways[i - 1] + ways[i - 2]`. As a graph, state i has arrows from states i − 1 and i − 2:

```text
  0 ──► 1 ──► 2 ──► 3 ──► 4 ──► …
  └──────────►┘└──────────►┘
     (and every i ──► i + 2)
```

Now match up the recipe from [The DP recipe: state, transition, base, order, answer](/dsa/learn/dp-recipe) with graph words:

| DP word | Graph word |
| --- | --- |
| state | vertex |
| transition | edge from the states it reads to the state it fills |
| base case | a vertex with no incoming edges (a source) |
| fill order | a topological order |
| "this recurrence has no valid order" | the graph has a cycle |

**Memoisation** is a DFS through this graph: asking for a state recursively asks for everything it depends on first, which is the finishing order from [Topological sort with DFS](/dsa/learn/topo-dfs). **Tabulation** is you choosing a topological order by hand, such as "increasing i" or "row by row". Both are correct for the same reason: every edge goes from earlier to later.

### What a cycle means

If a recurrence makes a state depend on itself, even through a long chain, there's no order to fill it in. "The cheapest way to reach a cell when you can move in all four directions" is like that: the cell to your left depends on you and you depend on it. That's not a DP any more. It's a shortest-path problem, and Dijkstra or Bellman–Ford from M44 handle it, because they don't need a fixed order in advance.

One cycle is fine: a state that depends on **itself directly** with a known probability can sometimes be solved algebraically. You'll see that in the next lesson.

## Paths in an explicit DAG

When the problem gives you a DAG directly, the plan is always the same:

1. Find a topological order with [Kahn's algorithm](/dsa/learn/topo-kahn), or with DFS finishing order.
2. Go through the vertices in that order. When you reach v, every vertex with an edge into v has already been finished, so v's value can be computed from them.

[Longest and shortest paths in a DAG](/dsa/learn/topo-dag-paths) did this for path lengths. **Counting paths** is the same loop with a sum instead of a max:

> `ways[v]` = the sum of `ways[u]` over every edge u → v, with `ways[source] = 1`.

Every path from the source to v arrives through exactly one last edge u → v, and the paths through different last edges are different, so adding them counts each path exactly once.

Step through Kahn's algorithm on this lesson's graph. The order it produces is exactly the order the DP below fills its table.

```swift run
// Kahn's algorithm: an order where every edge goes forwards (the graph must be a DAG)
func topologicalOrder(_ n: Int, _ edges: [[Int]]) -> [Int] {
    var outgoing = [[Int]](repeating: [], count: n)
    var inDegree = [Int](repeating: 0, count: n)
    for edge in edges {
        outgoing[edge[0]].append(edge[1])
        inDegree[edge[1]] += 1
    }
    var order = (0..<n).filter { inDegree[$0] == 0 }
    var head = 0
    while head < order.count {
        let v = order[head]
        head += 1
        for w in outgoing[v] {
            inDegree[w] -= 1
            if inDegree[w] == 0 { order.append(w) }
        }
    }
    return order
}

// Two DPs over the same order: the number of paths from source, and the longest path from source
func pathFacts(_ n: Int, _ edges: [[Int]], from source: Int) -> (ways: [Int], longest: [Int]) {
    var incoming = [[(from: Int, length: Int)]](repeating: [], count: n)
    for edge in edges {
        incoming[edge[1]].append((edge[0], edge.count > 2 ? edge[2] : 1))
    }
    var ways = [Int](repeating: 0, count: n)
    var longest = [Int](repeating: -1, count: n)      // -1: not reachable from source
    ways[source] = 1
    longest[source] = 0
    for v in topologicalOrder(n, edges) {
        for (u, length) in incoming[v] where longest[u] >= 0 {   // u comes earlier, so it is final
            ways[v] += ways[u]
            longest[v] = max(longest[v], longest[u] + length)
        }
    }
    return (ways, longest)
}

let edges = [[0, 1, 3], [0, 2, 2], [1, 3, 4], [2, 3, 1], [2, 4, 6], [3, 5, 2], [4, 5, 1], [1, 5, 9], [6, 4, 1]]
print("order:", topologicalOrder(7, edges))
let facts = pathFacts(7, edges, from: 0)
print("ways:", facts.ways)
print("longest:", facts.longest)

// Climbing 10 stairs, one or two at a time, is counting paths in a DAG too
var stairs: [[Int]] = []
for step in 0..<10 {
    stairs.append([step, step + 1])                   // one stair
    if step + 2 <= 10 { stairs.append([step, step + 2]) }   // two stairs
}
print("stairs:", pathFacts(11, stairs, from: 0).ways[10])
```

```output
order: [0, 6, 1, 2, 3, 4, 5]
ways: [1, 1, 1, 2, 1, 4, 0]
longest: [0, 3, 2, 7, 8, 12, -1]
stairs: 89
```

What to notice:

- From 0 there are 4 paths to vertex 5: 0 → 1 → 5, 0 → 1 → 3 → 5, 0 → 2 → 3 → 5 and 0 → 2 → 4 → 5. The longest is the first, 3 + 9 = 12, even though it has the fewest edges.
- Vertex 6 can't be reached from 0, so it has 0 ways and `longest` stays at −1. Its edge into 4 is skipped, because only reachable vertices pass the `where`.
- The same function counts the ways to climb 10 stairs, 89, by building the stairs' state graph explicitly. That's the "every DP is a DAG" claim, run as code.
- Both DPs are **O(V + E)**: Kahn's algorithm touches every edge once, and so does the DP loop.

## More questions, same loop

Once you have a topological order, a whole family of questions is one pass each:

| Question | Value per vertex | Combine incoming edges with |
| --- | --- | --- |
| Number of paths from s | count | sum |
| Longest path from s | length | max of `longest[u] + w` |
| Shortest path from s | length | min of `shortest[u] + w` (negative weights are fine) |
| Can s reach v? | true or false | or |
| Number of shortest paths | (length, count) | keep the best length; add counts on ties |

The last row is worth a second look. The edges that lie on **some** shortest path from s form a DAG of their own (the "shortest-path DAG"), and BFS from [BFS and unweighted shortest paths](/dsa/learn/gt-bfs) visits it layer by layer, which is a topological order. So counting shortest paths in an unweighted graph needs only one extra array beside the BFS distances: `count[v]` sums `count[u]` over every u with `dist[u] + 1 == dist[v]`.

A DP can also add its own dimension to a DAG. "The longest path that uses at most k red edges" has states `(vertex, red edges used)`, and those states form a bigger DAG: edges go from `(u, r)` to `(v, r)` or `(v, r + 1)`. Same loop, k + 1 values per vertex.

## Swift gotchas and common mistakes

<Callout kind="gotcha" title="Recursion on a deep DAG">
Memoised recursion on a DAG is a DFS, and a DAG can be a chain 100,000 vertices long. Inside a test, that overflows the stack. Kahn's algorithm is a loop with a queue, so it's safe at any depth: prefer it for big inputs.
</Callout>

<Callout kind="gotcha" title="Counting paths explodes">
The number of paths can grow exponentially: a chain of n vertices with two parallel edges at each step has 2ⁿ⁻¹ paths, which overflows an `Int` at n = 65. Problems that count paths almost always ask for the answer modulo some prime, which is the next-but-one lesson's subject. Once you count modulo p, a count of 0 no longer means "unreachable", which is why the code above tests reachability with `longest[u] >= 0` instead of `ways[u] > 0`.
</Callout>

- **Check that it really is a DAG.** If Kahn's algorithm produces fewer than n vertices, the graph has a cycle, and the counts and lengths are meaningless for the vertices left out.
- **Use the unreached marker carefully** for longest paths: −1 works here because lengths are non-negative. With negative weights, use an optional or `Int.min` plus an explicit check.
