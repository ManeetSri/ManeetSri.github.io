## Why it matters

How many numbers from 1 to 10¹⁸ have digits adding up to 100? How many invoice numbers below a limit contain no repeated digit, or no 4, or are divisible by 7 and also by the sum of their digits? A loop over the range is out of the question: a billion billion numbers would take decades. **Digit DP** answers all of these in a few thousand steps by building numbers one digit at a time and grouping together all the prefixes that behave the same from then on. It's a staple of competitive programming, and the "tight" idea behind it is worth knowing for any problem about counting things up to a limit.

## Counting up to a limit is enough

Every question about a range `low...high` reduces to two questions about prefixes of the number line:

> count(low...high) = count(0...high) − count(0...low − 1)

So the whole job is one function, `upTo(limit)`: how many numbers from 0 to `limit` have the property? Take care when `low` is 0: then there's nothing to subtract, and `low − 1` would be −1.

## Building a number digit by digit

Write the limit with its digits, say 253, and imagine choosing the digits of a number x from left to right, padding x with leading zeros to the same length. So 7 is written 007 and 41 is 041. Every number from 0 to 253 is exactly one way of choosing three digits that doesn't go above 253.

The rule for "doesn't go above" depends on what you've chosen so far:

- If every digit so far **equals** the limit's digit in that place, you're still **tight**: the next digit can only go up to the limit's next digit. Choose exactly that digit and you stay tight; choose anything smaller and you're free from then on.
- Once any digit has been **smaller** than the limit's, x is already below the limit whatever comes next. You're **loose**, and every later digit can be anything from 0 to 9.

For 253: the first digit can be 0, 1 or 2. Choose 0 or 1 and the remaining two digits are free, 00 to 99. Choose 2 and you're still tight, so the second digit can only be 0 to 5. And so on.

```text
position:      1     2     3
limit:         2     5     3
tight path:    2  →  5  →  3        (one number: 253 itself)
branch off:   0–1   0–4   0–2       (then every later digit is 0–9)
```

## The state: position, property, tight

Here's the key observation. Once you're loose, the number of ways to finish depends only on **how many digits are left** and **whatever the property needs to remember** about the digits so far. Two different prefixes that agree on those finish in exactly the same number of ways, so the count can be memoised.

For "the digit sum equals `target`", the property only needs the sum so far. So the state is:

> `count(position, sum, tight)` = the number of ways to choose the digits from `position` to the end, given the digits so far add up to `sum`.

- **Transition:** try every allowed digit d (0 to 9, or 0 to the limit's digit if tight). Recurse with `position + 1`, `sum + d`, and `tight && d == limit's digit`.
- **Base case:** at the end, count 1 if `sum == target`, otherwise 0.
- **Prune:** if `sum` is already over `target`, return 0 at once.
- **Answer:** `count(0, 0, true)`.

```swift run
// How many numbers from 0 to limit have digits adding up to target?
func countDigitSum(upTo limit: Int, target: Int) -> Int {
    let digits = String(limit).compactMap(\.wholeNumberValue)    // 253 → [2, 5, 3]
    // memo[position][sum] for loose states only: the count of ways to finish from there
    var memo = [[Int?]](repeating: [Int?](repeating: nil, count: target + 1), count: digits.count)
    func count(_ position: Int, _ sum: Int, _ tight: Bool) -> Int {
        if sum > target { return 0 }                          // already too big: prune
        if position == digits.count { return sum == target ? 1 : 0 }
        if !tight, let known = memo[position][sum] { return known }
        let highest = tight ? digits[position] : 9            // tight: can't go above limit's digit
        var total = 0
        for digit in 0...highest {
            total += count(position + 1, sum + digit, tight && digit == highest)
        }
        if !tight { memo[position][sum] = total }
        return total
    }
    return count(0, 0, true)
}

func digitSum(_ x: Int) -> Int {
    var x = x, sum = 0
    while x > 0 { sum += x % 10; x /= 10 }
    return sum
}

print(countDigitSum(upTo: 253, target: 7), (0...253).filter { digitSum($0) == 7 }.count)
print(countDigitSum(upTo: 99_999, target: 20), (0...99_999).filter { digitSum($0) == 20 }.count)

// Any range: count up to high, minus count up to low - 1
func countDigitSum(from low: Int, to high: Int, target: Int) -> Int {
    let below = low == 0 ? 0 : countDigitSum(upTo: low - 1, target: target)
    return countDigitSum(upTo: high, target: target) - below
}
print(countDigitSum(from: 100, to: 200, target: 5))
print(countDigitSum(from: 1, to: 1_000_000_000_000_000_000, target: 100))
```

```output
21 21
5631 5631
5
9869362547411187
```

What to notice:

- `String(limit).compactMap(\.wholeNumberValue)` turns a number into its digits, most significant first. `wholeNumberValue` gives a `Character`'s digit value as an `Int?`, and `compactMap` drops any `nil`.
- The DP matches the brute force on the small limits. The range 100 to 200 has five numbers with digit sum 5: 104, 113, 122, 131 and 140.
- The last line counts across a range of 10¹⁸ numbers. The memo has 19 positions × 101 sums, and each state tries 10 digits: about 19,000 steps.
- The recursion is only as deep as the number of digits, 19 at most, so it's perfectly safe.

### The count for 253, by hand

Follow the tight path of 253 for digit sum 7 and add up what branches off it:

| Prefix chosen | State | What's left | Ways |
| --- | --- | --- | --- |
| first digit 0 | loose | two free digits adding up to 7: 07, 16, …, 70 | 8 |
| first digit 1 | loose | two free digits adding up to 6: 06, 15, …, 60 | 7 |
| 2, then 0 to 4 | loose | one free digit making the total 7 (205, 214, 223, 232, 241) | 5 |
| 2, then 5 | tight | the last digit must be 0, and 0 ≤ 3 is allowed (250) | 1 |

That's 8 + 7 + 5 + 1 = 21, the number the code printed. Each "loose" row is one memo entry used over and over in bigger examples: "two free digits adding up to s" doesn't care which prefix came before.

### Why only loose states are memoised

A tight state's count depends on the limit's remaining digits, but there's only **one** tight prefix at each position: the limit's own digits. So each tight state is visited exactly once, and memoising it would save nothing. Loose states are visited many times (from every smaller digit at every earlier position) and their counts don't depend on the limit at all, only on how many digits remain. So `memo[position][sum]` is filled for loose states only.

A neat consequence: if you index loose states by **digits remaining** instead of position, the table doesn't depend on the limit at all and can be shared between the `high` and `low − 1` calls, or across many queries.

### The same count without recursion

Since loose states don't care about the limit, you can precompute `free[r][s]`, the number of ways r free digits can add up to s, and then walk the limit's digits once. At each position, every digit smaller than the limit's digit leaves the rest free, contributing one table lookup each. This is the same DP written bottom-up, and it's the shape of the reference solution for this lesson's problem.

## Leading zeros: a second flag

Padding with leading zeros was harmless for digit sums: zeros add nothing. For many properties they're poison. Take "**no digit appears twice**". Written as 007, the number 7 seems to repeat the digit 0, but those zeros aren't really there. So add a second flag:

- `started`: has a non-zero digit been placed yet? Until it has, a 0 is a leading zero and doesn't count as a digit.

The property's memory is a **bitmask** of digits used so far, 10 bits, as in [Bitmask DP: TSP and assignment](/dsa/learn/dpa-bitmask). The state becomes `(position, used, tight, started)`. At the end, count 1 only if `started` is true, because the all-zeros "number" is 0, which the question (1 to the limit) doesn't include.

```swift run
// How many numbers from 1 to limit have no repeated digit?
func countDistinctDigits(upTo limit: Int) -> Int {
    let digits = String(limit).compactMap(\.wholeNumberValue)
    // memo[position][used]: loose and started states only. used is a bitmask of the digits so far.
    var memo = [[Int]](repeating: [Int](repeating: -1, count: 1 << 10), count: digits.count)
    func count(_ position: Int, _ used: Int, _ tight: Bool, _ started: Bool) -> Int {
        if position == digits.count { return started ? 1 : 0 }   // the all-zeros "number" isn't counted
        if !tight && started && memo[position][used] >= 0 { return memo[position][used] }
        let highest = tight ? digits[position] : 9
        var total = 0
        for digit in 0...highest {
            let nextTight = tight && digit == highest
            if !started && digit == 0 {
                total += count(position + 1, used, nextTight, false)   // still a leading zero: uses nothing
            } else if used & (1 << digit) == 0 {
                total += count(position + 1, used | (1 << digit), nextTight, true)
            }
        }
        if !tight && started { memo[position][used] = total }
        return total
    }
    return count(0, 0, true, false)
}

func hasDistinctDigits(_ x: Int) -> Bool {
    var x = x, seen = 0
    while x > 0 {
        if seen & (1 << (x % 10)) != 0 { return false }
        seen |= 1 << (x % 10)
        x /= 10
    }
    return true
}

print(countDistinctDigits(upTo: 100), (1...100).filter(hasDistinctDigits).count)
print(countDistinctDigits(upTo: 54_321), (1...54_321).filter(hasDistinctDigits).count)
print(countDistinctDigits(upTo: 9_999_999_999))
```

```output
90 90
18854 18854
8877690
```

From 1 to 100, the 9 numbers 11, 22, …, 99 and 100 itself repeat a digit, leaving 90. The last line counts every positive number with distinct digits there is: none can have more than 10 digits, so 8,877,690 is the total for all numbers, ever.

Without the `started` flag, every leading zero would count as a real 0, so 7 (written 007) and 10 (written 010) would both be rejected for repeating a 0. Try it: the count up to 100 drops from 90 to 72.

## The general shape

Every digit DP is the same skeleton with a different middle:

| Part | Digit sum | Distinct digits | Divisible by k |
| --- | --- | --- | --- |
| Property's memory | sum so far | mask of used digits | remainder mod k |
| Transition for digit d | `sum + d` | `used \| (1 << d)` | `(rem * 10 + d) % k` |
| Accept at the end | `sum == target` | `started` | `rem == 0` |
| Leading zeros matter? | no | yes | no |

The cost is (number of digits) × (property states) × 2 × 10. With 19 digits, that's tiny unless the property's memory is large: the distinct-digits mask has 1,024 values, which is still only about 400,000 steps.

<Callout kind="analogy" title="Filling in a form with a maximum">
Picture a form with a box for each digit and a printed maximum above it. While every box you've filled matches the maximum, the next box is limited by the printed digit. The moment you write a smaller digit in any box, the maximum stops mattering: the rest of the boxes are yours to fill however you like.
</Callout>

## Swift gotchas and common mistakes

<Callout kind="gotcha" title="Off by one at the ends of the range">
`count(low...high) = upTo(high) − upTo(low − 1)`, not `− upTo(low)`, which would drop `low` itself. And decide once whether `upTo` counts 0: for digit sum 0, the number 0 is the only match, so it matters there.
</Callout>

<Callout kind="gotcha" title="Memoising tight states with the wrong key">
If you memoise tight states too, the key must include `tight`, or a tight count (limited by the limit's digits) gets reused as a loose one (free digits), and the answers come out too small. Skipping the memo for tight states, as above, avoids the trap entirely.
</Callout>

- **Reset the memo for each new limit** if it's indexed by position: positions line up with the limit's digits, and a different limit can have a different length. The digits-remaining indexing avoids this.
- **10¹⁸ fits in an `Int`**, which reaches about 9.2 × 10¹⁸, and so does every count up to it. Only adding 10¹⁸ to something big would overflow.
