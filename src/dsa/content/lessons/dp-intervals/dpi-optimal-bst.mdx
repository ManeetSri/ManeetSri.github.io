## Why it matters

A compiler checks every word of your code against its list of keywords. A spell checker looks up "the" far more often than "zygote". If the lookup table is a binary search tree that never changes, a perfectly balanced tree is not the best one: it makes the **worst** lookup fast, but you care about the **average** lookup, weighted by how often each key is searched. Putting popular keys near the root wins. Finding the very best tree is an interval DP, and it ties together the BSTs of [The BST property, search and insert](/dsa/learn/bst-property-search-insert) with everything in this module.

## The problem

You have n keys in sorted order, and `freq[i]`, how many times key i will be searched. A search for a key at depth d costs d comparisons, counting the root as depth 1. The **cost** of a tree is the total over all searches:

> cost = the sum of `freq[i] × depth(key i)` over all keys.

Find the BST over these keys with the smallest cost.

Take keys 10, 20, 30 and 40, searched 4, 2, 6 and 3 times:

```text
  Balanced, root 20            Optimal, root 30

        20                           30
       /  \                         /  \
     10    30                     10    40
             \                      \
              40                     20
```

| Tree | 10 (×4) | 20 (×2) | 30 (×6) | 40 (×3) | Cost |
| --- | --- | --- | --- | --- | --- |
| Balanced, root 20 | depth 2: 8 | depth 1: 2 | depth 2: 12 | depth 3: 9 | 31 |
| Optimal, root 30 | depth 2: 8 | depth 3: 6 | depth 1: 6 | depth 2: 6 | **26** |

The optimal tree puts 30, the most searched key, at the root, and doesn't mind that 20 ends up deeper, because it's rarely searched.

## Subtrees are ranges

Here's the fact that makes this interval DP. In a BST, the keys of any subtree form a **contiguous range** of the sorted keys. The root's left subtree holds every key smaller than the root, and its right subtree every key larger. The same holds at every node.

So, to build the best tree for keys i through j, choose a root r among them. Its left subtree must be built from keys i...r − 1 and its right subtree from r + 1...j, and the best tree uses the best subtree for each, because the two sides don't affect each other.

What does choosing r cost? Every key in the two subtrees is now one level deeper than it was in its own subtree, so each search for them costs one more comparison. And the root is found in one comparison. Together, that adds **the total frequency of the whole range**, once:

> `cost[i][j] = min over r of cost[i][r - 1] + cost[r + 1][j] + weight(i, j)`, where `weight(i, j)` is `freq[i] + … + freq[j]`.

An empty range costs 0. Prefix sums from [1D prefix sums and range queries](/dsa/learn/prefix-1d) give each weight in O(1).

## In Swift, with half-open ranges

Empty ranges like "keys 3...2" are awkward with closed ranges. Half-open ranges avoid them: let `cost[i][j]` be the best cost for keys `i..<j`. Then an empty range is `cost[i][i] = 0`, the left subtree of root r is `i..<r`, and the right subtree is `r + 1..<j`. The table is (n + 1) × (n + 1).

```swift run
func optimalBST(keys: [Int], freq: [Int]) -> (cost: Int, root: [[Int]]) {
    let n = keys.count
    var prefix = [0]                                     // prefix[i]: freq[0] + … + freq[i - 1]
    for f in freq {
        prefix.append(prefix.last! + f)
    }
    var cost = Array(repeating: Array(repeating: 0, count: n + 1), count: n + 1)   // keys i..<j
    var root = Array(repeating: Array(repeating: -1, count: n + 1), count: n + 1)
    for length in stride(from: 1, through: n, by: 1) {
        for i in 0...(n - length) {
            let j = i + length
            cost[i][j] = Int.max
            for r in i..<j where cost[i][r] + cost[r + 1][j] < cost[i][j] {
                cost[i][j] = cost[i][r] + cost[r + 1][j]  // left: i..<r, right: r + 1..<j
                root[i][j] = r
            }
            cost[i][j] += prefix[j] - prefix[i]           // everything in the range goes one level down
        }
    }
    return (cost[0][n], root)
}

let keys = [10, 20, 30, 40]
let result = optimalBST(keys: keys, freq: [4, 2, 6, 3])
print("cost:", result.cost)

// Print the tree sideways: each node, then its left and right subtrees indented
func show(_ i: Int, _ j: Int, depth: Int, side: String) {
    guard i < j else { return }
    let r = result.root[i][j]
    print(String(repeating: "    ", count: depth) + side + String(keys[r]))
    show(i, r, depth: depth + 1, side: "L: ")
    show(r + 1, j, depth: depth + 1, side: "R: ")
}
show(0, keys.count, depth: 0, side: "")
```

```output
cost: 26
30
    L: 10
        R: 20
    R: 40
```

What to notice:

- `stride(from: 1, through: n, by: 1)` is used instead of `1...n` so that an empty list of keys doesn't build an invalid range.
- The weight is added once per range, after trying every root, because every choice of root pays it.
- `root[i][j]` records the winner for each range, so the whole tree can be rebuilt recursively, just like the bracketing in [Matrix chain multiplication](/dsa/learn/dpi-matrix-chain).
- The search keys never appear in the DP. Only their order and frequencies matter.

## Cost of the DP

About n²/2 ranges, each trying up to n roots: **O(n³)** time and **O(n²)** memory. For a few hundred keys that's instant, and since the tree is built once and searched millions of times, it's usually time well spent.

<Callout kind="note" title="Knuth's observation">
In 1971 Donald Knuth noticed that the best root never moves backwards as a range grows: the best root for keys i...j lies between the best root for i...j − 1 and the best root for i + 1...j. So instead of trying every r in the range, you only try the roots in that window. The windows for all ranges of one length overlap so little that they add up to O(n) per length, and the whole DP drops to O(n²). The same trick speeds up some other interval DPs that satisfy a similar condition; [Monotonic queue, convex hull trick, Knuth and D&C optimisations](/dsa/learn/dpa-optimisations) covers when it applies.
</Callout>

## Variations

- **Failed searches.** The classic textbook version also gives a frequency to each **gap** between keys, the searches that end at a missing child. The gaps add to each range's weight, and the same DP works.
- **Unknown frequencies.** If you don't know the frequencies in advance, or they change, a self-adjusting tree adapts on its own: [Splay trees](/dsa/learn/bal-splay) move each searched key to the root, and over a long run they're within a constant factor of the optimal static tree.
- **Equal frequencies.** When every key is equally popular, the optimal tree is a balanced one, as built in [A balanced BST from a sorted array](/dsa/learn/bst-from-sorted).

<Callout kind="gotcha" title="Common mistakes">
- **Adding only the root's frequency.** Choosing a root pushes every key of both subtrees one level down, so the whole range's weight is added.
- **Summing frequencies in a loop for every range.** That makes it O(n⁴). Use prefix sums.
- **Counting depth from 0.** The root costs one comparison, so with depth from 0 you'd add the total frequency at the end. Either works if you're consistent.
- **Closed ranges and empty subtrees.** A root at either end of its range has an empty subtree. Half-open ranges make that `cost[i][i] = 0` with no special cases.
</Callout>
