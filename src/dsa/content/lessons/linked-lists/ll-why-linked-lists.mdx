## Why it matters

An array keeps its elements side by side in one block of memory. A **linked list** scatters them around and joins them with arrows instead. That one change makes some operations instant that are slow for arrays, and the reverse. You'll find linked lists inside LRU caches, undo histories, music playlists and the fast queues of M27. And the habit they teach, following and rewiring references, is exactly what you'll need for trees and graphs.

## Arrays, briefly

You saw in [Contiguous memory and O(1) indexing](/dsa/learn/arrays-memory) that an array stores its elements in one unbroken block. Swift finds element `i` with a little arithmetic, which is why `numbers[i]` is O(1).

The price is paid when you insert or remove anywhere but the end. To put a new value at the front of a 1,000-element array, Swift has to slide all 1,000 elements one place along to make room. That's O(n), as [The cost of inserting and deleting](/dsa/learn/arrays-insert-delete-cost) showed.

A linked list makes the opposite trade.

## A chain of nodes

A linked list is made of **nodes**. Each node holds two things:

- a **value**, such as an `Int`;
- a reference to the **next** node, or `nil` if it's the last one.

You keep hold of the first node, called the **head**. From the head you can reach every other node by following `next` references until you hit `nil`:

```text
head
 |
 v
[10 | •]--->[20 | •]--->[30 | nil]
```

The nodes don't need to sit next to each other in memory. Each one can live anywhere on the heap, because the arrows say where to go next. That's the whole idea.

## Building a list by hand

Here's a node type and a three-node list, built by hand and then walked from the head:

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

let third = ListNode(30)
let second = ListNode(20, next: third)
let head = ListNode(10, next: second)

var current: ListNode? = head
while let node = current {
    print(node.value, terminator: " -> ")
    current = node.next
}
print("nil")
```

```output
10 -> 20 -> 30 -> nil
```

What to notice:

- `current` is an **optional** node. It starts at the head and moves along one `next` at a time.
- `while let node = current` stops when `current` becomes `nil`, the end of the chain. You'll write this loop in almost every lesson of this module.
- The list was built back to front, because each node needs its `next` to exist before it's created.

## Why nodes are classes

You met the reason in [Value vs reference semantics](/dsa/learn/swift-value-vs-reference). A struct stores its properties inside itself, so a struct node containing a whole next node, containing a whole next node, would need infinite space. Swift refuses to compile it. A class property only stores a **reference**, a small fixed-size arrow, so `var next: ListNode?` is fine.

References give you two more things that linked lists rely on:

- **Sharing.** Several arrows can lead to the same node. The variable `second` and `head.next` above are two names for one object.
- **Identity.** You can ask whether two references point at the same node with `===`, from [Identity with ===](/dsa/learn/swift-identity). Two different nodes can both hold the value 20; `===` tells them apart.

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

let second = ListNode(20)
let head = ListNode(10, next: second)
let lookalike = ListNode(20)

print(head.next === second)
print(head.next === lookalike)
second.value = 25
print(head.next!.value)
```

```output
true
false
25
```

Changing `second` was visible through `head.next`: it's the same object. Mark the class `final` too, as in [Classes, inheritance and final](/dsa/learn/swift-classes): nothing will subclass a node, and `final` lets Swift call its members directly.

## Inserting after a node you already have

Here's where a linked list shines. Suppose you're holding a reference to the node `10` and want to put `15` straight after it. No sliding is needed. You create the node and change two arrows:

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

func describe(_ head: ListNode?) -> String {
    var parts: [String] = []
    var current = head
    while let node = current {
        parts.append(String(node.value))
        current = node.next
    }
    parts.append("nil")
    return parts.joined(separator: " -> ")
}

let head = ListNode(10, next: ListNode(20, next: ListNode(30)))
print(describe(head))

let fifteen = ListNode(15, next: head.next)   // 15 points at 20
head.next = fifteen                           // 10 points at 15
print(describe(head))

head.next = head.next?.next                   // skip over 15 to remove it
print(describe(head))
```

```output
10 -> 20 -> 30 -> nil
10 -> 15 -> 20 -> 30 -> nil
10 -> 20 -> 30 -> nil
```

Both the insertion and the removal took a fixed number of steps, however long the list. That's O(1). The order of the two insertion lines matters: `fifteen` must grab `head.next` **before** `head.next` is changed, or the rest of the list is lost.

Removing worked by pointing `10` past `15`. Nothing points at the `15` node any more, so ARC frees it, as you saw in [Automatic Reference Counting](/dsa/learn/swift-arc).

<Callout kind="analogy" title="A treasure hunt">
An array is a row of numbered lockers: you can walk straight to locker 500. A linked list is a treasure hunt: each clue tells you where the next one is hidden. Finding clue 500 means following 499 clues. But adding a new clue in the middle only means rewriting the clue before it.
</Callout>

## Finding the ith node costs O(i)

The flip side: there's no arithmetic shortcut to the ith node. You have to walk there from the head:

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

func node(at index: Int, from head: ListNode?) -> ListNode? {
    var current = head
    var steps = 0
    while let node = current, steps < index {
        current = node.next
        steps += 1
    }
    return current
}

let head = ListNode(10, next: ListNode(20, next: ListNode(30)))
print(node(at: 0, from: head)?.value ?? -1)
print(node(at: 2, from: head)?.value ?? -1)
print(node(at: 5, from: head)?.value ?? -1)
```

```output
10
30
-1
```

Reaching index `i` takes `i` steps, so it's O(n) in the worst case. That's why linked lists never offer a cheap `list[i]`, and why "insert after a node" is O(1) only when you **already have** that node. Inserting at position 500 is O(n): 499 steps to get there, then O(1) to link.

## Arrays vs linked lists

| Operation | Array | Singly linked list |
| --- | --- | --- |
| Read element `i` | O(1) | O(i) |
| Insert or remove at the front | O(n) | O(1) |
| Insert or remove after a node you hold | O(n) | O(1) |
| Append at the end | O(1) amortised | O(1) with a tail reference |
| Search for a value | O(n) | O(n) |
| Extra memory | little | a reference per node |

The table makes lists look good, but there's a catch the Big-O hides. An array's elements sit together, so the processor reads them in big efficient chunks from its **cache**, a small fast memory next to the processor. A list's nodes are scattered, and every arrow you follow may be a slow trip to main memory. Each node is also a separate heap allocation with reference counting. In practice, a Swift `Array` beats a linked list for most everyday work, even some that the table says should be a tie.

Linked lists win when you need to:

- insert or remove in the middle at places you already hold, again and again (an LRU cache, which you'll build in this module);
- remove from the front cheaply (a queue);
- splice whole chains together or cut them apart without copying;
- share structure between versions (persistent lists, at the end of this module).

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting to move on.** A `while let node = current` loop that never sets `current = node.next` runs forever.
- **Losing the rest of the list.** Change `node.next` only after you've saved whatever it pointed at, if you still need it.
- **Expecting `==`.** `ListNode` isn't `Equatable`, so `head == other` doesn't compile. Use `===` to ask "same node?" and compare `.value` to ask "same value?".
</Callout>
