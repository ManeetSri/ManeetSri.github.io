## Why it matters

Scroll through a photo feed and the app decodes hundreds of thumbnails. Keeping every one in memory would exhaust it; decoding each one again every time it scrolls back into view would make scrolling stutter. The usual answer is a **cache** with a fixed capacity that, when full, throws out the item used **least recently**: an **LRU cache**. The same policy keeps database pages, web responses and file blocks close at hand. "Design an LRU cache where every operation is O(1)" is also one of the most popular interview questions, because the answer needs two data structures working together: a dictionary and a doubly linked list.

## What least recently used means

The cache holds at most `capacity` entries, each a key with a value. **Reading** an entry or **writing** it counts as using it. When a new key arrives and the cache is full, the entry that has gone longest without being used is evicted.

Here's a cache with capacity 3, listing keys from most to least recently used:

| Operation | Cache afterwards | Notes |
| --- | --- | --- |
| set cat | cat | |
| set dog | dog, cat | |
| set owl | owl, dog, cat | full |
| read cat | cat, owl, dog | reading moves cat to the front |
| set fox | fox, cat, owl | dog was least recent: evicted |
| set owl again | owl, fox, cat | an update moves it to the front; nothing evicted |
| read dog | owl, fox, cat | a miss changes nothing |

Two operations, both of which must be O(1):

- `value(for:)`: return the value if the key is cached, and mark it as the most recent.
- `setValue(_:for:)`: insert or update, mark it as the most recent, and evict the least recent entry if that overfills the cache.

## Why one structure isn't enough

Try the obvious designs and see where each breaks:

| Design | Find a key | Mark as most recent | Find the least recent |
| --- | --- | --- | --- |
| Dictionary alone | O(1) | — | no idea: dictionaries have no order |
| Array of keys, in order of use | O(n) | O(n): remove and reinsert | O(1): the last element |
| Dictionary of "last used" timestamps | O(1) | O(1) | O(n): scan for the oldest |
| Dictionary + doubly linked list | O(1) | O(1) | O(1) |

The dictionary is great at finding things and useless at order. A list is great at order, and a **doubly** linked list can move any node you're holding in O(1), as you saw in [Doubly linked and circular lists](/dsa/learn/ll-doubly-circular). The trick is to let the dictionary hand you the node.

## The design

- A **doubly linked list** holds one node per entry, in order of use: the most recent right after the head sentinel, the least recent right before the tail sentinel.
- A **dictionary** maps each key to its node.

```text
dictionary:  "cat" -> node, "owl" -> node, "dog" -> node

list:  [head] <-> cat <-> owl <-> dog <-> [tail]
                  most recent      least recent
```

Every operation becomes a few O(1) steps:

- **Read**: look the node up in the dictionary, unlink it, relink it at the front.
- **Update**: the same, after changing its value.
- **Insert**: if the cache is full, the least recent node is `tail.previous`: unlink it and remove its key from the dictionary. Then create a node, add it to the dictionary and link it at the front.

To remove the evicted entry from the dictionary, you need its **key**, but all you have is the node at the back of the list. So each node stores its key as well as its value.

## Building it

Here's the cache for an app's thumbnails, with image names as keys and their sizes in kilobytes standing in for the decoded images:

```swift run
final class LRUCache {
    final class Node {
        let key: String
        var value: Int
        var next: Node?
        weak var previous: Node?

        init(key: String, value: Int) {
            self.key = key
            self.value = value
        }
    }

    let capacity: Int
    private var nodes: [String: Node] = [:]
    private let head = Node(key: "", value: 0)    // sentinel on the most recent side
    private let tail = Node(key: "", value: 0)    // sentinel on the least recent side

    init(capacity: Int) {
        precondition(capacity > 0, "An LRU cache needs room for at least one entry")
        self.capacity = capacity
        head.next = tail
        tail.previous = head
    }

    var count: Int { nodes.count }

    private func unlink(_ node: Node) {
        let before = node.previous!
        let after = node.next!
        before.next = after
        after.previous = before
    }

    private func insertAtFront(_ node: Node) {
        let first = head.next!
        node.previous = head
        node.next = first
        head.next = node
        first.previous = node
    }

    func value(for key: String) -> Int? {
        guard let node = nodes[key] else { return nil }
        unlink(node)
        insertAtFront(node)                       // reading counts as using
        return node.value
    }

    func setValue(_ value: Int, for key: String) {
        if let node = nodes[key] {                // update: no eviction needed
            node.value = value
            unlink(node)
            insertAtFront(node)
            return
        }
        if nodes.count == capacity {
            let oldest = tail.previous!
            unlink(oldest)
            nodes[oldest.key] = nil
            print("  evicted \(oldest.key)")
        }
        let node = Node(key: key, value: value)
        nodes[key] = node
        insertAtFront(node)
    }

    var keysByRecency: [String] {
        var keys: [String] = []
        var current = head.next!
        while current !== tail {
            keys.append(current.key)
            current = current.next!
        }
        return keys
    }
}

let thumbnails = LRUCache(capacity: 3)
thumbnails.setValue(120, for: "cat")
thumbnails.setValue(95, for: "dog")
thumbnails.setValue(240, for: "owl")
print(thumbnails.keysByRecency)

print("cat:", thumbnails.value(for: "cat") ?? 0)
print(thumbnails.keysByRecency)

print("set fox")
thumbnails.setValue(180, for: "fox")
print(thumbnails.keysByRecency)

thumbnails.setValue(250, for: "owl")
print(thumbnails.keysByRecency, thumbnails.count)
print("dog:", thumbnails.value(for: "dog") ?? 0, "owl:", thumbnails.value(for: "owl") ?? 0)
```

```output
["owl", "dog", "cat"]
cat: 120
["cat", "owl", "dog"]
set fox
  evicted dog
["fox", "cat", "owl"]
["owl", "fox", "cat"] 3
dog: 0 owl: 250
```

The output follows the table above row by row. Reading `cat` saved it from eviction, so `dog` went instead. Setting `owl` a second time updated it in place and moved it to the front without evicting anything.

### Why each piece is there

- **The update check comes first.** If `setValue` checked "is the cache full?" before "is this key already here?", updating an existing key in a full cache would evict an innocent entry for no reason.
- **Sentinels** mean `unlink` and `insertAtFront` never meet a `nil` neighbour, even when the cache holds one entry or none. Their empty-string keys never reach the dictionary.
- **`previous` is weak.** The dictionary and the `next` chain own the nodes. A strong `previous` would make every pair of neighbours a retain cycle, so when the cache itself is thrown away, for example when the screen that owns it closes, none of its nodes, nor the images they hold, would ever be freed.
- **The node stores its key**, so eviction can remove the dictionary entry knowing only the node.

### How fast is it?

Each operation is one dictionary lookup, insert or removal, plus a constant number of reference changes. Dictionary operations are O(1) on average, as you saw in [Load factor and rehashing](/dsa/learn/hash-load-factor), so `value(for:)` and `setValue(_:for:)` are **O(1) on average**. Memory is O(capacity): one node and one dictionary entry per cached key.

## In an iOS app

A thumbnail loader uses the cache like this. The first request for an image pays for the slow decode; repeats while it stays in the cache are instant:

```swift
func thumbnail(named name: String) -> Thumbnail {
    if let cached = cache.value(for: name) {
        return cached                          // fast path: a cache hit
    }
    let image = decodeThumbnail(named: name)   // slow: disk and decoding
    cache.setValue(image, for: name)
    return image
}
```

Real image caches add a few refinements:

- **Limit by cost, not count.** One panorama can be as big as fifty thumbnails. Store each entry's size, keep a running total, and evict from the back while the total is over the limit.
- **Empty it under memory pressure.** When the system warns that memory is low, throw everything away: the cache can always be refilled from disk.
- **Threads.** If several threads use the cache at once, it needs protecting, with a lock or an actor. That's a Part IX topic; until then, use it from one thread.

Foundation already has `NSCache`, which evicts entries automatically when the system needs memory. It doesn't promise **which** entries go first, though, and its keys and values must be class instances. When you need exact least-recently-used behaviour, or value types as keys, you build it, exactly as above.

<Callout kind="analogy" title="A desk with limited space">
You keep the papers you're using on your desk, and every paper you touch goes on top of the pile. When the desk is full and a new paper arrives, the one at the bottom, untouched for longest, goes back to the filing cabinet. The dictionary is your memory of where each paper is in the pile, so you never have to search.
</Callout>

## Variations you may be asked about

- **LFU, least frequently used**: evict the entry used the fewest times. It needs counts per entry and a way to find the smallest count in O(1), typically a dictionary of lists, one list per count.
- **Time-based expiry**: entries also expire after a fixed time. Each node stores when it was added; expired entries are removed when they're read, or by a periodic sweep from the back.
- **Peek without promoting**: some caches offer a read that doesn't count as a use, for debugging or for statistics.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting the dictionary on eviction.** Unlinking the oldest node but leaving its key in the dictionary leaves a "ghost" entry that still counts towards the capacity and can be read.
- **Evicting on update.** Check whether the key exists before checking whether the cache is full.
- **Not moving on read.** A read is a use. If `value(for:)` doesn't move the node to the front, the cache evicts entries you're actively using.
- **A strong `previous`.** Neighbours keep each other alive, so a discarded cache never frees its images. In an app, every screen that creates and drops a cache leaks everything that was in it.
</Callout>

## Practice

**LRU cache** asks you to build a **generic** version, `Cache<Key: Hashable, Value>`, with `removeValue(for:)` and `keysByRecency` as well. A generic cache can't make sentinel nodes, because there's no "empty" key or value of an unknown type to put in them, so you'll handle an empty list with optional `head` and `tail` references instead. The tests compare it with a simple model over thousands of operations, time it with 50,000 entries, and check that evicted values are really freed.

```cards
- id: lru-structures
  front: "Which two data structures make an LRU cache O(1), and what does each do?"
  back: "A dictionary maps each key to its node, for O(1) lookup. A doubly linked list keeps the nodes in order of use, so moving a node to the front and removing the least recent from the back are O(1)."
- id: lru-node-key
  front: "Why does each node in an LRU cache store its key?"
  back: "On eviction you only have the node at the back of the list, and you need its key to remove its dictionary entry."
- id: lru-update-first
  front: "In `setValue`, why check for an existing key before checking whether the cache is full?"
  back: "Updating an existing key doesn't add an entry. Checking fullness first would evict an innocent entry when updating in a full cache."
- id: lru-read-moves
  front: "Does reading a value change an LRU cache?"
  back: "Yes. A read counts as a use, so the node moves to the most recent end of the list."
```
