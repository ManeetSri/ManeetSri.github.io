## Why it matters

Merging two sorted sequences into one is the heart of merge sort, and it turns up wherever sorted streams meet: combining two time-ordered message feeds, joining sorted query results, merging change logs. With linked lists it's especially neat. You don't copy anything or allocate a buffer: you relink the existing nodes into one chain. It's also the clearest example of the dummy-and-tail pattern from [Dummy and sentinel nodes](/dsa/learn/ll-sentinel).

## The idea

Both lists are sorted, so the smallest value overall is at the front of one of them. Take whichever front node is smaller, attach it to the result, and repeat with what's left. When one list runs out, everything remaining in the other is larger than anything taken so far, and already in order, so attach it in one go.

```text
first:   1 -> 4 -> 6
second:  2 -> 3 -> 7 -> 8

take 1 (first),  2 (second), 3 (second), 4 (first), 6 (first)
first is empty: attach 7 -> 8

result:  1 -> 2 -> 3 -> 4 -> 6 -> 7 -> 8
```

## Merging with a dummy and a tail

Build the result with a dummy head, so attaching the very first node needs no special case, and a `tail` that always points at the last node attached:

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

func makeList(_ values: [Int]) -> ListNode? {
    var head: ListNode? = nil
    for value in values.reversed() {
        head = ListNode(value, next: head)
    }
    return head
}

func describe(_ head: ListNode?) -> String {
    var parts: [String] = []
    var current = head
    while let node = current {
        parts.append(String(node.value))
        current = node.next
    }
    parts.append("nil")
    return parts.joined(separator: " -> ")
}

func merge(_ first: ListNode?, _ second: ListNode?) -> ListNode? {
    let dummy = ListNode(0)
    var tail = dummy
    var a = first
    var b = second
    while let left = a, let right = b {
        if left.value <= right.value {
            tail.next = left
            a = left.next
        } else {
            tail.next = right
            b = right.next
        }
        tail = tail.next!
    }
    tail.next = a ?? b          // whatever is left is already sorted
    return dummy.next
}

print(describe(merge(makeList([1, 4, 6]), makeList([2, 3, 7, 8]))))
print(describe(merge(makeList([5, 5, 9]), makeList([1, 5]))))
print(describe(merge(nil, makeList([2, 4]))))
print(describe(merge(nil, nil)))
```

```output
1 -> 2 -> 3 -> 4 -> 6 -> 7 -> 8 -> nil
1 -> 5 -> 5 -> 5 -> 9 -> nil
2 -> 4 -> nil
nil
```

What to notice:

- `while let left = a, let right = b` runs only while **both** lists have nodes. It unwraps both fronts in one line.
- Each pass attaches one node and moves `tail` onto it. The node keeps its old `next` for now, but that gets overwritten on the next pass, or by the final `tail.next = a ?? b`.
- `a ?? b` picks whichever list still has nodes. If both are empty, it's `nil`, which correctly ends the result.
- No new nodes are made, apart from the dummy. The input lists are used up: afterwards, `first` and `second` are tangled into the result, so don't use them as separate lists any more.

Each node is attached exactly once, so merging lists of lengths n and m takes **O(n + m)** time and **O(1)** extra space.

## Ties and stability

The comparison is `<=`, not `<`. When the fronts are equal, the node from `first` goes first. That makes the merge **stable**: equal values keep the relative order they had, with everything from the first list before equal values from the second.

With plain numbers you can't see the difference. It matters when nodes carry more than their sort key, say messages sorted by timestamp, where two messages sent in the same second should stay in their original order. Merge sort relies on this to be a stable sort.

## Compared with merging arrays

[Merge sorted arrays](/dsa/learn/arrays-merge-sorted) does the same walk with two indices, but it has to write the result somewhere: a new array of n + m elements, or careful shuffling inside an existing one. Lists avoid that entirely, because "putting a node into the result" is just changing one `next` reference. That's a real advantage of linked structures: rearranging is cheap, because nothing ever moves.

## The recursive version

The merge also has a short recursive form. The smaller front node is the head of the answer, and its `next` is the merge of everything else:

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

func makeList(_ values: [Int]) -> ListNode? {
    var head: ListNode? = nil
    for value in values.reversed() {
        head = ListNode(value, next: head)
    }
    return head
}

func describe(_ head: ListNode?) -> String {
    var parts: [String] = []
    var current = head
    while let node = current {
        parts.append(String(node.value))
        current = node.next
    }
    parts.append("nil")
    return parts.joined(separator: " -> ")
}

func mergeRecursively(_ a: ListNode?, _ b: ListNode?) -> ListNode? {
    guard let a else { return b }
    guard let b else { return a }
    if a.value <= b.value {
        a.next = mergeRecursively(a.next, b)
        return a
    } else {
        b.next = mergeRecursively(a, b.next)
        return b
    }
}

print(describe(mergeRecursively(makeList([1, 4, 6]), makeList([2, 3, 7, 8]))))
```

```output
1 -> 2 -> 3 -> 4 -> 6 -> 7 -> 8 -> nil
```

It's lovely to read, but each node attached is one more call on the stack: n + m frames deep. As you saw in [Reverse a list, iteratively and recursively](/dsa/learn/ll-reverse), that crashes for long lists, especially inside tests. Prefer the loop.

## Sorting a whole list with merge sort

Merging is half of sorting a linked list. The other half is splitting it, and you already know how: find the middle with fast and slow pointers, from [Fast and slow pointers](/dsa/learn/ll-fast-slow), and cut the list there. Sort each half the same way, then merge:

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

func makeList(_ values: [Int]) -> ListNode? {
    var head: ListNode? = nil
    for value in values.reversed() {
        head = ListNode(value, next: head)
    }
    return head
}

func describe(_ head: ListNode?) -> String {
    var parts: [String] = []
    var current = head
    while let node = current {
        parts.append(String(node.value))
        current = node.next
    }
    parts.append("nil")
    return parts.joined(separator: " -> ")
}

func merge(_ first: ListNode?, _ second: ListNode?) -> ListNode? {
    let dummy = ListNode(0)
    var tail = dummy
    var a = first
    var b = second
    while let left = a, let right = b {
        if left.value <= right.value {
            tail.next = left
            a = left.next
        } else {
            tail.next = right
            b = right.next
        }
        tail = tail.next!
    }
    tail.next = a ?? b
    return dummy.next
}

func mergeSort(_ head: ListNode?) -> ListNode? {
    guard let head, head.next != nil else {
        return head                          // zero or one node: sorted
    }
    // Find the end of the first half (the first middle), then cut after it
    var slow = head
    var fast = head
    while let next = fast.next?.next {
        slow = slow.next!
        fast = next
    }
    let secondHalf = slow.next
    slow.next = nil
    return merge(mergeSort(head), mergeSort(secondHalf))
}

print(describe(mergeSort(makeList([5, 2, 9, 1, 5, 6, 3]))))
print(describe(mergeSort(makeList([2, 1]))))
print(describe(mergeSort(makeList([]))))
```

```output
1 -> 2 -> 3 -> 5 -> 5 -> 6 -> 9 -> nil
1 -> 2 -> nil
nil
```

Each level of splitting halves the lists, so there are about log₂ n levels, and the merges on each level touch every node once: **O(n log n)** time. The recursion is only log₂ n deep (about 17 levels for 100,000 nodes), so the stack is no worry here. Merge sort is the usual way to sort a linked list, because it never needs to jump to an index. You'll study it properly in M31.

Using the **first** middle matters. With the second middle, a two-node list would split into two nodes and nothing, and recurse on the same two nodes forever.

## Merging many lists

Interviewers often follow up with "now merge k sorted lists". Two good answers build on this lesson. Merge the lists in pairs, then merge the results in pairs, and so on, like merge sort's levels: O(N log k) for N nodes in total. Or keep the k front nodes in a priority queue and repeatedly take the smallest, which you'll be able to build in Part V.

<Callout kind="gotcha" title="Common mistakes">
- **Forgetting to move the tail.** Without `tail = tail.next!`, every node is attached to the same place and only the last one survives.
- **Walking one list to the end.** You don't need to: when either list is empty, attach the other in one step.
- **Using `<` on ties.** The result is still sorted, but no longer stable, and the tests for this module's problem expect `first` to win ties.
- **Splitting at the wrong middle in merge sort.** Use the first middle, or two-node lists never get smaller.
</Callout>
