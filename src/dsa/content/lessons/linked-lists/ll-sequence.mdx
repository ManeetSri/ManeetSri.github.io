## Why it matters

Your `LinkedList` works, but it feels foreign: you can't loop over it with `for-in`, and you can't `map` or `filter` it. Every built-in collection can, because they all conform to `Sequence`. Add one small iterator and your list joins them, picking up dozens of methods for free. You'll do the same for trees in Part V, so that `for value in tree` visits every node.

## What Sequence asks for

You met the two protocols in [Sequence and IteratorProtocol](/dsa/learn/swift-sequence-iterator):

- A **sequence** hands out iterators through `makeIterator()`.
- An **iterator** has a `mutating func next() -> Element?` that returns the next element, or `nil` when there are no more.

A `for-in` loop calls `makeIterator()` once, then `next()` until it gets `nil`. So the only question is: what does an iterator over a linked list need to remember? Just **where it's up to**: one node reference. Each call to `next()` returns that node's value and steps along to `node.next`.

## An iterator over nodes

The iterator goes inside the list, next to `Node`, so it can use `Node` and `Element`:

```swift
struct Iterator: IteratorProtocol {
    var current: Node?

    mutating func next() -> Element? {
        guard let node = current else {
            return nil             // walked off the end
        }
        current = node.next        // step along for next time
        return node.value
    }
}

func makeIterator() -> Iterator {
    Iterator(current: head)
}
```

It's the same `while let` walk you've written all module, broken into one step per call. `makeIterator()` starts a **fresh** iterator at the head each time, so every loop begins at the start, and two loops can run over the same list independently.

## Everything a Sequence gets for free

Declare the conformance with `: Sequence` and the rest of the standard library opens up. Here's a cut-down list with just `append`, plus the iterator:

```swift run
final class LinkedList<Element>: Sequence {
    final class Node {
        var value: Element
        var next: Node?

        init(_ value: Element, next: Node? = nil) {
            self.value = value
            self.next = next
        }
    }

    private var head: Node?
    private var tail: Node?

    func append(_ value: Element) {
        let node = Node(value)
        if let tail {
            tail.next = node
        } else {
            head = node
        }
        tail = node
    }

    struct Iterator: IteratorProtocol {
        var current: Node?

        mutating func next() -> Element? {
            guard let node = current else {
                return nil
            }
            current = node.next
            return node.value
        }
    }

    func makeIterator() -> Iterator {
        Iterator(current: head)
    }
}

let scores = LinkedList<Int>()
for score in [72, 95, 58, 88] {
    scores.append(score)
}

for score in scores {
    print(score, terminator: " ")
}
print()
print(Array(scores))
print(scores.map { $0 + 5 })
print(scores.filter { $0 >= 70 })
print(scores.reduce(0, +), scores.max() ?? 0, scores.contains(58))
for (place, score) in scores.sorted(by: >).enumerated() where place < 2 {
    print(place + 1, score)
}
```

```output
72 95 58 88
[72, 95, 58, 88]
[77, 100, 63, 93]
[72, 95, 88]
313 95 true
1 95
2 88
```

You wrote one method and one tiny struct. `map`, `filter`, `reduce`, `max`, `contains`, `sorted` and `enumerated` all came from the `Sequence` protocol extension. Notice that `map`, `filter` and `sorted` return **arrays**, not linked lists: that's how `Sequence` methods work for every type.

The list's `description` gets shorter too, now that `map` works on it:

```swift
var description: String {
    (map { "\($0)" } + ["nil"]).joined(separator: " -> ")
}
```

## Writing a list as a literal

One more protocol makes the list as pleasant to create as an array. With `ExpressibleByArrayLiteral`, from [ExpressibleByArrayLiteral](/dsa/learn/swift-array-literal), you can write `let list: LinkedList = [1, 2, 3]`:

```swift run
final class LinkedList<Element>: Sequence, ExpressibleByArrayLiteral {
    final class Node {
        var value: Element
        var next: Node?

        init(_ value: Element, next: Node? = nil) {
            self.value = value
            self.next = next
        }
    }

    private var head: Node?
    private var tail: Node?

    init() {}

    convenience init(arrayLiteral elements: Element...) {
        self.init()
        for element in elements {
            append(element)
        }
    }

    func append(_ value: Element) {
        let node = Node(value)
        if let tail {
            tail.next = node
        } else {
            head = node
        }
        tail = node
    }

    struct Iterator: IteratorProtocol {
        var current: Node?

        mutating func next() -> Element? {
            guard let node = current else {
                return nil
            }
            current = node.next
            return node.value
        }
    }

    func makeIterator() -> Iterator {
        Iterator(current: head)
    }
}

extension LinkedList: CustomStringConvertible {
    var description: String {
        (map { "\($0)" } + ["nil"]).joined(separator: " -> ")
    }
}

let primes: LinkedList = [2, 3, 5, 7]
let words: LinkedList = ["linked", "lists", "rock"]
print(primes)
print(words)
print(words.map { $0.count })
```

```output
2 -> 3 -> 5 -> 7 -> nil
linked -> lists -> rock -> nil
[6, 5, 4]
```

Swift infers `LinkedList<Int>` and `LinkedList<String>` from the literals. The initialiser is a `convenience init` that calls the plain `init()` and then appends. A protocol's initialiser requirement normally has to be marked `required` in a class, so that subclasses inherit it too, but a `final` class can't have subclasses, so it doesn't need to be.

## Why Sequence and not Collection?

`Array` goes further than `Sequence`: it's a `Collection`, with indices and a subscript. You could give a linked list a subscript, `list[3]`, but it would have to walk three nodes to get there. Swift's documentation expects a `Collection` subscript to be O(1), and code written for collections relies on that: a loop that reads `list[i]` for every `i` would quietly become O(n²).

So a linked list stays a `Sequence`: it promises a walk from front to back, which it can do well, and nothing it can't. (It's possible to make a list a `Collection` whose indices wrap node references, which keeps the subscript O(1), but that's more machinery than this module needs.)

## Walking loose nodes with sequence(first:next:)

Many problems hand you a bare head node rather than a `LinkedList`. You can still get `Sequence` methods on it with the standard library's `sequence(first:next:)`, from M10. Give it a first node and a closure that finds the next one; it stops when the closure returns `nil`:

```swift run
final class ListNode {
    var value: Int
    var next: ListNode?

    init(_ value: Int, next: ListNode? = nil) {
        self.value = value
        self.next = next
    }
}

let head = ListNode(4, next: ListNode(8, next: ListNode(15, next: ListNode(16))))

let nodes = sequence(first: head) { $0.next }
print(nodes.map { $0.value })
print(nodes.count(where: { $0.value.isMultiple(of: 2) }))

var last = head
for node in nodes {
    last = node
}
print("last node holds", last.value)
```

```output
[4, 8, 15, 16]
3
last node holds 16
```

This is a sequence of **nodes**, not values, which is handy when you need the node itself: the last one, or the one before a target. `count(where:)` counts the elements that pass a test.

<Callout kind="gotcha" title="Swift gotcha: changing a list while you loop over it">
An `Array` loop walks a copy, so appending inside the loop doesn't change what the loop visits. Your class-based list has no copy: the iterator follows live `next` references, so nodes appended during the loop **are** visited.

```swift
let list: LinkedList = [1, 2, 3]
for value in list where value < 3 {
    list.append(value + 10)
}
print(list)   // 1 -> 2 -> 3 -> 11 -> 12 -> nil
```

The loop visited 11 and 12 too (they didn't pass `value < 3`, so nothing more was added). Without that condition, the loop would append forever. The value-type version in [Copy-on-write and persistent lists](/dsa/learn/ll-persistent) behaves like an array instead.
</Callout>
