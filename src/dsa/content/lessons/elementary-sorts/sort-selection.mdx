## Why it matters

Selection sort is how most people sort a hand of cards laid out on a table: find the smallest, move it to the front, repeat. It's never adaptive and it's always O(n²), yet it has one property none of the other simple sorts share: it makes **at most n − 1 swaps**. When writing an element is much more expensive than reading one, that matters. Its first few passes also hand you the k smallest values, finished and in order, which is a useful trick on its own. And it's the standard example of a sort that **isn't stable**.

## Select the smallest, swap it to the front

Split the array into a sorted part on the left, empty at first, and an unsorted part on the right. Each pass:

1. Scan the unsorted part for its **smallest** value.
2. Swap it with the first element of the unsorted part.
3. The sorted part has grown by one.

```swift run
func selectionSort(_ items: inout [Int]) {
    guard items.count > 1 else { return }
    for i in 0..<(items.count - 1) {
        var smallest = i
        for j in (i + 1)..<items.count where items[j] < items[smallest] {
            smallest = j
        }
        if smallest != i {
            items.swapAt(i, smallest)
        }
        print("pass \(i + 1): smallest is \(items[i]) ->", items)
    }
}

var numbers = [29, 10, 14, 37, 13, 5]
selectionSort(&numbers)
```

```output
pass 1: smallest is 5 -> [5, 10, 14, 37, 13, 29]
pass 2: smallest is 10 -> [5, 10, 14, 37, 13, 29]
pass 3: smallest is 13 -> [5, 10, 13, 37, 14, 29]
pass 4: smallest is 14 -> [5, 10, 13, 14, 37, 29]
pass 5: smallest is 29 -> [5, 10, 13, 14, 29, 37]
```

What to notice:

- In pass 2, 10 was already in place, so there was nothing to swap. The `if smallest != i` skips that pointless swap.
- After pass i, positions 0 to i − 1 hold the i smallest values in order, and they're **final**: nothing will ever move them again. That's selection sort's invariant.
- Only n − 1 passes: when everything but the last element is in place, the last one is the largest, so it's in place too.
- `for j in … where …` runs the body only for the `j` values that pass the condition. Here the body runs whenever a new smallest value turns up.

## Always n(n − 1)/2 comparisons, at most n − 1 swaps

Pass 1 compares the first element with the other n − 1. Pass 2 compares n − 2, and so on down to 1. That's (n − 1) + (n − 2) + … + 1 = n(n − 1)/2 comparisons, **whatever the input looks like**. Each pass makes at most one swap. Count both:

```swift run
func selectionCounts(_ input: [Int]) -> (comparisons: Int, swaps: Int) {
    var items = input
    var comparisons = 0
    var swaps = 0
    guard items.count > 1 else { return (0, 0) }
    for i in 0..<(items.count - 1) {
        var smallest = i
        for j in (i + 1)..<items.count {
            comparisons += 1
            if items[j] < items[smallest] { smallest = j }
        }
        if smallest != i {
            items.swapAt(i, smallest)
            swaps += 1
        }
    }
    return (comparisons, swaps)
}

let n = 100
print("sorted:", selectionCounts(Array(0..<n)))
print("reversed:", selectionCounts(Array((0..<n).reversed())))
print("mixed:", selectionCounts((0..<n).map { ($0 * 37) % n }))
```

```output
sorted: (comparisons: 4950, swaps: 0)
reversed: (comparisons: 4950, swaps: 50)
mixed: (comparisons: 4950, swaps: 88)
```

Three very different inputs, the same 4,950 comparisons. Selection sort is **not adaptive**: even a sorted array costs O(n²), because the only way to be sure a value is the smallest is to look at every remaining value. Compare bubble sort, which made 4,950 swaps on the reversed array. Selection sort made 50: each swap put two values in place at once.

### When writes are expensive

Why would anyone accept O(n²) comparisons to save swaps? Because sometimes a write costs far more than a read:

- **Flash memory** wears out a little with every write, and writing is much slower than reading. Small embedded devices sometimes sort in flash.
- **Physical objects.** Reading a crate's label is cheap; moving the crate with a forklift isn't.
- **Large values.** Every swap of a big struct copies all its bytes, twice. (A common fix is to sort an array of indexes instead and leave the big values where they are.)

With at most n − 1 swaps, selection sort does about the fewest writes any sort can.

## Not stable

Selection sort's swap is a long-distance jump, and it can carry a value past others equal to it. Sort three cards by rank:

```swift run
func selectionSort(_ cards: inout [(rank: Int, name: String)]) {
    guard cards.count > 1 else { return }
    for i in 0..<(cards.count - 1) {
        var smallest = i
        for j in (i + 1)..<cards.count where cards[j].rank < cards[smallest].rank {
            smallest = j
        }
        if smallest != i {
            cards.swapAt(i, smallest)
        }
    }
}

var hand = [(rank: 5, name: "5♥"), (rank: 5, name: "5♠"), (rank: 2, name: "2♦")]
selectionSort(&hand)
print(hand.map(\.name))
```

```output
["2♦", "5♠", "5♥"]
```

The ranks are sorted, but 5♥ came before 5♠ and now comes after it. The first pass found 2♦ and swapped it with 5♥, at index 0, sending 5♥ to the back, straight past 5♠. Nothing in the algorithm ever puts it back.

You can make selection sort stable by **shifting** instead of swapping: take the smallest value out and slide everything between one place right to make room. But then each pass can do O(n) writes, and the one advantage of selection sort is gone.

## The first k passes: the k smallest, in order

Because the sorted prefix is final after every pass, you can stop early. After k passes, the first k positions hold the k smallest values, sorted. When k is tiny, that's O(n · k), much better than sorting everything:

```swift run
var lapTimes = [58, 41, 73, 39, 66, 45, 80, 52]
let k = 3
for i in 0..<min(k, lapTimes.count) {
    var smallest = i
    for j in (i + 1)..<lapTimes.count where lapTimes[j] < lapTimes[smallest] {
        smallest = j
    }
    lapTimes.swapAt(i, smallest)
}
print("podium:", lapTimes[..<k])
```

```output
podium: [39, 41, 45]
```

Insertion sort, next lesson, can't do this: its sorted prefix is sorted but not final, because a smaller value might still arrive from the right. (For large k, a heap does better still; you'll meet heaps in M39.) `swapAt(i, i)` is allowed and does nothing, so this short version skips the `if`.

## The properties

| Property | Selection sort |
| --- | --- |
| Comparisons | always n(n − 1)/2: O(n²) best, average and worst |
| Swaps | at most n − 1 |
| Extra memory | O(1): in-place |
| Stable | no: a swap can jump a value over an equal one |
| Adaptive | no |
| Online | no: it needs every element to find the smallest |

<Callout kind="gotcha" title="Swift gotcha: closed ranges can't be empty">
`(i + 1)..<items.count` is fine on the last pass, when `i + 1 == items.count`: a half-open range with equal ends is simply empty. The closed range `(i + 1)...(items.count - 1)` says the same thing in a different way, but there its upper bound would be one less than its lower bound, and Swift stops the program with `Range requires lowerBound <= upperBound`. Prefer `..<` for index ranges: it can always be empty.
</Callout>
