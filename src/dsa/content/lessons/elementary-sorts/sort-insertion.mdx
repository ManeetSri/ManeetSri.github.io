## Why it matters

Insertion sort is the simple sort that real software actually uses. Swift's own `sort()`, Python's and Java's Timsort, and C++'s `std::sort` all hand short stretches of data to insertion sort, because for a dozen or so elements nothing beats it. It's also the sort that shines on **nearly sorted** data, which is everywhere: a list that was sorted yesterday, timestamps that arrive slightly out of order, a leaderboard where a few scores changed. It's stable, in-place, adaptive and online, all at once. This is the most important lesson of the module.

## Sorting a hand of cards

Picture picking up playing cards one at a time. The cards in your hand are always in order. Each new card is slotted into place: you slide it in from the right, past every card bigger than it, and drop it where it fits.

That's the whole algorithm. Keep a **sorted prefix** at the front of the array, starting with just the first element. Then for each next element, the **key**:

1. Take the key out, leaving a gap where it was.
2. While the value just left of the gap is **bigger** than the key, shift that value one place right. The gap moves one place left.
3. Drop the key into the gap.

```swift run
func insertionSort(_ items: inout [Int]) {
    guard items.count > 1 else { return }
    for i in 1..<items.count {
        let key = items[i]
        var gap = i
        while gap > 0 && items[gap - 1] > key {
            items[gap] = items[gap - 1]       // shift the bigger value one place right
            gap -= 1
        }
        items[gap] = key                      // drop the key into the gap
        print("insert \(key) ->", items)
    }
}

var numbers = [12, 11, 13, 5, 6, 7]
insertionSort(&numbers)
```

```output
insert 11 -> [11, 12, 13, 5, 6, 7]
insert 13 -> [11, 12, 13, 5, 6, 7]
insert 5 -> [5, 11, 12, 13, 6, 7]
insert 6 -> [5, 6, 11, 12, 13, 7]
insert 7 -> [5, 6, 7, 11, 12, 13]
```

What to notice:

- Inserting 13 cost a single comparison: 12 isn't bigger than 13, so the loop stopped at once and nothing moved.
- Inserting 5 shifted 13, 12 and 11 one place each, and the gap reached the front.
- The prefix is always **sorted**, but unlike selection sort's prefix it isn't **final**: 5 arrived late and pushed everything along.

## Shifting, not swapping

You could also write the inner loop as a series of swaps: swap the key with its left neighbour while the neighbour is bigger. That's correct, but each swap writes **two** elements, and the key is written over and over on its way left. Shifting writes each bigger value once and the key once, at the end. On a reversed array of 100 values, that's 5,049 writes against 9,900. The comparisons are identical; the shifting version just does about half the work.

## The cost: O(n + inversions)

Recall from [bubble sort](/dsa/learn/sort-bubble) that an **inversion** is a pair of values in the wrong order. Each shift moves a bigger value past the key, fixing exactly one inversion, and nothing else ever moves. So:

- **Shifts = inversions**, exactly.
- **Comparisons ≤ shifts + (n − 1)**: each key's loop ends with at most one comparison that doesn't shift.

So insertion sort costs **O(n + d)**, where d is the number of inversions. Count it for 1,000 values:

```swift run
func insertionCounts(_ input: [Int]) -> (comparisons: Int, shifts: Int) {
    var items = input
    var comparisons = 0
    var shifts = 0
    guard items.count > 1 else { return (0, 0) }
    for i in 1..<items.count {
        let key = items[i]
        var gap = i
        while gap > 0 {
            comparisons += 1
            guard items[gap - 1] > key else { break }
            items[gap] = items[gap - 1]
            shifts += 1
            gap -= 1
        }
        items[gap] = key
    }
    return (comparisons, shifts)
}

let n = 1_000
var nearly = Array(0..<n)
for i in stride(from: 0, to: n - 1, by: 10) {
    nearly.swapAt(i, i + 1)                   // 100 neighbouring pairs swapped
}
print("sorted:", insertionCounts(Array(0..<n)))
print("nearly sorted:", insertionCounts(nearly))
print("mixed:", insertionCounts((0..<n).map { ($0 * 7_919) % n }))
print("reversed:", insertionCounts(Array((0..<n).reversed())))
```

```output
sorted: (comparisons: 999, shifts: 0)
nearly sorted: (comparisons: 1098, shifts: 100)
mixed: (comparisons: 251100, shifts: 250101)
reversed: (comparisons: 499500, shifts: 499500)
```

- **Sorted:** one comparison per key, nothing moves. **Best case O(n).**
- **Nearly sorted:** 100 inversions, 100 shifts. Barely more than sorted.
- **Mixed:** about n²/4 inversions, the average for a shuffled array. **Average case O(n²).**
- **Reversed:** every pair is inverted. **Worst case O(n²)**, n(n − 1)/2 shifts.

### Nearly sorted means fast

Suppose every value is at most k places from where it belongs. A key can then only be shifted past bigger values that started less than 2k places to its left, so each key shifts fewer than 2k times. The whole sort is **O(n · k)**. For a fixed k like 3 or 10, that's linear. No other simple sort can say that: selection sort would still make n(n − 1)/2 comparisons, and bubble sort is slowed by any turtle that has to crawl left.

## Online: sorting as data arrives

Insertion sort never looks to the right of the key. So it doesn't need the data in advance: append each new value to the end of a sorted array and insert it from there. Imagine messages arriving over a network, tagged with the time they were sent, mostly but not quite in order:

```swift run
var received: [Int] = []
var shifts = 0
for timestamp in [100, 102, 101, 105, 103, 104, 108, 107] {
    received.append(timestamp)
    var gap = received.count - 1
    while gap > 0 && received[gap - 1] > timestamp {
        received[gap] = received[gap - 1]
        gap -= 1
        shifts += 1
    }
    received[gap] = timestamp
}
print(received, "shifts:", shifts)
```

```output
[100, 101, 102, 103, 104, 105, 107, 108] shifts: 4
```

Each late message stepped back only a place or two. A chat app showing messages in the order they were sent faces exactly this, and insertion from the end keeps it cheap.

## Stable, in-place, adaptive and online

| Property | Insertion sort |
| --- | --- |
| Comparisons | O(n) best (sorted), O(n²) average and worst |
| Writes | O(n + d), where d is the number of inversions |
| Extra memory | O(1): in-place |
| Stable | yes: the shifting stops at the first value that isn't **strictly** bigger |
| Adaptive | yes: O(n · k) when every value is at most k places out |
| Online | yes |

Stability comes from `items[gap - 1] > key`. When the key meets an equal value, the loop stops, so the key lands **after** it, which is where it started relative to that value. With `>=`, equal values would be shifted past, and the sort would no longer be stable.

## Inside real-world sorts

Merge sort and quick sort, in M31, are O(n log n), but each step carries overhead: recursive calls, index arithmetic, sometimes a scratch buffer. For a handful of elements that overhead costs more than insertion sort's few shifts. So the fast sorts stop splitting once a piece is small, roughly 16 to 64 elements, and finish it with insertion sort:

- **Introsort**, behind C++'s `std::sort`, is a quick sort that finishes small partitions with insertion sort.
- **Timsort**, in Python and Java, finds stretches that are already in order (called **runs**) and merges them. Short runs are first extended with insertion sort. Swift's own sort works in a similar way. You'll see these ideas in [Shell sort and Timsort ideas](/dsa/learn/sort-shell-timsort) and [How Swift sorts](/dsa/learn/sort-swift-sort).

## Binary insertion sort

The sorted prefix is sorted, so why scan it one value at a time? [Binary search](/dsa/learn/bs-bounds) can find where the key belongs in O(log i) comparisons. To stay stable, find the **upper bound**: the first position holding a value strictly bigger than the key, so the key goes after any equal values.

```swift run
func binaryInsertionSort(_ items: inout [Int]) -> (comparisons: Int, moves: Int) {
    var comparisons = 0
    var moves = 0
    guard items.count > 1 else { return (0, 0) }
    for i in 1..<items.count {
        let key = items[i]
        // The first position in items[0..<i] holding a value bigger than the key
        var low = 0
        var high = i
        while low < high {
            let mid = (low + high) / 2
            comparisons += 1
            if items[mid] > key { high = mid } else { low = mid + 1 }
        }
        // Everything from there to i still has to shift one place right
        var gap = i
        while gap > low {
            items[gap] = items[gap - 1]
            gap -= 1
            moves += 1
        }
        items[low] = key
    }
    return (comparisons, moves)
}

var reversed = Array((0..<1_000).reversed())
print(binaryInsertionSort(&reversed))
print(reversed[..<5])
```

```output
(comparisons: 8977, moves: 499500)
[0, 1, 2, 3, 4]
```

Comparisons fell from 499,500 to under 9,000, which is O(n log n). But the moves didn't change at all: finding the spot faster doesn't make room for the key any faster. Binary insertion sort is still **O(n²)**. It pays off when comparing is much more expensive than moving, for example sorting long strings that share long prefixes, and Java's Timsort uses it for exactly that reason.

<Callout kind="gotcha" title="Swift gotcha: check the index before you use it">
The loop condition `gap > 0 && items[gap - 1] > key` must check `gap > 0` **first**. `&&` stops as soon as its left side is false, so `items[-1]` is never read. Swap the two sides and the sort crashes with "Index out of range" the moment a key needs to reach the front.

Also keep the `guard`: for an empty array, `1..<items.count` is `1..<0`, and Swift stops with `Range requires lowerBound <= upperBound`.
</Callout>
