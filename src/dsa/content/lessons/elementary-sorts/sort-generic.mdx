## Why it matters

So far every sort in this module has sorted `[Int]`. Real code sorts strings, dates, structs by any field you like, and sometimes only part of an array. You don't want a copy of insertion sort for each. The standard library's own `sort(by:)` is written once, as an extension on `MutableCollection where Self: RandomAccessCollection`, and it works on arrays, slices and any collection of yours that conforms. This lesson builds insertion sort up to that same shape, one step at a time, using the generics from [Generic functions and constraints](/dsa/learn/swift-generic-functions).

## Step 1: any Comparable element

The only thing insertion sort does with elements is compare them with `>`. So replace `Int` with a type parameter `T` and require `T: Comparable`, which supplies `<`, `>`, `<=` and `>=`, as [Comparable](/dsa/learn/swift-standard-protocols) showed:

```swift run
func insertionSort<T: Comparable>(_ items: inout [T]) {
    guard items.count > 1 else { return }
    for i in 1..<items.count {
        let key = items[i]
        var gap = i
        while gap > 0 && items[gap - 1] > key {
            items[gap] = items[gap - 1]
            gap -= 1
        }
        items[gap] = key
    }
}

var numbers = [42, 7, 19, 3]
var words = ["pear", "apple", "fig"]
insertionSort(&numbers)
insertionSort(&words)
print(numbers)
print(words)
```

```output
[3, 7, 19, 42]
["apple", "fig", "pear"]
```

The body didn't change at all. Only the signature did.

## Step 2: any order, with a closure

`Comparable` gives each type one natural order. To sort songs by play count, or numbers from largest to smallest, the caller has to say what "comes first" means. That's what `sorted(by:)` does: it takes a closure, conventionally named `areInIncreasingOrder`, that returns `true` when its first argument must come **before** its second.

```swift run
func insertionSort<T>(_ items: inout [T], by areInIncreasingOrder: (T, T) -> Bool) {
    guard items.count > 1 else { return }
    for i in 1..<items.count {
        let key = items[i]
        var gap = i
        while gap > 0 && areInIncreasingOrder(key, items[gap - 1]) {
            items[gap] = items[gap - 1]
            gap -= 1
        }
        items[gap] = key
    }
}

func insertionSort<T: Comparable>(_ items: inout [T]) {
    insertionSort(&items, by: <)
}

struct Song {
    let title: String
    let plays: Int
}

var songs = [
    Song(title: "Blue", plays: 40),
    Song(title: "Rain", plays: 95),
    Song(title: "Dawn", plays: 40),
]
insertionSort(&songs) { $0.plays > $1.plays }        // most played first
print(songs.map(\.title))

var scores = [3, 9, 1]
insertionSort(&scores)
print(scores)
```

```output
["Rain", "Blue", "Dawn"]
[1, 3, 9]
```

What to notice:

- `items[gap - 1] > key` became `areInIncreasingOrder(key, items[gap - 1])`: "must the key come before its left neighbour?" The **order of the arguments** matters. Swap them and the sort runs backwards.
- `T` has no constraint any more: the closure does all the comparing, so any type works, even one that isn't `Comparable`, like `Song`.
- The `Comparable` version is now one line that passes `<`. Functions like `<` can be passed wherever a closure of the right type is expected.
- Blue and Dawn both have 40 plays and stayed in their original order. The closure is strict (`>`, not `>=`), so the sort is still stable.
- The closure parameter isn't `@escaping`: the sort only calls it while it runs, as in [Escaping and non-escaping closures](/dsa/learn/swift-escaping).

## Step 3: any mutable, random-access collection

The functions above only take `[T]`. Try to sort part of an array with `insertionSort(&numbers[2..<5])` and it won't compile, because `numbers[2..<5]` is an `ArraySlice<Int>`, not an `[Int]`. The same goes for `ContiguousArray`, your `DynamicArray` from M18 and DSAKit's `Deque`.

The fix is to stop asking for a particular type and ask for the abilities the algorithm needs, as protocols. Write the sort as an extension, the way the standard library does:

```swift
extension MutableCollection where Self: RandomAccessCollection {
    mutating func insertionSort(by areInIncreasingOrder: (Element, Element) -> Bool) {
        guard !isEmpty else { return }
        var next = index(after: startIndex)          // everything before `next` is sorted
        while next != endIndex {
            let key = self[next]
            var gap = next
            while gap != startIndex {
                let before = index(before: gap)
                guard areInIncreasingOrder(key, self[before]) else { break }
                self[gap] = self[before]              // shift one place right
                gap = before
            }
            self[gap] = key
            formIndex(after: &next)                   // next = index(after: next)
        }
    }
}
```

Here's what each piece buys:

| Requirement | What the sort gets from it |
| --- | --- |
| `MutableCollection` | a subscript you can assign through, `self[gap] = …`, and `swapAt` |
| `RandomAccessCollection` | `index(before:)`, plus a promise that `count` and jumping any distance are O(1) |
| `Element` | the element type, whatever the collection holds |
| `mutating` | the method changes `self`, so it needs a `var` |

Strictly, insertion sort only ever steps one place at a time, so `BidirectionalCollection` (which provides `index(before:)`) would be enough. Asking for `RandomAccessCollection` matches the standard library's `sort`, and keeps any later jump, such as binary insertion sort's binary search, O(1).

### Index arithmetic that works everywhere

The extension never writes `0`, `1`, `i + 1` or `count - 1`. Generic code can't, for two reasons:

- A collection's `Index` type doesn't have to be `Int`. A `String`'s indexes aren't, as you saw in [String.Index](/dsa/learn/swift-string-index).
- Even when it is `Int`, the first index needn't be 0. A slice **keeps the indexes of the array it came from**, the pitfall from [ArraySlice and its index pitfalls](/dsa/learn/swift-array-slices).

So the code moves with `startIndex`, `endIndex`, `index(after:)` and `index(before:)`, and stops when an index **equals** `endIndex` or `startIndex` rather than comparing it with a number. Now it sorts slices in place, and other collections too:

```swift run
extension MutableCollection where Self: RandomAccessCollection {
    mutating func insertionSort(by areInIncreasingOrder: (Element, Element) -> Bool) {
        guard !isEmpty else { return }
        var next = index(after: startIndex)
        while next != endIndex {
            let key = self[next]
            var gap = next
            while gap != startIndex {
                let before = index(before: gap)
                guard areInIncreasingOrder(key, self[before]) else { break }
                self[gap] = self[before]
                gap = before
            }
            self[gap] = key
            formIndex(after: &next)
        }
    }
}

extension MutableCollection where Self: RandomAccessCollection, Element: Comparable {
    mutating func insertionSort() {
        insertionSort(by: <)
    }
}

var numbers = [9, 8, 7, 6, 5, 4, 3]
numbers[2..<5].insertionSort()                   // sorts indexes 2, 3 and 4 in place
print(numbers)

var tail = numbers[4...]                         // a separate slice: indexes 4, 5 and 6
tail.insertionSort()
print(tail, tail.startIndex, tail[4])
print(numbers)

var letters: ContiguousArray = ["c", "a", "b"]
letters.insertionSort(by: >)
print(letters)
```

```output
[9, 8, 5, 6, 7, 4, 3]
[3, 4, 7] 4 3
[9, 8, 5, 6, 7, 4, 3]
["c", "b", "a"]
```

- `numbers[2..<5].insertionSort()` sorted three elements **inside** `numbers` and left the rest alone. Calling a mutating method on a slice of a `var` array writes straight back into the array.
- `tail` is a separate value: sorting it didn't change `numbers`. Its first index is still 4, so `tail[4]` is its first element, 3.
- The second extension adds a no-argument version only when `Element: Comparable`, exactly as the standard library pairs `sort()` with `sort(by:)`.

Here's what goes wrong if you write the sort array-style, with `for i in 1..<count` and `self[gap - 1]`, constrained to `Index == Int` so that it compiles. On `tail`, whose indexes are 4 to 6, it reads `self[1]`:

```text title="What you'll see"
Fatal error: Index out of bounds
```

That's what Swift reports when a slice is read outside its own indexes. Worse than a crash, a version that happened to stay in bounds would quietly sort the wrong elements.

## DSAKit's elementary sorts

Your package now has all three sorts written this way, in `dsa-swift/Sources/DSAKit/ElementarySorts.swift`: `bubbleSort(by:)`, `selectionSort(by:)` and `insertionSort(by:)` on any `MutableCollection` that's a `RandomAccessCollection`, each with a no-argument version for `Comparable` elements. Each doc comment states whether the sort is stable and what it costs.

```swift
import DSAKit

var scores = [70, 95, 82, 95, 60]
scores.insertionSort(by: >)            // [95, 95, 82, 70, 60]
var middle = scores[1...3]             // [95, 82, 70], indexes 1 to 3
middle.selectionSort()                 // [70, 82, 95], still indexes 1 to 3
scores[3...].bubbleSort()              // sorts indexes 3 and 4 inside scores: [95, 95, 82, 60, 70]
```

Their tests run each sort on empty and single-element collections, duplicates, sorted and reversed input, slices that don't start at 0, `ContiguousArray`, DSAKit's own `Deque` and `DynamicArray`, records checked for stability, and hundreds of seeded random arrays compared with the standard library's `sorted()`.

<Callout kind="gotcha" title="Swift gotcha: don't name it sort">
If you write your own `mutating func sort(by:)` in an extension on `MutableCollection where Self: RandomAccessCollection`, Swift doesn't complain. It quietly prefers **your** method over the standard library's for every array in that module, so `numbers.sort(by: <)` everywhere now runs your code. Give your sorts distinct names, like `insertionSort`, as DSAKit does.
</Callout>
