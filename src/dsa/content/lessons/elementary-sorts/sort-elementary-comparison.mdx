## Why it matters

You now have three O(n²) sorts. On paper they look the same; in practice they behave very differently, and each one is the right answer to a different question. This lesson puts them side by side, counts their work on the same inputs, and turns that into a short guide for choosing. The same habit, counting instead of guessing, will serve you for every algorithm that follows.

## Count, don't time

Timing code is noisy: it depends on the machine, on what else is running, and on whether you built for debug or release, as [Debug vs release builds](/dsa/learn/swift-release-builds) showed. Counting is exact and repeatable. Two counts describe a sort well:

- **comparisons**: how many times it asks whether two elements are in order;
- **writes**: how many times it stores an element into the array. A swap is two writes; a shift is one.

Here are all three sorts with counters, run on the same 100 values in three orders. The "shuffled" input is a fixed mix-up, `(i * 37) % 100`, so every run gives the same numbers:

```swift run
struct Counts {
    var comparisons = 0
    var writes = 0
}

func bubble(_ input: [Int]) -> Counts {
    var items = input
    var counts = Counts()
    guard items.count > 1 else { return counts }
    for pass in 0..<(items.count - 1) {
        var swapped = false
        for j in 0..<(items.count - 1 - pass) {
            counts.comparisons += 1
            if items[j] > items[j + 1] {
                items.swapAt(j, j + 1)
                counts.writes += 2
                swapped = true
            }
        }
        if !swapped { break }
    }
    return counts
}

func selection(_ input: [Int]) -> Counts {
    var items = input
    var counts = Counts()
    guard items.count > 1 else { return counts }
    for i in 0..<(items.count - 1) {
        var smallest = i
        for j in (i + 1)..<items.count {
            counts.comparisons += 1
            if items[j] < items[smallest] { smallest = j }
        }
        if smallest != i {
            items.swapAt(i, smallest)
            counts.writes += 2
        }
    }
    return counts
}

func insertion(_ input: [Int]) -> Counts {
    var items = input
    var counts = Counts()
    guard items.count > 1 else { return counts }
    for i in 1..<items.count {
        let key = items[i]
        var gap = i
        while gap > 0 {
            counts.comparisons += 1
            guard items[gap - 1] > key else { break }
            items[gap] = items[gap - 1]
            counts.writes += 1
            gap -= 1
        }
        if gap != i {
            items[gap] = key
            counts.writes += 1
        }
    }
    return counts
}

let n = 100
let inputs = [
    ("sorted", Array(0..<n)),
    ("reversed", Array((0..<n).reversed())),
    ("shuffled", (0..<n).map { ($0 * 37) % n }),
]
let sorts = [("bubble", bubble), ("selection", selection), ("insertion", insertion)]
for (inputName, input) in inputs {
    for (sortName, sort) in sorts {
        let counts = sort(input)
        print("\(inputName), \(sortName): \(counts.comparisons) comparisons, \(counts.writes) writes")
    }
}
```

```output
sorted, bubble: 99 comparisons, 0 writes
sorted, selection: 4950 comparisons, 0 writes
sorted, insertion: 99 comparisons, 0 writes
reversed, bubble: 4950 comparisons, 9900 writes
reversed, selection: 4950 comparisons, 100 writes
reversed, insertion: 4950 comparisons, 5049 writes
shuffled, bubble: 4895 comparisons, 4896 writes
shuffled, selection: 4950 comparisons, 176 writes
shuffled, insertion: 2547 comparisons, 2542 writes
```

Read it column by column:

- **Sorted input.** Bubble and insertion sort make one pass of 99 comparisons and stop. Selection sort makes all 4,950. Only two of the three are adaptive.
- **Reversed input.** Everyone makes 4,950 comparisons, the worst case. But look at the writes: bubble sort 9,900, insertion sort about half that, selection sort 100.
- **Shuffled input.** Insertion sort makes about half the comparisons of the others, because each key stops as soon as it finds its place, on average halfway along the sorted prefix. Bubble sort does almost as many comparisons as on reversed input, and twice insertion sort's writes, because it swaps where insertion sort shifts.

Insertion sort's writes on shuffled input are close to its comparisons: both are about the number of inversions, 2,448 here. Bubble sort writes exactly twice the inversions, 4,896. Selection sort never writes more than 2(n − 1) times, however mixed up the input is.

## The three side by side

| | Bubble | Selection | Insertion |
| --- | --- | --- | --- |
| Best case | O(n), sorted | O(n²), always | O(n), sorted |
| Average and worst | O(n²) | O(n²) | O(n²) |
| Comparisons | up to n(n − 1)/2 | exactly n(n − 1)/2 | n − 1 to n(n − 1)/2 |
| Writes | 2 × inversions | at most 2(n − 1) | inversions + up to n − 1 |
| Extra memory | O(1) | O(1) | O(1) |
| Stable | yes | no | yes |
| Adaptive | yes (early exit) | no | yes: O(n + inversions) |
| Online | no | no | yes |

## When n is small, n² is small

All three are O(n²), and that's terrible for a million elements: about 500 billion comparisons. But for 10 elements, n² is 100, and n log₂ n is about 33. The difference is a few dozen operations, and the simple sorts don't pay for recursion, extra arrays or complicated index arithmetic. Slide n down to 10 or 20 and see how close the curves are, then up to 1,000:

That's the whole reason real sorts switch to insertion sort for short ranges, and why the faster sorts of M31 only win once n grows.

## Which one when?

- **Insertion sort** is the default simple sort. Use it for small arrays (up to a few dozen elements), for data that's already nearly sorted, for data that arrives one element at a time, and to finish small pieces inside a faster sort. It's stable, so it's safe for records.
- **Selection sort** is for when **writes are expensive** and n is small, or when you only need the **first k** values in order and k is tiny.
- **Bubble sort** is mostly for learning. Its one practical trick is a single pass with no swaps, which confirms an array is sorted in O(n), but `zip(a, a.dropFirst()).allSatisfy { $0 <= $1 }` says that more clearly.
- **Everything else:** call `sort()` or `sorted()`. Swift's sort is O(n log n) in the worst case, stable, and adaptive to runs that are already in order. M31 shows how it works.

<Callout kind="tip" title="A quick rule of thumb">
If you're about to write a simple sort in real code, write insertion sort. If n might be large, don't write a sort at all: use the standard library's.
</Callout>
