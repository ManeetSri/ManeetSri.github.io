## Why it matters

Sorting is everywhere in apps: contacts by surname, photos by date, a leaderboard by score, search results by relevance. It's also the first step of many algorithms: [binary search](/dsa/learn/bs-classic) needs sorted data, and so do merging, removing duplicates and many interval problems. This module and the next two teach a dozen sorting algorithms. To compare them you need a small vocabulary first: **comparison-based**, **stable**, **in-place**, **adaptive** and **online**. These words tell you which sort fits a job long before you look at any code.

## Records and keys

Real programs rarely sort bare numbers. They sort **records**, values with several fields, by one of those fields, called the **key**. In Swift a record is usually a struct, or a tuple for something quick:

```swift run
struct Task {
    let title: String
    let priority: Int      // 1 is the most urgent
    let due: Int           // day of the month
}

let tasks = [
    Task(title: "Pay rent", priority: 1, due: 28),
    Task(title: "Book dentist", priority: 2, due: 12),
    Task(title: "Fix login bug", priority: 1, due: 3),
    Task(title: "Renew passport", priority: 3, due: 12),
    Task(title: "Reply to Sam", priority: 2, due: 5),
]

let byPriority = tasks.sorted { $0.priority < $1.priority }
for task in byPriority {
    print(task.priority, task.title)
}
```

```output
1 Pay rent
1 Fix login bug
2 Book dentist
2 Reply to Sam
3 Renew passport
```

The key here is `priority`. The whole record moves, but only the key decides where it goes. Two tasks with the same key, like "Pay rent" and "Fix login bug", are **equal** as far as the sort is concerned, even though they're different tasks. What happens to equal records is the first property worth naming.

## Stable: equal keys keep their order

A sort is **stable** if records with equal keys come out in the same relative order they went in. Look at the output above: "Pay rent" came before "Fix login bug" in the input, and it still does. Same for "Book dentist" and "Reply to Sam". That's because Swift's `sorted(by:)` is guaranteed to be stable.

An **unstable** sort is free to put "Fix login bug" first. The output would still be correctly sorted by priority. It would just have lost the original order inside each priority.

Stability is invisible when you sort plain numbers: two 5s look exactly alike. It matters only when records carry more than their key.

### Why stability makes multi-pass sorting work

Stability has a powerful consequence. Suppose you want the tasks by priority, and tasks with the same priority by due date. Sort by the **secondary** key first, then do a stable sort by the **primary** key:

```swift run
struct Task {
    let title: String
    let priority: Int
    let due: Int
}

let tasks = [
    Task(title: "Pay rent", priority: 1, due: 28),
    Task(title: "Book dentist", priority: 2, due: 12),
    Task(title: "Fix login bug", priority: 1, due: 3),
    Task(title: "Renew passport", priority: 3, due: 12),
    Task(title: "Reply to Sam", priority: 2, due: 5),
]

let byDue = tasks.sorted { $0.due < $1.due }
let byPriorityThenDue = byDue.sorted { $0.priority < $1.priority }
for task in byPriorityThenDue {
    print(task.priority, task.due, task.title)
}
```

```output
1 3 Fix login bug
1 28 Pay rent
2 5 Reply to Sam
2 12 Book dentist
3 12 Renew passport
```

The second sort only looks at priority. Inside each priority, the stable sort keeps the order the first sort left behind, which was by due date. So the result is ordered by priority, then by due date. This is exactly what happens in a spreadsheet when you click the "Due" column header and then the "Priority" header.

<Callout kind="analogy">
Think of sorting a pile of exam papers. First you put them in alphabetical order by name. Then you deal them into piles by class, always placing each paper on top of its pile in the order you pick them up. Each class pile is still alphabetical, because dealing kept the order you already had. Dealing is a stable sort.
</Callout>

You could also write one comparison that does both, with a tuple, as [sorted(by:)](/dsa/learn/swift-sorting-searching-api) showed: `tasks.sorted { ($0.priority, $0.due) < ($1.priority, $1.due) }`. That's usually clearer in your own code. But the multi-pass idea matters when you can't write one comparison: when a user picks sort columns one at a time, or when the sort only ever looks at one key. Radix sort, in M32, sorts numbers one digit at a time with this exact trick, and it only works because each pass is stable.

## Comparison-based

A **comparison sort** learns about the data in only one way: by asking "must `a` come before `b`?" That question is the closure you pass to `sorted(by:)`, called `areInIncreasingOrder`. Bubble, selection and insertion sort in this module, and merge sort and quick sort in M31, are all comparison sorts. That's why they can sort anything you can compare: numbers, strings, dates, tasks.

The price is a speed limit. In M31's [lower bound lesson](/dsa/learn/sort-lower-bound) you'll see that every comparison sort needs about n log n comparisons in the worst case. Sorts that aren't comparison-based, such as counting sort and radix sort in M32, look at the keys themselves ("this score is 87, so it goes in slot 87") and can beat that limit, but only for keys like small integers.

## In-place

A sort is **in-place** if it rearranges the elements inside the array, using only a constant amount of extra memory: a few variables, never a second array that grows with n. The three sorts in this module are in-place: they only ever swap or shift elements within the array. Merge sort, in M31, normally isn't, because merging needs a scratch array of size n.

Don't confuse in-place with Swift's `sort()` versus `sorted()`. `sort()` changes the array you call it on, and `sorted()` returns a new one. That's about the **interface**. In-place is about how much **extra memory** the algorithm uses while it works. Swift's sort may use temporary memory internally even when you call `sort()`.

## Adaptive

A sort is **adaptive** if it does less work when the input is already partly in order. Real data often is: a list sorted yesterday with a few new entries, timestamps that arrive almost in order, a leaderboard where only a few scores changed. [Best, average and worst case](/dsa/learn/bigo-cases) showed that Swift's own sort needs only n − 1 comparisons for sorted input. In this module, insertion sort and bubble sort are adaptive, and selection sort isn't: it does the same amount of work whatever you give it.

## Online

A sort is **online** if it can take the elements one at a time, as they arrive, keeping everything seen so far sorted. You don't need the whole input before you start. A leaderboard that updates as each score comes in is the classic case:

```swift run
var leaderboard: [Int] = []              // kept sorted, highest first
for score in [40, 75, 60, 90, 75] {
    var position = leaderboard.count
    while position > 0 && leaderboard[position - 1] < score {
        position -= 1
    }
    leaderboard.insert(score, at: position)
    print(leaderboard)
}
```

```output
[40]
[75, 40]
[75, 60, 40]
[90, 75, 60, 40]
[90, 75, 75, 60, 40]
```

Each new score walks in from the end until it meets a score at least as big. That's the heart of insertion sort, which is online. Notice the second 75 stops *after* the first one, because the loop only moves past strictly smaller scores: that keeps it stable too. Selection sort can't work this way: it needs every element before it can pick the smallest.

## The properties at a glance

| Property | Question it answers | A quick test |
| --- | --- | --- |
| Comparison-based | Does it only ask "must a come before b"? | Could it sort strings with the same code? |
| Stable | Do equal keys keep their input order? | Sort records with repeated keys and look |
| In-place | Does it need only O(1) extra memory? | Does it allocate an array of size n? |
| Adaptive | Is it faster on nearly sorted input? | Count its comparisons on sorted input |
| Online | Can it sort elements as they arrive? | Can it start before seeing the last element? |

Over the next lessons you'll fill in this table for bubble, selection and insertion sort, and the final lesson of the module puts them side by side.

<Callout kind="gotcha" title="Swift gotcha: a non-strict comparison breaks stability">
The closure you pass to `sorted(by:)` must return `false` for two equal keys. Pass `$0.priority < $1.priority`, never `<=`. With `<=`, equal records count as "out of order" in both directions, so the sort may swap them, and stability is gone even though the sort itself is stable. Worse, it breaks the rules the sort relies on, so the result isn't guaranteed to be sorted at all. The same goes for the sorts you write yourself: in this module, swapping on `>=` instead of `>` quietly makes a stable sort unstable.
</Callout>
