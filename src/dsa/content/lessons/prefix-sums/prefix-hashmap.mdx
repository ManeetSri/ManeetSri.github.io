## Why it matters

A bank wants to know how many stretches of consecutive transactions net out to exactly £0. A step counter wants the longest run of days that added up to a target. Both ask about **subarrays**, contiguous runs of an array, with a given sum, and the values can be negative. The brute force checks every subarray, which is O(n²). Pairing prefix sums with a dictionary gets it to O(n). This is one of the most reused patterns in DSA interviews, and it works in exactly the cases where the sliding window you'll meet in M22 breaks down.

## The question

> Given an array of integers, which may be negative, and a target `k`, count the subarrays whose sum is exactly `k`.

For `[1, 2, -1, 3, -2, 2]` with `k = 3`, there are four:

| Subarray | Indexes | Sum |
| --- | --- | --- |
| `[1, 2]` | 0...1 | 3 |
| `[1, 2, -1, 3, -2]` | 0...4 | 3 |
| `[3]` | 3...3 | 3 |
| `[3, -2, 2]` | 3...5 | 3 |

## Brute force first

Try every start. From each start, extend the end one step at a time, keeping a running sum so each extension costs O(1):

```swift run
func countSlowly(_ numbers: [Int], summingTo k: Int) -> Int {
    var count = 0
    for start in numbers.indices {
        var sum = 0
        for end in start..<numbers.count {
            sum += numbers[end]
            if sum == k {
                count += 1
            }
        }
    }
    return count
}

print(countSlowly([1, 2, -1, 3, -2, 2], summingTo: 3))
print(countSlowly([1, -1, 1, -1], summingTo: 0))
```

```output
4
4
```

That's correct, and it's O(n²): fine for 1,000 numbers, too slow for 100,000. Keep it, though. It's the yardstick for testing the fast version.

## Turning the question around

From [the last lesson](/dsa/learn/prefix-1d), with `prefix[i]` the sum of the first `i` numbers:

> sum of `numbers[i..<j]` = `prefix[j] − prefix[i]`

So a subarray sums to `k` exactly when two prefix values are `k` apart:

> `prefix[j] − prefix[i] == k`, which is the same as `prefix[i] == prefix[j] − k`

Now flip the point of view. Walk through the array once. When you reach position `j`, you know `prefix[j]`: it's the running total. Every subarray that **ends** here corresponds to an **earlier** prefix value equal to `prefix[j] − k`. So the number of good subarrays ending here is:

> how many earlier prefix values equal `prefix[j] − k`?

A dictionary from "prefix value" to "how many times I've seen it" answers that in O(1) on average.

<Callout kind="analogy">
Think of a car's odometer. You're now at mile 57 and want journeys of exactly 7 miles that end right here. Each one started at a moment the odometer read 50. So you only need to count how many times you passed mile 50. You don't care what happened in between.
</Callout>

## The algorithm

```swift run
func countSubarrays(_ numbers: [Int], summingTo k: Int) -> Int {
    var seen: [Int: Int] = [0: 1]    // the empty prefix, before any number
    var running = 0
    var count = 0
    for value in numbers {
        running += value
        count += seen[running - k, default: 0]
        seen[running, default: 0] += 1
    }
    return count
}

print(countSubarrays([1, 2, -1, 3, -2, 2], summingTo: 3))
print(countSubarrays([1, -1, 1, -1], summingTo: 0))
print(countSubarrays([], summingTo: 0))
```

```output
4
4
0
```

Three details make it right:

1. **`seen` starts as `[0: 1]`.** That's `prefix[0]`, the sum of nothing. Without it, subarrays that start at index 0 have no earlier prefix to match, so `[1, 2]` would be missed.
2. **Look up first, then record.** The lookup must only see prefixes from *before* the current position. If you recorded `running` first, then with `k = 0` the current prefix would match itself, counting an empty subarray.
3. **Count, don't only remember.** The same prefix value can appear several times, and each earlier occurrence starts a different subarray. That's why the dictionary stores counts, using `default:` from [Counting with default: and grouping(by:)](/dsa/learn/swift-counting-grouping).

## Watching it run

Here's the same loop printing each step for the example:

```swift run
let numbers = [1, 2, -1, 3, -2, 2]
let k = 3
var seen: [Int: Int] = [0: 1]
var running = 0
var count = 0
for value in numbers {
    running += value
    let found = seen[running - k, default: 0]
    count += found
    seen[running, default: 0] += 1
    print("value \(value): running \(running), look for \(running - k), found \(found), count \(count)")
}
```

```output
value 1: running 1, look for -2, found 0, count 0
value 2: running 3, look for 0, found 1, count 1
value -1: running 2, look for -1, found 0, count 1
value 3: running 5, look for 2, found 1, count 2
value -2: running 3, look for 0, found 1, count 3
value 2: running 5, look for 2, found 1, count 4
```

Match each find to the table at the top. At value `2` (index 1), the running total 3 finds the starting 0: that's `[1, 2]`. At value `3`, the total 5 finds the earlier 2 (after index 2): that's `[3]`. At value `-2`, the total 3 finds the 0 again: `[1, 2, -1, 3, -2]`. And at the last value, 5 finds that same 2: `[3, -2, 2]`.

One pass, O(1) average work per number: **O(n) time** and **O(n) space** for the dictionary.

## Why a sliding window can't do this

M22 teaches the **sliding window**: keep a window `left...right`, grow it on the right while the sum is too small, and shrink it from the left when it's too big. It's O(n) and needs no dictionary. Why not use it here?

Because "too big, so shrink" is only safe when every number is positive. Then adding a number always raises the sum, and removing one always lowers it. With negatives, neither is true. Take `[4, -3, 2]` with `k = 3`:

- The window starts as `[4]`, with sum 4. That's too big, so it drops the 4.
- But `[4, -3, 2]` sums to 3. It started with the 4 that the window threw away, and the window can never go back for it.

The window made a decision that a later negative number proved wrong. Prefix sums make no decisions at all: they record every prefix, so nothing is thrown away. **When values can be negative, reach for prefix sum + dictionary.** When they're all positive, a sliding window also works, with O(1) space.

## The longest subarray with sum k

A close cousin asks for the **length of the longest** subarray summing to `k`. Same idea, different dictionary: instead of counting prefix values, store **the first position where each prefix value appeared**.

Why the first? The subarray from position `i` to the current position is longer when `i` is smaller. If a prefix value comes up again later, keep the old position, because it gives longer subarrays.

```swift run
func longestSubarray(_ numbers: [Int], summingTo k: Int) -> Int {
    var firstSeen: [Int: Int] = [0: 0]   // prefix value -> smallest i with prefix[i] equal to it
    var running = 0
    var best = 0
    for (index, value) in numbers.enumerated() {
        running += value
        let end = index + 1              // running is prefix[end]
        if let start = firstSeen[running - k] {
            best = max(best, end - start)
        }
        if firstSeen[running] == nil {
            firstSeen[running] = end
        }
    }
    return best
}

print(longestSubarray([1, -1, 5, -2, 3], summingTo: 3))
print(longestSubarray([2, 2, 2], summingTo: 5))
```

```output
4
0
```

For `[1, -1, 5, -2, 3]`, the prefix values are 0, 1, 0, 5, 3, 6. At the end of `-2`, the running total is 3, and `3 − 3 = 0` was first seen at position 0, so `[1, -1, 5, -2]` has length 4. The prefix 0 also turns up again at position 2, but the `if firstSeen[running] == nil` check keeps the earlier 0, and that's what makes the answer 4 rather than 2.

The seed is `[0: 0]` here: prefix value 0 at position 0. It plays the same role as `[0: 1]` did for counting.

## The same trick in disguise

Many problems become "subarray with sum k" after a small change of values. A classic: **find the longest stretch of a 0/1 array with equally many 0s and 1s.** Count each 1 as +1 and each 0 as −1. A stretch is balanced exactly when it sums to 0, so it's the longest subarray with sum 0:

```swift run
func longestBalanced(_ bits: [Int]) -> Int {
    var firstSeen: [Int: Int] = [0: 0]
    var running = 0
    var best = 0
    for (index, bit) in bits.enumerated() {
        running += bit == 1 ? 1 : -1
        if let start = firstSeen[running] {
            best = max(best, index + 1 - start)
        } else {
            firstSeen[running] = index + 1
        }
    }
    return best
}

print(longestBalanced([1, 1, 0, 1, 1, 0, 0, 1]))
print(longestBalanced([1, 1, 1]))
```

```output
6
0
```

With `k = 0`, "look for `running − k`" becomes "look for `running` itself", which is why the lookup and the record merge into one `if let`.

<Callout kind="gotcha" title="Swift gotcha: % can be negative">
A popular variant counts subarrays whose sum is **divisible by** `k`. Two prefixes whose remainders mod `k` are equal bracket such a subarray, so you key the dictionary by `running % k`. But Swift's `%` keeps the sign of the left side: `-7 % 5` is `-2`, while `3 % 5` is `3`, even though −7 and 3 differ by 10, a multiple of 5. Normalise with `((running % k) + k) % k` so equal remainders really are equal keys. [Floor and ceiling division, and overflow](/dsa/learn/math-floor-ceil-overflow) explains why `%` behaves this way.
</Callout>

## Common mistakes

- **Forgetting the seed.** Without `[0: 1]` (or `[0: 0]` for positions), every subarray that starts at index 0 is missed.
- **Recording before looking up.** With `k = 0`, the current prefix then matches itself.
- **Overwriting positions in the "longest" version.** Keep the first position of each prefix value, never a later one.
- **Using a sliding window with negative numbers.** It gives wrong answers, not merely slow ones.
