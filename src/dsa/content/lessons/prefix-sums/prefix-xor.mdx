## Why it matters

Prefix sums work because subtraction undoes addition. XOR undoes itself, so the same trick works with `^` in place of `+`. A **prefix XOR** array answers "what's the XOR of this range?" in O(1), and with a dictionary it counts subarrays whose XOR is a target. It turns up in bit-manipulation problems, and in checksums that combine a range of bytes. More importantly, it shows you *why* prefix sums work, so you'll know which other operations can use them.

## Building a prefix XOR

Exactly like a prefix sum, with `^` instead of `+`, and the sentinel is `0` because `x ^ 0 == x`:

> `prefixXor[i]` is the XOR of the first `i` items.

```swift run
let items = [5, 3, 6, 2, 7, 1]
var prefixXor = [0]
for value in items {
    prefixXor.append(prefixXor.last! ^ value)
}
print(prefixXor)
```

```output
[0, 5, 6, 0, 2, 5, 4]
```

`prefixXor[3]` is `5 ^ 3 ^ 6`, which happens to be `0`, and `prefixXor[6]`, the last value, is the XOR of the whole array.

## Any range with one XOR

For a sum, the shared beginning cancels by subtraction. For XOR, it cancels by XORing it again. From [XOR tricks](/dsa/learn/bits-xor-tricks): equal values cancel in pairs, wherever they are.

- `prefixXor[j + 1]` is `items[0] ^ … ^ items[i − 1] ^ items[i] ^ … ^ items[j]`.
- `prefixXor[i]` is `items[0] ^ … ^ items[i − 1]`.

XOR them, and every item before `i` appears twice and vanishes:

> XOR of `items[i...j]` = `prefixXor[j + 1] ^ prefixXor[i]`

```swift run
let items = [5, 3, 6, 2, 7, 1]
var prefixXor = [0]
for value in items {
    prefixXor.append(prefixXor.last! ^ value)
}

func rangeXor(from start: Int, through end: Int) -> Int {
    prefixXor[end + 1] ^ prefixXor[start]
}

print(rangeXor(from: 1, through: 3), 3 ^ 6 ^ 2)
print(rangeXor(from: 0, through: 5))
print(rangeXor(from: 4, through: 4))
```

```output
7 7
4
7
```

Same shape, same offsets, same O(1) per query. Only the operator changed.

## What made it work: an undo

Look at what both versions needed:

1. A starting value that changes nothing: `0` for `+`, `0` for `^`.
2. A way to **remove** the shared beginning: `−` undoes `+`, and `^` undoes `^`.

That second need is the real requirement. Mathematicians call it an **inverse**, and it tells you where prefix arrays work and where they don't:

| Operation | Starting value | Undo | Range query from a prefix array? |
| --- | --- | --- | --- |
| `+` | 0 | `−` | yes |
| `^` | 0 | `^` | yes |
| `*` | 1 | `/`, but not past a zero | only without zeros |
| `max`, `min` | `Int.min`, `Int.max` | none | only for ranges starting at index 0 |

You can't "un-max" a value. Knowing the largest of the first 6 items and the largest of the first 2 tells you nothing about the largest of items 2 to 5. Range maximums need a different structure, such as a sparse table or a segment tree, which Part VIII builds. Multiplication's problem with zeros is the reason for [Product of array except self](/dsa/learn/prefix-product-except-self), later in this module.

## Counting subarrays with a given XOR

The dictionary pattern from [the last lesson](/dsa/learn/prefix-hashmap) carries over too. A subarray `items[i..<j]` has XOR `k` when:

> `prefixXor[j] ^ prefixXor[i] == k`, which is the same as `prefixXor[i] == prefixXor[j] ^ k`

XOR both sides with `prefixXor[j]` to see why: it cancels on the left and moves to the right. So at each position, look for earlier prefixes equal to `running ^ k`:

```swift run
func countSubarrays(_ numbers: [Int], withXor k: Int) -> Int {
    var seen: [Int: Int] = [0: 1]
    var running = 0
    var count = 0
    for value in numbers {
        running ^= value
        count += seen[running ^ k, default: 0]
        seen[running, default: 0] += 1
    }
    return count
}

print(countSubarrays([5, 3, 6, 2, 7, 1], withXor: 7))
print(countSubarrays([5, 3, 6, 2, 7, 1], withXor: 0))
print(countSubarrays([1, 2, 3, 1, 2, 3], withXor: 0))
```

```output
2
2
5
```

For `k = 7`, the two subarrays are `[3, 6, 2]` and `[7]`. For `k = 0`, a subarray's XOR is zero exactly when the prefix values at its two ends are **equal**: `prefixXor[0]` and `prefixXor[3]` are both 0, giving `[5, 3, 6]`, and `prefixXor[1]` and `prefixXor[5]` are both 5, giving `[3, 6, 2, 7]`.

The seed `[0: 1]`, the lookup-before-record order and the O(n) time all stay the same. The only edit is `−` becoming `^`.

<Callout kind="gotcha" title="Two subtractions, one XOR">
For sums you look for `running - k`, and the order matters: `k - running` is wrong. XOR has no order, so `running ^ k` and `k ^ running` are the same. Don't let that symmetry trick you into writing `k - running` when you switch back to sums.
</Callout>

## Practice

**Triples that split into equal XORs** turns the question round: two touching pieces have equal XORs exactly when the whole stretch XORs to 0, so it's a count of equal prefix XORs, weighted by how far apart they are.
