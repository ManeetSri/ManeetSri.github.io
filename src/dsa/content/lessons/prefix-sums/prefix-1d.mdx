## Why it matters

A fitness app shows your steps for any stretch of days you pick. A finance screen totals the spending between two dates. A game adds up the points scored in levels 3 to 7. Each is a **range sum**: the total of a run of neighbouring values. Adding them up afresh for every question is slow when there are many questions. A **prefix sum** array, built once in O(n), answers every range sum with one subtraction. It's also the foundation for the rest of this module: the prefix sum + dictionary pattern, difference arrays and 2D sums all start here.

## The slow way: add up the range every time

Here's the obvious approach. To total `items[start...end]`, loop over that range:

```swift run
func slowRangeSum(_ items: [Int], from start: Int, through end: Int) -> Int {
    var total = 0
    for index in start...end {
        total += items[index]
    }
    return total
}

let items = [3, 1, 4, 1, 5, 9, 2]
print(slowRangeSum(items, from: 2, through: 5))
print(slowRangeSum(items, from: 0, through: 6))
```

```output
19
25
```

Each query costs O(length of the range), up to O(n). One query is fine. But with n = 100,000 items and q = 100,000 queries, that's up to 10¹⁰ additions, which the [feasibility table](/dsa/learn/bigo-feasibility-table) says is about a hundred times over budget.

Notice the repeated work, the thing [Brute force first](/dsa/learn/algo-brute-force-first) taught you to look for. The second query re-adds `4 + 1 + 5 + 9`, which the first query already added. Every query walks over values that earlier queries already summed.

## Running totals

The fix is to do the adding once, up front. Make a new array where each slot holds the total of everything **before** it:

> `prefix[i]` is the sum of the first `i` items, `items[0..<i]`.

For `[3, 1, 4, 1, 5, 9, 2]`:

| `i` | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `items[i]` | 3 | 1 | 4 | 1 | 5 | 9 | 2 | |
| `prefix[i]` | 0 | 3 | 4 | 8 | 9 | 14 | 23 | 25 |

Each prefix value is the one before it plus one more item, so the whole array takes a single pass:

```swift run
let items = [3, 1, 4, 1, 5, 9, 2]
var prefix = [0]
for value in items {
    prefix.append(prefix.last! + value)
}
print(prefix)
print(items.count, prefix.count)
```

```output
[0, 3, 4, 8, 9, 14, 23, 25]
7 8
```

What to notice:

- `prefix` has **one more** slot than `items`.
- `prefix[0]` is `0`, the sum of no items at all. It's a **sentinel**: a value placed at the edge so the edge needs no special code.
- `prefix.last!` is the total of the whole array. The force unwrap is safe because `prefix` always starts with one element.

## Any range with one subtraction

Now the key step. Take the range `items[2...5]`, which is `4 + 1 + 5 + 9`:

- `prefix[6]` is `3 + 1 + 4 + 1 + 5 + 9`, everything up to index 5.
- `prefix[2]` is `3 + 1`, everything before index 2.

Subtract, and the shared start `3 + 1` cancels, leaving exactly `4 + 1 + 5 + 9`:

> sum of `items[i...j]` = `prefix[j + 1] − prefix[i]`

Step through the build and the query here. The last frame shows the two prefix values being subtracted:

```visual arrayTrace

  items: [3, 1, 4, 1, 5, 9, 2]

```

```swift run
let items = [3, 1, 4, 1, 5, 9, 2]
var prefix = [0]
for value in items {
    prefix.append(prefix.last! + value)
}

func rangeSum(_ prefix: [Int], from start: Int, through end: Int) -> Int {
    prefix[end + 1] - prefix[start]
}

print(rangeSum(prefix, from: 2, through: 5))
print(rangeSum(prefix, from: 0, through: 6))
print(rangeSum(prefix, from: 4, through: 4))
```

```output
19
25
5
```

The answers match the slow version, but each query is now two lookups and a subtraction: O(1), however long the range.

## Why the leading zero

You could store running totals without the sentinel, so that `running[i]` is the sum of `items[0...i]`. Then the range formula becomes `running[j] − running[i − 1]`, and a range starting at index 0 asks for `running[-1]`, which crashes. You'd need an `if start == 0` in every query.

The leading `0` removes that special case. There's a neater way to read the formula, too. With the sentinel, a **half-open** range `start..<end`, the kind Swift writes with `..<`, has the cleanest formula of all:

> sum of `items[start..<end]` = `prefix[end] − prefix[start]`

No `+ 1` anywhere, and an empty range like `3..<3` gives `prefix[3] − prefix[3] = 0` with no extra code. The rest of this module uses that reading: **`prefix[i]` is the total of the first `i` items**, and a subarray is the gap between two prefix positions.

## Wrapping it in a struct

The prefix array belongs with the code that reads it. A small struct keeps it private, so nobody can query the wrong array or forget the offset:

```swift run
struct RangeSums {
    private let prefix: [Int]

    init(_ values: [Int]) {
        var prefix = [0]
        prefix.reserveCapacity(values.count + 1)
        for value in values {
            prefix.append(prefix.last! + value)
        }
        self.prefix = prefix
    }

    // The total of values[range], for a half-open range like 2..<5
    func sum(_ range: Range<Int>) -> Int {
        prefix[range.upperBound] - prefix[range.lowerBound]
    }
}

let steps = RangeSums([1200, 800, 3400, 0, 2600, 5100, 900])
print(steps.sum(0..<7))
print(steps.sum(2..<5))
print(steps.sum(3..<3))
```

```output
14000
6000
0
```

`reserveCapacity` (from [Amortised analysis](/dsa/learn/bigo-amortised)) allocates the right size once, since you know exactly how many prefix values there will be.

## What it costs

| | Time | Extra space |
| --- | --- | --- |
| Build the prefix array | O(n) | O(n) |
| One range query | O(1) | none |
| n items, q queries | O(n + q) | O(n) |
| Slow way, q queries | O(n × q) | none |

For n = q = 100,000, that's about 200,000 steps instead of up to 10¹⁰. You trade O(n) memory for the speed, which is almost always worth it.

Prefix sums work with negative numbers too. The formula is pure algebra, so nothing depends on the values being positive. That matters in the next lesson.

<Callout kind="gotcha" title="Common mistakes">
- **Mixing up the offset.** `prefix` is one longer than `items`. For an inclusive range `i...j`, the formula needs `prefix[j + 1]`; for a half-open range `i..<j`, it's `prefix[j]`. Write down which one you're using.
- **Overflow.** A prefix value can be far bigger than any single item. 100,000 items of up to 10⁹ add up to 10¹⁴: fine for Swift's 64-bit `Int`, but too big for `Int32`. See [the overflow checklist](/dsa/learn/math-floor-ceil-overflow).
- **Changing the array afterwards.** The prefix array is a snapshot. If an item changes, every later prefix value is wrong and rebuilding costs O(n). When updates and queries are mixed, you need a Fenwick or segment tree, which Part VIII builds.
</Callout>

## Practice

**Range sum queries** asks you to build a small struct like `RangeSums`, but with inclusive ranges, so you'll handle the `+ 1` yourself. Test it on a range that starts at index 0 and one that ends at the last index: those are where off-by-one mistakes show up.

```cards

  front: "With the sentinel convention, what does `prefix[i]` hold?"
  back: "The sum of the first `i` items, `items[0..<i]`. `prefix[0]` is `0`, and the array is one longer than `items`."
- id: range-formula
  front: "How do you get the sum of `items[i...j]` from a prefix array?"
  back: "`prefix[j + 1] - prefix[i]`. For a half-open range `i..<j` it's `prefix[j] - prefix[i]`."
- id: why-sentinel
  front: "Why start the prefix array with a 0?"
  back: "So a range starting at index 0 uses the same formula as every other range, with no `if start == 0` special case."
- id: prefix-cost
  front: "What do n items and q range-sum queries cost with prefix sums?"
  back: "O(n) to build and O(1) per query, so O(n + q) in total, against O(n × q) for summing each range afresh."
```
