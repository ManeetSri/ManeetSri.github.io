## Why it matters

Before Swift Testing arrived in 2024, Swift and Objective-C code was tested with **XCTest**, and most existing iOS projects, tutorials and answers online still use it. Xcode's UI tests are XCTest too. You don't need to write XCTest in this course, but you should be able to read it and translate it into what you already know.

## What an XCTest file looks like

Here are the second-largest tests from the last lesson, written the XCTest way:

```swift title="SecondLargestTests.swift"
import XCTest

final class SecondLargestTests: XCTestCase {
    var sample: [Int] = []

    override func setUp() {
        super.setUp()
        sample = [4, 9, 2, 7]
    }

    func testNormalCase() {
        XCTAssertEqual(secondLargest(in: sample), 7)
    }

    func testTooFewNumbers() {
        XCTAssertNil(secondLargest(in: [3]))
    }

    func testFirstOfSorted() throws {
        let first = try XCTUnwrap(sample.sorted().first)
        XCTAssertEqual(first, 2)
    }
}
```

The rules that make it work:

- Tests live in a **class** that inherits from `XCTestCase` (M09).
- A method is a test only if its name **starts with `test`**, takes no parameters and returns nothing. A method called `checkNormalCase` would silently never run.
- Checks are **functions** named `XCTAssert…`, not macros.
- `setUp()` runs before **each** test and `tearDown()` after each, so every test starts fresh. XCTest also creates a new instance of the class for each test.

## Translating to Swift Testing

| XCTest | Swift Testing |
| --- | --- |
| `import XCTest` | `import Testing` |
| `final class FooTests: XCTestCase` | `@Suite struct FooTests` |
| `func testSomething()` | `@Test func something()` |
| `XCTAssertEqual(a, b)` | `#expect(a == b)` |
| `XCTAssertTrue(x)`, `XCTAssertFalse(x)` | `#expect(x)`, `#expect(!x)` |
| `XCTAssertNil(x)` | `#expect(x == nil)` |
| `try XCTUnwrap(x)` | `try #require(x)` |
| `XCTAssertThrowsError(try f())` | `#expect(throws: (any Error).self) { try f() }` |
| `setUp()` | the suite's `init()` |
| one test method per case | `@Test(arguments:)` |

The biggest everyday difference is the failure message. XCTest needs a separate function for each kind of check so it can describe the values. `XCTAssertEqual` does it well:

```text title="What you'll see"
StatsTests.swift:13: error: -[StatsTests.SecondLargestTests testNormalCase] : XCTAssertEqual failed: ("Optional(9)") is not equal to ("Optional(3)")
```

But `XCTAssertTrue(secondLargest(in: numbers) == 3)` can only report "XCTAssertTrue failed", with no values, because a plain function only receives `false`. `#expect` is a macro, so it sees the whole expression and shows every part.

## Running XCTest

Nothing changes: `swift test` and Xcode run XCTest and Swift Testing tests together, even in the same test target. `--filter` matches XCTest class and method names as well as suite names.

<Callout kind="gotcha" title="Swift gotcha: don't mix the two in one test">
Use each library's checks only in its own tests. With current toolchains, a failing `XCTAssertEqual` inside a Swift Testing `@Test` is reported only as a warning ("Replace XCTest API such as 'XCTAssert' with a Swift Testing equivalent"), and the test still **passes**. When you convert a test, convert every check in it.
</Callout>
