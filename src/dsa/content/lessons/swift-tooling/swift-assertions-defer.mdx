## Why it matters

Every algorithm rests on assumptions: binary search assumes the array is sorted, a window function assumes its size is positive, an index must be in range. When an assumption is broken, the worst outcome is a program that carries on and quietly produces a wrong answer. Swift gives you tools to **stop loudly at the exact spot** instead: `precondition`, `assert` and `fatalError`. And `defer` makes sure clean-up code runs however a function exits.

## Stopping on purpose

You've already met a deliberate crash: reading `numbers[10]` from a five-element array stops the program with "Index out of range". Swift could have returned some random memory instead, but a crash at the line with the bug is far easier to fix. You can add checks like that to your own code.

| Function | Checked in debug builds | Checked in release builds | Use it for |
| --- | --- | --- | --- |
| `precondition(condition, message)` | yes | yes | promises a caller must keep |
| `assert(condition, message)` | yes | **no** | double-checking your own logic |
| `fatalError(message)` | always crashes | always crashes | code that must never run |

**Debug** builds are what `swift run`, `swift test` and Xcode's Run button make while you develop; **release** builds are optimised for speed. You'll compare them later in this module, in "Debug vs release builds".

## precondition: the caller's promise

A **precondition** is something that must be true before a function can do its job. `precondition` checks it and crashes with your message if it's false:

```swift
func average(of numbers: [Int]) -> Int {
    precondition(!numbers.isEmpty, "average(of:) needs at least one number")
    return numbers.reduce(0, +) / numbers.count
}

print(average(of: [4, 8, 9]))
print(average(of: []))
```

The first call prints `7`. The second stops the program:

```text title="What you'll see"
average/average.swift:2: Precondition failed: average(of:) needs at least one number
```

That's what Swift reports when this runs as `swift average.swift`: the file, the line of the check, and your message. Without the check, the empty array would still crash, but with "Division by zero" inside `average`: a message that says what happened but not who broke the rules.

`precondition` stays in release builds, so it protects your users as well as you. Swift's own array subscript uses the same kind of check.

## assert: checking your own logic

`assert` looks the same, but it only runs in debug builds. In an optimised build it's removed entirely, so it costs nothing. Use it to double-check things that should be true if *your own* code is correct, for example a step inside an algorithm:

```swift
var low = 0
var high = numbers.count - 1
while low <= high {
    let middle = (low + high) / 2
    assert(low <= middle && middle <= high, "middle escaped the search range")
    // …
}
```

If an assertion fails, you see a message like a precondition's:

```text title="What you'll see"
search/search.swift:5: Assertion failed: middle escaped the search range
```

Because release builds skip asserts, never put work your program needs inside one. `assert(list.removeFirst() == 1)` would remove the element in debug builds but not in release.

## fatalError: this must never happen

`fatalError` always crashes, in every kind of build. Its return type is `Never`, which tells Swift that the program can't continue past it. So you can use it where Swift needs a value but no value makes sense:

```swift run
enum Move {
    case up, down
}

func move(from letter: Character) -> Move {
    switch letter {
    case "U": return .up
    case "D": return .down
    default: fatalError("Unexpected move: \(letter)")
    }
}

print(move(from: "U"))
print(move(from: "D"))
```

```output
up
down
```

The `default` case doesn't need a `return`, because `fatalError` never returns. If a problem guarantees that the input only contains `U` and `D`, this documents that guarantee, and catches it instantly if it's ever broken. `preconditionFailure("…")` and `assertionFailure("…")` are the versions of the other two that always fail, for the same kind of spot.

## Crash, or throw?

All three of these crash, which is right for **programmer mistakes**. They're wrong for problems that can happen in a correct program:

- Input that comes from **outside** (a user, a file, the network, a test case) can be malformed in normal operation. Throw an error, as in [throws, try and Result](/dsa/learn/swift-errors), so the caller can react.
- A broken **promise between parts of your own code**, such as passing a negative capacity to your own data structure, is a bug. Crash with `precondition`, so you find and fix it.

In interviews and practice problems, the constraints usually promise valid input, so preconditions are mostly documentation there. In app code, the line between the two matters every day.

## defer: run this on the way out

`defer` schedules a block of code to run when the current scope ends, however it ends: falling off the end, `return`, `throw`, `break` or `continue`. When a scope has several `defer` blocks, they run in **reverse order**, last one first:

```swift run
func demo() {
    print("start")
    defer { print("first defer") }
    defer { print("second defer") }
    print("end of body")
}

demo()
```

```output
start
end of body
second defer
first defer
```

Neither `defer` block ran where it was written. Both waited for the function to end, then ran last-in, first-out, like plates taken off a stack.

The real value is that `defer` runs on *every* way out. This search has two `return` statements, and the message prints for both:

```swift run
func find(_ target: Int, in numbers: [Int]) -> Int? {
    print("searching for \(target)")
    defer { print("finished searching for \(target)") }
    for (index, number) in numbers.enumerated() where number == target {
        return index
    }
    return nil
}

print(find(7, in: [3, 7, 9]) ?? -1)
print(find(5, in: [3, 7, 9]) ?? -1)
```

```output
searching for 7
finished searching for 7
1
searching for 5
finished searching for 5
-1
```

## defer in recursive code

`defer` is perfect for undoing a change on the way out. Here a recursive function tracks how deep it is: each call adds one on entry, and `defer` subtracts it however the call ends. You'll use exactly this shape for backtracking in Part VII:

```swift run
var depth = 0

func visit(_ n: Int) {
    depth += 1
    defer { depth -= 1 }
    print(String(repeating: "  ", count: depth - 1) + "visit \(n), depth \(depth)")
    if n > 1 {
        visit(n / 2)
    }
}

visit(8)
print("depth afterwards: \(depth)")
```

```output
visit 8, depth 1
  visit 4, depth 2
    visit 2, depth 3
      visit 1, depth 4
depth afterwards: 0
```

Putting the undo right next to the change means you can't forget it, even if you later add an early `return`. Other common uses are closing a file after reading it, and freeing memory you allocated by hand, like the unsafe pointers in M11.

<Callout kind="gotcha" title="Swift gotchas with defer">
- **It belongs to the nearest scope, not the function.** A `defer` inside a loop body runs at the end of every iteration; inside an `if` block, when that block ends.
- **It runs after the return value is computed.** In `defer { count += 1 }; return count`, the function returns the old value, then the `defer` adds one.
- **It can't leave the scope itself.** You can't `return`, `break` or `throw` out of a `defer` block.
</Callout>
