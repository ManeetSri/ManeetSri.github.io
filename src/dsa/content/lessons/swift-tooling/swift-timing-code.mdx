## Why it matters

Big-O, which you'll learn in Part II, predicts how an algorithm's running time *grows*. But sometimes you need real numbers: is this fast enough for a million elements? Which of two versions is quicker? Did my change help? Measuring time sounds easy, and it's surprisingly easy to get wrong. This lesson shows Swift's tool for it, `ContinuousClock`, and the habits that make measurements trustworthy.

## Clocks, instants and durations

Swift's standard library has a **clock** type for measuring time: `ContinuousClock`. Two more types come with it:

- An **instant** is a moment in time, read with `clock.now`.
- A **duration** (the type `Duration`) is an amount of time. Subtracting one instant from a later one gives the duration between them.

```swift
let clock = ContinuousClock()
let start = clock.now

var total = 0
for i in 0..<1_000_000 {
    total += i
}

let elapsed = clock.now - start
print("Took \(elapsed)")
print(total)
```

```text title="Sample output (times differ every run)"
Took 0.072341625 seconds
499999500000
```

This example has no Run button: its output changes every time, and lesson examples must always print the same thing. Run it yourself and you'll see a different time on each run. That variation is the first lesson about timing: one measurement is never the whole story.

## measure: time a block of code

Reading `now` before and after is so common that the clock does it for you. `measure` runs a closure and returns how long it took:

```swift
let clock = ContinuousClock()
var numbers = (1...100_000).reversed().map { $0 }

let elapsed = clock.measure {
    numbers.sort()
}
print("Sorting took \(elapsed)")
print(numbers[0])
```

```text title="Sample output"
Sorting took 0.004127125 seconds
1
```

## Reading a Duration

Printing a `Duration` shows seconds, which for fast code gets awkward: very short times print in scientific notation, such as `7.0625e-05 seconds` for about 71 microseconds. Dividing one duration by another gives a plain `Double`, so dividing by one millisecond converts to milliseconds:

```swift run
let elapsed = Duration.milliseconds(1500)
print(elapsed)
print(elapsed / .milliseconds(1))
print(Duration.seconds(1) + .milliseconds(250))
print(Duration.seconds(2) / Duration.milliseconds(250))
```

```output
1.5 seconds
1500.0
1.25 seconds
8.0
```

Durations can be added, compared and multiplied like numbers. `.seconds(_:)`, `.milliseconds(_:)`, `.microseconds(_:)` and `.nanoseconds(_:)` create them.

## Timing well

A single measurement of debug code can be off by a factor of a hundred. These habits fix that:

1. **Build in release.** Time with `swift run -c release` or `swift -O`, as [Debug vs release builds](/dsa/learn/swift-release-builds) showed. Debug timings tell you almost nothing.
2. **Time only the algorithm.** Create the input *before* starting the clock, and print *after* stopping it. Printing is slow and would swamp the measurement.
3. **Repeat, and keep the best.** Other programs, power saving and the processor's caches all add noise. Run the work several times and keep the fastest, or the middle value. The fastest run is the one with the least interference.
4. **Use the result.** Print it or check it after timing. Otherwise the optimiser may notice it's unused and delete the work you were trying to measure.
5. **Compare like with like.** Give both versions exactly the same input.

Here's a small helper that follows those rules. It runs the work several times and returns the best time and the result:

```swift
func bestTime(repeats: Int = 5, _ work: () -> Int) -> (time: Duration, result: Int) {
    let clock = ContinuousClock()
    var best = Duration.seconds(1_000)
    var result = 0
    for _ in 0..<repeats {
        let elapsed = clock.measure {
            result = work()
        }
        best = min(best, elapsed)
    }
    return (best, result)
}
```

## Comparing two versions

With the helper, a fair comparison is a few lines. Here, 10,000 lookups check whether numbers are in a collection of 10,000 numbers, once with an array and once with a set (M07):

```swift
let numbers = Array(0..<10_000)
let numberSet = Set(numbers)
let queries = (0..<10_000).map { $0 * 3 }

let arrayRun = bestTime {
    queries.filter { numbers.contains($0) }.count
}
let setRun = bestTime {
    queries.filter { numberSet.contains($0) }.count
}
print("Array: \(arrayRun.result) found in \(arrayRun.time / .milliseconds(1)) ms")
print("Set:   \(setRun.result) found in \(setRun.time / .milliseconds(1)) ms")
```

```text title="One release-build run"
Array: 3334 found in 18.802542 ms
Set:   3334 found in 0.0615 ms
```

Both versions find the same 3,334 numbers, which is worth checking: a fast wrong answer is no use. The array checks its elements one by one, while the set jumps almost straight to the answer (you'll see how in Part III), and here that makes the set about 300 times faster. Notice that the input is built before either measurement, and both get exactly the same queries.

## Measuring growth

The most useful timing experiment for DSA is to **double the input** and watch what happens to the time. Here's a function that counts pairs adding up to a target by checking every pair, with two nested loops:

```swift
func countPairsWithSum(_ numbers: [Int], target: Int) -> Int {
    var count = 0
    for i in 0..<numbers.count {
        for j in (i + 1)..<numbers.count where numbers[i] + numbers[j] == target {
            count += 1
        }
    }
    return count
}

for n in [1_000, 2_000, 4_000, 8_000] {
    let numbers = (0..<n).map { ($0 * 7_919) % 1_000 }
    let (time, pairs) = bestTime { countPairsWithSum(numbers, target: 1_000) }
    let ms = time / .milliseconds(1)
    print("n = \(n): \(pairs) pairs in \((ms * 100).rounded() / 100) ms")
}
```

```text title="One release-build run"
n = 1000: 499 pairs in 0.22 ms
n = 2000: 1997 pairs in 0.79 ms
n = 4000: 7990 pairs in 3.13 ms
n = 8000: 31964 pairs in 13.94 ms
```

Each time `n` doubles, the time roughly **quadruples**. That's the signature of work that grows with n², which makes sense: two nested loops over the input check about n²/2 pairs. A loop that touches each element once would roughly double instead. Measured times are never perfectly neat, but the pattern of ratios shows through. In Part III you'll solve this same problem with one loop and a dictionary.

<Callout kind="gotcha" title="Swift gotcha: ContinuousClock needs macOS 13 in a package">
In a package that doesn't say which macOS versions it supports, using `ContinuousClock` fails with "'ContinuousClock' is only available in macOS 13.0 or newer". Add `platforms: [.macOS(.v13)]` (or later) to `Package.swift`. The companion package already says `.macOS(.v14)`, and single-file scripts run with `swift` don't need it.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: don't time with Date">
You may see older code timing with `Date()`. A `Date` follows the wall clock, which can jump when the computer syncs its time or the clocks change, so differences between two dates can even come out negative. `ContinuousClock` only ever moves forward.
</Callout>
