## Why it matters

When code gives the wrong answer, the quickest fix starts with seeing what it's actually doing. Adding `print` calls works, but each guess means editing and re-running. A **debugger** lets you pause a running program on any line, look at every variable, and move forward one step at a time. It's a trace table (M03) that fills itself in. Swift's debugger is **LLDB**. It's built into Xcode, and you can also use it from Terminal.

## Breakpoints: pause here

A **breakpoint** marks a line where the program should pause, just *before* that line runs. While it's paused, nothing changes, so you can inspect anything you like, then let it carry on.

**In Xcode:** click the line number in the editor's left margin. A blue arrow appears. Run the program (Command-R) and it stops when it reaches that line. The **debug area** at the bottom shows the current variables on the left and the LLDB **console** on the right, with an `(lldb)` prompt where you can type commands. Click the arrow again to switch the breakpoint off, or drag it out of the margin to delete it.

**For this course's problems,** open the `dsa-swift` folder in Xcode, put a breakpoint inside your function in `Sources/Exercises`, then run one test with the diamond next to it. The test calls your code and Xcode stops on your line.

Breakpoints need a debug build. In a release build the optimiser has rearranged and removed so much that lines and variables no longer match your source.

## A program to debug

Here's a small executable package's `main.swift`. It builds running totals: each element of the result is the sum of the numbers so far.

```swift title="Sources/Totals/main.swift" highlight=11
struct Point {
    var x: Int
    var y: Int
}

func runningTotals(_ numbers: [Int]) -> [Int] {
    var totals: [Int] = []
    var sum = 0
    for number in numbers {
        sum += number
        totals.append(sum)
    }
    return totals
}

let start = Point(x: 2, y: 3)
let result = runningTotals([3, 9, 4])
print(result, start.x)
```

## Starting LLDB from Terminal

Build in debug, then start LLDB with the path to the program. Set a breakpoint on line 11 and run:

```bash
swift build
lldb .build/debug/Totals
```

```text title="The session (trimmed)"
(lldb) breakpoint set --file main.swift --line 11
Breakpoint 1: where = Totals`runningTotals(_:) + 296 at main.swift:11:23, address = 0x0000000100000c54
(lldb) run
Process 16972 stopped
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
    frame #0: 0x0000000100000c54 Totals`runningTotals(numbers=3 values) at main.swift:11:23
   8        var sum = 0
   9        for number in numbers {
   10           sum += number
-> 11           totals.append(sum)
   12       }
   13       return totals
   14   }
```

The arrow `->` marks the line about to run. `sum += number` has happened; `totals.append(sum)` hasn't yet. The short form `b main.swift:11` sets the same breakpoint.

## Looking at values

Three commands show values, each a little differently.

**`frame variable`**, or **`v`** for short, lists the local variables of the current function. It reads memory directly, so it's fast and never runs your code:

```text
(lldb) frame variable
([Int]) numbers = 3 values {
  [0] = 3
  [1] = 9
  [2] = 4
}
([Int]) totals = 0 values {}
(Int) sum = 3
(Int) number = 3
```

Each line shows the type in brackets, the name and the value. On the first pass through the loop, `sum` is 3 and nothing has been appended yet.

**`p`** (print) shows the value of a variable or expression. It can also evaluate code such as `p sum * 2`:

```text
(lldb) p sum
(Int) 3
(lldb) p numbers
([Int]) 3 values {
  [0] = 3
  [1] = 9
  [2] = 4
}
```

**`po`** (print object) shows a value the way Swift describes it, which for structs reads nicely:

```text
(lldb) po numbers
▿ 3 elements
  - 0 : 3
  - 1 : 9
  - 2 : 4
(lldb) po start
▿ Point
  - x : 2
  - y : 3
```

Use `v` for locals, `p` for expressions, and `po` when you want Swift's own description.

## Where am I? The backtrace

**`bt`** (backtrace) lists the **call stack**: the function you're paused in, the function that called it, and so on. These are the call frames from [Stack vs heap](/dsa/learn/swift-stack-heap):

```text
(lldb) bt
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
  * frame #0: 0x0000000100000c54 Totals`runningTotals(numbers=3 values) at main.swift:11:23
    frame #1: 0x0000000100000a00 Totals`main at main.swift:17:14
    frame #2: 0x000000018fd9cd7c dyld`start + 6652
```

Frame 0 is `runningTotals`, called from line 17 of `main.swift`. In recursive code, `bt` shows one frame per active call, which is a great way to see how deep the recursion has gone. When a program crashes in the debugger, `bt` is the first thing to type: it shows exactly how the program reached the crash.

## Moving through the code

| Command | Short | What it does |
| --- | --- | --- |
| `continue` | `c` | run until the next breakpoint (or the end) |
| `next` | `n` | run the current line, stepping **over** any function it calls |
| `step` | `s` | run the current line, stepping **into** a function it calls |
| `finish` | | run until the current function returns |

Continuing from the breakpoint stops on line 11 again, in the next loop iteration:

```text
(lldb) continue
Process 16972 resuming
Process 16972 stopped
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
-> 11           totals.append(sum)
(lldb) p totals
([Int]) 1 value {
  [0] = 3
}
(lldb) next
-> 12       }
(lldb) next
-> 9        for number in numbers {
(lldb) p totals
([Int]) 2 values {
  [0] = 3
  [1] = 12
}
```

Each `next` ran one line. After the append, `totals` holds `[3, 12]`. Stepping and printing like this, you can watch an algorithm's state change exactly as you'd trace it on paper. (The session output is trimmed here; LLDB shows the surrounding lines after every step.)

In Xcode, the same commands are buttons above the console: Continue, Step Over, Step Into and Step Out, which is `finish`.

## Conditional breakpoints

A breakpoint inside a loop that runs 10,000 times is useless if the bug only appears near the end. Give it a **condition**, and it only pauses when the condition is true:

```text
(lldb) breakpoint set --file main.swift --line 11 --condition 'sum > 10'
Breakpoint 2: where = Totals`runningTotals(_:) + 296 at main.swift:11:23, address = 0x0000000100000c54
(lldb) run
(lldb) p sum
(Int) 12
```

It skipped the first iteration, where `sum` was 3, and stopped when `sum` became 12. In Xcode, right-click a breakpoint, choose **Edit Breakpoint**, and type the condition, such as `i == 999`.

## Changing a value to test an idea

`expression` runs code inside the paused program, including assignments. It lets you test a hunch, such as "what if `sum` were 100 here?", without editing and rebuilding:

```text
(lldb) expression sum = 100
(lldb) p sum
(Int) 100
```

## Cheat sheet

| Command | Short form | Use |
| --- | --- | --- |
| `breakpoint set --file f.swift --line 11` | `b f.swift:11` | pause on a line |
| `breakpoint list` / `breakpoint delete` | `br list` / `br del` | see or remove breakpoints |
| `run` | `r` | start the program |
| `frame variable` | `v` | show local variables |
| `p expr` / `po expr` | | show a value |
| `bt` | | show the call stack |
| `next` / `step` / `finish` / `continue` | `n` / `s` / `finish` / `c` | move through the code |
| `expression x = 5` | `e x = 5` | change a value |
| `quit` | `q` | leave LLDB |

## A debugging routine

1. **Shrink the input.** Find the smallest input that still goes wrong. Bugs in `[3, 9, 4]` are far easier to follow than in a thousand numbers.
2. **Predict.** Before running, write down what each variable should be at the line you'll stop on.
3. **Pause just before the suspect code** and compare the real values with your prediction. The first place they differ is where the bug is.
4. **Fix it, then add a test** for that input, so the bug can never come back unnoticed.

<Callout kind="gotcha" title="Swift gotcha: debug builds only">
In a release build, LLDB often says a variable is "optimised away" or jumps between lines in a strange order, because the optimiser has merged and removed code. If debugging looks confusing, check that you're running a debug build: `swift build` or Xcode's Run button, not `-c release`.
</Callout>
