## Why it matters

Every practice problem in this course is checked by tests in the companion package, and so far you've only run them. This lesson teaches you to read them properly and to write your own. Tests are runnable examples that check themselves: they catch the edge case you forgot, prove a fix worked, and tell you instantly when a later change breaks something. "How would you test this?" is also one of the most common follow-up questions in interviews.

**Swift Testing** is Swift's modern testing library. It ships with the Swift 6 toolchain and is what the companion package uses.

## A test file, line by line

Here's a real file from the companion package, `Tests/DSATests/orientation/LargestElementTests.swift`, shortened a little:

```swift title="LargestElementTests.swift"
import Testing
#if SOLUTIONS
import Solutions
#else
import Exercises
#endif

@Suite struct LargestElementTests {
    @Test("Works when every number is negative")
    func allNegative() {
        #expect(LargestElement.largest(in: [-5, -2, -8]) == -2)
    }

    @Test("Returns nil for an empty array")
    func empty() {
        #expect(LargestElement.largest(in: []) == nil)
    }
}
```

- **`import Testing`** brings in the library.
- **`#if SOLUTIONS`** is a compile-time switch. Normally the tests check your code in `Exercises`. Building with `-Xswiftc -DSOLUTIONS` defines the name `SOLUTIONS`, so the same tests check the reference answers instead.
- **`@Suite struct LargestElementTests`** groups related tests. The suite's name is what `swift test --filter LargestElementTests` matches.
- **`@Test`** marks a function as a test. The string is an optional display name shown in results.
- **`#expect(…)`** checks that something is true.

Words starting with `@` here are **attributes**, which attach extra meaning to a declaration. Words starting with `#` are **macros**: code that the compiler expands into more code. You don't need to know how either works inside to use them.

## @Test: a test is a function

A test is an ordinary function marked `@Test`. It takes no parameters (unless you give it arguments, below) and returns nothing. If it finishes without recording a problem, it passes.

```swift
@Test func addsTwoNumbers() {
    #expect(2 + 2 == 4)
}

@Test("Adding zero changes nothing")
func addingZero() {
    #expect(7 + 0 == 7)
}
```

The function name can be anything. Choose names, or display names, that say what behaviour is being checked, because that's what you'll read when a test fails.

## #expect: check, and keep going

`#expect` takes any condition. When it's false, the test records an **issue** and fails, but it keeps running, so one run can report several problems. Its best feature is the failure message. Suppose this test fails:

```swift
@Test func secondLargestOfFour() {
    #expect(secondLargest(in: [4, 9, 2, 7]) == 7)
}
```

```text title="What you'll see"
✘ Test secondLargestOfFour() recorded an issue at StatsTests.swift:5:5: Expectation failed: secondLargest(in: [4, 9, 2, 7]) == 7
  secondLargest(in: [4, 9, 2, 7]) == 7 → false
    secondLargest(in: [4, 9, 2, 7]) → 9
      some → 9
```

Because `#expect` is a macro, it can see the expression you wrote, not just `true` or `false`. It shows you each part's value: your function returned 9, the largest rather than the second largest. (`some → 9` is how it shows an optional that holds 9.) Write checks as plain comparisons like `actual == expected` and you get this detail for free.

## #require: stop if this fails

Sometimes the rest of a test makes no sense if one check fails. `#require` checks a condition and, if it's false, **stops the test** by throwing an error. So the test function must be marked `throws`, and you write `try` in front:

```swift
@Test func firstElementIsSmallest() throws {
    let sorted = [5, 3, 8].sorted()
    let first = try #require(sorted.first)    // stops here if sorted is empty
    #expect(first == 3)
}
```

`#require` has a second job, shown here: given an optional, it **unwraps** it. If `sorted.first` were `nil`, the test would stop there and report `sorted.first → nil`, instead of carrying on with a meaningless value. Use `#expect` by default, and `#require` when later lines depend on the result.

## Testing that code throws

To check that a function throws, pass the code in a closure to `#expect(throws:)`. You can name the exact error, if the error type is `Equatable`, or just its type:

```swift
enum AgeError: Error, Equatable {
    case empty
    case notANumber(String)
}

@Test func rejectsBadAges() {
    #expect(throws: AgeError.empty) {
        try parseAge("")
    }
    #expect(throws: AgeError.self) {
        try parseAge("forty")
    }
}
```

The first check passes only if `parseAge("")` throws exactly `AgeError.empty`. The second passes for any `AgeError`. Both fail if the code doesn't throw at all.

## Many cases with arguments

Testing a function on a table of inputs is so common that Swift Testing has a feature for it. Give `@Test` an `arguments:` collection and add a matching parameter. The test runs once per element, and each run is reported separately:

```swift
@Test("Second largest", arguments: [
    ([4, 9, 2, 7], 7),
    ([1, 2], 1),
    ([5, 5, 3], 3),
    ([-8, -3, -5], -5),
])
func secondLargestCases(numbers: [Int], expected: Int) {
    #expect(secondLargest(in: numbers) == expected)
}
```

Each element is a tuple (M02), and its two parts fill the two parameters. When one case fails, the report names it:

```text title="What you'll see"
✘ Test "Second largest" recorded an issue with 2 arguments numbers → [5, 5, 3], expected → 3 at StatsTests.swift:12:5: Expectation failed: secondLargest(in: numbers) == expected
  secondLargest(in: numbers) == expected → false
    secondLargest(in: numbers) → 5
      some → 5
    expected → 3
✘ Test "Second largest" with 4 test cases failed after 0.001 seconds with 1 issue.
```

Three cases passed and one didn't: duplicates of the largest value broke this version. Adding a row to the table is all it takes to cover a new edge case.

## Suites group tests

`@Suite` on a struct groups its tests, gives them one name to filter by, and lets them share helpers:

```swift
@Suite("Second largest") struct SecondLargestTests {
    let sample = [4, 9, 2, 7]

    @Test func normalCase() {
        #expect(secondLargest(in: sample) == 7)
    }

    @Test func tooFewNumbers() {
        #expect(secondLargest(in: [3]) == nil)
        #expect(secondLargest(in: []) == nil)
    }
}
```

Swift Testing creates a **new instance** of the suite for every test, so each test starts with fresh stored properties like `sample`. One test can't leave a mess behind for the next.

## Running tests

From the package folder in Terminal:

```bash
swift test                                   # every test
swift test --filter SecondLargestTests       # only names that match
swift test -Xswiftc -DSOLUTIONS --filter SecondLargestTests
```

In Xcode, open the package folder, then click the diamond next to a test or suite to run it, or press Command-U to run everything. Failed checks appear as red marks on the exact lines.

Tests run **in parallel** by default, and in no fixed order. That's fast, but it means two tests must never depend on, or change, the same global variable. Keep each test's data inside the test or the suite.

## Writing tests for your own code

When you've solved a problem, add tests in this order:

1. **The examples** from the problem statement.
2. **Edge cases**: empty input, one element, all elements equal, negatives, the largest allowed values.
3. **Anything the statement promises**, such as "returns `nil` when…".
4. **A case that broke** an earlier attempt, so the bug can never return unnoticed.

<Callout kind="gotcha" title="Swift gotchas in tests">
- **Don't use `assert` in tests.** It's removed in optimised builds and crashes the whole test run instead of reporting. Use `#expect` and `#require`.
- **Two argument lists test every combination.** `@Test(arguments: [1, 2], [10, 20])` runs four cases: (1, 10), (1, 20), (2, 10), (2, 20). To pair inputs with outputs, pass one list of tuples, or `zip(inputs, outputs)`.
- **Be careful comparing `Double` values with `==`.** `0.1 + 0.2 == 0.3` is false (M02). Check that the difference is tiny instead: `#expect(abs(result - 0.3) < 1e-9)`.
</Callout>
