## Why it matters

The same Swift code can run a hundred times faster or slower depending on one setting: whether it's built for **debugging** or for **release**. Everything you've run so far has been a debug build. That's right for writing and testing code, and completely wrong for judging how fast an algorithm is. Online judges, interview platforms and the App Store all use optimised builds, so before you measure anything, you need to know the difference.

## Two kinds of build

When the compiler turns your Swift into a program, it can aim for one of two things.

A **debug build** is made for you, the developer. It compiles quickly, every line of your code becomes its own steps in the program, and every variable stays in memory where the debugger can show it. `assert` checks are switched on. The compiler setting is called `-Onone`: no optimisation.

A **release build** is made for users. The compiler's **optimiser** rewrites your program to do the same thing in far fewer steps. It takes longer to compile, `assert` checks are removed, and the result is much harder to step through in a debugger. The setting is `-O`.

| | Debug (`-Onone`) | Release (`-O`) |
| --- | --- | --- |
| Speed of the program | slow | fast |
| Speed of compiling | fast | slower |
| Debugger | shows every line and variable | lines jump around; values "optimised away" |
| `assert` | checked | removed |
| `precondition`, bounds and overflow checks | checked | checked |

## Choosing the build from Terminal

`swift build`, `swift run` and `swift test` make debug builds unless you ask otherwise. Add `-c release` (`-c` is short for configuration) to get an optimised one:

```bash
swift build                    # debug build, in .build/debug/
swift build -c release         # release build, in .build/release/
swift run -c release           # build optimised, then run
```

Single files work the same way. `swift file.swift` runs your code unoptimised; add `-O` to optimise it, or compile it into a program with `swiftc`:

```bash
swift sort.swift               # unoptimised
swift -O sort.swift            # optimised
swiftc -O sort.swift -o sort   # compile an optimised program called sort
./sort                         # run it
```

In Xcode, the **Run** button (Command-R) and tests use the Debug configuration. **Profile** (Command-I) and **Archive**, which makes the version you submit to the App Store, use Release. You can change which configuration Run uses under Product › Scheme › Edit Scheme.

## Seeing the difference

Here's a deliberately slow sort, bubble sort, which you'll study properly in Part IV. It compares neighbouring elements and swaps them until the array is in order, doing about 12.5 million comparisons for 5,000 numbers:

```swift title="Sources/Bench/main.swift"
func bubbleSort(_ items: inout [Int]) {
    for end in stride(from: items.count - 1, to: 0, by: -1) {
        for i in 0..<end where items[i] > items[i + 1] {
            items.swapAt(i, i + 1)
        }
    }
}

let n = 5_000
var numbers = (0..<n).map { ($0 * 7_919) % n }

let clock = ContinuousClock()
let elapsed = clock.measure {
    bubbleSort(&numbers)
}
print("Sorted \(n) numbers in \(elapsed)")
print("First: \(numbers[0]), last: \(numbers[n - 1])")
```

Run in both configurations on one Mac, it printed:

```text title="One run on a recent Mac (your numbers will differ)"
$ swift run
Sorted 5000 numbers in 1.565883958 seconds
First: 0, last: 4999

$ swift run -c release
Sorted 5000 numbers in 0.008495875 seconds
First: 0, last: 4999
```

The same code, the same answer, and about **180 times faster**. Timing code is the next lesson's topic; for now, notice that a debug measurement would have told you this sort is hopeless for 5,000 numbers, when in a release build it takes under a hundredth of a second. Gaps of 10–100× are normal for tight loops over arrays, which is exactly what algorithms are made of.

## What the optimiser does

You don't need the details, but knowing the main tricks explains why the gap is so large:

- **Inlining.** `items[i]` and `items.swapAt(i, i + 1)` are function calls into the standard library. A debug build really makes those calls, millions of times. The optimiser copies the body of small functions straight into your loop, so the calls disappear.
- **Specialising generics.** `Array` works with any element type (M10). The optimiser makes a version of the code only for `Int`, which is much faster than code that handles any type.
- **Removing reference counting.** It deletes ARC count updates (M11) that it can prove aren't needed.
- **Keeping values in registers**, the processor's fastest storage, instead of memory.
- **Deleting unused work.** Code whose result is never used can be removed entirely.

## What release builds still check

An optimised build is not an unsafe build. These still stop the program with a clear message:

- integer overflow, such as `Int.max + 1` (M02);
- an array index out of range;
- force unwrapping `nil`;
- a failed `precondition` or a `fatalError`.

There is a third setting, `-Ounchecked`, which removes overflow checks, bounds checks and preconditions to squeeze out the last bit of speed. Mistakes then cause undefined behaviour instead of a clear crash. You'll see it in Part IX; don't use it for everyday code.

## Which one when

1. **Write and test in debug.** `swift test` and Xcode's Run button already do this. Correctness first, with every check and the debugger available.
2. **Measure in release.** Any time you ask "is this fast enough?", build with `-c release` or `-O`.
3. **Ship in release.** Judges, interview platforms and the App Store all run optimised code.

<Callout kind="gotcha" title="Swift gotcha: a slow test isn't proof of slow code">
`swift test` builds in debug, so a test over a large input can take seconds even when your algorithm is fine. Judge the *complexity* from the code, and time it in a release build before you rewrite it.
</Callout>

<Callout kind="gotcha" title="Swift gotcha: the optimiser deletes unused results">
If you time a loop whose result you never use, a release build may remove the loop completely and report a time of almost zero. Always use the result, for example by printing it, as the example above prints the first and last elements.
</Callout>
