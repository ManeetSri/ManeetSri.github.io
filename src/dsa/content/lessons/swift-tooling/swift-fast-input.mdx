## Why it matters

Competitive programming problems often give you hundreds of thousands, or millions, of numbers, with a time limit of one or two seconds. Reading the input is part of your program's running time, and so is printing the answer. The friendly `readLine()` approach from [Reading input with readLine](/dsa/learn/swift-reading-input) is fine for most problems; this lesson shows the faster technique competitive programmers use when the input is huge, and how to tell when you need it. Interviews never require it.

## Where the time goes

Reading a line of a million numbers the usual way looks like this:

```swift
let n = Int(readLine()!)!
let numbers = readLine()!.split(separator: " ").map { Int($0)! }
```

It's short and clear, but it does a lot of work behind the scenes:

1. `readLine()` builds one enormous `String`, millions of characters long.
2. `split` creates an array with a `Substring` for every number.
3. `Int($0)` parses each piece using general-purpose code that handles any kind of string.
4. `map` builds the final array.

Each step is reasonable, but together they handle every character several times and create a lot of short-lived objects.

## How slow is it really?

Here are measurements of reading a million numbers between -10⁹ and 10⁹ and adding them up, built in release mode on one Mac:

```text title="Processor time for 1,000,000 numbers (one run; yours will differ)"
readLine + split + map     about 0.17 seconds
byte scanner (below)       about 0.03 seconds
```

So the simple way is not a disaster on a fast computer: under a fifth of a second. But it's several times slower than it needs to be. Judges often run on slower machines, and if your algorithm already uses most of the time limit, the difference between 0.03 and 0.17 seconds can decide the verdict. With inputs below about 10⁵ numbers, don't bother: use `readLine()`.

## Read everything at once, as bytes

The fast approach skips strings entirely:

1. Read **all** of standard input in one go, as raw bytes.
2. Walk through the bytes with an index, building each number digit by digit.

Text is stored as bytes, one per character for digits, spaces and newlines, using **ASCII** codes: `"0"` is 48, `"9"` is 57, `"-"` is 45, a space is 32, and a newline is 10. You met these in M08's `asciiValue` and `[UInt8]` lessons. `UInt8(ascii: "0")` gives the code without having to remember it.

Reading everything needs `FileHandle` from **Foundation**, Apple's large library of extra tools beyond the standard library. `import Foundation` makes it available.

## A fast reader

Here's a complete, reusable reader. It keeps all the bytes and a `position`, and each call to `readInt()` reads the next whole number:

```swift title="FastReader.swift"
import Foundation

struct FastReader {
    private let bytes: [UInt8]
    private var position = 0

    init() {
        bytes = [UInt8](FileHandle.standardInput.readDataToEndOfFile())
    }

    mutating func readInt() -> Int {
        // Skip spaces, newlines and anything else up to ASCII 32
        while position < bytes.count && bytes[position] <= 32 {
            position += 1
        }
        var isNegative = false
        if position < bytes.count && bytes[position] == UInt8(ascii: "-") {
            isNegative = true
            position += 1
        }
        var value = 0
        while position < bytes.count {
            let byte = bytes[position]
            guard byte >= UInt8(ascii: "0") && byte <= UInt8(ascii: "9") else { break }
            value = value * 10 + Int(byte - UInt8(ascii: "0"))
            position += 1
        }
        return isNegative ? -value : value
    }
}
```

How `readInt()` works:

- **Skip separators.** Every byte with a code of 32 or less is a space, tab, newline or other invisible character, so it moves past all of them. It doesn't matter whether numbers are split across lines.
- **Sign.** If the next byte is `-`, remember that and move on.
- **Digits.** For each digit byte, `byte - 48` is its value from 0 to 9, and `value * 10 + digit` shifts the number one place left and adds the digit. Reading `"472"` gives 4, then 47, then 472: the same digit trick as M08's character conversions.
- It stops at the first byte that isn't a digit, ready for the next call.

Using it is one line per number, whatever the layout of the input:

```swift title="main.swift"
var reader = FastReader()
let n = reader.readInt()
var total = 0
for _ in 0..<n {
    total += reader.readInt()
}
print(total)
```

```text title="A session"
$ printf '4\n10 -3\n  7\n100\n' | swift main.swift
114
```

(`printf` prints text with `\n` turned into newlines, so it's a handy way to pipe in test input.) The numbers 10, -3, 7 and 100 are spread over three lines with odd spacing, and the reader doesn't care.

## Fast output

Printing has the same problem in reverse. Calling `print` a million times means a million separate trips to the output. Collect the lines and print once instead:

```swift
var output: [String] = []
output.reserveCapacity(n)
for answer in answers {
    output.append(String(answer))
}
print(output.joined(separator: "\n"))
```

Printing the numbers 0 to 999,999 to a file took about 0.31 seconds with one `print` per line, and 0.03 seconds collected and printed once, in the same release build. `reserveCapacity` (M07) sets aside room for all the lines up front, so the array never has to grow.

## When to use which

| Input size | Reading | Printing |
| --- | --- | --- |
| up to about 10⁵ numbers | `readLine()` and `split` | `print` per line is fine |
| 10⁵ to 10⁶ or more | byte reader | collect, then print once |

Whichever you use, test it with the problem's sample input in a file: `swift main.swift < sample.txt`.

<Callout kind="gotcha" title="Swift gotchas with fast input">
- **It trusts the input.** The scanner assumes well-formed numbers. It doesn't handle a leading `+`, decimals or numbers too big for `Int`; judge input is guaranteed valid, so that's normally fine.
- **Interactive problems are different.** In a few problems the judge replies to each answer you print. You can't read everything up front there, because the input doesn't exist yet: read line by line with `readLine()`.
- **Time it in release.** In a debug build both approaches are slow, and the comparison tells you little. Use `swiftc -O` or `swift -O`, as judges do.
</Callout>
