## Why it matters

Given n points on a plane, which two are closest together? Air traffic control asks it about aircraft, a map app asks it when merging duplicate pins, and a game asks it to find the first two objects about to collide. Checking every pair is O(n²): fine for a hundred points, hopeless for a million. Divide and conquer solves it in **O(n log n)**, and the argument behind it is one of the most elegant in the subject: after splitting, only a narrow strip near the dividing line needs checking, and each point in it needs only a handful of comparisons.

## The brute force, with squared distances

The distance between (x₁, y₁) and (x₂, y₂) is √((x₁ − x₂)² + (y₁ − y₂)²). To find the closest pair you only ever **compare** distances, and the square root never changes which of two distances is smaller: if a² is less than b², then a is less than b. So compare **squared** distances and skip the square root entirely. With whole-number coordinates, everything stays an exact `Int`.

```swift run
struct Point {
    let x: Int
    let y: Int
}

func squaredDistance(_ a: Point, _ b: Point) -> Int {
    let dx = a.x - b.x
    let dy = a.y - b.y
    return dx * dx + dy * dy
}

// Try every pair: n(n - 1)/2 distances
func closestBruteForce(_ points: [Point]) -> (Point, Point) {
    var best = (points[0], points[1])
    for i in points.indices {
        for j in (i + 1)..<points.count where squaredDistance(points[i], points[j]) < squaredDistance(best.0, best.1) {
            best = (points[i], points[j])
        }
    }
    return best
}

let points = [(2, 3), (12, 30), (40, 50), (5, 1), (12, 10), (3, 4)].map { Point(x: $0.0, y: $0.1) }
let (a, b) = closestBruteForce(points)
let squared = squaredDistance(a, b)
print("(\(a.x), \(a.y)) and (\(b.x), \(b.y)): squared distance \(squared), distance \((Double(squared).squareRoot() * 1_000).rounded() / 1_000)")
```

```output
(2, 3) and (3, 4): squared distance 2, distance 1.414
```

Take the square root once, at the very end, if the answer needs the real distance.

<Callout kind="gotcha" title="Why not Double?">
A `Double` holds integers exactly only up to 2⁵³, about 9 × 10¹⁵. Squared distances between coordinates of size 10⁹ reach 10¹⁸, where neighbouring whole numbers become indistinguishable:

```swift run
let first = 1_000_000_000_000_000_000
let second = first + 1
print(first < second)
print(Double(first) < Double(second))
```

```output
true
false
```

`Int` keeps them apart. With coordinates up to 10⁹ in size, a squared distance is at most 8 × 10¹⁸, which still fits below `Int.max`, about 9.2 × 10¹⁸. Much bigger coordinates would overflow, and Swift would stop with an overflow error rather than give a wrong answer.
</Callout>

## Split by x

Sort the points by x, and split them at the middle into a left half and a right half, separated by a vertical line at the middle point's x. The closest pair is either:

1. both in the **left** half;
2. both in the **right** half;
3. **split**: one on each side of the line.

Solve cases 1 and 2 recursively, and call the smaller of their answers **d**. It's the same three-way split as the maximum subarray, and again the third case is the combine step. Checking every left point against every right point would be O(n²) again, so the question is how to avoid it.

## The strip

A split pair that beats d has a horizontal gap smaller than d, so **both points lie within d of the dividing line**. Everything farther out can be ignored. That leaves a **strip** of width 2d around the line.

That might still be every point: picture all the points crowded near the line. The second observation saves the day. Sort the strip's points by y. For a point p, a partner closer than d must also be within d **vertically**, so you only need to look at the points after p in y order until the vertical gap reaches d.

And there can only be a few of those. They all sit in a rectangle d tall and 2d wide, just above p. Cut that rectangle into eight squares of side d/2, four on each side of the line. Two points in the same square would be at most d/√2 apart, which is less than d. But both would be on the same side of the line, and every pair on the same side is at least d apart. So each square holds at most one point: at most **8** points in the rectangle, p included, and at most **7** comparisons for p. The inner loop is O(1) per point, and the whole strip is O(n).

<Callout kind="analogy">
Think of chairs in a crowded hall where nobody on the same side of the aisle may sit closer than d to anyone else. However packed the hall is, only a few people can fit in the little d by 2d patch in front of you, so you never have to check more than a handful of neighbours.
</Callout>

## The algorithm

Sorting the strip by y at every level would cost O(n log n) per level, giving O(n log² n) overall. The fix is the trick from counting inversions: make each call return its range **sorted by y**, by merging the two halves as merge sort does. Then the strip comes out in y order with no sorting at all.

```swift run
struct Point {
    let x: Int
    let y: Int
}

func squaredDistance(_ a: Point, _ b: Point) -> Int {
    let dx = a.x - b.x
    let dy = a.y - b.y
    return dx * dx + dy * dy
}

var mostChecks = 0                                 // the most strip comparisons made for any one point

// The smallest squared distance in points[low..<high], which arrive sorted by x.
// Like merge sort, each call leaves its range sorted by y, so the strip comes out in y order for free.
func closest(_ points: inout [Point], _ buffer: inout [Point], _ low: Int, _ high: Int) -> Int {
    if high - low <= 3 {                           // tiny ranges: try every pair, then sort by y
        var best = Int.max
        for i in low..<high {
            for j in (i + 1)..<high {
                best = min(best, squaredDistance(points[i], points[j]))
            }
        }
        points[low..<high].sort { $0.y < $1.y }
        return best
    }
    let mid = low + (high - low) / 2
    let lineX = points[mid].x                      // read it before the calls reorder the range
    var best = min(closest(&points, &buffer, low, mid), closest(&points, &buffer, mid, high))

    // Merge the two halves by y, exactly as merge sort does
    for index in low..<high {
        buffer[index] = points[index]
    }
    var left = low
    var right = mid
    for write in low..<high {
        if right == high || (left < mid && buffer[left].y <= buffer[right].y) {
            points[write] = buffer[left]
            left += 1
        } else {
            points[write] = buffer[right]
            right += 1
        }
    }

    // The strip: points closer to the dividing line than the best distance so far, in y order
    var strip: [Point] = []
    for point in points[low..<high] where (point.x - lineX) * (point.x - lineX) < best {
        strip.append(point)
    }
    for i in strip.indices {
        var j = i + 1
        var checks = 0
        while j < strip.count && (strip[j].y - strip[i].y) * (strip[j].y - strip[i].y) < best {
            best = min(best, squaredDistance(strip[i], strip[j]))
            j += 1
            checks += 1
        }
        mostChecks = max(mostChecks, checks)
    }
    return best
}

func closestPair(_ input: [Point]) -> Int {
    var points = input.sorted { ($0.x, $0.y) < ($1.x, $1.y) }
    var buffer = points
    return closest(&points, &buffer, 0, points.count)
}

func closestBruteForce(_ points: [Point]) -> Int {
    var best = Int.max
    for i in points.indices {
        for j in (i + 1)..<points.count {
            best = min(best, squaredDistance(points[i], points[j]))
        }
    }
    return best
}

let small = [(2, 3), (12, 30), (40, 50), (5, 1), (12, 10), (3, 4)].map { Point(x: $0.0, y: $0.1) }
print("small example:", closestPair(small))

// A seeded generator, so the "random" points are the same on every run
var seed: UInt64 = 65
func nextRandom(_ range: ClosedRange<Int>) -> Int {
    seed = seed &* 6_364_136_223_846_793_005 &+ 1_442_695_040_888_963_407
    return range.lowerBound + Int((seed >> 33) % UInt64(range.count))
}

var agree = 0
for _ in 0..<200 {
    let points = (0..<nextRandom(2...60)).map { _ in Point(x: nextRandom(-50...50), y: nextRandom(-50...50)) }
    if closestPair(points) == closestBruteForce(points) {
        agree += 1
    }
}
print("agrees with brute force on \(agree) of 200 random sets")

mostChecks = 0
let many = (0..<100_000).map { _ in Point(x: nextRandom(0...1_000_000_000), y: nextRandom(0...1_000_000_000)) }
print("100,000 points: closest squared distance \(closestPair(many)), most strip checks for one point: \(mostChecks)")
```

```output
small example: 2
agrees with brute force on 200 of 200 random sets
100,000 points: closest squared distance 190394073, most strip checks for one point: 2
```

What to notice:

- **Ranges of 3 or fewer points** are solved by brute force. Splitting them further would leave a half with a single point, which has no pairs at all.
- **The strip test uses the current best**, which can only shrink as the strip finds closer pairs, so later points get an even narrower window.
- **The inner loop stops on the vertical gap**, not after a fixed 7 steps. The packing argument promises it stops quickly; on 100,000 random points no point needed more than 2 comparisons.
- **The brute force on 100,000 points** would compute about 5 billion distances. The divide-and-conquer version does a few million operations.

## Why it's O(n log n)

Sorting by x once costs O(n log n). After that, each call does two half-size calls, a linear merge, a linear pass to build the strip and a linear scan of the strip: T(n) = 2T(n / 2) + n, merge sort's recurrence again. Total: **O(n log n)** time and O(n) extra memory.

| Version | Recurrence | Total |
| --- | --- | --- |
| Every pair | | O(n²) |
| Sort the strip by y at every level | 2T(n / 2) + n log n | O(n log² n) |
| Return each range sorted by y | 2T(n / 2) + n | O(n log n) |

The middle row is a perfectly good solution in practice, and easier to write. The last lesson of this module shows how the Master theorem handles that extra log factor.

There's also a randomised method, built on a grid of cells of side d, that runs in expected O(n) time. You'll meet that style of algorithm in Part VIII, along with the rest of computational geometry.

<Callout kind="gotcha" title="Common mistakes">
- **Reading the dividing line after the recursive calls.** The calls re-sort their ranges by y, so `points[mid]` is a different point afterwards. Save `lineX` first.
- **Comparing against d instead of d².** Everything is squared: the strip test is `dx * dx < best` and the loop test is `dy * dy < best`, where `best` is a squared distance.
- **Using `<=` in the strip tests.** A point exactly d away can't give a pair strictly closer than d. `<=` is still correct, only slower.
- **Duplicate points.** Two identical points have distance 0. Nothing special is needed, as long as your code doesn't skip pairs with equal coordinates.
</Callout>
