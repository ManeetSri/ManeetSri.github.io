## Why it matters

You've already used divide and conquer several times without calling it a paradigm. [Merge sort](/dsa/learn/sort-merge) splits an array in half, sorts each half and merges them. [Binary search](/dsa/learn/bs-classic) throws half the range away and searches the rest. [Quick sort](/dsa/learn/sort-quick) partitions, then sorts both sides. This module names the pattern, so you can reach for it on purpose: multiplying huge numbers in cryptography, finding the closest pair among millions of points, and splitting work between processor cores all use the same three steps.

## Three steps

Every divide-and-conquer algorithm does the same three things:

1. **Divide** the problem into smaller problems of the **same kind**, usually two halves.
2. **Conquer** each smaller problem by calling the algorithm recursively. When a problem is small enough, solve it directly: that's the **base case**, exactly as in [Base case and recursive case](/dsa/learn/rec-what-is-recursion).
3. **Combine** the smaller answers into the answer for the whole problem.

Here's the smallest possible example: the largest value in an array, found by halves. Each call prints its range, indented by how deep it is:

```swift run
// The largest value, by divide and conquer. Each call prints its range, indented by depth.
func largest(_ numbers: [Int], _ low: Int, _ high: Int, depth: Int = 0) -> Int {
    let indent = String(repeating: "    ", count: depth)
    if high - low == 1 {                                   // base case: one element
        print("\(indent)\([numbers[low]]) → \(numbers[low])")
        return numbers[low]
    }
    print("\(indent)\(Array(numbers[low..<high]))")
    let mid = low + (high - low) / 2                       // divide
    let left = largest(numbers, low, mid, depth: depth + 1)    // conquer
    let right = largest(numbers, mid, high, depth: depth + 1)
    let answer = max(left, right)                          // combine
    print("\(indent)max(\(left), \(right)) = \(answer)")
    return answer
}

let numbers = [3, 9, 4, 1, 7, 2]
print("answer:", largest(numbers, 0, numbers.count))
```

```output
[3, 9, 4, 1, 7, 2]
    [3, 9, 4]
        [3] → 3
        [9, 4]
            [9] → 9
            [4] → 4
        max(9, 4) = 9
    max(3, 9) = 9
    [1, 7, 2]
        [1] → 1
        [7, 2]
            [7] → 7
            [2] → 2
        max(7, 2) = 7
    max(1, 7) = 7
max(9, 7) = 9
answer: 9
```

What to notice:

- The function works on a **range** `low..<high` of one shared array. Nothing is copied.
- The answers travel **upwards**: each call finishes only after both of its halves have finished.
- A loop would find the largest value just as fast. Divide and conquer earns its keep when the combine step is clever, as you'll see in every lesson of this module.

## Where the work happens

The three steps aren't equally hard in every algorithm. Some put the effort into dividing, some into combining:

| Algorithm | Divide | Subproblems | Combine |
| --- | --- | --- | --- |
| Binary search | compare with the middle | 1 of half the size | nothing |
| Merge sort | find the middle | 2 halves | merge: O(n) |
| Quick sort | partition: O(n) | 2 sides, any sizes | nothing |
| Largest by halves | find the middle | 2 halves | one `max` |

Merge sort and quick sort are mirror images. Merge sort splits without looking and does its thinking while merging. Quick sort does its thinking while partitioning, and then there's nothing left to combine.

In code, the shape is always the same:

```swift
func solve(_ low: Int, _ high: Int) -> Answer {
    if high - low <= smallSize {
        return directAnswer(low, high)          // base case
    }
    let mid = low + (high - low) / 2            // divide
    let left = solve(low, mid)                  // conquer
    let right = solve(mid, high)
    return combine(left, right)                 // combine
}
```

## Returning more than you were asked

Sometimes the combine step needs more than the answer itself. Suppose you want both the smallest **and** the largest value. Two separate scans compare every element twice: 2(n − 1) comparisons. Divide and conquer does better. A pair needs only one comparison to know which is smaller, and combining two (smallest, largest) answers needs two more:

```swift run
var comparisons = 0

// Both answers from one pass: smallest first, then largest
func twoScans(_ numbers: [Int]) -> (smallest: Int, largest: Int) {
    var smallest = numbers[0]
    var largest = numbers[0]
    for value in numbers.dropFirst() {
        comparisons += 2
        if value < smallest { smallest = value }
        if value > largest { largest = value }
    }
    return (smallest, largest)
}

// Divide and conquer: a pair needs one comparison, and combining two answers needs two
func smallestAndLargest(_ numbers: [Int], _ low: Int, _ high: Int) -> (smallest: Int, largest: Int) {
    if high - low == 1 {
        return (numbers[low], numbers[low])
    }
    if high - low == 2 {
        comparisons += 1
        let (a, b) = (numbers[low], numbers[low + 1])
        return a < b ? (a, b) : (b, a)
    }
    let mid = low + (high - low) / 2
    let left = smallestAndLargest(numbers, low, mid)
    let right = smallestAndLargest(numbers, mid, high)
    comparisons += 2
    return (min(left.smallest, right.smallest), max(left.largest, right.largest))
}

for n in [16, 1_024, 1_000_000] {
    let numbers = (0..<n).map { ($0 * 7_919) % n }
    comparisons = 0
    let first = twoScans(numbers)
    let scanCount = comparisons
    comparisons = 0
    let second = smallestAndLargest(numbers, 0, n)
    print("n = \(n): \(first == second ? "same answer" : "different!"), two scans \(scanCount), divide and conquer \(comparisons)")
}
```

```output
n = 16: same answer, two scans 30, divide and conquer 22
n = 1024: same answer, two scans 2046, divide and conquer 1534
n = 1000000: same answer, two scans 1999998, divide and conquer 1524286
```

About 3n/2 comparisons instead of 2n (exactly 3n/2 − 2 when n is a power of two). Both are O(n), so this only saves a constant factor, but the idea behind it runs through the whole module: **make each call return a small summary that's cheap to combine**. Counting inversions returns a sorted array alongside the count; the next lesson's maximum subarray returns four numbers instead of one.

## Independent or overlapping?

In everything so far, the two halves never share an element, so no piece of work is ever done twice. That's what makes divide and conquer efficient: the subproblems are **independent**.

Compare Fibonacci. `fib(n)` splits into `fib(n - 1)` and `fib(n - 2)`, but those two **overlap**: `fib(n - 1)` computes `fib(n - 2)` all over again inside itself.

```swift run
var fibonacciCalls = 0
var sortCalls = 0

// fib(n) splits into fib(n - 1) and fib(n - 2): the two parts overlap
func fibonacci(_ n: Int) -> Int {
    fibonacciCalls += 1
    return n < 2 ? n : fibonacci(n - 1) + fibonacci(n - 2)
}

// Merge sort's shape: the two halves never share an element
func mergeSortShape(_ low: Int, _ high: Int) {
    sortCalls += 1
    guard high - low > 1 else { return }
    let mid = low + (high - low) / 2
    mergeSortShape(low, mid)
    mergeSortShape(mid, high)
}

for n in [10, 20, 30] {
    fibonacciCalls = 0
    sortCalls = 0
    _ = fibonacci(n)
    mergeSortShape(0, n)
    print("n = \(n): fibonacci \(fibonacciCalls) calls for \(n + 1) different questions, merge sort \(sortCalls) calls")
}
```

```output
n = 10: fibonacci 177 calls for 11 different questions, merge sort 19 calls
n = 20: fibonacci 21891 calls for 21 different questions, merge sort 39 calls
n = 30: fibonacci 2692537 calls for 31 different questions, merge sort 59 calls
```

Fibonacci asks only n + 1 different questions, yet makes millions of calls, because the same questions are asked again and again. Merge sort's calls are all different ranges: 2n − 1 calls, each asked once. Watch the repeats appear in the Fibonacci tree:

```visual recursionTree
fn: fibonacci
n: 5
```

`fib(3)` is computed twice and `fib(2)` three times. When subproblems overlap like this, splitting alone doesn't help: you need to **remember** answers, as in [A preview of memoisation](/dsa/learn/rec-memo-preview). That's **dynamic programming**, which starts with [Overlapping subproblems and optimal substructure](/dsa/learn/dp-what-is-dp). A quick test tells the two paradigms apart: can the same subproblem turn up in two different branches? If not, it's divide and conquer.

## Recursion trees give the cost

To find the running time, draw the recursion tree, as in [Recursion trees and their complexity](/dsa/learn/rec-recursion-trees), write each call's own work beside it, and add up the tree level by level. For merge sort, each call merges as many elements as its range holds, so every level adds up to n. How evenly you split decides how many levels there are:

```swift run
// Work per level of the recursion tree when each call costs its size: halves vs a lopsided split
func levelTotals(_ n: Int, split: (Int) -> [Int]) -> [Int] {
    var totals: [Int] = []
    var level = [n]
    while !level.isEmpty {
        totals.append(level.filter { $0 > 1 }.reduce(0, +))   // a call on 1 element does no splitting work
        level = level.filter { $0 > 1 }.flatMap(split)
    }
    return totals.filter { $0 > 0 }
}

let halves = levelTotals(16) { [$0 / 2, $0 - $0 / 2] }
let lopsided = levelTotals(16) { [1, $0 - 1] }
print("halves:  ", halves, "total", halves.reduce(0, +))
print("lopsided:", lopsided, "total", lopsided.reduce(0, +))
```

```output
halves:   [16, 16, 16, 16] total 64
lopsided: [16, 15, 14, 13, 12, 11, 10, 9, 8, 7, 6, 5, 4, 3, 2] total 135
```

Halves give log₂ n levels of n work: O(n log n). Peeling off one element at a time gives n levels: O(n²), which is exactly quick sort's worst case. For a million elements, that's the difference between about 20 million steps and 500 billion. **Balanced splits** are what make divide and conquer fast.

Written as a [recurrence](/dsa/learn/bigo-recurrences), the balanced version is T(n) = 2T(n / 2) + n. Most divide-and-conquer costs have the form T(n) = a · T(n / b) + f(n), which the [Master theorem](/dsa/learn/bigo-master-theorem) solves at a glance. The last lesson of this module applies it to everything you meet here.

<Callout kind="gotcha" title="Common mistakes">
- **Copying instead of passing a range.** `Array(numbers[low..<mid])` copies, and doing that at every level adds O(n) memory traffic per level. Pass `low` and `high` instead. If you do pass an `ArraySlice`, remember that it keeps the original indices, as in [ArraySlice and its index pitfalls](/dsa/learn/swift-array-slices).
- **A split that doesn't shrink.** With half-open ranges and `mid = low + (high - low) / 2`, both halves are strictly smaller whenever the range has two or more elements. Mix closed and half-open ranges and a two-element range can recurse forever.
- **Forgetting the smallest inputs.** Decide what an empty range or a single element returns before writing the recursive case.
</Callout>
