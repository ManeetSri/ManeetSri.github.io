## Why it matters

You learned [the Master theorem](/dsa/learn/bigo-master-theorem) in M14 as a way to solve recurrences. In this module it's been quietly doing something more useful: telling you **which part of an algorithm to improve**. Karatsuba and Strassen won by cutting the number of subproblems; the four-number maximum subarray won by cutting the combine step; the closest pair won by keeping its combine step linear. This lesson collects every recurrence from the module, sorts them by case, and draws out the design lesson behind each case. It finishes with the recurrences the theorem can't handle, and what to do instead.

## The recipe

For **T(n) = a · T(n / b) + f(n)**, with f(n) = n^d · logᵏ n (k is usually 0, meaning no log factor), compare **a** with **b^d**:

| Comparison | Case | Result |
| --- | --- | --- |
| a less than b^d | root wins | Θ(n^d · logᵏ n), the combine work at the top |
| a = b^d | tie | Θ(n^d · logᵏ⁺¹ n), every level costs the same |
| a greater than b^d | leaves win | Θ(n^(log_b a)), the number of leaves |

The tie row with k = 0 is the familiar Θ(n^d log n); a log factor in f(n) gains one more log. The comparison is between two **whole numbers**, so do it exactly: b^d is 2² = 4, not log₂ 4 computed in floating point.

## Reading a, b and f from code

Getting the three numbers right matters more than remembering the cases:

- **a** is the number of recursive calls each call **actually makes**, not the number of pieces it divides into. Binary search splits into two halves but recurses into one: a = 1.
- **b** is how much smaller each call's input is: halves give b = 2.
- **f(n)** is **everything else** a call does: dividing, combining, and any copying.

That last point catches real code. Here's a binary search that recurses on a copy of the half it keeps:

```swift run
var copied = 0
var comparisons = 0

// Binary search that recurses on a copy of the half it keeps: correct, but every call copies
func containsByCopying(_ items: [Int], _ target: Int) -> Bool {
    if items.isEmpty { return false }
    comparisons += 1
    let mid = items.count / 2
    if items[mid] == target { return true }
    let half = items[mid] < target ? Array(items[(mid + 1)...]) : Array(items[..<mid])
    copied += half.count
    return containsByCopying(half, target)
}

// Binary search on indices: nothing is copied
func containsByIndex(_ items: [Int], _ target: Int) -> Bool {
    var low = 0
    var high = items.count
    while low < high {
        comparisons += 1
        let mid = low + (high - low) / 2
        if items[mid] == target { return true }
        if items[mid] < target { low = mid + 1 } else { high = mid }
    }
    return false
}

let items = Array(0..<1_000_000)
_ = containsByCopying(items, -1)
print("copying halves: \(comparisons) comparisons, \(copied) elements copied")
comparisons = 0
_ = containsByIndex(items, -1)
print("passing indices: \(comparisons) comparisons, nothing copied")
```

```output
copying halves: 20 comparisons, 999993 elements copied
passing indices: 20 comparisons, nothing copied
```

Both make 20 comparisons, but the copying version's f(n) is n, not 1: T(n) = T(n / 2) + n, which is Θ(n). The copies alone cost as much as a linear search. Passing indices keeps f(n) at O(1) and the search at Θ(log n).

## Every recurrence from this module

| Algorithm | Recurrence | a vs b^d | Case | Result |
| --- | --- | --- | --- | --- |
| Fast power | T(n/2) + 1 | 1 = 1 | tie | Θ(log n) |
| Fast power, half computed twice | 2T(n/2) + 1 | 2 greater than 1 | leaves | Θ(n) |
| Smallest and largest | 2T(n/2) + 2 | 2 greater than 1 | leaves | Θ(n) |
| Max subarray, crossing sums | 2T(n/2) + n | 2 = 2 | tie | Θ(n log n) |
| Max subarray, four numbers | 2T(n/2) + 1 | 2 greater than 1 | leaves | Θ(n) |
| Inversions; majority by halves | 2T(n/2) + n | 2 = 2 | tie | Θ(n log n) |
| Boyer–Moore summaries | 2T(n/2) + 1 | 2 greater than 1 | leaves | Θ(n) |
| Closest pair, merged by y | 2T(n/2) + n | 2 = 2 | tie | Θ(n log n) |
| Closest pair, strip re-sorted | 2T(n/2) + n log n | 2 = 2, k = 1 | tie | Θ(n log² n) |
| Closest pair, all split pairs | 2T(n/2) + n² | 2 less than 4 | root | Θ(n²) |
| Multiplication, four products | 4T(n/2) + n | 4 greater than 2 | leaves | Θ(n²) |
| Karatsuba | 3T(n/2) + n | 3 greater than 2 | leaves | Θ(n^1.585) |
| Block matrices, eight products | 8T(n/2) + n² | 8 greater than 4 | leaves | Θ(n³) |
| Strassen | 7T(n/2) + n² | 7 greater than 4 | leaves | Θ(n^2.807) |

### Leaves win: cut the number of subproblems

When a is greater than b^d, almost all the work is at the bottom of the tree, in its n^(log_b a) leaves. The combine step hardly matters: Karatsuba's extra additions and Strassen's 18 block additions change only the constant. What matters is **a**. Going from 4 products to 3 moved the exponent from 2 to 1.585; going from 8 to 7 moved it from 3 to 2.807. Computing fast power's half twice doubled a from 1 to 2, and the leaves took over: Θ(n).

### Tie: every level costs the same

When a = b^d, each level of the tree does the same total work, and there are log_b n levels, so you pay one log factor. Merge sort, inversions, majority by halves and the closest pair all live here. To do better, make the combine step cheaper **asymptotically**. The four-number summary turned the maximum subarray's f(n) from n into 1, moving it from the tie case (Θ(n log n)) into the leaves case (Θ(n)). A log factor in the combine step works the other way: re-sorting the closest pair's strip makes f(n) = n log n, and the answer gains a second log.

### Root wins: the recursion is wasted

When a is less than b^d, the top call's combine step dominates. Checking every split pair in the closest pair problem is f(n) = n²/4, and T(n) = 2T(n / 2) + n² is Θ(n²): all that dividing bought nothing over brute force. When you find yourself in this case, the recursion isn't the problem; the combine step is. The strip argument is precisely what moved the closest pair from here into the tie case. Not every root-wins recurrence is bad, though. Quickselect with ideal halving, T(n / 2) + n, is Θ(n) because each level does half the work of the one above, and linear is the best selection can do.

## Checking a prediction by doubling

If T(n) is Θ(n^p), doubling n multiplies T by about 2^p. That gives a quick experiment for any recurrence or any program: compute or measure it at n and at 2n, and look at the ratio. Here are seven of the module's recurrences, evaluated exactly at n = 2²⁰:

```swift run
import Foundation

// T(n) = a · T(n / 2) + f(n), with T(1) = 1, evaluated exactly for n a power of two
func evaluate(_ a: Double, _ f: (Double) -> Double, _ n: Int) -> Double {
    n <= 1 ? 1 : a * evaluate(a, f, n / 2) + f(Double(n))
}

let recurrences: [(name: String, shape: String, a: Double, f: (Double) -> Double, theorem: String)] = [
    ("fast power", "T(n/2) + 1", 1, { _ in 1 }, "Θ(log n)"),
    ("quickselect, ideal", "T(n/2) + n", 1, { $0 }, "Θ(n)"),
    ("four-number summary", "2T(n/2) + 1", 2, { _ in 1 }, "Θ(n)"),
    ("merge sort", "2T(n/2) + n", 2, { $0 }, "Θ(n log n)"),
    ("Karatsuba", "3T(n/2) + n", 3, { $0 }, "Θ(n^1.585)"),
    ("quadratic combine", "2T(n/2) + n²", 2, { $0 * $0 }, "Θ(n²)"),
    ("Strassen", "7T(n/2) + n²", 7, { $0 * $0 }, "Θ(n^2.807)"),
]

let n = 1 << 20
for r in recurrences {
    let ratio = evaluate(r.a, r.f, 2 * n) / evaluate(r.a, r.f, n)
    let name = r.name.padding(toLength: 21, withPad: " ", startingAt: 0)
    let shape = r.shape.padding(toLength: 14, withPad: " ", startingAt: 0)
    print("\(name)\(shape)\(String(format: "%.3f", ratio))   \(r.theorem)")
}
```

```output
fast power           T(n/2) + 1    1.048   Θ(log n)
quickselect, ideal   T(n/2) + n    2.000   Θ(n)
four-number summary  2T(n/2) + 1   2.000   Θ(n)
merge sort           2T(n/2) + n   2.095   Θ(n log n)
Karatsuba            3T(n/2) + n   3.000   Θ(n^1.585)
quadratic combine    2T(n/2) + n²  4.000   Θ(n²)
Strassen             7T(n/2) + n²  7.000   Θ(n^2.807)
```

Karatsuba's ratio is 3 = 2^1.585 and Strassen's is 7 = 2^2.807, the leaves' growth exactly. Log factors show up as ratios a little above the power of two: merge sort's 2.095 is 2 × 22/21, and fast power's 1.048 is 22/21, both creeping towards 2 and 1 as n grows. The same test works on real running times, which makes it a handy sanity check on code whose complexity you aren't sure of.

## When the theorem doesn't apply

The theorem needs a constant number of calls, all on inputs of size n/b. When a recurrence doesn't fit, these tools from [Recurrences: substitution and recursion trees](/dsa/learn/bigo-recurrences) do:

| Recurrence | Why it doesn't fit | What to do | Result |
| --- | --- | --- | --- |
| T(n/5) + T(7n/10) + n | two different sizes | recursion tree: each level shrinks by 9/10 | Θ(n) |
| T(n/10) + T(9n/10) + n | two different sizes | recursion tree: full levels of n, about log n deep | Θ(n log n) |
| T(n − 1) + n | subtracts, doesn't divide | unroll: n + (n − 1) + … + 1 | Θ(n²) |
| 2T(n − 1) + 1 | subtracts, doesn't divide | unroll: the calls double every level | Θ(2ⁿ) |
| 2T(n/2) + n / log n | f(n) falls in a gap | other methods | Θ(n log log n) |

The first row is [median of medians](/dsa/learn/sort-median-of-medians): because 1/5 + 7/10 is less than 1, the work shrinks geometrically down the tree. The second is quick sort with pivots that always split 1 to 9: lopsided, but the pieces still add up to n on every level and the depth is still logarithmic, which is why quick sort tolerates bad-but-not-terrible pivots. The third is quick sort's worst case and selection sort; the fourth is the Towers of Hanoi. The gap in the last row is the one M14 warned about: n / log n is smaller than n, but only by a log factor, not by a power n^ε, so neither the leaves case nor the tie case applies.

<Callout kind="note" title="Rounding doesn't matter">
Real code splits n elements into ⌊n/2⌋ and ⌈n/2⌉, never exactly n/2 twice. The theorem's answer is the same: rounding changes each call's size by at most 1, which changes the total by at most a constant factor. Write n/2 and move on.
</Callout>

<Callout kind="gotcha" title="Common mistakes">
- **Counting pieces instead of calls.** a is the number of recursive calls made, which is 1 for binary search and fast power, however many halves exist.
- **Forgetting hidden work in f(n).** Copying a slice, building a new array, or sorting inside each call all belong in f(n).
- **Comparing a with b^d in floating point.** `log(9.0) / log(3.0)` isn't guaranteed to come out as exactly 2.0. Compare whole numbers, or allow for rounding.
- **Forcing a recurrence into the form.** Unequal sizes and subtract-and-conquer need a recursion tree or unrolling, not a guess at a and b.
</Callout>
