## Why it matters

You've solved both of these problems before: [Counting inversions](/dsa/learn/sort-inversions) with merge sort in M31, and the majority element with [Boyer–Moore voting](/dsa/learn/arrays-leaders-majority) in M18. Looking at them again through the divide-and-conquer lens shows what makes a combine step work. Inversions need each half to come back **sorted** as well as counted. The majority needs one fact about halves, and then it turns out that Boyer–Moore itself is a summary you can combine. Ranking comparisons, "how many later scores were lower than mine?" in a leaderboard, and range-majority queries in Part VIII all grow from these two ideas.

## Inversions: the three kinds

An inversion is a pair of positions `i < j` with `numbers[i] > numbers[j]`. Split the array in half, and every inversion is one of three kinds:

| Kind | Both elements | How to count it |
| --- | --- | --- |
| left | in the left half | recursively |
| right | in the right half | recursively |
| across | bigger one left, smaller one right | the combine step |

The across pairs are the whole difficulty. Checking every left element against every right element is O(n²) again. The trick from M31 is to make each recursive call **also sort its half**. Sorting a half doesn't change which left elements are bigger than which right elements, and once both halves are sorted, the merge counts the across pairs as a side effect: whenever it takes an element from the right, that element is smaller than everything still waiting on the left.

```swift run
// Count inversions while merge sorting. Returns the count; sorts items[low..<high] as a side effect.
func sortAndCount(_ items: inout [Int], _ buffer: inout [Int], _ low: Int, _ high: Int) -> Int {
    guard high - low > 1 else { return 0 }
    let mid = low + (high - low) / 2
    let inLeft = sortAndCount(&items, &buffer, low, mid)
    let inRight = sortAndCount(&items, &buffer, mid, high)
    for index in low..<high {
        buffer[index] = items[index]
    }
    var across = 0
    var left = low
    var right = mid
    for write in low..<high {
        if right == high || (left < mid && buffer[left] <= buffer[right]) {
            items[write] = buffer[left]
            left += 1
        } else {
            items[write] = buffer[right]
            right += 1
            across += mid - left          // smaller than everything still waiting on the left
        }
    }
    if low == 0 && high == items.count {
        print("left half \(inLeft), right half \(inRight), across \(across)")
    }
    return inLeft + inRight + across
}

var items = [5, 2, 6, 1, 3, 4]
var buffer = items
let total = sortAndCount(&items, &buffer, 0, items.count)
print("total \(total), sorted \(items)")
```

```output
left half 1, right half 0, across 7
total 8, sorted [1, 2, 3, 4, 5, 6]
```

The left half `[5, 2, 6]` holds one inversion, (5, 2); the right half `[1, 3, 4]` holds none; the other 7 cross the middle. The recurrence is merge sort's, T(n) = 2T(n / 2) + n, so this is **O(n log n)**. The M31 lesson steps through each merge with a visualiser.

### The lesson in the shape

The question was "how many inversions?", but each call answers a **stronger** question: "how many inversions, and what does this range look like sorted?" The extra answer is what makes the combine step linear. You did the same in the last lesson, returning four numbers instead of one. When a combine step looks too expensive, ask what extra information from each half would make it cheap.

### Inversions per element

A popular variant asks, for **each** position, how many later values are smaller: `[6, 3, 8, 2]` gives `[2, 1, 1, 0]`. The total is the inversion count, but now each element needs its own tally, and sorting moves elements away from their positions. Two changes handle it:

- Sort **(value, original index)** pairs, so each element remembers whose tally it adds to.
- Count from the left element's point of view: when the merge takes an element from the **left**, every element already taken from the right is smaller and came after it. Add how many have been taken from the right so far.

Here's the final merge for `[6, 3, 8, 2]`. The halves come back sorted as `[3, 6]` (where 6 already has 1, for the 3) and `[2, 8]` (where 8 already has 1, for the 2):

| Takes | From | Taken from the right so far | Tally |
| --- | --- | --- | --- |
| 2 | right | 1 | |
| 3 | left | 1 | 3 gets 1 more: 1 |
| 6 | left | 1 | 6 gets 1 more: 2 |
| 8 | right | 2 | |

That's `[2, 1, 1, 0]` once the tallies are put back in their original positions. It's still one merge sort, so still O(n log n). You'll write it in **Smaller values to the right**.

## The majority, by halves

A **majority** element appears more than n/2 times. Here's the fact that makes divide and conquer possible:

> If m is the majority of the whole range, then m is the majority of the left half or of the right half (or both).

Why? Suppose m filled at most half of each half: at most L/2 of the left's L elements and at most R/2 of the right's R. Then m would fill at most L/2 + R/2 = n/2 of the whole, which isn't a majority. So at least one half must have m as its majority, whatever the sizes of the halves.

That gives the algorithm. Find each half's majority recursively. Each half returns a value, or nothing if it has no majority. The whole range's majority, if there is one, must be one of those at most two candidates, so count each candidate across the whole range:

```swift run
// Majority by divide and conquer: a majority of the whole must be a majority of one half
func occurrences(of value: Int, in numbers: [Int], _ low: Int, _ high: Int) -> Int {
    var count = 0
    for index in low..<high where numbers[index] == value {
        count += 1
    }
    return count
}

func combine(_ left: Int?, _ right: Int?, _ numbers: [Int], _ low: Int, _ high: Int) -> Int? {
    if left == right {
        return left                               // both halves agree, or neither has a majority
    }
    for candidate in [left, right] {
        if let candidate, occurrences(of: candidate, in: numbers, low, high) > (high - low) / 2 {
            return candidate
        }
    }
    return nil
}

func majority(_ numbers: [Int], _ low: Int, _ high: Int) -> Int? {
    if high - low == 1 {
        return numbers[low]                       // one element is its own majority
    }
    let mid = low + (high - low) / 2
    let left = majority(numbers, low, mid)
    let right = majority(numbers, mid, high)
    let answer = combine(left, right, numbers, low, high)
    let show = { (value: Int?) in value.map(String.init) ?? "none" }
    print("\(Array(numbers[low..<high])): left \(show(left)), right \(show(right)) → \(show(answer))")
    return answer
}

let numbers = [2, 2, 1, 1, 1, 2, 2]
_ = majority(numbers, 0, numbers.count)
```

```output
[2, 1]: left 2, right 1 → none
[2, 2, 1]: left 2, right none → 2
[1, 1]: left 1, right 1 → 1
[2, 2]: left 2, right 2 → 2
[1, 1, 2, 2]: left 1, right 2 → none
[2, 2, 1, 1, 1, 2, 2]: left 2, right none → 2
```

What to notice:

- `[1, 1, 2, 2]` has no majority even though both halves do: 1 and 2 each fill exactly half. Candidates are only candidates until they're counted.
- If both halves have the **same** majority, it's the majority of the whole without counting: more than L/2 plus more than R/2 is more than n/2. And if neither half has one, the whole has none.
- The counting must cover the **whole** current range, `low..<high`, not just the half the candidate came from.

Counting is O(n) per call, so the recurrence is T(n) = 2T(n / 2) + n again: **O(n log n)** time, with O(log n) of recursion stack.

## Boyer–Moore is a summary too

Here's how every approach compares:

| Approach | Time | Extra space |
| --- | --- | --- |
| count every value in a dictionary | O(n) | O(n) |
| sort, then check the middle element | O(n log n) | depends on the sort |
| divide and conquer, counting candidates | O(n log n) | O(log n) |
| Boyer–Moore voting | O(n) | O(1) |

Boyer–Moore wins. But its state, a candidate and a number of votes, has a meaning you can use. After any stretch of the array, it says: "cancel the elements in pairs of **different** values, and what's left is `votes` copies of `candidate`." Two such summaries can be merged. If the candidates match, the votes add up. If they differ, the two candidates cancel against each other pair by pair, and whoever had more votes keeps the difference.

```swift run
// Boyer–Moore's state as a summary that can be merged: what's left after cancelling pairs of different values
struct Votes {
    let candidate: Int
    let votes: Int
}

func merge(_ a: Votes, _ b: Votes) -> Votes {
    if a.candidate == b.candidate {
        return Votes(candidate: a.candidate, votes: a.votes + b.votes)
    }
    // Different candidates: cancel them against each other, pair by pair
    return a.votes >= b.votes ? Votes(candidate: a.candidate, votes: a.votes - b.votes)
                              : Votes(candidate: b.candidate, votes: b.votes - a.votes)
}

func summarise(_ numbers: [Int], _ low: Int, _ high: Int) -> Votes {
    if high - low == 1 {
        return Votes(candidate: numbers[low], votes: 1)
    }
    let mid = low + (high - low) / 2
    return merge(summarise(numbers, low, mid), summarise(numbers, mid, high))
}

for numbers in [[2, 2, 1, 1, 1, 2, 2], [3, 1, 3], [1, 2, 3], [4, 4, 1, 1], [7, 5, 7, 5, 7]] {
    let summary = summarise(numbers, 0, numbers.count)
    let count = numbers.filter { $0 == summary.candidate }.count
    let verdict = count > numbers.count / 2 ? "majority" : "no majority"
    print(numbers, "candidate", summary.candidate, "votes", summary.votes, "→", verdict)
}
```

```output
[2, 2, 1, 1, 1, 2, 2] candidate 2 votes 1 → majority
[3, 1, 3] candidate 3 votes 1 → majority
[1, 2, 3] candidate 1 votes 1 → no majority
[4, 4, 1, 1] candidate 4 votes 0 → no majority
[7, 5, 7, 5, 7] candidate 7 votes 1 → majority
```

The combine step is now O(1), so T(n) = 2T(n / 2) + 1: **O(n)**. The same argument as in M18 proves it: every cancelled pair holds at most one copy of the majority, so the majority can't be cancelled away. And, as in M18, a candidate is only a candidate: `[1, 2, 3]` ends with 1 standing, so the final counting pass is still needed when a majority isn't guaranteed.

Why would you ever do it this way round? Because a mergeable summary can be stored per block and combined in any grouping, exactly like the last lesson's four numbers. That's how Part VIII's segment trees answer "is there a majority between positions i and j?" quickly, for many different ranges.

<Callout kind="gotcha" title="Common mistakes">
- **Trusting the candidates.** Neither the divide-and-conquer candidates nor Boyer–Moore's survivor is guaranteed to be a majority. Count before you answer, unless the problem promises a majority exists.
- **Counting inside one half.** A left-half majority must be counted over the whole range `low..<high` to become the whole range's majority.
- **Ties in the inversion merge.** Take the left element on a tie (`<=`), or equal values get counted as inversions, as in M31.
</Callout>
