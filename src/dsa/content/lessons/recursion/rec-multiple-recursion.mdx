## Why it matters

So far, most functions in this module called themselves once. The interesting ones call themselves **two or more times**: once per choice, once per child, once per half. That's where recursion beats loops for clarity: generating every combination, solving puzzles, walking trees. It's also where running time can explode. This lesson shows both sides, and how to tell an explosion you can't avoid from one you can fix.

## One call per choice

Suppose you want every string of `0`s and `1`s of length 3. Think of building it one character at a time. At each position there are two choices, so make one recursive call for each:

```swift run
func printBinaryStrings(_ prefix: String, _ remaining: Int) {
    if remaining == 0 {
        print(prefix)                                  // a finished string
        return
    }
    printBinaryStrings(prefix + "0", remaining - 1)    // choice 1
    printBinaryStrings(prefix + "1", remaining - 1)    // choice 2
}

printBinaryStrings("", 3)
```

```output
000
001
010
011
100
101
110
111
```

The promise: `printBinaryStrings(prefix, remaining)` prints every string that starts with `prefix` and has `remaining` more characters. The base case is "nothing left to choose": print what you've built.

Draw the recursion tree and it's a perfect binary tree: 1 call at the top, then 2, 4 and 8. The 8 leaves are the 8 strings, and there are 15 calls in all. For length n there are 2ⁿ strings and 2ⁿ⁺¹ − 1 calls. The strings come out in sorted order for free, because every `"0"` branch finishes before its `"1"` branch starts.

## Tower of Hanoi

Three pegs, A, B and C. On peg A sits a stack of n disks, largest at the bottom. Move them all to peg C, one disk at a time, never putting a larger disk on a smaller one.

Trying moves at random gets you nowhere. Thinking recursively cracks it in three sentences. To move n disks from A to C:

1. Move the top n − 1 disks out of the way, from A to B, using C as the spare.
2. Move the largest disk from A to C. It's now free, and C is empty.
3. Move the n − 1 disks from B to C, on top of it, using A as the spare.

Steps 1 and 3 are the same problem with one fewer disk, and different pegs. The base case is zero disks: nothing to do. Here are the seven moves for three disks:

```text
1. disk 1: A → C
2. disk 2: A → B
3. disk 1: C → B      the top two disks are now on B
4. disk 3: A → C      the largest disk moves, exactly once
5. disk 1: B → A
6. disk 2: B → C
7. disk 1: A → C      the top two disks are back on top of it
```

How many moves does n disks take? Moving n disks costs two moves of n − 1 disks plus one, so the count follows the same recursion:

```swift run
func hanoiMoveCount(_ disks: Int) -> Int {
    if disks == 0 {
        return 0
    }
    return 2 * hanoiMoveCount(disks - 1) + 1
}

print("disks → moves")
for disks in [1, 2, 3, 10, 20] {
    print("\(disks) → \(hanoiMoveCount(disks))")
}
```

```output
disks → moves
1 → 1
2 → 3
3 → 7
10 → 1023
20 → 1048575
```

That's 2ⁿ − 1, and it's provably the fewest moves possible. Notice that `hanoiMoveCount` calls itself **once** and doubles the result. Writing `hanoiMoveCount(disks - 1) + 1 + hanoiMoveCount(disks - 1)` gives the same numbers with an exponential number of calls, the same trap as computing the half twice in fast power.

## Counting routes on a grid

A robot starts in the top-left cell of a grid and wants to reach the bottom-right cell, moving only right or down. How many different routes are there?

Think about the first move. Going down leaves a grid with one row fewer; going right leaves one with one column fewer. Every route starts with exactly one of those, so the answer is the routes from each, added together. A grid that's a single row or a single column has exactly one route: straight along it.

```swift run
var calls = 0

func paths(_ rows: Int, _ columns: Int) -> Int {
    calls += 1
    if rows == 1 || columns == 1 {
        return 1                     // a single row or column: one straight route
    }
    return paths(rows - 1, columns) + paths(rows, columns - 1)
}

for size in [3, 5, 10, 12] {
    calls = 0
    let count = paths(size, size)
    print("\(size)×\(size): \(count) routes, \(calls) calls")
}
```

```output
3×3: 6 routes, 11 calls
5×5: 70 routes, 139 calls
10×10: 48620 routes, 97239 calls
12×12: 705432 routes, 1410863 calls
```

The code is short and clearly correct. The call counts are the problem: the leaves of this tree each return 1, so the function makes about **twice as many calls as there are routes**. A 16×16 grid has over 155 million routes, so this version would make over 300 million calls.

## Necessary blow-up, and wasteful blow-up

All three examples are exponential, but for different reasons.

- **Binary strings and Hanoi** must produce 2ⁿ strings or 2ⁿ − 1 moves. No algorithm can do less work than writing out its answer, so the exponential cost is **necessary**. Every call in their trees does something new.
- **Grid routes and Fibonacci** return a single number. Their trees are huge because the same subproblems are solved over and over. That blow-up is **wasteful**.

You can see the waste by counting how often each subproblem is computed:

```swift run
var callsFor: [Int: Int] = [:]

func fib(_ n: Int) -> Int {
    callsFor[n, default: 0] += 1
    if n < 2 {
        return n
    }
    return fib(n - 1) + fib(n - 2)
}

print(fib(10))
for n in callsFor.keys.sorted(by: >) {
    print("fib(\(n)) computed \(callsFor[n]!) times")
}
```

```output
55
fib(10) computed 1 times
fib(9) computed 1 times
fib(8) computed 2 times
fib(7) computed 3 times
fib(6) computed 5 times
fib(5) computed 8 times
fib(4) computed 13 times
fib(3) computed 21 times
fib(2) computed 34 times
fib(1) computed 55 times
fib(0) computed 34 times
```

There are only 11 different questions, but 177 calls. `fib(2)` alone is worked out 34 times, always getting 1. (The counts are themselves Fibonacci numbers, which is a nice coincidence to puzzle over.) The keys are printed in sorted order because a dictionary's own order isn't predictable.

When different branches keep asking the same question, the subproblems **overlap**. Overlapping subproblems are the signal that the next lesson's technique, memoisation, will turn exponential into fast.

## How big is too big?

A tree where each call makes b calls and the depth is d has about bᵈ leaves. With two choices per level:

| Depth | Calls, roughly | Time on a typical laptop |
| --- | --- | --- |
| 20 | a million | instant |
| 30 | a billion | seconds to minutes |
| 40 | a trillion | hours |
| 60 | a billion billion | longer than you'll live |

A computer manages very roughly a few hundred million simple steps per second, the rule of thumb from [From n to a feasible complexity](/dsa/learn/bigo-feasibility-table). So when a problem says n can be 50 and your recursion branches twice per step, you know before running anything that it needs a better idea: memoisation for overlapping subproblems, or **pruning** (cutting off branches that can't lead to an answer), which you'll learn in backtracking in M48.

<Callout kind="gotcha" title="Never make the same call twice in one frame">
`f(n - 1) + f(n - 1)`, `half(x) * half(x)` and similar lines double the size of the tree at every level while computing nothing new. If you need a recursive result twice, store it in a constant first. This is the cheapest optimisation in all of recursion.
</Callout>
