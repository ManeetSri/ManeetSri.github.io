## Why it matters

The last lesson ended with a recursion that asked the same questions thousands of times. **Memoisation** fixes that with one idea: write each answer down the first time you work it out, and look it up after that. A few extra lines turn exponential `fib` into a linear one. It's your first step into **dynamic programming**, which gets a whole family of modules in Part VII. This lesson is only a preview, but it's a technique you can use straight away.

## Remember, don't recompute

Keep a dictionary from "question" to "answer". At the top of the function, check whether this question has been answered before. If it has, return the stored answer without recursing. If not, work it out as usual and store it before returning.

Here's `fib` both ways, counting calls:

```swift run
var calls = 0

func slowFib(_ n: Int) -> Int {
    calls += 1
    if n < 2 {
        return n
    }
    return slowFib(n - 1) + slowFib(n - 2)
}

var cache: [Int: Int] = [:]

func memoFib(_ n: Int) -> Int {
    calls += 1
    if n < 2 {
        return n
    }
    if let known = cache[n] {
        return known                       // answered before: no more calls
    }
    let result = memoFib(n - 1) + memoFib(n - 2)
    cache[n] = result                      // remember it for next time
    return result
}

calls = 0
print(slowFib(20), "in", calls, "calls")
calls = 0
print(memoFib(20), "in", calls, "calls")
```

```output
6765 in 21891 calls
6765 in 39 calls
```

From 21,891 calls to 39. The name comes from "memo", a note to yourself, and it's spelled without an r.

See it happen for a small n. Calls answered straight from the memo turn blue, and they never make calls of their own:

## Why it's linear now

Follow `memoFib(20)`. Its first call, `memoFib(19)`, goes all the way down the left side: 19, 18, 17, and so on to 1. On the way back up, each of those calls stores its answer. So when `memoFib(19)` makes its *second* call, `memoFib(17)`, the answer is already in the cache, and it returns at once. The same happens at every level.

The huge tree collapses into a single spine running down the left, with one instant cache lookup hanging off each level: about 2n calls instead of about 1.6ⁿ. Each distinct question, `fib(0)` to `fib(20)`, is computed exactly once.

That gives the general rule for memoised recursion:

> **time ≈ (number of different subproblems) × (work per subproblem, not counting recursive calls)**

For `fib`, that's n subproblems with O(1) work each: **O(n)** time. The cache holds n answers and the stack is n frames deep, so the space is O(n) too.

## Keeping the cache tidy

A global `cache` works, but it's shared by every caller forever, and it's easy to forget to reset it. A neater shape keeps the cache inside a wrapper function, with the recursion in a nested helper that captures it (M05 and M06):

```swift run
func fibonacci(_ n: Int) -> Int {
    var cache: [Int: Int] = [:]

    func fib(_ k: Int) -> Int {
        if k < 2 {
            return k
        }
        if let known = cache[k] {
            return known
        }
        let result = fib(k - 1) + fib(k - 2)
        cache[k] = result
        return result
    }

    return fib(n)
}

print(fibonacci(50))
print(fibonacci(90))
```

```output
12586269025
2880067194370816120
```

Naive recursion would need about 40 billion calls for `fib(50)`. This version needs 99. (`fib(92)` is the largest Fibonacci number that fits in an `Int`.)

## The recipe

Memoising any recursive function takes four steps:

1. **Write the plain recursion first**, and check that it's correct on small inputs.
2. **Identify the key**: the arguments that completely determine the answer.
3. **At the top**, after the base cases, return the cached answer if there is one.
4. **Before returning**, store the answer under its key.

The plain version does all the thinking. Memoisation is a mechanical layer on top.

## Keys with more than one argument

When the answer depends on two arguments, the key needs both. A small `Hashable` struct, from [Hashable and hash(into:)](/dsa/learn/swift-hashable), makes a clean key.

Here's the number of ways to choose k items from n, from M15's [Factorials, permutations and combinations](/dsa/learn/math-counting). Pascal's rule gives a recursion: either the first item is chosen, and you choose k − 1 from the other n − 1, or it isn't, and you choose all k from the other n − 1.

```swift run
struct Pair: Hashable {
    let n: Int
    let k: Int
}

var calls = 0

func choose(_ n: Int, _ k: Int) -> Int {
    calls += 1
    if k == 0 || k == n {
        return 1
    }
    return choose(n - 1, k - 1) + choose(n - 1, k)
}

func memoChoose(_ n: Int, _ k: Int) -> Int {
    var cache: [Pair: Int] = [:]

    func go(_ n: Int, _ k: Int) -> Int {
        calls += 1
        if k == 0 || k == n {
            return 1
        }
        if let known = cache[Pair(n: n, k: k)] {
            return known
        }
        let result = go(n - 1, k - 1) + go(n - 1, k)
        cache[Pair(n: n, k: k)] = result
        return result
    }

    return go(n, k)
}

calls = 0
print(choose(20, 10), "in", calls, "calls")
calls = 0
print(memoChoose(20, 10), "in", calls, "calls")
calls = 0
print(memoChoose(60, 30), "in", calls, "calls")
```

```output
184756 in 369511 calls
184756 in 201 calls
118264581564861424 in 1801 calls
```

There are only about n × k different `(n, k)` pairs the recursion can reach, so the memoised version is O(n × k). The naive version makes about twice as many calls as its answer, so `choose(60, 30)` would need over 200 million billion calls. `Pair` gets `Hashable` for free, because both of its properties are `Int`.

## When memoisation doesn't help

Memoisation only saves work when the same subproblem comes up more than once.

- **No overlap, no gain.** Every call that prints a binary string or a Hanoi move is different from every other. A cache would fill up with entries that are never looked up again.
- **The answer must depend only on the key.** If a function also reads a global variable, or the time, or anything not in the key, a cached answer can be wrong the second time. Memoise functions where the same arguments always give the same result.
- **The cache costs memory.** One entry per subproblem. Usually that's a bargain, but it's not free.

<Callout kind="gotcha" title="The cache must outlive the calls">
A `var cache` declared *inside* the recursive function is created fresh, empty, in every call's frame, and thrown away when that call returns, so it never helps. The cache has to live outside the recursion: in a wrapper function that the recursive helper captures, as a global, or passed along `inout`.
</Callout>

## Where this goes next

What you've done here is called **top-down dynamic programming**: start from the big question and let recursion, plus a cache, work out the smaller ones it needs. In M51 you'll also meet the **bottom-up** style, which fills a table from the smallest subproblems upwards with a loop, avoiding recursion entirely. For small integer keys, an array is a faster cache than a dictionary, which you'll use there too.
