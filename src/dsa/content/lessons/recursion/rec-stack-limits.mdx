## Why it matters

A recursive solution can be correct, fast and still crash, because it ran out of stack. It's one of the most confusing failures in Swift: no helpful message, sometimes fine in one place and broken in another. Knowing roughly how deep you can go, and recognising the crash when you see it, saves hours. It also explains why the tests in this course keep recursion shallow.

## How big is the stack?

Every thread has its own call stack, with a size fixed when the thread starts. On macOS:

| Thread | Stack size |
| --- | --- |
| The main thread, where your top-level code runs | about 8 MB |
| Any other thread | 512 KB |

The main thread's limit comes from your shell: `ulimit -s` prints it in kilobytes. Other threads get 512 KB, sixteen times less. You haven't created threads yourself yet (that's Part IX), but code you run often does: **Swift Testing runs your tests on other threads**, so a recursion inside a test gets the small stack.

## How deep can you go?

It depends on how much each frame needs: its parameters, its locals and some bookkeeping. Here's what one Apple-silicon Mac with Swift 6.4 managed for the simplest possible recursion, `sum(upTo:)` from earlier lessons, before crashing:

| Where it ran | Deepest recursion, roughly |
| --- | --- |
| Main thread, debug build | 130,000 calls |
| Main thread, `-O` build | 260,000 calls |
| Inside a Swift Testing test, debug | 8,000 calls |

Treat these as orders of magnitude, not promises. A function with more parameters, more local variables or `String` values in its frame uses more stack per call and crashes sooner. A different machine or Swift version gives different numbers. What stays true is the shape: **about a hundred thousand on the main thread, only thousands in a test**.

## What the crash looks like

There's no friendly "stack overflow" message. When the stack runs out, the program touches memory it isn't allowed to, and the operating system kills it. Here's a program that calls `sum(upTo: 1_000_000)`, built and run in Terminal:

```text title="What you'll see"
zsh: segmentation fault  ./sum
```

Run the same file with `swift sum.swift` and zsh reports a different signal:

```text title="What you'll see"
zsh: illegal hardware instruction  swift sum.swift
```

In a test, the whole test process dies mid-test. The test never reports passing or failing, and `swift test` says something like this (shortened):

```text title="What you'll see"
error: Process '.../swiftpm-testing-helper ...' exited with unexpected signal code 10
```

And in Xcode, the debugger stops inside the recursive function with `Thread 1: EXC_BAD_ACCESS (code=2, address=…)`.

None of these mention recursion. The giveaway is in the debugger: type `bt` and you'll see thousands of frames of the same function, one per call, exactly as in [The call stack, visualised](/dsa/learn/rec-call-stack). When a crash's backtrace is one function repeated over and over, think "stack overflow" first.

<Callout kind="gotcha" title="Swift gotcha: passes locally, crashes in tests">
A recursion 20,000 levels deep runs happily in a script or app on the main thread, then crashes when the same function runs inside `swift test`, because the test thread's stack is about sixteen times smaller. That's why every problem in this course keeps recursion depth in its tests well under 1,000. If your own tests crash with an "unexpected signal", check your recursion depth before anything else.
</Callout>

## Know your depth before you run

You can estimate a recursion's depth before writing a single test, from its shape:

| Recursion | Depth | Verdict |
| --- | --- | --- |
| Halves the input: binary search, fast power, two halves | about log₂ n: 60 frames for n = 10¹⁸ | always fine |
| One step per element, n up to a few thousand | n | fine everywhere |
| One step per element, n in the tens of thousands | n | fine on the main thread, crashes in tests |
| One step per element, n of 100,000 or more | n | rewrite it |

Watch for recursions whose depth isn't obvious from the code:

- **Linked lists.** Recursing node by node goes one frame per node. A list of 100,000 nodes is 100,000 frames.
- **Lopsided trees.** A balanced tree of a million nodes is about 20 levels deep. The same nodes in a lopsided tree, such as a binary search tree built by inserting sorted values (Part V), can be a million levels deep.
- **Grid flood fills.** Spreading from cell to neighbouring cell on a 1,000 × 1,000 grid can recurse up to a million levels deep.
- **Strings and arrays.** Recursing one character at a time over a 100,000-character string is 100,000 frames.

## What to do about deep recursion

In order of preference:

1. **Write a loop.** For a single chain of calls, the loop from [Recursion vs iteration, and tail calls](/dsa/learn/rec-vs-iteration) is usually as clear.
2. **Use an explicit stack.** For branching recursions, the technique from [Turning recursion into an explicit stack](/dsa/learn/rec-explicit-stack) moves the pending work to the heap.
3. **Reduce the depth.** Recursing on two halves instead of "first element plus the rest" does the same work with O(log n) depth.
4. **Don't count on tail calls.** As you saw, Swift never removes tail-call frames in debug builds, which is how your tests run.

Competitive programmers sometimes raise the main thread's limit instead, with `ulimit -s` before running a program. On macOS the most you can ask for is a little under 64 MB:

```bash
ulimit -s 65520
./sum
```

That makes the crashing `sum(upTo: 1_000_000)` above work, but only for programs started from that shell, only on the main thread, and an online judge sets its own limits. It's a workaround, not a fix.
