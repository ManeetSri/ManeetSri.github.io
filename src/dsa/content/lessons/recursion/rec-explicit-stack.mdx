## Why it matters

Recursion borrows the call stack to remember unfinished work. The call stack is small, and you can't see or control it. Replace it with an **array you manage yourself** and the same algorithm runs with no recursion at all: it can go millions of levels deep, and you decide exactly what gets remembered and in what order. This is how iterative depth-first search works, how many tree traversals are written in production code, and the answer to the interview follow-up "can you do it without recursion?".

## What the call stack was doing for you

Look at what each frame of `sum(n) = n + sum(n − 1)` remembers while it waits: its own `n`, and the fact that it still has to add `n` to whatever comes back. The call stack holds a pile of these waiting frames, newest on top.

You can keep that same pile in an array. Push what each call would have remembered on the way down; pop and finish each one on the way back up:

```swift run
func sumWithStack(_ n: Int) -> Int {
    var pending: [Int] = []                  // the "frames" waiting for an answer
    var current = n
    while current > 0 {                      // going down: remember each n
        pending.append(current)
        current -= 1
    }

    var result = 0                           // the base case's answer
    while let value = pending.popLast() {    // coming back up: finish each call
        result = value + result
    }
    return result
}

print(sumWithStack(100))
print(sumWithStack(1_000_000))
```

```output
5050
500000500000
```

The first loop is the recursion going down, and the second is the calls returning, newest first. And it handles a million levels without trouble. The recursive version crashes long before that in a debug build, as the next lesson measures, because the array lives on the **heap**, which is limited only by your computer's memory.

For a single chain like this, the plain loop from [Recursion vs iteration, and tail calls](/dsa/learn/rec-vs-iteration) is simpler still. The explicit stack earns its keep when the recursion **branches**, and a plain loop can't keep track of all the places it still has to go back to.

## A branching structure: folders

Here's a folder tree with a recursive function that prints it, indented by depth, and an explicit-stack version that prints the same thing:

```swift run
struct Folder {
    let name: String
    let subfolders: [Folder]
}

let projects = Folder(name: "Projects", subfolders: [
    Folder(name: "App", subfolders: [
        Folder(name: "Sources", subfolders: []),
        Folder(name: "Tests", subfolders: []),
    ]),
    Folder(name: "Notes", subfolders: []),
])

func printTree(_ folder: Folder, depth: Int = 0) {
    print(String(repeating: "  ", count: depth) + folder.name)
    for subfolder in folder.subfolders {
        printTree(subfolder, depth: depth + 1)
    }
}

func printTreeWithStack(_ root: Folder) {
    var stack: [(folder: Folder, depth: Int)] = [(root, 0)]
    while let (folder, depth) = stack.popLast() {
        print(String(repeating: "  ", count: depth) + folder.name)
        for subfolder in folder.subfolders.reversed() {
            stack.append((subfolder, depth + 1))
        }
    }
}

printTree(projects)
print("---")
printTreeWithStack(projects)
```

```output
Projects
  App
    Sources
    Tests
  Notes
---
Projects
  App
    Sources
    Tests
  Notes
```

How the stack version works:

- The stack holds **work still to do**: folders that haven't been printed yet, each paired with its depth. That pair is the state a recursive frame would have held in its parameters.
- Each pass pops one folder, prints it, and pushes its subfolders. Popping always takes the most recently pushed folder, so the loop goes deep into `App` before coming back to `Notes`, exactly like the recursion.
- The subfolders are pushed in **reverse** order. A stack is last in, first out, so to visit `App` before `Notes`, `Notes` must go in first. Without `.reversed()`, the output would list `Notes` before `App`.
- The loop ends when the stack is empty: `popLast()` returns `nil`, and the `while let` stops.

This visiting order, going as deep as possible before backing up, is called **depth-first**. You'll use it on trees in M35 and on graphs in M42.

## Work after the children

Printing a folder *before* its subfolders was easy, because the work happened as soon as a folder was popped. Some jobs need work **after** all the children are done: closing a bracket, adding up the children's sizes, freeing something. The recursive version puts that work after the loop:

```swift
func printTags(_ folder: Folder, depth: Int = 0) {
    let indent = String(repeating: "  ", count: depth)
    print("\(indent)<\(folder.name)>")
    for subfolder in folder.subfolders {
        printTags(subfolder, depth: depth + 1)
    }
    print("\(indent)</\(folder.name)>")      // after every child has finished
}
```

With an explicit stack, there's no "after the loop" to come back to, so you push a **reminder** instead. An enum describes the two kinds of work: open a folder, or close one. When you open a folder, push its "close" step first, *underneath* its children, so it only comes off the stack once all of them are done:

```swift run
struct Folder {
    let name: String
    let subfolders: [Folder]
}

enum Step {
    case open(Folder, depth: Int)
    case close(String, depth: Int)
}

func printTags(_ root: Folder) {
    var stack: [Step] = [.open(root, depth: 0)]
    while let step = stack.popLast() {
        switch step {
        case let .open(folder, depth):
            let indent = String(repeating: "  ", count: depth)
            if folder.subfolders.isEmpty {
                print("\(indent)<\(folder.name)/>")
            } else {
                print("\(indent)<\(folder.name)>")
                stack.append(.close(folder.name, depth: depth))   // comes off after the children
                for subfolder in folder.subfolders.reversed() {
                    stack.append(.open(subfolder, depth: depth + 1))
                }
            }
        case let .close(name, depth):
            print(String(repeating: "  ", count: depth) + "</\(name)>")
        }
    }
}

let projects = Folder(name: "Projects", subfolders: [
    Folder(name: "App", subfolders: [
        Folder(name: "Sources", subfolders: []),
        Folder(name: "Tests", subfolders: []),
    ]),
    Folder(name: "Notes", subfolders: []),
])
printTags(projects)
```

```output
<Projects>
  <App>
    <Sources/>
    <Tests/>
  </App>
  <Notes/>
</Projects>
```

Each `Step` is a tiny hand-made stack frame: it says what to do and carries the data needed to do it. A folder with no subfolders prints a self-closing tag, so it needs no reminder. This "push a reminder for later" trick is how iterative post-order tree traversal works, which you'll meet in M35.

## The trade-off

| | Recursion | Explicit stack |
| --- | --- | --- |
| Where the pending work lives | call stack (small, fixed size) | an array on the heap (as big as memory allows) |
| Code | short, mirrors the problem | longer: you manage the state yourself |
| Work after children | free: put it after the call | needs reminder entries |
| Control | fixed order | you can reorder, pause or inspect the stack |

Start with recursion when it's clearer. Convert to an explicit stack when the depth could be large, as with a very long linked list, a lopsided tree or a big grid flood fill, or when you need control the call stack doesn't give you.

<Callout kind="gotcha" title="A stack is not a queue">
Use `append` and `popLast()`, both O(1). Taking items from the front with `removeFirst()` instead is O(n) per call on an array, and it changes the algorithm: the oldest item comes out first, so the loop visits folders level by level instead of going deep. That's **breadth-first** order, done properly with a queue in M27 and on graphs in M42.
</Callout>

**Flatten a nested list** is a natural recursion. Once your recursive version passes, try a second one with an explicit stack instead, and check that it keeps the numbers in the same left-to-right order.

```cards
  back: "Keep an array of pending work. Push what each recursive call would have received, pop one item per loop pass, process it and push its 'children'. Stop when the stack is empty."
- id: push-reversed
  front: "Why push children in reverse order onto an explicit stack?"
  back: "A stack is last in, first out. Pushing the last child first means the first child is popped first, matching the recursive order."
- id: post-order-reminder
  front: "How does an explicit stack handle work that recursion does after the recursive calls?"
  back: "Push a reminder entry (such as `.close(name)`) before pushing the children, so it's popped only after all of them are finished."
- id: explicit-stack-why
  front: "What's the main benefit of an explicit stack over recursion?"
  back: "The pending work lives in an array on the heap, so depth is limited by memory, not by the small call stack. You also control the order and can inspect it."
```
