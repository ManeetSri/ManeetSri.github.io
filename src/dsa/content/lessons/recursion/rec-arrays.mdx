## Why it matters

"The sum of an array is its first element plus the sum of the rest" is a beautiful definition, and a trap. Written the obvious way in Swift, "the rest" is a fresh copy of the array at every level, and a linear algorithm quietly becomes quadratic. The fix, passing **indices** instead of pieces, is the pattern behind recursive binary search, merge sort, quicksort and nearly every recursive array algorithm you'll write.

## The tempting version

Here's the definition translated literally, with a counter for how many elements get copied along the way:

```swift run
var copied = 0

func sumByCopying(_ items: [Int]) -> Int {
    if items.isEmpty {
        return 0
    }
    let rest = Array(items.dropFirst())    // a brand-new array
    copied += rest.count
    return items[0] + sumByCopying(rest)
}

for n in [10, 100, 1_000] {
    copied = 0
    let total = sumByCopying(Array(1...n))
    print("n = \(n): sum \(total), \(copied) elements copied")
}
```

```output
n = 10: sum 55, 45 elements copied
n = 100: sum 5050, 4950 elements copied
n = 1000: sum 500500, 499500 elements copied
```

The sum is right, but look at the copying. Multiplying `n` by 10 multiplies the copying by about 100. The first call copies n − 1 elements, the next n − 2, and so on down to 0, which adds up to n(n − 1)/2. That's **O(n²)** work to add up n numbers, which a loop does in O(n).

It's memory too. Each frame keeps its `rest` alive until its call returns, so at the deepest point every copy exists at once: about n²/2 elements. For 10,000 numbers that's 50 million `Int`s, around 400 MB.

## Pass an index instead

Leave the array alone and pass a position that says where "the rest" begins:

```swift run
func sum(_ items: [Int], from index: Int = 0) -> Int {
    if index == items.count {
        return 0                            // nothing left
    }
    return items[index] + sum(items, from: index + 1)
}

print(sum([3, 1, 4, 1, 5]))
print(sum([]))
```

```output
14
0
```

The promise: `sum(items, from: index)` returns the sum of the elements from `index` to the end. The base case is an index that has run off the end, which also handles the empty array. Each call does O(1) work, so the whole thing is O(n) time, with O(n) stack.

Isn't passing `items` to every call a copy too? No. As you saw in [Copy-on-write explained](/dsa/learn/swift-copy-on-write-intro), passing an array shares its storage. A real copy only happens if someone **mutates** a shared array. Nothing here mutates, so every call reads the same buffer. The copy in the tempting version came from `Array(...)`, which builds a new array on purpose.

The default value `from index: Int = 0` keeps the call site clean: callers write `sum(numbers)` and never see the index.

## What about slices?

`items.dropFirst()` *without* the `Array(...)` around it is an `ArraySlice`: a window onto the original storage, made in O(1) (see [ArraySlice and its index pitfalls](/dsa/learn/swift-array-slices)). Recursing on slices avoids the copies:

```swift run
func sumSlice(_ items: ArraySlice<Int>) -> Int {
    guard let first = items.first else {
        return 0
    }
    return first + sumSlice(items.dropFirst())
}

let numbers = [3, 1, 4, 1, 5]
print(sumSlice(numbers[...]))
```

```output
14
```

`numbers[...]` turns the whole array into a slice. This works, and it's O(n). But remember the pitfall from M07: a slice keeps the **original** indices. After two `dropFirst()`s, the slice starts at index 2, and `items[0]` crashes. Code that only uses `first`, `dropFirst()` and `isEmpty` is safe; anything that indexes needs `items.startIndex`. Indices are more explicit and are what the rest of the course uses.

## More recursions over an index

The same shape answers many questions. Each function below says what to do at one position, and lets the recursion handle the rest:

```swift run
func largest(_ items: [Int], from index: Int = 0) -> Int {
    if index == items.count - 1 {
        return items[index]                 // one element: it's the largest
    }
    return max(items[index], largest(items, from: index + 1))
}

func firstIndex(of target: Int, in items: [Int], from index: Int = 0) -> Int? {
    if index == items.count {
        return nil                          // ran off the end: not found
    }
    if items[index] == target {
        return index                        // found: stop early
    }
    return firstIndex(of: target, in: items, from: index + 1)
}

func isSorted(_ items: [Int], from index: Int = 0) -> Bool {
    if index >= items.count - 1 {
        return true                         // zero or one element left
    }
    return items[index] <= items[index + 1] && isSorted(items, from: index + 1)
}

let data = [4, 8, 15, 16, 23, 42]
print(largest(data))
print(firstIndex(of: 16, in: data) ?? -1, firstIndex(of: 7, in: data) ?? -1)
print(isSorted(data), isSorted([3, 1, 2]))
```

```output
42
3 -1
true false
```

What to notice:

- `largest` has a different base case, the **last** element, because the largest of an empty array doesn't exist. Calling it with `[]` would crash on `items[0]`. A real version would return `Int?` or use `precondition`.
- `firstIndex` stops at the first match. Searching for 16 makes four calls, not six.
- `isSorted` stops early too: `&&` doesn't evaluate its right side if the left is `false`, so the recursion ends at the first pair out of order.

## Two indices: a range that shrinks from both sides

Some algorithms narrow a **range** instead of moving one index. Recursive binary search keeps `low` and `high`, looks at the middle, and recurses into whichever half could still hold the target:

```swift run
func binarySearch(_ items: [Int], for target: Int) -> Int? {
    func search(_ low: Int, _ high: Int) -> Int? {
        if low > high {
            return nil                      // empty range: not here
        }
        let mid = low + (high - low) / 2
        print("searching \(low)...\(high), mid \(mid)")
        if items[mid] == target {
            return mid
        } else if items[mid] < target {
            return search(mid + 1, high)
        } else {
            return search(low, mid - 1)
        }
    }
    return search(0, items.count - 1)
}

let sorted = [2, 5, 8, 12, 16, 23, 38, 56, 72, 91]
print(binarySearch(sorted, for: 23) ?? -1)
print(binarySearch(sorted, for: 7) ?? -1)
```

```output
searching 0...9, mid 4
searching 5...9, mid 7
searching 5...6, mid 5
5
searching 0...9, mid 4
searching 0...3, mid 1
searching 2...3, mid 2
-1
```

The nested helper captures `items` and `target`, so only the two indices change from call to call. Each call halves the range, so it makes O(log n) calls and the stack is only O(log n) deep. `low + (high - low) / 2` finds the middle without the risk of `low + high` overflowing, a habit from M15. You'll study binary search properly in Part IV.

## The costs side by side

| Recursing on… | Time | Extra memory |
| --- | --- | --- |
| `Array(items.dropFirst())` | O(n²) | up to O(n²): every copy alive at once |
| `items.dropFirst()` (a slice) | O(n) | O(n) stack |
| an index | O(n) | O(n) stack |
| two halves of an index range | O(n) | O(log n) stack |

The last row is the "two calls, input halves" shape from [Recursion trees and their complexity](/dsa/learn/rec-recursion-trees). It does the same total work as the index version, but the stack only grows to about log₂ n. That matters when n is large, as the last lesson of this module explains.

<Callout kind="gotcha" title="Copies hide in innocent-looking code">
All of these build a new array or string at every level and turn O(n) into O(n²): `Array(items.dropFirst())`, `Array(items[1...])`, `[items[0]] + rest`, `rest + [items[0]]` and `String(text.dropFirst())`. When you recurse over a collection, ask "does this line make a new collection?" If so, pass an index instead.
</Callout>
