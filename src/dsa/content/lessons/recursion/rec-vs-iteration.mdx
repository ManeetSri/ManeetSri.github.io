## Why it matters

Every recursion can be written as a loop, and every loop as a recursion. Knowing how to move between the two lets you pick the clearer version, and rescue a recursion that would go too deep. Along the way you'll meet **tail calls**, a kind of recursion some languages turn into loops automatically. Swift doesn't promise to, and believing it does is a classic way to crash a program that worked in testing.

## The same job, two ways

Adding up 1 to n, recursively and with a loop:

```swift run
func sumRecursive(_ n: Int) -> Int {
    if n <= 0 {
        return 0
    }
    return n + sumRecursive(n - 1)
}

func sumLoop(_ n: Int) -> Int {
    var total = 0
    var current = n
    while current > 0 {
        total += current
        current -= 1
    }
    return total
}

print(sumRecursive(100), sumLoop(100))
```

```output
5050 5050
```

Both are O(n) time. The difference is space: the recursive version keeps n frames alive at its deepest point, O(n) stack, while the loop needs two variables, O(1).

## Turning a simple recursion into a loop

When a function calls itself **once**, there's a mechanical recipe:

1. The **base case's answer** becomes the starting value of a variable.
2. The **recursive step** becomes the loop body.
3. The **change to the parameters** becomes an update of loop variables.
4. The **base case's condition** becomes the loop's stopping condition.

Euclid's algorithm is a tidy example, because the recursive call replaces `(a, b)` with `(b, a % b)`:

```swift run
func gcdRecursive(_ a: Int, _ b: Int) -> Int {
    if b == 0 {
        return a
    }
    return gcdRecursive(b, a % b)
}

func gcdLoop(_ a: Int, _ b: Int) -> Int {
    var (a, b) = (a, b)
    while b != 0 {
        (a, b) = (b, a % b)
    }
    return a
}

print(gcdRecursive(1071, 462), gcdLoop(1071, 462))
```

```output
21 21
```

The loop version shadows the parameters with variables of the same name, then updates both at once with a tuple assignment (M02), so the old `a` is used to compute the new `b`.

## Head recursion and tail recursion

Look at *where* the recursive call sits in the function.

- In **head recursion**, the recursive call happens first and the real work happens afterwards, as the calls return. M05's `countUp` was like this: it recursed, then printed, so the numbers came out smallest first.
- In **tail recursion**, the recursive call is the **very last thing** the function does. Nothing is left to do after it returns except pass its result straight back.

The test is strict. This is **not** a tail call:

```swift
return n * factorial(n - 1)
```

After `factorial(n - 1)` returns, there's still a multiplication to do, so the frame must stay alive to remember `n`. Neither is `return n + sumRecursive(n - 1)`.

You can usually make a function tail-recursive by passing the partial result **down** in an extra parameter, called an **accumulator**, instead of combining on the way back up:

```swift run
func factorial(_ n: Int, soFar: Int = 1) -> Int {
    print("factorial(\(n), soFar: \(soFar))")
    if n <= 1 {
        return soFar
    }
    return factorial(n - 1, soFar: soFar * n)     // nothing left to do afterwards
}

print(factorial(4))
```

```output
factorial(4, soFar: 1)
factorial(3, soFar: 4)
factorial(2, soFar: 12)
factorial(1, soFar: 24)
24
```

The multiplying now happens on the way **down**. By the time the base case is reached, `soFar` already holds the answer, and every frame above it returns that value unchanged. The default value `soFar: 1` means callers still write `factorial(4)`.

Notice how close this is to a loop: `n` and `soFar` change each step exactly as loop variables would. A tail-recursive function *is* a loop in disguise.

## Tail-call optimisation

Since a tail-recursive frame has nothing left to do, a compiler can **reuse** it for the next call instead of pushing a new one. That's **tail-call optimisation** (TCO). With it, a tail recursion runs in O(1) stack space, like the loop it really is. Some languages, such as Scheme, guarantee it.

**Swift doesn't.** The optimiser *may* do it in an optimised build, and it may not. Here's a tail-recursive sum, asked to go a million calls deep:

```swift
func sum(upTo n: Int, total: Int = 0) -> Int {
    if n == 0 {
        return total
    }
    return sum(upTo: n - 1, total: total + n)   // a tail call
}

print(sum(upTo: 1_000_000))
```

Compile it twice, once without optimisation and once with `-O` as in [Debug vs release builds](/dsa/learn/swift-release-builds), and run both:

```bash
swiftc -Onone sum.swift -o sum-debug
swiftc -O sum.swift -o sum-release
./sum-debug
./sum-release
```

```text title="What you'll see"
zsh: segmentation fault  ./sum-debug
500000500000
```

The debug build pushed a frame per call, ran out of stack and crashed. The release build happened to turn the recursion into a loop and printed the answer. Same code, different fate. Running it with `swift sum.swift` doesn't optimise either, so it crashes too (zsh reports `illegal hardware instruction` in that case).

Why you can't rely on the release-build behaviour:

- **Your tests and your debugging run in debug builds.** `swift test` builds without optimisation by default.
- **No error tells you when it stops working.** Add a `defer`, or any work that has to happen after the call, and it's no longer a tail call. The code compiles as before and crashes at depth.
- **It's not part of the language.** Today's optimiser does it for simple cases; nothing promises it will for yours.

So in Swift, write a tail-recursive function when it reads well, but if the depth can be large, **write the loop**.

<Callout kind="gotcha" title="Swift gotcha: tail recursion isn't stack-safe">
In Swift, a tail-recursive function uses one stack frame per call unless the optimiser chooses otherwise, and it never does in debug builds. Treat tail recursion as a style, not a safety feature. Recursion depth limits get their own lesson at the end of this module.
</Callout>

## Which one should you write?

| Prefer recursion when… | Prefer a loop when… |
| --- | --- |
| the problem branches: trees, nested data, trying choices | it's a straight line: counting, summing, scanning |
| the data is defined recursively | depth could reach tens of thousands or more |
| the recursive version is clearly shorter and easier to check | the loop is equally clear |

For a single straight chain of calls, like everything in this lesson, the loop is usually the better final answer in Swift. Recursion earns its place when a function calls itself **more than once**, which is where this module goes next. There, a loop needs a stack you manage by hand, a technique you'll learn in [Turning recursion into an explicit stack](/dsa/learn/rec-explicit-stack).
