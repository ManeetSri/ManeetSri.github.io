## Why it matters

Every recursive function runs on the **call stack**, and almost every recursion question comes down to a question about it. How much memory does this use? Why did it crash? Why did these lines print in this order? When you can picture the stack, recursion stops feeling like magic. It's also the mental model you'll need to turn recursion into loops later in this module, and to debug tree code in Part V.

## What a frame holds

You met stack frames in M05 and in [Stack vs heap](/dsa/learn/swift-stack-heap). Here's the full picture. Each time a function is called, Swift sets aside a **frame** holding:

- the call's **parameters**, such as this call's `n`;
- its **local variables**;
- the **return address**: the exact place in the caller to continue from when this call finishes. For `return n * factorial(n - 1)`, that place is "in the middle of the multiplication, waiting for the right-hand side".

Frames sit on top of each other, newest on top. A call **pushes** a frame; a return **pops** it, hands the return value to the frame below, and that frame carries on from its return address. Last in, first out, exactly like the `Stack<Element>` you built in [Generic types](/dsa/learn/swift-generic-types).

## Watch it step by step

Step through `factorial(4)` below. Each box is one call. Amber is the call running right now, grey calls are paused waiting for an answer, and green calls have finished and show what they returned. The call stack below the tree lists the frames that are alive at each moment, newest at the top.

```visual recursionTree
fn: factorial
n: 4
```

What to notice as you step:

- **Going down**, the stack grows by one frame per call. Each frame stops at the same line, paused mid-multiplication.
- **At the bottom**, `factorial(1)` is a base case. It's the only call that finishes without waiting for anyone.
- **Coming back up**, frames pop one at a time, newest first. Each popped frame's answer is exactly what the frame below was waiting for.
- At the deepest point there are four frames at once. That's the most memory this call ever uses.

## Printing the stack yourself

You can make the stack visible in plain Swift. Keep an array of call names outside the function, append a name when a call starts and remove it when the call ends:

```swift run
var callStack: [String] = []

func factorial(_ n: Int) -> Int {
    callStack.append("factorial(\(n))")
    print("stack:", callStack.joined(separator: " | "))

    let result: Int
    if n <= 1 {
        result = 1
    } else {
        result = n * factorial(n - 1)
    }

    callStack.removeLast()
    print("factorial(\(n)) returns \(result)")
    return result
}

print(factorial(3))
```

```output
stack: factorial(3)
stack: factorial(3) | factorial(2)
stack: factorial(3) | factorial(2) | factorial(1)
factorial(1) returns 1
factorial(2) returns 2
factorial(3) returns 6
6
```

The left end is the bottom of the stack and the right end is the top, the same as an array used as a stack. The three "stack" lines are three pushes; the three "returns" lines are three pops, in the opposite order.

## The real stack in LLDB

You don't have to imitate the stack: the debugger shows you the real one. In [Debugging with breakpoints and LLDB](/dsa/learn/swift-lldb) you used `bt` to print a backtrace. Here it is for the `factorial` from the visualiser above, compiled with `swiftc -g` and paused on the `return 1` line inside `factorial(4)`:

```text
(lldb) bt
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
  * frame #0: 0x0000000100000670 Factorial`factorial(n=1) at main.swift:3:9
    frame #1: 0x0000000100000694 Factorial`factorial(n=2) at main.swift:5:16
    frame #2: 0x0000000100000694 Factorial`factorial(n=3) at main.swift:5:16
    frame #3: 0x0000000100000694 Factorial`factorial(n=4) at main.swift:5:16
    frame #4: 0x00000001000005c8 Factorial`main at main.swift:8:7
    frame #5: 0x000000018fd9cd7c dyld`start + 6652
```

Read it from the top:

- **Frame #0** is the top of the stack, the call running now: `factorial(n=1)`, at line 3, the base case.
- **Frames #1 to #3** are the paused calls, each with its own `n`. All three are at line 5, column 16: the recursive call inside `n * factorial(n - 1)`. That's their return address.
- **Frame #4** is your top-level code, which called `factorial(4)` on line 8. Below that is the system code that started the program.

Typing `up` moves to frame #1, and `frame variable` then shows `n = 2`. Each frame really does have its own `n`.

## Every call has its own locals

Because each frame has its own local variables, a `var` inside a recursive function **isn't shared** between calls. That catches people out when they try to accumulate a result:

```swift run
func brokenSum(_ n: Int) -> Int {
    var total = 0
    if n > 0 {
        total += n
        _ = brokenSum(n - 1)       // this call's total is a different variable
    }
    return total
}

func sum(_ n: Int) -> Int {
    if n <= 0 {
        return 0
    }
    return n + sum(n - 1)          // use what the smaller call returns
}

print(brokenSum(3))
print(sum(3))
```

```output
3
6
```

`brokenSum(3)` adds 3 to *its* `total`. The call `brokenSum(2)` adds 2 to a completely separate `total` in its own frame, returns it, and the result is thrown away. Information travels between calls in only two ways: **down** through parameters, and **back up** through return values. (A variable declared outside the function, like `callStack` earlier, is shared by every call. That's sometimes useful, but it's easy to get wrong, so prefer parameters and return values.)

## Two calls, one path at a time

When a function calls itself twice, it's tempting to imagine both calls running at once. They don't. The first call runs to completion, and its frames are all gone, before the second call starts. Here's the classic Fibonacci function, printing the stack each time a call starts:

```swift run
var callStack: [String] = []

func fib(_ n: Int) -> Int {
    callStack.append("fib(\(n))")
    print(callStack.joined(separator: " | "))
    defer {
        callStack.removeLast()
    }
    if n < 2 {
        return n
    }
    return fib(n - 1) + fib(n - 2)
}

print(fib(3))
```

```output
fib(3)
fib(3) | fib(2)
fib(3) | fib(2) | fib(1)
fib(3) | fib(2) | fib(0)
fib(3) | fib(1)
2
```

`defer` (from M12) removes the name whenever the call ends, whichever `return` it takes. What to notice:

- There were **five** calls, but never more than **three** frames at once.
- The stack always holds a single path: from the first call down to whichever call is running now. `fib(2)` finished completely, popping `fib(1)` and `fib(0)` along the way, before `fib(1)` on the right even started.

That's an important distinction. The **number of calls** decides how long a recursion takes. The **deepest path** decides how much stack it needs. For `fib(n)` the first grows explosively, as you'll see in [Recursion trees and their complexity](/dsa/learn/rec-recursion-trees), while the second is only `n`.

<Callout kind="note" title="Stack space in Big-O">
A recursion whose deepest chain of calls is d frames long uses O(d) stack space, on top of anything else it allocates. M14 covered this in [Space complexity and the recursion stack](/dsa/learn/bigo-space). For `factorial(n)` and `fib(n)` that's O(n); for a recursion that halves its input each time, it's O(log n).
</Callout>

<Callout kind="gotcha" title="Swift gotcha: the stack isn't the heap">
The frames themselves live on the stack, but anything a frame creates on the heap, such as an array's elements or a class instance, lives on the heap and is only *referenced* from the frame. Stack overflow is about how many frames, and how big each one is, not about how much heap data you build. You'll see the real size limits in [Stack depth limits in Swift](/dsa/learn/rec-stack-limits).
</Callout>
