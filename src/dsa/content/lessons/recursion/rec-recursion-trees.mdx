## Why it matters

How fast is a recursive function? A loop wears its cost on its sleeve: count the passes. A recursion hides its cost in the pattern of calls it makes. Drawing that pattern as a **recursion tree** turns the question into counting boxes, and it's the single best tool for spotting the difference between a recursion that finishes instantly and one that would outlive you. You'll use it for every divide-and-conquer and dynamic programming algorithm later.

## Drawing the tree

A recursion tree has one box per call. A call's children are the calls it makes, left to right in the order it makes them. Base cases are the leaves, at the bottom.

When a function calls itself once, the "tree" is a straight chain. `factorial(4)`:

```text
factorial(4) → factorial(3) → factorial(2) → factorial(1)
```

When it calls itself twice, the tree branches. Here's `fib(4)` for the Fibonacci function from the last lesson, which returns `fib(n - 1) + fib(n - 2)` and has base case `n < 2`:

```text
                 fib(4)
              /         \
          fib(3)          fib(2)
         /      \        /      \
     fib(2)   fib(1)  fib(1)   fib(0)
    /      \
 fib(1)  fib(0)
```

Nine boxes, so nine calls. The tree is four levels tall, which is the deepest the stack ever gets.

## Two numbers to read off the tree

- **Time** is the total work in all the boxes. When each call does a constant amount of work besides recursing, that's the number of boxes.
- **Stack space** is the **height** of the tree: the longest path from the top box to a leaf, because that path is what's on the stack at the deepest moment.

Step through `fib(5)` and watch both. Count the boxes as they appear, and notice how often the same call turns up.

```visual recursionTree
fn: fibonacci
n: 5
```

`fib(5)` makes 15 calls, but the stack is never more than five frames deep. And the same work is done again and again: `fib(3)` is computed twice and `fib(2)` three times, each time from scratch.

## Counting calls in code

Drawing trees by hand gets old fast. A counter outside the function does the counting for you:

```swift run
var calls = 0

func fib(_ n: Int) -> Int {
    calls += 1
    if n < 2 {
        return n
    }
    return fib(n - 1) + fib(n - 2)
}

for n in [5, 10, 15, 20, 25] {
    calls = 0
    let value = fib(n)
    print("fib(\(n)) = \(value) after \(calls) calls")
}
```

```output
fib(5) = 5 after 15 calls
fib(10) = 55 after 177 calls
fib(15) = 610 after 1973 calls
fib(20) = 6765 after 21891 calls
fib(25) = 75025 after 242785 calls
```

Every time `n` goes up by 5, the number of calls is multiplied by about 11. That's **exponential growth**: adding to the input multiplies the work.

Why? Each call (except the leaves) makes two more, so each level of the tree can hold up to twice as many boxes as the one above. With about n levels, that's at most 2ⁿ boxes, so `fib` is **O(2ⁿ)**. The tree isn't completely full, because the right-hand branch shrinks by 2 instead of 1, so the true growth is closer to 1.618ⁿ. Either way it's exponential, and either way it's hopeless for large n: `fib(40)` makes 331,160,281 calls, and `fib(50)` makes over 40 billion.

The stack, meanwhile, is only O(n). The tree is enormous but not tall.

## The shapes you'll meet most

Most recursions you'll write fall into a handful of shapes. Learn to recognise them and you can read off the cost without drawing anything.

| Shape | Example | Calls | Height |
| --- | --- | --- | --- |
| One call, input shrinks by 1 | `factorial`, sum to n | n | n |
| One call, input halves | binary search, fast power | about log₂ n | about log₂ n |
| Two calls, input shrinks by 1 | `fib`, Tower of Hanoi | up to 2ⁿ | n |
| Two calls, input halves | sum of each half, merge sort | about 2n | about log₂ n |

The last row surprises people. Splitting into two halves sounds like it should explode the way `fib` does, but the halves get small very quickly. Here's a sum that adds up each half of an array separately:

```swift run
var calls = 0
var deepest = 0

func sum(_ items: [Int], _ low: Int, _ high: Int, depth: Int = 1) -> Int {
    calls += 1
    deepest = max(deepest, depth)
    if low == high {
        return items[low]
    }
    let mid = (low + high) / 2
    return sum(items, low, mid, depth: depth + 1) + sum(items, mid + 1, high, depth: depth + 1)
}

for n in [8, 1_000, 1_000_000] {
    calls = 0
    deepest = 0
    let items = Array(1...n)
    let total = sum(items, 0, n - 1)
    print("n = \(n): total \(total), \(calls) calls, \(deepest) deep")
}
```

```output
n = 8: total 36, 15 calls, 4 deep
n = 1000: total 500500, 1999 calls, 11 deep
n = 1000000: total 500000500000, 1999999 calls, 21 deep
```

The tree has n leaves, one per element, and every level above has half as many boxes: n + n/2 + n/4 + … + 1, which is about 2n. So the work is O(n), and the height is only about log₂ n: a million elements need only 21 frames. The difference from `fib` is that the input **halves** at each level instead of shrinking by one, so the tree is short.

## When each call does more work

So far each box did O(1) work. When a call also runs a loop, add up the work **level by level** instead of counting boxes:

- **Two halves, O(n) work per level.** If every call loops over its own part of the array, each level of the tree touches all n elements in total, and there are about log₂ n levels. That's O(n log n): the cost of merge sort, which you'll build in Part IV.
- **One call, input shrinks by 1, O(size) work per call.** The work is n + (n − 1) + … + 1, about n²/2, so O(n²). This is exactly the hidden cost of recursing on a *copy* of the rest of an array, which you'll meet in [Recursion over arrays with indices](/dsa/learn/rec-arrays).

M14 turned this level-by-level counting into a method in [Recurrences: substitution and recursion trees](/dsa/learn/bigo-recurrences), and [The Master theorem](/dsa/learn/bigo-master-theorem) packages the common cases into a formula. The recursion tree is the picture behind both.

<Callout kind="gotcha" title="Exponential recursion looks fine until it doesn't">
`fib(20)` returns instantly, so the code seems fine. `fib(45)` takes long enough to make you think the program has frozen. When a function calls itself more than once on inputs that shrink by only 1 or 2, assume exponential cost until you've shown otherwise. Two lessons from now, memoisation will fix `fib` with a few extra lines.
</Callout>
