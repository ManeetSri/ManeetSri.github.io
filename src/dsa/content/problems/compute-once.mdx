Some values are slow to work out, and you'd rather not work them out at all unless someone needs them. Write a function that takes a closure computing an `Int` and returns a new closure. The first call to the new closure runs the computation and returns its result. Every later call returns that same remembered result **without** running the computation again.

`ComputeOnce.wrap(_ compute: () -> Int) -> () -> Int`

That signature is missing one word, and it won't compile once your returned closure uses `compute`. Part of the task is adding it, and knowing why it's needed.

- `wrap` itself must not call `compute`. If the returned closure is never called, `compute` never runs.
- Each call to `wrap` returns a closure with its own memory, even if you wrap the same computation twice.
- The remembered result can be any `Int`, including `0` and negative numbers.

## Examples

With `var runs = 0`, and computations that add 1 to `runs` each time they run:

| Code | Result |
| --- | --- |
| `let answer = wrap { 6 * 7 }`, then `answer()`, `answer()` | `42`, `42` |
| `let slow = wrap { runs += 1; return 99 }` | nothing has run: `runs` is `0` |
| then `slow()`, `slow()`, `slow()` | `99`, `99`, `99`, and `runs` is `1` |
| `let zero = wrap { runs += 1; return 0 }`, then `zero()`, `zero()` | `0`, `0`, and `runs` went up by 1, not 2 |

## Constraints

- The returned closure is called at most 10,000 times.
- `compute` may have side effects, such as counting its runs, so the tests can see whether it ran more than once.

<Hints>
<Hint>
Write the obvious version first: return a closure that calls `compute()`. Swift refuses it with `escaping closure captures non-escaping parameter 'compute'`. Why? Your returned closure keeps `compute` and calls it later, after `wrap` has returned. Mark the parameter `@escaping` to say that's allowed.
</Hint>
<Hint>
The returned closure needs memory that survives between its calls, exactly like the counter in [Capturing values](/dsa/learn/swift-capturing). Declare a variable inside `wrap`, before the closure, and let the closure capture it.
</Hint>
<Hint>
Don't use `0` to mean "not worked out yet", because `0` might be the real answer. Use an optional, `var remembered: Int? = nil`: if it has a value, return it; otherwise run `compute`, store the result and return it.
</Hint>
</Hints>

## Solutions

<Approach title="Capture an optional result" time="O(1) per call after the first" space="O(1)">

The returned closure captures two things: `compute`, which it might call later, and `remembered`, its memory. Holding on to `compute` beyond the end of `wrap` is what makes the parameter escape, so it must be marked `@escaping`. The optional says "not worked out yet" with `nil`, which can never be confused with a real answer.

```swift
public enum ComputeOnce {
    public static func wrap(_ compute: @escaping () -> Int) -> () -> Int {
        var remembered: Int? = nil
        return {
            if let value = remembered {
                return value
            }
            let value = compute()
            remembered = value
            return value
        }
    }
}
```

Each call to `wrap` runs its body again, so each returned closure gets its own `remembered`. `wrap` never calls `compute`; only the returned closure does, on its first call. This "work it out on first use, then remember" idea is called **lazy initialisation**, and Swift builds it into the language as `lazy var` properties on your own types.

</Approach>

<Approach title="Why a sentinel value fails" time="O(1) per call after the first" space="O(1)">

A tempting shortcut stores the answer in an `Int` that starts at `0`, and treats `0` as "not worked out yet":

```swift
public static func wrap(_ compute: @escaping () -> Int) -> () -> Int {
    var remembered = 0
    return {
        if remembered == 0 {
            remembered = compute()
        }
        return remembered
    }
}
```

It works until the real answer is `0`. Then every call sees `0`, decides nothing has been computed, and runs `compute` again. Any sentinel has the same problem when the answer could be that value. A separate `Bool` flag, `var done = false`, fixes it as well as the optional does, but the optional keeps the flag and the value together so they can't disagree.

</Approach>
