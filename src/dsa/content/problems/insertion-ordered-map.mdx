swift-collections' `OrderedDictionary` remembers the order keys were added, but removing a key is O(n), because the later entries shift down and their stored positions are renumbered. Draining one from the front, as a "most recent 1,000 items" list does, is O(n²). Build an insertion-ordered dictionary, with no packages, whose removals are **amortised O(1)**, giving up the ability to index by position.

`InsertionOrderedMap.Map<Key: Hashable, Value>`, with `init()`, `count: Int`, `subscript(key: Key) -> Value?` (get and set), `removeValue(forKey:) -> Value?`, `popFirst() -> (key: Key, value: Value)?`, `keys: [Key]` and `values: [Value]`

- Setting a value for a **new** key adds it at the end. Setting a value for an **existing** key changes the value and keeps the key where it is. Setting `nil` removes the key.
- `removeValue(forKey:)` removes the key and returns its value, or returns `nil` if it isn't there.
- `popFirst()` removes and returns the oldest entry still present, or `nil` when the map is empty.
- `keys` and `values` list the entries from oldest to newest. A key that's removed and added again counts as new.

## Examples

| Code | Result |
| --- | --- |
| `map["volume"] = 7`, `map["contrast"] = 3`, `map["volume"] = 9`, then `keys`, `values` | `["volume", "contrast"]`, `[9, 3]` |
| then `map["brightness"] = 50`, `map.removeValue(forKey: "volume")`, `keys` | returns `9`; keys `["contrast", "brightness"]` |
| then `map["volume"] = 1`, `keys` | `["contrast", "brightness", "volume"]` |
| then `popFirst()`, `count` | `("contrast", 3)`, `2` |
| then `map["brightness"] = nil`, `map["missing"]`, `keys` | `nil`, `["volume"]` |
| `popFirst()` on an empty map | `nil` |

Updating `"volume"` from 7 to 9 left it first. Removing it and adding it back put it at the end, as a new key.

## Constraints

- Up to 300,000 operations in any mix.
- Lookups, insertions, updates, removals and `popFirst()` must be O(1) on average, amortised. `keys` and `values` may be O(n).
- The tests add 300,000 keys, then pop half of them from the front and remove a third of the rest from the middle. Shifting an array on every removal is about 10¹⁰ steps.
- Copying a map gives an independent map, as with any struct.

<Hints>
<Hint>
Keep the entries in an array in insertion order, plus a dictionary from each key to its slot in that array. Lookups and updates go through the dictionary. The problem is removal: deleting from the array's middle shifts everything after it, and every shifted key's slot number goes stale.
</Hint>
<Hint>
Don't shift. Leave a **tombstone**: make the array `[(key: Key, value: Value)?]` and set the removed slot to `nil`. Nothing moves, so no slot number changes. `keys` skips the tombstones. For `popFirst()`, keep a `head` index and skip tombstones from there; each slot is skipped at most once.
</Hint>
<Hint>
Tombstones waste space, and a map that keeps adding and removing would grow forever. When the tombstones outnumber the live entries, **compact**: rebuild the array without them, rewrite every key's slot in the dictionary, and reset `head` to 0. That costs O(n), but at least n / 2 removals happened since the last compaction, so it's O(1) amortised per removal.
</Hint>
</Hints>

## Solutions

<Approach title="Array and dictionary, shifting on removal" time="O(n) per removal" space="O(n)">

This is the `OrderedDictionary` design: an array of entries and a dictionary from key to index. Removal calls `remove(at:)` and renumbers every later key. Correct, and fine for a settings screen, but popping 150,000 entries from the front shifts the array 150,000 times.

</Approach>

<Approach title="Tombstones, a head index and compaction" time="O(1) amortised per operation" space="O(n)">

```swift
public enum InsertionOrderedMap {
    public struct Map<Key: Hashable, Value> {
        private var slots: [(key: Key, value: Value)?] = []
        private var slotOf: [Key: Int] = [:]
        private var head = 0                       // no live entry sits before this slot

        public init() {}

        public var count: Int { slotOf.count }

        public subscript(key: Key) -> Value? {
            get { slotOf[key].map { slots[$0]!.value } }
            set {
                guard let newValue else {
                    removeValue(forKey: key)
                    return
                }
                if let slot = slotOf[key] {
                    slots[slot]!.value = newValue      // an update keeps its place
                } else {
                    slotOf[key] = slots.count
                    slots.append((key, newValue))
                }
            }
        }

        @discardableResult
        public mutating func removeValue(forKey key: Key) -> Value? {
            guard let slot = slotOf.removeValue(forKey: key) else { return nil }
            let value = slots[slot]!.value
            slots[slot] = nil                          // a tombstone: nothing shifts
            compactIfWasteful()
            return value
        }

        public mutating func popFirst() -> (key: Key, value: Value)? {
            while head < slots.count && slots[head] == nil { head += 1 }
            guard head < slots.count, let entry = slots[head] else { return nil }
            removeValue(forKey: entry.key)
            return entry
        }

        public var keys: [Key] { slots.compactMap { $0?.key } }
        public var values: [Value] { slots.compactMap { $0?.value } }

        private mutating func compactIfWasteful() {
            guard slots.count >= 16, slots.count - count > count else { return }
            slots = slots.filter { $0 != nil }
            for (slot, entry) in slots.enumerated() { slotOf[entry!.key] = slot }
            head = 0
        }
    }
}
```

No operation ever moves a live entry except during compaction, which rewrites all of them at once and only happens after enough removals to pay for it. Order is preserved because compaction keeps the survivors in their original order.

</Approach>
