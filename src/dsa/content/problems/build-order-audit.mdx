A build tool has `targets` targets, numbered `0` to `targets - 1`. Each pair `[target, requirement]` in `needs` means `target` can only be built once `requirement` has been built. A teammate hands you a proposed `order`, and the tool replays it one step at a time. Return the index of the **first step that goes wrong**:

- the number isn't a target at all;
- that target was already built at an earlier step;
- or one of its requirements hasn't been built yet.

If every step works but some targets never got built, the order is incomplete: return `order.count`, the step that's missing. If the order builds every target exactly once with every requirement in time, return `-1`.

`BuildOrderAudit.firstBadStep(targets: Int, needs: [[Int]], order: [Int]) -> Int`

## Examples

All but the last two use `targets = 4` and `needs = [[1, 0], [2, 0], [3, 1], [3, 2]]`.

| `order` | Output | Why |
| --- | --- | --- |
| `[0, 2, 1, 3]` | `-1` | every target waits for what it needs |
| `[0, 1, 3, 2]` | `2` | target 3 needs 2, which isn't built yet |
| `[0, 1, 2]` | `3` | nothing goes wrong, but 3 is never built |
| `[0, 0, 1, 2, 3]` | `1` | target 0 is built twice |
| `[2, 7, 0, 1]` with `targets = 3`, `needs = []` | `1` | there's no target 7 |
| `[1, 0]` with `targets = 2`, `needs = [[0, 0]]` | `1` | target 0 needs itself, so it can never be built |

In the first example, `[0, 1, 2, 3]` would pass too: a dependency graph usually has many valid orders, which is exactly why you check the order's properties instead of comparing it with one answer.

## Constraints

- `1 ≤ targets ≤ 100,000` and `0 ≤ needs.count ≤ 250,000`, with `0 ≤ target, requirement < targets`. A pair can appear more than once.
- `0 ≤ order.count ≤ 100,001`. Its entries can be any `Int`, including negative ones.
- The tests use 100,000 targets and 250,000 needs, so scanning all of `needs` at every step is too slow.

<Hints>
<Hint>
Draw each pair as an edge from what must come first to what needs it: `requirement → target`. A valid order makes every edge point forwards. Watch the direction: the pair lists the target first.
</Hint>
<Hint>
Replay the order with a `built` array of `Bool`s. To check one step quickly, you need the requirements of that one target, not every pair: group the pairs by target before you start.
</Hint>
<Hint>
Each target's requirement list is read at most once, at its own step, because a second appearance of the same target fails before reading it. So the whole replay is O(targets + needs + order). After the loop, if `order.count` is smaller than `targets`, something was never built.
</Hint>
</Hints>

## Solutions

<Approach title="Scan every pair at every step" time="O(order · needs)" space="O(targets)">

For each step, loop over all of `needs` and look for pairs whose target is the one being built. It's correct, but with 100,000 steps and 250,000 pairs it does 25 billion checks.

</Approach>

<Approach title="Replay with grouped requirements" time="O(targets + needs + order)" space="O(targets + needs)">

Group the requirements by target once, then replay the order. Each step does three checks: is it a real target, is it still unbuilt, and is everything it needs already built?

```swift
public enum BuildOrderAudit {
    public static func firstBadStep(targets: Int, needs: [[Int]], order: [Int]) -> Int {
        // requirements[t]: what target t needs built before it. Edge requirement → t, "before → after".
        var requirements: [[Int]] = Array(repeating: [], count: targets)
        for pair in needs {
            requirements[pair[0]].append(pair[1])
        }
        var built = Array(repeating: false, count: targets)
        for (step, target) in order.enumerated() {
            guard (0..<targets).contains(target), !built[target] else { return step }   // unknown or twice
            if requirements[target].contains(where: { !built[$0] }) {
                return step                          // an edge pointing backwards (or a self-dependency)
            }
            built[target] = true
        }
        // No step failed, so every target in the order is distinct. Any left over were never built.
        return order.count < targets ? order.count : -1
    }
}
```

The `guard` checks the range before indexing `built`, so a target like `7` or `-1` never crashes. A self-dependency needs no special case: when its step comes, the target isn't built yet, so its own requirement fails. And a cycle means some step must fail, because whichever of its targets comes first is missing a requirement.

</Approach>
