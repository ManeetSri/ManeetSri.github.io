Design an iterator that walks a binary search tree in increasing order, one value per call, without copying all the values out first.

`BSTIteratorDesign.InorderIterator`, a struct conforming to `IteratorProtocol`, with:

- `init(_ root: TreeNode?)`: an iterator ready to return the smallest value.
- `mutating func next() -> Int?`: the next value in increasing order, or `nil` once every value has been returned.
- `var hasNext: Bool`: whether `next()` has another value to give.
- `func peek() -> Int?`: the value `next()` would return, without moving on.

Aim for O(h) memory, where h is the height of the tree, and amortised O(1) time per call.

## Examples

For the tree `[5, 3, 8, nil, 4]` (3 is the left child of 5, and 4 the right child of 3):

| Call | Result |
| --- | --- |
| `hasNext` | `true` |
| `peek()` | `3` |
| `next()` | `3` |
| `next()` | `4` |
| `next()` | `5` |
| `peek()` | `8` |
| `next()` | `8` |
| `hasNext` | `false` |
| `next()` | `nil` |

Because it conforms to `IteratorProtocol`, `Array(IteratorSequence(InorderIterator(root)).prefix(3))` gives the three smallest values.

## Constraints

- `0 ≤` number of nodes `≤ 200,000`
- The tree doesn't change while it's being iterated.
- Trees in the tests are at most 1,000 levels deep.

<Hints>
<Hint>
Copying the inorder traversal into an array in `init` is the easy version: O(1) per call, but O(n) memory and O(n) work up front even if only one value is wanted.
</Hint>
<Hint>
Do the iterative inorder walk, but pause it between values. The paused state is the stack of nodes whose left subtrees are done but which haven't been returned yet. In `init`, push the root and its chain of left children: the smallest value ends up on top.
</Hint>
<Hint>
`next()` pops the top node, pushes its right child and that child's chain of left children, and returns the popped value. `hasNext` is "the stack isn't empty", and `peek()` is the top's value.
</Hint>
</Hints>

## Solutions

<Approach title="Flatten first" time="O(n) to create, O(1) per call" space="O(n)">

Correct and simple, and fine for small trees. It misses the point of an iterator: all the work and memory are spent up front.

```swift
public struct InorderIterator: IteratorProtocol {
    private var values: [Int]
    private var position = 0

    public init(_ root: TreeNode?) {
        values = root?.inorder ?? []
    }

    public mutating func next() -> Int? {
        guard position < values.count else { return nil }
        position += 1
        return values[position - 1]
    }

    public var hasNext: Bool { position < values.count }

    public func peek() -> Int? {
        position < values.count ? values[position] : nil
    }
}
```

</Approach>

<Approach title="A paused inorder walk on a stack" time="amortised O(1) per call" space="O(h)">

The stack holds at most one node per level. A single `next()` can push a whole left spine, but each node is pushed once and popped once over the entire walk, so n calls cost O(n) in total.

```swift
public enum BSTIteratorDesign {
    public struct InorderIterator: IteratorProtocol {
        private var stack: [TreeNode] = []

        public init(_ root: TreeNode?) {
            pushLeftSpine(from: root)
        }

        private mutating func pushLeftSpine(from start: TreeNode?) {
            var current = start
            while let node = current {
                stack.append(node)
                current = node.left
            }
        }

        public mutating func next() -> Int? {
            guard let node = stack.popLast() else { return nil }
            pushLeftSpine(from: node.right)
            return node.value
        }

        public var hasNext: Bool {
            !stack.isEmpty
        }

        public func peek() -> Int? {
            stack.last?.value
        }
    }
}
```

</Approach>
