Real data is often partly sorted already: a list that was sorted yesterday with a few new items appended, or several sorted lists stuck end to end. Write a stable sort that takes advantage of that. It finds the stretches that are already in order, its **natural runs**, and merges them.

`RunAwareSort.sorted<Element>(_ items: [Element], by areInIncreasingOrder: (Element, Element) -> Bool) -> [Element]`

The tests count how often your sort calls `areInIncreasingOrder`:

- input that's **already sorted** may use at most **n** comparisons;
- input made of **8 sorted blocks** may use at most **4n**;
- **any** input may use at most n⌈log₂ n⌉ + n.

The sort must be **stable**: elements that `areInIncreasingOrder` treats as equal keep their original order. Don't use the standard library's sorts or DSAKit's.

## Examples

| `items` | Ascending runs | Returns |
| --- | --- | --- |
| `[1, 2, 3, 7, 4, 5, 6]` | `[1, 2, 3, 7]`, `[4, 5, 6]` | `[1, 2, 3, 4, 5, 6, 7]` |
| `[5, 2, 9, 1, 5, 6]` | `[5]`, `[2, 9]`, `[1, 5, 6]` | `[1, 2, 5, 5, 6, 9]` |
| `[2, 2, 2]` | `[2, 2, 2]` | `[2, 2, 2]` |
| words by length: `["pear", "fig", "plum", "yam"]` | `["pear"]`, `["fig", "plum"]`, `["yam"]` | `["fig", "yam", "pear", "plum"]` |

The first example needs 6 comparisons to find its two runs and at most 6 more to merge them. In the last, "fig" stays before "yam" and "pear" before "plum", because the sort is stable.

## Constraints

- `0 ≤ items.count ≤ 100,000`
- `areInIncreasingOrder` is a strict weak ordering, like `<`.

<Hints>
<Hint>
Find the runs in one pass. A run continues while the next element is **not** smaller than the one before it: `!areInIncreasingOrder(items[i], items[i - 1])`. That compares each neighbouring pair once, n − 1 comparisons in all, and a sorted array is a single run, so you're done.
</Hint>
<Hint>
Record where each run ends, then merge neighbouring runs in pairs: runs 1 and 2, runs 3 and 4, and so on. Repeat with the merged runs until one is left. Each pass costs at most n comparisons, and r runs need ⌈log₂ r⌉ passes.
</Hint>
<Hint>
Don't merge each run into one growing result from left to right: with many short runs that's O(n²). When a merge sees a tie, take the element from the left run, which keeps the sort stable. Bonus, not required: a stretch that's *strictly* decreasing can be reversed into a run, so reversed input costs n comparisons too.
</Hint>
</Hints>

## Solutions

<Approach title="Natural merge sort" time="O(n log n), O(n) on sorted input" space="O(n)">

The run-finding pass compares every neighbouring pair exactly once. Reversing a strictly descending stretch is safe for stability, because a strictly descending stretch contains no equal elements. The merge passes are bottom-up merge sort, except that they start from the natural runs instead of from runs of length 1. Few runs means few passes.

```swift
public enum RunAwareSort {
    public static func sorted<Element>(
        _ items: [Element], by areInIncreasingOrder: (Element, Element) -> Bool
    ) -> [Element] {
        var elements = items
        let n = elements.count
        guard n > 1 else { return elements }

        // 1. Find the natural runs. Run r is elements[bounds[r]..<bounds[r + 1]].
        var bounds = [0]
        var start = 0
        while start < n {
            var end = start + 1
            if end < n && areInIncreasingOrder(elements[end], elements[start]) {
                end += 1                                 // strictly descending: extend, then reverse
                while end < n && areInIncreasingOrder(elements[end], elements[end - 1]) {
                    end += 1
                }
                elements[start..<end].reverse()
            } else if end < n {
                end += 1                                 // ascending (equal neighbours allowed)
                while end < n && !areInIncreasingOrder(elements[end], elements[end - 1]) {
                    end += 1
                }
            }
            bounds.append(end)
            start = end
        }

        // 2. Merge neighbouring runs in pairs until one run is left
        var buffer = elements
        while bounds.count > 2 {
            var merged = [0]
            var pair = 0
            while pair + 2 < bounds.count {
                merge(&elements, &buffer, bounds[pair], bounds[pair + 1], bounds[pair + 2], areInIncreasingOrder)
                merged.append(bounds[pair + 2])
                pair += 2
            }
            if pair + 1 < bounds.count {
                merged.append(bounds[pair + 1])          // an odd run out waits for the next pass
            }
            bounds = merged
        }
        return elements
    }

    /// Merges the sorted runs elements[low..<mid] and elements[mid..<high].
    private static func merge<Element>(
        _ elements: inout [Element], _ buffer: inout [Element], _ low: Int, _ mid: Int, _ high: Int,
        _ areInIncreasingOrder: (Element, Element) -> Bool
    ) {
        for index in low..<mid {
            buffer[index] = elements[index]              // copy out the left run only
        }
        var left = low
        var right = mid
        var write = low
        while left < mid && right < high {
            if areInIncreasingOrder(elements[right], buffer[left]) {
                elements[write] = elements[right]
                right += 1
            } else {
                elements[write] = buffer[left]           // ties take the left run's element
                left += 1
            }
            write += 1
        }
        while left < mid {
            elements[write] = buffer[left]
            left += 1
            write += 1
        }
    }
}
```

Only the left run is copied out. The write position can never overtake the unread part of the right run, so the right run can be read where it is, and whatever is left of it at the end is already in place.

</Approach>
