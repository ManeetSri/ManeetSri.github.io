You keep a log of how many minutes you practise each day, and a day is *on track* when it reaches your daily `goal`. Find the longest run of consecutive days in which on-track days strictly outnumber the others, and return its length, or `0` if there's no such run.

`PracticeLogStretch.longestStretch(minutes: [Int], goal: Int) -> Int`

## Examples

| `minutes` | `goal` | Output |
| --- | --- | --- |
| `[10, 45, 10, 10, 50, 40, 10, 10, 10]` | `30` | `5` |
| `[40, 10, 35, 50, 5, 5, 60]` | `30` | `7` |
| `[5, 5, 5]` | `30` | `0` |
| `[30]` | `30` | `1` |

In the first example, days 1 to 5 (`45, 10, 10, 50, 40`) have three on-track days and two others. No longer run works: the whole log has three on-track days and six others. In the second, the whole week has four on-track days against three. A day that exactly reaches the goal counts as on track.

## Constraints

- `0 ≤ minutes.count ≤ 200,000`
- `0 ≤ minutes[i] ≤ 1,440` and `0 ≤ goal ≤ 1,440`
- The tests use 200,000 days, so checking every run, O(n²), is too slow.

<Hints>
<Hint>
Only on track or not matters, so turn the log into `+1` and `-1`. A run qualifies exactly when its values add up to more than 0. Does a sliding window work here? Think about whether a bad run can become good by growing.
</Hint>
<Hint>
It can, so a window's validity isn't monotonic. Use prefix sums instead: the run after position `i` up to position `j` qualifies when `prefix[i] < prefix[j]`. For each `j`, you want the **earliest** `i` with a smaller prefix.
</Hint>
<Hint>
The prefix starts at 0 and moves by exactly 1 each day. If `prefix[j] > 0`, the whole log so far qualifies. Otherwise, to get below `prefix[j]` it must first have reached `prefix[j] - 1`, so the earliest smaller prefix is the first time it equalled `prefix[j] - 1`. Store each prefix value's first position in a dictionary.
</Hint>
</Hints>

## Solutions

<Approach title="Check every run" time="O(n²)" space="O(1)">

Fix a start, then extend the end one day at a time, keeping a running score of `+1` and `-1`. Record the length whenever the score is positive. It's a clear reference, but 200,000 days means about 2 × 10¹⁰ steps.

</Approach>

<Approach title="Prefix sums with first positions" time="O(n)" space="O(n)">

This is the pattern from [Prefix sum + hashmap](/dsa/learn/prefix-hashmap), where the longest subarray with a given sum stores the **first** position of each prefix value. Here the condition is "sum greater than 0" rather than "sum equal to k", and the ±1 steps turn it back into an equality: look up `prefix - 1`.

```swift
public enum PracticeLogStretch {
    public static func longestStretch(minutes: [Int], goal: Int) -> Int {
        var firstSeen: [Int: Int] = [:]       // prefix value → first day index it appeared after
        var prefix = 0
        var best = 0
        for (day, value) in minutes.enumerated() {
            prefix += value >= goal ? 1 : -1
            if prefix > 0 {
                best = day + 1
            } else if let start = firstSeen[prefix - 1] {
                best = max(best, day - start)
            }
            if firstSeen[prefix] == nil {
                firstSeen[prefix] = day
            }
        }
        return best
    }
}
```

`firstSeen[prefix - 1] = start` means the prefix was one lower right after day `start`, so the run from day `start + 1` to `day` adds up to exactly `+1`: on-track days win by one. Why not look further back for an even lower prefix? Because the prefix moves one step at a time, any lower value is reached *after* the first `prefix - 1`, so `prefix - 1` gives the earliest start.

The wording ("the longest run of consecutive days") points at a sliding window, and that's the trap. A window needs validity to be monotonic, and here adding days can turn a losing run into a winning one. When a window's rule breaks, prefix sums are the next thing to try, as the table in [A sliding window template](/dsa/learn/sw-template) suggests.

</Approach>
