A search screen shouldn't hit the server on every keystroke. Simulate a **debounced** search field: each change to the text waits for a quiet period of `delay` milliseconds, and only if the user stops typing for that long does a search run, with the text as it is then. The clock is simulated: every call says what time it is, so no real timers are involved.

`SearchFieldDebounce.Debouncer`, with `init(delay: Int)`, `textChanged(to text: String, at time: Int)` and `advance(to time: Int) -> [Search]`, where `Search` has `time: Int` and `query: String`

The rules:

1. A change at time `t` schedules a search for `t + delay` with the new text, cancelling any search still waiting.
2. A waiting search runs at its time unless a change comes **before** then. A change at exactly that time is too late to cancel it: the search runs first.
3. A search that comes due doesn't run if its query is empty, or is the same as the query of the last search that did run.
4. `advance(to:)` moves the clock to `time` and returns every search that ran since the previous `advance`, oldest first, including any that ran at exactly `time`. Searches that ran between two `advance` calls, because a later change showed they were due, are returned by the next one.

Times never decrease from one call to the next. Apart from the exact tie in rule 2, these rules are what Combine's `debounce`, then `filter { !$0.isEmpty }`, then `removeDuplicates()` do to a text field's publisher.

## Examples

With `delay: 300`:

| Calls | `advance` returns |
| --- | --- |
| `"s"` at 0, `"sw"` at 120, `"swi"` at 250, then `advance(to: 500)` | `[]` |
| `advance(to: 550)` | `[550: swi]` |
| `"swif"` at 900, `"swift"` at 1000, `"swif"` at 1300, `"swift"` at 1450, then `advance(to: 2000)` | `[1300: swift]` |
| `""` at 2100, then `advance(to: 2500)` | `[]` |
| `"swift"` at 2600, then `advance(to: 3000)` | `[]` |
| `"kotlin"` at 3100, then `advance(to: 3400)` | `[3400: kotlin]` |

`[550: swi]` means a `Search` with `time` 550 and `query` `"swi"`. In the third row, the search for `"swift"` was due at 1300, exactly when the next change arrived, so it ran. The search for the final `"swift"` came due at 1750 but repeated the last query, so it didn't run. In the next two rows, the empty query is skipped, and so is `"swift"` again: the last search that *ran* was still `"swift"`.

## Constraints

- `1 ≤ delay ≤ 10⁶` and `0 ≤ time ≤ 10¹²`, never decreasing.
- Up to 100,000 changes and 100,000 calls to `advance`. Texts are at most 50 characters.

## Solutions

<Approach title="One waiting search and a buffer" time="O(1) per change, O(k) for an advance returning k searches" space="O(k)">

The whole simulation is three pieces of state: the waiting search, the last query that ran, and the searches that ran but haven't been returned yet. Both methods start by letting the clock catch up.

```swift
public enum SearchFieldDebounce {
    public struct Search: Equatable, CustomStringConvertible {
        public let time: Int
        public let query: String

        public init(time: Int, query: String) {
            self.time = time
            self.query = query
        }

        public var description: String { "\(time): \(query)" }
    }

    public final class Debouncer {
        public let delay: Int
        private var waiting: Search? = nil        // the search scheduled by the latest change
        private var lastRun: String? = nil        // the query of the last search that actually ran
        private var fired: [Search] = []          // ran since the last advance, oldest first

        public init(delay: Int) {
            self.delay = delay
        }

        /// Runs the waiting search if it is due by `time`.
        private func fireIfDue(by time: Int) {
            guard let search = waiting, search.time <= time else { return }
            waiting = nil
            if search.query.isEmpty || search.query == lastRun { return }
            lastRun = search.query
            fired.append(search)
        }

        public func textChanged(to text: String, at time: Int) {
            fireIfDue(by: time)          // a change at exactly the fire time is too late to cancel it
            waiting = Search(time: time + delay, query: text)
        }

        public func advance(to time: Int) -> [Search] {
            fireIfDue(by: time)
            defer { fired.removeAll(keepingCapacity: true) }
            return fired
        }
    }
}
```

`defer` runs after the return value has been taken, so the caller gets the searches and the buffer starts empty next time. The `<=` in `fireIfDue` is rule 2: change it to `<` and a change at exactly the fire time would cancel the search instead.

</Approach>

<Approach title="Going further: throttle instead of debounce" time="O(1) per event" space="O(1)">

A **throttle** is the other classic: run immediately on the first event, then ignore events until `interval` milliseconds have passed. It suits a scroll handler or a "like" button, where you want a response straight away but not a flood. With timestamps it's one comparison:

```swift
struct Throttle {
    let interval: Int
    private var lastRun: Int? = nil

    init(interval: Int) {
        self.interval = interval
    }

    mutating func shouldRun(at time: Int) -> Bool {
        if let lastRun, time - lastRun < interval { return false }
        lastRun = time
        return true
    }
}
```

Debounce waits for quiet and uses the *last* event; throttle acts on the *first* event and then rate-limits. Interviewers like asking for both and the difference between them.

</Approach>
