A video editor stores the colour label of every frame in an unsorted array. The playhead sits on frame `start`, and the editor wants to jump to the **nearest** frame carrying a given label, looking both backwards and forwards. Return that frame's index, or `nil` if no frame has the label. If two matches are equally close, one on each side, return the earlier one.

`NearestMatchScan.nearestIndex(of target: Int, in items: [Int], from start: Int) -> Int?`

The array isn't sorted, so this is a linear search, but stop as soon as you know the answer: a match d frames away should cost about 2d comparisons, not a scan of the whole array.

## Examples

| `items` | `target` | `start` | Output | Why |
| --- | --- | --- | --- | --- |
| `[4, 7, 1, 7, 9, 4, 7]` | `7` | `4` | `3` | 7s at 1, 3 and 6 are 3, 1 and 2 frames away |
| `[4, 7, 1, 7, 9, 4, 7]` | `4` | `3` | `5` | index 5 is 2 away, index 0 is 3 away |
| `[4, 7, 1, 7, 9, 4, 7]` | `9` | `4` | `4` | the playhead is already on a match |
| `[2, 5, 2]` | `2` | `1` | `0` | a tie: both 2s are 1 away, so the earlier wins |
| `[3, 3, 3]` | `8` | `0` | `nil` | no frame has label 8 |

## Constraints

- `1 ≤ items.count ≤ 1,000,000`
- `0 ≤ start < items.count`
- Labels can be any `Int`.
- The tests run thousands of searches whose answer is close to `start` in a big array, so scanning everything every time is too slow.

<Hints>
<Hint>
Finding every match and keeping the closest works, but it always looks at all n frames. The closest match is found first if you search in rings around `start`: distance 0, then 1, then 2, and so on.
</Hint>
<Hint>
At distance d there are two candidates, `start - d` and `start + d`. Check the left one first, so a tie goes to the earlier frame. Either candidate may be off the end of the array, so check each index before reading it.
</Hint>
<Hint>
Keep going while at least one of the two candidates is a real index. When both have run off the ends, every frame has been checked, and the answer is `nil`.
</Hint>
</Hints>

## Solutions

<Approach title="Scan everything, keep the closest" time="O(n)" space="O(1)">

Walk the whole array once, remembering the best match so far. Comparing with `<` means a later match at the same distance never replaces an earlier one.

```swift
public static func nearestIndex(of target: Int, in items: [Int], from start: Int) -> Int? {
    var best: Int? = nil
    for i in items.indices where items[i] == target {
        if best == nil || abs(i - start) < abs(best! - start) {
            best = i
        }
    }
    return best
}
```

Correct, but it never stops early: a match right next to the playhead still costs a million comparisons.

</Approach>

<Approach title="Search outwards in rings" time="O(d), O(n) when absent" space="O(1)">

Check `start`, then the two frames 1 away, then the two frames 2 away. The first match found is the nearest, and checking the left side of each ring first settles ties. The loop ends early as soon as it finds a match, and otherwise stops once both sides have run off the array.

```swift
public enum NearestMatchScan {
    public static func nearestIndex(of target: Int, in items: [Int], from start: Int) -> Int? {
        if items[start] == target { return start }
        var distance = 1
        while start - distance >= 0 || start + distance < items.count {
            let left = start - distance
            if left >= 0 && items[left] == target { return left }      // left first: ties go earlier
            let right = start + distance
            if right < items.count && items[right] == target { return right }
            distance += 1
        }
        return nil                                                      // both sides ran off the ends
    }
}
```

It's still a linear search, so the worst case, a label that isn't there, checks every frame. But the cost now depends on how far away the answer is, not on how long the video is, and that's what the editor needs.

</Approach>
