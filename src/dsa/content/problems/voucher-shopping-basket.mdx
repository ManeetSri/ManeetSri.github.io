A shop sells different items at the given `prices`, and you have `budget` to spend. You also have one voucher that halves the price of a single item in your basket. A halved price is rounded up, so an item costing 7 costs 4 with the voucher. You don't have to use it. Return the largest number of items you can buy.

`VoucherShoppingBasket.mostItems(_ prices: [Int], budget: Int) -> Int`

## Examples

| `prices` | `budget` | Output |
| --- | --- | --- |
| `[40, 10, 25, 60, 5]` | `70` | `4` |
| `[30, 30, 30]` | `89` | `3` |
| `[2, 3, 100]` | `4` | `2` |
| `[7]` | `4` | `1` |
| `[1, 1, 1]` | `2` | `2` |
| `[]` | `10` | `0` |

In the first example, without the voucher you'd stop after 5, 10 and 25. With it, buy 5, 10, 25 and 40, paying 20 for the 40: 60 in total. In the third, the voucher should go on the 3, which saves 1. Halving the 100 saves far more money, but buys you nothing. In the fifth, half of 1 rounds up to 1, so the voucher saves nothing at all.

## Constraints

- `0 ≤ prices.count ≤ 200,000` and `1 ≤ prices[i] ≤ 1,000,000,000`.
- `0 ≤ budget ≤ 10¹⁵`.
- The tests use 200,000 items, so trying the voucher on every item and every basket size is too slow.

<Hints>
<Hint>
Without the voucher, this is the lesson's shop: buy the cheapest item, then the next cheapest, while the money lasts. Now fix a basket size k. Which k items, and which one gets the voucher, make the basket as cheap as possible?
</Hint>
<Hint>
The voucher saves half of the item it's on, so in any basket it belongs on the dearest item. And for a fixed k, the k cheapest items are best: swap any item for a cheaper one left on the shelf, and the full prices drop by at least as much as the voucher's saving can.
</Hint>
<Hint>
Sort the prices. The k-item basket costs `prefix(k) − (k-th price) / 2` with integer division. As k grows, that cost never goes down, so walk k upwards and stop at the first one that doesn't fit.
</Hint>
</Hints>

## Solutions

<Approach title="Every voucher position, every size" time="O(n²)" space="O(n)">

Sort, then for each item that could take the voucher, add up the cheapest of the other items until the money runs out. That's correct, but it repeats the whole scan for every voucher choice: 200,000 scans of up to 200,000 items.

</Approach>

<Approach title="Cheapest first, voucher on the dearest so far" time="O(n log n)" space="O(n)">

Both halves of the greedy choice property come from exchange arguments. Some best basket of k items is the k cheapest, and in it the voucher should sit on the dearest. So the cost of buying k items is known after a sort, and the answer is the largest k whose cost fits. Going from k to k + 1 adds the new item's full price and moves the voucher onto it, which adds at least half its price, so the cost keeps rising and the loop can `break`.

```swift
public enum VoucherShoppingBasket {
    public static func mostItems(_ prices: [Int], budget: Int) -> Int {
        var total = 0                                    // full price of the k cheapest items
        var best = 0
        for (index, price) in prices.sorted().enumerated() {
            total += price
            if total - price / 2 > budget { break }      // the voucher saves half of the dearest, rounded down
            best = index + 1
        }
        return best
    }
}
```

Rounding the halved price **up** means the voucher saves `price / 2`, rounded **down**, which is exactly what Swift's integer division gives for positive numbers. The total fits in an `Int` easily: 200,000 items at 10⁹ each is 2 × 10¹⁴.

</Approach>
