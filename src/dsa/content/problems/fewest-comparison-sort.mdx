Every comparison in this sorting job is expensive: each one asks a person which of two photos they prefer. The lower-bound argument says sorting n items needs at least ⌈log₂ n!⌉ comparisons in the worst case. Show that the bound is **reached** for small n: sort up to 5 items using at most that many calls to `isLess`, for every possible input.

`FewestComparisonSort.sorted(_ values: [Int], by isLess: (Int, Int) -> Bool) -> [Int]`

Return `values` rearranged so that no element is `isLess` than the one before it. The only way to compare two values is to call `isLess`: don't use `<` on them, and don't call `sorted()`. The budget, for every input of that size:

| `values.count` | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| n! | 1 | 1 | 2 | 6 | 24 | 120 |
| most `isLess` calls allowed, ⌈log₂ n!⌉ | 0 | 0 | 1 | 3 | 5 | 7 |

## Examples

| `values` | `isLess` | Output | Calls allowed |
| --- | --- | --- | --- |
| `[3, 1, 2]` | `<` | `[1, 2, 3]` | 3 |
| `[4, 2, 3, 1]` | `<` | `[1, 2, 3, 4]` | 5 |
| `[5, 3, 9, 1, 7]` | `<` | `[1, 3, 5, 7, 9]` | 7 |
| `[5, 3, 9, 1, 7]` | `>` | `[9, 7, 5, 3, 1]` | 7 |
| `[2, 2, 1, 2, 1]` | `<` | `[1, 1, 2, 2, 2]` | 7 |
| `[]` | `<` | `[]` | 0 |

## Constraints

- `0 ≤ values.count ≤ 5`. Values may repeat; equal values can come out in any order.
- `isLess` is a strict ordering, like `<` or `>`.
- The tests try every ordering of distinct values for each size, and every input of 1s, 2s and 3s, counting the calls.

<Hints>
<Hint>
Up to 4 values, **binary insertion** is enough: insert each value into the sorted prefix using binary search. Inserting into k sorted values has k + 1 possible places, so it costs ⌈log₂(k + 1)⌉ comparisons: 1, then 2, then 2, for a total of 5 for four values. Inserting a fifth value would cost 3 more, giving 8: one too many.
</Hint>
<Hint>
For 5 values a, b, c, d, e, start by building information cheaply. Compare a with b and c with d, swapping so `a ≤ b` and `c ≤ d`. Then compare the two winners, b and d, swapping the pairs if needed so `b ≤ d`. Three comparisons give a chain `a ≤ b ≤ d`, plus the fact `c ≤ d`.
</Hint>
<Hint>
Insert e into the chain of 3 by binary search: 4 places, 2 comparisons. Now insert c, but only among the values **before d** in the chain, because you already know `c ≤ d`. That's at most 3 values (4 places, 2 comparisons). Total: 3 + 2 + 2 = 7. Keep track of where d ends up after e's insertion rather than searching for it by value, because values can repeat.
</Hint>
</Hints>

## Solutions

<Approach title="Binary insertion sort" time="O(n log n) comparisons" space="O(n)">

Insert each value into a sorted result with a binary search that calls `isLess`. It meets the budget for up to 4 values, but uses 8 comparisons on some inputs of 5. It's the right building block, though: the optimal sort below uses the same helper.

```swift
public static func sorted(_ values: [Int], by isLess: (Int, Int) -> Bool) -> [Int] {
    var result: [Int] = []
    for value in values {
        var low = 0
        var high = result.count
        while low < high {
            let mid = (low + high) / 2
            if isLess(value, result[mid]) { high = mid } else { low = mid + 1 }
        }
        result.insert(value, at: low)
    }
    return result
}
```

</Approach>

<Approach title="Merge insertion for five" time="at most ⌈log₂ n!⌉ comparisons" space="O(1)">

For five values, this is Ford and Johnson's merge insertion. Pairing first means every later binary search lands in a range of 3 values, which has 4 places: exactly the most that 2 comparisons can tell apart. Every comparison does as much work as one yes-or-no answer possibly can, so 7 comparisons sort all 120 orders, matching ⌈log₂ 120⌉ = 7.

```swift
public enum FewestComparisonSort {
    public static func sorted(_ values: [Int], by isLess: (Int, Int) -> Bool) -> [Int] {
        guard values.count == 5 else {
            var result: [Int] = []                               // binary insertion: 0, 1, 3 or 5 calls
            for value in values {
                insert(value, into: &result, before: result.count, by: isLess)
            }
            return result
        }
        var (a, b, c, d, e) = (values[0], values[1], values[2], values[3], values[4])
        if isLess(b, a) { swap(&a, &b) }                         // a ≤ b
        if isLess(d, c) { swap(&c, &d) }                         // c ≤ d
        if isLess(d, b) {                                        // make b ≤ d by swapping the pairs
            swap(&a, &c)
            swap(&b, &d)
        }
        var chain = [a, b, d]                                    // a ≤ b ≤ d, and c ≤ d
        let placeOfE = insert(e, into: &chain, before: 3, by: isLess)            // 2 calls
        let placeOfD = placeOfE <= 2 ? 3 : 2                     // e went before d, or after it
        insert(c, into: &chain, before: placeOfD, by: isLess)                    // at most 2 calls
        return chain
    }

    /// Inserts value into the sorted prefix sorted[0..<end] by binary search, returning its position.
    @discardableResult
    private static func insert(_ value: Int, into sorted: inout [Int], before end: Int,
                               by isLess: (Int, Int) -> Bool) -> Int {
        var low = 0
        var high = end
        while low < high {
            let mid = (low + high) / 2
            if isLess(value, sorted[mid]) { high = mid } else { low = mid + 1 }
        }
        sorted.insert(value, at: low)
        return low
    }
}
```

The same idea extends to any n, and merge insertion stays remarkably close to the bound: it's optimal up to 11 values. For larger inputs, though, nobody counts single comparisons; merge sort is already within a few percent of the bound, and memory traffic matters far more.

</Approach>
