A recipe app scales ingredient amounts to the number of servings the user types in. Users report that the app vanishes when they type something odd, or pick an ingredient the recipe doesn't use. This is the function behind it:

```swift
func scaledGrams(of ingredient: String, servingsText: String, recipe: [String: Int]) -> Int {
    let baseServings = Int("4")!          // every recipe in the app serves 4
    let servings = Int(servingsText)!     // typed by the user
    let grams = recipe[ingredient]!       // picked in a search box
    return grams * servings / baseServings
}
```

Write a version that never crashes. It returns the same answer as the original whenever the original works, and `nil` when:

- `servingsText` isn't a whole number that `Int(_:)` accepts,
- the number of servings is less than 1, or
- the recipe doesn't use `ingredient`.

`RecipeScalerDefused.scaledGrams(of ingredient: String, servingsText: String, recipe: [String: Int]) -> Int?`

Like the original, the answer is rounded down, because integer division drops any remainder.

## Examples

With `recipe = ["flour": 500, "sugar": 250, "butter": 125, "water": 0]`:

| `ingredient` | `servingsText` | Output | Why |
| --- | --- | --- | --- |
| `"flour"` | `"8"` | `1000` | 500 × 8 ÷ 4 |
| `"sugar"` | `"6"` | `375` | 250 × 6 ÷ 4 |
| `"butter"` | `"3"` | `93` | 93.75, rounded down |
| `"water"` | `"4"` | `0` | the recipe uses 0 grams, which is a real answer, not a missing one |
| `"flour"` | `"two"` | `nil` | not a number |
| `"flour"` | `"0"` | `nil` | fewer than 1 serving |
| `"salt"` | `"4"` | `nil` | the recipe doesn't use salt |

## Constraints

- The recipe has at most 100 ingredients, each between 0 and 10,000 grams. Ingredient names are case-sensitive.
- `servingsText` has at most 30 characters and may contain anything. Whenever `Int(servingsText)` succeeds, the number is between -1,000,000 and 1,000,000.

<Hints>
<Hint>
Not every `!` here is a bug. `Int("4")!` converts text typed into the code itself, so it can never fail (and plain `4` would be clearer still). The other two depend on what the user does, and those are the crashes.
</Hint>
<Hint>
Replace each risky `!` with a `guard let` that returns `nil`, and add a check that there's at least 1 serving.
</Hint>
<Hint>
One guard can do all of it, with commas between the parts: `guard let servings = Int(servingsText), servings >= 1, let grams = recipe[ingredient] else { return nil }`.
</Hint>
</Hints>

## Solutions

<Approach title="guard let instead of !" time="O(s)" space="O(1)">

The base number of servings is a fact about the app, so it becomes a plain constant. The two values that come from the user are unwrapped with `guard let`, and the extra condition rules out zero or negative servings. After the guard, everything is a plain `Int`, and the last line is the original calculation.

```swift
public enum RecipeScalerDefused {
    public static func scaledGrams(of ingredient: String, servingsText: String, recipe: [String: Int]) -> Int? {
        let baseServings = 4 // every recipe in the app serves 4
        guard let servings = Int(servingsText), servings >= 1,
              let grams = recipe[ingredient] else {
            return nil
        }
        return grams * servings / baseServings
    }
}
```

Converting the text takes time proportional to its length *s*, at most 30 characters; the dictionary lookup is quick. Note the `"water"` example: a recipe amount of 0 is a real answer, so the function returns `0`, not `nil`. Only missing values become `nil`.

</Approach>

<Approach title="Check first, then force unwrap" time="O(s)" space="O(1)">

You could keep the `!`s and put checks in front of them. This is safe, because each `!` sits right after a check that guarantees it:

```swift
public enum RecipeScalerDefused {
    public static func scaledGrams(of ingredient: String, servingsText: String, recipe: [String: Int]) -> Int? {
        guard Int(servingsText) != nil, recipe[ingredient] != nil else {
            return nil
        }
        let servings = Int(servingsText)!
        guard servings >= 1 else {
            return nil
        }
        let grams = recipe[ingredient]!
        return grams * servings / 4
    }
}
```

But it converts the text twice and looks the ingredient up twice, and its safety depends on the checks and the `!`s staying together. If someone later edits the guard, nothing warns them that a `!` below has become a crash again. When a check and a `!` sit side by side, `guard let` does both jobs in one step, which is why the first version is better.

</Approach>
