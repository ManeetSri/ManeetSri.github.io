When an app depends on your package, Swift Package Manager reads your repository's Git tags, keeps the ones that are valid versions and allowed by every requirement on the package, and picks the newest. When you release, you choose the next version by what changed in the public API. Write both halves.

`DependencyTagResolver.resolve(tags: [String], rules: [Rule]) -> String?` and `DependencyTagResolver.nextRelease(after current: String, oldAPI: Set<String>, newAPI: Set<String>) -> String`

`Rule` is an enum with cases `upToNextMajor(from: String)`, `upToNextMinor(from: String)` and `exact(String)`, each holding a version such as `"1.2.0"`.

**Valid tags.** A version is three numbers separated by dots, `MAJOR.MINOR.PATCH`, optionally written with a lowercase `v` in front (`v1.4.2`). Each number is ASCII digits with no leading zeros (`0` itself is fine) and must fit in an `Int`. Every other tag, such as `nightly`, `1.4`, `1.02.3` or `1.4.2-beta`, is ignored.

**Resolving.** Versions compare number by number: major first, then minor, then patch. A rule allows:

- `upToNextMajor(from: v)`: every version from `v` up to, but not including, the next major version. From `1.2.0`, that's `1.2.0` to `1.x.y`, never `2.0.0`.
- `upToNextMinor(from: v)`: from `v` up to, but not including, the next minor version.
- `exact(v)`: only `v`.

Return the newest valid tag that **every** rule allows, written as `major.minor.patch` without a `v`, or `nil` if there's none. With no rules, every valid tag is allowed.

**The next release.** Compare the public API before and after, as sets of names:

| What changed | From 1.0.0 on | Before 1.0.0 |
| --- | --- | --- |
| a name was removed (or renamed) | major: `1.2.0` → `2.0.0` | minor: `0.4.2` → `0.5.0` |
| names were only added | minor: `1.2.0` → `1.3.0` | patch: `0.4.2` → `0.4.3` |
| no names changed | patch: `1.2.0` → `1.2.1` | patch: `0.4.2` → `0.4.3` |

## Examples

With `tags = ["0.9.0", "0.10.0", "1.0.0", "1.2.0", "1.10.0", "1.9.3", "v1.10.1", "2.0.0", "nightly"]`:

| `rules` | Output | Why |
| --- | --- | --- |
| `[.upToNextMajor(from: "1.2.0")]` | `"1.10.1"` | the newest 1.x: 1.10 is newer than 1.9 |
| `[.upToNextMinor(from: "1.9.0")]` | `"1.9.3"` | |
| `[.upToNextMajor(from: "0.9.0")]` | `"0.10.0"` | the next major after 0.9.0 is 1.0.0 |
| `[.upToNextMajor(from: "1.2.0"), .upToNextMinor(from: "1.9.0")]` | `"1.9.3"` | both rules must allow it |
| `[.upToNextMajor(from: "1.2.0"), .upToNextMajor(from: "2.0.0")]` | `nil` | no version satisfies both |
| `[]` | `"2.0.0"` | |

| Call | Output |
| --- | --- |
| `nextRelease(after: "1.2.0", oldAPI: ["Heap.peek", "Heap.pop"], newAPI: ["Heap.peek", "Heap.pop", "Heap.replaceTop"])` | `"1.3.0"` |
| `nextRelease(after: "1.2.0", oldAPI: ["Heap.peek", "Heap.pop"], newAPI: ["Heap.top", "Heap.pop"])` | `"2.0.0"` |
| `nextRelease(after: "0.9.9", oldAPI: ["A"], newAPI: ["B"])` | `"0.10.0"` |

## Constraints

- Up to 10,000 tags, each up to 40 characters of any Unicode.
- Up to 10 rules. The versions in rules, and `current`, are always valid, with each number below 1,000,000.
- The API sets hold up to 10,000 names.

<Hints>
<Hint>
Parse a tag into a tuple `(major, minor, patch)`. Swift compares tuples of `Int`s element by element, so `(1, 10, 0) > (1, 9, 3)` is exactly version order, where the strings would compare the wrong way.
</Hint>
<Hint>
Parse strictly: drop one leading `v`, split on `"."` keeping empty pieces (`omittingEmptySubsequences: false`), and check every piece. `Int("+3")` is 3 and `Character.isNumber` accepts `"٢"`, so check for ASCII digits yourself, then reject leading zeros and numbers that overflow.
</Hint>
<Hint>
Each rule is a half-open range `[low, end)` of versions: `exact(v)` ends at the next patch. A version is allowed when it's inside every range. For the next release, `oldAPI.isSubset(of: newAPI)` tells you whether anything was removed.
</Hint>
</Hints>

## Solutions

<Approach title="Strict parsing, tuple comparison and set comparison" time="O(t · L + r · t + a)" space="O(t)">

Here t is the number of tags, L their length, r the number of rules and a the size of the API sets. Every rule becomes a half-open range, which makes "allowed by every rule" a single `allSatisfy`.

```swift
public enum DependencyTagResolver {
    public enum Rule: Equatable, Sendable {
        case upToNextMajor(from: String)
        case upToNextMinor(from: String)
        case exact(String)
    }

    private typealias Version = (major: Int, minor: Int, patch: Int)

    public static func resolve(tags: [String], rules: [Rule]) -> String? {
        let bounds = rules.compactMap(range)
        guard bounds.count == rules.count else { return nil }      // a rule with an invalid version
        var best: Version? = nil
        for tag in tags {
            guard let version = parse(tag),
                  bounds.allSatisfy({ !less(version, $0.low) && less(version, $0.end) }) else { continue }
            if best == nil || less(best!, version) { best = version }
        }
        return best.map(text)
    }

    public static func nextRelease(after current: String, oldAPI: Set<String>, newAPI: Set<String>) -> String {
        guard let version = parse(current) else { return current }
        let breaking = !oldAPI.isSubset(of: newAPI)
        let addition = !newAPI.isSubset(of: oldAPI)
        if version.major == 0 {
            // Before 1.0.0, a breaking change bumps the minor number and anything else the patch
            return breaking ? text((0, version.minor + 1, 0)) : text((0, version.minor, version.patch + 1))
        }
        if breaking { return text((version.major + 1, 0, 0)) }
        if addition { return text((version.major, version.minor + 1, 0)) }
        return text((version.major, version.minor, version.patch + 1))
    }

    /// The versions a rule allows, as a half-open range [low, end).
    private static func range(_ rule: Rule) -> (low: Version, end: Version)? {
        switch rule {
        case .upToNextMajor(let from):
            guard let low = parse(from) else { return nil }
            return (low, (low.major + 1, 0, 0))
        case .upToNextMinor(let from):
            guard let low = parse(from) else { return nil }
            return (low, (low.major, low.minor + 1, 0))
        case .exact(let version):
            guard let low = parse(version) else { return nil }
            return (low, (low.major, low.minor, low.patch + 1))
        }
    }

    /// "1.4.2" or "v1.4.2": three numbers without leading zeros, made of ASCII digits only.
    private static func parse(_ tag: String) -> Version? {
        var bytes = Array(tag.utf8)
        if bytes.first == UInt8(ascii: "v") { bytes.removeFirst() }
        let parts = bytes.split(separator: UInt8(ascii: "."), omittingEmptySubsequences: false)
        guard parts.count == 3 else { return nil }
        var numbers: [Int] = []
        for part in parts {
            guard !part.isEmpty,
                  part.allSatisfy({ $0 >= UInt8(ascii: "0") && $0 <= UInt8(ascii: "9") }),
                  part.count == 1 || part.first != UInt8(ascii: "0") else { return nil }
            var value = 0
            for digit in part {
                let (times10, overflow1) = value.multipliedReportingOverflow(by: 10)
                let (next, overflow2) = times10.addingReportingOverflow(Int(digit - UInt8(ascii: "0")))
                guard !overflow1, !overflow2 else { return nil }   // too big for Int: not a version
                value = next
            }
            numbers.append(value)
        }
        return (numbers[0], numbers[1], numbers[2])
    }

    private static func less(_ a: Version, _ b: Version) -> Bool {
        (a.major, a.minor, a.patch) < (b.major, b.minor, b.patch)
    }

    private static func text(_ version: Version) -> String {
        "\(version.major).\(version.minor).\(version.patch)"
    }
}
```

Notice that `from: "0.9.0"` allows `0.10.0`. By the pre-1.0 convention in the table, a minor bump before 1.0.0 may break callers, which is why packages that depend on a 0.x release should use `upToNextMinor`. And a rename counts as breaking because, to a caller, the old name has disappeared: the kind route is to add the new name in a minor release, deprecate the old one, and remove it only in the next major release.

</Approach>
