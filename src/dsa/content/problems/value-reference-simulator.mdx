Write a tiny interpreter that predicts what a program prints when its variables hold structs, and what it prints when they hold class instances. Each "thing" has one `Int` value. The same commands give different answers, and your interpreter has to know why.

`ValueReferenceSimulator.run(_ commands: [String], usingClasses: Bool) -> [Int]`

Each command is words separated by single spaces:

| Command | Means |
| --- | --- |
| `new a 5` | `a` gets a brand-new thing holding 5 |
| `copy b a` | `b = a` |
| `add b 3` | add 3 (which may be negative) to the value of the thing `b` holds |
| `show a` | report the value of the thing `a` holds |

Return the reported values in order. With `usingClasses` false, every thing is a struct, so `copy` makes an independent copy. With it true, every thing is a class instance, so `copy` makes `b` refer to the same object as `a`.

## Examples

| Commands | Structs | Classes |
| --- | --- | --- |
| `new a 1`, `copy b a`, `add b 99`, `show a`, `show b` | `[1, 100]` | `[100, 100]` |
| `new a 0`, `copy b a`, `copy c b`, `add c 5`, `show a` | `[0]` | `[5]` |
| `new a 1`, `copy b a`, `new a 7`, `add b 1`, `show a`, `show b` | `[7, 2]` | `[7, 2]` |
| `new a 3`, `copy a a`, `add a 1`, `show a` | `[4]` | `[4]` |

In the third example, `new a 7` points `a` at a different object. The object `b` refers to is untouched, so the two kinds agree.

## Constraints

- Up to 10,000 commands.
- Names are lowercase words. Every name used by `copy`, `add` or `show` has been given a thing earlier.
- Values stay well within `Int`.

## Solutions

<Approach title="Two dictionaries, one per kind" time="O(n)" space="O(n)">

Model each kind on its own. For structs, a dictionary from name to value: copying a value out of the dictionary and storing it under another name is already independent. For classes, a dictionary from name to object number and a second from object number to value. It works, but the parsing and the `add` and `show` logic appear twice.

```swift
var structValues: [String: Int] = [:]          // usingClasses == false
var objectOf: [String: Int] = [:]              // usingClasses == true
var objectValue: [Int: Int] = [:]
```

</Approach>

<Approach title="One model: copying a value makes a new thing" time="O(n)" space="O(n)">

Memory is a list of things, and each variable holds the number of the thing it uses. That matches the lesson's picture of references as arrows. A value-type copy is then "a new thing with the same contents", so the only line that depends on `usingClasses` is the `copy` case.

```swift
public enum ValueReferenceSimulator {
    public static func run(_ commands: [String], usingClasses: Bool) -> [Int] {
        var values: [Int] = []
        var thingOf: [String: Int] = [:]
        var shown: [Int] = []

        for command in commands {
            let words = command.split(separator: " ").map(String.init)
            switch words[0] {
            case "new":
                values.append(Int(words[2])!)
                thingOf[words[1]] = values.count - 1
            case "copy":
                let source = thingOf[words[2]]!
                if usingClasses {
                    thingOf[words[1]] = source
                } else {
                    values.append(values[source])
                    thingOf[words[1]] = values.count - 1
                }
            case "add":
                values[thingOf[words[1]]!] += Int(words[2])!
            default:
                shown.append(values[thingOf[words[1]]!])
            }
        }
        return shown
    }
}
```

Each command does a constant amount of work, so n commands take O(n) time. Things that no variable refers to any more stay in `values`; in a real program, Swift would free those objects, which M11 explains.

</Approach>
