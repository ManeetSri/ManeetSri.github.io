Both functions below are correct, and both crash when their input is large, because each call waits on one more call: a million-long chain of frames. Rewrite each as a loop that returns exactly the same answers and handles inputs a million long.

The first finds who survives when n people stand in a circle, numbered 0 to n − 1, and every k-th person in turn leaves the circle:

```swift
func survivor(_ n: Int, _ k: Int) -> Int {
    if n == 1 {
        return 0
    }
    return (survivor(n - 1, k) + k) % n
}
```

The second counts the hops from position 0 to past the end of `jumps`, where standing on position i you jump forward `jumps[i]` places:

```swift
func hops(_ jumps: [Int], from position: Int, count: Int) -> Int {
    if position >= jumps.count {
        return count
    }
    return hops(jumps, from: position + jumps[position], count: count + 1)
}
```

`UnrolledRecursions.survivor(people n: Int, step k: Int) -> Int` returns `survivor(n, k)`.

`UnrolledRecursions.hops(_ jumps: [Int]) -> Int` returns `hops(jumps, from: 0, count: 0)`.

## Examples

| Call | Output | Why |
| --- | --- | --- |
| `survivor(people: 5, step: 2)` | `2` | answers for 1 to 5 people: 0, 0, 2, 0, 2 |
| `survivor(people: 7, step: 3)` | `3` | |
| `survivor(people: 1, step: 9)` | `0` | the only person survives |
| `hops([2, 3, 1, 1, 4])` | `4` | positions 0 → 2 → 3 → 4 → 8 |
| `hops([5])` | `1` | one jump clears the array |
| `hops([])` | `0` | already past the end |

## Constraints

- `survivor`: `1 ≤ n ≤ 10⁶` and `1 ≤ k ≤ 10⁹`.
- `hops`: `0 ≤ jumps.count ≤ 10⁶` and `1 ≤ jumps[i] ≤ 10⁹`.
- The tests use inputs a million long. Swift's tests run on threads with small stacks, and Swift doesn't promise to turn tail calls into loops, so recursion would crash.

<Hints>
<Hint>
`hops` is tail-recursive: the recursive call is the very last thing it does, and its parameters change exactly like loop variables. Make `position` and `count` variables, turn the base case's condition into the loop's stopping condition, and the recursive call into updates.
</Hint>
<Hint>
`survivor` isn't tail-recursive: after the inner call returns, there's still `+ k` and `% n` to do. Think about the order the work actually happens in: the deepest call, `survivor(1, k)`, finishes first with 0, then `survivor(2, k)` uses that, then `survivor(3, k)`, and so on up to n.
</Hint>
<Hint>
So run a loop the same way, bottom up: start from the base case's answer, 0 for one person, and for m = 2, 3, …, n replace the answer with `(answer + k) % m`. The base case's answer becomes the starting value, and each unwinding step becomes one pass of the loop.
</Hint>
</Hints>

## Solutions

<Approach title="Keep the recursion" time="O(n)" space="O(n) stack">

The recursive versions are already O(n) time. The problem is space: each keeps up to n frames alive at once. In a test, a recursion that deep crashes the whole test process; on the main thread it might survive in a release build and crash in a debug one.

</Approach>

<Approach title="Loops, top down and bottom up" time="O(n)" space="O(1)">

`hops` carries its state downwards in its parameters, so its loop goes the same direction as the recursion. `survivor` builds its answer on the way back up, so its loop starts where the recursion bottoms out and climbs. Either way, the frames that held the state become two variables.

```swift
public enum UnrolledRecursions {
    public static func survivor(people n: Int, step k: Int) -> Int {
        var answer = 0
        if n >= 2 {
            for m in 2...n {
                answer = (answer + k) % m
            }
        }
        return answer
    }

    public static func hops(_ jumps: [Int]) -> Int {
        var position = 0
        var count = 0
        while position < jumps.count {
            position += jumps[position]
            count += 1
        }
        return count
    }
}
```

The `if n >= 2` matters: `2...1` is an invalid range in Swift and traps. `answer + k` stays below 10⁶ + 10⁹, and `position` below 10⁶ + 10⁹, so nothing overflows.

</Approach>
