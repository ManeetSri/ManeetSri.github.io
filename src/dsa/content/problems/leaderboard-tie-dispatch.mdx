A game shows leaderboards built from different kinds of entry: guild members, guests, bots. Write a generic ranking that works for any of them, and make sure each kind's own tie-break rule is really used, whether the entries arrive as one concrete type or as a mixed `[any Entry]`. The stub contains a trap from the lesson, and finding it is part of the problem.

`LeaderboardDispatch.top(_:count:)`, generic over `E: LeaderboardDispatch.Entry`, and `LeaderboardDispatch.top(mixed:count:)` for `[any LeaderboardDispatch.Entry]`

`Entry` is a protocol nested in `LeaderboardDispatch`. Every entry has `points`, and a `tieBreak` number that decides ties on points. A protocol extension gives every entry a default `tieBreak` of 0, and an entry type can provide its own, as a guild member does with its years in the guild. Both functions return the k best entries, best first:

1. more points first;
2. on equal points, the higher `tieBreak` first;
3. on equal points and tie-break, the one that came first in the input first.

If k is 0, return nothing; if k is more than the number of entries, return them all.

**The trap.** In the stub, `tieBreak` exists only in the protocol extension. Code that only knows "some `Entry`", which is what a generic function or an `any Entry` knows, can only call that extension version, so an entry type's own `tieBreak` is silently ignored. The tests define entry types with their own tie-breaks, including a class whose subclass overrides it. Change the protocol so they're respected.

## Examples

With guild members `ana` (points 50, tieBreak 3), `bo` (50, 7), `cy` (80, 1) and a guest `dee` (50, default tieBreak 0):

| Call | Output (names) |
| --- | --- |
| `top([ana, bo, cy], count: 2)` | `[cy, bo]` |
| `top([ana, bo, cy], count: 5)` | `[cy, bo, ana]` |
| `top(mixed: [dee, ana, cy, bo], count: 3)` | `[cy, bo, ana]` |
| `top(mixed: [dee, ana, cy, bo], count: 4)` | `[cy, bo, ana, dee]` |
| `top([ana, bo], count: 0)` | `[]` |

Three entries have 50 points. Bo's tie-break of 7 beats Ana's 3, which beats the guest's default 0. With the stub's extension-only `tieBreak`, every one of them would count as 0, and the ties would fall back to input order: `[cy, ana, bo]` in the first `count: 5` call.

## Constraints

- Up to 200,000 entries, and `0 ≤ k`.
- O(n log n) time is fine.
- Don't special-case the tests' types (you can't see them from your module anyway). The fix belongs in the protocol.

<Hints>
<Hint>
Only methods and properties **declared in the protocol** are looked up dynamically through the conformance. A member that exists only in a protocol extension is chosen at compile time from the static type, and inside a generic function, or on an `any Entry`, the static type knows nothing more than "an `Entry`".
</Hint>
<Hint>
Declare `var tieBreak: Int { get }` inside the protocol, and keep the extension's `{ 0 }` as the default implementation. Now every conforming type's own `tieBreak` is its witness for the requirement, and types without one get the default. A class's non-final property witnesses it through the class's vtable, so a subclass's `override` wins too.
</Hint>
<Hint>
Both functions can share one private generic helper that ranks any array given a key closure: compute `(points, tieBreak)` once per element, sort the indices by key descending and index ascending, and take the first k. Tuples of `Int`s compare with `<` and `>` lexicographically.
</Hint>
</Hints>

## Solutions

<Approach title="A protocol requirement with a default, and a shared helper" time="O(n log n)" space="O(n)">

```swift
public enum LeaderboardDispatch {
    public protocol Entry {
        var points: Int { get }
        var tieBreak: Int { get }               // a requirement: looked up through the conformance
    }

    private static func ranked<T>(_ items: [T], count k: Int, key: (T) -> (Int, Int)) -> [T] {
        guard k > 0 else { return [] }
        let keys = items.map(key)
        let order = items.indices.sorted { a, b in
            keys[a] != keys[b] ? keys[a] > keys[b] : a < b
        }
        return order.prefix(k).map { items[$0] }
    }

    public static func top<E: Entry>(_ entries: [E], count k: Int) -> [E] {
        ranked(entries, count: k) { ($0.points, $0.tieBreak) }
    }

    public static func top(mixed entries: [any Entry], count k: Int) -> [any Entry] {
        ranked(entries, count: k) { ($0.points, $0.tieBreak) }
    }
}

extension LeaderboardDispatch.Entry {
    public var tieBreak: Int { 0 }              // the default implementation
}
```

The one-line change, moving `tieBreak` into the protocol, is the whole fix: the code calling it doesn't change at all. That's what makes the trap dangerous. In an optimised build the generic `top` can still be specialised for a concrete type such as `[GuildMember]`, so getting dispatch right costs nothing there; `top(mixed:)` pays a witness-table lookup per entry, which is the price of mixing types.

</Approach>
