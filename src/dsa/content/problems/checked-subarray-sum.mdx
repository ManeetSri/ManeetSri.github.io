A function that sums part of an array has three preconditions: the length can't be negative, the start must be a real position, and the window must fit. The input here comes from outside your program, so instead of crashing, check each precondition and throw a descriptive error.

`CheckedSubarraySum.sum(of numbers: [Int], from start: Int, length: Int) throws -> Int`

Return the sum of the `length` numbers starting at index `start`. Check in this order and throw the first problem found:

1. `length` is negative: `RangeError.negativeLength(length)`.
2. `start` is below 0 or greater than `numbers.count`: `RangeError.startOutOfBounds(start)`. A start equal to `numbers.count` is allowed, for an empty window at the end.
3. The window runs past the end: `RangeError.tooLong(available:)`, with the number of elements that *are* available from `start`.

A window of length 0 sums to 0.

## Examples

With `numbers = [4, -2, 7, 1, 9]`:

| `start`, `length` | Result |
| --- | --- |
| `1, 3` | `6` (that's -2 + 7 + 1) |
| `0, 5` | `19` |
| `5, 0` | `0` |
| `0, -1` | throws `.negativeLength(-1)` |
| `6, 1` | throws `.startOutOfBounds(6)` |
| `3, 3` | throws `.tooLong(available: 2)` |
| `1, Int.max` | throws `.tooLong(available: 4)` |

## Constraints

- `0 ≤ numbers.count ≤ 100,000`
- `start` and `length` can be any `Int`, including `Int.max` and `Int.min`.

<Hints>
<Hint>
Write one `guard … else { throw … }` per rule, in the order given. Only after all three pass do you touch the array.
</Hint>
<Hint>
For the third rule, don't compute `start + length`: with `length` equal to `Int.max` that addition overflows and crashes. Compare `length` with `numbers.count - start`, which is safe once the second rule has passed.
</Hint>
<Hint>
After the checks, a loop over `start..<(start + length)` is safe, because you now know the sum is at most `numbers.count`.
</Hint>
</Hints>

## Solutions

<Approach title="Guard each precondition, then sum" time="O(length)" space="O(1)">

Each `guard` turns a precondition into an error the caller can handle. The order matters: it decides which error a caller sees when several rules are broken at once.

```swift
public enum CheckedSubarraySum {
    public enum RangeError: Error, Equatable {
        case negativeLength(Int)
        case startOutOfBounds(Int)
        case tooLong(available: Int)
    }

    public static func sum(of numbers: [Int], from start: Int, length: Int) throws -> Int {
        guard length >= 0 else {
            throw RangeError.negativeLength(length)
        }
        guard start >= 0 && start <= numbers.count else {
            throw RangeError.startOutOfBounds(start)
        }
        let available = numbers.count - start
        guard length <= available else {
            throw RangeError.tooLong(available: available)
        }
        var total = 0
        for index in start..<(start + length) {
            total += numbers[index]
        }
        return total
    }
}
```

If this function were only ever called by your own code with values you'd already checked, three `precondition` calls would be the right tool instead. You'll learn to answer many window queries in O(1) each with prefix sums in Part III.

</Approach>
