A car drives east along a straight road from position `0` to position `target`, using one litre of fuel per kilometre. It starts with `startFuel` litres, and its tank has no limit. Along the way are fuel stations, each `[position, litres]`, sorted by position. If the car stops at a station, it takes all of that station's fuel. Return the fewest stops needed to reach `target`, or `-1` if it can't be reached at all. Arriving at a station, or at the target, with exactly 0 litres left is fine.

`FewestRefuelStops.fewestStops(target: Int, startFuel: Int, stations: [[Int]]) -> Int`

## Examples

| `target` | `startFuel` | `stations` | Output |
| --- | --- | --- | --- |
| `60` | `20` | `[[5, 30], [10, 10], [20, 15], [45, 5]]` | `2` |
| `50` | `15` | `[[10, 10], [15, 20], [30, 5], [40, 25]]` | `3` |
| `10` | `10` | `[]` | `0` |
| `30` | `5` | `[[10, 100]]` | `-1` |

In the first example, the car can reach position 20 on its own fuel. Stopping at position 5 (30 litres) and position 20 (15 litres) gives it 65 litres in all, enough for 60 km. One stop is never enough. In the last, the car runs dry at position 5, before the only station.

## Constraints

- `1 ≤ target ≤ 1,000,000,000` and `1 ≤ startFuel ≤ 1,000,000,000`
- `0 ≤ stations.count ≤ 100,000`
- Positions are strictly increasing, with `0 < position < target`, and `1 ≤ litres ≤ 1,000,000,000`.
- The tests use 100,000 stations, so an O(n²) method is too slow.

<Hints>
<Hint>
"Fewest stops" might suggest BFS or DP, and a DP does work: for each number of stops `k`, track the farthest position you can reach. That's O(n²). Can you decide stops more cleverly?
</Hint>
<Hint>
You don't have to decide at a station whether to stop there. Drive as far as your fuel allows, and remember every station you passed. When you're about to run out, which of those stations do you wish you had stopped at?
</Hint>
<Hint>
The one with the most fuel. Keep the passed stations in a max-heap of litres. Whenever the fuel so far can't reach the next station or the target, pop the largest and count a stop. If the heap is empty at that point, return -1.
</Hint>
</Hints>

## Solutions

<Approach title="Farthest reach for each number of stops" time="O(n²)" space="O(n)">

Let `farthest[k]` be the farthest position reachable using exactly `k` stops among the stations seen so far, starting with `farthest[0] = startFuel`. For each station in order, and each `k` from high to low (as in a 0/1 knapsack, so each station is used at most once), if `farthest[k]` reaches the station then `farthest[k + 1]` can become `farthest[k] + litres`. The answer is the smallest `k` whose reach is at least `target`. It's correct, but 100,000 stations means about 5 × 10⁹ steps.

</Approach>

<Approach title="Greedy with a max-heap" time="O(n log n)" space="O(n)">

Postpone every decision until it's forced, then make the best possible choice in hindsight.

```swift
import DSAKit

public enum FewestRefuelStops {
    public static func fewestStops(target: Int, startFuel: Int, stations: [[Int]]) -> Int {
        var passed = Heap<Int>.maxHeap()
        var reach = startFuel                 // the farthest position the fuel so far can reach
        var stops = 0
        var next = 0                          // the next station not yet passed
        while reach < target {
            while next < stations.count, stations[next][0] <= reach {
                passed.insert(stations[next][1])
                next += 1
            }
            guard let best = passed.pop() else { return -1 }
            reach += best
            stops += 1
        }
        return stops
    }
}
```

Why is the largest passed station always a safe stop? Suppose an optimal plan makes `k` stops, and at the moment you first get stuck it hasn't used the largest station you've passed. It must use *some* passed station to get further, since nothing else is reachable. Swap that one for the largest: the plan gets at least as far with the same number of stops. This is the **exchange argument** from [Proving greedy: exchange argument and staying ahead](/dsa/learn/greedy-proofs), and the heap is the tool from [Task scheduler, reorganise string and IPO](/dsa/learn/heap-scheduling), where IPO uses the same "best available so far" move.

Each station is pushed once and popped at most once, so the whole drive is O(n log n). Notice what gave the pattern away: the decision at each station seemed to need knowledge of the future, and the trick was to delay it until the future had arrived.

</Approach>
