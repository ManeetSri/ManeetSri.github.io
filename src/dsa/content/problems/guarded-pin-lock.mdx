Build a PIN lock whose secret can't be read and whose rules can't be bypassed. The starter code already hides the PIN with `private` and makes the state `private(set)`, so the only way in is through the methods you write. Make them enforce every rule.

`GuardedPinLock.Lock`, with `init?(pin:)`, `isBlocked`, `enter(_:)`, `close()` and `changePin(to:)`

- **`init?(pin:)`** creates a closed lock with three attempts, or returns `nil` unless the PIN is exactly four characters, each one of the digits 0 to 9.
- **`enter(_:)`**: a blocked lock ignores every guess and returns `false`. Otherwise the right PIN opens the lock, restores all three attempts and returns `true`. A wrong PIN uses up one attempt, leaves the lock closed and returns `false`.
- **`isBlocked`** is `true` once no attempts are left. A blocked lock stays blocked.
- **`close()`** closes the lock.
- **`changePin(to:)`** changes the PIN only while the lock is open and only to a valid PIN. It returns whether the PIN changed.

## Examples

| Code | Result |
| --- | --- |
| `Lock(pin: "1234")`, `Lock(pin: "123")`, `Lock(pin: "12a4")` | a lock, `nil`, `nil` |
| `enter("1234")` on a new lock | `true`; `isOpen` is `true` |
| `enter("0000")` three times | `false` each time; `isBlocked` is `true` |
| then `enter("1234")` | `false`: the lock stays blocked |
| two wrong guesses, then `enter("1234")` | `true`, and `attemptsLeft` is back to 3 |
| `changePin(to: "5678")` while closed | `false` |

## Constraints

- Keep `pin` private and `isOpen` and `attemptsLeft` `private(set)`.
- Digits mean the ASCII characters `"0"` to `"9"`. Other characters that Swift counts as numbers, such as Arabic-Indic digits, aren't allowed.

<Hints>
<Hint>
A failable initialiser may `return nil` before setting any property. So check the PIN first with `guard`, and only then store it.
</Hint>
<Hint>
Write a `private static func isValid(_ pin: String) -> Bool` and use it in both `init?` and `changePin(to:)`. A character `c` is a digit you want when `("0"..."9").contains(c)`. Check `pin.count == 4` too.
</Hint>
<Hint>
In `enter(_:)`, deal with the blocked case first with `guard !isBlocked`. The methods can change `isOpen` and `attemptsLeft` even though code outside can't, because `private(set)` only hides the setter from outside the type.
</Hint>
</Hints>

## Solutions

<Approach title="Private state behind a few methods" time="O(1) per call" space="O(1)">

Access control turns the rules into guarantees. Because nothing outside `Lock` can set `isOpen` or `attemptsLeft`, or even read `pin`, the methods below are the only code that can change a lock, so checking the rules there is enough. The struct needs its own `public init`, since a memberwise initialiser is never public.

```swift
public enum GuardedPinLock {
    public struct Lock {
        private var pin: String
        public private(set) var isOpen = false
        public private(set) var attemptsLeft = 3

        public init?(pin: String) {
            guard Lock.isValid(pin) else {
                return nil
            }
            self.pin = pin
        }

        public var isBlocked: Bool {
            attemptsLeft == 0
        }

        private static func isValid(_ pin: String) -> Bool {
            pin.count == 4 && pin.allSatisfy { ("0"..."9").contains($0) }
        }

        public mutating func enter(_ guess: String) -> Bool {
            guard !isBlocked else {
                return false
            }
            if guess == pin {
                isOpen = true
                attemptsLeft = 3
                return true
            }
            isOpen = false
            attemptsLeft -= 1
            return false
        }

        public mutating func close() {
            isOpen = false
        }

        public mutating func changePin(to newPin: String) -> Bool {
            guard isOpen, Lock.isValid(newPin) else {
                return false
            }
            pin = newPin
            return true
        }
    }
}
```

`Character`'s `isNumber` would also accept digits from other writing systems, such as `"٤"`, which is why the check compares with the range `"0"..."9"`.

</Approach>
