A Fenwick array is usually built by calling `add` once per item, which costs O(n log n). Using what each slot is responsible for, build it in **O(n)** instead, and then go the other way: recover the original items from a finished Fenwick array, also in O(n).

`FenwickLinearBuild.build(_ items: [Int]) -> [Int]` and `FenwickLinearBuild.items(from tree: [Int]) -> [Int]`

`items[0]` is position 1. The array `build` returns has `items.count + 1` entries: index 0 is unused and holds 0, and slot i holds the sum of the items at positions `i - lowbit(i) + 1` through `i`, where `lowbit(i)` is `i & -i`. `items(from:)` takes such an array and returns the items it was built from.

## Examples

| Call | Output |
| --- | --- |
| `build([5, 3, 7, 9, 6, 4, 1, 2])` | `[0, 5, 8, 7, 24, 6, 10, 1, 37]` |
| `build([2, -1, 4])` | `[0, 2, 1, 4]` |
| `build([])` | `[0]` |
| `items(from: [0, 5, 8, 7, 24, 6, 10, 1, 37])` | `[5, 3, 7, 9, 6, 4, 1, 2]` |
| `items(from: [0])` | `[]` |

In the first example, slot 4 covers positions 1 to 4, so it holds 5 + 3 + 7 + 9 = 24, and slot 6 covers positions 5 and 6, so it holds 6 + 4 = 10.

## Constraints

- `0 ≤ items.count ≤ 1,000,000`, and every item is between −10⁹ and 10⁹.
- The array passed to `items(from:)` always came from `build`, so it has at least one entry.
- Aim for O(n) for both. Don't call a prefix-sum query per slot.

<Hints>
<Hint>
Slot i's range ends at i and starts right after slot `i - lowbit(i)`'s range ends. Which slot's range is the smallest one that strictly contains slot i's range? Try a few on paper: 1 sits inside 2, 3 inside 4, 2 inside 4, 5 inside 6.
</Hint>
<Hint>
It's slot `i + lowbit(i)`, the next stop of the update walk, often called i's **parent**. Slot i's range is exactly one of the blocks that tile its parent's range. So start with `tree[i] = items[i - 1]`, then visit i from 1 to n and add `tree[i]` into `tree[i + lowbit(i)]` if that slot exists. By the time you reach i, every block below it has already been added in.
</Hint>
<Hint>
To undo it, subtract instead, but in the opposite order, from n down to 1. Going downwards, `tree[i]` still holds its full built value when you subtract it from its parent, because only slots below i add into it, and you haven't reached them yet.
</Hint>
</Hints>

## Solutions

<Approach title="Push each slot into its parent" time="O(n)" space="O(n)">

```swift
public enum FenwickLinearBuild {
    public static func build(_ items: [Int]) -> [Int] {
        let n = items.count
        var tree = [0] + items
        for i in stride(from: 1, through: n, by: 1) {
            let parent = i + (i & -i)
            if parent <= n {
                tree[parent] += tree[i]
            }
        }
        return tree
    }

    public static func items(from tree: [Int]) -> [Int] {
        let n = tree.count - 1
        var values = tree
        for i in stride(from: n, through: 1, by: -1) {
            let parent = i + (i & -i)
            if parent <= n {
                values[parent] -= values[i]
            }
        }
        return Array(values.dropFirst())
    }
}
```

Each slot is added into exactly one parent, so the build does n additions. Undoing works slot by slot in reverse: a parent's built value is its own item plus its children's built values, so taking the children's values back out, highest first, leaves only the item.

</Approach>

<Approach title="Prefix sums, then differences" time="O(n)" space="O(n)">

Slot i is `prefix(i) − prefix(i − lowbit(i))`, where `prefix(k)` is the sum of the first k items. So compute ordinary prefix sums in one pass and fill every slot with that subtraction. For the reverse, first recover the prefix sums with the query walk, which costs O(n log n) in total, or rebuild them slot by slot in increasing order: `prefix(i) = prefix(i − lowbit(i)) + tree[i]`, where the smaller prefix is already known. Then the items are `prefix(i) − prefix(i − 1)`. That's O(n) too.

</Approach>
