A countdown timer app stores every duration in seconds. Convert a duration given in weeks, days, hours and minutes into a single number of seconds. Don't scatter bare numbers like `86400` through your code: give each conversion factor a clear name, such as `secondsPerMinute`, so the code explains itself without comments.

`NamedTimeUnits.totalSeconds(weeks: Int, days: Int, hours: Int, minutes: Int) -> Int`

A minute is 60 seconds, an hour is 60 minutes, a day is 24 hours and a week is 7 days. The parts are simply added together, so `days` can be more than 6 and `hours` more than 23.

## Examples

| Call | Returns | Why |
| --- | --- | --- |
| `totalSeconds(weeks: 0, days: 0, hours: 0, minutes: 1)` | `60` | one minute |
| `totalSeconds(weeks: 0, days: 0, hours: 1, minutes: 0)` | `3600` | 60 × 60 |
| `totalSeconds(weeks: 0, days: 1, hours: 0, minutes: 0)` | `86400` | 24 × 3,600 |
| `totalSeconds(weeks: 1, days: 2, hours: 3, minutes: 4)` | `788640` | 604,800 + 172,800 + 10,800 + 240 |
| `totalSeconds(weeks: 0, days: 0, hours: 0, minutes: 0)` | `0` | no time at all |

## Constraints

- `0 ≤ weeks, days, hours, minutes ≤ 10,000`
- The answer always fits comfortably in an `Int`.

<Hints>
<Hint>
Start with the smallest factor and build the others from it: once you have `secondsPerMinute`, you can write `let secondsPerHour = secondsPerMinute * 60`.
</Hint>
<Hint>
Follow the conventions from the lesson: lowerCamelCase, and the units in the name. `secondsPerDay` tells a reader everything; `spd`, `d` or `SECONDS_DAY` don't.
</Hint>
<Hint>
Multiply each part by its factor and add the four results: `weeks * secondsPerWeek + days * secondsPerDay + …`.
</Hint>
</Hints>

## Solutions

<Approach title="Named factors built from each other" time="O(1)" space="O(1)">

Each factor is defined in terms of the one before, so every number in the code is one a reader already knows: 60, 60, 24 and 7. The final line then reads almost like the problem statement.

```swift
public enum NamedTimeUnits {
    public static func totalSeconds(weeks: Int, days: Int, hours: Int, minutes: Int) -> Int {
        let secondsPerMinute = 60
        let secondsPerHour = secondsPerMinute * 60
        let secondsPerDay = secondsPerHour * 24
        let secondsPerWeek = secondsPerDay * 7
        return weeks * secondsPerWeek + days * secondsPerDay + hours * secondsPerHour + minutes * secondsPerMinute
    }
}
```

</Approach>

<Approach title="Magic numbers (works, but compare)" time="O(1)" space="O(1)">

This gives exactly the same answers:

```swift
public enum NamedTimeUnits {
    public static func totalSeconds(weeks: Int, days: Int, hours: Int, minutes: Int) -> Int {
        return weeks * 604800 + days * 86400 + hours * 3600 + minutes * 60
    }
}
```

But a reader has to stop and check that 604800 really is a week, and a typo such as `68400` would look just as plausible. Programmers call unexplained numbers like these **magic numbers**. Naming them costs four short lines and removes the doubt, which is why the first version is the one to aim for.

</Approach>
