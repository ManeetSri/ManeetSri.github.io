A load balancer sends each request to one of its servers, numbered from 0, at random but in proportion to their capacity: server i is chosen with probability `weights[i] / total`, where `total` is the sum of all the weights. Servers with weight 0 are being drained and must never be chosen. Build the picker.

`WeightedServerPick.Picker`, a class with `init(weights: [Int])` and `pick(using generator: inout some RandomNumberGenerator) -> Int`

Draw every random number from the generator passed to `pick`, so the tests can use a seeded one.

## Examples

| `weights` | What `pick` returns |
| --- | --- |
| `[5, 1, 3, 1]` | 0 half the time, 1 a tenth, 2 three tenths, 3 a tenth |
| `[0, 7, 0]` | always 1 |
| `[4]` | always 0 |
| `[1, 1, 1, 1]` | each server a quarter of the time |

## Constraints

- `1 ≤ weights.count ≤ 100,000`
- `0 ≤ weights[i] ≤ 1,000,000,000`, and at least one weight is positive.
- The tests make 100,000 picks from 100,000 servers, so scanning the weights on every pick (about five billion steps) is too slow. Aim for O(n) in `init` and O(log n) per pick.
- The tests count picks with seeded generators and allow for normal random variation, but not for a server picked noticeably too often or too rarely.

<Hints>
<Hint>
Lay the weights end to end on a number line from 0 to `total`. Server i owns a stretch as long as its weight. A uniformly random point lands in each stretch with the right probability.
</Hint>
<Hint>
The stretch ends are the prefix sums of the weights. With weights `[5, 1, 3, 1]`, they're `[5, 6, 9, 10]`: server 0 owns `0..<5`, server 1 owns `5..<6`, and so on.
</Hint>
<Hint>
Draw r uniformly from `0..<total`, then binary search for the first index whose prefix sum is greater than r. A weight of 0 owns an empty stretch, and "greater than" skips it automatically.
</Hint>
</Hints>

## Solutions

<Approach title="Scan the weights each time" time="O(1) init, O(n) per pick" space="O(1)">

Draw r from `0..<total` and walk the servers, subtracting each weight until r goes below it. It's correct, and too slow when many servers meet many requests.

</Approach>

<Approach title="Prefix sums and binary search" time="O(n) init, O(log n) per pick" space="O(n)">

```swift
public enum WeightedServerPick {
    public final class Picker {
        private let prefix: [Int]            // prefix[i] = weights[0] + ... + weights[i]

        public init(weights: [Int]) {
            var running = 0
            prefix = weights.map { weight in
                running += weight
                return running
            }
        }

        public func pick(using generator: inout some RandomNumberGenerator) -> Int {
            let r = Int.random(in: 0..<prefix[prefix.count - 1], using: &generator)
            var low = 0
            var high = prefix.count - 1
            while low < high {               // the first index with prefix > r
                let mid = low + (high - low) / 2
                if prefix[mid] > r {
                    high = mid
                } else {
                    low = mid + 1
                }
            }
            return low
        }
    }
}
```

The search always ends on a server with a positive weight: if `prefix[i] > r` but `prefix[i - 1] ≤ r`, then `weights[i] = prefix[i] - prefix[i - 1] > 0`. With weights up to a billion and 100,000 servers, the total stays below 10¹⁴, comfortably inside `Int`.

</Approach>

<Approach title="The alias method" time="O(n) init, O(1) per pick" space="O(n)">

For millions of picks from the same weights, Vose's alias method splits the weights into n columns of equal height, each holding at most two servers, so a pick is one random column and one biased coin flip. It's more intricate to build; prefix sums with binary search are what interviews expect.

</Approach>
