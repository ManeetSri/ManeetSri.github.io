A photo service spreads its images over cache servers that come and go. Build the consistent hashing ring that decides which server owns each key, with virtual nodes and exact rules for ties, so every client agrees.

`ConsistentHashRing.Ring`, a class with `init(virtualNodes:hash:)`, `servers`, `addServer(_:)`, `removeServer(_:)` and `server(for:)`

- `init(virtualNodes: Int, hash: @escaping (String) -> UInt64)`. The tests supply the hash function; `virtualNodes` is at least 1.
- **Points.** A server named `name` has `virtualNodes` points on the ring, at positions `hash("name#0")`, `hash("name#1")`, …, `hash("name#(virtualNodes − 1)")`.
- **Owners.** A key belongs to the point with the **smallest position ≥ `hash(key)`**. If no point is that large, it belongs to the point with the smallest position of all (the ring wraps round). If several points share that position, the one whose server name is smallest (by `<` on `String`) wins.
- `addServer(_:)` adds a server's points and returns `true`, or returns `false` if it's already on the ring. `removeServer(_:)` removes them and returns `true`, or `false` if it wasn't there.
- `servers` lists the servers on the ring, sorted by name. `server(for:)` returns a key's owner, or `nil` for an empty ring.

## Examples

With `virtualNodes: 1` and a hash that puts `"A#0"` at 10, `"B#0"` at 40, `"C#0"` at 75 and `"D#0"` at 60, and keys `"k5"`, `"k40"`, `"k41"`, `"k55"` and `"k90"` at 5, 40, 41, 55 and 90:

| Servers on the ring | Owners of k5, k40, k41, k55, k90 | Notes |
| --- | --- | --- |
| A, B, C | A, B, C, C, A | k40 is exactly at B; k90 wraps round to A |
| A, B, C, D | A, B, D, D, A | only the keys between B and D moved, to D |
| B, C, D (A removed) | B, B, D, D, B | only A's keys moved, to the next point clockwise |

## Constraints

- Up to 1,000 servers and 100 virtual nodes each, so up to 100,000 points.
- The tests look up 100,000 keys on a ring of 500 servers with 100 virtual nodes each. Scanning every point for every key would take billions of steps.
- Adding and removing servers is much rarer than looking up keys.

<Hints>
<Hint>
Keep every point as a (position, server) pair in one array sorted by position, and by server name when positions are equal. Then the owner of a key is the first point whose position is at least `hash(key)`: a lower-bound binary search. If the search runs off the end, use index 0.
</Hint>
<Hint>
Adding a server: append its points and re-sort, or sort its points and merge them in. Since adds come in bursts and lookups dominate, you can also mark the array as unsorted and sort it once, at the next lookup. Removing a server: `removeAll(where:)` keeps the remaining points in order.
</Hint>
<Hint>
Storing the server's name in every point means copying strings around whenever the array changes. Storing a small number for each server, with an array from number to name, keeps the points cheap; compare names only when two positions are equal.
</Hint>
</Hints>

## Solutions

<Approach title="Scan every point" time="O(p) per lookup" space="O(p)">

For each key, look at all p points and keep the best by the rules: the smallest (position, name) among positions ≥ the key's, or the smallest overall if there are none. It's the model the tests use, but 100,000 lookups over 50,000 points is 5 billion comparisons.

</Approach>

<Approach title="Sorted points and binary search" time="O(log p) per lookup, O(p log p) after adding servers" space="O(p)">

Lookups are a lower bound in a sorted array. Points store server numbers, and the array is sorted lazily, so adding 500 servers costs one sort, not 500.

```swift
public enum ConsistentHashRing {
    public final class Ring {
        public let virtualNodes: Int
        private let hash: (String) -> UInt64
        private var names: [String] = []                  // server number → name
        private var numbers: [String: Int] = [:]          // name → server number, for servers on the ring
        private var points: [(position: UInt64, server: Int)] = []
        private var needsSort = false

        public init(virtualNodes: Int, hash: @escaping (String) -> UInt64) {
            self.virtualNodes = max(1, virtualNodes)
            self.hash = hash
        }

        public var servers: [String] {
            numbers.keys.sorted()
        }

        @discardableResult
        public func addServer(_ name: String) -> Bool {
            guard numbers[name] == nil else { return false }
            let number = names.count
            names.append(name)
            numbers[name] = number
            for i in 0..<virtualNodes {
                points.append((hash("\(name)#\(i)"), number))
            }
            needsSort = true
            return true
        }

        @discardableResult
        public func removeServer(_ name: String) -> Bool {
            guard let number = numbers.removeValue(forKey: name) else { return false }
            points.removeAll { $0.server == number }      // keeps the rest in order
            return true
        }

        public func server(for key: String) -> String? {
            guard !points.isEmpty else { return nil }
            if needsSort {
                points.sort { $0.position != $1.position ? $0.position < $1.position : names[$0.server] < names[$1.server] }
                needsSort = false
            }
            let position = hash(key)
            var low = 0
            var high = points.count
            while low < high {
                let mid = (low + high) / 2
                if points[mid].position < position { low = mid + 1 } else { high = mid }
            }
            return names[points[low == points.count ? 0 : low].server]
        }
    }
}
```

The binary search finds the first point at or after the key's position, so a key exactly at a point belongs to it. Because equal positions are sorted by name, that first point is the one the tie rule picks.

</Approach>
