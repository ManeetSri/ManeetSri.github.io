Given three side lengths, say what kind of triangle they make: `"equilateral"` when all three sides are equal, `"isosceles"` when exactly two are equal, `"scalene"` when all three differ, and `"invalid"` when the sides can't make a triangle at all.

`TriangleKind.kind(a: Int, b: Int, c: Int) -> String`

Sides can't make a triangle when any of them is 0 or negative, or when two sides together are **not longer** than the third. Sides of 1, 2 and 3 would lie flat in a straight line, so they're invalid too.

## Examples

| Input | Output |
| --- | --- |
| `a: 3, b: 3, c: 3` | `"equilateral"` |
| `a: 5, b: 8, c: 5` | `"isosceles"` |
| `a: 3, b: 4, c: 5` | `"scalene"` |
| `a: 1, b: 2, c: 3` | `"invalid"` |
| `a: 2, b: 2, c: 5` | `"invalid"` |
| `a: 0, b: 4, c: 4` | `"invalid"` |

`2, 2, 5` has two equal sides, but the two short sides can't reach across the long one, so it's invalid rather than isosceles.

## Constraints

- `-1,000,000 ≤ a, b, c ≤ 1,000,000`
- The sides can come in any order: the longest isn't always `c`.

<Hints>
<Hint>
Decide "invalid" first and leave the function straight away with `return "invalid"`. After that, every later line can assume the sides make a real triangle.
</Hint>
<Hint>
Three checks catch flat and impossible triangles in any order: `a + b > c`, `a + c > b` and `b + c > a`. All three must be true. Add a check that every side is above 0, too.
</Hint>
<Hint>
Test for equilateral before isosceles. Three equal sides also means "two equal sides", so if you check isosceles first, an equilateral triangle gets the wrong answer.
</Hint>
</Hints>

## Solutions

<Approach title="Rule out, then classify" time="O(1)" space="O(1)">

A `guard` handles every invalid case at the top, so the rest of the function only deals with real triangles. Each later `return` ends the function as soon as the answer is known, so the checks can run from the most specific (all three equal) to the least.

```swift
public enum TriangleKind {
    public static func kind(a: Int, b: Int, c: Int) -> String {
        guard a > 0, b > 0, c > 0, a + b > c, a + c > b, b + c > a else {
            return "invalid"
        }
        if a == b && b == c {
            return "equilateral"
        }
        if a == b || b == c || a == c {
            return "isosceles"
        }
        return "scalene"
    }
}
```

The final `return "scalene"` has no `if` around it. That's deliberate: every path through a function that promises a `String` must reach a `return`, and this one catches everything the earlier checks didn't.

Are the `> 0` checks needed? Strictly, no: add `a + b > c` and `a + c > b` together and the `b` and `c` cancel out, leaving `2a > 0`, so the three sum checks already force every side to be positive. Keeping them costs nothing and says the rule plainly, so a reader doesn't have to do that algebra to trust the function.

</Approach>
