An array is **nearly sorted**: every value is at most `k` positions away from where it belongs in sorted order. Sort it into increasing order, **in place**, in O(n · k) time.

`NearlySortedArray.sort(_ numbers: inout [Int], maxDistance k: Int)`

## Examples

| `numbers` | `k` | After sorting |
| --- | --- | --- |
| `[2, 1, 4, 3, 6, 5]` | `1` | `[1, 2, 3, 4, 5, 6]` |
| `[3, 1, 2, 6, 4, 5]` | `2` | `[1, 2, 3, 4, 5, 6]` |
| `[5, 5, 4]` | `2` | `[4, 5, 5]` |
| `[10, 20, 30]` | `0` | `[10, 20, 30]` |
| `[]` | `3` | `[]` |

In the second example, the 3 at index 0 belongs at index 2, and the 6 at index 3 belongs at index 5: both are 2 places from home, and nothing is further.

## Constraints

- `0 ≤ numbers.count ≤ 200,000` and `k ≥ 0`
- The large tests use 200,000 values with k = 6.
- O(1) extra space. Sorting with `sort()` would be O(n log n); aim for O(n · k).

<Hints>
<Hint>
Which simple sort does less work the closer its input is to sorted? Its cost is O(n + d), where d is the number of pairs that are out of order.
</Hint>
<Hint>
Insertion sort shifts a key left past every bigger value before it. If every value is at most k places from home, a bigger value to the key's left must have started fewer than 2k places away, or one of the two would be more than k from home.
</Hint>
<Hint>
So each key shifts fewer than 2k times: O(n · k) in total. Plain insertion sort is the whole answer, and it doesn't even need to look at k.
</Hint>
</Hints>

## Solutions

<Approach title="Insertion sort" time="O(n · k)" space="O(1)">

Take each value in turn as the key, shift the bigger values before it one place right, and drop it into the gap. On nearly sorted input the inner loop stops after a few steps.

```swift
public enum NearlySortedArray {
    public static func sort(_ numbers: inout [Int], maxDistance k: Int) {
        guard numbers.count > 1 else { return }
        for i in 1..<numbers.count {
            let key = numbers[i]
            var gap = i
            while gap > 0 && numbers[gap - 1] > key {
                numbers[gap] = numbers[gap - 1]
                gap -= 1
            }
            numbers[gap] = key
        }
    }
}
```

Why fewer than 2k shifts per key? Say the key x is at index i and a bigger value y is at index j, to its left. In sorted order y comes after x. x belongs at index i − k or later, and y belongs at j + k or earlier, so j + k must be beyond i − k: j is more than i − 2k. Only values that started in those 2k positions can be shifted past x.

With k = 6 and 200,000 values, that's at most 2.4 million shifts, and usually far fewer. Selection sort, by contrast, would make 20 billion comparisons whatever k is.

</Approach>

<Approach title="A sliding heap (preview)" time="O(n log k)" space="O(k)">

The value that belongs at index 0 must be among the first k + 1 values. Keep those k + 1 values in a min-heap, pop the smallest into place, push the next value, and repeat. That's O(n log k), better when k is large. Heaps arrive in M39, so for now insertion sort is the tool, and for small k it's just as fast.

</Approach>
