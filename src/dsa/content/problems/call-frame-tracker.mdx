Every function call puts a frame on the stack, and every return throws the newest frame away in one step. Replay a log of calls and returns on a stack of limited size, and report how deep it got and whether it overflowed.

`CallFrameTracker.analyse(_ events: [String], limit: Int) -> CallFrameTracker.Report`

Each event is one of:

| Event | Means |
| --- | --- |
| `call <name> <bytes>` | a function is called, pushing a frame of that many bytes |
| `return` | the newest frame is popped |

Return a `Report` with:

- **`peakBytes`**: the most stack memory in use at any moment.
- **`peakDepth`**: the most frames on the stack at any moment.
- **`overflowIndex`**: the index of the first call that would take the stack above `limit` bytes, or `nil` if none does. That call crashes the program, so the replay stops there, and the peaks are the ones reached before it. Filling the stack to exactly `limit` is fine.

## Examples

| Events | `limit` | Report |
| --- | --- | --- |
| `call main 32`, `call sumDigits 48`, `call sumDigits 48`, `return`, `return`, `call print 16`, `return`, `return` | 1000 | 128 bytes, 3 frames, no overflow |
| `call main 10`, `call a 100`, `return`, `call b 100`, `return` | 1000 | 110 bytes, 2 frames, no overflow |
| `call main 8`, `call big 500`, `return`, `call f 8`, `call f 8`, `call f 8` | 1000 | 508 bytes, 4 frames, no overflow |
| `call main 32`, then `call f 48` four times | 200 | 176 bytes, 4 frames, overflow at index 4 |
| `call main 64` | 32 | 0 bytes, 0 frames, overflow at index 0 |

The third example shows that the most bytes and the most frames can happen at different moments: one big frame, then several small ones.

## Constraints

- Up to 200,000 events. Frame sizes are positive, and `limit` is at most 100,000,000.
- A `return` never happens with an empty stack.

<Hints>
<Hint>
The stack itself is the right model: an array of frame sizes. A call appends, and a return removes the last one, the frame that was pushed most recently.
</Hint>
<Hint>
Keep a running total of the bytes in use, so you never add the whole array up again. After each call, update both peaks with `max`.
</Hint>
<Hint>
Check for overflow *before* pushing: if `inUse + size > limit`, return the report straight away with the event's index. `events.enumerated()` gives you each index alongside its event.
</Hint>
</Hints>

## Solutions

<Approach title="Replay the stack, with a running total" time="O(n)" space="O(d) for the deepest d frames">

Pushing and popping at the end of an array are both O(1), and the running total means each event costs a constant amount of work. Returning frees a frame with one subtraction, which is the reason stack memory is so cheap compared with the heap.

```swift
public enum CallFrameTracker {
    // Report as in the starter code

    public static func analyse(_ events: [String], limit: Int) -> Report {
        var frames: [Int] = []
        var inUse = 0
        var peakBytes = 0
        var peakDepth = 0

        for (index, event) in events.enumerated() {
            let words = event.split(separator: " ")
            if words[0] == "return" {
                inUse -= frames.removeLast()
                continue
            }
            let size = Int(words[2])!
            if inUse + size > limit {
                return Report(peakBytes: peakBytes, peakDepth: peakDepth, overflowIndex: index)
            }
            frames.append(size)
            inUse += size
            peakBytes = max(peakBytes, inUse)
            peakDepth = max(peakDepth, frames.count)
        }
        return Report(peakBytes: peakBytes, peakDepth: peakDepth, overflowIndex: nil)
    }
}
```

With macOS's 8 MB main-thread stack and 80-byte frames, a recursion can go about 100,000 calls deep before it overflows. Real frame sizes vary, which is why the lesson says to reason about recursion depth rather than to rely on exact numbers.

</Approach>
