A quiz night's scoreboard lists each team's score in the order the teams played. For every team, count how many of the teams that played **after** it scored strictly lower. In other words: for each position i, return how many later positions j hold a value strictly smaller than `numbers[i]`.

`SmallerToTheRight.counts(_ numbers: [Int]) -> [Int]`

## Examples

| `numbers` | Output |
| --- | --- |
| `[6, 3, 8, 2]` | `[2, 1, 1, 0]` |
| `[1, 2, 3]` | `[0, 0, 0]` |
| `[3, 3, 1]` | `[1, 1, 0]` |
| `[-1, -2, -1]` | `[1, 0, 0]` |
| `[]` | `[]` |

In the first example, 6 has two smaller values after it (3 and 2), 3 has one (2), 8 has one (2), and the last value has nothing after it. In `[3, 3, 1]`, the two 3s don't count each other, because equal isn't smaller.

## Constraints

- `0 ≤ numbers.count ≤ 100,000`
- `-10⁹ ≤ numbers[i] ≤ 10⁹`, and values can repeat.
- The tests use arrays of 50,000 values, so checking every later position (O(n²)) is too slow.

<Hints>
<Hint>
The total of all the counts is the number of inversions, which merge sort counts in O(n log n). Can each element keep its own tally during the same merge sort?
</Hint>
<Hint>
Sorting moves values away from their positions, so sort the **positions** instead: an array of indices, compared by the values they point to. Then each element always knows whose tally to update.
</Hint>
<Hint>
When the merge takes an element from the **left** half, every element already taken from the right half is smaller than it and came after it in the original array. Add how many have been taken from the right so far, `right - mid`. On ties, take the left element first so that equal values aren't counted.
</Hint>
</Hints>

## Solutions

<Approach title="Check every later value" time="O(n²)" space="O(1)">

For each position, scan everything after it and count the smaller values. It's correct and a good checker for small inputs, but 50,000 values means more than a billion comparisons.

</Approach>

<Approach title="Merge sort the positions" time="O(n log n)" space="O(n)">

Merge sort an array of indices by their values. Whenever the merge places an index from the left half, the right-half indices placed before it are exactly the later, smaller values it hasn't counted yet.

```swift
public enum SmallerToTheRight {
    public static func counts(_ numbers: [Int]) -> [Int] {
        let n = numbers.count
        var tally = Array(repeating: 0, count: n)
        var order = Array(0..<n)                // positions, merge sorted by their values
        var buffer = order

        func sort(_ low: Int, _ high: Int) {
            guard high - low > 1 else { return }
            let mid = low + (high - low) / 2
            sort(low, mid)
            sort(mid, high)
            for index in low..<high {
                buffer[index] = order[index]
            }
            var left = low
            var right = mid
            for write in low..<high {
                if right == high || (left < mid && numbers[buffer[left]] <= numbers[buffer[right]]) {
                    tally[buffer[left]] += right - mid      // smaller values from the right, already placed
                    order[write] = buffer[left]
                    left += 1
                } else {
                    order[write] = buffer[right]
                    right += 1
                }
            }
        }

        sort(0, n)
        return tally
    }
}
```

Why is each smaller later value counted exactly once? A pair `i < j` with `numbers[i] > numbers[j]` sits in the same range until some merge puts i in the left half and j in the right half. In that merge, j is placed before i (it's smaller), so it's included in `right - mid` when i is placed. Smaller merges never see the pair split, and larger merges see both on the same side.

Part VIII's Fenwick trees give another O(n log n) solution: scan from the right, and for each value ask how many smaller values have been seen so far.

</Approach>
