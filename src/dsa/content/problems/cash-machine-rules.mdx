A cash machine checks every withdrawal against four rules, **in this order**, and reports the first rule that fails. If all four pass, it pays out.

| Order | The rule | Message when it fails |
| --- | --- | --- |
| 1 | `amount` is more than 0 | `"Enter an amount above zero"` |
| 2 | `amount` is a multiple of 10 (the machine only holds notes of 10) | `"Amounts must be in tens"` |
| 3 | `amount` is at most `dailyLimit` | `"Over the daily limit"` |
| 4 | `amount` is at most `balance` | `"Not enough money"` |

When every rule passes, return `"Paid out <amount>. Balance: <balance − amount>"`.

`CashMachineRules.withdraw(amount: Int, balance: Int, dailyLimit: Int) -> String`

## Examples

| `amount` | `balance` | `dailyLimit` | Output | Why |
| --- | --- | --- | --- | --- |
| `60` | `140` | `100` | `"Paid out 60. Balance: 80"` | every rule passes |
| `-20` | `140` | `100` | `"Enter an amount above zero"` | rule 1 comes first, although -20 is a multiple of 10 |
| `25` | `140` | `100` | `"Amounts must be in tens"` | 25 can't be made from notes of 10 |
| `150` | `140` | `100` | `"Over the daily limit"` | it's more than the balance too, but rule 3 is checked first |
| `100` | `90` | `200` | `"Not enough money"` | within the limit, but the balance is only 90 |
| `100` | `100` | `100` | `"Paid out 100. Balance: 0"` | "at most" allows exactly the limit and the balance |

## Constraints

- `-1,000,000 ≤ amount ≤ 1,000,000`
- `0 ≤ balance ≤ 10⁹`
- `0 ≤ dailyLimit ≤ 1,000,000`
- Messages must match exactly, including capitals and full stops.

<Hints>
<Hint>
Write one `guard` per rule, in the table's order. Each guard states what must be true; its `else` block returns that rule's message.
</Hint>
<Hint>
"A multiple of 10" means dividing by 10 leaves nothing over: `amount % 10 == 0`. "At most" is `<=`.
</Hint>
<Hint>
After the four guards, every rule is known to have passed, so the last line can simply build the success message. The subtraction can go straight inside the interpolation: `\(balance - amount)`.
</Hint>
</Hints>

## Solutions

<Approach title="One guard per rule" time="O(1)" space="O(1)">

Each guard reads as "make sure this is true, otherwise say why not and leave". Because the checks run top to bottom and each one leaves as soon as it fails, the order of the guards is exactly the order of the rules. The happy path sits at the bottom, at the left edge, with nothing nested around it.

```swift
public enum CashMachineRules {
    public static func withdraw(amount: Int, balance: Int, dailyLimit: Int) -> String {
        guard amount > 0 else {
            return "Enter an amount above zero"
        }
        guard amount % 10 == 0 else {
            return "Amounts must be in tens"
        }
        guard amount <= dailyLimit else {
            return "Over the daily limit"
        }
        guard amount <= balance else {
            return "Not enough money"
        }
        return "Paid out \(amount). Balance: \(balance - amount)"
    }
}
```

</Approach>

<Approach title="The same checks with if" time="O(1)" space="O(1)">

Every guard can be turned into an `if` with the condition flipped. It gives the same answers:

```swift
public enum CashMachineRules {
    public static func withdraw(amount: Int, balance: Int, dailyLimit: Int) -> String {
        if amount <= 0 {
            return "Enter an amount above zero"
        }
        if amount % 10 != 0 {
            return "Amounts must be in tens"
        }
        if amount > dailyLimit {
            return "Over the daily limit"
        }
        if amount > balance {
            return "Not enough money"
        }
        return "Paid out \(amount). Balance: \(balance - amount)"
    }
}
```

The difference is in how it reads. A guard states the rule itself, "amount is at most the daily limit", which is how the table phrases it. The `if` version states the rule broken, so each line has to be flipped in your head. Swift also checks that a guard's `else` always leaves, so a forgotten `return` is a compile error rather than a bug.

</Approach>
