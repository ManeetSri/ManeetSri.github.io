A vending machine pays change biggest-coin-first: it keeps handing out the largest coin that still fits. You're designing a new coin system and want to know whether that rule is safe. Given the coin values, return the **smallest amount** for which biggest-coin-first uses more coins than the fewest possible, or `nil` if biggest-coin-first is optimal for every amount.

`GreedyChangeBreaker.smallestFailure(_ coins: [Int]) -> Int?`

## Examples

| `coins` | Output | Why |
| --- | --- | --- |
| `[1, 3, 4]` | `6` | greedy pays 4 + 1 + 1; 3 + 3 is two coins |
| `[1, 2, 5, 10, 20, 50]` | `nil` | euro cents: greedy is always optimal |
| `[1, 3, 6, 12, 24, 30]` | `48` | greedy pays 30 + 12 + 6; 24 + 24 is two coins |
| `[1, 7, 10]` | `14` | greedy pays 10 and four 1s; 7 + 7 is two coins |
| `[4, 1, 3]` | `6` | the coins can come in any order |
| `[1]` | `nil` | |

Every amount below 6 is paid optimally with \{1, 3, 4\}, and every amount below 48 with the old British coins, which is what makes this kind of bug so easy to miss.

## Constraints

- `1 ≤ coins.count ≤ 17`. The values are distinct, between 1 and 100,000, and always include 1, so every amount can be paid.
- The tests include systems whose first failure is close to 200,000, and systems with coins up to 100,000 that never fail.

<Hints>
<Hint>
For one amount you need two numbers: how many coins greedy uses, and the true fewest. The fewest comes from a table filled from small amounts up: `fewest[x]` is one coin plus the smallest `fewest[x − coin]`. Greedy has a table too: `greedy[x]` is one plus `greedy[x − c]`, where c is the biggest coin that fits.
</Hint>
<Hint>
The hard part is knowing when to stop. You can't check every amount forever, so you need a limit past which a first failure can't hide. The lesson's note quoted one.
</Hint>
<Hint>
Kozen and Zaks: if greedy fails at all, it already fails for some amount below the sum of the two largest coins. So fill both tables up to that sum and return the first amount where greedy uses more. If none does, greedy is optimal everywhere: return `nil`.
</Hint>
</Hints>

## Solutions

<Approach title="Check up to a guessed limit" time="O(limit · m)" space="O(limit)">

Compare greedy and the fewest for every amount up to some large number you pick, say a million. It finds the failures in the examples, but a guess isn't a proof: either it's too small for some system and returns `nil` wrongly, or it's much bigger than needed and wastes time.

</Approach>

<Approach title="Two tables up to the Kozen–Zaks bound" time="O((c + d) · m)" space="O(c + d)">

With m coins, the largest two being c and d, every amount below c + d gets a greedy count and a true count, and the first mismatch is the answer. Greedy's table needs no loop over coins: it only ever takes the biggest coin that fits, and a pointer into the sorted coins moves up as the amount grows.

```swift
public enum GreedyChangeBreaker {
    public static func smallestFailure(_ coins: [Int]) -> Int? {
        let sorted = coins.sorted()
        guard sorted.count >= 2 else { return nil }                 // only the 1: always optimal
        let bound = sorted[sorted.count - 1] + sorted[sorted.count - 2]
        var greedy = [0]                                            // greedy[x]: coins biggest-first uses
        var fewest = [0]                                            // fewest[x]: the true minimum
        var largest = 0                                             // index of the biggest coin ≤ amount
        for amount in 1..<bound {
            while largest + 1 < sorted.count && sorted[largest + 1] <= amount { largest += 1 }
            greedy.append(1 + greedy[amount - sorted[largest]])     // take the biggest coin, then greedy again
            var best = Int.max
            for coin in sorted where coin <= amount {
                best = min(best, fewest[amount - coin] + 1)
            }
            fewest.append(best)
            if greedy[amount] > fewest[amount] { return amount }
        }
        return nil
    }
}
```

`fewest[amount - coin]` is never `Int.max`, because the coin 1 makes every amount payable, so `+ 1` can't overflow. The greedy recurrence works because biggest-coin-first has no memory: after its first coin, it pays the rest exactly as it would pay that smaller amount from scratch. The first failure for \{1, 99999, 100000\} is 199,998, just below the bound of 199,999, so the limit really is needed in full.

</Approach>
