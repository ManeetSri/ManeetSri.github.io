A ticket desk keeps a single line of people. Process a list of events in order and return the names of the people served, in the order they were served.

`OnePlaceInLine.servedOrder(_ events: [String]) -> [String]`

- An event that is a **name** means that person joins the back of the line. If they're already waiting, the event is ignored: nobody can hold two places at once.
- The event `"NEXT"` serves the person at the front of the line, who leaves it. If the line is empty, nothing happens.
- Someone who has been served may join again later, at the back.
- People still waiting after the last event aren't in the result.

## Examples

| `events` | Output |
| --- | --- |
| `["Ada", "Ben", "Ada", "NEXT", "Ada", "NEXT", "NEXT", "NEXT"]` | `["Ada", "Ben", "Ada"]` |
| `["Dee", "Dee", "Dee", "NEXT", "NEXT"]` | `["Dee"]` |
| `["NEXT", "Cy"]` | `[]` |
| `[]` | `[]` |

In the first example, Ada's second join is ignored because she's already waiting. After she's served she joins again, behind Ben. The fourth `"NEXT"` finds the line empty.

## Constraints

- `0 ≤ events.count ≤ 100,000`
- Names are non-empty and are never `"NEXT"`.
- Aim for O(1) work per event on average. One test has 50,000 different people joining before anyone is served.

<Hints>
<Hint>
Ask the lesson's three questions about each thing you need. "Who's next?" depends on order, so the line itself is an array. "Is this person already waiting?" is a membership question, so it belongs in a set.
</Hint>
<Hint>
`line.removeFirst()` shifts every remaining person forward, which is O(n) per serve. Instead, leave served people where they are and move a `head` index forward: the front of the line is `line[head]`, and the line is empty when `head == line.count`.
</Hint>
<Hint>
Keep the set in step with the line: insert a name when its person joins, and remove it when they're served, so they can join again later. `waiting.insert(name).inserted` tells you in one step whether they were already there.
</Hint>
</Hints>

## Solutions

<Approach title="Brute force: one array for everything" time="O(n²)" space="O(n)">

Use one array as the line, `contains` to check whether someone's waiting, and `removeFirst()` to serve:

```swift
public static func servedOrder(_ events: [String]) -> [String] {
    var line: [String] = []
    var served: [String] = []
    for event in events {
        if event == "NEXT" {
            if !line.isEmpty {
                served.append(line.removeFirst())
            }
        } else if !line.contains(event) {
            line.append(event)
        }
    }
    return served
}
```

It's correct, but both of its main operations walk the line. With 50,000 people waiting, each new join compares against up to 50,000 names, and each serve shifts up to 50,000 names forward. That's billions of steps in the worst case.

</Approach>

<Approach title="An array, a head index and a set" time="O(n)" space="O(n)">

Give each question to the collection that answers it fastest. The array keeps the order and appends in O(1); the `head` index makes serving O(1); the set answers "already waiting?" in O(1) on average.

```swift
public enum OnePlaceInLine {
    public static func servedOrder(_ events: [String]) -> [String] {
        var line: [String] = []
        var head = 0
        var waiting = Set<String>()
        var served: [String] = []
        for event in events {
            if event == "NEXT" {
                if head < line.count {
                    let person = line[head]
                    head += 1
                    waiting.remove(person)
                    served.append(person)
                }
            } else if waiting.insert(event).inserted {
                line.append(event)
            }
        }
        return served
    }
}
```

The set and the array always describe the same people: everyone in `line[head...]` is in `waiting`, and nobody else is. That's why removing a served person from the set matters. Leave it out and Ada could never join again after being served.

Served people stay in the array's memory, as in the lesson's queue. For one run over a list of events that's fine; the queues you'll build in M27 reclaim that space.

</Approach>
