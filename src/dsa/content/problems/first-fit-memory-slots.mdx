A cluster has a row of servers, each with some free memory. Jobs arrive one at a time, and the scheduler uses the **first-fit** rule: each job goes on the lowest-numbered server that still has at least as much free memory as the job needs, and that server's free memory drops by the job's size. If no server has room, the job is rejected and nothing changes. Return where each job went.

`FirstFitServers.place(_ jobs: [Int], on capacities: [Int]) -> [Int]`

`capacities[i]` is server i's free memory at the start. The result has one entry per job: the index of the server it went on, or `-1` if it was rejected.

## Examples

| `jobs` | `capacities` | Output |
| --- | --- | --- |
| `[5, 3, 6, 2, 9, 4, 1]` | `[4, 10, 3, 8]` | `[1, 0, 3, 1, -1, -1, 0]` |
| `[5, 1]` | `[5]` | `[0, -1]` |
| `[2, 2, 2]` | `[3, 3]` | `[0, 1, -1]` |
| `[1]` | `[]` | `[-1]` |
| `[]` | `[7, 7]` | `[]` |

In the first example, the job of 5 skips server 0 (4 free) and lands on server 1, leaving it 5. The job of 3 fits on server 0. The job of 6 skips servers 0 to 2 (1, 5 and 3 free) and lands on server 3. After the job of 2 goes on server 1, the most any server has free is 3, so the jobs of 9 and 4 are rejected. The job of 1 goes back to server 0, which had exactly 1 left.

## Constraints

- `0 ≤ capacities.count ≤ 200,000`, `0 ≤ jobs.count ≤ 200,000`.
- Every capacity is between 0 and 10⁹, and every job size between 1 and 10⁹.
- The tests place 200,000 jobs on 200,000 servers. Scanning the servers for every job is O(jobs × servers), far too slow.

<Hints>
<Hint>
The question for each job is "where is the first position whose value is at least `size`?", and the values keep changing. Prefix sums and sparse tables can't absorb the changes, and a Fenwick tree can't answer "where?" for a maximum. What can?
</Hint>
<Hint>
A segment tree of **maximums**. If the root's maximum is below the job's size, reject it. Otherwise walk down from the root: go left whenever the left child's maximum is at least the size (a fitting server on the left comes first), right otherwise. You reach the first fitting leaf in O(log n), with no binary search around it.
</Hint>
<Hint>
Then subtract the size at that leaf and recompute the maximums on the path back up. An iterative tree with leaves at `size + i` (round the size up to a power of two, and fill unused leaves with -1) keeps both steps to a few lines.
</Hint>
</Hints>

## Solutions

<Approach title="Scan for each job" time="O(jobs × servers)" space="O(servers)">

For each job, loop over the servers from 0 and take the first with enough room. Clear and correct, and the tests use it on small inputs, but it's 4 × 10¹⁰ steps on the largest one.

</Approach>

<Approach title="Walk down a maximum segment tree" time="O((servers + jobs) log servers)" space="O(servers)">

```swift
public enum FirstFitServers {
    public static func place(_ jobs: [Int], on capacities: [Int]) -> [Int] {
        var size = 1
        while size < capacities.count { size *= 2 }
        var tree = Array(repeating: -1, count: 2 * size)    // unused leaves can't fit anything
        for (i, free) in capacities.enumerated() { tree[size + i] = free }
        for node in stride(from: size - 1, through: 1, by: -1) {
            tree[node] = max(tree[2 * node], tree[2 * node + 1])
        }

        var placements: [Int] = []
        placements.reserveCapacity(jobs.count)
        for job in jobs {
            guard !capacities.isEmpty, tree[1] >= job else {
                placements.append(-1)
                continue
            }
            var node = 1
            while node < size {                     // the first fitting leaf is on the left if one fits there
                node = tree[2 * node] >= job ? 2 * node : 2 * node + 1
            }
            placements.append(node - size)
            tree[node] -= job
            node /= 2
            while node >= 1 {
                tree[node] = max(tree[2 * node], tree[2 * node + 1])
                node /= 2
            }
        }
        return placements
    }
}
```

The walk takes one root-to-leaf path because each node's maximum tells you whether a fitting server exists anywhere in its block, and the left block's servers all come before the right block's. This "where is the first…" walk is something only a segment tree among the range structures can do while the values change.

</Approach>
