A relay race runs past checkpoints `0` to `n - 1`. The baton starts at checkpoint 0 and has to finish at the last one. It travels in legs, and every leg moves it forward by **at least** `shortest` and **at most** `longest` checkpoints. A handover fee `fees[i]` is paid at checkpoint 0 and at every checkpoint where a leg ends. Return the smallest total fee, or `-1` if no sequence of legs ends exactly at the last checkpoint.

`BatonRelayCost.cheapestRelay(fees: [Int], shortest: Int, longest: Int) -> Int`

## Examples

| `fees` | `shortest` | `longest` | Output |
| --- | --- | --- | --- |
| `[2, 7, 3, 9, 1, 8, 8, 4, 6, 2]` | `2` | `3` | `12` |
| `[3, 100, 100, 1]` | `1` | `4` | `4` |
| `[5, 0, 0, 1]` | `2` | `2` | `-1` |
| `[4, 1, 1, 1, 1]` | `1` | `1` | `8` |
| `[5]` | `1` | `1` | `5` |

In the first example, the legs 0 → 2 → 4 → 7 → 9 cost 2 + 3 + 1 + 4 + 2 = 12. In the third, legs of exactly 2 from checkpoint 0 land on 2 and then 4, skipping the last checkpoint, 3. In the last, the baton starts at the finish, so only checkpoint 0's fee is paid.

## Constraints

- `1 ≤ n ≤ 200,000`, where `n = fees.count`
- `1 ≤ shortest ≤ longest ≤ n`
- `0 ≤ fees[i] ≤ 1,000,000,000`
- The tests use 200,000 checkpoints with windows up to 100,000 wide, so scanning the whole window for every checkpoint, O(n · longest), is too slow.

<Hints>
<Hint>
Let `cost[i]` be the cheapest way to get the baton to checkpoint i with a leg ending there. Which earlier checkpoints can the last leg have started from?
</Hint>
<Hint>
`cost[i] = fees[i] + min(cost[j])` over `i - longest ≤ j ≤ i - shortest`. As i moves right by one, that window of j's moves right by one too: a monotonic queue keeps its minimum.
</Hint>
<Hint>
At step i the candidate that **joins** is `i - shortest` (not `i - 1`), and only if it's reachable. Before pushing it, pop every back entry whose cost is no smaller. Then pop the front while it's below `i - longest`. If the queue is empty, checkpoint i can't be reached.
</Hint>
</Hints>

## Solutions

<Approach title="Scan the window" time="O(n · longest)" space="O(n)">

For every checkpoint, try every possible starting checkpoint for the last leg. It's the DP written out directly, and the tests compare against it on small routes.

</Approach>

<Approach title="A monotonic queue over the window" time="O(n)" space="O(n)">

The queue holds indexes whose costs increase from front to back, stored in an array with `head` and `tail` indexes so both ends are O(1). Unreachable checkpoints never join, so they can never be chosen.

```swift
public enum BatonRelayCost {
    public static func cheapestRelay(fees: [Int], shortest: Int, longest: Int) -> Int {
        let n = fees.count
        let unreachable = -1
        var cost = [Int](repeating: unreachable, count: n)
        cost[0] = fees[0]
        var queue = [Int](repeating: 0, count: n)       // a deque as an array with two ends
        var head = 0, tail = 0                          // queue[head..<tail] is live
        for i in 1..<max(n, 1) {
            let joining = i - shortest
            if joining >= 0 && cost[joining] != unreachable {
                while tail > head && cost[queue[tail - 1]] >= cost[joining] {
                    tail -= 1                           // never the cheapest again
                }
                queue[tail] = joining
                tail += 1
            }
            while tail > head && queue[head] < i - longest {
                head += 1                               // too far back to reach i
            }
            if tail > head {
                cost[i] = fees[i] + cost[queue[head]]
            }
        }
        return cost[n - 1]
    }
}
```

Each index joins at most once and leaves at most once, so the work is O(n) however wide the window. The largest possible total is 200,000 fees of 10⁹, 2 × 10¹⁴, well inside an `Int`.

</Approach>

<Approach title="A heap with lazy removal" time="O(n log n)" space="O(n)">

A min-heap of `(cost, index)` also works: push each candidate when it joins, and when you look at the top, pop it first if its index is too far back. It's slower than the queue but needs less care, and the tests use it to check the big cases.

</Approach>
