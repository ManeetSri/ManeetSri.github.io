A shop's reporting screen shows, for each price band a manager picks, the total of all sales whose price falls in that band. The first version is correct but far too slow once there are a few hundred thousand sales and bands. Write a fast one.

`PriceBandTotals.totals(prices: [Int], bands: [(low: Int, high: Int)]) -> [Int]`

Return one total per band, in the order of the bands: the sum of every price `p` with `low ≤ p ≤ high`. A band whose `low` is above its `high` is empty, so its total is 0. This is the version in production:

```swift
func totalsSlow(prices: [Int], bands: [(low: Int, high: Int)]) -> [Int] {
    bands.map { band in
        prices.filter { band.low <= $0 && $0 <= band.high }.reduce(0, +)
    }
}
```

## Examples

With `prices = [12, 5, 40, 5, 18, 27, 9]`:

| Band | Total | Why |
| --- | --- | --- |
| `(5, 12)` | `31` | 5 + 5 + 9 + 12: both ends count, and so do both 5s |
| `(13, 26)` | `18` | |
| `(18, 40)` | `85` | 18 + 27 + 40 |
| `(0, 100)` | `116` | every price |
| `(41, 50)` | `0` | no price in the band |
| `(12, 12)` | `12` | a band of one value |
| `(30, 20)` | `0` | low is above high |

## Constraints

- `0 ≤ prices.count ≤ 200,000` and `0 ≤ bands.count ≤ 200,000`.
- `-10⁹ ≤ prices[i] ≤ 10⁹`: refunds are negative prices. Band ends can be any `Int`.
- The slow version makes `prices.count × bands.count` comparisons, which is 4 × 10¹⁰ at the limits. Yours must be around O((n + q) log n).

<Hints>
<Hint>
Name the repeated work. For every band, the slow version looks at every price, though most of them are nowhere near the band. If the prices were sorted, where would one band's prices be?
</Hint>
<Hint>
After sorting, a band's prices are one contiguous run. Two binary searches find it: the first index whose price is `≥ low`, and the first index whose price is `> high`.
</Hint>
<Hint>
Adding up the run would still be O(n) per band. Prefix sums over the sorted prices give any run's total as a difference of two entries.
</Hint>
</Hints>

## Solutions

<Approach title="Sort once, binary search and prefix sums per band" time="O((n + q) log n)" space="O(n)">

The bottleneck is a search ("which prices are in the band?") that rescans everything. Sorting makes each band's prices contiguous, binary search finds the ends of the run in O(log n), and prefix sums answer "what's the total of this run?" in O(1). That's three patterns, each removing one piece of the slow version's work.

```swift
public enum PriceBandTotals {
    public static func totals(prices: [Int], bands: [(low: Int, high: Int)]) -> [Int] {
        let sorted = prices.sorted()
        var prefix = [0]                         // prefix[i] = sum of the i smallest prices
        prefix.reserveCapacity(sorted.count + 1)
        for price in sorted {
            prefix.append(prefix[prefix.count - 1] + price)
        }
        return bands.map { band in
            guard band.low <= band.high else { return 0 }
            let first = firstIndex(in: sorted) { $0 >= band.low }
            let end = firstIndex(in: sorted) { $0 > band.high }
            return prefix[end] - prefix[first]
        }
    }

    /// The first index whose value satisfies `isAtOrPast`, or `values.count`. The predicate must be
    /// false and then true along the sorted array.
    private static func firstIndex(in values: [Int], where isAtOrPast: (Int) -> Bool) -> Int {
        var low = 0
        var high = values.count
        while low < high {
            let mid = low + (high - low) / 2
            if isAtOrPast(values[mid]) {
                high = mid
            } else {
                low = mid + 1
            }
        }
        return low
    }
}
```

The best conceivable runtime is O(n + q), since every price and every band must be read. Sorting costs O(n log n), so this is close; if all the bands were known in advance and sorted too, a single sweep could answer them, but that only trades one log factor for another sort. The `guard` matters: with `low > high`, the second binary search can stop before the first, and the difference would then count the prices between them with the wrong sign. The totals fit in an `Int`: at most 200,000 × 10⁹ = 2 × 10¹⁴.

</Approach>
