A build system has `modules` modules, numbered from 0. A pair `[a, b]` in `dependencies` means module a depends on module b, so b must be built first. A **circular dependency** makes the build impossible, and the error message should show it.

Find one: return distinct modules `[m0, m1, …, mk]` where each depends on the next and the last depends on `m0`. Return `[]` if there's no circular dependency. Any cycle is accepted, starting from any of its modules.

`DependencyCycleFinder.cycle(_ modules: Int, dependencies: [[Int]]) -> [Int]`

## Examples

| `modules` | `dependencies` | Returns |
| --- | --- | --- |
| `3` | `[[0, 1], [1, 2], [2, 0]]` | `[0, 1, 2]`, `[1, 2, 0]` or `[2, 0, 1]` |
| `5` | `[[0, 1], [1, 2], [2, 3], [3, 1], [3, 4]]` | `[1, 2, 3]` (starting anywhere in it) |
| `2` | `[[0, 1], [1, 1]]` | `[1]` |
| `4` | `[[0, 1], [0, 2], [1, 3], [2, 3]]` | `[]` |
| `3` | `[]` | `[]` |

In the second example, module 0 isn't part of the loop: it depends on the loop, which is different. In the third, module 1 depends on itself. The fourth is a diamond: module 3 is reached twice, through 1 and through 2, but nothing leads back from 3, so there's no cycle.

## Constraints

- `1 ≤ modules ≤ 100,000`, with up to 300,000 dependencies. A pair may appear more than once.
- The tests include a chain of 100,000 modules closed into one big loop. A recursive DFS would go 100,000 calls deep and crash the test thread: use an explicit stack.

<Hints>
<Hint>
A plain "visited" check isn't enough in a directed graph. In the diamond, DFS reaches module 3 a second time, but that's not a cycle. What matters is whether you reach a module that's still **on the current path**.
</Hint>
<Hint>
Use three colours: white (not visited), grey (entered but not finished, so it's on the current path) and black (finished, with everything it depends on explored). An edge to a grey module closes a loop. An edge to a black one is harmless.
</Hint>
<Hint>
Without recursion, keep a stack of frames `(module, next)`, where `next` is the index of the next dependency to try. A module turns black when its `next` runs off the end. The frames on the stack are exactly the grey modules in path order, so the cycle is the slice from the grey module to the top.
</Hint>
</Hints>

## Solutions

<Approach title="Three-colour DFS with an explicit stack" time="O(modules + dependencies)" space="O(modules + dependencies)">

Each frame remembers how far through its module's dependencies it has got, which is exactly what a recursive call would remember in its local variables. That's what lets a module be marked black only after **all** its dependencies are done.

```swift
public enum DependencyCycleFinder {
    public static func cycle(_ modules: Int, dependencies: [[Int]]) -> [Int] {
        var needs = Array(repeating: [Int](), count: modules)
        for pair in dependencies {
            needs[pair[0]].append(pair[1])
        }

        var colour = Array(repeating: 0, count: modules)    // 0 white, 1 grey, 2 black
        var stack: [(module: Int, next: Int)] = []
        for root in 0..<modules where colour[root] == 0 {
            colour[root] = 1
            stack.append((root, 0))
            while let top = stack.last {
                if top.next == needs[top.module].count {
                    colour[top.module] = 2               // every dependency is done
                    stack.removeLast()
                    continue
                }
                stack[stack.count - 1].next += 1
                let dependency = needs[top.module][top.next]
                if colour[dependency] == 0 {
                    colour[dependency] = 1
                    stack.append((dependency, 0))
                } else if colour[dependency] == 1 {
                    // Back to a module on the current path: the path from it to here is a loop
                    let start = stack.firstIndex { $0.module == dependency }!
                    return stack[start...].map(\.module)
                }
            }
        }
        return []
    }
}
```

`firstIndex` is a linear search of the stack, but it runs once, just before returning, so it doesn't change the total.

</Approach>

<Approach title="Kahn's algorithm, then walk the leftovers" time="O(modules + dependencies)" space="O(modules + dependencies)">

[Kahn's algorithm](/dsa/learn/topo-kahn) repeatedly removes modules with no unbuilt dependencies. If some are never removed, there's a cycle among them, and every leftover module still depends on another leftover. Start at any leftover, keep following a leftover dependency, and you must eventually revisit a module: the stretch between its two visits is a cycle. It's a good alternative if you've already written Kahn's algorithm for the build order.

</Approach>
