You're given some non-negative whole numbers. Arrange them so that writing them one after another, with no separators, makes the biggest possible number, and return that number as a string.

`LargestConcatenation.largest(from numbers: [Int]) -> String`

The result can be far too long for any integer type, which is why it's a string. It must not start with a zero unless it **is** zero: `[0, 0]` gives `"0"`, not `"00"`.

## Examples

| `numbers` | Returns |
| --- | --- |
| `[5, 56, 50]` | `"56550"` |
| `[12, 121]` | `"12121"` |
| `[20, 2, 202]` | `"220220"` |
| `[10, 1]` | `"110"` |
| `[0, 7, 70]` | `"7700"` |
| `[0, 0, 0]` | `"0"` |

In the first example, 56 goes before 5 because 565 beats 556, and 5 goes before 50 because 550 beats 505. Sorting the numbers by value, or as plain strings, gets examples like these wrong.

## Constraints

- `1 ≤ numbers.count ≤ 10,000`
- `0 ≤ numbers[i] ≤ 1,000,000,000`

<Hints>
<Hint>
Sorting the digit strings in decreasing alphabetical order nearly works: it puts 9 before 5 before 1. Where does it fail? Try 12 and 121, or 5 and 50.
</Hint>
<Hint>
To decide which of two pieces a and b goes first, try both: compare a + b with b + a. They're the same length, so comparing them as strings compares them as numbers.
</Hint>
<Hint>
Sort with that rule, `sorted { $0 + $1 > $1 + $0 }`, and join. It's a strict weak ordering (it's false when the two joins are equal), so `sorted(by:)` handles it correctly. Finally, if the first piece is `"0"`, every piece is 0: return `"0"`.
</Hint>
</Hints>

## Solutions

<Approach title="Sort with a 'which join is bigger?' rule" time="O(n log n · d)" space="O(n · d)">

Here d is the number of digits in a piece, at most 10, so each comparison costs a few dozen character steps. The surprising part is that comparing two pieces at a time is enough: the rule is transitive (if a goes before b and b before c, then a goes before c), which is exactly what a sort needs. Proving it takes a little algebra, but you can check it on examples, and the tests try every possible order of some small lists.

```swift
public enum LargestConcatenation {
    public static func largest(from numbers: [Int]) -> String {
        let pieces = numbers.map(String.init).sorted { a, b in
            a + b > b + a                                // same length, so this compares digits as numbers
        }
        if pieces.first == "0" {
            return "0"                                   // every piece is 0
        }
        return pieces.joined()
    }
}
```

`a + b > b + a` is strict, so it's safe for `sorted(by:)`. Writing `>=` would break the rule that a sort's comparison must be false for equal elements, as [How Swift sorts, and sorting custom types](/dsa/learn/sort-swift-sort) explains.

</Approach>
