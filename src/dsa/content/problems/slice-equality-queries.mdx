A document-diff tool keeps asking the same question: do these two pieces of the text say exactly the same thing? Each query `[a, b, length]` asks whether `text[a..<a + length]` and `text[b..<b + length]` spell the same letters. Answer every query.

`SliceEqualityQueries.answer(text: String, queries: [[Int]]) -> [Bool]`

## Examples

For `text = "abracadabra"`:

| Query | Slices | Output |
| --- | --- | --- |
| `[0, 7, 4]` | `abra` and `abra` | `true` |
| `[0, 3, 1]` | `a` and `a` | `true` |
| `[1, 8, 3]` | `bra` and `bra` | `true` |
| `[0, 1, 4]` | `abra` and `brac` | `false` |
| `[2, 2, 5]` | the same slice twice | `true` |
| `[4, 9, 0]` | two empty slices | `true` |

So `answer(text: "abracadabra", queries: [[0, 7, 4], [0, 3, 1], [1, 8, 3], [0, 1, 4], [2, 2, 5], [4, 9, 0]])` returns `[true, true, true, false, true, true]`.

## Constraints

- `text` holds 0 to 100,000 lowercase letters, a to z.
- `0 ≤ queries.count ≤ 100,000`
- For every query, `length ≥ 0`, `a + length ≤ text.count` and `b + length ≤ text.count`.
- The tests ask 100,000 queries about slices of 40,000 to 60,000 letters. Comparing letter by letter is billions of steps.
- The tests include strings built to defeat a hash computed with wrapping `UInt64` arithmetic (`&*` and `&+`, which is arithmetic mod 2⁶⁴), whatever the base. Use a prime modulus.

<Hints>
<Hint>
You need to compare two slices in O(1), after some preparation. Comparing numbers is O(1): can each slice be given a number, a fingerprint, so that equal slices get equal numbers?
</Hint>
<Hint>
Store the polynomial hash of every prefix, and every power of the base. The hash of `text[a..<b]` is `prefix[b] − prefix[a] · power[b − a]`, modulo M: the prefix up to a, shifted up to line up, is subtracted away.
</Hint>
<Hint>
Use the prime M = 2⁶¹ − 1, multiply with `multipliedFullWidth(by:)` and fold the 128-bit product back below M, and choose the base at random when the function runs. Watch the subtraction: in `UInt64` it traps if it would go below zero, so add M first.
</Hint>
</Hints>

## Solutions

<Approach title="Compare letter by letter" time="O(q · L)" space="O(n)">

`elementsEqual` on two slices of a byte array. Always right, and fine for short slices, but 100,000 queries about 50,000-letter slices that are equal cost 5 billion comparisons, because equal slices have to be read all the way through.

</Approach>

<Approach title="Prefix hashes modulo 2⁶¹ − 1" time="O(n + q)" space="O(n)">

Prepare prefix hashes and powers once, then answer each query with two O(1) slice hashes.

```swift
public enum SliceEqualityQueries {
    public static func answer(text: String, queries: [[Int]]) -> [Bool] {
        let s = Array(text.utf8)
        let modulus: UInt64 = (1 << 61) - 1
        func mulMod(_ x: UInt64, _ y: UInt64) -> UInt64 {
            let (high, low) = x.multipliedFullWidth(by: y)
            let sum = ((high << 3) | (low >> 61)) + (low & modulus)
            return sum >= modulus ? sum - modulus : sum
        }

        let base = UInt64.random(in: 256..<modulus)
        var prefix = [UInt64](repeating: 0, count: s.count + 1)
        var power = [UInt64](repeating: 1, count: s.count + 1)
        for i in s.indices {
            let value = mulMod(prefix[i], base) + UInt64(s[i])
            prefix[i + 1] = value >= modulus ? value - modulus : value
            power[i + 1] = mulMod(power[i], base)
        }
        func hash(_ from: Int, _ length: Int) -> UInt64 {
            let shifted = mulMod(prefix[from], power[length])
            let end = prefix[from + length]
            return end >= shifted ? end - shifted : end + modulus - shifted
        }

        return queries.map { query in
            hash(query[0], query[2]) == hash(query[1], query[2])
        }
    }
}
```

Different hashes prove the slices differ. Equal hashes could in principle be a collision, but with a random base the chance for one query is at most L / M, about 1 in 23 trillion for 100,000-letter slices, so across all the queries a wrong answer is still far less likely than a hardware fault.

</Approach>

<Approach title="Why not let UInt64 wrap around?" time="O(n + q)" space="O(n)">

`h = h &* base &+ c` never overflows and needs no `%`, so it's tempting. But it's a hash modulo 2⁶⁴, which isn't prime. A Thue–Morse string of length 2048 and the same string with `a` and `b` swapped get equal hashes for **every** odd base, as [Rabin–Karp and rolling hashes](/dsa/learn/sa-rabin-karp) showed, and with an even base the first letters of a long slice stop mattering at all. The tests contain both traps. Two hashes with different 30-bit primes, kept as a pair, are a fine alternative to 2⁶¹ − 1 if you'd rather stay in plain `Int` arithmetic.

</Approach>
