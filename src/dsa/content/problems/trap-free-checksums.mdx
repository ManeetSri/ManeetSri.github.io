A log-ingestion service must never crash on strange input, in debug or release. In both builds Swift stops the program when `+`, `-` or `*` overflows, so every piece of arithmetic that might overflow must say what it wants instead: wrap around on purpose, or detect the overflow and report it. Write five small helpers that never trap, whatever `Int` values they get.

`TrapFreeChecksums.fnv1a(_:) -> UInt64`, `TrapFreeChecksums.wrappingSum(_:) -> Int`, `TrapFreeChecksums.checkedSum(_:) -> Int?`, `TrapFreeChecksums.checkedProduct(_:) -> Int?` and `TrapFreeChecksums.midpoint(_:_:) -> Int`

- `fnv1a(text)`: the 64-bit FNV-1a hash of the text's UTF-8 bytes. Start from 14,695,981,039,346,656,037; for each byte, XOR it into the hash, then multiply by 1,099,511,628,211, letting the multiplication wrap around.
- `wrappingSum(values)`: the sum with wrap-around, as two's complement `Int` arithmetic does it, like a checksum.
- `checkedSum(values)`: the sum, adding from left to right, or `nil` if any running total overflows. The empty sum is 0.
- `checkedProduct(values)`: the product, multiplying from left to right, or `nil` if any running product overflows. The empty product is 1.
- `midpoint(a, b)`: the average of a and b rounded down (towards negative infinity), for **any** two `Int`s, even when `a + b` itself would overflow.

## Examples

| Call | Output |
| --- | --- |
| `fnv1a("swift")` | `11823696842872234712` |
| `fnv1a("")` | `14695981039346656037` |
| `wrappingSum([Int.max, 1])` | `Int.min` (−9,223,372,036,854,775,808) |
| `checkedSum([Int.max, 1])` | `nil` |
| `checkedSum([Int.max, -1, 1])` | `9223372036854775807` |
| `checkedSum([Int.max, 1, -1])` | `nil` |
| `checkedProduct([3, -4, 5])` | `-60` |
| `checkedProduct([1 << 32, 1 << 31])` | `nil` |
| `midpoint(3, 8)` | `5` |
| `midpoint(-3, -8)` | `-6` |
| `midpoint(Int.max, Int.max - 2)` | `9223372036854775806` |
| `midpoint(Int.min, Int.max)` | `-1` |

`checkedSum([Int.max, 1, -1])` is `nil` even though the final answer would fit: the running total overflows after the second value. Adding in the other order, `[Int.max, -1, 1]`, never leaves the range. The midpoint of `Int.min` and `Int.max` is −0.5, rounded down to −1.

## Constraints

- Up to 1,000,000 values per call, and any `Int` values at all, including `Int.min` and `Int.max`. The text is any string.
- Nothing may trap. A version with a plain `+` or `*` crashes the whole test run on the first overflowing case, so read the hints before running the tests.
- Don't convert to `Double`: it can't hold every `Int` exactly.

<Hints>
<Hint>
Swift's wrapping operators `&+`, `&-` and `&*` wrap around in every build, on purpose. They're the right tool for hashes and checksums, where overflow is part of the design. For FNV-1a, `UInt64(byte)` and `^` do the XOR, and `&*` the multiplication.
</Hint>
<Hint>
To detect overflow instead, every integer type has `addingReportingOverflow(_:)` and `multipliedReportingOverflow(by:)`. Each returns the wrapped result and a `Bool`, `overflow`, saying whether it wrapped. Return `nil` as soon as one reports an overflow.
</Hint>
<Hint>
For the midpoint, the bits a and b share count fully, and the bits where they differ count half: `(a & b) + ((a ^ b) >> 1)`. `>>` on a signed `Int` is an arithmetic shift, which rounds down, and neither part can overflow.
</Hint>
</Hints>

## Solutions

<Approach title="Wrapping and reporting operators" time="O(n)" space="O(1)">

```swift
public enum TrapFreeChecksums {
    public static func fnv1a(_ text: String) -> UInt64 {
        var hash: UInt64 = 14_695_981_039_346_656_037
        for byte in text.utf8 {
            hash = (hash ^ UInt64(byte)) &* 1_099_511_628_211
        }
        return hash
    }

    public static func wrappingSum(_ values: [Int]) -> Int {
        values.reduce(0, &+)
    }

    public static func checkedSum(_ values: [Int]) -> Int? {
        var total = 0
        for value in values {
            let (sum, overflow) = total.addingReportingOverflow(value)
            if overflow { return nil }
            total = sum
        }
        return total
    }

    public static func checkedProduct(_ values: [Int]) -> Int? {
        var product = 1
        for value in values {
            let (next, overflow) = product.multipliedReportingOverflow(by: value)
            if overflow { return nil }
            product = next
        }
        return product
    }

    public static func midpoint(_ a: Int, _ b: Int) -> Int {
        (a & b) + ((a ^ b) >> 1)
    }
}
```

Every operation here behaves the same in `-Onone`, `-O` and even `-Ounchecked`, because none of them relies on a trap. That's the lesson's rule in practice: if wrapping is what you mean, say so with `&+`; if overflow is an error, detect it and handle it, rather than letting a trap (or, in an unchecked build, undefined behaviour) decide.

</Approach>

<Approach title="Widen first" time="O(n)" space="O(1)">

On macOS 15 and later, Swift 6 has a 128-bit `Int128`, and a sum of two `Int`s always fits in it, so `midpoint` could widen, add and divide. The companion package targets macOS 14, where `Int128` isn't available, and widening doesn't help with a running sum of a million values or with products anyway. The reporting operators work everywhere.

</Approach>
