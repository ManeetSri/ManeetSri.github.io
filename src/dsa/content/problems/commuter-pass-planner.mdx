You know in advance which days you'll take the train: `travelDays`, in increasing order. The railway sells passes, each `[length, price]`: a pass bought for day `d` lets you travel on every day from `d` to `d + length - 1`. You can buy any pass as many times as you like. Return the lowest total price that covers all your travel days.

`CommuterPassPlanner.cheapestCost(travelDays: [Int], passes: [[Int]]) -> Int`

## Examples

| `travelDays` | `passes` | Output |
| --- | --- | --- |
| `[1, 2, 3, 4, 5, 9, 20, 21]` | `[[1, 4], [7, 15], [30, 40]]` | `27` |
| `[3, 4, 8, 9, 10, 11, 12, 30]` | `[[1, 4], [7, 15], [30, 40]]` | `27` |
| `[5]` | `[[1, 4], [7, 15]]` | `4` |
| `[1, 2, 6, 7, 8, 12]` | `[[1, 2], [3, 5], [7, 9]]` | `11` |

In the first example, a 7-day pass from day 1 covers travel days 1 to 5 for 15, and day passes for days 9, 20 and 21 cost 12 more. In the second, day passes for days 3 and 4 (8), a 7-day pass from day 8 (15) and a day pass for day 30 (4) total 27. A 7-day pass from day 3 looks good, since it covers four travel days, but it leads to 31. In the last, day passes for days 1, 2 and 12 plus a 3-day pass from day 6 cost 2 + 2 + 2 + 5 = 11.

## Constraints

- `0 ≤ travelDays.count ≤ 100,000`, strictly increasing, with `1 ≤ travelDays[i] ≤ 1,000,000,000`
- `1 ≤ passes.count ≤ 10`, with `1 ≤ length ≤ 1,000,000,000` and `1 ≤ price ≤ 1,000,000`
- Days can be far apart, so an array indexed by day number won't fit. The tests use 100,000 travel days.

<Hints>
<Hint>
Try a simple rule first, such as "buy the longest pass whenever it covers enough travel days". The second example breaks rules like that. When local rules keep failing, think about trying every choice, and remembering the results.
</Hint>
<Hint>
Look at the earliest travel day that isn't covered yet. Some pass must cover it, and there's no point buying that pass before that day. So the only choice is *which* pass to buy on that day, and after it the plan continues from the first travel day the pass doesn't reach.
</Hint>
<Hint>
Let `cost[i]` be the cheapest way to cover travel days `i` onwards, with `cost[n] = 0`. Then `cost[i]` is the minimum, over the passes, of the price plus `cost[j]`, where `j` is the first index whose day is at least `travelDays[i] + length`. Fill it from `i = n - 1` down to 0. Find each `j` with a binary search, or with one pointer per pass that only ever moves left.
</Hint>
</Hints>

## Solutions

<Approach title="Try every plan" time="O(pⁿ)" space="O(n)">

At the earliest uncovered day, try each pass, skip the days it covers and recurse. It's correct and makes a good test reference, but the same suffix of days is solved again and again: exponential time.

</Approach>

<Approach title="DP over the travel days" time="O(n · p)" space="O(n + p)">

Run the recipe from [The DP recipe](/dsa/learn/dp-recipe). **State:** `cost[i]`, the cheapest cover for days `i` onwards. **Transition:** the minimum over the passes of the price plus the cost from the first day that pass doesn't reach. **Base:** `cost[n] = 0`. **Order:** `i` from `n - 1` down to 0. **Answer:** `cost[0]`.

```swift
public enum CommuterPassPlanner {
    public static func cheapestCost(travelDays: [Int], passes: [[Int]]) -> Int {
        let n = travelDays.count
        var cost = Array(repeating: 0, count: n + 1)
        var after = Array(repeating: n, count: passes.count)   // first day index each pass doesn't cover
        for i in stride(from: n - 1, through: 0, by: -1) {
            var best = Int.max
            for (p, pass) in passes.enumerated() {
                let firstUncovered = travelDays[i] + pass[0]
                while after[p] > i + 1, travelDays[after[p] - 1] >= firstUncovered {
                    after[p] -= 1
                }
                best = min(best, pass[1] + cost[after[p]])
            }
            cost[i] = best
        }
        return cost[0]
    }
}
```

As `i` moves left, `travelDays[i] + length` gets smaller, so each pass's `after` index only moves left too. Over the whole loop each pointer moves at most `n` times: O(n · p) in total. A binary search per pass, O(n · p · log n), is fine too.

The state is indexed by *travel day*, not calendar day. With days up to 10⁹ apart, a table with one cell per calendar day would need gigabytes, while the travel days number at most 100,000. Choosing a state that's as small as the real information is a recurring DP skill, as in [Bottom-up tabulation](/dsa/learn/dp-tabulation).

</Approach>
