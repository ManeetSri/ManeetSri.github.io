A heart-rate monitor smooths its readings by reporting the **median of the last `k` readings**: the middle value of the window once sorted, or the mean of the two middle values when `k` is even. Unlike an average, one glitchy reading can't drag it far. Given all the readings and `k`, return the median of every window of `k` consecutive readings, from left to right.

`RollingWindowMedian.medians(_ readings: [Int], window k: Int) -> [Double]`

There are `readings.count - k + 1` windows.

## Examples

| `readings` | `k` | Output |
| --- | --- | --- |
| `[5, 2, 8, 1, 9, 3]` | `3` | `[5.0, 2.0, 8.0, 3.0]` |
| `[5, 2, 8, 1, 9, 3]` | `2` | `[3.5, 5.0, 4.5, 5.0, 6.0]` |
| `[4, 4, 4, 4]` | `4` | `[4.0]` |
| `[7, -3, 7]` | `1` | `[7.0, -3.0, 7.0]` |
| `[2147483647, 2147483647]` | `2` | `[2147483647.0]` |

In the first example, the windows are [5, 2, 8], [2, 8, 1], [8, 1, 9] and [1, 9, 3], with medians 5, 2, 8 and 3.

## Constraints

- `1 ≤ k ≤ readings.count ≤ 100,000`
- `-1,000,000,000 ≤ readings[i] ≤ 1,000,000,000`
- Aim for O(n log k). The tests use 60,000 readings with windows of 30,000, so sorting each window is far too slow.

<Hints>
<Hint>
Two heaps keep a running median: the lower half in a max-heap and the upper half in a min-heap, with the lower half holding the same number of values or one more. The problem is removing the reading that leaves the window: it could be buried anywhere in either heap.
</Hint>
<Hint>
Don't remove it. Store `(value, index)` pairs instead of bare values: an entry is **stale** once its index has left the window. Pop entries off a heap's top only when the top is stale. Stale entries deeper down do no harm until they surface. Pairs also make every entry distinct, which keeps duplicates from causing trouble.
</Hint>
<Hint>
Because stale entries still sit in the heaps, their `count`s are wrong. Track the number of **live** entries in each half yourself. When a reading leaves, compare its pair with the lower half's top to know which half holds it (every pair in the lower half is ≤ that top, every pair in the upper half is greater), and decrement that half's live size. Rebalance by live sizes, cleaning a top before moving it across, and clean both tops before reading the median.
</Hint>
</Hints>

## Solutions

<Approach title="Sort each window" time="O(n · k log k)" space="O(k)">

Copy each window, sort it and read the middle. With 30,000 windows of 30,000 readings, that's billions of comparisons.

</Approach>

<Approach title="A sorted window" time="O(n · k)" space="O(k)">

Keep the window in a sorted array: binary search to find where the new reading goes and where the old one is, then `insert` and `remove(at:)`. The searches are O(log k), but each insert and remove shifts up to k elements. Fast memory moves make this respectable for moderate k, but it's still O(k) per step.

</Approach>

<Approach title="Two heaps with lazy deletion" time="O(n log n)" space="O(n)">

```swift
import DSAKit

public enum RollingWindowMedian {
    public static func medians(_ readings: [Int], window k: Int) -> [Double] {
        typealias Entry = (value: Int, index: Int)
        var lower = Heap<Entry>(areInIncreasingOrder: { $0 > $1 })   // the smaller half, largest on top
        var upper = Heap<Entry>(areInIncreasingOrder: { $0 < $1 })   // the larger half, smallest on top
        var lowerSize = 0                        // live entries in each half
        var upperSize = 0
        var windowStart = 0                      // entries with a smaller index are stale

        func clean(_ heap: inout Heap<Entry>) {
            while let top = heap.peek(), top.index < windowStart {
                heap.pop()
            }
        }

        var result: [Double] = []
        result.reserveCapacity(readings.count - k + 1)
        for (i, reading) in readings.enumerated() {
            let entry = (reading, i)
            if let top = lower.peek(), entry > top {
                upper.insert(entry)
                upperSize += 1
            } else {
                lower.insert(entry)
                lowerSize += 1
            }
            if i >= k {                          // readings[i - k] leaves the window
                let leaving = (readings[i - k], i - k)
                if let top = lower.peek(), leaving <= top { lowerSize -= 1 } else { upperSize -= 1 }
                windowStart = i - k + 1
            }
            if lowerSize > upperSize + 1 {       // rebalance by live sizes
                clean(&lower)
                upper.insert(lower.pop()!)
                lowerSize -= 1
                upperSize += 1
            } else if upperSize > lowerSize {
                clean(&upper)
                lower.insert(upper.pop()!)
                upperSize -= 1
                lowerSize += 1
            }
            clean(&lower)
            clean(&upper)
            if i >= k - 1 {
                let middle = lower.peek()!.value
                result.append(k % 2 == 1 ? Double(middle) : (Double(middle) + Double(upper.peek()!.value)) / 2)
            }
        }
        return result
    }
}
```

Every pair in `lower` is ≤ every pair in `upper`, stale or not: inserting by comparison with `lower`'s top and moving tops across both keep that true. So comparing the leaving pair with `lower`'s top tells you exactly which heap holds it, even when that top is itself stale. Comparing bare values would be ambiguous when a value appears in both halves.

Each step pushes one entry and moves at most one top across, and every entry pushed is popped at most once, so the whole run is O(n log n). Stale entries can make a heap hold more than k entries for a while; a balanced tree with removal by value would keep exactly k, at O(log k) per step.

</Approach>
