A search box suggests entries from a catalogue as you type. After each letter, it shows up to `limit` catalogue entries that start with everything typed so far, alphabetically smallest first. Return the suggestions shown after each letter of `typed`.

`TypeaheadSuggestions.suggestions(for typed: String, in catalogue: [String], limit: Int) -> [[String]]`

The result holds one list per letter of `typed`. An entry that appears in the catalogue more than once is suggested once. Once the typed text matches nothing, every later list is empty.

## Examples

With `catalogue = ["mango", "maple", "map", "marble", "mat", "melon", "mouse"]`:

| `typed` | `limit` | Output |
| --- | --- | --- |
| `"map"` | `3` | `[["mango", "map", "maple"], ["mango", "map", "maple"], ["map", "maple"]]` |
| `"mo"` | `1` | `[["mango"], ["mouse"]]` |
| `"mapsx"` | `3` | `[["mango", "map", "maple"], ["mango", "map", "maple"], ["map", "maple"], [], []]` |
| `"zz"` | `3` | `[[], []]` |

And with `catalogue = ["bee", "bee", "bear", "bee", "beetle"]`, typing `"bee"` with `limit` 2 gives `[["bear", "bee"], ["bear", "bee"], ["bee", "beetle"]]`.

## Constraints

- `0 ≤ catalogue.count ≤ 50,000`, and each entry holds 1 to 400 lowercase letters, a to z.
- `typed` holds 1 to 300 lowercase letters.
- `1 ≤ limit ≤ 20`
- The tests type 300 letters into a catalogue of 50,000 entries.

<Hints>
<Hint>
Build a trie of the catalogue, storing each entry at the node where it ends. Entries that repeat land on the same node, so they're stored once for free.
</Hint>
<Hint>
Don't walk from the root for every prefix. Keep the node for the text typed so far, and step to its child for each new letter. If the child is missing, every remaining list is empty.
</Hint>
<Hint>
To list suggestions, search depth first from the current node, visiting a node's own entry before its children and the children in alphabetical order. That meets entries alphabetically, so you can stop as soon as you have `limit` of them.
</Hint>
</Hints>

## Solutions

<Approach title="Sort, then binary search each prefix" time="O(L × n log n + typed.count × L × (log n + limit))" space="O(n)">

Sort the distinct entries. All entries starting with a prefix then sit side by side, beginning at the first entry that's not less than the prefix: the lower bound from [Lower bound, upper bound, first and last occurrence](/dsa/learn/bs-bounds). Take up to `limit` entries from there while they still start with the prefix. Here L is the length of the longest entry, since every comparison of two strings can cost that much.

```swift
public enum TypeaheadSuggestions {
    public static func suggestions(for typed: String, in catalogue: [String], limit: Int) -> [[String]] {
        let sorted = Array(Set(catalogue)).sorted()
        var result: [[String]] = []
        var prefix = ""
        for letter in typed {
            prefix.append(letter)
            var low = 0
            var high = sorted.count
            while low < high {                           // the first entry ≥ prefix
                let mid = low + (high - low) / 2
                if sorted[mid] < prefix { low = mid + 1 } else { high = mid }
            }
            var found: [String] = []
            while low < sorted.count && found.count < limit && sorted[low].hasPrefix(prefix) {
                found.append(sorted[low])
                low += 1
            }
            result.append(found)
        }
        return result
    }
}
```

This is a perfectly good answer, and it's short. Its weakness shows when the catalogue changes: keeping a sorted array sorted costs O(n) per insertion, while a trie adds an entry in O(L).

</Approach>

<Approach title="A trie, followed one letter at a time" time="O(total letters + typed.count × limit × L)" space="O(total letters)">

Each node keeps 26 child slots in alphabetical order, so a depth-first search that checks a node's own entry before its children meets entries in sorted order. The current node moves down one letter per keystroke, and each search stops after `limit` entries.

```swift
public enum TypeaheadSuggestions {
    final class Node {
        var children = [Node?](repeating: nil, count: 26)
        var word: String?
    }

    public static func suggestions(for typed: String, in catalogue: [String], limit: Int) -> [[String]] {
        let root = Node()
        for entry in catalogue {
            var node = root
            for byte in entry.utf8 {
                let slot = Int(byte - 97)
                if node.children[slot] == nil {
                    node.children[slot] = Node()
                }
                node = node.children[slot]!
            }
            node.word = entry
        }

        var result: [[String]] = []
        var current: Node? = root
        for byte in typed.utf8 {
            current = current?.children[Int(byte - 97)]
            var found: [String] = []
            if let node = current {
                collect(from: node, limit: limit, into: &found)
            }
            result.append(found)
        }
        return result
    }

    private static func collect(from node: Node, limit: Int, into found: inout [String]) {
        if found.count == limit { return }
        if let word = node.word {
            found.append(word)
        }
        for child in node.children {
            if found.count == limit { return }
            if let child {
                collect(from: child, limit: limit, into: &found)
            }
        }
    }
}
```

`current?.children[...]` uses optional chaining: once `current` is `nil`, it stays `nil`, and every later list is empty without any special case. A search engine would go one step further and store the best few suggestions at every node when the trie is built, making each keystroke O(1) at the cost of memory.

</Approach>
