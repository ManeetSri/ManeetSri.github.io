A shop runs a simulation that predicts the profit for any whole-number price, but each run takes minutes. The profit rises strictly to a single best price and then falls strictly. Find that best price using as few runs as you can.

`UnimodalArgmax.peak(in range: ClosedRange<Int>, profit: (Int) -> Int) -> Int`

Return the price in `range` with the highest profit. Only call `profit` with prices inside `range`. With n = `range.count` prices, you may call it at most `2 × (bit length of n) + 2` times, about 2 log₂ n: enough for binary search on the slope, but not for ternary search, which needs about 3.4 log₂ n.

## Examples

| `range` | `profit(p)` | Output | Why |
| --- | --- | --- | --- |
| `0...10_000` | `-(p - 6_180)²` | `6180` | the lesson's price curve |
| `1...5` | `[3, 8, 9, 4, 1]` at prices 1 to 5 | `3` | profit 9 at price 3 |
| `1...5` | `p` | `5` | still rising at the end of the range |
| `-8...2` | `-p` | `-8` | falling from the start |
| `7...7` | anything | `7` | one price, no calls needed |

## Constraints

- `1 ≤ range.count ≤ 2,000,000,000,000`, with bounds anywhere between −10¹² and 10¹².
- `profit` is strictly increasing up to the peak and strictly decreasing after it (either part can be empty), so no two neighbouring prices have equal profit.

<Hints>
<Hint>
Ternary search compares two points a third of the way in from each end and throws away a third of the range. It works, but each step costs 2 runs to discard only a third, so it needs too many runs here.
</Hint>
<Hint>
Compare `profit(mid)` with `profit(mid + 1)`. If the profit is still rising, the peak is to the right of mid; otherwise it's at mid or to its left. That discards **half** the range for the same 2 runs: the "peak element" binary search from [Peak element and mountain arrays](/dsa/learn/bs-peak-mountain), on a function instead of an array.
</Hint>
<Hint>
Use `while low < high` with `mid = low + (high - low) / 2`, so `mid + 1 ≤ high` is always a valid price. When the loop ends, `low` is the peak, and you never need to evaluate it again.
</Hint>
</Hints>

## Solutions

<Approach title="Ternary search" time="about 3.4 log₂ n evaluations" space="O(1)">

Each step evaluates the two points that split the range into thirds and keeps the two thirds that must contain the peak. Correct, but it uses about 70% more evaluations than the budget allows on large ranges.

```swift
public static func peak(in range: ClosedRange<Int>, profit: (Int) -> Int) -> Int {
    var low = range.lowerBound
    var high = range.upperBound
    while low < high {
        let third = (high - low) / 3
        let m1 = low + third
        let m2 = high - third
        if profit(m1) < profit(m2) {
            low = m1 + 1                                 // m1 is still on the way up
        } else {
            high = m2 - 1                                // m2 is already on the way down
        }
    }
    return low
}
```

</Approach>

<Approach title="Binary search on the slope" time="about 2 log₂ n evaluations" space="O(1)">

The sign of `profit(mid + 1) - profit(mid)` says which side of the peak mid is on, and it changes exactly once, at the peak. Searching for that change is an ordinary binary search, and it halves the range with every pair of evaluations.

```swift
public enum UnimodalArgmax {
    public static func peak(in range: ClosedRange<Int>, profit: (Int) -> Int) -> Int {
        var low = range.lowerBound
        var high = range.upperBound
        while low < high {
            let mid = low + (high - low) / 2             // mid < high, so mid + 1 is in range
            if profit(mid) < profit(mid + 1) {
                low = mid + 1                            // still rising: the peak is to the right
            } else {
                high = mid                               // falling: mid or something left of it
            }
        }
        return low
    }
}
```

For whole numbers, searching the slope beats ternary search every time. Ternary search (or its refinement, golden-section search) earns its place for functions of real numbers, where there's no "next price" to compare with.

</Approach>
